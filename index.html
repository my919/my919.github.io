企业经典架构图详解（进阶篇）：再十张高频实战图

发表于 2026-10-30 分类于 系统架构 本文字数： 5.7k 阅读时长 ≈ 5 分钟

企业经典架构图详解（进阶篇）

续 上篇：再十张高频架构图，覆盖分布式事务、缓存一致性、LLM 应用、IoT、IM 等进阶场景，全部 Mermaid 可直接复用。

1. CQRS 架构（命令查询职责分离）

适用：读写比例悬殊（>10:1）、查询模型与写入模型差异大（如订单写入是范式化表，查询是宽表+搜索）。关键设计点：读写模型各自演化、事件同步延迟必须可度量（监控 lag）、查询侧要容忍秒级不一致并在 UI 层做提示。反模式：没有读写分离痛点就强上 CQRS——一致性维护成本远超收益。

2. Saga 分布式事务（编排式 vs 编制式）

选型：步骤 ≤3 且参与方稳定的用编排式（无中心依赖）；步骤多、流程经常变、要可视化追踪的用编制式（状态机驱动，如 Seata Saga / Temporal）。关键设计点：每步必须可补偿（补偿不能依赖原操作成功）、状态持久化防编排器崩溃、超时兜底定时对账。详见 分布式事务实战。

3. 缓存一致性架构

关键设计点：更新采用”先写库、后删缓存”（Cache Aside）；主从延迟窗口用 binlog 订阅二次删除兜底；L1 通过消息广播失效；TTL 加随机抖动防雪崩。指标必看：缓存命中率、binlog 延迟、删除失败重试队列深度。详见 Redis 缓存架构实战。

4. 分库分表架构

关键设计点：分片键选择决定一切（按高频查询维度，如 user_id 取模）；全局唯一 ID 前置解决；跨片查询走广播表或 ES 冗余；扩容不停机靠”存量迁移 + binlog 增量追平 + 秒级切换”。反模式：单表没过 5000 万行就分片——先垂直拆分和索引优化。

5. LLM 应用架构（RAG + Agent）

关键设计点：网关统一计量成本与限流、大小模型路由（简单问题走小模型省成本）、检索质量靠”向量召回 + 重排序”双段式、输出必须经过护栏。详见 RAG 与向量检索实战、AI 网关实战。

6. IoT 物联网平台架构

关键设计点：边缘侧断网续传（本地缓存 + 恢复后补传）、设备影子解耦”设备实时状态”与”业务查询”、指令下发与数据上行通道分离、证书一机一密。详见 嵌入式与物联网协议系列。

7. IM 即时通讯架构

关键设计点：长连接网关与业务逻辑分离（网关无状态可水平扩）、消息 ID 全局有序（雪花 ID + 会话内序列号双保险）、消息”写扩散”到各端收件箱、离线消息拉取按 seq 增量同步、单聊写扩散/群聊读扩散按群规模切换。

8. 实时计算链路（CDC → 秒级大屏）

关键设计点：Exactly-Once 靠”Checkpoint + 两阶段提交 Sink”、状态后端用 RocksDB 并监控 state size、乱序容忍用 Watermark、维表 Join 走异步 IO + 缓存。详见 Flink 实时计算实战（如站内编号有变以 datascience 索引为准）。

9. API 开放平台架构

关键设计点：对外契约与内部实现解耦（内部重构不影响开放 API 版本）、签名防篡改 + 时间戳防重放、配额计量与计费一体、沙箱环境降低接入成本、密钥支持平滑轮换。详见 接口安全实战。

10. Serverless 架构

适用：流量波动剧烈（秒杀、活动页）、低频任务（对账、报表）、事件驱动处理（图片/视频转码）。关键设计点：冷启动延迟要实测（预留并发/预热）、函数保持无状态、单次执行有时限（长任务拆步骤或用 Step Functions 编排）、成本模型反直觉——稳定高并发时 FaaS 可能比常驻实例贵 3 倍，算账再选型。

企业经典架构图详解：从单体到云原生的十张图

发表于 2026-10-30 分类于 系统架构 本文字数： 4.8k 阅读时长 ≈ 4 分钟

企业经典架构图详解

架构图是技术团队的通用语言。本文收集企业系统中最经典的十张架构图——每张给出结构、适用场景与关键设计点，均可直接用 Mermaid 复用到你的设计文档中。

1. 架构图的四个视角

画图先确定视角——同一张图试图表达所有维度，结果就是谁也看不懂。

视角 回答的问题 受众
业务架构 系统支撑哪些业务能力 管理层、产品
应用/逻辑架构 系统分几层、几个模块、怎么交互 开发、架构师
数据架构 数据在哪存、怎么流动 DBA、数据团队
部署/物理架构 跑在什么机器、什么网络上 运维、SRE

推荐用 C4 模型控制粒度：System Context（系统在哪）→ Container（由哪些应用/存储组成）→ Component（应用内部结构）→ Code（类级，可选）。一张图只画一层。

2. 经典分层架构（单体时代基线）

适用：中小系统、业务早期。关键设计点：无状态应用层（Session 外置到 Redis）、数据库主从读写分离、静态资源走 CDN。瓶颈通常先出现在数据库，横向扩容只解决应用层。

3. 微服务架构（当前主流基线）

关键设计点：服务自治（每服务独立数据库）、治理下沉到注册配置中心、可观测三件套是必选项不是可选项。反面教材：微服务共享同一个数据库——拆了个寂寞。

4. 高并发交易链路（大促架构）

关键设计点：读路径多级缓存逐级兜底、写路径 MQ 削峰填谷、读写在存储层分离（binlog → ES/读库）、每一层都要有降级开关——缓存挂了限流直读，MQ 挂了同步降级。详见 高并发系统设计。

5. 事件驱动架构（最终一致性）

适用：跨服务业务流程（Saga）、读写分离同步、审计日志。关键设计点：消息至少一次投递 + 消费端幂等、死信队列必须有补偿流程、事件即事实（Event Sourcing 时再存事件本身）。详见 事件驱动架构实战指南。

6. 中台架构（阿里式，慎入）

适用：多条相似业务线、组织能力跟得上的中大厂。反面教材：业务线只有一两条就上中台——中台的成本是组织协作成本，不是技术成本。多数公司”中台”最后做成”又一层网关”。

7. 数据架构（湖仓一体）

关键设计点：流批同构（Iceberg 表既是批表也是流表）、一份数据多处消费（OLAP/实时/AI）、计算与存储分离弹性扩缩。详见 湖仓一体：Iceberg · Flink · Trino。

8. 云原生部署架构（K8s）

关键设计点：一切声明式（GitOps 为唯一变更入口）、HPA 按指标弹性伸缩、流量治理与安全下沉到 Mesh/Gateway API。详见 Kubernetes 实战指南。

9. 异地多活与容灾架构

关键设计点：单元化分片（用户按规则路由到固定单元，单元内闭环）、数据同步延迟是硬约束（同城 <10ms 可半同步，跨省只能异步+最终一致）、定期真实切换演练——不演练的容灾等于没有。RTO/RPO 指标要写进架构文档。

10. 零信任安全架构

原则：永不信任、始终验证——不再区分”内网可信/外网不可信”，每次访问都鉴权，最小权限 + 微分段。详见 零信任架构实战。

11. DevOps 交付流水线

关键设计点：质量左移（门禁在 MR 阶段拦截）、制品只构建一次逐级晋升、灰度按指标自动暂停/回滚。详见 CI/CD 实战指南。

12. 画好架构图的六条军规

  1. 一张图一个视角——别把逻辑模块和物理机器画在同一张图上
  2. 层次不超过三层——超过就拆图，用编号引用子图
  3. 箭头必须有语义——同步调用、异步消息、数据读写用不同线型，并在图例说明
  4. 标注关键约束——数据量级（QPS/存储量）、SLA、一致性要求，没有数字的架构图是装饰画
  5. 画出失败路径——降级开关、超时熔断、死信补偿，生产事故都发生在没画出来的路径上
  6. 图随代码走——架构图放仓库里（Mermaid/PlantUML 文本化），与代码同评审同演进

云真机私有化部署实战

数据不出内网、设备自己掌控——用 STF 把闲置手机变成公司级云真机平台。本文给出从单机验证到多节点生产集群的完整部署方案、iOS 扩展路线与运维要点。

1. 私有化方案现状（2026）

方案 状态 说明
STF (DeviceFarmer) 维护中，v3.8.0（2026-09） 开源私有化唯一活跃选择，Android 为主
Sonic 官方已停止维护 存量用户建议规划迁移到 STF；新项目勿入
商用私有化（WeTest 专有云、Testin 等） 在售 预算充足、要 iOS + 厂商支持时选型
自研（minicap/scrcpy + Appium） 可行 只需远程投屏操控时可轻量自研，见第 7 节

结论：私有化自建 = STF。本文以此为基线，Docker Compose 起步，逐层扩展到生产集群。

2. 架构与组件

单元 职责 扩展策略
stf-app Web 控制台 无状态，按并发用户横向扩
stf-api REST API（CI 占机/释放） 无状态，横向扩
stf-websocket 投屏视频流 按带宽扩，单节点千兆≈30 路 1080p
stf-provider USB 设备接入、minicap/minitouch 核心扩展单位：一台 Linux 带 10~15 台 Android
stf-processor 消息处理 按设备数扩，每百台 2~4 个
triproxy ZeroMQ 路由 一般 1 主 1 备即可
reaper 清理”僵尸设备”会话 单实例

3. 单机验证（30 分钟跑通）

验证清单：设备列表出现手机 → 点击能投屏操控 → adb connect 端口可连 → API 能占机。

4.3 硬件与布线（最容易踩的坑）

项 经验值
USB HUB 必须独立供电的工业级 Hub（如 16 口 90W 以上），总线供电带不动多机同时充电+投屏
散热 12 台手机叠放充电投屏，温度轻松上 45°C；机柜加风扇直吹，或间隔立式支架

4.4 认证与高可用

  • 认证：生产必须关掉 mock 登录。企业接 LDAP：--auth-type ldap --auth-options '["--ldap-url","ldap://ad.internal","--ldap-bind-dn","..."]'；或用 OAuth2/SAML 前置到 Nginx
  • HTTPS：Nginx 终结 TLS，WebSocket 记得 proxy_set_header Upgrade $http_upgrade;
  • RethinkDB：单节点够用但要做每日 rethinkdb dump 备份；状态丢了最多设备重新注册，不是致命数据
  • Provider 冗余：同区域部署 2 台 Provider，USB 故障时手机 5 分钟内换插重连

5. iOS 扩展路线

STF 官方不覆盖 iOS，私有化有三条路：

路线 原理 代价
WebDriverAgent + tidevice WDA 提供 :8100 HTTP 控制 + :9100 MJPEG 投屏，套一层自研 Web 前端 需要 Mac 机柜 + Apple 开发者签名（企业证书或 7 天重签自动化）
Appium 3 + XCUITest 直控 不做投屏，只做自动化占机调度 无实时画面，只能看截图日志
商用私有化补 iOS WeTest 专有云等混合部署 预算高，省心

实践经验：Android 私有化 + iOS 用商用公有云是多数团队的性价比最优解——iOS 自建的签名维护和 Mac 硬件折旧远超订阅费。

6. 与 CI 集成

调度建议：

  • 按标签分池：给设备打 tag（smoke/regression/低端机），CI 按标签占机，冒烟和全量不互相抢
  • 超时强制释放：CI 任务挂死时设备被占住不放，加看门狗——超过 2 小时无心跳自动调 API 释放并告警
  • 队列化：用例并发数 ≠ 设备数时，用消息队列排队，空闲设备主动拉取任务

7. 轻量替代：只要远程投屏

如果需求只是”让异地同事能看到并操作这台手机”，不需要完整 STF：

scrcpy + ws-scrcpy + Appium Grid 三件套能以 1/5 的复杂度覆盖 70% 场景（投屏、远控、自动化），代价是没有设备池管理、认证和占机排队——团队规模超过 10 人再切 STF。

手机云真机方案实战指南

云真机 = 把真实手机接入云端，浏览器里远程操控、跑自动化测试。本文盘点 2026 年仍稳定可用的方案：哪些商用平台值得用、自建怎么搭、哪些曾经流行的方案已经停更。

1. 为什么需要云真机

痛点 云真机的解法
Android 机型碎片化（品牌 × 系统版本 × 分辨率 × ROM） 上千台真机池，按机型筛选即点即用
买齐主流机型成本高、迭代快 按需租用，不用养设备柜

1. 具身智能浪潮与 ROS2 的定位

大模型把”智能”从纯文本扩展到视觉、语言与动作（Vision-Language-Action），机器人成为下一个主战场。具身智能（Embodied AI）要求算法真正驱动物理本体：感知、决策、控制、执行形成闭环。

在这条链路上，ROS2（Robot Operating System 2）扮演的是神经中枢角色：

  • 传感器、执行器、算法模块之间的标准化通信总线。
  • 坐标变换（TF2）、导航（Nav2）、机械臂规划（MoveIt2）等开箱即用的中间件。
  • 学术界与工业界的通用语言，绝大多数论文与开源项目都以 ROS2 接口发布。

一句话：大模型负责”想”，ROS2 负责”把想法变成电机的转速”。

2. ROS2 vs ROS1：为什么必须迁移

维度 ROS1 ROS2
通信机制 中心化 roscore（TCPROS） 去中心化 DDS（发布/订阅）
实时性 无保证 支持 QoS、实时调度
跨平台 主要 Ubuntu Linux / Windows / macOS / RTOS
多机通信 需手工配置 master 天然支持，自动发现
生命周期管理 无 Managed Nodes
安全性 无 SROS2（加密、鉴权）

DDS（Data Distribution Service）是工业级实时发布订阅标准。ROS2 把节点间通信抽象为 DDS topic，通过 QoS 策略（可靠性、持久性、历史深度）适配不同场景：激光雷达用 best_effort，指令下发用 reliable。

3. 核心概念

3.1 节点（Node）

最小执行单元，一个进程可跑多个节点。按职责拆分：相机驱动节点、目标检测节点、路径规划节点。

3.2 话题（Topic）

异步流式数据通道，发布/订阅模式。适合传感器数据、状态广播。

3.3 服务（Service）

同步请求/响应，适合一次性查询或配置：如”重置里程计”。

3.4 动作（Action）

长任务协议：目标（goal）+ 持续反馈（feedback）+ 最终结果（result），支持取消。导航到目标点就是典型 Action。

13. 常见坑 FAQ

Q1：ros2 topic list 看不到对端节点？
A：多为 DDS 发现问题。检查 ROS_DOMAIN_ID 是否一致；跨机器关闭防火墙或配置多播；不同网卡时设置 CYCLONEDDS_URI 绑定接口。

Q2：消息延迟大、抖动明显？
A：检查 QoS 是否匹配——发布端 reliable、订阅端 best_effort 会静默不连；大图像消息考虑零拷贝（loan message）或压缩传输。

Q3：colcon build 内存不够被 kill？
A：colcon build --parallel-workers 2 --executor sequential，或加 swap；大型包（如 Gazebo）单独编译。

Q4：TF 报 “Lookup would require extrapolation into the future”？
A：时间同步问题。多机部署开 chrony/NTP 对时；bag 回放加 --clock 且节点 use_sim_time:=true。

Q5：Nav2 机器人在原地打转？
A：90% 是 TF 树断（map→odom→base_link 缺失）或代价地图传感器坐标系填错。用 view_frames 检查。

Q6：真机部署与仿真行为不一致？
A：ros2_control 的 hardware interface 没写对；检查控制器频率、关节限位与 PID 是否和 URDF 一致。

第一章：CRDT 与 Yjs：实时协同编辑的原理与实战

发表于 2026-10-28 更新于 2026-10-29 分类于 实时通信 本文字数： 8.5k 阅读时长 ≈ 8 分钟

第一章：CRDT 与 Yjs：实时协同编辑的原理与实战

从并发冲突的本质出发，讲清 CRDT 的原理、Yjs 的数据结构与工程落地，并给出与主流编辑器集成的完整示例。

1. 协同编辑问题的本质

多人同时编辑同一份文档时，最棘手的问题是并发冲突：两个用户在不知道对方操作的情况下，同时修改了同一段内容。系统必须保证：

  • 收敛（Convergence）：所有副本最终一致。
  • 意图保留（Intention Preservation）：尽量保留每个用户的编辑意图。
  • 无中心协调：不能依赖全局锁，否则延迟与可用性都会崩塌。

经典的失败场景是”最后写入获胜”（LWW）直接覆盖文本：A 在开头插入”Hello”，B 在结尾插入”World”，如果只用字符位置索引，B 的插入位置在 A 的操作之后已经偏移，直接套用就会插错位置，产生”错位合并”。

2. OT vs CRDT

2.1 OT（Operational Transformation）

Google Docs 早期使用的方案。核心是操作变换：当收到一个基于旧版本的操作时，服务器把它”变换”成基于当前版本的操作。

  • 优点：算法成熟、文档模型可以是纯文本。
  • 缺点：变换函数的正确性证明极其复杂（已有多个著名实现被证明有反例）；需要中心服务器做”单一事实源”，离线合并困难。

2.2 CRDT（Conflict-free Replicated Data Type）

CRDT 通过数学上保证可交换、可结合、幂等的数据结构，让任意顺序合并都得到相同结果，无需中心协调。

维度 OT CRDT
一致性保证 依赖变换函数正确性 数学证明收敛
中心服务器 必需（变换中枢） 可选（P2P 可行）
离线支持 弱 天然支持
元数据开销 小 有（唯一 ID、tombstone）
实现复杂度 极高 中等

3. CRDT 的两种范式

3.1 基于状态（State-based / CvRDT）

副本之间交换完整状态，通过 merge(a, b) 函数合并。要求 merge 满足交换律、结合律、幂等律。典型例子：G-Counter（只增计数器，各节点各自累加自己的分量，取 max 合并）。

3.2 基于操作（Op-based / CmRDT）

副本之间广播操作，要求因果序交付。操作本身被设计成可交换的。典型例子：G-Set（只增集合）。

Yjs 属于两者的混合：对外表现为基于操作的更新传播，内部用状态向量（state vector）做增量同步与缺失补全，兼具两者优点。

4. Yjs 核心数据结构

Yjs 把文档抽象为 Y.Doc，内部是若干共享类型，所有共享类型都是 CRDT。

4.1 YArray

有序列表，支持插入、删除、按索引读取。元素可以是任意 JSON 值或另一个共享类型。

4.2 YMap

键值结构，并发写同一个 key 时按 clientID 决出胜者（确定性），不同 key 全部保留。

4.3 YText

富文本结构，是编辑器集成的主力。支持带格式的插入与删除（formatting attributes），底层是 YATA 算法的字符序列。

9. 性能与内存

  • tombstone（墓碑）：删除的字符不会物理移除，只做标记。超长文档反复编辑后墓碑占比可能超过 80%。
  • GC：Yjs 在 gc: true（默认）下会回收不再被引用的项；Y.Doc({ gc: true })。快照（snapshot）存在时会阻止 GC。
  • 结构化压缩：Yjs 内部把同 clientID 的连续操作合并为 Item 块，减少内存占用。
  • 二进制 update 编码：update 是紧凑的 varint 编码，比 JSON 小一个数量级。
  • 大文档初始化：首屏建议走 HTTP 拉全量 state，再切 WebSocket 做增量，避免握手消息过大。

11. 常见坑 FAQ

Q1：两个用户同时创建同名 YMap key，值会怎样？
A：确定性收敛到 clientID 较大的那次写入，所有副本结果一致，但业务上应尽量避免竞写同一 key。

Q2：撤销/重做为什么乱了？
A：混用了编辑器自带 history 与 yUndoPlugin。只能留一套，且 UndoManager 要加 trackedOrigins 过滤远端操作。

Q3：文档越用越慢，内存暴涨？
A：检查 tombstone 比例，考虑定期用快照重建文档（Y.createDocFromSnapshot）；排查 awareness 状态泄漏。

Q4：服务端重启后文档丢失？
A：y-websocket 默认内存存储，必须接入 y-leveldb 或 Hocuspocus 的持久化扩展。

Q5：如何做权限控制？
A：CRDT 本身不解决权限。在连接握手时校验 token，写操作在服务端钩子中按文档/字段级鉴权。

Q6：能不能跨语言？
A：可以。yrs（Rust 实现）与 Yjs 二进制兼容，Ruby/Go/Python 都有基于 yrs 的绑定。

1. 威胁模型：为什么要现在行动

1.1 Shor 算法与经典密码的死刑判决

1994 年 Peter Shor 证明：足够大的量子计算机可以在多项式时间内分解大整数、求解离散对数。这意味着：

  • RSA（所有密钥长度）：基于大整数分解，全部被破；
  • ECC（ECDH/ECDSA/Ed25519）：基于椭圆曲线离散对数，全部被破；
  • DH/DSA：基于有限域离散对数，全部被破。

唯一幸存的是对称密码与哈希：Grover 算法仅带来平方根级加速，AES-128 变 64 位有效强度不够看，但 AES-256、SHA-256/384 依然是后量子安全的——把密钥和输出加长即可。

1.2 「先存后解」（Harvest Now, Decrypt Later）

这是推动迁移的最现实威胁：攻击者今天就录制你的 TLS 流量、归档你的加密数据，等 10-15 年后量子计算机成熟再解密。

1.3 时间线感知

  • 2016：NIST 启动 PQC 标准化征集；
  • 2022：NIST 公布首批入选算法（CRYSTALS-Kyber/Dilithium 等）；
  • 2024 年 8 月：FIPS 203/204/205 正式发布，标准落地；
  • 2024-2025：Chrome、Cloudflare、Apple iMessage（PQ3）等大规模部署混合密钥交换；
  • 业界估计：2030-2035 年出现密码学相关量子计算机（CRQC）的概率不可忽略。

2. NIST 标准：三件套

标准 算法 用途 数学基础
FIPS 203 ML-KEM（源自 CRYSTALS-Kyber） 密钥封装（替代 ECDH） 模格上 Module-LWE
FIPS 204 ML-DSA（源自 CRYSTALS-Dilithium） 数字签名（替代 RSA/ECDSA 主选） 模格
FIPS 205 SLH-DSA（源自 SPHINCS+） 数字签名（保守备选） 纯哈希，无格假设

另有一个 FALCON（FIPS 206 制定中）用于签名尺寸敏感场景。

2.1 ML-KEM 参数集

参数集 对标经典强度 公钥 私钥 密文 共享密钥
ML-KEM-512 AES-128 800 B 1632 B 768 B 32 B
ML-KEM-768 AES-192（推荐默认） 1184 B 2400 B 1088 B 32 B
ML-KEM-1024 AES-256 1568 B 3168 B 1568 B 32 B

对比 X25519：公钥 32 字节、密文 32 字节——ML-KEM 的字节数大约 40 倍，这是迁移中最直观的工程成本。

2.2 选型建议

  • 密钥交换：ML-KEM-768 是行业共识默认（IETF TLS、Chrome、Cloudflare 均采用）；
  • 签名：优先 ML-DSA；合规保守场景（ Firmware 签名，一签管十年）可考虑 SLH-DSA——它只依赖哈希函数安全性，但签名约 8-40 KB、速度慢一个数量级；
  • 避开非主流算法的自研组合，只跟 NIST 标准和 IETF RFC 走。

5. 证书与 PKI 迁移难点

密钥交换可以「混合」无痛上线，证书链是真正的硬骨头。

5.1 五个现实难题

  1. 证书尺寸膨胀：ML-DSA-65 公钥约 1.9 KB、签名约 3.3 KB，一条三级证书链从 ~4 KB 涨到 ~15 KB，触发 TLS 分片、MTU 问题，部分老旧中间件直接拒收；
  2. HSM 不支持：多数现网 HSM 固件尚无 PQC 算法，密钥保护体系要整体换代，周期长、费用高；
  3. CA 生态未就绪：公共 CA 的 PQC 根证书与浏览器信任计划仍在试点（ISRG、DigiCert 已有测试目录），企业内 CA 需先行自建（可结合第二章本地 CA 流程，把签名算法换成 ML-DSA）；
  4. 协议协商缺失：TLS 的 signature_algorithms 扩展对 PQC 的支持在各 TLS 栈中落地不一，混合证书（一张证书两种签名）的 RFC 仍在草案阶段；
  5. 嵌入式/IoT：固件验签若换 SLH-DSA，验签耗时与存储占用都需实测，部分 MCU 直接放不下。

5.2 务实策略

  • 密钥交换先行：它不需要证书体系配合，先把混合 ECDHE 打开，立刻消除「先存后解」风险——这是性价比最高的一步；
  • 证书分步走：根/中间 CA 签名寿命长、签发量小，可以晚迁（它们被破解影响的是伪造，不是解密存量数据）；但长寿命设备的固件签名要早规划；
  • 内网 mTLS（呼应第九章零信任）可以先于公网 PKI 完成 PQC 化——你自己控制两端，不必等浏览器和公共 CA。

常见坑 FAQ

Q1：量子计算机不是还很远吗，急什么？
「先存后解」让风险前置：今天被录走的流量，保密期覆盖到 CRQC 时代的部分已经实质泄露。且迁移本身要 3-5 年，等你看到量子机新闻再动就晚了。

Q2：ML-KEM 会不会像某些候选算法一样被攻破？
NIST 流程经过 6 年多轮全球公开评审，ML-KEM（Kyber）安全性有充分分析；且混合模式保证了「即使格被攻破，仍有 X25519 兜底」。这正是行业标准要求混合的原因。

Q3：握手包变大把老客户端打挂怎么办？
混合组是协商制：不支持的客户端自然回退 X25519/P-256。真正要测的是中间件（旧 TLS inspector、防火墙）对大包 ClientHello 的容忍度——灰度+遥测，不要一把梭。

Q4：国密合规场景怎么选？
国内路线是 SM2/SM3/SM4 体系，后量子方向由中国密码学会与相关标准组织推进，与国际 ML-KEM 体系并行。跨国业务建议架构上做到「算法可插拔」，区域化配置不同的合规算法套件。

Q5：固件签名用 ML-DSA 还是 SLH-DSA？
固件签名寿命极长（设备可能 10 年不更新根信任），且验签失败影响远小于签名被伪造，保守选 SLH-DSA（只依赖哈希安全性）；若验签性能或尺寸受限，选 ML-DSA-87 并保留远程换根能力。

Q6：怎么验证我的站点已经支持混合握手？
openssl s_client -groups X25519MLKEM768 看协商组；或用 Cloudflare 的检测页、SSL Labs（已标注 PQ 支持）。

落地清单

  • 完成 CBOM 密码学资产盘点，标注长保密期数据
  • 基础组件升级：OpenSSL ≥ 3.5 / 最新 TLS 栈
  • 对外 TLS 开启 X25519MLKEM768 混合组并灰度
  • 内部 mTLS 网格同步启用混合密钥交换
  • 中间件/防火墙大包 ClientHello 兼容性测试通过
  • 内网 CA 具备 ML-DSA 签发能力
  • 代码/制品签名 PQC 迁移方案评审
  • HSM/KMS PQC 支持写入采购需求
  • 静态数据与备份的 PQC 再加密计划排期
  • 建立算法协商能力（crypto agility），杜绝硬编码

1. 核心理念：三个「不」

零信任（Zero Trust）不是某个产品，而是一套架构哲学，由 NIST SP 800-207 正式定义。核心三条：

  1. 永不信任，始终验证（Never trust, always verify）：网络位置不产生任何信任。内网 IP、VPN 隧道、办公网段——统统不算信任凭证；
  2. 最小权限（Least privilege）：每次访问只授予完成当前动作所需的最小权限，且尽量短时（just-in-time）；
  3. 假设已被攻破（Assume breach）：按「攻击者已在内网」设计防御，重点是限制横向移动与爆炸半径。

1.1 与边界安全模型的对比

维度 传统边界模型 零信任模型
信任基础 网络位置（内网=可信） 身份 + 设备 + 上下文，逐次验证
访问粒度 网段/VLAN 级 单个应用、单个 API 调用级
凭证寿命 VPN 一连一整天 短时凭证，分钟级过期
横向移动 进内网后基本畅通 每次跨服务调用都需授权
失效场景 VPN 账号泄露=全线失守 单一凭证泄露影响面受限
可见性 边界日志为主 全链路请求级审计

一句话：边界模型是城堡与护城河，零信任是每扇门都要刷卡的写字楼。

2. 身份是地基：SPIFFE/SPIRE 工作负载身份

人的身份有 OIDC/SAML 成熟方案，工作负载（服务、Pod、批任务）的身份却长期靠 API Key、静态密码硬撑——这正是零信任最难补的课。

2.1 SPIFFE：统一身份格式

SPIFFE（Secure Production Identity Framework for Everyone） 定义了工作负载身份标准：

  • 身份是 URI，包含信任域、命名空间、服务账号；
  • 凭证形态是 SVID：X.509 证书（X.509-SVID）或 JWT（JWT-SVID）；
  • 关键特性：短时（默认 1 小时）、自动轮换、无需硬编码密钥。

2.2 SPIRE：身份签发引擎

SPIRE 是 SPIFFE 的参考实现，架构分两层的：

  • SPIRE Server：信任根，负责注册条目（Registration Entry）管理与 SVID 签发；
  • SPIRE Agent：每个节点一个，通过 Node Attestation（云厂商 IAM、k8s PSAT、join token）向 Server 自证节点身份，再通过 Workload Attestation（校验 PID、容器 label、k8s service account）向工作负载颁发 SVID。

6.2 可借鉴的设计决策

  1. 所有应用 Web 化或代理化：不暴露直连端口，一切访问过 Access Proxy；
  2. 信任分层（Trust Tier）：设备按状态分为「完全受管 / 部分受管 / 不受信」，应用按敏感度分级，矩阵决定放行；
  3. 证书即设备身份：设备证书自动签发轮换，比 MAC 地址、IP 白名单可靠得多；
  4. 渐进推行：用多年时间按应用逐个迁移，保留回退通道，不搞大爆炸切换。

7. 分阶段迁移路线图

零信任没有「一键开启」，推荐按四阶段推进，每阶段独立交付价值。

阶段一：身份地基（1-3 个月）

  • 统一 IdP，全员 SSO + 强制 MFA（优先 FIDO2/硬件密钥）；
  • 盘点应用清单，标记敏感度分级；
  • 工作负载侧：选定 SPIFFE/SPIRE 或服务网格身份，先在 1 个核心域试点 mTLS。

阶段二：设备与入口（3-6 个月）

  • MDM 全量纳管，设备证书下发；
  • 部署应用代理（Access Proxy / ZTNA），高敏应用第一批切流，关 VPN 权限做对照组；
  • OPA 策略框架上线，先 audit 模式记录「假设执行会拦什么」。

阶段三：服务间默认加密（6-12 个月）

  • 服务网格 mTLS 从 PERMISSIVE 切 STRICT，覆盖核心生产命名空间；
  • 东西向流量按服务身份做授权策略（AuthorizationPolicy）；
  • 网络层做微分段兜底，默认拒绝。

阶段四：持续验证与自动化（12 个月+）

  • 会话级持续评估：设备/用户风险信号变化实时吊销会话；
  • SIEM 联动：异常行为自动触发降权或重认证；
  • 权限定期自动回收（access review 自动化），JIT 提权常态化。

常见坑 FAQ

Q1：零信任是不是必须上服务网格？
不是。服务网格解决「工作负载间 mTLS」这一段；人用 ZTNA 网关，设备用 MDM——三者可独立推进。小团队先用 Cloudflare Access 这类 SaaS 把「人访问应用」做掉，收益最快。

Q2：mTLS 全开后性能损失大吗？
TLS 1.3 + AES-GCM 硬件加速下，同机房延迟增加通常 <1ms；真正的成本在运维心智：证书轮换、身份注册、调试排障（加密后传统抓包失效，要靠网格自带遥测）。

Q3：OPA 策略会不会成为单点？
决策点要做高可用，且设计fail-open 还是 fail-close 要分场景：支付链路 fail-close，内部工具可 fail-open + 告警，避免 OPA 故障引发全站雪崩。

Q4：VPN 可以直接退休吗？
可以但分步：先把 Web 应用切到 ZTNA，再处理 SSH/数据库类协议（用 Access 的 TCP 代理或 Teleport 这类现代方案），最后关停 VPN。多数企业 6-18 个月完成。

Q5：证书这么多，吊销来得及吗？
零信任的思路是用短寿命替代吊销：SVID 1 小时、用户 token 15 分钟，攻击者拿到也快过期了。OCSP/CRL 留给设备证书这类长寿命凭证。

Q6：遗留系统改不动怎么办？
给它前面架代理（sidecar 或反向代理），由代理持有身份做 mTLS，遗留系统只监听 localhost——「身份外挂」是兼容存量的标准姿势。

落地清单

  • 全员 SSO + 强制 MFA，淘汰共享账号与静态密码
  • 应用敏感度分级清单完成并评审
  • SPIRE 或服务网格身份在至少一个核心域上线 mTLS
  • MDM 纳管率 >95%，设备证书全覆盖
  • 高敏应用经 ZTNA/Access Proxy 访问，VPN 权限回收对应人群
  • OPA 策略集中管理，关键策略有单元测试
  • mTLS 从 PERMISSIVE 切 STRICT 的命名空间清单与时间表
  • 风险信号（EDR/MDM/行为）联动会话吊销的自动化规则上线
