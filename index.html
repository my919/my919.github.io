感知机 · 多层感知机(MLP) · 反向传播 · 梯度下降变体(SGD/Momentum/Adam) · 集成学习。原理 + PyTorch CPU 落地代码（含详细注释）+ 应用。

1. 感知机（Perceptron）

1.1 原理

最简神经网络：输入加权求和，过阶跃/符号函数输出：

  • 权重 w 决定每个特征的”重要程度”
  • 训练算法：预测错了才更新，一次只纠正一个样本

1.3 应用

应用 说明
线性分类 简单二分类
神经网络启蒙 理解权重与更新
逻辑门模拟 AND/OR 门

局限：无法解决异或（XOR）等线性不可分问题——这催生了多层网络（MLP）。

2. 多层感知机（MLP）

2.1 原理

在输入和输出之间加隐藏层 + 非线性激活函数，就能拟合任意非线性函数：

  • 激活函数（非线性关键）：ReLU=max(0,x)、sigmoid、tanh
  • 训练算法：反向传播（Backpropagation）——从输出层向前逐层计算梯度，用链式法则更新每层权重

换成线性模型（去掉隐藏层）准确率会明显下降——这就是”深度”的意义。

2.3 应用

应用 说明
非线性分类/回归 表格数据的万能拟合器
图像分类（CNN 前身） 像素 → 类别
推荐系统 特征交互建模
一切深度模型基座 CNN/RNN/Transformer 都含 MLP 块

3.1 原理（链式法则）

以两层网络为例，损失对第一层权重的梯度要穿过第二层：

每层只需要”本地梯度 × 上游梯度”，从后往前逐层相乘。

4. 梯度下降变体（SGD / Momentum / Adam）

4.1 原理

优化器 更新规则（直觉） 特点
SGD w ← w - lr·g 简单，可能震荡
Momentum 带”惯性”：累加历史梯度方向 加速收敛、减少震荡
Adam 自适应每参数学习率 + 动量 默认首选，收敛快且稳

g 是梯度；Adam 为每个参数动态调整步长，几乎不用调 lr。

4.3 应用

SGD+Momentum 需要更好泛化的大模型微调
SGD 教学、极小网络
AdamW Transformer 类模型首选（带权重衰减修正）

5. 集成学习（Ensemble）

5.1 原理

多个弱模型一起决策，比单个强模型更稳：

方法 思想 典型
Bagging 并行训练多个模型（不同子样本），投票/平均 随机森林
Boosting 串行训练，后一个纠正前一个的错误 AdaBoost、GBDT
Stacking 多个模型输出再喂给一个元模型 竞赛常用

提升准确率 弱学习器组合
生产稳健性 多模型投票抗噪

4. 朴素贝叶斯（Naive Bayes）

4.1 原理

基于贝叶斯定理 + 特征独立假设：

  • P(类别)：先验（各类占比）
  • P(特征i|类别)：似然（该类别下某特征出现的概率）
  • 预测：取后验概率最大的类别

训练算法：从数据统计出先验和似然（连续特征假设高斯分布：算每类的均值、方差），无需梯度下降。

访问者模式详解（Visitor）

发表于 2026-09-14 本文字数： 1.2k 阅读时长 ≈ 4 分钟

设计模式 · 访问者模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 双分派。代码带详细注释。

1. 模式概述（意图）

访问者模式（Visitor）把数据结构与数据上的操作分离：在不修改元素类的前提下，为元素类增加新的操作（访问者）。

2. 要解决的问题

问题 说明
元素类频繁加操作 每个元素加”导出/统计/序列化”方法 → 类爆炸
操作变化快 操作经常变，元素结构稳定
结构固定 对象结构（元素类型）稳定，操作易变

典型场景：编译器（AST 节点 × 各种操作）、文档导出（不同节点×不同导出格式）、报表统计、对象结构稳定但操作繁多的系统。

适用前提：元素类型稳定（很少新增元素），操作经常变——反之（元素常加）则不要用访问者。

3. 结构（角色）

双分派：element.accept(v) 先按元素类型分派，visitor.visit(element) 再按访问者类型分派——两次动态绑定，才能”元素类型 × 操作”自由组合。

4. 代码实现（报表导出）

核心收益：加”新操作”= 加一个 Visitor 类；元素类（SaleRecord/RefundRecord）一行不改。

5. 应用场景

场景 说明
编译器 AST 节点 × 解析/检查/生成
报表导出 多类型节点 × 多格式导出
对象结构稳定 数据结构固定、操作易变
统计/审计 对对象结构做多种统计

6. 优缺点

优点 缺点
操作与结构分离（开闭） 违反依赖倒置（元素依赖访问者接口）
加操作易（加访问者） 加元素类型难（所有访问者都要改）
相关操作内聚在一个类 破坏封装（访问者需访问元素内部）
双分派机制强大 复杂度高，简单场景不值

7. 与其他模式对比

模式 区别
迭代器 迭代器遍历；访问者遍历中对每个节点执行操作
组合模式 常配合：组合树 + 访问者遍历操作
策略 策略换算法（单对象）；访问者作用于对象结构

模板方法模式详解（Template Method）

设计模式 · 模板方法

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与策略对比。代码带详细注释。

1. 模式概述（意图）

模板方法模式（Template Method）把算法的骨架定义在父类，把可变的步骤延迟到子类实现——父类控制流程，子类填充细节。

2. 要解决的问题

问题 说明
流程相同、细节不同 支付流程一样，各家签名/调用不同
流程被复制粘贴 每个子类都写一遍骨架（改流程要改多处）
骨架需要强制一致 子类可能打乱步骤顺序

典型场景：Spring 的 JdbcTemplate/RestTemplate、Servlet（doGet/doPost 由框架调）、流程引擎、游戏关卡、测试框架（JUnit 的生命周期）。

3. 结构（角色）

钩子方法（Hook）：父类提供默认实现、子类可选覆写的扩展点（如”是否需要做某步”）。

4. 代码实现（数据导出）

流程控制点：取数 → 格式化 → 写文件 的顺序由父类锁定，子类只换”格式化”这一步。

5. 应用场景

场景 说明
框架回调 Servlet、Spring 模板类
支付/对接 流程相同、签名/报文不同
批量任务 拉数→处理→落库→通知
测试框架 JUnit 生命周期（@Before/@Test/@After）
工作流 固定流程+可变步骤

6. 优缺点

优点 缺点
复用骨架，消除重复 父类与子类耦合（继承）
流程统一（final 防乱序） 骨架改动影响所有子类
扩展靠子类（开闭） 抽象步骤多时子类实现负担
钩子提供灵活扩展点 无法运行时换实现（继承静态）

7. 与策略对比（高频考点）

维度 模板方法 策略
关系 继承（子类填充） 组合（注入策略）
变的部分 步骤实现 整个算法
切换 编译期固定 运行时切换
适用 骨架固定 算法整体可换

实践建议：优先组合优于继承——如果只是”某一步可变”，用回调/函数式接口（如 JdbcTemplate 的 RowMapper）常比继承更灵活。
