第五章：OpenSSL 非对称加密与密钥交换：RSA、Ed25519、X25519

发表于 2026-05-01 更新于 2026-10-29 分类于 安全 本文字数： 5.3k 阅读时长 ≈ 5 分钟

第五章：OpenSSL 非对称加密与密钥交换：RSA、Ed25519、X25519

概念基础

  1. 非对称加密：公钥 / 私钥成对，公钥公开分发、私钥绝对保密——解决了对称加密「密钥如何安全送达」的死结（对称加密见第四章）。
  2. 三大用途：数字签名（私钥签、公钥验，见第六章）、密钥交换（ECDHE/X25519 在不安全信道协商会话密钥）、小数据加密（RSA-OAEP 加密对称密钥）。
  3. 为什么 TLS 用混合方案：非对称慢（比对称慢几个数量级），只用于握手阶段；海量数据用协商出的对称会话密钥（AES-GCM）加密。
  4. 前向保密（PFS）：握手使用临时密钥对（X25519 / ECDHE），即使服务器长期私钥日后泄露，历史会话也解不开——静态 RSA 密钥传输因此被淘汰。
  5. 选型一句话：签名与证书新系统优先 Ed25519 / ECDSA P-256，密钥交换用 X25519，RSA 2048+ 仍是最普遍的兼容选择。

推荐选型（2020s）

用途 推荐 避免 / legacy
TLS 证书 / 代码签名 ECDSA P-256、Ed25519；RSA 仍普遍 RSA < 2048 bit
TLS 密钥交换 X25519（ECDHE） 静态 RSA 密钥传输、DHE 1024 bit
SSH / 现代签名 Ed25519 DSA
小数据 RSA 加密 RSA-OAEP 2048+（仅短载荷） PKCS#1 v1.5 加密、裸 RSA
长期根 CA RSA 4096 或 EC P-384 RSA 1024

一、RSA

特点

  • 基于大整数分解困难性。
  • 加密：只适合很短数据（密钥长度限制）；长数据用 混合加密（RSA 包 AES 密钥）。
  • 签名 / 证书：仍大量存在；新站点可优先 EC/Ed25519。

二、椭圆曲线 EC / ECDSA

特点

  • 更短密钥达到相当安全强度（P-256 ≈ RSA-3072 量级）。
  • ECDSA：签名与证书（secp256r1 / prime256v1 最常用）。
  • ECDH：密钥交换（TLS 中 ECDHE）。

曲线选择速查

曲线 强度 建议
secp256r1 / prime256v1 / P-256 ≈128 bit TLS 证书默认选择，浏览器全兼容
secp384r1 / P-384 ≈192 bit 长寿命 CA、高合规场景
secp256k1 ≈128 bit 区块链常用，TLS 生态支持差，新系统不建议
Curve25519 系 ≈128 bit Ed25519/X25519 的底层曲线，见下节

三、Ed25519 / X25519（现代首选）

算法 类型 用途
Ed25519 签名 SSH、代码签名、部分 TLS 证书
X25519 密钥交换 TLS 1.3 (EC)DHE 主流

Ed25519 为何是现代首选

  • 快：签名与验签速度数倍于 ECDSA P-256。
  • 确定性签名：不依赖随机数（RFC 8032），消除了 ECDSA 「nonce 复用即私钥泄露」的经典事故。
  • 短：公钥 32 字节、签名 64 字节，证书与 JWT 体积显著变小。

四、国密 SM2（合规场景）

SM2（GM/T 0003）是基于椭圆曲线的国密非对称算法，安全强度对标 ECDSA P-256，一套算法同时覆盖签名、加密、密钥交换三种用途（EC 体系里这三者分别是 ECDSA / ECIES / ECDH 三个算法）。OpenSSL 3.5 LTS 已内置 SM2：

适用边界：等保、金融、政务等明确要求国密的场景启用 SM2/SM3/SM4 全家桶；国密 TLS（TLCP）需要 Tongsuo 等专用实现，OpenSSL 主线只提供算法原语。

五、证书字段与扩展速读（x509）

证书本质是一张「公钥 + 身份信息 + CA 签名」的结构化文件，排障时先看懂关键字段：

字段 含义 关注点
Subject / Issuer 持有者 / 签发者 链式对应，根 CA 自签
Validity 有效期 Not After 过期即失效
Subject Public Key Info 公钥与算法 RSA-2048 / ECDSA P-256 / Ed25519
Subject Alternative Name 绑定的域名/IP 现代浏览器只看 SAN，CN 已废弃
Key Usage / Extended KU 用途限制 服务器证书需 digitalSignature + serverAuth
Basic Constraints 是否 CA CA:FALSE 是叶子；CA:TRUE 才可签发
Authority Key Identifier 指向签发者公钥 构建证书链的路标

证书链验证过程（浏览器/OpenSSL 内部逻辑）：

  1. 从叶子证书出发，按 Issuer → AKI 找到上级 CA 证书，直到受信根 CA；
  2. 自底向上逐级用上级公钥验证下级签名；
  3. 检查每一级 Basic Constraints（路径长度）、有效期、吊销状态（CRL/OCSP）；
  4. 最后核对 SAN 是否覆盖访问的域名/IP。

握手时用 X25519 / secp256r1 协商临时对称密钥（前向保密 PFS），而非用 RSA 直接加密预主密钥。

七、查看、对比与性能基准

参考量级（OpenSSL 3.5 LTS，常见服务器 CPU）：

算法 签名/s 验签/s 公钥大小 备注
RSA-2048 ~1k ~50k 256 B 验签极快，签名慢
ECDSA P-256 ~20k ~8k 64 B 均衡
Ed25519 ~20k ~15k 32 B 最快且最短
RSA-4096 ~150 ~15k 512 B 仅用于根 CA 等长寿命场景

结论：高并发 TLS 终结点优先 ECDSA/Ed25519 证书——RSA 证书的签名开销在大量短连接场景会成为 CPU 瓶颈。

八、后量子展望：ML-KEM

Shor 算法对 RSA 与全部椭圆曲线方案构成理论威胁；NIST 已于 2024 年发布后量子标准：

标准 定位 OpenSSL 3.5 状态
ML-KEM（FIPS 203，原 Kyber） 后量子密钥交换 已内置（openssl list -kem-algorithms 可见）
ML-DSA（FIPS 204，原 Dilithium） 后量子签名 已内置
SLH-DSA（FIPS 205） 哈希签名备份方案 已内置

行业主流过渡方案是混合模式（X25519 + ML-KEM-768，Chrome/Cloudflare 已大规模灰度）：即使其一被攻破，另一重仍然安全。当前生产建议：关注但不必急于启用——先确认自己的私钥管理、证书自动化流程足够健壮，后量子迁移才有地基。
