第一章：OpenSSL 命令行入门与常用操作总览

概念基础

  1. OpenSSL 是一个开源密码学工具包：对外提供 openssl 命令行工具（生成密钥、证书、加解密、签名），对内提供底层密码库（libcrypto / libssl），是 TLS/HTTPS 生态的事实标准。
  2. 它解决三类安全问题：保密性（对称 / 非对称加密）、完整性（哈希 / HMAC）、身份认证（数字证书 + CA 信任链）；HTTPS 正是三者的组合应用。
  3. 四个核心对象：私钥（.key / .pem，必须保密，用于解密、签名）；公钥（从私钥导出，公开分发，用于加密、验签）；证书（.crt / .pem，包含公钥 + 身份信息 + 签名，证明公钥合法）；CSR（证书签名请求，.csr，向 CA 机构申请正式证书的文件）。
  4. 为什么重要：Nginx、curl、Python、Java、手机系统等几乎所有软件的加密通信都依赖它——掌握 OpenSSL 命令行，等于掌握证书、加密、签名的通用钥匙。
  5. 本章定位：侧重命令行实操，给出从摘要、密钥到证书签发、格式转换的完整工作流；各算法的原理与选型详见后续章节。

OpenSSL 是生成、管理非对称密钥和数字证书的标准工具，广泛用于 第四章：HTTPS 详解：TLS 握手、证书与 openssl/curl 示例、SSL/TLS、身份认证等。能力概览见 第二章：OpenSSL 功能全景与自建局域网 CA 实战；算法分类与推荐用法见下表。

摘要与编码（不依赖证书）

1. 文件摘要（MD5、SHA-256）

对任意文件计算密码学摘要，常用于校验下载包、比对文件是否一致。

其他算法同理，例如 -sha512、-sha1（SHA-1 已不推荐用于安全场景）。

2. 字符串 / 管道内容哈希

把待哈希内容通过标准输入喂给 dgst。注意 echo 默认会带换行，校验短字符串时一般用 echo -n。

3. Base64 编码与解码

适合在文本通道里传输二进制，或快速查看二进制内容（Base64 不是加密）。

对称加解密（enc）

用口令派生密钥加密文件，算法以 AES-256-CBC 为例；加解密必须使用相同算法与口令，解密侧需带 -d。

  • -salt：加密时加盐，避免相同明文产生相同密文（若版本默认已加盐，可省略显式写法，以本机 openssl enc -help 为准）。
  • 生产环境更推荐 随机二进制密钥 + 明确 KDF/模式（或直接用 age、GnuPG 等高层工具），口令仅作演示或临时场景。

非对称：公钥加密与私钥解密（RSA）

RSA 直接加密只适合很短载荷（长度受密钥与填充限制）；长数据应使用「随机对称密钥加密数据 + RSA 加密对称密钥」等混合方案（TLS、CMS 即类似思路）。

下面假设已有 PEM 私钥 private.key 与对应 公钥 public.key（见上文「从私钥导出公钥」）。

旧资料中的 openssl rsautl 已逐步被 pkeyutl 取代，新脚本优先用后者。

数字签名与验签

用私钥对消息摘要签名，任意持有公钥的一方可验证完整性及来源（前提是公钥可信）。

1. 私钥签名、公钥验签

验签成功会打印 Verified OK。

2. 从证书提取公钥再验签

生成自签名证书（开发/测试必备）

自签名证书 = 私钥 + 自己签发的证书
适合本地开发、内网测试，不能用于公网生产环境。

一步生成 私钥 + 证书（有效期 10 年）

  • -nodes：私钥不加密
  • -days 3650：有效期 10 年
  • 执行后按提示填信息（可以全部回车）

最终得到两个文件：

  • private.key：私钥
  • cert.crt：自签名证书

证书字段与扩展速览（排障高频）

用 openssl x509 -in cert.crt -text -noout 打出的内容里，下面几行决定证书好不好使：

字段 位置 关注点
Subject / Issuer 头部 主体与签发者；自签名证书二者相同
Validity 头部 Not Before / Not After：不在区间内即报”证书过期/未生效”
Subject Alternative Name X509v3 扩展 浏览器只认 SAN 不认 CN；IP 站点必须写 IP:x.x.x.x
Basic Constraints X509v3 扩展 CA:TRUE 才是 CA 证书；服务器证书必须 CA:FALSE
Key Usage / Extended Key Usage X509v3 扩展 服务器证书应有 Digital Signature, Key Encipherment + TLS Web Server Authentication
Signature Algorithm 尾部 推荐 sha256WithRSAEncryption 或 ecdsa-with-SHA256；sha1With... 已被浏览器拒绝

证书链验证（openssl verify）

服务器返回的证书可不可信，一条命令见分晓：

  • -CAfile：根 CA 证书（信任锚）
  • -untrusted：中间 CA 证书（仅用于拼链，不被信任本身）
  • 输出 server.crt: OK 即通过；unable to get local issuer certificate 说明中间链没给全——Web 服务器配置里要合并 server.crt + intermediate.crt（Nginx 的 fullchain.pem 就是这么来的）。

调试 HTTPS 连接（s_client 三件套）

1. 基础握手与证书查看

  • -servername 发送 SNI：一台服务器托管多个站点时，不带它会拿到默认证书，排障”证书和站点对不上”必备。
  • 输出中 Verify return code: 0 (ok) 表示验证通过；非 0 时看紧挨着的错误行。

2. 指定协议与 ALPN

ALPN protocol: h2 表示服务器支持 HTTP/2；No ALPN negotiated 则不支持。

3. 只看证书、不交互

4. 握手性能压测（s_time）

  • -new：每次都做完整握手，测新建连接成本；不加则复用会话。
  • 输出给出 10 秒内握手次数与每秒连接数（cps），评估服务器证书链大小与 CPU 压力时很直观。

常见误用速查

误用 现象 正确做法
用 MD5/SHA-1 签证书 浏览器直接拒绝 一律 -sha256 及以上
enc 不带 -pbkdf2 低版本默认 MD5 派生 1 轮，秒破 显式 -pbkdf2 -iter 100000，或改用 age/GnuPG
证书只填 CN 不加 SAN Chrome 报 ERR_CERT_COMMON_NAME_INVALID CSR 里加 subjectAltName 扩展
把私钥提交进 Git 证书形同虚设 私钥永不入库，泄露即吊销重签
s_client 忘带 -servername 多站点返回错证书 调 SNI 站点必带
用 genrsa 1024 弱密钥被扫描器标记 至少 2048，新签 CA 用 4096

展望：后量子密码

OpenSSL 3.5 LTS 起内置 ML-KEM（密钥封装）、ML-DSA（签名）、SLH-DSA 三组后量子算法，可用 openssl list -kem-algorithms 查看本机支持。生产 TLS 仍以 X25519 + Ed25519/ECDSA 为主，但对长期敏感数据可关注混合握手（X25519+ML-KEM-768）在 Nginx/浏览器侧的落地进度。

生产环境标准流程

  1. 生成安全私钥（4096 位，带密码）
  2. 生成 CSR
  3. 提交 CSR 给 CA → 获取正式证书
  4. 部署证书（Nginx/Apache/IIS）

本章小结

要点 结论
概念 私钥、公钥、证书、CSR 分工明确；私钥绝对不能泄露（证书失效且签名可被伪造）
摘要与编码 md5 / sha256 / dgst（文件或管道）；base64 与 -d 解码；Base64 不是加密
密钥 genrsa 生成、-aes256 保护、rsa -pubout 导出公钥
加解密 对称 enc（算法与口令一致）；非对称短数据 pkeyutl；长数据走混合加密或 TLS
签名 dgst -sign / -verify；可从 x509 -pubkey 取公钥验签
证书 开发用自签名；生产用 CSR → CA；会查看、匹配 modulus、格式转换与部署
排障 -noout -subject -dates -ext subjectAltName 速查；openssl verify 验链；s_client -servername/-alpn 调握手；s_time 压测握手
误用 拒 MD5/SHA-1、SAN 不可缺、私钥不入 Git、enc 显式 -pbkdf2
