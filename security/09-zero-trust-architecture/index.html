第九章：零信任架构落地：身份、设备与持续验证

内网不再是安全区，身份才是新边界——每次访问都要重新证明自己。

1. 核心理念：三个「不」

零信任（Zero Trust）不是某个产品，而是一套架构哲学，由 NIST SP 800-207 正式定义。核心三条：

  1. 永不信任，始终验证（Never trust, always verify）：网络位置不产生任何信任。内网 IP、VPN 隧道、办公网段——统统不算信任凭证；
  2. 最小权限（Least privilege）：每次访问只授予完成当前动作所需的最小权限，且尽量短时（just-in-time）；
  3. 假设已被攻破（Assume breach）：按「攻击者已在内网」设计防御，重点是限制横向移动与爆炸半径。

1.1 与边界安全模型的对比

维度 传统边界模型 零信任模型
信任基础 网络位置（内网=可信） 身份 + 设备 + 上下文，逐次验证
访问粒度 网段/VLAN 级 单个应用、单个 API 调用级
凭证寿命 VPN 一连一整天 短时凭证，分钟级过期
横向移动 进内网后基本畅通 每次跨服务调用都需授权
失效场景 VPN 账号泄露=全线失守 单一凭证泄露影响面受限
可见性 边界日志为主 全链路请求级审计

一句话：边界模型是城堡与护城河，零信任是每扇门都要刷卡的写字楼。

2. 身份是地基：SPIFFE/SPIRE 工作负载身份

人的身份有 OIDC/SAML 成熟方案，工作负载（服务、Pod、批任务）的身份却长期靠 API Key、静态密码硬撑——这正是零信任最难补的课。

2.1 SPIFFE：统一身份格式

SPIFFE（Secure Production Identity Framework for Everyone） 定义了工作负载身份标准：

  • 身份是 URI，包含信任域、命名空间、服务账号；
  • 凭证形态是 SVID：X.509 证书（X.509-SVID）或 JWT（JWT-SVID）；
  • 关键特性：短时（默认 1 小时）、自动轮换、无需硬编码密钥。

2.2 SPIRE：身份签发引擎

SPIRE 是 SPIFFE 的参考实现，架构分两层的：

  • SPIRE Server：信任根，负责注册条目（Registration Entry）管理与 SVID 签发；
  • SPIRE Agent：每个节点一个，通过 Node Attestation（云厂商 IAM、k8s PSAT、join token）向 Server 自证节点身份，再通过 Workload Attestation（校验 PID、容器 label、k8s service account）向工作负载颁发 SVID。

3. mTLS 落地：让身份跑在链路上

有了身份，下一步是所有服务间通信默认 mTLS——双向验证，加密传输，请求级身份。

3.1 两条主流路线

方案 原理 优点 代价
Istio ambient mesh 节点级 ztunnel 接管流量（L4），按需加 waypoint（L7） 无 sidecar，资源省，运维简单 L7 策略需额外 waypoint
Linkerd 每 Pod 注入 Rust 微代理 sidecar 延迟低、内存小、默认 mTLS 开箱即用 sidecar 模式固有的资源开销

3.2 Linkerd 快速上手

注入完成后，同网格内 Pod 间流量自动 mTLS，证书由 Linkerd identity 组件（兼容 SPIFFE 语义）每 24 小时自动轮换。

3.3 Istio ambient 模式

3.4 落地要点

  • 先 PERMISSIVE 后 STRICT：先放行明文 + mTLS 混合流量观察，再切严格模式，避免一刀切打挂存量服务；
  • 网格出口（Egress Gateway）统一收口，外部调用也要审计；
  • 与 SPIRE 联邦：跨集群、跨云时通过 SPIFFE Federation 交换信任域公钥，实现跨域 mTLS。

4. 设备信任：人之外的一半方程

零信任的访问决策是「什么人 + 用什么设备 + 访问什么」三元组。设备不信任，盗来的员工账号照样畅通。

4.1 设备信任信号来源

信号 来源 说明
设备注册与合规 MDM（Intune、Jamf、飞连） 是否纳管、加密盘、锁屏密码、越狱/root 检测
安全代理在线 EDR（CrowdStrike、SentinelOne） 杀软实时在线、无高危告警
补丁水位 MDM/漏扫 OS 与关键软件补丁等级
设备证书 企业 CA 签发（参考第二章本地 CA） 设备级 mTLS 身份，防仿冒

5. 策略引擎：OPA 统一决策

策略若散落在每个应用代码里，零信任永远落不了地。OPA（Open Policy Agent） 用声明式语言 Rego 把策略外置：

OPA 的部署形态灵活：Go 库内嵌、sidecar、中心化服务均可；Envoy、Istio、K8s admission、API 网关都有现成集成。策略即代码，进 Git 走评审与单测，变更全程可审计。

6. Google BeyondCorp：参考架构

BeyondCorp 是 Google 2011 年启动、公开于系列论文的零信任实践，核心成果：砍掉内网特权，全员远程与在办公室体验一致。

6.2 可借鉴的设计决策

  1. 所有应用 Web 化或代理化：不暴露直连端口，一切访问过 Access Proxy；
  2. 信任分层（Trust Tier）：设备按状态分为「完全受管 / 部分受管 / 不受信」，应用按敏感度分级，矩阵决定放行；
  3. 证书即设备身份：设备证书自动签发轮换，比 MAC 地址、IP 白名单可靠得多；
  4. 渐进推行：用多年时间按应用逐个迁移，保留回退通道，不搞大爆炸切换。

国内可参考的近似落地：腾讯 iOA、阿里 SASE、Cloudflare Zero Trust（Access + Gateway + Tunnel 组合）。

7. 分阶段迁移路线图

零信任没有「一键开启」，推荐按四阶段推进，每阶段独立交付价值。

阶段一：身份地基（1-3 个月）

  • 统一 IdP，全员 SSO + 强制 MFA（优先 FIDO2/硬件密钥）；
  • 盘点应用清单，标记敏感度分级；
  • 工作负载侧：选定 SPIFFE/SPIRE 或服务网格身份，先在 1 个核心域试点 mTLS。

阶段二：设备与入口（3-6 个月）

  • MDM 全量纳管，设备证书下发；
  • 部署应用代理（Access Proxy / ZTNA），高敏应用第一批切流，关 VPN 权限做对照组；
  • OPA 策略框架上线，先 audit 模式记录「假设执行会拦什么」。

阶段三：服务间默认加密（6-12 个月）

  • 服务网格 mTLS 从 PERMISSIVE 切 STRICT，覆盖核心生产命名空间；
  • 东西向流量按服务身份做授权策略（AuthorizationPolicy）；
  • 网络层做微分段兜底，默认拒绝。

阶段四：持续验证与自动化（12 个月+）

  • 会话级持续评估：设备/用户风险信号变化实时吊销会话；
  • SIEM 联动：异常行为自动触发降权或重认证；
  • 权限定期自动回收（access review 自动化），JIT 提权常态化。

常见坑 FAQ

Q1：零信任是不是必须上服务网格？
不是。服务网格解决「工作负载间 mTLS」这一段；人用 ZTNA 网关，设备用 MDM——三者可独立推进。小团队先用 Cloudflare Access 这类 SaaS 把「人访问应用」做掉，收益最快。

Q2：mTLS 全开后性能损失大吗？
TLS 1.3 + AES-GCM 硬件加速下，同机房延迟增加通常 <1ms；真正的成本在运维心智：证书轮换、身份注册、调试排障（加密后传统抓包失效，要靠网格自带遥测）。

Q3：OPA 策略会不会成为单点？
决策点要做高可用，且设计fail-open 还是 fail-close 要分场景：支付链路 fail-close，内部工具可 fail-open + 告警，避免 OPA 故障引发全站雪崩。

Q4：VPN 可以直接退休吗？
可以但分步：先把 Web 应用切到 ZTNA，再处理 SSH/数据库类协议（用 Access 的 TCP 代理或 Teleport 这类现代方案），最后关停 VPN。多数企业 6-18 个月完成。

Q5：证书这么多，吊销来得及吗？
零信任的思路是用短寿命替代吊销：SVID 1 小时、用户 token 15 分钟，攻击者拿到也快过期了。OCSP/CRL 留给设备证书这类长寿命凭证。

Q6：遗留系统改不动怎么办？
给它前面架代理（sidecar 或反向代理），由代理持有身份做 mTLS，遗留系统只监听 localhost——「身份外挂」是兼容存量的标准姿势。

落地清单

  • 全员 SSO + 强制 MFA，淘汰共享账号与静态密码
  • 应用敏感度分级清单完成并评审
  • SPIRE 或服务网格身份在至少一个核心域上线 mTLS
  • MDM 纳管率 >95%，设备证书全覆盖
  • 高敏应用经 ZTNA/Access Proxy 访问，VPN 权限回收对应人群
  • OPA 策略集中管理，关键策略有单元测试
  • mTLS 从 PERMISSIVE 切 STRICT 的命名空间清单与时间表
  • 风险信号（EDR/MDM/行为）联动会话吊销的自动化规则上线
