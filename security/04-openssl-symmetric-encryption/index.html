发表于 2026-05-01 更新于 2026-10-25 分类于 安全 本文字数： 5k 阅读时长 ≈ 5 分钟

第四章：OpenSSL 对称加密：AES-GCM、ChaCha20 与推荐用法

概念基础

  1. 对称加密：加密与解密使用同一把密钥，速度快、开销低，适合大块数据（文件、磁盘、TLS 记录层流量）。
  2. 两大要素：算法 + 工作模式（如 AES-256-GCM）决定安全性质；密钥来自随机数或口令派生（PBKDF2，见第七章）。
  3. 为什么推荐 AEAD：GCM / ChaCha20-Poly1305 属于认证加密，同时提供保密性 + 完整性（Auth Tag 防篡改）；裸 CBC / ECB 无认证，存在填充 oracle 等风险。
  4. Nonce 纪律：GCM 的 (key, nonce/IV) 绝不能重复，否则密钥流泄露、安全性崩塌——这是使用 AEAD 的头号大坑。
  5. 口令 ≠ 密钥：人类口令熵低、可猜测，必须经 KDF（salt + 高迭代） 派生密钥；生产环境更推荐随机 32 字节密钥。

推荐算法（2020s 生产）

优先级 算法 / 模式 用途
首选 AES-256-GCM 文件加密、磁盘、API 载荷（须唯一 nonce）
首选（无 AES 硬件加速时） ChaCha20-Poly1305 移动端、部分 TLS 1.3 套件
可用 AES-256-CBC + HMAC（Encrypt-then-MAC） 老系统；须正确实现
避免 AES-CBC 无 MAC、ECB、DES/3DES、RC4 填充 oracle、模式泄露、已淘汰 


flowchart LR
  Plain[明文] --> ENC[AES-256-GCM + 随机 IV]
  Key[256 bit 密钥] --> ENC
  ENC --> Cipher[密文 + Auth Tag]
  Cipher --> DEC[解密 + 验 Tag]
  Key --> DEC
  DEC --> Plain

一、算法特点

1. AES（Advanced Encryption Standard）

密钥长度 说明
AES-128 TLS 常用；足够多数场景
AES-256 文件加密、高合规场景 推荐
模式 特点 推荐
GCM 认证加密（AEAD），防篡改 是
CTR 流式；需额外 MAC 需配合 HMAC
CBC 传统模式；需随机 IV + 防 padding oracle legacy
ECB 相同块相同密文 否

2. ChaCha20-Poly1305

  • 256 bit 密钥，256 bit nonce（TLS 中规范用法由协议约束）。
  • 常数时间实现友好，TLS 1.3 默认套件之一。
  • OpenSSL enc 对 ChaCha20 支持依版本而异；应用层多用库 API 或 TLS。

3. 已淘汰（legacy provider）

DES、3DES、RC4、Blowfish — 仅维护老设备；新系统勿选。OpenSSL 3.x 需显式 -provider legacy 才能调用：

4. 国密 SM4（合规场景）

SM4（GB/T 32907）是国密体系的分组密码，128 bit 密钥、128 bit 分组，定位对标 AES；常配合 SM2（非对称）/ SM3（哈希） 组成全套国密方案。OpenSSL 3.5 LTS 已内置 SM4-CBC/ECB/CTR/OFB/CFB/GCM 等模式：

使用边界：SM4 仅在明确国密合规时启用；国际互操作仍以 AES / ChaCha20 为主。国密 TLS（TLCP/GB/T 38636）需专用 fork（如 Tongsuo），OpenSSL 主线不含。

5. 常见误用：ECB 与弱 IV

ECB 模式把每个 16 字节块独立加密——明文相同的块密文必然相同，图像的轮廓、数据库的等值字段全部泄露（教科书级的「ECB 企鹅图」即此问题）：

其余高频错误：

误用 后果 正确做法
CBC 固定 IV 首块明文可分析 每次随机 IV，随密文传输
GCM nonce 复用 密钥流泄露、认证失效 (key, nonce) 绝不重复；推荐随机 96 bit
口令直接当密钥 熵不足，秒级爆破 PBKDF2 派生（见第七章）
密文不加完整性校验 可篡改（比特翻转） 用 AEAD 或 Encrypt-then-MAC

三、AEAD（GCM）在 OpenSSL 中的注意点

GCM 必须保证 (key, nonce/IV) 永不重复。命令行 enc -aes-256-gcm 在 OpenSSL 3.x 可用，但 tag 处理 与 enc 默认行为 因版本而异；生产 bulk 加密更建议：

  • 应用代码使用 EVP_aes_256_gcm 并显式管理 IV + tag；或
  • 使用 age、libsodium 等封装好的文件加密工具。

TLS 1.3 服务器常按客户端特征自动在 AES-GCM 与 ChaCha20 间选择，正是这条曲线的产物。

要点：IV 由调用方生成并随密文保存；解密侧用 EVP_CTRL_GCM_SET_TAG 先灌入 tag 再 EVP_DecryptFinal_ex 校验——tag 校验失败必须丢弃全部输出，这是 AEAD 的安全底线。

六、与 TLS / HTTPS 的关系

浏览器访问 HTTPS 时：

  1. TLS 握手（第五章：OpenSSL 非对称加密与密钥交换：RSA、Ed25519、X25519）协商出 对称会话密钥；
  2. 记录层用 AES-GCM 或 ChaCha20-Poly1305 加密 HTTP 数据。

TLS 1.3 只保留了 5 个套件，全部为 AEAD：两个 AES-GCM、一个 ChaCha20-Poly1305、两个 AES-CCM——CBC 套件在 TLS 1.3 中被整体移除，这正是「填充 oracle」多年血泪史的结论。

七、选型小结

需求 推荐
本地加密单个文件 AES-256-CBC + PBKDF2 或专用 age
API / 数据库字段 AES-256-GCM，随机 IV 随密文存储
大流量通道 TLS 1.3（内置 AEAD）
不要用 ECB、裸 CBC、RC4、DES
