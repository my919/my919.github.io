8. 典型案例：Terraform 状态管理治理

8.1 问题背景

10 人团队共用本地 tfstate + 网盘同步：两人并发 apply 互相覆盖；有人嫌 apply 慢直接在控制台手改安全组；一次资源改名触发 30 个资源销毁重建，prod 数据库险些陪葬。

8.2 解决方案

远端 S3 后端 + DynamoDB 状态锁；state 按环境与模块拆分（爆炸半径最小化）；改名一律 terraform state mv 而非 delete+create；CI 用 -detailed-exitcode 每日跑漂移检测，发现漂移自动开 issue 并通知值班。

8.3 关键实现

8.4 踩坑点

  • state 里存了 RDS 密码明文输出，S3 桶一度对全公司可读；改 KMS 加密 + 敏感输出走 Secrets Manager
  • 改名直接改代码触发销毁重建，30 个资源下线；rename 必须 state mv
  • 单一大 state 全环境共用，apply 要 20 分钟且一坏全坏；按 env/module 拆成 12 个小 state
  • 漂移检测只跑了一次没人跟进；改为每日定时 + 未处理漂移升级到资源负责人

9. 常见误用与陷阱

坑 现象/后果 解法
本地 state 网盘同步 并发覆盖，资源错乱 S3 远端 + DynamoDB 锁
控制台手改资源 漂移累积，下次 apply 意外销毁 每日漂移检测 + import 纠偏
改名即销毁重建 停机事故 terraform state mv
单一大 state apply 慢、爆炸半径大 按环境/模块拆分 state
state 进 Git 仓库 敏感值泄露到提交历史 远端后端 + KMS + .gitignore
无 plan 审查直接 apply 删库级变更无人拦截 CI plan 门禁 + PR 审批

11. 总结

11.1 最佳实践

  • 模块化：可复用的基础设施组件
  • 环境隔离：dev/staging/prod 独立状态
  • 策略即代码：自动化合规检查
  • GitOps：所有变更通过 PR 审批
  • 成本可见：PR 中显示成本影响
  • 安全左移：扫描集成到 CI

11.2 2026 趋势

  • OpenTofu 成熟：Terraform 开源替代品进入生产
  • Crossplane 普及：K8s 原生云资源管理
  • 平台工程：自助基础设施平台
  • FinOps 集成：成本优化内置到 IaC 流程
