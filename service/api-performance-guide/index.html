1. 概念说明：先定指标，再谈优化

接口性能三指标：

指标 含义 目标
QPS 每秒请求数 按业务容量
P99 99% 请求在多少毫秒内完成 如 < 300ms
错误率 失败占比 < 0.1%

优化铁律：先定位，再优化——没有数据支撑的优化是瞎猜。定位顺序：压测复现 → 链路分段 → 数据库慢日志 → 逐层确认。

3. SQL 层优化（第一优先级）

为什么先治 SQL：数据库是共享资源，慢 SQL 不只拖慢自己，还占连接池拖垮其他接口——收益最大、最值得先做。

4. 缓存层优化（第二优先级）

4.1 多级缓存（本地 + Redis）

为什么本地 + Redis 两级：本地缓存把热点请求拦在最前面（0ms 无网络）；Redis 兜底多实例一致性。注意：本地缓存只放不常变的数据，更新时删 Redis 即可（本地缓存靠 5 分钟过期收敛）。

5. 异步层优化（第三优先级）

5.1 外部调用并行化（串行 → 并行）

为什么必须带超时：并行后最慢的一个外部服务决定总耗时——不带超时，对方挂掉你的接口也挂掉。并行调用必须配独立线程池 + 超时 + 失败降级。

5.2 非核心逻辑异步化（响应不等它）

判断标准：这个操作的结果不影响本次响应 → 异步化；影响响应 → 只能并行或优化它本身。

6. 代码层优化（第四优先级，常有意外收获）

7. 完整案例：订单列表从 800ms 到 50ms

为什么按这个顺序：SQL 层是根因（收益最大）；缓存治标但立竿见影；代码层扫尾。顺序反了会”先加缓存掩盖慢 SQL”，治标不治本。

8. 优化检查清单

9. 典型案例：商品详情页 1.2s → 80ms

问题背景：App 商品详情页 P99 高达 1.2s，大促压测时直接超时熔断。用户反馈”点开商品像刷新闻”——移动端对 300ms 以上的白屏感知极明显，详情页转化率比竞品低 15%。

方案：链路拆解后三管齐下：① 三个串行下游调用并行化；② 商品主数据多级缓存（Caffeine + Redis）+ 互斥锁防击穿；③ 非核心数据（推荐/评价）异步加载、默认兜底占位：

优化项 手段 收益
串行 → 并行 CompletableFuture + 独立线程池 530ms → 200ms
主数据多级缓存 Caffeine 5min + Redis 30min 命中率 98%，查库量降 95%
防击穿 Redis SETNX 互斥 + 未获取锁者读旧值重试 促销瞬时百万 QPS 不打穿 DB
非核心异步化 推荐/评价旁路加载 + 占位符 首屏不等长尾服务
大对象瘦身 只序列化前端需要的 12 个字段 响应体 86KB → 12KB

踩坑点：

  1. 缓存过期时间统一 30 分钟无随机抖动，某整点大批商品同时失效，DB 瞬时 QPS 冲到 20 倍——过期时间加 0-5 分钟随机抖动后削平。
  2. exceptionally 降级最初返回 null，前端把”价格查询中”渲染成”¥null”，客诉 40 单——降级必须返回带语义的占位对象，不允许 null 直接出接口。
  3. 并行化时偷懒用了 CompletableFuture.supplyAsync 不传线程池（走 ForkJoinPool.commonPool），压测时与其他异步任务互相争抢，P99 反而劣化——并行调用必须显式传独立线程池并设队列上限。
  4. 优化后只压测了缓存命中场景（80ms），未压”全量缓存失效”冷启动场景——上线首日 Redis 被运维清空，DB 被回源流量打挂 8 分钟。性能验收必须覆盖冷启动与热点失效场景。
  5. 详情页瘦身时把移动端还在用的 subtitle 字段裁掉，老版本 App 大面积空白——裁字段前先查各端版本的使用情况，或保留一个过渡期。

10. 常见误用与陷阱

坑 现象/后果 解法
没压测就凭感觉优化 优化了占耗时 5% 的代码，P99 纹丝不动 先压测复现 + 链路分段，按耗时占比从大到小逐层处理
缓存过期时间一刀切 整点大批 key 同时失效，DB 瞬时被打挂（雪崩） 过期时间加随机抖动（TTL ± 10%）；核心数据加互斥锁回源
并行调用共用 commonPool 与其他异步任务争抢线程，并行变串行甚至死锁 显式指定独立线程池，设合理核心数/队列上限/拒绝策略
join()/get() 不带超时 下游挂掉时并行变”永久等待”，线程池被占满 每个 get(timeout, unit) 都显式超时 + exceptionally 降级
用平均值/最优值汇报性能 平均 100ms 掩盖了 P99 2s，用户投诉与报表打架 只认 P95/P99 分位值；按端/接口/时段维度拆开看
优化后不回归功能 性能达标但数据错了（缓存脏读/降级值当真值） 每次优化跑回归用例；降级路径必须有可观测标志（日志/埋点）
缓存值体积不控制 单个 value 500KB，Redis 网络与内存双爆，大 key 阻塞 value 控制在 10KB 内；大对象裁字段/压缩/拆分
循环里逐条查缓存或查库（N+1） 100 条数据 100 次网络往返，P99 随页大小线性恶化 改 mGet 批量 + WHERE id IN 批量回源，往返次数降为 2
