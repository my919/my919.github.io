Git · 团队协作工作流

入门篇之后的团队实战。分支模型对比 · Pull Request 流程 · 冲突解决 · Code Review · 规范提交 · 保护分支与 CI 联动。

技术栈速查

类别 选型 用途
平台 GitHub / GitLab / Gitee 托管与评审
约定 Conventional Commits 提交规范
工具 git 2.47+ 版本控制
钩子 pre-commit / husky 质量门禁

1. 概念说明

单人 Git 只需 commit/branch；团队 Git 的核心是：分支模型（何时建分支）+ 评审流程（代码如何合入）+ 规范（提交/分支命名）+ 保护（主分支防破坏）。

核心原则：

  • main/master 永远可部署（合入即通过 CI）。
  • 每个功能一个分支，生命周期短（1-2 天）。
  • 代码必须经过 Review 才能合入。
  • 提交信息清晰可追溯（关联 issue 编号）。

2. 分支模型对比

2.1 GitHub Flow（最常用，推荐）

流程：从 main 拉分支 → 开发 → 推远程 → 开 PR → 评审+CI → 合并 → 删分支。

2.2 Git Flow（发布节奏固定）

适用：固定版本周期（如月发布）；对持续部署团队过重。

2.3 选择建议

场景 模型
持续部署的 Web 团队 GitHub Flow
版本化发布（SDK/App） Git Flow
中小团队/新项目 GitHub Flow 起步

4. 冲突解决

减少冲突的习惯：分支短命；每天 rebase 一次 main；多人尽量改不同文件。

5. Code Review 实践

Review 重点（不是只点赞）：

可维护 命名、重复代码、复杂度过高
测试 关键分支是否有用例

6. 合并策略选择

策略 效果 适用
Squash merge 所有提交压成一个 团队默认推荐
Rebase merge 保留提交、线性历史 需要保留粒度

7. 保护分支与 CI 联动

GitHub 设置：Settings → Branches → Add rule：

  • 保护 main：禁止直接 push（仅 PR 合入）。
  • 要求 PR 通过 CI 才能合并。
  • 要求 1-2 个 Review。
  • 强制线性历史 / 要求分支最新。

GitLab 对应：Settings → Repository → Protected branches + Merge request approvals。

8. 常见协作问题

问题 解决
提交信息乱写 commitlint + 团队规范
main 被直接 push 保护分支
大 PR 难评审 功能拆小；WIP 标注
合入后发现冲突/坏代码 CI 全量跑；回滚策略（revert）
误提交密钥 git filter-repo 清理 + 立即轮换密钥

9. 典型案例

案例：三人团队落地 GitHub Flow（含 rebase 冲突处理）

问题背景：3 人小组此前直接在 main 上开发，互相覆盖提交、main 频繁不可部署。目标：一周内落地 GitHub Flow——保护 main、PR 评审、短命功能分支。

方案：仓库配置分支保护 → 团队约定分支命名与 Squash 合并 → 每天用 rebase 同步 main，冲突在变基时暴露并解决。

关键操作：

踩坑点：

  • 变基只对自己的私有分支做；PR 已有人评审后再 force push，评审记录会对不上号。
  • rebase 中 --ours/--theirs 的方向与 merge 相反（ours=被变基到的 main），容易选反，建议手动看内容再改。
  • main 上的修复要带回功能分支时用 git rebase main，不要 merge main 进来——否则分支历史混入 merge 提交，PR diff 变脏。
  • 紧急修复也必须走 hotfix/* 分支 + PR，保护分支的意义就是不给你”就这一次”的例外。

10. 常见误用与陷阱

坑 现象/后果 解法
对公共分支 force push 同事本地历史与远程分叉，pull 后重复提交甚至丢码 保护分支禁 push；必须改历史时公告并让全员重新拉取
rebase 已共享的分支 历史被改写，协作者 pull 时冲突成灾 只 rebase 私有分支；共享分支只 merge
merge 与 rebase 随意混用 历史忽线忽叉，同一提交重复出现 统一约定：PR 内 rebase 同步，合入用 Squash merge
分支一活好几周 与 main 偏离巨大，合并冲突成山 拆小功能、每天 rebase main、分支寿命 ≤ 2 天
直接向 main push 修复 绕过 CI 与评审，坏代码直达主干 保护 main 禁 push，紧急修复走 hotfix 分支 + PR
--amend 已推送的提交 远程拒绝或需 force push，协作混乱 amend 只用于未推送提交；已推送用新提交或 revert
