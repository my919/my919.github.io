1. 概念说明

Git 是分布式版本控制系统：每个开发者的本地都是完整仓库，无需联网即可提交、回滚、分支。核心模型是快照 + 引用：

  • 工作区（Working Directory）：你编辑的文件。
  • 暂存区（Staging Area / Index）：git add 后的待提交内容。
  • 本地仓库（Repository）：git commit 后永久保存的快照。
  • 远程仓库（Remote）：如 GitHub，用于多人同步。

三个对象的本质：

对象 说明
Commit 一次提交的快照，含作者、时间、父提交哈希
Branch 指向某个 Commit 的可移动指针
HEAD 当前所在分支/提交的指针

4. 撤销与回滚（重点避坑）

场景 命令 效果
撤销工作区修改 git restore <file> 回到暂存区/HEAD 状态
撤销暂存 git restore --staged <file> 从暂存区移除
修改最后一次提交 git commit --amend 合并进上一条（未推送时用）
回退到某提交（保留历史） git revert <commit> 新增反向提交，安全
回退到某提交（丢弃历史） git reset --hard <commit> 危险，已推送禁止

铁律：已推送到远程的提交，用 revert 不用 reset。

12. 典型案例

案例：误提交密钥后用 filter-repo 清除历史

问题背景：新人把含数据库密码的 config/prod.yml 提交并推送到了 GitHub。仓库虽是私有但成员众多，仅删除当前版本不够——历史提交里依然能看到密码，必须从全部历史中抹掉该文件。

方案：① 立即轮换泄露的密钥（比清历史更紧急）→ ② 备份仓库 → ③ 用 git filter-repo 改写历史删除文件 → ④ 强推覆盖远程 → ⑤ 通知全员重新克隆。

关键命令：

踩坑点：

  • 顺序不能反：先轮换密钥再清历史。历史可能已被 fork 或平台缓存，清除不是 100% 可靠，密钥作废才是根治。
  • filter-repo 会改写所有提交哈希，基于旧历史的本地分支全部失效，必须通知成员重新克隆。
  • 不要用 git rm + 提交代替：那只删当前版本，历史仍在。
  • GitHub 上被 PR 引用的旧提交可能仍能通过 SHA 访问，必要时联系平台支持清理缓存。

13. 常见误用与陷阱

坑 现象/后果 解法
git push --force 强推共享分支 覆盖同事刚推的提交，直接丢代码 用 --force-with-lease；共享分支禁 force，改用 revert
merge 与 rebase 混用 同一改动在历史里出现两次，图形历史像辫子，blame/bisect 失效 团队约定：本地私有分支用 rebase，公共分支只 merge
.gitignore 对已跟踪文件无效 加了 ignore 后 config.yml 照样被提交 先 git rm --cached <file> 移出跟踪并提交，ignore 才生效
钩子被 --no-verify 跳过 lint/密钥检查形同虚设，坏提交进仓库 CI 端再设一道门禁；评审时抽查提交信息
已推送提交用 reset --hard 本地与远程分叉，同事 pull 后历史错乱 已推送用 git revert；reset 仅限未推送的本地提交
git pull 默认 merge main 上出现大量 “Merge branch ‘main’ of …” 噪声提交 git config --global pull.rebase true，拉取即变基
