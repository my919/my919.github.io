1. 概念说明

装饰器（Decorator）本质是一个语法糖：@deco 写在函数定义上方，等价于在定义之后手动执行一次「函数替换」：

事实 含义
装饰在定义时执行 import 模块时 @deco 就已运行，不是调用时才执行
装饰器是高阶函数 接收函数、返回函数（或返回一个可调用对象）
与矩阵 @ 无关 NumPy 里 a @ b 是矩阵乘法运算符，与装饰器只是共用符号

2. 从闭包到第一个装饰器

装饰器的地基是闭包：内层函数记住外层函数的局部变量，即使外层已返回。

要点：*args, **kwargs 让 wrapper 可以接住任意签名；wrapper 通过闭包「记住」了 func，timer 返回后 func 依然存活。

3. functools.wraps：保住函数的身份

不加 @functools.wraps，被装饰函数的 __name__、__doc__、签名都会变成 wrapper 的——这会让日志、文档生成、FastAPI 路由注册全部出错：

规则：写任何装饰器，第一件事就是给 wrapper 加 @functools.wraps(func)。

4. 带参数的装饰器（三层嵌套）

@retry(3) 这种带括号的写法，需要再套一层：外层接收参数，中层接收函数，内层是 wrapper。

记忆口诀：括号有几层，函数嵌几层。@deco 一层调用 → 两层嵌套；@deco(arg) 两层调用 → 三层嵌套。

业务背景：订单系统的写操作必须留审计日志，团队约定用 @audit 装饰器统一打日志；基类 OrderService 装饰好后，子类却踩了两个坑。

冲突③：子类 super() 链让装饰器重复触发

更隐蔽的情况：子类重写时规规矩矩地加了装饰器，但内部调用了 super()——基类方法上的装饰器被再次触发。支付系统的退款流程就踩过这个坑：

解法：用 contextvars 做「审计上下文」标记，同一次业务调用链上只由最外层记录一次，嵌套调用（super 链、内部互调）自动跳过：

用 ContextVar 而不是普通全局变量，是因为它在线程和 asyncio 协程中各自隔离——并发退款时不会互相干扰。

冲突④：@property 被继承重写，setter 静默丢失

@property 也是装饰器。商品系统里基类用 price 属性封装「含税价换算」读写，子类 VIP 商品只重写 getter 加折扣，结果 setter 被整个覆盖：

原因：@property 每次装饰都生成一个全新的 property 对象，子类的 price 与基类的 price 是两个互不相关的对象，基类上挂的 setter 不会自动带过来。

冲突⑤：方法上挂 lru_cache，整个继承体系共享缓存、实例被钉死

会员服务把「等级计算」这个昂贵操作用 @lru_cache 加速。装饰器贴在方法上，意味着缓存字典挂在类上——基类、子类、所有实例共用一份，且缓存的 key 里含着 self：

后果有两个：① 缓存 key 里的 self 让每个 service 实例永远无法被 GC（长驻进程内存持续上涨）；② 基类与子类、所有实例共享一份缓存，无法按实例失效，子类改了 rule 配置也清不掉旧值。

解法：把缓存挪进 __init__——每个实例一份缓存，key 里不再含 self，实例销毁时缓存随之释放：

注意 get_level 此时是实例属性而非类方法：MemberService.get_level(1) 这种类调用不再可用（本来也没意义），子类重写 _calc_level 即可改变行为，缓存策略不变。

冲突⑥：@singledispatchmethod 被重写，基类注册表整体丢失

通知服务用 @singledispatchmethod 按消息类型分发渠道（str 走短信、list 走批量邮件）。海外子服务重写 send 想加自己的分发，结果基类注册的类型全部失效：

原因与冲突④同源：@singledispatchmethod 每次装饰都生成全新的分发器对象，自带独立的类型注册表，基类注册表不会带过来。

解法：默认分支用 super() 回退到基类分发器，子类只增量注册新类型：

注意一个反向坑：默认分支里不能写 Notifier.send(self, msg)——send 经类访问后按第一个实参（self）的类型分发，会落到「未知类型」；super().send(msg) 才按 msg 的类型正确分发。若子类不需要新增任何类型，直接 send = Notifier.send 复用基类分发器即可，不要重写。

踩坑点：__init_subclass__ 在子类定义时（import 阶段）就执行，不要在基类模块未完成加载时触发循环导入；cls.__dict__.get(name) 只检查子类自己定义的方法，继承来的已装饰方法不会被重复包装；ContextVar.set() 的返回值必须配对 reset()，漏掉会导致后续调用全部丢日志；@property 是对象不是标记，重写时要明确决定 getter/setter/deleter 哪些换、哪些继承；方法上挂 lru_cache 会让缓存 key 含 self，实例永远无法被 GC；@singledispatchmethod 重写后必须显式回退基类分发，注册表不会自动继承。

8. 常见误用与陷阱

坑 现象/后果 解法
忘加 @functools.wraps 函数名/文档全变成 wrapper，日志与框架路由错乱 wrapper 上固定加一行 @functools.wraps(func)
以为调用时才装饰 模块 import 就执行装饰器，副作用提前发生 注册类副作用放装饰器没问题，但别在装饰器里做重 IO
wrapper 吞掉返回值 忘记 return func(...)，被装饰函数永远返回 None wrapper 最后一律 return func(*args, **kwargs)
装饰器顺序搞反 @a 在 @b 上方时 a 包装「b 包装后的函数」，顺序与直觉相反 从下往上读：离函数最近的装饰器最先执行
共享可变状态无锁 多线程下计数/限流状态竞态 状态修改处加 threading.Lock（见 7.3）
用 lru_cache 缓存会过期的数据 数据永久不刷新，且参数必须可哈希 需要过期用自写 TTL 缓存（见 7.4）或 cachetools
带参装饰器少套一层 @retry(3) 报 TypeError: 'NoneType' object is not callable 记住「括号几层嵌几层」，外层返回 decorator
子类重写丢失装饰 基类的日志/权限装饰器被重写静默绕过（见 7.5 冲突①） __init_subclass__ 在子类定义时自动补回装饰器
类装饰器贴实例方法 TypeError: missing 1 required positional argument: 'self'（见 7.5 冲突②） 类装饰器实现 __get__，返回 functools.partial(self.__call__, obj)
super() 链重复触发 子类重写后调 super()，基类装饰器再执行一次，日志/审计记双份（见 7.5 冲突③） 装饰器内用 ContextVar 标记调用上下文，嵌套调用跳过副作用
继承重写 @property 子类只重写 getter，基类 setter 静默丢失，赋值报 AttributeError（见 7.5 冲突④） 用 @基类.prop.getter 派生，只换需要的部分，其余自动继承
方法上挂 lru_cache 缓存挂类上被全继承体系共享，key 含 self 导致实例永不释放（见 7.5 冲突⑤） 在 __init__ 里建实例级缓存：self.f = lru_cache(...)(self._f)
重写 singledispatchmethod 基类类型注册表整体丢失，全部落到默认分支（见 7.5 冲突⑥） 子类默认分支 super().send(msg) 回退基类分发，只增量注册新类型
