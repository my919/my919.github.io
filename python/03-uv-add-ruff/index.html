第三章：UV 项目开发添加 Ruff：代码检查与格式化

概念基础

Ruff 是 Astral（uv 的同门）用 Rust 编写的 Python Linter + Formatter：

  1. 一个工具干两件事：同时覆盖静态检查（lint）与代码格式化（format），可替代 flake8 + isort + Black 的多工具组合，且速度快 10~100 倍。
  2. 规则集丰富：内置 pycodestyle（E）、Pyflakes（F）、import 排序（I）、pyupgrade（UP）、bugbear（B） 等 800+ 规则，通过 select 按团队规范按需启用。
  3. 与 uv 无缝协作：uv add --dev ruff 装入开发依赖组（不进入生产依赖），uv run ruff 保证本地与 CI 用同一份环境与版本。
  4. 配置集中：所有配置写在 pyproject.toml 的 [tool.ruff]，无需额外 dotfile，与第二章的项目化工作流一脉相承。

六、常用规则集速查

前缀 来源 作用
E / W pycodestyle 基础风格（行长、缩进、空白）
F Pyflakes 未使用导入、未定义变量等逻辑错误
I isort import 排序与分组
UP pyupgrade 自动升级到新语法（如 list[str] 替代 List[str]）
B flake8-bugbear 常见陷阱（可变默认参数等）
SIM flake8-simplify 简化冗余代码
C4 flake8-comprehensions 推导式优化
RUF Ruff 专属 Ruff 自研规则

推荐起步配置：select = ["E", "F", "I", "UP", "B", "SIM"]；与 Pyright 并用时不要启用 ANN（类型注解规则会与类型检查器职责重叠）。

八、常见坑 FAQ

坑 现象 处理
check --fix 与 format 顺序颠倒 先格式化再修 lint，格式又被破坏 固定顺序：先 ruff check --fix，后 ruff format
与 Black 双开 两个 formatter 互相打架 二选一；迁移期可用 ruff format（与 Black 风格几乎一致）
误开全部规则 select = ["ALL"] 后几百条警告淹没输出 按需启用，逐步收紧；老项目先 E,F,I 起步
target-version 与解释器不一致 UP 规则把代码改成运行环境不支持的语法 与 requires-python 对齐，如 py313
规则升级引入新告警 uv lock --upgrade-package ruff 后 CI 突然失败 升级前看 changelog；临时用 ignore 豁免再排期清理
.ruffignore 与 exclude 混用 配置分散排查困难 优先用 [tool.ruff] exclude，团队只维护一处

九、最佳实践清单

  1. 版本锁进 uv.lock：uv add --dev ruff + uv run ruff，本地/CI/编辑器同版本。
  2. 配置只写 pyproject.toml，不再维护 setup.cfg / .flake8 多处配置。
  3. 提交前 check --fix + format，并接入 pre-commit（见第五章）。
  4. CI 用 format --check 只校验，避免流水线里产生未提交 diff。
  5. 与 Pyright 分工：Ruff 管风格，Pyright 管类型，避免 ANN 重叠。
  6. 渐进收紧：老项目先小规则集跑绿，再逐步加 UP、B、SIM。

十、常用命令速查

目的 命令
安装为开发依赖 uv add --dev ruff
版本检查 uv run ruff --version
Lint 全仓库 uv run ruff check .
Lint 并修复 uv run ruff check . --fix
格式化 uv run ruff format .

要点 结论

安装方式 uv add --dev ruff 进入开发依赖组，uv run ruff 保证环境一致

日常命令 ruff check . --fix 检查并自动修复，ruff format . 统一格式

规则集 起步 ["E","F","I","UP","B","SIM"]，避免 ALL 与 ANN
执行顺序 本地先 check --fix 后 format；CI 用 format --check 只校验
