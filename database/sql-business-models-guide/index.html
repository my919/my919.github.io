经典业务 SQL 建模实战：订单 · 库存 · 权限 · 账务 · 内容十大模型

数据库 · 经典业务建模

十个最常被建错的业务模型，一次建对：订单 · 支付 · 购物车 · 库存 · 权限 · 组织树 · 地址 · 钱包 · 优惠券 · 关注点赞——每个都给可直接执行的 DDL、核心查询与踩坑清单。命名 / 范式 / 索引 / 分库分表等通则不在此展开，见数据库设计规范与建模实战。

技术栈速查

维度 选型 说明
数据库 MySQL 8.0+ 全文 DDL 按该版本语法编写，可直接执行
引擎 / 字符集 InnoDB + utf8mb4 事务与 emoji 缺一不可
并发控制 唯一键 · 条件 UPDATE · 乐观锁 version 防重复 / 防超卖 / 防覆盖三板斧
一致性 同事务写入 · 流水对账 · 计数校准 一切冗余都必须可推导、可校验
结构变更 Flyway 版本化迁移 通则见数据库设计规范

每个模型统一按六段展开：适用场景 → 业务与数据关系（简版 ER）→ DDL → 核心查询 → 常见坑 → 扩展点。

1. 订单与订单明细（orders / order_item）

适用：电商、本地生活、票务等一切”下单—支付—履约”交易主链路，业务建模的第一张表。

业务与数据关系

DDL

核心查询

常见坑

  • 状态流转不设条件：先 SELECT 读状态、内存判断后 UPDATE，”取消”与”支付回调”并发时会把已支付单覆盖成已取消。必须 WHERE 旧状态 AND version = ? 看影响行数。
  • 幂等键缺失：用户双击”提交订单”生成两笔真订单。uk_user_sku_idem 从数据库层兜底；撞唯一键按”下单成功”返回原单。
  • 用自增 ID 当对外单号：竞对按 ID 差值推算你的日单量。对外只用 order_no。
  • 深分页：运营后台 LIMIT 100000, 20 越翻越慢，改游标分页（见上文①）。
  • 金额字段用 FLOAT：汇总差几分钱且无从对账，一律 DECIMAL(18,2)。

扩展点

  • 数据量大了按 user_id 分库分表：C 端 95% 查询带 user_id，uk_user_sku_idem 含分片键仍能保证分片内唯一；order_no 尾部嵌入 user_id 分片基因，凭单号直达分片（做法见数据库设计规范第 8 节）。
  • 商户侧 / 运营侧查询异构：按 merchant_id 或时间维度另建宽表进 ES / 数仓，不在主链路广播查询。
  • 历史订单归档：已完成且超 N 月的单迁入归档表，主表保住索引体积。

2. 支付单与幂等表（pay_order / pay_idempotent）

适用：一切对接微信 / 支付宝 / 银联等外部渠道的支付场景——回调会重复、会乱序、会迟到，建模必须先承认这一点。

业务与数据关系

支付单与订单是 1:N：同一订单可有多笔支付尝试，只有”支付成功”的那笔有效；订单状态以支付回调为准。

DDL

channel_trade_no 允许 NULL：MySQL 唯一索引对 NULL 不生效，多个 NULL 可共存——恰好满足”发起时无渠道单号、回调后全局唯一”。

核心查询

常见坑

  • 回调先改状态再”发货”却不管影响行数：重复回调触发重复发货。条件更新 + 影响行数判断是唯一正确姿势。
  • 不校验回传金额：渠道回调的 amount 必须与本地 pay_order.amount 精确比对，防篡改与错分账。
  • 用回调时间戳判断先后：渠道重试乱序，”退款回调先于支付回调到达”真实存在。退款以支付单状态机 + 渠道单号为准，不比较时间。
  • 掉单：本地无支付单但渠道已扣款。定时任务拉渠道账单反向补单，对账 SQL（③）每日必跑。

扩展点

  • 支付单按 pay_no 分表，或按月归档已完成单；pay_idempotent 只保近期数据，过期清理（它没有业务含义，仅是防重闸门）。
  • 多渠道路由、聚合支付层的建模（渠道配置表、费率表）在此基础上追加，支付单增加 channel_mch_id 字段即可。

3. 购物车（cart_item）

适用：C 端商城”先逛后买”链路。购物车的核心矛盾是：登录前也要能用（游客态），登录后不能丢（持久化）。

业务与数据关系

选型对照：

形态 载体 适用 取舍
行存 MySQL cart_item 登录用户 可靠、可分析、跨端同步；写频度中等可承受
游客态 Redis Hash / localStorage 未登录用户 高频写零成本，但不持久、不能做分析
生产主流 Redis 为主 + 行存兜底 全量用户 加车走 Redis，异步落库；登录合并时两份都在

DDL

核心查询

常见坑

  • 合并用覆盖不用累加：游客加 2 件、账号里已有 1 件，登录后变成 2 件丢 1 件。必须 qty = qty + new.qty。
  • qty 无上限：恶意脚本把单行 qty 刷到百万，结算页算崩。LEAST(qty + new.qty, 99) + 应用层限制每车 ≤ 50 行。
  • 只在加车时校验库存：加车 ≠ 买到，结算与下单必须重新校验（第 4 节）。
  • SKU 失效不清：下架 SKU 长期躺在车里，结算页报错。定时任务或惰性标记失效行。

扩展点

  • 用户量大后购物车天然偏读写均衡的 KV 模型：Redis 为主存储（Hash + TTL），行存只作可靠兜底与营销分析数据源。
  • 大促前按”未结算且加车超 30 天”做清理与推送召回，任务是按 updated_at 游标分批跑。

4. 库存扣减与秒杀（sku_stock）

适用：一切”不能多卖”的场景——电商现货、秒杀、抢券、抢座。库存建模的全部难度都在并发写一张热点行。

业务与数据关系

DDL

核心查询（防超卖三招对照）

常见坑

  • 先 SELECT 判余量再 UPDATE：两个请求同时读到”剩 1 件”，各自放行，超卖。判与扣必须同一条 SQL（方案①②都满足）。
  • 方案② 高竞争自旋风暴：热门 SKU 上百并发互相踢版本号，重试刷爆 DB。冲突多时退回方案①，或直接上方案③。
  • 方案③ 双写不一致：MQ 丢消息 = 少卖（Redis 扣了 DB 没扣），重复消费 = 多卖。消费必须幂等（bizNo 唯一键），对账任务兜底。
  • 口径混乱：下单锁 stock_locked、支付才真正扣，但回补逻辑漏了”已支付取消走退款而非回补”。状态机（第 1 节）驱动库存动作，不要裸写。
  • 防超卖靠应用锁 / 分布式锁：能做但把简单行锁复杂化；DB 条件 UPDATE 本身就是正确的锁。

扩展点

  • 热点 SKU 库存分桶：(sku_id, bucket_no, stock) 拆 N 桶，随机写桶摊平行锁竞争，可用库存 = SUM(各桶)。
  • 秒杀常态化后 Redis 预扣为主、DB 异步落库为辅，DB 里的 sku_stock 退化为最终一致的账本。
  • 库存流水（入库 / 锁定 / 回补 / 扣实）落表后可复用第 8 节的”流水对账”套路。

5. RBAC 权限（四表 + 两关联表）

适用：后台管理、多角色 SaaS。RBAC 的价值是”人不动、动角色”，但只建三表（无资源 / 无数据权限）是最高频的半成品。

业务与数据关系

功能权限（能不能调这个接口）与数据权限（能看到哪些行）分开建：前者靠关联表，后者靠 data_scope 一个字段驱动查询条件拼装。

数据权限 scope 落地细节

一句话：scope 只负责「往业务 SQL 里拼什么 WHERE」——落地四步：求生效 scope → 四种翻译 → 性能兜底 → 单点拼装。

前置表：部门与用户归属（与上面六表配套）

第一步：求「生效 scope」——多角色取最宽

第二步：四种 scope 的完整翻译（以订单列表接口为例）

第三步：性能兜底——scope=3 别每个请求都跑递归

第四步：单点拼装——业务代码不许手拼

验收自查

常见坑

  • JOIN 不过滤 status：停用的角色 / 权限仍授出能力。上面①②的 r.status = 1 AND p.status = 1 不是装饰。
  • 前端隐藏按钮 = 鉴权：接口必须服务端再校验一遍（②），F12 一开前端控制形同虚设。
  • 权限缓存改完不失效：改角色权限后用户还带旧权限跑半天。缓存键带 role_id 版本号，或改权限即删相关缓存。
  • 关联表无唯一键：user_role 重复插入同一授权，①里 DISTINCT 掩盖了脏数据，权限管理页却翻倍。
  • 数据权限只在列表页生效：导出、详情、统计接口忘了拼同样的 WHERE，越权拖库。

扩展点

  • 用户量大：①的结果整段缓存 Redis（TTL + 变更主动失效），DB 只在缓存 miss 时 JOIN。
  • 多租户：所有表加 tenant_id，唯一键全部升级为 (tenant_id, ...) 前缀。
  • 组织数据权限的”本部门及以下”依赖树查询性能，见第 6 节选型。

6. 组织架构树（邻接表 / 路径枚举 / 闭包表）

适用：部门、类目、地区等一切树形数据。树建模的坑不在”建出来”，而在”查子树”和”移动子树”两件事上。

业务与数据关系

DDL（三种方案）

核心查询（查子树三方案对比）

选型结论：

方案 查子树 查全部祖先 移动子树 空间 / 写放大 适用
邻接表 递归 CTE（MySQL 8 原生） 同样递归 改一个 parent_id，最简单 最小 默认首选，层级浅、结构稳定
路径枚举 LIKE 前缀，最快 解析 path 字符串 重写子树所有行的 path path 变长，深度受限 读多写少、按部门筛业务数据
闭包表 JOIN，任意深度最优 JOIN 反查 重写子树全部组合 行数 O(n·深度)，写放大最大 深层树 + 频繁任意层级查询

结论：默认邻接表 + 递归 CTE；需要高频”按部门过滤业务数据”时给业务表冗余一个 path 列；两者不够再上闭包表。

常见坑

  • 应用层循环查库拼树（N+1）：每层一个 SELECT，十层树查十次。递归 CTE 一次取全。
  • 路径枚举移动子树漏改后代：把 40 挂到别的父节点，只 UPDATE 了 40 自己的 path，40 的子树全部变孤儿。移动必须 UPDATE ... JOIN 重写整棵子树 path。
  • 闭包表忘插自身行（depth=0）：查询结果永远少自己，反查祖先也少一层。插入节点时自身行与祖先行同一事务写全。
  • 尾斜杠约定丢失：path 存 1/40 不存 1/40/，LIKE '1/4%' 会匹配到 1/40/。约定尾斜杠 + 按尾斜杠 LIKE。
  • parent_id 无索引：递归 CTE 每层靠 parent_id 找孩子，没索引整树全表扫。

扩展点

  • 部门树通常几千行以内，不需要分表；先把递归 CTE 的索引做对。
  • 超大树 / 多租户：所有方案加 tenant_id 前缀索引；跨租户绝不共享节点。
  • 树变更审计：parent_id 变更记流水（who / when / from / to），组织调整回溯全靠它。

7. 收货地址（user_address）

适用：电商 / O2O 用户的地址簿。”默认地址”是唯一性约束设计里最经典的一道题。

业务与数据关系

DDL

生成列两个硬规则：只能引用同表中先于它定义的列（所以 default_uk 放在 is_default 之后）；表达式必须确定性（IF 可以，NOW 不行）。语法要求 MySQL 5.7+，本文按 8.0。

核心查询

常见坑

  • (user_id, is_default) 唯一键误用：如 ER 段所述，0/1 直接做唯一键把”多个非默认地址”禁掉了，业务直接不可用。
  • 两步更新无并发兜底：先取消旧默认再设新默认的两条 UPDATE 若无唯一键兜底，两个并发请求可交错出双默认或零默认。生成列唯一键就是兜底。
  • 删除默认地址后无默认：下单页拿不到默认地址。删除默认后按”最近使用”自动补位，或产品上强制选择。
  • 手机号明文可逆加密过度设计：地址表手机号通常脱敏展示（138****0000）+ 权限控制，加密存储要评估检索需求。

扩展点

  • 地址量与用户同量级（人均几条），按 user_id 哈希分表即可，生成列唯一键在分片内依然成立。
  • 省市区编码规范化：存 region_code（国标行政区划码）而非纯文本，配合字典表防脏地区数据。

8. 钱包账务（wallet_account / wallet_flow）

适用：余额、积分、虚拟币——一切”钱”的模型。铁律只有一条：余额只是流水推导出的缓存，账本才是事实。

业务与数据关系

DDL

核心查询

常见坑

  • 余额 UPDATE 不带 WHERE balance >= n：并发扣款双双通过判断，余额变负。条件更新 + 影响行数判断。
  • 退款只加余额不写流水：账面看似对，对账必然 diff ≠ 0，且无从审计。任何余额变动必须有一条流水。
  • 手工 UPDATE balance 改账：”补 10 块钱”直接改余额——账本从此不可信。调账也走流水（biz_type=5），误操作后的恢复手段见数据库备份与恢复。
  • 对账任务一次全表 SUM：百万账户 × 千万流水一次跑完，主库先崩。按 id 游标分批，放从库跑。
  • balance_after 不存：出问题时只有”账不平”没有”第一现场”，排查成本翻十倍。

扩展点

  • 流水按月分表（wallet_flow_202610）+ 冷数据归档数仓；账户按 user_id 分片——单账户操作不跨片，天然契合。
  • 风控与审计：流水异步入 ES，支持”按商户 / 按时段”的反查维度，不打主库。
  • 大额 / 高频账户加 version 乐观锁二级校验，或账户级互斥（同第 4 节思路）。

9. 优惠券（coupon_template / user_coupon）

适用：营销发券、领券中心、下单核销。优惠券 = “库存问题”（防超发）+ “状态机问题”（未用/已用/过期）的组合体。

业务与数据关系

DDL

核心查询

常见坑

  • 扣 issued_count 与插 user_coupon 不同事务：先插券后扣计数，撞唯一键回滚了券却没回滚计数（或反之），库存口径漂移直到超发。必须同事务 + 任意一步失败全部回滚。
  • 核销只看 status = 1：过期批任务是异步的，任务延迟期间”过期券”仍带 status=1 被核销。核销必须同时校验 expire_at > NOW()（③）。
  • 每人限领 N 张时误用唯一键：(user_id, template_id) 唯一键只支持限领 1 张；N>1 要去掉唯一键，用”领取记录计数 + 条件 INSERT”控制。
  • 过期任务一把梭：一次 UPDATE 千万行，长事务 + 主从延迟爆炸。分批（④）。
  • 模板信息冗余缺失：user_coupon 不冗余优惠金额，模板下线后”我的券”页 join 不出金额。可在券行冗余 title / 金额快照（与第 1 节订单明细快照同理）。

扩展点

  • 大促秒发：Redis 预扣模板库存 + MQ 异步落库（同第 4 节方案③），issued_count 退化为最终一致账本。
  • user_coupon 按 user_id 分表：uk_user_template 含分片键在分片内仍成立；模板维度的统计走数仓。
  • 券码用带校验位的随机串而非自增 ID，防遍历核销。

10. 关注 / 点赞与计数（user_relation / like_record / content_counter）

适用：社区、内容平台的关系链与互动数据。核心矛盾：关系要精确去重，计数要扛住热点读，两者天然冲突。

业务与数据关系

DDL

核心查询

常见坑

  • 点赞接口无唯一键：连点 / 重放插入多行，计数虚高且无法校准溯源。uk_post_user 是第一道闸。
  • 计数不做影响行数判断：INSERT IGNORE 影响 0 行（已赞过）仍 +1，重复点赞刷计数。
  • 热点行锁竞争：大 V 发帖瞬间上万写 content_counter 同一行。DB 只做兜底，高频计数走 Redis INCR 攒批回写（见Redis 缓存架构）。
  • 实时 COUNT(*) 撑列表页：百万行内容表每次互动都 COUNT，列表页全慢。读 counter，写 counter + 校准。
  • 粉丝列表只建了正向索引：idx_followee_id 缺失时”看粉丝”全表扫，关系表是先有的”我关注的人”查询场景。

扩展点

  • 关系表按 follower_id 分表（”我的关注列表”最高频）；粉丝维度查询量大时异构一份按 followee_id 分片的副表，或推拉结合做 fan-out。
  • 点赞冷热分离：90 天前的点赞归档，校准任务跨”在线表 + 归档表”合并口径。
  • 计数校准从”全量 COUNT”演进为”增量 binlog / 消息对账”，控制扫描成本。

12. 常见误用与陷阱

坑 现象 / 后果 解法
唯一键列可空 NULL 不参与唯一性，可无限重复（如邮箱、幂等键）去重失效 要求唯一的列 NOT NULL；”部分唯一”用生成列补位（第 7 节）
余额直接 UPDATE 无流水 对不上账、审计断档、无法追责 余额=流水推导，同事务写流水 + 更新余额（第 8 节）
(user_id, is_default 0/1) 当唯一键 第二条非默认地址插不进，约束方向反了 生成列 default_uk：默认=user_id，否则 NULL（第 7 节）
状态机更新无条件 并发下”取消”覆盖”已支付”，资金资损 UPDATE 带 旧状态 AND version=?，判断影响行数
软删除破坏唯一键 is_deleted 0/1 方案：死行占住唯一键，同邮箱无法重新注册 方案A deleted_at：唯一键 (email, deleted_at)，活跃行 deleted_at 固定占位值（如 ‘1970-01-01’）、删除置当前时间戳——活行仍唯一、死行互不冲突；方案B 唯一键不含软删列 + 应用层查重。flag 方案实现最简但挡重建，deleted_at 方案一行索引兼容
生产滥用外键 FOREIGN KEY 级联锁放大、大表 DDL 卡死、分库分表不可用 开发期可用外键保一致；生产关外键，靠应用层事务 + 定期对账
先 SELECT 判断再 UPDATE 竞态窗口内超卖 / 超发 条件 UPDATE + 影响行数判断（第 4 / 9 节）
金额用 FLOAT / DOUBLE 汇总差几分钱且难复现 DECIMAL(18,2)，禁浮点
状态存 VARCHAR(‘PAID’) 索引膨胀、易拼错、改文案要刷全表 TINYINT + 中文 COMMENT + 字典表
深分页 LIMIT 100000,20 扫描后丢弃，越翻越慢 游标分页：WHERE id/created_at < 上页末值
ON DUPLICATE KEY 全字段覆盖 重复请求把数量 / 状态改回旧值 只更新必要列（qty 累加）并设上限（第 3 节）
列表页实时 COUNT(*) 大表每次互动全扫，读性能崩塌 计数冗余表 + 校准任务（第 10 节）
