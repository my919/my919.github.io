MongoDB：索引、聚合与模式设计

发表于 2026-05-01 更新于 2026-10-29 分类于 数据库 本文字数： 8.5k 阅读时长 ≈ 8 分钟

MongoDB：索引、聚合与模式设计

概念基础

  1. MongoDB 慢查询九成是索引问题：无索引的 find 是全集合扫描（COLLSCAN）；建对索引变成 IXSCAN，与关系库的「先看执行计划」哲学一致。
  2. ESR 原则定复合索引字段序：Equality（等值）→ Sort（排序）→ Range（范围），顺序排对一条复合索引能同时服务过滤与排序。
  3. 聚合管道是 MongoDB 的「SQL+ETL」：$match → $group → $sort → $project ... 流水线处理，能下推的尽量下推（先 $match 后 $group）。
  4. 模式设计决定性能上限：文档模型核心取舍是内嵌（embed）还是引用（reference）——按「一起读写就内嵌、各自更新就引用」判断。
  5. explain 是证据不是感觉：executionStats 里的 totalKeysExamined / totalDocsExamined / nReturned 三值关系直接给出诊断。

本章承接 第一章：MongoDB 概述与入门 的 CRUD 与 MongoDB：Docker 部署实践 的环境；mongosh 语法按 MongoDB 8.0 官方文档书写（沙箱无实例，未逐条运行验证）。

一、explain：诊断查询

三个关键数字：

字段 含义 健康标准
nReturned 实际返回条数 —
totalKeysExamined 扫过的索引条目 接近 nReturned
totalDocsExamined 扫过的文档数 接近 nReturned（远大=回表浪费）

同时确认 winningPlan 里是 IXSCAN 而非 COLLSCAN；SORT_STAGE 出现说明排序没吃到索引（内存排序 32MB 上限会直接报错）。

二、索引体系

实践要点：

  • 每个额外索引都拖慢写入——索引不是越多越好，按真实查询建。
  • db.orders.getIndexes() 盘点存量；低效索引用 dropIndex 清理。
  • 大集合建索引用后台滚动构建（4.2+ 默认后台方式），避开写入高峰。
  • 最左前缀同样适用：{ userId, status, createdAt } 可服务 userId 与 userId+status 的查询。

三、聚合管道进阶

管道优化口诀：

原则 说明
$match/$limit 放最前 能被索引下推，后面的阶段数据越少越好
$project 砍字段 减少内存与网络传输
$group 用 _id: null 全表聚合（配合 $facet 一次算多组指标）
允许近似 超大集合统计可接受秒级误差时用 $sample 或预聚合

$lookup 进阶：pipeline 形式与性能

基础形式只能做等值关联；pipeline 形式能在关联侧再过滤、排序、截断：

性能三要点：

  • 被关联集合的 foreignField 必须有索引（上例是 orders.userId），否则每个外层文档触发一次 COLLSCAN，复杂度 O(N×M)。
  • $expr 负责把 let 变量与关联侧字段绑定；不等值条件（范围、数组包含）只有 pipeline 形式能写。
  • 只需「是否存在」时，用 pipeline + $limit: 1 + $project: { _id: 1 } 代替全量拉取。

$addFields 与 $replaceRoot：重塑文档

$addFields = SQL 的派生列；$replaceRoot（别名 $replaceWith）常作为管道收尾，把结果整理成下游直接可用的结构。

$bucket 与 $facet：分桶与多路统计

$facet 一次扫描产出多份报表，是仪表盘神器；$bucket 按边界分桶（$bucketAuto 自动均分）。注意 $facet 各子管道无法走索引且共享 100MB 内存上限，超大集合改用预聚合。

四、模式设计：内嵌还是引用

判断口诀：

场景 选择
1:1 或 1:少量（生命周期一致） 内嵌
1:多且子文档无限增长（评论、日志） 引用（或「内嵌最近 N 条 + 冷数据独立集合」）
多对多 引用
内嵌文档 16MB 上限 逼近上限必须拆

常见增强：$lookup 慢的高频关联可冗余一份 userName 到订单文档（写入时双写），用读时免 JOIN 换写时多一步——文档模型下的「反范式」是常规操作。

五、四个常用 Schema 设计模式

官方 Schema 设计模式清单里，业务系统最常用这四个：

1. Computed Pattern（预计算）

读多写少 + 重复计算贵时，把结果写时算好存下来：商品文档冗余 avgRating、reviewCount，每次评价写入时 $inc / $avg 重算，读详情页零计算。代价：写多一步、口径变更要回填历史。

2. Bucket Pattern（分桶）

时序数据（IoT 指标、行情、访问日志）一条一个文档会爆索引与文档数——按时间桶聚合：

收益：索引条目下降几个数量级，且「查某时段」的访问模式天然匹配桶边界。

3. Subset Pattern（子集）

文档太胖导致工作集（working set）放不进内存？把高频字段留在主文档（文章列表只需标题/摘要/作者），低频大块拆到独立集合（正文、历史版本）——列表查询不再拖着 KB 级正文跑。

4. Attribute Pattern（属性模式）

各品类属性差异大（手机有「屏幕尺寸」、衣服有「尺码」），为每种属性建索引不现实——统一存成键值数组：

选型速记：重复计算贵用 Computed、时序用 Bucket、文档过胖用 Subset、稀疏属性用 Attribute——模式可叠加，不必单选。

六、事务与批量写入

单文档天然原子：把需要原子性的关联数据内嵌进同一文档，很多「事务需求」就直接消失了——这是文档建模的隐藏红利。

七、Change Stream：监听数据变更

「数据一变就通知下游」（刷缓存、发消息、同步搜索引擎）不必轮询——Change Stream 基于 oplog 实时推送变更，要求副本集模式（单节点副本集即可，见 MongoDB：Docker 部署实践）：

要点：

  • watch(pipeline) 可用聚合语法预过滤，只推关心的变更，省网络与处理量。
  • fullDocument: "updateLookup" 让 update 事件也带上变更后的完整文档（默认只有增量字段）。
  • 生产用法：持久化 resumeToken，重启后用 resumeAfter 断点续传不丢事件；驱动断线自动重试。
  • 跨系统、大数据量的管道场景改用 Debezium / Kafka Connector；应用内轻量监听 Change Stream 足够。

本章小结

要点 结论
explain 看 COLLSCAN→IXSCAN；DocsExamined ≈ nReturned 才健康
复合索引 ESR（等值→排序→范围）定字段序；索引数量克制
特殊索引 TTL 管过期数据、partialFilterExpression 省空间、多键自动支持数组
聚合 $match 尽早、$project 砍字段；复杂关联用 $lookup pipeline 形式且 foreignField 必有索引
报表阶段 $addFields 派生列、$replaceRoot 收尾压平、$facet 一次多份报表、$bucket 区间分桶
模式设计 一起读写就内嵌，独立增长就引用；单文档原子性替代小事务
设计模式 Computed 预计算、Bucket 时序分桶、Subset 文档瘦身、Attribute 稀疏属性
Change Stream 基于 oplog 的变更推送（需副本集）；记 resumeToken 断点续传
