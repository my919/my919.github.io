PostgreSQL：存储引擎与表访问方法

发表于 2026-05-03 更新于 2026-10-29 分类于 数据库 本文字数： 6k 阅读时长 ≈ 5 分钟

PostgreSQL：存储引擎与表访问方法

概念基础

  1. 表访问方法（Table Access Method）：PostgreSQL 12+ 把「表数据如何组织与读写」抽象为可插拔接口，建表时可用 USING 指定，默认即 heap——这是 PostgreSQL 语境里最接近 MySQL「引擎」的概念。
  2. 堆表（Heap）：行按写入顺序无序堆放在页中，用 tid（块号 + 行号） 定位；索引里存的是 tid，查数据通常要「索引 → 回表」。
  3. MVCC 是配套设计：行头维护 xmin / xmax 版本信息，更新与删除产生新版本 / 死元组，由 VACUUM 回收——这直接决定了 PostgreSQL 的性能调优姿势。
  4. 与 MySQL 的本质差别：MySQL 建表时选 ENGINE=InnoDB，PostgreSQL 没有这个开关：统一内核 + 统一 heap，列存、分片等需求走扩展与架构层，而不是换「引擎」。

〇、建表与数据类型入门（DDL 速览）

保留字陷阱：order、user 等是保留字，直接当表名会在建表/查询时报语法错误——避开保留字，或统一带双引号（"order"）。

JSONB 的查询与索引写法见 PostgreSQL：高级查询 与 PostgreSQL：索引与性能优化；下面进入正题：这些数据到底怎么存。

一、表数据默认怎么存：Heap（堆表）

  • 普通 CREATE TABLE 默认即 heap 表：行以堆页存放，通过 tid（块号 + 行号） 定位。
  • MVCC 在元组头维护版本信息（xmin / xmax 等），更新与删除产生新版本/死元组，依赖 VACUUM 回收（见 PostgreSQL：索引与性能优化）。
  • 与 InnoDB 聚簇索引即整表不同：PostgreSQL 主键索引是二级索引，堆上存行，主键查找通常「索引 → 回表 tid」。

1. 堆页内部结构

每个堆页默认 8KB（编译期 BLCKSZ），从前往后分四段：

  • PageHeaderData：LSN、校验和、空闲空间起止位置等页级元数据。
  • ItemId（行指针）数组：定长 4 字节，记录页内每个元组的偏移与长度——tid 里的「行号」实际是这个数组的下标，索引指向行指针而非物理位置，所以页内整理（如 HOT 链修剪）不必改索引。
  • 元组区：从页尾向前生长，每行带 23 字节行头（xmin / xmax / ctid / 标志位等）。

2. 行头与 MVCC 版本链

每行元组头部的关键字段：

字段 作用
xmin 创建该行版本的事务 ID
xmax 删除/更新该行版本的事务 ID（0 表示存活）
ctid 指向下一版本的 tid（更新形成版本链）
t_infomask 标志位：事务是否已提交、行是否被锁等

一次 UPDATE = 插入新元组 + 把旧元组 xmax 置为当前事务 + ctid 指向新位置。这就是「更新在 PG 里本质是新增一版」的物理含义，也是死元组与膨胀的来源。

二、TOAST：大字段的行外存储

8KB 页放不下的超长字段（text、大 jsonb、bytea）由 TOAST（The Oversized-Attribute Storage Technique） 接管：超阈值（约 2KB）的值被压缩和/或切片存入附属 TOAST 表，主表行里只留指针。

每张宽表自动挂一张 pg_toast.pg_toast_<oid> 附属表：

四种存储策略（建表时可按列指定）：

策略 压缩 行外存储 适用列
PLAIN 否 否 短字段、int 等定长类型（默认）
EXTENDED 是 是 超长 text / jsonb（变长类型默认）
EXTERNAL 否 是 已压缩的二进制（图片、已 gzip 数据）
MAIN 是 尽量不 中等长度、想留在主表的字段

性能含义：SELECT 不碰 TOAST 列时不读 TOAST 表（天然列裁剪）；但更新 TOAST 列会产生整个新副本——频繁更新的超大字段要考虑拆分表。

三、HOT 更新与 FILLFACTOR

HOT（Heap Only Tuple）更新：当 UPDATE 不改任何索引列且同页有空位时，新元组直接放同页、索引条目不动——省掉一次索引维护 IO，热点行更新快很多。

参数 含义 建议
fillfactor=100（默认） 页塞满才开新页 只增不改的表（日志、数仓）
fillfactor=80~90 预留 10~20% 空间 高频 UPDATE 且不改索引列的表
改了索引列的 UPDATE 无法 HOT 设计上把「状态字段」与「索引字段」分离

判断 HOT 是否生效：

hot_pct 低 + 表膨胀快：检查是否更新了索引列，或 fillfactor 太满。

四、FSM 与 VM：两个辅助映射

映射 全称 作用
FSM Free Space Map（空闲空间映射） 记录每页剩余空间，插入时快速找页，不用全表翻
VM Visibility Map（可见性映射） 标记「页内所有行对所有事务可见」——Index Only Scan 靠它跳过回表；VACUUM 靠它跳过干净页

实务联动：大批量 UPDATE/DELETE 后 VM 失效 → Index Only Scan 退化为 Index Scan + 回表 → 执行计划里 Heap Fetches 暴涨。跑一次 VACUUM ANALYZE 表名 重建 VM 即恢复（详见 PostgreSQL：索引与性能优化）。

五、表访问方法（Table Access Method）

PostgreSQL 12+ 起，表可指定 USING heap（默认）；理论上可挂自定义表访问方法（需扩展提供）。
生产常见仍是 heap；列存、混存等多在扩展或外部产品（如某些分析型方案）中实现，不等价于 MySQL 换一个 ENGINE 字符串。

六、与「引擎」易混的几个概念

概念 说明
TABLESPACE 表/索引的文件放置位置（如 pg_default），不是另一种行存储引擎。
TOAST 大字段行外存储机制，对用户基本透明。
Foreign Data Wrapper（FDW） 外部表：数据在远程；语法像本地表，语义与本地 heap 完全不同，不是换存储引擎。
内置索引类型 B-Tree、Hash、GiST、GIN、BRIN 等是索引访问方法，不是替换 heap 的「表引擎」。

七、和 MySQL InnoDB 的粗对照（选型沟通用）

话题 MySQL（MySQL引擎.md） PostgreSQL（本文）
建表选「引擎」 ENGINE=InnoDB 等 无；默认 heap + 统一内核
行存与主键 InnoDB 聚簇主键与数据同树 堆行 + 主键索引
并发读写的核心 InnoDB MVCC + 锁 MVCC + 行锁（见 PostgreSQL：并发与 MVCC 入门）

八、WAL：堆页之外的第二套写入

heap 页是「数据落盘的最终形态」，但每次写先走 WAL（Write-Ahead Log）：

  1. 事务修改先在内存缓冲区改页，同时把重做记录追加进 WAL 缓冲区。
  2. COMMIT 时只需 WAL 刷盘（wal_writer / commit 触发 fsync）即算持久——数据页由后台 checkpointer 批量脏写。
  3. 崩溃重启时按 WAL 重放，把未落盘的修改补回数据页。

实务含义：顺序追加的 WAL 远快于随机写数据页——这是 PG 写入性能的根基；WAL 所在磁盘（可用 pg_wal 独立表空间/挂载点）的延迟直接决定提交延迟。

九、分区表：heap 的「水平切片」

声明式分区（PG 10+）把一张逻辑表切成多张物理 heap 子表，每个分区独立享有自己的页、FSM、VM 与索引：

收益 原理
分区裁剪 查询带分区键时只扫命中的子表，等效索引之外的「粗粒度裁剪」
快速归档 DROP TABLE orders_2025_01 或 DETACH PARTITION 秒级删旧数据，不产生死元组
分区级维护 VACUUM / REINDEX 可按分区跑，大表运维粒度变细

取舍：分区数控制在几百以内（过多拖慢规划）；分区键必须出现在所有唯一约束里；查询不带分区键时反而要扫所有分区。

十、实务建议

  1. 学习 PostgreSQL 时少问「用哪个引擎」，多问索引类型、执行计划、VACUUM、隔离级别与锁。
  2. 需要列存、分片、多副本高可用时，在架构层选专用扩展或产品（如 Citus、云厂商数仓、读写分离），而不是在 CREATE TABLE 里找一个 ENGINE 开关。
  3. 版本升级（16 → 17 → 18）会带执行器与优化器演进，「升级引擎」口语上常指升级主版本，与 MySQL 的 ENGINE 不是同一概念。
  4. 写多的表先想 fillfactor 与 HOT，宽表先想 TOAST 策略，只读大表先想 VM 与 Index Only Scan——三个杠杆都长在 heap 结构之上。
