第二章：Docker 部署 MongoDB 实践

发表于 2026-05-01 更新于 2026-10-25 分类于 数据库 本文字数： 9.4k 阅读时长 ≈ 9 分钟

第二章：Docker 部署 MongoDB 实践

概念基础

  1. 为什么用容器跑 MongoDB：一条命令拉起、版本随标签固定、环境与宿主机解耦——本地开发、测试与演示环境的最快路径，也是生产部署的基础单元。
  2. 数据持久化是底线：容器可丢、数据不能丢——必须把 /data/db 挂载到命名卷或宿主机目录，否则容器删除即数据清零。
  3. 初始化语义：MONGO_INITDB_ROOT_* 环境变量只在空数据目录首次初始化时生效；/docker-entrypoint-initdb.d/ 下的脚本同样只在首次初始化执行一次，已有数据卷时不会重复执行。
  4. 三种部署形态：docker run 单容器（最快上手）→ Docker Compose（声明式 + 健康检查）→ Kubernetes（Secret + PVC + 探针，面向集群），按环境复杂度逐级选用。
  5. 与第一章的关系：容器只解决「跑起来」；连接、CRUD、索引等用法见 第一章：MongoDB 概述与入门。

前置条件

本机已安装 docker，并能使用 docker compose（Compose V2 插件，命令为 docker compose；若仍使用旧版独立程序，则将下文中的 docker compose 换成 docker-compose）。

MongoDB 镜像选择

1. 官方镜像（推荐）

  • 仓库：mongo（Docker Hub 官方库，由 MongoDB Inc. 维护）。
  • 常用标签：
    • mongo:8.0：8.x 稳定线，当前主流大版本，驱动与工具链成熟。
    • mongo:7.0：旧稳定线，仍在支持期；mongo:latest 跟踪最新（以 Docker Hub mongo tags 为准）。
  • 生产建议：固定小版本标签（如 mongo:8.0.x）或记录 digest，避免 latest 漂移导致行为变化。

2. 变体说明

需求 说明
认证与 root 同时设置 MONGO_INITDB_ROOT_USERNAME、MONGO_INITDB_ROOT_PASSWORD 时启用超级用户；连接串中 authSource=admin 常指向管理库。
ARM64（Apple Silicon 等） 官方 mongo 多架构镜像一般可直接拉取；若某标签缺架构，换标签或查 Hub OS/ARCH。
极简/定制 社区有 bitnami/mongodb 等，环境变量与数据路径与官方不同，切换镜像时需对照该镜像文档。

3. 初始化脚本

/docker-entrypoint-initdb.d/ 下 *.js、*.sh 仅在首次初始化空数据目录时执行；已有数据卷时不会重复执行。

1Panel（推荐）：在 Linux 宿主机上若希望少手写命令、仍以容器方式跑 MongoDB，可先安装 1Panel（开源 Linux 运维面板），在 「应用商店」 中选择 MongoDB 一键部署：由面板管理镜像版本、数据持久化、27017 端口、MONGO_INITDB_ROOT_* 与（可选）备份，启停与日志可在界面查看。与下文 docker run / Compose / K8s 的环境变量、/data/db 与 /docker-entrypoint-initdb.d 语义对齐或排障时，自单容器一键部署一节起仍可作对照。适合单台 VPS、家庭服务器等「一台机子上稳态跑库」的场景。

备份与恢复：mongodump / mongorestore

逻辑备份直接用容器内自带的工具，把备份目录挂到宿主机：

要点：

  • --gzip --archive=<文件> 产出单文件压缩归档，便于转存对象存储；不加 --archive 则输出目录结构。
  • 定时备份用宿主机 cron / 计划任务 包一层 docker exec 即可；恢复演练（还原到临时库抽查文档数）必须定期做。
  • 需要**时间点恢复（PITR）**级别能力时，要用副本集 + mongodump --oplog 或 Ops Manager / 云厂商备份，纯单机 dump 只是快照。

WiredTiger 缓存与内存限额

WiredTiger 默认缓存为 0.5 × (RAM - 1GB)（下限 256MB）。容器里若设了内存 limit，新版镜像能识别 cgroup 限制，但显式声明更稳——缓存约占容器限额的 一半，剩下留给操作系统页缓存与连接开销：

判据：db.serverStatus().wiredTiger.cache 里 bytes currently in the cache 长期顶满且 unmodified pages evicted 高 → 缓存偏小；反之容器频繁 OOMKilled → 缓存或限额配比失衡。

部署方式速查

项 说明
前置 已安装 docker 与 docker compose（或 docker-compose）
镜像 优先官方 mongo:8.0 / 固定补丁标签；mongosh 与镜像主版本对齐
单容器 mkdir 后一条 docker run ...
Compose 保存 docker-compose.mongo.yml 后 docker compose -f ... up -d
Kubernetes 保存 mongo-k8s.yaml 后 kubectl apply -f ...
副本集 --replSet rs0 启动 + rs.initiate(...) 一次初始化，解锁事务与 Change Stream
备份 docker exec ... mongodump --gzip --archive，定时用 cron 包一层
内存 --wiredTigerCacheSizeGB 显式设容器限额的一半左右

生产环境请配合备份、监控、网络策略与 TLS；Secret 建议对接 External Secrets / Sealed Secrets 等管控流程。

本章小结

要点 结论
镜像选择 官方 mongo:8.0 起步，生产固定补丁标签或 digest，防 latest 漂移
单容器 mkdir 建卷目录后一条 docker run，MONGO_INITDB_* 设定 root 与初始库
Compose docker-compose.mongo.yml + .env 管理敏感项，healthcheck 探活
Kubernetes Secret + PVC + Deployment（Recreate）+ 探针，一条 kubectl apply
副本集 单节点 --replSet + rs.initiate 解锁事务/Change Stream；多成员加 keyFile（权限 400）
备份恢复 mongodump --gzip --archive 出单文件归档，mongorestore 配 nsFrom/nsTo 安全演练
内存 WiredTiger 缓存默认 (RAM-1GB)/2，容器中显式 --wiredTigerCacheSizeGB 更稳
生产提醒 数据卷 + 备份 + 认证 + TLS 一个都不能少；副本集/分片交给 Operator

库跑起来之后是查询工程：第三章：MongoDB 索引、聚合与模式设计 覆盖 explain 诊断、ESR 索引与文档建模；复制集、分片与 Operator 运维可按需深入。
