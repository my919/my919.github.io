第一章：ClickHouse 列式存储入门

发表于 2026-05-01 更新于 2026-10-25 分类于 数据库 本文字数： 5.7k 阅读时长 ≈ 5 分钟

第一章：ClickHouse 列式存储入门

概念基础

  1. 列式存储：ClickHouse 按列组织数据，SELECT avg(price) 只读 price 一列，IO 远小于行存全表扫描——这是它分析查询快的根源。
  2. 向量化执行：数据按列块批量进入对 CPU 缓存友好的计算路径，充分利用批量计算，吞吐远高于逐行解释执行。
  3. 专为 OLAP 而生：适合大规模聚合、日志与事件分析；不适合高并发单行点查、频繁小事务更新（OLTP 仍用 第一章：MySQL DDL 语句与表设计入门 等）。
  4. MergeTree 引擎家族：核心表引擎支持分区、排序键、TTL、副本，是绝大多数分析表的底座。
  5. 双协议接入：HTTP 8123（curl、JDBC HTTP、BI 工具）与 Native 9000（clickhouse-client、官方驱动）按场景选择。
  6. 版本基准：本文以 ClickHouse 25.x（2025 年稳定线）语法与行为为准；长期支持版（LTS）每年 3 月、8 月发布，生产建议选 LTS 标签。

1. 为何列存适合分析

  • 按列压缩与读取：SELECT avg(price) 只读 price 列，IO 远小于行存全表扫描。
  • 向量化执行：一批数据在 CPU 缓存友好地计算。
  • 不适合：高并发单行点查、频繁小事务更新（OLTP 仍用 第一章：MySQL DDL 语句与表设计入门 等）。

2. 建库建表

  • PARTITION BY：按月分区，便于 TTL 与删除旧分区。
  • ORDER BY：主键排序键，决定数据在磁盘上的排列与稀疏索引。

3. 稀疏索引：为什么主键不占多少内存

MergeTree 的主键索引不是 B-Tree，而是稀疏索引（Sparse Index）：

  • 数据按 ORDER BY 排序后切成 granule（默认每 8192 行一个）。
  • 索引只记录每个 granule 第一行的排序键值——亿行表的主键索引通常只有几万条，可常驻内存。
  • 查询时先二分查找索引定位到候选 granule 区间，再并行扫描这些 granule——这就是「索引在 ClickHouse 里很轻」的原因。
  • partition：分区键值（如 202605）。
  • part：分区内的物理数据块，后台 merge 会持续把小 part 合成大 part。
  • part 过多会触发 Too many parts 报错——写入批量化是预防关键（排查详见 第三章：ClickHouse 查询与性能调优）。

4. 数据类型选择：省空间就是省时间

ClickHouse 的类型选择直接影响压缩率与扫描速度：

需求 推荐类型 避免
枚举/状态（几十~几万取值） LowCardinality(String) 裸 String
整数 按需选 UInt8/16/32/64 一律 UInt64 浪费空间
金额 Decimal(18, 2) Float64（精度坑）
时间 DateTime（秒）/ DateTime64(3)（毫秒） 字符串存时间
可空 尽量不用 Nullable，用默认值代替 Nullable(String) 压缩差
IP 地址 IPv4 / IPv6 原生类型 String

经验法则：列越窄、基数越低，压缩越狠、扫描越快——LowCardinality 是字符串枚举列的必选项。

常用查询

FINAL、PREWHERE、物化视图（Materialized View） 是生产调优常用手段，需结合表引擎文档使用。

MergeTree 引擎家族（概念）

引擎 用途 典型场景
MergeTree 通用分析表，支持分区、TTL、二级索引 日志、事件明细
ReplacingMergeTree 按排序键去重（后台 merge 时，保留 ver 最大版本） 用户状态快照、订单最新态
SummingMergeTree merge 时把数值列相加（预聚合） 按天累计的指标宽表
AggregatingMergeTree 存储聚合中间状态（-State 函数写入） 物化视图的落表引擎
CollapsingMergeTree 用 Sign 列（1/-1）对冲删除旧行 实时变更流、可撤销统计
VersionedCollapsingMergeTree 带版本号的折叠，解决乱序写入 上游乱序送达的变更数据
ReplicatedMergeTree 以上引擎的副本版，靠 Keeper 协调 生产集群标配

分布式表 Distributed 引擎配合集群配置做水平扩展：本地表存分片数据，Distributed 表路由查询到各分片并归并结果。

引擎选型速记

  1. 明细表永远从 MergeTree（集群用 ReplicatedMergeTree）起步。
  2. 需要「同一 key 只留最新」用 ReplacingMergeTree，但去重只发生在 merge 时，查询要加 FINAL 或 GROUP BY + argMax 兜底。
  3. 需要「写入即聚合」用 AggregatingMergeTree 搭配物化视图，而不是让查询扫明细。

物化视图：写入时预聚合

物化视图（Materialized View） 是 ClickHouse 报表提速的第一手段：数据写入源表时，自动按视图定义的 SQL 算出结果并写入目标表。

要点：

  • 只对新写入生效，历史数据需手工 INSERT INTO ... SELECT 回填。
  • 查询端仍需再聚合一层（merge 时机不定），写完整的物化视图用法见 第三章：ClickHouse 查询与性能调优。

与 Doris / StarRocks 的横向对比

同赛道竞品常被一起评估，粗对照如下（2025 年视角）：

维度 ClickHouse 25.x Apache Doris StarRocks
单机性能 极致（向量化鼻祖之一） 高 高
SQL 兼容 自有方言，功能极多 接近 MySQL 协议 接近 MySQL 协议
JOIN 能力 较弱（右表进内存） 较强 较强（CBO 成熟）
高并发报表 一般（几十 QPS） 较好 较好
生态与资料 最丰富 中文社区活跃 中文社区活跃
运维复杂度 中（Keeper + 分片手工） 较低（FE/BE 自管理） 较低

选型一句话：单表超大规模、写入吞吐优先选 ClickHouse；多表关联 + 高并发报表多，评估 Doris / StarRocks；明细 + 报表混合负载可两者并存，各干各的强项。

与周边系统分工

  • 写入：业务库 → Kafka / 日志采集 → ClickHouse 批量写入（Buffer 表或外部引擎）。
  • 查询：Grafana、Metabase、自研报表；复杂 SQL 注意避免 SELECT * 大宽表。
  • 缓存热结果：短时指标可落 第一章：Redis 概述、安装与 CLI 入门，明细仍在 ClickHouse。

向量化执行：快在 CPU 层面

列存解决的是少读盘，向量化解决的是读进来之后算得快：

  • 批量而非逐行：表达式一次处理一个列块（通常几千行的数组），而不是一行行解释执行。
  • SIMD 指令：sum、count 等聚合经编译生成 AVX2/AVX-512 向量化指令，一条指令算多个值。
  • CPU 缓存友好：列块紧凑连续，预取命中率高；行存的「字段散布在行里」会频繁缓存失效。
  • 多核并行：查询按 granule 拆成任务流，默认吃满 max_threads（= CPU 核数）。

这也是为什么 ClickHouse 对虚机 / 容器限核敏感——CPU 被限到 2 核时，聚合吞吐近乎同比腰斩，容量规划要预留核数。

集群部署概览：ReplicatedMergeTree + Keeper

单机之上，生产最小可信拓扑是 2 分片 × 2 副本：

  1. ClickHouse Keeper（或 ZooKeeper）：3 节点小集群，存副本元数据与日志序号，协调「谁同步谁」；自身用 Raft 选主，独立于数据节点部署。
  2. ReplicatedMergeTree：建表加副本参数，同分片的多个副本通过 Keeper 交换 part 清单、互拉数据，写入任一副本即可。
  3. Distributed 表：建在每个节点上，按 sharding key（如 user_id 哈希）把写入/查询路由到目标分片。

要点：ON CLUSTER 让 DDL 在集群所有节点执行；分片键选基数高、分布均匀的列，避免数据倾斜。完整容器化集群清单见 第二章：Docker 部署 ClickHouse 实践。

生产注意

  • 副本与 Keeper：ClickHouse Keeper（或 ZooKeeper）协调复制与分布式 DDL；Keeper 集群必须奇数节点（3 或 5），与数据节点分开部署。
  • 资源：内存用于 merge 与查询；磁盘顺序写与 merge 压力需监控；CPU 核数直接决定聚合吞吐。
  • 写入纪律：批量写入（每批几万~几十万行），避免高频小批产生海量小 part 触发 Too many parts。
  • 升级：固定版本标签，阅读 Release Notes 中不兼容变更；跨大版本先在测试集群滚动验证。

官方文档：https://clickhouse.com/docs

本章小结

要点 结论
定位 列存 + 向量化执行，面向 OLAP 大规模聚合分析，不适合 OLTP 点查与小事务
建表关键 MergeTree 引擎 + PARTITION BY 分区 + ORDER BY 排序键
索引机制 稀疏索引：granule（8192 行）首行进索引，索引轻、可常驻内存
查询 聚合与 uniq 是强项；FINAL、PREWHERE、物化视图是常用调优手段
引擎家族 Replacing / Summing / Aggregating / CollapsingMergeTree 各司其职，Distributed 做水平扩展
物化视图 写入时预聚合落表，历史数据手工回填，查询端再聚合一层
横向对比 单表极致性能选 ClickHouse；高并发多表 JOIN 报表评估 Doris / StarRocks
生产底线 Keeper（奇数节点）协调副本与 DDL，批量写入防 Too many parts，固定版本升级
