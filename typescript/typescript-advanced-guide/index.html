踩坑点：

  • 只写类型不校验：as User 只是「骗过编译器」，运行时字段照样可能缺失——schema.parse 才是兜底。
  • Schema 与手写 type 双份维护：改一处忘一处，最终类型与真实数据漂移。坚持 z.infer 单一来源。
  • 泛型约束写成 T = any：类型安全瞬间退化成 anyScript。S extends z.ZodTypeAny 才能让 z.infer<S> 正常推导。

7. 常见误用与陷阱

坑 现象/后果 解法
any 滥用 类型系统形同虚设，重构全靠人肉排查 用 unknown + 类型收窄；配 ESLint no-explicit-any 逐步清零
enum 与 const enum 混用 isolatedModules 下编译报错；打包产物可能内联出错 用 as const 对象或字面量联合类型替代 enum
双重断言 as unknown as T 编译器闭嘴，运行时崩在语义之外 写类型守卫 / 判别联合收窄，而不是绕过检查
可选属性当必有属性用 obj.maybe.x 运行时 undefined 报错 optional chaining + noUncheckedIndexedAccess
同名 interface 意外合并 字段莫名多出/冲突，排查困难 业务类型用 type；避免全局作用域同名 interface
泛型递归过深 “Type instantiation is excessively deep” 编译报错 拆中间类型分步推导，或限制递归深度
strict 未全开 隐式 any / null 漏网，线上空指针 strict: true 全开，存量代码用注释渐进修复
