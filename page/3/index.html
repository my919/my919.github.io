组合模式详解（Composite）

发表于 2026-09-14 本文字数： 1k 阅读时长 ≈ 3 分钟

设计模式 · 组合模式

GoF 结构型模式。意图 · 结构 · 透明与安全 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

组合模式（Composite）把对象组织成树形结构，让单个对象和组合对象拥有一致的接口——客户端无需区分”叶子”还是”树枝”，统一处理。

2. 要解决的问题

问题 说明
树形结构普遍 目录树、组织架构、菜单、DOM、文件系统
客户端要区分层级 叶子与容器处理逻辑不同，代码散落 if-else
遍历/操作不统一 求总大小、递归删除要写多套代码

典型场景：文件系统（文件/目录）、公司组织架构（员工/部门）、菜单系统、HTML DOM、JPanel.add(Component)。

3. 结构（角色）

两种风格：

风格 说明
透明式 接口含 add/remove（叶子也实现，抛异常）——客户端更统一
安全式 容器独有 add/remove——类型安全，客户端需判断

4. 代码实现（文件系统）

递归结构：getSize()/delete() 都是”如果有子节点就委托，没有就自己处理”——叶子与容器的统一协议。

5. 应用场景

场景 说明
文件系统 文件/目录统一操作
组织架构 员工/部门递归统计
UI 组件 Swing JPanel（容器也是 Component）
DOM 树 元素节点统一遍历
权限树 菜单/权限递归渲染

6. 优缺点

优点 缺点
统一叶子与容器，客户端简单 树结构可能很深（递归性能/栈溢出）
天然支持递归操作 透明式接口对叶子不友好（抛异常）
符合开闭（加叶子类型易） 结构破坏后难维护（如循环引用）
层次清晰 不适合层级关系不明显的场景

7. 与其他模式对比

模式 区别
装饰器 装饰器也是树结构，但只一个”装饰者+被装饰者”链
迭代器 常配合组合模式遍历树（迭代器遍历）
访问者 访问者可在组合树上执行操作，不改节点类

设计模式 · 桥接模式

GoF 结构型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与适配器对比。代码带详细注释。

1. 模式概述（意图）

桥接模式（Bridge）把抽象部分与实现部分分离，让它们可以独立变化——用组合代替继承，解决”多维度变化”的类爆炸问题。

2. 要解决的问题

经典例子：消息系统有类型维度（普通/紧急/加急）和渠道维度（短信/邮件/企微）。用继承组合，类数 = 类型 × 渠道 = 9 个类：

桥接解法：9 个类 → 3 个类型类 + 3 个渠道类（组合桥接）。

3. 结构（角色）

4. 代码实现

类数公式：类型 N 个 + 渠道 M 个 = N+M 个类（而不是 N×M）。

5. 应用场景

场景 说明
多维度变化的业务 消息(类型×渠道)、支付(业务×渠道)、通知
跨平台 JDBC（驱动实现）× 业务抽象
UI 控件 形状 × 颜色（JDK AWT 的经典例子）
驱动架构 抽象 API × 平台驱动实现

6. 优缺点

优点 缺点
消除继承爆炸（N×M → N+M） 抽象与实现都要维护两套层级
两个维度独立扩展 需要先识别出”两个变化维度”
符合开闭原则 没有多维度变化时是过度设计
实现细节对抽象隐藏 理解门槛略高

7. 与适配器对比

模式 区别
适配器 解决”接口不匹配”（事后补救）
桥接 解决”维度独立变化”（事先设计）
策略 策略只变算法；桥接抽象+实现双维度

适配器模式详解（Adapter）

发表于 2026-09-14 本文字数： 1k 阅读时长 ≈ 3 分钟

设计模式 · 适配器模式

GoF 结构型模式。意图 · 结构 · 类适配器与对象适配器 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

适配器模式（Adapter）把一个类的接口转换成客户端期望的另一个接口——让不兼容的接口能一起工作，如同电源转换插头。

2. 要解决的问题

问题 说明
新旧系统对接 老系统的接口与新技术栈不匹配
第三方库适配 库的 API 与业务需要的形式不同
无法改源码 遗留代码/外部库不能直接改

典型场景：接入第三方支付（各家 API 不同 → 统一成自己的接口）、老系统 ESB 对接、Arrays.asList()（数组 → List 的适配）、日志门面 slf4j 适配 log4j/logback。

3. 结构（角色）

两种实现方式：

方式 原理 适用
对象适配器（推荐） 组合：Adapter 持有 Adaptee 通用，解耦
类适配器 继承：Adapter extends Adaptee 需覆写 Adaptee 行为时才用

4. 代码实现（对象适配器）

5. 应用场景

场景 说明
第三方 SDK 统一 支付/短信/OSS 各家 API 统一成自家接口
老系统对接 遗留 ESB/数据库适配新架构
JDK 实例 Arrays.asList()、InputStreamReader（字节流→字符流）
日志门面 slf4j → logback/log4j 适配器
数据格式转换 旧数据格式适配新模型

6. 优缺点

优点 缺点
让不兼容接口协同工作 过度使用导致”包装套包装”难排障
客户端解耦（只认目标接口） 适配层增加调用链
无需修改被适配者 需要理解双方接口差异
可插拔（换适配器即换实现） 适配逻辑要写好转换与异常

7. 与其他模式对比

模式 区别
装饰器 装饰器增强功能不改接口；适配器转换接口
代理 代理控制访问（同接口）；适配器转接口
门面 门面聚合多个接口为高层接口；适配器一对一转换

设计模式 · 建造者模式

GoF 创建型模式。意图 · 结构 · 链式调用 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

建造者模式（Builder）把一个复杂对象的构造过程与表示分离：同样的构建过程可以产出不同的表示。即把”构造步骤”封装在 Builder 里，一步步组装。

2. 要解决的问题

问题 说明
构造参数过多 十几个参数的构造函数难以使用、易传错
参数有依赖 有些参数有默认值、有必填校验
构造过程复杂 分步骤组装，直接 new 做不到

典型场景：StringBuilder、Lombok @Builder、Spring BeanDefinitionBuilder、配置对象（HTTP 客户端、Kafka 生产者）、对象不可变 + 可选参数。

3. 结构（角色）

4. 代码实现（链式建造者，最常用形式）

进阶写法：接口 + 多个 Builder 实现（Director 场景，如”标准配置””严格配置”两套构建流程）：

5. 应用场景

场景 说明
配置对象 HTTP 客户端、连接池、Kafka 生产者配置
复杂 DTO 分步骤组装请求对象
StringBuilder 字符串分步拼接（JDK 实例）
Lombok @Builder 编译期自动生成建造者
测试数据构造 快速构造各种状态的测试对象

6. 优缺点

优点 缺点
参数名化，可读性强（不再传错位） 需要额外 Builder 类（代码变多）
支持默认值与部分配置 简单对象用 Builder 是过度设计
不可变对象友好（无 setter） Lombok 可缓解但引入依赖
集中校验构造参数 继承场景要处理泛型自引用

7. 与其他模式对比

模式 区别
工厂 工厂”一步创建”；建造者”分步组装 + 参数化”
原型 原型”复制已有”；建造者”从零组装”
模板方法 Director 编排步骤类似模板方法思想

原型模式详解（Prototype）

发表于 2026-09-14 本文字数： 965 阅读时长 ≈ 3 分钟

设计模式 · 原型模式

GoF 创建型模式。意图 · 结构 · 深浅拷贝 · 代码实现 · 应用场景 · 优缺点。

1. 模式概述（意图）

原型模式（Prototype）通过复制已有对象（原型）来创建新对象，而不是通过 new 重新构造——当创建成本高时，复制往往更高效。

2. 要解决的问题

问题 说明
创建成本高 对象初始化涉及 DB 查询、IO、复杂计算
运行时才能确定类型 动态生成对象（编辑器复制粘贴）
构造参数复杂 复制比手动重建更省事

典型场景：文档编辑器复制粘贴、Spring @Scope("prototype") 的创建方式之一、缓存对象的复制（不想共享引用）。

3. 结构（角色）

4. 代码实现（Java 深/浅拷贝）

深浅拷贝对比：

方式 行为 风险
浅拷贝 只复制引用，对象内部引用共享 改内部对象影响所有副本
深拷贝 内部引用也复制新对象 实现复杂（嵌套层级深）

5. 应用场景

场景 说明
文档/图像复制粘贴 编辑器复制画布元素
表单/配置模板 从模板复制出具体实例
Spring Prototype Bean 每次获取新实例的创建机制
缓存对象防篡改 复制返回，避免调用方改缓存

6. 优缺点

优点 缺点
创建成本低（复制 vs 重建） 深拷贝实现复杂，嵌套对象易出错
运行时动态复制 需要克隆方法，类改造
与具体类解耦（面向原型接口） 循环引用对象无法直接克隆
性能高（比 new + 初始化快） record/不可变对象才最安全

7. 与其他模式对比

模式 关系
工厂模式 工厂创建新对象；原型是”复制已有对象”
单例 原型强调多副本；单例强调唯一
建造者 建造者逐步组装；原型一步复制

设计模式 · 抽象工厂

GoF 创建型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与工厂方法对比。代码带详细注释。

1. 模式概述（意图）

抽象工厂（Abstract Factory）提供一个接口，用于创建一族相关的对象（产品族），而不指定具体类——保证族内产品配套、风格一致。

2. 要解决的问题

现实中的产品往往成族：UI 有”亮色主题”和”暗色主题”（按钮、输入框、弹窗各一套）；数据库有”MySQL 连接”和”PostgreSQL 连接”（连接、事务、方言各一套）。错误做法：分别 new 各组件——容易混搭（亮色按钮配暗色弹窗）。

问题 说明
产品族混搭 各自创建导致配套不一致
换族成本高 换主题要改所有创建点
违反开闭原则 新增一族要改多处

3. 结构（角色）

4. 代码实现

扩展：加”高对比度主题” = 新增 3 个产品类 + 1 个工厂类，老代码不动。

5. 应用场景

场景 说明
UI 主题系统 亮/暗/高对比度一族
跨数据库访问 Connection/Statement/ResultSet 一族（JDBC 抽象工厂）
跨平台组件 Windows/Mac/Linux 原生控件
ORM 方言 MyBatis/JPA 的方言族

6. 优缺点

优点 缺点
保证产品族配套一致（核心价值） 加新产品类型要改抽象工厂（打破开闭）
客户端与具体类解耦 类数量膨胀
换族成本 = 换一个工厂 产品族概念复杂时难理解

7. 与工厂方法对比

维度 工厂方法 抽象工厂
创建对象 一种产品 一族产品
工厂粒度 每产品一工厂 每族一工厂
扩展方向 加产品（易） 加产品类型（难）、加族（易）
典型 JDBC Driver UI 主题、JDBC 产品族

1. 模式概述（意图）

工厂方法（Factory Method）定义创建对象的接口，把”创建哪个实例”延迟到子类决定——每个产品对应一个工厂子类，新增产品只加类不改老代码。

2. 要解决的问题

简单工厂的致命伤：加新产品必须修改工厂类（违反开闭原则）。工厂方法把”选择产品”的逻辑下沉到子类，扩展靠新增子类而非修改。

问题 简单工厂 工厂方法
新增产品 改 switch（违反开闭） 加一个工厂子类（符合开闭）
创建逻辑分散 集中但膨胀 每个工厂管一种，清晰

典型场景：框架的扩展点——JDBC DriverManager 与各数据库 Driver、日志框架 Logger 工厂、集合工厂。

3. 结构（角色）

4. 代码实现

新增产品流程：加 CsvParser + CsvParserFactory，老代码零修改——开闭原则落地。

5. 应用场景

场景 说明
JDBC DriverManager 用工厂方法创建各数据库 Connection
日志框架 log4j/slf4j 的 Logger 工厂
集合工厂 Collection 的 iterator() 工厂方法
Spring FactoryBean 容器创建 Bean 的扩展点
框架扩展 用户实现接口即获得框架能力

6. 优缺点

优点 缺点
符合开闭原则（扩展靠新类） 类数量翻倍（每产品多一个工厂）
创建逻辑集中且单一职责 产品体系简单时过度设计
客户端与具体产品解耦 需要理解继承结构

7. 与其他模式对比

模式 区别
简单工厂 一个工厂 + switch；工厂方法每个产品一个工厂
抽象工厂 工厂方法管”一种产品”，抽象工厂管”一族产品”
模板方法 工厂方法常被模板方法调用（如上面 createAndParse）

1. 模式概述（意图）

简单工厂（Simple Factory）用一个工厂类根据参数决定创建哪种产品，客户端只跟工厂打交道，不直接 new 具体类。

客户端依赖具体类 违反”面向接口编程”

典型场景：按类型创建消息、解析器、导出器、支付渠道；java.util.Calendar.getInstance()、Integer.valueOf() 都是简单工厂思想。

3. 结构（角色）

4. 代码实现

5. 应用场景

场景 说明
按类型创建对象 消息渠道、支付方式、文件解析
JDK 静态工厂 Integer.valueOf、Calendar.getInstance、Arrays.asList
Spring FactoryBean 复杂 Bean 的创建

优点 缺点

单例模式详解（Singleton）

发表于 2026-09-14 本文字数： 1k 阅读时长 ≈ 3 分钟

设计模式 · 单例模式

GoF 创建型模式。意图 · 结构 · 线程安全四种写法 · 应用场景 · 优缺点 · 与其他模式对比。代码带详细注释。

1. 模式概述（意图）

单例模式（Singleton）保证一个类只有一个实例，并提供一个全局访问点。核心：把构造函数私有化，由类自己管理唯一实例。

2. 要解决的问题

问题 说明
重复创建浪费资源 连接池、线程池、配置对象创建昂贵
状态不一致 多个实例各自持有状态，互相不同步
全局访问不方便 需要到处传递实例引用

典型场景：数据库连接池、Redis 客户端、Spring 容器、日志记录器、配置管理器——这些对象一个就够，多了反而有害。

3. 结构（角色）

4. 代码实现（四种写法，从简单到线程安全）

4.1 懒汉式（线程不安全，仅教学）

4.2 双重检查锁 DCL（推荐，兼顾懒加载与性能）

4.3 静态内部类（推荐，天然线程安全 + 懒加载）

4.4 枚举单例（最简洁，防反射防序列化）

5. 应用场景（JDK/Spring 实例）

场景 说明
Spring Bean 默认单例 @Bean 默认 singleton 作用域
JDK Runtime Runtime.getRuntime() 就是单例
数据库连接池 HikariCP DataSource 单例
线程池 Executors 返回的池对象全局共享
配置中心 应用配置只加载一次

6. 优缺点

优点 缺点
节省资源（一个实例） 违反开闭原则（扩展需改类）
全局访问方便 隐藏依赖（全局状态难测试）
保证状态一致 多线程实现要小心（写错有并发隐患）
懒加载可选 滥用导致”上帝对象”

现代观点：单例要克制——能用依赖注入（Spring 容器管单例）就不用全局静态单例；全局可变状态是测试和并发的地雷。

7. 与其他模式的关系

相关模式 关系
工厂模式 工厂常配合单例：返回唯一实例
享元模式 享元强调”复用共享对象”，单例是享元的一种特例
建造者模式 建造者常用于配置复杂对象，可与单例组合

1. 概念说明

入门篇掌握了 <script setup> 基础。进阶核心：

  • 组合式函数（Composable）：把可复用逻辑抽成函数（替代 mixin 的缺陷）。
  • 响应式原理：ref/reactive 基于 Proxy；理解 computed 缓存与 watch 时机。
  • 状态管理：跨组件共享状态用 Pinia（store），而非 props/emit 层层传。
  • 性能：虚拟列表、懒加载、缓存、减少响应式开销。

何时需要 Pinia：多个页面/组件共享同一状态（用户信息、购物车、主题）→ 用 store；只在父子组件 → props/emit。

2. 组合式函数（核心技能）

组合式函数规范：useXxx 命名；返回响应式对象；可接受参数配置；内部状态不泄漏。

性能注意：大数组/深层对象避免深度响应式（用 shallowRef）；循环里避免创建计算属性。
