第三章：高并发系统设计

概念基础

  1. 高并发三指标 QPS/RT/并发数：QPS 每秒请求数、RT 响应时间（区分 P50/P99/P999）、并发数同时在线请求数，三者满足 QPS = 并发数 / RT——降 RT 与提并发数都能提 QPS，但 RT 是用户体验底线。
  2. 扩展性：垂直 vs 水平：垂直扩展是单机升配（CPU/内存/SSD），有上限且成本指数增长；水平扩展是多实例分摊流量，理论上无上限，但要解决状态分布、数据分片、一致性。
  3. 缓存不是银弹：缓存能扛住读 QPS，但带来一致性、穿透、雪崩、击穿四大难题；写多读少或强一致场景缓存收益小且风险大，滥用缓存是高并发系统最常见的事故源。
  4. 降级保核心：流量洪峰时主动牺牲非核心功能（评论、推荐、日志）保全核心链路（下单、支付），降级要预案先行、开关可灰度，而非临时手忙脚乱。
  5. 容量规划先行：先估算峰值 QPS 与单机容量，倒推实例数与资源水位线，再配弹性伸缩；没有容量规划的高并发是赌博，全链路压测是上线前的强制校验。

本章聚焦缓存、数据库扩展、削峰、限流降级四板斧；缓存与数据库基础见 第一章：Redis 概述、安装与 CLI 入门 与 第一章：MySQL DDL 语句与表设计入门。

一、缓存架构

多级缓存

请求从前到后层层兜底：浏览器 → CDN → Nginx → 本地缓存（Caffeine）→ Redis → DB，每层挡住一部分流量，越靠前越快也越易失效。

缓存穿透 / 击穿 / 雪崩

问题 现象 解决方案
穿透 查不存在的 key，缓存 DB 都没有，每次打 DB 布隆过滤器拦截；空值缓存短 TTL
击穿 单个热点 key 过期瞬间，海量请求直击 DB 互斥锁（只放一个回源）+ 热点永不过期后台刷新
雪崩 大量 key 同时过期，DB 瞬时压力暴增 TTL 加随机偏移；多级缓存兜底；熔断限流

缓存一致性策略

策略 做法 一致性 复杂度
Cache Aside 先更 DB 再删缓存，读时回填 最终一致 低，推荐
Read Through 缓存代理回源，应用只读缓存 较强 中
Write Through 写穿缓存再写 DB，同步 强 中
Write Behind 写缓存即返回，异步刷 DB 弱但快 高

Cache Aside 的删缓存时机：先更 DB 后删缓存，配合延迟双删（删→更→延迟再删）可缓解主从延迟导致的脏读。

热点 Key

热点 Key 单分片扛不住时：本地缓存吸收读、分片打散（key 加随机后缀分散到多分片）、只读副本分流。

热点探测：京东 hotkey、阿里云 Tair 等组件用滑动窗口统计各实例访问频率，发现热点后自动本地缓存或打散；自建可用「客户端埋点上报 + 阈值判定」的最小实现。

二、数据库扩展

读写分离

主库写、从库读，主从复制异步。代码层用 ShardingSphere 自动路由：写走 master、读走 slave。

主从延迟的坑：写入后立刻读可能读不到（复制延迟几十毫秒到秒级）。对策：① 关键读强制走主库（transactionalReadQueryStrategy）；② 写后短时间内的读请求路由主库（时间窗策略）；③ 用 GTID/位点等待读己之写。

分库分表

  • 垂直拆分：按字段拆表（商品基本信息 vs 商品详情长文），解决单表字段过多。
  • 水平拆分：按分片键（如 user_id）把数据分散到多库多表，解决单表数据量过大。

分片键选择与全局 ID

  • 分片键：选高频查询条件（如 user_id），避免跨片查询；不带分片键的查询会广播所有分片。
  • 跨片查询：用 ES 建二级索引，或宽表汇总，避免广播扫描。
  • 全局唯一 ID：雪花算法（时间戳+机器 ID+序列号），趋势递增利于 B+树插入。
  • 扩容迁移：取模分片扩容要迁移大量数据；预分片（一次分足 64/128 逻辑分片，物理合并部署）或 一致性哈希/范围分片 能让扩容只迁少量数据。

连接池与线程池容量

池子是单机容量的隐形天花板，常见两类事故：池太小排队超时、池太大压垮 DB。

  • 经验公式：连接数 ≈ 核数 × 2 + 有效磁盘数（PostgreSQL 官方 wiki）；IO 密集业务按 (核数 / (1 - 阻塞系数)) 上浮。
  • 线程池同理：Tomcat max-threads 与业务线程池隔离（舱壁模式），一个慢下游不拖垮全局。
  • 队列别贪长：长队列把超时藏成 RT 毛刺，配合快速失败 + 重试上限比硬扛更稳。

三、消息队列削峰

消息队列在高并发里干三件事：削峰填谷（把瞬时洪峰蓄进队列、匀速消费）、异步解耦（写完即返回、下游异步处理）、最终一致（事件驱动跨服务状态同步）。

消费者背压与幂等

死信队列：消费失败重试达上限后转入 DLQ 人工介入；位移提交：业务成功后再 MarkMessage，避免处理失败丢消息。MQ 基础见 第一章：Kafka 消息中间件入门：核心概念与架构。

四、限流与降级

限流算法

算法 特点 场景
计数器 固定窗口、临界突刺 简单限频
滑动窗口 平滑、无突刺 接口 QPS 限流
令牌桶 允许突发、匀速补桶 网关入口限流
漏桶 匀速出水、削峰 下游保护

选型建议：

诉求 推荐
允许短时突发（如突发下单） 令牌桶（桶容量即突发余量）
严格匀速（保护脆弱下游） 漏桶（队列排队恒速流出）
精确到任意时间窗 滑动窗口（Redis ZSET 记录时间戳计数）
粗粒度简单限频 固定窗口计数器（INCR + EXPIRE），接受临界突刺

单机 vs 分布式：Guava RateLimiter 只管单实例，多实例总和会超配；全局限流必须走 Redis Lua（原子）或 Sentinel 集群流控（Token Server 均摊配额）。

降级与熔断实战

  • 降级分级：读降级（缓存/默认值）、写降级（同步转异步）、功能降级（关评论/推荐）。
  • 熔断：错误率/RT 超阈值触发，OPEN 直接拒绝，休眠后 HALF_OPEN 探活恢复。

降级预案清单（上线前必须逐项演练）：

级别 触发条件 动作 恢复
L3 轻度 RT P99 超阈值 关个性化推荐、关日志采样外上报 指标回落自动恢复
L2 中度 错误率 > 5% 非核心读走缓存兜底、写转 MQ 异步 人工确认后关闭
L1 重度 核心链路濒危 只保下单/支付，其余功能页降级 总指挥决策恢复

熔断限流工程落地见 第七章：集成 Sentinel：流控、熔断与服务保护。

五、CDN 与静态化

CDN 边缘缓存与动静分离

CDN 把静态资源缓存到离用户最近的边缘节点，回源率是成本与体验的关键。动静分离让动态请求走应用、静态走 CDN/Nginx。

页面静态化与图片服务

  • 页面静态化：把活动页/详情页预渲染成 HTML 推 CDN，QPS 由应用层降到 CDN 层。
  • 图片服务：上传后转多尺寸+WebP，CDN 按尺寸回源；预热提前把热点资源推 CDN，刷新保证更新及时。

Nginx 静态服务与反向代理见 第一章：Nginx 入门与静态服务。

六、容量评估与压测

容量评估方法论

容量评估不是拍脑袋，是一条可复用的估算链：

  1. 业务峰值估算：峰值 QPS = 日均 PV ÷ 86400 × 峰值系数(5~10) × 热点集中度修正——秒杀/大促类场景峰值系数可到 50。
  2. 单机容量测定：压测单实例找出 拐点 QPS（RT P99 开始劣化或 CPU 到 70% 的点），以拐点的 60%~70% 作为生产水位。
  3. 实例数倒推：实例数 = 峰值 QPS ÷ 单机水位 × 冗余系数(1.3~1.5)（N+1 冗余防单点）。
  4. 依赖容量核对：DB 连接数、Redis QPS、MQ 吞吐、下游接口配额逐一核对——最短板决定系统容量。

Little 定律：并发数 = QPS × RT。RT 恶化一倍，同样并发下 QPS 腰斩——降 RT 与限流是同一枚硬币的两面。

高并发监控指标

压测结果要靠线上监控持续校验，四类指标缺一不可：

层 核心指标 告警参考
流量 QPS、并发数、限流拒绝数 拒绝率突增
延迟 RT P50/P99/P999、慢调用数 P99 连续超阈值
资源 CPU/内存/GC 停顿、连接池占用、线程池队列长度 池化资源打满前兆
业务 下单成功率、库存扣减失败数、MQ 积压量 成功率掉线

USE/RED 方法：资源类用 USE（Utilization 利用率 / Saturation 饱和度 / Errors 错误），请求类用 RED（Rate / Errors / Duration）——照此配 Grafana 面板，排查时不会漏维度。

QPS 估算与压测工具

峰值 QPS 估算：日均 PV ÷ 秒数 × 峰值系数（通常 5~10 倍），再按二八定律收敛到高峰时段。

全链路压测与弹性伸缩

  • 全链路压测：在影子库影子表上模拟真实流量走过所有服务，发现瓶颈与雪崩点。
  • 影子隔离：压测流量带压测标（如 header x-load-test: 1），中间件按标路由到影子库/影子 Topic，绝不污染生产数据。
  • 流量来源：线上流量录制回放（GoReplay）最贴近真实分布；造数脚本需模拟缓存命中率、参数离散度，否则结论失真。
  • 容量水位线：CPU/内存/RT 水位线，超过扩容、低于缩容。
  • K8s HPA：按 CPU 或自定义指标自动伸缩 Pod 数。

容器编排与弹性伸缩见 第二章：Kubernetes 容器编排入门。

七、实战案例：秒杀系统设计

秒杀是高并发技术的综合考试：瞬时洪峰（几十万 QPS 抢几百库存）、库存不超卖、防刷、链路尽量短。



flowchart LR
  U[用户] --> CDN[CDN 静态页]
  CDN --> WAF[WAF/网关<br/>防刷+令牌桶限流]
  WAF --> APP[秒杀服务<br/>答题/验证码 错峰]
  APP --> R[(Redis<br/>库存预扣)]
  R -->|扣减成功| MQ[Kafka<br/>订单消息]
  MQ --> DB[(MySQL<br/>异步落库)]
  R -->|库存不足| X[直接返回抢完]

核心设计决策：

决策点 方案 理由
库存扣减 Redis Lua 原子预扣，DB 只做最终一致 DB 行锁扛不住十万级 QPS
削峰 答题/验证码把 0 秒洪峰拉成 10 秒；MQ 异步下单 瞬时并发降一个数量级
防超卖 Lua 脚本内 库存>0 才扣；DB 侧 UPDATE ... WHERE stock>0 双保险 原子判断+扣减，不留竞态窗口
防刷 网关层设备指纹 + IP/UID 限频 + 隐藏秒杀 URL（动态下发） 挡住机器流量
读链路 详情页全静态化走 CDN，库存状态轮询聚合接口 99% 的读请求不碰应用
兜底 售罄开关提前预埋；超卖对账任务事后校验 宁可少卖不可超卖

顺序关键：先扣 Redis 再发 MQ（成功才入队）；MQ 消费侧幂等落库，DB 失败可凭 Redis 记录补偿重试。任何一步的不可重入都会变成资损。

常见避坑

坑 现象 正确做法
缓存与 DB 强一致执念 加各种锁保强一致，性能崩盘 接受最终一致，用延迟双删+消息补偿
热点 key 过期集中 同时过期引发雪崩击穿 TTL 加随机偏移，热点永不过期后台刷
分片键选错 按自增 ID 分片导致写入热点 选离散度高的业务键（user_id），避免时间序
跨片查询广播 不带分片键的查询扫所有分片 建二级索引（ES/宽表），或冗余分片键
消费位移提前提交 处理未成就位移，宕机丢消息 业务成功后再 MarkMessage，处理失败重试
限流只限单机 单机限不住全局，总量仍超 网关层 + Redis Lua 做分布式限流
降级开关临时找 故障时才现加开关，来不及 预埋降级开关，演练验证可降级路径
压测压单接口 单接口扛住了，链路仍崩 全链路压测，覆盖依赖与共享资源
HPA 扩容滞后 流量突增时 Pod 还没起就过载 预留 buffer + 预扩容 + 缩容冷却防抖
缓存击穿用大锁 互斥锁锁全局，并发退化串行 锁粒度细化到 key，或逻辑过期异步刷新

第一章：测试方法论与单元测试

概念基础

  1. 测试金字塔 70/20/10：经验比例是 70% 单元 / 20% 集成 / 10% E2E——越往底越便宜、越快、越稳；倒置成「冰淇淋模型」会让 CI 慢得没人敢跑。
  2. 验证正确性 vs 设计反馈：测试一面证明代码做对了，一面反向驱动设计——写不动的测试往往暴露耦合过重的代码，是免费的设计评审。
  3. FIRST 原则：Fast 快、Isolated 隔离、Repeatable 可重复、Self-validating 自验证、Timely 及时；任一条破了，测试就开始腐烂。
  4. 测试不是 QA 专属：开发人员写单元 / 集成测试是职责的一部分；QA 更适合承接探索性测试、E2E、验收，二者互补而非甩锅。
  5. Mock vs Stub vs Fake 区别：Stub 只喂预设返回值，Mock 还验证交互，Spy 包装真实对象记录调用，Fake 是简化但能工作的实现（如内存仓库）；混用会让测试语义模糊。

本章聚焦单元测试与方法论；跨模块、外部依赖与浏览器自动化留给 第二章：集成测试与 E2E 测试。

一、测试金字塔与策略

三种测试模型对比：金字塔（底大顶小，单元 70%，经典稳妥）；钻石（中间最宽，单元 30%，微服务集成契约重）；冰淇淋（顶大底小，单元 10%，E2E 主导，慢、脆、贵）。

成本 vs 价值矩阵：

层级 速度 写入成本 缺陷定位 价值密度
单元 毫秒级 低 精确到函数 高
集成 秒级 中 模块边界 中
E2E 分钟级 高 仅「挂了」 低但不可替代

FIRST 原则逐条落地：

字母 含义 常见违背
Fast 毫秒级，全套几千用例分钟级跑完 单测连真库/真网络，越跑越慢越没人跑
Isolated 用例互不影响、任意顺序可跑 共享可变静态状态、依赖执行顺序
Repeatable 任何环境结果一致 依赖系统时钟、随机数、时区、网络
Self-validating 断言自动判定，无需人工看输出 只 System.out.println 不断言
Timely 与生产代码同步写（TDD 则先写） 上线前补测试，永远排不上期

什么该测：业务逻辑、状态机、纯函数、边界条件、错误分支。不该测：getter/setter、第三方库内部、框架配置、私有实现细节。慎测：时间逻辑（注入时钟）、随机数（固定种子）、并发时序（用可控同步）。

1. AAA 与 Given-When-Then

三、Mock 与依赖隔离

Test Double 对照表：

类型 预设返回值 验证交互 走真实逻辑
Dummy 否（占位参数） 否 否
Stub 是 否 否
Spy 是（包装真实） 是 部分
Mock 是 是 否
Fake 否（自实现） 否 是（简化版）

五类替身详解：

  • Dummy：只为凑参数签名，从不被使用——如 new Order(null, dummyAddress) 里根本不参与的地址对象。
  • Stub：喂固定答案——when(repo.findById(1)).thenReturn(user)；只关心被测对象拿到的输入。
  • Spy：包装真对象记录调用，部分真实部分拦截——spy(list) 后可 verify(spy).add(...) 又不破坏真实行为。
  • Mock：预设脚本 + 事后验证交互——关心「是否以正确参数调用了正确的协作者」。
  • Fake：能跑的简化实现——内存版 UserRepository（HashMap 实现接口），集成度最高。

选型口诀：协作者返回值影响分支 → Stub；要断言协作协议 → Mock；想保留真实行为又查调用 → Spy；想要轻量真实依赖 → Fake；只为编译通过 → Dummy。

Mockito（Java）：@Mock 造桩、when(...).thenReturn(...) 喂数据、verify(...) 查交互。

gomock（Go）：用 mockgen 生成接口桩，EXPECT() 声明期望调用。

unittest.mock（Python）：patch 替换目标对象，assert_called_once() 验证。

过度 Mock 反模式：Mock 一切 → 测试和生产代码同构，重构必碎。原则：只 Mock「自己拥有的边界」（端口），不要 Mock「别人的类型」（数据库内部、三方 SDK 私有方法）。

可测性设计：让代码天然好测

写不动测试的代码，问题几乎都在设计而非工具。三条军规：

  1. 依赖注入：依赖走构造函数传入而非 new 出来——OrderService(PaymentGateway gw) 让测试随手塞 Stub/Fake。
  2. 副作用外移（函数式核心 + 命令式外壳）：纯计算（定价、计税）做成无依赖纯函数，IO（DB、HTTP、时钟）挤到薄外壳；单测火力集中在纯函数上。
  3. 时间/随机显式化：Clock 与随机源注入——LocalDate.now(clock)，测试里传固定 Clock，Repeatable 自然达成。

四、TDD 实践

Red-Green-Refactor 循环：① Red 写一条失败测试描述新行为；② Green 用最简单的代码让它通过（哪怕硬编码）；③ Refactor 在测试保护下重构。循环周期应控制在分钟级，单个测试只验证一件事。适合纯逻辑、算法、状态机、契约明确接口；慎用于 UI 探索、原型验证、性能调优、未知 API 首次联调。

TDD 三个节奏技巧：

  • 测试清单先行：开工前把想到的行为列成 TODO 清单（空栈 pop 报错、push 后 size+1、LIFO 顺序…），每完成一条划掉一条，防遗漏也防一次性写太多。
  • 三角测量：第一条测试允许硬编码返回常量通过（Green 的最小实现），第二条不同输入的测试逼出真正的泛化逻辑——不抽象到第三条测试出现之前。
  • 步幅控制：卡住时缩小步幅（先测更简单的情形），顺手时加大步幅；绝不在 Red 状态停留太久去改生产代码。

一个常见的循环节奏：失败测试（1 分钟）→ 最小实现（2 分钟）→ 重构清理（1 分钟）→ 提交。每小时 10 个左右的小循环，比写两小时代码再补测试的缺陷密度低一个量级。

第二章：集成测试与 E2E 测试

概念基础

  1. 集成测试定义：验证模块间协作是否正确——服务与数据库、服务与服务、模块与模块的接线点，单元测试替不了，E2E 又太贵，集成测试填补中间地带。
  2. E2E：用户视角：从真实入口（浏览器 / App / CLI）走完整业务流，验证「用户真能完成这件事」；它不关心内部实现，只关心端到端结果。
  3. 契约测试：消费者驱动：消费方先写「我期望 Provider 返回什么」的契约，Provider 验证自己满足契约，避免双方联调时的集成地狱。
  4. Testcontainers 革命：用一次性 Docker 容器跑真实依赖（Postgres / Redis / Kafka），让集成测试接近单元测试的速度与隔离性，又不丢真实度。
  5. 测试环境一致性：本地、CI、预发跑的依赖版本必须对齐，否则「我这能过」频发；镜像化依赖是消除环境漂移的根本手段。

本章承接 第一章：测试方法论与单元测试 的单元层，把验证范围抬升到跨模块、真实依赖与浏览器全链路。

一、集成测试策略

模块间集成 vs 外部依赖集成：前者验证自家代码之间的接线（订单服务调用库存服务的客户端）；后者验证自家代码与外部系统（数据库、消息队列、三方 API）的接线。前者偏快、偏纯；后者需要环境，是 Testcontainers 的主战场。

三种反模式自检：

反模式 形态 病灶
冰淇淋筒 E2E 占大头，单元寥寥 反馈慢、脆性高，CI 没人敢跑
纸杯蛋糕 各层重复测同一逻辑，无职责分工 改一处三层全改，维护成本爆炸
沙漏/哑铃 单元与 E2E 多、集成层断档 模块接线缺陷无人接，全漏到 E2E

测试奖杯（Testing Trophy）：Kent C. Dodds 提出的现代变体——集成测试占最大比重（Static < Unit < Integration > E2E），适合前端与微服务：单元测纯函数，集成测组件协作，E2E 只留登录/支付等关键路径。

测试双金字塔：金字塔之外再叠一座「契约金字塔」——服务间用契约测试替代大量重型集成测试，E2E 只保留少量关键路径，整体成本骤降。

数据准备：Builder / Fixture / Factory：

  • Fixture：固定数据集（如 users.yml），适合不变的场景底座。
  • Factory：按需造数据（如 OrderFactory.paid()、OrderFactory.pending()），适合多变组合。
  • 原则：测试数据自给自足，不依赖其他测试留下的状态。

事务回滚 vs 清理策略：

策略 做法 优缺点
事务回滚 每个用例开事务，结束回滚 快、干净；不适用于跨连接场景
清理脚本 用例后 TRUNCATE / DELETE 通用；需注意外键顺序
一次性容器 每用例新容器 最隔离；启动开销需用单例缓存优化

HTTP 依赖拦截：WireMock。三方 API（支付、短信）不值得起容器——用 WireMock 起本地 HTTP 桩，返回录好的响应并验证请求格式：

二、Testcontainers 实战

真实依赖 vs Mock 取舍：涉及 SQL 方言、事务隔离、连接池行为的逻辑必须用真库；纯协议解析、错误码映射可 Mock。Testcontainers 把「用真库」的成本压到可接受区间。

1. Java：PostgreSQL + Redis

2. Go：testcontainers-go

3. Python：testcontainers-python

性能要点：用 @Container static 或单例缓存容器，跨用例复用，避免每个用例都拉镜像；用 Reuse 模式让本地反复跑更快。

4. 消息中间件与组合环境

  • 多容器编排：DB + Redis + Kafka 多个 @Container 共存即可；超过 3 个依赖考虑 Testcontainers Cloud 或预置 compose 环境。

第四章：Pinia 状态管理实战

概念基础

  1. 为什么需要状态管理：组件树越深，props 逐层透传越难维护；跨兄弟/跨路由共享的数据（登录态、购物车、主题）抽到全局 Store，单向数据流让变更可追踪。第一章：Vue 3 核心概念与组件开发 的组合式 API 正好与 Store 天然契合。
  2. Pinia vs Vuex：Pinia 是 Vue 官方推荐的新一代方案，移除 mutations、天然 TypeScript、模块扁平（每个 store 独立注册，无需 modules 嵌套）；Vuex 4 仍兼容旧项目，新项目首选 Pinia。
  3. Store 三种类型：基于 defineStore 的 Option Store（state/getters/actions 三段式）、Setup Store（返回 ref/computed/function）、组合式 Store（跨 store 组合复用），写法按团队习惯选择。

  5. 持久化：默认状态存内存，刷新即丢；用 pinia-plugin-persistedstate 把关键 store 同步到 localStorage / sessionStorage / cookie，SSR 场景需注意 hydration 一致性。

第一章：CI/CD 入门与 GitHub Actions

概念基础

  1. CI / CD / Continuous Deployment 是三个递进概念：CI（持续集成） 把代码合并到主干并自动构建测试；CD（持续交付 Continuous Delivery） 在 CI 基础上把可部署产物推到制品库，发布动作仍需人工点击；Continuous Deployment（持续部署） 把人工环节也省掉，每次主干合并自动上线，差异关键在”最后一公里是否需要人“。
  2. 流水线阶段（Pipeline Stages） 通常按 Checkout → Build → Test → Scan → Package → Publish → Deploy 串联，每阶段失败立即中断，避免错误向下传递；阶段之间通过**构建产物（Artifact）**而非源码传递，保证”构建一次、到处部署”。
  3. 声明式 vs 脚本式：声明式（GitHub Actions YAML、Jenkins Declarative Pipeline）用结构化语法描述”做什么”，可读、可静态校验、IDE 友好；脚本式（Jenkins Scripted Pipeline）用 Groovy 编排”怎么做”，灵活但难审阅，复杂分支逻辑才回退脚本式。
  4. 缓存策略 决定流水线是否”快得起来”：依赖（~/.m2、node_modules）按 依赖锁文件 hash 作 cache key 缓存；Docker 层走 BuildKit --mount=type=cache 共享；不可变产物（jar/wheel）只缓存构建输入，不缓存输出，避免污染发布物。
  5. 密钥管理 铁律是”密钥永远不进代码“：GitHub 用 Secrets（加密、日志自动打码）、Actions 用 OIDC 短期令牌替代长期 Access Key；生产环境靠 Environment + 审批 + 分支保护三重门，避免一人推主干即上线。

第二章：Jenkins 与发布策略

概念基础

  1. Jenkins 定位：开源、可自托管的流水线引擎之王，靠插件生态覆盖几乎所有语言/云/部署场景；与 GitHub Actions”云原生 SaaS”不同，Jenkins 强在完全可控、内网部署、Agent 可挂物理机/容器/K8s，劣势是运维成本高、插件兼容性坑多。
  2. Declarative vs Scripted Pipeline：Declarative 用 pipeline { stages {} } 结构化语法，可读、可静态校验、对 IDE 友好，适合 90% 场景；Scripted 用 Groovy 自由编程，灵活但难审阅，仅复杂动态逻辑才回退 Scripted，二者底层都是同一套 Graph 执行模型。
  3. 蓝绿 / 金丝雀 / 滚动 是三大发布策略：蓝绿准备一套完整备用环境瞬间切流（需双倍资源）；金丝雀按小比例流量灰度观察后再放量（需流量分流能力）；滚动逐批替换 Pod（默认策略，资源增量小但发布期间新旧并存）。
  4. 回滚策略遵循”代码可秒退，数据需慢退“：K8s rollout undo 与 Helm rollback 可瞬间切回上一版本镜像；但数据库 schema 变更必须前向兼容（扩列先加后删），靠”发布分两步“避免锁死回滚路径。
  5. 基础设施即代码（IaC） 是 GitOps 的前提：K8s 清单、Helm values、Kustomize overlay 全部进 Git，Git 即单一可信源，部署不靠”登录 master 手敲 kubectl”，而是PR 合并即同步，可审计、可回滚、可重现。

第一章：Prometheus 指标监控与 Grafana 可视化

概念基础

  1. 指标（Metrics）vs 日志（Logs）vs 链路（Traces）：指标是聚合后的数值时间序列（CPU、QPS），擅长告警与容量规划；日志是离散事件明细，擅长排障取证；链路是跨服务调用的因果树，擅长定位慢调用。三者构成可观测性三支柱，必须协同使用。
  2. Pull 拉取模型：Prometheus 主动按 scrape_interval 抓取各 exporter 的 /metrics 端点，而非被动接收推送。该模型天然契合服务发现，目标失联时可通过 up == 0 直接告警，比 Push 模型更易判断探活状态。
  3. PromQL 查询语言：声明式表达式语言，支持 rate()、increase()、histogram_quantile()、sum by(label) 等多维聚合运算，能在标签维度上做任意切片，是 Grafana 仪表盘与告警规则的核心引擎。
  4. 多维度标签：每个样本附带 {job, instance, method} 等标签，标签数量决定数据基数。合理设计可让一个指标复用上千个视图，但高基数标签（如 user_id）会撑爆存储，需克制。
  5. Grafana 生态：开源时序可视化平台，支持 Prometheus、Loki、Tempo 等数十种数据源，通过 Panel/Variable/Alert 构建一体化仪表盘，支持钉钉、企微、邮件、PagerDuty 等多种通知渠道。

可观测性三支柱环环相扣：本章专注指标维度，日志维度详见 第二章：ELK 日志收集与分析，链路维度详见 第三章：分布式链路追踪。

rate / irate / increase 怎么选

函数 特点 适用
rate(x[5m]) 窗口内平均速率，平滑 告警与大盘（默认选它）

histogram_quantile 的正确姿势

histogram_quantile(0.95, sum(rate(..._bucket[5m])) by (le)) 有三条铁律：必须按 le 聚合（少了 le 直接报错或失真）、先 rate 再聚合再分位（顺序反了无意义）、桶边界要覆盖目标分位 10 倍量程（P99 落在最大桶外时返回桶上界，严重低估）。原生直方图（Native Histograms，3.x 已稳定）不再依赖固定桶，长期是替代方向。

七、长期存储与多集群：联邦与 Thanos

单机 Prometheus 的 TSDB 适合 15~30 天热数据；跨机房汇总与长期留存有两条路：

  • 联邦（Federation）：上层 Prometheus 用 /federate 端点从下层拉已聚合的少量指标（如每集群 QPS 汇总），配置简单但只搬摘要，适合层级汇总。
  • Thanos / Mimir / VictoriaMetrics：Sidecar 把 TSDB 块上传对象存储（S3/OSS），Querier 全局查询、Compactor 降采样，实现无限留存 + 全局视图 + 高可用。Thanos 组件多、运维重；VictoriaMetrics 单机即可起步，集群版按需扩展；Grafana Mimir 与 Grafana 生态结合紧。

中小规模建议：单机 + 15d 留存 + remote_write 到 VictoriaMetrics 长期库，成本与复杂度最平衡。

第二章：ELK 日志收集与分析

概念基础

  1. 结构化日志：将日志输出为机器可解析的 JSON（含 timestamp、level、traceId、msg、fields），相比纯文本能被 Elasticsearch 直接索引，避免 grok 正则回溯，且支持任意字段聚合统计。
  2. 日志分层：访问日志（access）、应用日志（application）、审计日志（audit）、慢日志（slow）按用途分流到不同索引，避免一个 index 啥都装导致查询低效与成本失控。
  3. ELK vs EFK：经典 ELK 是 Elasticsearch + Logstash + Kibana；EFK 把 Logstash 换成 Fluentd/Fluent Bit。Filebeat 因轻量、资源占用低，常作为采集器替代 Logstash 前置，Logstash 退居过滤/路由角色。
  4. 索引生命周期管理（ILM）：按时间滚动建索引（如 app-logs-2026.09.02），通过 ILM 策略让索引经历 hot → warm → cold → delete，控制存储成本并保持热数据查询性能。
  5. 日志采样：对高频调用（如健康检查、依赖轮询）做 1% 采样，避免日志洪流淹没关键事件。错误日志必须 100% 落盘，正常路径按比例采样。

第一章：Elasticsearch 入门与索引管理

概念基础

  1. 倒排索引是 ES 的心脏：写入时经分词器把文本拆成 term，建立 term → 文档 ID 列表的倒排表；查询时先在 term 字典命中、再扫倒排表取文档。对比 MySQL 的 B+Tree 是「值→行位置」，倒排索引是「词→文档列表」。
  2. 近实时（NRT）不是实时：写入先入 translog + 内存 buffer，默认每 1 秒 refresh 一次生成新 segment 才可搜；写后立刻查可能查不到，要 ?refresh=wait_for 或手动 _refresh。
  3. 集群三件套：节点 / 分片 / 副本：主分片水平拆数据决定容量上限，副本分片做高可用 + 读扩展；节点角色分 master / data / coordinating / ingest，生产建议 master 与 data 分离。
  4. ES ≈ 倒排索引 + 分布式：MySQL 的事务 / 外键 / 强一致 ES 没有；ES 的全文检索 / 聚合 / 打分 MySQL 也弱——选型看场景，不是替代，常组合使用。
  5. ELK 生态：E + L + K 三件套：Filebeat/Logstash 采集 → Elasticsearch 存储 → Kibana 可视化；现代可观测性栈的事实标准之一，后续可观测性系列会展开。
  6. 9.x 关注点：BBQ（Better Binary Quantization）向量量化提速数倍、成向量检索默认；ES|QL 管道查询语法简化分析类查询（第二章提一句）；_type 早已是历史（7 弃用、8 移除），统一走 _doc。

本章是 ES 系列开篇，安装与索引管理是地基；查询与调优在 第二章：Elasticsearch 查询与性能调优 展开。ES 按 9.x（2025+）语法书写。

倒排索引与段合并

  1. 段（Segment）不可变：refresh 产生新 segment，文档更新/删除只是打标记（.del 文件），旧段不动——这是 ES 写快的根基，也是磁盘膨胀的来源；
  2. 后台 merge：Lucene 定期把小段合并成大段，顺带物理清除带删除标记的文档；merge 吃 IO/CPU，写入高峰期可能拖慢查询；
  3. forcemerge 只用于只读索引：POST /logs-2026.08/_forcemerge?max_num_segments=1 把段合成 1 个，查询提速明显；对仍在写入的索引做 forcemerge 是灾难（刚合完又被打碎）。

分片与路由

写入文档落在哪个分片，由公式决定：

  • 默认按 _id 均匀打散；自定义 routing（如 user_id）可让同用户数据聚在同一分片：
  • 收益：查询带 routing 只扫 1 个分片而非全部，延迟大降；
  • 代价：routing 值分布不均会数据倾斜——某大户独占一个分片的热点就是这么来的。

refresh / flush / translog 三段式

机制 默认节奏 管什么

第二章：Elasticsearch 查询与性能调优

概念基础

  1. Query DSL 是 JSON 化的查询语法：一切查询走 GET /idx/_search { body }，body 由 query / aggregations / sort / size / from 等组成——告别 SQL，拥抱嵌套 JSON。
  2. 精确匹配 vs 全文检索：term 对 keyword / 数值精确匹配（不打分），match 对 text 分词后匹配并打分——用错类型是新手头号坑。
  3. 相关性评分 BM25：ES 7+ 默认 BM25（替代 TF-IDF），核心是「词频饱和 + 文档长度归一」——短文档命中高权重，长文档被稀释。
  4. 聚合 = 分桶 + 算指标：bucket agg（terms / date_histogram / range）分组，metrics agg（avg / sum / cardinality）算值，可嵌套——OLAP 分析能力。
  5. 分页深翻是 ES 的痛：from + size 超过 10000 默认被拒（max_result_window），深翻用 search_after 游标或 scroll——选错方式直接 OOM。

本章承接 第一章：Elasticsearch 入门与索引管理 的索引与 mapping；查询 DSL、聚合、调优在此展开。ES 按 9.x 语法。

四、分页与深度翻页

方式 上限 适用 状态
from + size 10000（max_result_window） 浅分页、要跳页 通用
search_after 无上限 深翻、顺序翻（不可跳页） 推荐
scroll 无上限 全量导出、一次性 7.10+ 渐进弃用，优先 search_after

from + size 超过 10000 报错：协调节点要把 from+size 条数据都取到内存再截断，深翻是性能与内存双重压力。导出用 search_after 或 scroll。

五、性能调优

  • 分片数：单分片 30~50GB 为宜；过多分片使聚合 scatter-gather 开销大、元数据重。
  • filter 缓存：精确条件进 filter 上下文，bitset 复用。
  • routing：按维度（如 user_id）路由，查询带 routing 少扫分片。
  • 索引拆分：按时间（logs-2026.09）或业务隔离，缩扫描范围。
  • 避免 wildcard 前缀：*foo 无法走 term 字典跳查，等于全词典扫描——非用不可时建 wildcard 类型字段（为通配查询优化的存储结构）。
  • 只读索引 forcemerge：历史日志索引合并到 1 个 segment，查询提速 + 省句柄（段合并原理见第一章）。
  • ES|QL（9.x）：POST /_query { "query": "FROM order_idx | WHERE amount > 100 | STATS total = SUM(amount) BY status" }——管道语法可读性远好于嵌套 DSL，分析类查询优先尝试；复杂打分与精细控制仍以 DSL 兜底。
硬件项 建议
堆内存 物理内存 50%，剩给 Lucene 文件系统缓存
JVM 不超 31GB（指针压缩阈值），用 G1GC
磁盘 SSD 必备；HDD 只读副本勉强
副本 读 QPS 高加副本；写入期临时归零
