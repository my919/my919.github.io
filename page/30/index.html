第七章：SpringBoot 统一返回体与全局异常

概念基础

  1. 统一契约：成功与失败均使用同一 JSON 结构，便于前端统一解析；Result<T> 三字段 code / msg / data。
  2. 两层语义：HTTP 状态码表达协议层语义（400/409/500 等），code 字段表达业务语义（可与 HTTP 一致或自定义）。
  3. 异常即响应：业务错误抛 BusinessException，由 @RestControllerAdvice 的 GlobalExceptionHandler 全局捕获并转换为 Result.fail，Controller 免写 try-catch。
  4. 校验联动：@Valid / @Validated 触发的 MethodArgumentNotValidException 与 ConstraintViolationException 同样统一处理为 400。
  5. 模板复用：完整 GlobalExceptionHandler 源码模板见 第四章：Java 全局异常处理：@RestControllerAdvice 与统一 Result；本章描述 springboot 仓库中的落地方式与验证。

错误码规范

code 字段是前后端联调与日志检索的关键，建议遵循分段约定：

区间 语义 示例
200 成功 —
400-499 客户端错误，与 HTTP 语义对齐 400 参数错误、401 未登录、403 无权限、409 状态冲突、429 频率限制
500-599 服务端错误 500 通用异常、502 下游失败
10000+ 业务自定义错误（可选） 10001 库存不足、10002 订单已关闭

约定原则：

  • 通用错误复用 HTTP 语义，前端拦截器可按 code 统一处理（401 跳登录、403 提示无权限）。
  • 业务错误自定义五位数，全局唯一，配合文档可检索；不要为了细分而滥用，能用 400/409 表达的不新开码。
  • msg 面向用户可读；技术细节（堆栈、SQL）只进服务端日志，不进响应体。

要点：

  • @ExceptionHandler 匹配顺序：Spring 按最具体优先匹配，子类异常会命中父类处理器，兜底 Exception 永远最后。
  • 返回 ResponseEntity：让业务 code 与 HTTP 状态码同步（如 429 同时出现在两处），网关/前端拦截更顺畅。
  • 兜底分支不泄细节：生产环境 msg 固定话术，堆栈只进日志，防止泄露表结构、路径等敏感信息。

第六章：SpringBoot 全局枚举与字典 API

概念基础

  1. 枚举即字典：状态、类型等有限取值用枚举表达，数据库只存数字 code，避免魔法数字散落各处。
  2. 统一 JSON 契约：JSON 出入参为 { "code", "desc" }，前端不再解析裸数字，展示文案与 desc 自动一致。
  3. 统一字典入口：前端下拉字典统一走 /api/enums；新增枚举只改注册表，Jackson 序列化与字典 API 自动同步。
  4. 两端协同：存储端由 MyBatis-Flex @EnumValue 保证入库为 code；序列化端由 Jackson 模块按 BaseEnum 注册表统一处理。
  5. 容错约定：反序列化支持数字、字符串、常量名、{code,desc} 多种入参，非法枚举值由全局异常处理器返回 400。

第四章：SpringBoot 集成 MyBatis-Flex 与多数据源

概念基础

  1. ORM 增强：MyBatis-Flex 是 MyBatis 之上的轻量 ORM，提供 IService / ServiceImpl 与分页，低侵入、强调查询性能与 APT 编译期能力。
  2. 多数据源路由：dynamic-datasource 在运行时按 @DS 注解切换数据源（本项目：MySQL + PostgreSQL），与 ORM 选型解耦。
  3. 选型参照：与 MyBatis-Plus 分层模型相近（BaseMapper → IService → ServiceImpl），迁移成本低；差异主要在条件构造、APT 表定义与 Spring Boot 4 starter 支持（详见下文对比）。
  4. 连接池底座：数据源底层为 Hikari 池，最大连接数、最小空闲等参数在 dynamic-datasource 配置下统一管理。
  5. 通用 @DS 与事务边界见 第六章：Java 动态数据源：@DS 切换与事务边界；Flex API 见 第二章：MyBatis-Flex 入门与代码生成；连接池见 第十二章：数据库连接池：HikariCP与Druid对比与落地。

二者都是在 MyBatis 之上的增强框架，分层模型相近（BaseMapper → IService → ServiceImpl），CRUD 与分页 API 名称大多一致，迁移成本较低。主要差异如下。

dynamic-datasource 底层是 Spring 的 AbstractRoutingDataSource：把所有数据源（mysql/pgsql）装进一个 Map，在每次 getConnection() 时通过 determineCurrentLookupKey() 决定取哪一个。



sequenceDiagram
  participant M as Service方法
  participant A as @DS AOP
  participant R as RoutingDataSource
  participant P as Hikari(mysql/pgsql)
  M->>A: 进入方法
  A->>A: 解析 @DS 值，push 到 ThreadLocal 栈
  M->>R: getConnection
  R->>R: 读 ThreadLocal 栈顶作为 lookupKey
  R->>P: 委托给对应池
  M->>A: 方法返回
  A->>A: pop 栈，恢复上一层数据源

关键设计：

  • ThreadLocal 栈（DynamicDataSourceContextHolder）：支持嵌套 @DS（外层 mysql 方法调用内层 pgsql 方法），退出时自动恢复。
  • AOP 顺序：@DS 切面必须在 @Transactional 切面之前执行，否则事务已绑定错误数据源。
  • 每个逻辑数据源一个独立 Hikari 池：互不影响，可单独调参。

@DS 与事务边界

1. 默认行为

@DS 只决定取哪个池的连接，不开启事务；@Transactional 只负责当前连接的事务，不切换数据源。两者正交但顺序敏感。

2. 常见坑

现象 原因 处理
@DS 不生效 同类自调用（this.foo()） 经 Spring 代理调用：拆 Bean 或注入自身
事务里切换数据源失败 事务已绑定连接，连接属于开启时的数据源 事务方法内不要切换 @DS；如需跨库，拆两个事务方法或用 Seata
@DS 在 private 方法 AOP 默认只代理 public 改为 public 或开 AspectJ 织入
嵌套调用错库 内层方法标 @DS 但外层没标 明确每一层注解，依赖栈恢复
主从混用读旧数据 主从同步延迟 写后立即读用 @DS("master") 强制走主

3. 跨库操作

关系型数据库无法在一个本地事务中跨 MySQL 与 Pg 提交；可选方案：

  • 业务侧拆分：先写主库、再写从库，失败时记录对账任务（适合允许最终一致的场景）。
  • Saga / TCC：引入 Seata 等分布式事务框架。
  • 消息驱动：主库写完发 MQ，从库消费落库（本站 RocketMQ 章节有示例）。

缓存三兄弟：穿透 / 击穿 / 雪崩



flowchart TB
  Q[查询请求] --> C{缓存命中?}
  C -->|是| H[直接返回]

1. 缓存穿透——查询根本不存在的数据，缓存永不命中，流量直达 DB：

  • 方案 A：缓存空值（短 TTL，如 60s），cache-null-values: true 时配合短过期。
  • 方案 B：布隆过滤器（Redisson RBloomFilter）前置拦截非法 key，适合海量不存在的 ID。

2. 缓存击穿——热点 key 恰好在高并发时过期，大量请求同时回源：

  • 方案 B：逻辑过期（value 里带过期时间戳，后台线程异步续期），热点 key 永不过期。

3. 缓存雪崩——大量 key 同时过期或 Redis 宕机：

  • TTL 加随机抖动：30min + random(0~10min)，打散过期时间点。
  • 多级缓存：本地 Caffeine（秒级）+ Redis（分钟级），Redis 挂了还有一层。
  • 兜底降级：Redis 异常时走 @Cacheable(sync = true) 无效，需在切面捕获后降级直查 DB + 限流。

概念基础

  2. 激活方式多样：配置文件 spring.profiles.active、环境变量 SPRING_PROFILES_ACTIVE、启动参数 --spring.profiles.active=prod，本项目默认 dev。

概念基础

  1. 为什么单机锁不够用：服务多实例部署后，synchronized/ReentrantLock 只能约束同一 JVM 内的线程，跨进程的互斥必须借助外部共享存储实现。
  2. 本质：多个进程竞争在同一个外部系统上设置同一个标识（Redis 的 SET NX、ZooKeeper 的节点、MySQL 的行锁），谁设置成功谁持有锁，并依赖超时自动释放防死锁。
  3. 三大实现流派：Redis（高性能、主流方案）、Zookeeper（临时有序节点、强一致）、MySQL（悲观/乐观锁，零新增中间件）。
  4. 生产要点：原子加解锁、锁续期、可重入、防误删、主从切换丢锁一个都不能少——这正是推荐 Redisson 的原因。
  5. 主从切换丢锁的根治方案：普通 Redis 锁是单主节点锁——加锁成功后尚未同步到从节点就宕机，主从切换后锁凭空消失。**RedLock（红锁）**把锁同时写到 N 个完全独立的 Redis 主节点上，过半节点加锁成功且总耗时小于锁有效期才算成功，从根本上规避单点故障丢锁。
  6. 选型口诀：高并发选 Redisson，强一致选 Zookeeper，无中间件小项目选 MySQL，核心强一致（秒杀/支付/账务）用 RedLock。

包含：Redis原生Lua锁、Redisson锁、Redisson RedLock、Zookeeper锁、MySQL悲观锁、MySQL乐观锁，可直接运行。

演进史：为什么不能写成「先 SETNX 再 EXPIRE」

  1. 第一代：SETNX + EXPIRE 两条命令——加锁成功后、设过期前进程崩溃 → 永不释放，死锁。病根是两条命令不是原子。
  2. 第二代：SET key val NX PX 30000 一条命令——Redis 2.6.12+ 原生支持，原子加锁 + 过期，解决死锁。
  3. 第三代：+ Lua 原子解锁——「GET 判断归属再 DEL」合成一个脚本，解决「自己的锁过期后被他人加上，自己又执行 DEL 误删」。
  4. 第四代：+ 看门狗续期（Redisson）——业务没执行完锁先过期的问题，靠后台线程定期延长有效期解决。

每一步演进都对应一类线上事故——你手写出来的多半是第二代，这是「禁止手写」的论据。

锁续期与看门狗（Redisson 怎么做的）

  • lock() 不传 leaseTime 时默认锁 30s（lockWatchdogTimeout），后台每 10s（有效期的 1/3）检查一次：线程还持有就续回 30s；
  • 显式传 tryLock(10, 30, SECONDS) 里的 leaseTime 则看门狗关闭——到期自动释放，业务超时风险由你承担；
  • 进程宕机 → 续期线程随之消失 → 锁到期释放，不会死锁。

「锁必须防死锁」和「业务可能跑很久」这对矛盾就此解耦，这是 Redisson 成为默认答案的核心原因。

RLock 在 Redis 里的形态

RedLock 是架在单节点 RLock 之上的组合，先看清 RLock 的数据结构：

  • 加锁：一段 Lua 脚本——Hash 不存在则 HSET + PEXPIRE 新建；已存在且 field 是本线程则 HINCRBY 重入并刷新过期；否则 PTTL 返回剩余存活时间，客户端据此自旋等待。三段逻辑一次往返、原子执行。
  • 解锁：同样是 Lua——HINCRBY -1，归零才真正 DEL；不是自己的锁返回 nil，Java 侧抛 IllegalMonitorStateException。

三、Redisson RedLock（多独立主节点）

3.1 原理与适用边界

RedLock = 多个独立 Redis 主节点 + 过半写入成功才算加锁成功，目的是彻底解决主从切换丢锁；代价是写 N 个节点 + 严格多数派判定，部署与性能成本都高于单节点锁。

  • 基于**多数派（quorum）**机制：任一节点宕机/切换都不影响多数节点上的锁记录。
  • 节点必须相互独立（非主从、非集群）且为奇数个。
  • 适用边界：秒杀、库存、支付、账务等核心强一致场景用 RedLock；后台任务等非核心场景普通 Redisson 锁即可。

为什么 RedLock 要逐节点续期：红锁对 N 个节点各持一把 RLock，任一节点上的锁过期而未续约，多数派就可能凑不齐——看门狗按节点独立工作，与红锁的过半判定互不影响。

3.2 环境要求与依赖

  1. 至少 3 个独立的 Redis 主节点（无主从、无集群、互相独立）
  2. Redisson 版本 >= 3.5.0
  3. SpringBoot / Java 项目均可

3.5 加锁成功规则（必须记住）

3 个节点：必须 ≥ 2 个节点加锁成功 + 加锁耗时 < 锁超时时间才算加锁成功；5 个节点：必须 ≥ 3 个节点加锁成功。

为什么要把「耗时」算进去：客户端向 N 个节点顺序加锁，若网络慢导致总耗时逼近锁有效期，最后一把锁拿到时，前面节点的锁可能已临近过期——有效持锁时间 = leaseTime − 加锁总耗时 − 时钟漂移余量。这就是 Redisson 在 tryLock 内部做耗时校验、不达标即整体放弃并回滚已加节点的原因。

看门狗在红锁里生效吗？ 生效——RedLock 会对每个节点的锁自动续期，只要过半节点存活，锁就不会失效。

3.6 MultiLock：容易和 RedLock 搞混的「联锁」

RedissonMultiLock 与 RedissonRedLock 都是 RLock 的组合体，差异只在判定规则：

MultiLock（联锁） RedLock（红锁）
成功条件 全部锁都拿到才算成功 过半节点拿到即成功
典型场景 一个客户端要同时锁住多个资源（同时锁 A、B 两个账户做转账） 同一资源跨多个独立节点抗单点
节点要求 锁可来自同一或不同实例 必须是多个独立 Master

转账这类「多资源同锁」还有个更朴素的解法：按账户 ID 排序后逐个加锁，用确定性顺序消灭死锁环。

四、RedLock 之争：Kleppmann 与 Antirez 各说了什么

2016 年 Martin Kleppmann（DDIA 作者）发文质疑 RedLock，Antirez（Redis 作者）逐条反驳。要点各取一瓢：

质疑（Kleppmann） 反驳（Antirez） 工程结论
GC 停顿 / 网络延迟可让客户端拿着「已过期的锁」继续写 加锁耗时计入校验：耗时 > 有效期就主动放弃 反驳成立但不彻底——停顿发生在「拿锁之后、写之前」依然危险
时钟跳变（NTP 大步校时）可能让锁提前过期 运维应保证时钟稳定，崩溃节奏可控 生产盯 NTP（用渐进校时），并监控节点时钟漂移
缺 fencing token，挡不住「过期后继续写」 （未正面解决） 金融级写入：锁 + fencing token 下沉到存储层校验，缺一不可

适用边界（比「必须用 / 不能用」更有用）：

  • 按目的选型：防并发冲缓存、防任务重复调度 → RedLock 够用；账户余额这类错一次就赔钱的写入 → 锁 + fencing token，或改用 ZK/DB 强一致方案；
  • 节点跨机房部署时网络分区概率上升，多数派假设更脆弱——同机房独立物理机/虚机是更稳的落法。

一句话划界：为效率用 RedLock，为资产安全用「锁 + fencing token」。

八、生产参数与注意事项

8.1 RedLock 生产参数

  1. 必须使用奇数个节点：3、5、7 个，不能用 2、4、6 个。
  2. 节点之间完全独立：不能是主从、不能是集群，必须是独立 Master。
  3. 性能比普通锁低：因为要写多个 Redis，高并发秒杀可以接受。
  4. 核心业务才用 RedLock：秒杀、库存、订单、支付、账务 → 用 RedLock；后台任务、非核心 → 普通锁即可。
  5. 不要把 leaseTime 设置太长：默认 30s 足够，看门狗会自动续期。
  6. 监控 GC 与时钟：Full GC 长停顿是「持锁者假死」的头号来源，换 ZGC/Shenandoah 或合理设堆，把停顿压到秒级以下；NTP 用渐进校时（chrony 或 ntpd -x），避免大步跳变让锁提前过期；加锁日志里记录实际耗时，逼近 leaseTime 即告警。

8.2 通用参数

  • 锁粒度按业务主键收敛（seckill:stock:{skuId}），一把大锁等于把集群打回单机；
  • 加锁只是开始：拿不到锁的策略（快速失败 / 排队 / 降级）要在需求评审时就定下来；
  • 所有实现都要有防误删（归属校验）与超时兜底，否则一次异常就是死锁。

九、选型总结

  1. 互联网高并发 → Redisson（首选）
  2. 金融强一致 / 核心写入怕主从丢锁 → Redisson RedLock（配合 fencing token）
  3. 强一致协调 → Zookeeper
  4. 无中间件、小项目 → MySQL 乐观锁
  5. 低并发强阻塞 → MySQL 悲观锁
  6. 禁止手写Redis原生锁，坑多（续期、可重入、误删、主从丢锁）

两个高频反问：

  • 「Redis 主从切换丢锁怎么办？」→ RedLock（多独立节点过半）或 fencing token；
  • 「锁超时了业务还没跑完怎么办？」→ 看门狗续期（Redisson 默认行为），而不是把 leaseTime 调大。
