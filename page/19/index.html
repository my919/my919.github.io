类别 选型 用途

1. 概念说明

**动态规划（DP）**解决”多阶段决策最优化”问题，核心思想：把大问题拆成重叠子问题，用一张表记录子问题答案，避免重复计算。

DP 三要素：

  • 状态定义：dp[i] 表示什么（最常见：以 i 结尾 / 前 i 个）。
  • 状态转移：dp[i] 如何由更小的状态推出（核心方程）。
  • 初始条件：最小的子问题答案。

适用信号：求最值（最大/最小/方案数）、有重叠子问题、无后效性（当前决策只影响未来）。

贪心：每一步做局部最优，期望得到全局最优——只对满足”贪心选择性质”的问题成立（如活动安排、找零），必须证明或验证，不是所有最值都能贪心。

判断口诀：能用 DP 先想 DP；贪心是 DP 的特例（无后效 + 局部最优即全局）。

10. 典型案例

案例 1：会议室预订（最少会议室，LeetCode 253，贪心）

问题描述：给定若干会议的 [开始, 结束] 时间区间，求至少需要多少间会议室才能让所有会议互不冲突。

思路（贪心 + 最小堆）：

  1. 按开始时间升序排列会议——先开始的先安排。
  2. 用最小堆维护每间会议室的「结束时间」，堆顶是最早散会的房间。
  3. 每场会议开始前，若堆顶房间已散会（堆顶结束时间 <= 当前开始时间），复用该房间（弹出旧结束时间、压入新结束时间）；否则所有房间都忙，必须新开一间（只压入）。

贪心选择性质证明（交换论证）：会议按开始时间依次处理，若存在已散会的房间，把当前会议分配给「最早散会」的房间不会比分配给其他房间差——其他房间散得更晚，留着接待以后开始（开始时间不早于当前）的会议只会更宽裕；若连最早散会的房间都还没散会，则没有任何房间能接下当前会议，新开房间是被迫的、也是最优的。堆大小的峰值恰好等于最少会议室数。

案例 2：打家劫舍 II（环形 DP，LeetCode 213）

问题描述：房屋排成一个环，每间房内有金额 nums[i]，不能同时偷相邻两间（首尾也算相邻），求能偷到的最大金额。

思路（环形拆成两个线性问题）：

  • 状态定义：dp[i] = 只考虑前 i 间房（线性排列）时能偷到的最大金额。
  • 转移方程：第 i 间要么不偷（收益 dp[i-1]），要么偷（收益 dp[i-2] + nums[i]），取二者大值：dp[i] = max(dp[i-1], dp[i-2] + nums[i])。
  • 环形处理技巧：首尾不能同时选，任何合法方案必然属于「不偷第一间」或「不偷最后一间」之一，且这两类方案都合法。于是答案 = max(线性DP(1..n-1), 线性DP(0..n-2))，把环剪成两条链。

8. 典型案例

案例 1：TopK 问题三种解法对比（第 K 大元素，LeetCode 215）

问题描述：在无序数组中找第 K 大的元素（如 [3,2,1,5,6,4]，K=2，答案为 5）。

思路：

  • 堆：维护一个大小为 K 的小顶堆，遍历过程中堆超过 K 个就弹出堆顶最小值，结束时堆顶即第 K 大——适合流式数据与在线场景。
  • 快速选择：借鉴快排分区，每次只继续处理目标所在的那一段（不递归另一段），期望线性时间；最坏 O(n²)，需随机化 pivot。
  • 全排序：排序后直接取第 K 个，最省心，但做了多余的排序工作。

复杂度分析：

方法 时间复杂度 空间 适用场景
小顶堆 O(n log k) O(k) 流式数据、不能改原数组、k 较小
快速选择 平均 O(n)，最坏 O(n²) O(1) 追求最快、允许打乱原数组

易错点：求第 K 大用小顶堆（堆顶就是答案），求第 K 小才用大顶堆，堆的方向容易写反；快速选择会原地打乱数组，需要保留原序时先 nums.copy()；pivot 不随机化时，有序输入会退化到 O(n²)。

案例 2：旋转排序数组搜索（LeetCode 33）

问题描述：升序数组在某个下标处被旋转（如 [0,1,2,4,5,6,7] → [4,5,6,7,0,1,2]），元素互不相同。给定 target，返回其下标，不存在则返回 -1，要求 O(log n)。

思路（变体二分）：旋转后的数组分成两段，每段各自有序。每次算出 mid 后，先判断哪一段有序，再判断 target 是否落在该有序段内：

  1. 若 nums[left] <= nums[mid]，左段 [left, mid] 有序：target 落在 [nums[left], nums[mid]) 内则收缩右边界，否则去右段。
  2. 否则右段 [mid, right] 有序：target 落在 (nums[mid], nums[right]] 内则收缩左边界，否则去左段。

易错点：判断左段有序要用 <= 而非 <（两指针相邻时 left == mid）；必须先判断 mid 落在哪段有序，不能直接拿 target 与 nums[mid] 比较就决定方向；端点判断要带等号（nums[left] <= target），否则漏掉端点元素；收缩边界仍是 mid ± 1，写成 mid 会死循环。

9. 常见误用与陷阱

陷阱 错误表现 正确做法
二分边界混用 while left <= right 却配 right = mid，或 left < right 配 right = mid - 1，导致死循环或漏解 闭区间模板：<= 配 mid ± 1；左闭右开模板：< 配 right = mid，全程只用一套
mid 计算溢出 C++/Java 中 (left + right) / 2，两数接近 INT_MAX 时整数溢出 统一写 left + (right - left) // 2（Python 无溢出也保持习惯）
快排最坏 O(n²) 固定取首元素做 pivot，遇到有序数组递归树退化成链 随机 pivot 或三数取中；小区间切换插入排序
破坏稳定性 需要多关键字保序时用快排，相等元素的相对顺序被打乱 有稳定性需求用归并排序或内置 Timsort；合并时用 <= 而非 <
自定义比较器返回值错误 cmp_to_key 的回调返回布尔值，True/False 被当成 1/-1，排序语义全乱 比较函数严格返回负数/0/正数，分别表示小于/等于/大于
旋转数组直接套二分 未判断 mid 落在哪个有序段就收缩区间，答案时对时错 先用 nums[mid] 与端点比较确定有序段，再判断 target 归属

1. 概念说明

Vue 3 是渐进式前端框架：核心是声明式渲染——你声明”界面 = f(状态)”，状态变化自动更新视图。渐进式的含义是：可以从一个 <script> 引入的页面级脚本，一路扩展到路由、状态、SSR、工程化的完整应用，接入范围由项目需要决定。

四个核心概念：

  • 响应式（Reactivity）：基于 Proxy 拦截对象读写，依赖收集 + 派发更新。
  • 组件（Component）：UI 复用单元，props 进、事件出。
  • 模板（Template）：声明式描述 DOM，指令（v-if / v-for / v-model / @click）把状态与视图绑起来。
  • 生命周期：组件从创建、挂载、更新到卸载的钩子序列，用来放置副作用（请求、定时器、清理）。
  • Composition API：按逻辑组织代码（setup + ref/reactive/computed/watch），替代 Options API 的按选项组织——细节见进阶篇。
  • 虚拟 DOM：先算差异再更新真实 DOM，批量高效。

9. 典型案例：UGC 短视频上传转码管线

问题背景：App 允许用户上传 60s 竖屏视频，手机端拍出的码率/分辨率五花八门，Web 端播放常卡在加载；个别 4K 素材直接把转码机 CPU 打满，整个服务雪崩。

方案：上传后先 ffprobe 摸底 → Celery 队列限并发异步转码 → 转出 720p/480p 两档 HLS + 封面抽帧 → 对象存储托管，mp4 兜底输出加 -movflags +faststart 保证秒开。

踩坑点：

  • 忘加 -movflags +faststart：moov box 在文件尾，浏览器必须全量下载才能播，”卡在加载”多半是它。
  • 上传接口里同步转码：请求超时、用户重传、机器打满三连——转码必须丢队列异步做。
  • worker_concurrency 不限：10 个 4K 任务并行把 CPU 顶满，所有任务互相拖死。
  • 竖屏视频用 scale=1280:-2 写死宽度：画面被裁成横条——用 scale=-2:{height} 按高度缩放。
  • 任务不幂等：重试时 ffprobe 阶段源文件已被清理直接报错——重试前先检查产物是否存在。

11. 典型案例：新人入职环境一键搭建脚本

问题背景：团队每来一名新人，配本地环境平均耗时 1-2 天：装 JDK/Node/工具链、配 Git、装编辑器插件，各人环境还不一致，联调时”我这边好好的”频发。

配套把 .mise.toml、.vscode/extensions.json、settings.json 提交进仓库，环境随代码走。

关键实践：脚本幂等（重复执行不报错）；版本管理工具统一用 mise；IDE 配置进版本库。

踩坑点：macOS 与 Linux 包管理器命令不同导致脚本中断——用 brew install x || apt install x 兜底；mise activate 只对当前 shell 生效，忘记写进 rc 文件会”下次打开终端就没 node 了”。

测试 · 自动化

测试体系总体框架与学习导航。各层测试实战、压测与性能容量细节由专题文章承担，本文只讲概念与路径。

1. 概念说明

测试金字塔（投入与收益的平衡）：

层级 验证什么 特点
单元测试 单个类/函数逻辑 毫秒级、定位准
集成测试 模块与中间件协作 秒级、接近真实
API 测试 接口契约与业务流 模拟用户调用

测试原则：测行为不测实现、先写测试再写代码（TDD）、测试要独立可重复、快速反馈。

覆盖率不是一切：覆盖率衡量”哪些代码跑了”，不保证”断言是否正确”。重点测核心业务路径、边界条件、异常分支，追求 80% 行覆盖 + 高价值断言。

  • 第二章：集成测试与 E2E 测试：Testcontainers 真实中间件、API 契约测试
  • 端到端测试实战指南：Playwright 端到端落地与冒烟集设计
  • 全链路压测实战（生产环境）：生产压测的隔离、造数与风控
  • 性能测试与容量规划实战：压测指标、瓶颈定位与容量评估

3. 测试体系落地清单

阶段 动作
1. 单测补齐 Service/Mapper 核心逻辑 ≥80%
2. 集成测试 关键仓储与事务用 Testcontainers
3. API 测试 所有对外接口（成功+失败路径）
4. E2E 冒烟 核心用户旅程 5-10 条

4. 常见误用与陷阱

坑 现象/后果 解法
测试共享可变状态（static 字段/单例被改） 单独跑绿、全量跑红 每用例自建上下文，@BeforeEach 重置
误以为 @Transactional 会清理所有数据 只回滚本连接的 DB 操作，REQUIRES_NEW/Redis/MQ 不回滚 真清理用 @Sql 清表或容器重建

无断言测试 跑了等于没跑，覆盖率假高 断言结果 + verify 关键交互
用例依赖执行顺序 顺序一变全崩 用例相互独立，数据自备自清
时间相关用例不稳定 跨天/时区偶发失败 注入 Clock，测试用固定时钟
断言错误提示文案 改个提示语几十个用例全红 断言错误码等稳定契约

1. 概念说明

编码规范是团队统一的代码书写约定，目标是可读、可维护、可审查：代码是写给人看的，规范的代码降低沟通成本、减少低级 bug（命名歧义、魔法数字、空指针）。

规范三层落地：

  1. 文档层：团队约定成文（本文）。
  2. 工具层：编辑器 + CI 自动执行（强制，不靠自觉）。
  3. 审查层：Code Review 检查规范与设计。

核心原则：局部可读性 > 技巧炫耀；显式 > 隐式；简单 > 聪明。

11. 典型案例：规范从”墙上有”到”CI 门禁”的落地

问题背景：某 15 人团队早有编码规范文档，但形同虚设：缩进混用、魔法数字遍地、提交信息随缘。CR 时纠结格式浪费大量时间，线上问题却来自真正的逻辑缺陷。

方案：分层落地——格式问题交给工具自动修，规范问题交给 CI 门禁阻断，CR 只看设计、正确性与可维护性。

第一阶段：编辑器层（自动格式化，零成本）

第二阶段：CI 门禁（违规即失败）

第三阶段：SonarQube 门禁阈值（防”新债入场”而非”清旧债”）

指标 门禁条件 说明
新增阻断/严重问题 = 0 新代码必须干净
新增代码覆盖率 ≥ 60% 关键路径必须测试
重复率 ≤ 3% 控制复制粘贴

关键实践：先全量跑一次 Checkstyle 生成存量清单并单独治理，门禁只拦新增；规则从宽到严每两周收紧一次，不搞”一步到位”。

踩坑点：一上来开全量规则，积压几千个告警，团队第一反应是找 bug 工具关掉门禁——正确做法是”新代码零容忍、存量按计划偿还”；另一坑是 CI 只在合并时跑，发现问题太晚，需配合 pre-commit 钩子提前拦截。

规范只写文档不接工具 三个月后无人遵守，文档过期 CI 门禁强制，工具层优先
规则一步到位全量开启 存量告警几千条，团队关闭门禁 新代码零容忍 + 存量分批治理
