第四章：Nginx 缓存与性能调优

概念基础

  1. 缓存在网关层最划算：proxy_cache 让重复的后端响应停在 Nginx 本地磁盘/内存，QPS 高峰被削平，后端直接减负。
  2. 压缩是免费带宽：gzip（文本）与 brotli（第三方模块）能把 JS/CSS 压到原体积 20%~30%，首屏时间立竿见影。
  3. 静态路径靠 sendfile：sendfile + tcp_nopush 走内核零拷贝，open_file_cache 缓存文件元数据——静态服务的三连优化。
  4. 容量公式要心里有数：最大连接 ≈ worker_processes × worker_connections；长连接 keepalive 减少握手次数。
  5. 调优先测量：改参数前先 ab/wrk 压测拿基线，盯 access_log 的 $request_time 与系统 CPU/内存，避免「凭感觉调参」。

2. 缓存命中排查

动态接口慎缓存：带 Cookie/Authorization 的响应默认不该缓存；必要时用 proxy_cache_bypass $http_authorization; + proxy_no_cache $http_authorization; 显式绕开。缓存清理的完整方案见下文「缓存清除三种路子」。

3. 缓存目录分层与键设计

  1. levels=1:2：缓存文件按哈希建两级子目录（如 /var/cache/nginx/app/c/29/），避免单目录几十万文件拖垮文件系统查找；
  2. keys_zone 容量：1MB 共享内存约存 8000 个 key 的元数据——50MB ≈ 40 万条缓存，据此估算规模；
  3. proxy_cache_key 默认值：$scheme$proxy_host$request_uri——注意不含任何请求头；
  4. 多语言/多端站点：把差异维度加进 key，如 proxy_cache_key "$scheme$host$request_uri$http_accept_language";，否则中文用户可能拿到英文缓存。

4. 防回源击穿

热点 key 过期瞬间，上万请求同时穿透到后端（缓存击穿）——四个参数按住：

组合含义：lock 挡并发、stale 兜底、background_update 提前刷新、min_uses 防缓存被长尾污染。

顺带区分两个易混概念：

  1. 缓存穿透：查询不存在的数据，缓存永不命中、请求直达后端——对空结果也缓存短 TTL（proxy_cache_valid 404 1m;）或前端布隆过滤器应对；
  2. 缓存雪崩：大量 key 同时过期——给 TTL 加随机抖动（基础 10m ± 2m），避免齐刷刷同时失效。

六、OpenResty：会写 Lua 的 Nginx

OpenResty 把 LuaJIT 嵌进 Nginx 事件循环（lua-nginx-module），在请求各阶段执行 Lua 脚本——不用编译 C 模块就能获得可编程网关。Kong、APISIX 等知名 API 网关都是 OpenResty 之上的产物。Lua 可挂载的阶段：rewrite_by_lua（改写）、access_by_lua（鉴权）、content_by_lua（产出响应）、log_by_lua（日志），网关类逻辑大多落在 access 阶段。

适用场景 说明
动态限流/鉴权 查 Redis 令牌桶、验 JWT，毫秒级、不引入额外服务
请求改写 A/B 分流、灰度按 Header 打标转发
边缘计算 CDN 节点上就近处理简单逻辑
缓存增强 共享字典（lua_shared_dict）做进程内热点缓存
自定义监控 log 阶段把指标上报 Prometheus

普通反向代理不需要它；当你开始幻想「在 Nginx 里写业务逻辑」时，就是 OpenResty 的出场时机。

第三章：Nginx HTTPS 与安全

第三章：Nginx HTTPS 与安全

概念基础

  1. TLS 终结点：证书挂在 Nginx，客户端到 Nginx 走加密，Nginx 到后端走内网明文——证书申请、续期、算法升级集中在一处。
  2. 证书链要完整：浏览器校验的是「站点证书 → 中间证书 → 根证书」整条链，漏发中间证书是「本地 curl 通、用户浏览器报错」的常见根因。
  3. 301 比配置加密更重要：HTTP 全站 301 跳转 HTTPS，并配合 HSTS 头让浏览器后续强制走 TLS。
  4. 安全是分层的：TLS 之外，还有限流（limit_req）、访问控制（allow/deny、auth_basic）、安全响应头，每层挡一类攻击。
  5. 密码学背景看 OpenSSL：算法、密钥、证书格式等原理见 第一章：OpenSSL 命令行入门与常用操作总览，本章聚焦落地。

本章 openssl 自签命令已在 OpenSSL 3.x 验证；nginx 配置基于官方语法书写（沙箱未装 nginx）。

一、证书申请与自签

1. 生产环境：Let’s Encrypt（certbot）

certbot 会注册 systemd timer（certbot-renew.timer），到期自动续期并 reload nginx，无需人工干预。

2. 本地/内网：openssl 自签（已验证）

自签证书浏览器会告警「不受信任」，仅用于开发联调。

3. 证书自动化进阶

场景 选择
单域名、80 端口可达 certbot / acme.sh 的 HTTP-01 验证
泛域名（*.example.com） 必须 DNS-01 验证（API 自动添加 TXT 记录）
多机共用证书 一台签发 + 分发脚本（rsync/配置中心），别每台各自申请——会触发 CA 速率限制

二、HTTPS server 配置

fullchain.pem 必须包含中间证书（站点证书 + 中间证书按序拼接），只给站点证书就是上面说的「部分用户报错」。

OCSP Stapling 的意义：浏览器默认要向 CA 的 OCSP 服务器查询证书是否被吊销——多一次外部请求拖慢握手，还把访问习惯暴露给 CA。开启 stapling 后由 Nginx 代查并缓存，握手时随证书下发，省延迟又护隐私。

会话复用：把握手成本摊薄

完整 TLS 握手要 2-RTT + 证书校验，会话复用把这笔开销省掉大半：

机制 配置 注意

HTTP/3（QUIC）

  1. QUIC 基于 UDP 443，防火墙/云安全组别忘了放行 UDP；
  2. 首次连接仍走 TCP+TLS（HTTP/2），浏览器拿到 Alt-Svc 后才升级 HTTP/3；
  3. 弱网/移动网络收益最大：QUIC 无 TCP 队头阻塞，WiFi/4G 切换连接不断（connection migration）。

四、限流：limit_req 与 limit_conn

参数 含义
rate=10r/s 平均速率（也可 30r/m）
burst=20 允许突发排队 20 个请求
nodelay 突发请求立刻处理不排队（超 burst 即 503）

五、安全响应头

自查清单：ss -tlnp 确认 80/443 对外、后端端口只绑 127.0.0.1；证书到期监控（openssl x509 -enddate）；error.log 常态化告警。

进阶加固：

  1. DH 参数：若启用 DHE 套件，openssl dhparam -out dhparam.pem 2048 生成后配 ssl_dhparam，防 Logjam 降级攻击（纯 ECDHE 可忽略）；
  2. HSTS preload：max-age 拉到两年并加 includeSubDomains; preload 后可提交进浏览器 preload 列表——不可逆，所有子域名必须支持 HTTPS，慎重；
  3. 证书到期巡检：openssl x509 -enddate -in fullchain.pem 接 crontab 定期检查，别等用户投诉才发现过期。

第二章：Nginx 反向代理与负载均衡

概念基础

  1. 反向代理是系统入口：客户端只认识 Nginx，真实后端（Spring Boot/Node/Go）藏在 upstream 里——发布、扩缩容、灰度都对客户端无感。
  2. upstream 是逻辑集群：多个后端实例组成一个名字，proxy_pass http://集群名 即完成负载均衡；默认轮询，还有权重、ip_hash、least_conn。
  3. 转发要补头：后端想拿到真实 IP、真实协议，必须配 X-Real-IP、X-Forwarded-For、X-Forwarded-Proto——漏配是日志全是 127.0.0.1 的元凶。
  4. proxy_pass 末尾斜杠有语义：带 / 会替换 location 前缀，不带则原样拼接——路径多一层/少一层的事故九成出在这。
  5. 连接也要调参：proxy_http_version 1.1 + keepalive 复用连接，超时/缓冲/大文件上传各有专属参数。

一、最小反向代理

头 作用

X-Real-IP 客户端真实 IP（单层代理）
X-Forwarded-For 代理链 IP 列表，$proxy_add_x_forwarded_for 自动追加
X-Forwarded-Proto 客户端是 http 还是 https（后端生成 https 链接必需）

二、proxy_pass 路径规则（高频坑）

记忆法：proxy_pass 的 URL 部分会替换掉 location 匹配的部分；不带路径（只有 host:port）则原样透传。改一条 proxy_pass 必跑 nginx -t + 抓包/日志确认后端实际收到的路径。

四、健康检查与故障摘除

被动检查（开源版自带）

开源 Nginx 不主动探测后端，而是用真实请求的结果判定后端死活：

参数 含义
max_fails fail_timeout 窗口内失败次数达阈值即摘除
fail_timeout 既是统计窗口，也是被摘除后的「冷却时间」
slow_start 恢复节点缓慢放量，避免冷缓存/冷 JIT 被瞬间打满
proxy_next_upstream 定义哪些失败场景换机重试（默认 error + timeout）

第三章：PyTorch GPU 加速与混合精度

概念基础

  1. GPU 擅长并行不擅长分支：大矩阵乘/卷积在 GPU 上快几十倍；数据搬运（CPU↔GPU）反而是瓶颈，少拷贝、大批次是优化方向。
  2. 设备要对齐：模型与数据必须在同一设备，RuntimeError: Expected all tensors to be on the same device 是新手第一错。
  3. AMP 混合精度的本质：前向用 FP16/BF16 省显存提速，梯度更新用 FP32 保精度；autocast + GradScaler（FP16 场景）成对出现。
  4. 显存不够不等于换卡：梯度累积等效大 batch、梯度检查点用算力换显存、小批次 + 累加，都是工程正解。
  5. 测量优先：torch.cuda.synchronize() + 计时、nvidia-smi 看占用，先定位瓶颈（数据加载 or 计算 or 搬运）再优化。

概念基础

  1. nn.Module 是模型的骨架：继承后在 __init__ 里声明层、在 forward 里组织数据流；参数注册、.to(device)、state_dict 保存全部自动获得。

  4. train/eval 切换不可少：Dropout、BatchNorm 在训练与推理行为不同；验证前必须 model.eval()，验证后 model.train()。
  5. 泛化靠工程手段：验证集监控、早停、学习率调度、正则化（weight_decay/Dropout）共同决定模型能否落地。

八、视图、共享内存与就地操作

  • view/reshape/permute/t 多数是视图（共享底层存储），改视图会改原张量；
  • 就地操作带下划线：add_/mul_/zero_()，省显存但会破坏 autograd 需要的中间值，训练计算图里慎用；
  • clone() 才是深拷贝；x.data 已弃用，绕开 autograd 请用 detach()。

高频报错：RuntimeError: a view of a leaf Variable that requires grad is being used in an in-place operation——把就地运算改成普通运算即可。

8.1 einsum：复杂收缩一行可读

8.2 张量与 Python 标量的边界

规则：只要进了日志、列表、指标累加，就先 .item() 转成 Python 标量；留在张量形态会把整个计算图拖着不放，是显存缓慢上涨的隐形来源（第三章细讲）。

第十六章：Zigbee：基于 802.15.4 的 Mesh 组网

概念基础

  1. Zigbee 是构建在 IEEE 802.15.4（2.4GHz 低速率无线 PHY/MAC）之上的完整协议栈：802.15.4 只管「把帧发出去」，Zigbee 在其上定义 NWK / APS / ZDO 与应用层 ZCL，解决「组网、路由、互操作」。
  2. Mesh 自愈网络：Coordinator 建网，Router 中继扩展覆盖，End Device 低功耗休眠——多跳 mesh 让覆盖随节点密度增长，单点故障可绕行。
  3. 互操作靠 ZCL：Cluster（集群） 把「灯开关 0x0006、调光 0x0008」等语义标准化，不同厂商设备因此可以混搭组网。
  4. 功耗与角色绑定：Router 必须常供电，End Device 靠休眠 + 父节点代收省电；设计网络前要先想清楚每个节点的角色。
  5. 定位：智能家居（灯、开关、传感器）、楼宇自动化的主流方案之一；手机直连场景选 BLE，公里级广域选 LoRaWAN，高吞吐选 Wi-Fi。

一、802.15.4 基础

  • PHY/MAC：短帧、CSMA-CA、AES-128 链路加密。

频段 信道 速率 说明
2.4 GHz 16 个（11~26） 250 kbps 全球通用，Zigbee 主流
915 MHz 10 个 40 kbps 北美
868 MHz 1 个 20 kbps 欧洲
  • MTU：MAC 层帧最大 127 字节，扣除头尾后应用可用载荷约 80 字节——Zigbee 应用必须小包设计，大传输靠 APS 分片。

  • 2.4G 共存：与 Wi-Fi 频段重叠，信道选择（15/20/25/26 避开 Wi-Fi 1/6/11 主峰）是部署要点。

二、设备角色

角色职责详解

  • Coordinator（协调器）：上电扫信道选最优，创建 PAN；存放信任中心（Trust Center）职能，发放网络密钥。建网完成后它通常也兼 Router。
  • Router（路由器）：必须保持接收常开（所以不能用电池），维护路由表与子节点表，为 End Device 代收缓存报文。
  • End Device（终端）：默认睡死，周期醒来 Data Request 问父节点「有没有我的数据」； poll 间隔越短响应越快但越耗电。典型功耗：休眠 < 5 µA，收发瞬间 20~30 mA。

路由机制（AODVjr 概念）

  • Many-to-One：传感器网络常用变体，所有节点路由汇聚到网关，省各自发现的开销。
  • 地址分配：Zigbee PRO 用分布式随机分配；短地址冲突由冲突检测机制解决。
  • 自愈不是瞬时的：路由重建需要秒级时间，强实时场景要给路径冗余。

三、ZCL（Zigbee Cluster Library）

与 第十三章：Bluetooth 与 BLE：GATT 模型与低功耗设计 GATT 类似：标准化集群/属性/命令，保证互操作。

ZCL 帧结构（概念）

  • Client / Server 侧：Cluster 区分服务端（持有属性，如灯）与客户端（发命令，如开关面板）——一个设备的 Endpoint 上两侧都可挂。
  • 通用命令：Read/Write Attributes、Configure Reporting、Read Reporting Config 等对所有 Cluster 通用。
  • Cluster 专属命令：On/Off 的 On/Off/Toggle；Level Control 的 Move-to-Level（带渐变时间）。
  • Attribute Reporting：属性变化主动上报（带最小/最大间隔约束），是传感器低功耗上报的标准机制——与 CoAP Observe、BLE Notify 异曲同工。

绑定（Binding）机制

开关面板怎么知道控制哪盏灯？靠绑定表：把面板 Endpoint 的 On/Off Cluster Client 绑定到灯的短地址 + Endpoint。绑定可出厂预置，也可通过 ZDO 在入网时配置——这是 Zigbee「无中心本地控制」（网关断电灯照常可控）的实现基础。

第十五章：USB 总线：拓扑、描述符与 CDC 虚拟串口

概念基础

  1. USB（Universal Serial Bus，通用串行总线）是 主机中心（Host-centric） 的有线总线：所有事务都由 Host 发起，Device 只能被动响应——与 CAN 的多主对等、LIN 的主从调度都不相同。
  2. 树形寻址：Host 经 Root Hub → Hub 树形扩展挂载设备，靠枚举过程为每个设备分配唯一地址，再读描述符获知它是谁、能做什么。
  3. 描述符即自描述：设备描述符 → 配置 → 接口 → 端点层层描述，插入即枚举，无需跳线或硬编码地址——「即插即用」的机制本质。
  4. 速度分级演进：Low/Full/High Speed（1.5M/12M/480 Mbps）→ USB 3.x（5 Gbps+）→ USB4；MCU 侧 Full Speed 12 Mbps 仍最常见。
  5. 定位：PC 与外设的标准互联；嵌入式里最常见的玩法是 CDC 虚拟串口与 HID，Type-C 时代还要关注 PD 供电协商与 Alt Mode。

一、拓扑

  • Host 发起事务；Device 响应。
  • OTG 设备可切换 Host/Device（手机接 U 盘）。

补充规则：

  • 最多 5 级 Hub、127 个设备（7 位地址，地址 0 保留给未枚举设备）。
  • Host 轮询：连 Interrupt 端点也是 Host 按声明周期来「问」设备有没有数据——USB 没有真正意义上的设备中断。
  • 帧定时：Full Speed 每 1 ms 一个 SOF 帧，所有传输被调度进帧里，这是 USB 带宽分配的基本节拍。

二、速度等级

版本 速率（量级）

USB 3.x 5 Gbps+
USB4 基于 Thunderbolt 生态

完整分级：

等级 速率 典型场景
Low Speed 1.5 Mbps 键鼠（延迟不敏感、线材便宜）
Full Speed 12 Mbps MCU CDC/HID，绝大多数 STM32F1/F4

三、描述符与 Class

  • 设备描述符 → 配置 → 接口 → 端点。
  • Class：HID（键鼠）、MSC（U 盘）、CDC-ACM（虚拟 第四章：UART）、Audio、Video 等。
  • Vendor Specific：自定义 Bulk/Interrupt 端点 + 主机驱动/libusb。

描述符层级详解

一个设备可以有多个接口：如「CDC + HID」复合设备——调试串口与用户按键共存，PC 上同时出现 COM 口和 HID 设备。

四种传输类型

第十四章：NFC 近场通信：工作模式与 NDEF

概念基础

  1. NFC（Near Field Communication，近场通信）工作在 13.56MHz，通信距离仅几厘米——「近」是刻意设计：贴一下才触发，天然防误触，适合支付与门禁。
  2. 有源与无源：Reader 产生射频场并为 passive Tag 供电（无源卡没有电池，靠感应取电通信），这是它与蓝牙等「双方都要电池」技术最本质的差别。
  3. 三种工作模式：读卡/写卡（碰 Tag）、卡模拟（手机变门禁卡/交通卡）、点对点（两设备交换小数据，已较少用）。
  4. NDEF 是通用数据格式：把 URI、文本、Wi-Fi 配置、蓝牙配对信息统一封装进 Tag，手机一碰即触发对应系统动作。
  5. 定位：身份识别、小额支付、设备配对加速器（给 BLE 递密钥）；大数据传输交给 Wi-Fi/蓝牙，NFC 只负责「握手」。

一、工作模式

模式 说明
Reader/Writer 读或写 passive Tag
Card Emulation 手机模拟门禁/交通卡
Peer-to-Peer 两设备交换小数据（较少用）

物理层怎么工作

  • 负载调制：Tag 没有发射机——它通过切换自身负载阻抗，改变 Reader 天线上的电压，把数据「反射」回去（类似雷达应答机）。
  • 速率：ISO 14443 典型 106 kbps，也有 212/424/848 kbps 档位。
  • 供电：Reader 场强可为 Tag 提供数 mA 电流——能量采集型 Tag（如带 I2C 接口的 NTAG I2C）甚至能给外挂的小 MCU/传感器供电，做成「无电池、碰一下才活过来」的数据记录器。

三种模式的角色对照

模式 发起方 被动方 典型场景
Reader/Writer 手机/读卡器 无源 Tag 读海报标签、写配置
Card Emulation 闸机/ POS 机 手机（模拟成卡） 门禁、支付
Peer-to-Peer 双方有源 双方有源 安卓 Beam（已废弃）

二、Tag 标准

  • Type 1~4 Tag：不同容量与协议（NFC Forum）。
  • MIFARE Classic/Ultralight：交通、门禁（Classic 安全性已弱，新项目慎用）。
  • ISO 14443 A/B、ISO 15693（稍远，仍近场）。

NFC Forum Tag 类型速查

类型 基于 容量 速率 说明
Type 1 ISO 14443A 96 B~2 KB 106k 最便宜，玩具/标签
Type 2 ISO 14443A 48 B~2 KB 106k NTAG21x / MIFARE Ultralight，最常用
Type 3 FeliCa 大 212/424k 日本交通卡（Suica）
Type 4 ISO 14443A/B 32 KB 最高 848k 支持 APDU，银行卡/护照级安全

卡片家族与选型

  • NTAG213/215/216：NDEF 容量 144/504/888 字节，NDEF 应用事实标准，几毛钱一片。
  • MIFARE Classic 1K：Crypto-1 加密已被攻破（2008 年公开），存量巨大但新项目勿用；升级选 DESFire EV2/EV3。
  • MIFARE DESFire：真 AES/3DES + 文件系统式存储，支付与门禁主流。
  • ISO 15693（ vicinity card）：距离可到 1 米级，图书馆/资产管理用，严格说不算 NFC 手机可读写范围。

三、NDEF（NFC Data Exchange Format）

常用 payload 格式，可封装：

  • URI（打开网页）
  • 文本
  • Wi-Fi 配置（WSC）
  • Bluetooth LE 配对 OOB 数据

手机贴近 Tag 即可触发系统动作（依 OS 策略）。

NDEF 记录结构

关键标志位：MB（Message Begin）、ME（Message End）、SR（Short Record，长度字段 1 字节）、TNF（Type Name Format：Well-known / MIME / URI 等）。

Text 记录与多记录

  • Text（Type=”T”）：首字节为状态字节（bit7=UTF-8/16，低 6 位=语言码长度），随后 en + 实际文本。
  • 一条 Message 可含多 Record：如「URI + 应用包名 Android Application Record」——前者兜底，后者直接拉起指定 App。

天线与布局要点

  • 读卡器天线是 PCB 走线电感，需与匹配网络调谐到 13.56 MHz 谐振；金属外壳/电池遮挡会急剧缩短距离。
  • Tag 侧同理：柔性 FPC 线圈贴金属面要加铁氧体隔磁片。
  • 调试工具：用场强检测卡或示波器探头绕线圈定性看射频场；读距不达标先查匹配再查软件。
