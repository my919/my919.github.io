第二章：PyTorch 模型与训练

概念基础

  1. nn.Module 是模型的骨架：继承后在 __init__ 里声明层、在 forward 里组织数据流；参数注册、.to(device)、state_dict 保存全部自动获得。
  2. Dataset/DataLoader 解耦数据与模型：Dataset 定义「第 i 条样本怎么取」，DataLoader 负责批量化、打乱、多进程预取——大数据训练的前提。
  3. 训练循环是固定四步：optimizer.zero_grad() → forward → loss.backward() → optimizer.step()，一切复杂训练都是这四步的变体。
  4. train/eval 切换不可少：Dropout、BatchNorm 在训练与推理行为不同；验证前必须 model.eval()，验证后 model.train()。
  5. 泛化靠工程手段：验证集监控、早停、学习率调度、正则化（weight_decay/Dropout）共同决定模型能否落地。

  • num_workers：多进程预取，CPU 密集的预处理必开；Windows 下要在 if __name__ == "__main__": 里跑。
  • pin_memory=True：页锁定内存加速 CPU→GPU 拷贝（配合第三章）。
  • 变长序列：用 collate_fn 自定义打包（padding + mask）。

四大高频翻车点：

七、DataLoader 性能调优

GPU 利用率忽高忽低，九成是数据侧瓶颈。按这张表调：

参数 作用 建议
num_workers 预取进程数 CPU 核数的 1/2 ~ 全部；0 = 主进程加载（调试用）
pin_memory 页锁定加速 CPU→GPU 拷贝 GPU 训练恒开

八、早停与训练健壮性

健壮性三件套：早停防过拟合空转；clip_grad_norm_ 防梯度爆炸；每 N step 存 checkpoint 防断电白训（配合第四节断点续训）。

第一章：PyTorch 入门与张量

概念基础

  1. 动态图是 PyTorch 的性格：写 Python 即写模型，前向传播边执行边建图，调试跟普通程序一样打断点——科研与工业界均为主流选择。
  2. Tensor 是唯一主角：torch.Tensor 是带 GPU 加速与自动求导的多维数组，接口与 NumPy 高度相似，会 NumPy 就会一半 PyTorch。
  3. autograd 自动微分：requires_grad=True 的张量参与运算时自动记录计算图，backward() 一步拿到所有梯度，模型训练的地基。
  4. 形状思维：深度学习 90% 的报错是 shape 不对——view/reshape/squeeze/permute 这组变形记必须滚瓜烂熟。
  5. 生态覆盖全链路：torchvision/torchaudio 领域库、Hugging Face 预训练模型（见 第三章：LLM 大语言模型基础）、ONNX 导出部署、DDP 分布式训练。

七、autograd 深入

7.1 计算图是怎么建的

requires_grad=True 的张量参与运算后，产出的新张量带 grad_fn 属性指向上一步的求导函数；backward() 从标量出发沿 grad_fn 链反向遍历，把梯度写进叶子张量的 .grad。

7.2 detach 与 no_grad 的分工

部署级推理 with torch.inference_mode():（更省，禁用版本计数）
冻结参数 p.requires_grad_(False)（微调冻结底层常用）

八、视图、共享内存与就地操作

  • view/reshape/permute/t 多数是视图（共享底层存储），改视图会改原张量；
  • 就地操作带下划线：add_/mul_/zero_()，省显存但会破坏 autograd 需要的中间值，训练计算图里慎用；
  • clone() 才是深拷贝；x.data 已弃用，绕开 autograd 请用 detach()。

高频报错：RuntimeError: a view of a leaf Variable that requires grad is being used in an in-place operation——把就地运算改成普通运算即可。

8.1 einsum：复杂收缩一行可读

多 batch 多维张量的矩阵乘用 einsum 写，维度含义一目了然，比连环 permute + matmul 更不易错。

8.2 张量与 Python 标量的边界

规则：只要进了日志、列表、指标累加，就先 .item() 转成 Python 标量；留在张量形态会把整个计算图拖着不放，是显存缓慢上涨的隐形来源（第三章细讲）。

第十六章：Zigbee：基于 802.15.4 的 Mesh 组网

概念基础

  1. Zigbee 是构建在 IEEE 802.15.4（2.4GHz 低速率无线 PHY/MAC）之上的完整协议栈：802.15.4 只管「把帧发出去」，Zigbee 在其上定义 NWK / APS / ZDO 与应用层 ZCL，解决「组网、路由、互操作」。
  2. Mesh 自愈网络：Coordinator 建网，Router 中继扩展覆盖，End Device 低功耗休眠——多跳 mesh 让覆盖随节点密度增长，单点故障可绕行。
  3. 互操作靠 ZCL：Cluster（集群） 把「灯开关 0x0006、调光 0x0008」等语义标准化，不同厂商设备因此可以混搭组网。
  4. 功耗与角色绑定：Router 必须常供电，End Device 靠休眠 + 父节点代收省电；设计网络前要先想清楚每个节点的角色。
  5. 定位：智能家居（灯、开关、传感器）、楼宇自动化的主流方案之一；手机直连场景选 BLE，公里级广域选 LoRaWAN，高吞吐选 Wi-Fi。

一、802.15.4 基础

  • PHY/MAC：短帧、CSMA-CA、AES-128 链路加密。
  • Zigbee 在之上定义 NWK、APS、ZDO 与应用层 ZCL。

802.15.4 物理层参数

频段 信道 速率 说明
2.4 GHz 16 个（11~26） 250 kbps 全球通用，Zigbee 主流
915 MHz 10 个 40 kbps 北美
868 MHz 1 个 20 kbps 欧洲
  • MTU：MAC 层帧最大 127 字节，扣除头尾后应用可用载荷约 80 字节——Zigbee 应用必须小包设计，大传输靠 APS 分片。
  • CSMA-CA：发前先听（CCA），忙则随机退避，避免碰撞；但没有 ACK 之外的冲突恢复，密集网络吞吐会下降。
  • 2.4G 共存：与 Wi-Fi 频段重叠，信道选择（15/20/25/26 避开 Wi-Fi 1/6/11 主峰）是部署要点。

二、设备角色

角色 说明
Coordinator 建网、分配 PAN ID、短地址，通常 1 个
Router 中继、常供电

Mesh 多跳扩展覆盖；路由表由 AODV 类机制维护（依栈实现）。

角色职责详解

  • Coordinator（协调器）：上电扫信道选最优，创建 PAN；存放信任中心（Trust Center）职能，发放网络密钥。建网完成后它通常也兼 Router。
  • Router（路由器）：必须保持接收常开（所以不能用电池），维护路由表与子节点表，为 End Device 代收缓存报文。
  • End Device（终端）：默认睡死，周期醒来 Data Request 问父节点「有没有我的数据」； poll 间隔越短响应越快但越耗电。典型功耗：休眠 < 5 µA，收发瞬间 20~30 mA。

路由机制（AODVjr 概念）

  • Many-to-One：传感器网络常用变体，所有节点路由汇聚到网关，省各自发现的开销。
  • 地址分配：Zigbee PRO 用分布式随机分配；短地址冲突由冲突检测机制解决。
  • 自愈不是瞬时的：路由重建需要秒级时间，强实时场景要给路径冗余。

三、ZCL（Zigbee Cluster Library）

与 第十三章：Bluetooth 与 BLE：GATT 模型与低功耗设计 GATT 类似：标准化集群/属性/命令，保证互操作。

ZCL 帧结构（概念）

  • Client / Server 侧：Cluster 区分服务端（持有属性，如灯）与客户端（发命令，如开关面板）——一个设备的 Endpoint 上两侧都可挂。
  • 通用命令：Read/Write Attributes、Configure Reporting、Read Reporting Config 等对所有 Cluster 通用。
  • Cluster 专属命令：On/Off 的 On/Off/Toggle；Level Control 的 Move-to-Level（带渐变时间）。
  • Attribute Reporting：属性变化主动上报（带最小/最大间隔约束），是传感器低功耗上报的标准机制——与 CoAP Observe、BLE Notify 异曲同工。

绑定（Binding）机制

开关面板怎么知道控制哪盏灯？靠绑定表：把面板 Endpoint 的 On/Off Cluster Client 绑定到灯的短地址 + Endpoint。绑定可出厂预置，也可通过 ZDO 在入网时配置——这是 Zigbee「无中心本地控制」（网关断电灯照常可控）的实现基础。

第十五章：USB 总线：拓扑、描述符与 CDC 虚拟串口

概念基础

  1. USB（Universal Serial Bus，通用串行总线）是 主机中心（Host-centric） 的有线总线：所有事务都由 Host 发起，Device 只能被动响应——与 CAN 的多主对等、LIN 的主从调度都不相同。
  2. 树形寻址：Host 经 Root Hub → Hub 树形扩展挂载设备，靠枚举过程为每个设备分配唯一地址，再读描述符获知它是谁、能做什么。
  3. 描述符即自描述：设备描述符 → 配置 → 接口 → 端点层层描述，插入即枚举，无需跳线或硬编码地址——「即插即用」的机制本质。
  4. 速度分级演进：Low/Full/High Speed（1.5M/12M/480 Mbps）→ USB 3.x（5 Gbps+）→ USB4；MCU 侧 Full Speed 12 Mbps 仍最常见。
  5. 定位：PC 与外设的标准互联；嵌入式里最常见的玩法是 CDC 虚拟串口与 HID，Type-C 时代还要关注 PD 供电协商与 Alt Mode。

主机-设备树形拓扑：

一、拓扑

  • Host 发起事务；Device 响应。
  • OTG 设备可切换 Host/Device（手机接 U 盘）。

补充规则：

  • 最多 5 级 Hub、127 个设备（7 位地址，地址 0 保留给未枚举设备）。
  • Host 轮询：连 Interrupt 端点也是 Host 按声明周期来「问」设备有没有数据——USB 没有真正意义上的设备中断。
  • 帧定时：Full Speed 每 1 ms 一个 SOF 帧，所有传输被调度进帧里，这是 USB 带宽分配的基本节拍。

二、速度等级

完整分级：

三、描述符与 Class

  • 设备描述符 → 配置 → 接口 → 端点。
  • Class：HID（键鼠）、MSC（U 盘）、CDC-ACM（虚拟 第四章：UART）、Audio、Video 等。
  • Vendor Specific：自定义 Bulk/Interrupt 端点 + 主机驱动/libusb。

描述符层级详解

一个设备可以有多个接口：如「CDC + HID」复合设备——调试串口与用户按键共存，PC 上同时出现 COM 口和 HID 设备。

发表于 2026-05-01 更新于 2026-10-25 分类于 嵌入式 本文字数： 4.1k 阅读时长 ≈ 4 分钟

第十四章：NFC 近场通信：工作模式与 NDEF

概念基础

  1. NFC（Near Field Communication，近场通信）工作在 13.56MHz，通信距离仅几厘米——「近」是刻意设计：贴一下才触发，天然防误触，适合支付与门禁。
  2. 有源与无源：Reader 产生射频场并为 passive Tag 供电（无源卡没有电池，靠感应取电通信），这是它与蓝牙等「双方都要电池」技术最本质的差别。
  3. 三种工作模式：读卡/写卡（碰 Tag）、卡模拟（手机变门禁卡/交通卡）、点对点（两设备交换小数据，已较少用）。
  4. NDEF 是通用数据格式：把 URI、文本、Wi-Fi 配置、蓝牙配对信息统一封装进 Tag，手机一碰即触发对应系统动作。
  5. 定位：身份识别、小额支付、设备配对加速器（给 BLE 递密钥）；大数据传输交给 Wi-Fi/蓝牙，NFC 只负责「握手」。

一、工作模式

模式 说明
Reader/Writer 读或写 passive Tag
Card Emulation 手机模拟门禁/交通卡
Peer-to-Peer 两设备交换小数据（较少用）

物理层怎么工作

  • 负载调制：Tag 没有发射机——它通过切换自身负载阻抗，改变 Reader 天线上的电压，把数据「反射」回去（类似雷达应答机）。
  • 速率：ISO 14443 典型 106 kbps，也有 212/424/848 kbps 档位。
  • 供电：Reader 场强可为 Tag 提供数 mA 电流——能量采集型 Tag（如带 I2C 接口的 NTAG I2C）甚至能给外挂的小 MCU/传感器供电，做成「无电池、碰一下才活过来」的数据记录器。

三种模式的角色对照

模式 发起方 被动方 典型场景
Reader/Writer 手机/读卡器 无源 Tag 读海报标签、写配置
Card Emulation 闸机/ POS 机 手机（模拟成卡） 门禁、支付
Peer-to-Peer 双方有源 双方有源 安卓 Beam（已废弃）

二、Tag 标准

  • Type 1~4 Tag：不同容量与协议（NFC Forum）。
  • MIFARE Classic/Ultralight：交通、门禁（Classic 安全性已弱，新项目慎用）。
  • ISO 14443 A/B、ISO 15693（稍远，仍近场）。

NFC Forum Tag 类型速查

类型 基于 容量 速率 说明
Type 1 ISO 14443A 96 B~2 KB 106k 最便宜，玩具/标签
Type 2 ISO 14443A 48 B~2 KB 106k NTAG21x / MIFARE Ultralight，最常用
Type 3 FeliCa 大 212/424k 日本交通卡（Suica）
Type 4 ISO 14443A/B 32 KB 最高 848k 支持 APDU，银行卡/护照级安全

卡片家族与选型

  • NTAG213/215/216：NDEF 容量 144/504/888 字节，NDEF 应用事实标准，几毛钱一片。
  • MIFARE Classic 1K：Crypto-1 加密已被攻破（2008 年公开），存量巨大但新项目勿用；升级选 DESFire EV2/EV3。
  • MIFARE DESFire：真 AES/3DES + 文件系统式存储，支付与门禁主流。
  • ISO 15693（ vicinity card）：距离可到 1 米级，图书馆/资产管理用，严格说不算 NFC 手机可读写范围。

三、NDEF（NFC Data Exchange Format）

常用 payload 格式，可封装：

  • URI（打开网页）
  • 文本
  • Wi-Fi 配置（WSC）
  • Bluetooth LE 配对 OOB 数据

手机贴近 Tag 即可触发系统动作（依 OS 策略）。

NDEF 记录结构

关键标志位：MB（Message Begin）、ME（Message End）、SR（Short Record，长度字段 1 字节）、TNF（Type Name Format：Well-known / MIME / URI 等）。

第十三章：Bluetooth 与 BLE：GATT 模型与低功耗设计

概念基础

  1. Bluetooth（蓝牙）工作在 2.4GHz ISM 频段，是短距离无线技术；今天物联网的主角是 BLE（Bluetooth Low Energy，蓝牙低功耗，4.0 起），为纽扣电池供电的小设备而生。
  2. BLE 的核心是 GATT：设备暴露服务（Service）→ 特征值（Characteristic）的属性树，手机等 Central 通过读写/订阅特征值与 Peripheral 交互，数据模型像访问资源一样清晰。
  3. 广播先行：BLE 设备平时广播（可携带自定义数据，即 Beacon），Central 扫描后再发起连接——不连不上、先广播，这与 Wi-Fi「先关联再通信」完全不同。
  4. 为什么省电：深度休眠 + 快速建立连接，只在事件发生时短暂收发；配合 Notify/Indicate 让外设主动推送，避免轮询空耗电。
  5. 定位：手环、传感器、智能家居直连手机的场景；需要跨厂商标准化互操作时选 Zigbee（见 第十六章：Zigbee：基于 802.15.4 的 Mesh 组网），配对加速可用 NFC 递密钥。

连接后通过 ATT/GATT 读写特征值（Characteristic）。

广播与扫描的过程

要点：

  • 广播信道只有 3 个（37/38/39），避开 Wi-Fi 拥堵的 1/6/11 信道间隙，降低干扰碰撞。
  • 广播包 31 字节（BLE 4.x），5.0 起扩展广播可达 255 字节（在数据信道二次加载）。
  • Beacon（iBeacon/Eddystone）：永远只广播不连接，靠 MAC + 自定义字段做定位与触发，是 Broadcaster 角色的典型应用。
  • 连接间隔是功耗旋钮：间隔短延迟低但耗电，传感器常设 500 ms~1 s。

二、GATT 模型

  • UUID：16 位标准 UUID 或 128 位自定义。
  • Notify/Indicate：外设主动推送数据，省 polling 功耗。

ATT 属性协议的本质

GATT 是 ATT（Attribute Protocol） 的上层组织。ATT 把一切都抽象为属性：

  • Handle：属性的地址，客户端按 handle 读写。
  • Permissions：读/写/加密/认证要求，越权访问返回错误码。
  • 服务发现：客户端连接后先遍历属性表，找到各 Service/Characteristic 的 handle——这就是「连接后先转圈一秒」在做的事。

Characteristic 的三件套

以自定义温度特征为例：

组成 UUID 类型 内容
Declaration 0x2803 声明：这是个特征，属性在下一个 handle，支持 Read+Notify
Value 自定义 128 位 真正的数据（如 4 字节 float 温度）
CCCD 0x2902 Client Characteristic Configuration：客户端写它开关 Notify

CCCD 是 Notify 的开关：Central 写 0x0001 到 CCCD 后，Peripheral 才有权推送——忘写 CCCD 是「为什么我的 Notify 不工作」的头号原因。

发表于 2026-05-01 更新于 2026-10-25 分类于 嵌入式 本文字数： 4k 阅读时长 ≈ 4 分钟

第十二章：LoRaWAN：远距离低功耗星型组网

概念基础

  1. LoRaWAN 是构建在 LoRa 扩频射频之上的开放网络协议：终端节点通过网关接入 Network Server，典型覆盖公里级，专为电池供电、小数据量、上报为主的物联网场景设计。
  2. LoRa ≠ LoRaWAN：LoRa 是 Semtech 的物理层调制技术（Chirp Spread Spectrum，灵敏度高、抗干扰强）；LoRaWAN 是其上的 MAC 层协议（入网激活、速率自适应、双向调度）——「电台」与「通信规约」的关系。
  3. 星型拓扑换功耗：节点只与网关直连一跳，不做 mesh 路由转发，省去中继耗电，换来数年电池寿命；覆盖靠增加网关与 ADR 速率自适应来平衡。
  4. 速率换距离：SF（扩频因子）越大，速率越低、传得越远，网络侧按链路质量动态调整，本质是「速率-距离-容量」的三角权衡。
  5. 定位：智能抄表、资产追踪、农业监测等公里级、极低速率场景；高吞吐走 Wi-Fi/以太网 + MQTT/HTTP，局域 mesh 则选 Zigbee / 蓝牙 Mesh。

先看整体架构：

星型拓扑架构

  Dev1[终端节点] --> GW[LoRa 网关]
  Dev2[终端节点] --> GW
  GW --> NS[Network Server]
  NS --> App[应用服务器]

一、架构

  • Gateway：只做射频转发，不解密应用 payload（取决于模式）。
  • ADR（Adaptive Data Rate）：网络侧调节 SF/功率平衡距离与容量。

LoRa 物理层速览

  • Chirp Spread Spectrum：信号在带宽内线性扫频，扩频带来处理增益，接收灵敏度低至 -137 dBm（比 FSK 好 20 dB 以上）。
  • SF7~SF12：SF 每加 1，速率减半、距离增加、空中时间翻倍。
  • 正交性：不同 SF 的信号可在同频同时存在互不干扰，网关 8 通道并行接收。
  • 带宽：常用 125 kHz（EU868/CN470）、500 kHz（US915 上行）。

各角色职责

角色 职责
End Device 采集数据、按 Class 调度收发、维护会话密钥
Gateway 纯射频中继：把 RF 帧加元数据（RSSI/SNR/时间戳）转 IP，不做协议裁决
Network Server 去重（多网关收到同一帧）、ADR 控制、帧计数校验、路由到应用
Application Server 解密 AppSKey payload、业务逻辑

「网关笨、服务器聪明」让网关可以做到几十美元级，是 LoRaWAN 部署成本低的关键。

二、区域参数

区域 典型频段
EU868 863–870 MHz
US915 902–928 MHz
CN470 470–510 MHz

需遵守当地无线电法规；模块需合规认证。

区域差异不止是频率：

  • EU868：占空比限制（Duty Cycle，常见子带 1% 或 0.1%）——设备每小时最多发 36 秒，直接限制上报频率。
  • US915：频率跳变（FHSS），上行 64+8 信道；无占空比但有 400 ms 驻留时间限制，限制单包大小。
  • CN470：96 上行信道，国内合规主流选择。
  • 选型红线：硬件模块、固件 region 参数、网络服务器频段计划三者必须一致，否则入网即失败。

三、设备 Class

Class 下行窗口 功耗
A 仅上行后两个短窗口 最低，传感器常用
B 附加信标窗口 中
C 几乎常开接收 高，供电设备

Class A 时序（必须掌握）

  • 节点发完才听：RX1 用上行的同信道/速率（或由网络指定），RX2 用固定信道与 SF12（EU868 为 869.525 MHz）。
  • 两个窗口都没收到 → 回去睡觉，下行丢失。下行永远是「发上行时的副产品」，这就是 Class A 省电的本质。
  • 服务器想主动下发？只能等节点下一次上行——做「远程控制路灯」这类需求要么接受分钟级延迟，要么上 Class C。
  • Class B 增加网关周期广播的 Beacon，节点按预约时隙额外开窗；Class C 常供电、常开窗，下行近乎实时（电表、路灯控制器）。

四、MAC 帧结构（概念）

字段 说明
MHDR 消息类型（Join-Request / Confirmed-Up / Unconfirmed-Up 等）
DevAddr 4 字节设备地址，入网后分配
FCnt 帧计数器，防重放；ABP 模式下掉电归零会导致服务器拒收
FOpts 捎带 MAC 命令（如 ADR 应答）
FPort 0 = 纯 MAC 命令；1~223 = 应用端口（应用层多路复用）
MIC 4 字节消息完整性码，NwkSKey 计算

Confirmed 消息要求对端回 ACK，未收到则重发（默认 8 次）——但占空比宝贵，上行通常用 Unconfirmed，靠周期冗余保证到达率。

五、安全

  • Join：OTAA（Over-The-Air Activation，推荐）或 ABP（预置密钥）。
  • AES-128：NwkSKey、AppSKey 分层加密与完整性。
  • 应用层仍可封装 第十一章：CoAP：REST over UDP 的物联网应用协议 或自定义二进制。

OTAA 入网流程

  • 根密钥 AppKey/NwkKey 只出厂烧录一次，永不上空口传输；OTAA 每次入网派生新会话密钥，设备换网络也安全。
  • ABP 直接预置 DevAddr + 两把会话密钥，省一步握手，但密钥固定、FCnt 复位问题多，仅建议实验室用。
  • 双层加密的边界：NwkSKey 管到 Network Server 的完整性，AppSKey 端到端加密到应用服务器——网关和 NS 看不到应用数据明文（诚实网关模型）。

第十一章：CoAP：REST over UDP 的物联网应用协议

概念基础

  1. CoAP（Constrained Application Protocol，受限应用协议）是给单片机、低带宽网络用的应用层协议：把 Web 的 REST 模型（GET / PUT / POST / DELETE 操作资源）搬到 UDP 之上。
  2. 为什么轻量：报文头仅 4 字节起（对比 HTTP 动辄数百字节），二进制紧凑编码，默认端口 5683 / 5684（DTLS），RAM/Flash 占用极小，可直接跑在 6LoWPAN 等受限链路上。
  3. 请求/响应 + 订阅两种模式：既支持类 HTTP 的请求-响应，又通过 Observe（RFC 7641） 让服务器在资源变化时主动推送 NOTIFY，传感器上报无需反复轮询。
  4. 可靠性自选：UDP 本身不可靠，CoAP 用 CON / NON / ACK / RST 消息类型自己决定要不要确认重传——把「要不要可靠」交给应用按需选择。
  5. 定位：资源型设备（一台设备就是一组可读写的资源）的首选；海量消息汇聚与发布订阅则更适合 Broker 型的 MQTT，二者在同一系统里常互补出现。

一、设计目标

  • 低开销：适合 MCU、6LoWPAN、低带宽链路。
  • 异步：支持 Separate 响应（ACK 先回，结果稍后 CON 通知）。

第十章：LIN 总线：单主多从与调度表

概念基础

  1. LIN（Local Interconnect Network，局部互联网络）是低成本的单主多从串行总线：一根总线挂一个 Master 与若干 Slave，常见于车窗、座椅、雨刮等车身电子。
  2. 为什么便宜：基于普通 UART 硬件即可实现，物理层常用单线、12V 电平，收发器（如 TJA1021）远比 CAN 便宜，从节点甚至可用廉价 8 位 MCU——它就是 CAN 的「经济版补充」。
  3. 无仲裁、靠调度：与 CAN 的竞争仲裁不同，LIN 由 Master 固定调度：Master 发 Header（含 PID），对应 Slave 填 Response，时序确定、天然无冲突。
  4. 帧结构简单：Break + Sync(0x55) + PID + Data(1~8) + Checksum，速率约 20 kbps，只适合非安全、低带宽场景。
  5. 定位：动力底盘走 CAN、车身舒适系统走 LIN，网关 ECU 常同时挂两种总线；它的「单主轮询」思想与工业里的 Modbus 主从也一脉相承。

一、角色

  • Master：通常由 Body ECU 担任，发送 Header（含 PID）。
  • Slave：响应 Data 或发布自身数据；无仲裁，时隙由 Master 调度。

更精确地说，Master 节点内部还分两个任务：

  • Master Task：产生帧头（Break/Sync/PID），决定「现在轮到哪个 ID」。
  • Slave Task：Master 自己也挂一个从任务，用于响应「主节点自己需要发布的帧」（如整车状态）。

总线上只有 Master Task 能发起通信——任何时刻只有一个调度者，这就是「确定性」的来源，也是 LIN 不适合对等网络的原因。

二、帧结构（简化）

  • Break：显性低电平较长，同步从机。
  • PID：含 6 位 ID + 2 位奇偶。
  • Checksum：Classic 或 Enhanced（LIN 2.x）。

逐字段剖析

字段 细节
Break 至少 13 位显性低电平 + 间隔符；UART 无法产生普通帧里这么长的低电平，从机据此识别「新的一帧来了」
Sync 0x55 位型 01010101，从机用它测量主时钟并自动校准波特率（自同步），省去晶振——便宜的底气之一
PID 低 6 位 Frame ID（0~63，0x3C/0x3F 等保留）；P0 = ID0⊕ID1⊕ID2⊕ID4，P1 = ¬(ID1⊕ID3⊕ID4⊕ID5) 两位奇偶校验
Data 1/2/4/8 字节，长度由 ID 约定
Checksum Classic 只对 Data 求和取反（进位回卷）；Enhanced（LIN 2.x）把 PID 也纳入，诊断帧仍用 Classic

帧时序与间隔

Header 与 Response 之间有响应间隔，帧与帧之间有帧间隔（均为若干位时间），由调度表定义。从机必须在规定时间内响应，否则主站记为无响应错误。

三、调度表（Schedule Table）

Master 按固定周期发送各 Frame ID，保证确定性延迟；配置在 LDF（LIN Description File）中，工具链生成驱动代码。

调度表实例

  • 周期槽：每个帧分配固定时隙，最坏延迟可计算——这是 LIN 做「车窗防夹」类软实时功能的依据。
  • LDF 文件：描述节点、信号、帧、调度表、波特率，上游工具（如 Vector LINworks）生成 C 驱动骨架，主从双方共用同一份定义保证一致。
  • 事件触发帧：多个从机共用一时隙，仅在数据变化时抢答；冲突时主站回退到逐一轮询（Collision Resolving Table）。

硬件要点：

  • 电平：LIN 线在 0V（显性）与 VBAT（隐性，约 12V）间摆动；Master 端典型 1kΩ 上拉到 VBAT，Slave 端 30kΩ——兼作终端与漏电保护。
  • 收发器职责：把 MCU 的 3.3V UART 电平与 12V LIN 电平互换，并做短路/过温保护。
  • 休眠与唤醒：总线空闲超时后进入休眠（VBAT 侧微安级电流）；任一节点拉低总线 ≥250µs 即唤醒全网。

  • 常见坑：奇偶位算错导致 PID 不被识别；Enhanced/Classic 校验和版本混淆；从机响应超时（中断延迟过长）；调度周期太紧导致总线利用率 100%、诊断帧插不进来。

诊断帧与节点配置

  • 0x3C（Master Request）/ 0x3D（Slave Response）：保留的诊断帧 ID，载荷按 ISO 15765 类诊断服务组织，用于读故障码、刷写配置。
  • NAD 与 SNPD：每个从节点有 NAD（节点地址），出厂时通过 SNPD（从节点位置检测）服务在产线上自动分配——解决「同型号多个从机怎么区分」的量产问题。
  • 配置服务：读写从机的供应商 ID、功能 ID、版本号，OTA 与售后依赖这套机制。

第九章：CAN 总线：帧结构、多主仲裁与 CAN FD

概念基础

  1. CAN（Controller Area Network，控制器局域网）是 Bosch 为汽车电子设计的多主串行总线：所有 ECU 节点挂在一对差分线（CAN_H / CAN_L）上，以广播帧通信，各节点按 ID 自行过滤收帧。
  2. 为什么抗干扰：差分传输让共模噪声相互抵消，配合总线两端的 120Ω 终端电阻抑制信号反射，适合发动机舱等电磁环境恶劣的场景——这与单端电平的 RS232 是本质差别。
  3. 多主无损仲裁：总线空闲时任意节点都可发送，逐 bit 仲裁中发显性 0 的胜出、ID 越小优先级越高，败者自动退为接收方，既不丢帧也不需要中心主站。
  4. 硬件级可靠性：帧尾 CRC + ACK 硬件检错与确认，出错自动重发；故障节点经错误计数进入 bus-off 主动离线，不会拖垮整条总线。
  5. 定位：汽车动力、底盘、网关等实时、安全相关场景的主力总线，速率 125 kbps ~ 1 Mbps；CAN FD 把数据段扩到 64 字节并提升数据段速率；车身低成本传感器则交给 LIN（见 第十章：LIN 总线：单主多从与调度表）。

数据帧逐段剖析（标准帧）

  • SOF：1 个显性位，标志帧开始，所有节点据此硬同步。
  • 仲裁段：标准帧 11 位 ID；扩展帧拆为 11 位基本 ID + SRR + IDE + 18 位扩展 ID。
  • IDE 位：区分标准（显性）与扩展（隐性）帧。
  • ACK 槽：发送方发隐性，任一正确接收的节点拉显性——发送方只知道「至少有人收到」，不知道是谁。
  • 位填充（Bit Stuffing）：连续 5 个相同电平后强制插入反相位，保证时钟同步；计算帧长时要计入。

远程帧与错误帧

  • 远程帧（RTR=1）：请求对方发送某个 ID 的数据帧，无数据段；现代设计多用周期发送替代。
  • 错误帧：任一节点检出错误立即发送 6 个显性位「打破」当前帧，所有节点丢弃该帧，发送方稍后自动重发。
  • 过载帧：接收方来不及处理时请求延时，极少使用。

二、多主仲裁

总线空闲时多个节点可同时发送；ID 仲裁时逐 bit 比较，发显性 0 的胜出，失败者自动退为接收方，无中心主站。

要点：

  • 非破坏性：赢家的帧不受任何影响，无需重发，总线利用率因此可以很高。
  • ID 即优先级：设计报文 ID 分配表就是设计系统的实时性——越关键的信号 ID 越小。
