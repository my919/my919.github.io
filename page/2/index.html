1. 为什么供应链成了头号攻击面

传统安全模型把防御重心放在「自己写的代码」上：代码评审、SAST、渗透测试。但现代应用的代码构成早已反转：

  • 一个普通 Node.js 项目直接依赖几十个包，传递依赖轻松突破 1000 个；
  • Docker 镜像里 80% 以上的字节来自基础镜像与第三方包；
  • CI/CD 流水线本身（构建器、Action、插件）也是代码，也能被投毒。

攻击者发现：与其攻破你加固过的生产环境，不如在你上游投毒，让你自己把恶意代码请进门。

1.1 供应链攻击的四种典型形态

形态 说明 代表事件
上游源码投毒 维护者账号被盗或恶意贡献者长期潜伏 xz utils 后门（2024）
包仓库投毒 抢注相似包名（typosquatting）、发布恶意新版本 npm event-stream、ua-parser-js
构建系统入侵 攻破 CI，把恶意代码注入正常制品 SolarWinds Orion（2020）
依赖混淆 向公网仓库发布与内部包同名的高版本包 Alex Birsan 依赖混淆研究（2021）

2. 典型事件复盘

2.1 xz utils 后门（CVE-2024-3094）

2024 年 3 月，微软工程师 Andres Freund 偶然发现 sshd 异常耗时，顺藤摸瓜挖出 xz/liblzma 5.6.0/5.6.1 中隐藏的后门，CVSS 直接打满 10.0。

攻击链条极其精巧：

  1. 化名 Jia Tan 的贡献者用两年多时间在社区积累信任，最终成为共同维护者；
  2. 恶意代码伪装成二进制测试文件混入仓库，在 configure 阶段被提取；
  3. 后门劫持 sshd 的 RSA 验签函数，攻击者持特定私钥即可绕过认证远程执行命令；
  4. 只在特定构建条件（glibc + systemd 补丁的 sshd）下触发，普通测试环境难以复现。

教训：

  • 关键基础设施依赖少数无偿维护者，是社会工程的重灾区；
  • 发布 tarball 与 Git 仓库内容不一致，是隐蔽投毒的经典手法；
  • 仅靠「代码有人看」不够，需要可验证的构建与制品来源证明。

2.2 npm 生态投毒

npm 是投密度最高的生态之一，常见手法：

  • typosquatting：lodash vs lodahs，赌你手滑；
  • 账号接管：ua-parser-js（周下载 700 万+）维护者账号被盗，连发三个带挖矿/窃密后门的版本；
  • install 脚本执行：npm 包可声明 preinstall/postinstall 脚本，安装即执行，零交互；
  • 抗议软件（protestware）：node-ipc 作者主动在特定地区用户机器上写破坏性文件。

教训：npm install 本质上是「从互联网下载并执行陌生人的代码」，必须把它当作高危操作来治理。

4. SLSA：给供应链打成熟度分级

SLSA（Supply-chain Levels for Software Artifacts） 是 Google 主导的供应链安全框架，回答的问题是：「这个制品的构建过程有多可信？」

4.1 分级模型（SLSA v1.0 聚焦构建轨道）

级别 核心要求 防住的威胁
L1 构建过程脚本化，产出 provenance（来源证明） 事后可追溯
L2 在托管构建服务上构建，provenance 已签名 构建者本地环境被控
L3 隔离/短时构建环境，构建定义不可被用户篡改 构建任务间交叉污染、参数注入

（早期草案还有 L4：双人评审 + 可复现构建，v1.0 中暂被搁置。）

5. Sigstore/cosign：制品签名全流程

传统 GPG 签名的痛点是密钥管理：私钥分发、吊销、轮换都是体力活。Sigstore 用「keyless」思路解决：

  • Fulcio：短期证书 CA，用 OIDC 身份（如 GitHub Actions 的 workload identity）换证书；
  • Rekor：透明日志（类似 Certificate Transparency），所有签名记录公开可审计；
  • cosign：CLI 工具，一条龙完成签名、验证、镜像附加。

8. 私有制品库治理

公网仓库不可控，企业需要一层「缓冲与检疫」。

8.1 架构模式

  Dev[开发者/CI] --> Proxy[私有制品库<br/>Harbor / Artifactory / Nexus]
  Proxy -->|代理+缓存| Pub[公网上游<br/>npm/DockerHub/Maven Central]

8.2 治理要点

  1. 统一入口：开发与 CI 只允许访问私有库，防火墙封死直连公网仓库——这是防依赖混淆的第一道墙；
  2. 防依赖混淆：内部包名加入「保留命名空间」，禁止代理同名公网包；
  3. 检疫状态机：新拉取的制品先入 quarantine 区，扫描通过才进生产可用仓库；
  4. 签名验证前置：入库即验 cosign 签名与 provenance，验不过直接拒绝；
  5. 留存与追溯：SBOM、签名、扫描报告随制品一同存档，保留期对齐合规要求（常见 1 年起）。

常见坑 FAQ

Q1：生成了 SBOM 但漏洞扫描一堆误报，怎么办？
CPE 匹配噪声大，用 --add-cpes-if-none 或换成以包坐标（purl）匹配的扫描器；配合 VEX 文档标注「不适用」漏洞，避免每次重复评审。

Q2：cosign keyless 在私有 GitLab/Jenkins 能用吗？
可以，只要 CI 支持 OIDC token（GitLab 17+ 原生支持）；自托管场景也可部署私有 Fulcio + Rekor 实例，或退回密钥对模式 + KMS。

Q3：provenance 会不会泄露内部信息？
会暴露仓库名、workflow 路径等元数据。私有项目建议 provenance 只推内网 Rekor，或对 attestation 做访问控制，公开仓库则无需顾虑。

Q4：minimumReleaseAge 会不会拖慢安全补丁？
为 vulnerabilityAlerts 类 PR 单独豁免等待期（Renovate 支持按规则覆盖），安全修复走快车道，常规升级走冷静期。

落地清单

  • 全部制品构建时生成 SBOM（CycloneDX），随制品入库
  • SBOM 接入 grype/OSV 扫描，CI 设 --fail-on high 卡点
  • 镜像与制品使用 cosign 签名，部署端准入验签
  • 核心项目接入 SLSA provenance（目标 L3）
  • GitHub Actions：pin SHA、最小权限、OIDC 替代长期密钥
  • Renovate 启用 minimumReleaseAge + 漏洞警报豁免
  • npm/pip 全 CI 走 ci/--require-hashes，禁用 install 脚本
  • 私有制品库统一入口，防依赖混淆，检疫流程上线

1. 为什么需要 AI 网关

没有网关时的典型乱象：

  • 密钥散落：每个应用各自持有供应商 Key，泄露面 = 应用数；

  • 合规裸奔：用户 Prompt 里的身份证、手机号原样出境。

4. 多模型路由、降级与重试

路由策略设计是网关的核心价值：

  1. 负载均衡：同名模型多部署间分发，策略可选简单轮询、最低延迟、基于用量（推荐 usage-based-routing-v2，按 TPM/RPM 余量分配）；
  2. 故障降级（Fallback）：主模型超时/5xx → 自动切备选链。链设计要能力对齐：gpt-4o 降级到 gpt-4o-mini 可接受，降到 7B 本地模型要考虑能力断层；
  3. 内容路由：按请求特征分流——metadata.env=prod 走强模型，测试流量走便宜模型；长上下文请求路由到支持 200K 的模型；
  4. 重试纪律：只对连接错误与 5xx 重试，4xx（参数错误、内容审核）重试无意义；重试 ≤2 次且换部署，防止打爆同一路。

注意降级对业务是显式事件：在响应头加 x-litellm-model-id 让应用感知实际出参模型，关键业务可据此降级 UI 承诺（”当前为备用模型，答案可能不够精确”）。

5. Key 管理与配额

最佳实践分层：

  • 三级 Key：Master（网管）→ Team（预算主体）→ Service（应用运行时）；泄露任一 Service Key，爆炸半径仅限该应用的配额；
  • 预算硬顶：max_budget + budget_duration 设置周期预算，超限自动 429——比事后看账单有效；
  • 速率双层：Key 级 RPM/TPM 防单应用失控，模型级限流防供应商配额被打穿；
  • Key 轮换：Service Key 季度轮换，网关支持双 Key 并行窗口期平滑切换；
  • 禁止直连：网络策略上，除网关上联出口外，办公网/业务服务器到 api.openai.com 的直连全部封掉，否则治理形同虚设。

6. Token 成本统计

成本治理 = 计量 → 归因 → 优化。

计量：LiteLLM 把每次调用的 prompt_tokens / completion_tokens / spend 写入 Postgres，并可通过回调推给 Prometheus：

关键指标：litellm_total_tokens、litellm_spend_metric（按 api_key_alias / team / model 维度聚合）。

归因：要求所有调用带 metadata（LiteLLM 的 metadata.team_id 或自定义 header x-biz-line），月底按维度出账单报表，成本分摊到部门。

优化杠杆按收益排序：

  1. 模型分级：70% 的请求其实 mini 级模型就够，建”意图分类器前置路由”省下大头；
  2. Prompt 瘦身：定期审计最长的 system prompt，删废话（每 1000 token × 调用次数都是钱）；
  3. 缓存命中（下节）；
  4. 自托管替代：稳定大流量场景，自托管 vLLM（第八章）的单位成本通常低于 API 价 50%+。

7. Prompt 缓存

两级缓存机制：

供应商侧原生缓存：Anthropic 的 prompt caching、OpenAI 的 automatic caching 对长前缀（>1024 token）省 50%–90% 费用。网关侧要保证前缀稳定（system prompt 别拼时间戳、别乱序拼接），否则缓存形同虚设。

网关侧响应缓存：对幂等查询（知识库问答、翻译）缓存完整响应：

语义缓存（Qdrant/向量匹配）命中率比精确匹配高 3-5 倍，但有误命中风险：只在答案可复用的场景开（FAQ），涉个人数据的查询别开。缓存键务必包含模型名，避免跨模型串答。

8. 审计与安全

8.1 审计日志

记录维度：时间、Key、模型、token 用量、延迟、请求与响应内容（可配置脱敏后落盘）。合规要求下日志保留 6 个月以上，存储用 ELK 或 S3 + Athena。

8.2 PII 脱敏

在出网前对 Prompt 做实体识别与替换：

生产建议接 Presidio / HanLP 类 NER 做中文人名地名识别，纯正则覆盖率有限。注意脱敏不可逆地影响回答质量——客服场景建议”脱敏 + 映射表网关侧还原”两段式。

8.3 注入检测

对入站 Prompt 跑注入分类器（自研小模型或开源 prompt-guard），命中”忽略之前指令、输出系统提示词”类模式时：拦截、告警、记录攻击者 Key。面向 C 端的应用这是必选项，内部工具可降级为仅记录。

8.4 内容合规

国内场景对输入输出双向做内容安全审核（阿里云盾 / 自建词库 + 模型），网关是最合适的统一拦截点——应用各自接审核，必然有漏网之鱼。

常见坑 FAQ

  1. Q：上了网关后延迟明显变高？ A：网关本身应只加 5–15ms。高了通常是因为：开了响应缓存但 Redis 跨机房、审计同步写库阻塞（改异步）、或网关实例 CPU 打满。流式响应务必确认网关做的是 chunk 透传而非攒批。
  2. Q：Fallback 链触发后答非所问？ A：降级模型间的 system prompt 与参数（temperature、max_tokens）要统一由网关注入；能力差距大的链路要在应用侧做 UI 提示。
  3. Q：成本统计和供应商账单对不上？ A：缓存命中（供应商侧）部分不计费但网关按标准价记账；以供应商账单为财务口径，网关数据做归因分析口径，两者留 5% 误差预期。
  4. Q：语义缓存把 A 用户的答案给了 B 用户？ A：缓存键必须包含租户/用户维度（或在 Key 级隔离缓存命名空间）；涉个人数据的请求打 no-cache 标记。
  5. Q：虚拟 Key 太多了管不过来？ A：用 Key 别名 + 标签（env=prod, app=cs-bot）强制规范，接 CMDB 定期清理无主 Key；Master Key 权限收到平台组 2 人以内。
  6. Q：自托管模型怎么纳入统一路由？ A：vLLM/SGLang 的 OpenAI 兼容端点直接注册进 model_list（openai/ 前缀 + 自定义 api_base），与云厂商同权参与负载均衡与降级。

  • 压测网关自身吞吐，确认流式透传无攒批

1. 为什么需要编排平台

自己写代码串”LLM + 检索 + 工具 + 审批流”当然可行，但当需求变成”业务方每周改三次流程”时，代码迭代速度就是瓶颈。编排平台的价值：

  • 可视化流程：业务方能看懂、能验收，需求沟通成本骤降；
  • 组件复用：LLM 节点、HTTP 节点、条件分支都是预置的，不用重复造轮子；
  • 运行时内置：会话管理、日志追踪、并发调度开箱即用；
  • 权限与协作：多人编辑、版本管理、环境分离。

代价是灵活性受限与平台锁定。判断标准：流程变更频率 > 每月一次、参与方含非研发 → 上编排平台；核心交易链路、极致性能场景 → 自己写代码。

3. Dify RAG 应用编排

RAG 是 Dify 的强项，完整链路：知识库建索引 → 应用挂检索 → 编排后处理。

3.1 建知识库

  1. 创建知识库，选分段方式：通用（按长度切）或父子分段（小块召回、大块喂上下文，长文档推荐）；
  2. 配置 Embedding 模型：中文场景 bge-m3 / Qwen3-Embedding，自托管接第八章的 vLLM 端点；
  3. 索引方式：高质量（向量）为主，混合检索（向量 + 关键词）对专有名词、编号类查询显著更准；
  4. 上传文档触发异步解析，worker 日志可观察分段结果。

3.2 应用侧编排

关键配置：

  • 检索节点：TopK 3–8，开 Rerank（bge-reranker-v2-m3），Score 阈值按实测调；
  • LLM 节点提示词：明确”仅根据【上下文】回答，不知道就说不知道，答案末尾用 [^1] 标注来源”；
  • 引用与归属：打开”引用和归属”开关，前端自动渲染来源卡片——企业知识库的信任度命脉；
  • 多轮改写：对话型 RAG 开”问题改写”，用 LLM 把”那第二个呢”补全成完整问题再检索。

3.3 质量调优节奏

先跑通 → 收集 50 条真实问题建评测集 → 调分段大小（256/512/1024 对比）→ 调 TopK 与 Rerank → 只在前述都调完仍不达标时考虑微调 Embedding。分段策略与 Rerank 通常是收益最大的两步。

4. Dify Agent 节点与工具

Agent 类应用里，LLM 节点升级为 Agent 节点，挂工具让模型自主调用：

  • 内置工具：Google 搜索、Wikipedia、代码执行沙箱、图表生成；
  • 自定义工具（OpenAPI 导入）：贴一份 OpenAPI/Swagger 文档，Dify 自动生成可调工具——把内部 CRM、工单系统接进来的标准姿势；
  • MCP 工具：新版 Dify 支持直接挂第六章开发的 MCP Server，与业界生态打通。

自定义工具鉴权：在工具配置里填 Header（如 Authorization: Bearer xxx），凭据存 Dify 侧加密存储，不进提示词。

Agent 节点策略选 Function Calling（模型支持原生函数调用时）或 ReAct（兜底），max_iterations 设 5–10 防死循环，配合”超时熔断”与”人工审批节点”处理高风险动作。

编排平台与自研代码不是互斥选型，常见终态是”边缘场景平台快速覆盖，核心链路代码精耕”。

选型节奏建议：先用平台 1-2 周跑通业务验证价值，跑出稳定流量后再评估是否值得为性能与可控性重写为代码——大多数内部应用会一直停在平台层，这也是合理的工程经济账。

8. Webhook 与定时触发

  • Webhook 触发：n8n 的 Webhook 节点生成 URL 供外部系统回调，支持 Test/Production 双地址；Dify 侧可用”工作流应用”的 API 接收外部 POST。生产地址记得加签名校验或 IP 白名单。
  • 定时触发：n8n 的 Schedule Trigger 配 cron，做”每日 8 点汇总昨日工单 → LLM 生成日报 → 发飞书”类任务；Dify 本身不含调度器，定时任务统一放 n8n 侧调 Dify API。
  • 错误处理：n8n 工作流可配 Error Workflow（全局兜底告警）；节点级开”Continue On Fail + 重试 3 次”，AI 节点的超时单独放宽到 120s 以上。

9. 企业落地案例：售后知识助手

背景：某 SaaS 公司售后团队 30 人，60% 工单是重复问题。

方案：

常见坑 FAQ

  1. Q：Dify 升级后应用打不开/接口报错？ A：九成是跳版本升级漏了数据库 migration。恢复备份，按版本逐个升；升级前务必 pg_dump。
  2. Q：知识库检索总是召回无关段落？ A：先查分段是否把表格/标题切碎了（换父子分段）；再开混合检索与 Rerank；最后检查 Embedding 模型是否匹配语种——英文模型跑中文库是隐形重灾区。
  3. Q：Dify Agent 调内部 API 工具超时？ A：工具默认超时较短，在自定义工具的 OpenAPI 配置里加大 timeout；慢接口改为异步任务 + 轮询模式。
  4. Q：n8n 工作流跑了几次后内存暴涨？ A：Execution 数据没清理。设置 EXECUTIONS_DATA_MAX_AGE=168（小时）并开定期清理；二进制数据走对象存储而非内存。
  5. Q：两边都有 RAG，到底用哪边？ A：面向用户的高质量问答用 Dify（有运营工具）；自动化流程里”顺带查一下”的轻量检索用 n8n 向量节点即可。
  6. Q：Dify 的 API 并发扛不住？ A：worker 水平扩容（docker compose up -d --scale worker=3），检查 Celery 队列积压；同时把模型端点指向第八章的 vLLM 集群而非共享 Key。

1. 先想清楚：微调、RAG 还是 Prompt

决策框架一句话：Prompt 教任务、RAG 给知识、微调改行为。

诉求 首选方案 原因
知识时效性、可引用来源 RAG 微调记不住长尾事实，更新成本高
固定输出格式 / 语气 / 领域术语风格 微调 上千次提示不如梯度改一次权重
通用能力缺失（数学、推理） 换更强的基座 小数据微调补不了能力短板
降低提示词长度与成本 微调 把 2K token 的 few-shot 蒸进权重

判断标准：把你想让模型做的事写成 50 条指令数据，如果每一条都能用”例子示范”教会而不是”查资料回答”，那就是微调的活。

2. 全参 vs LoRA vs QLoRA

LoRA 原理：冻结原权重 W，用两个低秩矩阵 B×A（秩 r 通常 8–64）拟合增量 ΔW，训练参数量从 7B 降到 几百万到几千万。

维度 全参微调 LoRA QLoRA
7B 显存需求 ≥ 80GB（Adam 状态 3 倍权重） 16–24GB 10–12GB（4bit 基座）
效果上限 最高 接近全参（多数任务 95%+） 略低于 LoRA，格式任务足够
多任务切换 每任务一份全量权重 只换 Adapter（几十 MB） 同左
训练速度 基准 快 2-3 倍 略慢于 LoRA（量化开销）
适用 领域大改、持续预训练 默认选择 单卡消费级显卡

经验：默认 LoRA；一张 4090/3090 就 QLoRA；只有在”基座模型完全不懂你的领域语言”（如极端专业语料续训）时才考虑全参。

常见坑 FAQ

  1. Q：微调后模型变”复读机”，反复输出训练集原句？ A：典型过拟合 + 数据去重没做好。减 epoch、查近重复样本、混通用数据。
  2. Q：loss 降到接近 0 但效果很差？ A：检查是否把 prompt 部分也算了 loss（应只 mask 出答案部分计算，LLaMA-Factory train_on_prompt: false）；以及 chat template 是否配对——template 错一位全盘皆输。
  3. Q：QLoRA 训完合并后精度掉得厉害？ A：QLoRA 的正确姿势是合并 LoRA 到 BF16 基座再量化，而不是直接对 4bit 基座导出的权重上线。
  4. Q：DPO 训完模型变啰嗦/变哑巴？ A：beta 不合适或 chosen/rejected 长度差异太大（模型学会”长=好”的伪相关）。控制长度分布，或换 IPO/KTO。
  5. Q：只有 500 条数据值得微调吗？ A：格式类任务值得（rank 8、3 epoch 常有奇效）；知识类任务不值得，转 RAG。
  6. Q：基座选哪个版本？ A：直接选 Instruct 版做 SFT（别从 Base 重来）；中文任务优先 Qwen 系；留意模型 License（商用限制）。

1. 推理服务的技术挑战

LLM 推理与训练完全不同：它是自回归逐 token 生成，每个新 token 都要读一遍全部权重。由此产生三个工程瓶颈：

  1. 显存墙：权重 + KV Cache + 激活，7B 模型 FP16 权重就占 14GB；
  2. 内存带宽墙：解码阶段每 token 都要把权重从 HBM 搬进 SM，解码是访存密集型，算力空转；
  3. 批处理难：请求长短不一、到达时间随机，静态批处理要么浪费要么排队。

一个关键认知：Prefill（首 token）是计算密集，Decode（后续 token）是访存密集。优化目标因此分裂——首 token 延迟（TTFT）靠算力，吞吐靠带宽利用率。vLLM 与 SGLang 的所有黑科技都围绕这两个阶段展开。

2. vLLM：PagedAttention 与连续批处理

2.1 PagedAttention：像操作系统管内存一样管 KV Cache

传统实现为每个请求预分配 max_seq_len 的连续显存，内部碎片浪费 60% 以上。PagedAttention 把 KV Cache 切成固定大小的 Block（如 16 token/块），用页表映射逻辑块到物理块：

收益：碎片率降到 4% 以内；前缀共享天然支持（多个请求共享 system prompt 的块，写时复制）；显存利用率翻倍直接转化为更大的 batch。

2.2 连续批处理（Continuous Batching）

静态批处理等整批跑完才返回；连续批处理在每个 decode 步检查：有请求结束就踢出、有新请求就插入。GPU 永远满载，吞吐提升 2-4 倍（相对 HF Transformers 裸跑可达 10 倍以上）。

3. SGLang：RadixAttention 与结构化生成

8. 多卡与张量并行

单卡装不下时：

  • 张量并行（TP）：把每层的权重矩阵切到多卡，all-reduce 通信。NVLink 内高效，跨机慎用于 decode。
  • 流水并行（PP）：按层切段，通信少但有气泡，适合跨机补充。
  • 数据并行（DP）：多副本 + 负载均衡，扩容吞吐的首选，无通信开销。

经验：能单卡就别 TP（通信损耗 10-20%）；要吞吐优先加副本做 DP，要装大模型才 TP；8 卡机内 TP=8 是上限，再大走 PP 或专家并行（MoE 模型）。

  • 滚动升级用”–enable-lora 灰度 + 蓝绿实例”二选一，别在单实例上热换模型。

常见坑 FAQ

  1. Q：起服务就 OOM，明明权重算得过来？ A：KV Cache 是按 max-model-len × max-num-seqs 预分配预算的。先把 max-model-len 砍到业务真实上限，gpu-memory-utilization 降到 0.85 试。
  2. Q：吞吐上去了但用户嫌慢？ A：高吞吐靠大 batch，大 batch 拉高 TTFT。交互场景限 max-num-seqs 或按延迟 SLO 定并发上限，鱼和熊掌要显式取舍。
  3. Q：AWQ 模型某些 case 输出明显变蠢？ A：检查量化校准集是否与业务分布匹配；对精度敏感的任务（数学、代码）回退 FP16/BF16 或用 8bit。
  4. Q：长上下文请求把短请求拖死？ A：开 chunked prefill（vLLM --enable-chunked-prefill），把长 prefill 切片与 decode 混合调度，避免队头阻塞。
  5. Q：Ollama 上生产为什么被劝退？ A：GGUF 在 GPU 上 decode 吞吐远低于 vLLM 的 PagedAttention 路径，且并发调度简单；它适合 ≤10 并发的内网工具，不适合 C 端流量。
  6. Q：多轮对话越来越慢？ A：历史全量重算是元凶。确认前缀缓存已开启（vLLM --enable-prefix-caching 或 SGLang 默认开启），且消息结构保持前缀稳定——系统提示里别塞时间戳。

生产实践清单

  • 按业务真实上下文长度设 max-model-len，不盲目拉满模型标称值
  • 显存预算 = 权重 + KV Cache（用公式核算）+ 10% 余量
  • Agent/RAG 场景开启前缀缓存，系统提示放消息最前且保持稳定
  • 上线前用真实分布数据集做阶梯压测，确定并发上限与 P99
  • 监控 TTFT / TPOT / 队列深度 / cache 使用率四类指标
  • 量化模型上线前跑精度回归集（自建 100+ 条业务 case）
  • OpenAI 兼容接口 + 网关统一鉴权限流，引擎不直接暴露公网
  • 模型升级走蓝绿，保留旧版本快速回滚

1. 从补全到 Agent：编程范式的三级跳

三级跳的本质差异：

  • 补全：模型看当前文件光标附近，秒级响应，人无打断。
  • 对话：人把上下文喂给 Chat，模型产出 diff，人粘贴。
  • Agent：模型自己读文件、grep、跑测试、看报错再改，一轮任务可能执行几十步工具调用，人只在关键节点确认。

团队落地 Coding Agent 的关键不是”选哪个工具”，而是把仓库改造成 Agent 友好：清晰的目录约定、可一键运行的测试、写在仓库里的工程规范。Agent 的能力上限，往往被仓库的混乱度决定。

指标 定义 健康参考
采纳率 AI 生成代码进入合并主干的比例（行级或 commit 级） 30%–60% 属正常，>80% 要警惕”照单全收”

落地节奏建议：

  1. 第 1-2 周：小范围试点（2-3 人 + 一个边缘仓库），先把 AGENTS.md 与测试脚本补齐；
  2. 第 3-4 周：沉淀 Slash Command / Subagent / Hooks 进模板仓库；
  3. 第 2 月起：接 CI Review，开始采集采纳率与返工率；
  4. 持续：每月复盘”Agent 犯的典型错”，转化为 AGENTS.md 新条目——规范文件的迭代速度，就是团队 AI 能力的增长速度。

  6. Q：不同成员用不同工具，规范怎么统一？ A：以 AGENTS.md 为单一事实源，各工具的私有配置文件只做一行引用；Hooks 用仓库脚本实现，与工具解耦。

在第三章里我们实现了 Function Calling，但每接一个工具都要在应用里手写胶水代码；MCP 把这件事标准化为”任何 Host 都能插任何 Server“，如同 USB-C 之于外设。

1. MCP 解决什么问题

没有 MCP 之前，接入 N 个工具到 M 个 AI 应用是 M×N 的适配矩阵；MCP 之后变成 M+N：工具方只写一次 MCP Server，应用方只实现一次 MCP Client。

  • 统一协议：工具列表、入参 Schema、调用结果、错误码都有标准格式。
  • 动态发现：Host 启动时向 Server 询问”你有什么能力”，无需硬编码。
  • 双向能力：Server 不仅能提供工具，还能反向请求 LLM 采样（Sampling）、向用户征求确认（Elicitation）。
  • 安全边界清晰：工具运行在 Server 进程里，凭据不进入 LLM 上下文。

适用场景判断：工具会被多个 Host 复用、或要分发给第三方时用 MCP；只在一个 LangChain 应用内部用的工具，直接写 Function 更简单。

2. 协议架构：Host / Client / Server

三个角色的职责：

角色 职责 例子
Host 承载 LLM 与用户交互，管理生命周期与权限 Claude Desktop、Cursor、VS Code
Client Host 内部组件，与某个 Server 保持 1:1 会话 mcp.ClientSession
Server 暴露 Tools / Resources / Prompts 你写的工具进程

关键设计：Client 与 Server 是 1:1 的。一个 Host 接三个 Server，就起三个 Client。这样做让权限隔离、错误隔离、能力协商都按 Server 粒度进行。

3. 传输层与 JSON-RPC 消息

MCP 消息格式是 JSON-RPC 2.0，只有三种报文：Request（带 id）、Response（带 id）、Notification（不带 id）。

三种官方传输方式：

传输 适用 特点
stdio 本地子进程 Host 拉起 Server 子进程，走标准输入输出；零网络配置，最常用
SSE（已废弃） 远程 2024 版规范，HTTP POST 发请求 + SSE 推回包；被 Streamable HTTP 取代
Streamable HTTP 远程 单端点 POST/GET，可选升级为 SSE 流；支持无状态水平扩容

握手流程（生命周期三个阶段）：

  1. 初始化：Client 发 initialize（携带协议版本、自身能力）→ Server 回 InitializeResult（携带 serverInfo、能力清单）→ Client 发 notifications/initialized。
  2. 运行期：tools/list、tools/call、resources/read、prompts/get，以及 Server 反向发起的 sampling/createMessage。
  3. 关闭：stdio 下关闭子进程；HTTP 下关闭会话。

版本协商很重要：Client 报 protocolVersion: "2025-06-18"，Server 若不支持需返回自己支持的版本，双方取交集；谈不拢必须报错而不是静默降级。

4. 三大原语：Tools / Resources / Prompts

原语 控制方 类比 用途
Tools 模型决定调用 POST 接口 有副作用或可计算的动作：查库、发消息、跑命令
Resources 应用/用户选择 GET 接口 只读上下文：文件内容、数据库行、日志
Prompts 用户触发 模板 预置提示词模板，可带参数插值

Resource 用 URI 寻址，如 file:///project/README.md、postgres://db/users/42；支持模板 URI（file:///{path}）让 Server 暴露一族资源。

Prompt 示例：prompts/get 传 name: "code_review"、arguments: {lang: "python"}，Server 返回拼好的 messages 列表，Host 直接塞进对话。

8. 权限与安全边界

MCP 把”模型能做什么”变成可治理的工程问题：

  1. 用户确认（Human-in-the-loop）：Host 应在工具调用前展示工具名与参数，写操作必须显式确认。不要把”始终允许”当默认值。
  2. Roots 限定：文件类 Server 只接受 Host 声明的根目录之内的路径，Server 侧还要自己做 path.resolve 后的前缀校验，防 ../ 逃逸。
  3. 凭据隔离：API Key 放 Server 环境变量，绝不作为工具入参让模型传——模型上下文可能被泄露到日志。
  4. 输入校验即注入防线：工具入参是”模型生成的字符串”，一律按不可信输入处理：SQL 用参数化、Shell 禁拼接、路径做白名单。
  5. 远程 Server 鉴权：Streamable HTTP 端点必须加 Bearer Token 或 OAuth 2.1（新版规范内置）；公网裸奔等于把内网工具开放给所有人。
  6. Tool Poisoning 防护：第三方 Server 的 description 也是提示词注入面——只装可信来源的 Server，审查其工具描述是否夹带”忽略之前指令”类内容。

常见坑 FAQ

  1. Q：Server 起了但 Host 里看不到工具？ A：九成是 stdout 被污染。检查代码里所有 print/console.log 是否写到了 stdout；Python 里第三方库的启动横幅也算。用 Inspector 复现能看到具体哪条报文解析失败。
  2. Q：改了工具代码不生效？ A：Host 只在启动时建立会话并拉一次 tools/list，必须重启 Host 或重连该 Server。
  3. Q：工具返回大文本把上下文撑爆？ A：Server 侧做截断与分页（limit/offset 参数），大文件用 Resource 返回 URI 让 Host 按需取，而不是一次性塞进 Tool 结果。
  4. Q：stdio 下 Server 启动慢导致超时？ A：Host 默认等初始化数秒；把重初始化（建连接池、加载模型）挪到首次调用时懒加载，或改 HTTP 常驻部署。
  5. Q：Windows 下 npx 起不来？ A：Claude Desktop 对 npx 的 PATH 解析有坑，用 cmd /c npx ... 包裹，或直接写 node 的绝对路径加脚本路径。
  6. Q：想让模型”主动”用某个工具但它不用？ A：检查工具名与 description 是否和任务语义匹配；描述里写清”何时该用、何时不该用”，比调参有效得多。

1. 概念说明

MongoDB 是文档数据库，层级只有三层：Database → Collection → Document。集合不要求固定 Schema，同一集合中的文档可以有不同字段。这种灵活性来自 BSON 文档模型，代价是约束和一致性需要应用层自己兜底。

1.1 文档模型与 BSON

JSON 是文本协议，只有字符串、数字、布尔、null、数组和对象；BSON 是二进制编码，带类型信息和长度前缀，解析更快，并额外支持日期、高精度小数、二进制、ObjectId。单条文档上限 16MB，超出应拆分或用 GridFS / 对象存储。

BSON 类型 mongosh 中的样子 说明
ObjectId ObjectId("66f1a2b3c4d5e6f7a8b9c0d1") 12 字节，含时间戳、机器、进程、计数器，默认 _id
Date ISODate("2026-10-25T02:00:00Z") 毫秒时间戳，统一存 UTC，展示时再转时区
Decimal128 NumberDecimal("199.00") 128 位十进制，金额、汇率必须使用
BinData BinData(0, "...") 二进制数据，GridFS 分块的基础
Int32 / Int64 1 / NumberLong(1) 整型，计数器注意 32 位溢出
Double 1.5 默认数值类型，存在二进制浮点误差

1.2 与关系模型对照

关系型数据库 MongoDB 说明
表 Table 集合 Collection 集合无固定列，文档可缺字段
行 Row 文档 Document 可嵌套数组和子文档
列 Column 字段 Field 可动态增加、多层嵌套

1.3 适用与不适用场景

适合：数据结构多变或半结构化（商品目录、内容、用户画像）；读写以整份文档为单位；写入量大、需要水平扩展（日志、埋点、事件流）；早期 Schema 不稳定、需要快速迭代。

不适合：核心账务、强多表事务、复杂跨实体一致性；大量多表 JOIN 和窗口函数的报表；高度规范化、跨实体频繁更新；需要严格外键、约束和成熟 BI 生态的场景。

1.4 与 PostgreSQL JSONB 的取舍

PostgreSQL 的 JSONB 也能存半结构化数据，同时保留事务、JOIN 和 SQL 生态。选择的关键不是“能不能存 JSON”，而是数据访问模型：

  • 80% 是关系型数据、只有少数字段灵活，选 PostgreSQL JSONB，避免多一套技术栈。
  • 文档本身就是聚合根、读写总是整份文档，且写入需要水平扩展，选 MongoDB。
  • MongoDB 的 TTL、分片、变更流更贴近事件与内容场景；PostgreSQL 的分析和约束能力更强。
  • 不要因为“字段不固定”就上 MongoDB，JSONB + GIN 索引往往已经足够。

2. 安装部署

官方镜像通过环境变量初始化管理员，首次启动会自动开启认证。测试环境也不要长期使用 root，业务应使用最小权限账号。

连接后用 db.createUser 为业务创建最小权限账号（只授予业务库 readWrite），不要长期使用 root。

多文档事务要求副本集或分片集群。本地可以启动单节点副本集，它没有高可用能力，但能解锁事务、变更流和 majority 写关注。

副本集同时开启认证时，节点之间必须使用 keyFile 做内部认证，否则无法选举。keyFile 权限必须是 400，并通过 security.keyFile 挂载。

生产环境使用 mongod.conf，不要把参数都堆在命令行。

三个关键点：bindIp 默认只监听本地，容器里要显式放开，但云主机必须配合安全组；WiredTiger 缓存占满内存会挤压文件系统缓存，反而增加 IO；开启 authorization 后所有连接都必须认证，初始化账号要在开启前完成。

3. CRUD 与查询

插入时金额用 Decimal128，时间统一用 UTC 的 Date；批量写入用 ordered: false，单条失败不会中断其余文档。

find 返回游标，不是一次性数组。投影只返回必要字段，batchSize 控制每次从服务端拉取的文档数，避免把全量结果读进内存。

分页要避免深 skip。skip(n) 需要扫描并丢弃前 n 条，页码越深越慢；后台列表、导出、消息流应使用“上一页最后一条的排序键”做范围查询。

对应索引应覆盖 { status: 1, createdAt: -1, _id: -1 }，否则排序仍会走内存。

查询操作符按语义分组，常用如下。

类别 操作符 典型用途
比较 $eq $ne $gt $gte $lt $lte 数值、日期范围
逻辑 $and $or $not $nor 组合条件
集合 $in $nin 批量枚举值
存在 $exists 判断可选字段是否存在
正则 $regex $options 前缀、模糊匹配
数组 $elemMatch $size $all 数组元素条件

数组字段直接用点号匹配，表示“至少有一个元素满足”；$elemMatch 表示“同一个元素同时满足多个条件”。

注意：{"items.sku": "KB-01", "items.qty": 2} 可能匹配到不同元素，有“同一元素”语义时必须用 $elemMatch。

更新操作符是原子的：$set 设置、$unset 删除、$inc 自增、$push 追加、$addToSet 去重追加。

数组要防止无限增长：$slice 只保留最近 N 条；upsert 在文档不存在时插入，$setOnInsert 只在插入时写创建时间。

findOneAndUpdate 在单文档上完成“读 + 改”的原子操作，适合生成序列号、抢占任务、扣减库存。

bulkWrite 把插入、更新、删除合并成一次网络往返，适合数据同步和批量修正。

批量操作仍需为过滤条件建索引，否则只是把多次扫描合并成一次请求。

4. 索引

MongoDB 索引基于 B-tree，_id 自带唯一索引，其余索引按查询模式手动创建。索引不是越多越好，每个索引都会增加写入成本和内存占用。

复合索引 { userId: 1, status: 1, createdAt: -1 } 支持 userId、userId + status、userId + status + createdAt 的查询；单独按 status 查询用不上，这就是最左前缀原则。多键索引还有额外限制：一个复合索引最多只能有一个数组字段，且多键索引不能作为分片键。

用 explain("executionStats") 看执行计划，重点看阶段、扫描文档数和返回文档数。

输出很长，真正要看的字段可以概括为下面这段。

判断标准：COLLSCAN 是全集合扫描，数据量大时必须优化；IXSCAN 是索引扫描，FETCH 是回表取完整文档；totalDocsExamined 远大于 nReturned 说明索引选择性差或回表过多；totalKeysExamined 远大于 nReturned 说明扫描范围过大；hasSortStage: true 表示排序没走索引，大结果集上很危险。

复合索引字段顺序按 ESR 原则排列：Equality（等值条件）→ Sort（排序字段）→ Range（范围条件）。例如“某用户已支付订单按时间倒序，且时间在某区间”，索引应为 { userId: 1, status: 1, createdAt: -1 }；把 createdAt 放在 status 前面，等值字段就无法形成有效的最左前缀。

索引的代价：写放大（每次写入都要维护所有相关索引）、内存占用（索引常驻内存才快）、建索引成本（大集合建索引占用 IO 和 CPU）、无用索引拖慢写入。用 $indexStats 找出使用次数为 0 的索引并下线。

5. 聚合管道

聚合管道由多个阶段串联，前一个阶段的输出是后一个阶段的输入。常用阶段如下。

阶段 作用 常见位置
$match 过滤文档 尽量放最前，利用索引
$project 字段投影、计算字段 减少后续数据量
$group 分组聚合 统计、去重
$sort 排序 放 $limit 前，尽量走索引
$limit 限制结果数 分页、Top N
$unwind 展开数组 数组元素级统计
$lookup 关联其他集合 补充关联数据
$addFields 增加计算字段 派生指标
$facet 一次查询多维度 分页 + 总数
$bucket 按区间分桶 金额、年龄分布

按天统计 GMV 是典型管道：$dateToString 转时区，$group 按天聚合，$sum 累加 Decimal128 金额。

$lookup 类似 LEFT JOIN。foreignField 必须有索引，否则每个外层文档都会触发一次扫描；结果数组通常配合 $unwind 展平。

列表页通常同时要“当前页”和“总数”，$facet 让两个子管道共享同一次扫描。

$bucket 按区间分组；聚合默认有 100MB 内存上限，超过时用 allowDiskUse 落盘，但会明显变慢。

落盘只解决内存上限，不解决缺索引带来的扫描量。

6. 事务、副本集与分片

MongoDB 4.0 起副本集支持多文档事务，4.2 起分片集群支持。但事务不是默认选择：能通过内嵌文档、单文档原子操作、幂等补偿解决的，不要用事务。事务持锁时间长、冲突重试成本高，默认生命周期上限 60 秒。

适合事务的场景：跨集合转账、库存扣减与订单创建必须同时成功、跨文档唯一性约束。不适合：批量导入、长耗时计算、需要人工介入的流程。

事务内所有操作都要显式传 session，漏传会导致该操作不在事务里。生产代码还要加幂等键，遇到 TransientTransactionError 时重试整个事务。

读关注和写关注决定一致性与性能的取舍。

配置 取值 含义 代价
readConcern local 读本地最新数据，可能回滚 最低
readConcern majority 只读已确认多数的数据 延迟更高
readConcern snapshot 事务内一致性快照 事务专用
writeConcern w: 1 主节点确认即返回 主节点宕机可能丢数据
writeConcern w: "majority" 多数节点确认 写延迟增加
writeConcern j: true 写 journal 后才确认 更持久，略慢

关键业务用 majority + j: true；日志、埋点可以接受 w: 1 换取吞吐。

分片解决单机容量和写入瓶颈。分片键决定数据分布和查询路由，选错的代价远大于选错索引。

选择原则：基数要高（状态、性别这类低基数字段会导致 chunk 无法再切分）；写要分散（单调递增的 _id 或时间戳会让写入集中到最后一个分片，形成热点）；查询要有局部性（常用查询最好携带分片键，否则广播到所有分片）。hashed 适合写分散和点查，ranged 适合范围查询和租户隔离。

分片后的限制：唯一索引必须包含分片键；分片键选定后不能随意修改，7.x 可用 reshardCollection 重建但成本很高；跨分片 $lookup、跨分片事务性能明显下降；chunk 迁移由 balancer 控制，迁移期间有网络和 IO 抖动。

7. 数据建模

内嵌还是引用，是 MongoDB 建模的第一决策。经验规则：读多写少、数量有界、总是一起读取的数据内嵌；写多、数量无界、独立访问的数据引用。

关系 建议 理由
一对一 内嵌 一次查询取全，减少集合数量
一对少（≤ 几百） 内嵌 文档大小可控，读性能好
一对多（无界） 引用 避免 16MB 上限和写放大
多对多 引用 + 中间集合 关系独立演化，避免双向冗余
读多写少 适度冗余 用空间换查询次数
写多读少 规范化引用 减少多副本更新成本

三大常用模式：

  • 桶模式：把一段时间内的事件聚合到一个文档，保存 count、sum 和样本数组，控制文档数量并预聚合，适合时序、日志。
  • 预聚合：维护计数器或汇总文档，写入时 $inc，读取直接取结果，例如收藏数、阅读数、订单总额。
  • 扩展引用：引用时冗余少量高频字段，例如订单里保存 userName，避免列表页每次 $lookup。

反范式的代价是同步：源数据变化要同步所有副本，方式有应用层双写、变更流订阅、定时对账，都要接受最终一致窗口。金额、库存、状态机等强一致字段不要冗余。

电商商品 + SKU + 评论有两种典型方案。方案 A 把有界的 SKU 内嵌进商品，评论独立集合。

方案 B 把商品、SKU、评论拆成三个集合，全部用引用，适合 SKU 数量极大、库存高频更新、需要独立检索 SKU 的场景。

上面的两条文档分别存放在 skus 与 reviews 集合。两种方案的取舍如下。

8. 性能与监控

profiler 默认关闭。级别 1 只记录超过阈值的操作，级别 2 记录所有操作（生产慎用）。慢查询记录在 system.profile 集合。

planSummary: COLLSCAN 是最明确的优化信号。docsExamined 远大于 nreturned 说明索引选择性差。

连接池不是越大越好：总连接数 = 进程数 × maxPoolSize，超过 MongoDB 连接上限会直接拒绝。单实例常见 50～100，分片集群按 mongos 数量分摊；长事务和聚合会长时间占用连接，要单独评估。

重点关注：opcounters 突增或查询占比异常（通常缺索引或流量异常）；connections.current 接近上限（连接池或连接泄漏）；缓存脏页比例持续过高（写入过快或磁盘跟不上）；副本集延迟持续增大（影响 majority 写和一致性读）。

mongostat 看全局吞吐和连接，mongotop 看每个集合的读写耗时，适合故障现场快速定位。

这两个工具适合现场排查，长期监控应接入 Prometheus 或云监控。

9. Python / Java 接入

pymongo 示例包含连接、CRUD、聚合和事务。金额用 Decimal128，事务用 snapshot 读关注和 majority 写关注。

生产代码还要处理 DuplicateKeyError、TransientTransactionError 重试，以及连接关闭后的重连；业务校验失败不要重试。

Motor 是 pymongo 的异步封装，API 形态基本一致，方法需要 await。

Java 侧通常用 Spring Data MongoDB。配置只需一个 URI，索引建议关闭自动创建，改由迁移脚本管理，避免多实例启动时重复建索引。

Repository 只需声明接口，Spring Data 会按方法名生成查询：interface OrderRepository extends MongoRepository<Order, String> 中的 findByStatusOrderByCreatedAtDesc(String status) 等价于按状态过滤并按时间倒序；复杂查询用 @Query("{'amount': {$gt: ?0}}") 声明。

10. 备份与恢复

逻辑备份适合中小数据量、跨版本迁移和单集合恢复。--gzip 压缩，--archive 输出单文件，便于归档到对象存储。

mongodump 默认不保证跨集合一致性。副本集上用 --oplog 记录备份窗口内的 oplog，恢复时 --oplogReplay 补齐增量。

副本集优先在从节点备份，避免影响主节点；备份前确认从节点延迟可接受。分片集群要分别备份每个 shard 和 config server，并保证时间窗口对齐：先停 balancer，按同一时间点备份各 shard 和 config server，恢复时先 config server、再 shard、最后启动 mongos。

oplog 也是时间点恢复的基础，保留窗口决定可恢复范围。恢复全量后用 --oplogLimit 重放到指定时间点，格式是 秒级时间戳:序号，必须来自 oplog 记录，不能随意估算。

恢复后要校验集合数量、文档数量和关键业务数据，再切流量。

11. 落地案例：用户行为事件日志

需求：App 埋点写入量大，按天统计事件量、DAU 和漏斗，原始数据保留 90 天后自动清理。特点是写多读少、按时间聚合、天然可过期。

索引覆盖主要访问路径，TTL 负责过期清理；TTL 索引后台约每 60 秒扫描一次，不能当作精确定时任务。

埋点写入优先保证吞吐：应用层按 500～1000 条或每秒批量聚合，ordered: false 允许部分失败，w: 1 换取吞吐；计费、审计类事件改成 majority。

按天统计事件量时，$dateToString 统一到东八区，避免跨时区口径不一致。DAU 要先按“天 + 用户”去重，再按天计数，直接 $sum: 1 统计的是事件次数。

事件量再上一个量级时，可以引入桶模式：每小时一个文档保存事件计数和样本，报表直接读桶，原始事件仍按 TTL 清理。

1. 概念说明

1.1 四大组件

组件 角色 关键点
NameServer 路由注册中心 无状态、节点间互不通信，Broker 定时心跳上报路由
Broker 存储与转发 负责消息写入 CommitLog、消费拉取、主从同步
Producer 生产者 从 NameServer 取路由，按队列发送，支持重试
Consumer 消费者 拉取消息、提交位点，同组内分摊队列

为什么不用 ZooKeeper：RocketMQ 只需要「最终一致的路由信息」，Broker 向所有 NameServer 注册，客户端读任意一台即可。NameServer 之间不选举、不同步，单台挂掉不影响已缓存的客户端路由，可用性优先（AP）。ZooKeeper 的强一致选举在机房故障时可能不可写，且运维更重。代价是 NameServer 路由可能短暂不一致，客户端需容忍并定期刷新。

1.2 核心概念

概念 说明 备注
Topic 消息一级分类，如 ORDER_TOPIC 生产环境应预创建，关闭自动创建
MessageQueue Topic 的分片，又称队列 并行度与顺序性的基本单元
Tag 消息二级分类，消费端可过滤 只做轻量过滤，不要当路由用
Key 业务唯一键，如订单号 用于查询消息、幂等与排查
ConsumerGroup 消费者组 组内分摊队列，组间各自消费一份
Offset 消费位点 集群消费存在 Broker，广播消费存在本地

1.3 存储模型

高吞吐的三个原因：

  1. 顺序写：所有消息不分 Topic 追加到 CommitLog，磁盘寻道被降到最低。
  2. mmap 与页缓存：CommitLog 通过内存映射读写，命中页缓存时几乎不碰磁盘；消费按 ConsumeQueue 索引随机读，也优先命中页缓存。
  3. 异步刷盘：默认 ASYNC_FLUSH，写入页缓存即返回，由后台线程批量刷盘；可靠性要求高时再切 SYNC_FLUSH。

注意：Kafka 用 sendfile 做零拷贝，RocketMQ 因需要「按索引随机读」而选择 mmap，二者都是为了避免用户态与内核态之间的多余拷贝。

1.4 与 Kafka、RabbitMQ 对比

维度 RocketMQ Kafka RabbitMQ
吞吐 十万到百万级/s 百万级/s 万级/s
延迟 毫秒级 毫秒级 亚毫秒到毫秒
顺序 单队列内严格有序 单分区内有序 单队列内有序
事务消息 原生半消息 + 回查 事务 API 仅限 Kafka 读写 无原生，需要本地消息表
延时消息 原生，4.x 十八档 / 5.x 任意时刻 不支持，需外部调度 插件或 TTL + 死信
堆积能力 亿级，堆积主要占磁盘 亿级，分区过多时性能下降 堆积后内存与磁盘压力明显
运维复杂度 中等，NameServer 轻量 中等，KRaft 后简化 单机简单，集群与镜像队列复杂
生态 国内电商金融、阿里系 大数据与流处理最强 协议多、路由灵活

结论：业务消息、订单履约、需要事务/延时/顺序的场景优先 RocketMQ；日志采集、流式计算选 Kafka；复杂路由与传统企业集成选 RabbitMQ。Kafka 细节见 Kafka 指南，RabbitMQ 见 RabbitMQ 指南。

1.5 RocketMQ 5.x 的变化

Proxy 接入层：无状态网关，统一 gRPC 协议，多语言客户端不再各自实现 Remoting。gRPC 客户端：rocketmq-client-java 5.x，新项目推荐，存量仍可用经典客户端。任意时间定时消息：不再受 18 个固定档位限制，按时间戳投递，秒级精度。存算分离：Broker 计算与存储解耦，扩缩容更弹性，适合云原生部署。

3. 消息类型总览

类型 语义 适用场景 发送 API

4.3 位点提交与重复消费

Push 消费者底层仍是拉取，位点由客户端定时上报 Broker（默认每 5 秒）。消费成功但位点尚未上报时进程崩溃，重启后会从旧位点重新消费，因此重复不可避免。正确心态是接受「至少一次」，用业务唯一键做幂等，而不是追求「恰好一次」。可靠性机制的系统性梳理见 消息可靠性指南 与 可靠性最终方案。

5. 顺序消息

5.1 全局顺序与分区顺序

RocketMQ 只保证同一 MessageQueue 内的顺序。所谓全局顺序，只能把 Topic 建成 1 个队列并由单线程消费，吞吐极低，生产几乎不用。正确做法是分区顺序：按订单号、用户 ID 等业务键哈希选队列，让同一实体的事件串行。

5.2 生产端：MessageQueueSelector

注意：队列数变化会导致哈希取模结果变化，顺序被打乱。因此顺序 Topic 的队列数要在创建时定好，避免在线扩缩容。

5.3 消费端：MessageListenerOrderly

顺序消费失败会阻塞当前队列并持续重试，不具备并发消费那样「重试 16 次进死信」的兜底，必须配置堆积与失败告警，并保证消费逻辑不会永久失败。

5.4 顺序消息的三个前提

  1. 单队列：同一业务键的消息必须进入同一队列。
  2. 单线程消费：必须使用 MessageListenerOrderly，Broker 对队列加锁，同队列同一时刻只有一个消费者线程处理。
  3. 发送顺序一致：业务侧要保证「先创建后支付」的发送顺序，多线程并发发送同一订单仍可能乱序，必要时在发送端按订单号串行。

6.3 实现原理

  • 4.x：延时消息先写入内部 Topic SCHEDULE_TOPIC_XXXX，队列 ID 等于「级别减一」；ScheduleMessageService 按级别定时扫描到期消息，再还原到原 Topic 的真实队列。

定时扫表 实现简单、状态可控 扫表压力大、时间精度受调度周期限制
延时消息 + 扫表兜底 精准且可自愈 需要状态机与对账逻辑

生产建议第三种：延时消息做主路径，低频扫表补偿异常订单。分布式事务的其他方案见 分布式事务指南。

7.2 为什么能解决「本地事务与发消息不一致」

普通方案先落库再发消息，发消息失败就出现「订单存在但没有库存消息」；先发消息再落库，落库失败就出现「库存被扣但没有订单」。事务消息把半消息作为「预备状态」：本地事务成功才让消息可见，本地事务失败则回滚；提交结果丢失时 Broker 主动回查本地数据库，最终达成一致。它是最终一致，不是强一致，消费端仍需幂等。

7.4 回查次数、超时与幂等

参数 默认值 说明
transactionTimeOut 6s 单次回查超时

回查接口的要求：

  1. 幂等：同一订单被回查多次不能产生副作用。
  2. 只读：回查中不要再次发消息或修改订单状态。
  3. 可判定：查询结果要能明确区分「成功、失败、未知」，未知返回 UNKNOW，不要猜。

7.5 与本地消息表方案对比

方案 一致性 实现成本 吞吐影响 适用
RocketMQ 事务消息 最终一致，Broker 回查兜底 低，客户端原生支持 多一次半消息写入与回查 订单、支付等核心链路
本地消息表 + 定时补偿 最终一致，靠扫表重发 中，需要消息表与调度 业务库多一次写入 跨多种 MQ、无法改中间件
最大努力通知 弱，依赖重试 低 小 非核心通知

事务消息并不能替代消费端幂等；它只保证「本地事务成功则消息一定可投递」，重复投递仍然存在。

8. 可靠性保障

8.1 发送端

  • 核心消息使用同步发送，判断 SendStatus 是否为 SEND_OK，非 OK 立即重试或落库补偿。
  • 异步发送必须在 onException 中记录并补偿，不能只写一个空回调。
  • 设置合理超时与重试次数；重试仍失败的进入本地重试表，由定时任务兜底。

8.2 Broker 端

组合 可靠性 性能 场景
ASYNC_FLUSH + ASYNC_MASTER 最低，宕机可能丢 最高 日志、非核心
SYNC_FLUSH + ASYNC_MASTER 单机不丢，主宕机可能丢 中 一般业务
SYNC_FLUSH + SYNC_MASTER 最高，主从都落盘才返回 最低 订单、支付、资金

注意：SYNC_FLUSH 只保证本机刷盘，主节点磁盘损坏仍可能丢；ASYNC_MASTER 下主宕机时未同步的消息会丢。两者必须成对评估，不能混搭后误以为可靠。

8.3 消费端重试与死信

并发消费失败返回 RECONSUME_LATER，Broker 按递增间隔重试，默认最多 16 次，仍失败则转入死信 Topic：%DLQ% 加消费者组名。死信不会自动处理，必须监控并人工消费。

8.4 幂等：唯一业务键 + 去重表

处理流程：先 INSERT 去重记录，唯一键冲突说明已处理过，直接返回成功；插入成功再执行业务，业务失败则删除记录并返回重试。高并发场景也可用 Redis 做前置去重：

Redis 去重只能降低重复概率，最终仍要依赖数据库唯一约束兜底。业务幂等的更多写法见 SQL 业务模型进阶。

8.5 消息轨迹

原生客户端用 producer.setEnableMsgTrace(true) 与 consumer.setEnableMsgTrace(true) 开启轨迹，默认写入 RMQ_SYS_TRACE_TOPIC；Spring Boot 配置 rocketmq.producer.enable-msg-trace: true 即可。轨迹能回答「消息何时发送、何时入库、何时被谁消费」，是排查丢失与重复的第一手证据。

9. 堆积与消费治理

9.1 堆积原因定位

现象 可能原因 排查
堆积持续上涨 消费 TPS 小于生产 TPS 对比生产与消费 TPS 曲线
堆积突然上涨 消费线程阻塞、下游超时 看消费 RT、线程栈、下游监控
个别队列堆积 队列倾斜或 rebalance 频繁 看各队列 Diff 与消费者实例变化
堆积后回落慢 批量太小、并发不足 调大批次与消费线程

9.2 提升消费能力

  1. 增加队列数：队列是并行上限。队列数创建时确定，调整需评估 rebalance，缩容不支持，稳妥做法是新建 Topic 迁移。
  2. 批量消费：调大 consumeMessageBatchMaxSize（如 10 到 32），减少网络与位点提交开销。
  3. 提高并发度：consumeThreadMin/Max 调到与下游承受能力匹配，不要盲目拉满。
  4. 扩消费者实例：实例数不要超过队列数，否则多出的实例分不到队列，纯空转。
  5. 5.x POP 消费：无状态消费，避免 rebalance 造成的停顿，适合大规模弹性伸缩。

9.3 限流与降级

消费端用令牌桶限制对下游的 QPS；下游故障时快速失败并返回重试，避免线程全部阻塞。非核心消费可临时降级为「只记录、不调用下游」，恢复后补偿。

9.4 关键监控指标

指标 含义 告警建议
生产 TPS 每秒写入消息数 突降可能上游故障
消费 TPS 每秒消费消息数 持续低于生产 TPS 即堆积
堆积量 Diff 未消费消息总数 按业务设阈值，如 10 万
消费延迟 消息生产到消费的时间差 核心链路超过 1 分钟告警
消费失败率 重试与死信比例 死信出现即告警

1. 审批流（approval_node_define / approval_instance / approval_record）

适用：请假、报销、采购等一切”提交后按既定节点逐级审批”的流程场景，核心是流程定义与运行时分离。

业务与数据关系

DDL

核心查询

常见坑

  • 流程定义变更影响在途实例：直接改节点定义，在途实例的 current_node 与新定义对不上（四节点流程被删成三节点）。定义必须版本化：实例创建时快照 flow_version，改动 = 发新版本，老版本只读。
  • 审批人变动导致待办悬空：指定人离职后待办永远查不出也审不了。提供转交（action = 3，应用层把节点审批人改为受托人）+ 定时扫描”current_node 停留超 N 天”的实例告警。
  • 并发审批同一节点：两人同时点同意，各自 current_node + 1，节点被跳过。推进必须 CAS：WHERE current_node = 读到的值 AND instance_status = 1，影响行数 = 0 即已被处理，回滚重读（并发语义同并发编程的 CAS）。
  • 会签计票无唯一约束：同一人双击投两票，COUNT 提前等于应到人数，流程被”一人”通过。uk_node_approver 从数据库层兜底。
  • 驳回重走撞唯一键：回到节点 1 重走时旧记录占着 (instance_id, node_order, approver_id)，新意见插不进。重走事务里先删 node_order >= 回退节点 的旧记录；更严谨的方案是记录表加轮次号（round）不删数据，时间线按轮次展示。

扩展点

  • 条件分支与多路径流程：节点定义加 condition_expr JSON（如”金额 > 5000 加签总监”），运行时求值选路径；流程形态复杂到分支并行、子流程时，别再硬造轮子，评估 Flowable / Activiti。
  • 审批代理/请假委托：approver_delegate（委托人、受托人、生效区间），解析审批人时先查委托关系。
  • 超时催办与自动处理：扫描节点停留时长，超阈值发 MQ 提醒；可配置超时自动通过/自动驳回。
  • 抄送：approval_cc（instance_id, user_id, read_at），与时间线并列展示”抄送给了谁、谁看过”。

2. 操作日志 / 审计日志（audit_log）

适用：合规审查、问题追责、行为回放——回答”这条数据到底被谁、在什么时候、从什么值改成了什么值”。

业务与数据关系

写入方式对比——审计数据从哪来，决定了它能回答什么问题：

写入方式 侵入性 语义完整度 说明
应用层 AOP 切面 中（注解标记业务方法） 高：有操作人、业务语义，可只记变更字段 自定义 @Audit 注解 + 切面异步落库，主推方案
ORM 拦截器 低（框架层统一拦截） 中：拿到的是 SQL 与参数，需反解实体变更 MyBatis Interceptor 兜底全量写操作

要点：审计表只 INSERT 不 UPDATE；写入走内存队列或 MQ 异步落库，不阻塞业务主事务——审计晚几秒可接受，业务被审计拖慢不可接受；资金类关键操作可退化为同步写保时效。

DDL

核心查询

常见坑

  • 同步写阻塞主流程：审计 INSERT 混在下单事务里，日志量一大拖慢主链路。异步写（内存队列/MQ），接受极端情况丢日志；资金类操作同步写。
  • 审计记录可被 UPDATE / DELETE：业务代码”顺手”改审计表，审计即失效。约定只 INSERT，且数据库账号不给业务服务 DELETE/UPDATE 权限。
  • 全字段快照存储爆炸：before/after 存整行 100+ 字段，大字段翻倍存储。应用层算 diff，只存业务关心字段与变更字段。
  • CDC 方案拿不到操作人：binlog 里没有登录态，Canal 同步的日志只有数据差异，回答不了”谁改的”。需要操作人语义就必须应用层埋点，两者是互补不是互替。
  • 查询不命中前缀索引：后台查询不带实体/操作人维度乱查全表。日志表查询必须强制时间范围并命中 idx_entity / idx_operator_action 前缀。

扩展点

  • 数据量过千万行后按月分区：分区键必须包含在主键内，先改主键再分区，之后过期数据 DROP PARTITION 秒级清档（远胜 DELETE 千万行）：
  • 冷数据归档：过期分区导出对象存储或 ClickHouse，MySQL 只保留热数据；合规审计查询走异构引擎。
  • 敏感字段（手机号/身份证）脱敏后再入审计，避免审计表本身成为泄露源。
  • 手机号/身份证等隐私字段的查询走单独授权，审计后台按角色隔离（权限模型见基础篇 RBAC）。

3. 多租户 SaaS（tenant / tenant_plan / 业务表）

适用：一套系统服务多家公司/团队，核心决策是隔离方案——它决定了唯一键、索引、路由乃至运维成本。

业务与数据关系

三种隔离方案先对比再选型：

方案 隔离度 成本 租户迁移 适合规模
共享表（tenant_id 列） 逻辑隔离，靠约束与代码纪律 最低：一套表一个库 难：数据按行搬 数千级中小租户，SaaS 主流
独立 schema 物理命名空间隔离 中：DDL×N、连接池×N、备份×N 中：整 schema 导出导入 数十~数百个中大型租户
独立库（可独立实例） 强隔离，故障与性能互不影响 高：实例×N、运维×N 易：整库搬走即完成迁出 少量大客户 / 金融强合规

DDL

核心查询

常见坑

  • 跨租户统计忘了隔离：运营报表 SQL 少写 tenant_id 条件，把 A 公司数据出给 B 公司，是 SaaS 最严重的资损级事故。铁律：业务侧 SQL 一律由拦截器注入 tenant_id；跨租户聚合只存在于运营后台的专属数据源。
  • tenant_id 可空列进唯一键：MySQL 唯一索引对 NULL 不生效（基础篇已详述），tenant_id 必须 NOT NULL，否则”租户内唯一”名存实亡。
  • 索引不以 tenant_id 打头：单表小数据看不出差别，租户量上来后每个查询都在全租户范围扫。所有业务唯一键与普通索引第一列一律 tenant_id。
  • 大租户数据倾斜：共享表里一个巨无霸租户拖慢所有人。演进路径：独立 schema → 独立库迁出；应用层按 tenant_id 路由数据源的能力必须设计期留好，事后加等于重写。
  • 无登录态调用漏网：定时任务、MQ 消费、第三方回调没有用户上下文，TenantContext 为空——拦截器”放行”就是事故源。系统级调用必须显式声明并手动传 tenant_id。

扩展点

  • 独立库方案的租户路由：tenant 表加 db_host / db_name 元数据，动态数据源按租户懒加载连接池并设上限，防止长尾租户拖垮连接数。
  • 租户级个性化配置：tenant_config（tenant_id, config_key, config_value JSON）承接套餐之外的定制项。
  • 计量计费：用量事件表（tenant_id, metric, usage, occurred_at）按小时聚合出账，配额校验复用①的模式。
  • schema-per-tenant 的 DDL 变更：Flyway 对每个 schema 循环执行，编排脚本记录每租户版本号，避免漂移。

4. 站内信 / 消息通知（notification / user_notification / user_message_cursor）

适用：系统公告、互动提醒、业务通知——核心矛盾是”一条消息发给谁、存几份、已读记在哪”。

业务与数据关系

写扩散 vs 读扩散对比：

维度 写扩散（投递表） 读扩散（位点）
存储 一次群发 N 用户 = N 行投递 一条消息 1 行 + 每用户 1 个游标
未读数 COUNT 投递表（或冗余计数） COUNT id > 游标（或冗余计数）
单条已读 / 删除 精确到人，支持 只能推进游标，单条删除做不到
群发成本 写放大，需分批 + MQ 削峰 写零成本
适合 私信、定向通知、量级可控的群发 全局公告、系统广播
混合 粉丝数万级大 V：活跃粉丝写收件箱 + 沉默粉丝靠位点拉取（推拉结合）

DDL

核心查询

常见坑

  • 已读状态放 notification 主表：群发消息一人已读 = 全员已读。已读是”用户 × 消息”维度，只能放投递表或用户位点。
  • 未读数实时 COUNT 大表：每次进首页都 COUNT 几十万行投递记录。冗余未读计数，已读/投递动作同事务增减，定时校准；高频计数走 Redis INCR（见Redis 缓存架构）。
  • 群发 10 万用户一次性 INSERT：锁、binlog、主从延迟三杀。拆批（每批 ≤1000）+ MQ 削峰慢速消费，接受”投递完成有分钟级延迟”。
  • 位点方案的”假已读”：游标推进会把从未展示过的旧消息一并标已读。”全部已读”按钮推进游标是对的；逐条精确已读只能用写扩散，产品语义要先对齐。
  • 内容冗余进投递表：正文复制 N 万份。主表存内容，投递表只存引用，改文案也只改一处。

扩展点

  • 推拉结合：大 V 发博，在线粉丝推收件箱、沉默粉丝登录后按位点拉取；关注关系建模见基础篇第 10 节。
  • 分类未读（互动/公告分开）：位点表加 category 维度，游标按 (user_id, category) 唯一。
  • 多端已读同步：投递表加设备维度，或位点方案区分”设备已读位点”与”账号已读位点”。
  • 冷消息归档：投递表只留 90 天，更早的引导到异构存储的”消息中心”；归档策略见数据库备份与恢复。

5. 工单系统（ticket / ticket_reply / ticket_action_log）

适用：客服工单、运维工单、售后处理——核心是集中式状态机 + 可考核的 SLA 时限。

业务与数据关系

DDL

核心查询

常见坑

  • 状态机散落在业务代码：到处 if/setStatus，”已关闭 → 处理中”这类非法流转防不住。状态流转收敛为一处 CAS：UPDATE ... WHERE status = 旧值，影响行数 = 0 即拒绝，非法迁移矩阵用枚举/配置表集中定义。
  • SLA 截止时间用纯 NOW 差值：周末与夜间不该计入响应时长。deadline 与耗时统计都要按工作日历（工作时间、节假日）计算，否则周五晚的工单全部”秒超时”。
  • 附件大字段入库：截图/日志文件存 BLOB 撑爆 buffer pool 和备份。对象存储，表里只存 URL（与站内信 content 同一原则）。
  • 转派只改 assignee 不留痕：绩效与责任扯皮无据可查。转派 = 写 action_log（from/to/原因）+ 更新 assignee，同一事务。
  • 会话一次 JOIN 全量拉取：回复表几十条无所谓，几百条就拖慢详情页。回复同样按 idx_ticket 游标分页。

扩展点

  • SLA 策略表 sla_policy（优先级 × 客户等级 → 响应/解决分钟数 + 工作日历 ID），建单时统一算 deadline，避免每处业务各自硬编码。
  • 超时升级链：扫描任务发现超时未受理，自动升级到组长（action = 4）并通知。
  • 满意度评价 ticket_satisfaction（ticket_id, score, comment），关闭后邀请评价，反哺 SLA 考核。
  • 工单标题/正文全文检索异构到 ES，MySQL 只承担状态与统计数据。

6. 对账与差错处理（recon_batch / channel_bill / recon_local_flow / recon_error / recon_adjust）

适用：T+1 资金对账——渠道账单与本地流水逐笔核对，比不平的进差错池，处理凭证落冲正单。

业务与数据关系

DDL

核心查询

常见坑

  • 金额用 FLOAT/DOUBLE：对账是 <> 精确比较，浮点误差天天”比不平”。一律 DECIMAL(18,2)（基础篇通用规则，资金场景零容忍）。
  • 渠道账单时区/日期切分边界：渠道按它自己的时区出账，0 点前后的单子可能落进相邻两天账期。导入前确认账单时区；边界单靠相邻账期交叉核对兜底。
  • 对账键选错：用渠道单号做主键，渠道重发、一单多次支付、退款反向单都会打乱它。以”商户订单号 + 支付次数”为对账键，渠道单号两边都存、只用于查证。
  • 重跑批次不清理：账单重新导入，差错直接翻倍。重跑 = 先 DELETE 该批次的 channel_bill 与 recon_error、批次状态回 0，再导入；uk_batch_trade 批内唯一键兜底。
  • 对账完成 ≠ 差错清零：批次状态”对账完成”只代表比对跑完，差错池要有 aging——超 3 天未处理的差错告警到人。

扩展点

  • 自动跑批：用第 7 节调度表拉起 T+1 对账任务，批次表记录进度与断点，失败可整批重跑。
  • 差错自动分类：规则引擎先消化可自动挂账的类型（如小额长款），只把疑难差错推给人。
  • 大账期并行比对：按对账键哈希分片，多线程/多实例分片比对，批次表记分片水位。
  • 对账结果异构数仓出资金日报；本地流水的源头（钱包双记流水）建模见基础篇第 8 节，资金库误操作的最后防线见数据库备份与恢复。

7. 定时任务调度表（job_info / job_log）

适用：不引入 XXL-Job 等框架时，用两张表 + 调度器实现多实例安全的轻量任务调度，核心是”抢锁防重复执行”。

业务与数据关系

DDL

核心查询

常见坑

  • 依赖应用服务器时钟：多实例时钟漂移导致触发早迟不一。时间统一以 DB 为准（NOW()），全部机器 NTP 对时。
  • 任务执行超过调度间隔导致堆积：5 分钟一跑的任务跑了 8 分钟，上一次未结束又触发。CAS 抢锁天然挡住第二次触发；要并行时把单行锁泛化为 max_running（允许并发数）+ 执行中计数，超限即告警。
  • 锁残留：执行实例被 kill -9，instance 永远占着，任务再也不跑。lock_at 超时接管（①a 的 OR 条件）+ 接管时告警。
  • 日志表无限增长：每天几万行一年千万级。按第 2 节审计表的分区写法按月分区、定期 DROP PARTITION，或只留 30 天。
  • Cron 格式混淆：Quartz 6 位与 Linux crontab 5 位不兼容，0 */5 * * * ? 少一位直接解析失败。保存配置时先试解析。
  • 秒级以下精度硬撑 DB 轮询：DB 轮询秒级精度到顶；更高频率或更复杂的延迟语义交给时间轮 / MQ 延迟消息。

扩展点

  • 分片广播：route_strategy = 3 时执行器按分片参数（index/total）拆分处理大表扫描任务，与订单表分片键呼应（基础篇第 1 节）。
  • 任务依赖编排：job_dependency（job_id, depends_on_id）组成 DAG，前置任务成功才触发下游。
  • 抢锁外置 Redis：SET NX PX 抢分布式锁，DB 只留执行结果（见Redis 缓存架构）。
  • 规模上来直接用 XXL-Job / PowerJob——本文两张表就是它们的核心数据模型，原理同源。
