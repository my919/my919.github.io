设计模式 · 备忘录模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

备忘录模式（Memento）在不破坏封装的前提下，捕获并保存对象的内部状态，以便将来恢复到该状态——如同游戏的存档。

2. 要解决的问题

问题 说明
需要撤销/回滚 恢复到某个历史状态
状态封装性 外部直接读字段会破坏封装
状态保存多份 历史快照要管理（存档列表）

典型场景：编辑器撤销（配合命令模式）、游戏存档、事务回滚（数据库 undo 日志思想）、浏览器后退。

3. 结构（角色）

关键：备忘录对外不透明——只有 Originator 能读写其内部，Caretaker 只负责保存与归还。

4. 代码实现（游戏角色存档）

5. 应用场景

场景 说明
编辑器撤销 文档快照（常配合命令模式）
游戏存档 角色状态恢复
数据库事务 undo 日志/回滚段（思想）
表单重置 恢复初始数据
配置回滚 配置快照恢复

6. 优缺点

优点 缺点
保存状态且不破坏封装 状态大时快照耗内存
恢复逻辑简单 频繁保存性能开销
状态历史可管理 需注意快照的深拷贝（引用类型）
与命令模式配合强大 备忘录内容变化后难迁移

注意：备忘录保存的是对象状态——内部引用类型要深拷贝，否则存的是引用，状态早就变了。

7. 与其他模式对比

模式 区别
命令模式 命令记录”操作”；备忘录记录”状态快照”（常配合）
原型模式 原型复制当前对象；备忘录保存并恢复历史
观察者 观察者关注变化；备忘录保存过去

1. 模式概述（意图）

中介者模式（Mediator）用一个中介对象封装一组对象的交互——对象之间不再直接引用，全部通过中介通信，把”多对多”改成”多对一”。

2. 要解决的问题

问题 说明
对象间耦合网状 每个对象都要知道所有其他对象（多对多）
交互逻辑散落 谁通知谁、怎么协调散在各对象里
难以复用与测试 对象强耦合，无法单独测试

中介者结构（星形）：A/B/C/D → Mediator（n 条依赖）。

典型场景：聊天室（用户之间不直接通信，经服务器）、航班调度塔台、MVC 里的 Controller（协调 Model 与 View）、消息队列。

3. 结构（角色）

4. 代码实现（聊天室）

新增用户：只需要注册到聊天室——原有用户代码零修改。

5. 应用场景

场景 说明
聊天/协作系统 用户经服务器通信
表单组件协调 多个控件联动（互不引用）
航班/交通调度 塔台协调飞机
消息队列 生产者消费者经 MQ 解耦
MVC Controller 协调 Model 与 View

6. 优缺点

优点 缺点
网状耦合 → 星形（n² → n） 中介者可能膨胀成”上帝对象”
交互逻辑集中，易维护 中介者单点故障（挂了全断）
同事类独立可复用 交互逻辑复杂时中介者难理解
符合开闭（加同事不改老代码） 比直接调用多一层

7. 与外观对比（高频考点）

维度 中介者 外观
方向 同事互相交互（双向） 子系统被外观单向封装
协议 同级的同事间协调 上下层简化入口
关注 交互逻辑 接口简化

迭代器模式（Iterator）提供一种方法顺序访问聚合对象（集合）内的元素，而不暴露其内部表示——遍历逻辑与集合结构解耦。

内部结构暴露 客户端知道底层是数组还是链表
遍历方式单一 正序/逆序/过滤需要不同遍历器

典型场景：所有 Java 集合的 iterator()、Java 8 之后基本被 for-each/Stream 取代——迭代器已是语言级内建，本模式主要理解思想与 Iterable 接口。

3. 结构（角色）

4. 代码实现（自定义迭代器）

遍历期间修改：迭代器遍历时修改集合会抛 ConcurrentModificationException（Java 用 modCount 快照检测）；需要安全的移除用 iterator.remove()。

5. 应用场景

场景 说明
Java 集合 List/Set/Map 的 iterator()
for-each 语法 编译器展开为迭代器
数据库游标 结果集逐行遍历
自定义数据结构 树/图的自定义遍历
Stream Java 8+ 更声明式的遍历

优点 缺点

支持多种遍历方式 函数式语言中常被 Stream/for-each 取代
统一接口（换集合不改客户端） 并发修改检测增加复杂度

7. 与其他模式对比

模式 区别
组合模式 组合定义树结构；迭代器遍历它
访问者 迭代器遍历+访问者操作节点
工厂方法 createIterator() 就是工厂方法

命令模式详解（Command）

发表于 2026-09-14 本文字数： 919 阅读时长 ≈ 3 分钟

设计模式 · 命令模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与策略对比。代码带详细注释。

1. 模式概述（意图）

命令模式（Command）把”请求/操作”封装成独立对象——调用方只发命令，执行方只执行，中间可插入队列、撤销、日志等能力。

2. 要解决的问题

问题 说明
请求发送方与执行方耦合 按钮直接调业务方法
需要排队/延迟执行 命令需要进入队列、定时执行
需要撤销/重做 记录命令历史才能回退
需要日志重放 审计/恢复需要记录操作

典型场景：编辑器撤销重做、任务队列、按钮/菜单动作（Swing Action）、事务日志、宏录制。

3. 结构（角色）

4. 代码实现（编辑器撤销）

扩展：命令支持队列（放入 MQ 异步执行）、宏（一组命令组合）、日志（记录命令序列用于恢复）。

5. 应用场景

场景 说明
撤销/重做 编辑器、数据库事务日志
任务队列 命令入队异步/批量执行
UI 动作 菜单/按钮绑定命令（Swing/Javafx）
事务日志 记录操作序列，崩溃恢复重放
远程调用 RPC 命令序列化传输

6. 优缺点

优点 缺点
发送者与执行者完全解耦 每个操作一个类（类数量多）
天然支持撤销/重做/队列 命令对象需要管理（序列化等）
可组合成宏命令 简单场景过度设计
支持日志与恢复 历史记录占用内存

7. 与策略对比

维度 命令 策略
目的 把”操作”对象化（可排队/撤销） 封装”算法”可替换
状态 命令可携带状态（撤销栈） 策略无历史
关注 何时执行、能否回退 怎么执行

设计模式 · 责任链

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与装饰器对比。代码带详细注释。

1. 模式概述（意图）

责任链模式（Chain of Responsibility）把多个处理者串成链，请求沿着链传递，每个处理者决定自己处理还是传给下一个——解耦”请求发送者”与”处理者”。

2. 要解决的问题

问题 说明
if-else 层层嵌套 校验/审批/过滤器逻辑堆在调用方
处理者需动态组合 增删处理环节要改调用方
谁处理不确定 运行时才能决定（权限链、审批链）

典型场景：登录校验链（参数→token→权限）、请假审批链（组长→经理→总监）、过滤器链、中间件链（Express/Koa）。

3. 结构（角色）

4. 代码实现（审批链）

变体：责任链也支持”全链路处理”（过滤器/中间件：每个处理者处理完继续传），如登录拦截链。

5. 应用场景

场景 说明
审批流 请假/报销按级别审批
校验链 参数校验→业务校验→权限校验
过滤器 Servlet Filter、Spring Security FilterChain
中间件 Express/Koa 洋葱模型
日志级别 日志按级别逐级过滤

6. 优缺点

优点 缺点
发送者与处理者解耦 请求可能无人处理（需兜底）
动态增删处理环节（开闭） 链长时性能损耗
职责单一（每环一件事） 调试链的传递过程麻烦
组合灵活 处理顺序固化后难调整

7. 与装饰器对比

维度 责任链 装饰器
传递 请求沿链传递，可中途停止 功能层层包裹，全部执行
目的 职责分担/过滤 功能增强
结构 链式（next） 嵌套包装

类型 说明
静态代理 手写代理类（每目标一个）
JDK 动态代理 接口 + InvocationHandler（反射生成）
CGLIB 动态代理 继承 + 字节码生成（无接口可用）

4. 代码实现

4.1 静态代理（权限控制）

4.2 JDK 动态代理（AOP 基础）

5. 应用场景

场景 说明

MyBatis Mapper 接口的代理实现
RPC Dubbo/Feign 远程调用的本地代理
懒加载 JPA 实体关联的延迟加载代理
安全代理 权限/审计控制

6. 优缺点

优点 缺点
不改原类加控制逻辑（开闭） 代理层增加调用链（性能小损耗）

享元模式详解（Flyweight）

发表于 2026-09-14 本文字数： 1.1k 阅读时长 ≈ 4 分钟

设计模式 · 享元模式

GoF 结构型模式。意图 · 结构 · 内部/外部状态 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

享元模式（Flyweight）通过共享大量细粒度对象来减少内存占用——把对象拆成”可共享的不变部分（内部状态）”和”不可共享的变化部分（外部状态）”。

2. 要解决的问题

问题 说明
对象数量巨大 百万个字符/棋子/图标，每个都 new 内存爆炸
大量对象只有小差异 重复内容多，可共享
内存压力 大流量场景 GC 频繁

核心思想：内部状态（不变，共享）+ 外部状态（变化，调用时传入）。

状态 说明 示例（字符对象）
内部状态 不可变、可共享 字符本身的字形
外部状态 随场景变化 字符的位置、颜色

3. 结构（角色）

4. 代码实现（文本编辑器字符）

5. 应用场景

场景 说明
字符串常量池 JVM 字符串驻留（"a" == "a"）
包装类缓存 Integer.valueOf 缓存 -128~127
线程池/连接池 复用对象（池化思想）
文字渲染 字符/图标/棋子
JDK String String 对象不可变共享

6. 优缺点

优点 缺点
大幅减少内存（共享） 需要区分内/外部状态（设计复杂）
对象复用减少 GC 外部状态管理增加调用复杂度
池化提高创建效率 状态拆分不当会引入并发问题（内部状态必须不可变）

关键约束：内部状态必须不可变——享元被共享，任何人不能改它；外部状态由调用方持有（不共享），否则并发下互相污染。

7. 与其他模式对比

模式 区别
单例 单例全局唯一；享元是一类对象的池化共享（多实例）
对象池 对象池复用”昂贵对象”；享元共享”小对象”
工厂 享元工厂负责缓存与创建

外观模式（Facade）为子系统的一组接口提供一个统一的简化入口——客户端只跟”门面”打交道，不直接面对一堆子系统类。

4. 代码实现（下单门面）

场景 说明
业务编排 下单、注册、导出等组合操作
框架封装 SqlSession、RestTemplate 内部复杂对外简单
老系统包装 把分散接口收敛成友好 API
分层架构 Service 层就是 Repository+外部调用的门面

6. 优缺点

优点 缺点
客户端简单（一个入口） 门面可能膨胀成”上帝类”
解耦（客户端不碰子系统） 隐藏了子系统细节（想精细控制时不便）
集中管理调用顺序/事务 需要与业务分层配合，否则混乱
便于测试（mock 门面） 门面职责边界要清晰

模式 区别

装饰器模式详解（Decorator）

发表于 2026-09-14 本文字数： 900 阅读时长 ≈ 3 分钟

设计模式 · 装饰器模式

GoF 结构型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与继承/代理对比。代码带详细注释。

1. 模式概述（意图）

**装饰器模式（Decorator）**动态地给对象添加职责——把功能拆成一个个”装饰层”，层层包裹，比继承更灵活。

2. 要解决的问题

问题 继承方案 装饰器方案
加功能 每种组合一个子类（爆炸） 组合叠加装饰层
动态加/减 编译期定死 运行时按需组合
多个功能叠加 子类数量 = 2^n 装饰类线性增长

经典例子：咖啡加牛奶、加糖、加奶泡——继承要 8 个类，装饰器只要 3 个装饰类任意组合。

3. 结构（角色）

4. 代码实现（咖啡加料）

核心：装饰器与组件实现同一接口，因此可以无限嵌套；每个装饰器只关注自己的增强。

5. 应用场景

场景 说明
JDK IO 流 new BufferedInputStream(new FileInputStream(f)) 层层包装
Spring @Transactional、@Cacheable 本质是装饰（代理）
日志增强 记录耗时、重试、限流的切面
权限校验 包装对象加权限检查
Java 集合 Collections.synchronizedList(list) 包装增强

6. 优缺点

优点 缺点
比继承灵活（运行时组合） 装饰器链层级多，排障难
避免子类爆炸 小对象多（每层一个对象）
符合开闭原则 要求组件与装饰器同一接口
职责单一（每层一件事） 调试堆栈变深

7. 与代理模式对比（高频考点）

维度 装饰器 代理
目的 增强功能 控制访问
接口 与组件同接口 与被代理对象同接口
创建者 客户端组合 代理创建/被代理方
生命周期 客户端管理 代理方管理
实例 IO 流 Spring AOP 代理
