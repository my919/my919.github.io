7. 典型案例：N+1 问题 DataLoader 治理

问题背景：内容平台的 GraphQL 网关上线两周，DB CPU 从 30% 飙到 85%。定位发现：首页 posts(first: 20) { author { name } comments(first: 5) { author { name } } } 一个查询触发了 1 + 20 + 100 次 SQL（每篇 post 查一次 author，每条 comment 再查一次 author）。

方案：请求级 DataLoader 批量加载，把 N+1 压成 3 次批量 IN 查询：

措施 效果
请求级 DataLoader 实例 同一请求内批量合并，DB 次数 121 → 3
每请求新建（不用全局单例） 避免跨用户缓存串数据
复杂度限制 maxDepth=6 恶意深查询直接拒绝

关键设计：

踩坑点：① 把 DataLoader 建成全局单例”想复用缓存”——User A 的私有数据进入缓存后被 User B 的请求读到，事故级越权；loader 必须每请求新建。② 批处理返回结果没按 ids 顺序对齐，部分字段错位成别人的数据——DataLoader 的返回顺序契约必须遵守。③ 只有 load() 没有 prime()：一条 post 查 author 后，同请求里 author.posts 又回查——用 loader.prime(id, value) 回填已持有的数据，省掉二次批量。④ 复杂度只限深度没限”开销”：first: 1000 的扁平查询照样打爆 DB——深度 + 复杂度分数（列表字段加权）双限制。⑤ 前端没有持久化查询，攻击者可任意拼查询绕过复杂度限制——生产环境启用 APQ（Automatic Persisted Queries）白名单。

8. 常见误用与陷阱

坑 现象/后果 解法
N+1 放任不管 一个查询触发上百次 SQL，DB 打爆 请求级 DataLoader 批量加载
DataLoader 全局单例 跨请求缓存串数据（越权事故） 每请求在 context 新建实例
批量结果不按序对齐 字段错位，读到别人的数据 返回数组顺序与 ids 一一对应
查询深度无限制 a{b{c{...}}} 递归攻击打挂服务 maxDepth + 复杂度分数双限制
无持久化查询 任意构造恶意查询绕过限制 APQ/Persisted Queries 白名单
列表分页缺失 first: 100000 一次拉全表 强制 Relay Connection 分页 + 上限
错误信息带堆栈 内部结构/SQL 泄露给客户端 production 下 mask 错误 + 日志侧留痕
Mutation 不幂等 网络重试导致重复下单 客户端生成幂等键，服务端去重
裸奔无鉴权 字段级数据任何人可查 字段级/类型级 directive 鉴权

8. 典型案例：流式通信（日志实时上报）

问题背景：边缘网关集群（2000 台设备）每秒产生 5 万条访问日志，原先每条日志一次 REST 上报：HTTP 握手开销占 70% 带宽，高峰期上报延迟 12s，服务端连接数打满。

方案：客户端流 + 双向流改造：设备按批推日志（客户端流），服务端反压与配置下发（双向流），单连接多路复用：

模式 用途 关键点
客户端流 批量日志上报 攒批 flush + 断线续传序号
双向流 配置/反压通道 心跳保活 + 优雅重连
服务端流 配置广播 重连后重新拉全量配置

关键设计：

踩坑点：① 没有透传 deadline：网关 A 调 B 调 C，A 设了 5s 超时，B 却用全新 context 调 C，下游挂了上游还在傻等——context.WithTimeout 改为从入参 context 派生，让 deadline 沿调用链自动递减。② 流式长连接经过 LB 空闲 60s 被掐断，设备以为是业务故障疯狂重连——LB 空闲超时调到 30min + 每 20s 心跳。③ 服务端流无限推送，慢客户端把服务端内存撑爆——用 Send 前检查流状态，配合服务端限速/丢弃策略。④ proto 里复用旧字段号改语义，新旧版本数据串字段——字段号只加不改。⑤ 重试没加退避和幂等键，服务端抖动时重试风暴雪上加霜——仅幂等方法重试 + 指数退避 + jitter。

9. 常见误用与陷阱

坑 现象/后果 解法
超时未透传 deadline 下游挂了上游傻等，线程堆积 context 派生传递，deadline 逐层递减
无重试策略 偶发 UNAVAILABLE 直接失败 ServiceConfig 配置重试（仅幂等方法）
重试无退避 抖动时重试风暴放大故障 指数退避 + jitter + 重试预算
proto 字段号复用 新旧版本数据串字段 只加字段不改号；废弃标 reserved
LB 掐断空闲长连接 流式连接反复断开重连 LB 空闲超时 ≥ 30min + 应用层心跳
服务端流无背压 慢客户端拖爆服务端内存 发送限速 + 流状态检查 + 丢弃策略
流式当队列用 断线即丢数据 重要数据落 Kafka/本地 WAL 再传
大消息默认上限 4MB 消息直接报错 分片传输或调 max message size
错误码乱用 UNKNOWN 满天飞无法定位 标准Status + withDescription + 细节payload

6. 消息可靠性

7. 典型案例：WebSocket 在线协作（协作文档）

问题背景：团队要给 CMS 加多人实时协作编辑：10-50 人同编辑一个文档，要求光标位置实时同步、断网恢复后内容不冲突、不丢字。初版实现”每次按键全量发正文”，两人同时编辑必然互相覆盖。

方案：WebSocket 房间广播 + 操作级增量（OT 思路）+ 版本号补发，三层保证实时性、一致性与可靠性：

关注点 方案 说明
传输 WebSocket（Socket.IO 房间） 降级长轮询兜底
同步粒度 操作级（插入/删除+位置） 不传全文，带宽降 95%
一致性 服务端定序 + 确定性合并 各端最终收敛一致
可靠性 oplog + seq 补发 断线不丢不重
扩展 Redis Adapter 跨节点广播 房间成员分布在不同节点

关键设计：

踩坑点：① 直接广播客户端原始 op，两个节点各定各的序，同一文档两端结果不一致——必须服务端单点定序（Redis INCR 或单写者）。② Nginx 未配 sticky session，重连落到另一节点后房间成员表错乱——长连接要 IP hash/cookie 粘性，且房间路由用 Redis 共享而不是节点内存。③ 忘了心跳，手机切后台 30 分钟的”僵尸连接”占满 fd——30s ping/pong + 空闲踢除。④ 广播先于持久化，服务重启时未落盘的操作丢失——先 append oplog 再 emit。⑤ 光标位置不做变换，他人在前面插入后你的光标”跳走”——presence 光标也要过 OT 变换。

8. 常见误用与陷阱

坑 现象/后果 解法
每次按键发全文 带宽爆炸、互相覆盖 操作级增量 + 定序合并
客户端各自定序 两端最终状态不一致 服务端单点定序（每文档计数器）
广播先于持久化 重启丢操作，用户内容丢失 先写 oplog 再广播
无心跳保活 僵尸连接耗尽 fd 30s ping/pong + 空闲连接踢除
无 seq 补发机制 断线期间的消息永久丢失 客户端带 lastSeq 重连，服务端补发
消息不去重 重传导致操作重复应用 msgId 去重 + seq 连续性校验
房间状态存节点内存 多节点广播失效、成员错乱 Redis Adapter + sticky session
广播无房限 大房间万人广播打挂服务 房间人数上限 + 分片/分页 presence

8. 典型案例：商品搜索索引设计（零停机重建）

问题背景：商城商品搜索上线三个月问题集中爆发：中文搜不出结果（分词器没配对）、重建索引要停服、翻页翻到 5000 条就报错、索引一天天变大磁盘告警。

方案：IK 分词 + 精细 mapping（该分词的分词、不该索引的关掉）→ 别名机制支持零停机重建 → search_after 深分页 → 动态 mapping 收紧控制膨胀。

踩坑点：

  • IK 装了但 mapping 里 analyzer 没指到它，或索引/搜索两侧都用 ik_max_word 导致召回过杂——索引用 ik_max_word（细粒度）、搜索用 ik_smart（粗粒度）。
  • 直接改 mapping 字段类型：ES 直接报错，只能重建索引——别名机制必须第一天就上。
  • from+size 翻页过深直接 400：导出/翻页一律 search_after；跳页需求预查总数 + 关键词约束。
  • 动态 mapping 放飞：脏数据把 price 推成 text，聚合全挂——生产索引 dynamic: strict + 显式 mapping。

9. 常见误用与陷阱

坑 现象/后果 解法
深分页 from+size 翻页过万条报 Result window is too large search_after（交互翻页）/ scroll（离线导出）
分词器误配 中文整句成 token 搜不到；索引/搜索分词不分 索引 ik_max_word + 搜索 ik_smart，mapping 显式指定
动态 mapping 放飞 脏数据推歪字段类型，聚合/排序全挂 dynamic: strict + 显式 mapping + 写入前校验
索引膨胀 全字段建索引 + 冗余 _source，磁盘月增 30% 不搜索 index:false、不聚合 doc_values:false、_source 按需过滤
写后立查查不到 refresh 前的数据不可见，用户以为丢了 refresh_interval 30s + 关键路径手动 _refresh 或 wait_for
mapping 不可变 线上改类型报错才想起别名 索引带版本号 + 别名切换，重建流程剧本化

用户反馈「下单偶尔慢」，但 Grafana 大盘 QPS 与错误率全绿——单一指标回答不了”慢在哪”。团队只能逐台服务器翻日志，平均定位时间 40 分钟以上。

8.4 踩坑点

  • 日志没注入 traceId，三支柱各自为政只能靠时间戳人肉对齐——整合排障的第一前提

消息 MQ 异步下单 削峰填谷、失败重试
数据库 乐观锁兜底 最后防线
