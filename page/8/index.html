10. 典型案例：CDN 边缘计算（个性化页面 + 动静分离）

问题背景：跨境电商站点用户遍布 30 国，源站在美国：登录态用户的购物车/货币/语言都依赖源站动态渲染，东京用户 RTT 180ms，首页 TTFB 2.1s；大促时源站带宽费用暴涨。目标是：静态资源全球快，动态个性化也不能慢。

方案：动静分离 + 边缘个性化：静态走 CDN 缓存，个性化片段由 Cloudflare Worker 在边缘组装，Cookie/会话不过源站：

层 策略 说明
静态资源 CDN 长缓存 + 指纹版本 sw-cacheable 1 年 + 版本号失效
HTML 外壳 短缓存（60s）+ 语言维度 Vary 全球近源命中
个性化片段 Worker 边缘组装 会话校验/购物车/A-B 在边缘
强一致请求 回源 + mTLS 支付/库存写操作不缓存的场景

关键设计：

踩坑点：① 静态资源没带指纹版本，边缘缓存 1 年改版后用户看到旧 CSS——内容哈希文件名 + 不可变缓存头。② HTML 缓存键漏了语言维度，日本用户命中英文缓存——Vary/缓存键必须覆盖所有影响内容的请求维度。③ 把购物车价格计算放边缘 KV，库存变了边缘还是旧价，用户结算价与展示价不符——边缘只做”展示级个性化”，强一致数据回源并在结算页二次确认。④ Worker 里同步 await 两个慢查询（购物车+推荐），串行叠加延迟——Promise.all 并行 + ctx.waitUntil 把非关键路径（埋点/推荐）挪到响应后。⑤ 边缘 KV 写后读不一致（购物车刚加的 item 不显示），用户重复点击——写操作回源，读展示容忍秒级陈旧 + 客户端乐观更新。

11. 常见误用与陷阱

坑 现象/后果 解法
静态资源无指纹 改版后用户见旧样式 内容哈希文件名 + immutable 缓存头
缓存键漏请求维度 多语言/站点串缓存 键覆盖 URL+语言+站点等全部维度
边缘算强一致数据 展示价与结算价不一致 边缘只做展示个性化，一致性回源
边缘 KV 当强一致存储 写后读不一致，重复提交 写回源，读容忍陈旧 + 乐观更新
Worker 里串行慢调用 边缘延迟反而变高 Promise.all 并行 + waitUntil 后置
会话校验回源 每请求回源，边缘白干 JWT 边缘验签（JWKS 边缘缓存）
无降级预案 边缘故障等于全站故障 Worker 异常时回退纯 CDN 模式
日志只在边缘采样 安全事件无法审计 边缘结构化日志 → 中心聚合（Tail Worker）
跨境合规忽视 用户数据出境违规 按区域路由 + 数据本地驻留（EU→EU）

9. 典型案例：多租户隔离方案落地

问题背景：一家 B2B CRM SaaS 从 30 家客户增长到 3000 家。最初所有租户共库共表（tenant_id 行级隔离），某大客户（金融行业）要求「数据物理隔离 + 审计合规」，而长尾客户对价格敏感、必须摊薄成本——单一隔离模式两头不讨好。

方案：采用 Bridge（混合）模式：按客户等级路由到不同隔离单元，租户上下文全链路传播：

客户等级 隔离模式 数据策略 成本归属
金融/旗舰客户 Silo（独立部署） 独立数据库实例 独享计费
中型客户 Pool 共享库、独立 Schema 按量分摊
长尾/免费客户 Pool 共享 Schema + tenant_id 成本最优

关键设计：

踩坑点：① 定时任务和 MQ 消费线程没有租户上下文，TenantContext.get() 返回 null，把 A 租户的数据写给 B——所有异步入口必须显式携带并恢复租户 ID（消息头/任务参数）。② 线程池复用线程未 clear()，上一个请求的租户 ID “粘”到下一个请求，属于最隐蔽的越权。③ 缓存 key 不带租户（deals:list），A 公司看到 B 公司的客户列表——缓存键一律 t:{tenantId}:deals:list。④ 只靠应用层 WHERE tenant_id，一次手写 SQL 的报表功能漏了条件就跨租户——上 RLS 后这类事故归零。

10. 常见误用与陷阱

坑 现象/后果 解法
租户上下文不清理 线程复用后串租户（隐蔽越权） 请求结束 finally clear() + 接口强制非空
异步链路丢租户 MQ/定时任务查不到数据或查错数据 消息头/任务参数携带租户 ID，消费端恢复
缓存 key 不带租户 跨租户读到对方数据 键名统一 t:{tenantId}:... 前缀
只靠应用层过滤 手写 SQL 漏 WHERE 就跨租户 PostgreSQL RLS / 行级策略兜底
大租户拖垮共享池 一个大客户的导出任务打爆 Pool 大租户迁 Silo；共享池配额/并发限制
Schema 迁移漂移 3000 个 Schema 结构不一致 Flyway 按租户循环执行 + 版本对账
配额只在应用层 客户端并发把系统打挂 网关租户级限流 + 存储/算力硬配额
日志无租户标识 跨租户问题排查无从下手 MDC 注入 tenantId，日志平台按租户检索
计费与用量脱节 大用量客户按低档付费 用量事件化上报 + 账期对账

9. 典型案例：事件驱动订单系统

问题背景：外卖平台下单链路原先同步串行调用 6 个下游（库存、优惠券、积分、通知、风控、发票）：一个接口 5 层 HTTP 嵌套，P99 2.8s；任一下游抖动，下单整体失败率飙升。营销活动还要求”积分服务可以挂，下单不能挂”。

方案：下单核心（库存+订单）保持强一致，其余下游全部事件化解耦，复杂流程用 Temporal 编排：

改造项 改造前 改造后
下游依赖 同步 5 层调用，全链路同生共死 核心同步 1 次，其余事件异步
下游故障 下单整体失败 消费重试/重放，下单不受影响
新增下游 改下单代码 + 联调上线 订阅 topic 即可，发布方零改动
P99 2.8s 180ms（同步部分）

关键设计：

踩坑点：① 早期事件没带 eventId，Kafka at-least-once 重投导致积分翻倍发放——消费必须幂等（唯一键去重）。② 事件无版本演进：加字段后老消费者反序列化崩溃——Schema Registry + 向后兼容策略强制卡点。③ 「订单已创建」事件被库存服务当 RPC 响应反向回查发布方接口，耦合回来了——事件只携带消费所需最小事实，缺数据由消费方自查。④ 事务内直接 kafkaTemplate.send()，事务回滚了消息却发出去了——一律走事务发件箱（outbox）模式。⑤ Temporal Workflow 里写了非幂等的本地副作用，Worker 重放历史时重复执行——Activity 要幂等，副作用放 Activity 不放 Workflow 主干。

10. 常见误用与陷阱

坑 现象/后果 解法
事件无版本 加字段导致老消费者反序列化崩溃 Schema Registry + 向后兼容策略
消费不幂等 重复投递 → 积分/库存重复处理 eventId 唯一约束去重
消费不可重入 重放 offset 就产生二次副作用 副作用幂等设计 + 处理标记表
事务内直接发消息 事务回滚但消息已发出 事务发件箱（outbox）+ 中继发布
事件当 RPC 用 消费方反查发布方接口，耦合回归 事件携带最小事实，消费方自查缺失数据
死信无人管 DLQ 堆积，业务悄悄漏单 DLQ 告警 + 补偿工单流程
无死信只无限重试 一条毒消息卡死整个分区 有限重试 → 死信 → 人工介入
分区键乱选 同一订单事件乱序（先”已支付”后”已创建”） 按 orderId 分区 + 消费端按版本/时间戳判序
编排器里做副作用 Workflow 重放导致重复执行 副作用放 Activity 且幂等

问题背景：电商支付服务 payment-svc 从 v1 升级 v2（重构了渠道适配层）。此前用 K8s 原生 Rolling Update 灰度：错误率飙到 4% 时回滚，但此时 v1/v2 Pod 混布，出现”一半用户付款失败”的事故。需要按流量比例 + 按 Header 精准灰度，且失败能秒级回滚。

方案：Istio Ambient 模式 + VirtualService 分级灰度：先内部账号灰度，再按比例放量，全程金丝雀指标自动观测：

阶段 策略 观察指标 回滚手段
内部灰度 Header 精准路由 功能验证、日志 删除 header 规则
小流量 v2 10% 错误率、P99、渠道成功率 VS 权重改回 0
放量 50% → 100% 业务指标（支付成功率） 秒级改权重
全量 v2 100% 持续 24h 观察 保留 v1 镜像 7 天

关键设计：

踩坑点：① 只建了 VirtualService 忘了 DestinationRule 的 subset，路由报 no healthy upstream——subset 必须与 Pod label 严格对应。② 灰度期间 v1/v2 的数据库 schema 不兼容（v2 多写了一列），回滚 v1 后写入报错——schema 变更要向后兼容（加列不删列），应用与 DDL 分开发布。③ Ambient 模式下忘装 waypoint，L7 的 Header 匹配不生效，按权重规则匹配到了 header 规则——L7 精准路由必须给 namespace 挂 waypoint。④ 回滚只改了 VS 权重，但 Envoy 配置未推送（istiod 与 ztunnel 版本不匹配），”秒级回滚”变成 20 分钟——升级 mesh 组件保持版本矩阵一致。

8. 典型案例：Terraform 状态管理治理

8.1 问题背景

10 人团队共用本地 tfstate + 网盘同步：两人并发 apply 互相覆盖；有人嫌 apply 慢直接在控制台手改安全组；一次资源改名触发 30 个资源销毁重建，prod 数据库险些陪葬。

8.2 解决方案

远端 S3 后端 + DynamoDB 状态锁；state 按环境与模块拆分（爆炸半径最小化）；改名一律 terraform state mv 而非 delete+create；CI 用 -detailed-exitcode 每日跑漂移检测，发现漂移自动开 issue 并通知值班。

8.3 关键实现

8.4 踩坑点

  • state 里存了 RDS 密码明文输出，S3 桶一度对全公司可读；改 KMS 加密 + 敏感输出走 Secrets Manager
  • 改名直接改代码触发销毁重建，30 个资源下线；rename 必须 state mv
  • 单一大 state 全环境共用，apply 要 20 分钟且一坏全坏；按 env/module 拆成 12 个小 state
  • 漂移检测只跑了一次没人跟进；改为每日定时 + 未处理漂移升级到资源负责人

9. 常见误用与陷阱

9.1 问题背景

9.2 解决方案

用 Rust 编写 Wasm 边缘函数部署到 Cloudflare Workers：请求到达边缘即校验 Referer/签名，非法请求直接 403 不回源，合法请求重写签名 URL 透传；黑白名单进 KV 缓存；按 Country 头灰度放量。

9.3 关键实现

9.4 踩坑点

  • 未做 wasm-opt 裁剪，二进制 8MB 导致 Worker 加载超时；-Oz + 去掉 regex crate 压到 400KB

  • 直接 unwrap panic 触发 500 瀑布；全部 Result 化并加降级放行兜底（防盗链挂了不能影响正常出图）

8. 典型案例：用”面试复盘表”把挂掉的面试变成下一家的 offer

问题背景：小王半年面了 11 家全挂，每次挂完只留一句”感觉答得不好”，从不知道具体输在哪；下一场继续重复同样的错误。

方案：每场面试结束 24 小时内做结构化复盘，迭代”题库 + 答案 + 讲法”，第 5 场起通过率明显上升。

关键实践：按”出现频次 × 挂掉次数”排序，优先补高频弱项；项目讲述（STAR）录音回听，砍掉冗余背景铺垫；每场面试前只复习”答案库 + 两道新题”，不做无头苍蝇式泛刷。

踩坑点：复盘写成情绪日记（”面试官真刁钻”）而不落到题目与答案迭代；另一坑是只复盘知识题不复盘”讲故事”——很多人挂在项目深度追问链，而不是算法。

9. 常见误用与陷阱

坑 现象/后果 解法
海投不定位 面试全靠撞，精力耗尽 锁定 3 类岗位分层投递
背题不追深 一追问就露馅 每个知识点准备两层追问
项目讲成流水账 面试官抓不到亮点 STAR + 量化结果先行
不问需求先做题 系统设计跑偏被扣分 先澄清 QPS/数据量/约束
薪资谈判先报底价 被锚定，涨幅受限 让对方先出价，谈总包
挂掉就情绪内耗 影响下一场状态 24h 复盘落表，翻篇
简历造假注水 背调/追问崩盘 真实经历 + 打磨讲法
