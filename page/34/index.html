第三章：Docker 部署 1Panel

概念基础

  1. 1Panel 是开源的 Linux 服务器运维管理面板：在网页上即可管理网站、数据库、容器、防火墙、定时任务等，替代繁琐的命令行运维。
  2. 为什么用 Docker 部署：面板本体与依赖全部封进镜像，一条 docker run 即可拉起，升级与重建都围绕镜像和数据卷进行，不污染宿主机。
  3. 两类典型环境：Windows + Docker Desktop + WSL（必须端口映射 -p，勿用 --network host）与 Linux Docker 主机（可直接 host 网络）。
  4. 管理宿主机的关键：面板通过挂载 /var/run/docker.sock 获得管理宿主机 Docker 的能力，通过 /opt 与 BASE_DIR 约定数据目录。
  5. 安全底线：改强 PASSWORD、设 ENTRANCE 安全入口、按需放行安全组端口，避免面板暴露在公网被扫描。

共用前提

  • docker version 客户端与 Server 均正常，能拉取 Docker Hub（或已配置镜像加速）。
  • 建议内存 ≥ 1GB；多架构以 Hub 页为准。
  • 将 PASSWORD、ENTRANCE 等换成自己的值；变量含义见文末 「常用环境变量」。

第一类：Windows + Docker Desktop + WSL

场景：宿主机为 Windows，容器由 Docker Desktop 提供引擎；你在 WSL 里打开终端（发行版可为 Rocky Linux 10、Ubuntu 等），docker version 的 Server 往往显示 Docker Desktop 或上下文为 desktop-linux。此时容器里的 host 网络与你在 WSL 里访问的 localhost 不是同一概念，不要使用 --network host，应使用 -p <PORT>:<PORT>。

若曾误用 host 建过同名容器，先 docker rm -f 1panel-v2 再按本节重建。

第二类：Linux Docker 主机

场景：Linux 云服务器、物理机或虚拟机内安装 Docker Engine（非 Docker Desktop 作为服务端）。可用 --network host，面板监听端口即宿主机端口，与安全组、防火墙规则一致。

面板核心功能速览

部署完成后，1Panel 的能力远不止”装个面板”：

应用商店

内置 OpenResty（Nginx）、MySQL、PostgreSQL、Redis、MongoDB、Halo、WordPress、Memos、Vaultwarden 等百余款应用，一键安装即自动完成容器编排、端口映射与反向代理挂载；支持自定义应用仓库（Git 仓库形式的第三方应用集）与本地应用（上传自有 docker-compose 模板），团队内部标准化交付常用中间件非常方便。安装时可选端口外部访问开关，默认仅本机暴露，安全默认做得比多数面板好。

网站管理

  • 一键建站：静态站点 / 反向代理 / PHP 运行环境三类，自动生成 OpenResty 配置；
  • SSL 证书：集成 Let’s Encrypt / ZeroSSL，支持 DNS 自动验证（泛域名）与自动续签，对接阿里云、腾讯云、Cloudflare 等 DNS 厂商；
  • WAF：基于 OpenResty 的 CC 防护、IP 黑白名单、UA 拦截，免费版可用基础规则；
  • 防盗链、访问日志、错误日志 面板直查，省去上机 tail。

备份与计划任务

  • 备份账号：支持本地磁盘、S3 兼容对象存储、阿里云 OSS、腾讯 COS、七牛、WebDAV、SFTP，备份先落本地再推远端；
  • 计划任务：按 cron 周期备份网站、数据库、目录、面板快照，保留份数可配，失败邮件/Webhook 通知；
  • 快照：升级前一键打面板快照，异常时整体回滚。

数据库与文件管理

数据库页支持 MySQL/PostgreSQL/Redis 的建库、授权、远程访问开关与 phpMyAdmin/Adminer 直达；文件管理器支持在线编辑、压缩解压、权限修改与批量上传，临时改个配置不必再开 SFTP 客户端。

容器与镜像管理

容器页可直接创建/启停/重建容器、看日志、进终端、改 compose；镜像页支持拉取、清理 dangling、构建镜像；编排页以 docker-compose 文件管理整套栈，改动即 docker compose up -d，与命令行操作完全一致、互不冲突。

本地应用示例：把团队的 docker-compose.yml + .env 模板放到 /opt/1panel/resource/apps/local/<name>/ 下按约定组织，商店即出现”本地应用”，新同事装机从十分钟命令行变一分钟点选。

监控与审计

概览页实时展示 CPU/内存/磁盘/网络与负载趋势；进程守护（Supervisor）、防火墙（iptables/firewalld 规则图形化）、SSH 登录日志与面板操作审计一应俱全，多人共用时可回溯”谁在什么时间改了什么”。

安全加固清单

  1. 改强密码 + 开双因素（面板设置 → 安全 → 2FA）；
  2. ENTRANCE 安全入口 设为难猜路径，并开启授权 IP 白名单（仅公司/家庭出口 IP 可访问）；
  3. 面板端口不进公网：云安全组只放行必要业务端口（80/443），面板端口走白名单或 VPN/跳板；
  4. 关闭面板默认的未使用服务端口（如 phpMyAdmin 用完即关）；
  5. 定期升级镜像并备份快照，升级前看 CHANGELOG 与社区反馈。

升级与日常维护

数据位置：面板数据在 BASE_DIR/1panel（默认 /opt/1panel）下，含 apps/（应用）、www/sites/（网站）、backup/（本地备份）、db/（面板自身 SQLite）；迁移机器时整目录打包 + 面板快照即可。

常见端口约定：面板默认 10086，应用商店装的 MySQL/Redis 默认不对外暴露，需远程访问时在应用设置里显式开启并在安全组放行。

常见问题排查

问题 排查路径
面板打不开 docker logs 1panel-v2 看启动日志；确认 PORT 与安全组放行；检查 ENTRANCE 路径是否带错
忘记密码/入口 docker exec -it 1panel-v2 1pctl user-info 查看；1pctl reset password 重置

第十三章：网页自动化：Python + Selenium 入门与实战

概念基础

Selenium 是浏览器自动化的事实标准，让 Python 代码替你「亲手」操作浏览器：

  1. 驱动真实浏览器：用代码控制 Chrome / Edge / Firefox 完成打开网页、点击、填表、读取数据等人类操作，所见即所得。
  2. 工作原理：脚本遵循 W3C WebDriver 协议，经驱动程序把指令翻译给浏览器——因为跑的是真浏览器，JS 动态渲染后的页面内容也能拿到，这是它与普通 HTTP 爬虫库的本质区别。
  3. 免管驱动：Selenium 4.6+ 内置 Selenium Manager，自动匹配本机浏览器与驱动版本，不再手动下载 chromedriver。
  4. 两大典型场景：端到端（E2E）测试——模拟用户行为验证系统能否走通；数据采集——处理需要登录、翻页、JS 渲染的页面。
  5. 稳定性心法：页面加载是异步的，固定 sleep 不可靠；显式等待 + 稳定定位器才是自动化脚本不脆弱的关键。

第五章：Docker 部署 RocketMQ 实践

概念基础

  1. 没有「单容器一体」形态：NameServer 与 Broker 是两个独立进程（5.x 还有一个可选的 Proxy），最小栈就是两个容器——这与 Kafka 的 KRaft 单进程不同，下文用「网络 → NameServer → Broker」三步完成最小栈。
  2. brokerIP1 是第一坑：Broker 启动时把自己注册到 NameServer 的地址就是 brokerIP1，客户端拿这个地址直连 Broker——容器内不显式指定时往往是内网容器 IP，宿主机客户端会「能拿到路由却连不上」。本机访问写 127.0.0.1、跨机写宿主机可达 IP（对照 Kafka 的 advertised.listeners）。
  3. 端口按角色记忆：9876 NameServer；10909 / 10911 / 10912 分别是 Broker 的 VIP / 主 / HA 端口；8080 / 8081 是 5.x Proxy 的 gRPC 端口——只用经典 Remoting 客户端时，Proxy 端口可以不映射。
  4. 数据目录与边界：Broker 数据在 /home/rocketmq/store（日志在 logs），必须挂卷；单机部署面向开发验证，生产多 Master/Slave 或 DLedger 自动切换请用 RocketMQ Operator 或官方推荐拓扑。

架构速览：NameServer 与 Broker 如何协作



flowchart LR
  P[Producer] -->|① 拉路由| NS[NameServer]
  C[Consumer] -->|① 拉路由| NS
  B[Broker] -->|② 每30s注册路由| NS

角色 状态 关键点
NameServer 无状态，互相之间不通信 Broker 向每一个 NameServer 注册；客户端可配多个地址任取其一；挂了不影响已拿到路由的收发，只影响「新路由发现」
Broker 有状态（CommitLog + ConsumeQueue + IndexFile） 按 brokerName + brokerId 区分：brokerId=0 是 Master，>0 是 Slave；周期向 NameServer 上报路由
Proxy（5.x） 无状态接入层 面向 gRPC 新客户端；经典 Remoting 客户端可不开

存储模型一句话：所有消息顺序追加到 CommitLog，再异步分发到按 Topic/Queue 组织的 ConsumeQueue 索引——顺序写盘是 RocketMQ 高吞吐的根基，也是 store 目录必须挂好盘的原因。

第三章：ClickHouse 查询与性能调优

概念基础

  1. 快的前提是少读：ClickHouse 的调优永远围绕「让扫描更少」——分区裁剪、排序键前缀、跳数索引、只选需要的列。
  2. ORDER BY 是物理排序：MergeTree 的排序键决定磁盘数据布局，查询条件包含排序键前缀才能命中主键索引跳过 granule。
  3. PREWHERE 是 ClickHouse 特有的过滤下推：先读小列过滤、再读大列，比 WHERE 更省 IO（优化器常自动迁移，手动写大列场景更稳）。
  4. 物化视图是预聚合：写入时同步算好聚合结果落表，查询直接读聚合表——大屏/报表从分钟级到毫秒级的核心手段。
  5. JOIN 是短板不是黑洞：右表全量进内存的哈希 JOIN 模型要求右表小；大表关联优先改造成字典/宽表/物化视图。

本章承接 第一章：ClickHouse 列式存储入门 的表结构与 第二章：Docker 部署 ClickHouse 实践 的环境；SQL 按 ClickHouse 25.x 官方语法书写（沙箱无实例，未逐条运行验证）。

一、查到慢查询：system 表与 EXPLAIN

EXPLAIN indexes = 1 输出关注：Parts（分区裁剪后剩几个 part）、Granules（主键索引筛掉多少 granule）——两个数字没降说明查询没吃到索引。

补充两个日常诊断 SQL：

判读口诀：Parts 从几百降到个位数 = 分区裁剪生效；Granules 从全量降到百分之几 = 主键前缀生效；两者都纹丝不动 = 回到建表设计找问题。

二、让扫描更少：分区、排序键、跳数索引

手段 生效条件
分区裁剪 WHERE 带分区列（event_date），别对分区列套函数
主键索引 WHERE/ORDER BY 命中 ORDER BY 的最左前缀
minmax 索引 数值/日期列的范围过滤
bloom_filter payload = 'xxx'、IN 这类大列等值查询
LowCardinality 低基数枚举列（几十~几万个取值），压缩与速度双赢

与 MySQL 索引思想相通：最左前缀原则在 MergeTree 上同样成立，见 第一章：MySQL DDL 语句与表设计入门 的复合索引章节。

三、查询特性语法

写法 建议
uniq() 默认近似去重（误差 ~1%）；精确用 uniqExact()，代价高
FINAL 单表小范围用；大表改为 ORDER BY (排序键) + argMax 或查询时去重

LIMIT 大分页 避免深分页；按排序键游标翻页（WHERE key > last LIMIT n）

四、物化视图：预聚合

  • 只对「新写入」生效：建视图后历史数据要 INSERT INTO 目标表 SELECT ... FROM 源表 手工回填。
  • 查询端再聚合一层（SummingMergeTree 的 merge 时机不定，查询时仍需 GROUP BY）：

物化视图的三个陷阱

  1. 历史数据不会自动回填：建视图前的数据要 INSERT INTO 目标表 SELECT ... FROM 源表 GROUP BY ... 手工补。
  2. 视图串联要显式：视图 A 的源表如果是另一个视图 B 的目标表，A 不会自动触发——需要在 B 的 SQL 里继续写 TO 链。
  3. 目标表引擎要配对：聚合类视图的目标表用 SummingMergeTree / AggregatingMergeTree，普通 MergeTree 会存重复行。

五、Projection：预计算的第二种形态（25.x）

Projection 是 MergeTree 的表内预计算结构——同一张表存多份不同排序/聚合的数据副本，优化器自动选择最省的那份，不需要建第二张表、不需要改查询 SQL：

对比项 物化视图 Projection
存储位置 独立目标表 源表内部（随 part 一起 merge）
查询改写 手写查目标表 优化器自动命中
一致性 视图失败可能丢同步 与源表 part 级强一致
适用 跨表聚合、多张报表 同表多维度加速

经验：同表「换个维度 GROUP BY」优先 Projection；跨表、多下游报表才上物化视图。

六、写入端调优：Too many parts 与批量纪律

查询慢有时根因在写入侧——part 太多拖垮 merge 与查询规划：

症状 诊断 处方
Too many parts 拒写 system.parts 按分区统计 part 数 写入攒批（每批几万~几十万行）
merge 永远跑不完 system.merges 长期排队 降低写入频率、加 background_pool_size
查询 Planning 慢 part 上千后规划耗时陡增 同上 + OPTIMIZE ... FINAL 应急

七、资源护栏：别让一条 SQL 拖垮整机

  • max_memory_usage：超限报错而非 OOM 宕机，保住整实例。
  • max_execution_time：报表接口防呆，超时快速失败。
  • 配额（Quota）：按用户/时段限制查询总量，防止 BI 工具狂刷。

  1. SSH 是远程运维的生命线：服务器只在机房里亮灯，日常工作全靠 ssh 进入；密钥免密、~/.ssh/config 别名、端口转发是三件必修装备。
  2. systemd 是 PID 1：现代 Linux 的 1 号进程，统一管理服务、日志（journald）、定时任务（timer）——把自己的脚本注册成服务，才算真正「上线」。
  3. 日志先行：排障顺序永远是「先看日志，再猜原因」；journalctl 统一了服务的 stdout 与系统日志，带 --since、-f、-p err 精确定位。

  5. 重复的事交给调度器：临时脚本用 cron，需要依赖关系、日志、错峰的服务级调度用 systemd timer。

第二章：Windows 上 WSL（Rocky Linux）与 Docker Desktop

概念基础

  1. WSL 是什么：WSL（Windows Subsystem for Linux）让 Windows 直接运行真正的 Linux 发行版，无需双系统或整机虚拟机，一条命令即可进出 Linux 环境。
  2. WSL2 的意义：WSL2 基于轻量级虚拟机，系统调用兼容性完整，是 Docker Desktop 官方推荐的运行后端——没有 WSL2 就没有流畅的容器体验。
  3. 为什么选 Rocky Linux：与 RHEL 同源的企业级发行版，dnf 生态与生产服务器一致，作为本地演练环境最贴近真实运维。
  4. Docker Desktop 的角色：提供图形化引擎管理（更新、证书、镜像加速），通过 WSL integration 把 docker CLI 注入各发行版，Rocky 内无需再装 dockerd。
  5. 适用场景：在 Windows 机器上做 Linux 运维演练与容器开发；代码放在发行版内的 Linux 文件系统中可获得最佳 I/O 性能。

5. 镜像加速与构建缓存（Docker Engine）

在 Docker Desktop → Settings（设置）→ Docker Engine 中编辑 JSON（与引擎配置同源，保存后 Apply & restart 生效）。若已有其它键（如 insecure-registries），请把下面片段合并进现有对象，不要整段覆盖导致丢配置。

  • registry-mirrors：拉取镜像时优先走列表中的镜像站，减轻访问 docker.io 的延迟与失败（镜像站可用性与合规以你网络环境为准，可日后替换为团队提供的地址）。
  • builder.gc：为 BuildKit 构建缓存开启自动回收，defaultKeepStorage 限制默认保留量（示例 20GB），避免构建缓存占满磁盘。

修改后点击 Apply & restart；再在 Rocky 或 PowerShell 中执行 docker info，在输出里确认 Registry Mirrors 已包含上述地址。

6. 文件与性能建议

  • 项目代码放在 WSL 发行版自己的 Linux 文件系统里（例如在 wsl -d Rocky-10 里用 ~/project，即 /home/你的用户/project），不要放在 /mnt/c/... 下做大量编译与 Docker 构建，可减少跨系统 I/O 延迟。

  • Docker Desktop 的 Settings → Resources 可调 CPU、内存、磁盘镜像上限，与 Rocky 其它进程共用本机资源，按机器配置酌情调大。

2. 是否需要「登录」、如何设置与验证 root 密码

是否要登录：WSL 从 Windows Terminal、wsl -d Rocky-10 等方式进入时，一般是直接进入已配置的默认 Linux 用户的 shell，不会像 SSH 那样再在终端里提示输入一次用户名（除非你主动执行 login、su 等）。首次安装某些发行版时会交互式让你创建 UNIX 用户名与密码；Rocky 官方 .wsl 导入后的默认用户以该镜像说明为准（常见为 root 或需自行建普通用户，见下节）。

root 密码是什么、要不要设：root 账户始终存在；若从未执行过 passwd，root 可能没有可用登录密码（或镜像预置了密码，以发行版文档为准）。日常维护建议用带 sudo 的普通用户；需要 root shell 时再切。
