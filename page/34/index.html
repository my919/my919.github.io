ClickHouse：Docker 部署实践

概念基础

  1. 为什么用容器跑 ClickHouse：一条命令拉起、版本随标签固定、环境与宿主机解耦——本地分析环境与生产部署的基础单元。
  2. 数据持久化是底线：必须把数据目录 /var/lib/clickhouse 挂载到命名卷或宿主机目录，否则容器删除即数据清零。
  3. 初始化语义：.sql / .sh 放入 /docker-entrypoint-initdb.d（卷挂载），仅在首次初始化空数据目录时执行，已有数据卷时不会重复执行。
  4. 端口与账号：HTTP 8123 + Native 9000 双端口对外；CLICKHOUSE_USER / CLICKHOUSE_PASSWORD 配合 CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT=1 可用 SQL 管理用户与权限。
  5. 三种部署形态：docker run 单容器 → Docker Compose（声明式 + 健康检查）→ Kubernetes（Secret + PVC + 探针），按环境复杂度逐级选用；表引擎与查询用法见 ClickHouse：列式存储入门。

PostgreSQL：Docker 部署实践

概念基础

  1. PostgreSQL 是 C/S 架构的关系库：服务端 postgres 进程监听 5432 端口，客户端（psql、JDBC）通过连接串访问；「部署」的本质就是两件事——把服务端进程跑起来、让数据落在可靠的地方。
  2. 容器化 = 环境即代码：镜像内置二进制与依赖，一条命令起库；POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB 环境变量完成初始化，首次空数据目录时还会自动执行 /docker-entrypoint-initdb.d 下的脚本。
  3. 三种部署形态由小到大：docker run 单容器（本地开发）→ Docker Compose 编排（健康检查、.env 管敏感项）→ Kubernetes（探针、PVC 持久化、集群化运维）。
  4. 数据与容器分离：容器随时可删，数据必须在**卷（Volume）**上——镜像升级换容器、卷不动，这是容器化数据库的第一原则。

〇、PostgreSQL 简介与选型（入门速览）

PostgreSQL 是功能最全面的开源关系型数据库，与 MySQL 的核心差异：

  • MVCC 机制：读不阻塞写、写不阻塞读，多版本并发控制。
  • 丰富数据类型：JSONB、数组、范围、枚举、几何类型。
  • 强大扩展生态：pgvector（AI 向量检索）、PostGIS（地理）、TimescaleDB（时序）。
  • 标准 SQL 支持完善：窗口函数、CTE、递归查询开箱即用。
  • PL/pgSQL：内置存储过程语言。

选型建议：MySQL 侧重简单易用、生态广；PostgreSQL 适合复杂查询、JSON、地理位置、AI 向量检索等场景。新项目数据模型复杂时优先 PostgreSQL。

类别 选型 用途
数据库 PostgreSQL 17+ 开源关系型数据库（功能最全面）
客户端 psql 命令行
部署 Docker 本地与测试
扩展 pgvector / PostGIS / pg_stat_statements 向量检索/地理/监控
备份 pg_dump / pg_basebackup 逻辑/物理备份

概念基础

概念基础

  1. KRaft 让单进程成为可能：旧版 Kafka 需要 ZooKeeper + Kafka 两个进程；KRaft 模式下一个容器同时扮演 controller + broker，单机一条命令即可起集群（本章单容器示例的核心）。
  2. 监听器与 advertised.listeners 是第一坑：Kafka 会把 advertised.listeners 里的地址返回给客户端——容器内监听 0.0.0.0 没用，客户端拿到的是这个「广告地址」。本机访问写 127.0.0.1、Compose 内服务访问写服务名、跨网段要双监听，本章三种部署形态的差异全在这一个参数上。
  3. 数据目录与 page cache：数据在 /bitnami/kafka（Bitnami 镜像），必须挂卷；Kafka 依赖磁盘顺序写与 page cache，内存不宜压得过低。
  4. 边界要清楚：单容器 / Compose / 单副本 Deployment 都面向开发验证；生产多 Broker 应使用 Strimzi 等 Operator 或 StatefulSet，不要把单实例 Deployment 当集群扩。

KRaft 架构速览：没有 ZooKeeper 之后

Kafka 4.x 已彻底移除 ZooKeeper（3.x 是过渡双模期），集群元数据由一组 Controller 节点用 Raft 协议自管理：

角色 职责 在本章配置里的位置
Controller 维护元数据日志 __cluster_metadata（Topic、分区、ACL、配置），处理分区选主 KAFKA_CFG_PROCESS_ROLES=controller + KAFKA_CFG_CONTROLLER_QUORUM_VOTERS
Broker 存数据、服务读写 KAFKA_CFG_PROCESS_ROLES=broker
Combined 单进程同时扮演两者 controller,broker（本章单容器正是此形态）

关键点：

  • controller.quorum.voters 格式为 id@host:port[,...]，生产取奇数个（3 或 5）并把 Controller 与 Broker 分开部署；开发环境单节点写 0@... 即可。
  • 元数据变更先写 Raft 日志再生效，Broker 增量拉取元数据——不再有 ZK Watcher 风暴，重启大集群的元数据同步也快了一个量级。
  • node.id 必须唯一且稳定：挂卷重启不能变，Bitnami 镜像由 KAFKA_CFG_NODE_ID 指定；首次启动镜像会自动格式化元数据目录，换数据卷不换 NODE_ID（或反向）会导致 cluster.id 冲突，此时需清空数据目录重来。
  • Controller 端口（示例 9093）只做仲裁通信，永远不要映射给客户端。

分区、副本与 ISR：可靠性的三个旋钮

旋钮 作用域 含义与建议
分区数（partitions） Topic 决定并行度上限（消费组内同分区最多 1 个消费者）；创建后只能增不能减，按峰值吞吐估算后留余量
副本因子（replication-factor） Topic 副本总数（含 Leader）；生产至少 3，单机开发用 1
min.insync.replicas Topic / Broker 配合 acks=all 时 ISR 中至少要有这么多副本才确认写入；副本 3 时常设 2，牺牲一点可用性换不丢数据

ISR 是动态集合：Follower 落后超过 replica.lag.time.max.ms（默认 30s 无追平进展）即被踢出，追上后自动回归。unclean.leader.election.enable 默认 false：Leader 宕机只从 ISR 里选新 Leader，宁可分区暂不可用也不让落后副本当选而丢数据——除非业务明确接受丢消息，否则不要为可用性打开它。

多 Broker 集群（多 Compose service 或 K8s 多副本）就绪后，用 --replication-factor 3 建 Topic 再 --describe 观察 Leader 是否均摊，是验证数据面正确性的最快方式。

数据保留与磁盘防线

  • 清理策略：cleanup.policy=delete（默认，按 retention.ms / retention.bytes 删旧段）或 compact（按键保留最新值，适合做变更日志）；两者可同时启用。

第一章：Docker 部署 MySQL 实践

概念基础

容器化是「把 MySQL 实例连同版本、配置、账号一次性描述清楚」的部署方式：

  1. 环境一致、随起随删：一条命令拉起带指定版本、字符集、账号密码的实例，不污染宿主机；卸载即删容器，重装零成本——这正是第一章建好表结构之后最需要的环境。
  2. 数据与容器分离：容器可随时销毁，数据必须落在卷（volume）；命名卷 mysql-data 持久化 /var/lib/mysql，删容器不丢数据，但删卷等于删库，这是容器数据库的第一铁律。
  3. 镜像即版本契约：优先官方 mysql 镜像并固定小版本标签（如 mysql:8.0.40）或 digest，避免 latest 漂移；8.0 起默认认证插件 caching_sha2_password，老客户端需升级或调整参数。
  4. 初始化只发生一次：/docker-entrypoint-initdb.d 下的 .sql / .sh 仅在首次空数据目录时执行；之后的表结构变更要走 SQL 迁移，不会自动重放。
  5. 部署形态递进：单容器（docker run）→ 编排（Docker Compose）→ 集群（Kubernetes）；开发环境用前者即可，生产还要叠加备份、监控、网络策略、TLS 与 Secret 管控。

九、容器化注意事项（避坑清单）

1. 数据卷与文件系统

  • 必须用卷：容器层（容器可写层）性能差且随容器删除；命名卷或绑定挂载二选一，生产推荐绑定挂载到独立磁盘便于备份与迁移。
  • Windows / macOS 的 Docker Desktop 有文件系统翻译层，/var/lib/mysql 绑定挂载到宿主机目录时 I/O 性能显著下降且易遇权限问题——桌面系统上优先命名卷；生产一律 Linux 宿主机。
  • 勿把数据目录挂到 NFS/网盘类存储：锁语义与 fsync 行为不可靠，可能损坏数据。

2. 内存限制与 OOM（最高发事故）

MySQL 默认按宿主机内存估算缓冲池。容器若限制 2G 内存而 innodb_buffer_pool_size 是默认的 128M 还好，但一旦你在 my.cnf 里按「机器有 32G」的习惯写了 8G，容器会被 cgroup OOM Killer 直接杀掉，表现为随机重启：

3. 其他高频坑

  1. 时区：容器默认 UTC，务必 TZ=Asia/Shanghai + --default-time-zone='+8:00' 双保险，否则 NOW() 差 8 小时。
  2. lower_case_table_names 只能初始化时设定（数据目录非空后不可改），Linux 默认 0（大小写敏感），从 Windows 迁库前务必确认。
  3. 重启策略：restart: unless-stopped，但不要依赖自动重启代替监控——实例反复崩溃时重启循环会掩盖根因。
  4. 健康检查：应用编排中用 depends_on + condition: service_healthy 等健康检查通过再启动应用，避免应用先于数据库就绪而启动失败。
  5. 升级：不可直接换镜像标签原地升级大版本（8.0 → 8.4）——正确路径是先 dump 再灌入新实例，或按官方升级路径逐级替换镜像并让它跑完 mysql_upgrade 等价流程。

概念基础

  1. 镜像即环境：官方 redis 镜像内置匹配版本的 redis-server / redis-cli，一条命令即可获得与生产一致的运行时，避免「本机装不上 / 版本不对」。

内存策略：maxmemory 与淘汰

容器内存不是无限的，必须显式设上限，否则宿主机 OOM 时 Redis 首当其冲：

配置 说明
maxmemory 512mb 使用上限；不设则默认吃到宿主机内存耗尽
maxmemory-policy allkeys-lru 到上限后淘汰最近最少使用的 key（缓存场景推荐）
volatile-lru 只在设了 TTL 的 key 里淘汰；无 TTL 的 key 永不淘汰，写会报错
noeviction 到上限后拒绝写入（默认）；适合把 Redis 当存储而非缓存
allkeys-lfu / volatile-ttl 按访问频率 / 按剩余 TTL 淘汰，特定场景用

以上配置用启动参数 --maxmemory 512mb --maxmemory-policy allkeys-lru 或写进 redis.conf 均可。容器侧再配合 --memory 768m（大于 maxmemory，留 fork 与缓冲余量），双层护栏。
