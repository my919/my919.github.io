第一章：Redis 概述、安装与 CLI 入门

概念基础

Redis（REmote DIctionary Server）是一个基于内存的键值（KV）存储系统：

  1. 数据在内存：读写不落盘，单次操作微秒级，比磁盘数据库快 1~2 个数量级；同时提供 RDB / AOF 持久化把数据落到磁盘。
  2. KV 模型，值有类型：键（key） 永远是字符串；值（value） 支持多种数据类型（String / Hash / List / Set / ZSet 等），不同类型对应不同命令族与底层结构，这是 Redis 与 Memcached 这类「纯字符串 KV」最大的差别。
  3. 单线程命令执行：命令在单线程事件循环中顺序执行（基于 epoll / IO 多路复用），单个命令天然原子；Redis 6.0+ 引入的「多线程」只用于网络 IO 读写，命令执行仍是单线程。
  4. 为什么快：内存操作 + IO 多路复用 + 单线程无锁竞争 + 针对各类型优化的高效底层结构（SDS、跳表、quicklist 等）。
  5. 定位：缓存为主，兼任分布式锁、计数器、排行榜、消息队列、地理位置等；缓存 ≠ 数据库，关键数据以关系库为准，Redis 丢数据要有降级与重建预案。

理解了定位，再看它与周边的关系：

官网与定位

  • Redis 文档（当前产品站）：https://redis.io/docs/
  • 下载与发行说明：https://redis.io/downloads/
  • 命令参考：https://redis.io/commands/

Redis 以键值为核心，值支持多种数据类型（字符串、哈希、列表等）；默认监听 6379。与关系型数据库不同，数据主要在内存中，须结合淘汰策略、持久化与备份设计，避免单点丢数。

安全与网络要点

  1. 默认无密码时，只要网络能连上 6379 即可读写，仅允许本机或可信内网；公网暴露须配 requirepass 与 Redis ACL，并配合防火墙、TLS（视版本与部署形态）。
  2. bind：默认若监听 0.0.0.0，表示所有网卡可连；缩小监听地址可减少误暴露。
  3. 危险命令：FLUSHALL、CONFIG 等在生产应通过 rename-command 禁用或限制执行身份。

第三章：MyBatis-Plus 快速上手与分页原理

概念基础

MyBatis-Plus（简称 MP） 是 MyBatis 的增强工具，定位是「只做增强不做改变」：

  1. 通用 CRUD：Mapper 继承 BaseMapper 即可获得 selectById、insert、update 等单表增删改查能力，免写 XML。
  2. 插件体系：通过 MybatisPlusInterceptor 注册分页、乐观锁、防全表更新等内部拦截器，按需装配。
  3. 分页零侵入：内置 PaginationInnerInterceptor，基于 MyBatis 拦截器自动生成 count 语句、改写 SQL 拼接 LIMIT，业务代码只传 Page 参数。
  4. 代码生成：配合 IDEA 插件（如 MyBatisX-Generator）可从数据库表直接生成 Entity / Mapper / Service 代码。
  5. Spring Boot 集成：提供 mybatis-plus-spring-boot*-starter 起步依赖，配好 mapper-locations 与驼峰映射即可使用。

MyBatis-Plus 分页原理

一、核心一句话

MP 分页本质：MyBatis 拦截器 + 自动改写 SQL

  1. 你传入 Page<>(当前页,每页条数)
  2. MP 分页拦截器拦截 Mapper 查询方法
  3. 自动帮你生成 count 总数SQL + 拼接 limit 分页SQL
  4. 执行两条 SQL：查总数 → 查当前页数据
  5. 把总数、页码、数据封装到 IPage 返回

二、关键核心组件

  1. MybatisPlusInterceptor
    MP 核心插件容器，所有插件（分页、防全表更新、乐观锁）都往里注册。
  2. PaginationInnerInterceptor
    MP 真正的分页拦截器，核心逻辑全在这。
  3. Page / IPage
    分页参数载体，存：当前页、每页条数、总记录数、总页数、分页数据。

三、完整执行流程（一步一步走）

1. 配置分页拦截器（必须配置，否则分页无效）

2. 业务代码使用

3. 底层执行步骤

  1. 进入 Mapper 方法前
    PaginationInnerInterceptor 拦截到 selectPage 查询。
  2. 判断是否是分页查询
    检测方法参数里有没有 IPage/Page 对象，有就走分页逻辑。
  3. 自动生成 COUNT 语句
    原SQL：select id,name from user
    自动生成：select count(*) from user → 查询总记录数
  4. 改写原SQL 加 LIMIT
    原SQL 被改写为：
    select id,name from user limit 0,10
  5. 执行两条 SQL
    • 第一条：查总条数
    • 第二条：查分页数据
  6. 封装分页信息
    把总条数、当前页、每页大小、总页数、数据列表 全部塞进 IPage 返回。

四、为什么不用自己写 limit、不用自己写 count？

MP 拦截器动态解析 SQL、动态拼接 limit、动态生成 count，完全无侵入。

五、分页两个重要特性

1. 分页合理化 reasonable=true

  • 输入页码 <=0 自动变成第 1 页
  • 输入页码 大于总页数 自动返回最后一页

2. 溢出总页数后是否查最后一页

PaginationInnerInterceptor 可配置，防止页码乱输报错。

六、常见坑（原理衍生出来的）

  1. 没配置 PaginationInnerInterceptor → 分页无效，查全部数据
  2. 只有 Mapper 层用 Page 参数才生效，Service 自己写 list 不分页
  3. 自定义 XML SQL 也能自动分页，MP 照样拦截加 limit、count
  4. 多表联查、复杂 SQL 也支持，拦截器会解析原有 SQL 结构

七、极简总结

MP 分页 = 拦截器拦截SQL → 自动查总数 → 自动拼接LIMIT → 封装分页结果

不用手写 count、不用手写 limit，全靠拦截器动态代理实现。

本章小结

要点 结论
引入方式 mybatis-plus-spring-boot4-starter 起步依赖 + @MapperScan 扫描 Mapper 包
分页生效条件 必须注册 MybatisPlusInterceptor 并添加 PaginationInnerInterceptor，否则分页无效
分页原理 拦截器自动生成 count SQL 并改写原 SQL 拼接 LIMIT，两条 SQL 完成分页后封装进 IPage
实用特性 分页合理化 reasonable、溢出回退末页；自定义 XML 与多表联查 SQL 同样支持
常见坑 仅 Mapper 方法携带 Page 参数才触发分页；Service 自行 list() 不会分页

第二章：Gradle 构建工具：安装、配置与常用命令

概念基础

Gradle 是基于 JVM 的现代构建工具，广泛用于 Java / Kotlin / Android 项目：

  1. 脚本即代码：构建脚本用 Groovy DSL（build.gradle）或 Kotlin DSL（build.gradle.kts）编写，比 XML 更简洁、可编程。
  2. 复用 Maven 仓库体系：依赖坐标与 Maven Central、google() 等仓库完全兼容，可配置阿里云镜像加速下载。
  3. 增量构建与缓存：通过任务图、增量构建与构建缓存避免重复工作，大型项目构建明显更快。
  4. Gradle Wrapper：项目内提交 gradlew 即可固定团队 Gradle 版本，新成员免手工安装，保证构建环境一致。
  5. 与 Maven 的取舍：Maven 约定优先、上手简单；Gradle 更灵活、性能更好，但脚本自由度高，团队需要统一规范。

第一章：Maven 构建工具：安装、配置与常用命令

概念基础

Maven 是 Java 生态最主流的项目构建与依赖管理工具：

  1. 构建自动化：一条 mvn 命令即可完成编译、测试、打包、安装全流程，无需手工调用 javac、维护 classpath。
  2. 约定优于配置：默认标准目录结构（src/main/java、src/test/resources 等）与标准构建生命周期，代码按约定放置即可构建。
  3. POM 与坐标：项目由 pom.xml 描述，依赖以坐标（groupId / artifactId / version）唯一定位，Maven 据此自动下载并解析传递依赖。
  4. 仓库与镜像：依赖先查本地仓库（~/.m2/repository），再从远程仓库（Maven Central）下载；国内配置阿里云镜像可显著加速。
  5. 生命周期与插件：clean、compile、test、package、install 等命令本质是调用绑定在生命周期上的插件目标，可按需扩展。

mvn clean package 没跑测试就上线 单元测试本来挂着，被本地 -DskipTests 习惯掩盖 CI 必须不跳过测试；本地临时跳过用 -DskipTests（编译测试类），少用 -Dmaven.test.skip=true（连编译都跳过）
多模块循环依赖 构建阶段报错 “The projects in the reactor contain a cyclic reference” 抽公共代码到第三模块 common；或模块内拆 package，不要用「A 依赖 B，B 依赖 A」
target/ 目录提交到 Git 仓库中出现一堆 class/jar，每次 PR 冲突 项目根放 .gitignore，至少忽略：target/、*.iml、.idea/、.classpath、.project
本地仓库脏了 以前失败下载留下 _remote.repositories 标记，死活不再拉取 find ~/.m2 -name "*.lastUpdated" -delete；或直接清出问题包的整个目录让 Maven 重新下
JDK 版本与 maven.compiler.source 不一致 用 JDK 21 编译成 8，String.valueOf 某些重载、Record 等编译报错 固定 <java.version>21</java.version> 并引用 ${java.version}；CI 用 actions/setup-java 同 JDK 大版本

第八章：FastAPI：现代 Python Web API 框架入门

概念基础

FastAPI 是近年 Python 社区增长最快的 Web 框架，专精 API 服务开发：

  1. 现代框架组合：Web 层基于 Starlette（异步 ASGI 框架），数据层基于 Pydantic（类型校验与序列化），强强联合。
  2. 类型驱动开发：请求参数、请求体、响应模型都用 Python 类型标注声明，框架自动完成解析、校验、错误提示——写类型就是写约束，也是写文档。
  3. 自动交互文档：启动即得 Swagger UI（/docs）与 ReDoc（/redoc），接口可在浏览器里直接调试，无需手写接口文档。

  5. 定位取舍：相比 Django 的「全家桶」（ORM / Admin / 认证内置），FastAPI 只聚焦 API 层，数据库与认证按需组合，适合微服务、数据服务与 AI 推理接口。

坑 现象 正确做法
路径参数类型漏声明 /items/{id} 全按字符串收，内部 int(id) 可能抛 500 用 Pydantic 模型或 def read_item(id: int)，FastAPI 自动 422 + 友好错误
Body 参数忘加 Body(...) / Pydantic Model 单参数接口 Swagger 里永远是 query，不是 JSON body 显式 Body() 或定义 class Item(BaseModel)，两者二选一向 FastAPI 表明”从 body 读”
依赖注入（Depends）忘记调用 写了 get_db: Session = Depends(get_db)，但里面写的是同步 yield 却在异步路由里混用 同步路由 + 同步依赖，异步路由 + async def 依赖；数据库连接池按场景配 async-sqlalchemy 或同步库
422 但请求体没错 自定义模型里字段默认值用了 mutable [] / {}，数据互相污染 默认值永远写 Field(default_factory=list)，不要 items: list = []
CORS 没开或顺序错 前端浏览器报 No 'Access-Control-Allow-Origin'，Postman 却正常 最前面加 app.add_middleware(CORSMiddleware, …)，在路由注册之前；允许的 origins/headers/methods 写全
用了 run_in_threadpool 的同步 DB 查询也阻塞 Starlette 默认线程池小，并发高时排队 用 async SQLAlchemy + asyncpg 或 encode/databases；或 anyio.to_thread.run_sync + 调大 worker 数
Pydantic v1 vs v2 API 混用 旧教程的 @validator 提示不存在，Config 写成 class Config 报错 Pydantic v2 用 @field_validator，配置写 model_config = ConfigDict(...)；项目锁定 pydantic 大版本
响应模型写 response_model=None / 没写 数据库对象（带密码哈希）直接返回给前端，泄露敏感字段 严格定义 ReadUser、UpdateUser 等分离模型，显式写 response_model=
单文件 app.py 上千行 路由冲突、调试困难、import 循环 用 APIRouter 拆分模块：routers/users.py 中 router = APIRouter(prefix="/users")，主应用 app.include_router(router)
--reload 在生产用 内存泄漏、CPU 浪费、文件监听误触发重启 生产用 gunicorn -k uvicorn.workers.UvicornWorker 或 uvicorn main:app --workers 4，关闭 reload

第六章：UV 项目开发添加 Pytest：单元测试

概念基础

pytest 是 Python 事实标准的单元测试框架：

  1. 断言极简：直接用普通 assert 语句写断言，无需记忆 xUnit 风格的 assertEquals 等方法；失败时 pytest 自动展示表达式各部分的实际值，排障高效。
  2. 自动收集：按 test_*.py / *_test.py 文件名与 test_ 前缀函数自动发现用例，无需继承基类、无需注册。
  3. 工程化配置：通过 pyproject.toml 的 [tool.pytest.ini_options] 约定测试目录（testpaths）、标记（markers）与默认参数（addopts），团队与 CI 行为一致。
  4. 生态丰富：pytest-cov 出覆盖率报告、pytest-xdist 多核并行、marker 分组筛选（-m "not slow"），并可与 uv、pre-commit（见第五章）、CI 无缝衔接。

发表于 2026-05-01 更新于 2026-09-01 分类于 Python 本文字数： 1.2k 阅读时长 ≈ 4 分钟

第五章：UV 项目开发添加 pre-commit：Git 提交钩子

概念基础

pre-commit 是一个 Git 提交钩子管理框架，在 git commit 前自动执行质量检查：

  1. 质量门禁前置：把 Ruff、BasedPyright、pytest 等检查放到提交时刻自动执行，不合格代码进不了仓库，避免「CI 跑一半才发现格式问题」。
  2. 配置即代码：所有钩子集中在 .pre-commit-config.yaml，团队成员克隆仓库后 pre-commit install 一次接入，执行同一套检查链。
  3. 钩子链有序执行：本站推荐顺序为通用清理（pre-commit-hooks）→ Ruff → BasedPyright → pytest，由轻到重、快速失败。
  4. 与 uv 协作：工具钩子用 repo: local + uv run 调用，版本与 uv.lock 完全一致，本地与 CI 行为统一。
