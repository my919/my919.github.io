责任链模式详解（Chain of Responsibility）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.5k 阅读时长 ≈ 3 分钟

设计模式 · 责任链

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与装饰器对比。代码带详细注释。

1. 模式概述（意图）

责任链模式（Chain of Responsibility）把多个处理者串成链，请求沿着链传递，每个处理者决定自己处理还是传给下一个——解耦”请求发送者”与”处理者”。

2. 要解决的问题

问题 说明
if-else 层层嵌套 校验/审批/过滤器逻辑堆在调用方
处理者需动态组合 增删处理环节要改调用方
谁处理不确定 运行时才能决定（权限链、审批链）

典型场景：登录校验链（参数→token→权限）、请假审批链（组长→经理→总监）、过滤器链、中间件链（Express/Koa）。

3. 结构（角色）

4. 代码实现（审批链）

变体：责任链也支持”全链路处理”（过滤器/中间件：每个处理者处理完继续传），如登录拦截链。

5. 应用场景

场景 说明
审批流 请假/报销按级别审批
校验链 参数校验→业务校验→权限校验
过滤器 Servlet Filter、Spring Security FilterChain
中间件 Express/Koa 洋葱模型
日志级别 日志按级别逐级过滤

6. 优缺点

优点 缺点
发送者与处理者解耦 请求可能无人处理（需兜底）
动态增删处理环节（开闭） 链长时性能损耗
职责单一（每环一件事） 调试链的传递过程麻烦
组合灵活 处理顺序固化后难调整

7. 与装饰器对比

维度 责任链 装饰器
传递 请求沿链传递，可中途停止 功能层层包裹，全部执行
目的 职责分担/过滤 功能增强
结构 链式（next） 嵌套包装

8. 常见误用与陷阱

坑 现象 解法
链尾无兜底 请求走完所有节点无人处理，静默丢失 链尾必须加默认处理器（拒绝/记录/抛异常）
循环引用 A.setNext(B)、B.setNext(A) 导致死循环 用容器组装链（List），禁止手工 setNext
链过长性能损耗 每个请求遍历几十上百个节点，延迟飙升 控制链长 ≤ 10，或按类型路由到子链
处理者状态污染 Handler 用成员变量存请求上下文，并发串数据 方法参数传上下文，Handler 保持无状态

代理模式详解（Proxy）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.4k 阅读时长 ≈ 3 分钟

设计模式 · 代理模式

GoF 结构型模式。意图 · 结构 · 静态/动态代理 · 代码实现 · 应用场景 · 优缺点 · 与装饰器对比。代码带详细注释。

1. 模式概述（意图）

代理模式（Proxy）为其他对象提供一个替身/代理，由代理控制对真实对象的访问——在不修改原对象的前提下，加入控制逻辑。

2. 要解决的问题

问题 代理作用
对象创建昂贵 懒加载（真正用时才创建）
访问需控制 权限校验、访问日志
远程访问 本地代理转发到远程（RPC 代理）
横切逻辑 事务、缓存、安全（AOP 本质）

典型场景：Spring AOP 动态代理、MyBatis Mapper 代理（只定义接口就能执行 SQL）、RPC 远程代理、Proxy.newProxyInstance。

3. 结构（角色）

三种代理：

类型 说明
静态代理 手写代理类（每目标一个）
JDK 动态代理 接口 + InvocationHandler（反射生成）
CGLIB 动态代理 继承 + 字节码生成（无接口可用）

4. 代码实现

4.1 静态代理（权限控制）

4.2 JDK 动态代理（AOP 基础）

CGLIB 场景：类没有接口时（Spring 默认优先 CGLIB）。

5. 应用场景

场景 说明
Spring AOP @Transactional/@Cacheable 基于动态代理
MyBatis Mapper 接口的代理实现
RPC Dubbo/Feign 远程调用的本地代理
懒加载 JPA 实体关联的延迟加载代理
安全代理 权限/审计控制

6. 优缺点

优点 缺点
不改原类加控制逻辑（开闭） 代理层增加调用链（性能小损耗）
职责分离（控制与业务解耦） 动态代理调试困难（看不到真实类）
支持远程/懒加载等场景 JDK 代理只支持接口
可组合（多层代理） 过度代理导致调用栈深

7. 与装饰器对比（高频考点）

维度 代理 装饰器
目的 控制访问 增强功能
对象创建 代理常自己创建目标 客户端组合
关注点 权限/懒加载/远程 功能叠加
实例 Spring AOP IO 流包装

8. 常见误用与陷阱

坑 现象 解法
this 自调用绕过代理 同类内部 this.a() 调 this.b()，事务注解失效 拆成两个 Bean 跨调用，或注入自身代理（@Lazy/AopContext）
JDK 代理遇 final/无接口 Proxy.newProxyInstance 要求接口，final 方法不能被 CGLIB 增强 有接口用 JDK；无接口用 CGLIB；final 类/方法只能改设计
代理里抛原始异常 InvocationTargetException 直接抛给客户端，堆栈难看 e.getCause() 拆包后再抛真实业务异常
代理链顺序错乱 先缓存后事务 vs 先事务后缓存，结果完全不同 用 @Order 显式排序；关键链路写集成测试验证顺序

JVM 实战：CPU 飙高排查完整步骤

发表于 2026-09-14 更新于 2026-10-25 分类于 JVM 本文字数： 8k 阅读时长 ≈ 7 分钟

JVM · CPU 飙高排查

从 0 到定位根因：确认是不是 JVM 的锅 · top/jstack 定位线程 · 多次抓取对比 · async-profiler 火焰图 · 七类常见根因的判定与修复。代码带详细注释。

技术栈速查

类别 选型 用途
JDK 21 LTS 运行环境
定位 top / top -Hp 进程与线程级 CPU
线程栈 jstack / jcmd Thread.print 看线程在干什么
火焰图 async-profiler 3.x 精准定位热方法
辅助 GC 日志 / jstat 区分”真忙”与”假忙”

1. 概念说明：CPU 高的本质

CPU 飙高的两种类型，排查方向完全不同：

类型 特征 根因方向
真忙（业务/代码在烧 CPU） GC 正常，线程栈在业务代码里 死循环、正则回溯、序列化、大计算
假忙（GC 在烧 CPU） 堆快满、Full GC 频繁 内存泄漏、堆太小、对象分配过快

为什么第一步要分真假：假忙时去抓线程栈，看到的全是 GC 线程，业务线程在等待——方向错了浪费一小时。先看 GC 日志/jstat，再看线程栈。

排查铁律：现场优先——先抓线程栈和火焰图，再考虑重启；重启后热点线程消失，只能靠猜。

2. 步骤 0：先确认是不是 JVM 在烧 CPU

为什么用 jstat 先看：10 秒钟判断出”真忙/假忙”，避免在错误方向上抓半天线程栈。

3. 步骤 1：定位 CPU 高的线程（top + jstack）

定位示例（grep 输出长这样）：

为什么转十六进制：top -H 显示十进制线程号，jstack 用 nid=0x十六进制 标识线程——不转换就搜不到。

4. 步骤 2：多次抓取对比（区分死循环与正常切换）

判定规则：

两次栈对比 结论
同一线程、同一方法、栈几乎不变 死循环/自旋（一直卡在同一行）
同一线程、方法在变、但总是那几个 高频业务处理（真在干活，看是不是该这么重）
栈在等待（WAITING/BLOCKED） 不是它在烧 CPU，回去找别的线程

为什么必须抓两次：单次抓栈有偶然性——线程恰好在某个方法暂停。两次都停在同一个方法，才能确认它持续在烧 CPU。

5. 步骤 3：火焰图（终极手段，精准到方法）

线程栈只能看到”某个时刻”，火焰图能看到一段时间内所有方法消耗的 CPU 占比。

火焰图怎么读：

看什么 说明
最宽的平顶 烧 CPU 最多的方法，优先查它
一串窄条叠很高 深层调用链，可能有循环嵌套
大块 GC 相关 假忙，转内存排查
锁相关（park/contend） 锁竞争，看等待线程

为什么火焰图是终极手段：30 秒采集成千上万次栈，统计出每个方法真实的 CPU 占比——不用猜热点，图上最宽的平顶就是答案。

6. 七类常见根因（判定 + 修复）

6.1 死循环 / 空转（最常见）

判定：火焰图是又宽又平的 loopCheck 平顶；栈顶在 while 行。

6.2 正则回溯爆炸（文本处理高频）

判定：火焰图 java.util.regex 大平顶；GC 不高（纯 CPU）。

6.3 GC 频繁（假忙）

判定：jstat -gcutil 的 FGC/FGCT 快速上涨；火焰图 G1/GC 相关大块。

6.4 序列化 / 大数据对象

判定：火焰图序列化方法平顶；QPS 不高但 CPU 高。

6.5 锁竞争自旋

判定：火焰图 AQS/park 相关；jstack 大量 BLOCKED 线程。

6.6 无限递归 / 方法调用过深

6.7 日志刷屏（隐蔽的 CPU 杀手）

为什么日志也是 CPU 杀手：字符串拼接 + IO 写入 + 线程同步，每个请求多打几行，QPS 高时能吃掉整核 CPU，且线上还不容易察觉。

工具/命令 用途 什么时候用

9. 典型案例：一次上线后 CPU 100% 的正则回溯爆炸排查（top → jstack → 定位）

问题背景：会员服务发布 v2.3.0 后 20 分钟，单实例 CPU 从 35% 飙到 100%（1 核打满 4 核中的 1 核整），QPS 无变化，接口 P99 从 60ms 涨到 2.4s。

排查过程（铁律：先留现场，再定位，最后才谈重启）：

步骤 操作 观察

享元模式详解（Flyweight）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3k 阅读时长 ≈ 3 分钟

设计模式 · 享元模式

GoF 结构型模式。意图 · 结构 · 内部/外部状态 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

享元模式（Flyweight）通过共享大量细粒度对象来减少内存占用——把对象拆成”可共享的不变部分（内部状态）”和”不可共享的变化部分（外部状态）”。

2. 要解决的问题

问题 说明
对象数量巨大 百万个字符/棋子/图标，每个都 new 内存爆炸
大量对象只有小差异 重复内容多，可共享
内存压力 大流量场景 GC 频繁

核心思想：内部状态（不变，共享）+ 外部状态（变化，调用时传入）。

状态 说明 示例（字符对象）
内部状态 不可变、可共享 字符本身的字形
外部状态 随场景变化 字符的位置、颜色

3. 结构（角色）

4. 代码实现（文本编辑器字符）

5. 应用场景

场景 说明
字符串常量池 JVM 字符串驻留（"a" == "a"）
包装类缓存 Integer.valueOf 缓存 -128~127
线程池/连接池 复用对象（池化思想）
文字渲染 字符/图标/棋子
JDK String String 对象不可变共享

6. 优缺点

优点 缺点
大幅减少内存（共享） 需要区分内/外部状态（设计复杂）
对象复用减少 GC 外部状态管理增加调用复杂度
池化提高创建效率 状态拆分不当会引入并发问题（内部状态必须不可变）

关键约束：内部状态必须不可变——享元被共享，任何人不能改它；外部状态由调用方持有（不共享），否则并发下互相污染。

7. 与其他模式对比

模式 区别
单例 单例全局唯一；享元是一类对象的池化共享（多实例）
对象池 对象池复用”昂贵对象”；享元共享”小对象”
工厂 享元工厂负责缓存与创建

8. 常见误用与陷阱

坑 现象 解法
内部状态被改 享元被共享，某处 glyph.setFont() 改了共享实例 内部状态全 final + 无 setter，构造一次定型
外部状态误存 把位置/颜色存进享元字段，不同位置的对象互相覆盖 外部状态只通过方法参数传入，绝不入字段
缓存无限膨胀 key 设计太细（含时间戳），缓存不命中反成内存泄漏 评估 key 基数；基数大就别用享元，改用对象池或 LRU 限容
HashMap 非线程安全 并发 computeIfAbsent 在旧版 JDK 下偶发死循环/丢数据 用 ConcurrentHashMap（JDK 8+），别用 Collections.synchronizedMap 包 HashMap

1. 模式概述（意图）

**装饰器模式（Decorator）**动态地给对象添加职责——把功能拆成一个个”装饰层”，层层包裹，比继承更灵活。

2. 要解决的问题

问题 继承方案 装饰器方案
加功能 每种组合一个子类（爆炸） 组合叠加装饰层
动态加/减 编译期定死 运行时按需组合
多个功能叠加 子类数量 = 2^n 装饰类线性增长

经典例子：咖啡加牛奶、加糖、加奶泡——继承要 8 个类，装饰器只要 3 个装饰类任意组合。

3. 结构（角色）

4. 代码实现（咖啡加料）

核心：装饰器与组件实现同一接口，因此可以无限嵌套；每个装饰器只关注自己的增强。

5. 应用场景

场景 说明
JDK IO 流 new BufferedInputStream(new FileInputStream(f)) 层层包装
Spring @Transactional、@Cacheable 本质是装饰（代理）
日志增强 记录耗时、重试、限流的切面
权限校验 包装对象加权限检查
Java 集合 Collections.synchronizedList(list) 包装增强

6. 优缺点

优点 缺点
比继承灵活（运行时组合） 装饰器链层级多，排障难
避免子类爆炸 小对象多（每层一个对象）
符合开闭原则 要求组件与装饰器同一接口
职责单一（每层一件事） 调试堆栈变深

7. 与代理模式对比（高频考点）

维度 装饰器 代理
目的 增强功能 控制访问

生命周期 客户端管理 代理方管理
实例 IO 流 Spring AOP 代理

8. 常见误用与陷阱

坑 现象 解法
装饰顺序敏感 压缩(加密(数据)) vs 加密(压缩(数据)) 结果完全不同 文档/命名标明顺序约定；复杂顺序用 Builder 编排
类型识别失效 coffee instanceof Espresso 返回 false（被装饰器包住了） 别依赖具体类型判断；或提供 unwrap() 方法
装饰器吞掉方法 组件新增方法，装饰器忘记转发，调用丢失 装饰器只继承抽象基类，编译器强制实现所有抽象方法
无限嵌套调试难 8 层包装后抛异常，堆栈看不到真实对象 装饰器 toString() 打出链式结构；控制层数 ≤ 5

组合模式详解（Composite）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.3k 阅读时长 ≈ 3 分钟

设计模式 · 组合模式

GoF 结构型模式。意图 · 结构 · 透明与安全 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

组合模式（Composite）把对象组织成树形结构，让单个对象和组合对象拥有一致的接口——客户端无需区分”叶子”还是”树枝”，统一处理。

2. 要解决的问题

问题 说明
树形结构普遍 目录树、组织架构、菜单、DOM、文件系统
客户端要区分层级 叶子与容器处理逻辑不同，代码散落 if-else
遍历/操作不统一 求总大小、递归删除要写多套代码

典型场景：文件系统（文件/目录）、公司组织架构（员工/部门）、菜单系统、HTML DOM、JPanel.add(Component)。

3. 结构（角色）

两种风格：

风格 说明
透明式 接口含 add/remove（叶子也实现，抛异常）——客户端更统一
安全式 容器独有 add/remove——类型安全，客户端需判断

4. 代码实现（文件系统）

递归结构：getSize()/delete() 都是”如果有子节点就委托，没有就自己处理”——叶子与容器的统一协议。

5. 应用场景

场景 说明
文件系统 文件/目录统一操作
组织架构 员工/部门递归统计
UI 组件 Swing JPanel（容器也是 Component）
DOM 树 元素节点统一遍历
权限树 菜单/权限递归渲染

6. 优缺点

优点 缺点
统一叶子与容器，客户端简单 树结构可能很深（递归性能/栈溢出）
天然支持递归操作 透明式接口对叶子不友好（抛异常）
符合开闭（加叶子类型易） 结构破坏后难维护（如循环引用）
层次清晰 不适合层级关系不明显的场景

7. 与其他模式对比

模式 区别
装饰器 装饰器也是树结构，但只一个”装饰者+被装饰者”链
迭代器 常配合组合模式遍历树（迭代器遍历）
访问者 访问者可在组合树上执行操作，不改节点类

8. 常见误用与陷阱

坑 现象 解法
透明式叶子抛异常 FileNode.add() 抛 UnsupportedOperationException，运行时炸 用安全式（容器独有 add/remove）；或接口默认空实现
循环引用栈溢出 dir.add(dir) 或 A.add(B); B.add(A)，递归 getSize() 爆栈 add 时校验 child != this 且无祖先环；必要时维护 parent 指针
深层递归爆栈 万级节点递归 delete() 触发 StackOverflowError 改成显式栈 + 循环的迭代写法；或限制树深
缓存不一致 add/remove 后忘记更新缓存的 size，数据失真 不缓存，每次递归计算；或引入失效机制

4. 代码实现

场景 说明

适配器模式详解（Adapter）

设计模式 · 适配器模式

GoF 结构型模式。意图 · 结构 · 类适配器与对象适配器 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

适配器模式（Adapter）把一个类的接口转换成客户端期望的另一个接口——让不兼容的接口能一起工作，如同电源转换插头。

2. 要解决的问题

问题 说明
新旧系统对接 老系统的接口与新技术栈不匹配
第三方库适配 库的 API 与业务需要的形式不同
无法改源码 遗留代码/外部库不能直接改

典型场景：接入第三方支付（各家 API 不同 → 统一成自己的接口）、老系统 ESB 对接、Arrays.asList()（数组 → List 的适配）、日志门面 slf4j 适配 log4j/logback。

3. 结构（角色）

两种实现方式：

方式 原理 适用
对象适配器（推荐） 组合：Adapter 持有 Adaptee 通用，解耦
类适配器 继承：Adapter extends Adaptee 需覆写 Adaptee 行为时才用

4. 代码实现（对象适配器）

5. 应用场景

场景 说明
第三方 SDK 统一 支付/短信/OSS 各家 API 统一成自家接口
老系统对接 遗留 ESB/数据库适配新架构
JDK 实例 Arrays.asList()、InputStreamReader（字节流→字符流）
日志门面 slf4j → logback/log4j 适配器
数据格式转换 旧数据格式适配新模型

6. 优缺点

优点 缺点
让不兼容接口协同工作 过度使用导致”包装套包装”难排障
客户端解耦（只认目标接口） 适配层增加调用链
无需修改被适配者 需要理解双方接口差异
可插拔（换适配器即换实现） 适配逻辑要写好转换与异常

7. 与其他模式对比

模式 区别
装饰器 装饰器增强功能不改接口；适配器转换接口
代理 代理控制访问（同接口）；适配器转接口
门面 门面聚合多个接口为高层接口；适配器一对一转换

8. 常见误用与陷阱

坑 现象 解法
适配器吞异常 第三方抛 AlipayException，适配器 catch 后返回 null 或静默成功 转成统一业务异常（如 PaymentException）抛出，不吞

JVM 实战：从 jar 启动到参数优化与 OOM 排查

JVM · 实战落地

从 0 到生产：把一个 jar 完整跑起来 · JVM 每个参数为什么这么设、数值怎么定 · OOM dump 从导出到定位泄漏的完整步骤。代码带详细注释。

技术栈速查

类别 选型 用途
语言 Java 21（LTS） 运行环境
构建 Maven 3.9 / Spring Boot 4.1 产出可执行 jar
运行 java -jar / systemd 启动与守护
分析 MAT（Eclipse Memory Analyzer） OOM 堆分析
监控 jstat / jcmd / GC 日志 参数决策依据

1. 从一个 jar 开始

1.1 先拿到可执行 jar

为什么是”可执行 jar”：Spring Boot 的 repackage 会把依赖打进 jar 内的 BOOT-INF/lib，java -jar 直接能跑；普通 jar（只有自己编译的类）必须自己拼 classpath，不适合部署。

1.2 前台启动（先跑通）

为什么不直接这样上生产：前台运行 + 无内存上限 + 无 GC 日志 + OOM 不留现场——任何一个生产问题都无法事后分析。下面逐项补。

1.3 后台启动与停止

为什么用 SIGTERM 而不是 SIGKILL：SIGKILL（kill -9）直接杀死进程，正在写库的事务可能中断、缓存未刷盘；SIGTERM 让 Spring Boot 走优雅停机流程（见 Spring Boot 篇），生产停止一律先 SIGTERM。

1.4 用 systemd 守护（生产标准做法）

创建 /etc/systemd/system/app.service：

为什么用 systemd：进程崩溃自动拉起、开机自启、日志统一 journalctl、资源限制可配置——比裸 nohup 可靠得多。

2. JVM 参数为什么这么设（逐项讲透）

2.1 堆内存：-Xms / -Xmx

为什么 -Xms 必须等于 -Xmx：-Xms < -Xmx 时 JVM 会在使用中动态扩容、缩容堆，扩容是 STW 的（Full GC 才能扩容）——线上会出现”流量上来 → 堆不够 → 触发 Full GC 扩容 → 停顿变长 → 更慢”的恶性循环。相等后堆大小恒定，不会因扩容停顿。

数值怎么定（用数据，不拍脑袋）：

经验公式：-Xmx ≈ 物理内存 × 40%~50%（剩余给 OS 缓存、线程栈、堆外、Metaspace）。

2.2 元空间：-XX:MaxMetaspaceSize

为什么要设上限：Metaspace 存类元数据，默认无上限（只受物理内存限制）。一旦发生类加载器泄漏（热部署、反射生成类、动态代理），Metaspace 会一路涨到把内存吃光——设上限后 OOM 抛的是 Metaspace 错误并留下现场，不设上限则直接系统 OOM（系统被杀，什么都没留下）。

2.3 GC 日志：必须开

为什么必须开：GC 日志是事后分析唯一的”时间线证据”——Full GC 什么时候开始、多频繁、老年代怎么涨，全在日志里。filecount=5,filesize=20m 是滚动日志（最多 100MB），防磁盘爆。不开 GC 日志 = 出问题只能猜。

2.4 OOM 现场：必须开

为什么必须开：OOM 发生时自动把堆转储成 .hprof 文件。没有这个参数，进程一死现场就没了，内存泄漏只能靠猜。HeapDumpPath 要指向有足够磁盘空间的目录（dump 文件可能和堆一样大，2g 堆 ≈ 2g dump）。

2.5 容器环境：-XX:MaxRAMPercentage

为什么：JVM 默认按宿主机内存算默认堆（如宿主机 64G，JVM 默认堆 ≈ 1/4 = 16G），容器限额 2G 时会直接 OOM。MaxRAMPercentage=75 让 JVM 按容器 cgroup 限额的 75% 设堆——K8s/Docker 部署必须用百分比，不用写死的 -Xmx。

2.6 G1 相关：默认够用，个别才调

什么时候才调：绝大多数服务用默认 G1 就够。MaxGCPauseMillis 只是优化目标；ParallelGCThreads 在 2C 小容器里默认会按 2 算，一般无需手调。调参前必须有 GC 日志数据支撑，禁止”感觉慢就调”。

7. 典型案例：一次 K8s 频繁重启（OOMKilled 137）的参数纠错

问题背景：订单服务迁入 K8s（Pod limit 4G），发布后反复重启：Pod 状态 OOMKilled，退出码 137，平均存活 40 分钟。应用日志里却没有任何 OOM 异常——诡异点所在。

排查过程：

步骤 操作 观察
① kubectl describe pod 看事件 Last State: Terminated, Reason: OOMKilled, Exit Code: 137 → 是系统级杀进程，不是 JVM OOM
② 查启动命令 启动参数是老脚本带来的 -Xmx8g（物理机时代的配置）！容器 limit 只有 4G
③ 核实 JVM 实际堆 `jcmd 1 VM.flags
④ 观察 kubectl top pod 内存爬到 4G 即被杀：JVM 堆按 8G 规划，Metaspace+堆外+线程栈叠加越限
⑤ 修复：改百分比参数并压测复验 MaxRAMPercentage=75 → 实际堆 3G，Pod 稳定，峰值内存 3.4G / 4G

8. 常见误用与陷阱

坑 现象/后果 解法
容器里写死 -Xmx（沿用物理机配置） JVM 按宿主机/旧配置规划堆，Pod 被 OOMKilled 137 且无 dump 容器一律 MaxRAMPercentage=75，迁移必核参数
-Xms 与 -Xmx 不一致 运行期扩容 STW，高峰期停顿忽长忽短 生产 -Xms = -Xmx
堆设成机器/容器内存上限 Metaspace+堆外+线程栈把总内存顶爆，被 OOM Killer 杀 堆 ≤ 总内存 75%，其余留给堆外与栈
kill -9 停服务 正在处理的事务中断、注册中心摘流不及，用户请求报错 一律先 SIGTERM（systemd/K8s 默认），强杀只做兜底
Metaspace 未设上限 类泄漏静默吃光内存，系统被杀且无任何现场 -XX:MaxMetaspaceSize=512m 显式封顶
GC 日志未开 出问题无时间线，只能靠猜 -Xlog:gc*:file=... 滚动配置，启动即开
还配 -XX:+UseCMS 等 CMS 参数 JDK 14+ CMS 已移除，启动直接报错；误留 Parallel 参数与 G1 冲突 JDK 21 用默认 G1，参数从老环境迁移时逐个核对
不设时区 -Duser.timezone 容器 UTC，日志与定时任务时间差 8 小时，排障对时间线全乱 启动参数显式 Asia/Shanghai
