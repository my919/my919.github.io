空对象模式详解（Null Object）

发表于 2026-09-14 更新于 2026-10-29 分类于 设计模式 本文字数： 2.9k 阅读时长 ≈ 3 分钟

设计模式 · 空对象

扩展行为型模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与 Optional 对比。

1. 模式概述（意图）

空对象模式（Null Object）用一个”什么都不做”的空对象替代 null 返回——调用方无需判空，行为由空对象自己”安静地忽略”。

2. 要解决的问题

问题 说明
判空代码泛滥 if (x != null) 散落各处
空指针隐患 漏判即 NPE
空语义不明确 null 到底表示”不存在”还是”出错”

典型场景：日志的 Logger（无日志配置时用空 Logger）、缓存未命中返回空缓存、策略未配置用默认策略、集合为空返回空集合而非 null。

3. 结构（角色）

4. 代码实现（消息发送）

5. 应用场景

场景 说明
可选依赖 日志、监控、统计的可插拔实现
集合返回 返回空集合而非 null（JDK 已建议）
策略缺省 未配置的策略用”默认策略”
树形结构 空子节点对象
JDK Optional 现代替代方案之一

6. 优缺点

优点 缺点
消除判空代码（可读性） 空对象可能掩盖真实错误
杜绝 NPE 接口方法都要空实现（维护负担）
行为可预知（静默/默认值） 与”用 Optional 表达可能缺失”理念有重叠
客户端统一处理 不适用”缺失必须报错”的场景

7. 与 Optional 对比

维度 空对象 Optional
思路 提供”什么都不做”的替代对象 显式表达”可能有值”
判空 不需要 需要链式 orElse
适用 行为型接口（日志/策略） 返回值可能缺失
组合 可多态替换 函数式链式

实践：返回”可执行行为”用空对象；返回”数据”用 Optional/空集合。

8. 常见误用与陷阱

坑 现象 解法
空对象里塞副作用 NullService 里写库、计数、打日志，”空”对象不空 空对象必须零行为、零副作用，日志都不该打
与 Optional 滥用 字段声明 Optional<User>、把 Optional 当方法参数或集合元素 Optional 只作返回值；字段/参数缺省用空对象或显式默认值
null 对象状态被修改 单例 NullNode 被调用方 set 值，污染后续所有请求 空对象不可变（字段 final、无 setter），或每次返回新实例
掩盖真实错误 配置缺失本应启动失败，却静默 no-op，线上一路绿灯 仅「缺失=合法默认」才用；异常缺失要 fail-fast
返回数据也套空对象 NullUser 给 id=0、name=null，下游静默产生脏数据 行为型接口用空对象；数据缺失用 Optional/空集合/抛异常

访问者模式详解（Visitor）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 4k 阅读时长 ≈ 4 分钟

设计模式 · 访问者模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 双分派。代码带详细注释。

1. 模式概述（意图）

访问者模式（Visitor）把数据结构与数据上的操作分离：在不修改元素类的前提下，为元素类增加新的操作（访问者）。

2. 要解决的问题

问题 说明
元素类频繁加操作 每个元素加”导出/统计/序列化”方法 → 类爆炸
操作变化快 操作经常变，元素结构稳定
结构固定 对象结构（元素类型）稳定，操作易变

典型场景：编译器（AST 节点 × 各种操作）、文档导出（不同节点×不同导出格式）、报表统计、对象结构稳定但操作繁多的系统。

适用前提：元素类型稳定（很少新增元素），操作经常变——反之（元素常加）则不要用访问者。

3. 结构（角色）

双分派：element.accept(v) 先按元素类型分派，visitor.visit(element) 再按访问者类型分派——两次动态绑定，才能”元素类型 × 操作”自由组合。

4. 代码实现（报表导出）

核心收益：加”新操作”= 加一个 Visitor 类；元素类（SaleRecord/RefundRecord）一行不改。

5. 应用场景

场景 说明
编译器 AST 节点 × 解析/检查/生成
报表导出 多类型节点 × 多格式导出
对象结构稳定 数据结构固定、操作易变
统计/审计 对对象结构做多种统计

6. 优缺点

优点 缺点
操作与结构分离（开闭） 违反依赖倒置（元素依赖访问者接口）
加操作易（加访问者） 加元素类型难（所有访问者都要改）
相关操作内聚在一个类 破坏封装（访问者需访问元素内部）
双分派机制强大 复杂度高，简单场景不值

7. 与其他模式对比

模式 区别
迭代器 迭代器遍历；访问者遍历中对每个节点执行操作
组合模式 常配合：组合树 + 访问者遍历操作
策略 策略换算法（单对象）；访问者作用于对象结构

8. 常见误用与陷阱

坑 现象 解法
元素类型频繁新增 每加一个新节点类，所有 Visitor 都要改 元素稳定才用访问者，元素易变用策略模式
破坏元素封装 Visitor 需要访问元素私有字段，过度暴露 元素提供只读视图（DTO）或包级可见，禁止直接 getter
双分派性能损耗 大量元素频繁访问，动态绑定带来 GC 压力 对小数据量场景直接用 switch 类型判断
访问者依赖循环 Visitor 回调 Context 又触发新访问，形成死循环 访问时传入栈深度计数器，超过阈值中断并报警

模板方法模式详解（Template Method）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3k 阅读时长 ≈ 3 分钟

设计模式 · 模板方法

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与策略对比。代码带详细注释。

1. 模式概述（意图）

模板方法模式（Template Method）把算法的骨架定义在父类，把可变的步骤延迟到子类实现——父类控制流程，子类填充细节。

2. 要解决的问题

问题 说明
流程相同、细节不同 支付流程一样，各家签名/调用不同
流程被复制粘贴 每个子类都写一遍骨架（改流程要改多处）
骨架需要强制一致 子类可能打乱步骤顺序

典型场景：Spring 的 JdbcTemplate/RestTemplate、Servlet（doGet/doPost 由框架调）、流程引擎、游戏关卡、测试框架（JUnit 的生命周期）。

3. 结构（角色）

钩子方法（Hook）：父类提供默认实现、子类可选覆写的扩展点（如”是否需要做某步”）。

4. 代码实现（数据导出）

流程控制点：取数 → 格式化 → 写文件 的顺序由父类锁定，子类只换”格式化”这一步。

5. 应用场景

场景 说明
框架回调 Servlet、Spring 模板类
支付/对接 流程相同、签名/报文不同
批量任务 拉数→处理→落库→通知
测试框架 JUnit 生命周期（@Before/@Test/@After）
工作流 固定流程+可变步骤

6. 优缺点

优点 缺点
复用骨架，消除重复 父类与子类耦合（继承）
流程统一（final 防乱序） 骨架改动影响所有子类
扩展靠子类（开闭） 抽象步骤多时子类实现负担
钩子提供灵活扩展点 无法运行时换实现（继承静态）

7. 与策略对比（高频考点）

维度 模板方法 策略
关系 继承（子类填充） 组合（注入策略）
变的部分 步骤实现 整个算法
切换 编译期固定 运行时切换
适用 骨架固定 算法整体可换

实践建议：优先组合优于继承——如果只是”某一步可变”，用回调/函数式接口（如 JdbcTemplate 的 RowMapper）常比继承更灵活。

8. 常见误用与陷阱

坑 现象 解法
模板方法被覆写 子类覆写了模板方法，流程被打乱 模板方法必须加 final 修饰
抽象步骤过多 父类 10 个抽象方法，子类实现负担重 抽象步骤 ≤ 5 个，多的拆为接口或回调
钩子方法滥用 大量空实现的钩子，子类不知道要覆写 钩子方法 ≤ 2 个，且命名带 default 前缀提示
继承层级过深 模板方法嵌套 3 层以上，调试困难 改用组合+回调替代多层继承

1. 模式概述（意图）

策略模式（Strategy）定义一族可互换的算法，把它们各自封装成类，客户端可以运行时替换——把 if-else 分支变成”选择策略”。

问题 说明
if-else/switch 分支爆炸 每种算法一个分支，加算法改代码
算法与业务耦合 算法写在业务方法里
算法需要运行时切换 按配置/条件动态选算法

典型场景：价格计算（会员等级折扣）、支付方式（支付宝/微信/银联）、排序算法选择、压缩格式、登录方式（密码/短信/扫码）。

4. 代码实现（价格计算）

5. 应用场景

场景 说明

支付渠道 多种支付方式
加密/压缩/排序 算法可替换
登录方式 密码/短信/第三方
校验规则 不同业务不同校验策略

6. 优缺点

优点 缺点
消除分支（开闭原则） 策略类数量多
算法独立可测（每个策略单测） 客户端需要知道有哪些策略

坑 现象 解法
注册表返回 null registry.get("vip") 返回 null，下游 NPE 未命中抛异常或返回默认策略（Fail-fast）
策略里有共享状态 多线程下策略被复用，状态串扰 策略保持无状态；需要状态放 Context 或参数传
分支才 2-3 个就用策略 过度设计，类爆炸 分支少且稳定时直接 if-else 更直观
策略之间互相调用 策略 A 调策略 B，耦合回来了 策略必须相互独立，公共逻辑提到抽象层

新状态扩展难 加状态 = 改所有方法

播放器/电梯 状态驱动行为

观察者模式详解（Observer）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.4k 阅读时长 ≈ 3 分钟

设计模式 · 观察者模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与发布订阅对比。代码带详细注释。

1. 模式概述（意图）

观察者模式（Observer）定义对象间一对多依赖：当被观察者（Subject）状态变化时，自动通知所有观察者——发布-订阅思想的基础。

2. 要解决的问题

问题 说明
状态变化要通知多方 订单状态变了要通知库存/物流/用户
通知方与被通知方耦合 硬编码调用导致改一个动一片
观察者动态增删 运行时注册/注销订阅

典型场景：事件监听（GUI 按钮点击）、Spring 事件、消息队列（分布式观察者）、实时推送、MVC（Model 变化刷新 View）。

3. 结构（角色）

4. 代码实现（订单事件通知）

5. 应用场景

场景 说明
Spring 事件 @EventListener（发布-订阅内建）
GUI 事件 按钮点击、键盘事件
消息队列 Kafka/RabbitMQ（分布式观察者）
实时推送 WebSocket 订阅推送
MVC Model 变化刷新 View

6. 优缺点

优点 缺点
主题与观察者解耦（开闭） 通知顺序无保证
动态注册/注销 观察者过多时通知开销
一对多广播 观察者异常会冒泡（需隔离）
支持分布式（MQ 版） 循环依赖可能无限通知

工程注意：同步通知中一个观察者抛异常会中断后续——生产用异步 + 异常隔离（Spring 配 @Async 或事件表）。

7. 与发布-订阅对比

维度 观察者 发布-订阅
通信 主题直接调观察者 经消息队列中间件
解耦 主题认识观察者 完全解耦（互不认识）
场景 单机 JVM 内 分布式系统
实例 Spring 事件 Kafka/RabbitMQ

8. 常见误用与陷阱

坑 现象 解法
观察者异常中断链 一个观察者抛异常，后续观察者收不到通知 每个观察者的调用包 try-catch，或改用异步事件
内存泄漏 观察者注册后忘记 remove，Subject 一直持有引用 用弱引用（WeakReference）或注册时返回 Subscription 句柄
循环通知死锁 A 观察 B，B 观察 A，状态变化导致无限循环 引入版本号/时间戳防重入，或改单向数据流
通知顺序不可控 依赖 List 顺序，观察者优先级无法调整 用 PriorityQueue 或注解标顺序（如 Spring @Order）

1. 概念说明：先想清楚要什么

备份的核心是两个指标：

指标 含义 目标
RPO（恢复点目标） 最多丢多少数据 越小越好（如丢 ≤5 分钟）
RTO（恢复时间目标） 多久恢复可用 越小越好（如 1 小时内）

备份类型：

类型 说明 特点
全量备份 备份全部数据 基础，恢复最简单
增量备份 备份上次备份后的变化 省空间、恢复要叠加
逻辑备份 导出 SQL（mysqldump） 可读、跨版本、恢复慢
物理备份 复制数据文件（XtraBackup） 快、恢复快、依赖同版本

4. binlog 时间点恢复（PITR，RPO 趋近 0）

4.1 前提：binlog 必须开启

为什么 binlog 是恢复的最后一环：全量备份只能恢复到”备份时刻”，备份之后到故障前的数据变化全在 binlog 里——binlog 追到故障前一刻，数据丢得最少。

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

备忘录模式（Memento）在不破坏封装的前提下，捕获并保存对象的内部状态，以便将来恢复到该状态——如同游戏的存档。

2. 要解决的问题

问题 说明
需要撤销/回滚 恢复到某个历史状态
状态封装性 外部直接读字段会破坏封装
状态保存多份 历史快照要管理（存档列表）

典型场景：编辑器撤销（配合命令模式）、游戏存档、事务回滚（数据库 undo 日志思想）、浏览器后退。

3. 结构（角色）

关键：备忘录对外不透明——只有 Originator 能读写其内部，Caretaker 只负责保存与归还。

4. 代码实现（游戏角色存档）

5. 应用场景

场景 说明
编辑器撤销 文档快照（常配合命令模式）
游戏存档 角色状态恢复
数据库事务 undo 日志/回滚段（思想）
表单重置 恢复初始数据
配置回滚 配置快照恢复

6. 优缺点

优点 缺点
保存状态且不破坏封装 状态大时快照耗内存
恢复逻辑简单 频繁保存性能开销
状态历史可管理 需注意快照的深拷贝（引用类型）
与命令模式配合强大 备忘录内容变化后难迁移

注意：备忘录保存的是对象状态——内部引用类型要深拷贝，否则存的是引用，状态早就变了。

7. 与其他模式对比

模式 区别
命令模式 命令记录”操作”；备忘录记录”状态快照”（常配合）
原型模式 原型复制当前对象；备忘录保存并恢复历史
观察者 观察者关注变化；备忘录保存过去

8. 常见误用与陷阱

坑 现象 解法
浅拷贝导致状态污染 Memento 存的是 List/Map 引用，改原对象后快照失效 Memento 内对引用类型做深拷贝，或存不可变副本
快照内存爆炸 大对象全量快照频繁保存，OOM 只存变更字段（增量快照），或限制快照数量
恢复时对象状态不一致 Originator 有新字段但 restore 没恢复 用序列化/反序列化保证全字段一致，或加版本号校验
备忘录泄露内部结构 Memento 暴露 getter，外部篡改历史状态 Memento 设为内部类+私有构造，只给 Originator 访问

设计模式 · 中介者模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与外观对比。代码带详细注释。

1. 模式概述（意图）

中介者模式（Mediator）用一个中介对象封装一组对象的交互——对象之间不再直接引用，全部通过中介通信，把”多对多”改成”多对一”。

2. 要解决的问题

问题 说明
对象间耦合网状 每个对象都要知道所有其他对象（多对多）
交互逻辑散落 谁通知谁、怎么协调散在各对象里
难以复用与测试 对象强耦合，无法单独测试

错误结构（网状）：

中介者结构（星形）：A/B/C/D → Mediator（n 条依赖）。

典型场景：聊天室（用户之间不直接通信，经服务器）、航班调度塔台、MVC 里的 Controller（协调 Model 与 View）、消息队列。

3. 结构（角色）

4. 代码实现（聊天室）

新增用户：只需要注册到聊天室——原有用户代码零修改。

5. 应用场景

场景 说明
聊天/协作系统 用户经服务器通信
表单组件协调 多个控件联动（互不引用）
航班/交通调度 塔台协调飞机
消息队列 生产者消费者经 MQ 解耦
MVC Controller 协调 Model 与 View

6. 优缺点

优点 缺点
网状耦合 → 星形（n² → n） 中介者可能膨胀成”上帝对象”
交互逻辑集中，易维护 中介者单点故障（挂了全断）
同事类独立可复用 交互逻辑复杂时中介者难理解
符合开闭（加同事不改老代码） 比直接调用多一层

7. 与外观对比（高频考点）

维度 中介者 外观
方向 同事互相交互（双向） 子系统被外观单向封装
协议 同级的同事间协调 上下层简化入口
关注 交互逻辑 接口简化

8. 常见误用与陷阱

坑 现象 解法
中介者膨胀成上帝类 Mediator 内几百行 if-else，改一处动全身 按职责拆为多个中介者（Room/Channel/Topic）
同事类反向穿透 Colleague 直接 get 出其他同事引用调用 强制 Colleague 只持 Mediator 引用，不暴露同事列表
消息广播风暴 中介者广播所有消息，无关同事被迫处理 引入消息标签/主题过滤，只发给关心的订阅者
异步回调地狱 Mediator 内链式调用导致死锁或内存泄漏 用事件队列异步解耦，Mediator 只投递不回调

设计模式 · 迭代器模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

迭代器模式（Iterator）提供一种方法顺序访问聚合对象（集合）内的元素，而不暴露其内部表示——遍历逻辑与集合结构解耦。

2. 要解决的问题

问题 说明
遍历与集合耦合 每种集合写一套遍历代码
内部结构暴露 客户端知道底层是数组还是链表
遍历方式单一 正序/逆序/过滤需要不同遍历器

典型场景：所有 Java 集合的 iterator()、Java 8 之后基本被 for-each/Stream 取代——迭代器已是语言级内建，本模式主要理解思想与 Iterable 接口。

3. 结构（角色）

4. 代码实现（自定义迭代器）

遍历期间修改：迭代器遍历时修改集合会抛 ConcurrentModificationException（Java 用 modCount 快照检测）；需要安全的移除用 iterator.remove()。

5. 应用场景

场景 说明
Java 集合 List/Set/Map 的 iterator()
for-each 语法 编译器展开为迭代器
数据库游标 结果集逐行遍历
自定义数据结构 树/图的自定义遍历
Stream Java 8+ 更声明式的遍历

6. 优缺点

优点 缺点
遍历与集合解耦 简单集合用迭代器是多余抽象
隐藏内部结构（信息隐藏） 迭代器状态管理要小心
支持多种遍历方式 函数式语言中常被 Stream/for-each 取代
统一接口（换集合不改客户端） 并发修改检测增加复杂度

7. 与其他模式对比

模式 区别
组合模式 组合定义树结构；迭代器遍历它
访问者 迭代器遍历+访问者操作节点
工厂方法 createIterator() 就是工厂方法

8. 常见误用与陷阱

坑 现象 解法
遍历时直接改集合 for-each 中调用 list.remove()，抛 ConcurrentModificationException 用 iterator.remove() 或 Java 8 removeIf()
迭代器不复用 每次遍历 new 迭代器，大数据量时 GC 压力大 内部迭代器（forEach/Stream）替代外部迭代器
迭代器状态泄露 迭代器持有游标，跨线程共享导致遍历错乱 迭代器设为方法局部变量，禁止共享
嵌套遍历死循环 外层迭代器遍历时内层再 createIterator()，逻辑混乱 改用 Stream 的 flatMap 或收集到 List 再遍历
