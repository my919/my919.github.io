拦截过滤器模式详解（Intercepting Filter）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.9k 阅读时长 ≈ 4 分钟

设计模式 · 拦截过滤器

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与责任链对比。

1. 模式概述（意图）

拦截过滤器（Intercepting Filter）在请求到达目标处理前插入一组可插拔的过滤器，按链式顺序执行公共处理——每个过滤器只做一件事，可增可减。

2. 要解决的问题

问题 说明
公共处理杂乱 鉴权、日志、压缩、编码写在一起
处理不可插拔 加一个处理要改目标代码
顺序难控制 过滤器顺序影响行为（先鉴权再日志？）

典型场景：Servlet Filter（登录、编码、压缩、XSS）、Spring Security 的 FilterChain、网关过滤器、中间件洋葱模型。

3. 结构（角色）

4. 代码实现（登录请求过滤链）

5. 应用场景

场景 说明
Servlet Filter 编码、登录、压缩、XSS 过滤
Spring Security 认证/授权过滤器链
API 网关 限流、鉴权、灰度过滤器
Web 框架中间件 Express/Koa/ASP.NET 管道
日志/审计 统一日志过滤器

6. 优缺点

优点 缺点
过滤器可插拔（增删不动业务） 过滤链长时性能开销
职责单一（每过滤器一件事） 顺序配置错误影响全局
公共逻辑集中且复用 过滤器间状态传递要约定
顺序可控 调试多层过滤较麻烦

7. 与责任链对比

维度 拦截过滤器 责任链
传递 通常全部执行（洋葱） 可中途停止（能处理则处理）
用途 横切公共处理 职责分担/审批
结构 统一 FilterChain 管理 处理者持有 next

8. 常见误用与陷阱

坑 现象 解法
filter 顺序依赖隐式 Auth 依赖前一个过滤器塞的请求属性，注册顺序一变就 401 顺序显式配置（@Order / FilterRegistrationBean / 链组装处），依赖写注释
过滤器里改请求体 读取 getReader() 后 body 被消费，下游拿到空请求体 用 ContentCachingRequestWrapper 等包装类缓存并重放
异常被吞 catch 后既不 chain.doFilter 也不写响应，请求无声挂起 终止链必须显式返回 4xx/5xx；异常交给统一错误处理器
正常分支漏放行 拒绝路径写了 return，通过路径忘记调 chain.doFilter 每个过滤器结构对称：放行显式 chain，拒绝显式响应
过滤器持有可变状态 用成员变量存请求数据，并发请求互相串值 过滤器无状态单例，请求级数据存 request 属性

前端控制器模式详解（Front Controller）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.6k 阅读时长 ≈ 3 分钟

设计模式 · 前端控制器

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与网关对比。

1. 模式概述（意图）

前端控制器（Front Controller）用唯一入口处理所有请求，在入口处统一完成公共处理（鉴权、日志、路由、国际化），再分派到具体处理器。

2. 要解决的问题

问题 说明
公共逻辑重复 每个 Servlet/Controller 都要写鉴权、日志
处理逻辑分散 路由、异常处理散落各处
安全风险 未鉴权的请求直达业务

典型场景：Spring MVC 的 DispatcherServlet、所有 Web 框架的”中央分发器”、API 网关（微服务版的 Front Controller）。

3. 结构（角色）

4. 代码实现（统一入口 + 鉴权 + 路由）

5. 应用场景

场景 说明
Web 框架 Spring MVC DispatcherServlet、Struts
API 网关 微服务统一入口（鉴权/限流/路由）
门户系统 多模块统一入口
应用服务器 Servlet 容器（Filter + Dispatcher）

6. 优缺点

优点 缺点
公共逻辑集中（一处鉴权/日志） 入口成为瓶颈/单点
路由集中管理 简单应用是过度设计
统一异常/响应 入口逻辑膨胀风险
业务处理器轻量 需要与拦截器配合避免重复

7. 与相关模式对比

模式 区别
拦截过滤器 过滤器在请求到达控制器前链式处理；前端控制器是分发入口
外观 外观封装子系统调用；前端控制器是 Web 请求分发
网关 微服务版前端控制器（跨服务路由）

实践：Spring MVC 里 Front Controller 已内建（DispatcherServlet）；自己开发时把”公共逻辑”放拦截器（Interceptor）而非控制器内。

8. 常见误用与陷阱

坑 现象 解法
控制器变上帝类 鉴权、参数解析、业务处理、渲染全堆进 dispatch 一个方法 只保留「统一公共处理 + 分发」；业务下沉 Handler，横切下沉过滤器/拦截器
与 MVC 中 Controller 混淆 在前端控制器里写订单/用户业务，越写越大 前端控制器全局唯一（入口/路由）；MVC Controller 是按 URL 映射的一组处理器
分发硬编码 if-else 巨链 几十上百个 action 分支挤在 resolve 里 路由表 Map 或注解扫描注册（Spring 的 @RequestMapping）
与过滤器职责重复 入口鉴权一遍，Filter/Interceptor 又鉴权一遍 鉴权、编码放过滤器链；控制器只做路由与统一异常兜底
单点被异常拖垮 某个处理器抛出未捕获异常，整个入口挂掉 入口无状态、可多实例部署；异常在边界统一捕获转错误响应

数据传输对象模式详解（DTO）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 2.7k 阅读时长 ≈ 2 分钟

设计模式 · 数据传输对象（DTO）

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与 VO/PO 对比。

1. 模式概述（意图）

DTO（Data Transfer Object）是跨层传输数据的载体对象——把多个字段打包成一次传输，避免逐字段多次调用、也避免把内部实体直接暴露给外部。

2. 要解决的问题

问题 说明
网络往返过多 一次要多个数据 → 逐次调用
内部结构暴露 实体含敏感字段/内部结构，直接返回有风险
层间耦合 Controller 直接用 Entity，改表结构影响 API
传输粒度不匹配 前端要 A+B+C 拼装，接口要定制

典型场景：REST API 请求/响应对象、远程调用（RPC 参数）、分页结果封装、批量数据聚合。

3. 结构（角色）

4. 代码实现（用户 API）

转换工具：字段多时用 MapStruct（编译期生成，性能好）：

5. 应用场景

场景 说明
REST API 请求/响应对象
RPC/微服务 服务间传输参数
分页聚合 PageResult 封装
多源数据组装 组装多个来源为一个 DTO
大对象拆分 一次传输所需字段

6. 优缺点

优点 缺点
隔离内部模型（安全） DTO 与实体字段重复（样板代码）
减少网络往返 转换代码要维护
按需裁剪（不多传/不少传） 过细 DTO 导致类爆炸
层间解耦 需要字段映射约定

7. 与相关概念对比

概念 说明
DTO 跨层/跨网络传输（入参/出参）
VO（View Object） 专为视图层定制的 DTO
PO/Entity 持久化模型（对应表）
BO 业务模型（领域）
DO 领域对象

分层铁律：Entity/PO 只在内层；跨网络/跨层一律 DTO/VO——避免”接口直接暴露表结构”。

8. 常见误用与陷阱

坑 现象 解法
DTO 与实体混用 请求体直接绑定 Entity（@RequestBody UserEntity），改张表就破坏 API 入参/出参用独立 record，边界处显式转换
敏感字段未脱敏就暴露 passwordHash、salt、内部状态被 Jackson 原样序列化出去 响应 DTO 走字段白名单；敏感字段根本不放进出参 DTO
过度映射层级 DO→BO→DTO→VO 层层 BeanUtils.copy，样板代码淹没业务 每层都要有明确收益；简单链路允许 DO→DTO 直转
万能 DTO 走所有接口 一个类几十个字段，靠注释区分哪个接口填哪些 按场景定制（CreateUserRequest / UserListResponse）
DTO 里塞业务行为 在传输对象中下单、算价、调 Service DTO 保持贫血数据载体，行为归领域/应用服务

数据访问对象模式详解（DAO）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3k 阅读时长 ≈ 3 分钟

设计模式 · 数据访问对象（DAO）

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与 Repository 对比。

1. 模式概述（意图）

DAO（Data Access Object）把数据访问逻辑从业务逻辑中分离：业务层只面向 DAO 接口，不关心数据来自数据库、Redis 还是外部 API。

2. 要解决的问题

问题 说明
业务代码混 SQL Service 里写 SQL，改库伤筋动骨
数据源可切换 换数据库/缓存要改业务
访问逻辑重复 连接管理、异常处理、事务散落
测试困难 业务测试要连真实数据库

典型场景：所有 ORM 框架（MyBatis Mapper、JPA Repository）本质是 DAO 思想的实现；多数据源切换；缓存与 DB 的双读双写封装。

3. 结构（角色）

4. 代码实现（用户数据访问）

5. 应用场景

场景 说明
所有 ORM 项目 MyBatis Mapper / JPA Repository
多数据源 同接口多实现（MySQL/PG/缓存）
遗留系统 把老存储封装成统一 DAO
单元测试 Mock DAO 即可测业务

6. 优缺点

优点 缺点
业务与数据访问解耦 简单 CRUD 也建接口+实现（略重）
数据源可替换 接口方法粒度设计要慎重
便于测试（mock） 过度抽象可能”为接口而接口”
访问逻辑集中管理 复杂查询容易让 DAO 膨胀

7. 与 Repository 对比（DDD 语境高频）

维度 DAO Repository
视角 数据访问（面向表） 领域聚合（面向业务）
返回 Entity/数据传输对象 领域聚合对象
接口 CRUD 细粒度 业务语义方法（save(Order)）
场景 简单分层 DDD 战术设计

实践：CRUD 系统用 DAO/Mapper 即可；DDD 系统用 Repository（内部可用 DAO 实现）。

8. 常见误用与陷阱

坑 现象 解法
DAO 泄露连接 异常路径上 Connection 没关闭，连接池很快被耗尽 try-with-resources 或交给 MyBatis-Spring 托管，禁止把连接带出 DAO
N+1 查询 列表 N 条记录，循环里逐条调 DAO，触发 N+1 次 SQL 批量 in 查询 / join / fetch join，一次取回再组装
接口泄漏存储细节 DAO 方法签名出现 ResultSet、RowMapper、findByHql 接口里只出现领域类型，存储细节全部关在实现类
SQL 拼接注入 "where name='" + name + "'" 被 ' or '1'='1 打穿 参数化查询 / #{} 占位符 / PreparedStatement
DAO 里写业务逻辑 在 DAO 中算折扣、改状态机、发消息 DAO 只做存取，业务判断归 Service

数据库 · SQL 优化与慢查询治理

从 0 到可落地的性能治理。慢查询发现 · EXPLAIN 深度解读 · 索引设计实战 · 常见慢 SQL 改写 · 大表治理 · 治理流程与案例。SQL 带详细注释。

技术栈速查

类别 选型 用途
数据库 MySQL 8.4 LTS 主存储
慢查询 慢日志 + mysqldumpslow 发现问题
分析 EXPLAIN / optimizer trace 定位根因
索引 联合索引/覆盖索引 提速手段

1. 概念说明：SQL 为什么慢

慢 SQL 的本质：扫描了太多行。优化 = 让数据库少干活。

三类典型慢：

类型 特征 主因
全表扫描 type=ALL 没走索引
回表过多 走索引但大量回表 覆盖索引不足
锁/事务等待 耗时在等待 大事务/锁竞争

2. 第一步：发现慢 SQL

2.1 开启慢查询日志

为什么必须开 log_queries_not_using_indexes：全表扫描是慢 SQL 的最大来源，但很多”刚好不到 1 秒”的查询每天跑几万次——没走索引就要记录，否则漏掉最大隐患。

2.2 分析慢日志

治理优先级：出现次数 × 单次耗时 最大的先治（高频慢 > 偶发超慢）。

3. 第二步：EXPLAIN 深度解读

每个字段怎么看（生产实战口径）：

字段 看什么 健康标准
type 访问方式 ref/range 优；ALL（全表）必须治
key 实际用的索引 为 NULL = 没走索引
rows 预估扫描行数 越小越好（万级可接受，百万级要治）
Extra 附加信息 见下表重点

Extra 里的红灯：

Extra 值 含义 对策
Using filesort 文件排序（没走索引排序） 排序字段加进联合索引
Using temporary 临时表（GROUP BY/DISTINCT） 优化分组字段索引
Using index 覆盖索引（不用回表） ✅ 理想状态
Using where 过滤在存储引擎层之后 补索引
Using index condition 索引下推（ICP） ✅ 正常

4. 第三步：索引设计实战

4.1 联合索引（最左前缀原则）

9. 典型案例：积分流水表深分页治理

问题背景：积分流水表 8000 万行，用户端”我的积分”翻到第 5 万页时 RT 飙到 4s，高峰期连接池被拖满。

方案（EXPLAIN → 覆盖索引 → 延迟关联 → 验证）：

踩坑点：业务侧最终改为游标分页（WHERE user_id=? AND id < 上次末尾id LIMIT 20），延迟关联只作兜底——游标分页把”翻页”变成”续读”，任意深度都是恒定 20 行代价；新索引顺手覆盖了”查某用户最新 20 条流水”的高频场景，一索两用。

10. 常见误用与陷阱

坑 现象/后果 解法
最左前缀误解为”包含最左列即可” (a,b) 索引下 WHERE b=1 直接不走路由 等值条件按最左顺序组织联合索引
函数包裹列，建了索引也失效 WHERE DATE(t)='2026-09-14' type=ALL 改范围写法，或 8.0+ 建函数索引
隐式类型转换 varchar 列 WHERE order_no=202609 全表扫 条件值与列类型严格一致
深度分页直接 OFFSET 扫描并丢弃前 N 行，P99 随页深恶化 游标分页 / 延迟关联
SELECT * 让覆盖索引白建 Extra 无 Using index，回表翻倍 按需取列，大字段拆附属表
冗余索引不清理 idx_status 与 idx_status_created 并存，写放大 定期查 sys.schema_redundant_indexes
大事务被误判为索引问题 事务内含 RPC 耗时 3s，SQL 本身仅 10ms 区分执行耗时与锁等待，查 data_lock_waits
只治单次最慢的 SQL 高频 0.8s 的 SQL 总损耗远超周频 30s 按”次数 × 耗时”排治理优先级

设计模式 · 空对象

扩展行为型模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与 Optional 对比。

1. 模式概述（意图）

空对象模式（Null Object）用一个”什么都不做”的空对象替代 null 返回——调用方无需判空，行为由空对象自己”安静地忽略”。

2. 要解决的问题

问题 说明
判空代码泛滥 if (x != null) 散落各处
空指针隐患 漏判即 NPE
空语义不明确 null 到底表示”不存在”还是”出错”

典型场景：日志的 Logger（无日志配置时用空 Logger）、缓存未命中返回空缓存、策略未配置用默认策略、集合为空返回空集合而非 null。

3. 结构（角色）

4. 代码实现（消息发送）

5. 应用场景

场景 说明
可选依赖 日志、监控、统计的可插拔实现
集合返回 返回空集合而非 null（JDK 已建议）
策略缺省 未配置的策略用”默认策略”
树形结构 空子节点对象
JDK Optional 现代替代方案之一

6. 优缺点

优点 缺点
消除判空代码（可读性） 空对象可能掩盖真实错误
杜绝 NPE 接口方法都要空实现（维护负担）
行为可预知（静默/默认值） 与”用 Optional 表达可能缺失”理念有重叠
客户端统一处理 不适用”缺失必须报错”的场景

7. 与 Optional 对比

维度 空对象 Optional
思路 提供”什么都不做”的替代对象 显式表达”可能有值”
判空 不需要 需要链式 orElse
适用 行为型接口（日志/策略） 返回值可能缺失
组合 可多态替换 函数式链式

实践：返回”可执行行为”用空对象；返回”数据”用 Optional/空集合。

8. 常见误用与陷阱

坑 现象 解法
空对象里塞副作用 NullService 里写库、计数、打日志，”空”对象不空 空对象必须零行为、零副作用，日志都不该打
与 Optional 滥用 字段声明 Optional<User>、把 Optional 当方法参数或集合元素 Optional 只作返回值；字段/参数缺省用空对象或显式默认值
null 对象状态被修改 单例 NullNode 被调用方 set 值，污染后续所有请求 空对象不可变（字段 final、无 setter），或每次返回新实例
掩盖真实错误 配置缺失本应启动失败，却静默 no-op，线上一路绿灯 仅「缺失=合法默认」才用；异常缺失要 fail-fast
返回数据也套空对象 NullUser 给 id=0、name=null，下游静默产生脏数据 行为型接口用空对象；数据缺失用 Optional/空集合/抛异常

访问者模式详解（Visitor）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 4k 阅读时长 ≈ 4 分钟

设计模式 · 访问者模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 双分派。代码带详细注释。

1. 模式概述（意图）

访问者模式（Visitor）把数据结构与数据上的操作分离：在不修改元素类的前提下，为元素类增加新的操作（访问者）。

2. 要解决的问题

问题 说明
元素类频繁加操作 每个元素加”导出/统计/序列化”方法 → 类爆炸
操作变化快 操作经常变，元素结构稳定
结构固定 对象结构（元素类型）稳定，操作易变

典型场景：编译器（AST 节点 × 各种操作）、文档导出（不同节点×不同导出格式）、报表统计、对象结构稳定但操作繁多的系统。

适用前提：元素类型稳定（很少新增元素），操作经常变——反之（元素常加）则不要用访问者。

3. 结构（角色）

双分派：element.accept(v) 先按元素类型分派，visitor.visit(element) 再按访问者类型分派——两次动态绑定，才能”元素类型 × 操作”自由组合。

4. 代码实现（报表导出）

核心收益：加”新操作”= 加一个 Visitor 类；元素类（SaleRecord/RefundRecord）一行不改。

5. 应用场景

场景 说明
编译器 AST 节点 × 解析/检查/生成
报表导出 多类型节点 × 多格式导出
对象结构稳定 数据结构固定、操作易变
统计/审计 对对象结构做多种统计

6. 优缺点

优点 缺点
操作与结构分离（开闭） 违反依赖倒置（元素依赖访问者接口）
加操作易（加访问者） 加元素类型难（所有访问者都要改）
相关操作内聚在一个类 破坏封装（访问者需访问元素内部）
双分派机制强大 复杂度高，简单场景不值

7. 与其他模式对比

模式 区别
迭代器 迭代器遍历；访问者遍历中对每个节点执行操作
组合模式 常配合：组合树 + 访问者遍历操作
策略 策略换算法（单对象）；访问者作用于对象结构

8. 常见误用与陷阱

坑 现象 解法
元素类型频繁新增 每加一个新节点类，所有 Visitor 都要改 元素稳定才用访问者，元素易变用策略模式
破坏元素封装 Visitor 需要访问元素私有字段，过度暴露 元素提供只读视图（DTO）或包级可见，禁止直接 getter
双分派性能损耗 大量元素频繁访问，动态绑定带来 GC 压力 对小数据量场景直接用 switch 类型判断
访问者依赖循环 Visitor 回调 Context 又触发新访问，形成死循环 访问时传入栈深度计数器，超过阈值中断并报警

模板方法模式详解（Template Method）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3k 阅读时长 ≈ 3 分钟

设计模式 · 模板方法

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与策略对比。代码带详细注释。

1. 模式概述（意图）

模板方法模式（Template Method）把算法的骨架定义在父类，把可变的步骤延迟到子类实现——父类控制流程，子类填充细节。

2. 要解决的问题

问题 说明
流程相同、细节不同 支付流程一样，各家签名/调用不同
流程被复制粘贴 每个子类都写一遍骨架（改流程要改多处）
骨架需要强制一致 子类可能打乱步骤顺序

典型场景：Spring 的 JdbcTemplate/RestTemplate、Servlet（doGet/doPost 由框架调）、流程引擎、游戏关卡、测试框架（JUnit 的生命周期）。

3. 结构（角色）

钩子方法（Hook）：父类提供默认实现、子类可选覆写的扩展点（如”是否需要做某步”）。

4. 代码实现（数据导出）

流程控制点：取数 → 格式化 → 写文件 的顺序由父类锁定，子类只换”格式化”这一步。

5. 应用场景

场景 说明
框架回调 Servlet、Spring 模板类
支付/对接 流程相同、签名/报文不同
批量任务 拉数→处理→落库→通知
测试框架 JUnit 生命周期（@Before/@Test/@After）
工作流 固定流程+可变步骤

6. 优缺点

优点 缺点
复用骨架，消除重复 父类与子类耦合（继承）
流程统一（final 防乱序） 骨架改动影响所有子类
扩展靠子类（开闭） 抽象步骤多时子类实现负担
钩子提供灵活扩展点 无法运行时换实现（继承静态）

7. 与策略对比（高频考点）

维度 模板方法 策略
关系 继承（子类填充） 组合（注入策略）
变的部分 步骤实现 整个算法
切换 编译期固定 运行时切换
适用 骨架固定 算法整体可换

实践建议：优先组合优于继承——如果只是”某一步可变”，用回调/函数式接口（如 JdbcTemplate 的 RowMapper）常比继承更灵活。

8. 常见误用与陷阱

坑 现象 解法
模板方法被覆写 子类覆写了模板方法，流程被打乱 模板方法必须加 final 修饰
抽象步骤过多 父类 10 个抽象方法，子类实现负担重 抽象步骤 ≤ 5 个，多的拆为接口或回调
钩子方法滥用 大量空实现的钩子，子类不知道要覆写 钩子方法 ≤ 2 个，且命名带 default 前缀提示
继承层级过深 模板方法嵌套 3 层以上，调试困难 改用组合+回调替代多层继承
