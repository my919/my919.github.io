第五章：高可用与备份恢复

概念基础

  1. 三层防护：Oracle 高可用由「集群防节点故障（RAC） + 容灾防站点故障（Data Guard） + 备份防逻辑/物理损坏（RMAN）」三层叠加构成，各有侧重、互补配合。
  2. RAC 解决单点：多实例共享存储并发读写，任一节点宕机业务自动漂移，做到节点级高可用 + 横向扩展，但不防存储损坏与站点灾难。
  3. Data Guard 解决容灾：主库 redo 实时同步到异地备库，可只读/灾备切换，做到站点级容灾 + 数据零丢失，是 RAC 之外的异地防线。
  4. RMAN 解决恢复：物理备份 + 归档日志支持任意时点恢复，配合闪回快速逆转人为误操作——备份是最后一道防线，”没备份就准备跑路”不是玩笑。
  5. 本章目标：掌握 RAC、Data Guard、RMAN、闪回四大支柱的原理与实操，构建企业级容灾方案。

本章承接 第四章：体系结构与存储管理。高可用设计的前提是理解实例/数据库/归档的运行机制，本章在此基础上构建可用性方案。

二、RAC 集群

1. 架构

RAC（Real Application Clusters）多实例共享访问同一数据库：



flowchart TB
  APP[应用] --> SCAN[SCAN DNS 3 虚拟 IP]
  SCAN --> VIP1[节点1 VIP]
  SCAN --> VIP2[节点2 VIP]
  VIP1 --> I1[实例1 SGA+进程]
  VIP2 --> I2[实例2 SGA+进程]
  I1 <-->|Cache Fusion 融合| I2
  I1 & I2 --> ASM[共享存储 ASM]
  I1 & I2 --> VOTE[投票盘]
  I1 & I2 --> OCR[OCR 集群注册表]
组件 作用
SCAN Single Client Access Name，单一接入点，客户端连 SCAN 不连节点
VIP 节点虚拟 IP，故障时漂移，快速失败转移
ASM 共享存储，所有节点访问同一套数据文件
OCR Oracle Cluster Registry，集群配置仓库
投票盘 Voting Disk 衄裂脑检测，决定哪个节点存活
Cache Fusion 节点间通过私有网络传递数据块锁，统一内存视图

2. 工作机制

  1. 多实例共享同一数据文件，各自有独立 SGA/Redo Thread。
  2. 节点 A 要改节点 B 缓存的块，通过私有网络（Cache Fusion）传递，而非走磁盘。
  3. 节点宕机时，VIP 漂移、SCAN 重定向，会话重连到存活节点。
  4. 私有网络心跳丢失时，投票盘决定少数派节点被驱逐（evict）防脑裂。

3. 优缺点

优势 代价
节点故障自动切换 架构复杂、运维门槛高
横向扩展读、部分扩展写 写仍共享存储，扩展性有限
在线滚动升级 License 昂贵
单库视图，应用透明 Cache Fusion 网络是瓶颈

RAC 防节点不防存储：共享存储是单点，必须配合 ASM 镜像或外部 RAID。RAC 也防不了站点灾难，需 Data Guard 异地容灾。应用要做「无状态 + 重连」才能享受故障切换红利。

4. RAC 常用运维命令

应用接入 RAC 的关键是 Service 而非 SID：客户端连 Service，节点宕机时 Service 自动漂移；配合 TAF / Fast Connection Failover（连接池 ONS 配置）可实现会话透明重连。

三、Data Guard 容灾

1. 架构

主库 redo 实时传输到备库重做应用，形成异地冗余：



flowchart LR
  PRIMARY[主库 Primary] -->|LGWR/LNS 传 redo| STBY[备库 Standby]
  STBY -->|MRP 重做应用| APPLY[数据同步]
  APPLY -.可读.-> RO[只读查询]
  APPLY -.可切换.-> SWITCH[角色切换]

2. 三种保护模式

模式 数据丢失风险 性能影响 适用
最大保护 MAXPROTECTION 零丢失，redo 必须落备库主库才提交 高 金融核心
最大可用 MAXAVAILABILITY 故障时可能丢少量 中 关键业务
最大性能 MAXPERFORMANCE 异步，可能丢 低（默认） 一般容灾

3. 备库类型

类型 应用方式 只读
物理备库 redo 应用，块级一致 12c+ Active Data Guard 可只读+应用
逻辑备库 redo 转 SQL 应用，可改结构 可读写，可做报表
快照备库 暂停应用做快照 可读写，恢复时回滚

4. 物理备库搭建步骤（要点）

tnsnames.ora 与监听要在主备双向配通（orcl、stby 两个服务名互相可解析），密码文件从主库拷贝到备库保持 SYS 密码一致。搭建完成后推荐用 Data Guard Broker（DGMGRL） 管理，切换与监控大幅简化。

5. 角色切换

切换类型 场景 数据丢失
Switchover 计划维护，主备都正常 无
Failover 主库宕机，强制激活备库 取决于模式与延迟

切换演练清单（建议每季度一次）：

  1. 演练前确认 v$dataguard_stats 延迟为 0、主备日志序列连续。
  2. 应用侧准备连接串切换方案（DNS 切换 / 连接池 Failover / TAF）。
  3. Switchover 后主备互换，验证新主可读写、新备正常应用 redo。
  4. 演练结束再切回，记录耗时与问题，更新应急预案。
  5. 用 Broker 时 DGMGRL> SWITCHOVER TO stby; 一条命令完成，避免手敲 SQL 出错。

Active Data Guard 让备库边应用 redo 边只读，分摊报表负载；Fast-Start Failover 配合 Observer 实现故障自动切换。生产容灾演练要定期做 Switchover 验证可用性——未演练的容灾等于没有。

七、容灾方案设计要点

  1. RPO/RTO 目标：RPO（可丢数据量）决定同步模式，RTO（恢复时间）决定切换自动化程度。
  2. 三层叠加：RAC 防节点 + Data Guard 防站点 + RMAN 防物理损坏，缺一不可。
  3. 演练：定期 Switchover 演练验证容灾可用，”未演练的容灾等于没有”。
  4. 备份验证：备份不仅要”做了”，要定期”恢复验证”——未验证的备份可能在恢复时才发现损坏。
  5. 监控：归档空间、备库延迟、RMAN 备份成功率、闪回保留窗口纳入监控告警。
  6. 人为误操作优先闪回：闪回分钟级，RMAN 时点恢复小时级，先试闪回。
  7. 监控脚本化：把备库延迟、归档空间纳入日常巡检——

八、常见陷阱

陷阱 说明
NOARCHIVELOG 无时点恢复 生产必须开归档，否则只能恢复到上次备份
备份未验证 恢复时才发现损坏，定期做恢复演练
归档目录满挂起库 监控 + 保留策略 + 自动清理
RAC 不防存储损坏 共享存储单点，配 ASM 镜像/Data Guard
Data Guard 不同步 网络延迟、备库未应用，定期查 v$dataguard_stats
闪回窗口过短 UNDO 被覆盖闪回失效，调大 UNDO_RETENTION 与 DB_FLASHBACK_RETENTION_TARGET
Failover 后丢数据 最大性能模式异步可能丢，关键业务用最大可用/保护
RESETLOGS 后忘新基线 化身改变，旧增量备份失效，需立即全量

要点 结论
三层防护 RAC 防节点 + Data Guard 防站点 + RMAN 防物理损坏

第四章：Golang 工程实践

概念基础

  1. 从会写到能维护：语法与标准库之外，工程化能力（模块管理、测试、错误规范、性能分析）决定代码能否在团队中长期演进。
  2. 测试是一等公民：go test 内建，无第三方框架；表驱动测试与基准测试是 Go 社区的统一语言，CI 里 -race 必开。
  3. 错误处理要规范：%w 包装 + errors.Is/As 判断是 1.13+ 的标准范式；团队需统一「在哪里包装、在哪里兜底日志」。
  4. 泛型已成熟：1.18+ 类型参数消除 interface{} 转换样板，标准库 slices/maps 已泛型化——但泛型不是银弹，接口优先。
  5. 可观测性内建：pprof CPU/内存/协程剖析开箱即用，配合 expvar/metrics 定位线上问题。

第二章：Golang 并发编程

概念基础

  1. 并发是语言内建能力：Go 在语言层面提供 goroutine 与 channel，无需第三方库即可写出高并发程序，这是 Go 最具辨识度的特性。
  2. CSP 模型：遵循「不要通过共享内存来通信，而要通过通信来共享内存」，用 channel 在 goroutine 之间传递数据与所有权。
  3. M:N 调度：运行时把成千上万个轻量 goroutine 复用到少量 OS 线程上，创建成本远低于线程，适合海量并发任务。
  4. 传统同步工具仍在：sync.Mutex/WaitGroup/Once 处理共享状态与协作，context 统一传递取消与超时。
  5. 工程红线清晰：goroutine 泄漏、循环变量捕获、无界并发是三大常见陷阱；开发与 CI 应常开 go test -race 竞态检测。

一、goroutine 与调度模型

  • goroutine：用 go f() 启动；栈初始很小、可按需增长，创建成本远低于操作系统线程，因此可以大量存在。
  • 调度器：运行时把许多 goroutine 映射到少量 OS 线程（M:N 模型），在阻塞或抢占点切换，避免「一线程一连接」把机器拖垮。
  • 何时用：IO 密集、扇出扇入、后台任务；CPU 密集仍要控制并发度（见第七节），否则和线程池一样会抢满核心。

1.1 GMP 调度模型

Go 1.25 运行时的调度器由三类实体构成，理解它对排查性能问题至关重要：

实体 含义 要点
G（Goroutine） 待执行的任务单元 初始栈仅 2KB 按需增长；含栈、指令指针、上下文
M（Machine） OS 线程 真正跑代码的载体，数量与系统调用阻塞情况联动
P（Processor） 逻辑处理器 默认数 = GOMAXPROCS（CPU 核数）；每个 P 持一个本地可运行队列（LRQ）

调度要点：

  • M:N 复用：N 个 G 跑在 M 个线程上，但任一时刻并行执行的 G 数量受 P 数限制——CPU 密集任务的「有效并发」上限就是 GOMAXPROCS。
  • 工作窃取（work stealing）：某 P 的本地队列空了，会从全局队列（GRQ）或其他 P 的队列偷一半 G 过来，保证负载均衡。
  • 阻塞处理：G 陷入阻塞式系统调用时，其 M 带着 G 脱离 P，P 立即绑定新 M 继续跑其他 G——这就是「几千个并发连接拖不垮 Go」的原因。
  • 抢占：Go 1.14+ 引入基于信号的异步抢占，长时间纯计算（无函数调用）的 G 也会被让出 CPU，避免单个死循环饿死全进程。

容器环境注意：Go 1.25 起 GOMAXPROCS 默认感知 cgroup CPU limit；旧版本在 K8s 里会看到宿主机核数，导致 P 过多、频繁上下文切换，需用 automaxprocs 修正。

二、channel：通信优先于共享内存

  • 声明与创建：var ch chan int 为 nil，发送/接收会永久阻塞；ch := make(chan int) 无缓冲；make(chan int, 10) 带容量为缓冲 channel。
  • 无缓冲：发送方与接收方必须同时就绪，完成一次「交接」，常用于同步节拍。
  • 缓冲：未满时可先发送，常用于限流或解耦；容量为 0 与无缓冲语义一致。
  • 关闭：仅发送方应调用 close(ch)；接收方可用 v, ok := <-ch，ok == false 表示 channel 已关闭且无剩余数据。
  • 单向 channel：类型 chan<- T（只发）、<-chan T（只收）用于函数签名，约束使用方式、减少误用。

操作 nil/关闭 channel 的行为表：向 nil channel 收发→永久阻塞；关闭 nil channel、重复关闭、向已关闭 channel 发送→panic；从已关闭 channel 接收→立即返回零值（ok=false）。「由发送方关闭、只关一次」是避免 panic 的铁律。

2.1 channel 底层结构

make(chan T) 创建的 hchan 结构体核心字段：

  • buf：环形缓冲区（仅缓冲 channel 有），sendx/recvx 记录读写下标。
  • sendq / recvq：因发送/接收而阻塞的 goroutine 等待队列——无缓冲 channel 的交接本质：发送方挂进 sendq，接收方到达后直接从对方栈上拷数据（不经 buf），再唤醒发送方。
  • lock：每个 channel 一把互斥锁，所有队列与缓冲区操作都在锁内——channel 的「无锁」是使用者视角，内部仍有锁。

由此可解释三个现象：

  1. 无缓冲 channel 是同步点：发送方必须等接收方接手才能完成，天然形成「交接内存屏障」，这是它能替代锁做同步的底层依据。
  2. 缓冲 channel 的容量只是解耦窗口：满了照样阻塞发送方；cap 设多大取决于上下游速率差，不是越大越好。
  3. close 是广播：关闭时唤醒所有 recvq 中的接收方（返回零值 + ok=false），所以 close 常作多接收方统一退出信号（比挨个发消息高效）。

三、select：多路等待与超时

  • select 在多个 channel 操作上等待，随机选择一个可执行的 case；若都阻塞且无 default，则阻塞；有 default 则立即走默认分支（常用于非阻塞尝试）。
  • 超时模式：用 time.After 或 context（推荐生产代码）控制最长等待。

四、sync 包：锁与协作原语

4.1 Mutex / RWMutex

  • 多 goroutine 读写同一内存且无 channel 串行化时，用 sync.Mutex 保护临界区；读多写少可考虑 RWMutex。
  • 锁粒度要小、持有时间要短；避免在持锁时做 IO 或可能阻塞很久的逻辑。
  • 读多写少用 RWMutex：读用 RLock/RUnlock 可多读并发，写用 Lock/Unlock 与所有读写互斥；当读操作远多于写、且读临界区稍长时，比 Mutex 更利于吞吐。

注意：RWMutex 并非「必优于 Mutex」。读临界区很短时，RLock/RUnlock 的计数开销可能反超 Mutex；不确定时先 Mutex，用 go test -race + benchmark 验证再换。

4.2 WaitGroup

  • Add / Done / Wait：主 goroutine Wait() 等待一组子任务结束；Add 要在启动 goroutine 之前（或确保不竞态地提前 Add），避免 Wait 早于 Add 导致计数错误。

Add 必须在启动 goroutine 之前调用：Wait() 在计数归零时立即返回，若 Add 落到子 goroutine 内部，Wait 可能在任何 Add 之前就执行而提前放行。这是逻辑时序错误，go test -race 未必能检出，需靠规范避免——Add 在前、Done 用 defer 在内。

4.3 Once

  • sync.Once 保证 Do(f) 里的 f 全局只执行一次，常用于懒初始化单例。

七、常见陷阱与实践建议

  • main 退出即进程退出：未 Wait 或未收完结果的 goroutine 会被直接掐掉；要有明确的汇合点（WaitGroup、channel 关闭、errgroup 等）。
  • 泄漏 goroutine：向无人接收的 channel 发送、或 goroutine 永远阻塞在 select，都会导致泄漏；长生命周期任务要设计退出信号。
  • 闭包与循环变量：在循环里 go func() { ... } 若引用循环变量，应用参数传入当前值，避免经典「全部打印最后一个」问题（Go 1.22+ 对循环变量语义有调整，仍建议显式传参以增强可读性与兼容旧版本）。
  • CPU 密集：用 runtime.NumCPU() 或带缓冲的 worker channel 限制并发 worker 数量，而不是无节制 go。
  • 竞态检测：开发与 CI 中开启 go test -race，能发现大量数据竞态。

整体上，Go 鼓励用 channel 表达所有权与流水线，在热点路径或简单共享计数时用 Mutex；取消与超时交给 context，代码意图会更清晰、也更容易在团队中保持一致。

第四章：体系结构与存储管理

概念基础

  1. 内存 + 进程 + 文件三件套：Oracle 实例由 SGA（共享内存）+ PGA（私有内存）+ 后台进程构成，操作 Database 物理文件——理解三者的协作就抓住了 Oracle 运行的本质。
  2. 日志先行是命脉：事务提交时 LGWR 先把 redo 写联机日志才算「提交成功」，脏块由 DBWn 延迟批量落盘。这套 WAL 机制保证了实例崩溃后可恢复，是 Oracle 可靠性的根基。
  3. 逻辑/物理存储两层映射：逻辑上「表空间→段→区→块」，物理上「数据文件→操作系统块」——段对应表/索引、区是分配单位、块是最小 IO 单元。
  4. 多版本读一致性靠 UNDO：查询看到的是「查询开始时点」的数据快照，靠 UNDO 表空间的撤销数据回构——这是 Oracle 实现「读不阻塞写、写不阻塞读」的核心。
  5. 本章目标：从内存、进程、文件到存储分层与 ASM，建立完整的 Oracle 内部运行图景，为高可用与调优打基础。

本章承接 第三章：PL/SQL 程序设计。体系结构是 DBA 与架构师的必修课，也是后续高可用、调优章节的底层依据。

一、内存结构

1. SGA（System Global Area，共享全局区）

SGA 是所有服务进程共享的内存大区，由若干子池组成：

子池 职责 调优要点
Buffer Cache 缓存数据块，减少物理读 DB_CACHE_SIZE，命中率核心
Shared Pool 库缓存（SQL/PL/SQL 解析结果）+ 数据字典缓存 SHARED_POOL_SIZE，绑定变量缓解
Redo Log Buffer 缓存 redo 条目，LGWR 异步写盘 LOG_BUFFER，通常较小
Large Pool RMAN 备份、并行查询、共享服务器会话 可选，避免挤占 Shared Pool
Java Pool / Streams Pool JVM、GoldenGate/Streams 按需

Buffer Cache 内部：默认缓存 8KB 数据块，可细分三个池——

池 用途
DEFAULT 默认池，未指定的对象进这里
KEEP 钉住热表（STORAGE(BUFFER_POOL KEEP)），防被挤出
RECYCLE 放大表全扫的块，快进快出防污染

脏块通过检查点队列等待 DBWn 落盘，干净块按 LRU 变冷淘汰。

Shared Pool 内部：库缓存（SQL 文本/执行计划，按 SQL_ID 哈希存放）+ 数据字典缓存（row cache，表/列定义）+ 结果缓存（11g+，RESULT_CACHE）。硬解析频繁时 library cache 闩锁争用会成为瓶颈——绑定变量是根治手段（见第六章）。

2. PGA（Program Global Area，私有区）

PGA 是每个会话私有的内存，存放排序区、会话状态、游标：

区域 作用
Sort Area 排序中间结果，不足则写临时段
Hash Area 哈希连接用
Session Memory 会话变量、游标状态

workarea executions - onepass / multipass 持续增长说明排序/哈希内存不足、溢出到 TEMP 磁盘，需调大 PGA_AGGREGATE_TARGET 或优化 SQL（减少排序、加索引消除 ORDER BY）。理想状态是 optimal 占绝对多数。

SGA 是共享、PGA 是私有——这是内存模型的核心区分。排序/哈希在 PGA 跑，超限溢出到 TEMP 表空间（磁盘），是慢查询的常见元凶。

实例恢复（Crash Recovery）流程

实例异常宕机（断电、SHUTDOWN ABORT）后再次启动时，SMON 自动执行实例恢复，无需人工干预：



flowchart LR
  A[启动 MOUNT] --> B[OPEN 前: 前滚 Roll Forward]
  B --> C[重放 redo 恢复脏块]
  C --> D[库可 OPEN 提供服务]
  D --> E[SMON 回滚未提交事务]
  1. 前滚（Roll Forward）：用联机 redo 把最后一次检查点之后的所有变更重放到数据文件，包括未提交事务的脏块——先把「磁盘状态」追平到宕机瞬间。
  2. 打开数据库：此时库中尚有未提交事务的数据，但已可对外服务。
  3. 回滚（Roll Back）：SMON 用 UNDO 回滚所有未提交事务，恢复一致性；新事务碰到未回滚的行时会触发事务恢复自动清理。

「先追平、再清理」：前滚依赖 redo（已落盘的变更），回滚依赖 UNDO（未提交的旧值）。这解释了为什么实例崩溃不丢已提交数据（redo 已写盘），也不留未提交数据（UNDO 回滚）。FAST_START_MTTR_TARGET 控制前滚时间上限。

1. 数据块内部

一个数据块（默认 8KB）内部结构：

六、UNDO 与读一致性

1. UNDO 的作用

UNDO 表空间存放「改之前」的旧值，支撑三大机制：

  1. 事务回滚：ROLLBACK 时用 UNDO 恢复原值。
  2. 读一致性：查询看到查询开始时点的数据，靠 UNDO 回构已被改的块。
  3. 闪回查询：AS OF TIMESTAMP 利用 UNDO 看历史数据。

2. 多版本读一致性

参数 作用
UNDO_RETENTION UNDO 保留时间（秒），降低 ORA-01555
UNDO_TABLESPACE 指定 UNDO 表空间
TEMP_UNDO_ENABLED 12c+ 临时表 UNDO 独立

自动 UNDO 管理（AUM）要点：

  • 表空间自动扩展（AUTOEXTEND ON）时，UNDO_RETENTION 是「努力目标」，空间紧张时保留时间可能被压缩。
  • RETENTION GUARANTEE 强制保留（宁可 DML 报错也不覆盖未过期 UNDO），代价是影响并发事务。
  • 估算所需 UNDO 大小：峰值每秒 undo 生成量 × UNDO_RETENTION，生成速率查 V$UNDOSTAT 的 UNDOBLKS。

ORA-01555 快照太旧是长查询经典错误：UNDO 数据被新事务覆盖，旧版本回构不出来。调大 UNDO_RETENTION 与 UNDO 表空间、避免长查询跨大事务可缓解。

  1. 会话修改块，生成 redo 条目入 Redo Log Buffer。
  2. 提交时 LGWR 把 redo 写联机日志（同步），提交返回。
  3. DBWn 延迟把脏块写数据文件（异步批量）。
  4. 联机日志写满切换，ARCn 归档（ARCHIVELOG 模式）。

LGWR 触发写的时机（满足任一即写）：

  • 事务 COMMIT（同步等待，这是「提交成功」的定义）。
  • Redo Log Buffer 达到 1/3 满。
  • 每 3 秒超时。
  • DBWn 写脏块之前（对应 redo 必须先落盘）。

redo 先行的严格性：DBWn 写任何脏块前，该块对应的 redo 必须已落盘——否则实例崩溃后无法前滚这个块。COMMIT 的 log file sync 等待即等 LGWR 落盘，是 OLTP 提交延迟的关键指标（见第六章）。

3. 稀疏索引：为什么主键不占多少内存

MergeTree 的主键索引不是 B-Tree，而是稀疏索引（Sparse Index）：

  • 数据按 ORDER BY 排序后切成 granule（默认每 8192 行一个）。
  • 索引只记录每个 granule 第一行的排序键值——亿行表的主键索引通常只有几万条，可常驻内存。
  • 查询时先二分查找索引定位到候选 granule 区间，再并行扫描这些 granule——这就是「索引在 ClickHouse 里很轻」的原因。
  • partition：分区键值（如 202605）。
  • part：分区内的物理数据块，后台 merge 会持续把小 part 合成大 part。
  • part 过多会触发 Too many parts 报错——写入批量化是预防关键（排查详见 第三章：ClickHouse 查询与性能调优）。

向量化执行：快在 CPU 层面

列存解决的是少读盘，向量化解决的是读进来之后算得快：

  • 批量而非逐行：表达式一次处理一个列块（通常几千行的数组），而不是一行行解释执行。
  • SIMD 指令：sum、count 等聚合经编译生成 AVX2/AVX-512 向量化指令，一条指令算多个值。
  • CPU 缓存友好：列块紧凑连续，预取命中率高；行存的「字段散布在行里」会频繁缓存失效。
  • 多核并行：查询按 granule 拆成任务流，默认吃满 max_threads（= CPU 核数）。

这也是为什么 ClickHouse 对虚机 / 容器限核敏感——CPU 被限到 2 核时，聚合吞吐近乎同比腰斩，容量规划要预留核数。

集群部署概览：ReplicatedMergeTree + Keeper

单机之上，生产最小可信拓扑是 2 分片 × 2 副本：

  1. ClickHouse Keeper（或 ZooKeeper）：3 节点小集群，存副本元数据与日志序号，协调「谁同步谁」；自身用 Raft 选主，独立于数据节点部署。
  2. ReplicatedMergeTree：建表加副本参数，同分片的多个副本通过 Keeper 交换 part 清单、互拉数据，写入任一副本即可。
  3. Distributed 表：建在每个节点上，按 sharding key（如 user_id 哈希）把写入/查询路由到目标分片。

要点：ON CLUSTER 让 DDL 在集群所有节点执行；分片键选基数高、分布均匀的列，避免数据倾斜。完整容器化集群清单见 第二章：Docker 部署 ClickHouse 实践。

生产注意

  • 副本与 Keeper：ClickHouse Keeper（或 ZooKeeper）协调复制与分布式 DDL；Keeper 集群必须奇数节点（3 或 5），与数据节点分开部署。
  • 资源：内存用于 merge 与查询；磁盘顺序写与 merge 压力需监控；CPU 核数直接决定聚合吞吐。
  • 写入纪律：批量写入（每批几万~几十万行），避免高频小批产生海量小 part 触发 Too many parts。
  • 升级：固定版本标签，阅读 Release Notes 中不兼容变更；跨大版本先在测试集群滚动验证。

概念基础

  1. SQL 标准为主、方言为辅：Oracle 支持 ANSI SQL，但有自己的方言细节——VARCHAR2 而非 VARCHAR、DUAL 伪表、ROWNUM 伪列、字符串拼接用 ||。

概念基础

  1. 企业级关系型数据库：Oracle Database 是老牌商业 RDBMS，在银行、电信、政务等对稳定性、安全合规与厂商支持要求高的核心系统中长期占主导地位。
  2. 实例与数据库分离：Instance（内存 SGA + 后台进程）挂载并打开 Database（物理文件集合），多实例可共享访问同一套库（即 RAC）。理解「实例是内存进程、数据库是文件」是入门第一关。

1. 三层对应关系

Instance 实例 SGA（共享内存）+ 后台进程 内存态，重启即重建
Database 数据库 数据文件、控制文件、重做日志 磁盘态，持久存在

关键区分：实例是「跑起来的内存进程」，数据库是「磁盘上的文件」。实例挂掉数据不丢（落盘），但内存中的未提交事务会因 undo 回滚。这套机制详见 第四章：体系结构与存储管理。

2. 后台进程速记

进程 职责 记忆点

SMON 系统监控，实例恢复、合并空闲空间 System Monitor
DBWn 数据库写进程，把脏块从 Buffer Cache 落盘 DataBase Writer
LGWR 日志写进程，把 Redo Log Buffer 写联机日志 LoG Writer（写顺序的命脉）
CKPT 检查点，同步数据文件头与控制文件 CheckPoint

LGWR 是性能与安全的命脉：事务提交时 LGWR 把 redo 落盘即算提交成功，DBWn 则延迟批量落盘。所谓「日志先行（WAL）」即此。

行为差异要点

  1. 事务：Oracle 默认手动提交；MySQL 默认 autocommit=1；PG 默认自动提交但 DDL 可回滚（Oracle 的 DDL 隐式提交且不可回滚）。
  2. 空字符串：Oracle 把 '' 当 NULL；MySQL/PG 视为空串——WHERE col = '' 在 Oracle 永远查不到。
  3. 大小写：Oracle 未加引号的标识符自动转大写；PG 转小写；MySQL 依操作系统。迁移时带引号的混合大小写对象名是坑。
  4. 隔离级别：Oracle 默认 READ COMMITTED（语句级读一致）；MySQL InnoDB 默认 REPEATABLE READ。
  5. 序列：Oracle SEQUENCE 是独立对象，可多表共用、可缓存（CACHE 20）；MySQL 自增列绑定单表。

六、常用数据字典视图速查

1. 静态字典视图（USER_ / ALL_ / DBA_ 三前缀）

前缀 可见范围 典型视图

V$ 反映实例运行时状态，随库运行持续更新、重启即清空：

视图 内容
V$INSTANCE 实例名、状态、启动时间
V$DATABASE 库名、日志模式、当前 SCN
V$SESSION 会话清单（含 SQL_ID、等待事件）
V$SQL 共享池中的 SQL 与执行统计
V$VERSION 版本横幅
V$PDBS 12c+ 各 PDB 状态

记忆法：USER_ 看自己、ALL_ 看能用、DBA_ 看全库、V$ 看运行时。查对象定义找静态视图，查运行状态找 V$。更完整的诊断视图清单见 第四章 与 第六章。

七、运维红线速记

  • 字符集：建库时定 AL32UTF8，后期修改成本极高（需导入导出重建）。
  • 归档模式：生产必须 ARCHIVELOG，否则只能恢复到上次备份、无法时点恢复。
  • 连接数：应用侧用连接池控制会话数，避免耗尽 processes / sessions。
  • 补丁周期：LTS 与 Extended Support 周期需与采购合同对齐，过期无补丁有安全风险。
  • UNDO/TEMP：别在 UNDO/TEMP 表空间建业务表，SYSTEM/SYSAUX 亦然。

第三章：MongoDB 索引、聚合与模式设计

概念基础

  1. MongoDB 慢查询九成是索引问题：无索引的 find 是全集合扫描（COLLSCAN）；建对索引变成 IXSCAN，与关系库的「先看执行计划」哲学一致。
  2. ESR 原则定复合索引字段序：Equality（等值）→ Sort（排序）→ Range（范围），顺序排对一条复合索引能同时服务过滤与排序。
  3. 聚合管道是 MongoDB 的「SQL+ETL」：$match → $group → $sort → $project ... 流水线处理，能下推的尽量下推（先 $match 后 $group）。
  4. 模式设计决定性能上限：文档模型核心取舍是内嵌（embed）还是引用（reference）——按「一起读写就内嵌、各自更新就引用」判断。
  5. explain 是证据不是感觉：executionStats 里的 totalKeysExamined / totalDocsExamined / nReturned 三值关系直接给出诊断。

本章承接 第一章：MongoDB 概述与入门 的 CRUD 与 第二章：Docker 部署 MongoDB 实践 的环境；mongosh 语法按 MongoDB 8.0 官方文档书写（沙箱无实例，未逐条运行验证）。

一、explain：诊断查询

三个关键数字：

字段 含义 健康标准
nReturned 实际返回条数 —
totalKeysExamined 扫过的索引条目 接近 nReturned
totalDocsExamined 扫过的文档数 接近 nReturned（远大=回表浪费）

同时确认 winningPlan 里是 IXSCAN 而非 COLLSCAN；SORT_STAGE 出现说明排序没吃到索引（内存排序 32MB 上限会直接报错）。

二、索引体系

实践要点：

  • 每个额外索引都拖慢写入——索引不是越多越好，按真实查询建。
  • db.orders.getIndexes() 盘点存量；低效索引用 dropIndex 清理。
  • 大集合建索引用后台滚动构建（4.2+ 默认后台方式），避开写入高峰。
  • 最左前缀同样适用：{ userId, status, createdAt } 可服务 userId 与 userId+status 的查询。

三、聚合管道进阶

管道优化口诀：

原则 说明
$match/$limit 放最前 能被索引下推，后面的阶段数据越少越好
$project 砍字段 减少内存与网络传输
$group 用 _id: null 全表聚合（配合 $facet 一次算多组指标）
允许近似 超大集合统计可接受秒级误差时用 $sample 或预聚合

$lookup 进阶：pipeline 形式与性能

基础形式只能做等值关联；pipeline 形式能在关联侧再过滤、排序、截断：

性能三要点：

  • 被关联集合的 foreignField 必须有索引（上例是 orders.userId），否则每个外层文档触发一次 COLLSCAN，复杂度 O(N×M)。
  • $expr 负责把 let 变量与关联侧字段绑定；不等值条件（范围、数组包含）只有 pipeline 形式能写。
  • 只需「是否存在」时，用 pipeline + $limit: 1 + $project: { _id: 1 } 代替全量拉取。

$addFields 与 $replaceRoot：重塑文档

$addFields = SQL 的派生列；$replaceRoot（别名 $replaceWith）常作为管道收尾，把结果整理成下游直接可用的结构。

$bucket 与 $facet：分桶与多路统计

$facet 一次扫描产出多份报表，是仪表盘神器；$bucket 按边界分桶（$bucketAuto 自动均分）。注意 $facet 各子管道无法走索引且共享 100MB 内存上限，超大集合改用预聚合。

四、模式设计：内嵌还是引用

判断口诀：

场景 选择
1:1 或 1:少量（生命周期一致） 内嵌
1:多且子文档无限增长（评论、日志） 引用（或「内嵌最近 N 条 + 冷数据独立集合」）
多对多 引用
内嵌文档 16MB 上限 逼近上限必须拆

常见增强：$lookup 慢的高频关联可冗余一份 userName 到订单文档（写入时双写），用读时免 JOIN 换写时多一步——文档模型下的「反范式」是常规操作。

五、四个常用 Schema 设计模式

官方 Schema 设计模式清单里，业务系统最常用这四个：

1. Computed Pattern（预计算）

读多写少 + 重复计算贵时，把结果写时算好存下来：商品文档冗余 avgRating、reviewCount，每次评价写入时 $inc / $avg 重算，读详情页零计算。代价：写多一步、口径变更要回填历史。

2. Bucket Pattern（分桶）

时序数据（IoT 指标、行情、访问日志）一条一个文档会爆索引与文档数——按时间桶聚合：

收益：索引条目下降几个数量级，且「查某时段」的访问模式天然匹配桶边界。

3. Subset Pattern（子集）

文档太胖导致工作集（working set）放不进内存？把高频字段留在主文档（文章列表只需标题/摘要/作者），低频大块拆到独立集合（正文、历史版本）——列表查询不再拖着 KB 级正文跑。

4. Attribute Pattern（属性模式）

各品类属性差异大（手机有「屏幕尺寸」、衣服有「尺码」），为每种属性建索引不现实——统一存成键值数组：

六、事务与批量写入

单文档天然原子：把需要原子性的关联数据内嵌进同一文档，很多「事务需求」就直接消失了——这是文档建模的隐藏红利。

七、Change Stream：监听数据变更

「数据一变就通知下游」（刷缓存、发消息、同步搜索引擎）不必轮询——Change Stream 基于 oplog 实时推送变更，要求副本集模式（单节点副本集即可，见 第二章）：

要点：

  • watch(pipeline) 可用聚合语法预过滤，只推关心的变更，省网络与处理量。
  • fullDocument: "updateLookup" 让 update 事件也带上变更后的完整文档（默认只有增量字段）。
  • 生产用法：持久化 resumeToken，重启后用 resumeAfter 断点续传不丢事件；驱动断线自动重试。
