Oracle：数据库入门

Oracle：数据库入门

概念基础

  1. 企业级关系型数据库：Oracle Database 是老牌商业 RDBMS，在银行、电信、政务等对稳定性、安全合规与厂商支持要求高的核心系统中长期占主导地位。
  2. 实例与数据库分离：Instance（内存 SGA + 后台进程）挂载并打开 Database（物理文件集合），多实例可共享访问同一套库（即 RAC）。理解「实例是内存进程、数据库是文件」是入门第一关。
  3. 逻辑存储分层：数据组织在表空间（SYSTEM / SYSAUX / USERS / TEMP / UNDO）中，向下再划分为段、区、块——这套分层决定了建库、扩容、调优的思维方式。
  4. 高可用与容灾：RAC 多节点共享存储集群、Data Guard 主备容灾，配合 RMAN 备份恢复构成企业级方案，这是 Oracle 区别于开源库的核心竞争力。
  5. PL/SQL 过程化扩展：存储过程、包、触发器可在库内实现复杂业务逻辑，减少应用与数据库之间的往返——既是优势也是「业务逻辑下沉」的双刃剑。

本章是 Oracle 系列的总览与起点。先建立「实例/数据库/Schema」的体系结构心智模型，再跑通最小 SQL 与连接示例，后续章节逐层深入 SQL、PL/SQL、存储、高可用与调优。

一、版本与发行版

Oracle 版本号采用「主版本.数据库发布更新」的形式，常见长期支持版本：

版本 发布 特性要点 支持状态
11g 2007 引入 Result Cache、ADDM 成熟 EOL，存量系统
12c 2013 多租户 CDB/PDB、Identity Column、JSON Extended Support
19c 2019 长期支持版（LTS）、自动索引、Active Directory 存量主流（延长支持期，建议规划升级）
23ai 2024 AI 向量原生支持、Boolean 类型、Microcluster 当前长期支持版（云上已演进至 26ai）

23ai 是当前长期支持版（AI 向量原生支持），存量生产系统仍以 19c 为主（已处延长支持期，建议规划升级）。学习建议用免费版 XE / Database Free。

免费发行版：

  • Oracle Database Express Edition（XE）：固定上限（2 CPU、2GB SGA、12GB 用户数据），适合学习与小型部署。
  • Database Free（23ai 起改名）：开发与容器化友好，container-registry.oracle.com 提供官方镜像。
  • Oracle Cloud Always Free：云端永久免费层，含 2 个 Autonomous Database（各 20GB），免安装体验 23ai。

23ai 新特性尝鲜：免费版即可体验 Boolean 类型（CREATE TABLE t (flag BOOLEAN)）、IF NOT EXISTS（CREATE TABLE IF NOT EXISTS t (...) 避免重复建表报错）、AI 向量（VECTOR 类型 + 向量距离函数）。这些在 19c 及之前均不存在，学习环境建议直接上 23ai Free。

1. 三层对应关系

层次 组成 性质
Instance 实例 SGA（共享内存）+ 后台进程 内存态，重启即重建
Database 数据库 数据文件、控制文件、重做日志 磁盘态，持久存在
Schema 模式 用户拥有的对象（表、视图、过程等） 逻辑概念，隶属于用户

关键区分：实例是「跑起来的内存进程」，数据库是「磁盘上的文件」。实例挂掉数据不丢（落盘），但内存中的未提交事务会因 undo 回滚。这套机制详见 Oracle：体系结构与存储管理。

2. 后台进程速记

进程 职责 记忆点
PMON 进程监控，清理异常死掉的会话 Process Monitor
SMON 系统监控，实例恢复、合并空闲空间 System Monitor
DBWn 数据库写进程，把脏块从 Buffer Cache 落盘 DataBase Writer
LGWR 日志写进程，把 Redo Log Buffer 写联机日志 LoG Writer（写顺序的命脉）
CKPT 检查点，同步数据文件头与控制文件 CheckPoint
ARCn 归档进程，联机重做日志写满后拷贝归档 Archiver（ARCHIVELOG 模式才有）

LGWR 是性能与安全的命脉：事务提交时 LGWR 把 redo 落盘即算提交成功，DBWn 则延迟批量落盘。所谓「日志先行（WAL）」即此。

行为差异要点

  1. 事务：Oracle 默认手动提交；MySQL 默认 autocommit=1；PG 默认自动提交但 DDL 可回滚（Oracle 的 DDL 隐式提交且不可回滚）。
  2. 空字符串：Oracle 把 '' 当 NULL；MySQL/PG 视为空串——WHERE col = '' 在 Oracle 永远查不到。
  3. 大小写：Oracle 未加引号的标识符自动转大写；PG 转小写；MySQL 依操作系统。迁移时带引号的混合大小写对象名是坑。
  4. 隔离级别：Oracle 默认 READ COMMITTED（语句级读一致）；MySQL InnoDB 默认 REPEATABLE READ。
  5. 序列：Oracle SEQUENCE 是独立对象，可多表共用、可缓存（CACHE 20）；MySQL 自增列绑定单表。

六、常用数据字典视图速查

Oracle 把元数据全部暴露在数据字典中，分静态字典视图与动态性能视图两类，是日常查询与排障的入口。

1. 静态字典视图（USER_ / ALL_ / DBA_ 三前缀）

前缀 可见范围 典型视图
USER_* 当前用户拥有的对象 USER_TABLES、USER_INDEXES、USER_OBJECTS
ALL_* 当前用户可访问的对象（含被授权的） ALL_TABLES
DBA_* 全库对象（需 DBA 权限） DBA_TABLESPACES、DBA_USERS、DBA_DATA_FILES

2. 动态性能视图（V$）

V$ 反映实例运行时状态，随库运行持续更新、重启即清空：

视图 内容
V$INSTANCE 实例名、状态、启动时间
V$DATABASE 库名、日志模式、当前 SCN
V$SESSION 会话清单（含 SQL_ID、等待事件）
V$SQL 共享池中的 SQL 与执行统计
V$VERSION 版本横幅
V$PDBS 12c+ 各 PDB 状态

记忆法：USER_ 看自己、ALL_ 看能用、DBA_ 看全库、V$ 看运行时。查对象定义找静态视图，查运行状态找 V$。更完整的诊断视图清单见 Oracle：体系结构与存储管理 与 Oracle：性能调优与运维。

七、运维红线速记

  • 字符集：建库时定 AL32UTF8，后期修改成本极高（需导入导出重建）。
  • 归档模式：生产必须 ARCHIVELOG，否则只能恢复到上次备份、无法时点恢复。
  • 连接数：应用侧用连接池控制会话数，避免耗尽 processes / sessions。
  • 补丁周期：LTS 与 Extended Support 周期需与采购合同对齐，过期无补丁有安全风险。
  • UNDO/TEMP：别在 UNDO/TEMP 表空间建业务表，SYSTEM/SYSAUX 亦然。

MongoDB：索引、聚合与模式设计

概念基础

  1. MongoDB 慢查询九成是索引问题：无索引的 find 是全集合扫描（COLLSCAN）；建对索引变成 IXSCAN，与关系库的「先看执行计划」哲学一致。
  2. ESR 原则定复合索引字段序：Equality（等值）→ Sort（排序）→ Range（范围），顺序排对一条复合索引能同时服务过滤与排序。
  3. 聚合管道是 MongoDB 的「SQL+ETL」：$match → $group → $sort → $project ... 流水线处理，能下推的尽量下推（先 $match 后 $group）。
  4. 模式设计决定性能上限：文档模型核心取舍是内嵌（embed）还是引用（reference）——按「一起读写就内嵌、各自更新就引用」判断。
  5. explain 是证据不是感觉：executionStats 里的 totalKeysExamined / totalDocsExamined / nReturned 三值关系直接给出诊断。

一、explain：诊断查询

三个关键数字：

字段 含义 健康标准
nReturned 实际返回条数 —
totalKeysExamined 扫过的索引条目 接近 nReturned
totalDocsExamined 扫过的文档数 接近 nReturned（远大=回表浪费）

同时确认 winningPlan 里是 IXSCAN 而非 COLLSCAN；SORT_STAGE 出现说明排序没吃到索引（内存排序 32MB 上限会直接报错）。

二、索引体系

实践要点：

  • 每个额外索引都拖慢写入——索引不是越多越好，按真实查询建。
  • db.orders.getIndexes() 盘点存量；低效索引用 dropIndex 清理。
  • 大集合建索引用后台滚动构建（4.2+ 默认后台方式），避开写入高峰。
  • 最左前缀同样适用：{ userId, status, createdAt } 可服务 userId 与 userId+status 的查询。

三、聚合管道进阶

管道优化口诀：

原则 说明
$match/$limit 放最前 能被索引下推，后面的阶段数据越少越好
$project 砍字段 减少内存与网络传输
$group 用 _id: null 全表聚合（配合 $facet 一次算多组指标）
允许近似 超大集合统计可接受秒级误差时用 $sample 或预聚合

$lookup 进阶：pipeline 形式与性能

基础形式只能做等值关联；pipeline 形式能在关联侧再过滤、排序、截断：

性能三要点：

  • 被关联集合的 foreignField 必须有索引（上例是 orders.userId），否则每个外层文档触发一次 COLLSCAN，复杂度 O(N×M)。
  • $expr 负责把 let 变量与关联侧字段绑定；不等值条件（范围、数组包含）只有 pipeline 形式能写。
  • 只需「是否存在」时，用 pipeline + $limit: 1 + $project: { _id: 1 } 代替全量拉取。

$addFields 与 $replaceRoot：重塑文档

$addFields = SQL 的派生列；$replaceRoot（别名 $replaceWith）常作为管道收尾，把结果整理成下游直接可用的结构。

$bucket 与 $facet：分桶与多路统计

$facet 一次扫描产出多份报表，是仪表盘神器；$bucket 按边界分桶（$bucketAuto 自动均分）。注意 $facet 各子管道无法走索引且共享 100MB 内存上限，超大集合改用预聚合。

四、模式设计：内嵌还是引用

判断口诀：

场景 选择
1:1 或 1:少量（生命周期一致） 内嵌
1:多且子文档无限增长（评论、日志） 引用（或「内嵌最近 N 条 + 冷数据独立集合」）
多对多 引用
内嵌文档 16MB 上限 逼近上限必须拆

常见增强：$lookup 慢的高频关联可冗余一份 userName 到订单文档（写入时双写），用读时免 JOIN 换写时多一步——文档模型下的「反范式」是常规操作。

五、四个常用 Schema 设计模式

官方 Schema 设计模式清单里，业务系统最常用这四个：

1. Computed Pattern（预计算）

读多写少 + 重复计算贵时，把结果写时算好存下来：商品文档冗余 avgRating、reviewCount，每次评价写入时 $inc / $avg 重算，读详情页零计算。代价：写多一步、口径变更要回填历史。

2. Bucket Pattern（分桶）

时序数据（IoT 指标、行情、访问日志）一条一个文档会爆索引与文档数——按时间桶聚合：

收益：索引条目下降几个数量级，且「查某时段」的访问模式天然匹配桶边界。

3. Subset Pattern（子集）

文档太胖导致工作集（working set）放不进内存？把高频字段留在主文档（文章列表只需标题/摘要/作者），低频大块拆到独立集合（正文、历史版本）——列表查询不再拖着 KB 级正文跑。

4. Attribute Pattern（属性模式）

各品类属性差异大（手机有「屏幕尺寸」、衣服有「尺码」），为每种属性建索引不现实——统一存成键值数组：

一、核心一句话

MP 分页本质：MyBatis 拦截器 + 自动改写 SQL

    分页参数载体，存：当前页、每页条数、总记录数、总页数、分页数据。

  1. 进入 Mapper 方法前
    PaginationInnerInterceptor 拦截到 selectPage 查询。
  2. 判断是否是分页查询
    检测方法参数里有没有 IPage/Page 对象，有就走分页逻辑。
  3. 自动生成 COUNT 语句
    原SQL：select id,name from user
    自动生成：select count(*) from user → 查询总记录数
  4. 改写原SQL 加 LIMIT
    原SQL 被改写为：

  6. 封装分页信息
    把总条数、当前页、每页大小、总页数、数据列表 全部塞进 IPage 返回。

四、为什么不用自己写 limit、不用自己写 count？

MP 拦截器动态解析 SQL、动态拼接 limit、动态生成 count，完全无侵入。

五、分页两个重要特性

1. 分页合理化 reasonable=true

  • 输入页码 <=0 自动变成第 1 页

2. 溢出总页数后是否查最后一页

PaginationInnerInterceptor 可配置，防止页码乱输报错。

六、常见坑（原理衍生出来的）

  1. 没配置 PaginationInnerInterceptor → 分页无效，查全部数据
  2. 只有 Mapper 层用 Page 参数才生效，Service 自己写 list 不分页
  3. 自定义 XML SQL 也能自动分页，MP 照样拦截加 limit、count
  4. 多表联查、复杂 SQL 也支持，拦截器会解析原有 SQL 结构

七、极简总结

MP 分页 = 拦截器拦截SQL → 自动查总数 → 自动拼接LIMIT → 封装分页结果

不用手写 count、不用手写 limit，全靠拦截器动态代理实现。

生命周期与绑定原理

Maven 核心是三套独立生命周期，每套由若干**阶段（phase）**组成，按序执行：

生命周期 关键阶段 用途
clean clean 清理 target/
default validate → compile → test → package → verify → install → deploy 编译到发布全流程
site site → site-deploy 生成项目站点文档

绑定原理：命令行输入的是阶段，真正干活的是绑定在阶段上的插件目标（goal）——compile 绑定 maven-compiler-plugin:compile，test 绑定 maven-surefire-plugin:test。执行 mvn package 时会从 validate 起按序跑完到 package 为止的所有阶段；<executions> 可把额外 goal 显式挂到任意阶段（如代码生成插件绑 generate-sources）。clean 属另一套生命周期，所以才有 mvn clean install 组合写法。

依赖调解规则（Dependency Mediation）

同一构件出现多个版本时，Maven 按固定规则选其一，与声明顺序无关：

  1. 就近原则：依赖树中路径最短的版本胜出。A→B→X-1.0 与 A→X-2.0，X-2.0 胜。
  2. 第一声明原则：路径等长时，POM 中先声明的一方胜出。
  3. <dependencyManagement> 锁定：父 POM 显式锁版本后以其为准，优先级最高。

排查套路：dependency:tree 找两个版本来源 → 定保留方 → 用 <exclusions> 排除多余传递依赖，或在 <dependencyManagement> 统一锁版本。

Profile 用于「同一套代码，不同环境不同构建」——开发/测试/生产的配置、JDK 级别、依赖均可切换：

多模块：继承与聚合

大型项目用一个父 POM承担两个角色：

  • 继承：子模块经 <parent> 继承父的 groupId、version、dependencyManagement、插件配置，消除重复。
  • 聚合：父的 <modules> 列出子模块，根目录 mvn install 一次构建全部（reactor 自动按依赖排序）。

八、常见坑 FAQ

坑 现象 处理
check --fix 与 format 顺序颠倒 先格式化再修 lint，格式又被破坏 固定顺序：先 ruff check --fix，后 ruff format
与 Black 双开 两个 formatter 互相打架 二选一；迁移期可用 ruff format（与 Black 风格几乎一致）
误开全部规则 select = ["ALL"] 后几百条警告淹没输出 按需启用，逐步收紧；老项目先 E,F,I 起步
target-version 与解释器不一致 UP 规则把代码改成运行环境不支持的语法 与 requires-python 对齐，如 py313
规则升级引入新告警 uv lock --upgrade-package ruff 后 CI 突然失败 升级前看 changelog；临时用 ignore 豁免再排期清理
.ruffignore 与 exclude 混用 配置分散排查困难 优先用 [tool.ruff] exclude，团队只维护一处

九、最佳实践清单

  1. 版本锁进 uv.lock：uv add --dev ruff + uv run ruff，本地/CI/编辑器同版本。
  2. 配置只写 pyproject.toml，不再维护 setup.cfg / .flake8 多处配置。
  3. 提交前 check --fix + format，并接入 pre-commit（见第五章）。
  4. CI 用 format --check 只校验，避免流水线里产生未提交 diff。
  5. 与 Pyright 分工：Ruff 管风格，Pyright 管类型，避免 ANN 重叠。
  6. 渐进收紧：老项目先小规则集跑绿，再逐步加 UP、B、SIM。
