第三章：MyBatis-Plus 快速上手与分页原理

概念基础

MyBatis-Plus（简称 MP） 是 MyBatis 的增强工具，定位是「只做增强不做改变」：

  1. 通用 CRUD：Mapper 继承 BaseMapper 即可获得 selectById、insert、update 等单表增删改查能力，免写 XML。
  2. 插件体系：通过 MybatisPlusInterceptor 注册分页、乐观锁、防全表更新等内部拦截器，按需装配。
  3. 分页零侵入：内置 PaginationInnerInterceptor，基于 MyBatis 拦截器自动生成 count 语句、改写 SQL 拼接 LIMIT，业务代码只传 Page 参数。
  4. 代码生成：配合 IDEA 插件（如 MyBatisX-Generator）可从数据库表直接生成 Entity / Mapper / Service 代码。
  5. Spring Boot 集成：提供 mybatis-plus-spring-boot*-starter 起步依赖，配好 mapper-locations 与驼峰映射即可使用。

MyBatis-Plus 分页原理

一、核心一句话

MP 分页本质：MyBatis 拦截器 + 自动改写 SQL

  1. 你传入 Page<>(当前页,每页条数)
  2. MP 分页拦截器拦截 Mapper 查询方法
  3. 自动帮你生成 count 总数SQL + 拼接 limit 分页SQL
  4. 执行两条 SQL：查总数 → 查当前页数据
  5. 把总数、页码、数据封装到 IPage 返回

二、关键核心组件

  1. MybatisPlusInterceptor
    MP 核心插件容器，所有插件（分页、防全表更新、乐观锁）都往里注册。
  2. PaginationInnerInterceptor
    MP 真正的分页拦截器，核心逻辑全在这。
  3. Page / IPage
    分页参数载体，存：当前页、每页条数、总记录数、总页数、分页数据。

三、完整执行流程（一步一步走）

1. 配置分页拦截器（必须配置，否则分页无效）

2. 业务代码使用

3. 底层执行步骤

  1. 进入 Mapper 方法前
    PaginationInnerInterceptor 拦截到 selectPage 查询。
  2. 判断是否是分页查询
    检测方法参数里有没有 IPage/Page 对象，有就走分页逻辑。
  3. 自动生成 COUNT 语句
    原SQL：select id,name from user
    自动生成：select count(*) from user → 查询总记录数
  4. 改写原SQL 加 LIMIT
    原SQL 被改写为：
    select id,name from user limit 0,10
  5. 执行两条 SQL
    • 第一条：查总条数
    • 第二条：查分页数据
  6. 封装分页信息
    把总条数、当前页、每页大小、总页数、数据列表 全部塞进 IPage 返回。

四、为什么不用自己写 limit、不用自己写 count？

MP 拦截器动态解析 SQL、动态拼接 limit、动态生成 count，完全无侵入。

五、分页两个重要特性

1. 分页合理化 reasonable=true

  • 输入页码 <=0 自动变成第 1 页
  • 输入页码 大于总页数 自动返回最后一页

2. 溢出总页数后是否查最后一页

PaginationInnerInterceptor 可配置，防止页码乱输报错。

六、常见坑（原理衍生出来的）

  1. 没配置 PaginationInnerInterceptor → 分页无效，查全部数据
  2. 只有 Mapper 层用 Page 参数才生效，Service 自己写 list 不分页
  3. 自定义 XML SQL 也能自动分页，MP 照样拦截加 limit、count
  4. 多表联查、复杂 SQL 也支持，拦截器会解析原有 SQL 结构

七、极简总结

MP 分页 = 拦截器拦截SQL → 自动查总数 → 自动拼接LIMIT → 封装分页结果

不用手写 count、不用手写 limit，全靠拦截器动态代理实现。

常用内部拦截器

MybatisPlusInterceptor 是插件容器，除分页外常用：

拦截器 作用 关键配置
PaginationInnerInterceptor 物理分页 DbType、overflow、maxLimit
OptimisticLockerInnerInterceptor 乐观锁（@Version） 实体加 @Version 字段即可
TenantLineInnerInterceptor 多租户（自动拼 tenant_id） 实现 TenantLineHandler
BlockAttackInnerInterceptor 防全表 update/delete 无 where 的写操作直接阻断
IllegalSQLInnerInterceptor 拦截低效 SQL（如全表扫描） 索引规范审计，建议仅 dev 开启

顺序敏感：TenantLineInnerInterceptor 必须先于分页注册，否则 count SQL 可能漏掉租户条件导致总数失真；BlockAttackInnerInterceptor 建议生产必开，一行误写的 update 没带 where 就能挡住删库事故。

删除变更新（deleted = 1），查询自动过滤：

效果：removeById(id) → UPDATE t SET deleted=1 WHERE id=? AND deleted=0；selectList 自动追加 AND deleted=0。注意自定义 XML SQL 不受全局过滤，需自己写条件；唯一索引也要把 deleted 纳入，否则逻辑删除后同名记录无法再次插入。

字段自动填充

创建/更新时间不再手写赋值：

只对 MP 提供的 insert/update 方法生效；XML 手写 SQL 需自行赋值。需要填充「操作人」时，在 handler 里从登录上下文（如 SecurityContextHolder）取当前用户 ID 填入。

乐观锁实战

更新时自动改写：UPDATE goods SET stock=?, version=version+1 WHERE id=? AND version=?，版本不匹配返回 0 行——配合「更新行数为 0 即重试或报错」即可防并发覆盖。扣库存场景更常见的写法是数据库层原子扣减：

stock >= #{qty} 条件让超卖在数据库层被物理阻止，比先查再改安全得多；乐观锁更适合「订单状态流转」这类读多写少、冲突概率低的字段。

Wrapper 条件构造器

Lambda 写法在字段重命名/重构时由编译器兜底，比字符串列名安全；动态条件用 eq(ObjectUtils.isNotEmpty(x), ...) 的重载形式，条件为 false 时自动跳过该片段。

第二章：Gradle 构建工具：安装、配置与常用命令

概念基础

Gradle 是基于 JVM 的现代构建工具，广泛用于 Java / Kotlin / Android 项目：

  1. 脚本即代码：构建脚本用 Groovy DSL（build.gradle）或 Kotlin DSL（build.gradle.kts）编写，比 XML 更简洁、可编程。
  2. 复用 Maven 仓库体系：依赖坐标与 Maven Central、google() 等仓库完全兼容，可配置阿里云镜像加速下载。
  3. 增量构建与缓存：通过任务图、增量构建与构建缓存避免重复工作，大型项目构建明显更快。
  4. Gradle Wrapper：项目内提交 gradlew 即可固定团队 Gradle 版本，新成员免手工安装，保证构建环境一致。
  5. 与 Maven 的取舍：Maven 约定优先、上手简单；Gradle 更灵活、性能更好，但脚本自由度高，团队需要统一规范。

任务图与增量构建

Gradle 构建的本质是任务有向无环图（DAG）：

  • 配置阶段：解析脚本，根据 dependsOn/finalizedBy 构建任务图；执行阶段只运行图中需要的任务。
  • 增量构建：任务声明 @InputFiles/@OutputDir 等输入输出；输入输出与上次一致（哈希比对）则任务标记 UP-TO-DATE 直接跳过。Java 编译还支持增量编译——只重编受影响的类。
  • 构建缓存：任务输出按哈希存入缓存（默认本地 ~/.gradle/caches），换个分支、换台机器也能命中；CI 上开启可省大量重复编译。

Gradle vs Maven 的本质差异：Maven 是「固定生命周期 + 阶段绑定插件」，Gradle 是「自由任务图 + 输入输出声明」。前者约定强，后者灵活且因增量/缓存机制在大型项目上快得多。

  1. 构建自动化：一条 mvn 命令即可完成编译、测试、打包、安装全流程，无需手工调用 javac、维护 classpath。

生命周期与绑定原理

Maven 核心是三套独立生命周期，每套由若干**阶段（phase）**组成，按序执行：

生命周期 关键阶段 用途
clean clean 清理 target/
default validate → compile → test → package → verify → install → deploy 编译到发布全流程
site site → site-deploy 生成项目站点文档

绑定原理：命令行输入的是阶段，真正干活的是绑定在阶段上的插件目标（goal）——compile 绑定 maven-compiler-plugin:compile，test 绑定 maven-surefire-plugin:test。执行 mvn package 时会从 validate 起按序跑完到 package 为止的所有阶段；<executions> 可把额外 goal 显式挂到任意阶段（如代码生成插件绑 generate-sources）。clean 属另一套生命周期，所以才有 mvn clean install 组合写法。

依赖调解规则（Dependency Mediation）

同一构件出现多个版本时，Maven 按固定规则选其一，与声明顺序无关：

  1. 就近原则：依赖树中路径最短的版本胜出。A→B→X-1.0 与 A→X-2.0，X-2.0 胜。
  2. 第一声明原则：路径等长时，POM 中先声明的一方胜出。
  3. <dependencyManagement> 锁定：父 POM 显式锁版本后以其为准，优先级最高。

排查套路：dependency:tree 找两个版本来源 → 定保留方 → 用 <exclusions> 排除多余传递依赖，或在 <dependencyManagement> 统一锁版本。

Profile 用于「同一套代码，不同环境不同构建」——开发/测试/生产的配置、JDK 级别、依赖均可切换：

多模块：继承与聚合

大型项目用一个父 POM承担两个角色：

  • 继承：子模块经 <parent> 继承父的 groupId、version、dependencyManagement、插件配置，消除重复。
  • 聚合：父的 <modules> 列出子模块，根目录 mvn install 一次构建全部（reactor 自动按依赖排序）。

概念基础

  1. 为什么需要版本管理：Node 大版本迭代快，LTS 与 Current 并行发布，不同项目常依赖不同 Node 版本——全局只装一个版本很快就捉襟见肘。
  2. nvm 的解决思路：nvm（Node Version Manager）从源码或官方预编译包拉取 Node，把各版本隔离安装在用户目录 $HOME/.nvm 下，通过 nvm use 切换当前终端使用的 node / npm，各版本互不干扰。
  3. 与全局安装的区别：不把某个 Node 强行装进系统目录，无需 root 权限；切换版本只影响当前 Shell（及子进程），其他终端不受牵连。
  4. 按项目锁定版本：项目根目录放一个 .nvmrc 写明版本号，进入目录执行 nvm use 即可对齐环境，避免「在我机器上能跑」的版本漂移。
  5. 平台边界：经典 nvm-sh 只支持 macOS / Linux；Windows 原生需改用 nvm-windows 或在 WSL 中使用 nvm-sh，详见文末说明。
