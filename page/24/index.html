第三章：Bash 脚本编程

概念基础

  1. 脚本 = 运维自动化的最小单元：把第一章的命令按逻辑串起来（变量、分支、循环、函数），批量操作从「人肉重复」变成「一键执行」。
  2. 退出码是通用语言：每个命令都返回 0~255，0 表示成功、非 0 表示失败；&&/||、if、set -e 全部建立在退出码之上。
  3. 文本流是通用接口：脚本的核心工作是「读文本 → 加工 → 写文本」，与 第四章：文本处理三剑客与管道 的 grep/sed/awk 天然配套。
  4. 引号规则决定一切：双引号允许变量展开、单引号完全字面量、不加引号会被空格分词——空格路径事故九成源于此。
  5. 防呆三件套：set -euo pipefail（出错即停、未定义变量报错、管道错误不被吞）+ trap 清理 + ShellCheck 静态检查，是脚本进工程的前提。

第二章：Windows 上 WSL（Rocky Linux）与 Docker Desktop

概念基础

  1. WSL 是什么：WSL（Windows Subsystem for Linux）让 Windows 直接运行真正的 Linux 发行版，无需双系统或整机虚拟机，一条命令即可进出 Linux 环境。
  2. WSL2 的意义：WSL2 基于轻量级虚拟机，系统调用兼容性完整，是 Docker Desktop 官方推荐的运行后端——没有 WSL2 就没有流畅的容器体验。
  3. 为什么选 Rocky Linux：与 RHEL 同源的企业级发行版，dnf 生态与生产服务器一致，作为本地演练环境最贴近真实运维。
  4. Docker Desktop 的角色：提供图形化引擎管理（更新、证书、镜像加速），通过 WSL integration 把 docker CLI 注入各发行版，Rocky 内无需再装 dockerd。
  5. 适用场景：在 Windows 机器上做 Linux 运维演练与容器开发；代码放在发行版内的 Linux 文件系统中可获得最佳 I/O 性能。

环境与版本说明

  1. 操作系统：Windows 10（建议 22H2 及以后）或 Windows 11。
  2. 体系结构：下载 Rocky Linux 镜像时选 x86_64 或 aarch64，与 Windows、Docker Desktop 安装包一致。
  3. WSL：使用 WSL2；Docker Desktop 的 WSL 2 后端依赖此版本。
  4. Rocky Linux：官方 .wsl 镜像（推荐）或 wsl --import。
  5. 权威文档：
    • Rocky Linux（本文默认 10，文档内可切换版本）：Import Rocky Linux to WSL or WSL2
    • Microsoft：安装 WSL
    • Docker：Docker Desktop on Windows、WSL 与 Docker Desktop

  • builder.gc：为 BuildKit 构建缓存开启自动回收，defaultKeepStorage 限制默认保留量（示例 20GB），避免构建缓存占满磁盘。

修改后点击 Apply & restart；再在 Rocky 或 PowerShell 中执行 docker info，在输出里确认 Registry Mirrors 已包含上述地址。

6. 文件与性能建议

  • 项目代码放在 WSL 发行版自己的 Linux 文件系统里（例如在 wsl -d Rocky-10 里用 ~/project，即 /home/你的用户/project），不要放在 /mnt/c/... 下做大量编译与 Docker 构建，可减少跨系统 I/O 延迟。

  • Docker Desktop 的 Settings → Resources 可调 CPU、内存、磁盘镜像上限，与 Rocky 其它进程共用本机资源，按机器配置酌情调大。

第二章：Docker 部署 Kafka 实践

概念基础

  1. KRaft 让单进程成为可能：旧版 Kafka 需要 ZooKeeper + Kafka 两个进程；KRaft 模式下一个容器同时扮演 controller + broker，单机一条命令即可起集群（本章单容器示例的核心）。
  2. 监听器与 advertised.listeners 是第一坑：Kafka 会把 advertised.listeners 里的地址返回给客户端——容器内监听 0.0.0.0 没用，客户端拿到的是这个「广告地址」。本机访问写 127.0.0.1、Compose 内服务访问写服务名、跨网段要双监听，本章三种部署形态的差异全在这一个参数上。
  3. 数据目录与 page cache：数据在 /bitnami/kafka（Bitnami 镜像），必须挂卷；Kafka 依赖磁盘顺序写与 page cache，内存不宜压得过低。
  4. 边界要清楚：单容器 / Compose / 单副本 Deployment 都面向开发验证；生产多 Broker 应使用 Strimzi 等 Operator 或 StatefulSet，不要把单实例 Deployment 当集群扩。

第二章：Docker 部署 MySQL 实践

概念基础

容器化是「把 MySQL 实例连同版本、配置、账号一次性描述清楚」的部署方式：

  1. 环境一致、随起随删：一条命令拉起带指定版本、字符集、账号密码的实例，不污染宿主机；卸载即删容器，重装零成本——这正是第一章建好表结构之后最需要的环境。
  2. 数据与容器分离：容器可随时销毁，数据必须落在卷（volume）；命名卷 mysql-data 持久化 /var/lib/mysql，删容器不丢数据，但删卷等于删库，这是容器数据库的第一铁律。

第一章：ZooKeeper 核心概念与 CLI 实战

概念基础

  1. 分布式协调服务：ZooKeeper 为分布式系统提供配置管理、命名服务、分布式锁与选主等基础原语，是 Kafka、Hadoop 等大数据组件的经典协调底座。

  3. 强一致靠多数派：基于 ZAB 协议，写请求需过半节点确认；集群必须奇数个节点（3 节点容忍 1 故障，5 节点容忍 2）。

三、Watcher：一次性通知

关键语义：

  • Watcher 是一次性的——触发一次即失效，客户端 SDK 需重新注册（Curator 的 Cache 帮你做了）。
  • 通知的是**「事件发生了」，不带新数据；收到通知后要自己再读一次**，避免丢增量。
  • 会话断开期间的事件不会补发，重连后应主动全量拉取对齐。

四、经典配方：锁与选主

1. 分布式锁（临时顺序节点）

只监听前一个节点而非所有节点（羊群效应规避），通知风暴从 N 降到 1。

2. 选主（Master Election）

与锁同理：/election/node- 最小序号为 leader；leader 会话断开（进程崩溃）后临时节点消失，次小序号自动上位——故障感知由会话心跳完成，无需额外探活。

生产不手写这些协议：Java 用 Apache Curator（封装好 InterProcessMutex、LeaderLatch），Kafka 2.8+ 更是用 KRaft 替代了 ZK——理解原理是为了看懂你正在用的库。

强一致的少量关键状态 最终一致可接受的大流量场景（用 MQ/Redis 更合适）

会话参数：tickTime（心跳单位）、sessionTimeout = 2~20 × tickTime；网络抖动超过 sessionTimeout 临时节点即消失——服务注册场景要把它与业务健康检查区分开。

第七章：OpenSSL 密钥派生与随机数：PBKDF2、rand 与推荐用法

概念基础

  1. 随机数是密码学之根：密钥、IV/nonce、salt、session token、HMAC secret 全部来自 CSPRNG（openssl rand 内部即此）——随机性不足，再强的算法也是空谈。
  2. 口令 ≠ 密钥：人类口令熵低、可猜测、常重复，直接当 AES 密钥会被暴力破解；必须经 KDF（密钥派生函数） 处理。
  3. KDF 的两大武器：salt（防彩虹表与预计算）+ 高迭代次数（把每次猜测的成本拉高千万倍），PBKDF2 建议迭代 ≥ 600000。

第六章：OpenSSL 数字签名与 HMAC：完整性、身份与推荐用法

概念基础

  1. 数字签名 = 私钥签名 + 公钥验证：一次性保证完整性（内容未被篡改）、身份认证（签名者身份可信）与不可否认（只有私钥持有者能签出）。
  2. 标准流程：先对消息做哈希（SHA-256，见第三章），再用私钥对摘要签名；验证方用公钥复算比对——这也是「对大数据直接 RSA 签名」是错误做法的原因。
  3. HMAC 是对称认证：双方共享同一 secret，用 HMAC-SHA256 计算带密钥的摘要；快、实现简单，但双方都能生成，因此不可否认。
  4. 怎么选：公开分发场景（软件发布、证书、JWT）→ 数字签名；双方已有共享密钥的场景（API / Webhook 鉴权）→ HMAC。
