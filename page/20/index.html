踩坑点：

  1. @Value 忘写 :false 兜底——新环境配置缺失直接启动失败，整条流水线卡住。

1. 概念说明

Spring Boot 解决什么：Spring 原生配置繁琐（XML、Bean 装配），Spring Boot 用约定优于配置 + 自动配置大幅降低门槛，内置 Tomcat 独立运行，一个 main 方法启动应用。

核心机制：

  • Starter：一组依赖的集合（如 spring-boot-starter-web = Web + Tomcat + Jackson），引入即用。
  • 自动配置（Auto-Configuration）：类路径有某依赖（如 Redis 客户端）时，@ConditionalOnClass 生效，自动装配默认 Bean（如 RedisTemplate）。
  • spring.factories / AutoConfiguration.imports：自动配置类的注册清单。
  • 外部化配置：application.yml 优先级高于默认值，可被环境变量/启动参数覆盖。

10. 典型案例：启动优化（30 秒 → 8 秒）

问题背景：一个聚合服务引入了 Redis、ES、RabbitMQ、Kafka 等十几个 starter，冷启动 30 秒。K8s 滚动更新时新 Pod 迟迟不就绪，发布窗口拖长，偶发健康检查超时被 kill 陷入重启循环。

方案（先测量，再逐项优化）：

优化项 做法 收益
定位耗时 Actuator startup 端点 + ApplicationStartup 采样 找到 3 个慢 Bean
全局懒加载 spring.main.lazy-initialization=true 启动期不初始化 Bean
排除无用自动配置 exclude 掉用不到的 DataSourceAutoConfiguration 等 少扫描少装配
探针分离 liveness 与 readiness 分开 先 live 后 ready，不被误杀
预热 就绪后主动打一次核心接口 首请求不慢

关键配置与代码：

踩坑点：

  1. 全局懒加载后配置错误被延迟暴露：数据源密码错在启动时不再报错，直到第一个请求才炸——保留关键 Bean 用 @Lazy(false) 强制急切初始化。
  2. exclude 排除了还在用的自动配置，启动是快了，运行时直接 NoSuchBeanDefinitionException——排除前先确认 Bean 没人用。
  3. 没做基线测量就开始”优化”，改完发现瓶颈在别处——先跑 startup 端点拿到耗时分布再动手。
  4. readiness 探针在 Bean 初始化完成前就开始探测，Pod 被判定就绪但请求打进来还是懒加载状态——预热放在 readiness 放行之前。

11. 常见误用与陷阱

坑 现象/后果 解法
@Transactional 同类自调用 内部 this 调用不走代理，事务静默失效不回滚 拆到另一个 Bean，或注入自身代理（AopContext.currentProxy）
@Scheduled 默认单线程调度 一个任务卡住，同应用所有定时任务全部停摆 自定义 ThreadPoolTaskScheduler，size 按任务数规划
配置占位符没兜底 新环境少一个配置项就启动失败 ${key:default} 给安全默认值
@Value 标在 static 字段 注入不生效，值恒为 null 改实例字段，或统一用 @ConfigurationProperties
@Transactional 方法里 catch 吞异常 异常没抛出，事务照常提交，数据半更新 重抛异常，或确认 rollbackFor 覆盖受检异常
@Async 用默认执行器 SimpleAsyncTaskExecutor 每次新建线程，无上限 自定义 ThreadPoolTaskExecutor 并标 @EnableAsync
循环依赖靠乱加 @Lazy 硬解 掩盖职责不清的设计问题，初始化顺序不可控 重构拆分 Bean 职责，用事件/中间类解耦

11. 典型案例：下单接口的幂等令牌设计

问题背景：支付页”提交订单”按钮用户连点了 3 次（前端防抖在弱网下失效），网关重试又放大了流量，同一笔订单在数据库里产生 3 条记录、扣了 3 次库存。事后统计该问题月均出现 200+ 笔，全部靠人工客服退单。

方案：前端提交前先到后端领一个幂等令牌（token），提交时带上 token；后端用 Redis 原子操作校验并消费，同一 token 第二次提交直接拒绝：

1. 概念说明（导论）

Redis 是基于内存的高性能键值数据库：单线程（6.x 前）事件循环 + IO 多路复用，吞吐可达 10 万+ QPS。定位是缓存与中间件，不是主存储（数据可丢失场景除外）。

Redis 8 新增：Redis 8.0（2025 年发布）带来原生向量检索（Redis Vector Sets）、增强持久化等能力，是当前主推版本。

单机 Redis 有两大天花板：可用性（宕机全挂）和容量/吞吐（单节点上限）。进阶要解决：

  • 主从复制：数据冗余 + 读写分离（解决可用性基础）。
  • 哨兵（Sentinel）：监控主节点，宕机自动选举新主（解决自动故障转移）。
  • 集群（Cluster）：数据分片到多主多从（解决容量与吞吐）。
  • Lua 脚本：把多条命令打包原子执行（解决”检查-执行”竞态）。

1. 概念说明

Nginx 是高性能 HTTP 服务器与反向代理，事件驱动 + 异步非阻塞模型，单机可支撑数万并发连接。三大用途：

用途 说明
静态文件服务 HTML/CSS/JS/图片，QPS 极高

负载均衡 多后端实例按策略分发

正向代理 vs 反向代理：

  • 正向代理：代理客户端（翻墙、缓存），客户端知道目标。
  • 反向代理：代理服务器（用户访问 Nginx，Nginx 转发后端），客户端无感知。

进程模型：一个 master（管理）+ N 个 worker（处理请求）。nginx -s reload 平滑重载配置，不中断服务。

问题背景：App 推送网关接入 50 万长连接，运行一周后告警频发：堆内存持续走高、连接数只涨不跌。排查发现运营商 NAT 空闲表项约 5 分钟回收，大量 TCP 连接已「半开」——服务端仍显示 ESTABLISHED，客户端早已失联，僵尸连接持有 ByteBuf 与 Session 不释放。

踩坑点：服务端读空闲阈值必须 ≥ 客户端心跳间隔的 2 倍，否则一次网络抖动就误杀正常连接；重连逻辑不要在 channelInactive 里 Thread.sleep()——那是 EventLoop 线程，会卡住同组所有 Channel；心跳走独立轻量类型，别进业务解码链路。
