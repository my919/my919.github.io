第七章：SpringBoot 全局枚举与字典 API

概念基础

  1. 枚举即字典：状态、类型等有限取值用枚举表达，数据库只存数字 code，避免魔法数字散落各处。
  2. 统一 JSON 契约：JSON 出入参为 { "code", "desc" }，前端不再解析裸数字，展示文案与 desc 自动一致。
  3. 统一字典入口：前端下拉字典统一走 /api/enums；新增枚举只改注册表，Jackson 序列化与字典 API 自动同步。
  4. 两端协同：存储端由 MyBatis-Flex @EnumValue 保证入库为 code；序列化端由 Jackson 模块按 BaseEnum 注册表统一处理。
  5. 容错约定：反序列化支持数字、字符串、常量名、{code,desc} 多种入参，非法枚举值由全局异常处理器返回 400。

第五章：SpringBoot 集成 MyBatis-Flex 与多数据源

概念基础

  1. ORM 增强：MyBatis-Flex 是 MyBatis 之上的轻量 ORM，提供 IService / ServiceImpl 与分页，低侵入、强调查询性能与 APT 编译期能力。
  2. 多数据源路由：dynamic-datasource 在运行时按 @DS 注解切换数据源（本项目：MySQL + PostgreSQL），与 ORM 选型解耦。
  3. 选型参照：与 MyBatis-Plus 分层模型相近（BaseMapper → IService → ServiceImpl），迁移成本低；差异主要在条件构造、APT 表定义与 Spring Boot 4 starter 支持（详见下文对比）。
  4. 连接池底座：数据源底层为 Hikari 池，最大连接数、最小空闲等参数在 dynamic-datasource 配置下统一管理。
  5. 通用 @DS 与事务边界见 第六章：Java 动态数据源：@DS 切换与事务边界；Flex API 见 第七章：MyBatis-Flex 入门与代码生成；连接池见 第十三章：数据库连接池：HikariCP与Druid对比与落地。

MyBatis-Flex 与 MyBatis-Plus 对比

二者都是在 MyBatis 之上的增强框架，分层模型相近（BaseMapper → IService → ServiceImpl），CRUD 与分页 API 名称大多一致，迁移成本较低。主要差异如下。

维度 MyBatis-Flex MyBatis-Plus
定位 轻量、低侵入，强调查询性能与 APT 编译期能力 生态成熟、文档与社区体量大
核心包 com.mybatisflex com.baomidou.mybatisplus
Mapper BaseMapper<T> BaseMapper<T>
Service IService / ServiceImpl IService / ServiceImpl
条件构造 QueryWrapper、QueryChain（链式） QueryWrapper、LambdaQueryWrapper
分页 Page<T>（Page.of(pageNumber, pageSize)） Page<T>（new Page<>(current, size)）
实体表映射 @Table、APT 生成 *TableDef 类型安全列名 @TableName、@TableField 等
代码生成 MyBatis-Flex Codegen MyBatis-Plus Generator
多数据源 常与 dynamic-datasource（Baomidou）搭配，注解 @DS 同上，同一套 dynamic-datasource
Spring Boot 4 mybatis-flex-spring-boot4-starter（本项目使用） 需关注对应 starter 版本是否已支持 Boot 4

查询写法示例（语义等价）：

Flex 通过 APT 生成 SysUserTableDef，列名在编译期校验；Plus 更常用 Lambda 方法引用，运行时反射解析字段。

选型参考（与本模板相关）：

  • 已熟悉 Plus 且团队无迁移诉求：继续用 Plus 即可，多数据源仍可用 dynamic-datasource。
  • 希望依赖更轻、查询链路与 APT 表定义、或需要 Spring Boot 4 官方 starter：选 Flex（本仓库默认方案）。
  • 二者均不绑定特定数据库；本项目的 MySQL + PostgreSQL 切换由 dynamic-datasource 负责，与选 Flex 还是 Plus 无关。

第四章：SpringBoot 集成 Redis 与缓存

概念基础

缓存把热点数据放进内存数据库，用空间换时间，降低数据库压力、缩短响应时间：

  1. 三种接入方式：本项目集成 Spring Data Redis（StringRedisTemplate）、Redisson（分布式对象、Bucket 等）、Spring Cache（@Cacheable，底层为 Redis），按场景选用。
  2. 统一连接层：三者最终都经 Lettuce 连接访问同一个 Redis（见架构图），连接与超时配置集中管理。
  3. TTL 必设：缓存写入务必带过期时间（如探针 120 秒），防止脏数据长期滞留与内存膨胀。
  4. 业务耦合点：防重、幂等、缓存探针均依赖 Redis——防重用 SET NX + TTL，幂等缓存首次成功的 Result JSON。
  5. 测试隔离：单测排除 Redis 自动配置、缓存切换 simple 并注入 Mock Bean，保证无 Redis 也能跑通测试。

第三章：SpringBoot 集成 RustFS 对象存储

概念基础

对象存储以「Bucket + objectKey」平铺组织文件，通过 HTTP API 读写，适合图片、附件等非结构化数据：

  1. S3 兼容协议：RustFS 提供 S3 兼容 API，凡支持 AWS S3 协议的客户端均可直接对接，迁移成本低。
  2. SDK 与访问风格：本工程使用 AWS SDK for Java v2 访问，并开启 forcePathStyle: true（路径风格访问，兼容 MinIO/RustFS 等自建服务）。
  3. 预签名 URL：服务端签发带过期时间的临时链接（本项目 15 分钟），客户端直连存储完成下载，应用不代理文件流量。
  4. 开关与外部化：app.rustfs.oss.enabled 控制装配（@ConditionalOnProperty），endpoint 与密钥经环境变量注入，生产勿写入仓库。
  5. 测试友好：单元测试默认关闭 OSS，真实环境联调用 RUSTFS_LIVE_TEST=true 单独触发。

前置条件

  1. 已部署 RustFS 服务（示例：http://192.168.1.22:30009）
  2. 在控制台创建 Access Key：http://<host>:<port>/rustfs/console/access-keys
  3. 创建或确认 Bucket 名称

注意：SDK 的 endpoint 填 S3 API 根地址，不要带 /rustfs/console/... 路径。

常见问题

KMS encryption service is not initialized

RustFS 服务端 Bucket 默认启用了 KMS/SSE，但 KMS 未初始化。在 RustFS 控制台关闭该 Bucket 的默认加密，或完成 KMS 配置。属于服务端问题，非应用代码错误。

启用开关不生效

确认 app.rustfs.oss.enabled=true，且未在测试 Profile 中被覆盖为 false。

404 / 签名错误

  • 检查 endpoint 是否为 API 根路径
  • 确认 path-style: true
  • 核对 Access Key / Secret 与 Bucket 名

第二章：SpringBoot 多环境配置：Profile 激活与优先级

发表于 2026-05-16 更新于 2026-09-01 分类于 SpringBoot 本文字数： 927 阅读时长 ≈ 3 分钟

第二章：SpringBoot 多环境配置：Profile 激活与优先级

概念基础

多环境配置让同一份代码在开发、测试、生产之间只切换配置、不改代码：

  1. Profile 机制：Spring 用 Profile 在 dev / test / prod 之间切换配置；本仓库（springboot）以 application.yaml 承载公共配置，各环境文件只写差异项；相同 key 时环境文件覆盖公共配置。
  2. 激活方式多样：配置文件 spring.profiles.active、环境变量 SPRING_PROFILES_ACTIVE、启动参数 --spring.profiles.active=prod，本项目默认 dev。
  3. 职责划分：端口、应用名、框架级默认值放公共；数据库/Redis 地址与密码、日志级别、Swagger 开关放环境。
  4. 敏感信息外部化：密码经环境变量注入，生产禁止提交 Git；更大规模可接 Nacos 配置中心（共享 dataId + 环境 dataId，后者覆盖前者）。
  5. 测试隔离：src/test/resources/application.yaml 独立于业务 Profile，用 H2 内存库与 Mock 中间件保证 gradlew test 稳定可重复。

微服务多模块 + Nacos spring.config.import 见 第二章：Spring Cloud 多环境配置与 Nacos：Profile 与 config.import 分层（2025.1.x 无 bootstrap，与单体 Profile 思路不同）。

第十章：Redisson 红锁 RedLock 原理与生产实践

概念基础

  1. 要解决的问题：普通 Redis 锁是单主节点锁——加锁成功后尚未同步到从节点就宕机，主从切换后锁凭空消失，两个客户端可能同时持锁。
  2. 核心思想：把锁同时写到 N 个完全独立的 Redis 主节点上，过半节点加锁成功且总耗时小于锁有效期才算加锁成功。
  3. 为什么有效：基于**多数派（quorum）**机制，任一节点宕机/切换都不影响多数节点上的锁记录，从根本上规避单点故障丢锁。
  4. 代价：要写多个节点，性能低于普通锁；节点必须相互独立（非主从、非集群）且为奇数个。
  5. 适用边界：秒杀、库存、支付、账务等核心强一致场景用 RedLock；后台任务等非核心场景普通 Redisson 锁即可。

最标准、生产可直接用的 Redisson RedLock 实现，包含：配置 + 代码 + 原理 + 生产注意事项

一、先记住一句话

RedLock = 多个独立 Redis 主节点 + 过半写入成功才算加锁成功
目的：彻底解决主从切换丢锁问题

二、环境要求

  1. 至少 3 个独立的 Redis 主节点（无主从、无集群、互相独立）
  2. Redisson 版本 >= 3.5.0
  3. SpringBoot / Java 项目均可

六、RedLock 加锁成功规则（必须记住）

3个节点：
必须 ≥ 2 个节点加锁成功 + 加锁耗时 < 锁超时时间
才算加锁成功。

5个节点：
必须 ≥ 3 个节点加锁成功

七、RedLock 看门狗（自动续期）生效吗？

生效！

RedLock 会对每个节点的锁自动续期。
只要过半节点存活，锁就不会失效。

八、生产使用注意事项（非常重要）

1. 必须使用 奇数个节点

3、5、7 个，不能用 2、4、6 个。

2. 节点之间完全独立

不能是主从、不能是集群，必须是独立 Master。

3. 性能比普通锁低

因为要写多个 Redis，高并发秒杀可以接受。

4. 核心业务才用 RedLock

  • 秒杀、库存、订单、支付、账务 → 用 RedLock
  • 后台任务、非核心 → 普通锁即可

5. 不要把 leaseTime 设置太长

默认 30s 足够，看门狗会自动续期。

九、最终结论

RedLock 是生产上唯一能彻底解决 Redis 主从丢锁的方案
金融、电商、支付、秒杀必须使用！

概念基础

  1. 为什么单机锁不够用：服务多实例部署后，synchronized/ReentrantLock 只能约束同一 JVM 内的线程，跨进程的互斥必须借助外部共享存储实现。
  2. 本质：多个进程竞争在同一个外部系统上设置同一个标识（Redis 的 SET NX、ZooKeeper 的节点、MySQL 的行锁），谁设置成功谁持有锁，并依赖超时自动释放防死锁。
  3. 三大实现流派：Redis（高性能、主流方案）、Zookeeper（临时有序节点、强一致）、MySQL（悲观/乐观锁，零新增中间件）。

  5. 选型口诀：高并发选 Redisson，强一致选 Zookeeper，无中间件小项目选 MySQL。
