1. 概念说明

Vue 3 是渐进式前端框架：核心是声明式渲染——你声明”界面 = f(状态)”，状态变化自动更新视图。渐进式的含义是：可以从一个 <script> 引入的页面级脚本，一路扩展到路由、状态、SSR、工程化的完整应用，接入范围由项目需要决定。

四个核心概念：

  • 响应式（Reactivity）：基于 Proxy 拦截对象读写，依赖收集 + 派发更新。
  • 组件（Component）：UI 复用单元，props 进、事件出。
  • 模板（Template）：声明式描述 DOM，指令（v-if / v-for / v-model / @click）把状态与视图绑起来。
  • 生命周期：组件从创建、挂载、更新到卸载的钩子序列，用来放置副作用（请求、定时器、清理）。
  • Composition API：按逻辑组织代码（setup + ref/reactive/computed/watch），替代 Options API 的按选项组织——细节见进阶篇。
  • 虚拟 DOM：先算差异再更新真实 DOM，批量高效。

1. 概念说明

视频 = 连续图像帧 + 音频，通过**编码（Codec）**压缩存储。三个核心概念：

  • 编码标准：H.264（兼容性最好）、H.265/HEVC（同画质省 50% 码率）、AV1（新一代开源，省更多但编码慢）、VP9。
  • 封装格式（Container）：MP4（通用）、MKV（多轨）、WebM（网页）。编码与封装独立组合：H.264 视频 + AAC 音频 → MP4。
  • 关键参数：分辨率（1080p）、帧率（fps）、码率（bitrate，决定画质与体积）、GOP（关键帧间隔）。

转码为什么重要：源视频（如手机 4K）码率高、格式杂，服务端需统一转成 H.264/AAC + MP4 便于全端播放；按分辨率出多档（1080p/720p/480p）做自适应。

9. 典型案例：UGC 短视频上传转码管线

问题背景：App 允许用户上传 60s 竖屏视频，手机端拍出的码率/分辨率五花八门，Web 端播放常卡在加载；个别 4K 素材直接把转码机 CPU 打满，整个服务雪崩。

方案：上传后先 ffprobe 摸底 → Celery 队列限并发异步转码 → 转出 720p/480p 两档 HLS + 封面抽帧 → 对象存储托管，mp4 兜底输出加 -movflags +faststart 保证秒开。

踩坑点：

  • 忘加 -movflags +faststart：moov box 在文件尾，浏览器必须全量下载才能播，”卡在加载”多半是它。
  • 上传接口里同步转码：请求超时、用户重传、机器打满三连——转码必须丢队列异步做。
  • worker_concurrency 不限：10 个 4K 任务并行把 CPU 顶满，所有任务互相拖死。
  • 竖屏视频用 scale=1280:-2 写死宽度：画面被裁成横条——用 scale=-2:{height} 按高度缩放。
  • 任务不幂等：重试时 ffprobe 阶段源文件已被清理直接报错——重试前先检查产物是否存在。

坑 现象/后果 解法

1. 概念说明

Spring Boot 解决什么：Spring 原生配置繁琐（XML、Bean 装配），Spring Boot 用约定优于配置 + 自动配置大幅降低门槛，内置 Tomcat 独立运行，一个 main 方法启动应用。

核心机制：

  • Starter：一组依赖的集合（如 spring-boot-starter-web = Web + Tomcat + Jackson），引入即用。
  • 自动配置（Auto-Configuration）：类路径有某依赖（如 Redis 客户端）时，@ConditionalOnClass 生效，自动装配默认 Bean（如 RedisTemplate）。
  • spring.factories / AutoConfiguration.imports：自动配置类的注册清单。
  • 外部化配置：application.yml 优先级高于默认值，可被环境变量/启动参数覆盖。

10. 典型案例：启动优化（30 秒 → 8 秒）

问题背景：一个聚合服务引入了 Redis、ES、RabbitMQ、Kafka 等十几个 starter，冷启动 30 秒。K8s 滚动更新时新 Pod 迟迟不就绪，发布窗口拖长，偶发健康检查超时被 kill 陷入重启循环。

方案（先测量，再逐项优化）：

优化项 做法 收益
定位耗时 Actuator startup 端点 + ApplicationStartup 采样 找到 3 个慢 Bean

排除无用自动配置 exclude 掉用不到的 DataSourceAutoConfiguration 等 少扫描少装配
探针分离 liveness 与 readiness 分开 先 live 后 ready，不被误杀
预热 就绪后主动打一次核心接口 首请求不慢

踩坑点：

  1. 全局懒加载后配置错误被延迟暴露：数据源密码错在启动时不再报错，直到第一个请求才炸——保留关键 Bean 用 @Lazy(false) 强制急切初始化。

11. 典型案例：下单接口的幂等令牌设计

问题背景：支付页”提交订单”按钮用户连点了 3 次（前端防抖在弱网下失效），网关重试又放大了流量，同一笔订单在数据库里产生 3 条记录、扣了 3 次库存。事后统计该问题月均出现 200+ 笔，全部靠人工客服退单。

方案：前端提交前先到后端领一个幂等令牌（token），提交时带上 token；后端用 Redis 原子操作校验并消费，同一 token 第二次提交直接拒绝：

关键点 选择 原因
校验方式 Redis GETDEL（原子） “先查再删”两步操作在并发下会同时通过，必须原子
token 生命周期 600 秒过期 覆盖用户停留收银台时长，过期自动清理
token 存储 Redis + 表单隐藏域 无状态，多实例共享校验结果
失败回补 下单异常时归还 token 避免用户重试时被误判为重复请求

踩坑点：

  1. 第一版用”先 GET 再 DEL”两步校验，压测 50 并发出现 3 笔重复订单——查询和删除之间线程被切换，两个请求同时 GET 到 token。改用 GETDEL（或 Lua 脚本）原子化后归零。

  4. 下单失败没有归还 token，用户改完地址重试永远提示”请勿重复提交”，客诉量反升——失败路径必须回补 token（或只在明确的不可重试错误上不归还）。

12. 常见误用与陷阱

坑 现象/后果 解法
幂等校验”先查后删”两步执行 并发下两个请求同时查到 token 都放行，幂等失效 用 GETDEL 或 Lua 脚本把校验+消费做成原子操作

接口 URL 不带版本号（/api/order） 字段变更后老客户端批量报错，发版被迫所有端同步上线 路径版本化 /api/v1/order，新老版本并存一个发布周期

1. 概念说明（导论）

Redis 是基于内存的高性能键值数据库：单线程（6.x 前）事件循环 + IO 多路复用，吞吐可达 10 万+ QPS。定位是缓存与中间件，不是主存储（数据可丢失场景除外）。

Redis 8 新增：Redis 8.0（2025 年发布）带来原生向量检索（Redis Vector Sets）、增强持久化等能力，是当前主推版本。

单机 Redis 有两大天花板：可用性（宕机全挂）和容量/吞吐（单节点上限）。进阶要解决：

  • 主从复制：数据冗余 + 读写分离（解决可用性基础）。
  • 哨兵（Sentinel）：监控主节点，宕机自动选举新主（解决自动故障转移）。
  • 集群（Cluster）：数据分片到多主多从（解决容量与吞吐）。
  • Lua 脚本：把多条命令打包原子执行（解决”检查-执行”竞态）。

11. 典型案例：商品详情缓存三件套（穿透/击穿/雪崩）整体落地

问题背景：商品服务日活 300 万，详情页读多写少（读写比 100:1）。上线初期裸查库：一次恶意爬虫扫描 20 万个不存在的商品 ID 把 DB 打挂 15 分钟；修复后又因为”热点商品缓存固定 30 分钟过期”，两次整点出现 DB QPS 瞬时 8 倍尖峰。

21. 典型案例：ZSet 延迟队列实现订单 30 分钟未支付自动关闭

入门篇

坑 现象/后果 解法
SETNX 抢锁不设过期时间 持锁线程崩溃后锁永不释放，业务全被”没抢到锁”分支卡死 setIfAbsent(key, val, ttl) 一条命令原子完成；finally 中 DEL
锁的 value 不带身份标识 A 超时后 B 拿到锁，A 恢复后误删 B 的锁，并发重新发生 value 存唯一 ID（UUID+线程 ID），释放用 Lua 校验身份再删
先删缓存再更新数据库 并发读把旧值重新填回缓存，不一致持续到过期 Cache Aside 固定顺序：先更新库，再 DEL 缓存；敏感场景延迟双删
INCR 计数器不设 TTL 统计类 key 只增不减，内存缓慢耗尽开始淘汰 计数器创建即 INCR key; EXPIRE key 86400（仅首次设 TTL）
缓存对象用 JDK 序列化 value 二进制不可读、跨语言不兼容、类结构变更后反序列化失败 统一 JSON（Jackson），配合 @JsonIgnore 排除敏感字段
