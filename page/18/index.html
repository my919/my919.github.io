1. 概念说明：可靠性三环节

消息可靠性三问（面试与生产核心）：

  1. 不丢：消息从生产 → broker → 消费，任何环节都不能丢。
  2. 不重：网络重试导致重复投递，消费端必须幂等。
  3. 不乱：需要顺序的场景保证按序处理。

消息丢失的三个环节：

“不丢”不等于”不重”：保证不丢必然可能重复（网络重试）——所以可靠性 = 不丢（机制保证）+ 不重（幂等消费）。

可靠性铁律：消息丢失的责任最终在消费端兜底——生产者/Broker 尽量可靠，但消费端必须能容忍任意环节的重复与乱序（幂等 + 重试 + 对账）。

5. 幂等消费（”不重”的保证）

为什么必须幂等：网络/重试机制天然会重复投递——消费端必须保证”同一条消息处理两次 = 处理一次”。

幂等三方案对比：

方案 实现 适用
唯一键 + 数据库 INSERT IGNORE / 唯一索引冲突即已处理 通用（最可靠）
Redis SETNX setIfAbsent(orderId, 1, TTL) 高频场景
状态机校验 业务状态前置校验（已支付不再支付） 状态明确

为什么”查重→处理→记录”要同一事务：分开了会出现”处理成功但记录失败”→ 下次重发又处理一次（不幂等）。同事务保证原子性。并发场景下”先查后插”不安全，必须用数据库唯一键的原子插入兜底。

1. 概念说明

微服务拆分本质：把”一个能跑的大应用”变成”多个能独立部署的小应用”——目标是独立演进、独立伸缩、故障隔离，代价是分布式复杂度（网络、事务、一致性、排障）。

拆分决策前提（先回答）：

9.1 问题背景

9.3 网关：路由 + 统一鉴权

9.4 Feign 调用：超时 + 重试 + 熔断降级（Resilience4j）

重试只能给幂等查询 / 带幂等键的写开放；裸写接口重试会造成重复扣减。多层调用只允许最内层一层重试，避免重试相乘形成风暴。

9.5 链路追踪：traceId 跨服务透传

引入 micrometer-tracing-bridge-brave 后，同进程日志 MDC 自动注入 traceId；跨进程通过 Feign 拦截器透传 B3 头，下游归入同一条 Trace。

9.6 踩坑点

  • 超时层层不设：Feign、网关任一处无限等待，一个慢下游吃光整条链路线程池——全链路统一超时，且上游超时要大于下游超时之和。
  • 写接口盲目重试：非幂等扣减被重试 2 次，库存扣了 3 份——重试白名单化，写接口必须带幂等键。
  • 降级静默：fallback 直接返回空数据，无日志无打点，业务故障无人知——降级路径必须埋点告警并接入异步补偿。
  • 熔断器粒度过粗：整个服务一个熔断器，边缘接口故障把核心扣库存也熔断——按核心方法/业务资源分组隔离。
  • 链路在 MQ 处断开：HTTP 头透传了 traceId，发消息后断链——消息头携带 traceId，消费端恢复 MDC 续接。

数据读取 selectListAll 全量 4GB 游标分批 5000 条/批

关键代码：

踩坑点：

  1. 处理慢时顺手改成 parallelStream()——但聚合里对共享 HashMap 做了写操作，跑出丢数据；并行流要么用 collect 的组合器，要么别碰共享可变状态。

分布式 · 分布式事务

从 0 到生产选型。事务演进与问题 · XA/AT/TCC/SAGA 对比 · Seata 实战 · 可靠消息最终一致 · 对账与补偿。代码带详细注释。

技术栈速查

类别 选型 用途
框架 Seata 2.x 分布式事务

消息 Kafka 4.x 最终一致
数据库 MySQL 8.4 事务存储
场景 订单/库存/账户三服务 典型案例

1. 概念说明

为什么需要分布式事务：微服务拆分后，一次下单跨”订单库 + 库存库 + 账户库”三个独立事务——本地事务无法保证一致性。

分布式事务核心指标：

  • 强一致（CP）：所有节点要么全成功要么全失败（XA/AT/TCC）。
  • 最终一致（AP）：先各自提交，通过异步补偿最终一致（SAGA/消息）。

工程共识：互联网业务 90% 用最终一致；只有资金类强约束场景用强一致。能用单库事务绝不分布式。

2. 四种方案对比

方案 原理 一致性 侵入性 性能 适用
XA 数据库原生 2PC 强 低 差（锁久） 老旧系统
AT 代理层生成反向 SQL 强 低 中 Seata 首选
TCC 业务三方法(Try/Confirm/Cancel) 强 高 高 资金/高并发
SAGA 正向+补偿事务 最终 中 高 长流程

2PC 问题（XA 的短板）：协调者单点、同步阻塞（资源锁定）、脑裂时不一致——所以现代方案用 AT/TCC/SAGA 规避。

7. 选型决策树

8. 典型案例：订单-库存-账户三服务分布式事务

8.1 问题背景

一次下单要跨三个独立服务与数据库：订单服务写 orders、库存服务扣 sku_stock、账户服务扣 account.balance。三个本地事务无法用 @Transactional 统一提交或回滚，必须选择分布式事务方案。团队对 Seata AT 与本地消息表/事务消息做了对比选型。

8.2 两种落地方案对比

维度 Seata AT 模式 本地消息表 / 事务消息
一致性 强一致（TC 协调 + 全局锁） 最终一致（通常秒级，异常时分钟级）
性能 中：undo 镜像 + 全局锁，热点行易瓶颈 高：本地短事务，无跨库锁等待
业务侵入 低：一个 @GlobalTransactional 中：消息表、轮询、幂等、对账都要自建
额外依赖 TC Server + 每库 undo_log MQ + 定时任务 + 对账任务
适用场景 低并发、内部系统、余额/库存要求实时强一致 高并发电商下单，容忍短暂「处理中」状态
失败处理 自动反向 SQL 回滚 消息重试 + 死信 + 对账补偿

结论：下单主链路用本地消息表（高并发最终一致），资金划拨等少数强一致点用 Seata AT。RocketMQ 事务消息可省掉自建 outbox 轮询（半消息 + 事务回查）；本案例用 Kafka + 本地消息表演示完整骨架。

8.3 方案结构（本地消息表）

8.4 完整代码骨架

建表（订单库的消息表与业务表必须同库，才能纳入同一本地事务）：

① 生产端：业务数据与消息同事务写入。

② 轮询投递：至少一次（at-least-once），进程崩溃可重试。

③ 消费端：先占幂等坑，再执行业务。

④ 对账兜底：重试耗尽、消息进死信、消费遗漏时的最后防线。

一致性保证链条：同库事务写业务+消息（不丢）→ 定时重发（可达）→ 消费端幂等（不重）→ 对账（最终收敛）。

8.5 踩坑点

  • 消息表与业务表不同库：无法纳入同一本地事务，写库成功写表失败就会丢消息——outbox 必须与业务共库。
  • 先发消息再写库：业务回滚了消息却已发出，出现「幽灵订单」，库存凭空被扣——严格先写库（含消息表），再异步投递。
  • 消费端不幂等：at-least-once 重试导致重复扣库存、重复扣款——先插入幂等记录再处理，唯一键冲突即跳过。
  • 没有对账：消息进入死信后无人感知，三方数据永久不一致——定时对账 + 死信告警 + 自动补偿。
  • AT 模式热点行：秒杀商品同一行被全局锁串行化，TPS 上不去——热点链路改用本地消息表 / Redis 预扣。
  • AT 中开异步线程：XID 只在同步调用链透传，子线程分支脱离全局事务无法回滚——跨线程显式传播 XID 或改为同步。
