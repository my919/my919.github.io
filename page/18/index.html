数据库 · 设计规范

从 0 到可落地的建模规范。范式与反范式 · 索引设计 · 命名规范 · 分库分表 · 大表优化 · 建模工具。

1. 概念说明

数据库设计的目标：数据一致、查询高效、易维护、可扩展。

核心矛盾：范式化（消除冗余，写友好）vs 反范式化（冗余加速读）。生产实践：逻辑上按范式设计，物理上按查询反范式（冗余字段、汇总表）。

设计五步：需求分析（实体与关系）→ 概念设计（ER 图）→ 逻辑设计（表结构）→ 物理设计（索引/存储）→ 评审上线。

快照冗余字段被联动更新 改商品名把历史订单快照也改了 快照字段只写不改；可计算冗余才维护一致性

1. 概念说明

事务：一组操作要么全部成功要么全部回滚（ACID：原子性、一致性、隔离性、持久性）。

数据库隔离级别（从宽松到严格）：

级别 脏读 不可重复读 幻读
READ UNCOMMITTED ✅可能 ✅可能 ✅可能
READ COMMITTED ❌ ✅可能 ✅可能
REPEATABLE READ ❌ ❌ ✅可能（MySQL 可防）
SERIALIZABLE ❌ ❌ ❌

MySQL 默认 REPEATABLE READ（MVCC 下已防幻读）；PostgreSQL 默认 READ COMMITTED。

何时需要多数据源：读写分离、多库分片、老系统对接、微服务各自建库。

8. 何时引入分布式事务

场景 方案
单库多表 本地事务（默认）
跨库（同应用多数据源） Seata AT
跨服务（微服务） Seata TCC / SAGA / 可靠消息
高一致 vs 高可用权衡 多数场景用”最终一致”（本地消息表 + 定时对账）

原则：能本地事务就不分布式；能用最终一致就不用强一致（分布式事务有性能与复杂度代价）。

9. 典型案例：秒杀下单（防超卖 + 日志独立 + 可靠消息）

问题背景：秒杀下单一次要做三件事——扣库存、写订单、记操作日志。线上出过两类事故：高并发下库存被扣成负数（超卖，平台资损）；操作日志与订单共用一个事务，订单回滚时日志一并消失，事后无法追溯。

方案：

操作日志 REQUIRES_NEW 独立事务 主流程回滚，审计日志也保留
发 MQ 消息 定时任务扫 outbox 事务外发送，杜绝长事务与消息丢失

10. 常见误用与陷阱

坑 现象/后果 解法
同类内部调用 this.deduct() @Transactional 完全失效，无事务执行 拆分到其他 Bean，或注入自身代理（self）调用
事务内远程调用 / 发 MQ 锁持有 200ms+，连接池被占满，RT 飙升 缩小事务边界，用 outbox/事件表异步化
不写 rollbackFor 抛受检异常不回滚，脏数据入库 统一 @Transactional(rollbackFor = Exception.class)
异常被 try-catch 吞掉 事务照常提交，半截数据落库 catch 后重新抛出，或 setRollbackOnly()
@Transactional 内切 @DS 数据源 切换不生效，读写全落主库 切换在事务开启前完成；跨库用 Seata
REQUIRES_NEW 用在同类自调用 传播行为不生效，仍是同一事务 必须跨 Bean 走代理调用
大事务锁热点行 死锁频发、主从延迟拉大 缩短事务，热点行改乐观锁或队列串行化
子线程操作数据库 子线程不在当前事务内，回滚不完全 事务内禁止开线程池；需要异步用事务消息

Java 并发进阶：JUC 与线程池

发表于 2026-09-14 更新于 2026-10-25 分类于 并发编程 本文字数： 5.6k 阅读时长 ≈ 5 分钟

并发 · Java 并发进阶

入门篇之后深入并发核心。synchronized 与锁原理 · volatile 与可见性 · JUC 工具类 · 线程池深度 · 并发容器 · 性能调优。代码带详细注释。

技术栈速查

类别 选型 用途
语言 Java 21 实现
并发包 java.util.concurrent 并发工具
构建 Maven 3.9 项目管理

1. 概念说明

并发编程三个核心问题：

  • 原子性：一个操作不可分割（i++ 不是原子的）。
  • 可见性：线程修改了变量，其他线程能看到（CPU 缓存导致看不到）。
  • 有序性：指令重排导致执行顺序与代码不一致。

Java 内存模型（JMM）：线程共享主内存，各自有工作内存（缓存）；volatile、synchronized、Lock 通过内存屏障保证可见性与有序性。

选择铁律：能用 synchronized 就不用 Lock（jdk8+ 已优化）；能用并发容器就不用手动加锁；锁粒度越小越好。

5. 并发容器选择

容器 特性 适用
ConcurrentHashMap 分段/粒度锁，读并发 缓存、KV
CopyOnWriteArrayList 写时复制，读无锁 读多写极少（白名单）

避免：用 Collections.synchronizedMap（全表锁）、HashTable、Vector。

6. 并发测试与坑

高频坑：

坑 表现 对策
共享可变状态无锁 数据错乱 原子类/加锁/不可变对象
死锁 线程互相等待 锁顺序一致 + tryLock 超时
线程池资源耗尽 拒绝异常 监控队列长度 + 合理容量
任务异常吞掉 无感知 全局异常处理 + 日志
使用 Executors 快捷方法 OOM（无界队列） 手写 ThreadPoolExecutor

7. Java 21 虚拟线程（新选择）

适用：IO 密集（HTTP 调用、DB 访问）场景吞吐大幅提升；CPU 密集无收益。Spring Boot 3.2+ 可开启 spring.threads.virtual.enabled=true。

8. 常见误用与陷阱

坑 现象 解法
volatile 当计数器用（count++） 多线程下结果偏小——volatile 只保证可见性、不保证 ++ 原子性 改用 AtomicInteger / 高竞争用 LongAdder（§2.2）
ConcurrentHashMap 复合操作未原子化 先 containsKey 再 put，两步之间被插入 → 仍然出现重复或覆盖 用 putIfAbsent / compute / merge 等原子方法，锁粒度交给内部实现
ReentrantLock 忘记 finally unlock 异常路径下锁不释放 → 后续线程全部阻塞，等价死锁 lock() 紧跟 try，finally 中 unlock()（§3.2），可用 try-with-resources 风格包装
StampedLock 乐观读后改写没升级 tryOptimisticRead 失败后直接写值 → 乐观读期间已被写过 → 数据错乱 乐观读仅用于纯读；写必须走 writeLock()；validate 失败后升级读锁再读（§3.4）
CopyOnWriteArrayList 用在写多场景 每次写都复制底层数组，写放大严重 → CPU 飙升、GC 频繁、内存抖动 读多写少才用它（白名单/配置）；写多用 ConcurrentLinkedQueue 或 Collections.synchronizedList

9. 典型案例：限量 NFT 铸造（防机器人 + 防重入）

问题背景：项目方发 10000 枚限量 NFT，单价 0.01 ETH。首次开放铸造 10 分钟被机器人脚本批量扫走 8000 枚，普通用户一个没抢到；提款函数又被重入攻击盯上，差点资金受损。

方案：合约层每地址限购 + ReentrancyGuard + 先改状态后转账（CEI）；前端层铸造按钮防连点、先预估 gas；链上层用事件 + The Graph 索引铸造记录。

踩坑点：

  • 只靠前端限制购买数量没用——机器人绕过页面直接调合约，限购必须写在链上。
  • payable 函数不校验 msg.value，0.0001 ETH 也能 mint，等于白送。
  • 提款先转账后改状态，重入攻击一次掏空合约（The DAO 就是这么挂的）。
  • 上线前在 Foundry 写「攻击者合约」用例验证防重入，别指望审计兜住一切。

8. 典型案例：WebRTC 语音通话端到端

问题背景：在线客服系统上线网页语音通话，用户反馈两个问题：能听到自己说话的回声；对方声音忽大忽小、开头卡几秒。

方案：浏览器 getUserMedia 强制开启回声消除（AEC）与自动增益（AGC），Opus 48kHz 单声道走 WebRTC（WHIP 接入流服务器），延迟压到 300ms 内；录音存档走服务端 FFmpeg 独立链路。

踩坑点：

  • 用户戴耳机没问题，但外放却关 AEC 必出回声——按输出设备类型动态调整约束。
  • 在 WebAudio 里自己加增益/滤波会绕过 AEC 参考信号，回声消除直接失效——通话链路上不做旁路 DSP。
  • Opus 码率给到 32-64kbps + DTX（静音不发包），带宽波动才不破音。
  • 延迟与卡顿是跷跷板：jitter buffer 调小延迟降了但卡顿上升，200-400ms 动态缓冲是甜点区。
  • 录音是另一条链路：服务端 FFmpeg 拉流转码，别指望 WebRTC 端自己录。

9. 常见误用与陷阱

坑 现象/后果 解法
回声消除误解 “戴耳机就不用 AEC”——切到外放立刻回声轰鸣 AEC/AGC/NS 常开，按输出设备动态微调
WebAudio 旁路处理 自加 GainNode 后 AEC 失效，回声回归 通话链路不做旁路 DSP，可视化用 AnalyserNode 只读
延迟与卡顿权衡 jitter buffer 压到 50ms，声音一顿一顿 200-400ms 动态缓冲 + 丢包隐藏（PLC）兜底
Opus 参数想当然 48kHz 立体声 24kbps，又闷又劈 通话单声道 32-64kbps + DTX 省带宽
loudnorm 一遍流用于直播 实时场景无法两遍测量，动态压缩失真 实时链路用 AGC；loudnorm 两遍只离线用
-re 用在文件转码 转码速度被人为限制成实时，白白浪费 CPU 仅推流（模拟实时）用 -re，转码绝不加

1. 概念说明

**动态规划（DP）**解决”多阶段决策最优化”问题，核心思想：把大问题拆成重叠子问题，用一张表记录子问题答案，避免重复计算。

DP 三要素：

  • 状态定义：dp[i] 表示什么（最常见：以 i 结尾 / 前 i 个）。
  • 状态转移：dp[i] 如何由更小的状态推出（核心方程）。
  • 初始条件：最小的子问题答案。

适用信号：求最值（最大/最小/方案数）、有重叠子问题、无后效性（当前决策只影响未来）。

贪心：每一步做局部最优，期望得到全局最优——只对满足”贪心选择性质”的问题成立（如活动安排、找零），必须证明或验证，不是所有最值都能贪心。

判断口诀：能用 DP 先想 DP；贪心是 DP 的特例（无后效 + 局部最优即全局）。

案例 1：会议室预订（最少会议室，LeetCode 253，贪心）

问题描述：给定若干会议的 [开始, 结束] 时间区间，求至少需要多少间会议室才能让所有会议互不冲突。

思路（贪心 + 最小堆）：

  1. 按开始时间升序排列会议——先开始的先安排。
  2. 用最小堆维护每间会议室的「结束时间」，堆顶是最早散会的房间。
  3. 每场会议开始前，若堆顶房间已散会（堆顶结束时间 <= 当前开始时间），复用该房间（弹出旧结束时间、压入新结束时间）；否则所有房间都忙，必须新开一间（只压入）。

贪心选择性质证明（交换论证）：会议按开始时间依次处理，若存在已散会的房间，把当前会议分配给「最早散会」的房间不会比分配给其他房间差——其他房间散得更晚，留着接待以后开始（开始时间不早于当前）的会议只会更宽裕；若连最早散会的房间都还没散会，则没有任何房间能接下当前会议，新开房间是被迫的、也是最优的。堆大小的峰值恰好等于最少会议室数。

案例 2：打家劫舍 II（环形 DP，LeetCode 213）

问题描述：房屋排成一个环，每间房内有金额 nums[i]，不能同时偷相邻两间（首尾也算相邻），求能偷到的最大金额。

思路（环形拆成两个线性问题）：

  • 状态定义：dp[i] = 只考虑前 i 间房（线性排列）时能偷到的最大金额。
  • 转移方程：第 i 间要么不偷（收益 dp[i-1]），要么偷（收益 dp[i-2] + nums[i]），取二者大值：dp[i] = max(dp[i-1], dp[i-2] + nums[i])。
  • 环形处理技巧：首尾不能同时选，任何合法方案必然属于「不偷第一间」或「不偷最后一间」之一，且这两类方案都合法。于是答案 = max(线性DP(1..n-1), 线性DP(0..n-2))，把环剪成两条链。
  • 空间优化：转移只依赖前两项，用两个滚动变量替代 dp 数组。

案例 1：TopK 问题三种解法对比（第 K 大元素，LeetCode 215）

问题描述：在无序数组中找第 K 大的元素（如 [3,2,1,5,6,4]，K=2，答案为 5）。

思路：

  • 堆：维护一个大小为 K 的小顶堆，遍历过程中堆超过 K 个就弹出堆顶最小值，结束时堆顶即第 K 大——适合流式数据与在线场景。
  • 快速选择：借鉴快排分区，每次只继续处理目标所在的那一段（不递归另一段），期望线性时间；最坏 O(n²)，需随机化 pivot。
  • 全排序：排序后直接取第 K 个，最省心，但做了多余的排序工作。

案例 2：旋转排序数组搜索（LeetCode 33）

问题描述：升序数组在某个下标处被旋转（如 [0,1,2,4,5,6,7] → [4,5,6,7,0,1,2]），元素互不相同。给定 target，返回其下标，不存在则返回 -1，要求 O(log n)。

思路（变体二分）：旋转后的数组分成两段，每段各自有序。每次算出 mid 后，先判断哪一段有序，再判断 target 是否落在该有序段内：

  1. 若 nums[left] <= nums[mid]，左段 [left, mid] 有序：target 落在 [nums[left], nums[mid]) 内则收缩右边界，否则去右段。
  2. 否则右段 [mid, right] 有序：target 落在 (nums[mid], nums[right]] 内则收缩左边界，否则去左段。

9. 常见误用与陷阱

陷阱 错误表现 正确做法
二分边界混用 while left <= right 却配 right = mid，或 left < right 配 right = mid - 1，导致死循环或漏解 闭区间模板：<= 配 mid ± 1；左闭右开模板：< 配 right = mid，全程只用一套
mid 计算溢出 C++/Java 中 (left + right) / 2，两数接近 INT_MAX 时整数溢出 统一写 left + (right - left) // 2（Python 无溢出也保持习惯）
快排最坏 O(n²) 固定取首元素做 pivot，遇到有序数组递归树退化成链 随机 pivot 或三数取中；小区间切换插入排序
破坏稳定性 需要多关键字保序时用快排，相等元素的相对顺序被打乱 有稳定性需求用归并排序或内置 Timsort；合并时用 <= 而非 <
自定义比较器返回值错误 cmp_to_key 的回调返回布尔值，True/False 被当成 1/-1，排序语义全乱 比较函数严格返回负数/0/正数，分别表示小于/等于/大于
