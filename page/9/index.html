8. 典型案例：单体到微服务演进决策

问题背景：某 SaaS 公司 20 人团队、单体 Spring Boot 应用、DAU 8 万。痛点：发布互相阻塞（一天 2 次排队发版）、单模块 CPU 打满被迫整机扩容。管理层提出”直接上微服务”，架构组需要用数据做演进决策。

方案：不一步到位，按「痛点 → 动作」分三阶段演进，每阶段有明确的进入/退出条件：

阶段 进入条件 动作 退出标准（做完了再进下一阶段）
1→2 团队 > 10 人，发布冲突出现 按领域分包、禁止跨模块访问 DB 表、ArchUnit 守护 模块间零表级依赖，CI 检查通过
2→3 单模块资源曲线背离 / 需独立扩容 先拆”资源大户”（如报表/IM），事件驱动解耦 拆出的服务 SLA 独立、回滚方案演练过
3 之后 平台负担 > 业务收益 平台工程：IDP + Golden Path 新服务自助创建 < 1 天

关键设计：拆分顺序用「资源曲线 + 变更频率」二维打分，而不是按”看起来好拆”：

踩坑点：阶段 2 时团队为了”以后好拆”，模块间直接互查对方 schema 的表——拆分时发现 order 模块 17 处 JOIN 了 user 表，被迫回炉。规则必须从第一天就用 ArchUnit 卡死：模块间只许走接口，禁止跨包访问 *Mapper。另一个坑：拆出的第一个服务没有先建事件总线，服务间用同步 HTTP 串了 5 层，可用性变成 0.99^5——正确做法是先落 Kafka/NATS，再拆服务。

2. 第一层：生产端可靠发送（确认机制）

2.1 RabbitMQ Publisher Confirms

为什么确认回调里失败要”补偿”：发布确认只告诉你”这次没成”——不补偿 = 消息悄悄丢了。补偿手段：重试 N 次 → 仍失败进”本地待重发表”（配合对账）。

2.2 Kafka acks 对照

为什么选 all：acks=all = 主副本 + 所有从副本都落盘才确认——单副本确认（acks=1）在主节点宕机时丢数据。

3. 第二层：Broker 持久化

为什么”持久化”是三层中最容易漏的：发消息时没设 PERSISTENT，Broker 宕机重启 → 内存里的消息全没——配置了确认机制但没持久化，等于白配。

4. 第三层：消费端可靠消费

4.1 手动 ACK（核心配置）

三种确认方式：

方式 行为 风险
自动 ACK 一收到就确认 处理失败 = 消息丢失 ❌
手动 ACK（推荐） 成功才确认 正确
手动 REJECT/NACK 拒绝/重新入队 需配合死信（防死循环）

为什么必须配死信：basicNack(requeue=true) 无限重入队 = 坏消息死循环（CPU 烧满 + 正常消息被堵）——重试有上限，超限进死信队列。

5. 幂等消费（”不重”的保证）

为什么必须幂等：网络/重试机制天然会重复投递——消费端必须保证”同一条消息处理两次 = 处理一次”。

为什么”查重→处理→记录”要同一事务：分开了会出现”处理成功但记录失败”→ 下次重发又处理一次（不幂等）。同事务保证原子性。

踩坑点：

  1. hash tag 上线时图省事，把商品详情也加了 tag（product:{categoryId}），某分类下 3 万个商品全落在同一槽，该分片内存是其他分片 6 倍、CPU 90%——tag 只给”必须同槽”的数据用，其他数据保持散列。

1. 概念说明：为什么必须会读 GC 日志

GC 是性能杀手：GC 发生时应用线程要停顿（STW，Stop The World）——停顿总时长直接决定接口延迟。

不读 GC 日志 = 盲调 JVM 参数（见 jar 启动篇的”为什么用数据定堆”）。

2. 开启 GC 日志（JDK 21）

2.1 生产启动参数（直接可用的组合）

为什么必须配滚动（filecount/filesize）：不滚动的话，一个进程跑几个月 GC 日志能占几十 GB 磁盘——磁盘被日志打满是线上故障第一高频。

2.2 线上临时开启（不用重启）

3. G1 日志逐字段解读（JDK 21 默认）

3.1 一次 Young GC 的完整日志

逐行解读：

片段 含义 健康判断
Pause Young (Normal) Young GC（G1 常规停顿） 正常行为
Eden regions: 128->0(256) Eden 区 128 个 → 清空；总容量 256 每次都清空 = 正常
Old regions: 512->512 老年代不变（年轻代回收不碰老年代） 正常
512M->96M(6G) 堆从 512M 用到 96M 活（堆总 6G） 存活率低 = 正常
12.345ms 本次停顿耗时（关注点） < 100ms 正常
Real=0.012s 真实停顿时间 与耗时一致

3.2 老年代增长（Mixed GC / 并发标记）

关键信号：

信号 含义 要警惕什么
Concurrent Start 老年代占比达到阈值（默认 45%）触发并发标记 出现频率升高 = 老年代增长快
Humongous Allocation 大对象分配（> 区域 50%） 大对象直接进老年代，频繁 = 问题

3.3 Full GC（红色警报）

Full GC 为什么是警报：全程 STW（1.2 秒应用完全卡死）、需要压缩整理。Full GC 频繁 = 内存有问题（泄漏/堆太小），见内存排查篇。

9. 典型案例：GC 日志正常但接口每 30 秒抖一次（Safepoint 真凶）

问题背景：商品服务每约 30 秒出现一波 200-400ms 的接口抖动，P99 告警持续。第一反应是 GC——但 GC 日志停顿全部 < 30ms，GC 被排除，很多人到这一步就卡住了。

排查过程：

步骤 操作 观察
① GC 日志全量统计（本篇 §4.1 命令） Young GC 每 2 秒一次、每次 15-25ms；Full GC 为 0 → GC 解释不了 300ms 抖动
② 抖动时刻与 GC 时刻对齐 时间轴上 300ms 抖动点不与任何 GC 停顿重合
③ 开 safepoint 日志：-Xlog:safepoint:file=... 每 30 秒一条：Reaching safepoint: 280ms（线程到达安全点慢）← 真凶特征
④ 排查 30 秒周期任务 有个本地统计任务每 30 秒跑一次：单循环遍历 800 万条内存数据做聚合（counted loop 长期不进安全点）
⑤ 修复：任务拆批 + 降频 循环每次处理 50 万条后让出；频率 30s → 5min；可选 -XX:LoopStripMiningIter=1000
