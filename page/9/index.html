网络 · 计算机网络

从 0 到排查实战。OSI/TCP-IP 分层 · TCP/UDP · 三次握手四次挥手 · HTTP/1.1·2·3 · HTTPS/TLS · DNS · 抓包与排障。

技术栈速查

类别 选型 用途
协议 TCP/IP / HTTP / TLS 网络核心协议
抓包 Wireshark / tcpdump 报文分析

1. 概念说明

计算机网络是分层协作的系统，每层只关心自己的职责，向上层提供接口。两种分层模型：

层 OSI 七层 TCP/IP 四层 代表协议
应用层 7 应用 / 6 表示 / 5 会话 应用层 HTTP、DNS、SMTP
传输层 4 传输 传输层 TCP、UDP
网络层 3 网络 网际层 IP、ICMP
链路层 2 数据链路 / 1 物理 网络接口 以太网、WiFi

数据封装：发送方从上到下逐层加头部（Header），接收方从下到上逐层剥头。

2. TCP 核心机制

2.1 三次握手（建立连接）

  • 第一次：客户端 SYN（我准备连接）
  • 第二次：服务端 SYN+ACK（收到，我也准备）
  • 第三次：客户端 ACK（确认双方都能收发）

为什么是三次：两次无法确认客户端接收能力；防止已失效的连接请求突然到达服务端造成资源浪费。

2.2 四次挥手（断开连接）

TIME_WAIT 为什么等 2MSL：保证最后一个 ACK 可达、旧连接报文在网络中消失，避免污染新连接。

2.3 可靠传输三件套

机制 作用
确认应答（ACK） 确认收到
超时重传 / 快速重传 丢失恢复
滑动窗口 + 拥塞控制 流量与拥塞控制（慢启动、拥塞避免、快恢复）

3. UDP 与 TCP 对比

维度 TCP UDP
连接 面向连接 无连接
可靠性 可靠 尽力而为
顺序 保证 不保证
头部 20 字节 8 字节
场景 HTTP、数据库、文件 DNS、视频通话、游戏、QUIC

4. HTTP 协议演进

版本 特点
HTTP/1.1 持久连接、管道化受限、队头阻塞
HTTP/2 二进制分帧、多路复用（一个连接并发请求）、头部压缩 HPACK、服务端推送
HTTP/3 基于 QUIC（UDP），0-RTT、彻底解决队头阻塞

常用状态码（必须掌握）：

分类 代表
1xx 100 继续
2xx 200 OK、201 Created、204 No Content
3xx 301 永久重定向、302 临时重定向、304 缓存命中
4xx 400 参数错、401 未认证、403 无权限、404 不存在、429 限流
5xx 500 服务器错、502 网关错、503 服务不可用、504 网关超时

HTTPS = HTTP + TLS，解决加密、防篡改、身份认证。

9. 高频面试题速答

问题 核心答案
三次握手为什么不是两次 需确认双方收发能力，防失效请求
四次挥手为什么四次 服务端 FIN 与 ACK 可分离（CLOSE_WAIT 期间还有数据）

HTTPS 性能开销 握手一次，后续对称加密开销小；可开会话复用

1. 概念说明

RabbitMQ 是基于 AMQP 协议的消息队列，以灵活的路由能力著称（对比 Kafka 的线性吞吐，RabbitMQ 胜在交换机模型与低延迟、复杂路由）。

Virtual Host 隔离环境（租户）
ACK 确认 消费者处理成功后通知删除消息

1. 概念说明

**消息队列（MQ）**是生产者和消费者之间的异步通道，解决三大问题：

  1. 异步解耦：下单后发消息，邮件/积分/通知各自消费，互不影响。
  2. 削峰填谷：秒杀流量先入队，消费者按自身能力消费。
  3. 最终一致：跨服务状态同步。

Kafka 核心架构：

概念 说明
Broker 一台 Kafka 服务器，集群由多个 Broker 组成
Topic 消息分类（如 order-events）
Partition Topic 的分片，并行与扩展的单元，内部有序
Offset 消息在分区内的序号
Producer 生产者，写入消息
Consumer / Consumer Group 消费者；同组内分区消费，组间互不影响
Replica 副本（Leader/Follower），保证可用性

为什么选 Kafka：相比 RabbitMQ，Kafka 吞吐更高（百万级/s）、天然分布式、消息可重放，适合大数据与事件驱动；RabbitMQ 更适合复杂路由与低延迟业务。Kafka 4.x 已用 KRaft 替代 ZooKeeper，部署更简单。

微服务 · 架构

从 0 到架构落地。微服务 vs 单体 · 拆分方法论 · 微服务全景（注册/配置/网关/熔断）· 技术选型 · 落地路线与避坑。配置带详细注释。

技术栈速查

类别 选型 用途
底座 Spring Boot 4 + Spring Cloud Alibaba Java 微服务生态
注册/配置 Nacos 服务发现与配置中心
网关 Spring Cloud Gateway / APISIX 统一入口
熔断限流 Sentinel 稳定性保障
消息 Kafka / RocketMQ 异步解耦
观测 Prometheus + Grafana 指标监控

1. 概念说明

微服务（Microservices）是把一个大型应用拆分为一组小型独立服务，每个服务围绕一个业务能力（如订单、库存、用户），独立开发、独立部署、独立扩展，服务间通过轻量协议（HTTP/RPC/消息）通信。

单体 vs 微服务：

维度 单体架构 微服务
部署 一个包 N 个服务独立部署
扩展 整体扩展 按服务扩展
故障影响 全挂 局部故障
开发协作 全队改一个仓库 按服务分团队
运维成本 低 高（注册中心/网关/链路追踪）
适用 中小项目、起步阶段 大团队、高复杂度业务

铁律：微服务是”高复杂度”的解药，不是”高性能”的解药。团队小于 20 人、业务初期，单体 + 模块化是更优选择。分布式拆分要付出分布式代价（网络、事务、调试）。

2. 什么情况该上微服务（决策清单）

以下信号出现 ≥3 个才考虑：

  • 团队 20+ 人，协作冲突频繁
  • 模块间解耦需求强烈（不同发布节奏）
  • 部分模块扩展性要求差异大
  • 已有清晰的业务边界
  • 具备运维能力（容器化、监控）

3. 拆分方法论

3.1 按限界上下文拆分（DDD 战略设计）

3.2 拆分原则

原则 说明
高内聚低耦合 一个服务只干一件事
数据库独立 每个服务独享数据库（否则失去隔离意义）
服务粒度适中 业务能力为界，不按”层”拆（不拆 controller-service-dao 服务）
禁止循环依赖 服务依赖必须成 DAG
数据所有权清晰 每个数据字段只有一个所有者服务

从 0 到调优实战。JVM 内存结构 · 类加载机制 · 垃圾回收 · 诊断工具 · GC 日志分析 · 内存/CPU 问题排查 · 参数调优。代码带详细注释。

技术栈速查

类别 选型 用途
JDK 21 LTS HotSpot JVM

GC G1（默认）/ ZGC 垃圾回收器

1. 概念说明

JVM（Java Virtual Machine）是 Java 跨平台的基石：把字节码翻译为机器指令并管理内存。理解 JVM 是定位内存溢出、CPU 飙高、停顿过长问题的基础。

一次 Java 程序的生命周期：源码 .java → 编译为字节码 .class → 类加载到内存 → 执行引擎解释/编译执行 → 垃圾回收自动清理无用对象。

2. 内存结构（运行时数据区）

区域 共享 作用 溢出错误
堆 是 对象分配 OutOfMemoryError: Java heap space
元空间 是 类元数据 Metaspace
虚拟机栈 否 方法调用帧 StackOverflowError
程序计数器 否 字节码行号 无

3. 类加载机制

加载 → 验证 → 准备 → 解析 → 初始化 五阶段。

双亲委派模型：类加载请求先交给父加载器（App → Platform → Bootstrap），父加载不了才自己加载——保证核心类（如 java.lang.String）不被篡改。

4. 垃圾回收（GC）

判断对象可回收：可达性分析（GC Roots 出发不可达即回收）。GC Roots 包括：栈帧局部变量、静态变量、JNI 引用等。

分代收集（对象年龄小者升代）：新生代用复制算法（Eden/S0/S1），老年代用标记-整理/标记-清除。

JDK 21 可用的收集器：

收集器 特点 适用
G1（默认） 分区化、可预测停顿 大多数服务，默认即最佳
ZGC 亚毫秒停顿、超大堆 大内存低延迟（数百 GB）

7. 实战排查案例

7.1 案例一：内存溢出（OOM）

现象：服务报 java.lang.OutOfMemoryError: Java heap space。

排查流程：

用 MAT / Eclipse Memory Analyzer 打开 heap.hprof，看 Dominator Tree 找占用最大的对象路径，定位到泄漏代码（常见：静态 Map 无限累积、连接未关闭）。

7.2 案例二：CPU 飙高

常见原因：死循环、频繁 Full GC（大量分配）、正则回溯爆炸。

7.3 案例三：频繁 Full GC

常见原因与对策：

原因 对策
堆太小 调大 -Xmx，观察是否稳定
内存泄漏 堆 dump 分析，修复引用
大对象直接进老年代 -XX:PretenureSizeThreshold 或优化代码
系统换页（堆大于物理内存） 保持 -Xmx ≤ 物理内存 70%

8. 调优方法论（不盲目调参）

  1. 先观测：jstat / GC 日志跑一天，看正常基线。
  2. 定位问题：是停顿长（GC）还是吞吐低（业务）还是内存泄漏。
  3. 单点修改：每次只改一个参数，用数据验证。
  4. 对照：压测（wrk / JMH）前后对比 GC 停顿、QPS、P99。

9. 生产基线配置建议

监控指标：GC 频率（Full GC 每天应 < 几次）、P99 停顿、堆使用率曲线。
