6.4 踩坑点

1. 概念说明：可靠性三环节

消息丢失的三个环节：

“不丢”不等于”不重”：保证不丢必然可能重复（网络重试）——所以可靠性 = 不丢（机制保证）+ 不重（幂等消费）。

2. 第一层：生产端可靠发送（确认机制）

2.1 RabbitMQ Publisher Confirms

为什么确认回调里失败要”补偿”：发布确认只告诉你”这次没成”——不补偿 = 消息悄悄丢了。补偿手段：重试 N 次 → 仍失败进”本地待重发表”（配合对账）。

2.2 Kafka acks 对照

为什么选 all：acks=all = 主副本 + 所有从副本都落盘才确认——单副本确认（acks=1）在主节点宕机时丢数据。

3. 第二层：Broker 持久化

为什么”持久化”是三层中最容易漏的：发消息时没设 PERSISTENT，Broker 宕机重启 → 内存里的消息全没——配置了确认机制但没持久化，等于白配。

4. 第三层：消费端可靠消费

4.1 手动 ACK（核心配置）

三种确认方式：

方式 行为 风险
自动 ACK 一收到就确认 处理失败 = 消息丢失 ❌
手动 ACK（推荐） 成功才确认 正确
手动 REJECT/NACK 拒绝/重新入队 需配合死信（防死循环）

为什么必须配死信：basicNack(requeue=true) 无限重入队 = 坏消息死循环（CPU 烧满 + 正常消息被堵）——重试有上限，超限进死信队列。

5. 幂等消费（”不重”的保证）

为什么必须幂等：网络/重试机制天然会重复投递——消费端必须保证”同一条消息处理两次 = 处理一次”。

为什么”查重→处理→记录”要同一事务：分开了会出现”处理成功但记录失败”→ 下次重发又处理一次（不幂等）。同事务保证原子性。

  1. 消息表与业务表必须同库：跨库无法保证原子性——必须放在同一个数据源、同一个事务中。
  2. 重试必须有上限：若消息体本身有问题（如 payload 过大），无限重试会导致死循环；需设置 max_retries，超限进人工处理。
  3. 幂等消费是另一半：本地消息表只保证”消息一定发出”，消费端仍需幂等（见 §5），否则补发会导致重复扣库存。

10. 常见误用与陷阱

坑 现象/后果 解法
消息重复消费未做幂等 重试/补发导致同一消息处理多次（重复扣库存） 消费端用唯一键 + consume_log 表去重，查重/处理/记录同事务
消息堆积未处理 队列消息数持续增长，业务延迟增大 监控队列消息数 + 消费速率；扩容消费者；非核心消息临时降级
顺序消息误解 认为先进先出就全局有序，多消费者时会乱序 按业务 key 路由到同一队列/分区；单消费者或分区内有序
重试风暴 消费失败无限重试，打爆下游 + 坏消息堵队列 重试设上限（max-attempts=3），超限进死信；用延迟队列指数退避
死信队列未监控 坏消息进 DLQ 无人处理，业务静默漏单 DLQ 必须有消费者/监控，数量 > 0 即告警，定期人工重放
消费者位移/ACK 提交时机错误 自动 ACK 下处理失败消息丢失；手动 ACK 忘记 ack 导致重复 禁用自动 ACK，业务成功才 ack；失败走重试/死信；try/finally 保证 ack

踩坑点：
