设计模式 · 单例模式

GoF 创建型模式。意图 · 结构 · 线程安全四种写法 · 应用场景 · 优缺点 · 与其他模式对比。代码带详细注释。

1. 模式概述（意图）

单例模式（Singleton）保证一个类只有一个实例，并提供一个全局访问点。核心：把构造函数私有化，由类自己管理唯一实例。

2. 要解决的问题

问题 说明
重复创建浪费资源 连接池、线程池、配置对象创建昂贵
状态不一致 多个实例各自持有状态，互相不同步
全局访问不方便 需要到处传递实例引用

典型场景：数据库连接池、Redis 客户端、Spring 容器、日志记录器、配置管理器——这些对象一个就够，多了反而有害。

4. 代码实现（四种写法，从简单到线程安全）

4.1 懒汉式（线程不安全，仅教学）

5. 应用场景（JDK/Spring 实例）

场景 说明
Spring Bean 默认单例 @Bean 默认 singleton 作用域
JDK Runtime Runtime.getRuntime() 就是单例
数据库连接池 HikariCP DataSource 单例
线程池 Executors 返回的池对象全局共享
配置中心 应用配置只加载一次

6. 优缺点

优点 缺点
节省资源（一个实例） 违反开闭原则（扩展需改类）
全局访问方便 隐藏依赖（全局状态难测试）
保证状态一致 多线程实现要小心（写错有并发隐患）
懒加载可选 滥用导致”上帝对象”

现代观点：单例要克制——能用依赖注入（Spring 容器管单例）就不用全局静态单例；全局可变状态是测试和并发的地雷。

7. 与其他模式的关系

相关模式 关系
工厂模式 工厂常配合单例：返回唯一实例
享元模式 享元强调”复用共享对象”，单例是享元的一种特例
建造者模式 建造者常用于配置复杂对象，可与单例组合

8. 常见误用与陷阱

坑 现象 解法
懒汉式多线程创建多个 高并发下 instance 被 new 两次 用 DCL（volatile + 双重检查）或静态内部类
反射破坏单例 反射调私有构造器创建新实例 用枚举单例（JVM 保证唯一）
序列化反序列化出新实例 反序列化后 != 原实例 枚举单例 / 加 readResolve()
单例持有可变全局状态 测试互相污染，并发难排查 单例只放只读配置，可变状态交给请求上下文

1. 概念说明

入门篇掌握了 <script setup> 基础。进阶核心：

  • 组合式函数（Composable）：把可复用逻辑抽成函数（替代 mixin 的缺陷）。
  • 响应式原理：ref/reactive 基于 Proxy；理解 computed 缓存与 watch 时机。
  • 状态管理：跨组件共享状态用 Pinia（store），而非 props/emit 层层传。
  • 性能：虚拟列表、懒加载、缓存、减少响应式开销。

何时需要 Pinia：多个页面/组件共享同一状态（用户信息、购物车、主题）→ 用 store；只在父子组件 → props/emit。

Pinia vs Vuex：Pinia 是 Vue 官方推荐的新一代方案，移除 mutations、天然 TypeScript、模块扁平（每个 store 独立注册，无需 modules 嵌套）；Vuex 4 仍兼容旧项目，新项目首选 Pinia。

2. 组合式函数（核心技能）

组合式函数规范：useXxx 命名；返回响应式对象；可接受参数配置；内部状态不泄漏。

3. 响应式深入

性能注意：大数组/深层对象避免深度响应式（用 shallowRef）；循环里避免创建计算属性。

4.7 Store 设计规范

粒度划分 —— 按「业务域」而非「页面」拆 store：

做法 评价
一个巨型 appStore 装所有状态 ❌ 改一处全量订阅者重渲染，测试困难
每页一个 store ❌ 跨页共享状态被复制多份
按业务域拆（user / cart / order） ✅ 边界清晰，可独立测试与持久化

命名约定：文件名与 store id 一致（stores/order.ts → defineStore('order', ...)），导出函数统一 useXxxStore。

单一职责检查清单：

  1. state 只存原始数据，推导值一律放 getter（即 computed）。
  2. action 只编排本 store 的状态变更；跨域流程（如下单后清购物车）放 composable。
  3. 接口请求封装在 api/ 层，store 不直接写 fetch——换 HTTP 库时不动 store。
  4. 组件私有状态（弹窗开关、表单草稿）留在组件，不进 store。

3.5 三个必须配的安全项

项 不配的后果 配置
deny play all 任何人可绕过 HLS 直接拉 RTMP 原始流 在 application 内声明，播放只走 /hls/
on_publish 回调 推流地址泄漏后被人顶替推流 业务服务校验 token、流名归属，失败返回 403

3.6 本节专属坑

  • 回调超时：on_publish 默认通知超时很短，业务服务一旦慢查询就会把正常推流拒掉；回调里只做轻量校验（查 Redis / 本地缓存），不要查大表。
  • 录制文件永不清理：hls_cleanup 只清 ts，不清 record 目录，录制必须另配定时清理或对象存储转存。
  • 切片时长与 GOP 不匹配：推流端 -g 大于 hls_fragment 时，切片会被迫对齐关键帧，配置的 2s 实际变成 4s。
  • 模块停更风险：新内核 / 新 Nginx 版本下编译失败或 HLS 行为异常时，社区基本不会再修；这是选 SRS 的主要理由。

10. 典型案例：HLS 直播延迟从 12s 优化到 3s

问题背景：带货直播用标准 HLS（6s 切片 × 播放器缓冲 3 片 + CDN 缓存 60s），主播喊”3、2、1 上链接”后观众要 12 秒才看到，互动场直接冷场。

方案：四层压缩延迟——推流端 GOP 对齐切片 → 服务端 2s 切片 → 播放器 lowLatencyMode + 只缓冲 1-2 片 + 超限追帧 → CDN 分级缓存（m3u8 不缓存、ts 长缓存）。

踩坑点：

  • hls_fragment 盲目压到 0.5s：切片数暴涨，CDN 请求量翻 4 倍，回源把源站打死——2s 是平衡点。
  • m3u8 被 CDN 缓存 60s：观众永远落后一分钟且刷新无用，m3u8 必须 no-cache 或 1-2s 微缓存。
  • 主播端编码器 GOP 设 4s、切片 2s：切片被迫对齐 GOP 变成 4s，服务端配置全白改——推流端 GOP ≤ 切片时长。
  • 延迟优化不是免费的：缓冲越浅，弱网观众越容易卡顿——自适应降码率优先保流畅。

8. 典型案例：商品价格缓存一致性改造（改价后 5 分钟才生效）

问题背景：商品中心价格体系为三层缓存：Caffeine（本地 5min）+ Redis（1h）+ DB。运营在后台改价后，用户端最长 5 分钟仍显示旧价格，期间下单按旧价成交，每月产生约 300 单价格客诉；更严重的一次，某商品成本录错，调价指令发出 8 分钟后仍然在按错误价格自动下单，触发批量取消流程。

  3. 布隆过滤器上线时用 tryInit(10万, 1%)，半年后商品量涨到 80 万，实际误判率升到 8%，大量新商品被误拦”不存在”——布隆过滤器容量必须按预估增长留余量（按 3 倍规划），且定期重建。
  4. 改价接口高并发压测时发现”先更新 DB 再删缓存”的窗口内，读请求把旧值回填，不一致仍可能出现——对价格这类强敏感 key 加”延迟双删”（更新后 500ms 再删一次），窗口收敛到读请求耗时内。
  5. 三层缓存各自的 TTL（30s/1h/∞）没有对齐设计，排障时”哪里存的旧值”要逐层排查——建立分层 TTL 表（如上），所有缓存变更对照表执行，排查时按层定位。
