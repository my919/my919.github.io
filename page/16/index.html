10. 典型案例：安全门禁拦下一批”带病上线”

问题背景：某电商团队从”上线前人工安全检查”转向”CI 安全门禁”。接入首月，扫描在合并前拦下 9 个高危问题：2 处 SQL 拼接、3 个依赖 CVE、1 个硬编码数据库口令、3 处水平越权接口。

方案：SAST + 依赖扫描 + 密钥扫描 + 越权清单四道闸，全部进 CI，任一高危即阻断合并。

越权专项（人工 CR 清单，机器扫不出来）：每个新增接口回答三问——资源归属查了吗？userId 来自登录态还是入参？返回数据做了脱敏吗？

关键实践：门禁规则只拦 HIGH/CRITICAL，中低危生成周报跟进不阻塞；gitleaks 在 pre-commit 阶段也装一份，密钥根本进不了仓库。

踩坑点：依赖扫描误报多，直接 failBuildOnCVSS=7 会天天误伤——先用 9 起步跑稳，再逐步收紧；历史泄露进过 git 的密钥只删文件没用，必须”作废密钥 + 轮换”，git 历史里还躺着。

8. 典型案例：大促热点商品防打爆（热点参数限流）

问题背景：商城大促，某爆款商品上了首页 Banner。商品详情接口平时总 QPS 200 左右，活动开始后被单品刷到 8000+ QPS——普通 QPS 限流（阈值 1000）拦不住”单 key 打爆”：阈值调低会误伤其他商品，不调低则 product-service 线程池被爆款占满，其他商品也看不了。

方案（三层防护，层层递进）：

层 手段 阈值依据 兜底
网关 路由流控（资源名=路由 id） 全链路压测容量 × 1.2 429 JSON
服务 @SentinelResource QPS 限流 压测得出的容量水位 “系统繁忙”
热点 ParamFlowRule 按 skuId 单品缓存可支撑的回源量 旧快照降级

关键代码（热点限流 + 旧快照降级）：

踩坑点：

  1. 热点参数限流只支持基本类型 / String 参数——如果接口传的是 ProductQuery 对象，paramIdx 取不到值，规则形同虚设；改造时把 skuId 单独提为第一个参数。
  2. 资源名必须与 @SentinelResource 的 value 逐字符一致，控制台配了 getProduct、代码里是 get_product 时静默不生效。
  3. 只在控制台点过规则没落 Nacos——发版重启后限流全丢，大促当天裸奔（本例用 param-flow 数据源持久化）。
  4. 降级返回旧快照时忘了标记 stale，用户拿旧价格下单引发资损——降级数据必须可见地”打折信任”。

9. 常见误用与陷阱

坑 现象/后果 解法
Sentinel 规则只配在控制台 服务重启后规则全部丢失，限流裸奔 Nacos 数据源持久化（datasource.rule-type），控制台只做调参
blockHandler / fallback 方法签名不一致 兜底方法永远不触发，BlockException 直接抛给用户 参数列表与原方法一致，末尾追加 BlockException/Throwable
@SentinelResource 打在同类内部调用上 不走 AOP 代理，限流熔断静默失效 从外部 Bean 调用，或注入自身代理（AopContext）
网关过滤器里做阻塞操作（查库/同步 HTTP） WebFlux 事件循环线程被卡，全网关吞吐暴跌 用 reactive 客户端（WebClient/R2DBC），重逻辑下沉到下游服务
Feign 重试与读超时叠加 一次 5s 超时被重试放大成 3 次调用，下游雪崩 重试次数设 0、按最坏耗时定超时、写接口幂等
fallback 把所有异常都吞掉 真实 bug（如 SQL 报错）被降级掩盖数周 fallback 里必须记录异常日志+告警，与 blockHandler 分开排查
Nacos 心跳超时误摘实例 服务明明在线，调用方却 404/连接拒绝 排查 GC 停顿与网络抖动，客户端与服务端版本对齐，必要时调大心跳超时

11. 典型案例：敏感配置加密（数据库密码与 JWT 密钥入库）

问题背景：安全审计发现 application-prod.yml 里数据库密码、JWT 签名密钥全是明文，且文件已提交 Git 历史——拿到仓库读权限就等于拿到生产库。要求：仓库与配置中心里的敏感值必须密文，主密钥不落代码与镜像。

关键代码与配置：

踩坑点：

  1. 图省事把主密钥也写进 yml 或启动脚本——等于锁和钥匙放一个抽屉；主密钥只能走环境变量/Secret，且与代码分开管理。

服务 · 高可用保障

从 0 到生产级稳定性。可用性度量 · 冗余与故障转移 · 超时重试熔断 · 限流降级 · 容量规划 · 故障演练与复盘。代码带详细注释。

1. 概念说明

高可用（HA）目标：服务持续可用，单点故障不影响整体。核心思想是冗余 + 故障转移 + 优雅降级。

可用性度量（SLA）：

可用性 年停机时间 俗称
99% 3.65 天 2 个 9
99.9% 8.76 小时 3 个 9
99.99% 52.6 分钟 4 个 9
99.999% 5.26 分钟 5 个 9

可用性公式：MTBF / (MTBF + MTTR)——减少故障次数（MTBF）与缩短恢复时间（MTTR）同样重要。99.9% 靠自动化监控+快速回滚即可实现，无需过度设计。

2. 冗余架构（消除单点）

层 冗余方案
入口 多 Nginx + Keepalived VIP（见 Nginx 篇）

注册中心 Nacos 集群（≥3 节点）
数据库 主从 + 半同步 / 集群
Redis 主从 + 哨兵 / 集群
MQ 多副本（Kafka 副本 ≥3）
机房 多可用区部署（跨区容灾）

反单点检查：架构图里找”唯一实例”——任何只有一份的组件都要冗余。

8. 典型案例：商品价格缓存一致性改造（改价后 5 分钟才生效）

问题背景：商品中心价格体系为三层缓存：Caffeine（本地 5min）+ Redis（1h）+ DB。运营在后台改价后，用户端最长 5 分钟仍显示旧价格，期间下单按旧价成交，每月产生约 300 单价格客诉；更严重的一次，某商品成本录错，调价指令发出 8 分钟后仍然在按错误价格自动下单，触发批量取消流程。

方案：按”写路径改造 + 读路径降级 + 本地缓存广播失效”三步收紧一致性窗口，把改价生效时间从 5 分钟压到 1 秒内：

层 失效机制 生效时间 兜底
DB → MQ 本地消息表（同事务） 毫秒级 扫描补偿
MQ → Redis 消费者 DEL <50ms 重试 5 次+告警
Redis → 本地 Pub/Sub 广播 evict <100ms 本地 TTL 30s 收敛
极端情况 本地 TTL 到期 ≤30s 可接受的最终一致窗口

  4. 改价接口高并发压测时发现”先更新 DB 再删缓存”的窗口内，读请求把旧值回填，不一致仍可能出现——对价格这类强敏感 key 加”延迟双删”（更新后 500ms 再删一次），窗口收敛到读请求耗时内。
  5. 三层缓存各自的 TTL（30s/1h/∞）没有对齐设计，排障时”哪里存的旧值”要逐层排查——建立分层 TTL 表（如上），所有缓存变更对照表执行，排查时按层定位。

第 2-5 周 每周五迭代评审 + 回顾，速率数据化（28→32 点） 速率稳定，交付日期可预测
第 6 周 回归测试 + 灰度 20% 客户 → 全量 按冻结范围如期上线

踩坑点：

  • 救火第一步不是加班而是砍范围：范围不冻结，所有流程改进都是白忙。
  • 站会开成汇报会：只允许回答”昨天做了什么/今天做什么/有什么阻塞”，超时议题会后单聊。

9. 典型案例：API 限流防刷

问题背景：某开放 API 平台被恶意刷接口，单 IP 每秒发起上千次请求，导致后端数据库连接池打满、正常用户请求超时。需要在 Nginx 层做多层限流：按 IP 限请求速率、按 IP 限并发连接数、对登录等敏感接口单独加严，保护后端服务。

方案：

限流维度 配置 阈值 作用
请求速率 limit_req 10r/s + burst 20 防刷接口
并发连接 limit_conn 单 IP 20 防连接耗尽
敏感接口 limit_req 2r/s + burst 5 防爆破登录
限流响应 limit_req_status 429 返回 Too Many Requests

关键配置：

踩坑点：

  1. limit_req 的 burst + nodelay 组合：burst=20 nodelay 表示突发 20 个请求立即处理，超过的返回 429。不加 nodelay 则突发请求会排队延迟处理，可能导致请求超时。
  2. 限流区共享内存大小：zone=api_limit:10m 中 10m 是共享内存大小，约可存 16 万个 IP 状态。高并发场景若太小会导致限流失效（Nginx 会丢弃无法存储状态的请求），需按 IP 数量调大。
  3. $binary_remote_addr vs $remote_addr：用 $binary_remote_addr（二进制，4 字节）比 $remote_addr（字符串，7-15 字节）省内存，限流区能存更多 IP。
