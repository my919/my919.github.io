1. 概念说明

消息可靠性三问（面试与生产核心）：

  1. 不丢：消息从生产 → broker → 消费，任何环节都不能丢。
  2. 不重：网络重试导致重复投递，消费端必须幂等。
  3. 不乱：需要顺序的场景保证按序处理。

9. 典型案例：库存扣减的幂等消费

问题背景：订单服务发消息通知库存服务扣减库存。由于网络重试、消费者重启后 offset 未提交等原因，同一条”扣库存”消息可能被投递多次。若库存服务不幂等，会导致超卖（库存被扣成负数）。

方案：

步骤 说明
① 查重 用 order_id 查 consume_log 表（order_id 是主键）
② 去重 已存在说明处理过，直接返回成功（不重复扣）
③ 业务 扣减库存（UPDATE stock SET qty=qty-1）
④ 记录 插入 consume_log，与扣库存同事务

踩坑点：

  1. 查重与业务必须同事务：若先查再扣但分两个事务，会出现”查不到 → 扣库存 → 写记录失败”→ 下次又扣一次。必须用 INSERT ... ON DUPLICATE KEY 或同事务包裹。

10. 常见误用与陷阱

坑 现象/后果 解法
消息重复消费未做幂等 重试/重平衡导致重复处理（重复扣库存/重复发券） 用消息唯一 ID + 数据库唯一键（INSERT IGNORE）或 Redis SETNX 去重
消息堆积未处理 consumer lag 持续增长，业务延迟增大甚至超时 监控 lag 告警；扩容消费者（受分区数限制）；临时降级非核心消费

死信队列未监控 坏消息进 DLQ 无人处理，业务静默漏单 DLQ 必须有消费者/监控，数量 > 0 即告警，定期人工重放

9.6 踩坑点

  • 超时层层不设：Feign、网关任一处无限等待，一个慢下游吃光整条链路线程池——全链路统一超时，且上游超时要大于下游超时之和。
  • 写接口盲目重试：非幂等扣减被重试 2 次，库存扣了 3 份——重试白名单化，写接口必须带幂等键。
  • 降级静默：fallback 直接返回空数据，无日志无打点，业务故障无人知——降级路径必须埋点告警并接入异步补偿。
  • 熔断器粒度过粗：整个服务一个熔断器，边缘接口故障把核心扣库存也熔断——按核心方法/业务资源分组隔离。
  • 链路在 MQ 处断开：HTTP 头透传了 traceId，发消息后断链——消息头携带 traceId，消费端恢复 MDC 续接。

分布式事务核心指标：

  • 强一致（CP）：所有节点要么全成功要么全失败（XA/AT/TCC）。
  • 最终一致（AP）：先各自提交，通过异步补偿最终一致（SAGA/消息）。

维度 Seata AT 模式 本地消息表 / 事务消息

8.4 完整代码骨架

建表（订单库的消息表与业务表必须同库，才能纳入同一本地事务）：

① 生产端：业务数据与消息同事务写入。

② 轮询投递：至少一次（at-least-once），进程崩溃可重试。

③ 消费端：先占幂等坑，再执行业务。

④ 对账兜底：重试耗尽、消息进死信、消费遗漏时的最后防线。

一致性保证链条：同库事务写业务+消息（不丢）→ 定时重发（可达）→ 消费端幂等（不重）→ 对账（最终收敛）。

8.5 踩坑点

  • 消息表与业务表不同库：无法纳入同一本地事务，写库成功写表失败就会丢消息——outbox 必须与业务共库。
  • 先发消息再写库：业务回滚了消息却已发出，出现「幽灵订单」，库存凭空被扣——严格先写库（含消息表），再异步投递。
  • 消费端不幂等：at-least-once 重试导致重复扣库存、重复扣款——先插入幂等记录再处理，唯一键冲突即跳过。
  • 没有对账：消息进入死信后无人感知，三方数据永久不一致——定时对账 + 死信告警 + 自动补偿。
  • AT 模式热点行：秒杀商品同一行被全局锁串行化，TPS 上不去——热点链路改用本地消息表 / Redis 预扣。
  • AT 中开异步线程：XID 只在同步调用链透传，子线程分支脱离全局事务无法回滚——跨线程显式传播 XID 或改为同步。
