10. 典型案例：5 人团队延期项目救火

问题背景：某 SaaS 客户端改版项目原计划 8 周上线，第 4 周进度只完成 30%，需求还在每周新增，成员天天加班但里程碑持续后移。

方案：砍范围、定节奏、透明化——需求重排冻结（砍 40% 进二期）→ 转双周迭代 + 每日 15 分钟站会 → 看板可视化 + 风险每周滚动刷新 → 6 周后按新范围如期交付。

周 动作 产出
第 1 周 需求重排：与业务方逐条确认优先级，砍 40% 进二期 冻结版需求清单（变更走评审）
第 1 周 迭代规划：拆 2 周迭代，每个需求写验收标准 迭代 Backlog 30 点（留 20% 缓冲）
第 2-5 周 每日站会只答三问，阻塞项当场指派 owner 看板流动 + 阻塞项 <24h 响应
第 2-5 周 每周五迭代评审 + 回顾，速率数据化（28→32 点） 速率稳定，交付日期可预测
第 6 周 回归测试 + 灰度 20% 客户 → 全量 按冻结范围如期上线

踩坑点：

  • 救火第一步不是加班而是砍范围：范围不冻结，所有流程改进都是白忙。
  • 站会开成汇报会：只允许回答”昨天做了什么/今天做什么/有什么阻塞”，超时议题会后单聊。
  • 迭代中途插需求不换等量任务：速率失真，交付日期永远测不准——插 5 点必须移出 5 点。
  • 风险只登记不跟踪：每周评审风险状态（恶化/缓解/关闭），无 owner 的风险等于没有风险。

坑 现象/后果 解法

迭代中途硬插需求 速率失真，交付日期永远测不准 插需求置换等量任务，紧急需求走评审
里程碑=deadline 只定死线不定依赖，到期才发现被卡 里程碑倒排关键依赖，风险前置暴露

14. 典型案例：个人项目从 0 到上线（90 天）

问题背景：想做一款”云书签”工具（收藏/分类/全文搜索）。第一版规划了团队协作、浏览器插件、移动端 App……半年写了三个废弃仓库，一个都没上线。

方案：用全流程砍出 MVP——两周需求（只保留”收藏 + 搜索”，其余全部进”不做清单”）→ 一周架构（单体 + Postgres + Docker）→ 六周迭代开发（双周一个里程碑）→ 两周测试与上线（VPS + CI/CD + 备份监控）。

落地节奏（真实时间线）：

  • 第 1-2 周：需求裁到一页纸，画完 3 个页面原型，其余全写进”不做清单”。
  • 第 3-8 周：三个双周里程碑（收藏 CRUD → 全文搜索 → 部署脚本），每个里程碑末自测 + 打 tag。
  • 第 9-10 周：买域名 + HTTPS（Caddy 自动签证书）、备份 cron（pg_dump 每日异地）、UptimeRobot 探活告警。
  • 第 10 周末：邀请 5 个朋友试用，反馈排进 v1.1，而不是推翻重来。

踩坑点：

  • “本地能跑，上线就挂”：环境变量/时区/数据库版本不一致——第一天就容器化，开发与生产同构。
  • 没有备份意识：上线第 3 周误删数据才想起 pg_dump——备份自动化必须写进”完成定义”。
  • MVP 定义漂移：做到一半又想加插件，靠”不做清单”顶住，新想法一律进 backlog。
  • 没监控：服务挂了两天靠用户说出来才知道——探活告警是上线检查项，不是”以后再说”。

Nginx · 反向代理、负载均衡与高可用

从最小反向代理到生产级高可用。proxy_pass 路径规则 · upstream 负载均衡策略 · 健康检查与故障摘除 · 超时缓冲与 WebSocket · 限流防刷 · 会话保持 · Keepalived 双机高可用 · 性能调优。配置带详细注释。

技术栈速查

类别 选型 用途
反向代理 Nginx 1.28 负载均衡
高可用 Keepalived 2.3 VIP 漂移
健康检查 nginx upstream / 外部脚本 摘除故障节点
会话 Redis 会话共享 无状态化

1. 概念说明

反向代理是系统入口：客户端只认识 Nginx，真实后端藏在 upstream 里——发布、扩缩容、灰度都对客户端无感。

负载均衡：多台应用服务器分担流量——提升吞吐（横向扩展）与可用性（单点故障不影响）。

Nginx 核心：upstream（后端服务器组）+ proxy_pass（转发）+ 调度算法。

高可用：Nginx 自身不能是单点——两台 Nginx 用 Keepalived 共享虚拟 IP（VIP），主挂备自动接管。

现代替代：K8s Ingress、云 LB（ALB/SLB）；但 Nginx 仍是自建与边缘网关主力。

2. 最小反向代理

头 作用
Host 透传原域名，后端按域名路由/生成绝对链接
X-Real-IP 客户端真实 IP（单层代理）
X-Forwarded-For 代理链 IP 列表，$proxy_add_x_forwarded_for 自动追加
X-Forwarded-Proto 客户端是 http 还是 https（后端生成 https 链接必需）

3. proxy_pass 路径规则（高频坑）

记忆法：proxy_pass 的 URL 部分会替换掉 location 匹配的部分；不带路径（只有 host:port）则原样透传。改一条 proxy_pass 必跑 nginx -t + 抓包/日志确认后端实际收到的路径。

4. upstream 与负载均衡策略

策略对比（完整版）：

策略 写法 分发逻辑 适用

1. 概念说明：可靠性三环节

消息可靠性三问（面试与生产核心）：

  1. 不丢：消息从生产 → broker → 消费，任何环节都不能丢。

消息丢失的三个环节：

“不丢”不等于”不重”：保证不丢必然可能重复（网络重试）——所以可靠性 = 不丢（机制保证）+ 不重（幂等消费）。

可靠性铁律：消息丢失的责任最终在消费端兜底——生产者/Broker 尽量可靠，但消费端必须能容忍任意环节的重复与乱序（幂等 + 重试 + 对账）。

10. 常见误用与陷阱

坑 现象/后果 解法
-Xms 与 -Xmx 不一致 运行期堆扩容抖动，GC 停顿忽长忽短 生产 -Xms = -Xmx，启动即定死
-Xmx 设成物理内存/容器 limit 上限 堆外+Metaspace+线程栈被挤没，容器被 OOM Killer 杀 堆 ≈ 容器内存的 70-75%（或 MaxRAMPercentage=75）
误用 jmap -F 强制 dump 全程 STW，服务假死几分钟，线上事故扩大 用 jcmd GC.heap_dump 或 OOM 自动 dump；-F 仅救命用
GC 日志未开 出问题无线索，性能退化只能盲猜 启动就配 -Xlog:gc*:file=...，轮转防写满磁盘
Metaspace 未设上限 动态类泄漏静默吃光机器内存 -XX:MaxMetaspaceSize=512m 显式封顶
只盯堆内存不看堆外 堆用 60% 却被 OOM Killer 杀（DirectBuffer/Netty/gzip） NMT 跟踪堆外 + 容器内存告警与堆告警分开
OOM 自动 dump 未配路径/未留磁盘 dump 写到默认目录或写满盘，二次事故 HeapDumpPath=/data/dumps + 该目录磁盘告警
