9. 典型案例：NocoBase 工单 + n8n 自动化端到端

问题背景：客服工单原来靠群里吼：新工单没人认领、处理超时没人管、处理结果要人工同步回系统，月均漏单 30+。

方案：NocoBase 建工单表与页面（收集/流转/看板）→ 工单创建触发 Webhook 给 n8n → n8n 校验幂等后按类型分派、企微通知、24h 未关单升级 → 处理结果回调 NocoBase 回写状态。全程幂等可重试。

踩坑点：

  • n8n 节点失败默认静默：必须给工作流挂 Error Workflow + 告警，否则分派失败没人知道，漏单换个地方继续漏。
  • 双向同步没有幂等：NocoBase → n8n → 回写 NocoBase 又触发 Webhook，无限循环刷爆队列——回写用专用 API Key、只更新状态字段，且事件过滤掉 source=automation 的更新。
  • n8n 里硬编码 API Token：换密钥要改几十个节点——统一走环境变量/凭据管理，按流程分配最小权限 Key。
  • 升级通知的 Wait 节点等 24h：n8n 重启后内存队列会丢——Wait 必须用持久化模式（Redis/DB）。

10. 常见误用与陷阱

坑 现象/后果 解法
Webhook 无重试 n8n 发布重启那几分钟的工单永久丢失 服务端 Webhook 配重试 + 定时对账任务兜底扫漏
无幂等键 重试导致重复分派/重复通知 业务单号做幂等键，处理前先查是否已存在
双向同步环形更新 A 写 B、B 写 A，死循环打爆两边 回写走专用凭据并打来源标记，事件按来源过滤
流程无 Error Workflow 节点失败静默，问题一周后才发现 每个工作流挂统一错误处理 + 告警
Token 硬编码 密钥泄露或轮换时全流程返工 凭据走环境变量/密钥管理，最小权限分 Key
schema 漂移 平台改了字段名，n8n 里静默取到 undefined 字段变更进变更流程；关键节点加字段存在性校验

10. 常见误用与陷阱

坑 现象/后果 解法
-Xms 与 -Xmx 不一致 运行期堆扩容抖动，GC 停顿忽长忽短 生产 -Xms = -Xmx，启动即定死
-Xmx 设成物理内存/容器 limit 上限 堆外+Metaspace+线程栈被挤没，容器被 OOM Killer 杀 堆 ≈ 容器内存的 70-75%（或 MaxRAMPercentage=75）
误用 jmap -F 强制 dump 全程 STW，服务假死几分钟，线上事故扩大 用 jcmd GC.heap_dump 或 OOM 自动 dump；-F 仅救命用
GC 日志未开 出问题无线索，性能退化只能盲猜 启动就配 -Xlog:gc*:file=...，轮转防写满磁盘
Metaspace 未设上限 动态类泄漏静默吃光机器内存 -XX:MaxMetaspaceSize=512m 显式封顶
只盯堆内存不看堆外 堆用 60% 却被 OOM Killer 杀（DirectBuffer/Netty/gzip） NMT 跟踪堆外 + 容器内存告警与堆告警分开
OOM 自动 dump 未配路径/未留磁盘 dump 写到默认目录或写满盘，二次事故 HeapDumpPath=/data/dumps + 该目录磁盘告警

从 0 到生产选型。事务演进与问题 · XA/AT/TCC/SAGA 对比 · Seata 实战 · 可靠消息最终一致 · 对账与补偿。代码带详细注释。

技术栈速查

类别 选型 用途
框架 Seata 2.x 分布式事务

数据库 MySQL 8.4 事务存储

1. 概念说明

为什么需要分布式事务：微服务拆分后，一次下单跨”订单库 + 库存库 + 账户库”三个独立事务——本地事务无法保证一致性。

分布式事务核心指标：

  • 强一致（CP）：所有节点要么全成功要么全失败（XA/AT/TCC）。
  • 最终一致（AP）：先各自提交，通过异步补偿最终一致（SAGA/消息）。

工程共识：互联网业务 90% 用最终一致；只有资金类强约束场景用强一致。能用单库事务绝不分布式。

2. 四种方案对比

方案 原理 一致性 侵入性 性能 适用
XA 数据库原生 2PC 强 低 差（锁久） 老旧系统
AT 代理层生成反向 SQL 强 低 中 Seata 首选
TCC 业务三方法(Try/Confirm/Cancel) 强 高 高 资金/高并发
SAGA 正向+补偿事务 最终 中 高 长流程

2PC 问题（XA 的短板）：协调者单点、同步阻塞（资源锁定）、脑裂时不一致——所以现代方案用 AT/TCC/SAGA 规避。

7. 选型决策树

8. 典型案例：订单-库存-账户三服务分布式事务

8.1 问题背景

一次下单要跨三个独立服务与数据库：订单服务写 orders、库存服务扣 sku_stock、账户服务扣 account.balance。三个本地事务无法用 @Transactional 统一提交或回滚，必须选择分布式事务方案。团队对 Seata AT 与本地消息表/事务消息做了对比选型。

8.2 两种落地方案对比

维度 Seata AT 模式 本地消息表 / 事务消息
一致性 强一致（TC 协调 + 全局锁） 最终一致（通常秒级，异常时分钟级）
性能 中：undo 镜像 + 全局锁，热点行易瓶颈 高：本地短事务，无跨库锁等待
业务侵入 低：一个 @GlobalTransactional 中：消息表、轮询、幂等、对账都要自建
额外依赖 TC Server + 每库 undo_log MQ + 定时任务 + 对账任务
适用场景 低并发、内部系统、余额/库存要求实时强一致 高并发电商下单，容忍短暂「处理中」状态
失败处理 自动反向 SQL 回滚 消息重试 + 死信 + 对账补偿

结论：下单主链路用本地消息表（高并发最终一致），资金划拨等少数强一致点用 Seata AT。RocketMQ 事务消息可省掉自建 outbox 轮询（半消息 + 事务回查）；本案例用 Kafka + 本地消息表演示完整骨架。

8.3 方案结构（本地消息表）

8.4 完整代码骨架

建表（订单库的消息表与业务表必须同库，才能纳入同一本地事务）：

① 生产端：业务数据与消息同事务写入。

② 轮询投递：至少一次（at-least-once），进程崩溃可重试。

③ 消费端：先占幂等坑，再执行业务。

④ 对账兜底：重试耗尽、消息进死信、消费遗漏时的最后防线。

一致性保证链条：同库事务写业务+消息（不丢）→ 定时重发（可达）→ 消费端幂等（不重）→ 对账（最终收敛）。

8.5 踩坑点

  • 消息表与业务表不同库：无法纳入同一本地事务，写库成功写表失败就会丢消息——outbox 必须与业务共库。
  • 先发消息再写库：业务回滚了消息却已发出，出现「幽灵订单」，库存凭空被扣——严格先写库（含消息表），再异步投递。
  • 消费端不幂等：at-least-once 重试导致重复扣库存、重复扣款——先插入幂等记录再处理，唯一键冲突即跳过。
  • 没有对账：消息进入死信后无人感知，三方数据永久不一致——定时对账 + 死信告警 + 自动补偿。
  • AT 模式热点行：秒杀商品同一行被全局锁串行化，TPS 上不去——热点链路改用本地消息表 / Redis 预扣。
  • AT 中开异步线程：XID 只在同步调用链透传，子线程分支脱离全局事务无法回滚——跨线程显式传播 XID 或改为同步。

9. 常见误用与陷阱

坑 现象/后果 解法
TCC 空回滚 Try 请求因丢包未执行，Cancel 先到，回滚了一笔从不存在的冻结 Cancel 先查 xid/分支记录；不存在则插入空回滚标记后直接返回成功
TCC 悬挂 空回滚后迟到的 Try 才执行，冻结的资源再无人 Confirm/Cancel Try 前检查是否已回滚；存在空回滚标记则拒绝 Try
TCC 三方法不幂等 TC 超时重试 Confirm/Cancel，造成重复扣款 每阶段以 xid+branchId 建唯一记录，已处理直接返回成功
AT 全局锁热点 热点账户/商品行排队等全局锁，吞吐骤降、锁等待超时 热点数据改 TCC 或本地消息表；合并扣减、缩短全局事务
消息重复消费 at-least-once 投递加消费重试，库存/余额被重复扣 消费端 event_id 唯一表幂等，叠加业务状态机与唯一索引
本地消息表无对账 死信/漏消费永久卡单，且无任何告警 定时对账三方数据，死信告警，状态机驱动自动补偿
XID 跨线程/异步丢失 子线程或 MQ 中的分支不加入全局事务，失败无法回滚 同线程同步调用；必须异步时手动传播 XID，或改用最终一致方案
手工修改参与库数据 undo_log 镜像与实际数据不符，AT 回滚失败、脏数据残留 禁止手工 DML；回滚失败查 rollback_info 后人工对账补偿

8. 典型案例：防腐层落地实战

问题背景：某零售平台订单服务需要对接遗留的会员系统 legacy-member-svc（SOAP 接口、字段如 LEVEL_CODE=3 的魔法数字、命名混乱）。若订单领域模型直接依赖其 DTO，遗留系统任何字段变更都会污染订单模型。

方案：在订单上下文的基础设施层建防腐层（ACL），把遗留系统翻译成本上下文的通用语言：

决策点 选择 理由
防腐层归属 订单侧基础设施层 谁受益谁负责，不改遗留系统
接口定义 领域层定义 MemberGateway 依赖倒置，实现可替换
翻译方向 遗留 DTO → 本上下文模型 领域层只见通用语言

关键设计：

踩坑点：团队起初图省事，在应用服务里直接调 LegacyMemberClient 并写死 levelCode == 3；两周后遗留系统把 3 改成 4，只能全库翻找魔法数字。收敛到防腐层后，遗留系统变更只需改 MemberTranslator 一处，单测覆盖翻译逻辑即可回归。另外注意：防腐层不等于”随便包一层”，翻译器要有单测，否则防腐层自身就成了新的遗留代码。
