第二章：SpringBoot 多环境配置：Profile 激活与优先级

概念基础

多环境配置让同一份代码在开发、测试、生产之间只切换配置、不改代码：

  1. Profile 机制：Spring 用 Profile 在 dev / test / prod 之间切换配置；本仓库（springboot）以 application.yaml 承载公共配置，各环境文件只写差异项；相同 key 时环境文件覆盖公共配置。
  2. 激活方式多样：配置文件 spring.profiles.active、环境变量 SPRING_PROFILES_ACTIVE、启动参数 --spring.profiles.active=prod，本项目默认 dev。
  3. 职责划分：端口、应用名、框架级默认值放公共；数据库/Redis 地址与密码、日志级别、Swagger 开关放环境。
  4. 敏感信息外部化：密码经环境变量注入，生产禁止提交 Git；更大规模可接 Nacos 配置中心（共享 dataId + 环境 dataId，后者覆盖前者）。
  5. 测试隔离：src/test/resources/application.yaml 独立于业务 Profile，用 H2 内存库与 Mock 中间件保证 gradlew test 稳定可重复。

微服务多模块 + Nacos spring.config.import 见 第二章：Spring Cloud 多环境配置与 Nacos：Profile 与 config.import 分层（2025.1.x 无 bootstrap，与单体 Profile 思路不同）。

  5. application-{profile}.yaml（jar 外）
  6. config/application.yaml
  7. jar 外 application.yaml
  8. jar 内 config/application-{profile}.yaml
  9. jar 内 application-{profile}.yaml

  11. jar 内 application.yaml（最低，打仓库默认值）

第十一章：Java本地持久化队列方案与实战

概念基础

  1. 是什么：任务先写入磁盘再消费的本地队列——进程重启、宕机后任务不丢失，重启自动恢复继续消费。
  2. 为什么需要：内存队列（如 LinkedBlockingQueue）重启即丢；引入 Redis/MQ 又增加部署与运维成本——本地持久化队列在轻量与可靠之间取得平衡。
  3. 三大成熟方案：Chronicle Queue（MMAP 磁盘映射、零依赖、超高吞吐、金融级）、LMDBQueue（嵌入式 KV、极轻量）、MapDB（纯 Java、一行代码建队列）。
  4. 核心能力：磁盘存储 + 重启恢复 + 自动序列化——任务对象只要实现 Serializable 即可入队出队。
  5. 选型记忆：最强成熟方案选 Chronicle Queue，最简单上手选 MapDB。

🔥 最佳推荐（3 个真正的本地持久化队列）

按易用性、性能、成熟度排序：

1. Chronicle Queue（企业级首选，零依赖、高性能）

最适合你：本地持久化 + 可序列化 + 超高吞吐 + 重启不丢

  • 纯 Java 本地队列
  • 磁盘持久化（MMAP）
  • 支持任意对象序列化
  • 无锁、低延迟、生产级稳定
  • 支持多线程读写
  • 重启自动恢复数据

Maven 依赖

最简 Demo（入队 + 出队 + 持久化）

特点：

  • 关机、重启、kill 进程 都不丢数据
  • 支持超大队列（GB 级）
  • 序列化自动完成
  • 金融系统广泛使用

2. LMDBQueue（极轻量、嵌入式、超快）

极简本地持久化队列

  • 基于 LMDB 嵌入式数据库
  • 极快、极小、稳定
  • 支持 key/value 持久化
  • 天然支持序列化

3. MapDB（嵌入式 Java 数据库，自带持久化队列）

最简单、最容易上手

  • 一行代码创建持久化队列
  • 支持序列化
  • 纯 Java
  • 适合小项目、后台任务

一句话选型：

  • 极致吞吐/低延迟、可投入学习成本 → Chronicle Queue
  • 5 分钟集成、中小流量后台任务 → MapDB
  • 已依赖 H2、需要事务语义 → MVStore
  • 极致读性能、可接受 JNI → LMDB

生产注意事项

  1. 容量与滚动：Chronicle Queue 按天滚动 .cq4 文件，需配置保留策略防磁盘写满；MapDB / MVStore 单文件持续增长，要定期 compact 或归档清理。
  2. 消费位点：Chronicle 的 Tailer 位点需自行持久化，否则重启后从头或从尾重复消费；MapDB / MVStore「出队即删」，天然无位点问题。
  3. 崩溃一致性：MVStore / MapDB 入队后记得 commit()；Chronicle 依赖 MMAP flush 语义。kill -9 场景下的丢失窗口以实际压测为准，不要凭文档承诺设计。
  4. 多实例边界：本地队列不能跨进程共享——集群部署时每个实例只消费自己的队列文件；需要全局可见的任务请升级 Redis / RocketMQ。
  5. 监控：把 size() 暴露到 Micrometer 指标，队列积压时告警；消费线程挂掉时队列会静默堆积，务必加消费线程存活探针。

第十章：Redisson 红锁 RedLock 原理与生产实践

发表于 2026-05-05 更新于 2026-10-25 分类于 分布式 本文字数： 5.6k 阅读时长 ≈ 5 分钟

第十章：Redisson 红锁 RedLock 原理与生产实践

概念基础

  1. 要解决的问题：普通 Redis 锁是单主节点锁——加锁成功后尚未同步到从节点就宕机，主从切换后锁凭空消失，两个客户端可能同时持锁。
  2. 核心思想：把锁同时写到 N 个完全独立的 Redis 主节点上，过半节点加锁成功且总耗时小于锁有效期才算加锁成功。
  3. 为什么有效：基于**多数派（quorum）**机制，任一节点宕机/切换都不影响多数节点上的锁记录，从根本上规避单点故障丢锁。
  4. 代价：要写多个节点，性能低于普通锁；节点必须相互独立（非主从、非集群）且为奇数个。
  5. 适用边界：秒杀、库存、支付、账务等核心强一致场景用 RedLock；后台任务等非核心场景普通 Redisson 锁即可。

最标准、生产可直接用的 Redisson RedLock 实现，包含：配置 + 代码 + 原理 + 生产注意事项

一、先记住一句话

RedLock = 多个独立 Redis 主节点 + 过半写入成功才算加锁成功
目的：彻底解决主从切换丢锁问题
代价：写 N 个节点 + 严格多数派判定，部署与性能成本都高于单节点锁。

二、先懂普通 RLock：可重入与看门狗的实现

RedLock 是架在单节点 RLock 之上的组合，先看清 RLock 在 Redis 里的形态：

  • 加锁：一段 Lua 脚本——Hash 不存在则 HSET + PEXPIRE 新建；已存在且 field 是本线程则 HINCRBY 重入并刷新过期；否则 PTTL 返回剩余存活时间，客户端据此自旋等待。三段逻辑一次往返、原子执行。
  • 解锁：同样是 Lua——HINCRBY -1，归零才真正 DEL；不是自己的锁返回 nil，Java 侧抛 IllegalMonitorStateException。
  • 看门狗：不显式传 leaseTime 时，加锁成功即注册定时任务（默认 30s / 3 = 10s 一次）执行续期；进程死亡 → 续期消失 → 锁到期自然释放。

为什么 RedLock 要逐节点续期：红锁对 N 个节点各持一把 RLock，任一节点上的锁过期而未续约，多数派就可能凑不齐——看门狗按节点独立工作，与红锁的过半判定互不影响。

3. 性能比普通锁低

演进史：为什么不能写成「先 SETNX 再 EXPIRE」

  1. 第一代：SETNX + EXPIRE 两条命令——加锁成功后、设过期前进程崩溃 → 永不释放，死锁。病根是两条命令不是原子。
  2. 第二代：SET key val NX PX 30000 一条命令——Redis 2.6.12+ 原生支持，原子加锁 + 过期，解决死锁。
  3. 第三代：+ Lua 原子解锁——「GET 判断归属再 DEL」合成一个脚本，解决「自己的锁过期后被他人加上，自己又执行 DEL 误删」。
  4. 第四代：+ 看门狗续期（Redisson）——业务没执行完锁先过期的问题，靠后台线程定期延长有效期解决。

每一步演进都对应一类线上事故——你手写出来的多半是第二代，这是「禁止手写」的论据。

锁续期与看门狗（Redisson 怎么做的）

  • lock() 不传 leaseTime 时默认锁 30s（lockWatchdogTimeout），后台每 10s（有效期的 1/3）检查一次：线程还持有就续回 30s；
  • 显式传 tryLock(10, 30, SECONDS) 里的 leaseTime 则看门狗关闭——到期自动释放，业务超时风险由你承担；
  • 进程宕机 → 续期线程随之消失 → 锁到期释放，不会死锁。

「锁必须防死锁」和「业务可能跑很久」这对矛盾就此解耦，这是 Redisson 成为默认答案的核心原因。

底层原理：AQS（AbstractQueuedSynchronizer）

ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 的骨架都是 AQS——理解它等于理解半个 JUC：

  1. 一个 volatile int state：锁的抽象状态。ReentrantLock 里 0=自由、N=重入次数；Semaphore 里是剩余许可数；CountDownLatch 里是剩余计数。
  2. 一条 CLH 变体的 FIFO 等待队列：抢锁失败的线程封装成 Node 入队并 LockSupport.park 挂起，持有者释放时唤醒后继。
  3. 模板方法 + CAS：acquire() 先调子类的 tryAcquire()（CAS 改 state），失败入队；release() 改 state 后唤醒队首。公平与非公平的唯一区别：非公平在 tryAcquire 前先「插队」抢一把——抢到就省一次入队，吞吐更高，代价是可能饿死排队线程。

Condition 则是挂在同一把锁上的另一条等待队列（await 出同步队列进条件队列，signal 移回）——这就是「多 Condition 精准唤醒」的由来。

为何浏览器还常要 TCP、和 QUIC 设计是否冲突

不冲突。 QUIC（RFC 9000）只规定跑在 UDP 上；HTTP/3 也完全可以在只有 UDP 的情况下工作（例如本节的 aioquic 客户端直连 quic_bind）。

浏览器在地址栏输入 https://主机:端口/ 时，多数实现仍沿用历史习惯：先按「TLS over TCP」去建第一条连接，再通过响应里的 Alt-Svc、或 DNS HTTPS/SVCB 等线索，得知同一站点也可用 HTTP/3，之后才发起 QUIC。这是浏览器与 Web 生态的部署/发现策略，不是 QUIC 协议里「必须先有 TCP」的要求。本地演示若没有 DNS、没有事先缓存的 Alt-Svc，只监听 UDP 时，用户只输入 https:// 就容易连不上，因此示例里同时开同端口的 TCP TLS 是为了兼容这种建连路径，属于工程上的折中，与 QUIC 规范无矛盾。

第六章：Java 动态数据源：@DS 切换与事务边界

概念基础

  1. 为什么需要多数据源：主从读写分离、按库分业务、迁移期新旧库并存等场景，要求应用在运行时切换数据库连接。
  2. 动态数据源方案：Spring 提供 AbstractRoutingDataSource 路由骨架；Baomidou 的 dynamic-datasource 在此之上提供开箱即用的实现。
  3. 核心注解 @DS：通过 @DS("逻辑名") 声明当前类/方法使用的数据源，底层借助 AOP 代理 + ThreadLocal 上下文完成切换，对 MyBatis-Plus、MyBatis-Flex、JdbcTemplate 等均透明适用。
  4. 切换时机是关键：数据源在获取连接时确定；已开启事务并绑定连接后，再切换通常不会生效，须注意事务边界。
  5. 常见陷阱：同类自调用绕过 Spring 代理导致 @DS 失效；编程式切换 push 后忘记 poll 会污染线程上下文。

springboot 仓库落地见 第五章：SpringBoot 集成 MyBatis-Flex 与多数据源。下文以 Boot 4 + MyBatis-Plus 3.5.x + dynamic-datasource 4.x 为例。

切换原理：从注解到连接获取

@DS 的生效链路可拆成四步：

  1. AOP 拦截：@DS 由 dynamic-datasource 内置切面 DynamicDataSourceAnnotationInterceptor 解析，方法级优先于类级，注解值压入 DynamicDataSourceContextHolder 的 ThreadLocal 栈——栈结构天然支持嵌套（外层 mysql、内层 pgsql，内层返回后自动恢复外层）。
  2. 路由数据源：DynamicRoutingDataSource 继承 Spring 的 AbstractRoutingDataSource，determineCurrentLookupKey() 返回栈顶逻辑名，框架据此在内部的 dataSourceMap 里选出真实数据源。
  3. 连接获取时机：MyBatis 在每次执行 SQL 时才向数据源 getConnection()——因此只要切面在 SQL 执行前完成切换，路由就能生效；反之连接已绑定再切换就晚了（详见下文事务边界）。
  4. 清理：切面 finally 中 poll() 弹栈；编程式 push 必须配对 poll，否则线程池复用线程时会串库（上一个请求的数据源泄漏到下一个请求）。

事务与边界情况

  • 同一事务内：已进入 @Transactional 且已绑定连接后，再切换数据源通常不会按预期切到新库（连接已固定）。多数据源写操作应拆到不同事务方法，或调整事务边界，使切换发生在开启事务之前。
  • 只读事务：若使用 @Transactional(readOnly = true)，仍要注意连接从哪个数据源取得，与 @DS 所在方法的事务传播一致。
  • 自调用：同类内 this.method() 不会经过 Spring 代理，@DS 可能不生效，应抽到另一个 Bean 或通过代理调用。

「切换不生效」几乎都源于连接绑定早于切换，对照下表定位：

场景 结果 原因
@Transactional 方法内切库 无效 事务管理器在方法入口已取连接并绑定线程
事务内调另一个 @DS Bean 看传播级别 REQUIRED 复用外层连接；REQUIRES_NEW 挂起外层、取新连接
@DS 标在事务方法上层入口 有效 切换发生在连接获取之前
无事务方法内切库 有效 每条 SQL 现取连接，随切随换

实践规则：

  1. 多库写操作拆成多个事务方法，每个方法自带 @DS + @Transactional，由外层无事务方法编排。
  2. 需要「一次切换覆盖整个事务」时，把 @DS 放在调用事务方法的上层入口（如 Controller 或外层 Service），dynamic-datasource 的切面默认优先级高于事务切面，能保证先切换后开事务。
  3. 跨库原子性本地事务管不了，需要 Seata 之类的全局事务——dynamic-datasource 与 Seata AT 联用时关闭自动代理，改 spring.datasource.dynamic.seata: true，见 Spring Cloud Alibaba 第六章：集成 Seata：AT 模式分布式事务。

概念基础

泛型（Generics） 是 JDK 5 引入的参数化类型机制，示例代码直接复制即可运行，覆盖常用泛型符号：

  1. 为什么需要泛型：避免 Object 强转与 ClassCastException 风险，让类型检查提前到编译期，集合存取更安全、可读性更好。
  2. 字母约定：T（Type 通用类型）、E（Element 集合元素）、K / V（Key / Value 键值对）、U（第二个泛型参数）。
  3. 通配符 ?：表示未知类型；? extends 限定上界（只读）、? super 限定下界（可写），对应 PECS 原则（Producer Extends, Consumer Super）。
  4. 泛型方法与多限定：<T> 声明方法级泛型；T extends A & B 用 & 要求同时满足多个接口约束。
  5. 类型擦除：泛型信息只在编译期存在，运行时统一擦除为 Object，因此不能 new T()、不能用 T.class。
