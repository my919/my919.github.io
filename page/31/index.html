第三章：SpringBoot 集成 Redis 与缓存

概念基础

缓存把热点数据放进内存数据库，用空间换时间，降低数据库压力、缩短响应时间：

  1. 三种接入方式：本项目集成 Spring Data Redis（StringRedisTemplate）、Redisson（分布式对象、Bucket 等）、Spring Cache（@Cacheable，底层为 Redis），按场景选用。
  2. 统一连接层：三者最终都经 Lettuce 连接访问同一个 Redis（见架构图），连接与超时配置集中管理。
  3. TTL 必设：缓存写入务必带过期时间（如探针 120 秒），防止脏数据长期滞留与内存膨胀。
  4. 业务耦合点：防重、幂等、缓存探针均依赖 Redis——防重用 SET NX + TTL，幂等缓存首次成功的 Result JSON。
  5. 测试隔离：单测排除 Redis 自动配置、缓存切换 simple 并注入 Mock Bean，保证无 Redis 也能跑通测试。

缓存三兄弟：穿透 / 击穿 / 雪崩



flowchart TB
  Q[查询请求] --> C{缓存命中?}
  C -->|是| H[直接返回]
  C -->|否| DB[查数据库]
  DB --> F[回填缓存 + TTL]
  F --> H

1. 缓存穿透——查询根本不存在的数据，缓存永不命中，流量直达 DB：

  • 方案 A：缓存空值（短 TTL，如 60s），cache-null-values: true 时配合短过期。
  • 方案 B：布隆过滤器（Redisson RBloomFilter）前置拦截非法 key，适合海量不存在的 ID。

2. 缓存击穿——热点 key 恰好在高并发时过期，大量请求同时回源：

  • 方案 B：逻辑过期（value 里带过期时间戳，后台线程异步续期），热点 key 永不过期。

3. 缓存雪崩——大量 key 同时过期或 Redis 宕机：

  • TTL 加随机抖动：30min + random(0~10min)，打散过期时间点。
  • 多级缓存：本地 Caffeine（秒级）+ Redis（分钟级），Redis 挂了还有一层。
  • 兜底降级：Redis 异常时走 @Cacheable(sync = true) 无效，需在切面捕获后降级直查 DB + 限流。

对照速查：

问题 触发条件 核心防御
穿透 查不存在的数据 空值缓存 / 布隆过滤器
击穿 热点 key 瞬间过期 互斥锁回源 / 逻辑过期
雪崩 批量过期 / Redis 宕机 TTL 抖动 / 多级缓存 / 降级

第二章：SpringBoot 集成 RustFS 对象存储

概念基础

对象存储以「Bucket + objectKey」平铺组织文件，通过 HTTP API 读写，适合图片、附件等非结构化数据：

  1. S3 兼容协议：RustFS 提供 S3 兼容 API，凡支持 AWS S3 协议的客户端均可直接对接，迁移成本低。
  2. SDK 与访问风格：本工程使用 AWS SDK for Java v2 访问，并开启 forcePathStyle: true（路径风格访问，兼容 MinIO/RustFS 等自建服务）。
  3. 预签名 URL：服务端签发带过期时间的临时链接（本项目 15 分钟），客户端直连存储完成下载，应用不代理文件流量。
  4. 开关与外部化：app.rustfs.oss.enabled 控制装配（@ConditionalOnProperty），endpoint 与密钥经环境变量注入，生产勿写入仓库。
  5. 测试友好：单元测试默认关闭 OSS，真实环境联调用 RUSTFS_LIVE_TEST=true 单独触发。

前置条件

  1. 已部署 RustFS 服务（示例：http://192.168.1.22:30009）
  2. 在控制台创建 Access Key：http://<host>:<port>/rustfs/console/access-keys
  3. 创建或确认 Bucket 名称

注意：SDK 的 endpoint 填 S3 API 根地址，不要带 /rustfs/console/... 路径。

第一章：SpringBoot 多环境配置：Profile 激活与优先级

概念基础

多环境配置让同一份代码在开发、测试、生产之间只切换配置、不改代码：

  1. Profile 机制：Spring 用 Profile 在 dev / test / prod 之间切换配置；本仓库（springboot）以 application.yaml 承载公共配置，各环境文件只写差异项；相同 key 时环境文件覆盖公共配置。
  2. 激活方式多样：配置文件 spring.profiles.active、环境变量 SPRING_PROFILES_ACTIVE、启动参数 --spring.profiles.active=prod，本项目默认 dev。
  3. 职责划分：端口、应用名、框架级默认值放公共；数据库/Redis 地址与密码、日志级别、Swagger 开关放环境。
  4. 敏感信息外部化：密码经环境变量注入，生产禁止提交 Git；更大规模可接 Nacos 配置中心（共享 dataId + 环境 dataId，后者覆盖前者）。
  5. 测试隔离：src/test/resources/application.yaml 独立于业务 Profile，用 H2 内存库与 Mock 中间件保证 gradlew test 稳定可重复。

微服务多模块 + Nacos spring.config.import 见 第一章：Spring Cloud 多环境配置与 Nacos：Profile 与 config.import 分层（2025.1.x 无 bootstrap，与单体 Profile 思路不同）。

完整优先级链（常用节选）

Spring Boot 实际有约 17 级配置源，高优先级覆盖低优先级，日常只需记住这条链：

  1. JVM 启动参数 --key=value（最高）
  2. OS 环境变量（SPRING_PROFILES_ACTIVE 这类大写下划线形式）
  3. SPRING_APPLICATION_JSON（整段 JSON 注入）
  4. config/application-{profile}.yaml（jar 外 config 目录）
  5. application-{profile}.yaml（jar 外）
  6. config/application.yaml
  7. jar 外 application.yaml
  8. jar 内 config/application-{profile}.yaml
  9. jar 内 application-{profile}.yaml
  10. jar 内 config/application.yaml
  11. jar 内 application.yaml（最低，打仓库默认值）

实战要点：

  • 环境变量是生产的最后赢家：MYSQL_PASSWORD 永远能盖过 yaml 里的默认值，这也是「敏感信息外部化」的机制基础。
  • jar 外 config/ 目录适合容器挂载场景，改配置不必重新打镜像。
  • 同一属性多处出现时，可用 spring.config.location 显式指定，但会禁用默认搜索路径，慎用。

规则：

概念基础

  1. 为什么单机锁不够用：服务多实例部署后，synchronized/ReentrantLock 只能约束同一 JVM 内的线程，跨进程的互斥必须借助外部共享存储实现。
  2. 本质：多个进程竞争在同一个外部系统上设置同一个标识（Redis 的 SET NX、ZooKeeper 的节点、MySQL 的行锁），谁设置成功谁持有锁，并依赖超时自动释放防死锁。
  3. 三大实现流派：Redis（高性能、主流方案）、Zookeeper（临时有序节点、强一致）、MySQL（悲观/乐观锁，零新增中间件）。
  4. 生产要点：原子加解锁、锁续期、可重入、防误删、主从切换丢锁一个都不能少——这正是推荐 Redisson 的原因。
  5. 主从切换丢锁的根治方案：普通 Redis 锁是单主节点锁——加锁成功后尚未同步到从节点就宕机，主从切换后锁凭空消失。**RedLock（红锁）**把锁同时写到 N 个完全独立的 Redis 主节点上，过半节点加锁成功且总耗时小于锁有效期才算成功，从根本上规避单点故障丢锁。
  6. 选型口诀：高并发选 Redisson，强一致选 Zookeeper，无中间件小项目选 MySQL，核心强一致（秒杀/支付/账务）用 RedLock。

包含：Redis原生Lua锁、Redisson锁、Redisson RedLock、Zookeeper锁、MySQL悲观锁、MySQL乐观锁，可直接运行。

演进史：为什么不能写成「先 SETNX 再 EXPIRE」

  1. 第一代：SETNX + EXPIRE 两条命令——加锁成功后、设过期前进程崩溃 → 永不释放，死锁。病根是两条命令不是原子。
  2. 第二代：SET key val NX PX 30000 一条命令——Redis 2.6.12+ 原生支持，原子加锁 + 过期，解决死锁。
  3. 第三代：+ Lua 原子解锁——「GET 判断归属再 DEL」合成一个脚本，解决「自己的锁过期后被他人加上，自己又执行 DEL 误删」。
  4. 第四代：+ 看门狗续期（Redisson）——业务没执行完锁先过期的问题，靠后台线程定期延长有效期解决。

每一步演进都对应一类线上事故——你手写出来的多半是第二代，这是「禁止手写」的论据。

锁续期与看门狗（Redisson 怎么做的）

  • lock() 不传 leaseTime 时默认锁 30s（lockWatchdogTimeout），后台每 10s（有效期的 1/3）检查一次：线程还持有就续回 30s；
  • 显式传 tryLock(10, 30, SECONDS) 里的 leaseTime 则看门狗关闭——到期自动释放，业务超时风险由你承担；
  • 进程宕机 → 续期线程随之消失 → 锁到期释放，不会死锁。

「锁必须防死锁」和「业务可能跑很久」这对矛盾就此解耦，这是 Redisson 成为默认答案的核心原因。

Fencing Token：锁之外的最后一道防线

Martin Kleppmann 在 How to do distributed locking 中指出：锁解决互斥，但没解决「持锁者被 STW/网络暂停后醒来继续写」——此时锁已易主，两个客户端先后写同一资源。

三、Redisson RedLock（多独立主节点）

3.1 原理与适用边界

RedLock = 多个独立 Redis 主节点 + 过半写入成功才算加锁成功，目的是彻底解决主从切换丢锁；代价是写 N 个节点 + 严格多数派判定，部署与性能成本都高于单节点锁。

  • 基于**多数派（quorum）**机制：任一节点宕机/切换都不影响多数节点上的锁记录。
  • 节点必须相互独立（非主从、非集群）且为奇数个。
  • 适用边界：秒杀、库存、支付、账务等核心强一致场景用 RedLock；后台任务等非核心场景普通 Redisson 锁即可。

为什么 RedLock 要逐节点续期：红锁对 N 个节点各持一把 RLock，任一节点上的锁过期而未续约，多数派就可能凑不齐——看门狗按节点独立工作，与红锁的过半判定互不影响。

3.2 环境要求与依赖

  1. 至少 3 个独立的 Redis 主节点（无主从、无集群、互相独立）
  2. Redisson 版本 >= 3.5.0
  3. SpringBoot / Java 项目均可

节点部署建议：3 台独立物理机/虚机、同机房；不要把节点配成主从或集群——那会让「独立多数派」前提直接失效。

3.5 加锁成功规则（必须记住）

3 个节点：必须 ≥ 2 个节点加锁成功 + 加锁耗时 < 锁超时时间才算加锁成功；5 个节点：必须 ≥ 3 个节点加锁成功。

为什么要把「耗时」算进去：客户端向 N 个节点顺序加锁，若网络慢导致总耗时逼近锁有效期，最后一把锁拿到时，前面节点的锁可能已临近过期——有效持锁时间 = leaseTime − 加锁总耗时 − 时钟漂移余量。这就是 Redisson 在 tryLock 内部做耗时校验、不达标即整体放弃并回滚已加节点的原因。

看门狗在红锁里生效吗？ 生效——RedLock 会对每个节点的锁自动续期，只要过半节点存活，锁就不会失效。

RedissonMultiLock 与 RedissonRedLock 都是 RLock 的组合体，差异只在判定规则：

四、RedLock 之争：Kleppmann 与 Antirez 各说了什么

2016 年 Martin Kleppmann（DDIA 作者）发文质疑 RedLock，Antirez（Redis 作者）逐条反驳。要点各取一瓢：

质疑（Kleppmann） 反驳（Antirez） 工程结论
GC 停顿 / 网络延迟可让客户端拿着「已过期的锁」继续写 加锁耗时计入校验：耗时 > 有效期就主动放弃 反驳成立但不彻底——停顿发生在「拿锁之后、写之前」依然危险
时钟跳变（NTP 大步校时）可能让锁提前过期 运维应保证时钟稳定，崩溃节奏可控 生产盯 NTP（用渐进校时），并监控节点时钟漂移
缺 fencing token，挡不住「过期后继续写」 （未正面解决） 金融级写入：锁 + fencing token 下沉到存储层校验，缺一不可

适用边界（比「必须用 / 不能用」更有用）：

  • 按目的选型：防并发冲缓存、防任务重复调度 → RedLock 够用；账户余额这类错一次就赔钱的写入 → 锁 + fencing token，或改用 ZK/DB 强一致方案；
  • 节点跨机房部署时网络分区概率上升，多数派假设更脆弱——同机房独立物理机/虚机是更稳的落法。

一句话划界：为效率用 RedLock，为资产安全用「锁 + fencing token」。

八、生产参数与注意事项

8.1 RedLock 生产参数

  1. 必须使用奇数个节点：3、5、7 个，不能用 2、4、6 个。
  2. 节点之间完全独立：不能是主从、不能是集群，必须是独立 Master。
  3. 性能比普通锁低：因为要写多个 Redis，高并发秒杀可以接受。
  4. 核心业务才用 RedLock：秒杀、库存、订单、支付、账务 → 用 RedLock；后台任务、非核心 → 普通锁即可。
  5. 不要把 leaseTime 设置太长：默认 30s 足够，看门狗会自动续期。
  6. 监控 GC 与时钟：Full GC 长停顿是「持锁者假死」的头号来源，换 ZGC/Shenandoah 或合理设堆，把停顿压到秒级以下；NTP 用渐进校时（chrony 或 ntpd -x），避免大步跳变让锁提前过期；加锁日志里记录实际耗时，逼近 leaseTime 即告警。

8.2 通用参数

  • 锁粒度按业务主键收敛（seckill:stock:{skuId}），一把大锁等于把集群打回单机；
  • 加锁只是开始：拿不到锁的策略（快速失败 / 排队 / 降级）要在需求评审时就定下来；
  • 所有实现都要有防误删（归属校验）与超时兜底，否则一次异常就是死锁。

九、选型总结

  1. 互联网高并发 → Redisson（首选）
  2. 金融强一致 / 核心写入怕主从丢锁 → Redisson RedLock（配合 fencing token）
  3. 强一致协调 → Zookeeper
  4. 无中间件、小项目 → MySQL 乐观锁
  5. 低并发强阻塞 → MySQL 悲观锁
  6. 禁止手写Redis原生锁，坑多（续期、可重入、误删、主从丢锁）

两个高频反问：

  • 「Redis 主从切换丢锁怎么办？」→ RedLock（多独立节点过半）或 fencing token；
  • 「锁超时了业务还没跑完怎么办？」→ 看门狗续期（Redisson 默认行为），而不是把 leaseTime 调大。

为何浏览器还常要 TCP、和 QUIC 设计是否冲突

不冲突。 QUIC（RFC 9000）只规定跑在 UDP 上；HTTP/3 也完全可以在只有 UDP 的情况下工作（例如本节的 aioquic 客户端直连 quic_bind）。

浏览器在地址栏输入 https://主机:端口/ 时，多数实现仍沿用历史习惯：先按「TLS over TCP」去建第一条连接，再通过响应里的 Alt-Svc、或 DNS HTTPS/SVCB 等线索，得知同一站点也可用 HTTP/3，之后才发起 QUIC。这是浏览器与 Web 生态的部署/发现策略，不是 QUIC 协议里「必须先有 TCP」的要求。本地演示若没有 DNS、没有事先缓存的 Alt-Svc，只监听 UDP 时，用户只输入 https:// 就容易连不上，因此示例里同时开同端口的 TCP TLS 是为了兼容这种建连路径，属于工程上的折中，与 QUIC 规范无矛盾。

概念基础

  1. 为什么需要多数据源：主从读写分离、按库分业务、迁移期新旧库并存等场景，要求应用在运行时切换数据库连接。
  2. 动态数据源方案：Spring 提供 AbstractRoutingDataSource 路由骨架；Baomidou 的 dynamic-datasource 在此之上提供开箱即用的实现。
  3. 核心注解 @DS：通过 @DS("逻辑名") 声明当前类/方法使用的数据源，底层借助 AOP 代理 + ThreadLocal 上下文完成切换，对 MyBatis-Plus、MyBatis-Flex、JdbcTemplate 等均透明适用。
  4. 切换时机是关键：数据源在获取连接时确定；已开启事务并绑定连接后，再切换通常不会生效，须注意事务边界。
  5. 常见陷阱：同类自调用绕过 Spring 代理导致 @DS 失效；编程式切换 push 后忘记 poll 会污染线程上下文。

事务：一组操作要么全部成功要么全部回滚（ACID：原子性、一致性、隔离性、持久性）。

数据库隔离级别（从宽松到严格）：

级别 脏读 不可重复读 幻读
READ UNCOMMITTED ✅可能 ✅可能 ✅可能
READ COMMITTED ❌ ✅可能 ✅可能
REPEATABLE READ ❌ ❌ ✅可能（MySQL 可防）
SERIALIZABLE ❌ ❌ ❌

MySQL 默认 REPEATABLE READ（MVCC 下已防幻读）；PostgreSQL 默认 READ COMMITTED。

切换原理：从注解到连接获取

@DS 的生效链路可拆成四步：

  1. AOP 拦截：@DS 由 dynamic-datasource 内置切面 DynamicDataSourceAnnotationInterceptor 解析，方法级优先于类级，注解值压入 DynamicDataSourceContextHolder 的 ThreadLocal 栈——栈结构天然支持嵌套（外层 mysql、内层 pgsql，内层返回后自动恢复外层）。
  2. 路由数据源：DynamicRoutingDataSource 继承 Spring 的 AbstractRoutingDataSource，determineCurrentLookupKey() 返回栈顶逻辑名，框架据此在内部的 dataSourceMap 里选出真实数据源。
  3. 连接获取时机：MyBatis 在每次执行 SQL 时才向数据源 getConnection()——因此只要切面在 SQL 执行前完成切换，路由就能生效；反之连接已绑定再切换就晚了（详见下文事务边界）。
  4. 清理：切面 finally 中 poll() 弹栈；编程式 push 必须配对 poll，否则线程池复用线程时会串库（上一个请求的数据源泄漏到下一个请求）。

事务与数据源的边界

  • 同一事务内：已进入 @Transactional 且已绑定连接后，再切换数据源通常不会按预期切到新库（连接已固定）。多数据源写操作应拆到不同事务方法，或调整事务边界，使切换发生在开启事务之前。
  • 只读事务：若使用 @Transactional(readOnly = true)，仍要注意连接从哪个数据源取得，与 @DS 所在方法的事务传播一致。
  • 自调用：同类内 this.method() 不会经过 Spring 代理，@DS 可能不生效，应抽到另一个 Bean 或通过代理调用。
  • 跨库事务：@Transactional 管不了跨库原子性，必须用 Seata 之类的全局事务。

「切换不生效」几乎都源于连接绑定早于切换，对照下表定位：

场景 结果 原因
@Transactional 方法内切库 无效 事务管理器在方法入口已取连接并绑定线程
事务内调另一个 @DS Bean 看传播级别 REQUIRED 复用外层连接；REQUIRES_NEW 挂起外层、取新连接
@DS 标在事务方法上层入口 有效 切换发生在连接获取之前
无事务方法内切库 有效 每条 SQL 现取连接，随切随换

实践规则：

  1. 多库写操作拆成多个事务方法，每个方法自带 @DS + @Transactional，由外层无事务方法编排。
  2. 需要「一次切换覆盖整个事务」时，把 @DS 放在调用事务方法的上层入口（如 Controller 或外层 Service），dynamic-datasource 的切面默认优先级高于事务切面，能保证先切换后开事务。
  3. 跨库原子性本地事务管不了，需要 Seata 之类的全局事务——dynamic-datasource 与 Seata AT 联用时关闭自动代理，改 spring.datasource.dynamic.seata: true，见 Spring Cloud Alibaba 第五章：集成 Seata：AT 模式分布式事务。

第三章：Java 泛型符号与通配符实战

概念基础

泛型（Generics） 是 JDK 5 引入的参数化类型机制，示例代码直接复制即可运行，覆盖常用泛型符号：

  1. 为什么需要泛型：避免 Object 强转与 ClassCastException 风险，让类型检查提前到编译期，集合存取更安全、可读性更好。
  2. 字母约定：T（Type 通用类型）、E（Element 集合元素）、K / V（Key / Value 键值对）、U（第二个泛型参数）。
  3. 通配符 ?：表示未知类型；? extends 限定上界（只读）、? super 限定下界（可写），对应 PECS 原则（Producer Extends, Consumer Super）。
  4. 泛型方法与多限定：<T> 声明方法级泛型；T extends A & B 用 & 要求同时满足多个接口约束。
  5. 类型擦除：泛型信息只在编译期存在，运行时统一擦除为 Object，因此不能 new T()、不能用 T.class。
