外观模式详解（Facade）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.5k 阅读时长 ≈ 3 分钟

设计模式 · 外观模式

GoF 结构型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与适配器/中介者对比。代码带详细注释。

1. 模式概述（意图）

外观模式（Facade）为子系统的一组接口提供一个统一的简化入口——客户端只跟”门面”打交道，不直接面对一堆子系统类。

2. 要解决的问题

问题 说明
客户端与子系统强耦合 一个操作要 new/调用 5 个类
调用顺序易错 步骤多、顺序要求严（初始化→校验→执行→清理）
职责暴露过多 客户端不需要知道内部细节

典型场景：下单要调”库存+支付+优惠券+物流”四个系统——业务代码不用知道细节；java.net.URL 封装协议细节；MyBatis SqlSession 封装 JDBC 细节。

3. 结构（角色）

4. 代码实现（下单门面）

5. 应用场景

场景 说明
业务编排 下单、注册、导出等组合操作
框架封装 SqlSession、RestTemplate 内部复杂对外简单
老系统包装 把分散接口收敛成友好 API
分层架构 Service 层就是 Repository+外部调用的门面

6. 优缺点

优点 缺点
客户端简单（一个入口） 门面可能膨胀成”上帝类”
解耦（客户端不碰子系统） 隐藏了子系统细节（想精细控制时不便）
集中管理调用顺序/事务 需要与业务分层配合，否则混乱
便于测试（mock 门面） 门面职责边界要清晰

7. 与其他模式对比

模式 区别
适配器 适配器转换接口（一对一）；外观聚合简化（一对多）
中介者 中介者协调对象间通信（网状）；外观是单向入口
单例 外观常配合单例（一个门面实例）

8. 常见误用与陷阱

坑 现象 解法
门面膨胀成上帝类 OrderFacade 塞了 20 个方法管订单+库存+物流+售后 按业务域拆分（OrderFacade/InventoryFacade），一门面一事
绕过门面直调子系统 部分代码走 Facade、部分直接 new InventoryService，行为不一致 子系统 Bean 设为 package-private 或仅通过门面注入
隐藏失败细节 门面 catch 所有异常返回 false，调用方不知哪步失败 抛带上下文的业务异常（如 PaymentFailedException），保留原因
泄露子系统对象 门面方法返回内部 Service，调用方拿到后绕过编排 门面只返回 DTO/值对象，不暴露子系统引用

装饰器模式详解（Decorator）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.1k 阅读时长 ≈ 3 分钟

设计模式 · 装饰器模式

GoF 结构型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与继承/代理对比。代码带详细注释。

1. 模式概述（意图）

**装饰器模式（Decorator）**动态地给对象添加职责——把功能拆成一个个”装饰层”，层层包裹，比继承更灵活。

2. 要解决的问题

问题 继承方案 装饰器方案
加功能 每种组合一个子类（爆炸） 组合叠加装饰层
动态加/减 编译期定死 运行时按需组合
多个功能叠加 子类数量 = 2^n 装饰类线性增长

经典例子：咖啡加牛奶、加糖、加奶泡——继承要 8 个类，装饰器只要 3 个装饰类任意组合。

3. 结构（角色）

4. 代码实现（咖啡加料）

核心：装饰器与组件实现同一接口，因此可以无限嵌套；每个装饰器只关注自己的增强。

5. 应用场景

场景 说明
JDK IO 流 new BufferedInputStream(new FileInputStream(f)) 层层包装
Spring @Transactional、@Cacheable 本质是装饰（代理）
日志增强 记录耗时、重试、限流的切面
权限校验 包装对象加权限检查
Java 集合 Collections.synchronizedList(list) 包装增强

6. 优缺点

优点 缺点
比继承灵活（运行时组合） 装饰器链层级多，排障难
避免子类爆炸 小对象多（每层一个对象）
符合开闭原则 要求组件与装饰器同一接口
职责单一（每层一件事） 调试堆栈变深

7. 与代理模式对比（高频考点）

维度 装饰器 代理
目的 增强功能 控制访问
接口 与组件同接口 与被代理对象同接口
创建者 客户端组合 代理创建/被代理方
生命周期 客户端管理 代理方管理
实例 IO 流 Spring AOP 代理

8. 常见误用与陷阱

坑 现象 解法
装饰顺序敏感 压缩(加密(数据)) vs 加密(压缩(数据)) 结果完全不同 文档/命名标明顺序约定；复杂顺序用 Builder 编排
类型识别失效 coffee instanceof Espresso 返回 false（被装饰器包住了） 别依赖具体类型判断；或提供 unwrap() 方法
装饰器吞掉方法 组件新增方法，装饰器忘记转发，调用丢失 装饰器只继承抽象基类，编译器强制实现所有抽象方法
无限嵌套调试难 8 层包装后抛异常，堆栈看不到真实对象 装饰器 toString() 打出链式结构；控制层数 ≤ 5

组合模式详解（Composite）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.3k 阅读时长 ≈ 3 分钟

设计模式 · 组合模式

GoF 结构型模式。意图 · 结构 · 透明与安全 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

组合模式（Composite）把对象组织成树形结构，让单个对象和组合对象拥有一致的接口——客户端无需区分”叶子”还是”树枝”，统一处理。

2. 要解决的问题

问题 说明
树形结构普遍 目录树、组织架构、菜单、DOM、文件系统
客户端要区分层级 叶子与容器处理逻辑不同，代码散落 if-else
遍历/操作不统一 求总大小、递归删除要写多套代码

典型场景：文件系统（文件/目录）、公司组织架构（员工/部门）、菜单系统、HTML DOM、JPanel.add(Component)。

3. 结构（角色）

两种风格：

风格 说明
透明式 接口含 add/remove（叶子也实现，抛异常）——客户端更统一
安全式 容器独有 add/remove——类型安全，客户端需判断

4. 代码实现（文件系统）

递归结构：getSize()/delete() 都是”如果有子节点就委托，没有就自己处理”——叶子与容器的统一协议。

5. 应用场景

场景 说明
文件系统 文件/目录统一操作
组织架构 员工/部门递归统计
UI 组件 Swing JPanel（容器也是 Component）
DOM 树 元素节点统一遍历
权限树 菜单/权限递归渲染

6. 优缺点

优点 缺点
统一叶子与容器，客户端简单 树结构可能很深（递归性能/栈溢出）
天然支持递归操作 透明式接口对叶子不友好（抛异常）
符合开闭（加叶子类型易） 结构破坏后难维护（如循环引用）
层次清晰 不适合层级关系不明显的场景

7. 与其他模式对比

模式 区别
装饰器 装饰器也是树结构，但只一个”装饰者+被装饰者”链
迭代器 常配合组合模式遍历树（迭代器遍历）
访问者 访问者可在组合树上执行操作，不改节点类

8. 常见误用与陷阱

坑 现象 解法
透明式叶子抛异常 FileNode.add() 抛 UnsupportedOperationException，运行时炸 用安全式（容器独有 add/remove）；或接口默认空实现
循环引用栈溢出 dir.add(dir) 或 A.add(B); B.add(A)，递归 getSize() 爆栈 add 时校验 child != this 且无祖先环；必要时维护 parent 指针
深层递归爆栈 万级节点递归 delete() 触发 StackOverflowError 改成显式栈 + 循环的迭代写法；或限制树深
缓存不一致 add/remove 后忘记更新缓存的 size，数据失真 不缓存，每次递归计算；或引入失效机制

桥接模式详解（Bridge）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.2k 阅读时长 ≈ 3 分钟

设计模式 · 桥接模式

GoF 结构型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与适配器对比。代码带详细注释。

1. 模式概述（意图）

桥接模式（Bridge）把抽象部分与实现部分分离，让它们可以独立变化——用组合代替继承，解决”多维度变化”的类爆炸问题。

2. 要解决的问题

经典例子：消息系统有类型维度（普通/紧急/加急）和渠道维度（短信/邮件/企微）。用继承组合，类数 = 类型 × 渠道 = 9 个类：

桥接解法：9 个类 → 3 个类型类 + 3 个渠道类（组合桥接）。

3. 结构（角色）

4. 代码实现

类数公式：类型 N 个 + 渠道 M 个 = N+M 个类（而不是 N×M）。

5. 应用场景

场景 说明
多维度变化的业务 消息(类型×渠道)、支付(业务×渠道)、通知
跨平台 JDBC（驱动实现）× 业务抽象
UI 控件 形状 × 颜色（JDK AWT 的经典例子）
驱动架构 抽象 API × 平台驱动实现

6. 优缺点

优点 缺点
消除继承爆炸（N×M → N+M） 抽象与实现都要维护两套层级
两个维度独立扩展 需要先识别出”两个变化维度”
符合开闭原则 没有多维度变化时是过度设计
实现细节对抽象隐藏 理解门槛略高

7. 与适配器对比

模式 区别
适配器 解决”接口不匹配”（事后补救）
桥接 解决”维度独立变化”（事先设计）
策略 策略只变算法；桥接抽象+实现双维度

8. 常见误用与陷阱

坑 现象 解法
维度识别错误 把不相关的两个维度硬拆成桥，代码反而更绕 先验证两维度独立变化（类数真出现 N×M）再上桥
单维度滥用 只有渠道变化也拆桥接，平白多一层抽象 单维度用策略/工厂即可，桥接是”双维度专属”
抽象层泄漏实现 Message 里 if (sender instanceof SmsSender) 特判，桥失效 抽象层只面向 Implementor 接口，不感知具体实现
忘记注入实现 new UrgentMessage(null) 运行 NPE 构造器强制要求 final MessageSender，不留 setter

适配器模式详解（Adapter）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.2k 阅读时长 ≈ 3 分钟

设计模式 · 适配器模式

GoF 结构型模式。意图 · 结构 · 类适配器与对象适配器 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

适配器模式（Adapter）把一个类的接口转换成客户端期望的另一个接口——让不兼容的接口能一起工作，如同电源转换插头。

2. 要解决的问题

问题 说明
新旧系统对接 老系统的接口与新技术栈不匹配
第三方库适配 库的 API 与业务需要的形式不同
无法改源码 遗留代码/外部库不能直接改

典型场景：接入第三方支付（各家 API 不同 → 统一成自己的接口）、老系统 ESB 对接、Arrays.asList()（数组 → List 的适配）、日志门面 slf4j 适配 log4j/logback。

3. 结构（角色）

两种实现方式：

方式 原理 适用
对象适配器（推荐） 组合：Adapter 持有 Adaptee 通用，解耦
类适配器 继承：Adapter extends Adaptee 需覆写 Adaptee 行为时才用

4. 代码实现（对象适配器）

5. 应用场景

场景 说明
第三方 SDK 统一 支付/短信/OSS 各家 API 统一成自家接口
老系统对接 遗留 ESB/数据库适配新架构
JDK 实例 Arrays.asList()、InputStreamReader（字节流→字符流）
日志门面 slf4j → logback/log4j 适配器
数据格式转换 旧数据格式适配新模型

6. 优缺点

优点 缺点
让不兼容接口协同工作 过度使用导致”包装套包装”难排障
客户端解耦（只认目标接口） 适配层增加调用链
无需修改被适配者 需要理解双方接口差异
可插拔（换适配器即换实现） 适配逻辑要写好转换与异常

7. 与其他模式对比

模式 区别
装饰器 装饰器增强功能不改接口；适配器转换接口
代理 代理控制访问（同接口）；适配器转接口
门面 门面聚合多个接口为高层接口；适配器一对一转换

8. 常见误用与陷阱

坑 现象 解法
适配器吞异常 第三方抛 AlipayException，适配器 catch 后返回 null 或静默成功 转成统一业务异常（如 PaymentException）抛出，不吞
双向适配耦合 一个类既做 A→B 又做 B→A，方法互相缠绕 拆成两个单向适配器（AlipayAdapter、ReverseAlipayAdapter）
单位/语义漏换算 元 vs 分、秒 vs 毫秒，适配器忘记转换导致金额差 100 倍 转换逻辑集中在适配层，配单元测试断言边界值
套娃式适配 Adapter 包 Adapter 包 Adapter，调用链 5 层难排障 直接面向目标接口写新实现，最多包一层

建造者模式详解（Builder）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.6k 阅读时长 ≈ 3 分钟

设计模式 · 建造者模式

GoF 创建型模式。意图 · 结构 · 链式调用 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

建造者模式（Builder）把一个复杂对象的构造过程与表示分离：同样的构建过程可以产出不同的表示。即把”构造步骤”封装在 Builder 里，一步步组装。

2. 要解决的问题

问题 说明
构造参数过多 十几个参数的构造函数难以使用、易传错
参数有依赖 有些参数有默认值、有必填校验
构造过程复杂 分步骤组装，直接 new 做不到

典型场景：StringBuilder、Lombok @Builder、Spring BeanDefinitionBuilder、配置对象（HTTP 客户端、Kafka 生产者）、对象不可变 + 可选参数。

3. 结构（角色）

4. 代码实现（链式建造者，最常用形式）

进阶写法：接口 + 多个 Builder 实现（Director 场景，如”标准配置””严格配置”两套构建流程）：

5. 应用场景

场景 说明
配置对象 HTTP 客户端、连接池、Kafka 生产者配置
复杂 DTO 分步骤组装请求对象
StringBuilder 字符串分步拼接（JDK 实例）
Lombok @Builder 编译期自动生成建造者
测试数据构造 快速构造各种状态的测试对象

6. 优缺点

优点 缺点
参数名化，可读性强（不再传错位） 需要额外 Builder 类（代码变多）
支持默认值与部分配置 简单对象用 Builder 是过度设计
不可变对象友好（无 setter） Lombok 可缓解但引入依赖
集中校验构造参数 继承场景要处理泛型自引用

7. 与其他模式对比

模式 区别
工厂 工厂”一步创建”；建造者”分步组装 + 参数化”
原型 原型”复制已有”；建造者”从零组装”
模板方法 Director 编排步骤类似模板方法思想

8. 常见误用与陷阱

坑 现象 解法
Builder 复用状态污染 同一 Builder build() 两次，第二次带着上次的残留参数 每次新建 Builder，或 build() 后调 reset()
校验时机错误 setter 里就校验，参数还没设完就报错 集中到 build() 校验完整状态（本文做法）
多线程共享 Builder 两个线程同时调 setter，产物参数错乱 Builder 不可共享；build() 产物本身不可变
简单对象滥用 3 个必填参数也上 Builder，代码翻倍 参数 ≤ 4 且全必填 → 直接构造器或 record

原型模式详解（Prototype）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.1k 阅读时长 ≈ 3 分钟

设计模式 · 原型模式

GoF 创建型模式。意图 · 结构 · 深浅拷贝 · 代码实现 · 应用场景 · 优缺点。

1. 模式概述（意图）

原型模式（Prototype）通过复制已有对象（原型）来创建新对象，而不是通过 new 重新构造——当创建成本高时，复制往往更高效。

2. 要解决的问题

问题 说明
创建成本高 对象初始化涉及 DB 查询、IO、复杂计算
运行时才能确定类型 动态生成对象（编辑器复制粘贴）
构造参数复杂 复制比手动重建更省事

典型场景：文档编辑器复制粘贴、Spring @Scope("prototype") 的创建方式之一、缓存对象的复制（不想共享引用）。

3. 结构（角色）

4. 代码实现（Java 深/浅拷贝）

深浅拷贝对比：

方式 行为 风险
浅拷贝 只复制引用，对象内部引用共享 改内部对象影响所有副本
深拷贝 内部引用也复制新对象 实现复杂（嵌套层级深）

5. 应用场景

场景 说明
文档/图像复制粘贴 编辑器复制画布元素
表单/配置模板 从模板复制出具体实例
Spring Prototype Bean 每次获取新实例的创建机制
缓存对象防篡改 复制返回，避免调用方改缓存

6. 优缺点

优点 缺点
创建成本低（复制 vs 重建） 深拷贝实现复杂，嵌套对象易出错
运行时动态复制 需要克隆方法，类改造
与具体类解耦（面向原型接口） 循环引用对象无法直接克隆
性能高（比 new + 初始化快） record/不可变对象才最安全

7. 与其他模式对比

模式 关系
工厂模式 工厂创建新对象；原型是”复制已有对象”
单例 原型强调多副本；单例强调唯一
建造者 建造者逐步组装；原型一步复制

8. 常见误用与陷阱

坑 现象 解法
浅拷贝状态泄漏 clone 后改副本的 items，原型的 items 也被改 引用类型全部深拷贝；能用 record/不可变类就用
循环引用死循环 A 持有 B、B 持有 A，clone() 互相调用栈溢出 打破环（ID 引用代替对象引用）或用 Kryo/序列化拷贝
原生 Cloneable 坑 不实现接口抛 CloneNotSupportedException；super.clone() 只浅拷贝 手写拷贝构造器 new Order(src)，比 Cloneable 可控
clone 里查库/IO 原型本意是”省掉昂贵创建”，clone 里又访问 DB 克隆只复制内存状态；需要数据刷新走显式 reload 方法

设计模式 · 抽象工厂

GoF 创建型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与工厂方法对比。代码带详细注释。

1. 模式概述（意图）

抽象工厂（Abstract Factory）提供一个接口，用于创建一族相关的对象（产品族），而不指定具体类——保证族内产品配套、风格一致。

2. 要解决的问题

现实中的产品往往成族：UI 有”亮色主题”和”暗色主题”（按钮、输入框、弹窗各一套）；数据库有”MySQL 连接”和”PostgreSQL 连接”（连接、事务、方言各一套）。错误做法：分别 new 各组件——容易混搭（亮色按钮配暗色弹窗）。

问题 说明
产品族混搭 各自创建导致配套不一致
换族成本高 换主题要改所有创建点
违反开闭原则 新增一族要改多处

3. 结构（角色）

4. 代码实现

扩展：加”高对比度主题” = 新增 3 个产品类 + 1 个工厂类，老代码不动。

5. 应用场景

场景 说明
UI 主题系统 亮/暗/高对比度一族
跨数据库访问 Connection/Statement/ResultSet 一族（JDBC 抽象工厂）
跨平台组件 Windows/Mac/Linux 原生控件
ORM 方言 MyBatis/JPA 的方言族

6. 优缺点

优点 缺点
保证产品族配套一致（核心价值） 加新产品类型要改抽象工厂（打破开闭）
客户端与具体类解耦 类数量膨胀
换族成本 = 换一个工厂 产品族概念复杂时难理解

7. 与工厂方法对比

维度 工厂方法 抽象工厂
创建对象 一种产品 一族产品
工厂粒度 每产品一工厂 每族一工厂
扩展方向 加产品（易） 加产品类型（难）、加族（易）
典型 JDBC Driver UI 主题、JDBC 产品族

8. 常见误用与陷阱

坑 现象 解法
绕过工厂直接 new 客户端 new DarkButton() 配 factory.createInput()，族内混搭 具体产品构造器包私有，强制走工厂；代码评审拦截
加产品类型灾难 抽象工厂加 createDialog()，所有具体工厂都要改（破坏开闭） 抽象接口用 default 方法返回 Optional.empty() 兜底，逐步迁移
族内不一致 LightThemeFactory.createInput() 误返回 DarkInput 单元测试断言「同一工厂产出的产品风格一致」
退化成简单工厂 用 switch 返回族内产品，失去”换族 = 换工厂”的灵活性 接受开闭破坏，或拆回多个具体工厂类

设计模式 · 工厂方法

GoF 创建型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与简单工厂/抽象工厂对比。代码带详细注释。

1. 模式概述（意图）

工厂方法（Factory Method）定义创建对象的接口，把”创建哪个实例”延迟到子类决定——每个产品对应一个工厂子类，新增产品只加类不改老代码。

2. 要解决的问题

简单工厂的致命伤：加新产品必须修改工厂类（违反开闭原则）。工厂方法把”选择产品”的逻辑下沉到子类，扩展靠新增子类而非修改。

问题 简单工厂 工厂方法
新增产品 改 switch（违反开闭） 加一个工厂子类（符合开闭）
创建逻辑分散 集中但膨胀 每个工厂管一种，清晰

典型场景：框架的扩展点——JDBC DriverManager 与各数据库 Driver、日志框架 Logger 工厂、集合工厂。

3. 结构（角色）

4. 代码实现

新增产品流程：加 CsvParser + CsvParserFactory，老代码零修改——开闭原则落地。

5. 应用场景

场景 说明
JDBC DriverManager 用工厂方法创建各数据库 Connection
日志框架 log4j/slf4j 的 Logger 工厂
集合工厂 Collection 的 iterator() 工厂方法
Spring FactoryBean 容器创建 Bean 的扩展点
框架扩展 用户实现接口即获得框架能力

6. 优缺点

优点 缺点
符合开闭原则（扩展靠新类） 类数量翻倍（每产品多一个工厂）
创建逻辑集中且单一职责 产品体系简单时过度设计
客户端与具体产品解耦 需要理解继承结构

7. 与其他模式对比

模式 区别
简单工厂 一个工厂 + switch；工厂方法每个产品一个工厂
抽象工厂 工厂方法管”一种产品”，抽象工厂管”一族产品”
模板方法 工厂方法常被模板方法调用（如上面 createAndParse）

8. 常见误用与陷阱

坑 现象 解法
类爆炸失控 10 个产品 = 20+ 个类，新人找不到工厂在哪 产品数 ≤ 5 且稳定时退回简单工厂，别为开闭而开闭
工厂里全是模板方法 createAndParse 塞了校验、缓存、日志，工厂变成业务类 工厂只负责创建，公共流程抽成独立服务或用模板方法模式明确分层
工厂方法返回 null 子类忘记重写或分支漏写，返回 null 导致 NPE 抽象方法强制重写；无法创建时抛异常，快速失败
客户端直接 new 具体工厂 new JsonParserFactory() 散落各处，失去解耦意义 工厂也用配置/注册表管理（如 Spring 注入 Map<String, ParserFactory>）

设计模式 · 简单工厂

创建型模式（非 GoF 23，但最常用）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与工厂方法对比。代码带详细注释。

1. 模式概述（意图）

简单工厂（Simple Factory）用一个工厂类根据参数决定创建哪种产品，客户端只跟工厂打交道，不直接 new 具体类。

2. 要解决的问题

问题 说明
客户端到处 new 创建逻辑散落各处，改一个产品要改所有调用点
创建逻辑重复 对象构造需要参数组装、初始化
客户端依赖具体类 违反”面向接口编程”

典型场景：按类型创建消息、解析器、导出器、支付渠道；java.util.Calendar.getInstance()、Integer.valueOf() 都是简单工厂思想。

3. 结构（角色）

4. 代码实现

5. 应用场景

场景 说明
按类型创建对象 消息渠道、支付方式、文件解析
JDK 静态工厂 Integer.valueOf、Calendar.getInstance、Arrays.asList
Spring FactoryBean 复杂 Bean 的创建
框架配置驱动 根据配置创建实现（策略注册）

6. 优缺点

优点 缺点
创建逻辑集中，调用方解耦 开闭原则破坏：加新产品要改工厂（switch 加分支）
客户端面向接口编程 工厂类职责膨胀（所有产品都归它管）
使用简单，无需继承 不适用于产品体系复杂场景

改进方向：产品增多后升级为工厂方法（每个产品一个工厂，符合开闭）或注册表 + 反射（Spring 的 BeanFactory 思路）。

7. 与工厂方法对比

维度 简单工厂 工厂方法
工厂数量 一个工厂管所有 每种产品一个工厂
新增产品 改工厂代码 加新工厂类（开闭）
结构复杂度 低 中
适用 产品少且稳定 产品经常扩展

8. 常见误用与陷阱

坑 现象 解法
工厂返回 null 未知类型静默返回 null，下游 NPE 抛 IllegalArgumentException 快速失败（本文已用）
产品超过 5-8 个 switch 变成长链表，工厂膨胀 升级为工厂方法/注册表，或交给 Spring
在工厂里塞业务逻辑 工厂既创建又发消息，职责不清 工厂只管创建，业务逻辑留给产品类
每次 create 都 new 无状态产品反复创建浪费 无状态产品可缓存成 Map 单例复用
