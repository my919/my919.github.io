设计模式 · 解释器模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与编译原理关联。代码带详细注释。

1. 模式概述（意图）

解释器模式（Interpreter）为某种语言/表达式定义文法，并建立解释器来解释句子——把”规则”建模成语法树，逐个节点求值。

2. 要解决的问题

问题 说明
规则经常变化 硬编码 if-else 改一次动一次代码
规则是”语言” 表达式、SQL、配置、正则
需要外部定义规则 让业务人员/配置文件定义规则

典型场景：规则引擎表达式（age > 18 && score >= 60）、SQL 解析器、正则表达式、数学表达式计算器、Aviator/QLExpress 这类表达式库。

注意：现代实践通常用现成表达式库（Aviator、SpEL、Drools），手写解释器只在特殊场景（语法简单、需深度控制）。

5. 应用场景

场景 说明
规则引擎 营销规则、风控规则表达式
SQL/正则解析 解析器内部实现
数学表达式 计算器求值
配置表达式 SpEL、OGNL、Aviator
协议解析 简单 DSL 解释

实践建议：先评估现成库（Aviator/SpEL/Drools），手写解释器维护成本高。

6. 优缺点

优点 缺点
规则以代码形式扩展（开闭） 文法复杂时类爆炸（每规则一类）
语法树清晰可维护 需要理解编译原理概念
易于实现简单 DSL 性能差（解释执行）
组合灵活 现代实践更多用现成表达式引擎

7. 与其他模式对比

模式 区别
组合模式 解释器语法树就是组合结构（组合+解释器配合）
策略 策略选算法；解释器定义语言规则
命令 命令封装操作；解释器解析”规则语言”

坑 现象 解法
手写复杂文法 表达式稍复杂就类爆炸，维护噩梦 文法超过 3 层立即换 Aviator/SpEL
上下文线程不安全 Context 用 HashMap，并发解释串数据 Context 用 ThreadLocal 或不可变 Map 传参
语法树重复构建 每次求值都 new 一遍表达式对象，GC 压力大 语法树缓存复用，Context 只传变量值
错误信息无定位 表达式出错只报”解释失败”，不知道哪段错 每个节点记录位置信息，异常带行列号

命令模式详解（Command）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3k 阅读时长 ≈ 3 分钟

设计模式 · 命令模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与策略对比。代码带详细注释。

1. 模式概述（意图）

命令模式（Command）把”请求/操作”封装成独立对象——调用方只发命令，执行方只执行，中间可插入队列、撤销、日志等能力。

2. 要解决的问题

问题 说明
请求发送方与执行方耦合 按钮直接调业务方法
需要排队/延迟执行 命令需要进入队列、定时执行
需要撤销/重做 记录命令历史才能回退
需要日志重放 审计/恢复需要记录操作

典型场景：编辑器撤销重做、任务队列、按钮/菜单动作（Swing Action）、事务日志、宏录制。

3. 结构（角色）

4. 代码实现（编辑器撤销）

扩展：命令支持队列（放入 MQ 异步执行）、宏（一组命令组合）、日志（记录命令序列用于恢复）。

5. 应用场景

场景 说明
撤销/重做 编辑器、数据库事务日志
任务队列 命令入队异步/批量执行
UI 动作 菜单/按钮绑定命令（Swing/Javafx）
事务日志 记录操作序列，崩溃恢复重放
远程调用 RPC 命令序列化传输

6. 优缺点

优点 缺点
发送者与执行者完全解耦 每个操作一个类（类数量多）
天然支持撤销/重做/队列 命令对象需要管理（序列化等）
可组合成宏命令 简单场景过度设计
支持日志与恢复 历史记录占用内存

7. 与策略对比

维度 命令 策略
目的 把”操作”对象化（可排队/撤销） 封装”算法”可替换
状态 命令可携带状态（撤销栈） 策略无历史
关注 何时执行、能否回退 怎么执行

8. 常见误用与陷阱

坑 现象 解法
命令膨胀 每个操作一个类，类数量爆炸 用函数式接口（Runnable/Consumer）或 Lambda 替代简单命令
撤销栈泄漏 undoStack 无限增长，内存溢出 限制历史深度（如 100 条），或定期清理
宏命令不回滚 组合命令部分成功部分失败，状态不一致 宏命令内实现补偿逻辑，或配合 Saga 模式
序列化困难 命令含接收者引用，无法直接序列化到 MQ 命令只存参数+接收者 ID，执行时重建接收者

责任链模式详解（Chain of Responsibility）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.5k 阅读时长 ≈ 3 分钟

设计模式 · 责任链

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与装饰器对比。代码带详细注释。

1. 模式概述（意图）

责任链模式（Chain of Responsibility）把多个处理者串成链，请求沿着链传递，每个处理者决定自己处理还是传给下一个——解耦”请求发送者”与”处理者”。

2. 要解决的问题

问题 说明
if-else 层层嵌套 校验/审批/过滤器逻辑堆在调用方
处理者需动态组合 增删处理环节要改调用方
谁处理不确定 运行时才能决定（权限链、审批链）

典型场景：登录校验链（参数→token→权限）、请假审批链（组长→经理→总监）、过滤器链、中间件链（Express/Koa）。

3. 结构（角色）

4. 代码实现（审批链）

变体：责任链也支持”全链路处理”（过滤器/中间件：每个处理者处理完继续传），如登录拦截链。

5. 应用场景

场景 说明
审批流 请假/报销按级别审批
校验链 参数校验→业务校验→权限校验
过滤器 Servlet Filter、Spring Security FilterChain
中间件 Express/Koa 洋葱模型
日志级别 日志按级别逐级过滤

6. 优缺点

优点 缺点
发送者与处理者解耦 请求可能无人处理（需兜底）
动态增删处理环节（开闭） 链长时性能损耗
职责单一（每环一件事） 调试链的传递过程麻烦
组合灵活 处理顺序固化后难调整

7. 与装饰器对比

维度 责任链 装饰器
传递 请求沿链传递，可中途停止 功能层层包裹，全部执行
目的 职责分担/过滤 功能增强
结构 链式（next） 嵌套包装

8. 常见误用与陷阱

坑 现象 解法
链尾无兜底 请求走完所有节点无人处理，静默丢失 链尾必须加默认处理器（拒绝/记录/抛异常）
循环引用 A.setNext(B)、B.setNext(A) 导致死循环 用容器组装链（List），禁止手工 setNext
链过长性能损耗 每个请求遍历几十上百个节点，延迟飙升 控制链长 ≤ 10，或按类型路由到子链
处理者状态污染 Handler 用成员变量存请求上下文，并发串数据 方法参数传上下文，Handler 保持无状态

代理模式详解（Proxy）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.4k 阅读时长 ≈ 3 分钟

设计模式 · 代理模式

GoF 结构型模式。意图 · 结构 · 静态/动态代理 · 代码实现 · 应用场景 · 优缺点 · 与装饰器对比。代码带详细注释。

1. 模式概述（意图）

代理模式（Proxy）为其他对象提供一个替身/代理，由代理控制对真实对象的访问——在不修改原对象的前提下，加入控制逻辑。

2. 要解决的问题

问题 代理作用
对象创建昂贵 懒加载（真正用时才创建）
访问需控制 权限校验、访问日志
远程访问 本地代理转发到远程（RPC 代理）
横切逻辑 事务、缓存、安全（AOP 本质）

典型场景：Spring AOP 动态代理、MyBatis Mapper 代理（只定义接口就能执行 SQL）、RPC 远程代理、Proxy.newProxyInstance。

3. 结构（角色）

三种代理：

类型 说明
静态代理 手写代理类（每目标一个）
JDK 动态代理 接口 + InvocationHandler（反射生成）
CGLIB 动态代理 继承 + 字节码生成（无接口可用）

4. 代码实现

4.1 静态代理（权限控制）

4.2 JDK 动态代理（AOP 基础）

CGLIB 场景：类没有接口时（Spring 默认优先 CGLIB）。

5. 应用场景

场景 说明
Spring AOP @Transactional/@Cacheable 基于动态代理
MyBatis Mapper 接口的代理实现
RPC Dubbo/Feign 远程调用的本地代理
懒加载 JPA 实体关联的延迟加载代理
安全代理 权限/审计控制

6. 优缺点

优点 缺点
不改原类加控制逻辑（开闭） 代理层增加调用链（性能小损耗）
职责分离（控制与业务解耦） 动态代理调试困难（看不到真实类）
支持远程/懒加载等场景 JDK 代理只支持接口
可组合（多层代理） 过度代理导致调用栈深

7. 与装饰器对比（高频考点）

维度 代理 装饰器
目的 控制访问 增强功能
对象创建 代理常自己创建目标 客户端组合
关注点 权限/懒加载/远程 功能叠加
实例 Spring AOP IO 流包装

8. 常见误用与陷阱

坑 现象 解法
this 自调用绕过代理 同类内部 this.a() 调 this.b()，事务注解失效 拆成两个 Bean 跨调用，或注入自身代理（@Lazy/AopContext）
JDK 代理遇 final/无接口 Proxy.newProxyInstance 要求接口，final 方法不能被 CGLIB 增强 有接口用 JDK；无接口用 CGLIB；final 类/方法只能改设计
代理里抛原始异常 InvocationTargetException 直接抛给客户端，堆栈难看 e.getCause() 拆包后再抛真实业务异常
代理链顺序错乱 先缓存后事务 vs 先事务后缓存，结果完全不同 用 @Order 显式排序；关键链路写集成测试验证顺序

JVM 实战：CPU 飙高排查完整步骤

发表于 2026-09-14 更新于 2026-10-25 分类于 JVM 本文字数： 8k 阅读时长 ≈ 7 分钟

JVM · CPU 飙高排查

从 0 到定位根因：确认是不是 JVM 的锅 · top/jstack 定位线程 · 多次抓取对比 · async-profiler 火焰图 · 七类常见根因的判定与修复。代码带详细注释。

技术栈速查

类别 选型 用途
JDK 21 LTS 运行环境
定位 top / top -Hp 进程与线程级 CPU
线程栈 jstack / jcmd Thread.print 看线程在干什么
火焰图 async-profiler 3.x 精准定位热方法
辅助 GC 日志 / jstat 区分”真忙”与”假忙”

1. 概念说明：CPU 高的本质

CPU 飙高的两种类型，排查方向完全不同：

类型 特征 根因方向
真忙（业务/代码在烧 CPU） GC 正常，线程栈在业务代码里 死循环、正则回溯、序列化、大计算
假忙（GC 在烧 CPU） 堆快满、Full GC 频繁 内存泄漏、堆太小、对象分配过快

为什么第一步要分真假：假忙时去抓线程栈，看到的全是 GC 线程，业务线程在等待——方向错了浪费一小时。先看 GC 日志/jstat，再看线程栈。

排查铁律：现场优先——先抓线程栈和火焰图，再考虑重启；重启后热点线程消失，只能靠猜。

2. 步骤 0：先确认是不是 JVM 在烧 CPU

为什么用 jstat 先看：10 秒钟判断出”真忙/假忙”，避免在错误方向上抓半天线程栈。

3. 步骤 1：定位 CPU 高的线程（top + jstack）

定位示例（grep 输出长这样）：

为什么转十六进制：top -H 显示十进制线程号，jstack 用 nid=0x十六进制 标识线程——不转换就搜不到。

4. 步骤 2：多次抓取对比（区分死循环与正常切换）

判定规则：

两次栈对比 结论
同一线程、同一方法、栈几乎不变 死循环/自旋（一直卡在同一行）
同一线程、方法在变、但总是那几个 高频业务处理（真在干活，看是不是该这么重）
栈在等待（WAITING/BLOCKED） 不是它在烧 CPU，回去找别的线程

为什么必须抓两次：单次抓栈有偶然性——线程恰好在某个方法暂停。两次都停在同一个方法，才能确认它持续在烧 CPU。

5. 步骤 3：火焰图（终极手段，精准到方法）

线程栈只能看到”某个时刻”，火焰图能看到一段时间内所有方法消耗的 CPU 占比。

火焰图怎么读：

看什么 说明
最宽的平顶 烧 CPU 最多的方法，优先查它
一串窄条叠很高 深层调用链，可能有循环嵌套
大块 GC 相关 假忙，转内存排查
锁相关（park/contend） 锁竞争，看等待线程

为什么火焰图是终极手段：30 秒采集成千上万次栈，统计出每个方法真实的 CPU 占比——不用猜热点，图上最宽的平顶就是答案。

6. 七类常见根因（判定 + 修复）

6.1 死循环 / 空转（最常见）

判定：火焰图是又宽又平的 loopCheck 平顶；栈顶在 while 行。

6.2 正则回溯爆炸（文本处理高频）

判定：火焰图 java.util.regex 大平顶；GC 不高（纯 CPU）。

6.3 GC 频繁（假忙）

判定：jstat -gcutil 的 FGC/FGCT 快速上涨；火焰图 G1/GC 相关大块。

6.4 序列化 / 大数据对象

判定：火焰图序列化方法平顶；QPS 不高但 CPU 高。

6.5 锁竞争自旋

判定：火焰图 AQS/park 相关；jstack 大量 BLOCKED 线程。

6.6 无限递归 / 方法调用过深

6.7 日志刷屏（隐蔽的 CPU 杀手）

为什么日志也是 CPU 杀手：字符串拼接 + IO 写入 + 线程同步，每个请求多打几行，QPS 高时能吃掉整核 CPU，且线上还不容易察觉。

8. 工具速查表

工具/命令 用途 什么时候用
top 进程级 CPU 第一步：确认哪个进程高
top -Hp <pid> 线程级 CPU 定位烧 CPU 的线程

9. 典型案例：一次上线后 CPU 100% 的正则回溯爆炸排查（top → jstack → 定位）

问题背景：会员服务发布 v2.3.0 后 20 分钟，单实例 CPU 从 35% 飙到 100%（1 核打满 4 核中的 1 核整），QPS 无变化，接口 P99 从 60ms 涨到 2.4s。

排查过程（铁律：先留现场，再定位，最后才谈重启）：

步骤 操作 观察
① 分真假忙 jstat -gcutil <pid> 1000 FGC=0、O=48%、GC 停顿 15ms → GC 正常，真忙
② 定位线程 top -Hp <pid> 按 P 线程 PID 26311 占 99%，线程名 http-nio-8080-exec-3
③ 抓线程栈 printf '%x' 26311 → 0x66c7，jstack 搜 nid 栈顶：java.util.regex.Pattern$Curly.match0，业务帧 MobileValidator.check

享元模式详解（Flyweight）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3k 阅读时长 ≈ 3 分钟

设计模式 · 享元模式

GoF 结构型模式。意图 · 结构 · 内部/外部状态 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

享元模式（Flyweight）通过共享大量细粒度对象来减少内存占用——把对象拆成”可共享的不变部分（内部状态）”和”不可共享的变化部分（外部状态）”。

2. 要解决的问题

问题 说明
对象数量巨大 百万个字符/棋子/图标，每个都 new 内存爆炸
大量对象只有小差异 重复内容多，可共享
内存压力 大流量场景 GC 频繁

核心思想：内部状态（不变，共享）+ 外部状态（变化，调用时传入）。

状态 说明 示例（字符对象）
内部状态 不可变、可共享 字符本身的字形
外部状态 随场景变化 字符的位置、颜色

3. 结构（角色）

4. 代码实现（文本编辑器字符）

5. 应用场景

场景 说明
字符串常量池 JVM 字符串驻留（"a" == "a"）
包装类缓存 Integer.valueOf 缓存 -128~127
线程池/连接池 复用对象（池化思想）
文字渲染 字符/图标/棋子
JDK String String 对象不可变共享

6. 优缺点

优点 缺点
大幅减少内存（共享） 需要区分内/外部状态（设计复杂）
对象复用减少 GC 外部状态管理增加调用复杂度
池化提高创建效率 状态拆分不当会引入并发问题（内部状态必须不可变）

关键约束：内部状态必须不可变——享元被共享，任何人不能改它；外部状态由调用方持有（不共享），否则并发下互相污染。

7. 与其他模式对比

模式 区别
单例 单例全局唯一；享元是一类对象的池化共享（多实例）
对象池 对象池复用”昂贵对象”；享元共享”小对象”
工厂 享元工厂负责缓存与创建

8. 常见误用与陷阱

坑 现象 解法
内部状态被改 享元被共享，某处 glyph.setFont() 改了共享实例 内部状态全 final + 无 setter，构造一次定型
外部状态误存 把位置/颜色存进享元字段，不同位置的对象互相覆盖 外部状态只通过方法参数传入，绝不入字段
缓存无限膨胀 key 设计太细（含时间戳），缓存不命中反成内存泄漏 评估 key 基数；基数大就别用享元，改用对象池或 LRU 限容
HashMap 非线程安全 并发 computeIfAbsent 在旧版 JDK 下偶发死循环/丢数据 用 ConcurrentHashMap（JDK 8+），别用 Collections.synchronizedMap 包 HashMap

外观模式详解（Facade）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.5k 阅读时长 ≈ 3 分钟

设计模式 · 外观模式

GoF 结构型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与适配器/中介者对比。代码带详细注释。

1. 模式概述（意图）

外观模式（Facade）为子系统的一组接口提供一个统一的简化入口——客户端只跟”门面”打交道，不直接面对一堆子系统类。

2. 要解决的问题

问题 说明
客户端与子系统强耦合 一个操作要 new/调用 5 个类
调用顺序易错 步骤多、顺序要求严（初始化→校验→执行→清理）
职责暴露过多 客户端不需要知道内部细节

典型场景：下单要调”库存+支付+优惠券+物流”四个系统——业务代码不用知道细节；java.net.URL 封装协议细节；MyBatis SqlSession 封装 JDBC 细节。

3. 结构（角色）

4. 代码实现（下单门面）

5. 应用场景

场景 说明
业务编排 下单、注册、导出等组合操作
框架封装 SqlSession、RestTemplate 内部复杂对外简单
老系统包装 把分散接口收敛成友好 API
分层架构 Service 层就是 Repository+外部调用的门面

6. 优缺点

优点 缺点
客户端简单（一个入口） 门面可能膨胀成”上帝类”
解耦（客户端不碰子系统） 隐藏了子系统细节（想精细控制时不便）
集中管理调用顺序/事务 需要与业务分层配合，否则混乱
便于测试（mock 门面） 门面职责边界要清晰

7. 与其他模式对比

模式 区别
适配器 适配器转换接口（一对一）；外观聚合简化（一对多）
中介者 中介者协调对象间通信（网状）；外观是单向入口
单例 外观常配合单例（一个门面实例）

8. 常见误用与陷阱

坑 现象 解法
门面膨胀成上帝类 OrderFacade 塞了 20 个方法管订单+库存+物流+售后 按业务域拆分（OrderFacade/InventoryFacade），一门面一事
绕过门面直调子系统 部分代码走 Facade、部分直接 new InventoryService，行为不一致 子系统 Bean 设为 package-private 或仅通过门面注入
隐藏失败细节 门面 catch 所有异常返回 false，调用方不知哪步失败 抛带上下文的业务异常（如 PaymentFailedException），保留原因
泄露子系统对象 门面方法返回内部 Service，调用方拿到后绕过编排 门面只返回 DTO/值对象，不暴露子系统引用

装饰器模式详解（Decorator）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.1k 阅读时长 ≈ 3 分钟

设计模式 · 装饰器模式

GoF 结构型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与继承/代理对比。代码带详细注释。

1. 模式概述（意图）

**装饰器模式（Decorator）**动态地给对象添加职责——把功能拆成一个个”装饰层”，层层包裹，比继承更灵活。

2. 要解决的问题

问题 继承方案 装饰器方案
加功能 每种组合一个子类（爆炸） 组合叠加装饰层
动态加/减 编译期定死 运行时按需组合
多个功能叠加 子类数量 = 2^n 装饰类线性增长

经典例子：咖啡加牛奶、加糖、加奶泡——继承要 8 个类，装饰器只要 3 个装饰类任意组合。

3. 结构（角色）

4. 代码实现（咖啡加料）

核心：装饰器与组件实现同一接口，因此可以无限嵌套；每个装饰器只关注自己的增强。

5. 应用场景

场景 说明
JDK IO 流 new BufferedInputStream(new FileInputStream(f)) 层层包装
Spring @Transactional、@Cacheable 本质是装饰（代理）
日志增强 记录耗时、重试、限流的切面
权限校验 包装对象加权限检查
Java 集合 Collections.synchronizedList(list) 包装增强

6. 优缺点

优点 缺点
比继承灵活（运行时组合） 装饰器链层级多，排障难
避免子类爆炸 小对象多（每层一个对象）
符合开闭原则 要求组件与装饰器同一接口
职责单一（每层一件事） 调试堆栈变深

7. 与代理模式对比（高频考点）

维度 装饰器 代理
目的 增强功能 控制访问
接口 与组件同接口 与被代理对象同接口
创建者 客户端组合 代理创建/被代理方
生命周期 客户端管理 代理方管理
实例 IO 流 Spring AOP 代理

8. 常见误用与陷阱

坑 现象 解法
装饰顺序敏感 压缩(加密(数据)) vs 加密(压缩(数据)) 结果完全不同 文档/命名标明顺序约定；复杂顺序用 Builder 编排
类型识别失效 coffee instanceof Espresso 返回 false（被装饰器包住了） 别依赖具体类型判断；或提供 unwrap() 方法
装饰器吞掉方法 组件新增方法，装饰器忘记转发，调用丢失 装饰器只继承抽象基类，编译器强制实现所有抽象方法
无限嵌套调试难 8 层包装后抛异常，堆栈看不到真实对象 装饰器 toString() 打出链式结构；控制层数 ≤ 5

组合模式详解（Composite）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.3k 阅读时长 ≈ 3 分钟

设计模式 · 组合模式

GoF 结构型模式。意图 · 结构 · 透明与安全 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

组合模式（Composite）把对象组织成树形结构，让单个对象和组合对象拥有一致的接口——客户端无需区分”叶子”还是”树枝”，统一处理。

2. 要解决的问题

问题 说明
树形结构普遍 目录树、组织架构、菜单、DOM、文件系统
客户端要区分层级 叶子与容器处理逻辑不同，代码散落 if-else
遍历/操作不统一 求总大小、递归删除要写多套代码

典型场景：文件系统（文件/目录）、公司组织架构（员工/部门）、菜单系统、HTML DOM、JPanel.add(Component)。

3. 结构（角色）

两种风格：

风格 说明
透明式 接口含 add/remove（叶子也实现，抛异常）——客户端更统一
安全式 容器独有 add/remove——类型安全，客户端需判断

4. 代码实现（文件系统）

递归结构：getSize()/delete() 都是”如果有子节点就委托，没有就自己处理”——叶子与容器的统一协议。

5. 应用场景

场景 说明
文件系统 文件/目录统一操作
组织架构 员工/部门递归统计
UI 组件 Swing JPanel（容器也是 Component）
DOM 树 元素节点统一遍历
权限树 菜单/权限递归渲染

6. 优缺点

优点 缺点
统一叶子与容器，客户端简单 树结构可能很深（递归性能/栈溢出）
天然支持递归操作 透明式接口对叶子不友好（抛异常）
符合开闭（加叶子类型易） 结构破坏后难维护（如循环引用）
层次清晰 不适合层级关系不明显的场景

7. 与其他模式对比

模式 区别
装饰器 装饰器也是树结构，但只一个”装饰者+被装饰者”链
迭代器 常配合组合模式遍历树（迭代器遍历）
访问者 访问者可在组合树上执行操作，不改节点类

8. 常见误用与陷阱

坑 现象 解法
透明式叶子抛异常 FileNode.add() 抛 UnsupportedOperationException，运行时炸 用安全式（容器独有 add/remove）；或接口默认空实现
循环引用栈溢出 dir.add(dir) 或 A.add(B); B.add(A)，递归 getSize() 爆栈 add 时校验 child != this 且无祖先环；必要时维护 parent 指针
深层递归爆栈 万级节点递归 delete() 触发 StackOverflowError 改成显式栈 + 循环的迭代写法；或限制树深
缓存不一致 add/remove 后忘记更新缓存的 size，数据失真 不缓存，每次递归计算；或引入失效机制

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.2k 阅读时长 ≈ 3 分钟

设计模式 · 桥接模式

GoF 结构型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与适配器对比。代码带详细注释。

1. 模式概述（意图）

桥接模式（Bridge）把抽象部分与实现部分分离，让它们可以独立变化——用组合代替继承，解决”多维度变化”的类爆炸问题。

2. 要解决的问题

经典例子：消息系统有类型维度（普通/紧急/加急）和渠道维度（短信/邮件/企微）。用继承组合，类数 = 类型 × 渠道 = 9 个类：

桥接解法：9 个类 → 3 个类型类 + 3 个渠道类（组合桥接）。

3. 结构（角色）

4. 代码实现

类数公式：类型 N 个 + 渠道 M 个 = N+M 个类（而不是 N×M）。

5. 应用场景

场景 说明
多维度变化的业务 消息(类型×渠道)、支付(业务×渠道)、通知
跨平台 JDBC（驱动实现）× 业务抽象
UI 控件 形状 × 颜色（JDK AWT 的经典例子）
驱动架构 抽象 API × 平台驱动实现

6. 优缺点

优点 缺点
消除继承爆炸（N×M → N+M） 抽象与实现都要维护两套层级
两个维度独立扩展 需要先识别出”两个变化维度”
符合开闭原则 没有多维度变化时是过度设计
实现细节对抽象隐藏 理解门槛略高

7. 与适配器对比

模式 区别
适配器 解决”接口不匹配”（事后补救）
桥接 解决”维度独立变化”（事先设计）
策略 策略只变算法；桥接抽象+实现双维度

8. 常见误用与陷阱

坑 现象 解法
维度识别错误 把不相关的两个维度硬拆成桥，代码反而更绕 先验证两维度独立变化（类数真出现 N×M）再上桥
单维度滥用 只有渠道变化也拆桥接，平白多一层抽象 单维度用策略/工厂即可，桥接是”双维度专属”
抽象层泄漏实现 Message 里 if (sender instanceof SmsSender) 特判，桥失效 抽象层只面向 Implementor 接口，不感知具体实现
忘记注入实现 new UrgentMessage(null) 运行 NPE 构造器强制要求 final MessageSender，不留 setter
