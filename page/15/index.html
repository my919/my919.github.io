建造者模式详解（Builder）

设计模式 · 建造者模式

GoF 创建型模式。意图 · 结构 · 链式调用 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

建造者模式（Builder）把一个复杂对象的构造过程与表示分离：同样的构建过程可以产出不同的表示。即把”构造步骤”封装在 Builder 里，一步步组装。

2. 要解决的问题

问题 说明
构造参数过多 十几个参数的构造函数难以使用、易传错
参数有依赖 有些参数有默认值、有必填校验
构造过程复杂 分步骤组装，直接 new 做不到

典型场景：StringBuilder、Lombok @Builder、Spring BeanDefinitionBuilder、配置对象（HTTP 客户端、Kafka 生产者）、对象不可变 + 可选参数。

3. 结构（角色）

4. 代码实现（链式建造者，最常用形式）

进阶写法：接口 + 多个 Builder 实现（Director 场景，如”标准配置””严格配置”两套构建流程）：

5. 应用场景

场景 说明
配置对象 HTTP 客户端、连接池、Kafka 生产者配置
复杂 DTO 分步骤组装请求对象
StringBuilder 字符串分步拼接（JDK 实例）
Lombok @Builder 编译期自动生成建造者
测试数据构造 快速构造各种状态的测试对象

6. 优缺点

优点 缺点
参数名化，可读性强（不再传错位） 需要额外 Builder 类（代码变多）
支持默认值与部分配置 简单对象用 Builder 是过度设计
不可变对象友好（无 setter） Lombok 可缓解但引入依赖
集中校验构造参数 继承场景要处理泛型自引用

7. 与其他模式对比

模式 区别
工厂 工厂”一步创建”；建造者”分步组装 + 参数化”
原型 原型”复制已有”；建造者”从零组装”
模板方法 Director 编排步骤类似模板方法思想

8. 常见误用与陷阱

坑 现象 解法
Builder 复用状态污染 同一 Builder build() 两次，第二次带着上次的残留参数 每次新建 Builder，或 build() 后调 reset()
校验时机错误 setter 里就校验，参数还没设完就报错 集中到 build() 校验完整状态（本文做法）
多线程共享 Builder 两个线程同时调 setter，产物参数错乱 Builder 不可共享；build() 产物本身不可变
简单对象滥用 3 个必填参数也上 Builder，代码翻倍 参数 ≤ 4 且全必填 → 直接构造器或 record

原型模式详解（Prototype）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.1k 阅读时长 ≈ 3 分钟

设计模式 · 原型模式

GoF 创建型模式。意图 · 结构 · 深浅拷贝 · 代码实现 · 应用场景 · 优缺点。

1. 模式概述（意图）

原型模式（Prototype）通过复制已有对象（原型）来创建新对象，而不是通过 new 重新构造——当创建成本高时，复制往往更高效。

2. 要解决的问题

问题 说明
创建成本高 对象初始化涉及 DB 查询、IO、复杂计算
运行时才能确定类型 动态生成对象（编辑器复制粘贴）
构造参数复杂 复制比手动重建更省事

典型场景：文档编辑器复制粘贴、Spring @Scope("prototype") 的创建方式之一、缓存对象的复制（不想共享引用）。

3. 结构（角色）

4. 代码实现（Java 深/浅拷贝）

深浅拷贝对比：

方式 行为 风险
浅拷贝 只复制引用，对象内部引用共享 改内部对象影响所有副本
深拷贝 内部引用也复制新对象 实现复杂（嵌套层级深）

5. 应用场景

场景 说明
文档/图像复制粘贴 编辑器复制画布元素
表单/配置模板 从模板复制出具体实例
Spring Prototype Bean 每次获取新实例的创建机制
缓存对象防篡改 复制返回，避免调用方改缓存

6. 优缺点

优点 缺点
创建成本低（复制 vs 重建） 深拷贝实现复杂，嵌套对象易出错
运行时动态复制 需要克隆方法，类改造
与具体类解耦（面向原型接口） 循环引用对象无法直接克隆
性能高（比 new + 初始化快） record/不可变对象才最安全

7. 与其他模式对比

模式 关系
工厂模式 工厂创建新对象；原型是”复制已有对象”
单例 原型强调多副本；单例强调唯一
建造者 建造者逐步组装；原型一步复制

8. 常见误用与陷阱

坑 现象 解法
浅拷贝状态泄漏 clone 后改副本的 items，原型的 items 也被改 引用类型全部深拷贝；能用 record/不可变类就用
循环引用死循环 A 持有 B、B 持有 A，clone() 互相调用栈溢出 打破环（ID 引用代替对象引用）或用 Kryo/序列化拷贝
原生 Cloneable 坑 不实现接口抛 CloneNotSupportedException；super.clone() 只浅拷贝 手写拷贝构造器 new Order(src)，比 Cloneable 可控
clone 里查库/IO 原型本意是”省掉昂贵创建”，clone 里又访问 DB 克隆只复制内存状态；需要数据刷新走显式 reload 方法

抽象工厂模式详解（Abstract Factory）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.2k 阅读时长 ≈ 3 分钟

设计模式 · 抽象工厂

GoF 创建型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与工厂方法对比。代码带详细注释。

1. 模式概述（意图）

抽象工厂（Abstract Factory）提供一个接口，用于创建一族相关的对象（产品族），而不指定具体类——保证族内产品配套、风格一致。

2. 要解决的问题

现实中的产品往往成族：UI 有”亮色主题”和”暗色主题”（按钮、输入框、弹窗各一套）；数据库有”MySQL 连接”和”PostgreSQL 连接”（连接、事务、方言各一套）。错误做法：分别 new 各组件——容易混搭（亮色按钮配暗色弹窗）。

问题 说明
产品族混搭 各自创建导致配套不一致
换族成本高 换主题要改所有创建点
违反开闭原则 新增一族要改多处

3. 结构（角色）

4. 代码实现

扩展：加”高对比度主题” = 新增 3 个产品类 + 1 个工厂类，老代码不动。

5. 应用场景

场景 说明
UI 主题系统 亮/暗/高对比度一族
跨数据库访问 Connection/Statement/ResultSet 一族（JDBC 抽象工厂）
跨平台组件 Windows/Mac/Linux 原生控件
ORM 方言 MyBatis/JPA 的方言族

6. 优缺点

优点 缺点
保证产品族配套一致（核心价值） 加新产品类型要改抽象工厂（打破开闭）
客户端与具体类解耦 类数量膨胀
换族成本 = 换一个工厂 产品族概念复杂时难理解

7. 与工厂方法对比

维度 工厂方法 抽象工厂
创建对象 一种产品 一族产品
工厂粒度 每产品一工厂 每族一工厂
扩展方向 加产品（易） 加产品类型（难）、加族（易）
典型 JDBC Driver UI 主题、JDBC 产品族

8. 常见误用与陷阱

坑 现象 解法
绕过工厂直接 new 客户端 new DarkButton() 配 factory.createInput()，族内混搭 具体产品构造器包私有，强制走工厂；代码评审拦截
加产品类型灾难 抽象工厂加 createDialog()，所有具体工厂都要改（破坏开闭） 抽象接口用 default 方法返回 Optional.empty() 兜底，逐步迁移
族内不一致 LightThemeFactory.createInput() 误返回 DarkInput 单元测试断言「同一工厂产出的产品风格一致」
退化成简单工厂 用 switch 返回族内产品，失去”换族 = 换工厂”的灵活性 接受开闭破坏，或拆回多个具体工厂类

工厂方法模式详解（Factory Method）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3k 阅读时长 ≈ 3 分钟

设计模式 · 工厂方法

GoF 创建型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与简单工厂/抽象工厂对比。代码带详细注释。

1. 模式概述（意图）

工厂方法（Factory Method）定义创建对象的接口，把”创建哪个实例”延迟到子类决定——每个产品对应一个工厂子类，新增产品只加类不改老代码。

2. 要解决的问题

简单工厂的致命伤：加新产品必须修改工厂类（违反开闭原则）。工厂方法把”选择产品”的逻辑下沉到子类，扩展靠新增子类而非修改。

问题 简单工厂 工厂方法
新增产品 改 switch（违反开闭） 加一个工厂子类（符合开闭）
创建逻辑分散 集中但膨胀 每个工厂管一种，清晰

典型场景：框架的扩展点——JDBC DriverManager 与各数据库 Driver、日志框架 Logger 工厂、集合工厂。

3. 结构（角色）

4. 代码实现

新增产品流程：加 CsvParser + CsvParserFactory，老代码零修改——开闭原则落地。

5. 应用场景

场景 说明
JDBC DriverManager 用工厂方法创建各数据库 Connection
日志框架 log4j/slf4j 的 Logger 工厂
集合工厂 Collection 的 iterator() 工厂方法
Spring FactoryBean 容器创建 Bean 的扩展点
框架扩展 用户实现接口即获得框架能力

6. 优缺点

优点 缺点
符合开闭原则（扩展靠新类） 类数量翻倍（每产品多一个工厂）
创建逻辑集中且单一职责 产品体系简单时过度设计
客户端与具体产品解耦 需要理解继承结构

7. 与其他模式对比

模式 区别
简单工厂 一个工厂 + switch；工厂方法每个产品一个工厂
抽象工厂 工厂方法管”一种产品”，抽象工厂管”一族产品”
模板方法 工厂方法常被模板方法调用（如上面 createAndParse）

8. 常见误用与陷阱

坑 现象 解法
类爆炸失控 10 个产品 = 20+ 个类，新人找不到工厂在哪 产品数 ≤ 5 且稳定时退回简单工厂，别为开闭而开闭
工厂里全是模板方法 createAndParse 塞了校验、缓存、日志，工厂变成业务类 工厂只负责创建，公共流程抽成独立服务或用模板方法模式明确分层
工厂方法返回 null 子类忘记重写或分支漏写，返回 null 导致 NPE 抽象方法强制重写；无法创建时抛异常，快速失败
客户端直接 new 具体工厂 new JsonParserFactory() 散落各处，失去解耦意义 工厂也用配置/注册表管理（如 Spring 注入 Map<String, ParserFactory>）

设计模式 · 简单工厂

创建型模式（非 GoF 23，但最常用）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与工厂方法对比。代码带详细注释。

1. 模式概述（意图）

简单工厂（Simple Factory）用一个工厂类根据参数决定创建哪种产品，客户端只跟工厂打交道，不直接 new 具体类。

2. 要解决的问题

问题 说明
客户端到处 new 创建逻辑散落各处，改一个产品要改所有调用点
创建逻辑重复 对象构造需要参数组装、初始化
客户端依赖具体类 违反”面向接口编程”

典型场景：按类型创建消息、解析器、导出器、支付渠道；java.util.Calendar.getInstance()、Integer.valueOf() 都是简单工厂思想。

3. 结构（角色）

4. 代码实现

5. 应用场景

场景 说明
按类型创建对象 消息渠道、支付方式、文件解析
JDK 静态工厂 Integer.valueOf、Calendar.getInstance、Arrays.asList
Spring FactoryBean 复杂 Bean 的创建
框架配置驱动 根据配置创建实现（策略注册）

6. 优缺点

优点 缺点
创建逻辑集中，调用方解耦 开闭原则破坏：加新产品要改工厂（switch 加分支）
客户端面向接口编程 工厂类职责膨胀（所有产品都归它管）
使用简单，无需继承 不适用于产品体系复杂场景

改进方向：产品增多后升级为工厂方法（每个产品一个工厂，符合开闭）或注册表 + 反射（Spring 的 BeanFactory 思路）。

7. 与工厂方法对比

维度 简单工厂 工厂方法
工厂数量 一个工厂管所有 每种产品一个工厂
新增产品 改工厂代码 加新工厂类（开闭）
结构复杂度 低 中
适用 产品少且稳定 产品经常扩展

8. 常见误用与陷阱

坑 现象 解法
工厂返回 null 未知类型静默返回 null，下游 NPE 抛 IllegalArgumentException 快速失败（本文已用）
产品超过 5-8 个 switch 变成长链表，工厂膨胀 升级为工厂方法/注册表，或交给 Spring
在工厂里塞业务逻辑 工厂既创建又发消息，职责不清 工厂只管创建，业务逻辑留给产品类
每次 create 都 new 无状态产品反复创建浪费 无状态产品可缓存成 Map 单例复用

单例模式详解（Singleton）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 2.7k 阅读时长 ≈ 2 分钟

设计模式 · 单例模式

GoF 创建型模式。意图 · 结构 · 线程安全四种写法 · 应用场景 · 优缺点 · 与其他模式对比。代码带详细注释。

1. 模式概述（意图）

单例模式（Singleton）保证一个类只有一个实例，并提供一个全局访问点。核心：把构造函数私有化，由类自己管理唯一实例。

2. 要解决的问题

问题 说明
重复创建浪费资源 连接池、线程池、配置对象创建昂贵
状态不一致 多个实例各自持有状态，互相不同步
全局访问不方便 需要到处传递实例引用

典型场景：数据库连接池、Redis 客户端、Spring 容器、日志记录器、配置管理器——这些对象一个就够，多了反而有害。

3. 结构（角色）

4. 代码实现（四种写法，从简单到线程安全）

4.1 懒汉式（线程不安全，仅教学）

4.2 双重检查锁 DCL（推荐，兼顾懒加载与性能）

4.3 静态内部类（推荐，天然线程安全 + 懒加载）

4.4 枚举单例（最简洁，防反射防序列化）

5. 应用场景（JDK/Spring 实例）

场景 说明
Spring Bean 默认单例 @Bean 默认 singleton 作用域
JDK Runtime Runtime.getRuntime() 就是单例
数据库连接池 HikariCP DataSource 单例
线程池 Executors 返回的池对象全局共享
配置中心 应用配置只加载一次

6. 优缺点

优点 缺点
节省资源（一个实例） 违反开闭原则（扩展需改类）
全局访问方便 隐藏依赖（全局状态难测试）
保证状态一致 多线程实现要小心（写错有并发隐患）
懒加载可选 滥用导致”上帝对象”

现代观点：单例要克制——能用依赖注入（Spring 容器管单例）就不用全局静态单例；全局可变状态是测试和并发的地雷。

7. 与其他模式的关系

相关模式 关系
工厂模式 工厂常配合单例：返回唯一实例
享元模式 享元强调”复用共享对象”，单例是享元的一种特例
建造者模式 建造者常用于配置复杂对象，可与单例组合

8. 常见误用与陷阱

坑 现象 解法
懒汉式多线程创建多个 高并发下 instance 被 new 两次 用 DCL（volatile + 双重检查）或静态内部类

10. 典型案例：HLS 直播延迟从 12s 优化到 3s

问题背景：带货直播用标准 HLS（6s 切片 × 播放器缓冲 3 片 + CDN 缓存 60s），主播喊”3、2、1 上链接”后观众要 12 秒才看到，互动场直接冷场。

方案：四层压缩延迟——推流端 GOP 对齐切片 → 服务端 2s 切片 → 播放器 lowLatencyMode + 只缓冲 1-2 片 + 超限追帧 → CDN 分级缓存（m3u8 不缓存、ts 长缓存）。

踩坑点：

  • hls_fragment 盲目压到 0.5s：切片数暴涨，CDN 请求量翻 4 倍，回源把源站打死——2s 是平衡点。
  • m3u8 被 CDN 缓存 60s：观众永远落后一分钟且刷新无用，m3u8 必须 no-cache 或 1-2s 微缓存。
  • 主播端编码器 GOP 设 4s、切片 2s：切片被迫对齐 GOP 变成 4s，服务端配置全白改——推流端 GOP ≤ 切片时长。
  • 延迟优化不是免费的：缓冲越浅，弱网观众越容易卡顿——自适应降码率优先保流畅。

11. 常见误用与陷阱

坑 现象/后果 解法
切片越短延迟越低 0.5s 切片请求风暴，源站/CDN 率先崩溃 2s 起步；优化顺序：切片 > 缓冲 > 追帧
m3u8 配长缓存 观众集体落后且不收敛，刷新也没用 m3u8 no-cache（或 1-2s 微缓存），ts 才长缓存
GOP 与切片不对齐 切片实际时长翻倍，配置的延迟没生效 推流端 GOP ≤ hls_fragment + hls_wait_keyframe on
lowLatencyMode 万能论 源站不支持 LL-HLS，开了没效果也不报错 服务端（SRS/NGINX-hls）与播放器同时支持才生效
ts 不做鉴权 m3u8 带 token 但 ts 裸奔，盗链照样白嫖带宽 ts 请求同样校验 token/referer，或用临时签名 URL
只压延迟不管追帧 网络抖一下延迟累积到几十秒 liveMaxLatencyDuration 强制跳到直播边缘

9. 常见误用与陷阱

坑 现象/后果 解法
空表/小数据量压测 QPS 虚高数倍，容量结论失真 造生产量级数据 + 冷热分布
只看平均 RT 平均 80ms 掩盖 P99 800ms 长尾 看 P90/P99/P999 与 RT 分布
一次打到最大并发 拐点定位不了，直接打崩无归因数据 阶梯加压，每级跑满 5 分钟
压测机自身是瓶颈 端口/CPU 耗尽，误判服务问题 监控压测机资源，必要时分布式施压

未预热就采数 JIT 未编译、连接池未建，数据偏低 先热身 5 分钟再正式采集
