第十三章：数据库连接池：HikariCP与Druid对比与落地

概念基础

JDBC 连接池负责复用数据库连接，避免每次请求都新建 TCP 与认证开销。本仓库（Spring Boot 4.0.6 + dynamic-datasource + MyBatis-Flex）默认使用 HikariCP；本文对比 HikariCP 与 Druid，并给出在本项目中的配置方式、监控与选型建议。

  1. 连接池是什么：容器维护一批已建立的数据库连接，getConnection() 变成「借出 / 归还」，省去每次 TCP 握手与认证的开销。
  2. 为什么必须用池：无池时高并发下连接数暴涨、数据库被打满；有池后 maximum-pool-size 上限保护数据库，等待队列 + connection-timeout 让过载行为可控。
  3. 应用线程 ≠ 数据库连接：Web 线程等待 IO 时可提前归还连接回池，供其他请求使用，少量连接即可服务大量请求。
  4. HikariCP vs Druid：HikariCP 是 Spring Boot 2+ 内置默认，极致性能、依赖最少；Druid 用一定开销换来监控页、慢 SQL 统计、Wall 防火墙等治理能力。
  5. 本项目现状：dynamic-datasource 管理 MySQL（primary）+ PostgreSQL 双库，未引入 Druid 依赖时框架默认 HikariCP；下文给出落地配置、监控、Druid 切换与选型建议。

前置阅读：第二章：SpringBoot 多环境配置：Profile 激活与优先级、第五章：SpringBoot 集成 MyBatis-Flex 与多数据源。

为什么需要连接池

无池 有池
每次 getConnection() 走完整握手 从池中借出已建连，用完归还
高并发下连接数暴涨、DB 被打满 maximum-pool-size 上限保护数据库
慢请求拖垮数据库 等待队列 + 超时（connection-timeout）可控

应用线程 ≠ 数据库连接：Web 线程可在等待 IO 时释放连接回池，供其他请求使用。

HikariCP 内部实现要点

HikariCP 之所以快，核心在三个非常规设计：

1. ConcurrentBag：无锁借还

传统池用 BlockingQueue 存空闲连接，借还都要拿锁。Hikari 自研 ConcurrentBag：

  • 每个线程持有 ThreadLocal 副本列表，先查自己最近用过的连接——大概率直接命中，零竞争。
  • 没命中再扫共享列表（CopyOnWriteArrayList），通过 CAS 标记借用。
  • 都没有才走全局等待队列（SynchronousQueue 模式）阻塞或超时。

热点路径几乎无锁，这是 Hikari 高 QPS 下延迟稳定的主因。

2. FastList 替代 ArrayList

PoolEntry/Statement 列表用自研 FastList：去掉 ArrayList 的范围检查，并按 Hikari「尾删为主」的访问模式把 remove 改为从尾部反向扫描。微小改动带来显著 I-cache 友好性。

3. 字节码级优化

通过 Javassist 生成 ProxyConnection/ProxyStatement 等代理类，把 Connection.close() 改写为「归还到池」而不是真正关闭；同时把 isClosed() 等检查内联，减少栈帧。

4. 连接状态机与 Housekeeper

后台 houseKeeper 线程每 30s 扫一次池：

  • 关闭超出 max-lifetime 的连接。
  • 空闲连接超过 idle-timeout 且高于 minimum-idle 时回收。
  • keepalive-time 到点发送轻量探测（默认 SELECT 1 或 JDBC4 isValid）防半死连接。

理解这四点后再看参数表（下文），调优会更有体感：max-lifetime 是给 houseKeeper 看的，keepalive-time 是给半死连接兜底。

HikariCP 与 Druid 对比

1. 定位

维度 HikariCP Druid（Alibaba）
Spring Boot 默认 Boot 2+ 内置默认（spring-boot-starter-jdbc） 需额外依赖与配置
设计目标 极致性能、代码精简、稳定 性能 + 监控统计 + SQL 防火墙
监控 JMX / Micrometer（连接数、等待时间等） StatViewServlet、慢 SQL、Wall 防注入
多数据源 与 dynamic-datasource 天然搭配（本项目现状） 支持，配置项更多
社区与许可 BSD，Spring 生态一等公民 Apache 2.0，国内 Java 项目常见
典型适用 云原生、微服务、追求默认即最优 需要 SQL 审计、慢查询分析、运维可视化

2. 性能与资源（经验结论）

  • HikariCP：字节码级优化、锁粒度小，Benchmark 中长期领先，内存占用通常更低；Spring 官方默认有其理由。
  • Druid：性能同样优秀，额外功能（Filter、Wall、监控页）带来一定开销；换来可观测与 SQL 治理能力。

二者在生产环境都能稳定运行；差异更多在运维需求而非「能不能用」。

3. 功能差异（程序员需知道的）

能力 HikariCP Druid
连接泄漏检测 leak-detection-threshold remove-abandoned 等
慢 SQL 需配合 P6Spy / datasource-proxy / APM 内置 stat Filter
SQL 防火墙 无（靠 ORM / 预编译） WallFilter 防全表更新等
Web 控制台 无 /druid/* 统计页
Actuator 指标 hikaricp.connections.* 需 Druid Spring Boot Starter 集成

概念基础

Spring Cloud Alibaba（SCA） 是 Spring Cloud 生态的阿里实现，在 Spring Cloud 之上提供 Nacos、Sentinel、Seata、RocketMQ 等集成：

  1. 解决什么问题：Spring Cloud 只定义了注册发现、配置管理、熔断限流、分布式事务等标准接口；SCA 提供这些接口的落地实现，让「API → 实现」通过引入 starter 即可完成。
  2. 版本对齐靠 BOM：SCA、Spring Cloud、Spring Boot 三者版本矩阵严格绑定，统一由 spring-cloud-alibaba-dependencies BOM 管理，避免子模块各写版本号引发冲突。
  3. 本仓库形态：cloud 为 Maven 多模块 工程（非 Gradle 演示项目），已落地 Nacos、Sentinel、Seata、Gateway、OpenFeign；未引入 Dubbo、RocketMQ（见 第十章：Dubbo：RPC 与服务治理扩展、第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展 作扩展阅读）。
  4. 2025.1.x 关键变更：已移除 bootstrap，必须用 spring.config.import 连接 Nacos（详见 第三章：集成 Nacos：注册中心与配置中心）。

第八章：订单下单与库存扣减：Feign 链路与 Seata 全局事务

概念基础

这是本仓库最核心的一条跨服务业务链路，用来验证前面各章组件协作：

  1. 核心链路：下单 POST /order/place（cloud-order）→ OpenFeign → 扣库存 POST /stock/goods/deduct（cloud-stock），一次业务横跨两个服务、两个数据库。
  2. 为什么需要分布式事务：成功时要同时写入 t_order 并减少 goods.stock；两个写操作分属不同服务，任何一步失败都会造成数据不一致。
  3. Seata 全局事务兜底：失败时由 Seata 全局事务回滚（默认开启），cloud-order 侧用 @GlobalTransactional 发起，保证「要么都成功、要么都回滚」。
  4. 统一响应约定：Result，code==0 成功，code==1 业务失败（如库存不足），调用方据此判断结果。
  5. 测试数据：见 sql/test-data-goods.sql，专门设计了低库存商品用于验证回滚。

链路剖析：XID 与分支事务

一次下单在 Seata 视角下的完整动作：



sequenceDiagram
  participant O as cloud-order
  participant F as Feign 拦截器
  participant S as cloud-stock
  participant TC as Seata TC

  O->>TC: ① 开启全局事务，获得 XID
  O->>O: ② 本地事务 INSERT t_order，注册 order 分支，写 undo_log
  O->>F: ③ 调用 deductGoods
  F->>F: ④ 把 XID 放入 HTTP Header
  F->>S: ⑤ POST /stock/goods/deduct
  S->>TC: ⑥ 绑定 XID，注册 stock 分支
  S->>S: ⑦ UPDATE goods，写 undo_log（前后镜像）
  S-->>O: ⑧ 返回结果
  alt 全部成功
    O->>TC: ⑨ 全局提交 → 各分支异步删除 undo_log
  else 任一步异常
    O->>TC: ⑩ 全局回滚 → 各分支按 undo_log 反向补偿
  end

关键点：

  1. XID 传播：Seata starter 的 Feign 拦截器自动把 XID 塞进请求头；stock 侧收到后绑定到当前线程，后续 SQL 都挂在同一全局事务下——无需手写传递代码。
  2. undo_log 时机：分支在本地 SQL 执行后、提交前记录前后镜像；校验失败（如库存不足先抛异常）时 SQL 未执行，不会产生 stock 侧 undo_log。
  3. 全局锁：一阶段提交后行锁即释放，但被改行的全局锁持有到二阶段结束，防止其他全局事务交叉修改同一行造成脏写。

第七章：集成 Sentinel：流控、熔断与服务保护

概念基础

Sentinel 是面向分布式服务架构的流量防卫组件，提供流控、熔断降级、系统保护能力：

  1. 为什么需要：微服务链路中，流量突增、下游变慢都可能引发雪崩；Sentinel 以「资源 + 规则」模型对调用做实时统计与控制，在故障扩散前快速失败，保护服务自身。
  2. 接入方式：本仓库通过 Spring Cloud Alibaba Sentinel 集成；Web 接口、Feign 调用、Gateway 路由都会自动被识别为资源，基本无需侵入业务代码。
  3. 控制台（Dashboard）：默认 http://192.168.1.22:30012（K8s NodePort，Pod 内端口 8858），可视化查看资源与监控，并临时下发流控/熔断规则。
  4. 客户端与控制台通信：使用 8719 端口（可 SENTINEL_TRANSPORT_PORT 覆盖）；传输层使用 netty-http，需排除默认的 simple-http。
  5. 规则存放：默认在内存中（重启失效）；生产可通过 spring.cloud.sentinel.datasource 接 Nacos 等实现持久化，本仓库默认未配置。

规则类型速查

流控规则（FlowRule）：

阈值类型 说明 适用
QPS 每秒请求数超限即拒绝 常规接口保护
并发线程数 同时在处理的请求数上限 慢调用隔离，防线程池耗尽

流控效果（controlBehavior）：直接拒绝（默认）、Warm Up（冷启动期内缓慢放量，防系统刚启动被冲垮）、匀速排队（漏桶，削峰填谷，适合定时任务突发）。

熔断规则（DegradeRule）：

策略 触发条件 适用
慢调用比例 RT 超阈值且比例达标 下游变慢时自我摘流
异常比例 时间窗内异常占比达标 下游不稳定
异常数 时间窗内异常次数达标 粗粒度兜底

熔断后进入半开探测：放行少量请求试探，成功则闭合恢复，失败继续熔断。三种策略都要求设置统计时长与最小请求数，样本过少时不会触发，避免零星异常误伤。

系统规则：按全局 Load / CPU / RT / 线程数 / 入口 QPS 兜底，是最后一道防线而非主力手段；热点参数规则见下文。

第六章：集成 Seata：AT 模式分布式事务

概念基础

  1. 分布式事务：微服务下一次业务操作跨越多个服务与数据库（如下单要写订单库、扣库存库），本地事务无法保证整体原子性，需要全局事务统一协调提交或回滚。
  2. Seata 是阿里开源的分布式事务解决方案，提供 AT、TCC、Saga、XA 等模式；本工程用最常用的 AT 模式——业务 SQL 执行时自动记录前后镜像到 undo_log，异常时据此反向补偿。
  3. 三大角色：TC（事务协调器，独立部署，本工程地址 :30014）、TM（事务发起方，cloud-order 标注 @GlobalTransactional）、RM（资源方，cloud-stock，分支事务注册到 TC）。
  4. 两阶段提交：一阶段各分支本地提交并上报（不长时间锁库，性能好）；二阶段由 TC 统一 commit，或通知各分支用 undo_log 回滚。
  5. 为什么默认开启：下单扣库存是强一致场景，库存不能多扣也不能少扣；AT 模式对业务代码侵入极小——一个注解加一张 undo_log 表即可落地。

概述

Apache Seata 在本项目中以 AT 模式 协调 cloud-order（TM）与 cloud-stock（RM）的跨库事务。默认 开启（SEATA_ENABLED 默认 true），TC 地址 192.168.1.22:30014。与 dynamic-datasource 联用时关闭自动数据源代理，改由 spring.datasource.dynamic.seata: true 接入。

事务模式对比：AT / TCC / Saga / XA

Seata 2.x 提供四种模式，按侵入性与一致性取舍：

模式 原理 侵入性 一致性 适用
AT（本仓库） 代理数据源，自动记录前后镜像到 undo_log，二阶段自动补偿 零业务侵入 全局提交前存在中间态可见（默认读未提交级） 绝大多数 CRUD 场景
TCC 业务手写 Try / Confirm / Cancel 三个方法 高（每个接口拆三个方法） 强（Try 阶段可冻结资源） 资金、票务等强一致核心场景
Saga 一长串本地事务 + 逐条逆向补偿 中（需写补偿动作） 最终一致 长流程、跨组织链路（审批、履约）
XA 数据库原生两阶段协议，全程持锁 低 最强（全程互斥） 短事务、低频但要求严苛的场景

选型速记：常规业务选 AT；TCC 留给「扣钱」级场景；链路长、允许中间态选 Saga；XA 性能差，慎用。本仓库下单链路是典型 AT 场景：写库简单、要求强回滚、不想手写补偿。

对比 AT 的关键差异：

  • 资源冻结在 Try 完成：不会出现 AT「一阶段提交后中间态可见」的窗口，一致性更强。
  • 代码量约 3 倍：每个操作都要写 Try/Confirm/Cancel，且要自己保证幂等（Confirm/Cancel 可能重试）与防悬挂（Cancel 先于 Try 到达时不能解冻出负数）。
  • 不依赖 undo_log 表，也无需代理数据源，可与任意存储（含非关系型）组合。

undo_log 与回滚原理

AT 的「自动补偿」全部建立在 undo_log 的前后镜像上：

  1. 一阶段：RM 代理解析业务 SQL，在本地事务内同时写入业务数据与 undo_log（beforeImage + afterImage，JSON/序列化二进制存于 rollback_info），随后本地提交——行锁即释放，不长时间占库。
  2. 二阶段提交：TC 通知分支成功，RM 异步删除 undo_log，开销极小。
  3. 二阶段回滚：TC 通知回滚，RM 用 beforeImage 生成反向 SQL 还原数据；还原前会用 afterImage 与当前数据做脏校验——若数据在全局事务外被改写过，校验失败则回滚失败转人工（或按策略告警），防止把别人的修改覆盖掉。

因此 undo_log 表必须和业务表在同一个本地事务中写入，这也是 AT 要求「每个参与库都建 undo_log」的原因。

全局锁与写隔离

一阶段提交后行锁已释放，但 RM 会为被修改的行向 TC 申请全局锁并持有到二阶段结束：其他全局事务想改同一行会被阻塞/快速失败，从而避免两个全局事务交叉修改导致的脏写。普通本地事务（不走 Seata）不受全局锁约束——所以同一行数据不要一半走全局事务、一半走裸本地事务。

性能要点

  • AT 一阶段本地提交，锁占用远短于 XA；但每条 DML 都要解析 SQL + 写镜像，写放大约为普通业务的 1.5~2 倍，热点行慎用大字段。
  • rollback_info 是 LONGBLOB，批量 update 千行以上会产生大镜像——批量操作拆小事务或评估是否真需要全局事务。
  • 全局锁竞争集中在热点行（如爆款商品库存行）；可通过库存分桶（stock 拆多行随机扣）降低冲突。
  • TC 自身是单点风险：生产至少 2 节点 + db 模式存储会话，避免 TC 宕机时全局事务悬挂。

常见问题

Q：ConfigNotFoundException: service.vgroupMapping.default_tx_group？
A：补全 default_tx_group 映射，并保证 tx-service-group 与 mapping 键一致；见本仓库 application-seata.yml。

Q：为何 stock 没有 undo_log 但订单回滚了？
A：分支在 真正执行 UPDATE 之后 才写 undo；库存校验失败时可能无 stock 分支 undo，全局仍回滚 order 分支。

Q：dynamic-datasource 与 Seata？
A：必须 enable-auto-data-source-proxy: false + dynamic.seata: true；勿与自动代理同时开启。历史 issue 见 seata#1511。

Q：单元测试如何跑？
A：cloud-order 集成测试 seata.enabled=false，H2 + Mock Feign，见 OrderPlaceIntegrationTest。

Q：AT 和 TCC 能混用吗？
A：同一全局事务的不同分支可以不同模式（如订单库走 AT、积分账户走 TCC），但分支注册方式不同；混合前先在独立链路验证，本仓库未采用。

Q：全局事务里能调用不参事务的第三方 HTTP 接口吗？
A：可以调用，但 Seata 无法回滚第三方副作用；这类调用应放到全局事务提交之后（如发消息通知），或改用 Saga 手写补偿。

Q：undo_log 表需要定期清理吗？
A：正常二阶段完成后由 RM 异步删除；只有异常残留才需要人工介入，清理前先确认对应全局事务已终结，勿在事务进行中删除。

Q：AT 模式下读写一致性怎么保证？
A：默认「读未提交」——一阶段提交的数据在全局提交前可被读到；需要全局一致的读可用 SELECT ... FOR UPDATE（Seata 会代为检查全局锁），或对关键查询走 @GlobalLock 注解。

概念基础

  1. OpenAPI 是 REST API 的描述规范（结构化 JSON/YAML），Swagger UI 把规范渲染成可交互文档：在线查看接口与参数，并直接发起调试请求。
  2. springdoc-openapi 是 Spring Boot 生态的规范实现：启动时扫描 Controller 与注解自动生成 /v3/api-docs，文档与代码同源，不靠手写维护；本工程用 springdoc 3.0.1 配 Spring Boot 4。
  3. 注解驱动：@Schema 描述字段含义，@ExampleObject 提供可复现请求示例（下单成功 / 触发回滚两种），配合常量类避免魔法字符串。
  4. 为什么重要：微服务接口多、调用方多，文档即契约——示例与仓库文件一致，联调效率与前后端/服务间一致性显著提升。
  5. 边界：网关不聚合各服务 OpenAPI，日常走服务直连端口打开 UI；生产环境应关闭文档或加访问控制，避免接口信息泄露。

第四章：集成 SpringCloudGateway：统一入口与路由

概念基础

  1. Spring Cloud Gateway 是 Spring 生态的 API 网关，基于 WebFlux 响应式模型（Netty），本工程 cloud-gateway 以它作为对外唯一入口（端口 9000）。
  2. 路由（Route）是核心概念：由 Predicate（断言） 匹配请求（如 Path=/order/**），转发到目标 uri；本仓库用 lb://服务名 经 Spring Cloud LoadBalancer 从 Nacos 取实例，实现客户端负载均衡。
  3. 服务发现路由：开启 discovery locator 后可按服务名自动生成路由（小写 serviceId），开发期省配置；生产建议关闭，改用显式 routes 严格控制暴露面。
  4. 为什么需要网关：统一入口便于统一鉴权、限流、可观测与 HTTPS 终结；业务服务不直接暴露公网，路由与部署解耦，下游扩缩容对客户端透明。
  5. 技术边界：Gateway 是响应式栈，不要引入基于 spring-webmvc 的 UI 依赖（如 Swagger UI starter），避免 WebFlux/MVC 混用冲突。

概述

cloud-gateway 基于 Spring Cloud Gateway（WebFlux），端口 9000，作为对外统一入口。路由使用 lb://服务名 经 Spring Cloud LoadBalancer 从 Nacos 取实例；同时启用 discovery locator 可按服务名自动生成路由。

路由谓词（Predicate）速查

谓词决定「请求是否命中该路由」，多个谓词之间是 AND 关系：

谓词 作用 示例
Path 路径模式匹配 Path=/order/**
Method HTTP 方法 Method=GET,POST

Query 查询参数 Query=env, gray
Cookie Cookie 匹配 Cookie=uid, \d+
Host Host 通配 Host=**.example.com
RemoteAddr 来源 IP / CIDR RemoteAddr=192.168.1.0/24
Weight 权重分组（灰度分流） Weight=gray, 2 配 weight.group=gray
After / Before / Between 时间窗口 After=2026-01-01T00:00:00+08:00

第三章：集成 Nacos：注册中心与配置中心

概念基础

  1. Nacos（Naming + Configuration service）是阿里开源的注册中心 + 配置中心一体化组件，本工程用它同时完成服务发现与远程配置两件事。
  2. 注册中心解决「服务在哪」：服务启动后把实例（IP + 端口）注册进去并心跳保活，消费方（如 Gateway 的 lb://）订阅服务列表实现动态寻址，扩缩容无需改任何配置。
  3. 配置中心解决「配置共享与动态化」：公共配置以 DataId 为单位托管，多环境用 namespace / Group 隔离，支持控制台编辑、监听查询、历史版本回滚。
  4. SCA 2025.1 接入方式：经 nacos-discovery / nacos-config starter 接入，配置必须走 spring.config.import（bootstrap 已移除），optional: 前缀保证 Nacos 不可用时仍可本地启动。
  5. 为什么选 Nacos：与 Spring Cloud Alibaba 同栈兼容、临时实例默认 AP 模式高可用、控制台开箱即用，是 SCA 微服务体系默认的基座组件。

概述

Nacos 在本项目中同时承担 服务注册发现 与 配置中心。版本线：SCA 2025.1.0.0 + Spring Boot 4，客户端通过 spring-cloud-starter-alibaba-nacos-discovery 与 nacos-config 接入；不再使用 spring-cloud-starter-bootstrap。

注册发现

fail-fast: false：Nacos 暂不可用时仍允许进程启动（适合本地先起应用后起 Nacos）。

实例模型与健康检查

维度 临时实例（默认） 持久实例
健康判定 客户端心跳保活（默认 5s 一次），超 15s 标记不健康、30s 剔除 Server 端主动探测（TCP/HTTP）
一致性 AP 模式，注册表在内存，牺牲一致保可用 CP 模式（Raft），数据落盘
适用 绝大多数微服务 MySQL、DNS 等「不能误剔除」的基础设施

临时实例宕机时，宁可列表中短暂残留并由调用方容错，也不让注册中心自身成为瓶颈——这是微服务默认选 AP 的原因。声明持久实例：spring.cloud.nacos.discovery.ephemeral: false。

集群与权重

  • 集群划分：spring.cloud.nacos.discovery.cluster-name（如 HZ / SH），配合 NacosRule 负载均衡可实现同集群优先调用，减少跨机房流量。
  • 权重：控制台可对实例设置 0~1 权重，权重为 0 即摘流——发布前先在控制台把老实例权重归零，配合连接排空实现优雅下线。
  • 元数据：spring.cloud.nacos.discovery.metadata.* 携带自定义键值（如 version: v2），配合自定义负载均衡或 Gateway 谓词实现灰度路由。

配置监听与灰度发布

  • 监听机制：2.x/3.x 客户端与 Server 走 gRPC 长连接，配置变更即时推送；控制台「监听查询」可看到已订阅的客户端 IP。
  • 动态刷新：@ConfigurationProperties 与 @RefreshScope Bean 自动生效；普通 @Value 字段需加 @RefreshScope；数据源、Seata 等基础设施项建议重启生效。
  • 灰度（Beta）发布：编辑配置时可按 IP 列表 先对少量实例下发灰度内容，验证后全量——适合数据源参数、功能开关的试点。
  • 历史版本：每次发布留存历史版本，误改可在控制台一键回滚。

常见问题

Q：报错 No spring.config.import set？
A：SCA 2025.1 强制要求。在 application-dev.yml 增加 spring.config.import 的 nacos: 项（见上文）。

Q：服务注册成功但网关 503？
A：检查 gateway 的 lb://服务名 与 Nacos 中 serviceId 是否一致（本仓库为小写 cloud-order 等）；discovery.locator.lower-case-service-id: true 已开启。

Q：Nacos 3.x 与 2.x 客户端兼容性？
A：SCA 2025.1 发布说明建议 Nacos Server 3.1.0+；若用 2.x 服务端，以实际集群文档为准。

Q：控制台已建配置，应用仍用本地 jdbc？
A：检查 DataId/Group/命名空间；确认 spring.config.import 含对应 nacos: 项且已重启；optional: 时拉取失败会静默 fallback 到 classpath。

Q：能否用 application-dev.yml 作为 DataId？
A：可以，但须在 import 中写 optional:nacos:application-dev.yml，与本仓库约定的 application.yml 等不同；团队需统一命名，避免每人一个 DataId。

Q：临时实例与持久实例怎么选？
A：微服务默认临时实例（心跳、AP）；MySQL、DNS 等基础设施类注册用持久实例（Server 探测、CP 落盘），通过 spring.cloud.nacos.discovery.ephemeral: false 声明。

Q：发布时如何避免流量打到正在重启的实例？
A：先在控制台把实例权重置 0 或下线，等存量请求处理完再停进程；直接 kill 依赖心跳剔除（最长约 30s），期间可能产生少量失败。

Q：namespace 填了名称却拉不到配置？
A：spring.cloud.nacos.config.namespace 要填命名空间的 ID（控制台命名空间列表里那串 UUID），不是显示名称。

Q：多实例部署 Gateway 后路由不生效？
A：确认 Gateway 自身也注册到了同一 namespace；lb:// 只能解析本 namespace 内的服务，跨 namespace 不可见。

第二章：Spring Cloud 多环境配置与 Nacos：Profile 与 config.import 分层

概念基础

  1. 多环境指同一套代码在 dev / test / prod 等环境中运行，地址、密码、开关等差异通过配置隔离表达，而不是改代码重新打包。
  2. Profile 是 Spring 的环境开关：spring.profiles.active 决定加载哪份 application-{profile}.yml，可用环境变量 SPRING_PROFILES_ACTIVE 在启动时覆盖。
  3. 配置分层指按职责拆分 yaml（shared / datasource / seata / sentinel-client），经 spring.config.import 依次叠加，后加载者覆盖先加载者，顺序即语义。
  4. Nacos Config 作为远程配置中心：公共配置下沉为 DataId，多实例共享、修改即时可见；SCA 2025.1.x 已移除 bootstrap，必须用 optional:nacos:... 经 import 引入。
  5. 为什么重要：配置错误是最常见的事故来源之一——分层清晰、优先级明确，才能保证本地能跑、线上可控、回滚有据。

概述

本仓库（cloud）用 Profile（dev / test / prod）区分环境，用 spring.config.import 分层加载 classpath 与 Nacos 配置。Spring Cloud Alibaba 2025.1.x 已移除 bootstrap，不得在 bootstrap.yml 里连 Nacos，必须在 application-{profile}.yml 中通过 optional:nacos:... 引入（见 SCA 2025 Nacos 进阶）。

单体 Spring Boot 仅用 Profile + 本地 yaml 见 第二章：SpringBoot 多环境配置：Profile 激活与优先级。

Nacos 配置监听原理

客户端并非「定时轮询控制台」，而是通过长连接监听感知变更：



sequenceDiagram
  participant App as cloud-order
  participant N as Nacos Server
  App->>N: 启动时拉取 DataId 全量内容
  App->>N: 建立监听（登记内容 MD5）
  Note over App,N: 配置未变：连接挂起，几乎无流量
  N-->>App: 控制台发布新配置 → 推送变更通知
  App->>N: 拉取最新内容
  App->>App: 刷新 Environment + 重建刷新域 Bean
  • Nacos 2.x / 3.x：客户端与 Server 之间走 gRPC 长连接（9848 等端口由 SDK 处理），变更即时推送；1.x 时代的 HTTP 长轮询（约 30s 挂起）已被取代。
  • 变更判定：客户端持有配置内容的 MD5，Server 通知变更时对比 MD5，不一致才拉取全量，避免无效传输。
  • 监听查询：控制台「监听查询」看到的客户端 IP，就是当前建立了监听的实例——排障时先查这里确认客户端是否真的订阅成功。

动态刷新

配置变更后哪些 Bean 会生效，取决于其作用域：

Bean 类型 是否自动刷新 说明
@ConfigurationProperties 是 Spring Cloud 的 EnvironmentChangeEvent 触发重新绑定
@RefreshScope + @Value 是 Bean 延迟销毁重建，下次访问读取新值
普通 @Component + @Value 否 启动时注入一次，需重启或加 @RefreshScope

本仓库对数据源、Seata 等基础设施项以重启为准——连接池、事务代理在运行期重建风险高，不要盲目依赖热刷新；开关类、阈值类参数才适合 @RefreshScope。

灰度发布

Nacos 3.x 控制台支持配置的灰度（Beta）发布：

  1. 编辑配置时选择 Beta 发布，填写目标 IP 列表（灰度实例）。
  2. 灰度内容只推送给列表内的实例，其余实例仍用正式配置。
  3. 验证无误后停止 Beta 并全量发布，灰度内容覆盖正式配置；不达预期则直接停止 Beta，实例自动回到正式配置。

典型用法：

场景 做法
新数据源参数试点 先对 1 台 order 实例 Beta 发布 application-datasource.yml
功能开关灰度 新开关先推给内部测试实例，观察日志与指标
快速止损 Beta 异常 → 停止 Beta，无需改回内容即可恢复

灰度按 IP 识别实例，K8s 环境下 Pod 重建后 IP 变化，需同步更新灰度列表。

与「多 Profile」的区别：Profile 解决环境级差异（dev/test/prod 整体切换），Beta 灰度解决同环境内的小流量试点，两者互补——先用 namespace 隔开环境，再在同一 namespace 内用 Beta 做灰度。

第七章：MySQL 数据库设计

概念基础

数据库设计是把业务模型翻译成表结构的工程——前六章的所有知识在这里汇合成一次综合实战：

  1. 从实体与关系开始：识别业务实体（用户、商品、订单）与它们的关系，一对多用外键字段关联，多对多拆出中间表（如 sys_user_role、sys_role_menu）——这就是第一章「建表即建模」的完整落地。
  2. 工程约定优先于教科书范式：本仓库采用逻辑删除（deleted 字段，数据可追溯）、无外键约束（业务字段关联，利于分库分表与迁移）、统一审计字段（create_time / update_time）三大约定，是互联网业务的主流取舍。
  3. 树形结构用路径换递归：parent_id + ancestors（祖级 ID 路径） 一次查询整棵子树，避免逐层递归，部门、菜单、通用分类都是此法。
  4. 快照与关联的分寸：订单明细把商品名、价格冗余快照进 order_item，商品后续改价不改历史订单——「该快照的快照，该关联的关联」，冗余是有目的的设计而非错误。
  5. 索引随查询而设计：组合索引把 deleted 纳入（如 idx_parent_deleted）配合逻辑删除过滤，唯一键（uk_username、uk_order_no）在数据库层兜底业务唯一性；建表与建索引是一体两面，与第五章的索引原则呼应。

本文档描述仓库 sql/init.sql 中的 MySQL 8+ 库表设计，覆盖以下业务模块：

七、范式与反范式：权衡而非教条

教科书要求 1NF（原子列）→ 2NF（消除部分依赖）→ 3NF（消除传递依赖），但工程实践中范式是起点不是终点：

选择 适用场景 代价
严格范式 强一致交易系统（金融、库存核心） 查询多 JOIN，复杂报表慢
适度反范式 读多写少、热点查询（订单列表冗余用户名） 冗余字段需双写一致性维护，改一处忘改处处出错

经验法则：

  1. 先按 3NF 设计，再针对实测出来的慢查询做定点反范式冗余——不要「预防性冗余」；
  2. 冗余字段必须回答「谁负责同步」：应用双写、binlog 订阅（Canal）、还是定时对账；
  3. 本章 order_item 冗余商品名/价格属快照型冗余——它本来就该定格历史，不参与同步，是反范式的正当用法。

八、字段类型选型表（含存储开销）

类型选错，索引与内存开销成倍放大。常用类型对照：

类型 存储字节 选型建议
TINYINT 1 状态、布尔（0/1），勿用 tinyint(1) 以外宽度当语义
INT 4 一般主键/外键，上限约 21 亿（无符号 42 亿）
BIGINT 8 订单号、分布式 ID、预期大表主键
DECIMAL(M,D) 定点精确 金额唯一正确选择，禁止用 FLOAT/DOUBLE 存钱
FLOAT/DOUBLE 4/8 科学计算可容忍误差场景
VARCHAR(N) 变长，N 按字符计 utf8mb4 下最长按 N×4 字节预留；够用即可，索引列尽量短
CHAR(N) 定长 仅长度恒定场景（MD5=CHAR(32)、手机号 CHAR(11)）
DATETIME 8（5.6.4+ 实际 5~8） 业务时间，不受时区转换影响，推荐
TIMESTAMP 4 自动更新时间戳，存 UTC 按会话时区显示，范围只到 2038
DATE 3 纯日期（生日、对账日）
JSON 变长 半结构化扩展字段，高频查询键抽虚拟列建索引
TEXT/BLOB 溢出页存储 大文本；列表查询禁止 SELECT * 带出，建议拆子表

通用红线：

  1. 金额只许 DECIMAL；DOUBLE 累加误差在对账时必然爆雷；
  2. 主键列能用 INT 不用 VARCHAR——聚簇索引与所有二级索引都会携带主键值，主键越宽全库越胖；
  3. NOT NULL 默认 + 明确默认值，NULL 让索引统计与 != 语义都变复杂。

九、字符集：utf8mb4 是唯一答案

项 说明
utf8（=utf8mb3） 最多 3 字节/字符，存不了 emoji 与部分生僻字——MySQL 的 utf8 是历史残缺版，禁止使用
utf8mb4 完整 UTF-8（1~4 字节），8.0+ 默认字符集
排序规则 utf8mb4_0900_ai_ci（8.0 默认，Unicode 9.0，不区分大小写/口音）；老驱动兼容可用 utf8mb4_unicode_ci；需要大小写敏感用 utf8mb4_bin（如校验码）
连接层 应用连接串必须 charset=utf8mb4；四层（client/connection/database/server）不一致是乱码根因，查 SHOW VARIABLES LIKE 'character_set%';

索引长度换算：utf8mb4 下 VARCHAR(255) 最多 1020 字节，InnoDB 单列索引上限 3072 字节（innodb_large_prefix 已默认），超长需前缀索引。

十、主键设计：自增 vs UUID vs 雪花 ID

方案 优点 缺点 适用
自增 BIGINT 顺序写、页分裂少、索引最小、可读 暴露业务量、分库后冲突、迁移麻烦 单库单表默认选择
UUID（字符串 36 位） 全局唯一、应用可生成 36 字节宽、无序导致随机插入与页分裂、聚簇索引膨胀 不建议；要用存 BINARY(16) 并选有序变体
UUID v7 / ULID 时间有序 + 全局唯一 宽度仍大于 BIGINT 需要「可读 + 有序 + 分布式」折中
雪花 ID（Snowflake） BIGINT 8 字节、趋势递增、分布式免协调 依赖时钟（回拨需防护）、运维多一套发号器 分库分表 / 多实例写入的标配

InnoDB 视角的根因：聚簇索引按主键顺序组织，无序主键 = 随机插入 = 页分裂 + 碎片 + 缓冲池命中率下降。所以无论选哪种，都遵守：

  1. 趋势递增优先；
  2. 整型优先（8 字节以内）；
  3. 每张 InnoDB 表必须有显式主键——不建则 InnoDB 生成隐藏 6 字节 ROW_ID，浪费且不可控。

十一、分库分表预备设计（先铺路，不施工）

单表建议水位：行数 500 万~2000 万或单表 10GB 级开始评估拆分（经验值，非铁律）。当前不拆，也要把「拆的伏笔」埋好：

  1. 主键预用雪花 ID：将来分表后主键天然全局唯一，免二次改造；
  2. 无外键约束：本章已遵守——跨库后外键必然失效，业务关联从一开始就代码层保证；
  3. 路由键前置设计：订单表以 user_id 为未来分片键，所有高频查询都带 user_id；无路由键的查询（按订单号反查）预建映射表（order_no → user_id）；
  4. 全局唯一业务号：uk_order_no 用「时间 + 用户尾号 + 随机」编码，分库后仍唯一可读；
  5. 禁止跨片 JOIN/事务的幻想：设计查询时就按「只能查一个用户的单表」约束自己，跨片统计走离线数仓或汇总表。

信号与方案：真到拆分时，优先中间件（ShardingSphere / MyCat 系）而非自研路由；拆库优先于拆表（连接与运维成本更低）。

不该拆的信号：单表行数未到千万级、慢查询本质是缺索引——先把索引与 SQL 优化做穿（第五章），分库分表是最后手段而非性能银弹：它用查询能力（跨片 JOIN、分布式事务）换容量，成本极高，能晚一天是一天。

十二、DDL 变更规范（团队协作红线）

  1. 所有变更走版本化迁移脚本（Flyway/Liquibase/Atlas），禁止手工直连生产执行 DDL；
  2. 变更脚本可重复执行或明确一次性，带回滚方案（ADD COLUMN 的回滚是 DROP COLUMN——先备份）；
  3. 大表 DDL 低峰执行，先查长事务（第三章 MDL 一节）；千万行以上走 gh-ost / pt-online-schema-change；
  4. 加索引优先 ALGORITHM=INPLACE, LOCK=NONE（8.0 默认），并在测试环境验证耗时；
  5. 禁止 SELECT INTO 备份当变更方案；禁止直接 RENAME 线上大表做「热切换」而未演练；
  6. 字段变更只加不改：MODIFY COLUMN 缩窄类型/长度有截断风险，先全量校验数据再执行；
  7. 一次变更单只做一件事，便于定位与回滚。

常见问题

脚本执行后表已存在

init.sql 对每张表先 DROP TABLE IF EXISTS 再 CREATE，会清空该表数据。生产环境请勿直接全量执行，应使用迁移工具（Flyway/Liquibase）做增量变更。

逻辑删除查询不到数据

MyBatis-Flex 或业务层需统一过滤 deleted = 0；关联表 sys_user_role 等无 deleted，删除关系应物理 DELETE。

订单与商品库存

当前 DDL 未包含库存扣减、支付流水表；goods.stock / goods_sku.sku_stock 需在业务代码中维护一致性。

多数据源切换后表结构不一致

多数据源环境下，init.sql 默认只初始化主库；从库/报表库若需相同结构需单独执行，且逻辑删除、审计字段等约定须逐库对齐，否则 MyBatis-Flex 生成的 SQL 会因缺列报错。

树形 ancestors 维护时机

ancestors（祖级路径）在节点移动/新增时由应用层重算并级联更新整棵子树；数据库层无触发器约束，须保证「先查父节点路径 → 拼接写入」在同一事务内完成，避免并发移动造成路径错乱。
