第四章：Redis List 数据类型：概念、命令与案例

概念基础

List 是一个 key 下的双向序列，从左右两端都能进出：

  1. 有序、可重复；同一 value 可出现多次。
  2. TYPE key 为 list。
  3. 两端操作是它的设计重心（入队/出队都很快），中间插入/删除代价高于两端（需遍历指针）；设计时尽量从两头消费。
  4. 下标支持负数（-1 表最后一个元素），LRANGE key 0 -1 即取全表。
  5. 与 Java 里的 LinkedList 心智模型接近：当队列、栈、时间线用，不要当随机访问数组用。
  6. 同一根 List 通过「左进右出」或「右进左出」可分别扮演队列（FIFO）与栈（LIFO）——两端同侧进出即栈，异侧进出即队列。

核心原理：底层结构与阻塞机制

1. quicklist：链表与压缩段的折中

List 的底层是 quicklist——一条双向链表，但每个链表节点内部是一段 listpack（7.0 前为 ziplist）压缩段。这样兼顾两头：链表保证两端 O(1)，listpack 保证小段数据省内存。段大小由 list-max-listpack-size 控制：

配置取值 含义
正数（如 128） 每段最多 128 个元素
-2（默认） 每段不超过 8 KB
-1 每段不超过 4 KB（更省内存，段更多）

2. 时间复杂度表

命令 复杂度 说明
LPUSH / RPUSH / LPOP / RPOP O(1) 两端进出是设计主场
LLEN O(1) 长度有缓存
LRANGE start stop O(S+N) S 为偏移，N 为返回元素数
LINDEX / LSET / LINSERT O(N) 需定位，「按下标读写」在大列表上是危险操作
LREM O(N) 按值删除
BLPOP / BRPOP / BLMOVE O(1) + 阻塞等待 见下

3. 阻塞命令：把轮询变成推送

BLPOP / BRPOP 在列表为空时挂起客户端连接，把客户端按 key 排进等待队列；一旦别的客户端推入数据，立刻唤醒第一个等待者（先到先服务）。这把「轮询」变成了「推送」，是简单队列的关键机制。timeout 为 0 表示无限等待；生产建议设非零超时（如 5s）以便消费者定期回收连接、响应退出信号。

4. 安全队列模式：LMOVE

LMOVE src dst LEFT RIGHT（旧 RPOPLPUSH / BRPOPLPUSH，已废弃） 弹出的同时塞回备份队列，消费者处理完再从备份队列删除——用「两队列」模拟 ack，防止消费者崩溃丢任务。配合 BLMOVE 可获得「阻塞 + 安全迁移」的完整语义。

常用命令（必会子集）

命令 作用
LPUSH / RPUSH 左/右入队
LPOP / RPOP 左/右出队（7.x 支持 count 参数批量弹出）
LRANGE key start stop 闭区间下标范围（-1 表末尾）
LLEN 长度
LTRIM key start stop 裁剪只保留区间，常用于「固定窗口」
LINDEX / LSET 按下标读 / 写
BLPOP / BRPOP 阻塞出队（简单队列常用）
LMOVE / BLMOVE 安全迁移元素（安全队列）
LMPOP / BLMPOP（7.0+） 一次弹多个元素、可跨多 key，批量消费减少往返

典型应用场景

  1. FIFO 队列：RPUSH + LPOP（或反向一对）。
  2. 最新消息流：LPUSH + LTRIM key 0 99 保留最近 100 条。
  3. 阻塞消费：BLPOP 多个 key 时按顺序等待，可做简单任务队列（复杂语义建议 Stream 或专业消息中间件）。
  4. 栈式回溯：同侧进出（LPUSH + LPOP）实现「最近操作撤销栈」。
  5. 分页时间线：个人动态 feed 用 List 存最近 N 条 ID，读时 LRANGE 分页后回库查详情。
  6. 任务缓冲削峰：突发流量先 RPUSH 进 List，下游消费者按能力 BLPOP 匀速拉取，把尖峰摊平——写库、发短信类「慢下游」场景的经典用法。
  7. 会话内操作历史：编辑器/表单草稿把每步操作 LPUSH 进 hist:{doc}:{user}，LTRIM 保留最近 50 步，崩溃恢复后按序回放。
  8. 秒杀下单暂存：请求先 LPUSH seckill:{sku} 立即返回「排队中」，后端按库存量 RPOP 出队逐个落单——用 List 长度做天然的流量闸门。

6. 多消费者竞争语义

多个客户端同时对同一 key 执行 BLPOP：Redis 按等待先后顺序唤醒，先等先得——这是负载分发而非广播，一条消息只会被一个消费者拿到。想要「一条消息多方消费」（发布订阅）请用 PUB/SUB 或 Stream 消费组，List 做不到。

进阶：观察 quicklist 与段大小

OBJECT ENCODING 恒为 quicklist（对外不暴露段细节）；想验证段切分效果，可对比 list-max-listpack-size 取 -1（4KB/段）与 -2（8KB/段）下相同数据量的 MEMORY USAGE：段越小越省内存，但段数变多、指针开销上升，默认 -2 是通用平衡点。

常见坑与注意事项

  1. 消费者崩溃：LPOP 后数据即丢，需业务确认机制或改用 LMOVE + 处理完再删 模式；严肃场景评估 Stream、RabbitMQ 等。
  2. 长列表：LRANGE 0 -1 大列表慎用（一次扛回全部字节）；分页用 LRANGE 分段。
  3. 大 key 风险：无人消费的队列会无限增长，务必配合 LLEN 监控告警或 LTRIM 兜底。
  4. 按下标操作：LINDEX / LSET 为 O(N)，把它当数组随机访问是典型误用。
  5. 与 Set/ZSet 区别：List 有序可重复；Set 无序唯一；ZSet 有序唯一带分值。
  6. BLPOP 超时循环：消费者拿 BLPOP key 5 轮询时，超时返回 nil 属正常路径，勿当异常打日志刷屏；也勿用 timeout 0 无限挂死后忘记实现优雅退出。
  7. 多 key 监听顺序即优先级：BLPOP k1 k2 k3 5 从左到右检查，k1 有数据就不会等 k2——利用这点可做「高优队列在前」的简易优先级，但别堆太多 key，逐个检查有开销。
  8. LTRIM 与并发写入：「LLEN 看长度再 LTRIM」两步之间有竞态，期间新元素可能被误裁；固定窗口一律用「先 LPUSH 后 LTRIM」的原子习惯（同连接顺序执行，Lua 更稳）。
  9. 元素体积：List 单元素不宜塞大 JSON——quicklist 段按 8KB 切分，超大元素会破坏段内压缩收益；feed/队列里存 ID，正文回库或 MGET。

第二章：Redis String 数据类型：概念、命令与案例

概念基础

String 是 Redis 最基本的值类型——一个 key 对应一个字符串值：

  1. Redis 是 KV 模型：键（key） 永远是字符串；值（value） 可以是 String / Hash / List 等类型之一。
  2. 本文说的 String 指 value 的类型为 string（TYPE key 显示 string）。
  3. 二进制安全：值可以是任意字节序列——文本、JSON、序列化对象，甚至图片字节，不需要担心内容里出现特殊字符。
  4. 容量上限：单个 String 最大 512 MB，但业务上应把「大 value」视为反模式（见注意事项）。
  5. 编码：底层可能为 int、embstr、raw 等（OBJECT ENCODING key 可查看），对使用者多数时候透明，选型时更关心语义与命令（原理见下一节）。

核心原理：编码与底层结构

  1. SDS（简单动态字符串）：Redis 的字符串不是 C 语言以 \0 结尾的字符数组，而是自研的 SDS 结构——头部记录已用长度与剩余空间，因此 STRLEN 是 O(1)；追加时可预分配空间减少 realloc；内容可含 \0，这是「二进制安全」的基础。
  2. 三种编码与转换：
    • int：值是能放进 64 位有符号整数的数字（如 INCR 计数器），直接存整数，最省内存。
    • embstr：短字符串（≤ 44 字节），redisObject 与 SDS 一次性分配在一块连续内存，读多写少时最省且缓存友好；embstr 是只读的，一旦修改就转成 raw。
    • raw：长字符串（> 44 字节）或被修改过的短字符串，SDS 独立分配，支持高效追加。
  3. 观察方法：
  1. 内存账：同样是 100 万个小 key，编码差异能拉开明显内存差距——int 编码的计数器 key 几乎只有 redisObject 与 dictEntry 开销；raw 长字符串 还要叠一份独立 SDS。海量 key 场景先用 MEMORY USAGE key 抽查，再决定要不要「多 key 合并成 Hash」（见第四章）。
  2. 原子性：命令单线程执行，INCR、SET key val NX 等都是原子操作——这就是「计数器」和「占位锁」不惧并发的根本原因，不需要应用层再包一层锁。

常用命令（必会子集）

1. 读写与删除

MSET / MGET：一次多键，减少往返（注意原子性与键命名规范）。

2. 带条件的写入与过期（业务高频）

SET 常用选项（Redis 2.6+ 语法，具体以你版本文档为准）：

选项 含义
EX 秒 / PX 毫秒 设置过期时间（TTL）
NX 仅当 key 不存在 时写入（常用于抢锁占位）
XX 仅当 key 已存在 时覆盖
KEEPTTL（6.0+） 覆盖时保留原 TTL，不再被默认清空
GET（6.2+） 返回旧值，等价 GETSET 合并进 SET

3. 计数器：INCR / DECR / INCRBY

INCR 在值可解析为整数时原子自增；不存在时按 0 开始。

4. 其它实用命令

命令 作用
APPEND 尾部追加字节
STRLEN 返回字节长度
GETRANGE / SETRANGE 按偏移读写子串（仍整体是 String）
GETSET / GETEX 读旧值并写新值 / 读值并改过期（6.2+，适合做「读后刷新 TTL」的会话续期）

典型应用场景

  1. 缓存整页或对象：值存 JSON 字符串，配合 EX 做短期缓存；更新数据库后删键或覆盖避免脏读。
  2. 会话 / 登录态：SET … EX … 存 token → 用户信息；过期自动消失；续期用 GETEX key EX 3600 一步完成「读 + 续期」。
  3. 计数与限流：INCR 做浏览量、接口调用次数；与滑动窗口等逻辑配合（复杂限流可再引入 Hash / ZSet）。
  4. 分布式锁（谨慎）：SET key token NX PX ttl 仅占位；完整锁需唯一 token、Lua 校验身份释放、续期、Redlock 争议等专题，本文给最小正确版（见案例 3）。
  5. 配置与功能开关：SET feature:x:enabled 1，读时 GET 转布尔。

注意事项与选型

  5. 字符集：Redis String 是字节；UTF-8 文本由客户端编码/解码，不要在服务端假设「一定是中文几个字符」与字节长度一一对应。
  6. TTL 覆盖：SET 不带 KEEPTTL 会清掉旧 TTL，「更新缓存却意外变永久」是高频事故；6.0+ 记得加 KEEPTTL 或重写时重设 EX。

PostgreSQL：并发与 MVCC 入门

概念基础

  1. 并发问题：多个事务同时读写同一批行时，会出现脏读、不可重复读、幻读与丢失更新；数据库必须给出确定性的答案——这就是隔离级别要解决的问题。
  2. MVCC（多版本并发控制）：每行保留多个版本，行头部的 xmin / xmax 记录创建与删除它的事务；读按快照判断可见性，做到读写互不阻塞。
  3. 隔离级别决定快照粒度：默认 READ COMMITTED 每条语句一个快照；REPEATABLE READ 整个事务一个快照；SERIALIZABLE 进一步检测读写冲突，冲突时需应用重试。
  4. MVCC 不是免费的：旧版本（死元组）要靠 VACUUM 回收；「先读后改」的临界区仍需显式行锁（FOR UPDATE），并发抢任务用 SKIP LOCKED。

一、快照与默认隔离级别

  • 默认 READ COMMITTED：单条 SQL 内看到语句开始时已提交的数据版本。
  • REPEATABLE READ：事务内首条 SQL 建立快照，后续读一致。
  • SERIALIZABLE：可检测读写依赖，失败时返回 40001 serialization_failure，应用应重试。

SAVEPOINT：事务内的部分回滚

由于 MVCC，PostgreSQL 读永远不会被写阻塞；默认隔离级别为 READ COMMITTED。

二、显式行锁：FOR UPDATE / FOR SHARE

  • FOR UPDATE：排他行锁，用于「先读后改」的临界区。
  • FOR SHARE：共享行锁，允许他人并发读，阻塞写。

三、SKIP LOCKED 与 NOWAIT（队列与抢锁）

SKIP LOCKED：跳过已被其他事务锁定的行，取下一批可用行——常用于任务队列、公平抢单。

NOWAIT：若不能立即加锁则立刻报错，适合避免长时间等待（由应用捕获错误后重试或放弃）。

四、死锁（deadlock detected）

PostgreSQL 会自动检测事务间循环等待，回滚其中一个事务（报错 40P01 deadlock_detected）。
规避思路与 MySQL 类似：固定加锁顺序、缩短事务、避免无关长耗时在事务内执行。

五、表级锁冲突矩阵（实战版）

PostgreSQL 有 8 种表级锁模式，完整矩阵只需记住实战常用的六行：

持有操作（锁模式） 会阻塞谁
SELECT（ACCESS SHARE） 仅阻塞 ACCESS EXCLUSIVE（ALTER TABLE / DROP / TRUNCATE / VACUUM FULL）
SELECT … FOR UPDATE（ROW SHARE） 阻塞 SHARE（普通 CREATE INDEX）及以上
INSERT/UPDATE/DELETE（ROW EXCLUSIVE） 阻塞 SHARE、EXCLUSIVE、ACCESS EXCLUSIVE；不阻塞 SELECT，也不阻塞别人的 DML
VACUUM / ANALYZE / CREATE INDEX CONCURRENTLY（SHARE UPDATE EXCLUSIVE） 互相阻塞（同表不能并发建两个索引）、阻塞 DDL
CREATE INDEX（SHARE，不带 CONCURRENTLY） 阻塞写入 DML——大表建索引务必加 CONCURRENTLY
ALTER TABLE 等 DDL（ACCESS EXCLUSIVE） 阻塞一切，包括只读 SELECT

速记：读写互不阻塞（MVCC 红利）；普通建索引阻塞写；DDL 阻塞一切，上线要走低峰 + lock_timeout 保护。

八、事务 ID 回卷（xid wraparound）与 freeze

1. 问题是什么

xmin / xmax 是 32 位无符号整数，全局约 40 亿个事务号环形复用：一个事务号「跑完一圈」约 20 亿事务后会被当成新事务——如果不处理，旧数据会突然「变成未来的数据」而不可见，等效于数据丢失。

2. 解法：freeze（冻结）

VACUUM 扫描时把足够老的行版本 xmin 改写成特殊的 FrozenTransactionId（=2）——冻结行对所有未来事务永久可见，不再参与年龄计算。相关参数：

参数 默认 含义
autovacuum_freeze_max_age 2 亿 表的 relfrozenxid 年龄超过它就强制 autovacuum（拦不住也要拦）
vacuum_freeze_min_age 5000 万 行年龄超过它才允许被 freeze
vacuum_freeze_table_age 1.5 亿 超过则整表扫描（而非只扫脏页）

3. 监控与应急

应急：年龄逼近 autovacuum_freeze_max_age 时对大表手动 VACUUM (FREEZE, VERBOSE) tbl;；若数据库已因回卷保护拒绝写入，按官方文档以单用户模式启动做 VACUUM FREEZE。防大于治：别让 autovacuum 长期追不上，监控 datfrozenxid 年龄是巡检标配。

PostgreSQL：索引与性能优化

概念基础

  1. 索引 = 用空间换时间的检索结构：默认 B-Tree 以平衡树组织键值，把等值 / 范围查询从全表扫描降为树查找；代价是占存储、拖慢写入。
  2. 慢的常见根源：大表 Seq Scan、统计信息过期导致选错计划、死元组堆积（表膨胀）、函数包裹列让索引失效。
  3. 优化是闭环不是玄学：慢日志 / pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) 看真实计划 → 改索引或改写法 → VACUUM ANALYZE 更新统计再验证。
  4. 性能之外还有「稳」：事务隔离级别选型、VACUUM/autovacuum 运维、备份恢复（pg_dump / PITR） 演练，都是可靠性的一部分。

先建立对默认索引的直觉：

一、索引在干什么：B-Tree 直觉（默认）

PostgreSQL 默认 CREATE INDEX 多为 B-Tree（USING btree，可省略）。
直觉与 MySQL InnoDB 二级索引类似：以平衡树组织键，等值 / 范围查询减少随机读；主键 / 唯一约束底层也会建索引。

1. 五种常用索引类型对比

类型 内部结构 适用场景 典型写法
B-Tree（默认） 平衡树 等值、范围、排序（< <= = >= >、ORDER BY），绝大多数业务索引 CREATE INDEX ON t (col);
GIN 倒排索引 多值内含检索：jsonb @>、数组、全文检索 CREATE INDEX ON t USING gin (attrs);
GiST 广义搜索树 几何/地理（PostGIS）、范围类型、相似度（pg_trgm） CREATE INDEX ON t USING gist (geom);
BRIN 块级摘要 超大表且物理顺序与列值强相关（如按时间追加的日志） CREATE INDEX ON t USING brin (created_at);
Hash 哈希桶 仅 = 等值；PG 10+ 起才有 WAL 日志可安全使用，多数场景被 B-Tree 覆盖 CREATE INDEX ON t USING hash (col);

选型速记：拿不准就用 B-Tree；jsonb / 数组 / 全文 用 GIN；地理 / 范围类型 用 GiST；只追加的巨型表试 BRIN——体积可能只有 B-Tree 的千分之一，但只擅长「顺序相关」列的范围过滤。

2. 其他类型一句话

SP-GiST（四叉树/基数树，适合非平衡结构如电话号码前缀）、Bloom（扩展，多列任意组合的「可能存在」过滤）属进阶选项，选型需读官方文档与压测。

二、联合索引与最左前缀

联合索引 CREATE INDEX idx_abc ON t (a, b, c); 的排序语义仍是先 a 再 b 再 c。
WHERE a = ? AND b = ? 易命中；仅 WHERE b = ? 往往用不上该索引（与 MySQL 同款直觉）。
函数包裹列（如 WHERE lower(email) = ?）常导致无法走 btree，需表达式索引（CREATE INDEX ON t ((lower(email)))）或改写法。

三、仅索引扫描（Index Only Scan）

若查询列均可由某索引覆盖，且可见性映射（VM）允许优化器认为堆页全可见，EXPLAIN 可能出现 Index Only Scan。
与 MySQL 的 Using index 类似但不等价；仍以 EXPLAIN (ANALYZE, BUFFERS) 实测为准。

四、部分索引与覆盖索引（INCLUDE）

1. 部分索引（Partial Index）：只给需要的行建索引

带 WHERE 的索引只覆盖满足条件的行——更小、更快、更便宜。经典场景：软删除表只索引未删除行、任务表只索引待处理状态：

生效前提：查询的 WHERE 必须蕴含索引条件——WHERE status = 'pending' AND created_at > now() - interval '1 day' 能用；查 status = 'done' 则用不上。

2. 覆盖索引（INCLUDE）：把非键列挂在叶子页

  • 键列决定搜索顺序、可被 WHERE 利用；INCLUDE 列只存储、不参与比较——适合「按 A 列过滤、返回还要 B、C 列」的场景，把回表（Heap Fetches）彻底消掉。
  • 与联合索引 (dept_id, name, salary) 的区别：后者让 name、salary 也进入排序键，树更「重」且多数时候无谓；INCLUDE 语义更诚实、索引更轻。
  • 唯一索引同样支持：CREATE UNIQUE INDEX ON t (email) INCLUDE (id);——唯一约束只作用于键列。

五、怎么看执行计划：EXPLAIN / EXPLAIN ANALYZE

入门优先看：

字段 / 标记 含义（入门）
Seq Scan 顺序扫表，大表 + 高 rows 要警惕
Index Scan / Index Only Scan 走索引访问
Nested Loop / Hash Join / Merge Join 连接策略
ANALYZE 的 actual time、rows 真实耗时与行数（与统计信息、缓存有关）
BUFFERS 读了多少共享缓冲区（判断是否 I/O 重）

一次逐字段解读

可能的输出（数字为演示）：

字段 读法
cost=0.00..41.97 估算代价：启动成本..总成本，抽象单位，只用于比较计划优劣
rows=2（逗号前） 估算行数；与 actual rows 差一个数量级以上 → 统计信息过期，先 ANALYZE
actual time 实测：首行返回..全部返回耗时（毫秒，每次循环的值）
loops=1 节点执行次数；嵌套循环内侧 loops 会放大，actual time × loops 才是总耗时
Rows Removed by Filter 被过滤掉的行数——「扫 5 留 2」尚可，「扫百万留十行」就该建索引
Buffers: shared hit=1 命中共享缓冲 1 页；read 多 = 磁盘 I/O 重，hit 多 = 内存命中
Execution Time 服务端执行总耗时（不含网络与客户端渲染）

解读顺序：从下往上、从内往外看（缩进越深越早执行）；先抓 actual 耗时最大的节点，再核对它的 rows 估算偏差与 Buffers。

统计信息维护：ANALYZE tbl;（VACUUM ANALYZE 亦可），大变更后应跑。

六、事务与隔离级别（用法向）

1. 基本写法

默认 READ COMMITTED：每条语句看到语句开始时已提交的快照（简化理解）。
REPEATABLE READ：事务内第一条语句建立快照，读一致性更强。
SERIALIZABLE：最强，可能出现 serialization_failure，应用需重试。

八、VACUUM、膨胀与索引维护

PostgreSQL 的 MVCC 会使更新/删除留下死元组；VACUUM（通常由 autovacuum 自动跑）回收空间、更新统计信息。长期不 vacuum 会导致表膨胀、性能变差。
日常开发：大批量导入/更新后，测试库可手动 VACUUM ANALYZE；生产依赖 autovacuum 参数与监控。

1. 索引也会膨胀

PostgreSQL：存储引擎与表访问方法

概念基础

  1. 表访问方法（Table Access Method）：PostgreSQL 12+ 把「表数据如何组织与读写」抽象为可插拔接口，建表时可用 USING 指定，默认即 heap——这是 PostgreSQL 语境里最接近 MySQL「引擎」的概念。
  2. 堆表（Heap）：行按写入顺序无序堆放在页中，用 tid（块号 + 行号） 定位；索引里存的是 tid，查数据通常要「索引 → 回表」。
  3. MVCC 是配套设计：行头维护 xmin / xmax 版本信息，更新与删除产生新版本 / 死元组，由 VACUUM 回收——这直接决定了 PostgreSQL 的性能调优姿势。
  4. 与 MySQL 的本质差别：MySQL 建表时选 ENGINE=InnoDB，PostgreSQL 没有这个开关：统一内核 + 统一 heap，列存、分片等需求走扩展与架构层，而不是换「引擎」。

先看建表与数据类型入门，再看默认的存储方式：

〇、建表与数据类型入门（DDL 速览）

保留字陷阱：order、user 等是保留字，直接当表名会在建表/查询时报语法错误——避开保留字，或统一带双引号（"order"）。

JSONB 的查询与索引写法见 PostgreSQL：高级查询 与 PostgreSQL：索引与性能优化；下面进入正题：这些数据到底怎么存。

一、表数据默认怎么存：Heap（堆表）

  • 普通 CREATE TABLE 默认即 heap 表：行以堆页存放，通过 tid（块号 + 行号） 定位。
  • MVCC 在元组头维护版本信息（xmin / xmax 等），更新与删除产生新版本/死元组，依赖 VACUUM 回收（见 PostgreSQL：索引与性能优化）。
  • 与 InnoDB 聚簇索引即整表不同：PostgreSQL 主键索引是二级索引，堆上存行，主键查找通常「索引 → 回表 tid」。

1. 堆页内部结构

每个堆页默认 8KB（编译期 BLCKSZ），从前往后分四段：

  • PageHeaderData：LSN、校验和、空闲空间起止位置等页级元数据。
  • ItemId（行指针）数组：定长 4 字节，记录页内每个元组的偏移与长度——tid 里的「行号」实际是这个数组的下标，索引指向行指针而非物理位置，所以页内整理（如 HOT 链修剪）不必改索引。
  • 元组区：从页尾向前生长，每行带 23 字节行头（xmin / xmax / ctid / 标志位等）。

2. 行头与 MVCC 版本链

每行元组头部的关键字段：

字段 作用
xmin 创建该行版本的事务 ID
xmax 删除/更新该行版本的事务 ID（0 表示存活）
ctid 指向下一版本的 tid（更新形成版本链）
t_infomask 标志位：事务是否已提交、行是否被锁等

一次 UPDATE = 插入新元组 + 把旧元组 xmax 置为当前事务 + ctid 指向新位置。这就是「更新在 PG 里本质是新增一版」的物理含义，也是死元组与膨胀的来源。

二、TOAST：大字段的行外存储

8KB 页放不下的超长字段（text、大 jsonb、bytea）由 TOAST（The Oversized-Attribute Storage Technique） 接管：超阈值（约 2KB）的值被压缩和/或切片存入附属 TOAST 表，主表行里只留指针。

每张宽表自动挂一张 pg_toast.pg_toast_<oid> 附属表：

四种存储策略（建表时可按列指定）：

策略 压缩 行外存储 适用列
PLAIN 否 否 短字段、int 等定长类型（默认）
EXTENDED 是 是 超长 text / jsonb（变长类型默认）
EXTERNAL 否 是 已压缩的二进制（图片、已 gzip 数据）
MAIN 是 尽量不 中等长度、想留在主表的字段

性能含义：SELECT 不碰 TOAST 列时不读 TOAST 表（天然列裁剪）；但更新 TOAST 列会产生整个新副本——频繁更新的超大字段要考虑拆分表。

三、HOT 更新与 FILLFACTOR

HOT（Heap Only Tuple）更新：当 UPDATE 不改任何索引列且同页有空位时，新元组直接放同页、索引条目不动——省掉一次索引维护 IO，热点行更新快很多。

参数 含义 建议
fillfactor=100（默认） 页塞满才开新页 只增不改的表（日志、数仓）
fillfactor=80~90 预留 10~20% 空间 高频 UPDATE 且不改索引列的表
改了索引列的 UPDATE 无法 HOT 设计上把「状态字段」与「索引字段」分离

判断 HOT 是否生效：

hot_pct 低 + 表膨胀快：检查是否更新了索引列，或 fillfactor 太满。

四、FSM 与 VM：两个辅助映射

映射 全称 作用
FSM Free Space Map（空闲空间映射） 记录每页剩余空间，插入时快速找页，不用全表翻
VM Visibility Map（可见性映射） 标记「页内所有行对所有事务可见」——Index Only Scan 靠它跳过回表；VACUUM 靠它跳过干净页

实务联动：大批量 UPDATE/DELETE 后 VM 失效 → Index Only Scan 退化为 Index Scan + 回表 → 执行计划里 Heap Fetches 暴涨。跑一次 VACUUM ANALYZE 表名 重建 VM 即恢复（详见 PostgreSQL：索引与性能优化）。

五、表访问方法（Table Access Method）

PostgreSQL 12+ 起，表可指定 USING heap（默认）；理论上可挂自定义表访问方法（需扩展提供）。
生产常见仍是 heap；列存、混存等多在扩展或外部产品（如某些分析型方案）中实现，不等价于 MySQL 换一个 ENGINE 字符串。

六、与「引擎」易混的几个概念

概念 说明
TABLESPACE 表/索引的文件放置位置（如 pg_default），不是另一种行存储引擎。
TOAST 大字段行外存储机制，对用户基本透明。
Foreign Data Wrapper（FDW） 外部表：数据在远程；语法像本地表，语义与本地 heap 完全不同，不是换存储引擎。
内置索引类型 B-Tree、Hash、GiST、GIN、BRIN 等是索引访问方法，不是替换 heap 的「表引擎」。

八、WAL：堆页之外的第二套写入

heap 页是「数据落盘的最终形态」，但每次写先走 WAL（Write-Ahead Log）：

  1. 事务修改先在内存缓冲区改页，同时把重做记录追加进 WAL 缓冲区。
  2. COMMIT 时只需 WAL 刷盘（wal_writer / commit 触发 fsync）即算持久——数据页由后台 checkpointer 批量脏写。
  3. 崩溃重启时按 WAL 重放，把未落盘的修改补回数据页。

实务含义：顺序追加的 WAL 远快于随机写数据页——这是 PG 写入性能的根基；WAL 所在磁盘（可用 pg_wal 独立表空间/挂载点）的延迟直接决定提交延迟。

九、分区表：heap 的「水平切片」

声明式分区（PG 10+）把一张逻辑表切成多张物理 heap 子表，每个分区独立享有自己的页、FSM、VM 与索引：

收益 原理
分区裁剪 查询带分区键时只扫命中的子表，等效索引之外的「粗粒度裁剪」
快速归档 DROP TABLE orders_2025_01 或 DETACH PARTITION 秒级删旧数据，不产生死元组
分区级维护 VACUUM / REINDEX 可按分区跑，大表运维粒度变细

取舍：分区数控制在几百以内（过多拖慢规划）；分区键必须出现在所有唯一约束里；查询不带分区键时反而要扫所有分区。

十、实务建议

  1. 学习 PostgreSQL 时少问「用哪个引擎」，多问索引类型、执行计划、VACUUM、隔离级别与锁。
  2. 需要列存、分片、多副本高可用时，在架构层选专用扩展或产品（如 Citus、云厂商数仓、读写分离），而不是在 CREATE TABLE 里找一个 ENGINE 开关。
  3. 版本升级（16 → 17 → 18）会带执行器与优化器演进，「升级引擎」口语上常指升级主版本，与 MySQL 的 ENGINE 不是同一概念。
  4. 写多的表先想 fillfactor 与 HOT，宽表先想 TOAST 策略，只读大表先想 VM 与 Index Only Scan——三个杠杆都长在 heap 结构之上。

第五章：MySQL 存储引擎

概念基础

存储引擎是 MySQL 「表数据如何存、如何取」的可插拔实现：

  1. 分层架构的产物：Server 层负责 SQL 解析、优化、权限；引擎层负责数据在磁盘与内存上的组织——索引结构、事务、锁、崩溃恢复都由引擎决定；同一份表结构，换引擎行为完全不同。
  2. InnoDB 是唯一默认答案：支持 ACID 事务、行级锁、MVCC、崩溃恢复（redo / undo）、聚簇索引与外键；官方默认且推荐，第五章讲的 B+ 树与回表，说的就是 InnoDB 的组织方式。
  3. MyISAM 是历史遗产：表级锁、不支持事务、崩溃安全性弱，只存在于老系统与只读库中；新业务一律避开——它也解释了第三章「表锁并发差」的历史背景。
  4. 换引擎不解决性能问题：性能瓶颈优先从索引、SQL 写法、事务与连接设计入手（第三、四、五章的内容）；引擎选型是「事务要不要」的问题，不是「快不快」的问题。
  5. 插件式带来专用选择：ARCHIVE（冷归档压缩）、CSV（数据管道交换）、BLACKHOLE（写入即弃的中继）、NDB（分布式集群）各有专属场景，是否可用以 SHOW ENGINES 为准。

InnoDB 架构深入：内存与磁盘的协作

InnoDB 的高性能不是来自单一技巧，而是内存结构 + 磁盘结构 + 后台线程三者协作的结果。理解下面四个组件，才能解释「为什么写入快、为什么崩溃不丢数据」。

1. 缓冲池（Buffer Pool）

  • 定位：InnoDB 最大的内存区域，缓存数据页与索引页（默认页大小 16KB）；读请求先查缓冲池，命中则零磁盘 I/O。
  • ** sizing**：专用库服务器常配物理内存的 50%–70%：
  • 淘汰策略：改良版 LRU——新读入的页先放在「中点」（约 5/8 处），全表扫描的页不会立刻挤掉热数据，由 innodb_old_blocks_pct / innodb_old_blocks_time 控制。
  • 脏页刷盘：修改先在内存中进行，页变「脏页」后由后台线程异步刷回磁盘；这就是写入快的第一层原因。

2. Change Buffer（写缓冲）

  • 解决的问题：二级索引页的更新是随机 I/O——更新一行可能要改散落在磁盘各处的多个索引页。
  • 做法：若目标二级索引页不在缓冲池，先把变更记录到 Change Buffer（缓冲池的一部分），稍后在页被读入内存时再合并（merge），把随机写变成顺序写。
  • 限制：只对非唯一二级索引有效；唯一索引必须立刻读页做唯一性检查，无法缓冲。
  • 适用场景：写多读少、二级索引多的表（如日志表）；8.0 起由 innodb_change_buffering 控制（默认 all）。

3. Doublewrite Buffer（双写缓冲）

  • 解决的问题：页部分写（partial page write）——16KB 的页在操作系统 4KB 扇区下可能只写了一半就宕机，redo log 无法修复不完整的页。
  • 做法：刷脏页时先把页顺序写入共享表空间的 doublewrite 区（2 份，约 2MB×2），确认成功后再写回数据文件；崩溃恢复时若发现数据文件页损坏，从 doublewrite 拷贝完整页再用 redo 前滚。
  • 代价与取舍：带来约一倍写入量，但 doublewrite 区是顺序写，实际开销通常 <10%；严禁为追求性能关闭（innodb_doublewrite=ON 默认）。

4. 自适应哈希索引（Adaptive Hash Index, AHI）

  • InnoDB 观察到某些索引值被频繁等值访问时，自动在内存中为其建立哈希索引，把 B+ 树的 O(log n) 查找降为 O(1)。
  • 全自动：由 innodb_adaptive_hash_index 控制（默认 ON），无需人工干预；高并发下 AHI 的互斥锁偶成瓶颈，可通过 SHOW ENGINE INNODB STATUS 的 SEMAPHORES 段观察，必要时关闭。

5. Redo 与 Undo 的分工回顾

日志 作用 物理/逻辑

第四章：MySQL 索引与性能优化

概念基础

索引是数据库用额外空间与写成本换取查询速度的有序数据结构：

  1. 本质是一棵 B+ 树：把无序的表数据额外组织成有序树，查询从「全表逐行扫」变成「沿树下降读少量页」——随机 I/O 大幅减少；代价是每次 INSERT/UPDATE/DELETE 都要同步维护树，所以索引不是越多越好。
  2. 聚簇索引即数据本身：InnoDB 表数据按主键组织成 B+ 树，叶子节点存「主键 + 整行」；二级索引叶子只存「索引列 + 主键」，命中后常需回表再查一次聚簇索引——这就是主键要自增、查询要少 SELECT * 的根因。
  3. 联合索引遵守最左前缀：(a, b, c) 先按 a 排、a 相同再按 b、再按 c；跳过 a 的条件用不上树，等值列在前、范围列在后是最常见的设计。
  4. 覆盖索引是回表的解药：查询列全在索引里就只扫索引不回表（EXPLAIN 显示 Using index）；与之配套的 ICP 把过滤条件下推到引擎层，进一步少回表。
  5. 优化是一个闭环而非玄学：慢日志抓 Top SQL → EXPLAIN 看 type / key / rows / Extra → 改索引或改写法 → 再对比慢日志；本章同时覆盖事务隔离与备份恢复，给出完整的「开发侧性能地图」。

从 B+ 树的直觉开始：

一、索引在干什么：B+ 树直觉（够用版）

InnoDB 里，表数据按主键组织成一棵 B+ 树（聚簇索引）：叶子节点存「主键 + 整行数据」。
二级索引（你建的 INDEX / UNIQUE）叶子节点存「索引列 + 主键」，需要整行时往往要再回表到聚簇索引取数据。

  • 索引不是越多越好：每次 INSERT/UPDATE/DELETE 都可能维护多棵索引树。

二、联合索引与最左前缀

联合索引 KEY idx_abc (a, b, c) 的排序语义是：先按 a，再 a 相同时按 b，再按 c。

能较好利用该索引的典型条件（示意）：

  • WHERE a = ?
  • WHERE a = ? AND b = ?
  • WHERE a = ? AND b BETWEEN ? AND ?

容易用不上或只用一截的情况：

  • WHERE b = ? AND c = ?（缺 a，与「最左」不一致）
  • WHERE a = ? OR d = ?（OR 另一侧常走另一条路径，易优化成 UNION 或改写法）
  • 对 a 做函数/隐式类型转换导致无法走树（例如 WHERE DATE(a_col) = ...）。

设计经验：把区分度高、过滤性大的列尽量放左侧；把范围查询列放联合索引右侧更常见（仍要结合 EXPLAIN 验证）。

查询写法 能否用上 idx_u_s_c 原因

WHERE user_id = 100 AND status = 1 ✅ 用到前 2 列 连续等值
WHERE user_id = 100 AND status = 1 AND created_at > '2026-01-01' ✅ 全用上（范围列截断） 范围之后无法再精确定位，但范围本身也走索引

三、覆盖索引（Using index）

若 SELECT 里出现的列都能从某条二级索引的叶子直接凑齐（含 WHERE 用到的索引列），InnoDB 可能只扫索引、不回表，EXPLAIN 的 Extra 常见 Using index。

典型收益：大宽表上只查少数列 + 条件列恰好在同一联合索引上，I/O 明显下降。

覆盖索引实例对比

实战推论：

  1. 列表接口只 SELECT 需要的列，常能把慢查询「救」成覆盖索引；
  2. 热点查询可以把展示列一起放进联合索引尾部（适度冗余换免回表），但索引变宽后写放大与缓存占用同步上升，需权衡；
  3. 二级索引叶子天然带主键，所以 SELECT id 永远不需要额外加主键列进索引。

四、索引条件下推 ICP

Index Condition Pushdown：把部分 WHERE 条件下推到存储引擎层，在索引扫描过程中就过滤，少回表。
在 EXPLAIN 里常见 Using index condition（与 Using index 不同：后者多为覆盖索引）。

ICP 生效前 vs 生效后

  • 无 ICP（5.6 之前）：引擎按 user_id = 100 扫出所有索引项 → 每行回表取整行 → 再由 Server 层过滤 created_at；回表次数 = user_id=100 的全部行数。
  • 有 ICP（默认开启）：created_at LIKE '2026-06%' 被下推到引擎层，在索引扫描途中就用索引里的 created_at 列先过滤一遍，只有通过的行才回表；Extra 显示 Using index condition。

结论：ICP 对「联合索引只命中前缀、剩余列做过滤」的场景收益最大；它不改变索引选择，只减少回表行数。

九、索引进阶：MRR、隐形索引、索引合并与选型决策树

1. MRR（Multi-Range Read，回表前的「攒批排序」）

问题：二级索引范围扫描命中 N 行后，需要按主键回表 N 次——主键无序时这是 N 次随机 I/O。

做法（MRR）：先把命中的主键收集到 buffer 排序，再按主键顺序回表，把随机 I/O 尽量变成顺序 I/O。EXPLAIN 的 Extra 中可见 Using MRR。

适用：非覆盖索引的范围扫描（如 BETWEEN、大 IN 列表）；等值点查无所谓 MRR。它与 ICP 是同一链路上的两个优化：ICP 减少「要回表的行数」，MRR 优化「回表的 I/O 方式」。

2. 隐形索引（Invisible Index，8.0+）

  • 隐藏后优化器当它不存在，但索引仍随 DML 维护（不产生回滚风险）；
  • 典型用途：想删索引又怕删错——先 INVISIBLE 观察一段时间，确认无慢查询再真正 DROP；也可用来 A/B 验证某索引是否被使用；
  • 主键不能隐藏；全局开关 optimizer_switch = 'use_invisible_indexes=on' 可临时让隐藏索引参与优化（测试用）。

3. 索引合并（Index Merge，了解即可）

当单表上存在多个单列索引、查询条件是它们的 AND/OR 组合时，优化器可能同时扫多棵索引再取交/并集，type 显示 index_merge，Extra 见 Using intersect(...) / Using union(...)。

态度：索引合并通常是**「没有建联合索引」的次优补偿**，效率一般不如一条设计良好的联合索引。看到 index_merge 应视为合并成联合索引的信号，而不是优化成功的标志。

第三章：MySQL 高级查询

概念基础

高级查询是超越单表 SELECT ... WHERE 的多表、分组、窗口类查询，核心是把拆开存的关系拼回来：

  1. 为什么数据要拆开存：关系模型按范式把业务拆成多张表（如 emp 员工表与 dept 部门表），避免重复存储；查询的本质就是用 JOIN / 子查询按关联字段把数据重新拼装——第一章建的表结构，在这里被「消费」。
  2. JOIN 的语义差异决定丢不丢数据：INNER JOIN 只保留两表都匹配的行；LEFT JOIN 保留左表全量、右表无匹配补 NULL。选错连接类型，统计结果会悄悄少行，是报表错乱的头号来源。
  3. 聚合把「多行」压成「一行」：GROUP BY 分组后才能用 COUNT / SUM / AVG；过滤顺序是 WHERE（分组前滤行）→ GROUP BY → HAVING（分组后滤组），颠倒位置直接报错或结果不对。
  4. MySQL 8.0+ 的两大武器：CTE（WITH） 把复杂查询拆成可读的「临时结果」并支持 RECURSIVE 查树；窗口函数在不减少行数的前提下做组内排名、累计——「每组 Top N」从此有了标准解法。
  5. 性能意识贯穿始终：判断存在性优先 EXISTS，合并结果优先 UNION ALL（免去去重排序），深分页 LIMIT 大 OFFSET 会越来越慢、生产改用键集分页——写法差异就是性能差异。

第二章：MySQL 锁详解

概念基础

锁是数据库的并发控制机制，让多个事务在共享同一份数据时「不打架」：

  1. 没有锁会发生什么：多个会话同时读写同一行，会出现脏读、不可重复读、幻读与更新丢失；锁的本质是给「当前读」排队，保证数据一致性。
  2. 核心权衡是一致性 vs 并发：锁粒度越粗（全局锁、表锁）越安全但并发差，粒度越细（行锁）并发越高但开销越大——InnoDB 的答案是以行锁为主 + MVCC 快照读，普通 SELECT 不加锁，读写大部分场景互不阻塞。
  3. InnoDB 行锁的本质是锁索引：锁加在索引记录上而不是物理数据行上；查询条件无索引或索引失效时，行锁会退化为表锁，并发直接崩塌，这是本章最重要的一条结论。
  4. 隔离级别决定加锁行为：**RR（可重复读）默认用临键锁（记录锁 + 间隙锁）**抑制幻读，代价是范围锁会阻塞插入；**RC（读已提交）**没有间隙锁，并发更高但存在幻读。
  5. 锁是双刃剑：用好了高并发不冲突，用坏了就是锁等待、死锁、业务雪崩——长事务、无索引更新、交叉加锁是线上三大事故来源，本章实验与面试题全部围绕这些展开。

七、实战高频坑（必避）

  • 行锁三形态：记录锁、间隙锁、临键锁（RR 防幻读）

十、五大实验：现象、原理与面试标准答

与第九节中五个脚本场景一一对应：现象 → 底层原理 → 面试可直接背诵的表述。

统一前提：

  • 引擎：InnoDB
  • 隔离级别：RR 可重复读（默认）
  • 锁粒度：行锁依赖索引，无索引降级为表锁

实验一：行排他锁 FOR UPDATE 阻塞演示

执行流程

会话1：开启事务 → id=1 加 FOR UPDATE 不提交
会话2：修改 id=1 被阻塞；修改 id=2 正常执行

现象

  1. 同一条主键记录：写操作被阻塞
  2. 不同主键记录：完全不受影响
  3. 会话1 commit 后，会话2立刻执行成功

底层原理

  1. FOR UPDATE 加 行级排他锁（X锁）
  2. 排他锁规则：写写互斥、读写互斥
  3. InnoDB 行锁只锁索引命中的单行，不影响其他行

面试标准答案

InnoDB 中通过主键/唯一索引精准查询加 FOR UPDATE，会加行级排他锁；只锁定当前命中的单行记录，其他行不受影响，能保证高并发。排他锁与任何读写操作都互斥，事务提交后锁自动释放。

实验二：无索引导致行锁退化为表锁

执行流程

按无索引字段 age=20 更新，会话1不提交，会话2更新完全无关的 id=2 也被阻塞

现象

明明更新不同行，却整张表都被锁住，所有写操作全部阻塞

底层原理

  1. InnoDB 行锁是锁索引，不是锁数据行
  2. 条件字段无索引，MySQL 无法定位具体行
  3. 只能逐行加行锁扫描全表，最终退化成表级锁

面试标准答案

InnoDB 行锁必须依赖索引。如果更新/删除条件没有索引或索引失效，MySQL 无法精确定位行记录，会扫描全表并逐行加锁，最终行锁降级为表锁，严重降低并发性能，开发中必须保证更新条件走索引。

实验三：共享锁与读写互斥演示

执行流程

会话1：LOCK IN SHARE MODE 加共享锁
会话2：普通SELECT能查，UPDATE/DELETE被阻塞

现象

  1. 多个事务可以同时加共享锁（读读兼容）
  2. 加了共享锁后，其他事务不能加排他锁、不能修改数据
  3. 事务提交后，写操作立刻放行

底层原理

  • 共享锁（S锁）：读读兼容，读写互斥
  • 意向锁辅助，S锁阻塞所有写操作，保证数据当前快照不被修改

面试标准答案

共享锁（S锁）又叫读锁，使用 LOCK IN SHARE MODE 加锁。特性是读读可以并发，读写、写写互斥；适合需要强一致性、临时禁止别人修改数据的场景，事务提交自动释放锁。

实验四：间隙锁与临键锁阻塞插入（RR 与幻读）

执行流程

会话1：范围查询 between 1 and 3 for update 不提交
会话2：插入区间内新 ID，直接被阻塞

现象

没有任何行被修改，只是范围加锁，却无法往区间里插入新数据

底层原理

  1. MySQL RR 隔离级别默认使用 Next-Key Lock 临键锁
  2. 临键锁 = 记录锁 + 间隙锁
  3. 范围查询会锁住索引区间间隙，禁止其他事务插入新记录，解决幻读
  4. 间隙锁只在 RR 存在，RC 隔离级别没有间隙锁

面试标准答案

InnoDB 在 RR 可重复读隔离级别下，采用临键锁（Next-Key Lock） 解决幻读。临键锁由记录锁+间隙锁组成，范围查询会锁定索引左右间隙，禁止其他事务在区间内插入数据；RC 读已提交级别会关闭间隙锁，因此无法彻底避免幻读，但并发更高。

实验五：经典死锁复现

执行流程

  • 事务1：先锁 id=1 → 再请求锁 id=2
  • 事务2：先锁 id=2 → 再请求锁 id=1
  • 互相等待，立刻触发死锁，MySQL 自动回滚一个事务

现象

  1. 互相持有对方需要的锁，循环等待
  2. InnoDB 自动死锁检测，回滚代价小的事务，抛出死锁异常
  3. 不会无限阻塞

底层原理

死锁产生四个必要条件同时满足：

  1. 互斥条件：锁资源独占
  2. 持有并等待：自己拿着锁，还等别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务形成等待环路

面试标准答案（必背）

死锁产生必须同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待。
规避方案：

  1. 统一多事务访问资源的顺序；
  2. 拆分长事务，尽早提交；
  3. 避免在事务中做无关耗时操作；
  4. 合理设置锁等待超时时间。
    InnoDB 自带死锁检测机制，发现循环等待会自动回滚一个事务，避免程序卡死。

十一、面试高频一句话速记

  1. 行锁靠索引，无索引变表锁
  2. S 锁读读兼容，X 锁完全独占
  3. RR 有间隙锁防幻读，RC 没有
  4. 交叉改不同行、顺序乱写易出死锁

十二、二十道高频面试题与标准答

全部面试可直接背诵，基于 InnoDB、RR 隔离级别，精简不废话。

1. MySQL 有哪些锁分类？

答案

  1. 按粒度：全局锁、表级锁、行级锁
  2. 按读写：共享锁S、排他锁X
  3. InnoDB 特有：意向锁、记录锁、间隙锁、临键锁

2. 全局锁作用是什么？怎么加？

答案
整库只读，所有库表只能读不能写、阻塞 DDL/DML。
加锁：FLUSH TABLES WITH READ LOCK;
解锁：UNLOCK TABLES;
多用于全库逻辑备份；生产优先用 mysqldump --single-transaction 快照备份，不加锁。

3. 什么是 MDL 元数据锁？

答案
访问表时自动加，保护表结构不被中途修改/删除。
长事务不提交 + 执行 DDL 改表结构，会造成 MDL 锁等待阻塞，线上高发故障点。

4. 表锁和行锁区别？

答案

  • 表锁：粒度大、开销小、并发低、MyISAM 默认
  • 行锁：粒度小、开销大、并发高、InnoDB 支持
    InnoDB 优先用行锁提升并发。

5. 共享锁S、排他锁X 特性？

答案

  • 共享锁S：读读兼容，读写/写写互斥
  • 排他锁X：读写、写写全部互斥，独占资源
    加锁：
    S：select ... lock in share mode
    X：select ... for update

6. 意向锁 IS/IX 作用？

答案
意向锁是表级锁，事务加行锁前必须先加意向锁。
作用：快速判断表内是否有行锁，不用遍历所有行锁，提升加锁效率。

  • IS：要加 S 行锁
  • IX：要加 X 行锁
    意向锁之间互相兼容，只和表级 S/X 锁互斥。

7. InnoDB 行锁本质是什么？

答案
行锁锁的是索引，不是物理数据行。
查询条件无索引、索引失效，行锁会退化成表锁，并发骤降。

8. 什么情况下行锁会降级为表锁？

答案

  1. where 条件无索引字段
  2. 索引失效（函数、隐式类型转换、like 前缀模糊等）
  3. 没有命中任何记录，全表扫描加锁

9. InnoDB 三种行锁算法？

答案

  1. 记录锁：锁单行索引记录
  2. 间隙锁 Gap Lock：锁索引间隙，不锁记录，防止幻读插入
  3. 临键锁 Next-Key Lock = 记录锁+间隙锁，左开右闭区间，RR 默认

10. 间隙锁什么时候生效？什么时候关闭？

答案

  • 生效：RR 可重复读隔离级别、范围查询/不走唯一索引等值查询
  • 关闭：RC 读已提交 没有间隙锁，并发更高，但会有幻读

11. 临键锁解决了什么问题？

答案
在 RR 隔离级别下，通过临键锁+间隙锁彻底解决幻读，禁止其他事务在索引区间插入新数据。

12. 什么是幻读？怎么解决？

答案
同一事务内，前后两次范围查询，查到别人新插入的数据。
解决：

  • 数据库层：InnoDB RR + 临键锁
  • 业务层：悲观锁、分布式锁限制插入

13. 死锁产生的四个必要条件？

答案

  1. 互斥：锁资源独占
  2. 持有并等待：拿着自己的锁，等待别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务互相等待形成环路

14. MySQL 怎么处理死锁？

答案
InnoDB 有自动死锁检测，检测到循环等待后，自动回滚代价更小的一个事务，抛出死锁异常，避免无限阻塞。

15. 如何避免 MySQL 死锁？

答案

  1. 统一所有事务访问资源/更新行的顺序
  2. 精简事务，避免长事务，尽早 commit
  3. 事务内不做耗时网络/IO 操作
  4. 合理设置锁等待超时 innodb_lock_wait_timeout

16. for update 和 lock in share mode 区别？

答案

  • for update：加排他锁X，别人不能读也不能改
  • lock in share mode：加共享锁S，别人可以读、不能改

17. RR 和 RC 在锁层面最大区别？

答案

  1. RR 有间隙锁/临键锁，防幻读；RC 没有
  2. RC 行锁范围更小、并发更高，但存在幻读
  3. RC 锁释放更早，阻塞更少

18. 长事务有什么锁风险？

答案
长事务不提交：

  1. 行锁、MDL 锁长期不释放
  2. 造成大量锁等待、业务阻塞
  3. undo log 不能清理，占用磁盘
  4. 容易触发死锁、数据库性能雪崩

20. 线上开发写 UPDATE 防锁坑要注意什么？

答案

  1. 更新条件必须走索引，防止行锁变表锁
  2. 尽量用主键/唯一索引精准等值，少用范围查询
  3. 事务尽量短小，及时提交

1. MDL 元数据锁实战案例（线上最高发的锁事故）

场景复现

会话 1：一个忘记提交的长事务，哪怕只是查了一次：

会话 2：DBA 在低峰期加个字段：

会话 3 及之后：所有新查询全部排队：

现象：整张表读写全堵，连接数飙升，业务报警——而根源只是一个没提交的事务。

原理

  • MDL 不需要显式加：访问一张表自动加 MDL 共享锁（读/写），DDL 需要 MDL 排他锁；
  • 排他锁在队列里等待时，后来的共享锁也要排队（防饿死策略），所以一个被卡住的 DDL 会堵死整张表的所有新请求；
  • 等待超时由 lock_wait_timeout（默认 1 年！）控制——DDL 被 MDL 卡住默认永不超时，必须人工干预。

排查与止血（MySQL 8.0）

预防三件套：

  1. 应用侧严禁长事务，autocommit=1 保持默认；
  2. DDL 前查长事务：SELECT * FROM information_schema.innodb_trx WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;
  3. DDL 语句显式缩短等待：ALTER TABLE ... , LOCK=DEFAULT 无效于 MDL，要靠低峰窗口 + 语句超时（部分版本支持 lock_wait_timeout 会话级临时调小）。

2. Online DDL 与锁（8.0/8.4 的三种算法）

算法 锁表行为 速度 典型操作
INSTANT 仅瞬间 MDL 秒级（与表大小无关） 末尾加列、删列（8.0.29+）
INPLACE 开始/结束各一次短暂 MDL，中间可读写 与表大小成正比 加索引、改列类型（部分）
COPY 全程禁写 慢，双倍磁盘 改存储引擎等兜底场景

实战要点：

  1. 优先 INSTANT：ADD COLUMN 默认就走 INSTANT（8.0），无需指定；可用 SHOW WARNINGS 或 information_schema.tables 的 ALGORITHM 记录确认；
  2. INPLACE 仍会抢两次 MDL——长事务环境下照样卡，执行前照第 1 节流程排查；
  3. **大表变更（千万行以上）**生产惯例走 gh-ost / pt-online-schema-change：影子表 + binlog 追增量，把锁窗口压到毫秒级切换；
  4. DDL 期间磁盘：COPY/部分 INPLACE 需要额外一份表大小的空间，磁盘水位不足会直接失败。
