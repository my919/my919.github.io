第九章：Redis Geospatial：概念、命令与案例

概念基础

Geospatial（GEO） 是 Redis 的地理位置模块——存经纬度坐标，提供「附近有什么」「两点距离多远」的原生查询能力：

  1. 数据仍落在 ZSet 上：TYPE key 一般为 zset；member 为地点 ID，score 为 Geohash 编码（使用者通常只调 GEO 命令）。
  2. 坐标使用经度、纬度（GEOADD 参数顺序为 lon lat，勿写反——这是 GEO 最常见的第一个坑）。
  3. 它是 第六章：Redis ZSet 数据类型：概念、命令与案例 的空间特化：排序键从「积分」变成了「地理位置编码」，排序即「从西到东、从南到北」，近邻查询就是一次score 范围扫描。
  4. 地球模型为球面近似，极高精度场景需自行评估误差。
  5. 合法坐标范围：经度 [-180, 180]、纬度 [-85.05112878, 85.05112878]（Web 墨卡托边界），越界写入会报错。

核心原理：Geohash 编码与近邻查询

1. Geohash 编码

把经度区间 [-180,180]、纬度区间 [-90,90] 反复二分——经度偏西记 0、偏东记 1，纬度偏南记 0、偏北记 1，两边比特交错拼成一串二进制。二分越深，编码越精确。

2. 为什么「二分交错」有效

交错后，前缀相同的两个编码，地理位置必然相近；编码的大小顺序 ≈ 地理位置顺序。Redis 把这个二进制串转成 52 位整数作为 ZSet 的 score——于是「附近查询」变成了「score 在邻域区间内的范围扫描」，完全复用跳表的 O(logN) 能力（这正是第七章双结构的红利）。

3. 距离计算

GEODIST 用球面距离（Haversine 类公式）计算两点弧长，可选 m / km / ft / mi 单位；成员不存在返回 nil。

4. API 演进

Redis 6.2+ 推荐 GEOSEARCH（支持 BYRADIUS / BYBOX、ASC/DESC、COUNT、带 WITHDIST/WITHCOORD/WITHHASH），GEORADIUS / GEORADIUSBYMEMBER 已被视为过时接口；GEOSEARCHSTORE 可把结果直接落到新 key。新代码优先 GEOSEARCH 系列。

5. 时间复杂度

命令 复杂度 说明
GEOADD O(logN) 每成员 本质是 ZADD
GEOSEARCH O(N + logN·M) 级 N 为返回数，邻域扫描
GEODIST / GEOPOS / GEOHASH O(1) 查分/解码

常用命令

命令 作用
GEOADD key lon lat member [lon lat member …] 添加或更新坐标
GEODIST key m1 m2 [单位] 两点距离；单位 m / km / ft / mi
GEOSEARCH key FROMLONLAT lon lat BYRADIUS r km 以坐标为中心查半径内成员（6.2+ 推荐）

GEOSEARCHSTORE dest src … 把查询结果落到新 key（可 STOREDIST）

典型应用场景

  1. 附近门店：GEOADD shops …，用户定位后 GEOSEARCH 取 3 km 内门店按距离升序。
  2. 配送范围校验：GEODIST 与阈值比较，或 GEOSEARCH FROMMEMBER user BYRADIUS 3 km 看骑手是否在圈。
  3. 附近的人/动态：社交 App 把用户实时位置定期 GEOADD，下拉刷新时 GEOSEARCH。
  4. 共享单车/充电宝点位：车锁开关闭合时上报坐标，找车页 GEOSEARCH BYRADIUS 1 km。
  5. 同城内容粗筛：动态发布时 GEOADD 到 feed:geo:{city}，同城 Tab 按用户坐标拉附近动态 ID 再回库。
  6. 与外部地图：Redis 做粗筛（候选集），精确路径规划与 ETA 交给地图 API。

要点：更新即 GEOADD 重写、下线即 ZREM；另可给 key 本身或业务层「最后活跃时间」配合定时任务清扫僵尸位置，避免「附近的人」里躺着三天前的幽灵坐标。

4. GEOSEARCHSTORE：结果物化与分页

适合「用户原地翻页」场景：第一次查算邻域，后续翻页零地理计算；用户移动了再重算。

5. 城市分片：多 key 路由

分片把单 key 规模锁在「一城 POI 量级」，跨城查询（少见）由应用层并发查多个 key 再归并；这也是第七章「热 key 分片」思路在 GEO 上的复用。

6. 配送范围校验：GEODIST 判圈

注意 GEODIST 是直线球面距离，真实骑行距离更长——阈值要按「直线 × 绕行系数（常取 1.3~1.5）」校准，或候选通过后再调地图 API 算路网距离二次过滤。

7. 与 ZSet 命令混用：清点城市存量

这条「混用通道」是 GEO 运维的常备手段：计数用 ZCARD、删除用 ZREM、遍历用 ZSCAN；只读坐标才走 GEOPOS。

进阶：52 位 Geohash 的精度账

score 用 52 bit：经纬度各 26 bit 交错。经度 360° / 2^26 ≈ 5.4×10^-6°，对应地面约 0.6 m——编码分辨率远高于手机定位精度（通常 5~50 m），所以瓶颈在定位信号，不在 Redis 编码。GEO 系列查询的网格边界效应（同一格子两端可能被算作远邻）由 Redis 内部「查 8 邻域格子」抹平，业务无需处理；但跨 ±180° 经线与两极附近邻域拼接有边界效应，常规城市业务无感。

常见坑与注意事项

  1. 经度纬度顺序：lon 在前 lat 在后；写反后不会报错，但查询结果全错——录入后立即 GEOPOS 抽检一个点。
  2. 跨版本 API：Redis 6.2+ 引入 GEOSEARCH 等，生产以当前版本文档为准；Redis 8.x 下旧 GEORADIUS 仍兼容但应迁移。
  3. 数据量：全国级 POI 全进一个 key 可能过大，可按城市分片多个 GEO key（shops:sh / shops:bj），查询时按用户所在城市路由。
  4. 位置更新频率：「附近的人」类业务若每秒 GEOADD 百万次，写放大明显；应降频上报（如移动超 200 m 才更新）并给不活跃成员 ZREM 清理。
  5. 本质是 ZSet：可直接用 ZREM / ZCARD 管理成员；但不要直接 ZADD 数字 score——会破坏 Geohash 语义。
  6. 两极与 180° 经线：Geohash 在经度 ±180° 与纬度极限附近有边界效应，普通业务（城市内）无感，跨国/极地场景需评估。
  7. 坐标系一致性：国内地图常用 GCJ-02（火星坐标），GPS/海外 API 多为 WGS-84，两者同一地点可差数百米——入库前必须统一到同一坐标系，否则 Redis 里的「附近 500 m」全错；且 Redis 不做坐标转换，转换在接入层完成。
  8. GEODIST 的 nil：任一成员不存在返回 nil 而非报错，应用层判空别当成 0 距离；门店被 ZREM 下架后未同步清理依赖方就会出现这种情况。
  9. GEOADD 是「添加或更新」：同 member 重写坐标不报错——这既是更新手段也是坑，写入前确认 member 命名唯一（如统一 store:{id}），误用同名 member 会静默覆盖别人坐标。

第七章：Redis Bitmap 数据类型：概念、命令与案例

概念基础

Bitmap（位图） 不是一种独立类型，而是 String 的「位视角」——把值的每个二进制位当作一个独立元素来读写：

  1. 按位偏移读写 0/1，可 BITCOUNT 统计 1 的个数，BITOP AND/OR/XOR/NOT 做位运算。
  2. 省空间：1 亿个布尔标记理论上只需 ~12 MB（10^8 ÷ 8 字节），比「每个用户一个 String key」的 key 头开销小得多（仍要算总内存）。
  3. offset 从 0 开始；未设置位视为 0。
  4. 心智模型：offset 是「编号」（用户 ID、第几天），位值是「状态」（是否签到/是否活跃）——用之前先设计好编号 → offset 的映射规则，是 Bitmap 唯一的难点。
  5. SETBIT 返回该位原来的值——利用这一点可以判断「今天是否首次签到」（旧值 0 → 首次）。

核心原理：存储与内存账

1. 本质是 String

位图数据就存在 SDS 字节串里；所以 EXPIRE 照常可用，STRLEN 返回占用字节数（BITCOUNT 统计的是 1 的个数，两者含义不同）。底层用 popcount 指令做统计，O(N) 但极快（现代 CPU 单指令处理 8 字节）。

2. 内存账

占用 ≈ (最大 offset ÷ 8) 字节。与设了几个 1 无关，只与最大 offset 有关：

最大 offset 约占用内存
100 万 122 KB
1 亿 12 MB
10 亿 119 MB

稀疏 ID 是大坑：只有 100 个用户但 ID 是十亿级时，SETBIT dau 1000000000 1 也会为最大 offset 分配整段空间——这就是注意事项里「分桶」的原因。

3. offset 上限与位序

offset 上限 2^32 - 1（约 42.9 亿位，对应 512 MB 的 String 上限）。字节内位序为大端（offset 0 是第 0 字节的最高位），这影响 GET 原样读出后人工解读，但不影响 SETBIT/GETBIT 的正确性。

4. 时间复杂度

命令 复杂度 说明
SETBIT / GETBIT O(1) 直接定位字节与位
BITCOUNT O(N) N 为字节数，popcount 极快
BITPOS O(N) 顺序扫
BITOP O(N) 对两个大位图做 AND/OR 是同步执行——超大位图运算放低峰期或拆小
BITFIELD O(1) 每子命令 一次操作多个位域（如 2 位存「未读/已读/置顶」三态）

常用命令

命令 作用
SETBIT key offset value value 为 0 或 1；返回旧值
GETBIT key offset 读某一位
BITCOUNT key [start end [BIT]] 统计 1 的个数（7.0+ 支持 BIT 按位区间）
BITOP operation destkey key [key ...] 多 key 位运算写入 dest（AND/OR/XOR/NOT）
BITPOS key bit [start [end]] 找第一个 0/1 的位置
BITFIELD key [GET/SET/INCRBY …] 位域级读写（多状态压缩存储）

典型应用场景

  1. 签到：sign:2026:05:user:1001 用「当月第几天 - 1」映射 offset，31 天只占 4 字节；连续签到天数用 BITPOS 找最近一次 0 的位置推算。
  2. 日活标记：dau:2026-05-03 下 offset = 用户整型 ID，次日 BITOP AND 两天位图即得「留存」（昨日活跃 ∩ 今日活跃）。
  3. 与 HyperLogLog：Bitmap 偏「谁来了」的位图（能回答「某用户来没来」）；UV 近似计数用 HLL（回答「大约多少人」）。
  4. 布隆过滤器底座：自研 Bloom Filter 可用 Bitmap 存位数组，多哈希函数对应多个 offset（生产直接用 RedisBloom 模块更省心）。
  5. 多状态压缩：BITFIELD 用 2~4 位存一个枚举状态，比每位图只存布尔利用率更高。

常见坑与注意事项

  1. 稀疏 ID：用户 ID 为 十亿级 时，SETBIT dau 1000000000 1 会促使底层分配很长空间，可能极度浪费；需分桶（如 dau:{date}:{uid/1000000} 段内取模）或换结构。
  2. TTL：位图也是 String，可 EXPIRE；按周期命名的 key（如 dau:2026-05-03）记得设过期防堆积。
  3. 统计口径：BITCOUNT 是「1 的个数」，业务上对应「签到天数」等要先设计好 offset 含义。
  4. 大位图 BITOP：两个 119 MB 位图做 AND 要扫全部字节，同步执行会阻塞，放低峰或分桶。
  5. 跨 key 长度不一：BITOP AND 结果长度取最长输入，短 key 缺位按 0 处理——口径不一致时结果可能出乎意料。
  6. BITOP NOT 的补位陷阱：NOT 只接受单操作数，且结果位数取决于输入 key 长度；对「从未写过的高位」取反会得到 1——「求未签到名单」不能简单 NOT，要用全 1 基准位图做 XOR。
  7. BITPOS 找不到时的返回值：全 0 位图找 1 返回 -1；找 0 时若 key 不存在按「offset 0 即 0」返回 0——判空 key 与真实位要区分。
  8. 与 Set 存标记的取舍：1 亿布尔标记用 Set 需数 GB（每成员一份 SDS + dictEntry），Bitmap 仅 ~12 MB；但 Set 能枚举成员、Bitmap 不能反向查「所有签了的人」——要明细回查选 Set，要极致省空间选 Bitmap。
  9. 首次写超大 offset 的瞬时分配：SETBIT 需要把 SDS 扩展到对应长度，首次写 offset=4 亿会一次性分配 ~50 MB 并清零——单线程下这是一次可感知的卡顿，生产上预热（启动时对各桶写一次最高位再清 0）或分桶规避。

第八章：Redis HyperLogLog：概念、命令与案例

概念基础

HyperLogLog（HLL） 是一种基数（去重计数）估算算法的数据结构——用极小的固定内存回答「这批元素大约有多少个不同的」：

  1. 不是存明细，只支持 PFADD 添加元素、PFCOUNT 估算基数、PFMERGE 合并多个 HLL。
  2. 内存奇迹：无论存 1 万还是 1 亿个元素，每个 HLL 固定约 12 KB——对比 Set 存 1 亿个 ID 要数 GB，差距是数量级的。
  3. 代价是近似：标准误差约 0.81%（1 亿 UV 估出 99.2M±80 万属正常）。
  4. 适合：海量 UV、IP 去重计数等允许近似的报表。
  5. 不适合：必须精确计数、需要枚举曾出现过的元素。
  6. 命令前缀 PF：纪念算法作者 Philippe Flajolet，与结构名 HyperLogLog 不同是历史习惯，别疑惑。

核心原理：直觉理解

1. 伯努利试验直觉

把每个元素哈希成比特串，观察末尾连续 0 的个数。连续 0 越长越罕见；记录见过的最大连续 0 数 k，就用 2^k 粗估基数——「见过 5 个连续 0」说明大约掷过 2^5 量级的硬币。

2. 分桶降方差

单一估计抖动太大，HLL 把哈希值前若干位作桶号，分成 2^14 = 16384 个桶，每桶各自记录最大连续 0 数，最后对全部桶取调和平均再修正——误差稳定在 0.81% 左右。

3. 内存去向

16384 桶 × 每桶 6 bit ≈ 12 KB，与数据量无关；这就是「固定内存估算海量基数」的全部秘密。

4. 两种内部表示

  • dense：12 KB 定长数组，每个桶 6 bit，始终占满 12 KB；
  • sparse：基数很小时用更省内存的稀疏列表表示，元素增多后自动转 dense（hll-sparse-max-bytes 默认 3000 字节控制转换阈值）。

对使用者透明，但解释了「新 HLL 实际占用远小于 12 KB」的现象。

5. 合并即并集

两桶对应位置取最大值就是 PFMERGE——所以「按天分 key、周报 PFMERGE」天然正确，且合并结果仍是近似误差，不会叠加放大。

6. 边界

拿不回成员（哈希不可逆）；PFCOUNT key1 key2 的多 key 形式需要临时合并，开销随 key 数上升（高版本有缓存优化），多 key 高频查询建议先 PFMERGE 落地再查。

命令 作用

PFCOUNT key [key ...] 单个或合并估算基数

典型应用场景

  1. 页面 / 活动 UV：PFADD uv:2026-05-03:page1 <userId 或 sessionId>，定时 PFCOUNT。
  2. 多维度合并：按天分 key，日报用 PFMERGE 聚合成周 UV。
  3. 搜索引擎独立查询词统计：每天搜索词基数，无需存词本身。
  4. 接口独立 IP 粗估：风控「该接口今天被多少不同 IP 打过」的低成本近似答案。
  5. A/B 实验触达人数：实验组/对照组各一个 HLL，合并即总体触达。
  6. 跨端去重触达：App / Web / 小程序三端各记一个 HLL，总触达 PFMERGE 三端，天然去掉「同人多端」重复。
  7. 爬虫/日志去重粗估：抓取管线按小时 PFADD crawl:{hour} <url指纹>，PFCOUNT 粗估「本小时新 URL 量级」，替代昂贵的全量布隆判重——只要趋势不要精确值时足够。

8. A/B 实验触达人数

进阶：误差为什么是 0.81%

HLL 的相对标准误差公式为 1.04 / √m，m 为桶数。Redis 固定 m = 2^14 = 16384，代入得 1.04 / 128 ≈ 0.81%——误差只由桶数决定，与数据量无关，这就是「10 个元素和 10 亿个元素误差率相同」的数学原因。桶数在实现里写死，用户不可调；要更小误差只能换算法（如 Datasketches 的 Theta），或接受它。

常见坑与注意事项

  1. 误差：报表若要求精确 UV，需 Set（内存大）或离线数仓；把 HLL 结果写进计费系统是典型误用。
  2. 元素语义：PFADD 把参数当字节串；业务上应用统一 ID（如用户 ID），勿混多种粒度（一会 userId 一会 sessionId，基数立刻失真）。
  3. 无法查询成员：不能问「谁访问过」，只能问「大约多少人」。
  4. PFADD 返回值：1 只表示「桶状态变了」，不能当「这是新用户」用——新元素落入已记录过的桶位时不返回 1，旧元素也可能偶然触发状态变化。
  5. key 数量膨胀：按「天 × 页面」分 key 时记得给明细 key 设 TTL，否则 12 KB × 天 × 页面 也会积少成多。
  6. 多 key PFCOUNT 的开销：PFCOUNT k1 k2 … kN 需临时把 N 个 HLL 合并再估，key 多时单次调用变慢；高频多维查询应先 PFMERGE 落物化 key 再单查。
  7. 稀疏 key 内存幻觉：元素少时 sparse 表示只有几百字节，别据此断言「HLL 很省所以随便建」——基数涨上来每个 key 都会爬到 12 KB，亿级 key 总量依然要规划。
  8. HLL 不是普通 String：虽然 TYPE 显示 string，但别对它 GET / APPEND——内容是二进制桶数据，读出无意义，写入会直接毁结构；运维脚本要按类型白名单跳过。

第六章：Redis ZSet 数据类型：概念、命令与案例

概念基础

ZSet（Sorted Set，有序集合）给每个成员挂一个分值（score），集合内部始终按 score 排序：

  1. TYPE key 为 zset。
  2. member 唯一；同一 member 再次 ZADD 会更新 score（不是报错、也不是新增——这是「改积分」的基础语义）。
  3. 排序方向：score 从小到大是「正序」；排行榜通常要 ZREVRANGE 降序取 Top N。
  4. 范围查询、排名 ZRANK/ZREVRANK 为高频 API——「第几名」「前 100 名」「积分区间成员」都是 O(logN) 级别的现成能力，这是 Set 给不了的。
  5. score 相同按 member 字典序排序——排行榜想打破并列，可把「先到先排前」编码进 member 或微调 score（如整数积分 + 小数时间戳倒数）。

核心原理：跳表与双结构

1. 两种编码

元素少且成员短时用 listpack（7.0 前 ziplist），阈值默认 zset-max-listpack-entries 128、zset-max-listpack-value 64；一般情况用 skiplist 编码（OBJECT ENCODING 可查）。

2. skiplist 编码 = 双结构

同一份数据同时挂在两个索引上：

  • 跳表（zskiplist）：按 score 排序的有序跳表，负责 ZRANGE / ZRANGEBYSCORE / ZRANK 等范围与排名操作，复杂度 O(logN)。每个节点带随机层数（Redis 中约 1/4 概率升层，最大 32 层），高层是「快车道」，查找时从顶层逐层下沉。
  • 字典（dict）：member → score 映射，负责 ZSCORE 这类按成员查分值的 O(1) 操作。


flowchart LR
  Z[ZSet key] --> S[skiplist 按 score 排序<br/>范围 / 排名 O logN]
  Z --> D[dict: member→score<br/>查分 O 1]

3. 为什么用跳表而不是平衡树

范围查询同样高效、实现远比红黑树简单（无旋转）、节点上的 span 跨度字段让「按排名定位」天然支持（这是 ZRANK O(logN) 的关键）——是工程权衡的典型案例。

ZSCORE O(1) 走 dict

5. score 精度与并发安全

score 是 double，能精确表示的整数范围约 2^53；时间戳做 score 时统一毫秒或秒，避免大数值浮点误差。ZADD 更新、ZINCRBY 加分都是单线程原子操作，排行榜「并发刷分」不丢更新。

  2. 延时任务：score=执行时间戳，定时 ZRANGEBYSCORE 拉到期任务再 ZREM。

第三章：Redis Hash 数据类型：概念、命令与案例

概念基础

Hash 是「key → 若干 field/value 对」的映射，类似一张微型数据行或一个对象文档：

  1. 一个 key 下挂多对 field / value，field 与 value 均为字符串（二进制安全）。
  2. TYPE key 显示 hash。
  3. 与 String 存 JSON 的区别：String 改一个字段要「读出 → 反序列化 → 改 → 序列化 → 写回」四步，Hash 只需 HSET 一个 field——这就是「局部更新」的价值。
  4. 适合「用户资料、购物车行、配置项分组」等属性较多且常单独更新的场景。
  5. 字段级过期：Redis 7.4 起（含 8.x）Hash 支持字段级 TTL（HEXPIRE / HPEXPIRE / HTTL），可让同一 Hash 内不同字段有不同生命周期；旧版本只能对整个 key 设 EXPIRE，这是选型时容易忽略的版本差异点。

核心原理：编码与底层结构

1. 两种编码（OBJECT ENCODING key 可观察）

  • listpack（Redis 7.0 前为 ziplist）：字段少且值短的紧凑编码，所有 field/value 连续存放，省内存但对中间元素的访问是 O(N)——靠「元素少」保证不慢。listpack 是一段连续字节数组，每个 entry 记录自身长度与编码类型，无指针开销，这正是它比 hashtable 省内存的原因。
  • hashtable：字典结构，field → value 的 O(1) 哈希访问。

2. 编码转换阈值

任一条件超出即从 listpack 转 hashtable（默认如下，以 CONFIG GET hash-max-listpack-* 为准）；转换是单向的，转回不再发生：

配置项 默认值 含义
hash-max-listpack-entries 128 字段数超过该值即转换
hash-max-listpack-value 64（字节） 任一 field 或 value 超过该长度即转换

3. 渐进式 rehash

hashtable 扩容时 Redis 同时持有两张哈希表，把数据分批从旧表搬到新表（每次命令顺带迁一小批 + 定时任务），避免一次搬家阻塞服务——这是单线程 Redis 能平滑扩容的关键设计。

4. 时间复杂度表

命令 复杂度 说明
HSET / HGET / HDEL（单字段） O(1) 多字段形式为 O(N)，N 为本次字段数
HINCRBY / HINCRBYFLOAT O(1) 原子字段加减
HEXISTS / HLEN / HSTRLEN O(1) 判存在 / 字段数 / 值长度
HMGET / HMSET O(N) N 为本次字段数
HGETALL / HKEYS / HVALS O(N) N 为总字段数，大 Hash 慎用

5. 内存占用对比：一个 Hash vs 拆成多个 String key

「100 个字段放一个 Hash」与「100 个 String key」的内存差距主要来自 key 头开销：每个 String key 都有 redisObject、SDS、dictEntry 等固定成本（约 50~90 字节/key），而 Hash 在 listpack 编码下 field/value 是纯数据连续存放。字段多而值短的对象，Hash 明显更省；反之字段少、值大时两者差距不大，按语义选。

第五章：Redis Set 数据类型：概念、命令与案例

概念基础

Set 是无序、不重复的字符串成员集合，直接对应数学里的「集合」：

  1. TYPE key 为 set。
  2. 不保证顺序（遍历顺序实现依赖，勿当有序结构用）。
  3. 成员即字符串；同一成员重复 SADD 只保留一份，判重是 O(1)——这是它与 List 最本质的差异。
  4. 集合间可做 SINTER / SUNION / SDIFF（交 / 并 / 差），把「共同关注」「可能认识的人」这类关系计算下推到 Redis 里完成。
  5. 没有分值、没有序号——需要「第几名」「Top N」请直接上 ZSet，不要用 Set 硬撑。

核心原理：编码与复杂度

1. 两种编码（OBJECT ENCODING key 观察）

  • intset：成员全部是整数且个数不超过 set-max-intset-entries（默认 512）时使用，有序整数数组 + 二分查找，最省内存。intset 内部按值升序排列，查找 O(logN) 但 N≤512 时依旧飞快；一旦有任一成员不是整数或个数超阈值，整体转 hashtable。
  • hashtable：一般情况使用，member 作字典的 key、value 恒为 NULL——「唯一性」由哈希表天然保证，SADD / SISMEMBER / SREM 均 O(1)。

2. 时间复杂度表

命令 复杂度 说明
SADD / SREM / SISMEMBER O(1) 多成员形式 O(N)，N 为本次成员数
SCARD O(1) 计数有缓存
SMEMBERS O(N) 一次返回全量，大集合慎用
SSCAN 单次 O(1) 级别 大集合迭代唯一正确姿势
SPOP / SRANDMEMBER O(1)（带 count 为 O(count)） 见「随机语义」
SINTER O(N·M) 最坏 N、M 为各集合大小
SUNION / SDIFF O(N) N 为所有集合成员总数

3. 集合运算的代价

SINTER / SUNION / SDIFF 是同步计算——两个大集合求交可能耗时几十毫秒甚至秒级，期间 Redis 无法处理其他请求。生产上建议：

  • 用 SINTERSTORE / SUNIONSTORE / SDIFFSTORE 把结果写入新 key，再异步消费；
  • 大运算放到从库或低峰期执行；
  • 能通过业务预计算（如每日离线算好共同关注）就不要实时算。

4. 随机语义

SPOP 是弹出（取出并从集合删除，不放回）；SRANDMEMBER 只读不删——count 为正给不重复成员、为负允许重复。抽奖「不放回」用 SPOP、「仅看看」或「可重复抽取」用 SRANDMEMBER。

SCARD 成员个数
SRANDMEMBER / SPOP 随机读 / 随机弹出

SMOVE 把成员从一个 Set 搬到另一个（原子）

典型应用场景

  2. 抽奖池 / 去重 ID 池：SPOP 不放回抽样（需理解并发下多个客户端抢 SPOP 的语义——同一成员不会被弹出两次，天然防重）。
  3. 共同关注 / 共同好友：SINTER user:1:following user:2:following。
  4. 可能认识的人：SDIFF user:2:followers user:1:following——「关注了我但我还没回关的人」。
  5. 黑白名单 / 去重过滤：SISMEMBER blacklist:ip 1.2.3.4 O(1) 判定，比查库快几个数量级。
  6. 已读回执去重：消息下发前 SADD msg:9:read u1 返回 0 说明已记录过，实现幂等。

发表于 2026-05-03 更新于 2026-10-29 分类于 Redis 缓存 本文字数： 5.7k 阅读时长 ≈ 5 分钟

第四章：Redis List 数据类型：概念、命令与案例

概念基础

List 是一个 key 下的双向序列，从左右两端都能进出：

  1. 有序、可重复；同一 value 可出现多次。
  2. TYPE key 为 list。
  3. 两端操作是它的设计重心（入队/出队都很快），中间插入/删除代价高于两端（需遍历指针）；设计时尽量从两头消费。
  4. 下标支持负数（-1 表最后一个元素），LRANGE key 0 -1 即取全表。
  5. 与 Java 里的 LinkedList 心智模型接近：当队列、栈、时间线用，不要当随机访问数组用。
  6. 同一根 List 通过「左进右出」或「右进左出」可分别扮演队列（FIFO）与栈（LIFO）——两端同侧进出即栈，异侧进出即队列。

核心原理：底层结构与阻塞机制

1. quicklist：链表与压缩段的折中

List 的底层是 quicklist——一条双向链表，但每个链表节点内部是一段 listpack（7.0 前为 ziplist）压缩段。这样兼顾两头：链表保证两端 O(1)，listpack 保证小段数据省内存。段大小由 list-max-listpack-size 控制：

配置取值 含义
正数（如 128） 每段最多 128 个元素
-2（默认） 每段不超过 8 KB
-1 每段不超过 4 KB（更省内存，段更多）

2. 时间复杂度表

命令 复杂度 说明
LPUSH / RPUSH / LPOP / RPOP O(1) 两端进出是设计主场
LLEN O(1) 长度有缓存
LRANGE start stop O(S+N) S 为偏移，N 为返回元素数
LINDEX / LSET / LINSERT O(N) 需定位，「按下标读写」在大列表上是危险操作
LREM O(N) 按值删除
BLPOP / BRPOP / BLMOVE O(1) + 阻塞等待 见下

3. 阻塞命令：把轮询变成推送

BLPOP / BRPOP 在列表为空时挂起客户端连接，把客户端按 key 排进等待队列；一旦别的客户端推入数据，立刻唤醒第一个等待者（先到先服务）。这把「轮询」变成了「推送」，是简单队列的关键机制。timeout 为 0 表示无限等待；生产建议设非零超时（如 5s）以便消费者定期回收连接、响应退出信号。

4. 安全队列模式：LMOVE

LMOVE src dst LEFT RIGHT（旧 RPOPLPUSH / BRPOPLPUSH，已废弃） 弹出的同时塞回备份队列，消费者处理完再从备份队列删除——用「两队列」模拟 ack，防止消费者崩溃丢任务。配合 BLMOVE 可获得「阻塞 + 安全迁移」的完整语义。

常用命令（必会子集）

命令 作用
LPUSH / RPUSH 左/右入队
LPOP / RPOP 左/右出队（7.x 支持 count 参数批量弹出）
LRANGE key start stop 闭区间下标范围（-1 表末尾）
LLEN 长度
LTRIM key start stop 裁剪只保留区间，常用于「固定窗口」
LINDEX / LSET 按下标读 / 写
BLPOP / BRPOP 阻塞出队（简单队列常用）
LMOVE / BLMOVE 安全迁移元素（安全队列）
LMPOP / BLMPOP（7.0+） 一次弹多个元素、可跨多 key，批量消费减少往返

典型应用场景

  1. FIFO 队列：RPUSH + LPOP（或反向一对）。
  2. 最新消息流：LPUSH + LTRIM key 0 99 保留最近 100 条。
  3. 阻塞消费：BLPOP 多个 key 时按顺序等待，可做简单任务队列（复杂语义建议 Stream 或专业消息中间件）。
  4. 栈式回溯：同侧进出（LPUSH + LPOP）实现「最近操作撤销栈」。
  5. 分页时间线：个人动态 feed 用 List 存最近 N 条 ID，读时 LRANGE 分页后回库查详情。
  6. 任务缓冲削峰：突发流量先 RPUSH 进 List，下游消费者按能力 BLPOP 匀速拉取，把尖峰摊平——写库、发短信类「慢下游」场景的经典用法。
  7. 会话内操作历史：编辑器/表单草稿把每步操作 LPUSH 进 hist:{doc}:{user}，LTRIM 保留最近 50 步，崩溃恢复后按序回放。
  8. 秒杀下单暂存：请求先 LPUSH seckill:{sku} 立即返回「排队中」，后端按库存量 RPOP 出队逐个落单——用 List 长度做天然的流量闸门。

常见坑与注意事项

  1. 消费者崩溃：LPOP 后数据即丢，需业务确认机制或改用 LMOVE + 处理完再删 模式；严肃场景评估 Stream、RabbitMQ 等。
  2. 长列表：LRANGE 0 -1 大列表慎用（一次扛回全部字节）；分页用 LRANGE 分段。
  3. 大 key 风险：无人消费的队列会无限增长，务必配合 LLEN 监控告警或 LTRIM 兜底。
  4. 按下标操作：LINDEX / LSET 为 O(N)，把它当数组随机访问是典型误用。
  5. 与 Set/ZSet 区别：List 有序可重复；Set 无序唯一；ZSet 有序唯一带分值。
  6. BLPOP 超时循环：消费者拿 BLPOP key 5 轮询时，超时返回 nil 属正常路径，勿当异常打日志刷屏；也勿用 timeout 0 无限挂死后忘记实现优雅退出。
  7. 多 key 监听顺序即优先级：BLPOP k1 k2 k3 5 从左到右检查，k1 有数据就不会等 k2——利用这点可做「高优队列在前」的简易优先级，但别堆太多 key，逐个检查有开销。
  8. LTRIM 与并发写入：「LLEN 看长度再 LTRIM」两步之间有竞态，期间新元素可能被误裁；固定窗口一律用「先 LPUSH 后 LTRIM」的原子习惯（同连接顺序执行，Lua 更稳）。
  9. 元素体积：List 单元素不宜塞大 JSON——quicklist 段按 8KB 切分，超大元素会破坏段内压缩收益；feed/队列里存 ID，正文回库或 MGET。

第二章：Redis String 数据类型：概念、命令与案例

概念基础

String 是 Redis 最基本的值类型——一个 key 对应一个字符串值：

  1. Redis 是 KV 模型：键（key） 永远是字符串；值（value） 可以是 String / Hash / List 等类型之一。
  2. 本文说的 String 指 value 的类型为 string（TYPE key 显示 string）。
  3. 二进制安全：值可以是任意字节序列——文本、JSON、序列化对象，甚至图片字节，不需要担心内容里出现特殊字符。
  4. 容量上限：单个 String 最大 512 MB，但业务上应把「大 value」视为反模式（见注意事项）。
  5. 编码：底层可能为 int、embstr、raw 等（OBJECT ENCODING key 可查看），对使用者多数时候透明，选型时更关心语义与命令（原理见下一节）。

核心原理：编码与底层结构

  1. SDS（简单动态字符串）：Redis 的字符串不是 C 语言以 \0 结尾的字符数组，而是自研的 SDS 结构——头部记录已用长度与剩余空间，因此 STRLEN 是 O(1)；追加时可预分配空间减少 realloc；内容可含 \0，这是「二进制安全」的基础。
  2. 三种编码与转换：
    • int：值是能放进 64 位有符号整数的数字（如 INCR 计数器），直接存整数，最省内存。
    • embstr：短字符串（≤ 44 字节），redisObject 与 SDS 一次性分配在一块连续内存，读多写少时最省且缓存友好；embstr 是只读的，一旦修改就转成 raw。
    • raw：长字符串（> 44 字节）或被修改过的短字符串，SDS 独立分配，支持高效追加。
  3. 观察方法：
  1. 内存账：同样是 100 万个小 key，编码差异能拉开明显内存差距——int 编码的计数器 key 几乎只有 redisObject 与 dictEntry 开销；raw 长字符串 还要叠一份独立 SDS。海量 key 场景先用 MEMORY USAGE key 抽查，再决定要不要「多 key 合并成 Hash」（见第四章）。
  2. 原子性：命令单线程执行，INCR、SET key val NX 等都是原子操作——这就是「计数器」和「占位锁」不惧并发的根本原因，不需要应用层再包一层锁。

INCR 在值可解析为整数时原子自增；不存在时按 0 开始。

4. 其它实用命令

典型应用场景

  1. 缓存整页或对象：值存 JSON 字符串，配合 EX 做短期缓存；更新数据库后删键或覆盖避免脏读。
  2. 会话 / 登录态：SET … EX … 存 token → 用户信息；过期自动消失；续期用 GETEX key EX 3600 一步完成「读 + 续期」。

PostgreSQL：并发与 MVCC 入门

概念基础

  1. 并发问题：多个事务同时读写同一批行时，会出现脏读、不可重复读、幻读与丢失更新；数据库必须给出确定性的答案——这就是隔离级别要解决的问题。
  2. MVCC（多版本并发控制）：每行保留多个版本，行头部的 xmin / xmax 记录创建与删除它的事务；读按快照判断可见性，做到读写互不阻塞。
  3. 隔离级别决定快照粒度：默认 READ COMMITTED 每条语句一个快照；REPEATABLE READ 整个事务一个快照；SERIALIZABLE 进一步检测读写冲突，冲突时需应用重试。
  4. MVCC 不是免费的：旧版本（死元组）要靠 VACUUM 回收；「先读后改」的临界区仍需显式行锁（FOR UPDATE），并发抢任务用 SKIP LOCKED。

一、快照与默认隔离级别

  • 默认 READ COMMITTED：单条 SQL 内看到语句开始时已提交的数据版本。
  • REPEATABLE READ：事务内首条 SQL 建立快照，后续读一致。
  • SERIALIZABLE：可检测读写依赖，失败时返回 40001 serialization_failure，应用应重试。

SAVEPOINT：事务内的部分回滚

由于 MVCC，PostgreSQL 读永远不会被写阻塞；默认隔离级别为 READ COMMITTED。

二、显式行锁：FOR UPDATE / FOR SHARE

  • FOR UPDATE：排他行锁，用于「先读后改」的临界区。
  • FOR SHARE：共享行锁，允许他人并发读，阻塞写。

三、SKIP LOCKED 与 NOWAIT（队列与抢锁）

SKIP LOCKED：跳过已被其他事务锁定的行，取下一批可用行——常用于任务队列、公平抢单。

NOWAIT：若不能立即加锁则立刻报错，适合避免长时间等待（由应用捕获错误后重试或放弃）。

四、死锁（deadlock detected）

PostgreSQL 会自动检测事务间循环等待，回滚其中一个事务（报错 40P01 deadlock_detected）。
规避思路与 MySQL 类似：固定加锁顺序、缩短事务、避免无关长耗时在事务内执行。

五、表级锁冲突矩阵（实战版）

PostgreSQL 有 8 种表级锁模式，完整矩阵只需记住实战常用的六行：

持有操作（锁模式） 会阻塞谁
SELECT（ACCESS SHARE） 仅阻塞 ACCESS EXCLUSIVE（ALTER TABLE / DROP / TRUNCATE / VACUUM FULL）
SELECT … FOR UPDATE（ROW SHARE） 阻塞 SHARE（普通 CREATE INDEX）及以上
INSERT/UPDATE/DELETE（ROW EXCLUSIVE） 阻塞 SHARE、EXCLUSIVE、ACCESS EXCLUSIVE；不阻塞 SELECT，也不阻塞别人的 DML
VACUUM / ANALYZE / CREATE INDEX CONCURRENTLY（SHARE UPDATE EXCLUSIVE） 互相阻塞（同表不能并发建两个索引）、阻塞 DDL
CREATE INDEX（SHARE，不带 CONCURRENTLY） 阻塞写入 DML——大表建索引务必加 CONCURRENTLY
ALTER TABLE 等 DDL（ACCESS EXCLUSIVE） 阻塞一切，包括只读 SELECT

速记：读写互不阻塞（MVCC 红利）；普通建索引阻塞写；DDL 阻塞一切，上线要走低峰 + lock_timeout 保护。

八、事务 ID 回卷（xid wraparound）与 freeze

1. 问题是什么

xmin / xmax 是 32 位无符号整数，全局约 40 亿个事务号环形复用：一个事务号「跑完一圈」约 20 亿事务后会被当成新事务——如果不处理，旧数据会突然「变成未来的数据」而不可见，等效于数据丢失。

2. 解法：freeze（冻结）

VACUUM 扫描时把足够老的行版本 xmin 改写成特殊的 FrozenTransactionId（=2）——冻结行对所有未来事务永久可见，不再参与年龄计算。相关参数：

参数 默认 含义
autovacuum_freeze_max_age 2 亿 表的 relfrozenxid 年龄超过它就强制 autovacuum（拦不住也要拦）
vacuum_freeze_min_age 5000 万 行年龄超过它才允许被 freeze
vacuum_freeze_table_age 1.5 亿 超过则整表扫描（而非只扫脏页）

3. 监控与应急

应急：年龄逼近 autovacuum_freeze_max_age 时对大表手动 VACUUM (FREEZE, VERBOSE) tbl;；若数据库已因回卷保护拒绝写入，按官方文档以单用户模式启动做 VACUUM FREEZE。防大于治：别让 autovacuum 长期追不上，监控 datfrozenxid 年龄是巡检标配。

PostgreSQL：索引与性能优化

概念基础

  1. 索引 = 用空间换时间的检索结构：默认 B-Tree 以平衡树组织键值，把等值 / 范围查询从全表扫描降为树查找；代价是占存储、拖慢写入。
  2. 慢的常见根源：大表 Seq Scan、统计信息过期导致选错计划、死元组堆积（表膨胀）、函数包裹列让索引失效。
  3. 优化是闭环不是玄学：慢日志 / pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) 看真实计划 → 改索引或改写法 → VACUUM ANALYZE 更新统计再验证。
  4. 性能之外还有「稳」：事务隔离级别选型、VACUUM/autovacuum 运维、备份恢复（pg_dump / PITR） 演练，都是可靠性的一部分。

先建立对默认索引的直觉：

一、索引在干什么：B-Tree 直觉（默认）

PostgreSQL 默认 CREATE INDEX 多为 B-Tree（USING btree，可省略）。
直觉与 MySQL InnoDB 二级索引类似：以平衡树组织键，等值 / 范围查询减少随机读；主键 / 唯一约束底层也会建索引。

1. 五种常用索引类型对比

类型 内部结构 适用场景 典型写法
B-Tree（默认） 平衡树 等值、范围、排序（< <= = >= >、ORDER BY），绝大多数业务索引 CREATE INDEX ON t (col);
GIN 倒排索引 多值内含检索：jsonb @>、数组、全文检索 CREATE INDEX ON t USING gin (attrs);
GiST 广义搜索树 几何/地理（PostGIS）、范围类型、相似度（pg_trgm） CREATE INDEX ON t USING gist (geom);
BRIN 块级摘要 超大表且物理顺序与列值强相关（如按时间追加的日志） CREATE INDEX ON t USING brin (created_at);
Hash 哈希桶 仅 = 等值；PG 10+ 起才有 WAL 日志可安全使用，多数场景被 B-Tree 覆盖 CREATE INDEX ON t USING hash (col);

选型速记：拿不准就用 B-Tree；jsonb / 数组 / 全文 用 GIN；地理 / 范围类型 用 GiST；只追加的巨型表试 BRIN——体积可能只有 B-Tree 的千分之一，但只擅长「顺序相关」列的范围过滤。

2. 其他类型一句话

SP-GiST（四叉树/基数树，适合非平衡结构如电话号码前缀）、Bloom（扩展，多列任意组合的「可能存在」过滤）属进阶选项，选型需读官方文档与压测。

二、联合索引与最左前缀

联合索引 CREATE INDEX idx_abc ON t (a, b, c); 的排序语义仍是先 a 再 b 再 c。
WHERE a = ? AND b = ? 易命中；仅 WHERE b = ? 往往用不上该索引（与 MySQL 同款直觉）。
函数包裹列（如 WHERE lower(email) = ?）常导致无法走 btree，需表达式索引（CREATE INDEX ON t ((lower(email)))）或改写法。

三、仅索引扫描（Index Only Scan）

若查询列均可由某索引覆盖，且可见性映射（VM）允许优化器认为堆页全可见，EXPLAIN 可能出现 Index Only Scan。
与 MySQL 的 Using index 类似但不等价；仍以 EXPLAIN (ANALYZE, BUFFERS) 实测为准。

四、部分索引与覆盖索引（INCLUDE）

1. 部分索引（Partial Index）：只给需要的行建索引

带 WHERE 的索引只覆盖满足条件的行——更小、更快、更便宜。经典场景：软删除表只索引未删除行、任务表只索引待处理状态：

生效前提：查询的 WHERE 必须蕴含索引条件——WHERE status = 'pending' AND created_at > now() - interval '1 day' 能用；查 status = 'done' 则用不上。

2. 覆盖索引（INCLUDE）：把非键列挂在叶子页

  • 键列决定搜索顺序、可被 WHERE 利用；INCLUDE 列只存储、不参与比较——适合「按 A 列过滤、返回还要 B、C 列」的场景，把回表（Heap Fetches）彻底消掉。
  • 与联合索引 (dept_id, name, salary) 的区别：后者让 name、salary 也进入排序键，树更「重」且多数时候无谓；INCLUDE 语义更诚实、索引更轻。
  • 唯一索引同样支持：CREATE UNIQUE INDEX ON t (email) INCLUDE (id);——唯一约束只作用于键列。

五、怎么看执行计划：EXPLAIN / EXPLAIN ANALYZE

入门优先看：

字段 / 标记 含义（入门）
Seq Scan 顺序扫表，大表 + 高 rows 要警惕
Index Scan / Index Only Scan 走索引访问
Nested Loop / Hash Join / Merge Join 连接策略
ANALYZE 的 actual time、rows 真实耗时与行数（与统计信息、缓存有关）
BUFFERS 读了多少共享缓冲区（判断是否 I/O 重）

一次逐字段解读

可能的输出（数字为演示）：

字段 读法
cost=0.00..41.97 估算代价：启动成本..总成本，抽象单位，只用于比较计划优劣
rows=2（逗号前） 估算行数；与 actual rows 差一个数量级以上 → 统计信息过期，先 ANALYZE
actual time 实测：首行返回..全部返回耗时（毫秒，每次循环的值）
loops=1 节点执行次数；嵌套循环内侧 loops 会放大，actual time × loops 才是总耗时
Rows Removed by Filter 被过滤掉的行数——「扫 5 留 2」尚可，「扫百万留十行」就该建索引
Buffers: shared hit=1 命中共享缓冲 1 页；read 多 = 磁盘 I/O 重，hit 多 = 内存命中
Execution Time 服务端执行总耗时（不含网络与客户端渲染）

解读顺序：从下往上、从内往外看（缩进越深越早执行）；先抓 actual 耗时最大的节点，再核对它的 rows 估算偏差与 Buffers。

统计信息维护：ANALYZE tbl;（VACUUM ANALYZE 亦可），大变更后应跑。

六、事务与隔离级别（用法向）

1. 基本写法

默认 READ COMMITTED：每条语句看到语句开始时已提交的快照（简化理解）。
REPEATABLE READ：事务内第一条语句建立快照，读一致性更强。
SERIALIZABLE：最强，可能出现 serialization_failure，应用需重试。

与 MySQL InnoDB 默认 RR 不同：PostgreSQL 默认 RC；跨库迁移时注意语义差异。行级锁、FOR UPDATE、死锁见 PostgreSQL：并发与 MVCC 入门。

七、慢语句与观测「三板斧」（点到为止）

1. 日志：log_min_duration_statement

在 postgresql.conf 或 ALTER SYSTEM（需 reload）中设置，例如记录超过 200ms 的语句（数值按环境调）。

2. pg_stat_statements（扩展）

需 shared_preload_libraries 预加载（运维配置），此处不展开。

3. auto_explain（扩展）

自动对超时语句打计划，适合测试环境；生产按规范启用。

落地顺序：先慢日志或 pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) → 改索引或改写法 → VACUUM ANALYZE。

八、VACUUM、膨胀与索引维护

PostgreSQL 的 MVCC 会使更新/删除留下死元组；VACUUM（通常由 autovacuum 自动跑）回收空间、更新统计信息。长期不 vacuum 会导致表膨胀、性能变差。
日常开发：大批量导入/更新后，测试库可手动 VACUUM ANALYZE；生产依赖 autovacuum 参数与监控。

1. 索引也会膨胀

反复 UPDATE 的表，其 B-Tree 索引同样积累死元组与空页——索引文件越来越大、扫描变慢，而普通 VACUUM 只把空间标记为可复用，不会把索引文件缩小。观测死元组占比：

2. 三种重建手段

手段 锁表 在线 说明
REINDEX INDEX CONCURRENTLY 否 是 PG 12+，逐个索引在线重建，首选
REINDEX TABLE 排他锁 否 重建整表全部索引，仅维护窗口用
pg_repack（扩展） 短暂 是 表 + 索引一起在线重整，顺带消表膨胀，需单独安装

写入重的表，每多一个索引就多一份 INSERT / UPDATE 的维护成本——索引不是越多越好。
