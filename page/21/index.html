1. 概念说明

**消息队列（MQ）**是生产者和消费者之间的异步通道，解决三大问题：

  1. 异步解耦：下单后发消息，邮件/积分/通知各自消费，互不影响。
  2. 削峰填谷：秒杀流量先入队，消费者按自身能力消费。
  3. 最终一致：跨服务状态同步。

Kafka 核心架构：

概念 说明
Broker 一台 Kafka 服务器，集群由多个 Broker 组成
Topic 消息分类（如 order-events）
Partition Topic 的分片，并行与扩展的单元，内部有序
Offset 消息在分区内的序号
Producer 生产者，写入消息
Consumer / Consumer Group 消费者；同组内分区消费，组间互不影响
Replica 副本（Leader/Follower），保证可用性

为什么选 Kafka：相比 RabbitMQ，Kafka 吞吐更高（百万级/s）、天然分布式、消息可重放，适合大数据与事件驱动；RabbitMQ 更适合复杂路由与低延迟业务。Kafka 4.x 已用 KRaft 替代 ZooKeeper，部署更简单。

10. 常见误用与陷阱

坑 现象/后果 解法
消息重复消费未做幂等 同一订单被处理多次（重复扣库存/重复发券） 用消息唯一 ID + Redis SETNX 或数据库唯一键去重
消息堆积未处理 lag 持续增长，业务延迟越来越大 监控 lag 告警；扩容消费者（受分区数限制）；临时降级非核心消费
顺序消息误解 认为整个 Topic 有序，实际只有单分区内有序 需要全局有序只能单分区（吞吐极低）；按业务 key（如 orderId）分区保证局部有序
重试风暴 消费者异常后不断重试，打爆下游 重试有上限（max-attempts），超限进死信；用指数退避延迟重试
死信队列未监控 坏消息静默进入 DLQ，无人知晓，业务漏单 DLQ 必须有消费者或监控，数量 > 0 即告警
消费者位移提交时机错误 自动提交下，处理成功前崩溃导致消息丢失；或处理完未提交导致重复 关闭自动提交，业务处理成功后手动 ack/acknowledge

微服务 · 架构

从 0 到架构落地。微服务 vs 单体 · 拆分方法论 · 微服务全景（注册/配置/网关/熔断）· 技术选型 · 落地路线与避坑。配置带详细注释。

类别 选型 用途

1. 概念说明

微服务（Microservices）是把一个大型应用拆分为一组小型独立服务，每个服务围绕一个业务能力（如订单、库存、用户），独立开发、独立部署、独立扩展，服务间通过轻量协议（HTTP/RPC/消息）通信。

单体 vs 微服务：

维度 单体架构 微服务
部署 一个包 N 个服务独立部署
扩展 整体扩展 按服务扩展
故障影响 全挂 局部故障
开发协作 全队改一个仓库 按服务分团队
运维成本 低 高（注册中心/网关/链路追踪）
适用 中小项目、起步阶段 大团队、高复杂度业务

铁律：微服务是”高复杂度”的解药，不是”高性能”的解药。团队小于 20 人、业务初期，单体 + 模块化是更优选择。分布式拆分要付出分布式代价（网络、事务、调试）。

2. 什么情况该上微服务（决策清单）

以下信号出现 ≥3 个才考虑：

  • 团队 20+ 人，协作冲突频繁
  • 模块间解耦需求强烈（不同发布节奏）
  • 部分模块扩展性要求差异大
  • 已有清晰的业务边界
  • 具备运维能力（容器化、监控）

服务粒度适中 业务能力为界，不按”层”拆（不拆 controller-service-dao 服务）

10. 典型案例：电商订单服务从单体拆分落地

10.1 问题背景

某电商平台单体应用 mall-all 运行 3 年：订单、库存、商品、营销全部在一个工程、一个 MySQL 库里。痛点：

  • 大促只想扩容下单链路，却必须整体扩容，资源浪费；
  • 营销活动改一个优惠券规则，要和订单模块一起发版，互相阻塞；
  • 一次下单在单体内只是方法调用，链路边界无人说得清。

决策：先按限界上下文识别边界，再拆服务、定契约、选通信方式。

10.2 边界识别：从限界上下文到服务目录

用 DDD 的方法：找出业务聚合（订单、商品、库存……），一个聚合一个数据所有者，聚合之间只通过 API/事件协作。

服务 拥有的数据 核心接口 与下单链路的协作
order-service orders / order_items / order_events 下单、查单、状态流转 链路发起方
product-service spu / sku / price 商品查询、价格查询 同步（实时价格、上下架）
inventory-service sku_stock / stock_log 扣减、回补、查询 异步事件（最终一致）

10. 典型案例：自研低代码表单引擎（schema 驱动）

问题背景：内部 30+ 个管理后台页面 80% 都是”表单 + 表格”，每次改个字段都要走一遍完整发版流程，前端团队疲于奔命。

方案：做一个 schema 驱动的表单引擎——字段配置存 JSON，运行时按组件注册表渲染；联动/校验规则也进 schema；预留自定义组件插槽兜底长尾需求。加一个字段 = 改一份 JSON，不用发版。

踩坑点：

  • schema 没有版本号：平台升级后旧页面渲染错乱、数据落错字段——version + 迁移函数是第一条军规。
  • 联动规则写在页面代码里，三个月后 schema 与代码”漂移”成两套真相——联动/校验必须全部进 schema。
  • 没留自定义组件插槽：遇到富文本/级联/子表格就推倒重构——预留 custom 类型 + 注册表扩展点。
  • 下拉选项硬编码 1000 条进 schema：渲染卡死——大选项集改接口拉取 + 远程搜索。

踩坑点：

  1. liveness 探针误配导致重启风暴：若 liveness 探测的接口依赖数据库，数据库短暂抖动会触发 Pod 重启，重启又加重数据库压力，形成雪崩。liveness 应只探测应用自身存活（如一个不依赖外部的轻量接口）。

1. 概念说明

容器是把应用及其依赖（代码、运行时、库、配置）打包成标准单元，实现”一次构建、到处运行”。

镜像 vs 容器：

概念 类比 说明
镜像（Image） 类/模板 只读的打包产物，docker images
容器（Container） 对象/实例 镜像的运行实例，docker ps
Dockerfile 图纸 构建镜像的配方文件
仓库（Registry） 应用商店 存放分发镜像

为什么比虚拟机轻：容器共享宿主机内核，没有完整操作系统，秒级启动、资源占用小。镜像采用分层存储（每层只读，可复用），拉取与构建都很快。

10. 典型案例：Spring Boot 镜像从 800MB 瘦身到 120MB

问题背景：一个 Spring Boot 应用用 FROM eclipse-temurin:21 直接构建，镜像体积 823MB，CI 构建慢、拉取慢、攻击面大。需要通过多阶段构建 + JRE 精简 + 层缓存优化，把体积压到 120MB 左右。

方案：

优化项 效果
多阶段构建 排除 Maven/JDK，省约 400MB
JRE 替代 JDK 省约 200MB
依赖层缓存 CI 重复构建加速 80%
.dockerignore 排除 target/.git，省约 50MB

踩坑点：

  1. COPY 顺序决定缓存命：必须 COPY pom.xml 在 COPY src 之前。若先拷源码，改一行代码就触发依赖重新下载。
  2. 多阶段不是万能：阶段一的构建产物必须显式 COPY --from=build，否则运行镜像里没有应用。
  3. JRE 版本要匹配：用 JDK 21 编译的 class 必须用 JRE 21 运行，低版本会报 UnsupportedClassVersionError。

11. 实战：1Panel 可视化管理 Docker

纯 CLI 适合自动化脚本，但日常运维多容器、多套应用时，可视化面板能显著降低心智负担。1Panel 是开源（GPLv3）的 Linux 服务器运维管理面板，Docker 容器编排、应用商店、防火墙、定时备份一站搞定，国内中小团队自建服务的热门选择（与宝塔相比更偏容器化、无强制注册）。

11.4 生产建议

  1. 改默认端口 + 强密码 + IP 白名单：面板是服务器最高权限入口，别把默认端口直接暴露公网。
  2. 面板做「查看/应急」，compose/CI 做「变更」：生产变更走 GitOps 或脚本，面板用于排障看日志，避免手工操作无审计。
  3. 备份面板自身配置：/opt/1panel/ 下的配置纳入备份，重装时可整体恢复。

12. 常见误用与陷阱

坑 现象/后果 解法
镜像体积巨大未多阶段构建 镜像 800MB+，拉取慢、磁盘占用大 用多阶段构建，运行阶段只拷产物和运行时
容器内写日志撑爆磁盘 容器不断写 stdout/文件，宿主机磁盘满 日志走 stdout + 日志驱动轮转（max-size）；文件日志挂卷
privileged 滥用 容器获宿主机 root 权限，安全风险极高 避免 –privileged；按需加 –cap-add 指定能力
latest 标签不可追溯 线上运行哪个版本说不清，回滚困难 固定版本号/构建号 tag，如 app:v1.2.3-20261008
数据未挂载卷丢失 容器删除后数据消失（数据库/上传文件） 用 volume 或 bind mount 持久化数据目录
