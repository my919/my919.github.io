1. 概念说明

Python 是解释型、动态类型、多范式语言：语法简洁、生态庞大（AI、数据分析、Web、自动化都是主场）。

动态类型 vs 静态类型：变量不声明类型，运行时推断；配合类型注解（Python 3.5+）可获静态检查能力，生产项目强烈建议使用。

执行模型：GIL（全局解释器锁）限制同一进程多线程并行计算；CPU 密集用多进程/原生库，IO 密集用 asyncio 协程。

1. 概念说明

Nginx 是高性能 HTTP 服务器与反向代理，事件驱动 + 异步非阻塞模型，单机可支撑数万并发连接。三大用途：

用途 说明
静态文件服务 HTML/CSS/JS/图片，QPS 极高
反向代理 接收外部请求，转发到内部服务（隐藏后端、统一入口）
负载均衡 多后端实例按策略分发

正向代理 vs 反向代理：

  • 正向代理：代理客户端（翻墙、缓存），客户端知道目标。
  • 反向代理：代理服务器（用户访问 Nginx，Nginx 转发后端），客户端无感知。

进程模型：一个 master（管理）+ N 个 worker（处理请求）。nginx -s reload 平滑重载配置，不中断服务。

12. 典型案例：前后端分离 + 反向代理 + 负载均衡

问题背景：某电商站点前端是 Vue SPA（静态资源），后端是 Spring Boot API，还有 WebSocket 实时通知。需要用 Nginx 做统一入口：静态资源直接服务、API 反向代理到后端集群、WebSocket 升级、HTTPS 全站加密。

方案骨架：一个 443 server 内按路径分流——/ 静态文件（try_files $uri $uri/ /index.html 做 SPA 路由回退）、/api/ 转发 upstream backend（least_conn + weight + max_fails 被动摘除 + backup 兜底）、/ws/ 转发 WebSocket（必配 Upgrade $http_upgrade + Connection "upgrade"，proxy_read_timeout 3600s 保长连接）；80 端口 return 301 跳转 HTTPS。

三大踩坑点：① proxy_pass 末尾有无斜杠语义完全不同（无斜杠保留完整 URI，有斜杠替换前缀）；② WebSocket 不配 Upgrade 头无法升级；③ SPA 不配 try_files 刷新页面 404。

完整可落地的配置全文与 upstream 参数详解：深入了解：Nginx · 反向代理、负载均衡与高可用

13. 常见误用与陷阱

坑 现象/后果 解法
proxy_pass 末尾斜杠语义不清 路径被错误替换，API 404 无斜杠保留完整 URI，有斜杠替换前缀；按需选择
if 判断陷阱 if 指令在 location 中行为不可预期 尽量用 try_files/return；避免 if 内复杂逻辑
worker_connections 误解 认为是全局连接数，实际是每 worker 全局连接数 = worker_processes × worker_connections
缓冲区大小不合理 大请求/响应被缓冲到磁盘，性能下降 调大 proxy_buffer_size/proxy_buffers；大文件用 sendfile
超时未分级 所有接口用同一超时，慢接口拖累快接口 按接口设 proxy_connect/read/send_timeout
未透传真实 IP 后端收到的全是 Nginx 的 IP 配 X-Real-IP 和 X-Forwarded-For

计算机网络是分层协作的系统，每层只关心自己的职责，向上层提供接口：

1. 概念说明

Netty 是基于 NIO 的高性能异步事件驱动网络框架，是 Java 网络编程的事实标准：Dubbo、RocketMQ、Elasticsearch、gRPC-Java 都基于它。

为什么不用原生 NIO：原生 NIO 的 Selector 编程复杂（连接管理、拆包、线程模型都要手写），Netty 封装好线程模型、编解码、重连、心跳，开发者只关注业务。

核心线程模型（Reactor 模式）：BossGroup（少量线程）只 Accept 连接并注册到 WorkerGroup，WorkerGroup（N 线程）处理读写事件；每个 Channel 绑定固定 EventLoop 线程，天然无并发竞争。select/poll/epoll 差异、Reactor 三种形态与 EventLoop 源码级主循环：深入了解：第一章：IO 多路复用与 Netty 线程模型

核心组件一句话速记：EventLoopGroup（线程组）、Channel（连接抽象）、ChannelPipeline（入站/出站 Handler 链）、ByteBuf（池化字节缓冲，引用计数需手动 release）。各组件的异步语义、传播机制与引用计数细节：深入了解：第二章：Netty 核心组件深入

10. 典型案例：长连接网关的心跳保活与断线重连

问题背景：App 推送网关接入 50 万长连接，运行一周后告警频发：堆内存持续走高、连接数只涨不跌。排查发现运营商 NAT 空闲表项约 5 分钟回收，大量 TCP 连接已「半开」——服务端仍显示 ESTABLISHED，客户端早已失联，僵尸连接持有 ByteBuf 与 Session 不释放。

方案：双端心跳——客户端写空闲 30s 发 PING（< NAT 5 分钟回收期），服务端读空闲 60s 踢线（≈ 心跳间隔 2 倍，容忍一次抖动）；客户端断线后指数退避重连 3s→6s→12s（60s 封顶），防服务端重启时的重连风暴。

踩坑点：服务端读空闲阈值必须 ≥ 客户端心跳间隔的 2 倍，否则一次网络抖动就误杀正常连接；重连逻辑不要在 channelInactive 里 Thread.sleep()——那是 EventLoop 线程，会卡住同组所有 Channel；心跳走独立轻量类型，别进业务解码链路。

1. 概念说明

**消息队列（MQ）**是生产者和消费者之间的异步通道，解决三大问题：

  1. 异步解耦：下单后发消息，邮件/积分/通知各自消费，互不影响。

10. 典型案例：电商订单服务从单体拆分落地

10.1 问题背景

某电商平台单体应用 mall-all 运行 3 年：订单、库存、商品、营销全部在一个工程、一个 MySQL 库里。痛点：

  • 大促只想扩容下单链路，却必须整体扩容，资源浪费；
  • 营销活动改一个优惠券规则，要和订单模块一起发版，互相阻塞；
  • 一次下单在单体内只是方法调用，链路边界无人说得清。

决策：先按限界上下文识别边界，再拆服务、定契约、选通信方式。

10.2 边界识别：从限界上下文到服务目录

用 DDD 的方法：找出业务聚合（订单、商品、库存……），一个聚合一个数据所有者，聚合之间只通过 API/事件协作。

服务 拥有的数据 核心接口 与下单链路的协作
order-service orders / order_items / order_events 下单、查单、状态流转 链路发起方
product-service spu / sku / price 商品查询、价格查询 同步（实时价格、上下架）
inventory-service sku_stock / stock_log 扣减、回补、查询 异步事件（最终一致）
user-service users / address 用户信息、地址 同步（仅取展示快照）
marketing-service coupon / campaign 核销、试算 异步事件（可延后）

粒度原则：宁粗勿细。曾尝试把订单拆成 order-query / order-command / order-item 三个服务，结果一次下单跨 3 个进程，发布联动、延迟叠加——这是典型的”分布式单体”，随即按业务能力聚合回一个 order-service。

  • 共享数据库：拆分初期五个服务连同一个库，库存服务给 orders 加索引导致订单发布事故——拆服务必须同步拆库，跨服务只走 API/事件。

1. 概念说明

低代码（Low-Code）是通过可视化配置 + 少量代码快速构建应用的方法论；**无代码（No-Code）**则完全不需要写代码。目标都是：把重复的 CRUD 页面、流程审批、数据管理从手写代码中解放出来。

适用场景：

  • ✅ 内部管理系统（CRM、进销存、审批流、报表）
  • ✅ 原型验证与 MVP
  • ✅ 数据收集与展示类应用
  • ❌ 高并发、复杂算法、深度定制业务

低代码的组成要素：数据模型（表）、页面（表单/列表/详情）、权限（角色/字段级）、流程（审批/自动化）、集成（API/Webhook）。

低代码落地三层：

核心价值：业务快速上线（天级）、变更灵活、减少重复 CRUD 开发；边界：复杂算法、高并发、强一致性场景仍要专业开发。

关键原则：低代码平台是”业务中台的一部分”，必须可编程扩展（脚本/API），否则是死路。

12. 自建低代码平台思路（进阶）

若团队要自研内部低代码平台，核心模块：

  1. 元数据驱动：表结构/字段/页面布局存 JSON，运行时解释渲染
  2. 表单引擎：组件注册表 + schema 渲染（如 formily / x-render）
  3. 流程引擎：BPMN 2.0 规范（Flowable / Camunda）
  4. 权限模型：RBAC + 数据行级权限
  5. 扩展点：插件机制 + 自定义组件入口

13. 典型案例一：自研低代码表单引擎（schema 驱动）

问题背景：内部 30+ 个管理后台页面 80% 都是”表单 + 表格”，每次改个字段都要走一遍完整发版流程，前端团队疲于奔命。

方案：做一个 schema 驱动的表单引擎——字段配置存 JSON，运行时按组件注册表渲染；联动/校验规则也进 schema；预留自定义组件插槽兜底长尾需求。加一个字段 = 改一份 JSON，不用发版。

踩坑点：

  • schema 没有版本号：平台升级后旧页面渲染错乱、数据落错字段——version + 迁移函数是第一条军规。
  • 联动规则写在页面代码里，三个月后 schema 与代码”漂移”成两套真相——联动/校验必须全部进 schema。
  • 没留自定义组件插槽：遇到富文本/级联/子表格就推倒重构——预留 custom 类型 + 注册表扩展点。
  • 下拉选项硬编码 1000 条进 schema：渲染卡死——大选项集改接口拉取 + 远程搜索。

14. 典型案例二：NocoBase 工单 + n8n 自动化端到端

问题背景：客服工单原来靠群里吼：新工单没人认领、处理超时没人管、处理结果要人工同步回系统，月均漏单 30+。

方案：NocoBase 建工单表与页面（收集/流转/看板）→ 工单创建触发 Webhook 给 n8n → n8n 校验幂等后按类型分派、企微通知、24h 未关单升级 → 处理结果回调 NocoBase 回写状态。全程幂等可重试。

踩坑点：

  • n8n 节点失败默认静默：必须给工作流挂 Error Workflow + 告警，否则分派失败没人知道，漏单换个地方继续漏。
  • 双向同步没有幂等：NocoBase → n8n → 回写 NocoBase 又触发 Webhook，无限循环刷爆队列——回写用专用 API Key、只更新状态字段，且事件过滤掉 source=automation 的更新。
  • n8n 里硬编码 API Token：换密钥要改几十个节点——统一走环境变量/凭据管理，按流程分配最小权限 Key。
  • 升级通知的 Wait 节点等 24h：n8n 重启后内存队列会丢——Wait 必须用持久化模式（Redis/DB）。

14. 关键参数逐项讲透（为什么这么设）

14.1 堆内存：-Xms / -Xmx

为什么 -Xms 必须等于 -Xmx：-Xms < -Xmx 时 JVM 会在使用中动态扩容、缩容堆，扩容是 STW 的（Full GC 才能扩容）——线上会出现”流量上来 → 堆不够 → 触发 Full GC 扩容 → 停顿变长 → 更慢”的恶性循环。相等后堆大小恒定，不会因扩容停顿。

数值怎么定（用数据，不拍脑袋）：

经验公式：-Xmx ≈ 物理内存 × 40%~50%（剩余给 OS 缓存、线程栈、堆外、Metaspace）。

14.2 元空间：-XX:MaxMetaspaceSize

为什么要设上限：Metaspace 存类元数据，默认无上限（只受物理内存限制）。一旦发生类加载器泄漏（热部署、反射生成类、动态代理），Metaspace 会一路涨到把内存吃光——设上限后 OOM 抛的是 Metaspace 错误并留下现场，不设上限则直接系统 OOM（系统被杀，什么都没留下）。

14.3 GC 日志与 OOM 现场：必须开

为什么必须开：GC 日志是事后分析唯一的”时间线证据”——Full GC 什么时候开始、多频繁、老年代怎么涨，全在日志里；filecount=5,filesize=20m 是滚动日志（最多 100MB），防磁盘爆。OOM 自动 dump 同理：没有这个参数，进程一死现场就没了，内存泄漏只能靠猜。HeapDumpPath 要指向有足够磁盘空间的目录（dump 文件可能和堆一样大）。

14.4 容器环境：-XX:MaxRAMPercentage

为什么：JVM 默认按宿主机内存算默认堆（如宿主机 64G，JVM 默认堆 ≈ 1/4 = 16G），容器限额 2G 时会直接 OOM。MaxRAMPercentage=75 让 JVM 按容器 cgroup 限额的 75% 设堆——K8s/Docker 部署必须用百分比，不用写死的 -Xmx。

14.5 G1 相关：默认够用，个别才调

绝大多数服务用默认 G1 就够。调参前必须有 GC 日志数据支撑，禁止”感觉慢就调”。
