14. 实战：CasOS —— 构建在 Kubernetes 之上的云操作系统

CasOS 是一个构建在 Kubernetes 之上的云操作系统，口号是「一个文件装下你自己的云」。与传统方案的最大区别：它把 Kubernetes API server、controller-manager、scheduler 全部嵌进单个可执行文件，双击或一条命令就能在笔记本、游戏 PC 或服务器上拉起一个真实的 K8s 集群，附带 Web UI、应用商店、私有 AI 和 AI Agent 接入能力——无需 YAML，无需预先准备集群。

14.5 踩坑点

  1. Windows 节点依赖 WSL：首次启动若系统无 WSL 会自动安装，公司域控机器可能因策略失败，需先手动启用 WSL2。
  2. 单文件≠单机的限制：起步是单节点，但要发挥「加机器扩容」的价值，需保证节点间 SSH 互通与端口放行。
  3. 私有 AI 吃显存：自动选模型按显存上限来，多卡机器要留意模型副本在 GPU 间的分布，避免单卡 OOM。
  4. 别把单节点当生产：单文件集群适合个人/边缘/开发场景，生产仍需多节点 + etcd 高可用（CasOS 支持加节点，但控制面冗余要按官方文档单独规划）。

1. 概念说明

JVM（Java Virtual Machine）是 Java 跨平台的基石：把字节码翻译为机器指令并管理内存。理解 JVM 是定位内存溢出、CPU 飙高、停顿过长问题的基础。

一次 Java 程序的生命周期：源码 .java → 编译为字节码 .class → 类加载到内存 → 执行引擎解释/编译执行 → 垃圾回收自动清理无用对象。

2. 内存结构（运行时数据区）

区域 共享 作用 溢出错误
堆 是 对象分配 OutOfMemoryError: Java heap space
元空间 是 类元数据 Metaspace
虚拟机栈 否 方法调用帧 StackOverflowError
程序计数器 否 字节码行号 无

3. 类加载机制

加载 → 验证 → 准备 → 解析 → 初始化 五阶段。

双亲委派模型：类加载请求先交给父加载器（App → Platform → Bootstrap），父加载不了才自己加载——保证核心类（如 java.lang.String）不被篡改。

4. 垃圾回收（GC）

判断对象可回收：可达性分析（GC Roots 出发不可达即回收）。GC Roots 包括：栈帧局部变量、静态变量、JNI 引用等。

分代收集（对象年龄小者升代）：新生代用复制算法（Eden/S0/S1），老年代用标记-整理/标记-清除。

JDK 21 可用的收集器：

收集器 特点 适用
G1（默认） 分区化、可预测停顿 大多数服务，默认即最佳
ZGC 亚毫秒停顿、超大堆 大内存低延迟（数百 GB）

8. 调优方法论（不盲目调参）

  1. 先观测：jstat / GC 日志跑一天，看正常基线。
  2. 定位问题：是停顿长（GC）还是吞吐低（业务）还是内存泄漏。
  3. 单点修改：每次只改一个参数，用数据验证。
  4. 对照：压测（wrk / JMH）前后对比 GC 停顿、QPS、P99。

探针 作用 配置要点

关键 Deployment：

踩坑点：

  1. liveness 探针误配导致重启风暴：若 liveness 探测的接口依赖数据库，数据库短暂抖动会触发 Pod 重启，重启又加重数据库压力，形成雪崩。liveness 应只探测应用自身存活（如一个不依赖外部的轻量接口）。

1. 概念说明

分布式系统是把一个系统拆成多个独立部署、通过网络协作的节点。带来的核心矛盾：网络不可靠 + 节点会失败。

CAP 定理：分布式系统无法同时保证一致性（C）、可用性（A）、分区容错性（P），网络分区必然发生（P 必选），只能在 C 和 A 之间取舍。

BASE 理论（AP 系统的落地指导）：

  • Basically Available：基本可用（降级、限流）
  • Soft State：软状态（允许中间态）
  • Eventually Consistent：最终一致

9. 典型案例：秒杀下单的分布式 ID 与分布式锁

9.1 问题背景

秒杀下单有两个硬需求：

  1. 订单号全局唯一且趋势递增：分库分表后数据库自增主键会撞号，无序 UUID 会导致 InnoDB 聚簇索引页分裂，需要本地高性能发号器；
  2. 多实例互斥扣库存：订单服务部署多个实例同时扣同一 SKU，JVM 本地锁完全失效，需要分布式锁互斥，且不能因持锁节点宕机造成死锁。

9.2 Snowflake 雪花算法（含时钟回拨处理）

ID 结构：1 bit 符号 + 41 bit 毫秒时间戳 + 10 bit 机器位 + 12 bit 序列，单个节点每毫秒可发 4096 个号。

workerId 不能手工硬编码（多实例必然冲突），应在启动时用「IP 哈希 + 端口」或向协调组件（Nacos / 数据库号段表）申请。

9.3 Redis 分布式锁：SET NX PX + owner 校验 + Lua 释放

看门狗续期思路：固定 30s TTL 下，业务一旦执行超过 30s 锁就会提前失效。生产做法（Redisson 已内置）是加锁后启动后台调度，每 10s 检查”当前线程仍持锁且业务未结束”，就把 TTL 续回 30s；业务执行完立即停止续期并主动释放；持锁节点宕机时调度随进程消失，锁到期自动释放——既不误删又不死锁。

选择点 AP 取向 CP 取向
注册中心 Nacos/Eureka：分区时仍可发现服务（可能拿到脏实例，靠超时重试剔除） ZK/etcd：分区时少数派不可注册发现，保证视图一致

9.5 踩坑点

  • 释放锁只 DEL 不校验 owner：A 超时后 B 拿到锁，A 执行完把 B 的锁删掉，第三个请求乘虚而入——必须 UUID + Lua 比对删除。
  • 加锁不设过期时间：持锁节点 OOM 宕机后锁永久存在，该 SKU 再也无法下单——必须带 NX PX。
  • TTL 固定且无续期：GC 停顿 / 慢 SQL 导致业务没做完锁先过期——看门狗续期 + 业务幂等双保险。
  • workerId 配置冲突：两个实例同机号同毫秒发号，ID 重复——启动时自动协调分配机号。
  • 锁粒度过粗：用 lock:stock 全局一把锁，所有 SKU 被串成一队——按 skuId 拆键。

10. 常见误用与陷阱

坑 现象/后果 解法
释放锁只 DEL 不校验 owner 锁超时后误删他人锁，互斥失效、并发超卖 value 存 UUID owner，Lua 原子「比对 + 删除」

DDD 解决什么问题：业务逻辑复杂时，按”数据库表/技术分层”组织代码会导致业务规则散落各处、改一处坏一片。DDD 把业务规则收敛到领域层，让代码可读、可维护、可演进。

13. 常见误用与陷阱

坑 现象/后果 解法
以为 GIN 索引万能 ->> 过滤 + ORDER BY 仍 Seq Scan 过滤/排序字段升级独立列或表达式索引
大批量导入/更新后不 ANALYZE 统计过期，优化器弃用索引 导入后 ANALYZE，关注 last_analyze
长事务挂起不提交 旧版本无法回收，表膨胀 + XID 堆积 监控 pg_stat_activity，长事务告警
用 count(*) 做大表分页总数 每次全扫计数，接口慢 keyset 分页；总数用估算或缓存
NOT IN 子查询含 NULL 结果恒为空集，业务”查无数据” 改 NOT EXISTS / LEFT JOIN … IS NULL
关闭 autovacuum 省资源 表膨胀，磁盘涨、查询慢 保持 autovacuum，调参而非关闭
PITR 只备了 pg_dump 无法按时间点恢复，只能回备份时刻 物理备份 + WAL 归档（archive_mode）
保留字当表名不带引号 order、user 建表/查询报语法错 避开保留字或统一 "order" 带引号
