1. 概念说明

微服务（Microservices）是把一个大型应用拆分为一组小型独立服务，每个服务围绕一个业务能力（如订单、库存、用户），独立开发、独立部署、独立扩展，服务间通过轻量协议（HTTP/RPC/消息）通信。

单体 vs 微服务：

维度 单体架构 微服务
部署 一个包 N 个服务独立部署
扩展 整体扩展 按服务扩展
故障影响 全挂 局部故障
开发协作 全队改一个仓库 按服务分团队
运维成本 低 高（注册中心/网关/链路追踪）
适用 中小项目、起步阶段 大团队、高复杂度业务

铁律：微服务是”高复杂度”的解药，不是”高性能”的解药。团队小于 20 人、业务初期，单体 + 模块化是更优选择。分布式拆分要付出分布式代价（网络、事务、调试）。

2. 什么情况该上微服务（决策清单）

以下信号出现 ≥3 个才考虑：

  • 团队 20+ 人，协作冲突频繁
  • 模块间解耦需求强烈（不同发布节奏）
  • 部分模块扩展性要求差异大
  • 已有清晰的业务边界
  • 具备运维能力（容器化、监控）

10. 典型案例：电商订单服务从单体拆分落地

10.1 问题背景

某电商平台单体应用 mall-all 运行 3 年：订单、库存、商品、营销全部在一个工程、一个 MySQL 库里。痛点：

  • 大促只想扩容下单链路，却必须整体扩容，资源浪费；
  • 营销活动改一个优惠券规则，要和订单模块一起发版，互相阻塞；
  • 一次下单在单体内只是方法调用，链路边界无人说得清。

决策：先按限界上下文识别边界，再拆服务、定契约、选通信方式。

10.2 边界识别：从限界上下文到服务目录

用 DDD 的方法：找出业务聚合（订单、商品、库存……），一个聚合一个数据所有者，聚合之间只通过 API/事件协作。

服务 拥有的数据 核心接口 与下单链路的协作
order-service orders / order_items / order_events 下单、查单、状态流转 链路发起方
product-service spu / sku / price 商品查询、价格查询 同步（实时价格、上下架）
inventory-service sku_stock / stock_log 扣减、回补、查询 异步事件（最终一致）
user-service users / address 用户信息、地址 同步（仅取展示快照）
marketing-service coupon / campaign 核销、试算 异步事件（可延后）

粒度原则：宁粗勿细。曾尝试把订单拆成 order-query / order-command / order-item 三个服务，结果一次下单跨 3 个进程，发布联动、延迟叠加——这是典型的”分布式单体”，随即按业务能力聚合回一个 order-service。

10.4 同步 vs 异步：下单链路通信选择

  • 同步（Feign）：只保留”下单瞬间必须拿到实时结果”的调用——查商品价格、校验收货地址；
  • 异步（Kafka）：扣库存、核销优惠券、加积分都通过 ORDER_CREATED 事件触发，下游慢或宕机不拖下单，失败靠事件补偿 + 对账。

10.5 踩坑点

  • 共享数据库：拆分初期五个服务连同一个库，库存服务给 orders 加索引导致订单发布事故——拆服务必须同步拆库，跨服务只走 API/事件。
  • 同步链过长：最初下单同步串行调库存、营销、积分，营销一抖动整个下单超时——能异步的全部事件化，同步深度控制在 ≤ 2。
  • 契约耦合：为省事把服务端实体类打成公共 jar 给消费方，字段一改全员编译失败，还引入循环 Maven 依赖——契约独立模块、DTO 与实体隔离。
  • 漏幂等键：网络重试导致重复建单——写接口强制 Idempotency-Key，服务端用唯一索引去重。

11. 常见误用与陷阱

坑 现象/后果 解法
拆分过细，变成”分布式单体” 一次业务跨 5+ 服务，发布联动、延迟叠加、排障困难 按限界上下文聚合，宁粗勿细；一个服务对应一个业务能力
多服务共享数据库 改一列全服务回归，跨服务事务与锁竞争，自治名存实亡 每服务独享库；跨服务数据只走 API/事件，禁止直连他库
服务间循环依赖（A→B→A） Feign 调用栈循环、启动失败，职责边界无法自洽 依赖关系必须成 DAG；抽公共第三方服务或用事件反转依赖
同步调用链过长引发雪崩 下游抖动层层放大，上游线程池被占满 同步深度 ≤ 2，能异步则 MQ；每跳设超时 + 熔断降级
不设超时 / 无限重试 慢请求堆积耗尽线程池；重试风暴把下游流量放大数倍 connect/read 超时必设；重试仅限幂等接口，指数退避 + 最大次数
接口无版本、无灰度直接改 老消费方字段缺失反序列化失败，全站联动故障 路径/Header 版本化（/v1/），契约向后兼容，金丝雀灰度发布
注册中心心跳误摘实例 实例长 GC 心跳超时被摘除，剩余实例流量突增报错 调大心跳容忍、开启保护阈值（如 Nacos 0.8），实例优雅上下线
配置中心变更无审计 一条错误配置热刷新全集群，且无法追溯回滚 配置变更走审批 + 审计留痕 + 灰度生效 + 一键回滚

1. 概念说明

低代码（Low-Code）是通过可视化配置 + 少量代码快速构建应用的方法论；**无代码（No-Code）**则完全不需要写代码。目标都是：把重复的 CRUD 页面、流程审批、数据管理从手写代码中解放出来。

适用场景：

  • ✅ 内部管理系统（CRM、进销存、审批流、报表）
  • ✅ 原型验证与 MVP
  • ✅ 数据收集与展示类应用
  • ❌ 高并发、复杂算法、深度定制业务

低代码的组成要素：数据模型（表）、页面（表单/列表/详情）、权限（角色/字段级）、流程（审批/自动化）、集成（API/Webhook）。

低代码落地三层：

核心价值：业务快速上线（天级）、变更灵活、减少重复 CRUD 开发；边界：复杂算法、高并发、强一致性场景仍要专业开发。

关键原则：低代码平台是”业务中台的一部分”，必须可编程扩展（脚本/API），否则是死路。

若团队要自研内部低代码平台，核心模块：

13. 典型案例一：自研低代码表单引擎（schema 驱动）

问题背景：内部 30+ 个管理后台页面 80% 都是”表单 + 表格”，每次改个字段都要走一遍完整发版流程，前端团队疲于奔命。

方案：做一个 schema 驱动的表单引擎——字段配置存 JSON，运行时按组件注册表渲染；联动/校验规则也进 schema；预留自定义组件插槽兜底长尾需求。加一个字段 = 改一份 JSON，不用发版。

踩坑点：

  • schema 没有版本号：平台升级后旧页面渲染错乱、数据落错字段——version + 迁移函数是第一条军规。
  • 联动规则写在页面代码里，三个月后 schema 与代码”漂移”成两套真相——联动/校验必须全部进 schema。
  • 没留自定义组件插槽：遇到富文本/级联/子表格就推倒重构——预留 custom 类型 + 注册表扩展点。
  • 下拉选项硬编码 1000 条进 schema：渲染卡死——大选项集改接口拉取 + 远程搜索。

14. 典型案例二：NocoBase 工单 + n8n 自动化端到端

问题背景：客服工单原来靠群里吼：新工单没人认领、处理超时没人管、处理结果要人工同步回系统，月均漏单 30+。

踩坑点：

  • n8n 节点失败默认静默：必须给工作流挂 Error Workflow + 告警，否则分派失败没人知道，漏单换个地方继续漏。

  • 升级通知的 Wait 节点等 24h：n8n 重启后内存队列会丢——Wait 必须用持久化模式（Redis/DB）。

14. 关键参数逐项讲透（为什么这么设）

14.1 堆内存：-Xms / -Xmx

为什么 -Xms 必须等于 -Xmx：-Xms < -Xmx 时 JVM 会在使用中动态扩容、缩容堆，扩容是 STW 的（Full GC 才能扩容）——线上会出现”流量上来 → 堆不够 → 触发 Full GC 扩容 → 停顿变长 → 更慢”的恶性循环。相等后堆大小恒定，不会因扩容停顿。

数值怎么定（用数据，不拍脑袋）：

经验公式：-Xmx ≈ 物理内存 × 40%~50%（剩余给 OS 缓存、线程栈、堆外、Metaspace）。

14.2 元空间：-XX:MaxMetaspaceSize

为什么要设上限：Metaspace 存类元数据，默认无上限（只受物理内存限制）。一旦发生类加载器泄漏（热部署、反射生成类、动态代理），Metaspace 会一路涨到把内存吃光——设上限后 OOM 抛的是 Metaspace 错误并留下现场，不设上限则直接系统 OOM（系统被杀，什么都没留下）。

14.3 GC 日志与 OOM 现场：必须开

为什么必须开：GC 日志是事后分析唯一的”时间线证据”——Full GC 什么时候开始、多频繁、老年代怎么涨，全在日志里；filecount=5,filesize=20m 是滚动日志（最多 100MB），防磁盘爆。OOM 自动 dump 同理：没有这个参数，进程一死现场就没了，内存泄漏只能靠猜。HeapDumpPath 要指向有足够磁盘空间的目录（dump 文件可能和堆一样大）。

14.4 容器环境：-XX:MaxRAMPercentage

为什么：JVM 默认按宿主机内存算默认堆（如宿主机 64G，JVM 默认堆 ≈ 1/4 = 16G），容器限额 2G 时会直接 OOM。MaxRAMPercentage=75 让 JVM 按容器 cgroup 限额的 75% 设堆——K8s/Docker 部署必须用百分比，不用写死的 -Xmx。

14.5 G1 相关：默认够用，个别才调

绝大多数服务用默认 G1 就够。调参前必须有 GC 日志数据支撑，禁止”感觉慢就调”。

13. 发布分支与热修规范

发布分支（release/*）：功能冻结后从 develop 切出，只接受 bug 修复，不再合入新功能；验证通过后合入 main 并打 tag，同时回合到 develop，避免修复丢失。

热修分支（hotfix/*）：线上故障从 main（生产基线）切出，修完经 PR 合入 main 并立即发布补丁版本，再回合 develop。

约定：

  • 主线以外分支只做一件事，release/* 不掺新功能，hotfix/* 不掺重构。
  • 发布前确认 tag 与变更记录（CHANGELOG）一致。
  • 紧急修复也必须走 hotfix/* + PR，保护分支的意义就是不给你”就这一次”的例外。

踩坑点：

  • Basically Available：基本可用（降级、限流）

9. 典型案例：秒杀下单的分布式 ID 与分布式锁

9.1 问题背景

秒杀下单有两个硬需求：

  1. 订单号全局唯一且趋势递增：分库分表后数据库自增主键会撞号，无序 UUID 会导致 InnoDB 聚簇索引页分裂，需要本地高性能发号器；
  2. 多实例互斥扣库存：订单服务部署多个实例同时扣同一 SKU，JVM 本地锁完全失效，需要分布式锁互斥，且不能因持锁节点宕机造成死锁。

9.2 Snowflake 雪花算法（含时钟回拨处理）

ID 结构：1 bit 符号 + 41 bit 毫秒时间戳 + 10 bit 机器位 + 12 bit 序列，单个节点每毫秒可发 4096 个号。

workerId 不能手工硬编码（多实例必然冲突），应在启动时用「IP 哈希 + 端口」或向协调组件（Nacos / 数据库号段表）申请。

9.3 Redis 分布式锁：SET NX PX + owner 校验 + Lua 释放

看门狗续期思路：固定 30s TTL 下，业务一旦执行超过 30s 锁就会提前失效。生产做法（Redisson 已内置）是加锁后启动后台调度，每 10s 检查”当前线程仍持锁且业务未结束”，就把 TTL 续回 30s；业务执行完立即停止续期并主动释放；持锁节点宕机时调度随进程消失，锁到期自动释放——既不误删又不死锁。

9.4 CAP 取舍

选择点 AP 取向 CP 取向
注册中心 Nacos/Eureka：分区时仍可发现服务（可能拿到脏实例，靠超时重试剔除） ZK/etcd：分区时少数派不可注册发现，保证视图一致

发号器 Snowflake：本地发号无网络依赖，时钟问题需自行防护 数据库号段：严格可控，但发号组件宕机即不可用

9.5 踩坑点

  • 释放锁只 DEL 不校验 owner：A 超时后 B 拿到锁，A 执行完把 B 的锁删掉，第三个请求乘虚而入——必须 UUID + Lua 比对删除。
  • 加锁不设过期时间：持锁节点 OOM 宕机后锁永久存在，该 SKU 再也无法下单——必须带 NX PX。
  • TTL 固定且无续期：GC 停顿 / 慢 SQL 导致业务没做完锁先过期——看门狗续期 + 业务幂等双保险。
  • workerId 配置冲突：两个实例同机号同毫秒发号，ID 重复——启动时自动协调分配机号。
  • 锁粒度过粗：用 lock:stock 全局一把锁，所有 SKU 被串成一队——按 skuId 拆键。
