第八章：Java并发锁全解与选型

概念基础

  1. 为什么需要锁：多个线程同时读写共享变量（如 count++）会因原子性、可见性、有序性三大问题产生数据错乱，锁是保证线程安全最直接的手段。
  2. 两大流派：悲观锁先加锁再操作（synchronized、ReentrantLock），乐观锁先操作再校验冲突（Atomic 原子类的 CAS 机制）。
  3. JVM 内置锁 vs JDK 显式锁：synchronized 由 JVM 自动加解锁、可重入、非公平；Lock 接口（ReentrantLock 等）额外支持超时、可中断、公平锁、多 Condition 精准唤醒。
  4. 读写分离优化：读多写少场景用 ReentrantReadWriteLock（读读共享）；追求极致读性能再上 StampedLock 的无锁乐观读。
  5. 无锁更轻：单变量的计数/状态标志可用 Atomic 原子类或 volatile（保证可见性、禁止重排），避免加锁开销。

涵盖：synchronized、ReentrantLock、ReentrantReadWriteLock、StampedLock、Atomic原子类、volatile

锁类型 核心特点 适用场景
synchronized 简单自动加解锁、可重入 简单临界区、低并发、快速开发

常见避坑

坑 现象 正确做法
synchronized 锁错对象 锁了不同实例，并发问题依旧；或锁 String/Integer 缓存对象导致”意料之外的互斥” 锁私有 final 监视器对象 private final Object lock = new Object()；或明确锁当前类 Xxx.class（静态）
ReentrantLock 忘写 finally unlock 异常路径下锁未释放 → 死锁/永远阻塞 固定模板：lock.lock(); try { … } finally { lock.unlock(); }
wait/notify 不在循环中判断条件 虚假唤醒（spurious wakeup）或多线程抢占 → 条件不满足仍继续往下跑 永远用 while (条件不满足) wait()，不要 if；用 Condition.await() 同样规则
notify() 而不是 notifyAll() 两个等待队列（消费/生产）互发通知，只有一个被唤醒，另一个永远挂起 除非只存在一种等待条件且线程数严格为 2，否则一律 notifyAll() / signalAll()
volatile 当原子用 volatile int i; i++ 仍竞态；以为可见性=原子性 计数类用 AtomicInteger.getAndIncrement，复合操作上 synchronized 或 ReentrantLock
线程池用 Executors.newFixedThreadPool 无界队列 任务堆积 OOM，线上几小时后 JVM 崩溃 自己 new ThreadPoolExecutor(…, new ArrayBlockingQueue<>(N), new CallerRunsPolicy())：有界队列 + 拒绝策略
ThreadLocal 不 remove Tomcat/Netty 线程池复用时上下文串号、内存泄漏、类加载器泄漏 try 里用，finally { tl.remove(); } 必写；跨请求不要依赖 ThreadLocal 传值
死锁：锁顺序不一致 A 线程拿 lock1 再 lock2，B 线程拿 lock2 再 lock1 → 双方互等 统一全局加锁顺序；用 tryLock(timeout) 加锁失败回退；一次性 Lock 组合对象封装
ConcurrentHashMap 的 putIfAbsent/compute 误用 if (!map.contains(k)) map.put(k, v) 仍竞态，出现重复初始化 用 map.computeIfAbsent(k, k -> new Resource())，单步原子
共享可变对象没同步 把非线程安全的 SimpleDateFormat、HashMap 当静态字段共用 SimpleDateFormat 替换为 DateTimeFormatter（线程安全）；跨线程共享集合统一用 JUC 并发集合
CountDownLatch/Semaphore 数量对不上 await() 不结束或过早结束 主线程和工作线程都打印剩余计数做联调；每一条异常路径都必须 countDown() / release()（放进 finally）
Future.get() 不加超时 单个线程 hang → 整个线程池被拖死 future.get(5, TimeUnit.SECONDS) + 捕获 TimeoutException 并记录/取消任务

要点 结论
synchronized 简单、自动加解锁、可重入，适合低并发简单临界区
ReentrantLock 超时/可中断/公平/Condition，复杂同步与生产者消费者首选
读写锁 ReentrantReadWriteLock 读读共享，读多写少（缓存、配置）场景

Atomic / volatile 无锁方案：CAS 原子操作与可见性保证，单变量场景开销最小

第十六章：QUIC 实践：自签名证书与 HTTP/3 服务端、客户端（Python）

概念基础

本章把第十五章的 QUIC / HTTP/3 概念落地为可运行的最小工程：

  1. 为什么需要自签名证书：QUIC 强制加密（TLS 1.3），本地实验没有域名与 CA，用 OpenSSL 一行生成自签名证书即可起步；SAN 决定浏览器与客户端的 SNI 校验能否通过。
  2. 服务端为什么选 Hypercorn：基于 aioquic 的 ASGI 服务器，bind（TCP TLS）+ quic_bind（UDP） 同端口并存，兼顾浏览器「先 TCP 后 HTTP/3」的建连习惯。
  3. 客户端为什么手写 aioquic：官方栈直接暴露 QUIC + HTTP/3 事件，能看清「头插帧、流、证书校验」；用 load_verify_locations 显式信任自签名证书而不是跳过校验。
  4. 验证路径：先 Python 客户端打通 UDP/QUIC，再用支持 HTTP/3 的 curl 复测——两条独立证据链确认 HTTP/3 真正生效。

启动

说明：bind 与 quic_bind 都写 127.0.0.1:4433 时，在 Linux 上可同时监听 TCP 与 UDP（端口号相同、协议不同）。这样 Chrome / Firefox / Edge 打开 https://127.0.0.1:4433/ 会先走 TCP TLS 拿到页面；支持 HTTP/3 的浏览器还可能通过 Alt-Svc 等机制再尝试 QUIC。若坚持只开 UDP（例如 cfg.bind = []），多数浏览器无法仅靠 https:// 完成首次加载，因为常见实现会先做 TCP 连接。

为何浏览器还常要 TCP、和 QUIC 设计是否冲突

不冲突。 QUIC（RFC 9000）只规定跑在 UDP 上；HTTP/3 也完全可以在只有 UDP 的情况下工作（例如本节的 aioquic 客户端直连 quic_bind）。

浏览器在地址栏输入 https://主机:端口/ 时，多数实现仍沿用历史习惯：先按「TLS over TCP」去建第一条连接，再通过响应里的 Alt-Svc、或 DNS HTTPS/SVCB 等线索，得知同一站点也可用 HTTP/3，之后才发起 QUIC。这是浏览器与 Web 生态的部署/发现策略，不是 QUIC 协议里「必须先有 TCP」的要求。本地演示若没有 DNS、没有事先缓存的 Alt-Svc，只监听 UDP 时，用户只输入 https:// 就容易连不上，因此示例里同时开同端口的 TCP TLS 是为了兼容这种建连路径，属于工程上的折中，与 QUIC 规范无矛盾。

在浏览器里打开时的证书提示

自签名证书会触发「不安全」或「您的连接不是私密连接」：本地实验可在 高级 中选择继续访问（Chrome），或把 cert.pem 导入系统/浏览器的受信任根（更安全、少打扰）。不要用这种方式处理公网真实用户流量。

第七章：MyBatis-Flex 入门与代码生成

概念基础

  1. 是什么：MyBatis-Flex 是基于 MyBatis 的轻量级增强框架，在保留 MyBatis 全部能力的同时，提供 BaseMapper 通用 CRUD、QueryWrapper/QueryChain 链式查询、内置分页等开箱即用的能力。
  2. 为什么选它：同为「MyBatis 增强」框架，比 MyBatis-Plus 拦截器更轻、SQL 解析更强、自动 Count 更智能，且自动装配，无需手动注册分页插件。
  3. 底层原理：复用 MyBatis 拦截器机制（MyBatisFlexInterceptor → PageInterceptor），分页写法与 MyBatis-Plus 几乎一模一样，可无缝切换。
  4. 代码生成：配合 IDEA 插件 MyBatisX-Generator，在数据库表上右键即可自动生成 CRUD 代码，省去手写模板。
  5. 迁移友好：从 MyBatis-Plus 迁移只需换依赖、换注解包，业务 CRUD 与分页代码零改动。

核心逻辑：
MyBatis 拦截器 → 拦截查询SQL → 自动生成 count 总数 → 原SQL 拼接 LIMIT → 封装分页结果

    Flex 全局核心拦截器，替代 MP 的 MybatisPlusInterceptor
  2. PageInterceptor

  3. Page、IPage
    分页载体，和 MP 几乎一模一样：当前页、页大小、总条数、分页数据

第六章：Java 动态数据源：@DS 切换与事务边界

概念基础

  1. 为什么需要多数据源：主从读写分离、按库分业务、迁移期新旧库并存等场景，要求应用在运行时切换数据库连接。
  2. 动态数据源方案：Spring 提供 AbstractRoutingDataSource 路由骨架；Baomidou 的 dynamic-datasource 在此之上提供开箱即用的实现。
  3. 核心注解 @DS：通过 @DS("逻辑名") 声明当前类/方法使用的数据源，底层借助 AOP 代理 + ThreadLocal 上下文完成切换，对 MyBatis-Plus、MyBatis-Flex、JdbcTemplate 等均透明适用。
  4. 切换时机是关键：数据源在获取连接时确定；已开启事务并绑定连接后，再切换通常不会生效，须注意事务边界。
  5. 常见陷阱：同类自调用绕过 Spring 代理导致 @DS 失效；编程式切换 push 后忘记 poll 会污染线程上下文。

事务与边界情况

  • 同一事务内：已进入 @Transactional 且已绑定连接后，再切换数据源通常不会按预期切到新库（连接已固定）。多数据源写操作应拆到不同事务方法，或调整事务边界，使切换发生在开启事务之前。
  • 只读事务：若使用 @Transactional(readOnly = true)，仍要注意连接从哪个数据源取得，与 @DS 所在方法的事务传播一致。
  • 自调用：同类内 this.method() 不会经过 Spring 代理，@DS 可能不生效，应抽到另一个 Bean 或通过代理调用。

与 MyBatis-Plus / MyBatis 的配合

引入 MyBatis-Plus 后，SqlSessionFactory 仍使用 Spring 容器中的动态 DataSource，与 dynamic-datasource 无额外冲突。Mapper（含继承 BaseMapper 的接口）或 XML 无需单独为多数据源改一套配置即可随当前线程数据源路由；若某几个 Mapper 固定走副库，可在 Mapper 接口上加 @DS("pgsql")。

第十章：Redis Geospatial：概念、命令与案例

概念基础

Geospatial（GEO） 是 Redis 的地理位置模块——存经纬度坐标，提供「附近有什么」「两点距离多远」的原生查询能力：

  1. 数据仍落在 ZSet 上：TYPE key 一般为 zset；member 为地点 ID，score 为 Geohash 编码（使用者通常只调 GEO 命令）。
  2. 坐标使用经度、纬度（GEOADD 参数顺序为 lon lat，勿写反——这是 GEO 最常见的第一个坑）。
  3. 它是 第七章：Redis ZSet 数据类型：概念、命令与案例 的空间特化：排序键从「积分」变成了「地理位置编码」，排序即「从西到东、从南到北」，近邻查询就是一次score 范围扫描。
  4. 地球模型为球面近似，极高精度场景需自行评估误差。

核心原理：Geohash 编码与近邻查询

  1. Geohash 编码：把经度区间 [-180,180]、纬度区间 [-90,90] 反复二分——经度偏西记 0、偏东记 1，纬度偏南记 0、偏北记 1，两边比特交错拼成一串二进制。二分越深，编码越精确。
  2. 为什么「二分交错」有效：交错后，前缀相同的两个编码，地理位置必然相近；编码的大小顺序 ≈ 地理位置顺序。Redis 把这个二进制串转成 52 位整数作为 ZSet 的 score——于是「附近查询」变成了「score 在邻域区间内的范围扫描」，完全复用跳表的 O(logN) 能力（这正是第七章双结构的红利）。
  3. 距离计算：GEODIST 用球面距离（Haversine 类公式）计算两点弧长，可选 m / km / ft / mi 单位。
  4. API 演进：Redis 6.2+ 推荐 GEOSEARCH（支持 BYRADIUS / BYBOX、ASC/DESC、COUNT、带 WITHDIST/WITHCOORD），GEORADIUS / GEORADIUSBYMEMBER 已被视为过时接口——新代码优先 GEOSEARCH。

常用命令

命令 作用
GEOADD key lon lat member 添加或更新坐标
GEODIST key m1 m2 [单位] 两点距离；单位 m / km / ft / mi
GEORADIUS / GEORADIUSBYMEMBER 以坐标点 / 已知成员为中心，半径内成员（新版本有 GEOSEARCH，以文档为准）
GEOPOS / GEOHASH 取坐标 / Geohash 字符串

典型应用场景

  1. 附近门店：GEOADD shops …，用户定位后 GEORADIUS。
  2. 配送范围校验：GEODIST 与阈值比较。
  3. 与外部地图：Redis 做粗筛，精确路径导航交给地图 API。

综合案例（redis-cli）

注意事项

  1. 经度纬度顺序：lon 在前 lat 在后。
  2. 跨版本 API：Redis 6.2+ 引入 GEOSEARCH 等，生产以当前版本文档为准。
  3. 数据量：全国级 POI 全进一个 key 可能过大，可按城市分片多个 GEO key。

第八章：Redis Bitmap 数据类型：概念、命令与案例

概念基础

Bitmap（位图） 不是一种独立类型，而是 String 的「位视角」——把值的每个二进制位当作一个独立元素来读写：

  1. 按位偏移读写 0/1，可 BITCOUNT 统计 1 的个数，BITOP AND/OR/XOR/NOT 做位运算。
  2. 省空间：1 亿个布尔标记理论上只需 ~12 MB（10^8 ÷ 8 字节），比「每个用户一个 String key」的 key 头开销小得多（仍要算总内存）。
  3. offset 从 0 开始；未设置位视为 0。
  4. 心智模型：offset 是「编号」（用户 ID、第几天），位值是「状态」（是否签到/是否活跃）——用之前先设计好编号 → offset 的映射规则，是 Bitmap 唯一的难点。

核心原理：存储与内存账

  1. 本质是 String：位图数据就存在 SDS 字节串里；所以 EXPIRE 照常可用，STRLEN 返回占用字节数（BITCOUNT 统计的是 1 的个数，两者含义不同）。底层用 popcount 指令做统计，O(N) 但极快。
  2. 内存账：占用 ≈ (最大 offset ÷ 8) 字节。与设了几个 1 无关，只与最大 offset 有关：
    • offset = 1 亿 → 约 12 MB；offset = 10 亿 → 约 119 MB。
    • 稀疏 ID 是大坑：只有 100 个用户但 ID 是十亿级时，SETBIT dau 1000000000 1 也会为最大 offset 分配整段空间——这就是注意事项里「分桶」的原因。
  3. offset 上限：2^32 - 1（约 42.9 亿位，对应 512 MB 的 String 上限）。
  4. BITOP 的代价：对两个大位图做 AND/OR 是 O(N) 且同步执行——超大位图运算放低峰期或拆小。

常用命令

命令 作用
SETBIT key offset value value 为 0 或 1
GETBIT key offset 读某一位
BITCOUNT key [start end] 统计 1 的个数（字节区间可选）
BITOP operation destkey key [key ...] 多 key 位运算写入 dest
BITPOS 找第一个 0/1 的位置

典型应用场景

  1. 签到：sign:2026:05:user:1001 用日期映射 offset（需统一映射规则防冲突）。
  2. 日活标记：dau:2026-05-03 下 offset = 用户整型 ID（ID 空间稀疏时浪费内存，要评估）。
  3. 与 HyperLogLog：Bitmap 偏「谁来了」的位图（能回答「某用户来没来」）；UV 近似计数用 HLL（回答「大约多少人」）。

综合案例（redis-cli）

注意事项

  1. 稀疏 ID：用户 ID 为 十亿级 时，SETBIT dau 1000000000 1 会促使底层分配很长空间，可能极度浪费；需分桶（按用户段拆 key）或换结构。
  2. TTL：位图也是 String，可 EXPIRE。
  3. 统计口径：BITCOUNT 是「1 的个数」，业务上对应「签到天数」等要先设计好 offset 含义。

第九章：Redis HyperLogLog：概念、命令与案例

概念基础

HyperLogLog（HLL） 是一种基数（去重计数）估算算法的数据结构——用极小的固定内存回答「这批元素大约有多少个不同的」：

  1. 不是存明细，只支持 PFADD 添加元素、PFCOUNT 估算基数、PFMERGE 合并多个 HLL。
  2. 内存奇迹：无论存 1 万还是 1 亿个元素，每个 HLL 固定约 12 KB——对比 Set 存 1 亿个 ID 要数 GB，差距是数量级的。
  3. 代价是近似：标准误差约 0.81%（1 亿 UV 估出 99.2M±80 万属正常）。
  4. 适合：海量 UV、IP 去重计数等允许近似的报表。
  5. 不适合：必须精确计数、需要枚举曾出现过的元素。

核心原理：直觉理解

  1. 伯努利试验直觉：把每个元素哈希成比特串，观察末尾连续 0 的个数。连续 0 越长越罕见；记录见过的最大连续 0 数 k，就用 2^k 粗估基数——「见过 5 个连续 0」说明大约掷过 2^5 量级的硬币。
  2. 分桶降方差：单一估计抖动太大，HLL 把哈希值前若干位作桶号，分成 2^14 = 16384 个桶，每桶各自记录最大连续 0 数，最后对全部桶取调和平均再修正——误差稳定在 0.81% 左右。
  3. 内存去向：16384 桶 × 每桶 6 bit ≈ 12 KB，与数据量无关；这就是「固定内存估算海量基数」的全部秘密。
  4. 合并即并集：两桶取最大值就是 PFMERGE——所以「按天分 key、周报 PFMERGE」天然正确，且合并结果仍是近似误差，不会叠加放大。
  5. 边界：拿不回成员（哈希不可逆），PFCOUNT 大 key 的多 key 形式可能触发临时合并开销（高版本有缓存优化）。

常用命令

命令 作用
PFADD key element [element ...] 向 HLL 增加元素（可批量）
PFCOUNT key [key ...] 单个或合并估算基数
PFMERGE destkey sourcekey [sourcekey ...] 合并到 dest

典型应用场景

  1. 页面 / 活动 UV：PFADD uv:2026-05-03:page1 <userId 或 sessionId>，定时 PFCOUNT。
  2. 多维度合并：按天分 key，日报用 PFMERGE 聚合成周 UV。

综合案例（redis-cli）

注意事项

  1. 误差：报表若要求精确 UV，需 Set（内存大）或离线数仓。
  2. 元素语义：PFADD 把参数当字节串；业务上应用统一 ID（如用户 ID），勿混多种粒度。
  3. 无法查询成员：不能问「谁访问过」，只能问「大约多少人」。

本章小结

要点 结论
定位 固定 ~12 KB 估算基数，误差 ~0.81%
三个命令 PFADD / PFCOUNT / PFMERGE，无成员查询
原理直觉 哈希尾 0 长度 + 16384 桶调和平均
与 Set 精确去重 → Set（内存换准确）；近似报表 → HLL
与 Bitmap 位图答「谁来过」；HLL 答「多少人」

发表于 2026-05-03 更新于 2026-09-01 分类于 Redis 本文字数： 903 阅读时长 ≈ 3 分钟

第七章：Redis ZSet 数据类型：概念、命令与案例

概念基础

ZSet（Sorted Set，有序集合）给每个成员挂一个分值（score），集合内部始终按 score 排序：

  1. TYPE key 为 zset。
  2. member 唯一；同一 member 再次 ZADD 会更新 score（不是报错、也不是新增——这是「改积分」的基础语义）。
  3. 排序方向：score 从小到大是「正序」；排行榜通常要 ZREVRANGE 降序取 Top N。
  4. 范围查询、排名 ZRANK/ZREVRANK 为高频 API——「第几名」「前 100 名」「积分区间成员」都是 O(logN) 级别的现成能力，这是 Set 给不了的。

核心原理：跳表与双结构

  1. 两种编码：元素少且成员短时用 listpack（7.0 前 ziplist）；一般情况用 skiplist 编码（OBJECT ENCODING 可查）。

  2. skiplist 编码 = 双结构：同一份数据同时挂在两个索引上：

    • 跳表（zskiplist）：按 score 排序的有序跳表，负责 ZRANGE / ZRANGEBYSCORE / ZRANK 等范围与排名操作，复杂度 O(logN)。
    • 字典（dict）：member → score 映射，负责 ZSCORE 这类按成员查分值的 O(1) 操作。
    

flowchart LR
  Z[ZSet key] --> S[skiplist 按 score 排序<br/>范围 / 排名 O logN]
  Z --> D[dict: member→score<br/>查分 O 1]

  3. 为什么用跳表而不是平衡树：范围查询同样高效、实现远比红黑树简单（无旋转）、按排名定位（span 跨度字段）天然支持——是工程权衡的典型案例。

  4. score 精度：score 是 double，能精确表示的整数范围约 2^53；时间戳做 score 时统一毫秒或秒，避免大数值浮点误差。

  5. 并发安全：ZADD 更新、ZINCRBY 加分都是单线程原子操作，排行榜「并发刷分」不丢更新。

常用命令（必会子集）

命令 作用
ZADD key score member 添加或更新分值
ZRANGE / ZREVRANGE 按排名升/降序取片段（WITHSCORES 带出分数）
ZRANGEBYSCORE 按 score 区间取
ZRANK / ZREVRANK 升序 / 降序名次（0 基）
ZSCORE / ZCARD / ZINCRBY 查分 / 成员数 / 原子加分
ZREM / ZPOPMIN / ZPOPMAX 删除成员 / 弹出最小/大

典型应用场景

  1. 游戏 / 活动排行榜：member=用户 ID，score=积分。
  2. 延时任务：score=执行时间戳，定时 ZRANGEBYSCORE 拉到期任务再 ZREM。
  3. 热搜权重：结合时间衰减可周期性重算 score（逻辑在应用层）。

综合案例（redis-cli）

注意事项

  1. 热 key：单排行榜 key 超高并发时考虑分片或本地缓存 + 合并。
  2. 大 ZSet：避免一次 ZRANGE 0 -1；分页用 ZRANGE 窗口。
  3. score 精度：浮点比较注意误差；时间戳建议统一毫秒或秒。

要点 结论
