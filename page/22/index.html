第四章：Redis Hash 数据类型：概念、命令与案例

概念基础

Hash 是「key → 若干 field/value 对」的映射，类似一张微型数据行或一个对象文档：

  1. 一个 key 下挂多对 field / value，field 与 value 均为字符串（二进制安全）。
  2. TYPE key 显示 hash。
  3. 与 String 存 JSON 的区别：String 改一个字段要「读出 → 反序列化 → 改 → 序列化 → 写回」四步，Hash 只需 HSET 一个 field——这就是「局部更新」的价值。
  4. 适合「用户资料、购物车行、配置项分组」等属性较多且常单独更新的场景。

核心原理：编码与底层结构

  1. 两种编码（OBJECT ENCODING key 可观察）：
    • listpack（Redis 7.0 前为 ziplist）：字段少且值短的紧凑编码，所有 field/value 连续存放，省内存但对中间元素的访问是 O(N)——靠「元素少」保证不慢。
    • hashtable：字典结构，field → value 的 O(1) 哈希访问。
  2. 编码转换阈值：任一条件超出即从 listpack 转 hashtable（默认 hash-max-listpack-entries 128、hash-max-listpack-value 64，以 CONFIG GET hash-max-* 为准）；转换是单向的，转回不再发生。
  3. 渐进式 rehash：hashtable 扩容时 Redis 同时持有两张哈希表，把数据分批从旧表搬到新表（每次命令顺带迁一小批 + 定时任务），避免一次搬家阻塞服务——这是单线程 Redis 能平滑扩容的关键设计。
  4. 复杂度与注意点：HGET / HSET（单字段）为 O(1)；HGETALL / HKEYS / HVALS 为 O(N)（N 为字段数），大 Hash 上应改用 HSCAN 分批遍历；HINCRBY 是原子的字段加减。

常用命令（必会子集）

命令 作用
HSET key field value [field value …] 设置一个或多个字段（Redis 4.0+ 推荐 HSET 多字段；旧 HMSET 已废弃）
HGET / HMGET / HGETALL 读单字段 / 多字段 / 全表
HDEL 删字段
HEXISTS / HLEN 字段是否存在 / 字段个数
HINCRBY / HINCRBYFLOAT 字段数值原子增减
HSCAN 大 Hash 迭代遍历（生产避免 HGETALL 撑爆网络）

典型应用场景

  1. 用户资料：user:1001 下 name / vip / city 等，改一项只动一个 field。
  2. 购物车行：cart:uid:1001 下 sku:2001 → 数量 JSON 或纯数字。
  3. 对象缓存：比整串 String 更易做局部更新；仍要注意过期策略与缓存一致性。

综合案例（redis-cli）

注意事项

  1. 大 Hash：字段极多时 HGETALL 成本高，列表页用 HSCAN 或只取需要的 HMGET。
  2. 小 Hash 编码：字段少且短时可能 listpack 等紧凑编码，内存更省（OBJECT ENCODING 可观察）。
  3. 与 String JSON 选型：读多写少、整体替换频繁 → String；字段独立更新多 → Hash。

本章小结

要点 结论
本质 key → 多对 field/value，像「数据行」
编码 listpack（小而省）→ hashtable（O(1) + 渐进式 rehash）
复杂度 单字段 O(1)；HGETALL O(N)，大 Hash 用 HSCAN
高频命令 HSET / HGET / HGETALL / HINCRBY / HDEL
选型 字段常单独更新 → Hash；整体读写 → String JSON

第六章：Redis Set 数据类型：概念、命令与案例

概念基础

Set 是无序、不重复的字符串成员集合，直接对应数学里的「集合」：

  1. TYPE key 为 set。
  2. 不保证顺序（遍历顺序实现依赖，勿当有序结构用）。
  3. 成员即字符串；同一成员重复 SADD 只保留一份，判重是 O(1)——这是它与 List 最本质的差异。
  4. 集合间可做 SINTER / SUNION / SDIFF（交 / 并 / 差），把「共同关注」「可能认识的人」这类关系计算下推到 Redis 里完成。

核心原理：编码与复杂度

  1. 两种编码（OBJECT ENCODING key 观察）：
    • intset：成员全部是整数且个数不超过 set-max-intset-entries（默认 512）时使用，有序整数数组 + 二分查找，最省内存。
    • hashtable：一般情况使用，member 作字典的 key、value 恒为 NULL——「唯一性」由哈希表天然保证，SADD / SISMEMBER / SREM 均 O(1)。
  2. 集合运算的代价：SINTER / SUNION / SDIFF 最坏 O(N·M)（两个集合都大时开销显著），且是同步计算——生产上建议用 SINTERSTORE 等 STORE 系列写入新 key，再异步消费结果，避免大运算阻塞在交互命令里。
  3. 随机语义：SPOP 是弹出（取出并从集合删除，不放回）；SRANDMEMBER 只读不删（count 为正给不重复成员、为负允许重复）——抽奖「不放回」用 SPOP、「仅看看」用 SRANDMEMBER。

常用命令（必会子集）

命令 作用
SADD / SREM 增删成员
SMEMBERS 返回全部成员（大集合慎用）
SISMEMBER / SCARD 是否在集合 / 成员个数
SRANDMEMBER / SPOP 随机读 / 随机弹出
SINTER / SUNION / SDIFF 交 / 并 / 差（可带 STORE 写到新 key）

典型应用场景

  1. 标签：SADD article:7:tags Java Redis。
  2. 抽奖池 / 去重 ID 池：SPOP 不放回抽样（需理解并发下多个客户端抢 SPOP 的语义）。
  3. 共同关注：SINTER user:1:following user:2:following。

综合案例（redis-cli）

注意事项

  1. 大 Set：SMEMBERS 一次性拉全量可能阻塞与占带宽，用 SSCAN 迭代。
  2. 与 List：Set 无序且唯一；List 有序可重复。
  3. 需要按分数排序（排行榜）→ 用 ZSet，不要用 Set 硬撑。

本章小结

要点 结论
本质 无序、唯一，O(1) 判重
编码 intset（全整数小集合）→ hashtable
集合运算 SINTER/SUNION/SDIFF，大集合用 STORE 系列异步化
高频命令 SADD / SISMEMBER / SCARD / SINTER / SPOP
场景 标签、去重、抽奖、共同关注

第五章：Redis List 数据类型：概念、命令与案例

发表于 2026-05-03 更新于 2026-09-01 分类于 Redis 本文字数： 850 阅读时长 ≈ 3 分钟

第五章：Redis List 数据类型：概念、命令与案例

概念基础

List 是一个 key 下的双向序列，从左右两端都能进出：

  1. 有序、可重复；同一 value 可出现多次。
  2. TYPE key 为 list。
  3. 两端操作是它的设计重心（入队/出队都很快），中间插入/删除代价高于两端（需遍历指针）；设计时尽量从两头消费。
  4. 下标支持负数（-1 表最后一个元素），LRANGE key 0 -1 即取全表。
  5. 与 Java 里的 LinkedList 心智模型接近：当队列、栈、时间线用，不要当随机访问数组用。

核心原理：底层结构与阻塞机制

  1. quicklist：List 的底层是 quicklist——一条双向链表，但每个链表节点内部是一段 listpack（7.0 前为 ziplist）压缩段。这样兼顾两头：链表保证两端 O(1)，listpack 保证小段数据省内存（每段大小由 list-max-listpack-size 控制，负数表示按元素个数/大小限制）。
  2. 复杂度：LPUSH / RPUSH / LPOP / RPOP 为 O(1)；LINDEX / LSET / LINSERT 需定位，为 O(N)——「按下标读」在大列表上是危险操作。
  3. 阻塞命令：BLPOP / BRPOP 在列表为空时挂起客户端连接，把客户端按 key 排进等待队列；一旦别的客户端推入数据，立刻唤醒第一个等待者。这把「轮询」变成了「推送」，是简单队列的关键机制（设 timeout 0 表示无限等待）。
  4. 安全队列模式：LMOVE（旧 RPOPLPUSH/BRPOPLPUSH，已废弃） 弹出的同时塞回备份队列，消费者处理完再从备份队列删除——用「两队列」模拟 ack，防止消费者崩溃丢任务。

常用命令（必会子集）

命令 作用
LPUSH / RPUSH 左/右入队
LPOP / RPOP 左/右出队
LRANGE key start stop 闭区间下标范围（-1 表末尾）
LLEN 长度
LINDEX / LSET 按下标读 / 写
BLPOP / BRPOP 阻塞出队（简单队列常用）

说明：高版本提供 LMOVE / BLMOVE 等，用于安全队列迁移元素；与已废弃的 BRPOPLPUSH 同类需求可查当前版本文档。

典型应用场景

  1. FIFO 队列：RPUSH + LPOP（或反向一对）。
  2. 最新消息流：LPUSH + LTRIM key 0 99 保留最近 100 条。
  3. 阻塞消费：BLPOP 多个 key 时按顺序等待，可做简单任务队列（复杂语义建议 Stream 或专业消息中间件）。

综合案例（redis-cli）

注意事项

  1. 消费者崩溃：LPOP 后数据即丢，需业务确认机制或改用 BRPOP + 处理完再 ack` 等模式；严肃场景评估 Stream、RabbitMQ 等。
  2. 长列表：LRANGE 0 -1 大列表慎用；分页用 LRANGE 分段。
  3. 与 Set/ZSet 区别：List 有序可重复；Set 无序唯一；ZSet 有序唯一带分值。

本章小结

要点 结论
本质 双向序列：有序、可重复，两端 O(1)
底层 quicklist（双向链表 + listpack 压缩段）
高频命令 LPUSH/RPUSH、LPOP/RPOP、LRANGE、BLPOP
队列模式 FIFO、最新 N 条（LPUSH+LTRIM）、阻塞消费
边界 消费无 ack、按下标 O(N)；严肃队列用 Stream/MQ

第三章：Redis String 数据类型：概念、命令与案例

发表于 2026-05-03 更新于 2026-09-01 分类于 Redis 本文字数： 1.6k 阅读时长 ≈ 5 分钟

第三章：Redis String 数据类型：概念、命令与案例

概念基础

String 是 Redis 最基本的值类型——一个 key 对应一个字符串值：

  1. Redis 是 KV 模型：键（key） 永远是字符串；值（value） 可以是 String / Hash / List 等类型之一。
  2. 本文说的 String 指 value 的类型为 string（TYPE key 显示 string）。
  3. 二进制安全：值可以是任意字节序列——文本、JSON、序列化对象，甚至图片字节，不需要担心内容里出现特殊字符。
  4. 容量上限：单个 String 最大 512 MB，但业务上应把「大 value」视为反模式（见注意事项）。
  5. 编码：底层可能为 int、embstr、raw 等（OBJECT ENCODING key 可查看），对使用者多数时候透明，选型时更关心语义与命令（原理见下一节）。

核心原理：编码与底层结构

  1. SDS（简单动态字符串）：Redis 的字符串不是 C 语言以 \0 结尾的字符数组，而是自研的 SDS 结构——头部记录已用长度与剩余空间，因此 STRLEN 是 O(1)；追加时可预分配空间减少 realloc；内容可含 \0，这是「二进制安全」的基础。
  2. 三种编码与转换：
    • int：值是能放进 64 位有符号整数的数字（如 INCR 计数器），直接存整数，最省内存。
    • embstr：短字符串（≤ 44 字节），redisObject 与 SDS 一次性分配在一块连续内存，读多写少时最省且缓存友好；embstr 是只读的，一旦修改就转成 raw。
    • raw：长字符串（> 44 字节）或被修改过的短字符串，SDS 独立分配，支持高效追加。
  3. 观察方法：
  1. 原子性：命令单线程执行，INCR、SET key val NX 等都是原子操作——这就是「计数器」和「占位锁」不惧并发的根本原因，不需要应用层再包一层锁。

常用命令（必会子集）

1. 读写与删除

MSET / MGET：一次多键，减少往返（注意原子性与键命名规范）。

2. 带条件的写入与过期（业务高频）

SET 常用选项（Redis 2.6+ 语法，具体以你版本文档为准）：

选项 含义
EX 秒 / PX 毫秒 设置过期时间（TTL）
NX 仅当 key 不存在 时写入（常用于抢锁占位）
XX 仅当 key 已存在 时覆盖

3. 计数器：INCR / DECR / INCRBY

INCR 在值可解析为整数时原子自增；不存在时按 0 开始。

4. 其它实用命令

命令 作用
APPEND 尾部追加字节
STRLEN 返回字节长度
GETRANGE / SETRANGE 按偏移读写子串（仍整体是 String）
GETSET 读旧值并写新值（单原子操作，适合简单状态切换）

典型应用场景

  1. 缓存整页或对象：值存 JSON 字符串，配合 EX 做短期缓存；更新数据库后删键或覆盖避免脏读。
  2. 会话 / 登录态：SET … EX … 存 token → 用户信息；过期自动消失。
  3. 计数与限流：INCR 做浏览量、接口调用次数；与滑动窗口等逻辑配合（复杂限流可再引入 Hash / ZSet）。
  4. 分布式锁（谨慎）：SET key token NX PX ttl 仅占位；完整锁需唯一 token、Lua 校验身份释放、续期、Redlock 争议等专题，本文只给入门占位思路。
  5. 配置与功能开关：SET feature:x:enabled 1，读时 GET 转布尔。

综合案例（redis-cli 可直接敲）

以下默认本机 redis-cli 无密码；若启用了 requirepass，请加 -a <密码>（见 第二章：Docker 部署 Redis 实践）。

1. 用户信息缓存（带过期）

2. 文章阅读量

3. 简单「占位锁」（演示用，生产请用成熟方案）

4. 条件更新：仅存在时改

注意事项与选型

  1. 大 value：单 String 过大占用内存与网络带宽，序列化大对象可评估 Hash 分字段或拆 key。
  2. 热 key：同一 key 超高并发时，单线程处理该 key 易成瓶颈，需业务侧分片或换结构。
  3. KEY 命名：建议 业务:实体:id:属性> 一类可读前缀，避免全局 KEYS * 在生产使用（用 SCAN）。
  4. 持久化与丢失：String 在内存里，是否落盘取决于 RDB/AOF 与策略；缓存≠数据库，关键数据以库为准并设计降级。
  5. 字符集：Redis String 是字节；UTF-8 文本由客户端编码/解码，不要在服务端假设「一定是中文几个字符」与字节长度一一对应。

本章小结

要点 结论
本质 二进制安全的字节串，最大 512 MB
编码 int / embstr（≤44B，只读）/ raw，OBJECT ENCODING 可查
原子性 INCR / SET NX 单命令原子，天然抗并发
高频命令 SET(EX/PX/NX/XX) / GET / INCR / MSET / MGET
场景 缓存、会话、计数限流、占位锁、开关

第六章：PostgreSQL 并发与 MVCC 入门

发表于 2026-05-03 更新于 2026-09-01 分类于 PostgreSQL 本文字数： 1k 阅读时长 ≈ 3 分钟

第六章：PostgreSQL 并发与 MVCC 入门

概念基础

  1. 并发问题：多个事务同时读写同一批行时，会出现脏读、不可重复读、幻读与丢失更新；数据库必须给出确定性的答案——这就是隔离级别要解决的问题。
  2. MVCC（多版本并发控制）：每行保留多个版本，行头部的 xmin / xmax 记录创建与删除它的事务；读按快照判断可见性，做到读写互不阻塞。
  3. 隔离级别决定快照粒度：默认 READ COMMITTED 每条语句一个快照；REPEATABLE READ 整个事务一个快照；SERIALIZABLE 进一步检测读写冲突，冲突时需应用重试。
  4. MVCC 不是免费的：旧版本（死元组）要靠 VACUUM 回收；「先读后改」的临界区仍需显式行锁（FOR UPDATE），并发抢任务用 SKIP LOCKED。

快照读（概念）



flowchart LR
  T1[事务 T1 xid=100] --> Snap[可见 xmin xmax]
  Snap --> Row1[行版本 v1]
  Snap --> Row2[行版本 v2 对 T1 不可见]

一、快照与默认隔离级别

  • 默认 READ COMMITTED：单条 SQL 内看到语句开始时已提交的数据版本。
  • REPEATABLE READ：事务内首条 SQL 建立快照，后续读一致。
  • SERIALIZABLE：可检测读写依赖，失败时返回 40001 serialization_failure，应用应重试。

二、显式行锁：FOR UPDATE / FOR SHARE

  • FOR UPDATE：排他行锁，用于「先读后改」的临界区。
  • FOR SHARE：共享行锁，允许他人并发读，阻塞写。

三、SKIP LOCKED 与 NOWAIT（队列与抢锁）

SKIP LOCKED：跳过已被其他事务锁定的行，取下一批可用行——常用于任务队列、公平抢单。

NOWAIT：若不能立即加锁则立刻报错，适合避免长时间等待（由应用捕获错误后重试或放弃）。

四、死锁（deadlock detected）

PostgreSQL 会自动检测事务间循环等待，回滚其中一个事务（报错 40P01 deadlock_detected）。
规避思路与 MySQL 类似：固定加锁顺序、缩短事务、避免无关长耗时在事务内执行。

默认隔离 常为 RR RC
幻读与范围锁 间隙锁 / Next-Key 叙述多 SSI / 谓词锁 等在 SERIALIZABLE 下讨论多
队列抢任务 FOR UPDATE + 设计索引 FOR UPDATE SKIP LOCKED 一等公民

第五章：PostgreSQL 索引与性能优化

发表于 2026-05-03 更新于 2026-09-01 分类于 PostgreSQL 本文字数： 1.4k 阅读时长 ≈ 5 分钟

第五章：PostgreSQL 索引与性能优化

概念基础

  1. 索引 = 用空间换时间的检索结构：默认 B-Tree 以平衡树组织键值，把等值 / 范围查询从全表扫描降为树查找；代价是占存储、拖慢写入。
  2. 慢的常见根源：大表 Seq Scan、统计信息过期导致选错计划、死元组堆积（表膨胀）、函数包裹列让索引失效。
  3. 优化是闭环不是玄学：慢日志 / pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) 看真实计划 → 改索引或改写法 → VACUUM ANALYZE 更新统计再验证。
  4. 性能之外还有「稳」：事务隔离级别选型、VACUUM/autovacuum 运维、备份恢复（pg_dump / PITR） 演练，都是可靠性的一部分。

先建立对默认索引的直觉：

一、索引在干什么：B-Tree 直觉（默认）

PostgreSQL 默认 CREATE INDEX 多为 B-Tree（USING btree，可省略）。
直觉与 MySQL InnoDB 二级索引类似：以平衡树组织键，等值 / 范围查询减少随机读；主键 / 唯一约束底层也会建索引。

其他索引类型（点到为止）：GIN（全文、jsonb 含键）、GiST（地理、范围类型）、BRIN（超大顺序相关表）等，选型需读官方文档与压测。

二、联合索引与最左前缀

联合索引 CREATE INDEX idx_abc ON t (a, b, c); 的排序语义仍是先 a 再 b 再 c。
WHERE a = ? AND b = ? 易命中；仅 WHERE b = ? 往往用不上该索引（与 MySQL 同款直觉）。
函数包裹列（如 WHERE lower(email) = ?）常导致无法走 btree，需表达式索引（CREATE INDEX ON t ((lower(email)))）或改写法。

三、仅索引扫描（Index Only Scan）

若查询列均可由某索引覆盖，且可见性映射（VM）允许优化器认为堆页全可见，EXPLAIN 可能出现 Index Only Scan。
与 MySQL 的 Using index 类似但不等价；仍以 EXPLAIN (ANALYZE, BUFFERS) 实测为准。

四、怎么看执行计划：EXPLAIN / EXPLAIN ANALYZE

入门优先看：

字段 / 标记 含义（入门）
Seq Scan 顺序扫表，大表 + 高 rows 要警惕
Index Scan / Index Only Scan 走索引访问
Nested Loop / Hash Join / Merge Join 连接策略
ANALYZE 的 actual time、rows 真实耗时与行数（与统计信息、缓存有关）
BUFFERS 读了多少共享缓冲区（判断是否 I/O 重）

统计信息维护：ANALYZE tbl;（VACUUM ANALYZE 亦可），大变更后应跑。

五、事务与隔离级别（用法向）

1. 基本写法

默认 READ COMMITTED：每条语句看到语句开始时已提交的快照（简化理解）。
REPEATABLE READ：事务内第一条语句建立快照，读一致性更强。
SERIALIZABLE：最强，可能出现 serialization_failure，应用需重试。

与 MySQL InnoDB 默认 RR 不同：PostgreSQL 默认 RC；跨库迁移时注意语义差异。行级锁、FOR UPDATE、死锁见 第六章：PostgreSQL 并发与 MVCC 入门。

六、慢语句与观测「三板斧」（点到为止）

1. 日志：log_min_duration_statement

在 postgresql.conf 或 ALTER SYSTEM（需 reload）中设置，例如记录超过 200ms 的语句（数值按环境调）。

2. pg_stat_statements（扩展）

需 shared_preload_libraries 预加载（运维配置），此处不展开。

3. auto_explain（扩展）

自动对超时语句打计划，适合测试环境；生产按规范启用。

落地顺序：先慢日志或 pg_stat_statements 抓 Top SQL → EXPLAIN (ANALYZE, BUFFERS) → 改索引或改写法 → VACUUM ANALYZE。

七、VACUUM 与膨胀（可靠性常识）

PostgreSQL 的 MVCC 会使更新/删除留下死元组；VACUUM（通常由 autovacuum 自动跑）回收空间、更新统计信息。长期不 vacuum 会导致表膨胀、性能变差。
日常开发：大批量导入/更新后，测试库可手动 VACUUM ANALYZE；生产依赖 autovacuum 参数与监控。

八、备份恢复与 PITR 概念

1. 逻辑备份 pg_dump / pg_restore

-Fc 为自定义目录格式，便于并行恢复；纯 SQL 可用 -Fp。

2. 物理与 WAL

PITR 依赖：基础备份（文件系统级或 pg_basebackup）+ 连续归档的 WAL + 恢复目标时间。与 MySQL binlog 地位类似的是 PostgreSQL WAL；具体恢复命令属 DBA 手册级。

3. 与 Docker 的关系

容器内 $PGDATA 一般在卷上（见 第二章：Docker 部署 PostgreSQL 实践）；备份策略要约定「从宿主机 pg_dump 连容器端口」还是「卷快照 + WAL 归档」，并做恢复演练。

第三章：PostgreSQL 存储引擎与表访问方法

发表于 2026-05-03 更新于 2026-09-01 分类于 PostgreSQL 本文字数： 1k 阅读时长 ≈ 3 分钟

第三章：PostgreSQL 存储引擎与表访问方法

概念基础

  1. 表访问方法（Table Access Method）：PostgreSQL 12+ 把「表数据如何组织与读写」抽象为可插拔接口，建表时可用 USING 指定，默认即 heap——这是 PostgreSQL 语境里最接近 MySQL「引擎」的概念。
  2. 堆表（Heap）：行按写入顺序无序堆放在页中，用 tid（块号 + 行号） 定位；索引里存的是 tid，查数据通常要「索引 → 回表」。
  3. MVCC 是配套设计：行头维护 xmin / xmax 版本信息，更新与删除产生新版本 / 死元组，由 VACUUM 回收——这直接决定了 PostgreSQL 的性能调优姿势。
  4. 与 MySQL 的本质差别：MySQL 建表时选 ENGINE=InnoDB，PostgreSQL 没有这个开关：统一内核 + 统一 heap，列存、分片等需求走扩展与架构层，而不是换「引擎」。

先看默认的存储方式：

一、表数据默认怎么存：Heap（堆表）

  • 普通 CREATE TABLE 默认即 heap 表：行以堆页存放，通过 tid（块号 + 行号） 定位。
  • MVCC 在元组头维护版本信息（xmin / xmax 等），更新与删除产生新版本/死元组，依赖 VACUUM 回收（见 第五章：PostgreSQL 索引与性能优化）。
  • 与 InnoDB 聚簇索引即整表不同：PostgreSQL 主键索引是二级索引，堆上存行，主键查找通常「索引 → 回表 tid」。

二、表访问方法（Table Access Method）

PostgreSQL 12+ 起，表可指定 USING heap（默认）；理论上可挂自定义表访问方法（需扩展提供）。
生产常见仍是 heap；列存、混存等多在扩展或外部产品（如某些分析型方案）中实现，不等价于 MySQL 换一个 ENGINE 字符串。

三、与「引擎」易混的几个概念

概念 说明
TABLESPACE 表/索引的文件放置位置（如 pg_default），不是另一种行存储引擎。
TOAST 大字段行外存储机制，对用户基本透明。
Foreign Data Wrapper（FDW） 外部表：数据在远程；语法像本地表，语义与本地 heap 完全不同，不是换存储引擎。
内置索引类型 B-Tree、Hash、GiST、GIN、BRIN 等是索引访问方法，不是替换 heap 的「表引擎」。

四、和 MySQL InnoDB 的粗对照（选型沟通用）

话题 MySQL（MySQL引擎.md） PostgreSQL（本文）
建表选「引擎」 ENGINE=InnoDB 等 无；默认 heap + 统一内核
行存与主键 InnoDB 聚簇主键与数据同树 堆行 + 主键索引
并发读写的核心 InnoDB MVCC + 锁 MVCC + 行锁（见 第六章：PostgreSQL 并发与 MVCC 入门）

五、实务建议

  1. 学习 PostgreSQL 时少问「用哪个引擎」，多问索引类型、执行计划、VACUUM、隔离级别与锁。
  2. 需要列存、分片、多副本高可用时，在架构层选专用扩展或产品（如 Citus、云厂商数仓、读写分离），而不是在 CREATE TABLE 里找一个 ENGINE 开关。
  3. 版本升级（14 → 16 → 17）会带执行器与优化器演进，「升级引擎」口语上常指升级主版本，与 MySQL 的 ENGINE 不是同一概念。

第六章：MySQL 存储引擎

发表于 2026-05-03 更新于 2026-09-01 分类于 MySQL 本文字数： 1.1k 阅读时长 ≈ 4 分钟

第六章：MySQL 存储引擎

概念基础

存储引擎是 MySQL 「表数据如何存、如何取」的可插拔实现：

  1. 分层架构的产物：Server 层负责 SQL 解析、优化、权限；引擎层负责数据在磁盘与内存上的组织——索引结构、事务、锁、崩溃恢复都由引擎决定；同一份表结构，换引擎行为完全不同。
  2. InnoDB 是唯一默认答案：支持 ACID 事务、行级锁、MVCC、崩溃恢复（redo / undo）、聚簇索引与外键；官方默认且推荐，第五章讲的 B+ 树与回表，说的就是 InnoDB 的组织方式。
  3. MyISAM 是历史遗产：表级锁、不支持事务、崩溃安全性弱，只存在于老系统与只读库中；新业务一律避开——它也解释了第三章「表锁并发差」的历史背景。
  4. 换引擎不解决性能问题：性能瓶颈优先从索引、SQL 写法、事务与连接设计入手（第三、四、五章的内容）；引擎选型是「事务要不要」的问题，不是「快不快」的问题。
  5. 插件式带来专用选择：ARCHIVE（冷归档压缩）、CSV（数据管道交换）、BLACKHOLE（写入即弃的中继）、NDB（分布式集群）各有专属场景，是否可用以 SHOW ENGINES 为准。

先看怎么查看与确认当前引擎：

一、如何查看支持的引擎与默认值

建表未写 ENGINE 时使用 default_storage_engine（一般为 InnoDB）。

二、InnoDB（事实上的唯一首选）

维度 说明
事务 ACID；COMMIT / ROLLBACK、崩溃恢复（redo / undo）。
锁与并发 以行锁为主；隔离级别与间隙锁等见 MySQL锁详解.md。
索引与数据 聚簇索引即主键 B+ 树，二级索引叶子存主键；详见 MySQL索引与性能优化.md。
外键 支持 FOREIGN KEY（与 MySQL.md 中 DDL 一致）。
适用 OLTP、绝大多数业务库；官方默认与推荐。

三、MyISAM（ legacy，新业务避免）

维度 说明
事务 不支持事务与崩溃安全意义上的 InnoDB 同级别恢复。
锁 表级锁，写多读少场景易成为瓶颈。
索引 数据与索引布局与 InnoDB 不同；无聚簇主键同义实现。
典型遗留场景 老系统、只读库、部分空间索引历史用法；新表请勿选用。

四、MEMORY（内存表，谨慎）

  • 数据驻内存，进程崩溃或重启后易失；容量受 max_heap_table_size 等限制。
  • 曾用于临时高速缓存；现代实践更常见 Redis 或 InnoDB + 足够内存 + 合理索引。

五、其它引擎（知道名字即可）

引擎 一句话
ARCHIVE 高压缩追加存储，适合冷归档、很少更新。
CSV 以 CSV 形式存文件，多用于导入导出管道，非通用 OLTP。
BLACKHOLE 写入即丢弃，有时用于复制拓扑中的「中继」等特殊场景。
NDB（MySQL Cluster） 分布式集群专用，与普通单机 InnoDB 运维模型不同。

具体是否编译进你的 mysqld，以 SHOW ENGINES 为准。

六、选型与迁移建议

  1. 新表一律 ENGINE=InnoDB，并显式 DEFAULT CHARSET=utf8mb4（与 MySQL.md 一致）。
  2. 发现 MyISAM 老表：评估后 ALTER TABLE … ENGINE=InnoDB（需在低峰窗口做；大表走 gh-ost / pt-online-schema-change 等在线 DDL 工具，属运维专题）。
  3. 不要用 ENGINE 解决「性能问题」：优先索引、SQL、连接与事务设计。

第五章：MySQL 索引与性能优化

发表于 2026-05-03 更新于 2026-09-01 分类于 MySQL 本文字数： 2.4k 阅读时长 ≈ 8 分钟

第五章：MySQL 索引与性能优化

概念基础

索引是数据库用额外空间与写成本换取查询速度的有序数据结构：

  1. 本质是一棵 B+ 树：把无序的表数据额外组织成有序树，查询从「全表逐行扫」变成「沿树下降读少量页」——随机 I/O 大幅减少；代价是每次 INSERT/UPDATE/DELETE 都要同步维护树，所以索引不是越多越好。
  2. 聚簇索引即数据本身：InnoDB 表数据按主键组织成 B+ 树，叶子节点存「主键 + 整行」；二级索引叶子只存「索引列 + 主键」，命中后常需回表再查一次聚簇索引——这就是主键要自增、查询要少 SELECT * 的根因。
  3. 联合索引遵守最左前缀：(a, b, c) 先按 a 排、a 相同再按 b、再按 c；跳过 a 的条件用不上树，等值列在前、范围列在后是最常见的设计。
  4. 覆盖索引是回表的解药：查询列全在索引里就只扫索引不回表（EXPLAIN 显示 Using index）；与之配套的 ICP 把过滤条件下推到引擎层，进一步少回表。
  5. 优化是一个闭环而非玄学：慢日志抓 Top SQL → EXPLAIN 看 type / key / rows / Extra → 改索引或改写法 → 再对比慢日志；本章同时覆盖事务隔离与备份恢复，给出完整的「开发侧性能地图」。

从 B+ 树的直觉开始：

一、索引在干什么：B+ 树直觉（够用版）

InnoDB 里，表数据按主键组织成一棵 B+ 树（聚簇索引）：叶子节点存「主键 + 整行数据」。
二级索引（你建的 INDEX / UNIQUE）叶子节点存「索引列 + 主键」，需要整行时往往要再回表到聚簇索引取数据。

下图便于建立直觉（示意：键值与层数为教学简化，与真实页大小、填充率无关）。

读图要点：上层结点只存分界键与子树指针；最底层叶子由双向链表串起，方便范围扫描；聚簇索引叶子是主键 + 行数据；二级索引叶子多一步按主键回表读完整行。

直觉：

  • 等值 / 范围命中索引列 → 树高度低、少读页 → 随机 I/O 变少。
  • 全表扫 → 叶子链顺序读，数据量一大就慢。
  • 索引不是越多越好：每次 INSERT/UPDATE/DELETE 都可能维护多棵索引树。

二、联合索引与最左前缀

联合索引 KEY idx_abc (a, b, c) 的排序语义是：先按 a，再 a 相同时按 b，再按 c。

能较好利用该索引的典型条件（示意）：

  • WHERE a = ?
  • WHERE a = ? AND b = ?
  • WHERE a = ? AND b BETWEEN ? AND ?

容易用不上或只用一截的情况：

  • WHERE b = ? AND c = ?（缺 a，与「最左」不一致）
  • WHERE a = ? OR d = ?（OR 另一侧常走另一条路径，易优化成 UNION 或改写法）
  • 对 a 做函数/隐式类型转换导致无法走树（例如 WHERE DATE(a_col) = ...）。

设计经验：把区分度高、过滤性大的列尽量放左侧；把范围查询列放联合索引右侧更常见（仍要结合 EXPLAIN 验证）。

三、覆盖索引（Using index）

若 SELECT 里出现的列都能从某条二级索引的叶子直接凑齐（含 WHERE 用到的索引列），InnoDB 可能只扫索引、不回表，EXPLAIN 的 Extra 常见 Using index。

典型收益：大宽表上只查少数列 + 条件列恰好在同一联合索引上，I/O 明显下降。

四、索引条件下推 ICP（一眼带过）

Index Condition Pushdown：把部分 WHERE 条件下推到存储引擎层，在索引扫描过程中就过滤，少回表。
在 EXPLAIN 里常见 Using index condition（与 Using index 不同：后者多为覆盖索引）。不必一次讲透优化器细节，看到术语知道「在索引层多干了一点过滤」即可。

2. 建议优先盯的列（入门够用）

列 / 信息 大致含义（入门）
type 访问类型，从差到好常见：ALL（全表扫）→ index（扫整棵二级索引树）→ range → ref → eq_ref → const。出现 ALL 且行很大时要警惕。

八、备份恢复与 PITR 概念

1. 逻辑备份（mysqldump）

  • --single-transaction：InnoDB 下用一致性读做导出，尽量避免 FLUSH TABLES WITH READ LOCK 式全库只读（与全局锁备份对比，见 MySQL锁详解.md 中「全局锁 + mysqldump --single-transaction」相关说明）。
  • 恢复：mysql -uroot -p < backup.sql（注意字符集与目标实例版本）。

2. 物理备份与快照

对大数据量，常用物理热备（厂商工具或存储快照）+ binlog；与 Docker 场景结合时，数据在卷上，备份策略要在「卷快照 / 容器外 mysqldump」之间选一种或组合，并做恢复演练（参见 MySQL-Docker.md 中数据卷与持久化思路）。

3. PITR（Point-in-Time Recovery，按时间点恢复）

含义：不只恢复到「昨晚整库备份」，而是恢复到某事故前一秒。通常需要：

  1. 周期全量 / 增量（逻辑或物理）；
  2. 连续归档的 binlog（log_bin 打开，并安全保存 binlog 文件）；
  3. 恢复时：先还原备份到某一时刻，再重放 binlog 到目标时间点（具体命令与工具因版本与平台而异，属 DBA 操作手册级）。

可靠性＝备份自动化 + 定期恢复演练 + binlog 留存策略；开发至少要懂「为什么不能只靠一台机子从不备份」。
