1. 概念说明

分布式系统是把一个系统拆成多个独立部署、通过网络协作的节点。带来的核心矛盾：网络不可靠 + 节点会失败。

CAP 定理：分布式系统无法同时保证一致性（C）、可用性（A）、分区容错性（P），网络分区必然发生（P 必选），只能在 C 和 A 之间取舍。

BASE 理论（AP 系统的落地指导）：

  • Basically Available：基本可用（降级、限流）
  • Soft State：软状态（允许中间态）
  • Eventually Consistent：最终一致

分布式系统三大基础设施问题：分布式锁（多节点互斥）、分布式 ID（全局唯一）、分布式事务（跨库一致性）。

9. 典型案例：秒杀下单的分布式 ID 与分布式锁

9.1 问题背景

秒杀下单有两个硬需求：

  1. 订单号全局唯一且趋势递增：分库分表后数据库自增主键会撞号，无序 UUID 会导致 InnoDB 聚簇索引页分裂，需要本地高性能发号器；
  2. 多实例互斥扣库存：订单服务部署多个实例同时扣同一 SKU，JVM 本地锁完全失效，需要分布式锁互斥，且不能因持锁节点宕机造成死锁。

9.2 Snowflake 雪花算法（含时钟回拨处理）

ID 结构：1 bit 符号 + 41 bit 毫秒时间戳 + 10 bit 机器位 + 12 bit 序列，单个节点每毫秒可发 4096 个号。

workerId 不能手工硬编码（多实例必然冲突），应在启动时用「IP 哈希 + 端口」或向协调组件（Nacos / 数据库号段表）申请。

9.3 Redis 分布式锁：SET NX PX + owner 校验 + Lua 释放

看门狗续期思路：固定 30s TTL 下，业务一旦执行超过 30s 锁就会提前失效。生产做法（Redisson 已内置）是加锁后启动后台调度，每 10s 检查”当前线程仍持锁且业务未结束”，就把 TTL 续回 30s；业务执行完立即停止续期并主动释放；持锁节点宕机时调度随进程消失，锁到期自动释放——既不误删又不死锁。

9.4 CAP 取舍

选择点 AP 取向 CP 取向
注册中心 Nacos/Eureka：分区时仍可发现服务（可能拿到脏实例，靠超时重试剔除） ZK/etcd：分区时少数派不可注册发现，保证视图一致
分布式锁 Redis：性能高，但主从异步复制下极端 failover 可能两人同时持锁 ZK/etcd（Raft/ZAB 多数派）或 Redlock：互斥更严格，代价是延迟
发号器 Snowflake：本地发号无网络依赖，时钟问题需自行防护 数据库号段：严格可控，但发号组件宕机即不可用

本案例秒杀业务选 AP：Redis 锁 + Snowflake 本地发号换取万级 TPS；极低概率的锁失效用「库存条件扣减 + 订单号唯一索引」兜底，不会出现超卖。资金账户等强约束场景则倒向 CP（Seata/TCC，见分布式事务篇）。

9.5 踩坑点

  • 释放锁只 DEL 不校验 owner：A 超时后 B 拿到锁，A 执行完把 B 的锁删掉，第三个请求乘虚而入——必须 UUID + Lua 比对删除。
  • 加锁不设过期时间：持锁节点 OOM 宕机后锁永久存在，该 SKU 再也无法下单——必须带 NX PX。
  • TTL 固定且无续期：GC 停顿 / 慢 SQL 导致业务没做完锁先过期——看门狗续期 + 业务幂等双保险。
  • workerId 配置冲突：两个实例同机号同毫秒发号，ID 重复——启动时自动协调分配机号。
  • 锁粒度过粗：用 lock:stock 全局一把锁，所有 SKU 被串成一队——按 skuId 拆键。

10. 常见误用与陷阱

坑 现象/后果 解法
释放锁只 DEL 不校验 owner 锁超时后误删他人锁，互斥失效、并发超卖 value 存 UUID owner，Lua 原子「比对 + 删除」
锁超时但业务未执行完 第二人拿到锁，同一业务被并发执行 看门狗定时续期；业务本身做幂等与条件更新
Snowflake 时钟回拨 生成重复或倒退 ID，主键冲突、索引乱序 小回拨等待追平、大回拨拒发告警；NTP 禁止大步回拨
误把主从复制当 Quorum 以为写主即多数确认，主宕机 failover 后丢数据 严格多数派写（W > N/2，ZK/etcd）；Redis 异步复制需业务兜底
把最终一致当强一致 下单后立刻查余额显示未扣，引发客诉与资损误判 接口/UI 显式「处理中」状态，配对账补偿；资金类上 TCC/AT
脑裂后双主写入 网络分区出现两个主，各自写入数据冲突 多数派选举，少数派拒写（Raft/ZAB）；Redis 配 min-replicas-to-write
锁不可重入 同一线程二次加锁把自己阻塞，形成死锁 用 Hash 记录线程重入次数（Redisson），或重构消除重入
Redis 主从切换瞬间丢锁 主未同步锁键即宕机，新主上他人获锁 强互斥选 CP 协调系统或 Redlock，并以数据库唯一约束兜底

1. 概念说明

设计模式（Design Pattern）是软件设计中经过验证的、可复用的解决方案模板，解决特定场景下的重复问题。它不是代码库，而是一套”经验公式”。

为什么要学：不是所有代码都需要模式，但理解模式能让你：

  1. 用准确词汇描述设计（沟通成本低）
  2. 复用成熟方案，避免重复造轮子
  3. 看懂主流框架（Spring、Netty、JDK 大量使用模式）

1. 概念说明

**领域驱动设计（DDD, Domain-Driven Design）**是一套应对复杂业务的方法论，核心思想：让软件模型与业务语言保持一致。业务专家和开发用同一种语言（通用语言）沟通，软件结构围绕领域模型而非技术框架设计。

DDD 解决什么问题：业务逻辑复杂时，按”数据库表/技术分层”组织代码会导致业务规则散落各处、改一处坏一片。DDD 把业务规则收敛到领域层，让代码可读、可维护、可演进。

两大阶段：

  • 战略设计：先划清业务边界（限界上下文），确定系统间的协作方式。
  • 战术设计：在边界内设计聚合、实体、值对象、领域服务、仓储等模型要素。

7. 常见误区（避坑）

把 DDD 当技术框架 DDD 是设计方法，不绑定任何框架

9. 典型案例：聚合边界划分实战

问题背景：电商团队最初把「订单 + 库存 + 物流」塞进一个巨型 Order 聚合：下单时一次事务改三张主表，秒杀期间数据库行锁冲突频发；改一个收货地址也要加载全部商品明细。需要重新划分聚合边界。

方案：按「是否必须在同一事务内保持一致」重新切分——聚合间用领域事件解耦：

聚合 职责 一致性 事件
Order 订单项、金额、状态机 聚合内强一致 OrderCreated / OrderCancelled
Inventory 库存数量、占用/释放 聚合内强一致 StockDeducted / StockInsufficient
Shipment 发货单、物流轨迹 聚合内强一致 ShipmentCreated

关键设计：

踩坑点：第一次拆分时把「扣库存」放进了 Order.cancel() 的事务里同步调用库存服务——网络抖动导致订单取消频繁失败。正确姿势是事件驱动：订单先落库，库存消费事件异步释放，失败重投 + 对账兜底。另外注意事件不要携带整个聚合快照，只带 ID 和最小字段，否则消费方会把事件当成 RPC 响应来用，边界又糊了。

类别 选型 用途

1. 概念说明

**并发（Concurrency）**指多个任务在时间上交替执行（宏观并行、微观串行），**并行（Parallelism）**指多个任务真正同时执行（多核）。并发解决的是”多任务协同”，并行解决的是”更快”。

三个层次：

  • 进程（Process）：操作系统资源分配单位，内存隔离，切换开销大。
  • 线程（Thread）：进程内执行单位，共享进程内存，切换开销较小。
  • 协程（Coroutine）：用户态调度，栈极小，可创建十万级（Java 虚拟线程、Go goroutine、Python async）。

核心问题：多个线程同时读写共享变量会产生竞态条件（Race Condition），导致结果不确定。解决方案：互斥（锁）、原子操作、不可变对象、线程本地存储。

1. 概念说明

CI/CD 是”自动化交付”的三种实践的合称：

  • 持续集成（CI, Continuous Integration）：每次代码提交都自动触发构建 + 测试，尽早发现集成问题。核心是”频繁合并、快速反馈”。
  • 持续交付（CD, Continuous Delivery）：CI 通过后自动把产物（镜像/包）准备好，处于”随时可发布”状态。
  • 持续部署（Continuous Deployment）：产物自动部署到生产环境，全流程无人干预。

**流水线（Pipeline）**是这些阶段的编排：提交代码 → 安装依赖 → Lint → 单元测试 → 构建镜像 → 推送制品 → 部署。**质量门禁（Quality Gate）**指某一步失败即中断流水线，保证坏代码无法进入下一步。

1. 概念说明

区块链是一个去中心化的分布式账本：数据被打包成区块，通过哈希指针串联成链，由全网节点共同维护，靠共识机制（如 PoS）保证一致，具有不可篡改、公开透明、去信任三大特性。

核心概念：

  • 区块（Block）：包含交易列表、时间戳、前一区块哈希。
  • 哈希（Hash）：SHA-256 等单向函数，内容一变哈希全变，是防篡改的基础。
  • 共识机制：PoW（工作量证明）/ PoS（权益证明），决定谁来打包新区块。
  • 钱包地址：由私钥推导出的公钥哈希，私钥即资产控制权，绝不能泄露。
  • Gas：执行交易的燃料费，单位 gwei（1 ETH = 10⁹ gwei）。
  • 智能合约：运行在链上的程序，部署后地址固定、逻辑不可更改，人人可调用。

10. 典型案例：重入攻击与修复全流程

问题背景：一个「存款/提款」合约上线后被攻击者把金库搬空。代码看起来毫无破绽——余额校验、转账、清零一个不少，资金却没了。这就是重入（Reentrancy）。

方案：先写攻击合约复现漏洞，再用「检查-生效-交互」（CEI）+ ReentrancyGuard 双保险修复，最后把攻击用例改造成回归测试。

踩坑点：

  • Solidity 0.8 修的是整数溢出，不防重入——两类问题别混为一谈。
  • ERC-20/721 的回调（onERC721Received、transfer hook）同样能重入，不只 call 转账这一处。
  • 修复后必须把攻击用例改成回归测试跑绿，不能”改完就上线”。
  • 审计前先跑 Slither 静态扫描，重入这类模式化漏洞机器就能揪出来。

11. 常见误用与陷阱

坑 现象/后果 解法
以为 0.8 编译器万事大吉 溢出防了，重入、权限失控照样亏钱 重入用 CEI + ReentrancyGuard，权限用多签
owner 单私钥一把梭 私钥泄露 = 合约资金全没，且无法追回 Ownable 换多签（Safe）+ Timelock 延时执行
滥用 unchecked 绕过溢出检查 边界值下计数器回绕，账目错乱 unchecked 只用于数学上确定不会溢出的循环计数

1. 概念说明

数字音频是把连续声波采样成离散数字序列。三个核心参数：

  • 采样率（Sample Rate）：每秒采样的次数，单位 Hz。CD 为 44100 Hz，视频通用 48000 Hz。采样率决定可还原的最高频率（奈奎斯特定理：最高频率 = 采样率/2）。
  • 位深（Bit Depth）：每次采样用多少 bit 表示振幅，16 bit（CD）、24 bit（录音室）。位深决定动态范围。
  • 声道（Channels）：单声道（mono）、双声道（stereo）或多声道（5.1）。

常见格式：WAV（无损 PCM）、MP3 / AAC（有损压缩）、FLAC（无损压缩）、M4A / OGG。

核心处理手段：转码（格式/码率转换）、剪辑（截取/拼接）、音量调整（增益/归一化）、降噪（滤波）、提取（音视频分离）、混音（多轨叠加）。

9. 典型案例：播客上架流水线（响度标准化 → 去静音 → 切章）

问题背景：编辑部每周收到 20+ 期播客音频，音量忽大忽小、片头片尾静音几十秒，人工整理一期要半小时；上架平台还常被打回”响度不达标”。

方案：批处理流水线一次搞定——两遍 loudnorm 标准化到 -16 LUFS（播客主流标准）→ 检测并切除首尾静音 → 按静音点合并切片成章节 → 输出 m4a 并回写元数据，全部脚本化并行执行。

踩坑点：

  • 单遍 loudnorm 是动态压缩，语音有”呼吸感”失真——两遍测量 + linear=true 才是正解。
  • split_on_silence 的 silence_thresh 要按素材实测响度调整，标准化后用 -40dBFS 才稳。
  • librosa/pydub 读 mp3 底层依赖 ffmpeg，服务器必须先装，否则报 CouldntDecodeError。
  • pydub 全量载入内存，2 小时节目先确认内存余量，超长素材改用 ffmpeg 流式处理。

10. 常见误用与陷阱

坑 现象/后果 解法
峰值归一化当响度标准化 峰值一致但响度差 6dB，平台判定不达标 用 loudnorm（EBU R128 / LUFS）：播客 -16、流媒体 -14
单遍 loudnorm 直出 语音动态被压，忽强忽弱有”呼吸感” 两遍测量 + linear=true 精确修正
重采样只改采样率标签 变速变调，音频时长错乱 用 -ar 重采样（ffmpeg 内部做 SRC），禁止手工改文件头
pydub 处理超长文件 OOM 或进程被 kill 长素材用 ffmpeg 流式处理，pydub 只切短段
