1. 概念说明

Git 是分布式版本控制系统：每个开发者的本地都是完整仓库，无需联网即可提交、回滚、分支。核心模型是快照 + 引用：

  • 工作区（Working Directory）：你编辑的文件。
  • 暂存区（Staging Area / Index）：git add 后的待提交内容。
  • 本地仓库（Repository）：git commit 后永久保存的快照。
  • 远程仓库（Remote）：如 GitHub，用于多人同步。

三个对象的本质：

对象 说明
Commit 一次提交的快照，含作者、时间、父提交哈希
Branch 指向某个 Commit 的可移动指针
HEAD 当前所在分支/提交的指针

单人 Git 只需 commit/branch；团队 Git 的核心是：分支模型（何时建分支）+ 评审流程（代码如何合入）+ 规范（提交/分支命名）+ 保护（主分支防破坏）。

团队协作核心原则：

  • main/master 永远可部署（合入即通过 CI）。
  • 每个功能一个分支，生命周期短（1-2 天）。
  • 代码必须经过 Review 才能合入。
  • 提交信息清晰可追溯（关联 issue 编号）。

12. 保护分支与 CI 联动

13. 发布分支与热修规范

发布分支（release/*）：功能冻结后从 develop 切出，只接受 bug 修复，不再合入新功能；验证通过后合入 main 并打 tag，同时回合到 develop，避免修复丢失。

热修分支（hotfix/*）：线上故障从 main（生产基线）切出，修完经 PR 合入 main 并立即发布补丁版本，再回合 develop。

约定：

  • 主线以外分支只做一件事，release/* 不掺新功能，hotfix/* 不掺重构。
  • 发布前确认 tag 与变更记录（CHANGELOG）一致。
  • 紧急修复也必须走 hotfix/* + PR，保护分支的意义就是不给你”就这一次”的例外。

踩坑点：

踩坑点：

9. 典型案例：秒杀下单的分布式 ID 与分布式锁

9.1 问题背景

秒杀下单有两个硬需求：

  1. 订单号全局唯一且趋势递增：分库分表后数据库自增主键会撞号，无序 UUID 会导致 InnoDB 聚簇索引页分裂，需要本地高性能发号器；
  2. 多实例互斥扣库存：订单服务部署多个实例同时扣同一 SKU，JVM 本地锁完全失效，需要分布式锁互斥，且不能因持锁节点宕机造成死锁。

9.2 Snowflake 雪花算法（含时钟回拨处理）

ID 结构：1 bit 符号 + 41 bit 毫秒时间戳 + 10 bit 机器位 + 12 bit 序列，单个节点每毫秒可发 4096 个号。

workerId 不能手工硬编码（多实例必然冲突），应在启动时用「IP 哈希 + 端口」或向协调组件（Nacos / 数据库号段表）申请。

9.3 Redis 分布式锁：SET NX PX + owner 校验 + Lua 释放

看门狗续期思路：固定 30s TTL 下，业务一旦执行超过 30s 锁就会提前失效。生产做法（Redisson 已内置）是加锁后启动后台调度，每 10s 检查”当前线程仍持锁且业务未结束”，就把 TTL 续回 30s；业务执行完立即停止续期并主动释放；持锁节点宕机时调度随进程消失，锁到期自动释放——既不误删又不死锁。

9.4 CAP 取舍

选择点 AP 取向 CP 取向
注册中心 Nacos/Eureka：分区时仍可发现服务（可能拿到脏实例，靠超时重试剔除） ZK/etcd：分区时少数派不可注册发现，保证视图一致

9.5 踩坑点

  • 释放锁只 DEL 不校验 owner：A 超时后 B 拿到锁，A 执行完把 B 的锁删掉，第三个请求乘虚而入——必须 UUID + Lua 比对删除。
  • 加锁不设过期时间：持锁节点 OOM 宕机后锁永久存在，该 SKU 再也无法下单——必须带 NX PX。
  • TTL 固定且无续期：GC 停顿 / 慢 SQL 导致业务没做完锁先过期——看门狗续期 + 业务幂等双保险。
  • workerId 配置冲突：两个实例同机号同毫秒发号，ID 重复——启动时自动协调分配机号。
  • 锁粒度过粗：用 lock:stock 全局一把锁，所有 SKU 被串成一队——按 skuId 拆键。

1. 概念说明

**领域驱动设计（DDD, Domain-Driven Design）**是一套应对复杂业务的方法论，核心思想：让软件模型与业务语言保持一致。业务专家和开发用同一种语言（通用语言）沟通，软件结构围绕领域模型而非技术框架设计。

DDD 解决什么问题：业务逻辑复杂时，按”数据库表/技术分层”组织代码会导致业务规则散落各处、改一处坏一片。DDD 把业务规则收敛到领域层，让代码可读、可维护、可演进。

两大阶段：

  • 战略设计：先划清业务边界（限界上下文），确定系统间的协作方式。
  • 战术设计：在边界内设计聚合、实体、值对象、领域服务、仓储等模型要素。

1. 分层理念

**数据访问层（DAL, Data Access Layer）**是业务逻辑与数据库之间的隔离层，职责包括：

  • 屏蔽 SQL 细节：业务层不写 SQL，只调用方法。
  • 统一管理连接：连接池复用连接，避免频繁建连。
  • 事务控制：保证一组操作要么全成功要么全回滚。
  • 对象映射（ORM）：把表记录映射为对象，行转实体。

分层职责：Controller（入参出参）→ Service（业务规则）→ Mapper/Repository（数据访问） → DB。DAL 只做”怎么取数据”，不做业务判断。

1. 概念说明

**并发（Concurrency）**指多个任务在时间上交替执行（宏观并行、微观串行），**并行（Parallelism）**指多个任务真正同时执行（多核）。并发解决的是”多任务协同”，并行解决的是”更快”。

三个层次：

  • 进程（Process）：操作系统资源分配单位，内存隔离，切换开销大。
  • 线程（Thread）：进程内执行单位，共享进程内存，切换开销较小。
  • 协程（Coroutine）：用户态调度，栈极小，可创建十万级（Java 虚拟线程、Go goroutine、Python async）。

核心问题：多个线程同时读写共享变量会产生竞态条件（Race Condition），导致结果不确定。解决方案：互斥（锁）、原子操作、不可变对象、线程本地存储。

Java 并发三大特性：原子性（操作不可分割，i++ 不是原子的）、可见性（线程改了变量其他线程能看到，CPU 缓存导致看不到）、有序性（指令重排导致执行顺序与代码不一致）。Java 内存模型（JMM）中，volatile、synchronized、Lock 通过内存屏障保证可见性与有序性。

1. 概念说明

CI/CD 是”自动化交付”的三种实践的合称：

  • 持续集成（CI, Continuous Integration）：每次代码提交都自动触发构建 + 测试，尽早发现集成问题。核心是”频繁合并、快速反馈”。
  • 持续交付（CD, Continuous Delivery）：CI 通过后自动把产物（镜像/包）准备好，处于”随时可发布”状态。
  • 持续部署（Continuous Deployment）：产物自动部署到生产环境，全流程无人干预。

**流水线（Pipeline）**是这些阶段的编排：提交代码 → 安装依赖 → Lint → 单元测试 → 构建镜像 → 推送制品 → 部署。**质量门禁（Quality Gate）**指某一步失败即中断流水线，保证坏代码无法进入下一步。

2. 通用最佳实践

实践 说明
流水线快 缓存依赖（npm cache / docker layer cache）
失败即中断 每一步都是质量门禁
部署用制品 不要重复构建，测试通过的镜像一路到生产
环境隔离 dev/staging/prod 三套环境与密钥
密钥不入库 全部走 Secrets / Vault
并行化 无依赖的 Job 并行跑，缩短总时长
版本可回溯 镜像 tag 用 commit SHA，不用 latest，回滚有据
