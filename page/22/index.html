1. 核心概念速览

MySQL 是流行的开源关系型数据库，数据以表为单位组织，通过 SQL 操作。

  • 表 / 行 / 列：二维结构组织数据。
  • 主键：唯一标识一行，默认聚簇索引。
  • 索引：加速查询，代价是写入变慢、占空间。
  • 事务：一组 SQL 要么全部成功要么全部回滚，满足 ACID。

DAL · 数据访问层

从 0 到分层落地。DAL 职责与分层 · ORM 选型 · 连接池 · 事务管理 · MyBatis-Plus 实战 · 多数据源 · 读写分离。代码带详细注释。

类别 选型 用途

1. 概念说明

**数据访问层（DAL, Data Access Layer）**是业务逻辑与数据库之间的隔离层，职责包括：

  • 屏蔽 SQL 细节：业务层不写 SQL，只调用方法。
  • 统一管理连接：连接池复用连接，避免频繁建连。
  • 事务控制：保证一组操作要么全成功要么全回滚。
  • 对象映射（ORM）：把表记录映射为对象，行转实体。

分层职责：Controller（入参出参）→ Service（业务规则）→ Mapper/Repository（数据访问） → DB。DAL 只做”怎么取数据”，不做业务判断。

ORM vs 原生 JDBC：

维度 原生 JDBC ORM（MyBatis-Plus / JPA）
开发效率 低（样板代码多） 高（CRUD 自动生成）
复杂 SQL 可控 MyBatis 用 XML、JPA 用 JPQL
性能 精细可控 需注意 N+1 问题
学习成本 低 中

14. 常见误用与陷阱

坑 现象/后果 解法
循环里逐条查询（N+1） 一页数据发上百条 SQL，接口 RT 秒级 IN 批量查 + Map 回填，或 JOIN
大批量 insert 一把梭 超过 max_allowed_packet 整批失败 分批 500~1000 条，JDBC 串加 rewriteBatchedStatements=true
HikariCP maxLifetime 大于 wait_timeout 拿到已被 DB 回收的连接，报 CommunicationsException maxLifetime 调小于 wait_timeout（留 30s 余量）
动态 SQL 用 ${} 拼接用户输入 SQL 注入，数据被拖库 一律 #{} 参数化；排序字段用白名单映射
LIKE '%关键词%' 前导通配符不走索引，全表扫描 改前缀匹配 LIKE 'x%'，或接全文索引/ES
分页不设上限 page_size=10000 一次拖垮数据库与带宽 服务端硬约束（le=100），大数据量改游标
SELECT * 带出大字段 网络 IO 翻倍，无法利用覆盖索引 按需选列，列表页不查 TEXT/BLOB
逻辑删除后唯一键冲突 软删用户重新注册报 Duplicate entry 唯一索引带上删除标记（如 email+deleted 组合）

1. 概念说明

**并发（Concurrency）**指多个任务在时间上交替执行（宏观并行、微观串行），**并行（Parallelism）**指多个任务真正同时执行（多核）。并发解决的是”多任务协同”，并行解决的是”更快”。

三个层次：

  • 进程（Process）：操作系统资源分配单位，内存隔离，切换开销大。
  • 线程（Thread）：进程内执行单位，共享进程内存，切换开销较小。
  • 协程（Coroutine）：用户态调度，栈极小，可创建十万级（Java 虚拟线程、Go goroutine、Python async）。

核心问题：多个线程同时读写共享变量会产生竞态条件（Race Condition），导致结果不确定。解决方案：互斥（锁）、原子操作、不可变对象、线程本地存储。

CI/CD 持续集成持续部署从入门到落地

发表于 2026-09-14 更新于 2026-10-25 分类于 CI/CD 本文字数： 7.6k 阅读时长 ≈ 7 分钟

CICD · 持续集成与部署

从 0 到自动化流水线。CI/CD 概念 · GitHub Actions · GitLab CI · 构建/测试/镜像/部署 · 质量门禁。配置带详细注释。

技术栈速查

类别 选型 用途
CI 平台 GitHub Actions / GitLab CI 流水线执行
容器 Docker + Buildx 镜像构建与多架构
制品 GHCR / Docker Hub 镜像仓库
部署 SSH / K8s / 云函数 发布目标
质量门禁 ESLint / pytest / SonarQube 合并前检查

1. 概念说明

CI/CD 是”自动化交付”的三种实践的合称：

  • 持续集成（CI, Continuous Integration）：每次代码提交都自动触发构建 + 测试，尽早发现集成问题。核心是”频繁合并、快速反馈”。
  • 持续交付（CD, Continuous Delivery）：CI 通过后自动把产物（镜像/包）准备好，处于”随时可发布”状态。
  • 持续部署（Continuous Deployment）：产物自动部署到生产环境，全流程无人干预。

**流水线（Pipeline）**是这些阶段的编排：提交代码 → 安装依赖 → Lint → 单元测试 → 构建镜像 → 推送制品 → 部署。**质量门禁（Quality Gate）**指某一步失败即中断流水线，保证坏代码无法进入下一步。

踩坑点：

镜像永远用 latest 标签 生产跑的版本说不清，回滚无据 tag 用 commit SHA/版本号，latest 只做别名

1. 概念说明

区块链是一个去中心化的分布式账本：数据被打包成区块，通过哈希指针串联成链，由全网节点共同维护，靠共识机制（如 PoS）保证一致，具有不可篡改、公开透明、去信任三大特性。

核心概念：

  • 区块（Block）：包含交易列表、时间戳、前一区块哈希。
  • 哈希（Hash）：SHA-256 等单向函数，内容一变哈希全变，是防篡改的基础。
  • 共识机制：PoW（工作量证明）/ PoS（权益证明），决定谁来打包新区块。
  • 钱包地址：由私钥推导出的公钥哈希，私钥即资产控制权，绝不能泄露。
  • Gas：执行交易的燃料费，单位 gwei（1 ETH = 10⁹ gwei）。
  • 智能合约：运行在链上的程序，部署后地址固定、逻辑不可更改，人人可调用。

10. 典型案例：重入攻击与修复全流程

问题背景：一个「存款/提款」合约上线后被攻击者把金库搬空。代码看起来毫无破绽——余额校验、转账、清零一个不少，资金却没了。这就是重入（Reentrancy）。

方案：先写攻击合约复现漏洞，再用「检查-生效-交互」（CEI）+ ReentrancyGuard 双保险修复，最后把攻击用例改造成回归测试。

踩坑点：

  • Solidity 0.8 修的是整数溢出，不防重入——两类问题别混为一谈。
  • ERC-20/721 的回调（onERC721Received、transfer hook）同样能重入，不只 call 转账这一处。
  • 修复后必须把攻击用例改成回归测试跑绿，不能”改完就上线”。
  • 审计前先跑 Slither 静态扫描，重入这类模式化漏洞机器就能揪出来。

1. 概念说明

数字音频是把连续声波采样成离散数字序列。三个核心参数：

  • 采样率（Sample Rate）：每秒采样的次数，单位 Hz。CD 为 44100 Hz，视频通用 48000 Hz。采样率决定可还原的最高频率（奈奎斯特定理：最高频率 = 采样率/2）。
  • 位深（Bit Depth）：每次采样用多少 bit 表示振幅，16 bit（CD）、24 bit（录音室）。位深决定动态范围。
  • 声道（Channels）：单声道（mono）、双声道（stereo）或多声道（5.1）。

常见格式：WAV（无损 PCM）、MP3 / AAC（有损压缩）、FLAC（无损压缩）、M4A / OGG。

核心处理手段：转码（格式/码率转换）、剪辑（截取/拼接）、音量调整（增益/归一化）、降噪（滤波）、提取（音视频分离）、混音（多轨叠加）。

9. 典型案例：播客上架流水线（响度标准化 → 去静音 → 切章）

问题背景：编辑部每周收到 20+ 期播客音频，音量忽大忽小、片头片尾静音几十秒，人工整理一期要半小时；上架平台还常被打回”响度不达标”。

方案：批处理流水线一次搞定——两遍 loudnorm 标准化到 -16 LUFS（播客主流标准）→ 检测并切除首尾静音 → 按静音点合并切片成章节 → 输出 m4a 并回写元数据，全部脚本化并行执行。

踩坑点：

  • 单遍 loudnorm 是动态压缩，语音有”呼吸感”失真——两遍测量 + linear=true 才是正解。
  • split_on_silence 的 silence_thresh 要按素材实测响度调整，标准化后用 -40dBFS 才稳。
  • librosa/pydub 读 mp3 底层依赖 ffmpeg，服务器必须先装，否则报 CouldntDecodeError。
  • pydub 全量载入内存，2 小时节目先确认内存余量，超长素材改用 ffmpeg 流式处理。

峰值归一化当响度标准化 峰值一致但响度差 6dB，平台判定不达标 用 loudnorm（EBU R128 / LUFS）：播客 -16、流媒体 -14

1. 概念说明

REST（Representational State Transfer，表现层状态转移）是一套架构风格而非协议，核心思想是把一切都抽象为资源，用 HTTP 方法表达对资源的操作：

HTTP 方法 语义 幂等
GET 查询资源 ✅
POST 创建资源 ❌
PUT 整体更新 ✅
PATCH 局部更新 ✅
DELETE 删除资源 ✅

两点细节：① POST 不幂等的生产解法（Idempotency-Key）见 §9.1；② DELETE 重复调用返回 404 还是 204 是设计选择——要暴露「不存在」信息返回 404（本文采用），要严格「目标状态已达成」语义返回 204，全 API 保持一致即可。

RESTful API 设计五原则：资源用名词复数命名（/users 而非 /getUser）、用 HTTP 方法表达动作、无状态（每个请求携带全部信息）、状态码表达结果、版本化管理接口（/v1/users）。

2. 规范速查

2.1 资源命名

命名细则：多词路径用 kebab-case（/v1/user-groups）；嵌套不超过 2 层（过深用顶层资源+过滤参数替代）；查询参数全篇统一 snake_case 或 camelCase。

2.2 状态码

状态码 含义 典型场景
200 OK 查询成功
201 Created 创建成功
204 No Content 删除成功
202 Accepted 异步任务已受理（配合轮询/Webhook）
400 Bad Request 请求格式错误（JSON 语法错、缺必需头）
401 Unauthorized 未认证
403 Forbidden 无权限
404 Not Found 资源不存在
405 Method Not Allowed 方法不允许
409 Conflict 资源冲突（如重复创建）
412 Precondition Failed If-Match/版本冲突（见 §9.2）
422 Unprocessable 语义错误

9. 幂等键与 202 长任务设计

9.1 幂等键：POST 不幂等的生产解法

POST 创建资源天然不幂等（重复调用会创建多条），网络超时后客户端重试无法判断「创建成功还是失败」。标准解法：客户端在请求头里带唯一幂等键 Idempotency-Key: <UUID>，服务端先查该 key 是否已有结果——有则直接返回缓存结果，没有才执行业务：

幂等键 请求体 结果 服务端行为
abc {“name”:”a”} 成功(id=1) 首次执行 → 创建 + 缓存结果
abc {“name”:”b”} 成功(id=1) key 已存在 → 直接返回第一次的结果（请求体不再次校验）
xyz {“name”:”a”} 成功(id=2) 新 key → 正常执行

幂等键的作用范围：同一 key + 同一 API 端点。key 一般在客户端生成（UUID），服务端只做「见 key 识结果」。

9.2 并发控制：ETag + If-Match（乐观锁）

多人同时编辑同一资源时，后提交的人可能覆盖前一个人的修改。REST 标准做法是乐观锁：

FastAPI 里用 response.headers["ETag"] = ... 和 if_match = Header(default=None) 配合实现。核心规则：写操作（PUT/PATCH/DELETE）读操作前必须校验 ETag，不一致就拒绝。

9.3 202 Accepted：长任务的 REST 设计

创建需要几秒到几分钟完成的异步任务（如批量导入、视频转码、报表生成），不应让客户端挂等：

202 的设计要点：① 返回任务 ID 和状态查询地址；② 提供任务列表/取消接口；③ 任务完成回调（Webhook）优于客户端轮询；④ 超时任务明确标 timeout 状态。

4. 复杂度分析速查

复杂度 典型算法
O(1) 数组随机访问、哈希查找
O(log n) 二分查找、平衡树操作
O(n) 线性遍历、多数排序
O(n log n) 归并排序、快速排序、堆排序
O(n²) 冒泡/选择/插入排序、双重循环
O(2ⁿ) 递归枚举、暴力组合

4.1 怎么推导复杂度（方法论）

  • 顺序结构：取最大项，常数系数忽略（O(n) + O(n) = O(n)）
  • 嵌套循环：内外相乘，但内层范围受外层影响时要细算（如冒泡是 1+2+…+n ≈ n²/2）
  • 递归：用主定理或递归树估算。二分 T(n)=T(n/2)+O(1)=O(log n)；归并 T(n)=2T(n/2)+O(n)=O(n log n)
  • 均摊分析：动态数组 append 偶尔扩容是 O(n)，但分摊到每次操作是 O(1)（哈希表、栈的批量弹出同理）

常见误区：把「循环次数」当复杂度。实际是「基本操作执行次数随 n 的增长量级」。两层 for i in range(n) 是 O(n²)，但内层 range(i) 时仍是 O(n²)；内层恒为常数时（如固定窗口 k）是 O(n)。

7. 动态规划进阶（背包/LIS/编辑距离）

DP 三板斧：定义状态 → 写转移方程 → 确定边界。以下三个经典题覆盖最常见的 DP 形态。

7.1 0-1 背包（容量约束下的最优选择）

n 个物品各有重量和价值，背包容量 W，每个物品选或不选，求最大价值。滚动数组把 O(nW) 空间降到 O(W)。

创建 src/algo/knapsack.py：

关键细节：cap 必须倒序遍历。正序会用本物品更新后的值再更新更大的容量，导致同一物品被重复选择（变成完全背包）。

7.2 最长递增子序列（LIS，LeetCode 300）

dp[i] 表示以 nums[i] 结尾的最长递增子序列长度。转移：往前找比 nums[i] 小的所有 j，取最大 dp[j]+1。

1. 概念说明

人工智能（AI）是让机器具备”智能”的技术总称，包含三个层次：

  • 机器学习（ML）：从数据中自动学习规律，不显式编程。典型任务：回归（预测房价）、分类（识别垃圾邮件）、聚类（用户分群）。
  • 深度学习（DL）：用多层神经网络（NN）学习，是机器学习的子集，擅长图像、语音、文本等高维数据。
  • 大语言模型（LLM）：基于 Transformer 架构、在海量文本上预训练的超大模型，能理解并生成自然语言，是当前 AI 应用的主流形态。

核心流程：数据收集 → 数据清洗 → 特征工程 → 模型训练 → 模型评估 → 部署上线。本项目将从经典机器学习入手，再到深度学习，最后用 LLM 完成一个可落地的应用。

11. 常见误用与陷阱

坑 现象 解法
scaler 在全量数据上 fit 测试集均值/方差参与预处理，指标虚高上线掉 划分后只 fit(X_train)，测试集仅 transform
推理忘记 model.eval() Dropout 随机丢弃、BN 用批次统计，同输入结果抖动 加载权重后立刻 eval()；恢复训练前再 train()
验证/推理忘记 no_grad 显存暴涨，偶发自变量报错 with torch.inference_mode()（或 no_grad()）
学习率过大 loss 变 NaN/剧烈震荡；过小则几百轮不降 Adam 从 1e-3 起步，配 warmup + clip_grad_norm_
只看训练 loss 训练 loss 一直降，验证 loss 反弹（过拟合） 验证集选最优权重 + 早停 + Dropout/正则
保存整个模型 torch.save(model, ...) 跨目录/跨环境反序列化失败 只存 state_dict，网络结构随代码走
线上预处理与训练不一致 忘记标准化或特征顺序错位，预测全偏 scaler 与模型一起保存，固定特征列顺序

15. 常见误用与陷阱

坑 现象 解法
GORM 软删除 + uniqueIndex 冲突 删除某用户后用相同 email 新建报 Duplicate entry gorm.Model 的 deleted_at 使记录仍存在；唯一索引改为 (email, deleted_at) 联合，或 gorm:"uniqueIndex:idx_email,where:deleted_at IS NULL"
gin.Context 在 goroutine 里用 请求结束后偶发 panic / 读到脏数据 c 非线程安全；跨 goroutine 必须 cCopy := c.Copy() 传副本，原 c 仅在请求生命周期内可用
生产用 AutoMigrate schema 漂移、删列删索引不生效、并发启动冲突 AutoMigrate 只增不删；生产用 golang-migrate 或 Atlas 管理迁移，AutoMigrate 仅限开发
Viper 配置不识别环境变量覆盖 设了 APP_PORT 但 Unmarshal 仍是 yaml 值 需 viper.AutomaticEnv() + viper.SetEnvKeyReplacer(strings.NewReplacer(".","_"))，且 key 与 SetDefault 对齐才生效
*gorm.DB 连接池未限制 高并发下 DB 连接数飙升、被拒连 sqlDB, _ := db.DB(); sqlDB.SetMaxOpenConns(50); SetMaxIdleConns(10)，默认 0=无上限
goctl 重新生成覆盖手改代码 改了 handler 又跑 goctl，业务逻辑被覆盖 go-zero 业务写 logic/ 层（不被覆盖），handler 只做参数转换；用 //goctl:ref 标记保护自定义段
