第三章：数仓分层与数据管道调度

概念基础

  1. 数仓分层的目的是治理复杂度：ODS 贴源、DWD 明细、DIM 维度、DWS 汇总、ADS 应用——每层职责单一，下游依赖上游，坏数据能定位到层。
  2. 批流一体靠统一模型：Spark（第一章：Spark 大数据批处理入门）跑离线重算，Flink（第二章：Flink 流式计算入门）跑实时增量，两边共用口径才能「T+1 准确、实时大致对」互为校验。
  3. Kafka 是管道骨架：CDC 与日志先进 Kafka（第三章：Kafka 大数据数据总线）缓冲解耦，再分流到批/流/OLAP 各消费者。
  4. 调度是数据可靠性核心：Airflow/DolphinScheduler 把「每天 2 点跑批」变成有依赖、可重试、有告警的 DAG，而不是一堆 crontab。
  5. ClickHouse 承接分析层：DWS/ADS 汇总结果落到列存引擎供 BI 查询，见 ClickHouse：查询与性能调优。

本章聚焦管道编排与分层建模方法论；沙箱无 Airflow/Spark 集群，代码按 Airflow 2.x 官方语法书写未逐条运行验证。

一、分层模型



flowchart LR
  S[(业务库/日志)] -->|CDC/采集| O[ODS 贴源层]
  O --> W[DWD 明细层]
  DIM[(维度表)] --> W
  W --> S2[DWS 汇总层]
  S2 --> A[ADS 应用层]
  A --> BI[BI/报表/API]
层 职责 关键约束
ODS 原样落地，不做加工 保留原始格式；按天分区快照
DWD 清洗、去重、脱敏、拆平明细 一行一件事务/事件；只依赖 ODS
DIM 维度表（用户、商品、地区） 缓慢变化维（SCD2）记录历史
DWS 按主题预聚合（日/用户粒度） 口径唯一，重算成本可控
ADS 面向报表/大屏/接口的最终宽表 只依赖 DWS+DIM，不碰 ODS

分层价值：重复计算下沉、口径收敛（改一处全局生效）、问题定位快（ADS 错 → 查 DWS → 查 DWD）。

各层建模案例

二、维度建模：星型与雪花

维度建模三件套：事实表（度量 + 外键）、维度表（描述性属性）、粒度声明（一行代表什么）。

模型 结构 取舍
星型 事实表直连各维表，维表反范式冗余 查询 Join 少、速度快，数仓主流
雪花 维表再拆子维表（商品→类目→行业） 省存储但 Join 链长，仅高基数层级用

事实表三种类型：

类型 语义 案例
事务事实表 一行一事件，可加 订单流水、支付流水
周期快照事实表 定时快照状态，半可加 每日库存、每日账户余额
累积快照事实表 一行跟踪流程全生命周期，可更新 订单从下单→支付→发货→签收各时点

粒度声明是建模第一问：先回答「一行代表什么」（一行 = 一笔订单的一个商品行），再定维度与度量；粒度混乱是数仓后期所有口径打架的根源。

缓慢变化维（SCD）

维度属性会随时间变化（用户换城市、商品改类目），历史报表要不要跟着变？

类型 做法 适用
SCD1 直接覆盖，不留历史 不关心历史的属性（错别字修正）
SCD2 加版本行：生效/失效时间 + 当前标记 需要回溯历史（主流选择）
SCD3 加「前值」列，只记上一次 只需对比新旧两个值的场景

三、CDC 采集：业务库变更入仓

ODS 两种落地形态：每天全量快照（简单、可回溯）与增量 upsert（省存储、需主键合并）——中小规模优先全量快照 + 关键表才做增量。

四、Airflow：把批处理编排成 DAG

调度实践要点：

实践 说明
数据就绪探测 用 Sensor 等「源表分区就绪」（/data/ods/dt=2026-05-01/_SUCCESS）再开跑
幂等设计 所有任务以 dt=日期分区 覆盖写，重跑不产生重复
回刷 补数 = 对历史日期重放 DAG；幂等是回刷安全的前提
分区约定 全公司统一 dt/hh 分区字段，下游依赖检查分区存在性
SLA 与告警 任务超过预期时长告警；失败走 IM webhook（见 第四章：系统运维进阶 的日志与监控）

调度系统选型：Airflow vs DolphinScheduler

维度 Airflow 2.x DolphinScheduler 3.x
DAG 定义 Python 代码，灵活可编程 Web UI 拖拽 + JSON，上手快
扩展性 Operator/Hook 生态极丰富 内置任务类型多（Shell/SQL/Spark/Flink）
多租户/权限 较弱（靠 RBAC 自定义） 原生多租户，适合数据中台
运维 需管 Scheduler/Webserver/Worker 分布式去中心化，国产文档友好
选型倾向 工程团队、代码化偏好 数据分析团队、可视化偏好

共同点：幂等任务 + 分区依赖 + 失败重试 + SLA 告警四件套是任何调度系统落地的底线。

五、批流双跑与一致性

问题 方案
实时与离线口径不一致 统一 DWS 层 SQL 口径，代码同源（或用 Flink 批模式跑离线）
迟到数据 Flink 水位线 + allowed lateness；离线重算兜底
重复写入 Kafka 事务 + 幂等 sink（主键去重），见第三章「精确一次」
大宽表爆炸 ADS 只建高频查询宽表，长尾需求走即席查询

六、数据质量门禁

检查 时机
表行数/波动率 ODS 就绪后
主键唯一、非空 DWD 产出后
口径对账（批 vs 流） ADS 产出后
下游新鲜度 报表侧每天首次访问校验数据日期

质量规则体系化

零散 SQL 检查多了以后难维护，用规则表或框架托管：

规则类别 示例 处置
完整性 非空率 ≥ 99.5% 超阈值阻断下游
唯一性 主键重复数 = 0 阻断
一致性 订单金额 = 明细求和 告警 + 对账任务
时效性 分区在 08:00 前就绪 延迟告警
有效性 枚举值在字典范围内 脏数据进隔离区

工具：自研规则引擎（规则表 + SQL 模板 + Airflow 任务生成）最贴合分层体系；开源侧 Great Expectations（声明式 expectation 套件，可挂进 Airflow）与 Deequ（Spark 原生）是常见选型。质量结果本身也建一张 dqc_result 表，按天趋势监控——坏规则会被时间看出来。

七、分层反模式

反模式 症状 解法
烟囱式直通 报表 SQL 直查 ODS，口径遍地开花 强制 ADS 只依赖 DWS+DIM
层级过多 ODS→DWD→DWS 又插两层中间表，链路一周改不动 层数服务于定位效率，不为分层而分层
维度穿透 DWD 里冗余几十列维度属性 维度归 DIM，Join 在 DWS/ADS 做
口径漂移 同一指标三张表三个数 指标字典 + DWS 层口径唯一收敛
回刷无门禁 补数直接覆盖生产分区 影子分区验证 + 质量门禁通过后切换

要点 结论
分层 ODS 贴源 → DWD 明细 → DIM 维度 → DWS 汇总 → ADS 应用；坏数据逐层定位
建模 星型为主、粒度先行；事实表分事务/周期快照/累积快照；维表用 SCD2/拉链 留历史

质量 完整性/唯一性/一致性/时效性/有效性五类规则做成门禁，不过检不放行下游

第五章：RAG 与向量检索实战

概念基础

  1. RAG = 检索增强生成：把私有知识向量化入库，提问时先检索最相关的片段塞进上下文，再让 LLM 作答——不用重训模型就能注入领域知识，是 LLM 落地性价比最高的路线。
  2. Embedding 是语义坐标系：文本被编码为高维向量（如 1024 维），语义相近的文本距离相近；「检索」从关键词匹配升级为最近邻搜索。
  3. 向量库专管 ANN：Milvus/Qdrant/pgvector 用 HNSW 等索引做近似最近邻查询，毫秒级从千万级向量里捞 Top-K；小规模用 Redis/Postgres 也能起步。
  4. 效果好坏在数据管道：切块（chunking）粒度、检索 Top-K、重排序（rerank）三件事对答案质量的影响大于换模型。
  5. 评估要有 ground truth：召回率（该找的找没找到）与答案忠实度（说的对不对）分开评，肉眼抽查不可持续。

本章把 RAG 概念落到工程实现。代码按 LangChain 0.3 / OpenAI SDK 官方 API 风格书写（沙箱未装依赖，未逐条运行验证）。

一、RAG 全链路



flowchart LR
  D[文档] --> C[切块 Chunking]
  C --> E[Embedding 向量化]
  E --> V[(向量库)]
  Q[用户提问] --> QE[问题向量化]
  QE --> V
  V --> R[Top-K 检索 + Rerank]
  R --> P[拼装 Prompt]
  P --> LLM[LLM 生成]

两条管道：

管道 内容 执行时机
离线索引 文档 → 清洗 → 切块 → 向量化 → 入库 文档新增/变更时
在线问答 问题向量化 → 检索 → 拼 Prompt → LLM 每次提问

三、在线检索与生成

Prompt 三原则：明确告知「只依据资料」、资料带来源标记（答案可引用）、temperature=0 降低发挥。

四、向量库选型

方案 定位 适用
Qdrant / Milvus 专用向量库，HNSW/量化，十亿级 独立检索服务
pgvector Postgres 扩展 已有 PG、千万级以内（运维最省）
Redis 向量检索 + 缓存一体 热点数据、低延迟

五、评估与迭代

调优顺序（从便宜到贵）：

  1. 切块参数：调 chunk_size/separators，对结构化文档用标题感知切块
  2. 检索深度：先取 Top-20 再 rerank 到 Top-4（召回与精排分工）
  3. 混合检索：加 BM25，专治型号、代码、专有名词
  4. 换 Embedding 模型：领域强的换领域微调模型（中文场景 BGE 系列常用）
  5. 最后才动 LLM：检索对了答案基本就对了

六、切块策略对比

策略 做法 优点 缺点 适用
定长切块 按字符数硬切 简单快 断句断语义 日志、流水文本
递归切块 按分隔符优先级切 保句子完整 块大小不均 通用首选
结构感知 按标题/代码块/表格切 语义单元完整 需要解析器 Markdown、技术文档
语义切块 按 embedding 变化点切 主题内聚 慢、贵 长报告、书籍
父子切块 小块入库、命中取父块 精度与上下文兼得 实现复杂 高质量问答

经验：技术文档优先结构感知；拿不到结构再退回递归切块。chunk_size 以 embedding 模型的有效窗口为上限，别盲目调大。

九、评估指标：从召回到忠实度

指标 度量什么 计算方式
Recall@K 期望文档是否进 Top-K 命中数 / 总用例数
MRR 第一个正确结果排多前 平均 1/rank
Faithfulness 答案是否忠于检索内容 LLM 拆解答案逐句核对来源
Answer Relevancy 答案是否切题 LLM 反问生成 + 相似度

工程化做法：检索侧盯 Recall@K 与 MRR（改动快、反馈快），生成侧用 RAGAS 类框架跑 faithfulness（慢，按版本跑）。两维分开归因——召回差改数据管道，忠实度差改 prompt 与上下文拼装。

十、GraphRAG 简介

向量 RAG 把知识切成碎片，遇到”这些事件之间什么关系””整个语料的主线是什么”这类全局性、关系性问题会失灵。GraphRAG（微软开源）的思路：

  1. 离线索引时让 LLM 从每个 chunk 抽取实体与关系，构建知识图谱；
  2. 社区检测把图谱聚成主题簇，预生成社区摘要；
  3. 在线查询按类型分流：局部问题走实体邻域检索，全局问题走社区摘要问答。

代价是索引成本数倍于普通 RAG（每 chunk 多次 LLM 调用）。结论：默认从向量 + BM25 + rerank 起步，确认有全局分析类刚需再上 GraphRAG。

第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3

概念基础

QUIC（Quick UDP Internet Connections）是运行在 UDP 之上的可靠、加密、多路复用传输协议，是 HTTP/3 的底座：

  1. 解决什么问题：TCP 字节流「一丢全等」的队头阻塞、TCP + TLS 分层握手往返多、四元组一变连接即断——QUIC 在 UDP 上逐一重构。
  2. 三大关键设计：流（Stream）级隔离让丢包影响面缩小；内置 TLS 1.3 把加密与传输握手合并（目标 1-RTT 建连，0-RTT 可选加速）；Connection ID 让网络切换后连接依旧存活（连接迁移）。
  3. 实现在用户态：与 第一章：TCP 协议详解：连接、可靠传输与编程示例 内核栈不同，QUIC 多由用户态库（ngtcp2、quiche、MsQuic 等）实现，迭代快但排障更依赖日志与指标。
  4. 代价与前提：依赖 UDP/443 放行与企业网策略对齐；0-RTT 有重放风险，写操作需谨慎。

先看设计目标与作用的全貌：

一、设计目标与作用

1. 解决什么问题

  • 在 UDP 上重建可靠管道：丢包检测、重传、拥塞控制发生在 QUIC 层，而不依赖 第一章：TCP 协议详解：连接、可靠传输与编程示例 单一流上的队头阻塞。
  • 默认加密：传输与握手深度绑定 TLS 1.3（RFC 9001），减少「明文旁路」与分层带来的额外往返。
  • 多流与连接标识：Stream 隔离应用数据；Connection ID 让四元组变化时仍能延续同一逻辑连接（连接迁移）。

2. 相对 TCP + TLS 的典型取舍

问题 第一章：TCP 协议详解：连接、可靠传输与编程示例 + TLS 常见表现 QUIC 思路
队头阻塞 TCP 字节流级丢包会阻塞后续所有应用数据 QUIC 在流级相对独立地做丢包恢复
握手 RTT 常需 TCP 三次握手再叠 TLS 往返 常把加密与传输握手合并，目标 1-RTT 建连（0-RTT 为可选加速）
NAT 重绑定 四元组变化常被视作「新连接」 Connection ID 标识逻辑连接，支持连接迁移
中间设备 TCP 成熟、穿透好 依赖 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 放行（如 UDP/443）；企业网策略需对齐

二、连接与完整通信流程（原理）

QUIC 报文封装在 UDP 数据报中（常见 HTTPS 场景为 UDP/443）。以下极度简化，省略版本协商、重试包、地址验证等细节。

1. 建立连接（简化）

首包常带 TLS ClientHello；成功后在 1-RTT 密钥下发送应用数据。0-RTT 可在重复连接时提前带数据，见第五节安全注意。

带地址验证的完整握手（更接近真实）：



sequenceDiagram
  participant C as Client
  participant S as Server
  C->>S: Initial（TLS ClientHello）
  opt 服务端要求地址验证
    S-->>C: Retry（携带 token）
    C->>S: Initial（回显 token + ClientHello）
  end
  S-->>C: Initial（ACK）+ Handshake（ServerHello…Finished）
  C->>S: Handshake（Finished）+ 1-RTT 数据
  S-->>C: 1-RTT 响应数据

Retry 包的作用：服务端在投入连接状态之前，先让客户端证明「它真的拥有所声称的源地址」，从源头抑制地址伪造型放大攻击（QUIC 要求服务端在地址验证前发送的字节数不超过收到的 3 倍）。

2. 关闭连接（简化）

任一方可发送 CONNECTION_CLOSE 帧；对端进入排空（draining）期，不再发送新数据。与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 FIN/ACK 不同，QUIC 在连接粒度表达关闭，内部再回收流与 UDP 套接字资源。

3. 与典型「套接字 / 协议栈」的对应

与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 connect/accept 由内核一条龙完成不同，QUIC 一般由用户态库（如 ngtcp2、quiche、MsQuic、aioquic）或浏览器网络栈实现：底层仍是 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 sendto/recvfrom，其上是 TLS 1.3、ACK/重传、流控与 HTTP/3 帧。HTTP/3 客户端日常通过 curl --http3-only 或内置 HTTP/3 的 SDK 使用，而不是手写裸 UDP 报文。

三、包结构与帧（概念）

1. 长首部与短首部

项 长首部（Long Header） 短首部（Short Header）
用途 握手阶段（Initial / 0-RTT / Handshake / Retry） 建立后的 1-RTT 数据
明文可见 版本、DCID/SCID、包类型、长度 仅 DCID（与少量标志）
首部开销 较大 小（数据面常态）

2. 常见帧类型（RFC 9000 §19）

帧 作用
PADDING / PING 填充 / 保活探测
ACK 确认收到的包号范围（支持 ACK Range 与 ECN 计数）
CRYPTO 承载 TLS 1.3 握手字节流

PATH_CHALLENGE / PATH_RESPONSE 连接迁移时的路径验证

四、流、可靠性与拥塞控制（原理要点）

  • Connection：加密上下文、ACK 与拥塞控制的归属单位（类似「一条加密了的类 TCP 管道」）。
  • Stream：单向或双向；HTTP/3 将请求/响应映射到不同流，减轻应用级队头阻塞。
  • Packet Number：单调递增，配合 ACK 范围与密钥更新，降低与 第一章：TCP 协议详解：连接、可靠传输与编程示例 序号相关的歧义；重传不重用旧 PN（新包新号）。
  • 拥塞控制：在 Connection 上运作（如 Cubic、BBR 等实现依栈而定），与 第一章：TCP 协议详解：连接、可靠传输与编程示例 一样受网络条件约束，但并非「一条字节流管所有多路复用对象」。

两级流控：MAX_DATA 限制整条连接的在途字节总量，MAX_STREAM_DATA 限制单条流——接收方两侧同时收紧，发送方须同时满足。流控窗口耗尽时发送方会被阻塞，Wireshark/qlog 中常见 blocked 事件即源于此。

Stream ID 编码（低 2 bit 表意）：bit0 区分发起方（0=客户端，1=服务端），bit1 区分方向（0=双向，1=单向）——例如客户端发起的第一个双向流 ID 为 0，服务端第一个单向流为 3。

五、Connection ID、端口与「会话标识」

  • UDP 四元组仍用于路由首个报文；Connection ID 使源 IP/端口变化（如蜂窝切换 Wi-Fi）后，对端仍能识别同一 QUIC 连接。
  • 公网 HTTP/3 常见端口为 443（UDP），与 第一章：TCP 协议详解：连接、可靠传输与编程示例 443 并存、互不替代。
  • 服务端可协商 CID 长度与轮换策略，以兼顾隐私与路由。

连接迁移时序（简化）：



sequenceDiagram
  participant C as Client
  participant S as Server
  Note over C: 网络切换（Wi-Fi → 蜂窝），四元组变化
  C->>S: 新路径首发（PATH_CHALLENGE + 新 CID）

六、TLS 1.3 与 QUIC（原理）

QUIC 使用 TLS 1.3 做身份认证与密钥导出；载荷由 AEAD 保护，PADDING 等机制缓解流量分析。0-RTT 可加速重复连接，但存在重放风险：对金融类写操作应禁用或在应用层做幂等与二次校验。

加密分层细节：

  • 密钥分四级：Initial（从 DCID 公开导出，仅防被动观察者篡改）→ Handshake → 1-RTT（分 0-RTT 与应用数据），各级独立密钥。
  • 首部保护（Header Protection）：除版本与 CID 外，包号等元数据也加密——中间盒连「这是第几个包」都看不到，这是「防 ossification（协议僵化）」的刻意设计。
  • 密钥更新（Key Update）：长连接可轮换 1-RTT 密钥，限制单密钥加密的数据量。

七、HTTP/3 与 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例 对比（概念）

项 HTTP/2 over 第一章：TCP 协议详解：连接、可靠传输与编程示例 HTTP/3 over QUIC
传输 TCP 字节流 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 上的 QUIC

第十四章：RPC 概念详解：原理、形态与 JSON-RPC / curl 示例

概念基础

RPC（Remote Procedure Call，远程过程调用）的目标：让调用远程服务像调用本地函数一样自然：

  1. 解决什么问题：分布式系统中，网络通信的序列化、连接管理、协议细节不应散落在业务代码里，RPC 框架把它们收敛到 stub（存根）。
  2. 如何做到：客户端 stub 把调用序列化成消息发出去；服务端 stub 反序列化、执行、再原路返回——开发者只见函数签名。
  3. 不规定字节格式：JSON-RPC（人可读易调试）、protobuf（见 第十三章：gRPC 详解：Protobuf、HTTP/2 与 grpcurl / Python 示例）、Thrift 等都是可选载体，传输可用 HTTP 或自定义 TCP。
  4. 核心难点：网络不可靠——超时后客户端不知道服务端是否已执行，重试可能重复扣款，必须用幂等设计兜底。

先看一次 RPC 调用的完整链路：

一、原理（.stub 与存根）

RPC 不规定具体字节格式；可由 JSON、protobuf、Thrift 等定义。

  • 链上节点：Ethereum JSON-RPC 等文本 RPC。
  • 脚本自动化：轻量 JSON-RPC 管理接口。

四、失败语义与幂等（原理）

  • 超时：客户端不知服务端是否已执行；重试可能导致重复扣款。
  • 对策：幂等键、去重表、At-least-once 消费语义与业务配合。

三种投递语义——分布式系统的根本约束是「恰好一次只能在单个参与者内部保证」：

语义 机制 业务要求
At-most-once 不重试，超时即失败 可容忍丢失（日志采集、心跳）
At-least-once 超时重试直到确认 必须幂等（绝大多数业务选此）
Exactly-once 业务层去重 + 状态机 仅能在幂等设计上「等效」实现

配套防护三件套：

  • 超时：每次调用必设截止时间（不是单次重试超时，而是整个调用链预算）。
  • 重试：只对连接失败/明确可重试错误重试；指数退避 + 抖动；限制次数防重试风暴。
  • 熔断：下游持续失败时短路调用，给系统恢复时间（如 Sentinel、resilience4j）。

第十二章：MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例

概念基础

MQTT（Message Queuing Telemetry Transport）是面向 IoT 的轻量级发布/订阅消息协议，默认运行在 TCP 1883：

  1. 解决什么问题：设备多、带宽窄、网络不稳——MQTT 报文头最小仅 2 字节，支持断线重连、遗嘱消息与会话保持。
  2. 角色解耦：发布者与订阅者都只连 Broker，按 Topic 字符串路由，双方互不知晓对方存在。
  3. QoS 三档：0 至多一次 / 1 至少一次 / 2 恰好一次，按业务对丢失与重复的容忍度选择。
  4. 为什么适合物联网：低功耗设备常发小遥测消息，Pub/Sub 天然一对多广播；对比 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例 请求-响应模型更省连接与电量。

先看发布订阅模型的总体结构：

发布订阅模型



flowchart TB
  P1[Publisher 传感器] -->|publish topic/sensor| B[MQTT Broker]
  P2[Publisher 设备] --> B
  B -->|subscribe| C1[Consumer 大屏]
  B --> C2[Consumer 规则引擎]

一、模型与作用（原理）

Broker 根据 Topic 字符串路由消息；发布者不必知道订阅者列表。

报文结构（概念）：每条 MQTT 报文 = 固定头（报文类型 4bit + 标志 4bit + 剩余长度 1–4 字节） + 可变头 + 载荷。控制报文类型共 14 种，常用的有：CONNECT / CONNACK（建连）、PUBLISH（发消息）、PUBACK / PUBREC / PUBREL / PUBCOMP（QoS 确认链）、SUBSCRIBE / SUBACK、PINGREQ / PINGRESP（心跳）、DISCONNECT。

二、主题与通配符（作用）

  • 层级：用 / 分层，如 factory/line1/temp。
  • 单级通配 +：匹配一层，如 factory/+/temp。
  • 多级通配 #：匹配剩余层级，须在末尾（细节以 v5 文档为准）。

Topic 大小写敏感；$SYS/ 常为 Broker 系统主题（依实现）。

设计建议：

  • 以「区域/产线/设备/测点」分层，便于按级授权与聚合订阅。
  • Topic 中不放变化频繁的值（如时间戳），那是 Payload 的职责；否则订阅方无法稳定匹配。
  • 设备 → 平台与平台 → 设备（下行命令）用不同前缀分开，如 up/device1/telemetry 与 down/device1/cmd。

三、QoS（原理）

QoS 名称 语义
0 至多一次 可能丢，不重试
1 至少一次 可能重复，需业务幂等
2 恰好一次 四次握手，开销最大

QoS 在发布方向与订阅方向可分别指定，最终有效语义取二者较高一侧规则（以 Broker 实现与文档为准）。

QoS 1 与 QoS 2 的确认链：



sequenceDiagram
  participant P as Publisher
  participant B as Broker
  Note over P,B: QoS 1：一次确认
  P->>B: PUBLISH (QoS1, PacketId=n)
  B-->>P: PUBACK (n)
  Note over P,B: QoS 2：两段四次确认
  P->>B: PUBLISH (QoS2, PacketId=m)
  B-->>P: PUBREC (m)
  P->>B: PUBREL (m)
  B-->>P: PUBCOMP (m)

QoS 2 通过 PUBREC/PUBREL/PUBCOMP 两段确认保证「恰好一次」，代价是状态存储与双倍往返——除计费、开关量等强一致场景外，多数遥测用 QoS 1 + 幂等消费即可。

四、遗嘱消息（Last Will，概念）

连接异常断开时 Broker 可代发预设 Payload 到指定 Topic，用于设备离线告警；须正确配置 Keep Alive 与心跳。

工作机制：CONNECT 报文中携带遗嘱主题与载荷；Broker 在 Keep Alive × 1.5 时间内没收到任何报文（含 PINGREQ），判定设备异常断线并发布遗嘱。正常 DISCONNECT 不触发遗嘱。

另外两个常配合使用的特性：

  • 保留消息（Retained）：Broker 为每个 Topic 存最新一条 retained 消息，新订阅者立刻收到——适合做「设备当前状态」主题（如 device/1/status）。
  • 会话保持：MQTT 3.1.1 的 Clean Session=0 / MQTT 5.0 的 Session Expiry Interval，让断线期间的 QoS 1/2 消息在重连后补投。

第十一章：WebSocket 详解：握手、帧与 Python 示例

概念基础

WebSocket 是建立在 TCP 上的全双工应用层协议：借一次 HTTP 握手完成「升级」，此后双方随时互发帧：

  1. 解决什么问题：HTTP 是请求-响应模型，服务器无法主动推送；轮询延迟高、空耗连接，WebSocket 用一条长连接双向实时通信。
  2. 与 HTTP 的关系：握手就是 HTTP 101 Switching Protocols（同端口、复用反代与证书基建），升级后传输的是 WebSocket 帧，不再走 HTTP 语义。
  3. 帧级多路复用：文本帧、二进制帧、Ping/Pong 心跳、关闭帧都在单 TCP 连接上交错传输，消息可分片。
  4. 典型场景：行情推送、协作编辑、聊天、游戏状态、IoT 面板实时刷新；服务端单向文本流更轻的替代是 SSE。

先看握手与全双工时序：

握手与全双工



sequenceDiagram
  participant C as Client
  participant S as Server
  C->>S: HTTP Upgrade websocket
  S-->>C: 101 Switching Protocols
  C->>S: WebSocket 帧 文本/二进制
  S-->>C: WebSocket 帧 推送

一、作用与模型

  • 服务器推送：行情、协作编辑、游戏状态无需客户端轮询。
  • 双向二进制：除文本帧外可传 ArrayBuffer 类数据。
  • 与 SSE 对比：SSE 多为服务端单向文本流，仍基于 HTTP；WebSocket 真双向。

第十章：DNS 详解：解析原理、记录类型与命令/代码示例

概念基础

DNS（Domain Name System）是互联网的「电话簿」：把人类易记的域名翻译成机器路由所需的 IP 地址：

  1. 解决什么问题：IP 难记且可能变化，域名稳定易读；DNS 把二者解耦，换机房只改记录、不改品牌。
  2. 分层委派：根 → TLD → 权威逐级授权，任何递归解析器都能沿这条链问出答案，无单点存储全部数据。
  3. 缓存与 TTL：各级结果按 TTL 缓存，命中秒回；副作用是记录变更存在生效延迟。
  4. 不只有「名字 → IP」：MX（邮件）、TXT（SPF/DKIM/域名验证）、PTR（反向解析）等记录支撑大量基础设施。
  5. 为什么重要：几乎所有 Web 访问的第一步；DNS 故障常表现为「ping IP 正常但域名不通」。

先看一次完整解析的全貌：

递归解析



flowchart LR
  App[应用] --> LR[本地递归解析器]
  LR --> Root[根 DNS]
  Root --> TLD[.com TLD]
  TLD --> Auth[权威 DNS]
  Auth --> IP[A 记录 IP]

一、分层与解析原理

1. 角色

角色 作用
Stub resolver 运行在终端或系统库内，把查询发给递归解析器
Recursive resolver 代客户端迭代问根、TLD、权威 直到拿到答案并缓存 TTL
Authoritative server 对某区（zone）拥有权威数据（NS 委派链终点）

2. 递归解析过程（概念）

查询 www.example.com.（末尾点表示根）时，递归器从根得到 .com 的 NS，再问 .com 得到 example.com 的 NS，最后问 example.com 权威得到 www 的 A / AAAA。结果按 TTL 缓存，命中则直接返回。

更细的时序（客户端只发一问，剩下都是递归器代劳）：



sequenceDiagram
  participant A as 应用(Stub)
  participant R as 递归解析器
  participant Root as 根服务器
  participant TLD as .com TLD
  participant Auth as example.com 权威
  A->>R: www.example.com A?（RD=1）
  R->>Root: www.example.com A?
  Root-->>R: 去问 .com NS（Referral）
  R->>TLD: www.example.com A?
  TLD-->>R: 去问 example.com NS（Referral）
  R->>Auth: www.example.com A?
  Auth-->>R: A 93.184.216.34（AA=1）
  R-->>A: A 93.184.216.34（按 TTL 缓存）

术语：递归查询（RD=1）是客户端对递归器的请求方式；递归器对各级服务器做的是迭代查询——每跳只给「下一层去哪问」的指引。

二、报文与传输（原理）

  • 传统 53 端口：多数查询用 第五章：UDP 协议详解：数据报语义、MTU 与示例代码，报文小、往返少。
  • 响应过大或区域传送等：回退 第一章：TCP 协议详解：连接、可靠传输与编程示例（TCP/53）。
  • DNS 消息结构（概念）：Header（ID、flags、各计数器）+ Question + Answer / Authority / Additional。

首部 12 字节逐字段（RFC 1035）：

字段 位宽 说明
ID 16 请求/响应匹配标识（须随机化）
QR 1 0=查询，1=响应
Opcode 4 0=标准查询
AA 1 权威应答（来自权威服务器时置位）
TC 1 截断：UDP 放不下，提示改用 TCP 重问
RD 1 期望递归
RA 1 递归可用（递归器应答时置位）
RCODE 4 结果码：0 NOERROR、2 SERVFAIL、3 NXDOMAIN
QD/AN/NS/AR COUNT 16×4 四个区段的记录数

ID 用于匹配请求与响应；客户端应随机化 ID 与源端口以降低投毒风险（实现依赖系统解析器）。

三、常见记录类型（作用）

类型 作用
A 主机名 → IPv4
AAAA 主机名 → IPv6
CNAME 别名到另一域名（继续解析目标名）
MX 邮件交换：优先级 + 目标主机
NS 某区的权威服务器
TXT 任意文本（SPF、DKIM、域名验证等）
PTR IP → 主机名（反向解析）

补充两个运维常用类型：SOA（区起始权威，含序列号与刷新/重试/过期计时器，dig example.com SOA 可见）、CAA（声明哪些 CA 允许为本域签发证书，误配会导致证书申请失败）。

第九章：SSH 详解：加密远程登录、密钥与端口转发示例

概念基础

SSH（Secure Shell）是运行在 TCP 之上的加密远程管理与通道协议：

  1. 解决什么问题：Telnet / rlogin 等明文远程登录会把账号密码与全部数据暴露在链路上，SSH 用加密与完整性校验防窃听、防篡改。
  2. 两层认证：主机密钥证明「服务器是它自己」（首次连接写入 known_hosts），用户认证证明「你是你」（公钥 / 密码 / 证书，推荐公钥）。
  3. 不只是登录：SSH 还是加密隧道——端口转发（-L/-R/-D）、跳板（ProxyJump），并可承载 SFTP 等子系统。
  4. 为什么可靠：基于 第一章：TCP 协议详解：连接、可靠传输与编程示例 的可靠字节流，配合协议内建的密钥交换与重协商，全程不暴露明文凭据。

第八章：SFTP 详解：SSH 子系统、协议栈与 sftp 示例

概念基础

  1. 跑在 SSH 上的文件传输子系统：SFTP 是 SSH 协议族中的子系统，直接复用 SSH 的加密、完整性与认证——单端口（22）单连接搞定文件操作。
  2. 不是「FTP over SSH」：与 第七章：FTP 详解：双连接模型、主动/被动与 lftp 示例 的双连接模型无关；也不同 scp（单次拷贝）与 rsync（增量同步，协议不等同 SFTP）。
  3. 为什么是公网首选：默认强加密、防火墙只需放行一个端口、可复用 SSH 密钥免密认证；而 FTPS 虽加密仍保留双连接复杂性。
  4. 交互与批处理兼得：sftp 支持交互浏览目录（ls/cd/get/put），也支持 -b 批处理脚本，适合自动化。

作用与协议栈（原理）

SFTP 是 SSH 协议族中的子系统，与 shell 会话可并存于同一 SSH 连接实现上（由服务器策略决定）。

协议报文要点（概念）：SFTP 是二进制请求/响应协议，每条消息为「长度 + 类型 + 请求 ID + 载荷」。客户端发 SSH_FXP_OPEN / READ / WRITE / CLOSE / READDIR / STAT / REMOVE / RENAME 等请求，服务端回 SSH_FXP_HANDLE / DATA / STATUS / ATTRS 等响应；请求 ID 允许多请求并行在途（pipelining），这是它比「一问一答」的 FTP 控制连接更适合高延迟链路的原因之一。协议版本常见为 v3（OpenSSH 实现），扩展能力在 SSH_FXP_INIT 握手时协商。

工具 说明
SFTP 交互浏览目录、断点续传能力依客户端而定

现象 优先怀疑

安全注意

  • 优先 密钥认证，禁用密码（PasswordAuthentication no，变更前确认已有可用密钥）。
  • 公网暴露 22 必配 fail2ban 或改高位端口 + 安全组白名单；密钥定期轮换。
  • SFTP 全程密文，抓包只能看到加密后的 第九章：SSH 详解：加密远程登录、密钥与端口转发示例 通道流量，排障主要靠客户端 -v 与服务端 auth.log。
