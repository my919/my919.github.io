第六章：RS485

概念基础

  1. RS485（TIA/EIA-485） 是差分电气标准：用 A/B 两线电压差表示信号，抗共模干扰强、可达上千米，是工业现场最常用的物理层。
  2. 总线型多机：一条双绞线手拉手（daisy-chain）挂多个节点，配合地址协议实现多机组网；总线两端各接 120Ω 终端电阻。
  3. 半双工：两线制同一时刻只能一个方向发送，收发器需 DE/RE 引脚切换方向。
  4. 只管电气不管语义：RS485 只解决「电信号怎么传」，上层要跑 Modbus RTU 等主从协议才能完成有效通信。
  5. 与 UART 的关系：MCU 的 UART 产生字节流，经 MAX485/SN65HVD 收发器转成差分信号——UART 管逻辑、485 管物理。

一、拓扑

  • 半双工：同一时刻只能一个方向发送；需 DE/RE 引脚控制收发器方向。
  • 共模范围：约 -7V ~ +12V，适合工业现场。

差分电平怎么判定

接收端只看压差，不参考绝对地——所以电机启停、地电位浮动产生的共模噪声被天然抵消。这是 485 能在车间拉几百米的根本原因。

关键电气参数

参数 值 说明
最大节点数 32（标准负载）/ 128、256（分数负载收发器） 由收发器输入阻抗决定
最远距离 ~1200 m（低速率） 速率与距离反相关
最高速率 10 Mbps（短距离） 典型应用 ≤ 115200 bps
共模范围 -7V ~ +12V 超范围收发器损坏

速率与距离的经验组合：100 kbps 下约 1200 m；1 Mbps 下约 120 m；10 Mbps 仅限十几米。

三、与 Modbus RTU

第一章：Modbus RTU 在 RS485 上最常见：主站轮询、从站地址 1~247、CRC16 帧尾。
与 第三章：Modbus ASCII 比，RTU 更紧凑、工业现场更常用。

RS485 本身不限制上层协议，现场还能见到：

  • Modbus RTU：绝对主流。
  • Profibus DP：西门子系 PLC 现场总线，同样跑在 485 电气层上。
  • 自定义主从协议：小型设备集联常自定义「地址 + 长度 + 数据 + 校验」帧。
  • DMX512：舞台灯光控制，也是 485 物理层。

补充几个工程维度：

项目 RS232 RS485

还有全双工 485（4 线制）：两对差分线分别收发，等价于差分版 RS232，常见于长距离点对点，但失去了总线多机能力。

五、布线注意

  • 双绞线、屏蔽层单端接地（现场依规范）。
  • 终端电阻 120Ω 仅在总线两端；中间节点不加。
  • GND 参考：虽为差分，仍建议可靠参考地，避免共模超范围。
  • ESD 与浪涌：户外/电机旁加保护器件。

终端电阻与偏置电阻

  • 为什么 120Ω：匹配双绞线特征阻抗，吸收线末反射。总线两端各一个，等效 60Ω 负载——这也是驱动器输出能力按 60Ω 设计的原因。
  • 失效偏置（Fail-safe bias）：总线空闲无驱动时，A/B 压差接近 0，接收端输出不确定，可能被误判为起始位而产生幽灵字节。解法：总线上（通常主站侧）加一对上拉/下拉偏置电阻（如 560Ω~1kΩ），强制空闲时 A>B；现代收发器（如 SN65HVD 系列）内置失效保护，输出固定为高，可省掉外部偏置。
  • 中间节点 Stub 越短越好：分支引线超过几十厘米会形成反射点；星型拓扑是 485 大忌，必须用集线器。

六、调试与排查

  • USB-485 适配器搭车监听：旁路挂在总线上只收不发，记录主从全部流量。
  • 示波器看差分：探头分别接 A、B 用 MATH 相减，或差分探头直接看；重点看摆幅、反射台阶、共模漂移。
  • 逐节点排除法：总线异常时按手拉手顺序逐个断电，定位拉垮总线的故障节点（收发器击穿会把整条总线钳死）。
  • 万用表静态检查：断电测 A-B 间电阻 ≈60Ω；测各节点 A/B 对地电压，异常节点常有明显偏移。

七、隔离与失效保护设计

工业级节点的常见加固手段：

  • 隔离收发器：ADM2483、ISOW7841 等把 UART 侧与总线侧电气隔离（磁耦/电容隔离 + 隔离电源），阻断地环流与高压串入，变频器、电力柜场景几乎必选。
  • TVS + 自恢复保险丝：A/B 线上双向 TVS（SMBJ12CA 类）吸收浪涌，PPTC 限制持续故障电流。
  • 共模电感：端口侧串共模扼流圈抑制高频干扰，常与 TVS 组成 EMC 三件套。
  • 失效保护收发器：SN65HVD 系列等在总线开路/短路/空闲时输出固定逻辑，替代外部偏置电阻。
  • 上电静默：MCU 复位期间 DE 引脚电平不确定，可能误发数据污染总线——DE 加上下拉电阻固定初态，或选上电三态的收发器。

八、485 集线器与拓扑扩展

当现场布线确实无法手拉手（多楼层、多方向出线），**RS485 集线器（Hub）**是合规解法：每个端口是独立隔离的收发段，主站侧一条线接入，下行分出多条总线，同时实现：

  • 星型布线的物理便利 + 每段独立的终端电阻配置；
  • 故障段自动隔离，不影响其他分支；
  • 级联延长距离，突破单段 1200 m 限制。

注意 Hub 只做电气转发，地址冲突仍需靠上层协议（如 Modbus 地址规划）解决；各级延迟叠加也要算进主站超时时间。

第五章：RS232

概念基础

  1. RS232 是 EIA 定义的串行物理层标准，规定电气电平、信号线与连接器（DB9）——「PC 老式 COM 口」背后的标准。
  2. 负逻辑电平：逻辑 1 是负电压（-5V~-15V），逻辑 0 是正电压（+5V~+15V），与 MCU 的 TTL UART（0/3.3V）完全不同，必须经 MAX232 等芯片做电平转换。
  3. 点对点、单端：一收一发加共地，抗干扰弱、典型距离 < 15m，速率与距离反相关。
  4. 为什么仍要学：工业仪器、老式 PLC、条码枪仍大量保留 DB9 口；PC 侧 USB 转 RS232 线依然是常用调试手段。
  5. 与 UART 的关系：UART 是控制器逻辑，RS232 是物理层电气标准；其上仍可跑 Modbus RTU 或自定义帧协议。

先看典型的 DTE-DCE 连接：

  PC[DTE PC] -->|TXD RXD GND| Conv[USB-RS232 转换]

一、电平与特点

  • 逻辑 1：负电压（如 -5V ~ -15V）
  • 逻辑 0：正电压（如 +5V ~ +15V）
  • 单端：抗干扰弱于 第六章：RS485 差分；距离通常 < 15m（与波特率反相关）。
  • 点对点：多机需额外切换，不像 RS485 总线型。

MCU 侧为 TTL 第四章：UART（0/3.3V），需 MAX232、SP3232 等芯片做电平转换。

电平门限细节

区域 发送端输出 接收端判定
逻辑 1（Mark） -5V ~ -15V -3V ~ -15V
不定区 — -3V ~ +3V
逻辑 0（Space） +5V ~ +15V +3V ~ +15V

±3V 之间是接收端的「不确定区」，给了线路衰减的裕量。注意两个容易混淆的点：

  • 空闲状态是逻辑 1 = 负电压，所以量到 -9V 左右说明链路正常待机，不是故障。
  • RS232 与 TTL 不仅电压不同，极性也相反（负逻辑 vs 正逻辑），MAX232 同时完成「升压」与「反相」两件事。

二、最小三线连接

交叉连接 TX/RX；不要把 RS232 口直接接 MCU UART 引脚。

DB9 引脚定义（DTE，PC 侧）

引脚 信号 方向 说明
2 RXD 输入 接收数据
3 TXD 输出 发送数据
5 GND — 信号地
7 RTS 输出 请求发送
8 CTS 输入 允许发送
4 DTR 输出 数据终端就绪
6 DSR 输入 数据设备就绪
1 DCD 输入 载波检测
9 RI 输入 振铃指示

DTE（数据终端，如 PC）与 DCE（数据设备，如 Modem）引脚定义相反，因此 DTE↔DCE 用直通线，两台 DTE 互连用交叉线（Null Modem）——买线时分清「直连串口线」和「交叉串口线」，接错表现为完全无数据。

三、流控（可选）

信号 作用
RTS/CTS 硬件流控，防缓冲区溢出
DTR/DSR 设备就绪（Modem 时代遗留）
软件流控 XON/XOFF 字符

嵌入式调试常 115200 8N1 无流控。

流控什么时候需要：

  • 硬件流控 RTS/CTS：接收方缓冲区将满时拉低 CTS（对端视角），发送方暂停。高速、大数据量、双方处理速度不匹配时启用。
  • 软件流控 XON/XOFF：接收方发 0x13（XOFF）要求停发、0x11（XON）恢复。只占用数据线，但二进制数据中若恰好出现 0x11/0x13 会被误吞，不适合透传任意二进制。
  • 多数现代场景：处理速度足够 → 直接无流控，配大缓冲区 + DMA 更省心。

四、速率与距离的关系

RS232 标准限定负载电容 ≤ 2500 pF，普通电缆每米约 40~150 pF，由此决定距离上限：

波特率 经验最大距离
9600 ~15 m（标准上限）
19200 ~15 m（需低电容电缆）
115200 2~3 m 内较稳妥

超出范围的表现不是「完全不通」，而是误码率上升、偶发乱码。要长距离：换 第六章：RS485 或加光电隔离中继。

五、应用场景

  • 工业仪器、老式 PLC、条码枪 DB9 口。
  • USB 转 RS232 dongle 在 PC 上模拟 COM 口。
  • 长距离、多机、抗干扰场景优先 RS485 或 以太网（第二章：Modbus TCP）。

协议层仍可能是 第一章：Modbus RTU 或自定义 ASCII 帧。

USB 转串口芯片选型

芯片 特点
CH340/CH341 最便宜，Windows 需装驱动，量产消费电子常用
CP2102/CP2104 免驱（Win10+ 自带），稳定性好
FT232 老牌稳定，支持 MPSSE 模式可模拟 SPI/I2C，价格高
PL2303 早期常见，注意市面上仿冒芯片与新版驱动不兼容

调试技巧

  • 环回测试：短接 DB9 的 2、3 脚，终端敲键应回显——30 秒确认串口线和驱动没问题。
  • 量电平：万用表测 TXD 对 GND，空闲应为 -5V 以下；若是 0V/+3.3V，说明量到的是 TTL 侧而非 RS232 侧。
  • 示波器看摆幅：健康 RS232 信号摆幅 ±9V 以上；只有 ±5V 的边缘设备在长线缆下容易误判。
  • 共地干扰：两台设备由不同插座供电时，地电位差会叠加在单端信号上——这是 RS232 在车间现场误码的头号原因，必要时上光电隔离 RS232 隔离器。

常见坑清单

现象 根因
接 MCU 后芯片发烫 RS232 电平直怼 TTL 引脚（±12V 超压）
完全无数据 直通线/交叉线用错；DB9 公母头定义想当然
数据隔字节丢 对端开了硬件流控而本端 RTS 悬空
远距离乱码 超 15m 或线缆电容超标，换低电容线或降波特率

六、隔离与中继

车间现场地电位差与浪涌是 RS232 的两大杀手，工程解法：

  • 光电隔离器：串接在链路中的 RS232 隔离器（内部光耦 + DC/DC 隔离电源），隔离耐压常见 2500Vrms，专治地环流与浪涌。
  • RS232↔RS485 转换器：不换协议只换物理层，距离立刻从 15 m 变 1200 m，是存量设备延寿的便宜方案。
  • 串口服务器：RS232 转以太网，老仪器直接接入局域网，上位机用虚拟 COM 或原始 TCP socket 访问。
  • 浪涌保护：户外进线加 TVS；雷击多发区光电隔离与 TVS 并用。

七、历史坐标

RS232 诞生于 1962 年（电传打字机与 Modem 互联），比大多数读者年龄都大；它的握手信号（DTR/DSR/RI）全是电话 Modem 时代的遗物。理解这些信号为什么存在，比背引脚定义更有价值——今天嵌入式常用的「三线最小连接」就是把 Modem 语义全部裁剪后的结果。它的思想（异步帧、流控、DTE/DCE 角色）也完整遗传给了后来的 USB CDC 与各种串口透传方案。

顺带一提连接器变迁：早期还有 DB25（完整 25 针定义），PC 时代收缩为 DB9，今天设备上更多是 3.5mm 耳机座、RJ45 走 RS232 电平等「伪装」形态——思科网络设备的 console 线就是 RJ45 承载 RS232 的著名例子。遇到非标接口先量电平再接线，是比查线序更保险的第一步。

八、RS232/RS422/RS485 三兄弟速查

项目 RS232 RS422 RS485
信号 单端 差分 差分
拓扑 点对点 一发多收 多机总线
双工 全双工 全双工（4 线） 半双工（2 线）为主
距离 ~15 m ~1200 m ~1200 m
驱动/接收数 1/1 1/10 32/32（标准负载）

一句话记忆：422 是「差分版 232」（单向广播、全双工），485 是「总线版 422」（多机、半双工）。三者电平互不兼容，互接必须用对应收发器或转换器，不能靠转接头混线。

第四章：UART

概念基础

  1. UART（通用异步收发器）是异步串行通信控制器：只用 TX/RX 两根信号线加共地，不传时钟，收发双方按约定的波特率各自采样。
  2. 异步帧：起始位(0) + 数据位(通常 8) + 可选校验位 + 停止位(1)；空闲为高电平，起始位拉低完成一次同步，数据 LSB 先发。
  3. 为什么无处不在：实现极简、调试直观，日志打印、AT 指令、GPS NMEA、Bootloader 都走 UART，是嵌入式最基础的调试与互联手段。
  4. 只是逻辑层：UART 引脚是 TTL 电平（0/3.3V），接 PC 老串口或工业总线需 MAX232（RS232）、MAX485（RS485） 等收发器转换物理层。
  5. 点对点：无从机地址、无仲裁，多机组网要靠上层协议或改用总线型物理层。

一、异步帧结构

  • 空闲：线路高电平。
  • 起始位：拉低，通知接收方开始采样。
  • LSB 先发：数据位从低位到高位。
  • 校验：None / Odd / Even（可选）。
  • 停止位：1 或 2 位高电平，恢复空闲。

逐位时序（以发送 0x55 为例，8N1）

接收方的采样策略：

  • 检测到下降沿后，等待 0.5 个位时间，在起始位中央采样确认仍为低（防毛刺误判）。
  • 之后每隔 1 个位时间采样一次，硬件 UART 通常每位过采样 16 次取中间值，容忍一定时钟误差。
  • 采样到停止位不是高电平 → 报帧错误（Framing Error），常见于波特率不匹配或线路干扰。

一帧的时间成本

8N1 配置下每字符 10 位：

波特率 位时间 每字符 每秒字符数（约）
9600 104 µs 1.04 ms 960
115200 8.68 µs 86.8 µs 11520
921600 1.09 µs 10.9 µs 92160

估算「打印一条日志会不会拖慢系统」时用得上：115200 下每秒最多输出约 11 KB。

二、波特率

常见：9600、115200、921600。收发双方波特率必须一致（误差通常 < 2%）。

波特率误差从哪来

  • 分频取整误差：72 MHz 时钟要 115200，USARTDIV = 39.0625，取整后实际 115107，误差 -0.08%，可接受；但某些时钟/波特率组合误差可达 1% 以上。
  • 内部 RC 振荡器温漂：HSI 典型 ±1%，高低温下更差——工业级产品串口建议用外部晶振。
  • 双方误差叠加：两端各偏 1%，叠加后逼近 2% 极限，边界工况开始丢字节。

经验法则：收发总误差 < 2% 可靠工作，< 1% 安心；超了就会出现「大部分正常、偶发乱码」这种最难排查的症状。

三、收发方式：轮询 / 中断 / DMA

选型建议：调试打印用阻塞或 DMA；AT 指令逐字节中断；GPS/数传等连续流式数据用 DMA + Idle 中断，配合环形缓冲区几乎不丢字节。

第三章：Modbus ASCII

概念基础

  1. Modbus ASCII 是 Modbus 的文本编码变体：每个字节用两个 ASCII 十六进制字符（0-9 A-F）表示，帧以 : 开始、CR LF 结束。
  2. 为什么存在：早期调制解调器/串口终端时代，文本帧人眼可读、可直接粘贴调试，字符间容忍度也比 RTU 严格的 3.5 字符静默宽松。
  3. 校验不同：RTU 用 CRC16，ASCII 用 LRC（8 位求和取补码）——检错能力较弱但实现极简。
  4. 代价：同样数据传输长度约 2 倍、带宽利用率低，新项目工业现场几乎都选 RTU，ASCII 只保留在老设备与维护口。
  5. 同一套 PDU：与 RTU/TCP 的功能码与寄存器语义完全一致，切换链路层不影响上层应用逻辑。

第二章：Modbus TCP

概念基础

  1. Modbus TCP 把 Modbus 的主从语义搬到以太网/TCP：报文仍是「功能码 + 数据」，但帧定界交给 TCP、校验交给 TCP 校验和，因此没有 CRC、没有静默时序。
  2. MBAP 头（7 字节）取代 RTU 的「从站地址 + 静默界定」：Transaction ID 让一条连接可区分多个并发事务，Unit ID 负责映射网关后的串口从站。
  3. 默认端口 502：约定俗成；接入即用，可跨交换机、跨网段访问远程设备，无需 485 布线与收发方向切换。
  4. 网关共存：大量存量设备仍是 RTU 串口设备，TCP ↔ RTU 网关完成两者转换，是工业现场新旧系统融合的典型形态。
  5. 边界：明文、无认证，安全只能靠工控内网隔离、VPN、TLS 隧道，绝不能直接暴露公网。

并发与超时实践

  • Transaction ID 递增：客户端每发一请求自增，响应原样带回，异步收发也能正确配对。
  • 连接数受限：很多小型 PLC 只支持 4~16 个并发 TCP 连接，SCADA 侧应做连接池 + 请求串行化。
  • 长连接保活：现场交换机可能静默回收空闲连接，建议启用 TCP Keepalive 或定期发空读。
  • 超时与重试：默认超时 1~3 s；超时后先重发同 Transaction ID 的请求，连续失败再重建连接。
  • 半开连接：PLC 掉电时 TCP 不会立刻断开，读取超时往往是唯一的故障信号。

四、串口网关

Modbus TCP ↔ RTU 网关：
Unit ID 映射 RS485 从站地址；网关内维护 第六章：RS485 轮询时序。

网关工作原理

  1. 网关收到 TCP 帧后，剥离 MBAP，按 Unit ID 查映射表得到串口从站地址。
  2. 重新计算 CRC16，拼成 RTU 帧发往 485 总线，并遵守 3.5 字符静默时序。
  3. 收到 RTU 应答后剥离 CRC，装回 MBAP（Transaction ID 取自原请求），经 TCP 回传。

注意坑点：

  • 串口是串行资源：多个 TCP 客户端并发请求同一串口总线时，网关内部必须排队，响应时间会被拉长。
  • 广播不可达：RTU 的地址 0 广播语义在多数网关上不支持转发。
  • Unit ID 冲突：部分网关把 Unit ID=255 保留给网关本身的寄存器。

  • Shodan 风险：公网暴露的 502 端口会被搜索引擎索引，工控安全事故中屡见不鲜。
  • 纵深防御：防火墙白名单限制源 IP；DMZ 区部署数据网关，控制网与办公网物理/逻辑隔离。
  • Modbus Security（2018）：规范定义的 TLS 版本（端口 802），支持证书认证，但现场普及率仍低。
  • 最小权限：读采集与写控制走不同账号/通道，写操作加二次确认。

八、性能与工程实践

  • 吞吐估算：一次读 10 寄存器往返约 24+31 字节，千兆网下毫秒级；瓶颈往往在 PLC 的扫描周期而非网络。
  • 轮询编排：采集上百个测点时按优先级分周期（快变量 100 ms、慢变量数秒），避免一次性洪泛请求压垮设备。
  • 寄存器合并：把相邻测点合并成一次连续读，减少事务数——这是上位机优化最常用的手段。
  • 写操作安全：关键控制写入后读回校验；通信中断时设备侧应有看门狗/安全状态（超时回到安全输出）。
  • 时间同步：数据采集打时间戳应在 PLC 侧做，而非以太网到达时刻（网络抖动会引入误差）。
  • 冗余：关键链路双网卡/双交换机；客户端断线自动重连 + 指数退避，避免风暴式重连打满 PLC 连接表。

第一章：Modbus RTU

概念基础

  1. Modbus 是 Modicon 于 1979 年为 PLC 设计的应用层主从协议，如今是工业通信最通用的事实标准之一；RTU 是其中「二进制编码 + 异步串口」的变体。
  2. 主从轮询模型：一个主站（PLC/SCADA）按从站地址轮询，从站永不主动上报，只有被寻址才应答——模型简单、时序确定、实现成本低。
  3. 帧结构极简：地址 + 功能码 + 数据 + CRC16，一帧即一次完整的请求/应答；统一的寄存器语义（线圈、保持寄存器等）让不同厂商设备能用同一套报文访问。
  4. 为什么选 RTU：跑在 RS485 差分总线上，一根双绞线可挂多设备、传数百米，抗干扰强、布线便宜，是工业现场最常见组合。
  5. 边界：RTU 只定义数据读写语义，不含认证加密；帧界定靠静默时间而非特殊字符，底层串口由 UART 控制器提供。

三、时序（RTU 特有）

帧间静默 ≥ 3.5 字符时间（与波特率相关），用于帧界定；波特率高时该间隔很短，实现需精确。

  • 115200 下对 MCU 中断延迟更敏感。
  • 半双工 第六章：RS485 需在发送前使能 DE。

3.5 字符时间怎么算

一个字符 = 起始位 + 8 数据位 + 校验/停止位 ≈ 11 bit（8N1 时）。则：

波特率 1 字符时间 3.5 字符时间
9600 ~1.146 ms ~4.01 ms
19200 ~0.573 ms ~2.01 ms
115200 ~95.6 µs ~335 µs

实现要点：

  • 用定时器 + 接收中断：每收到一字节重置定时器，定时器超时即判帧结束。
  • 高波特率（>19200）时规范允许固定 1.75 ms 简化实现。
  • 帧内字节间隔不得超过 1.5 字符时间，否则从站应丢弃该帧。
  • 从站应答前需保证 ≥ 3.5 字符的静默，避免与主站残余发送交叠。

第三章：数仓分层与数据管道调度

概念基础

  1. 数仓分层的目的是治理复杂度：ODS 贴源、DWD 明细、DIM 维度、DWS 汇总、ADS 应用——每层职责单一，下游依赖上游，坏数据能定位到层。
  2. 批流一体靠统一模型：Spark（第一章：Spark 大数据批处理入门）跑离线重算，Flink（第二章：Flink 流式计算入门）跑实时增量，两边共用口径才能「T+1 准确、实时大致对」互为校验。
  3. Kafka 是管道骨架：CDC 与日志先进 Kafka（第三章：Kafka 大数据数据总线）缓冲解耦，再分流到批/流/OLAP 各消费者。
  4. 调度是数据可靠性核心：Airflow/DolphinScheduler 把「每天 2 点跑批」变成有依赖、可重试、有告警的 DAG，而不是一堆 crontab。
  5. ClickHouse 承接分析层：DWS/ADS 汇总结果落到列存引擎供 BI 查询，见 ClickHouse：查询与性能调优。

本章聚焦管道编排与分层建模方法论；沙箱无 Airflow/Spark 集群，代码按 Airflow 2.x 官方语法书写未逐条运行验证。

各层建模案例

二、维度建模：星型与雪花

维度建模三件套：事实表（度量 + 外键）、维度表（描述性属性）、粒度声明（一行代表什么）。

模型 结构 取舍
星型 事实表直连各维表，维表反范式冗余 查询 Join 少、速度快，数仓主流
雪花 维表再拆子维表（商品→类目→行业） 省存储但 Join 链长，仅高基数层级用

事实表三种类型：

类型 语义 案例

周期快照事实表 定时快照状态，半可加 每日库存、每日账户余额
累积快照事实表 一行跟踪流程全生命周期，可更新 订单从下单→支付→发货→签收各时点

缓慢变化维（SCD）

维度属性会随时间变化（用户换城市、商品改类目），历史报表要不要跟着变？

类型 做法 适用
SCD1 直接覆盖，不留历史 不关心历史的属性（错别字修正）
SCD2 加版本行：生效/失效时间 + 当前标记 需要回溯历史（主流选择）
SCD3 加「前值」列，只记上一次 只需对比新旧两个值的场景

第五章：RAG 与向量检索实战

概念基础

  1. RAG = 检索增强生成：把私有知识向量化入库，提问时先检索最相关的片段塞进上下文，再让 LLM 作答——不用重训模型就能注入领域知识，是 LLM 落地性价比最高的路线。
  2. Embedding 是语义坐标系：文本被编码为高维向量（如 1024 维），语义相近的文本距离相近；「检索」从关键词匹配升级为最近邻搜索。
  3. 向量库专管 ANN：Milvus/Qdrant/pgvector 用 HNSW 等索引做近似最近邻查询，毫秒级从千万级向量里捞 Top-K；小规模用 Redis/Postgres 也能起步。
  4. 效果好坏在数据管道：切块（chunking）粒度、检索 Top-K、重排序（rerank）三件事对答案质量的影响大于换模型。
  5. 评估要有 ground truth：召回率（该找的找没找到）与答案忠实度（说的对不对）分开评，肉眼抽查不可持续。

本章把 RAG 概念落到工程实现。代码按 LangChain 0.3 / OpenAI SDK 官方 API 风格书写（沙箱未装依赖，未逐条运行验证）。

  2. 检索深度：先取 Top-20 再 rerank 到 Top-4（召回与精排分工）
  3. 混合检索：加 BM25，专治型号、代码、专有名词

九、评估指标：从召回到忠实度

指标 度量什么 计算方式

十、GraphRAG 简介

向量 RAG 把知识切成碎片，遇到”这些事件之间什么关系””整个语料的主线是什么”这类全局性、关系性问题会失灵。GraphRAG（微软开源）的思路：

  1. 离线索引时让 LLM 从每个 chunk 抽取实体与关系，构建知识图谱；
  2. 社区检测把图谱聚成主题簇，预生成社区摘要；
  3. 在线查询按类型分流：局部问题走实体邻域检索，全局问题走社区摘要问答。

代价是索引成本数倍于普通 RAG（每 chunk 多次 LLM 调用）。结论：默认从向量 + BM25 + rerank 起步，确认有全局分析类刚需再上 GraphRAG。

第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3

概念基础

QUIC（Quick UDP Internet Connections）是运行在 UDP 之上的可靠、加密、多路复用传输协议，是 HTTP/3 的底座：

  1. 解决什么问题：TCP 字节流「一丢全等」的队头阻塞、TCP + TLS 分层握手往返多、四元组一变连接即断——QUIC 在 UDP 上逐一重构。
  2. 三大关键设计：流（Stream）级隔离让丢包影响面缩小；内置 TLS 1.3 把加密与传输握手合并（目标 1-RTT 建连，0-RTT 可选加速）；Connection ID 让网络切换后连接依旧存活（连接迁移）。
  3. 实现在用户态：与 第一章：TCP 协议详解：连接、可靠传输与编程示例 内核栈不同，QUIC 多由用户态库（ngtcp2、quiche、MsQuic 等）实现，迭代快但排障更依赖日志与指标。
  4. 代价与前提：依赖 UDP/443 放行与企业网策略对齐；0-RTT 有重放风险，写操作需谨慎。

先看设计目标与作用的全貌：

一、设计目标与作用

1. 解决什么问题

  • 在 UDP 上重建可靠管道：丢包检测、重传、拥塞控制发生在 QUIC 层，而不依赖 第一章：TCP 协议详解：连接、可靠传输与编程示例 单一流上的队头阻塞。
  • 默认加密：传输与握手深度绑定 TLS 1.3（RFC 9001），减少「明文旁路」与分层带来的额外往返。
  • 多流与连接标识：Stream 隔离应用数据；Connection ID 让四元组变化时仍能延续同一逻辑连接（连接迁移）。

2. 相对 TCP + TLS 的典型取舍

问题 第一章：TCP 协议详解：连接、可靠传输与编程示例 + TLS 常见表现 QUIC 思路
队头阻塞 TCP 字节流级丢包会阻塞后续所有应用数据 QUIC 在流级相对独立地做丢包恢复
握手 RTT 常需 TCP 三次握手再叠 TLS 往返 常把加密与传输握手合并，目标 1-RTT 建连（0-RTT 为可选加速）
NAT 重绑定 四元组变化常被视作「新连接」 Connection ID 标识逻辑连接，支持连接迁移
中间设备 TCP 成熟、穿透好 依赖 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 放行（如 UDP/443）；企业网策略需对齐

二、连接与完整通信流程（原理）

QUIC 报文封装在 UDP 数据报中（常见 HTTPS 场景为 UDP/443）。以下极度简化，省略版本协商、重试包、地址验证等细节。

1. 建立连接（简化）

首包常带 TLS ClientHello；成功后在 1-RTT 密钥下发送应用数据。0-RTT 可在重复连接时提前带数据，见第五节安全注意。

带地址验证的完整握手（更接近真实）：



sequenceDiagram
  participant C as Client
  participant S as Server
  C->>S: Initial（TLS ClientHello）
  opt 服务端要求地址验证
    S-->>C: Retry（携带 token）
    C->>S: Initial（回显 token + ClientHello）
  end
  S-->>C: Initial（ACK）+ Handshake（ServerHello…Finished）
  C->>S: Handshake（Finished）+ 1-RTT 数据
  S-->>C: 1-RTT 响应数据

Retry 包的作用：服务端在投入连接状态之前，先让客户端证明「它真的拥有所声称的源地址」，从源头抑制地址伪造型放大攻击（QUIC 要求服务端在地址验证前发送的字节数不超过收到的 3 倍）。

2. 关闭连接（简化）

任一方可发送 CONNECTION_CLOSE 帧；对端进入排空（draining）期，不再发送新数据。与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 FIN/ACK 不同，QUIC 在连接粒度表达关闭，内部再回收流与 UDP 套接字资源。

3. 与典型「套接字 / 协议栈」的对应

与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 connect/accept 由内核一条龙完成不同，QUIC 一般由用户态库（如 ngtcp2、quiche、MsQuic、aioquic）或浏览器网络栈实现：底层仍是 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 sendto/recvfrom，其上是 TLS 1.3、ACK/重传、流控与 HTTP/3 帧。HTTP/3 客户端日常通过 curl --http3-only 或内置 HTTP/3 的 SDK 使用，而不是手写裸 UDP 报文。

三、包结构与帧（概念）

1. 长首部与短首部

项 长首部（Long Header） 短首部（Short Header）
用途 握手阶段（Initial / 0-RTT / Handshake / Retry） 建立后的 1-RTT 数据
明文可见 版本、DCID/SCID、包类型、长度 仅 DCID（与少量标志）
首部开销 较大 小（数据面常态）

2. 常见帧类型（RFC 9000 §19）

帧 作用
PADDING / PING 填充 / 保活探测
ACK 确认收到的包号范围（支持 ACK Range 与 ECN 计数）
CRYPTO 承载 TLS 1.3 握手字节流
STREAM 应用数据（携带 Stream ID、偏移、长度）
RESET_STREAM / STOP_SENDING 中止发送 / 请求对方停止发送
MAX_DATA / MAX_STREAM_DATA 连接级 / 流级流控窗口更新
NEW_CONNECTION_ID / RETIRE_CONNECTION_ID 签发与退役 CID（迁移与隐私）
CONNECTION_CLOSE 关闭连接（区分传输层与应用层错误码）
PATH_CHALLENGE / PATH_RESPONSE 连接迁移时的路径验证

四、流、可靠性与拥塞控制（原理要点）

  • Connection：加密上下文、ACK 与拥塞控制的归属单位（类似「一条加密了的类 TCP 管道」）。
  • Stream：单向或双向；HTTP/3 将请求/响应映射到不同流，减轻应用级队头阻塞。
  • Packet Number：单调递增，配合 ACK 范围与密钥更新，降低与 第一章：TCP 协议详解：连接、可靠传输与编程示例 序号相关的歧义；重传不重用旧 PN（新包新号）。
  • 拥塞控制：在 Connection 上运作（如 Cubic、BBR 等实现依栈而定），与 第一章：TCP 协议详解：连接、可靠传输与编程示例 一样受网络条件约束，但并非「一条字节流管所有多路复用对象」。

两级流控：MAX_DATA 限制整条连接的在途字节总量，MAX_STREAM_DATA 限制单条流——接收方两侧同时收紧，发送方须同时满足。流控窗口耗尽时发送方会被阻塞，Wireshark/qlog 中常见 blocked 事件即源于此。

Stream ID 编码（低 2 bit 表意）：bit0 区分发起方（0=客户端，1=服务端），bit1 区分方向（0=双向，1=单向）——例如客户端发起的第一个双向流 ID 为 0，服务端第一个单向流为 3。

五、Connection ID、端口与「会话标识」

  • UDP 四元组仍用于路由首个报文；Connection ID 使源 IP/端口变化（如蜂窝切换 Wi-Fi）后，对端仍能识别同一 QUIC 连接。
  • 公网 HTTP/3 常见端口为 443（UDP），与 第一章：TCP 协议详解：连接、可靠传输与编程示例 443 并存、互不替代。
  • 服务端可协商 CID 长度与轮换策略，以兼顾隐私与路由。

连接迁移时序（简化）：

  participant C as Client
  participant S as Server
  Note over C: 网络切换（Wi-Fi → 蜂窝），四元组变化
  C->>S: 新路径首发（PATH_CHALLENGE + 新 CID）

对比 第一章：TCP 协议详解：连接、可靠传输与编程示例：四元组任何一变即「新连接」、上层必须重连——这正是移动端体验上 QUIC 的核心卖点。

六、TLS 1.3 与 QUIC（原理）

QUIC 使用 TLS 1.3 做身份认证与密钥导出；载荷由 AEAD 保护，PADDING 等机制缓解流量分析。0-RTT 可加速重复连接，但存在重放风险：对金融类写操作应禁用或在应用层做幂等与二次校验。

加密分层细节：

  • 密钥分四级：Initial（从 DCID 公开导出，仅防被动观察者篡改）→ Handshake → 1-RTT（分 0-RTT 与应用数据），各级独立密钥。
  • 首部保护（Header Protection）：除版本与 CID 外，包号等元数据也加密——中间盒连「这是第几个包」都看不到，这是「防 ossification（协议僵化）」的刻意设计。
  • 密钥更新（Key Update）：长连接可轮换 1-RTT 密钥，限制单密钥加密的数据量。
