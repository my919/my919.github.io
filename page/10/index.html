1. 概念说明：为什么需要”对账”

背景：分布式系统没有完美的事务（2PC 性能差、TCC 复杂），生产实践是保证最终一致性 + 定期对账兜底。

对账的定义：定期把两边的数据拉出来比对（本地库 vs 渠道/对方系统），找出不一致并修复。

对账 vs 事务：

方式 保证 代价
分布式事务（TCC/2PC） 强一致 复杂、性能差、可用性下降
消息可靠投递 + 幂等 最终一致（大部分场景） 仍有极端丢失
对账（兜底） 最终一致（查漏补缺） 延迟发现（T+1）

结论：事务 + 消息保证”常态正确”，对账保证”出错能发现”——三者是组合关系，不是替代。

2. 对账方案对比

方案 原理 适用
全量对账 两边全量拉取比对 数据量小（万级）
增量对账 只比对变化窗口（如当日） 数据量大，生产主流
事件对账 每笔业务完成后立即登记，定时核对登记表 实时性要求高
渠道账单对账 用渠道提供的账单文件比对 支付/清算必备

生产标准组合：增量日对账（每日凌晨跑）+ 异常实时对账（关键单即时核对）。

8. 典型案例：Pod OOMKilled 与资源调优

问题背景：线上某 Java 服务频繁出现 OOMKilled，同时部分 Pod 处于 Pending 状态调度不了。经排查：limits.memory 设太小（256Mi）但 JVM 实际需要 512Mi；而 requests.cpu 设太大（2 核）导致节点资源不够调度。需要合理设置 requests/limits，平衡稳定性与资源利用率。

方案：

配置项 原值 调优值 原因
requests.memory 256Mi 300Mi 保证调度，略高于稳态
limits.memory 256Mi 768Mi 覆盖峰值 + 余量
requests.cpu 2000m 500m 稳态只需 0.5 核
limits.cpu 2000m 1000m 允许突发到 1 核

关键 Deployment：

踩坑点：

  1. limits.memory 必须大于 JVM 最大堆 + 非堆内存：JVM 内存 = 堆 + 元空间 + 线程栈 + 直接内存。只设 -Xmx512m 但 limits=512Mi 会因为非堆内存超限而 OOMKilled。建议 limits = Xmx * 1.5。
  2. requests 太大会导致 Pending：若 requests.cpu=2 但节点只剩 1.5 核，Pod 永远调度不了。requests 应按稳态而非峰值设置。
  3. 不设 limits 的风险：无 limits 时容器可占用节点全部资源，异常时可能拖垮整个节点。生产环境必须设 limits。

方法上挂 lru_cache 缓存挂类上被全继承体系共享，key 含 self 导致实例永不释放（见 7.5 冲突⑤） 在 __init__ 里建实例级缓存：self.f = lru_cache(...)(self._f)

1. 概念说明：HTTPS 与 TLS

HTTPS = HTTP + TLS，不是新协议——先经 TLS 加密、再传输 HTTP 报文。URL 以 https:// 开头，默认端口 443（明文 HTTP 为 80）。

TLS 提供三件事：

能力 说明
机密性 对称加密载荷，防窃听
完整性 MAC / AEAD 防篡改
身份认证 X.509 证书链证明「服务器是它声称的那个」

不解决什么：TLS 不能替代应用层鉴权与输入校验，https:// 不等于站点没有 XSS/CSRF 等业务漏洞。

握手定密钥，传输用对称：TLS 握手协商出对称会话密钥，之后 HTTP 记录用对称算法加密以获得性能。

key_share 在首个 ClientHello 就带上客户端的 (EC)DHE 公钥，省掉 TLS 1.2 里单独的 ServerKeyExchange 往返，这是 1-RTT 的关键。

0-RTT 风险：有重放风险，敏感操作应禁用或二次校验。

3. 证书链与主机名校验

浏览器/客户端会校验：

  1. 证书是否由受信任 CA 签发，链是否完整
  2. SAN（Subject Alternative Name） 是否覆盖当前访问主机名
  3. 有效期、吊销信息（OCSP Stapling 等）

证书关键字段（openssl x509 -text 可见）：

字段 含义
Subject / Issuer 持有者 / 签发者 DN
SAN 覆盖的域名列表（现代客户端以此为准）
Not Before / After 有效期
Subject Public Key Info 公钥算法与位长（RSA-2048、ECDSA P-256 等）
Authority Key Identifier 指向上级 CA，用于组链

自签名证书仅适合内网或开发，公网须使用可信 CA 或组织内 PKI。

4. ALPN

在 TLS 握手中通过 ALPN 协商应用层协议：h2 表示后续走 HTTP/2 帧；h3 与 QUIC/HTTP/3 相关（QUIC 内含 TLS 1.3 集成握手）。

11. 安全加固清单

  • 仅启用 TLS 1.2+（优先 1.3），禁用 SSLv3 / TLS 1.0 / 1.1

  • 私钥权限 chmod 600、与证书分离存放
  • 自动化续期（ACME / certbot）并监控到期时间
  • 全站 HTTPS：HTTP→HTTPS 301 跳转，杜绝 mixed content
