第一章：Kafka 消息中间件入门：核心概念与架构

概念基础

Apache Kafka 是分布式事件流平台：高吞吐、持久化、可回放的分区日志，用于消息队列、日志管道、流式处理与数据集成。本文侧重 MQ / 微服务视角。

  1. 本质是「分区日志」：每条消息只是追加到分区末尾的日志记录，不消费即删除，消费只移动游标（offset）——所以消息可以被多组消费者反复回放，这是它与 RabbitMQ 这类「消费即删除」传统 MQ 最大的差别。
  2. 为什么快：磁盘顺序写 + page cache + 零拷贝 + 批量压缩，单机即可达到十万级 TPS 量级；吞吐是 Kafka 设计的第一目标。
  3. 三大角色：当消息队列（削峰、解耦）、当日志总线（各系统日志/埋点统一进 Kafka）、当流计算数据源（Flink/Spark 从 Kafka 读）。本站对应：微服务集成见 第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展，大数据总线见 第三章：Kafka 大数据数据总线。
  4. 权衡：为吞吐放弃了部分「业务 MQ」能力（无内置延迟消息、事务消息偏流式），这些场景通常选 RocketMQ（见本章对照小节与 第四章：RocketMQ 核心概念与架构）。

先看它的整体架构：

flowchart LR
  P[Producer] --> B[Broker]

核心概念

概念 说明
Topic 逻辑消息流名称
Partition Topic 的分片，有序日志；并行度与分区数相关
Offset 分区内每条消息的唯一递增序号
Producer 写入消息，可指定 key 做分区路由
Consumer Group 组内消费者分摊分区，同组不重复消费同一分区
Broker 存储与 Serving 分区的服务器进程

消息持久化在磁盘（顺序写 + page cache），可配置保留时间与大小。

理解要点：「分区内有序、分区间无序」——需要顺序的业务（同一订单的状态变更）必须用同一 key 路由到同一分区；并行度上限 = 分区数，消费者实例多于分区数时空闲。

生产者与消费者

1. 生产者

  • acks：0 / 1 / all 权衡延迟与持久性。
  • 幂等生产者：避免重试导致重复（下游仍可能需要业务去重）。
  • 事务：跨分区 exactly-once 与 Kafka Streams 场景。

2. 消费者

  • auto.offset.reset：earliest / latest。
  • 手动提交 offset：处理成功后再 commitSync / commitAsync。
  • 再均衡（Rebalance）：组成员变化时重新分配分区；消费逻辑应支持幂等。

3. 投递语义（需业务配合）

语义 说明
At most once 先提交 offset 再处理，可能丢
At least once 先处理再提交，可能重复
Exactly once 事务 + 幂等存储，成本高

分区、副本与 ISR

  • Leader / Follower：每个分区一个 Leader 负责读写，Follower 同步。
  • ISR（In-Sync Replicas）：与 Leader 差距在阈值内的副本；min.insync.replicas 与 acks=all 共同定义「写成功」。
  • 扩容：增加分区数不会重分布历史 key；规划分区数宜前置。

KRaft 与 ZooKeeper

Kafka 3.x+ 可用 KRaft（内置 Raft 元数据）替代 ZooKeeper。新集群建议 KRaft；存量 ZK 集群按官方迁移指南操作。本站 第二章：Docker 部署 Kafka 实践 采用 KRaft 单节点示例。

与 RocketMQ 的对照

维度 Kafka RocketMQ
模型 分区日志、流式优先 Topic + Queue、顺序/延迟/事务消息
生态 Connect、Streams、Flink/Spark 国内电商、SCA 集成
典型场景 日志、指标、CDC、流计算 订单、定时、强业务 MQ

部署与命令行探测

生产注意事项

项 建议
分区数 与消费者并行度、磁盘并行写相关；不宜过少
保留 retention.ms 与磁盘容量；合规场景可能需归档到对象存储

要点 结论
本质 分区日志：追加写、可回放、消费只动 offset

第四章：Nginx 缓存与性能调优

概念基础

  1. 缓存在网关层最划算：proxy_cache 让重复的后端响应停在 Nginx 本地磁盘/内存，QPS 高峰被削平，后端直接减负。
  2. 压缩是免费带宽：gzip（文本）与 brotli（第三方模块）能把 JS/CSS 压到原体积 20%~30%，首屏时间立竿见影。
  3. 静态路径靠 sendfile：sendfile + tcp_nopush 走内核零拷贝，open_file_cache 缓存文件元数据——静态服务的三连优化。
  4. 容量公式要心里有数：最大连接 ≈ worker_processes × worker_connections；长连接 keepalive 减少握手次数。
  5. 调优先测量：改参数前先 ab/wrk 压测拿基线，盯 access_log 的 $request_time 与系统 CPU/内存，避免「凭感觉调参」。

第三章：Nginx HTTPS 与安全

概念基础

  1. TLS 终结点：证书挂在 Nginx，客户端到 Nginx 走加密，Nginx 到后端走内网明文——证书申请、续期、算法升级集中在一处。
  2. 证书链要完整：浏览器校验的是「站点证书 → 中间证书 → 根证书」整条链，漏发中间证书是「本地 curl 通、用户浏览器报错」的常见根因。
  3. 301 比配置加密更重要：HTTP 全站 301 跳转 HTTPS，并配合 HSTS 头让浏览器后续强制走 TLS。
  4. 安全是分层的：TLS 之外，还有限流（limit_req）、访问控制（allow/deny、auth_basic）、安全响应头，每层挡一类攻击。
  5. 密码学背景看 OpenSSL：算法、密钥、证书格式等原理见 第一章：OpenSSL 命令行入门与常用操作总览，本章聚焦落地。

本章 openssl 自签命令已在 OpenSSL 3.x 验证；nginx 配置基于官方语法书写（沙箱未装 nginx）。

第二章：Nginx 反向代理与负载均衡

概念基础

  1. 反向代理是系统入口：客户端只认识 Nginx，真实后端（Spring Boot/Node/Go）藏在 upstream 里——发布、扩缩容、灰度都对客户端无感。
  2. upstream 是逻辑集群：多个后端实例组成一个名字，proxy_pass http://集群名 即完成负载均衡；默认轮询，还有权重、ip_hash、least_conn。
  3. 转发要补头：后端想拿到真实 IP、真实协议，必须配 X-Real-IP、X-Forwarded-For、X-Forwarded-Proto——漏配是日志全是 127.0.0.1 的元凶。
  4. proxy_pass 末尾斜杠有语义：带 / 会替换 location 前缀，不带则原样拼接——路径多一层/少一层的事故九成出在这。
  5. 连接也要调参：proxy_http_version 1.1 + keepalive 复用连接，超时/缓冲/大文件上传各有专属参数。

本章承接 第一章：Nginx 入门与静态服务 的 location 语法，配置基于 nginx 1.24+ 官方语法书写（沙箱未装 nginx，未逐条运行验证）。

一、最小反向代理

头 作用
Host 透传原域名，后端按域名路由/生成绝对链接
X-Real-IP 客户端真实 IP（单层代理）
X-Forwarded-For 代理链 IP 列表，$proxy_add_x_forwarded_for 自动追加
X-Forwarded-Proto 客户端是 http 还是 https（后端生成 https 链接必需）

二、proxy_pass 路径规则（高频坑）

记忆法：proxy_pass 的 URL 部分会替换掉 location 匹配的部分；不带路径（只有 host:port）则原样透传。改一条 proxy_pass 必跑 nginx -t + 抓包/日志确认后端实际收到的路径。

三、upstream 与负载均衡策略

策略对比：

策略 写法 适用
轮询（默认） 无参数 无状态服务
加权轮询 weight=n 机器配置不均
ip_hash ip_hash; 会话粘性（同 IP 固定打同实例）
least_conn least_conn; 请求耗时不均，优先打空闲实例

故障摘除：后端挂掉 Nginx 自动重试下一个（proxy_next_upstream），配合 max_fails=3 fail_timeout=30s 控制判定阈值。

SSE/流式响应必须关缓冲：proxy_buffering off;（或后端发 X-Accel-Buffering: no），否则事件被攒着不吐。

第一章：Nginx 入门与静态服务

概念基础

  1. 事件驱动架构：Nginx 用一个 worker 进程 + epoll 事件循环处理成千上万连接，不像 Apache 那样一连接一线程——这是「高并发低内存」的根源。
  2. master/worker 模型：master 读配置、管 worker；worker 真正处理请求。nginx -s reload 平滑切换的底气就在于此。
  3. 配置是分层树：main → events → http → server → location，作用域向下继承；server 按域名分流，location 按 URI 前缀/正则分流。
  4. 静态服务的强项：sendfile 零拷贝直接从内核送文件，root + try_files 组合是托管前端构建产物（dist）的事实标准。
  5. 一切皆模块：限流、缓存、重写、gzip 开箱即用，也是 K8s Ingress Controller 的主流实现之一。

本章是 Nginx 系列起点：安装、配置结构、静态站点与日志。反向代理见 第二章：Nginx 反向代理与负载均衡，HTTPS 见 第三章：Nginx HTTPS 与安全，缓存与调优见 第四章：Nginx 缓存与性能调优。

Git 版本控制入门

概念基础

  1. 分布式版本控制：每个开发者本地都有完整的仓库与历史，提交、分支、回滚离线可用；GitHub/Gitee 等远端只是同步与协作节点。
  2. 三大工作区流转：工作区 → 暂存区（git add）→ 本地仓库（git commit）→ 远程仓库（git push），理解这条流水线就掌握了日常九成操作。
  3. 分支极其轻量：分支只是指向提交的可移动指针，创建与切换几乎零成本，因此鼓励「功能分支 + 合并」的协作方式。
  4. 改历史要克制：未推送的提交可用 reset 自由整理；已推送的公共历史应使用 revert 生成反向提交，避免强推坑队友。
  5. 配置先行：首次使用先全局配置 user.name / user.email，提交记录才有可信的作者信息。

十、rebase：变基与历史整理

git rebase（变基）会把当前分支上「自分歧点以来」的提交逐条摘下、再依次重放到指定的新基之上，使历史变成一条直线。常用于同步上游更新、整理杂乱提交、换一个更合适的基础分支。

一句话区分：merge 保留分叉历史（生成合并提交），rebase 改写历史为线性（重放提交、哈希会变）。

6. 已推送分支的 rebase：黄金法则与强推

黄金法则：不要 rebase 已推送、且他人可能基于其开发的历史。因为 rebase 会改写提交哈希，他人 pull 时会出现「历史分叉」，被迫处理大量冲突甚至重复提交。

因此：

  • main / develop 等公共分支：只 merge，不 rebase。
  • 个人功能分支：rebase 后需强推覆盖远程，且确认无他人使用：
  • 用 --force-with-lease 而非 --force：若远程有你未拉取的新提交，它会拒绝推送，避免误覆盖他人劳动。
  • 已开启分支保护的分支（如 main）通常禁止强推，rebase 后推不上去是预期行为。

8. rebase 与 merge 的取舍

需求 更合适
公共分支同步、保留完整分叉历史 git merge
个人分支同步上游、追求线性历史 git rebase
清理碎提交、改写未推送历史 git rebase -i
拉取更新且不想留「Merge branch」噪音 git pull --rebase

记法：公共历史用 merge（只增不改），私有历史用 rebase（可改可整）。

第一章：Linux 常用命令与运维入门

概念基础

  1. 内核与发行版：Linux 内核只有一份，日常使用的是「内核 + 包管理器 + 软件仓库」组成的发行版（RHEL 系、Debian 系、Arch 等），选型直接决定包管理器与生态。
  2. 一切皆文件：配置（/etc）、可变数据（/var）、设备与进程信息都以文件形式呈现，运维工作的本质常常就是「读文件、改文件、管进程」。
  3. 权限模型：每个文件有 user / group / other 三组 rwx 权限，chmod / chown 是多用户系统的第一道防线。
  4. Shell 是操作入口：默认多为 bash，脚本首行 #!/bin/bash；服务器运维的主战场是命令行而非图形界面。
  5. 服务由 systemd 托管：常驻服务以 .service 单元交给 systemd 管理，systemctl / journalctl 是服务排障的标配工具。

第四章：PyTorch 部署与分布式

概念基础

  1. 训练与推理是两种工程：训练求快求全（Python 动态图），部署求稳求小（静态图、无 Python 依赖、常驻服务）。
  2. ONNX 是推理通用货币：把模型导出为 ONNX 后，可用 ONNX Runtime、OpenCV cv2.dnn（见 第五章：视频与深度学习）、TensorRT 等引擎推理，摆脱 Python 环境。
  3. DDP 是多卡标配：每卡一份完整模型 + 独立 DataLoader 分片，前向各算各的、反向自动同步梯度——比早期的 DP 快且稳。
  4. 服务化就是套壳 HTTP：FastAPI 包一层推理函数即可上线；关键在 batch 合并、并发与预热，不在框架。
  5. 大模型时代的延伸：单卡装不下 → 模型并行/ZeRO（FSDP）；Hugging Face Transformers（见 第三章：LLM 大语言模型基础）把这一层封装好。

一、模型导出：TorchScript 与 ONNX

2. ONNX 导出（跨框架部署首选）

方案 优点 适用

二、FastAPI 服务化

上线三件事：model.eval() + inference_mode()（必做）；推理进程与训练进程分开部署；给服务加超时与限流（Nginx 层见 第三章：Nginx HTTPS 与安全）。

三、DDP 多卡训练

DDP 三条铁律：模型先 .to(device) 再包 DDP；DataLoader 必须用 DistributedSampler；保存权重用 model.module.state_dict() 且只在 rank 0 做。

四、大规模训练一瞥

技术 一句话 工具
FSDP / ZeRO 参数/梯度/优化器状态分片到各卡，单卡装得下超大模型 torch.distributed.fsdp

一般工程结论：多卡数据并行（DDP）覆盖绝大多数场景；模型大到单卡放不下才进 FSDP/量化的世界。

第三章：PyTorch GPU 加速与混合精度

发表于 2026-05-01 更新于 2026-09-01 分类于 AI 本文字数： 1.1k 阅读时长 ≈ 4 分钟

第三章：PyTorch GPU 加速与混合精度

概念基础

  1. GPU 擅长并行不擅长分支：大矩阵乘/卷积在 GPU 上快几十倍；数据搬运（CPU↔GPU）反而是瓶颈，少拷贝、大批次是优化方向。
  2. 设备要对齐：模型与数据必须在同一设备，RuntimeError: Expected all tensors to be on the same device 是新手第一错。
  3. AMP 混合精度的本质：前向用 FP16/BF16 省显存提速，梯度更新用 FP32 保精度；autocast + GradScaler（FP16 场景）成对出现。
  4. 显存不够不等于换卡：梯度累积等效大 batch、梯度检查点用算力换显存、小批次 + 累加，都是工程正解。
  5. 测量优先：torch.cuda.synchronize() + 计时、nvidia-smi 看占用，先定位瓶颈（数据加载 or 计算 or 搬运）再优化。

本章承接 第二章：PyTorch 模型与训练 的训练模板。代码按 PyTorch 2.x 官方 API 书写（沙箱无 GPU 与 torch，未逐条运行验证）。

一、设备管理

省一个错误的三行习惯：

别在循环里写 torch.cuda.current_device() 之类的查询；多卡选卡用 CUDA_VISIBLE_DEVICES=1,2 python train.py 从环境层面隔离最干净。

二、混合精度训练（AMP）

要点：

环节 说明
autocast 只包前向 + loss；backward 在上下文外
GradScaler FP16 必需；BF16 不需要 scaler（dtype=torch.bfloat16）
梯度裁剪 必须夹在 unscale_ 与 step 之间
显存收益 权重/激活约省一半，batch 可开大一倍以上

A100/H100 等新卡优先 BF16：指数位与 FP32 相同，无下溢问题，代码更简单（省去 scaler）。

三、显存不够怎么办

1. 梯度累积：小 batch 等效大 batch

2. 梯度检查点：用算力换显存

3. 其他手段

定位显存泄漏：

泄漏最常见原因：把带计算图的 loss/tensor 存进了 list（应 loss.item()），或在验证循环里忘了 no_grad()。

四、torch.compile：内核融合提速

适用 不适用
固定 shape 的静态网络（CNN、MLP） 动态 shape 频繁变化（重编译开销大）
长时间训练（编译费一次摊薄） 短脚本/交互调试

五、测量：瓶颈在哪

瓶颈判别：

现象 瓶颈 对策
GPU 利用率忽高忽低 数据加载跟不上 num_workers 加大、persistent_workers=True、预取
GPU 利用率恒定但很慢 计算本身 AMP、torch.compile、减小模型
memory_allocated 不高但 OOM 显存碎片 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
CPU 单核吃满 DataLoader 简化 __getitem__、预处理离线化

本章小结

要点 结论
设备 模型与每个 batch 都 .to(device)；non_blocking + pin_memory 提速搬运
AMP autocast 包前向，FP16 配 GradScaler；BF16 免 scaler
显存 梯度累积等效大 batch；checkpoint 换显存；memory_allocated 定位泄漏
编译 torch.compile 对固定 shape 长训练收益最大
测量 计时前 synchronize()；GPU 忽高忽低查数据加载

第二章：PyTorch 模型与训练

发表于 2026-05-01 更新于 2026-09-01 分类于 AI 本文字数： 1k 阅读时长 ≈ 3 分钟

第二章：PyTorch 模型与训练

概念基础

  1. nn.Module 是模型的骨架：继承后在 __init__ 里声明层、在 forward 里组织数据流；参数注册、.to(device)、state_dict 保存全部自动获得。
  2. Dataset/DataLoader 解耦数据与模型：Dataset 定义「第 i 条样本怎么取」，DataLoader 负责批量化、打乱、多进程预取——大数据训练的前提。
  3. 训练循环是固定四步：optimizer.zero_grad() → forward → loss.backward() → optimizer.step()，一切复杂训练都是这四步的变体。
  4. train/eval 切换不可少：Dropout、BatchNorm 在训练与推理行为不同；验证前必须 model.eval()，验证后 model.train()。
  5. 泛化靠工程手段：验证集监控、早停、学习率调度、正则化（weight_decay/Dropout）共同决定模型能否落地。

本章承接 第一章：PyTorch 入门与张量 的张量与 autograd。代码按 PyTorch 2.x 官方 API 书写（沙箱未装 torch，未逐条运行验证）。

一、定义模型：nn.Module

常用层速查：

层 用途
nn.Linear(in, out) 全连接
nn.Conv2d(cin, cout, k) 图像卷积
nn.BatchNorm2d(c) / LayerNorm 归一化（稳定训练）
nn.ReLU / GELU 激活
nn.Embedding(vocab, dim) 离散 ID → 向量（NLP 必备）
nn.LSTM / nn.TransformerEncoder 序列建模

二、Dataset 与 DataLoader

  • num_workers：多进程预取，CPU 密集的预处理必开；Windows 下要在 if __name__ == "__main__": 里跑。
  • pin_memory=True：页锁定内存加速 CPU→GPU 拷贝（配合第三章）。
  • 变长序列：用 collate_fn 自定义打包（padding + mask）。

三、训练循环：完整模板

四大高频翻车点：

症状 原因
loss 不降 学习率过大/过小；标签与 logits 形状不配
loss 变 NaN lr 过大爆炸、除零、FP16 溢出（见第三章 GradScaler）
验证 acc 虚高 忘了 model.eval()，Dropout 还在随机丢弃
显存随轮次上涨 把带计算图的 loss 累加到 list（应 loss.item()）

四、断点续训：保存与恢复

推荐保存 state_dict() 而非整个模型对象：反序列化整个对象要求类定义路径一致，state_dict 只存权重、跨代码结构可用。

五、回归与二分类的损失选择

任务 输出层 损失函数
多分类 Linear(→n_classes) CrossEntropyLoss
二分类 Linear(→1) BCEWithLogitsLoss
回归 Linear(→1) MSELoss / HuberLoss
多标签 Linear(→n) BCEWithLogitsLoss（标签 multi-hot）

本章小结

要点 结论
模型 继承 nn.Module，__init__ 声明层、forward 串数据流
数据 Dataset 取样 + DataLoader 批量化；变长数据用 collate_fn
训练四步 zero_grad → forward → backward → step；验证前 model.eval()
排障 NaN 查 lr/精度；显存涨查计算图泄漏；acc 虚高查 eval 切换
存取 存 state_dict() + 优化器状态，跨机器恢复
