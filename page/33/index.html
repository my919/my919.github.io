第四章：构建与工程实践

概念基础

  1. 编译四阶段：预处理（-E）→ 编译（-S）→ 汇编（-c）→ 链接——理解各阶段产物是排查「头文件缺失 / 未定义引用」的基础。
  2. 静态库 vs 动态库：.a 链进可执行文件（体积大、部署简单），.so 运行时加载（体积小、可热更新但需管理路径）。
  3. Make 是 C 工程的事实构建标准：依赖关系 + 增量编译，几十行 Makefile 管理中型项目绰绰有余。
  4. 调试三件套：gdb（断点/查看）、ASan（内存错误）、perf（性能热点）——修复效率取决于工具而非脑补。
  5. C ABI 是互操作边界：头文件 + 符号约定是所有语言与 C 打交道的接口，extern "C"、void*、回调是三大常见桥接。

本章承接 第三章：字符串与常用标准库，是 C 系列收官章。示例基于 gcc 14 / GNU make。

一、gcc 工具链与编译四阶段

常用选项 作用
-Wall -Wextra 高强度告警；-Werror 告警即错误
-g 生成调试信息（gdb/ASan 符号必需）
-O0/-O2/-Os 优化等级：调试用 O0、发布用 O2、嵌入用 Os
-std=c11/-std=c17 指定标准，避免 GNU 扩展依赖
-I/-L/-l 头文件路径 / 库路径 / 链接库名（-lm 数学库）
-fsanitize=address,undefined ASan+UBSan 运行时检查

调试构建与发布构建分离：make DEBUG=1 走 -O0 -g -fsanitize，发布走 -O2 -DNDEBUG（关闭 assert）。

二、多文件组织与头文件

头文件三规则：

  1. include guard（或 #pragma once）防重复包含。
  2. 头文件只放声明（类型/原型/宏），定义放 .c——static 保持内部链接。
  3. 头文件自身可独立编译（自带所需 include）。

三、Makefile

四个自动变量：$@ 目标、$^ 全部依赖、$< 首个依赖、$(SRC:.c=.o) 模式替换。TAB 缩进是 Makefile 的铁律（空格报错）。

四、静态库与动态库

维度 静态库 .a 动态库 .so
链接时机 编译期拷入 运行时加载
体积 可执行文件大 共享，多程序复用
升级 需重新链接 替换 .so 即可
部署 单文件简单 需管理库路径/版本（soname）

运行时找不到 .so 是新手高频问题：LD_LIBRARY_PATH 临时、ldconfig 配 /etc/ld.so.conf 持久、或编译时 -Wl,-rpath,/path 内嵌路径。

五、调试与性能

run / next / step 运行 / 逐过程 / 逐语句（可进函数）
print expr 查看变量（p *s、p arr[2]@3）
bt 崩溃回溯调用栈（配合 core 文件）
watch var 数据断点：变量被改即停
info locals / frame n 局部变量 / 切栈帧

2. perf 热点分析

六、C ABI 与 FFI 桥接

1. 被 C++/Rust/Python 调用：稳定 ABI 头

三个桥接惯例：

  1. extern "C"：关闭 C++ 名字修饰，符号保持 C 约定。
  2. 不透明指针（typedef struct X X;）：实现隐藏在 .c，跨语言只需传指针。
  3. 回调传函数指针 + void *user_data：C 侧「多态」的标准接缝（见第二章）。

七、常见陷阱

陷阱 说明
未定义引用 忘链库/漏 .c 文件；-l 顺序在后（gcc main.o -lfoo）
头文件循环包含 guard 只防重入；互引改前置声明 struct X;

.so 找不到 rpath/ldconfig/LD_LIBRARY_PATH 三选一

要点 结论

头文件 guard + 只声明；static 内部链接；可独立编译
Makefile 自动变量 $@ $^ $<；DEBUG 分流；TAB 铁律

调试 gdb 断点/watch/bt+core；perf record 热点；ASan 抓内存错
FFI extern “C” + 不透明指针 + 回调 user_data 三惯例

第三章：字符串与常用标准库

概念基础

  1. 字符串即约定：C 没有字符串类型，只有「以 '\0' 结尾的 char 数组」这一约定——所有 str* 函数都依赖这个约定，长度信息不存在于类型中，越界由此而生。
  2. 安全边界是第一课：strcpy/sprintf/gets 不检查边界，是缓冲区溢出漏洞的历史源头；现代代码一律 snprintf/strncat（小心）/长度校验。
  3. 标准库分层清晰：stdio.h（IO）、string.h（内存/串）、stdlib.h（分配/转换/退出）、time.h（时间）、math.h（数学）覆盖 80% 日常需求。
  4. 格式串即契约：printf/scanf 的格式符必须与实参类型严格匹配（%zu 对 size_t、%lld 对 long long），不匹配是 UB；gcc -Wformat 能查出大半。
  5. 本章目标：把日常高频库函数串成速查手册，每个函数标注安全用法与替代方案。

本章承接 第二章：指针、数组与内存管理。示例在 gcc 14 下编译运行验证。

第二章：指针、数组与内存管理

概念基础

  1. 指针是 C 的灵魂：直接持有内存地址，是高效数据结构（链表/树/回调）与系统编程的基石，也是绝大多数 C 缺陷（越界、悬空、泄漏）的源头——理解指针才算入门 C。
  2. 内存五段模型：代码段、数据段、BSS、堆（malloc）、栈（局部变量）——变量的生命期与存放位置由此决定。
  3. 动态内存四函数：malloc/calloc/realloc/free 成对出现，谁分配谁释放；双重释放与悬空指针是未定义行为（UB）。
  4. 工具可验证：-fsanitize=address（ASan）能在运行时精确报告越界/UAF，valgrind 报告泄漏——现代 C 开发标配，不是可选项。
  5. 本章目标：从指针算术到函数指针、从栈帧到堆分配，建立完整的 C 内存心智模型。

本章承接 第一章：C 语言基础 的类型与语法。示例均可在 gcc 下用 gcc -Wall -fsanitize=address 编译验证。

一、指针基础回顾与指针大小

sizeof(指针) == sizeof(所指类型)？错。指针大小取决于平台字长（x86-64 全是 8），与所指类型无关——它是「地址」不是「盒子」。

二、指针与数组

a[i] 就是 *(a + i)——下标运算是指针算术的语法糖。数组退化为指针后长度信息丢失，跨函数必须「指针 + 长度」配套传递。

三、多级指针与 const

读法：从右往左——int *const b 读作「b 是 const 指针，指向 int」；const int *a 读作「a 指向 const int」。

四、函数指针：回调的基石

函数指针用于回调（qsort/信号处理）、策略切换、C 语言「多态」（结构体内嵌函数指针表，见第四章）。

五、栈与堆：内存五段模型

区域 生命期 管理者 典型错误
栈 所在函数执行期 自动 返回局部变量地址、大数组爆栈（默认 8MB）
堆 malloc 到 free 程序员 泄漏、双重释放、UAF
数据/BSS 整个程序 自动 全局状态滥用
代码段 整个程序 只读 写字符串字面量（UB）

六、动态内存四函数

四条铁律：

  1. 成对：每个 malloc/calloc/realloc 恰有一个 free；所有权在模块边界写清楚。
  2. 检查 NULL：分配失败返回 NULL，解引用即 UB。
  3. realloc 用临时变量接：直接 p = realloc(p, ...) 失败时原地址丢失 → 泄漏。
  4. free 后置 NULL：free(NULL) 安全，free(悬空) 是 UB。

七、内存错误的检测与预防

ASan（AddressSanitizer）实战

错误清单与对策

错误 后果 对策

八、常见陷阱

陷阱 说明
数组退化为指针 跨函数丢失长度，必须配长度参数
sizeof 在指针上 sizeof(p) 是指针大小，不是所指缓冲大小
realloc 直赋 失败丢原地址，用临时变量接
malloc 不判空 失败返回 NULL，解引用即崩
字符串字面量不可写 char *s = "hi"; s[0]='H'; UB，用 char s[] = "hi"
栈 8MB 限制 大缓冲区上堆；递归深度控制
返回局部变量地址 返回 static、堆或传出参数
指针算术越界 仅同数组内合法，end（尾后）可比较不可解引用

本章小结

要点 结论
指针本质 存地址、按所指类型移动；大小=平台字长，与类型无关
数组 a[i] ≡ *(a+i)；退化为指针后长度丢失，传「指针+长度」
函数指针 回调与 C 式多态基石，qsort 比较函数是标准范式
内存五段 栈自动/堆手动；返回栈地址是经典 UB
动态内存 malloc/calloc/realloc/free 成对；realloc 临时变量接；free 置 NULL
工具 -fsanitize=address 运行时抓错，valgrind 查泄漏，-Wall -Wextra 编译期拦截

第一章：C 语言基础

概念基础

  1. 编译型语言：源码经预处理 → 编译 → 汇编 → 链接生成机器码直接执行，不依赖虚拟机，执行路径清晰、开销可预期。
  2. 贴近机器模型：指针、内存布局、调用约定都可由程序员掌控，至今仍是操作系统内核、嵌入式、高性能库的事实标准之一。
  3. 小核心、大标准库：语言关键字很少，能力来自 ISO C 标准库（stdio.h、stdlib.h、string.h 等）与平台 API。
  4. 可移植性：遵循 ISO C（如 C99、C11）的代码在多数平台用对应工具链重新编译即可；平台差异隔离在少量实现定义处。
  5. C ABI 是互操作边界：几乎所有语言都提供与 C 的互操作（FFI），系统级编程绕不开 C。

一、语言特点（为何仍值得学）

  • 贴近机器模型：整型与指针宽度、内存布局、调用约定都可由实现定义，便于写驱动、解释器底层、与汇编或硬件协同。
  • 表达力强、语法紧凑：少量关键字即可完成算法与数据结构；没有面向对象语法糖，但可用结构体 + 函数指针组织模块。
  • 可移植性：遵循 ISO C（如 C99、C11）的代码在多数平台用对应工具链即可重新编译；与平台相关的部分通常隔离在少量文件中。
  • 生态成熟：几乎所有系统提供 C 调用约定，其他语言常以 C ABI 为边界导出/导入库。

二、最小程序与翻译单元

每个可执行程序必须有一个 main 入口（宿主环境下常见两种签名之一）：

  • #include：预处理阶段把头文件文本插入当前翻译单元；<stdio.h> 等尖括号形式通常表示系统/实现提供的头。
  • return 0：向操作系统报告成功退出；省略时 C99 起对 main 有特殊规则（等价于返回 0），其他函数仍必须显式返回值（或 void）。

三、基本类型与字面量

3.1 整数与字符

  • char：至少 8 位，可表示字符（常与 unsigned char 用于字节）；signed char / unsigned char 与 char 是否带符号由实现定义。
  • short / int / long / long long：各有 signed / unsigned 变体；宽度随平台变化，可移植代码应使用 <stdint.h> 中的 int32_t、uint64_t 等定宽别名（若平台提供）。
  • 整数字面量：42（int）、42U（unsigned）、42L（long）、0x2A（十六进制）、052（八进制，易踩坑，少用）。

3.2 浮点

  • float / double / long double：遵循 IEEE 754 的实现上，double 最常用；不要用 == 比较浮点相等，应比较误差或使用整数域计算。

3.3 void 与派生类型

  • void：无值类型，用于「无返回值」或「通用指针」void *（可指向任意对象，不能直接解引用，需先转换）。

四、变量、作用域与存储期

  • 自动变量：块内 int x = 1;，进入块分配（概念上在栈帧），离开块结束生命期；未初始化则值不确定。
  • static（局部）：仍只在块内可见，但只初始化一次，生命期贯穿程序。
  • static（全局/函数）：内部链接，仅在当前翻译单元可见，避免符号冲突。
  • extern：声明在其他翻译单元定义的全局对象或函数。

五、运算符与控制流

5.1 常用运算符

  • 算术：+ - * / %；整数相除向零截断。
  • 关系与逻辑：< <= > >= == !=、&& || !；短路求值：a && b 中 a 为假则不计算 b。
  • 位运算：& | ^ ~ << >>；仅对无符号或明确语义时使用移位更安全。
  • 三元：cond ? a : b。
  • 复合赋值：+=、-= 等。

5.2 分支与循环

  • switch 的 case 通常需要 break，否则落入下一分支（fall-through），有时故意利用，多数情况要避免。

六、数组与指针

6.1 数组

  • 数组名在大多数表达式中会退化为指向首元素的指针，不携带长度信息；跨函数传递数组时常传指针 + 长度或使用哨兵（如字符串的 '\0'）。

6.2 指针

  • NULL：空指针常量；解引用空指针是未定义行为。
  • 指针算术：p + 1 按所指类型大小移动；仅对同一数组对象内或尾后一位置才有标准保证。

6.3 字符串

  • C 字符串是以 '\0' 结尾的 char 序列；字面量 "hi" 类型为 char 数组，在表达式中退化为 char *（C++ 中为 const char *）。
  • 常用 <string.h>：strlen、strcmp、strcpy（注意缓冲区溢出，优先 strncpy/snprintf 或自行边界检查）。

七、函数

  • 按值传递：形参是实参的副本；要通过函数修改调用方变量，传指针。
  • 原型：C99 起调用前必须可见原型，否则旧式隐式声明规则已移除，利于编译器检查实参个数与类型。
  • static 函数：仅本翻译单元可见。

八、结构体、联合体与枚举

8.1 结构体

  • 内存布局：可能有填充字节以满足对齐；不要假设 sizeof 等于各成员之和。
  • typedef 可为 struct 起别名，减少每次写 struct 关键字。

8.2 联合体与枚举

  • union：成员共享同一块存储，同一时刻通常只应语义上使用其中一个成员；写入与读取不同类型成员涉及有效类型规则，滥用为未定义行为。
  • enum：提供命名整型常量；底层仍为整数类型，不提供新类型安全边界。

九、动态内存

  • malloc / calloc / realloc / free：成对使用；双重 free、使用已 free 的指针均为未定义行为。
  • 谁分配谁释放：在模块边界约定清晰，避免交叉所有权。

十、预处理与宏

  • #include / #define / #if 在编译前由预处理器处理；宏不做类型检查，复杂逻辑优先 static inline 函数 或枚举常量。

十一、与「安全可移植」相关的习惯

  • 显式 {} 包住 if/for 体，避免宏或维护时出错。
  • 比较时把常量放左侧：if (NULL == p) 可防止误写 =。
  • 整数运算注意溢出（有符号溢出为未定义行为）；必要时用更大宽度或检查范围。
  • 使用 -Wall -Wextra -Werror（在可接受时）与静态分析工具，尽早暴露问题。

第二章：TypeScript 语言入门：类型系统与工程实践

概念基础

  1. TS = JS + 类型系统：TypeScript 是 JavaScript 的超集，在 JS 语法之上叠加静态类型；合法 JS 代码基本就是合法 TS 代码，存量项目可以平滑迁移。
  2. 编译期检查：类型不匹配、属性拼错、漏传参数在 tsc 编译期就报错，而不是等上线后在运行时炸掉——这是它与纯 JS「跑到才知道」最大的差别。

第一章：Netty 网络编程框架入门

概念基础

  1. Netty 是基于 Java NIO 的异步事件驱动网络应用框架：帮你快速开发高性能、高可维护性的协议服务器与客户端，而不必直面原生 NIO 的复杂 API。

第二章：IO 多路复用与 Netty 线程模型

概念基础

  1. I/O 多路复用在干什么：一条线程调用 Selector.select() 阻塞等待，直到一批 Channel 上有就绪的 I/O 事件（可读、可写等），再依次分发处理——一条线程可以注册并监视成千上万个连接，而不是为每个连接各开一条阻塞线程。
  2. 「很多连接」≠「每条连接占满一条线程」：大量长连接（推送、网关、IM 在线）中许多连接长时间无读写，适合交给一个 Selector 统一等就绪；高 QPS 短连接的瓶颈常在 CPU、GC、协议栈，与「单 Selector 挂很多空闲连接」不是同一维度的问题。
  3. Netty 扮演的角色：在 Java NIO / Epoll（Linux） 之上封装了 Reactor 风格的 EventLoop、Pipeline、内存与缓冲策略，让你用少量 EventLoop 线程管理大量 Channel，并把编解码、业务入 ChannelPipeline。
  4. 线程模型与前提：Boss 负责 accept 新连接并注册给 Worker；每个 Worker EventLoop 是「一条线程 + 一个 Selector」。业务若阻塞（重度 CPU、同步 JDBC、大 Thread.sleep）会占满该 EventLoop 上的所有 Channel——阻塞操作必须丢到业务线程池，这是多路复用发挥作用的前提。
  5. 上量边界：连接规模还受进程最大打开文件数、内核参数、堆外内存约束，多路复用属于应用层模型，不能替代容量规划。

Netty 常见线程模型（Boss / Worker）

1. 典型服务端写法（概念）

  • bossGroup：线程数常为 1（也可更多），负责接受新连接并把 SocketChannel 注册进 workerGroup 中某个 EventLoop 的 Selector。
  • workerGroup：每个 NioEventLoop 内一条线程 + 一个 Selector，多路复用其上的所有 Channel 的读/写就绪事件。整体是少量线程 + 大量连接，业务逻辑仍在 Pipeline 里按事件触发执行。

2. 一张逻辑关系（文字版）

角色 大致职责

Worker EventLoop 已连接 Channel 的读/写就绪事件、入站出站 Pipeline

第三章：Netty 核心组件深入

概念基础

  1. 从「能跑」到「能调」：第二章的 Echo 示例只用了最简的 ChannelInboundHandlerAdapter，真正写协议、做调优时必须理解 Channel / EventLoop / Pipeline / ByteBuf 四件套的协作机制。
  2. 组件即契约：Netty 的所有高级能力（编解码、零拷贝、心跳、线程切换）都建立在这四个组件之上；掌握它们的 API 与生命周期，是读懂源码、定位问题的前提。
  3. ByteBuf 是 Netty 的「内存」：与 JDK ByteBuffer 不同，ByteBuf 用读写指针分离、堆内/堆外双模、池化分配三项设计，撑起高吞吐与低 GC。
  4. Pipeline 是「加工流水线」：每个 Channel 绑定一条 ChannelPipeline，入站/出站事件在 Handler 链上双向传播，编解码与业务逻辑都是流水线上的一个工位。
  5. EventLoop 是「执行器」：一个 Channel 终身绑定一个 EventLoop（一条线程），所有事件都在该线程串行执行——这是 Netty 无线程安全担忧的关键。

二、EventLoop 与 EventLoopGroup：执行器

EventLoop = 一条线程 + 一个任务队列（NIO 下还绑一个 Selector）。核心契约：

  1. 一个 Channel 终身只属于一个 EventLoop（注册时分配，不再变更）。
  2. 该 Channel 的所有事件（读、写、触发 Handler）都在这个 EventLoop 的线程上执行。
  3. 因此同一 Channel 上的 Handler 无需加锁——单线程串行。

1. 线程数与分配

新 Channel 注册时，EventLoopGroup 按轮询挑一个 EventLoop 绑定给它，使连接均匀分散。

2. 在 EventLoop 上调度任务

若从非 EventLoop 线程访问 Channel，Netty 会把操作封装成 task投递到该 EventLoop 队列，保证线程安全。这也是 ch.writeAndFlush() 可在任意线程调用的原因。

3. 阻塞操作是头号陷阱

EventLoop 上挂了大量 Channel，若某 Handler 内执行 Thread.sleep、同步 JDBC、重 CPU 计算，会拖死该 EventLoop 上所有连接。正确做法见 第六章：Netty 高级特性与性能调优——把阻塞操作丢进业务线程池。

三、ChannelPipeline 与 Handler：加工流水线

第四章：编解码与粘包拆包

概念基础

  1. TCP 是字节流，不是消息流：发送方连续 write 两条消息，接收方可能一次读到两条粘在一起（粘包），也可能读到半条（拆包）。这是 TCP 本性，不是 bug。
  2. Netty 的解决思路：在 Pipeline 入口加一个 FrameDecoder（帧解码器），按某种边界规则把字节流切成一条条完整消息，再交给后续 Handler。
  3. 编解码两层：解码（Decoder） 把字节→对象（入站方向），编码（Encoder） 把对象→字节（出站方向）。二者常成对出现，组成「协议层」。
  4. 内置即用：Netty 预置了按换行、分隔符、长度域等切分的解码器，覆盖大多数二进制协议；不满足时继承 ByteToMessageDecoder 自定义。
  5. 正确性 > 性能：编解码是协议正确性的根基，错一个长度域会触发整条连接崩溃。务必先保证语义正确，再做池化/零拷贝优化。

八、常见陷阱

陷阱 说明
漏 FrameDecoder 业务直接读 ByteBuf，粘包下解析错乱。任何二进制协议都必须先切包
MessageToByteEncoder 不释放 框架会释放 encode 产出的 ByteBuf；但若你 write 的是外部传入的 ByteBuf，需自己管理引用计数
解码 throw 异常未处理 异常会触发 exceptionCaught，默认关闭连接；非法帧应记录日志后 ctx.close()
LengthFieldBasedFrameDecoder 参数错 长度值含不含长度字段自身、有没有调整量，配错会一直读到错位数据。打印十六进制对照
未限制最大帧长 maxFrameLength 过大或缺失，恶意端发巨帧触发 OOM
StringDecoder 后又当 ByteBuf 用 一旦解码成 String，下游类型已变，不会再有 ByteBuf
