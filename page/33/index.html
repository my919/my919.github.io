第四章：PostgreSQL 高级查询

概念基础

  1. 单表 SELECT 之上：多表连接（JOIN）、子查询与 EXISTS、集合运算（UNION）、CTE（WITH）、窗口函数——把散落在多张表里的数据拼成业务想要的答案。
  2. 为什么重要：报表、榜单、去重、累计等需求，本质都是查询表达能力；能用一条 SQL 讲清楚的，就不必拉到应用内存里拼装。
  3. PostgreSQL 特色武器：DISTINCT ON 每组取一条、FILTER 条件聚合、string_agg 有序拼串——这些在 MySQL 里要绕着写的写法，PG 是一等公民。
  4. 学习方法：先用下文「示例数据」一键建表，逐条 SQL 亲手跑一遍并对照示例结果；会写之后再进阶到执行计划（见 第五章：PostgreSQL 索引与性能优化）看快不快。

3. 分桶与首尾：ntile / first_value / last_value

4. 帧子句：累计与滑动窗口

GROUPS 按同值分组框定 介于两者之间

七、LATERAL：让子查询引用左侧的行

第三章：PostgreSQL 存储引擎与表访问方法

发表于 2026-05-03 更新于 2026-10-25 分类于 数据库 本文字数： 5.2k 阅读时长 ≈ 5 分钟

第三章：PostgreSQL 存储引擎与表访问方法

概念基础

  1. 表访问方法（Table Access Method）：PostgreSQL 12+ 把「表数据如何组织与读写」抽象为可插拔接口，建表时可用 USING 指定，默认即 heap——这是 PostgreSQL 语境里最接近 MySQL「引擎」的概念。
  2. 堆表（Heap）：行按写入顺序无序堆放在页中，用 tid（块号 + 行号） 定位；索引里存的是 tid，查数据通常要「索引 → 回表」。
  3. MVCC 是配套设计：行头维护 xmin / xmax 版本信息，更新与删除产生新版本 / 死元组，由 VACUUM 回收——这直接决定了 PostgreSQL 的性能调优姿势。
  4. 与 MySQL 的本质差别：MySQL 建表时选 ENGINE=InnoDB，PostgreSQL 没有这个开关：统一内核 + 统一 heap，列存、分片等需求走扩展与架构层，而不是换「引擎」。

先看默认的存储方式：

一、表数据默认怎么存：Heap（堆表）

  • 普通 CREATE TABLE 默认即 heap 表：行以堆页存放，通过 tid（块号 + 行号） 定位。
  • MVCC 在元组头维护版本信息（xmin / xmax 等），更新与删除产生新版本/死元组，依赖 VACUUM 回收（见 第五章：PostgreSQL 索引与性能优化）。
  • 与 InnoDB 聚簇索引即整表不同：PostgreSQL 主键索引是二级索引，堆上存行，主键查找通常「索引 → 回表 tid」。

1. 堆页内部结构

每个堆页默认 8KB（编译期 BLCKSZ），从前往后分四段：

  • PageHeaderData：LSN、校验和、空闲空间起止位置等页级元数据。
  • ItemId（行指针）数组：定长 4 字节，记录页内每个元组的偏移与长度——tid 里的「行号」实际是这个数组的下标，索引指向行指针而非物理位置，所以页内整理（如 HOT 链修剪）不必改索引。
  • 元组区：从页尾向前生长，每行带 23 字节行头（xmin / xmax / ctid / 标志位等）。

2. 行头与 MVCC 版本链

每行元组头部的关键字段：

字段 作用
xmin 创建该行版本的事务 ID
xmax 删除/更新该行版本的事务 ID（0 表示存活）
ctid 指向下一版本的 tid（更新形成版本链）
t_infomask 标志位：事务是否已提交、行是否被锁等

一次 UPDATE = 插入新元组 + 把旧元组 xmax 置为当前事务 + ctid 指向新位置。这就是「更新在 PG 里本质是新增一版」的物理含义，也是死元组与膨胀的来源。

二、TOAST：大字段的行外存储

8KB 页放不下的超长字段（text、大 jsonb、bytea）由 TOAST（The Oversized-Attribute Storage Technique） 接管：超阈值（约 2KB）的值被压缩和/或切片存入附属 TOAST 表，主表行里只留指针。

每张宽表自动挂一张 pg_toast.pg_toast_<oid> 附属表：

四种存储策略（建表时可按列指定）：

策略 压缩 行外存储 适用列
PLAIN 否 否 短字段、int 等定长类型（默认）
EXTENDED 是 是 超长 text / jsonb（变长类型默认）
EXTERNAL 否 是 已压缩的二进制（图片、已 gzip 数据）
MAIN 是 尽量不 中等长度、想留在主表的字段

性能含义：SELECT 不碰 TOAST 列时不读 TOAST 表（天然列裁剪）；但更新 TOAST 列会产生整个新副本——频繁更新的超大字段要考虑拆分表。

三、HOT 更新与 FILLFACTOR

HOT（Heap Only Tuple）更新：当 UPDATE 不改任何索引列且同页有空位时，新元组直接放同页、索引条目不动——省掉一次索引维护 IO，热点行更新快很多。

参数 含义 建议
fillfactor=100（默认） 页塞满才开新页 只增不改的表（日志、数仓）
fillfactor=80~90 预留 10~20% 空间 高频 UPDATE 且不改索引列的表
改了索引列的 UPDATE 无法 HOT 设计上把「状态字段」与「索引字段」分离

判断 HOT 是否生效：

hot_pct 低 + 表膨胀快：检查是否更新了索引列，或 fillfactor 太满。

四、FSM 与 VM：两个辅助映射

映射 全称 作用
FSM Free Space Map（空闲空间映射） 记录每页剩余空间，插入时快速找页，不用全表翻
VM Visibility Map（可见性映射） 标记「页内所有行对所有事务可见」——Index Only Scan 靠它跳过回表；VACUUM 靠它跳过干净页

实务联动：大批量 UPDATE/DELETE 后 VM 失效 → Index Only Scan 退化为 Index Scan + 回表 → 执行计划里 Heap Fetches 暴涨。跑一次 VACUUM ANALYZE 表名 重建 VM 即恢复（详见 第五章：PostgreSQL 索引与性能优化）。

五、表访问方法（Table Access Method）

PostgreSQL 12+ 起，表可指定 USING heap（默认）；理论上可挂自定义表访问方法（需扩展提供）。
生产常见仍是 heap；列存、混存等多在扩展或外部产品（如某些分析型方案）中实现，不等价于 MySQL 换一个 ENGINE 字符串。

六、与「引擎」易混的几个概念

概念 说明
TABLESPACE 表/索引的文件放置位置（如 pg_default），不是另一种行存储引擎。
TOAST 大字段行外存储机制，对用户基本透明。
Foreign Data Wrapper（FDW） 外部表：数据在远程；语法像本地表，语义与本地 heap 完全不同，不是换存储引擎。
内置索引类型 B-Tree、Hash、GiST、GIN、BRIN 等是索引访问方法，不是替换 heap 的「表引擎」。

七、和 MySQL InnoDB 的粗对照（选型沟通用）

话题 MySQL（MySQL引擎.md） PostgreSQL（本文）
建表选「引擎」 ENGINE=InnoDB 等 无；默认 heap + 统一内核
行存与主键 InnoDB 聚簇主键与数据同树 堆行 + 主键索引
并发读写的核心 InnoDB MVCC + 锁 MVCC + 行锁（见 第六章：PostgreSQL 并发与 MVCC 入门）

八、WAL：堆页之外的第二套写入

heap 页是「数据落盘的最终形态」，但每次写先走 WAL（Write-Ahead Log）：

  1. 事务修改先在内存缓冲区改页，同时把重做记录追加进 WAL 缓冲区。
  2. COMMIT 时只需 WAL 刷盘（wal_writer / commit 触发 fsync）即算持久——数据页由后台 checkpointer 批量脏写。
  3. 崩溃重启时按 WAL 重放，把未落盘的修改补回数据页。

实务含义：顺序追加的 WAL 远快于随机写数据页——这是 PG 写入性能的根基；WAL 所在磁盘（可用 pg_wal 独立表空间/挂载点）的延迟直接决定提交延迟。

九、分区表：heap 的「水平切片」

声明式分区（PG 10+）把一张逻辑表切成多张物理 heap 子表，每个分区独立享有自己的页、FSM、VM 与索引：

收益 原理
分区裁剪 查询带分区键时只扫命中的子表，等效索引之外的「粗粒度裁剪」
快速归档 DROP TABLE orders_2025_01 或 DETACH PARTITION 秒级删旧数据，不产生死元组
分区级维护 VACUUM / REINDEX 可按分区跑，大表运维粒度变细

取舍：分区数控制在几百以内（过多拖慢规划）；分区键必须出现在所有唯一约束里；查询不带分区键时反而要扫所有分区。

十、实务建议

  1. 学习 PostgreSQL 时少问「用哪个引擎」，多问索引类型、执行计划、VACUUM、隔离级别与锁。
  2. 需要列存、分片、多副本高可用时，在架构层选专用扩展或产品（如 Citus、云厂商数仓、读写分离），而不是在 CREATE TABLE 里找一个 ENGINE 开关。
  3. 版本升级（16 → 17 → 18）会带执行器与优化器演进，「升级引擎」口语上常指升级主版本，与 MySQL 的 ENGINE 不是同一概念。
  4. 写多的表先想 fillfactor 与 HOT，宽表先想 TOAST 策略，只读大表先想 VM 与 Index Only Scan——三个杠杆都长在 heap 结构之上。

第六章：MySQL 存储引擎

概念基础

存储引擎是 MySQL 「表数据如何存、如何取」的可插拔实现：

  1. 分层架构的产物：Server 层负责 SQL 解析、优化、权限；引擎层负责数据在磁盘与内存上的组织——索引结构、事务、锁、崩溃恢复都由引擎决定；同一份表结构，换引擎行为完全不同。
  2. InnoDB 是唯一默认答案：支持 ACID 事务、行级锁、MVCC、崩溃恢复（redo / undo）、聚簇索引与外键；官方默认且推荐，第五章讲的 B+ 树与回表，说的就是 InnoDB 的组织方式。
  3. MyISAM 是历史遗产：表级锁、不支持事务、崩溃安全性弱，只存在于老系统与只读库中；新业务一律避开——它也解释了第三章「表锁并发差」的历史背景。
  4. 换引擎不解决性能问题：性能瓶颈优先从索引、SQL 写法、事务与连接设计入手（第三、四、五章的内容）；引擎选型是「事务要不要」的问题，不是「快不快」的问题。
  5. 插件式带来专用选择：ARCHIVE（冷归档压缩）、CSV（数据管道交换）、BLACKHOLE（写入即弃的中继）、NDB（分布式集群）各有专属场景，是否可用以 SHOW ENGINES 为准。

InnoDB 架构深入：内存与磁盘的协作

InnoDB 的高性能不是来自单一技巧，而是内存结构 + 磁盘结构 + 后台线程三者协作的结果。理解下面四个组件，才能解释「为什么写入快、为什么崩溃不丢数据」。

1. 缓冲池（Buffer Pool）

  • 定位：InnoDB 最大的内存区域，缓存数据页与索引页（默认页大小 16KB）；读请求先查缓冲池，命中则零磁盘 I/O。

  • 淘汰策略：改良版 LRU——新读入的页先放在「中点」（约 5/8 处），全表扫描的页不会立刻挤掉热数据，由 innodb_old_blocks_pct / innodb_old_blocks_time 控制。
  • 脏页刷盘：修改先在内存中进行，页变「脏页」后由后台线程异步刷回磁盘；这就是写入快的第一层原因。

2. Change Buffer（写缓冲）

  • 解决的问题：二级索引页的更新是随机 I/O——更新一行可能要改散落在磁盘各处的多个索引页。
  • 做法：若目标二级索引页不在缓冲池，先把变更记录到 Change Buffer（缓冲池的一部分），稍后在页被读入内存时再合并（merge），把随机写变成顺序写。
  • 限制：只对非唯一二级索引有效；唯一索引必须立刻读页做唯一性检查，无法缓冲。
  • 适用场景：写多读少、二级索引多的表（如日志表）；8.0 起由 innodb_change_buffering 控制（默认 all）。

3. Doublewrite Buffer（双写缓冲）

  • 解决的问题：页部分写（partial page write）——16KB 的页在操作系统 4KB 扇区下可能只写了一半就宕机，redo log 无法修复不完整的页。
  • 做法：刷脏页时先把页顺序写入共享表空间的 doublewrite 区（2 份，约 2MB×2），确认成功后再写回数据文件；崩溃恢复时若发现数据文件页损坏，从 doublewrite 拷贝完整页再用 redo 前滚。
  • 代价与取舍：带来约一倍写入量，但 doublewrite 区是顺序写，实际开销通常 <10%；严禁为追求性能关闭（innodb_doublewrite=ON 默认）。

4. 自适应哈希索引（Adaptive Hash Index, AHI）

  • InnoDB 观察到某些索引值被频繁等值访问时，自动在内存中为其建立哈希索引，把 B+ 树的 O(log n) 查找降为 O(1)。
  • 全自动：由 innodb_adaptive_hash_index 控制（默认 ON），无需人工干预；高并发下 AHI 的互斥锁偶成瓶颈，可通过 SHOW ENGINE INNODB STATUS 的 SEMAPHORES 段观察，必要时关闭。

5. Redo 与 Undo 的分工回顾

日志 作用 物理/逻辑

第五章：MySQL 索引与性能优化

发表于 2026-05-03 更新于 2026-10-25 分类于 MySQL 深入 本文字数： 7.7k 阅读时长 ≈ 7 分钟

第五章：MySQL 索引与性能优化

概念基础

索引是数据库用额外空间与写成本换取查询速度的有序数据结构：

  1. 本质是一棵 B+ 树：把无序的表数据额外组织成有序树，查询从「全表逐行扫」变成「沿树下降读少量页」——随机 I/O 大幅减少；代价是每次 INSERT/UPDATE/DELETE 都要同步维护树，所以索引不是越多越好。
  2. 聚簇索引即数据本身：InnoDB 表数据按主键组织成 B+ 树，叶子节点存「主键 + 整行」；二级索引叶子只存「索引列 + 主键」，命中后常需回表再查一次聚簇索引——这就是主键要自增、查询要少 SELECT * 的根因。
  3. 联合索引遵守最左前缀：(a, b, c) 先按 a 排、a 相同再按 b、再按 c；跳过 a 的条件用不上树，等值列在前、范围列在后是最常见的设计。
  4. 覆盖索引是回表的解药：查询列全在索引里就只扫索引不回表（EXPLAIN 显示 Using index）；与之配套的 ICP 把过滤条件下推到引擎层，进一步少回表。
  5. 优化是一个闭环而非玄学：慢日志抓 Top SQL → EXPLAIN 看 type / key / rows / Extra → 改索引或改写法 → 再对比慢日志；本章同时覆盖事务隔离与备份恢复，给出完整的「开发侧性能地图」。

从 B+ 树的直觉开始：

一、索引在干什么：B+ 树直觉（够用版）

InnoDB 里，表数据按主键组织成一棵 B+ 树（聚簇索引）：叶子节点存「主键 + 整行数据」。
二级索引（你建的 INDEX / UNIQUE）叶子节点存「索引列 + 主键」，需要整行时往往要再回表到聚簇索引取数据。

读图要点：上层结点只存分界键与子树指针；最底层叶子由双向链表串起，方便范围扫描；聚簇索引叶子是主键 + 行数据；二级索引叶子多一步按主键回表读完整行。

直觉：

  • 等值 / 范围命中索引列 → 树高度低、少读页 → 随机 I/O 变少。
  • 全表扫 → 叶子链顺序读，数据量一大就慢。
  • 索引不是越多越好：每次 INSERT/UPDATE/DELETE 都可能维护多棵索引树。

二、联合索引与最左前缀

联合索引 KEY idx_abc (a, b, c) 的排序语义是：先按 a，再 a 相同时按 b，再按 c。

能较好利用该索引的典型条件（示意）：

  • WHERE a = ?
  • WHERE a = ? AND b = ?
  • WHERE a = ? AND b BETWEEN ? AND ?

容易用不上或只用一截的情况：

  • WHERE b = ? AND c = ?（缺 a，与「最左」不一致）
  • WHERE a = ? OR d = ?（OR 另一侧常走另一条路径，易优化成 UNION 或改写法）
  • 对 a 做函数/隐式类型转换导致无法走树（例如 WHERE DATE(a_col) = ...）。

设计经验：把区分度高、过滤性大的列尽量放左侧；把范围查询列放联合索引右侧更常见（仍要结合 EXPLAIN 验证）。

最左前缀案例集（逐条对照）

设有订单表与联合索引：

查询写法 能否用上 idx_u_s_c 原因
WHERE user_id = 100 ✅ 用到第 1 列 命中最左列
WHERE user_id = 100 AND status = 1 ✅ 用到前 2 列 连续等值
WHERE user_id = 100 AND status = 1 AND created_at > '2026-01-01' ✅ 全用上（范围列截断） 范围之后无法再精确定位，但范围本身也走索引
WHERE user_id = 100 AND created_at > '2026-01-01' ⚠️ 只用第 1 列 跳过中间的 status，后续列无法参与定位（仅索引过滤）
WHERE status = 1 AND user_id = 100 ✅ 用到前 2 列 优化器会重排等值条件，书写顺序不影响
WHERE status = 1 ❌ 不走（或全索引扫） 缺最左列 user_id
WHERE user_id = 100 ORDER BY status, created_at ✅ 顺便免排序 索引天然有序，Extra 无 Using filesort
WHERE DATE(created_at) = '2026-06-01' ❌ 函数包裹失效 应改写为范围：created_at >= '2026-06-01' AND created_at < '2026-06-02'
WHERE amount = 99.00 ❌ 不在索引中 索引列未覆盖

记忆口诀：等值连续从左走，范围命中就停口；函数隐转全没有，排序分组能搭手。

三、覆盖索引（Using index）

若 SELECT 里出现的列都能从某条二级索引的叶子直接凑齐（含 WHERE 用到的索引列），InnoDB 可能只扫索引、不回表，EXPLAIN 的 Extra 常见 Using index。

典型收益：大宽表上只查少数列 + 条件列恰好在同一联合索引上，I/O 明显下降。

覆盖索引实例对比

实战推论：

  1. 列表接口只 SELECT 需要的列，常能把慢查询「救」成覆盖索引；
  2. 热点查询可以把展示列一起放进联合索引尾部（适度冗余换免回表），但索引变宽后写放大与缓存占用同步上升，需权衡；
  3. 二级索引叶子天然带主键，所以 SELECT id 永远不需要额外加主键列进索引。

四、索引条件下推 ICP

Index Condition Pushdown：把部分 WHERE 条件下推到存储引擎层，在索引扫描过程中就过滤，少回表。
在 EXPLAIN 里常见 Using index condition（与 Using index 不同：后者多为覆盖索引）。

ICP 生效前 vs 生效后

  • 无 ICP（5.6 之前）：引擎按 user_id = 100 扫出所有索引项 → 每行回表取整行 → 再由 Server 层过滤 created_at；回表次数 = user_id=100 的全部行数。
  • 有 ICP（默认开启）：created_at LIKE '2026-06%' 被下推到引擎层，在索引扫描途中就用索引里的 created_at 列先过滤一遍，只有通过的行才回表；Extra 显示 Using index condition。

结论：ICP 对「联合索引只命中前缀、剩余列做过滤」的场景收益最大；它不改变索引选择，只减少回表行数。

九、索引进阶：MRR、隐形索引、索引合并与选型决策树

1. MRR（Multi-Range Read，回表前的「攒批排序」）

问题：二级索引范围扫描命中 N 行后，需要按主键回表 N 次——主键无序时这是 N 次随机 I/O。

做法（MRR）：先把命中的主键收集到 buffer 排序，再按主键顺序回表，把随机 I/O 尽量变成顺序 I/O。EXPLAIN 的 Extra 中可见 Using MRR。

适用：非覆盖索引的范围扫描（如 BETWEEN、大 IN 列表）；等值点查无所谓 MRR。它与 ICP 是同一链路上的两个优化：ICP 减少「要回表的行数」，MRR 优化「回表的 I/O 方式」。

2. 隐形索引（Invisible Index，8.0+）

  • 隐藏后优化器当它不存在，但索引仍随 DML 维护（不产生回滚风险）；
  • 典型用途：想删索引又怕删错——先 INVISIBLE 观察一段时间，确认无慢查询再真正 DROP；也可用来 A/B 验证某索引是否被使用；
  • 主键不能隐藏；全局开关 optimizer_switch = 'use_invisible_indexes=on' 可临时让隐藏索引参与优化（测试用）。

3. 索引合并（Index Merge，了解即可）

当单表上存在多个单列索引、查询条件是它们的 AND/OR 组合时，优化器可能同时扫多棵索引再取交/并集，type 显示 index_merge，Extra 见 Using intersect(...) / Using union(...)。

态度：索引合并通常是**「没有建联合索引」的次优补偿**，效率一般不如一条设计良好的联合索引。看到 index_merge 应视为合并成联合索引的信号，而不是优化成功的标志。

第四章：MySQL 高级查询

概念基础

高级查询是超越单表 SELECT ... WHERE 的多表、分组、窗口类查询，核心是把拆开存的关系拼回来：

  1. 为什么数据要拆开存：关系模型按范式把业务拆成多张表（如 emp 员工表与 dept 部门表），避免重复存储；查询的本质就是用 JOIN / 子查询按关联字段把数据重新拼装——第一章建的表结构，在这里被「消费」。
  2. JOIN 的语义差异决定丢不丢数据：INNER JOIN 只保留两表都匹配的行；LEFT JOIN 保留左表全量、右表无匹配补 NULL。选错连接类型，统计结果会悄悄少行，是报表错乱的头号来源。
  3. 聚合把「多行」压成「一行」：GROUP BY 分组后才能用 COUNT / SUM / AVG；过滤顺序是 WHERE（分组前滤行）→ GROUP BY → HAVING（分组后滤组），颠倒位置直接报错或结果不对。
  4. MySQL 8.0+ 的两大武器：CTE（WITH） 把复杂查询拆成可读的「临时结果」并支持 RECURSIVE 查树；窗口函数在不减少行数的前提下做组内排名、累计——「每组 Top N」从此有了标准解法。
  5. 性能意识贯穿始终：判断存在性优先 EXISTS，合并结果优先 UNION ALL（免去去重排序），深分页 LIMIT 大 OFFSET 会越来越慢、生产改用键集分页——写法差异就是性能差异。

第三章：MySQL 锁详解

概念基础

锁是数据库的并发控制机制，让多个事务在共享同一份数据时「不打架」：

  1. 没有锁会发生什么：多个会话同时读写同一行，会出现脏读、不可重复读、幻读与更新丢失；锁的本质是给「当前读」排队，保证数据一致性。
  2. 核心权衡是一致性 vs 并发：锁粒度越粗（全局锁、表锁）越安全但并发差，粒度越细（行锁）并发越高但开销越大——InnoDB 的答案是以行锁为主 + MVCC 快照读，普通 SELECT 不加锁，读写大部分场景互不阻塞。
  3. InnoDB 行锁的本质是锁索引：锁加在索引记录上而不是物理数据行上；查询条件无索引或索引失效时，行锁会退化为表锁，并发直接崩塌，这是本章最重要的一条结论。
  4. 隔离级别决定加锁行为：**RR（可重复读）默认用临键锁（记录锁 + 间隙锁）**抑制幻读，代价是范围锁会阻塞插入；**RC（读已提交）**没有间隙锁，并发更高但存在幻读。
  5. 锁是双刃剑：用好了高并发不冲突，用坏了就是锁等待、死锁、业务雪崩——长事务、无索引更新、交叉加锁是线上三大事故来源，本章实验与面试题全部围绕这些展开。

  • 行锁三形态：记录锁、间隙锁、临键锁（RR 防幻读）

实验一：行排他锁 FOR UPDATE 阻塞演示

执行流程

会话1：开启事务 → id=1 加 FOR UPDATE 不提交
会话2：修改 id=1 被阻塞；修改 id=2 正常执行

现象

  1. 同一条主键记录：写操作被阻塞
  2. 不同主键记录：完全不受影响
  3. 会话1 commit 后，会话2立刻执行成功

底层原理

  1. FOR UPDATE 加 行级排他锁（X锁）
  2. 排他锁规则：写写互斥、读写互斥
  3. InnoDB 行锁只锁索引命中的单行，不影响其他行

面试标准答案

InnoDB 中通过主键/唯一索引精准查询加 FOR UPDATE，会加行级排他锁；只锁定当前命中的单行记录，其他行不受影响，能保证高并发。排他锁与任何读写操作都互斥，事务提交后锁自动释放。

实验二：无索引导致行锁退化为表锁

执行流程

按无索引字段 age=20 更新，会话1不提交，会话2更新完全无关的 id=2 也被阻塞

现象

明明更新不同行，却整张表都被锁住，所有写操作全部阻塞

底层原理

  1. InnoDB 行锁是锁索引，不是锁数据行
  2. 条件字段无索引，MySQL 无法定位具体行
  3. 只能逐行加行锁扫描全表，最终退化成表级锁

面试标准答案

InnoDB 行锁必须依赖索引。如果更新/删除条件没有索引或索引失效，MySQL 无法精确定位行记录，会扫描全表并逐行加锁，最终行锁降级为表锁，严重降低并发性能，开发中必须保证更新条件走索引。

实验三：共享锁与读写互斥演示

执行流程

会话1：LOCK IN SHARE MODE 加共享锁
会话2：普通SELECT能查，UPDATE/DELETE被阻塞

现象

  1. 多个事务可以同时加共享锁（读读兼容）
  2. 加了共享锁后，其他事务不能加排他锁、不能修改数据
  3. 事务提交后，写操作立刻放行

底层原理

  • 共享锁（S锁）：读读兼容，读写互斥
  • 意向锁辅助，S锁阻塞所有写操作，保证数据当前快照不被修改

面试标准答案

共享锁（S锁）又叫读锁，使用 LOCK IN SHARE MODE 加锁。特性是读读可以并发，读写、写写互斥；适合需要强一致性、临时禁止别人修改数据的场景，事务提交自动释放锁。

实验四：间隙锁与临键锁阻塞插入（RR 与幻读）

执行流程

会话1：范围查询 between 1 and 3 for update 不提交
会话2：插入区间内新 ID，直接被阻塞

现象

没有任何行被修改，只是范围加锁，却无法往区间里插入新数据

底层原理

  1. MySQL RR 隔离级别默认使用 Next-Key Lock 临键锁
  2. 临键锁 = 记录锁 + 间隙锁
  3. 范围查询会锁住索引区间间隙，禁止其他事务插入新记录，解决幻读
  4. 间隙锁只在 RR 存在，RC 隔离级别没有间隙锁

面试标准答案

InnoDB 在 RR 可重复读隔离级别下，采用临键锁（Next-Key Lock） 解决幻读。临键锁由记录锁+间隙锁组成，范围查询会锁定索引左右间隙，禁止其他事务在区间内插入数据；RC 读已提交级别会关闭间隙锁，因此无法彻底避免幻读，但并发更高。

实验五：经典死锁复现

执行流程

  • 事务1：先锁 id=1 → 再请求锁 id=2
  • 事务2：先锁 id=2 → 再请求锁 id=1
  • 互相等待，立刻触发死锁，MySQL 自动回滚一个事务

现象

  1. 互相持有对方需要的锁，循环等待
  2. InnoDB 自动死锁检测，回滚代价小的事务，抛出死锁异常
  3. 不会无限阻塞

底层原理

死锁产生四个必要条件同时满足：

  1. 互斥条件：锁资源独占
  2. 持有并等待：自己拿着锁，还等别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务形成等待环路

面试标准答案（必背）

死锁产生必须同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待。
规避方案：

  1. 统一多事务访问资源的顺序；
  2. 拆分长事务，尽早提交；
  3. 避免在事务中做无关耗时操作；
  4. 合理设置锁等待超时时间。
    InnoDB 自带死锁检测机制，发现循环等待会自动回滚一个事务，避免程序卡死。

十一、面试高频一句话速记

  1. 行锁靠索引，无索引变表锁
  2. S 锁读读兼容，X 锁完全独占
  3. RR 有间隙锁防幻读，RC 没有
  4. 交叉改不同行、顺序乱写易出死锁

十二、二十道高频面试题与标准答

全部面试可直接背诵，基于 InnoDB、RR 隔离级别，精简不废话。

1. MySQL 有哪些锁分类？

答案

  1. 按粒度：全局锁、表级锁、行级锁
  2. 按读写：共享锁S、排他锁X
  3. InnoDB 特有：意向锁、记录锁、间隙锁、临键锁

2. 全局锁作用是什么？怎么加？

答案
整库只读，所有库表只能读不能写、阻塞 DDL/DML。
加锁：FLUSH TABLES WITH READ LOCK;
解锁：UNLOCK TABLES;
多用于全库逻辑备份；生产优先用 mysqldump --single-transaction 快照备份，不加锁。

3. 什么是 MDL 元数据锁？

答案
访问表时自动加，保护表结构不被中途修改/删除。
长事务不提交 + 执行 DDL 改表结构，会造成 MDL 锁等待阻塞，线上高发故障点。

4. 表锁和行锁区别？

答案

  • 表锁：粒度大、开销小、并发低、MyISAM 默认
  • 行锁：粒度小、开销大、并发高、InnoDB 支持
    InnoDB 优先用行锁提升并发。

5. 共享锁S、排他锁X 特性？

答案

  • 共享锁S：读读兼容，读写/写写互斥
  • 排他锁X：读写、写写全部互斥，独占资源
    加锁：
    S：select ... lock in share mode
    X：select ... for update

6. 意向锁 IS/IX 作用？

答案
意向锁是表级锁，事务加行锁前必须先加意向锁。
作用：快速判断表内是否有行锁，不用遍历所有行锁，提升加锁效率。

  • IS：要加 S 行锁
  • IX：要加 X 行锁
    意向锁之间互相兼容，只和表级 S/X 锁互斥。

7. InnoDB 行锁本质是什么？

答案
行锁锁的是索引，不是物理数据行。
查询条件无索引、索引失效，行锁会退化成表锁，并发骤降。

8. 什么情况下行锁会降级为表锁？

答案

  1. where 条件无索引字段
  2. 索引失效（函数、隐式类型转换、like 前缀模糊等）
  3. 没有命中任何记录，全表扫描加锁

9. InnoDB 三种行锁算法？

答案

  1. 记录锁：锁单行索引记录
  2. 间隙锁 Gap Lock：锁索引间隙，不锁记录，防止幻读插入
  3. 临键锁 Next-Key Lock = 记录锁+间隙锁，左开右闭区间，RR 默认

10. 间隙锁什么时候生效？什么时候关闭？

答案

  • 生效：RR 可重复读隔离级别、范围查询/不走唯一索引等值查询
  • 关闭：RC 读已提交 没有间隙锁，并发更高，但会有幻读

11. 临键锁解决了什么问题？

答案
在 RR 隔离级别下，通过临键锁+间隙锁彻底解决幻读，禁止其他事务在索引区间插入新数据。

12. 什么是幻读？怎么解决？

答案
同一事务内，前后两次范围查询，查到别人新插入的数据。
解决：

  • 数据库层：InnoDB RR + 临键锁
  • 业务层：悲观锁、分布式锁限制插入

13. 死锁产生的四个必要条件？

答案

  1. 互斥：锁资源独占
  2. 持有并等待：拿着自己的锁，等待别人的锁
  3. 不可剥夺：锁不能被强行抢占
  4. 循环等待：事务互相等待形成环路

14. MySQL 怎么处理死锁？

答案
InnoDB 有自动死锁检测，检测到循环等待后，自动回滚代价更小的一个事务，抛出死锁异常，避免无限阻塞。

15. 如何避免 MySQL 死锁？

答案

  1. 统一所有事务访问资源/更新行的顺序
  2. 精简事务，避免长事务，尽早 commit
  3. 事务内不做耗时网络/IO 操作
  4. 合理设置锁等待超时 innodb_lock_wait_timeout

16. for update 和 lock in share mode 区别？

答案

  • for update：加排他锁X，别人不能读也不能改
  • lock in share mode：加共享锁S，别人可以读、不能改

17. RR 和 RC 在锁层面最大区别？

答案

  1. RR 有间隙锁/临键锁，防幻读；RC 没有
  2. RC 行锁范围更小、并发更高，但存在幻读
  3. RC 锁释放更早，阻塞更少

18. 长事务有什么锁风险？

答案
长事务不提交：

  1. 行锁、MDL 锁长期不释放
  2. 造成大量锁等待、业务阻塞
  3. undo log 不能清理，占用磁盘
  4. 容易触发死锁、数据库性能雪崩

20. 线上开发写 UPDATE 防锁坑要注意什么？

答案

  1. 更新条件必须走索引，防止行锁变表锁
  2. 尽量用主键/唯一索引精准等值，少用范围查询

现象：整张表读写全堵，连接数飙升，业务报警——而根源只是一个没提交的事务。

原理

  • MDL 不需要显式加：访问一张表自动加 MDL 共享锁（读/写），DDL 需要 MDL 排他锁；
  • 排他锁在队列里等待时，后来的共享锁也要排队（防饿死策略），所以一个被卡住的 DDL 会堵死整张表的所有新请求；
  • 等待超时由 lock_wait_timeout（默认 1 年！）控制——DDL 被 MDL 卡住默认永不超时，必须人工干预。

排查与止血（MySQL 8.0）

预防三件套：

  1. 应用侧严禁长事务，autocommit=1 保持默认；
  2. DDL 前查长事务：SELECT * FROM information_schema.innodb_trx WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;
  3. DDL 语句显式缩短等待：ALTER TABLE ... , LOCK=DEFAULT 无效于 MDL，要靠低峰窗口 + 语句超时（部分版本支持 lock_wait_timeout 会话级临时调小）。

2. Online DDL 与锁（8.0/8.4 的三种算法）

算法 锁表行为 速度 典型操作
INSTANT 仅瞬间 MDL 秒级（与表大小无关） 末尾加列、删列（8.0.29+）
INPLACE 开始/结束各一次短暂 MDL，中间可读写 与表大小成正比 加索引、改列类型（部分）
COPY 全程禁写 慢，双倍磁盘 改存储引擎等兜底场景

实战要点：

  1. 优先 INSTANT：ADD COLUMN 默认就走 INSTANT（8.0），无需指定；可用 SHOW WARNINGS 或 information_schema.tables 的 ALGORITHM 记录确认；
  2. INPLACE 仍会抢两次 MDL——长事务环境下照样卡，执行前照第 1 节流程排查；
  3. **大表变更（千万行以上）**生产惯例走 gh-ost / pt-online-schema-change：影子表 + binlog 追增量，把锁窗口压到毫秒级切换；
  4. DDL 期间磁盘：COPY/部分 INPLACE 需要额外一份表大小的空间，磁盘水位不足会直接失败。

概念基础

Selenium 是浏览器自动化的事实标准，让 Python 代码替你「亲手」操作浏览器：

  1. 驱动真实浏览器：用代码控制 Chrome / Edge / Firefox 完成打开网页、点击、填表、读取数据等人类操作，所见即所得。

第五章：Docker 部署 RocketMQ 实践

概念基础

  1. 没有「单容器一体」形态：NameServer 与 Broker 是两个独立进程（5.x 还有一个可选的 Proxy），最小栈就是两个容器——这与 Kafka 的 KRaft 单进程不同，下文用「网络 → NameServer → Broker」三步完成最小栈。
  2. brokerIP1 是第一坑：Broker 启动时把自己注册到 NameServer 的地址就是 brokerIP1，客户端拿这个地址直连 Broker——容器内不显式指定时往往是内网容器 IP，宿主机客户端会「能拿到路由却连不上」。本机访问写 127.0.0.1、跨机写宿主机可达 IP（对照 Kafka 的 advertised.listeners）。
  3. 端口按角色记忆：9876 NameServer；10909 / 10911 / 10912 分别是 Broker 的 VIP / 主 / HA 端口；8080 / 8081 是 5.x Proxy 的 gRPC 端口——只用经典 Remoting 客户端时，Proxy 端口可以不映射。
  4. 数据目录与边界：Broker 数据在 /home/rocketmq/store（日志在 logs），必须挂卷；单机部署面向开发验证，生产多 Master/Slave 或 DLedger 自动切换请用 RocketMQ Operator 或官方推荐拓扑。

架构速览：NameServer 与 Broker 如何协作

  B[Broker] -->|② 每30s注册路由| NS

角色 状态 关键点
NameServer 无状态，互相之间不通信 Broker 向每一个 NameServer 注册；客户端可配多个地址任取其一；挂了不影响已拿到路由的收发，只影响「新路由发现」
Broker 有状态（CommitLog + ConsumeQueue + IndexFile） 按 brokerName + brokerId 区分：brokerId=0 是 Master，>0 是 Slave；周期向 NameServer 上报路由
Proxy（5.x） 无状态接入层 面向 gRPC 新客户端；经典 Remoting 客户端可不开

存储模型一句话：所有消息顺序追加到 CommitLog，再异步分发到按 Topic/Queue 组织的 ConsumeQueue 索引——顺序写盘是 RocketMQ 高吞吐的根基，也是 store 目录必须挂好盘的原因。

第三章：ClickHouse 查询与性能调优

概念基础

  1. 快的前提是少读：ClickHouse 的调优永远围绕「让扫描更少」——分区裁剪、排序键前缀、跳数索引、只选需要的列。
  2. ORDER BY 是物理排序：MergeTree 的排序键决定磁盘数据布局，查询条件包含排序键前缀才能命中主键索引跳过 granule。
  3. PREWHERE 是 ClickHouse 特有的过滤下推：先读小列过滤、再读大列，比 WHERE 更省 IO（优化器常自动迁移，手动写大列场景更稳）。
  4. 物化视图是预聚合：写入时同步算好聚合结果落表，查询直接读聚合表——大屏/报表从分钟级到毫秒级的核心手段。
  5. JOIN 是短板不是黑洞：右表全量进内存的哈希 JOIN 模型要求右表小；大表关联优先改造成字典/宽表/物化视图。

一、查到慢查询：system 表与 EXPLAIN

EXPLAIN indexes = 1 输出关注：Parts（分区裁剪后剩几个 part）、Granules（主键索引筛掉多少 granule）——两个数字没降说明查询没吃到索引。

补充两个日常诊断 SQL：

判读口诀：Parts 从几百降到个位数 = 分区裁剪生效；Granules 从全量降到百分之几 = 主键前缀生效；两者都纹丝不动 = 回到建表设计找问题。

二、让扫描更少：分区、排序键、跳数索引

手段 生效条件
分区裁剪 WHERE 带分区列（event_date），别对分区列套函数
主键索引 WHERE/ORDER BY 命中 ORDER BY 的最左前缀
minmax 索引 数值/日期列的范围过滤
bloom_filter payload = 'xxx'、IN 这类大列等值查询
LowCardinality 低基数枚举列（几十~几万个取值），压缩与速度双赢

与 MySQL 索引思想相通：最左前缀原则在 MergeTree 上同样成立，见 第一章：MySQL DDL 语句与表设计入门 的复合索引章节。

三、查询特性语法

写法 建议
uniq() 默认近似去重（误差 ~1%）；精确用 uniqExact()，代价高
FINAL 单表小范围用；大表改为 ORDER BY (排序键) + argMax 或查询时去重
SELECT * 禁止——列存优势全无；只写需要的列
LIMIT 大分页 避免深分页；按排序键游标翻页（WHERE key > last LIMIT n）

四、物化视图：预聚合

  • 只对「新写入」生效：建视图后历史数据要 INSERT INTO 目标表 SELECT ... FROM 源表 手工回填。
  • 查询端再聚合一层（SummingMergeTree 的 merge 时机不定，查询时仍需 GROUP BY）：

物化视图的三个陷阱

  1. 历史数据不会自动回填：建视图前的数据要 INSERT INTO 目标表 SELECT ... FROM 源表 GROUP BY ... 手工补。
  2. 视图串联要显式：视图 A 的源表如果是另一个视图 B 的目标表，A 不会自动触发——需要在 B 的 SQL 里继续写 TO 链。
  3. 目标表引擎要配对：聚合类视图的目标表用 SummingMergeTree / AggregatingMergeTree，普通 MergeTree 会存重复行。

五、Projection：预计算的第二种形态（25.x）

Projection 是 MergeTree 的表内预计算结构——同一张表存多份不同排序/聚合的数据副本，优化器自动选择最省的那份，不需要建第二张表、不需要改查询 SQL：

对比项 物化视图 Projection
存储位置 独立目标表 源表内部（随 part 一起 merge）
查询改写 手写查目标表 优化器自动命中
一致性 视图失败可能丢同步 与源表 part 级强一致
适用 跨表聚合、多张报表 同表多维度加速

经验：同表「换个维度 GROUP BY」优先 Projection；跨表、多下游报表才上物化视图。

六、写入端调优：Too many parts 与批量纪律

查询慢有时根因在写入侧——part 太多拖垮 merge 与查询规划：

症状 诊断 处方
Too many parts 拒写 system.parts 按分区统计 part 数 写入攒批（每批几万~几十万行）
merge 永远跑不完 system.merges 长期排队 降低写入频率、加 background_pool_size
查询 Planning 慢 part 上千后规划耗时陡增 同上 + OPTIMIZE ... FINAL 应急

批量纪律：客户端侧用异步插入（async_insert=1 + wait_for_async_insert=0）或 Buffer 表，把毫秒级小包聚成大块再落盘。容器侧完整排查命令见 第二章：Docker 部署 ClickHouse 实践。

七、资源护栏：别让一条 SQL 拖垮整机

  • max_memory_usage：超限报错而非 OOM 宕机，保住整实例。
  • max_execution_time：报表接口防呆，超时快速失败。
  • 配额（Quota）：按用户/时段限制查询总量，防止 BI 工具狂刷。
