第三章：Modbus ASCII

概念基础

  1. Modbus ASCII 是 Modbus 的文本编码变体：每个字节用两个 ASCII 十六进制字符（0-9 A-F）表示，帧以 : 开始、CR LF 结束。
  2. 为什么存在：早期调制解调器/串口终端时代，文本帧人眼可读、可直接粘贴调试，字符间容忍度也比 RTU 严格的 3.5 字符静默宽松。
  3. 校验不同：RTU 用 CRC16，ASCII 用 LRC（8 位求和取补码）——检错能力较弱但实现极简。
  4. 代价：同样数据传输长度约 2 倍、带宽利用率低，新项目工业现场几乎都选 RTU，ASCII 只保留在老设备与维护口。
  5. 同一套 PDU：与 RTU/TCP 的功能码与寄存器语义完全一致，切换链路层不影响上层应用逻辑。

字符时序差异

  • RTU：帧内字节间隔 ≤ 1.5 字符，帧间 ≥ 3.5 字符，超时即丢帧。
  • ASCII：允许字符间最大 1 秒间隔而不丢帧——正因为人可以慢慢敲、慢慢贴。超过 1 秒视为帧错误。

这是 ASCII 模式在手工调试、电话线 modem 场景下不可替代的原因。

对 地址到数据末字节 求和（8 位），取二进制补码（256 - sum），再转两个 ASCII 十六进制字符。

RTU 使用 CRC16；ASCII 用 LRC，检错能力较弱但实现简单。

五、调试

  • 串口终端可直接粘贴 : 帧（若设备支持 ASCII 模式）。
  • 物理层常为 第五章：RS232 或 第六章：RS485 + 第四章：UART。

ASCII 模式独有的调试技巧：

  • 终端直连：打开任意串口终端（PuTTY 串口模式、minicom），手敲 :01030000000AF2 回车即可看到设备回复，无需任何专用软件。
  • 日志可读：直接把收发记录写进文本日志，事后用肉眼即可审计，不像 RTU 需要 hex 转储再解析。
  • 常见坑：忘了设备要求大写 HEX；串口参数沿用 RTU 的 8N1 导致校验位错误；行尾必须是 CRLF，只发 LF 不被识别。
  • 帧错误处理：收到非法字符（非 0-9 A-F）或超时应丢弃整帧并等待下一个 :，不要在帧中间尝试恢复。

六、什么时候还会遇到 ASCII

  • 老式变频器、温控表的维护串口，出厂默认 ASCII 模式便于现场人员用终端排障。
  • 电话线 / 电台链路：字符间容忍度大，对不稳定链路更宽容。
  • 教学与协议学习：报文可读，适合作为 Modbus 入门的第一课。
  • 新项目选型：只要链路允许，优先 RTU；ASCII 的 2 倍带宽开销在 485 总线多节点轮询时会显著拖慢扫描周期。

第二章：Modbus TCP

概念基础

  1. Modbus TCP 把 Modbus 的主从语义搬到以太网/TCP：报文仍是「功能码 + 数据」，但帧定界交给 TCP、校验交给 TCP 校验和，因此没有 CRC、没有静默时序。
  2. MBAP 头（7 字节）取代 RTU 的「从站地址 + 静默界定」：Transaction ID 让一条连接可区分多个并发事务，Unit ID 负责映射网关后的串口从站。
  3. 默认端口 502：约定俗成；接入即用，可跨交换机、跨网段访问远程设备，无需 485 布线与收发方向切换。
  4. 网关共存：大量存量设备仍是 RTU 串口设备，TCP ↔ RTU 网关完成两者转换，是工业现场新旧系统融合的典型形态。
  5. 边界：明文、无认证，安全只能靠工控内网隔离、VPN、TLS 隧道，绝不能直接暴露公网。

三、连接模型

  • 单连接多事务：常见一客户端对一 PLC 长连接 502。
  • 并发：多客户端连同一设备需注意 PLC 连接数限制。
  • 与 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例：不同协议；工业网关可能同时提供 Modbus TCP 与 OPC UA。

并发与超时实践

  • Transaction ID 递增：客户端每发一请求自增，响应原样带回，异步收发也能正确配对。
  • 连接数受限：很多小型 PLC 只支持 4~16 个并发 TCP 连接，SCADA 侧应做连接池 + 请求串行化。
  • 长连接保活：现场交换机可能静默回收空闲连接，建议启用 TCP Keepalive 或定期发空读。
  • 超时与重试：默认超时 1~3 s；超时后先重发同 Transaction ID 的请求，连续失败再重建连接。
  • 半开连接：PLC 掉电时 TCP 不会立刻断开，读取超时往往是唯一的故障信号。

四、串口网关

Modbus TCP ↔ RTU 网关：
Unit ID 映射 RS485 从站地址；网关内维护 第六章：RS485 轮询时序。

网关工作原理

  1. 网关收到 TCP 帧后，剥离 MBAP，按 Unit ID 查映射表得到串口从站地址。
  2. 重新计算 CRC16，拼成 RTU 帧发往 485 总线，并遵守 3.5 字符静默时序。
  3. 收到 RTU 应答后剥离 CRC，装回 MBAP（Transaction ID 取自原请求），经 TCP 回传。

注意坑点：

  • 串口是串行资源：多个 TCP 客户端并发请求同一串口总线时，网关内部必须排队，响应时间会被拉长。
  • 广播不可达：RTU 的地址 0 广播语义在多数网关上不支持转发。
  • Unit ID 冲突：部分网关把 Unit ID=255 保留给网关本身的寄存器。

六、抓包与调试

  • Wireshark：内置 modbus 解析器，过滤表达式 modbus 或 tcp.port == 502，可逐字段展开 MBAP 与功能码，是 TCP 版调试的第一利器。
  • tcpdump 抓包后离线分析：tcpdump -i eth0 port 502 -w modbus.pcap。
  • Modbus Poll 也支持 TCP 模式，可与自研从站互测。
  • 诊断计数器：许多 PLC 暴露连接数、报文错误计数寄存器，排障时先读它们。
  • 对比 RTU：TCP 版可以用普通网卡抓包，不再需要串口搭车监听，调试门槛低很多。

七、安全

  • 502 明文、无认证 → 仅放工控内网或 VPN；勿暴露公网。
  • 现代方案：TLS 隧道、VPN、专用安全网关。
  • 与 第三章：Modbus ASCII 比：TCP 适合跨交换机、远程 SCADA。

补充要点：

  • Shodan 风险：公网暴露的 502 端口会被搜索引擎索引，工控安全事故中屡见不鲜。
  • 纵深防御：防火墙白名单限制源 IP；DMZ 区部署数据网关，控制网与办公网物理/逻辑隔离。
  • Modbus Security（2018）：规范定义的 TLS 版本（端口 802），支持证书认证，但现场普及率仍低。
  • 最小权限：读采集与写控制走不同账号/通道，写操作加二次确认。

八、性能与工程实践

  • 吞吐估算：一次读 10 寄存器往返约 24+31 字节，千兆网下毫秒级；瓶颈往往在 PLC 的扫描周期而非网络。
  • 轮询编排：采集上百个测点时按优先级分周期（快变量 100 ms、慢变量数秒），避免一次性洪泛请求压垮设备。
  • 寄存器合并：把相邻测点合并成一次连续读，减少事务数——这是上位机优化最常用的手段。
  • 写操作安全：关键控制写入后读回校验；通信中断时设备侧应有看门狗/安全状态（超时回到安全输出）。
  • 时间同步：数据采集打时间戳应在 PLC 侧做，而非以太网到达时刻（网络抖动会引入误差）。
  • 冗余：关键链路双网卡/双交换机；客户端断线自动重连 + 指数退避，避免风暴式重连打满 PLC 连接表。

第一章：Modbus RTU

概念基础

  1. Modbus 是 Modicon 于 1979 年为 PLC 设计的应用层主从协议，如今是工业通信最通用的事实标准之一；RTU 是其中「二进制编码 + 异步串口」的变体。
  2. 主从轮询模型：一个主站（PLC/SCADA）按从站地址轮询，从站永不主动上报，只有被寻址才应答——模型简单、时序确定、实现成本低。
  3. 帧结构极简：地址 + 功能码 + 数据 + CRC16，一帧即一次完整的请求/应答；统一的寄存器语义（线圈、保持寄存器等）让不同厂商设备能用同一套报文访问。
  4. 为什么选 RTU：跑在 RS485 差分总线上，一根双绞线可挂多设备、传数百米，抗干扰强、布线便宜，是工业现场最常见组合。
  5. 边界：RTU 只定义数据读写语义，不含认证加密；帧界定靠静默时间而非特殊字符，底层串口由 UART 控制器提供。

三、时序（RTU 特有）

帧间静默 ≥ 3.5 字符时间（与波特率相关），用于帧界定；波特率高时该间隔很短，实现需精确。

  • 115200 下对 MCU 中断延迟更敏感。
  • 半双工 第六章：RS485 需在发送前使能 DE。

3.5 字符时间怎么算

一个字符 = 起始位 + 8 数据位 + 校验/停止位 ≈ 11 bit（8N1 时）。则：

波特率 1 字符时间 3.5 字符时间
9600 ~1.146 ms ~4.01 ms
19200 ~0.573 ms ~2.01 ms
115200 ~95.6 µs ~335 µs

实现要点：

  • 用定时器 + 接收中断：每收到一字节重置定时器，定时器超时即判帧结束。
  • 高波特率（>19200）时规范允许固定 1.75 ms 简化实现。

第四章：数仓分层与数据管道调度

概念基础

  1. 数仓分层的目的是治理复杂度：ODS 贴源、DWD 明细、DIM 维度、DWS 汇总、ADS 应用——每层职责单一，下游依赖上游，坏数据能定位到层。
  2. 批流一体靠统一模型：Spark（第一章：Spark 大数据批处理入门）跑离线重算，Flink（第二章：Flink 流式计算入门）跑实时增量，两边共用口径才能「T+1 准确、实时大致对」互为校验。
  3. Kafka 是管道骨架：CDC 与日志先进 Kafka（第三章：Kafka 大数据数据总线）缓冲解耦，再分流到批/流/OLAP 各消费者。
  4. 调度是数据可靠性核心：Airflow/DolphinScheduler 把「每天 2 点跑批」变成有依赖、可重试、有告警的 DAG，而不是一堆 crontab。
  5. ClickHouse 承接分析层：DWS/ADS 汇总结果落到列存引擎供 BI 查询，见 第三章：ClickHouse 查询与性能调优。

本章聚焦管道编排与分层建模方法论；沙箱无 Airflow/Spark 集群，代码按 Airflow 2.x 官方语法书写未逐条运行验证。

第四章：RAG 与向量检索实战

概念基础

  1. RAG = 检索增强生成：把私有知识向量化入库，提问时先检索最相关的片段塞进上下文，再让 LLM 作答——不用重训模型就能注入领域知识，是 LLM 落地性价比最高的路线。
  2. Embedding 是语义坐标系：文本被编码为高维向量（如 1024 维），语义相近的文本距离相近；「检索」从关键词匹配升级为最近邻搜索。
  3. 向量库专管 ANN：Milvus/Qdrant/pgvector 用 HNSW 等索引做近似最近邻查询，毫秒级从千万级向量里捞 Top-K；小规模用 Redis/Postgres 也能起步。
  4. 效果好坏在数据管道：切块（chunking）粒度、检索 Top-K、重排序（rerank）三件事对答案质量的影响大于换模型。
  5. 评估要有 ground truth：召回率（该找的找没找到）与答案忠实度（说的对不对）分开评，肉眼抽查不可持续。

十、GraphRAG 简介

向量 RAG 把知识切成碎片，遇到”这些事件之间什么关系””整个语料的主线是什么”这类全局性、关系性问题会失灵。GraphRAG（微软开源）的思路：

  1. 离线索引时让 LLM 从每个 chunk 抽取实体与关系，构建知识图谱；
  2. 社区检测把图谱聚成主题簇，预生成社区摘要；
  3. 在线查询按类型分流：局部问题走实体邻域检索，全局问题走社区摘要问答。

代价是索引成本数倍于普通 RAG（每 chunk 多次 LLM 调用）。结论：默认从向量 + BM25 + rerank 起步，确认有全局分析类刚需再上 GraphRAG。

第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3

概念基础

QUIC（Quick UDP Internet Connections）是运行在 UDP 之上的可靠、加密、多路复用传输协议，是 HTTP/3 的底座：

  1. 解决什么问题：TCP 字节流「一丢全等」的队头阻塞、TCP + TLS 分层握手往返多、四元组一变连接即断——QUIC 在 UDP 上逐一重构。
  2. 三大关键设计：流（Stream）级隔离让丢包影响面缩小；内置 TLS 1.3 把加密与传输握手合并（目标 1-RTT 建连，0-RTT 可选加速）；Connection ID 让网络切换后连接依旧存活（连接迁移）。
  3. 实现在用户态：与 第一章：TCP 协议详解：连接、可靠传输与编程示例 内核栈不同，QUIC 多由用户态库（ngtcp2、quiche、MsQuic 等）实现，迭代快但排障更依赖日志与指标。
  4. 代价与前提：依赖 UDP/443 放行与企业网策略对齐；0-RTT 有重放风险，写操作需谨慎。

先看设计目标与作用的全貌：

一、设计目标与作用

1. 解决什么问题

  • 在 UDP 上重建可靠管道：丢包检测、重传、拥塞控制发生在 QUIC 层，而不依赖 第一章：TCP 协议详解：连接、可靠传输与编程示例 单一流上的队头阻塞。
  • 默认加密：传输与握手深度绑定 TLS 1.3（RFC 9001），减少「明文旁路」与分层带来的额外往返。
  • 多流与连接标识：Stream 隔离应用数据；Connection ID 让四元组变化时仍能延续同一逻辑连接（连接迁移）。

2. 相对 TCP + TLS 的典型取舍

问题 第一章：TCP 协议详解：连接、可靠传输与编程示例 + TLS 常见表现 QUIC 思路
队头阻塞 TCP 字节流级丢包会阻塞后续所有应用数据 QUIC 在流级相对独立地做丢包恢复
握手 RTT 常需 TCP 三次握手再叠 TLS 往返 常把加密与传输握手合并，目标 1-RTT 建连（0-RTT 为可选加速）
NAT 重绑定 四元组变化常被视作「新连接」 Connection ID 标识逻辑连接，支持连接迁移
中间设备 TCP 成熟、穿透好 依赖 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 放行（如 UDP/443）；企业网策略需对齐

二、连接与完整通信流程（原理）

QUIC 报文封装在 UDP 数据报中（常见 HTTPS 场景为 UDP/443）。以下极度简化，省略版本协商、重试包、地址验证等细节。

1. 建立连接（简化）

首包常带 TLS ClientHello；成功后在 1-RTT 密钥下发送应用数据。0-RTT 可在重复连接时提前带数据，见第五节安全注意。

带地址验证的完整握手（更接近真实）：



sequenceDiagram
  participant C as Client
  participant S as Server
  C->>S: Initial（TLS ClientHello）
  opt 服务端要求地址验证
    S-->>C: Retry（携带 token）
    C->>S: Initial（回显 token + ClientHello）
  end
  S-->>C: Initial（ACK）+ Handshake（ServerHello…Finished）
  C->>S: Handshake（Finished）+ 1-RTT 数据
  S-->>C: 1-RTT 响应数据

Retry 包的作用：服务端在投入连接状态之前，先让客户端证明「它真的拥有所声称的源地址」，从源头抑制地址伪造型放大攻击（QUIC 要求服务端在地址验证前发送的字节数不超过收到的 3 倍）。

2. 关闭连接（简化）

任一方可发送 CONNECTION_CLOSE 帧；对端进入排空（draining）期，不再发送新数据。与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 FIN/ACK 不同，QUIC 在连接粒度表达关闭，内部再回收流与 UDP 套接字资源。

3. 与典型「套接字 / 协议栈」的对应

与 第一章：TCP 协议详解：连接、可靠传输与编程示例 的 connect/accept 由内核一条龙完成不同，QUIC 一般由用户态库（如 ngtcp2、quiche、MsQuic、aioquic）或浏览器网络栈实现：底层仍是 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 sendto/recvfrom，其上是 TLS 1.3、ACK/重传、流控与 HTTP/3 帧。HTTP/3 客户端日常通过 curl --http3-only 或内置 HTTP/3 的 SDK 使用，而不是手写裸 UDP 报文。

三、包结构与帧（概念）

1. 长首部与短首部

项 长首部（Long Header） 短首部（Short Header）
用途 握手阶段（Initial / 0-RTT / Handshake / Retry） 建立后的 1-RTT 数据
明文可见 版本、DCID/SCID、包类型、长度 仅 DCID（与少量标志）
首部开销 较大 小（数据面常态）

2. 常见帧类型（RFC 9000 §19）

帧 作用
PADDING / PING 填充 / 保活探测
ACK 确认收到的包号范围（支持 ACK Range 与 ECN 计数）
CRYPTO 承载 TLS 1.3 握手字节流
STREAM 应用数据（携带 Stream ID、偏移、长度）
RESET_STREAM / STOP_SENDING 中止发送 / 请求对方停止发送
MAX_DATA / MAX_STREAM_DATA 连接级 / 流级流控窗口更新
NEW_CONNECTION_ID / RETIRE_CONNECTION_ID 签发与退役 CID（迁移与隐私）
CONNECTION_CLOSE 关闭连接（区分传输层与应用层错误码）
PATH_CHALLENGE / PATH_RESPONSE 连接迁移时的路径验证

四、流、可靠性与拥塞控制（原理要点）

  • Connection：加密上下文、ACK 与拥塞控制的归属单位（类似「一条加密了的类 TCP 管道」）。
  • Stream：单向或双向；HTTP/3 将请求/响应映射到不同流，减轻应用级队头阻塞。
  • Packet Number：单调递增，配合 ACK 范围与密钥更新，降低与 第一章：TCP 协议详解：连接、可靠传输与编程示例 序号相关的歧义；重传不重用旧 PN（新包新号）。
  • 拥塞控制：在 Connection 上运作（如 Cubic、BBR 等实现依栈而定），与 第一章：TCP 协议详解：连接、可靠传输与编程示例 一样受网络条件约束，但并非「一条字节流管所有多路复用对象」。

两级流控：MAX_DATA 限制整条连接的在途字节总量，MAX_STREAM_DATA 限制单条流——接收方两侧同时收紧，发送方须同时满足。流控窗口耗尽时发送方会被阻塞，Wireshark/qlog 中常见 blocked 事件即源于此。

Stream ID 编码（低 2 bit 表意）：bit0 区分发起方（0=客户端，1=服务端），bit1 区分方向（0=双向，1=单向）——例如客户端发起的第一个双向流 ID 为 0，服务端第一个单向流为 3。

五、Connection ID、端口与「会话标识」

  • UDP 四元组仍用于路由首个报文；Connection ID 使源 IP/端口变化（如蜂窝切换 Wi-Fi）后，对端仍能识别同一 QUIC 连接。
  • 公网 HTTP/3 常见端口为 443（UDP），与 第一章：TCP 协议详解：连接、可靠传输与编程示例 443 并存、互不替代。
  • 服务端可协商 CID 长度与轮换策略，以兼顾隐私与路由。

连接迁移时序（简化）：



sequenceDiagram
  participant C as Client
  participant S as Server
  Note over C: 网络切换（Wi-Fi → 蜂窝），四元组变化
  C->>S: 新路径首发（PATH_CHALLENGE + 新 CID）
  S-->>C: PATH_RESPONSE（验证新路径可达且归属同一连接）
  Note over C,S: 迁移完成，原有流与拥塞状态延续

对比 第一章：TCP 协议详解：连接、可靠传输与编程示例：四元组任何一变即「新连接」、上层必须重连——这正是移动端体验上 QUIC 的核心卖点。

六、TLS 1.3 与 QUIC（原理）

QUIC 使用 TLS 1.3 做身份认证与密钥导出；载荷由 AEAD 保护，PADDING 等机制缓解流量分析。0-RTT 可加速重复连接，但存在重放风险：对金融类写操作应禁用或在应用层做幂等与二次校验。

加密分层细节：

  • 密钥分四级：Initial（从 DCID 公开导出，仅防被动观察者篡改）→ Handshake → 1-RTT（分 0-RTT 与应用数据），各级独立密钥。
  • 首部保护（Header Protection）：除版本与 CID 外，包号等元数据也加密——中间盒连「这是第几个包」都看不到，这是「防 ossification（协议僵化）」的刻意设计。
  • 密钥更新（Key Update）：长连接可轮换 1-RTT 密钥，限制单密钥加密的数据量。

第十四章：RPC 概念详解：原理、形态与 JSON-RPC / curl 示例

概念基础

RPC（Remote Procedure Call，远程过程调用）的目标：让调用远程服务像调用本地函数一样自然：

  1. 解决什么问题：分布式系统中，网络通信的序列化、连接管理、协议细节不应散落在业务代码里，RPC 框架把它们收敛到 stub（存根）。
  2. 如何做到：客户端 stub 把调用序列化成消息发出去；服务端 stub 反序列化、执行、再原路返回——开发者只见函数签名。
  3. 不规定字节格式：JSON-RPC（人可读易调试）、protobuf（见 第十三章：gRPC 详解：Protobuf、HTTP/2 与 grpcurl / Python 示例）、Thrift 等都是可选载体，传输可用 HTTP 或自定义 TCP。
  4. 核心难点：网络不可靠——超时后客户端不知道服务端是否已执行，重试可能重复扣款，必须用幂等设计兜底。

先看一次 RPC 调用的完整链路：

一、原理（.stub 与存根）

RPC 不规定具体字节格式；可由 JSON、protobuf、Thrift 等定义。

  • 链上节点：Ethereum JSON-RPC 等文本 RPC。
  • 脚本自动化：轻量 JSON-RPC 管理接口。

四、失败语义与幂等（原理）

  • 超时：客户端不知服务端是否已执行；重试可能导致重复扣款。
  • 对策：幂等键、去重表、At-least-once 消费语义与业务配合。

三种投递语义——分布式系统的根本约束是「恰好一次只能在单个参与者内部保证」：

语义 机制 业务要求
At-most-once 不重试，超时即失败 可容忍丢失（日志采集、心跳）
At-least-once 超时重试直到确认 必须幂等（绝大多数业务选此）
Exactly-once 业务层去重 + 状态机 仅能在幂等设计上「等效」实现

配套防护三件套：

  • 超时：每次调用必设截止时间（不是单次重试超时，而是整个调用链预算）。
  • 重试：只对连接失败/明确可重试错误重试；指数退避 + 抖动；限制次数防重试风暴。
  • 熔断：下游持续失败时短路调用，给系统恢复时间（如 Sentinel、resilience4j）。

第十二章：MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例

概念基础

MQTT（Message Queuing Telemetry Transport）是面向 IoT 的轻量级发布/订阅消息协议，默认运行在 TCP 1883：

  1. 解决什么问题：设备多、带宽窄、网络不稳——MQTT 报文头最小仅 2 字节，支持断线重连、遗嘱消息与会话保持。
  2. 角色解耦：发布者与订阅者都只连 Broker，按 Topic 字符串路由，双方互不知晓对方存在。
  3. QoS 三档：0 至多一次 / 1 至少一次 / 2 恰好一次，按业务对丢失与重复的容忍度选择。
  4. 为什么适合物联网：低功耗设备常发小遥测消息，Pub/Sub 天然一对多广播；对比 第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例 请求-响应模型更省连接与电量。

先看发布订阅模型的总体结构：

发布订阅模型



flowchart TB
  P1[Publisher 传感器] -->|publish topic/sensor| B[MQTT Broker]
  P2[Publisher 设备] --> B
  B -->|subscribe| C1[Consumer 大屏]
  B --> C2[Consumer 规则引擎]

一、模型与作用（原理）

Broker 根据 Topic 字符串路由消息；发布者不必知道订阅者列表。

报文结构（概念）：每条 MQTT 报文 = 固定头（报文类型 4bit + 标志 4bit + 剩余长度 1–4 字节） + 可变头 + 载荷。控制报文类型共 14 种，常用的有：CONNECT / CONNACK（建连）、PUBLISH（发消息）、PUBACK / PUBREC / PUBREL / PUBCOMP（QoS 确认链）、SUBSCRIBE / SUBACK、PINGREQ / PINGRESP（心跳）、DISCONNECT。

二、主题与通配符（作用）

  • 层级：用 / 分层，如 factory/line1/temp。
  • 单级通配 +：匹配一层，如 factory/+/temp。
  • 多级通配 #：匹配剩余层级，须在末尾（细节以 v5 文档为准）。

Topic 大小写敏感；$SYS/ 常为 Broker 系统主题（依实现）。

设计建议：

  • 以「区域/产线/设备/测点」分层，便于按级授权与聚合订阅。
  • Topic 中不放变化频繁的值（如时间戳），那是 Payload 的职责；否则订阅方无法稳定匹配。
  • 设备 → 平台与平台 → 设备（下行命令）用不同前缀分开，如 up/device1/telemetry 与 down/device1/cmd。

三、QoS（原理）

QoS 名称 语义
0 至多一次 可能丢，不重试
1 至少一次 可能重复，需业务幂等
2 恰好一次 四次握手，开销最大

QoS 在发布方向与订阅方向可分别指定，最终有效语义取二者较高一侧规则（以 Broker 实现与文档为准）。

QoS 1 与 QoS 2 的确认链：



sequenceDiagram
  participant P as Publisher
  participant B as Broker
  Note over P,B: QoS 1：一次确认
  P->>B: PUBLISH (QoS1, PacketId=n)
  B-->>P: PUBACK (n)
  Note over P,B: QoS 2：两段四次确认
  P->>B: PUBLISH (QoS2, PacketId=m)
  B-->>P: PUBREC (m)
  P->>B: PUBREL (m)
  B-->>P: PUBCOMP (m)

QoS 2 通过 PUBREC/PUBREL/PUBCOMP 两段确认保证「恰好一次」，代价是状态存储与双倍往返——除计费、开关量等强一致场景外，多数遥测用 QoS 1 + 幂等消费即可。

四、遗嘱消息（Last Will，概念）

连接异常断开时 Broker 可代发预设 Payload 到指定 Topic，用于设备离线告警；须正确配置 Keep Alive 与心跳。

工作机制：CONNECT 报文中携带遗嘱主题与载荷；Broker 在 Keep Alive × 1.5 时间内没收到任何报文（含 PINGREQ），判定设备异常断线并发布遗嘱。正常 DISCONNECT 不触发遗嘱。

另外两个常配合使用的特性：

  • 保留消息（Retained）：Broker 为每个 Topic 存最新一条 retained 消息，新订阅者立刻收到——适合做「设备当前状态」主题（如 device/1/status）。
  • 会话保持：MQTT 3.1.1 的 Clean Session=0 / MQTT 5.0 的 Session Expiry Interval，让断线期间的 QoS 1/2 消息在重连后补投。

第十一章：WebSocket 详解：握手、帧与 Python 示例

概念基础

WebSocket 是建立在 TCP 上的全双工应用层协议：借一次 HTTP 握手完成「升级」，此后双方随时互发帧：

  1. 解决什么问题：HTTP 是请求-响应模型，服务器无法主动推送；轮询延迟高、空耗连接，WebSocket 用一条长连接双向实时通信。
  2. 与 HTTP 的关系：握手就是 HTTP 101 Switching Protocols（同端口、复用反代与证书基建），升级后传输的是 WebSocket 帧，不再走 HTTP 语义。
  3. 帧级多路复用：文本帧、二进制帧、Ping/Pong 心跳、关闭帧都在单 TCP 连接上交错传输，消息可分片。
  4. 典型场景：行情推送、协作编辑、聊天、游戏状态、IoT 面板实时刷新；服务端单向文本流更轻的替代是 SSE。

先看握手与全双工时序：

握手与全双工



sequenceDiagram
  participant C as Client
  participant S as Server

一、作用与模型

  • 服务器推送：行情、协作编辑、游戏状态无需客户端轮询。
  • 双向二进制：除文本帧外可传 ArrayBuffer 类数据。
  • 与 SSE 对比：SSE 多为服务端单向文本流，仍基于 HTTP；WebSocket 真双向。

Sec-WebSocket-Accept = Base64( SHA1( Sec-WebSocket-Key + GUID ) )，其中 GUID 为 RFC 6455 固定魔数（258EAFA5-E914-47DA-95CA-C5AB0DC85B11）；用于证明服务端理解 WebSocket 协议。

三、帧（原理要点）

类型 opcode 含义
0x1 文本（UTF-8）
0x2 二进制
0x8 关闭
0x9 / 0xA Ping / Pong

大消息可分片（FIN 位与 opcode 组合规则见 RFC 6455）。

帧字节布局（RFC 6455 §5）：

要点：

  • FIN=1 表示消息最后一帧；首帧带 opcode，后续分片用 0x0（continuation）。
  • 载荷长度：<126 用 7 bit；=126 后跟 16 bit；=127 后跟 64 bit。
  • 掩码（Mask）：客户端→服务端的帧必须掩码（防缓存投毒类攻击）；服务端→客户端不掩码。服务端收到未掩码帧应直接关闭连接。

常见关闭码（Close Code）：

Code 含义
1000 正常关闭
1001 端点离开（页面刷新/导航）
1006 异常断开（无关闭帧，抓包/日志里最常见）
1008 策略违反（如 Origin 被拒）
1009 消息过大
1011 服务端内部错误

六、反向代理配置（Nginx）

握手失败八成出在反代。Nginx 关键配置：

漏掉 Upgrade/Connection 透传 → 后端按普通 HTTP 处理返回 400/426；proxy_read_timeout 默认 60 秒 → 空闲一分钟连接被代理静默断开（客户端只见 1006）。

七、心跳与重连（工程实践）

  • Ping/Pong 由协议层处理，但多数库默认间隔偏长；NAT/代理 常在 60–300 秒回收空闲连接，应用层建议每 30s 发一次业务心跳。
  • 客户端实现指数退避重连（如 1s、2s、4s…上限 30s，加抖动）；重连后重新订阅会话态数据。
  • 服务端横向扩容时，连接有状态：用 Redis Pub/Sub 或消息队列做跨节点广播。

八、安全注意

  • 生产使用 wss://；校验 Origin；首帧或握手带不可猜测 Token。
  • 限流与最大消息长度，防内存与 CPU 耗尽。
  • CSWSH（跨站 WebSocket 劫持）：浏览器会自动带 Cookie，服务端若只校验 Cookie 不校验 Origin，恶意站点可冒用用户身份建连——Origin 校验 + 一次性 Token 双保险。
  • 文本帧必须是合法 UTF-8；二进制帧内容仍需应用层解析校验，别把「协议安全」当「数据可信」。
