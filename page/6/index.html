Git · 团队协作工作流

入门篇之后的团队实战。分支模型对比 · Pull Request 流程 · 冲突解决 · Code Review · 规范提交 · 保护分支与 CI 联动。

技术栈速查

类别 选型 用途
平台 GitHub / GitLab / Gitee 托管与评审

工具 git 2.47+ 版本控制

1. 概念说明

单人 Git 只需 commit/branch；团队 Git 的核心是：分支模型（何时建分支）+ 评审流程（代码如何合入）+ 规范（提交/分支命名）+ 保护（主分支防破坏）。

核心原则：

  • main/master 永远可部署（合入即通过 CI）。
  • 每个功能一个分支，生命周期短（1-2 天）。
  • 代码必须经过 Review 才能合入。
  • 提交信息清晰可追溯（关联 issue 编号）。

2. 分支模型对比

2.1 GitHub Flow（最常用，推荐）

流程：从 main 拉分支 → 开发 → 推远程 → 开 PR → 评审+CI → 合并 → 删分支。

2.2 Git Flow（发布节奏固定）

适用：固定版本周期（如月发布）；对持续部署团队过重。

2.3 选择建议

场景 模型
持续部署的 Web 团队 GitHub Flow
版本化发布（SDK/App） Git Flow
中小团队/新项目 GitHub Flow 起步

7. 保护分支与 CI 联动

GitHub 设置：Settings → Branches → Add rule：

  • 保护 main：禁止直接 push（仅 PR 合入）。
  • 要求 PR 通过 CI 才能合并。
  • 要求 1-2 个 Review。
  • 强制线性历史 / 要求分支最新。

GitLab 对应：Settings → Repository → Protected branches + Merge request approvals。

分布式 · 分布式事务

从 0 到生产选型。事务演进与问题 · XA/AT/TCC/SAGA 对比 · Seata 实战 · 可靠消息最终一致 · 对账与补偿。代码带详细注释。

技术栈速查

类别 选型 用途
框架 Seata 2.x 分布式事务
注册中心 Nacos 3.x 配置与发现
消息 Kafka 4.x 最终一致
数据库 MySQL 8.4 事务存储
场景 订单/库存/账户三服务 典型案例

1. 概念说明

为什么需要分布式事务：微服务拆分后，一次下单跨”订单库 + 库存库 + 账户库”三个独立事务——本地事务无法保证一致性。

分布式事务核心指标：

  • 强一致（CP）：所有节点要么全成功要么全失败（XA/AT/TCC）。
  • 最终一致（AP）：先各自提交，通过异步补偿最终一致（SAGA/消息）。

工程共识：互联网业务 90% 用最终一致；只有资金类强约束场景用强一致。能用单库事务绝不分布式。

2. 四种方案对比

方案 原理 一致性 侵入性 性能 适用
XA 数据库原生 2PC 强 低 差（锁久） 老旧系统
AT 代理层生成反向 SQL 强 低 中 Seata 首选
TCC 业务三方法(Try/Confirm/Cancel) 强 高 高 资金/高并发
SAGA 正向+补偿事务 最终 中 高 长流程

2PC 问题（XA 的短板）：协调者单点、同步阻塞（资源锁定）、脑裂时不一致——所以现代方案用 AT/TCC/SAGA 规避。

3. Seata AT 模式实战（自动回滚）

原理：事务拦截器记录前后镜像（undo_log 表），提交时全局协调（TC）确认；失败时用反向 SQL 自动回滚——业务代码几乎零侵入。

4. TCC 模式（资金强一致）

业务实现三方法，Seata 只负责协调：

TCC 铁律：三方法都要幂等（Seata 会重试）；Confirm/Cancel 不能失败（失败走人工）。

5. SAGA 模式（长流程）

适用：跨天/多步骤长流程（旅行预订、审批流）；每步提交后释放资源，只在失败时执行反向补偿。

1. 概念说明

并发编程三个核心问题：

  • 原子性：一个操作不可分割（i++ 不是原子的）。
  • 可见性：线程修改了变量，其他线程能看到（CPU 缓存导致看不到）。
  • 有序性：指令重排导致执行顺序与代码不一致。

Java 内存模型（JMM）：线程共享主内存，各自有工作内存（缓存）；volatile、synchronized、Lock 通过内存屏障保证可见性与有序性。

选择铁律：能用 synchronized 就不用 Lock（jdk8+ 已优化）；能用并发容器就不用手动加锁；锁粒度越小越好。

容器 特性 适用
