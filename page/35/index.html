第一章：Golang 语言基础

概念基础

  1. 为工程而生：Go 由 Google 2009 年发布，目标是解决大型工程的编译慢、依赖乱、并发难三大痛点——编译秒级、go mod 原生依赖管理、语言级并发。
  2. 语法极简：全语言只有 25 个关键字，无类继承、无异常、无隐式转换，强制 gofmt 统一格式——评审时不再为风格争吵。
  3. 静态类型 + 垃圾回收：编译型语言享受类型安全与运行速度，GC 免去手动内存管理；值语义为主，切片/映射/指针是理解内存行为的关键。
  4. 组合优于继承：结构体嵌组合复用，接口隐式实现（duck typing 的静态化），小接口（io.Reader/error）组合出灵活抽象。
  5. 错误是值：没有 try/catch，函数用多返回值显式返回 error，调用方必须处理——代码啰嗦但流向清晰。

本章是 Golang 系列的起点，覆盖语法核心与工程结构。并发是 Go 的招牌，单独成章见 第二章：Golang 并发编程。

「接受接口，返回结构体」：函数参数用接口（宽进），返回具体类型（严出），调用方拿到的信息更多。接口值 = (动态类型, 动态值) 二元组，nil 接口 ≠ 持有 nil 指针的接口（陷阱：往 error 接口返回了 *MyErr(nil)，err != nil 为真）。

第四章：体系结构与存储管理

第四章：体系结构与存储管理

概念基础

  1. 内存 + 进程 + 文件三件套：Oracle 实例由 SGA（共享内存）+ PGA（私有内存）+ 后台进程构成，操作 Database 物理文件——理解三者的协作就抓住了 Oracle 运行的本质。
  2. 日志先行是命脉：事务提交时 LGWR 先把 redo 写联机日志才算「提交成功」，脏块由 DBWn 延迟批量落盘。这套 WAL 机制保证了实例崩溃后可恢复，是 Oracle 可靠性的根基。
  3. 逻辑/物理存储两层映射：逻辑上「表空间→段→区→块」，物理上「数据文件→操作系统块」——段对应表/索引、区是分配单位、块是最小 IO 单元。
  4. 多版本读一致性靠 UNDO：查询看到的是「查询开始时点」的数据快照，靠 UNDO 表空间的撤销数据回构——这是 Oracle 实现「读不阻塞写、写不阻塞读」的核心。
  5. 本章目标：从内存、进程、文件到存储分层与 ASM，建立完整的 Oracle 内部运行图景，为高可用与调优打基础。

本章承接 第三章：PL/SQL 程序设计。体系结构是 DBA 与架构师的必修课，也是后续高可用、调优章节的底层依据。

一、内存结构

1. SGA（System Global Area，共享全局区）

SGA 是所有服务进程共享的内存大区，由若干子池组成：

子池 职责 调优要点
Buffer Cache 缓存数据块，减少物理读 DB_CACHE_SIZE，命中率核心
Shared Pool 库缓存（SQL/PL/SQL 解析结果）+ 数据字典缓存 SHARED_POOL_SIZE，绑定变量缓解
Redo Log Buffer 缓存 redo 条目，LGWR 异步写盘 LOG_BUFFER，通常较小
Large Pool RMAN 备份、并行查询、共享服务器会话 可选，避免挤占 Shared Pool
Java Pool / Streams Pool JVM、GoldenGate/Streams 按需

2. PGA（Program Global Area，私有区）

PGA 是每个会话私有的内存，存放排序区、会话状态、游标：

区域 作用
Sort Area 排序中间结果，不足则写临时段
Hash Area 哈希连接用
Session Memory 会话变量、游标状态

SGA 是共享、PGA 是私有——这是内存模型的核心区分。排序/哈希在 PGA 跑，超限溢出到 TEMP 表空间（磁盘），是慢查询的常见元凶。

3. 内存管理演进

模式 机制 参数
手动 各池手动设固定值 DB_CACHE_SIZE 等逐个设
ASMM（10g+） SGA 内自动分配 SGA_TARGET + PGA_AGGREGATE_TARGET
AMM（11g+） SGA+PGA 全自动 MEMORY_TARGET（含 PGA）

生产推荐 ASMM（SGA_TARGET+PGA_AGGREGATE_TARGET）。AMM 在大内存/RAC/巨页场景有兼容问题，慎用。

二、后台进程

进程协作图



flowchart LR
  SESS[服务进程 Server] -->|修改块| BC[Buffer Cache 脏块]
  SESS -->|生成 redo| RLB[Redo Log Buffer]
  SESS -->|提交| LGWR
  RLB --> LGWR[LGWR 写盘]
  LGWR --> REDO[(联机重做日志)]
  BC --> DBWn[DBWn 异步落盘]
  DBWn --> DF[(数据文件)]
  REDO -.写满.-> ARCn[ARCn 归档]
  ARCn --> ARC[(归档日志)]

核心进程详解

进程 触发时机 作用
SMON 实例启动 / 定期 系统监控：实例恢复（前滚未落盘的 redo、回滚未提交事务）、合并空闲空间
PMON 会话异常退出 进程监控：清理死会话、释放锁与 PGA、注册服务到监听器
DBWn 脏块过多 / 检查点 把 Buffer Cache 脏块写数据文件，延迟批量，可多个（DBW0~DBW9）
LGWR 提交 / 1/3 满 / 每3秒 把 Redo Buffer 写联机日志，日志先行，提交的命脉
CKPT 检查点 同步数据文件头与控制文件的 SCN，触发 DBWn
ARCn 联机日志切换 归档模式才启用，把写满的联机日志拷贝到归档目录

LGWR 写顺序、DBWn 写数据：理解这点就懂了「为什么实例崩了数据不丢」——redo 已落盘，恢复时重放 redo + 回滚未提交。这也解释了归档模式为何是时点恢复的前提。

四、逻辑存储分层

Oracle 逻辑存储自上而下四层：



flowchart TB
  TS[表空间 Tablespace] -->|包含| SEG[段 Segment]
  SEG -->|由| EXT[区 Extent] -->|组成| BLK[数据块 Block]

层次 说明 关键点
表空间 逻辑容器，对应多个数据文件 业务隔离单位
段 Segment 一个表/索引一个段 占空间的对象
区 Extent 连续块的分配单位 扩展时按区分配
块 Block 最小 IO/分配单元 默认 8KB，DB_BLOCK_SIZE

1. 数据块内部

一个数据块（默认 8KB）内部结构：

  • ITL（Interested Transaction List）：块内事务槽，记录哪些事务在改本块。INITRANS 初始事务数（默认 1），MAXTRANS 上限。
  • PCTFREE：预留空闲比例（默认 10%），给 UPDATE 留空间，避免行迁移。
  • 高水位线 HWM：段曾用到的最高块位置，SELECT 全表扫到 HWM 即止。TRUNCATE 重置 HWM，DELETE 不重置。

2. 行迁移与行链接

现象 原因 影响
行迁移 Row Migration UPDATE 后行变长，块 PCTFREE 不够，整行移到新块，原块留指针 多一次 IO
行链接 Row Chaining 行本身超一个块（大字段），跨块存储 不可避免

PCTFREE 调高可减少行迁移（留更多更新空间），代价是空间利用率下降。大字段用 LOB 单独存。

六、UNDO 与读一致性

1. UNDO 的作用

UNDO 表空间存放「改之前」的旧值，支撑三大机制：

  1. 事务回滚：ROLLBACK 时用 UNDO 恢复原值。
  2. 读一致性：查询看到查询开始时点的数据，靠 UNDO 回构已被改的块。
  3. 闪回查询：AS OF TIMESTAMP 利用 UNDO 看历史数据。

2. 多版本读一致性

参数 作用
UNDO_RETENTION UNDO 保留时间（秒），降低 ORA-01555
UNDO_TABLESPACE 指定 UNDO 表空间
TEMP_UNDO_ENABLED 12c+ 临时表 UNDO 独立

ORA-01555 快照太旧是长查询经典错误：UNDO 数据被新事务覆盖，旧版本回构不出来。调大 UNDO_RETENTION 与 UNDO 表空间、避免长查询跨大事务可缓解。

七、REDO 与归档

1. REDO 的写入流程

  1. 会话修改块，生成 redo 条目入 Redo Log Buffer。
  2. 提交时 LGWR 把 redo 写联机日志（同步），提交返回。
  3. DBWn 延迟把脏块写数据文件（异步批量）。
  4. 联机日志写满切换，ARCn 归档（ARCHIVELOG 模式）。

2. NOARCHIVELOG vs ARCHIVELOG

模式 联机日志 能力 适用
NOARCHIVELOG 写满即覆盖 只能恢复到上次冷备 开发/测试
ARCHIVELOG 归档保留 可时点恢复（PITR） 生产必须

生产必须 ARCHIVELOG——否则磁盘损坏只能恢复到上次备份点，丢失期间所有数据。归档目录要监控空间，写满会挂起数据库。

八、ASM（自动存储管理）

ASM 是 Oracle 提供的卷管理器，直接管理裸磁盘，免去文件系统层：



flowchart TB
  DG[磁盘组 Disk Group] --> D1[磁盘 1]
  DG --> D2[磁盘 2]
  DG --> D3[磁盘 3]
  DG -->|条带/镜像| AU[分配单元 AU 1~64MB]
  AU --> FILE[ASM 文件 .dbf]
  DB[Oracle 实例] -->|直接 IO| FILE
概念 说明
磁盘组 Disk Group 一组磁盘的逻辑集合
AU 分配单元，1~64MB（大库建议 4MB+）
冗余 External（外部 RAID）/ Normal（2 镜像）/ High（3 镜像）
条带化 跨磁盘条带，提升吞吐

ASM 的优势：

  1. 自动条带与镜像，I/O 均衡。
  2. 在线增减磁盘、自动重平衡（ASM_POWER_LIMIT 控制速度）。
  3. 与 RAC 共享存储天然契合。
  4. 避开文件系统开销，裸设备级性能。

RAC + ASM 是 Oracle 推荐的共享存储组合。单实例也可用 ASM，但运维门槛高于文件系统，小库用文件系统更简单。

九、CDB/PDB 多租户架构

12c 引入的多租户架构，一个 CDB 容器承载多个 PDB：



flowchart TB
  CDB[CDB 根容器] --> ROOT[CDB$ROOT 根 - 元数据/公共用户]
  CDB --> SEED[PDB$SEED 种子 - 建库模板]
  CDB --> PDB1[业务 PDB 1]
  CDB --> PDB2[业务 PDB 2]
层 说明
CDB$ROOT 系统级元数据、公共用户（C##）
PDB$SEED 创建 PDB 的只读模板
PDB 可插拔数据库，业务隔离单位

多租户价值： consolidation（多库合一降运维）、资源隔离、快速克隆（克隆开发库）、可拔插迁移。19c 后多租户成为默认架构，单 PDB 免费。

第一章：Oracle 数据库入门

概念基础

  1. 企业级关系型数据库：Oracle Database 是老牌商业 RDBMS，在银行、电信、政务等对稳定性、安全合规与厂商支持要求高的核心系统中长期占主导地位。
  2. 实例与数据库分离：Instance（内存 SGA + 后台进程）挂载并打开 Database（物理文件集合），多实例可共享访问同一套库（即 RAC）。理解「实例是内存进程、数据库是文件」是入门第一关。
  3. 逻辑存储分层：数据组织在表空间（SYSTEM / SYSAUX / USERS / TEMP / UNDO）中，向下再划分为段、区、块——这套分层决定了建库、扩容、调优的思维方式。
  4. 高可用与容灾：RAC 多节点共享存储集群、Data Guard 主备容灾，配合 RMAN 备份恢复构成企业级方案，这是 Oracle 区别于开源库的核心竞争力。
  5. PL/SQL 过程化扩展：存储过程、包、触发器可在库内实现复杂业务逻辑，减少应用与数据库之间的往返——既是优势也是「业务逻辑下沉」的双刃剑。

本章是 Oracle 系列的总览与起点。先建立「实例/数据库/Schema」的体系结构心智模型，再跑通最小 SQL 与连接示例，后续章节逐层深入 SQL、PL/SQL、存储、高可用与调优。

1. 三层对应关系

层次 组成 性质
Instance 实例 SGA（共享内存）+ 后台进程 内存态，重启即重建
Database 数据库 数据文件、控制文件、重做日志 磁盘态，持久存在
Schema 模式 用户拥有的对象（表、视图、过程等） 逻辑概念，隶属于用户

关键区分：实例是「跑起来的内存进程」，数据库是「磁盘上的文件」。实例挂掉数据不丢（落盘），但内存中的未提交事务会因 undo 回滚。这套机制详见 第四章：体系结构与存储管理。

2. 后台进程速记

进程 职责 记忆点
PMON 进程监控，清理异常死掉的会话 Process Monitor
SMON 系统监控，实例恢复、合并空闲空间 System Monitor
DBWn 数据库写进程，把脏块从 Buffer Cache 落盘 DataBase Writer
LGWR 日志写进程，把 Redo Log Buffer 写联机日志 LoG Writer（写顺序的命脉）
CKPT 检查点，同步数据文件头与控制文件 CheckPoint
ARCn 归档进程，联机重做日志写满后拷贝归档 Archiver（ARCHIVELOG 模式才有）

LGWR 是性能与安全的命脉：事务提交时 LGWR 把 redo 落盘即算提交成功，DBWn 则延迟批量落盘。所谓「日志先行（WAL）」即此。

第三章：MongoDB 索引、聚合与模式设计

概念基础

  1. MongoDB 慢查询九成是索引问题：无索引的 find 是全集合扫描（COLLSCAN）；建对索引变成 IXSCAN，与关系库的「先看执行计划」哲学一致。
  2. ESR 原则定复合索引字段序：Equality（等值）→ Sort（排序）→ Range（范围），顺序排对一条复合索引能同时服务过滤与排序。
  3. 聚合管道是 MongoDB 的「SQL+ETL」：$match → $group → $sort → $project ... 流水线处理，能下推的尽量下推（先 $match 后 $group）。
  4. 模式设计决定性能上限：文档模型核心取舍是内嵌（embed）还是引用（reference）——按「一起读写就内嵌、各自更新就引用」判断。
  5. explain 是证据不是感觉：executionStats 里的 totalKeysExamined / totalDocsExamined / nReturned 三值关系直接给出诊断。

一、explain：诊断查询

三个关键数字：

字段 含义 健康标准

totalKeysExamined 扫过的索引条目 接近 nReturned
totalDocsExamined 扫过的文档数 接近 nReturned（远大=回表浪费）

同时确认 winningPlan 里是 IXSCAN 而非 COLLSCAN；SORT_STAGE 出现说明排序没吃到索引（内存排序 32MB 上限会直接报错）。

二、索引体系

实践要点：

  • 每个额外索引都拖慢写入——索引不是越多越好，按真实查询建。
  • db.orders.getIndexes() 盘点存量；低效索引用 dropIndex 清理。
  • 大集合建索引用后台滚动构建（4.2+ 默认后台方式），避开写入高峰。
  • 最左前缀同样适用：{ userId, status, createdAt } 可服务 userId 与 userId+status 的查询。

三、聚合管道进阶

管道优化口诀：

原则 说明
$match/$limit 放最前 能被索引下推，后面的阶段数据越少越好
$project 砍字段 减少内存与网络传输
$group 用 _id: null 全表聚合（配合 $facet 一次算多组指标）
允许近似 超大集合统计可接受秒级误差时用 $sample 或预聚合

四、模式设计：内嵌还是引用

判断口诀：

场景 选择
1:1 或 1:少量（生命周期一致） 内嵌
1:多且子文档无限增长（评论、日志） 引用（或「内嵌最近 N 条 + 冷数据独立集合」）
多对多 引用
内嵌文档 16MB 上限 逼近上限必须拆

常见增强：$lookup 慢的高频关联可冗余一份 userName 到订单文档（写入时双写），用读时免 JOIN 换写时多一步——文档模型下的「反范式」是常规操作。

五、事务与批量写入

单文档天然原子：把需要原子性的关联数据内嵌进同一文档，很多「事务需求」就直接消失了——这是文档建模的隐藏红利。

第一章：MongoDB 概述与入门

概念基础

  1. 文档数据库：MongoDB 是面向文档的 NoSQL 数据库，数据以 JSON/BSON 文档存储，字段可嵌套、可数组——一个文档天然对应一个业务对象。
  2. 层级模型：Database → Collection → Document，类似关系库的「库 → 表 → 行」，但 Collection 不强制固定 Schema，同一集合内文档字段可以不一致，适合业务快速演进。
  3. 主键默认自带：每个文档有唯一 ObjectId 主键 _id，无需提前设计自增列。
  4. 默认端口与工具：默认监听 27017，交互用 mongosh（替代旧版 mongo CLI），命令风格贴近 JavaScript。
  5. 定位与取舍：需要强事务、复杂 JOIN 时关系库更成熟；需要灵活文档 + 水平扩展时 MongoDB 更常见——二者互补而非替代。

第一章：PostgreSQL 概述与 DDL 入门

概念基础

  1. PostgreSQL 是开源的对象-关系型数据库：以 SQL 标准兼容与丰富的数据类型、扩展生态著称；数据按 数据库 → 模式（SCHEMA）→ 表 分层组织，客户端用 psql 或 JDBC 等驱动访问。
  2. SQL 按职责分两层：DDL（数据定义语言）管结构——库、模式、表、列、索引等对象的创建与变更；DML（数据操作语言）管数据——行级增删改查。本章聚焦 DDL。
  3. 为什么从 DDL 学起：结构是一切的地基——后面的高级查询、索引与性能、并发与 MVCC 都建立在「先有表结构」之上；类型与约束设计得当，能直接挡住一大批脏数据。
  4. 一条主线：CREATE 建、ALTER 改、DROP 删；生产环境永远先确认影响面（活跃连接、依赖对象），并养成 IF EXISTS 幂等习惯。

先看一条 DDL 在「客户端 → 引擎」链路中的位置：

DDL：数据定义语言

DDL：Data Definition Language 数据定义语言
作用：定义/修改/删除 数据库、模式（SCHEMA）、表、字段、索引等对象结构，不直接操作「行级业务数据」本身（数据由 DML 写入）。

第一章：MySQL DDL 语句与表设计入门

概念基础

DDL（Data Definition Language，数据定义语言）是 MySQL 中定义「结构」的语言：

  1. 管结构，不管数据：DDL 负责定义/修改/删除数据库、表、字段、索引、视图等对象，不操作表里的业务数据；管数据的是 DML（INSERT / UPDATE / DELETE / SELECT）——一句话记忆：「DDL 改架子，DML 改数据」。
  2. 建表即建模：把业务对象翻译成表，核心是选字段类型（INT / VARCHAR / DATETIME…）与定约束（主键、非空、唯一、默认值、外键）；结构一次设计、长期使用，返工成本高，所以建表是数据库学习的第一课。
  3. 结构最终落在存储引擎上：客户端 SQL 经 MySQL Server 交给 InnoDB，数据按主键组织成 B+ 树，通过 Buffer Pool 缓存、Redo Log 保证崩溃安全——表与索引结构如何组织，直接决定后面的查询性能（详见第五章、第六章）。
  4. 三大类对象：库操作、表操作，以及视图 / 索引 / 存储过程等对象定义；语句形式永远是 CREATE / ALTER / DROP 三板斧。
  5. 约束的权衡：FOREIGN KEY、UNIQUE 等约束由数据库兜底完整性，但会带来额外维护开销、且不利于分库分表，互联网业务常改用「逻辑外键」；入门先学会用，进阶再权衡取舍。
