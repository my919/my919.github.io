第一章：ZooKeeper 实践：核心概念、CLI 与 Docker 部署

概念基础

  1. 分布式协调服务：ZooKeeper 为分布式系统提供配置管理、命名服务、分布式锁与选主等基础原语，是 Kafka、Hadoop 等大数据组件的经典协调底座。
  2. 数据模型像文件树：数据组织为 ZNode 树（如 /app/config），节点可存少量元数据（默认 1MB 上限），客户端可挂 Watcher 监听变化——读多写少是它的设计前提。
  3. 强一致靠多数派：基于 ZAB 协议，写请求需过半节点确认；集群必须奇数个节点（3 节点容忍 1 故障，5 节点容忍 2）。
  4. 四种节点类型：持久、持久顺序、临时、临时顺序——临时节点随会话消失，是「服务注册与故障感知」的基石。
  5. Client 用 zkCli 上手：官方脚本 zkCli.sh 覆盖增删改查与监听，本地理解语义后再看 Java/Go 客户端。
  6. 部署形态：本地开发用 docker run 单容器，自托管服务用 Docker Compose 编排，K8s 环境用清单部署（生产建议 StatefulSet/Operator）。

本章命令基于 ZooKeeper 3.9 官方 CLI 语法书写（沙箱无实例，未逐条运行验证）。

三、ZAB 协议：过半写与崩溃恢复

ZK 的一致性由 ZAB（ZooKeeper Atomic Broadcast） 协议保证，协议只有两种运行模式：

模式 进入时机 职责
广播（Broadcast） 集群正常服务 Leader 把每个写请求变成 Proposal 发给 Follower，过半 ACK 后 Commit 并广播提交结果
恢复（Recovery） Leader 宕机 / 过半失联 先选主（zxid 最大、myid 大者优先），再以新 Leader 为基准同步差异数据，同步完成前不对外服务

zxid（64 位事务 ID）：高 32 位是 epoch（任期），每换一次 Leader 加 1；低 32 位是该任期内的递增计数。比较两个 zxid 就是在比较「谁的数据更新」，选主与数据同步全靠它——stat 输出里的 czxid / pzxid 也是这个结构。

读写路径要分清：

  • 读走本地：客户端连到哪个节点就从哪个节点读，所以读性能随节点数水平扩展（代价是可能读到稍旧的数据，强一致读时先 sync）；
  • 写走 Leader：客户端发给 Follower 的写请求会被转发给 Leader 广播，加节点不提升写吞吐，反而增加多数派通信开销——这是「3 或 5 个节点足够」的根本原因。

过半机制的推论：3 节点容忍 1 故障、5 节点容忍 2；4 节点仍只容忍 1，白养一台机器——所以集群总是奇数。

四、Watcher：一次性通知

关键语义：

  • Watcher 是一次性的——触发一次即失效，客户端 SDK 需重新注册（Curator 的 Cache 帮你做了）。
  • 通知的是**「事件发生了」，不带新数据；收到通知后要自己再读一次**，避免丢增量。
  • 会话断开期间的事件不会补发，重连后应主动全量拉取对齐。

事件类型（get -w 关注节点本身，ls -w 关注子节点列表）：

事件 触发时机 典型注册方式
NodeCreated 节点被创建 exists -w
NodeDataChanged 数据被 set get -w
NodeChildrenChanged 直接子节点增删（不含子节点数据变化） ls -w
NodeDeleted 节点被删除 exists -w / get -w / ls -w

3.6+ 新增 addWatch 持久监听：注册一次持续生效（可选只监听本节点或递归子树），消除了「触发后重新注册」之间的丢失窗口——Curator 5.x 的 Cache 已切到这条路径。

五、会话管理：临时节点的生命线

临时节点的生与死绑在**会话（Session）**上，理解会话才能理解 ZK 的故障语义：

  1. 创建：客户端连接时协商 sessionTimeout（合法区间 2~20 × tickTime），服务端返回 sessionID + password。
  2. 保活：客户端周期发心跳（任何读写请求也算），服务端在 sessionTimeout 内没收到任何消息即判定过期。
  3. 过期的后果：该会话所有临时节点被删除、持有的锁自动释放、其上 Watcher 一并失效——这是「进程崩溃自动释放锁」的正确性来源。
  4. 重连与迁移：网络断开 ≠ 过期。客户端带 sessionID + password 连到集群任意节点即可恢复会话；重连期间其它客户端看到的临时节点还在。
  5. 两个回调状态必须区分：Disconnected 只是暂时失联（节点未必没了），Expired 才是真过期（节点确定没了，必须重建注册/重新抢锁）。Curator 的 ConnectionStateListener 就是干这个的。

典型坑：sessionTimeout 设太短 + Full GC 长停顿 → 心跳超时被误判死亡，临时节点集体消失，锁被「偷」。JVM 停顿治理和会话超时要放在一起看。

七、经典配方：锁与选主

1. 分布式锁（临时顺序节点）

只监听前一个节点而非所有节点（羊群效应规避），通知风暴从 N 降到 1。

2. 选主（Master Election）

与锁同理：/election/node- 最小序号为 leader；leader 会话断开（进程崩溃）后临时节点消失，次小序号自动上位——故障感知由会话心跳完成，无需额外探活。

生产不手写这些协议：Java 用 Apache Curator（封装好 InterProcessMutex、LeaderLatch），Kafka 2.8+ 更是用 KRaft 替代了 ZK——理解原理是为了看懂你正在用的库。

八、典型应用场景

场景 用到的原语 说明
配置中心 持久节点 + Watcher /app/config/db 存配置，客户端挂监听实现热更新；数据量大了换 Nacos/Apollo
服务注册/命名 临时节点 提供者启动即注册 /services/svc/addr-0001，宕机会话过期自动摘除
选主 临时顺序节点 HDFS NameNode HA、HBase Master 都是这个模式
分布式锁 临时顺序节点 + 前驱监听 见上一节配方；Curator InterProcessMutex 即用
集群成员管理 临时节点 + 子节点监听 老版本 Kafka（2.8 前）的 Broker 列表与 Topic 元数据全在 ZK

共同点画像：数据小、读多写少、要强一致 + 变更通知——超出画像就该换工具。

以「配置中心」为例把前面各节串起来的最小数据流：



flowchart LR
  Admin[运维改配置] -->|set /app/config| ZK[(ZooKeeper)]
  ZK -->|NodeDataChanged 通知| App[业务实例]

九、ZooKeeper 的边界

适合 不适合
元数据、配置、注册表（小数据） 业务数据存储（1MB 上限、写吞吐有限）
选主、锁、分布式队列等协调原语 高频计数器/实时指标（写多场景）
强一致的少量关键状态 最终一致可接受的大流量场景（用 MQ/Redis 更合适）

会话参数：tickTime（心跳单位）、sessionTimeout = 2~20 × tickTime；网络抖动超过 sessionTimeout 临时节点即消失——服务注册场景要把它与业务健康检查区分开。

第七章：OpenSSL 密钥派生与随机数：PBKDF2、rand 与推荐用法

概念基础

  1. 随机数是密码学之根：密钥、IV/nonce、salt、session token、HMAC secret 全部来自 CSPRNG（openssl rand 内部即此）——随机性不足，再强的算法也是空谈。
  2. 口令 ≠ 密钥：人类口令熵低、可猜测、常重复，直接当 AES 密钥会被暴力破解；必须经 KDF（密钥派生函数） 处理。
  3. KDF 的两大武器：salt（防彩虹表与预计算）+ 高迭代次数（把每次猜测的成本拉高千万倍），PBKDF2 建议迭代 ≥ 600000。
  4. 场景分流：文件加密口令 → PBKDF2（enc -pbkdf2 已内置，见第四章）；协议密钥 → HKDF（TLS 1.3 内部自动完成）；口令存储 → Argon2id（应用层专用库）。
  5. 本章定位：作为末章收束全书——把前几章密钥的「来源」讲透：第四章的 AES 密钥、第六章的 HMAC secret，都在这里生成与派生。

第六章：OpenSSL 数字签名与 HMAC：完整性、身份与推荐用法

概念基础

  1. 数字签名 = 私钥签名 + 公钥验证：一次性保证完整性（内容未被篡改）、身份认证（签名者身份可信）与不可否认（只有私钥持有者能签出）。
  2. 标准流程：先对消息做哈希（SHA-256，见第三章），再用私钥对摘要签名；验证方用公钥复算比对——这也是「对大数据直接 RSA 签名」是错误做法的原因。
  3. HMAC 是对称认证：双方共享同一 secret，用 HMAC-SHA256 计算带密钥的摘要；快、实现简单，但双方都能生成，因此不可否认。
  4. 怎么选：公开分发场景（软件发布、证书、JWT）→ 数字签名；双方已有共享密钥的场景（API / Webhook 鉴权）→ HMAC。
  5. 常见坑：对明文直接 RSA 签名大数据、HMAC 密钥硬编码进代码、验签时不检查证书链——本章末尾「常见错误」逐条纠正。

第五章：OpenSSL 非对称加密与密钥交换：RSA、Ed25519、X25519

概念基础

  1. 非对称加密：公钥 / 私钥成对，公钥公开分发、私钥绝对保密——解决了对称加密「密钥如何安全送达」的死结（对称加密见第四章）。
  2. 三大用途：数字签名（私钥签、公钥验，见第六章）、密钥交换（ECDHE/X25519 在不安全信道协商会话密钥）、小数据加密（RSA-OAEP 加密对称密钥）。
  3. 为什么 TLS 用混合方案：非对称慢（比对称慢几个数量级），只用于握手阶段；海量数据用协商出的对称会话密钥（AES-GCM）加密。
  4. 前向保密（PFS）：握手使用临时密钥对（X25519 / ECDHE），即使服务器长期私钥日后泄露，历史会话也解不开——静态 RSA 密钥传输因此被淘汰。
  5. 选型一句话：签名与证书新系统优先 Ed25519 / ECDSA P-256，密钥交换用 X25519，RSA 2048+ 仍是最普遍的兼容选择。

第四章：OpenSSL 对称加密：AES-GCM、ChaCha20 与推荐用法

概念基础

  1. 对称加密：加密与解密使用同一把密钥，速度快、开销低，适合大块数据（文件、磁盘、TLS 记录层流量）。
  2. 两大要素：算法 + 工作模式（如 AES-256-GCM）决定安全性质；密钥来自随机数或口令派生（PBKDF2，见第七章）。
  3. 为什么推荐 AEAD：GCM / ChaCha20-Poly1305 属于认证加密，同时提供保密性 + 完整性（Auth Tag 防篡改）；裸 CBC / ECB 无认证，存在填充 oracle 等风险。
  4. Nonce 纪律：GCM 的 (key, nonce/IV) 绝不能重复，否则密钥流泄露、安全性崩塌——这是使用 AEAD 的头号大坑。
  5. 口令 ≠ 密钥：人类口令熵低、可猜测，必须经 KDF（salt + 高迭代） 派生密钥；生产环境更推荐随机 32 字节密钥。

第三章：OpenSSL 哈希算法：SHA-256、SHA-3 与推荐用法

概念基础

  1. 哈希（Hash）是单向函数：任意长度输入 → 固定长度摘要（SHA-256 输出 256 bit），不可逆——无法从摘要还原原文。
  2. 三大特性：确定性（同输入必得同输出）、雪崩效应（改动 1 bit，摘要面目全非）、抗碰撞性（极难找到两个不同输入对应同一摘要）。
  3. 为什么需要：完整性校验（下载包比对、防篡改）、签名输入（先哈希再签名，见第六章）、口令派生（加盐迭代，见第七章）、区块链 Merkle 树等。
  4. 哈希 ≠ 加密：哈希不可逆、无密钥，用于完整性与指纹；对称加密可逆、有密钥，用于保密性（本章末尾有对照表）。
  5. 选型一句话：新系统一律 SHA-256 / SHA-512，需要算法多样性时上 SHA-3；MD5、SHA-1 仅用于遗留系统兼容。

二、图像即 NumPy 数组（核心心智模型）

OpenCV 读入的彩色图是 H×W×C 的 uint8 数组，通道顺序 BGR：

三个易错点：

  1. 坐标顺序：img[y, x] 是「行、列」，即先纵坐标 y 再横坐标 x，与 (x, y) 直觉相反。
  2. BGR 不是 RGB：matplotlib 显示需先 cv2.cvtColor(img, cv2.COLOR_BGR2RGB)，否则红蓝颠倒。
  3. shape 顺序：shape = (H, W, C)，高在前；cv2.resize(img, (W, H)) 传参是「宽、高」，两处顺序相反。

Mat 内存模型（C++ 侧同理）

cv::Mat 是「头 + 数据体」结构：头记录维度、类型、步长（step/strides），数据体按引用计数共享——

Python 侧对应关系：img2 = img 是视图/引用，img2 = img.copy() 是深拷贝，img[y1:y2, x1:x2] 切片也是视图（写切片会写回原图，需要独立副本时加 .copy()）。数据连续与否可用 img.flags['C_CONTIGUOUS'] / mat.isContinuous() 判断——连续的 Mat 可以一次性 memcpy 整块，很多底层优化依赖这一点。

dtype 与通道数：CV_8UC3 = uint8 × 3 通道（Python 中体现为 dtype=uint8, shape=(H,W,3)）。常见还有 CV_32FC1（float32 单通道，滤波/深度图常用）。用错 dtype 是数值类 bug 之源：比如把 uint8 梯度直接相加会饱和，需先 img.astype(np.float32)。
