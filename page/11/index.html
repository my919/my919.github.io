踩坑点：

  1. hash tag 上线时图省事，把商品详情也加了 tag（product:{categoryId}），某分类下 3 万个商品全落在同一槽，该分片内存是其他分片 6 倍、CPU 90%——tag 只给”必须同槽”的数据用，其他数据保持散列。
  2. 购物车结算用的 Redisson 分布式锁 key 没加 tag，锁和被锁的数据不在同一节点，锁语义失效出现超卖——分布式锁与受保护资源使用相同 hash tag（如 lock:{1001} 对 cart:{1001}）。
  3. reshard 迁移槽时选了业务高峰，迁移中的槽（ASKING 状态）请求延迟 200ms+，接口 P99 抖到 800ms——槽迁移必须在低峰分批执行，每批观察客户端错误率再继续。
  4. 客户端没开拓扑刷新（Lettuce 默认 enableAllAdaptiveRefreshTriggers 未开启），扩容新增节点后老节点返回 MOVED，客户端重试风暴持续 5 分钟——集群模式必须开启拓扑刷新 + 重试退避。
  5. 迁移前未演练”半迁移状态”（一部分用户已在新 key 结构、一部分在旧结构），双读兼容逻辑上线时才发现漏了旧 key 的降级读取，造成 30 分钟购物车”丢商品”的假象——迁移类改造必须先写双读/双写影子验证。

1. 概念说明：为什么需要”对账”

背景：分布式系统没有完美的事务（2PC 性能差、TCC 复杂），生产实践是保证最终一致性 + 定期对账兜底。

对账的定义：定期把两边的数据拉出来比对（本地库 vs 渠道/对方系统），找出不一致并修复。

对账 vs 事务：

方式 保证 代价
分布式事务（TCC/2PC） 强一致 复杂、性能差、可用性下降
消息可靠投递 + 幂等 最终一致（大部分场景） 仍有极端丢失
对账（兜底） 最终一致（查漏补缺） 延迟发现（T+1）

结论：事务 + 消息保证”常态正确”，对账保证”出错能发现”——三者是组合关系，不是替代。

8. 典型案例：Pod OOMKilled 与资源调优

问题背景：线上某 Java 服务频繁出现 OOMKilled，同时部分 Pod 处于 Pending 状态调度不了。经排查：limits.memory 设太小（256Mi）但 JVM 实际需要 512Mi；而 requests.cpu 设太大（2 核）导致节点资源不够调度。需要合理设置 requests/limits，平衡稳定性与资源利用率。

方案：

配置项 原值 调优值 原因
requests.memory 256Mi 300Mi 保证调度，略高于稳态
limits.memory 256Mi 768Mi 覆盖峰值 + 余量
requests.cpu 2000m 500m 稳态只需 0.5 核
limits.cpu 2000m 1000m 允许突发到 1 核

关键 Deployment：

踩坑点：

  1. limits.memory 必须大于 JVM 最大堆 + 非堆内存：JVM 内存 = 堆 + 元空间 + 线程栈 + 直接内存。只设 -Xmx512m 但 limits=512Mi 会因为非堆内存超限而 OOMKilled。建议 limits = Xmx * 1.5。
  2. requests 太大会导致 Pending：若 requests.cpu=2 但节点只剩 1.5 核，Pod 永远调度不了。requests 应按稳态而非峰值设置。
  3. 不设 limits 的风险：无 limits 时容器可占用节点全部资源，异常时可能拖垮整个节点。生产环境必须设 limits。
