1. 应急响应流程（先救命，再查因）

排障铁律：先恢复服务，再定位根因——用户在用系统，不是等你研究。

为什么先缓解再查因：故障现场可能被重启清掉，但先保证用户可用是第一位；现场证据靠”监控 + 日志 + 快照”保留，重启前可顺手抓 jstack/jmap（见 JVM 篇）。

11. 常见误用与陷阱

坑 现象/后果 解法
故障时先查根因不先缓解 用户持续受损 40 分钟，就为了搞清”为什么” 严格执行”先恢复再查因”：回滚/重启/切流/扩容优先，现场用日志快照保留
重启解决一切 连接池打满、慢 SQL、依赖故障场景下重启无效，还丢现场 先看日志错误分类（pool/timeout/OOM），再决定重启还是处置依赖
告警全部同一级别不分级 30 条告警一起响，值班分不清主次，错过关键信号 告警分级（P0 电话/P1 群通知/P2 看板），并按影响面（接口/用户量）聚合
KILL 长事务前不确认归属 误杀结算/迁移任务，制造第二起故障 KILL 前查 INNODB_TRX 确认事务来源，高危会话先问业务方
临时调大连接池当长期方案 慢 SQL 还在，只是把数据库连接耗尽变成数据库 CPU 耗尽 连接池只调到压测验证值；根因（慢 SQL/锁）必须另开行动项治理
复盘变成追责大会 当事人隐瞒细节，行动项空泛（”加强意识”） 复盘对事不对人：时间线+根因+为什么没提前发现+可验证行动项（负责人+期限）
恢复后立即结案 半小时后二次复现，二次故障影响翻倍 指标回归基线后观察 30 分钟再宣布恢复，复盘 24 小时内产出

踩坑点：

  • top 里 %Cpu(s) 的构成先分清：us 高查应用代码、sy 高查 syscall/上下文切换、wa 高查磁盘 IO——wa 高时杀进程无济于事。

组合实体模式详解（Composite Entity）

发表于 2026-09-14 更新于 2026-10-29 分类于 设计模式 本文字数： 3.2k 阅读时长 ≈ 3 分钟

设计模式 · 组合实体

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点。

1. 模式概述（意图）

组合实体（Composite Entity）把一组相互关联的对象（粒度对象）聚合为一个粗粒度实体，通过它统一访问——外部只与组合实体打交道，内部对象对外隐藏。

2. 要解决的问题

问题 说明
多个对象协同更新 用户资料=基本信息+地址+偏好，分别更新易不一致
外部接口太碎 表现层要分别调用多个对象的 get/set
一致性难以保证 一次会话/请求要更新多个对象

典型场景：会话管理（Session 里多个粒度对象）、用户档案聚合、订单聚合（订单+明细+地址）、EJB 实体 Bean 的粗粒度设计。

3. 结构（角色）

4. 代码实现（用户档案）

5. 应用场景

场景 说明
用户档案 基本信息+地址+偏好聚合
订单聚合 订单+明细+配送
会话管理 Session 粒度对象组合
EJB 实体 粗粒度实体 Bean
表单提交 多子表单一次提交

6. 优缺点

优点 缺点
外部接口统一（少而稳） 内部粒度对象失去独立访问
更新一致（一次协调） 组合实体易膨胀
隐藏内部结构 需要时难以单独操作某个子对象
简化表现层 结构固定后难以拆分

7. 与其他模式对比

模式 区别
组合模式 组合是树形结构递归；组合实体是固定一组对象聚合
门面 门面封装接口；组合实体封装数据对象组
DTO DTO 是传输载体；组合实体含协调逻辑（不只数据）

8. 常见误用与陷阱

坑 现象 解法
粗粒度锁 整个组合实体一把大锁，只改一个子对象也阻塞其他全部更新 缩小锁粒度或用乐观锁版本号，按实际变更的子对象加锁
持久化状态与组合不一致 两个子对象写库，第二个失败，内存却已改完，状态分裂 划定一个事务边界统一提交、失败整体回滚，由组合根保证一致性
照搬 EJB 实体 Bean 新项目仍手写粗粒度对象 + 多层 dependent object 层级 现代用 DDD 聚合根 + Repository：聚合内强一致，聚合间最终一致
内部对象引用外泄 getter 返回内部子对象，外部绕过协调逻辑直接改 返回副本或不可变视图，修改只能走组合实体的方法
组合无限膨胀 什么对象都往里塞，setData 参数列表越来越长 按一致性边界拆分聚合，一个事务只保护一个聚合

业务代表模式详解（Business Delegate）

发表于 2026-09-14 更新于 2026-10-29 分类于 设计模式 本文字数： 2.9k 阅读时长 ≈ 3 分钟

设计模式 · 业务代表

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与门面/代理对比。

1. 模式概述（意图）

业务代表（Business Delegate）在表现层与业务层之间加一个中间代表：表现层只调用代表，代表负责查找服务、调用业务、处理异常——表现层不再直接碰远程/业务服务。

2. 要解决的问题

问题 说明
表现层直接调远程服务 JSP/Servlet 里写 JNDI 查找 + RMI 调用
业务调用细节重复 每次调用都处理查找、异常、重试
远程异常泄漏到视图 表现层要理解底层异常

典型场景：J2EE 老架构（JSP → 业务代表 → EJB）、客户端调用远程服务的封装层、表现层需要稳定 API 的场景。

3. 结构（角色）

4. 代码实现（订单业务代表）

5. 应用场景

场景 说明
J2EE 老架构 JSP → 业务代表 → EJB
远程服务封装 表现层调远程业务统一入口
客户端 SDK 封装服务发现与调用
多后端切换 表现层 API 稳定，后端可换

6. 优缺点

优点 缺点
表现层解耦（稳定 API） 多一层调用
封装查找/异常/重试 简单应用是过度设计
便于测试（mock 代表） 表现层可能绕过代表直接用服务
后端可替换 代表易膨胀

7. 与其他模式对比

模式 区别
门面 门面封装子系统调用；业务代表封装业务服务调用（含查找）
代理 代理控制访问；业务代表提供”业务语义”入口
服务定位器 业务代表内部常用服务定位器查找服务

8. 常见误用与陷阱

坑 现象 解法
委派层变贫血转发 代表方法体只有一行 return service.xxx()，纯多一层、无任何收益 代表至少承担查找/异常翻译/重试/日志之一；纯转发直接注入 Service
异常被吞 catch (Exception) 后直接返回兜底文案，故障无日志、无告警 先记日志/打点再转成业务异常并保留 cause，禁止静默吞掉
与服务定位器职责混淆 代表内部维护静态 Map、注册服务实例，编排与查找两套职责纠缠 查找与缓存归 ServiceLocator/容器，代表只做调用编排与异常翻译
代表塞入业务规则 参数校验、价格计算、状态流转都写进 placeOrder，代表变上帝类 业务规则归领域服务，代表只做接入层编排
表现层绕过代表 图方便直接 new RemoteXxxService，时间一长形成两套调用路径 收敛依赖方向，架构评审禁止表现层直连业务服务

3. SQL 层优化（第一优先级）

为什么先治 SQL：数据库是共享资源，慢 SQL 不只拖慢自己，还占连接池拖垮其他接口——收益最大、最值得先做。

4. 缓存层优化（第二优先级）

4.1 多级缓存（本地 + Redis）

为什么本地 + Redis 两级：本地缓存把热点请求拦在最前面（0ms 无网络）；Redis 兜底多实例一致性。注意：本地缓存只放不常变的数据，更新时删 Redis 即可（本地缓存靠 5 分钟过期收敛）。

4.2 批量获取（消灭循环查缓存/查库）

5. 异步层优化（第三优先级）

5.1 外部调用并行化（串行 → 并行）

为什么必须带超时：并行后最慢的一个外部服务决定总耗时——不带超时，对方挂掉你的接口也挂掉。并行调用必须配独立线程池 + 超时 + 失败降级。

5.2 非核心逻辑异步化（响应不等它）

判断标准：这个操作的结果不影响本次响应 → 异步化；影响响应 → 只能并行或优化它本身。

6. 代码层优化（第四优先级，常有意外收获）

7. 完整案例：订单列表从 800ms 到 50ms

为什么按这个顺序：SQL 层是根因（收益最大）；缓存治标但立竿见影；代码层扫尾。顺序反了会”先加缓存掩盖慢 SQL”，治标不治本。

8. 优化检查清单

9. 典型案例：商品详情页 1.2s → 80ms

问题背景：App 商品详情页 P99 高达 1.2s，大促压测时直接超时熔断。用户反馈”点开商品像刷新闻”——移动端对 300ms 以上的白屏感知极明显，详情页转化率比竞品低 15%。

方案：链路拆解后三管齐下：① 三个串行下游调用并行化；② 商品主数据多级缓存（Caffeine + Redis）+ 互斥锁防击穿；③ 非核心数据（推荐/评价）异步加载、默认兜底占位：

优化项 手段 收益
串行 → 并行 CompletableFuture + 独立线程池 530ms → 200ms
主数据多级缓存 Caffeine 5min + Redis 30min 命中率 98%，查库量降 95%
防击穿 Redis SETNX 互斥 + 未获取锁者读旧值重试 促销瞬时百万 QPS 不打穿 DB
非核心异步化 推荐/评价旁路加载 + 占位符 首屏不等长尾服务
大对象瘦身 只序列化前端需要的 12 个字段 响应体 86KB → 12KB

踩坑点：

  1. 缓存过期时间统一 30 分钟无随机抖动，某整点大批商品同时失效，DB 瞬时 QPS 冲到 20 倍——过期时间加 0-5 分钟随机抖动后削平。
  2. exceptionally 降级最初返回 null，前端把”价格查询中”渲染成”¥null”，客诉 40 单——降级必须返回带语义的占位对象，不允许 null 直接出接口。
  3. 并行化时偷懒用了 CompletableFuture.supplyAsync 不传线程池（走 ForkJoinPool.commonPool），压测时与其他异步任务互相争抢，P99 反而劣化——并行调用必须显式传独立线程池并设队列上限。
  4. 优化后只压测了缓存命中场景（80ms），未压”全量缓存失效”冷启动场景——上线首日 Redis 被运维清空，DB 被回源流量打挂 8 分钟。性能验收必须覆盖冷启动与热点失效场景。
  5. 详情页瘦身时把移动端还在用的 subtitle 字段裁掉，老版本 App 大面积空白——裁字段前先查各端版本的使用情况，或保留一个过渡期。

10. 常见误用与陷阱

坑 现象/后果 解法
没压测就凭感觉优化 优化了占耗时 5% 的代码，P99 纹丝不动 先压测复现 + 链路分段，按耗时占比从大到小逐层处理
缓存过期时间一刀切 整点大批 key 同时失效，DB 瞬时被打挂（雪崩） 过期时间加随机抖动（TTL ± 10%）；核心数据加互斥锁回源
并行调用共用 commonPool 与其他异步任务争抢线程，并行变串行甚至死锁 显式指定独立线程池，设合理核心数/队列上限/拒绝策略
join()/get() 不带超时 下游挂掉时并行变”永久等待”，线程池被占满 每个 get(timeout, unit) 都显式超时 + exceptionally 降级
用平均值/最优值汇报性能 平均 100ms 掩盖了 P99 2s，用户投诉与报表打架 只认 P95/P99 分位值；按端/接口/时段维度拆开看
优化后不回归功能 性能达标但数据错了（缓存脏读/降级值当真值） 每次优化跑回归用例；降级路径必须有可观测标志（日志/埋点）
缓存值体积不控制 单个 value 500KB，Redis 网络与内存双爆，大 key 阻塞 value 控制在 10KB 内；大对象裁字段/压缩/拆分
循环里逐条查缓存或查库（N+1） 100 条数据 100 次网络往返，P99 随页大小线性恶化 改 mGet 批量 + WHERE id IN 批量回源，往返次数降为 2

设计模式 · 服务定位器

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与依赖注入对比。

1. 模式概述（意图）

服务定位器（Service Locator）提供一个中央注册表，客户端通过它查找并获取服务实例——缓存已查到的服务，避免重复创建。

2. 要解决的问题

问题 说明
服务获取逻辑分散 各处 new/初始化服务
服务创建昂贵 连接池、客户端对象重复创建
查找逻辑重复 每个使用方都要知道怎么拿服务

典型场景：JNDI 查找、EJB 容器、老式企业应用、需要”运行时按名字找服务”的框架。

3. 结构（角色）

4. 代码实现

5. 应用场景

场景 说明
JNDI 查找 Java EE 服务查找
框架容器 运行时按名取服务
多实现选择 按配置选择服务实现
客户端缓存 昂贵的客户端对象复用

6. 优缺点

优点 缺点
服务获取统一 隐藏依赖（代码看不出来用了什么服务）
缓存提升性能 测试困难（全局静态缓存）
按名查找灵活 违反依赖倒置（依赖定位器而非接口）
实现简单 定位器易成”上帝对象”

7. 与依赖注入对比（高频考点）

维度 服务定位器 依赖注入（DI）
依赖可见性 代码内查找（隐藏） 构造器/注解声明（显式）
测试 难（全局状态） 易（注入 mock）
反转 客户端主动找（弱反转） 容器注入（强反转）
现代实践 老式方案 现代首选（Spring 容器）

结论：新项目一律用 DI（Spring IoC 容器），服务定位器只出现在遗留系统。

8. 常见误用与陷阱

坑 现象 解法
隐藏依赖导致不可测 类内部 ServiceLocator.get("x")，单测不读源码不知道要 mock 什么 依赖走构造器注入、测试传 mock；定位器只留在组合根
与依赖注入取舍失当 新 Spring 项目仍手写静态定位器，放弃容器能力 能用容器注入就不用定位器；仅「运行时按名动态选择」保留注册表
定位器变全局可变注册表 任意代码都能 register/put，服务在运行时被悄悄替换 注册表启动期一次性填充、只暴露查找；禁止运行时 mutate
缓存有状态服务 静态缓存的实例带成员变量，并发请求共享后串数据 缓存只放无状态单例；有状态对象交容器按作用域管理
查找失败返回 null 未知服务名返回 null，调用方漏判再次 NPE 未知名字快速失败抛异常，或显式返回 Optional

设计模式 · 拦截过滤器

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与责任链对比。

1. 模式概述（意图）

拦截过滤器（Intercepting Filter）在请求到达目标处理前插入一组可插拔的过滤器，按链式顺序执行公共处理——每个过滤器只做一件事，可增可减。

2. 要解决的问题

问题 说明
公共处理杂乱 鉴权、日志、压缩、编码写在一起
处理不可插拔 加一个处理要改目标代码
顺序难控制 过滤器顺序影响行为（先鉴权再日志？）

典型场景：Servlet Filter（登录、编码、压缩、XSS）、Spring Security 的 FilterChain、网关过滤器、中间件洋葱模型。

3. 结构（角色）

4. 代码实现（登录请求过滤链）

5. 应用场景

场景 说明
Servlet Filter 编码、登录、压缩、XSS 过滤
Spring Security 认证/授权过滤器链
API 网关 限流、鉴权、灰度过滤器
Web 框架中间件 Express/Koa/ASP.NET 管道
日志/审计 统一日志过滤器

6. 优缺点

优点 缺点
过滤器可插拔（增删不动业务） 过滤链长时性能开销
职责单一（每过滤器一件事） 顺序配置错误影响全局
公共逻辑集中且复用 过滤器间状态传递要约定
顺序可控 调试多层过滤较麻烦

7. 与责任链对比

维度 拦截过滤器 责任链
传递 通常全部执行（洋葱） 可中途停止（能处理则处理）
用途 横切公共处理 职责分担/审批
结构 统一 FilterChain 管理 处理者持有 next

8. 常见误用与陷阱

坑 现象 解法
filter 顺序依赖隐式 Auth 依赖前一个过滤器塞的请求属性，注册顺序一变就 401 顺序显式配置（@Order / FilterRegistrationBean / 链组装处），依赖写注释
过滤器里改请求体 读取 getReader() 后 body 被消费，下游拿到空请求体 用 ContentCachingRequestWrapper 等包装类缓存并重放
异常被吞 catch 后既不 chain.doFilter 也不写响应，请求无声挂起 终止链必须显式返回 4xx/5xx；异常交给统一错误处理器
正常分支漏放行 拒绝路径写了 return，通过路径忘记调 chain.doFilter 每个过滤器结构对称：放行显式 chain，拒绝显式响应
过滤器持有可变状态 用成员变量存请求数据，并发请求互相串值 过滤器无状态单例，请求级数据存 request 属性

设计模式 · 前端控制器

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与网关对比。

1. 模式概述（意图）

前端控制器（Front Controller）用唯一入口处理所有请求，在入口处统一完成公共处理（鉴权、日志、路由、国际化），再分派到具体处理器。

2. 要解决的问题

问题 说明
公共逻辑重复 每个 Servlet/Controller 都要写鉴权、日志
处理逻辑分散 路由、异常处理散落各处
安全风险 未鉴权的请求直达业务

典型场景：Spring MVC 的 DispatcherServlet、所有 Web 框架的”中央分发器”、API 网关（微服务版的 Front Controller）。

3. 结构（角色）

4. 代码实现（统一入口 + 鉴权 + 路由）

5. 应用场景

场景 说明
Web 框架 Spring MVC DispatcherServlet、Struts
API 网关 微服务统一入口（鉴权/限流/路由）
门户系统 多模块统一入口
应用服务器 Servlet 容器（Filter + Dispatcher）

6. 优缺点

优点 缺点
公共逻辑集中（一处鉴权/日志） 入口成为瓶颈/单点
路由集中管理 简单应用是过度设计
统一异常/响应 入口逻辑膨胀风险
业务处理器轻量 需要与拦截器配合避免重复

7. 与相关模式对比

模式 区别
拦截过滤器 过滤器在请求到达控制器前链式处理；前端控制器是分发入口
外观 外观封装子系统调用；前端控制器是 Web 请求分发
网关 微服务版前端控制器（跨服务路由）

实践：Spring MVC 里 Front Controller 已内建（DispatcherServlet）；自己开发时把”公共逻辑”放拦截器（Interceptor）而非控制器内。

8. 常见误用与陷阱

坑 现象 解法
控制器变上帝类 鉴权、参数解析、业务处理、渲染全堆进 dispatch 一个方法 只保留「统一公共处理 + 分发」；业务下沉 Handler，横切下沉过滤器/拦截器
与 MVC 中 Controller 混淆 在前端控制器里写订单/用户业务，越写越大 前端控制器全局唯一（入口/路由）；MVC Controller 是按 URL 映射的一组处理器
分发硬编码 if-else 巨链 几十上百个 action 分支挤在 resolve 里 路由表 Map 或注解扫描注册（Spring 的 @RequestMapping）
与过滤器职责重复 入口鉴权一遍，Filter/Interceptor 又鉴权一遍 鉴权、编码放过滤器链；控制器只做路由与统一异常兜底
单点被异常拖垮 某个处理器抛出未捕获异常，整个入口挂掉 入口无状态、可多实例部署；异常在边界统一捕获转错误响应

设计模式 · 数据传输对象（DTO）

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与 VO/PO 对比。

1. 模式概述（意图）

DTO（Data Transfer Object）是跨层传输数据的载体对象——把多个字段打包成一次传输，避免逐字段多次调用、也避免把内部实体直接暴露给外部。

2. 要解决的问题

问题 说明
网络往返过多 一次要多个数据 → 逐次调用
内部结构暴露 实体含敏感字段/内部结构，直接返回有风险
层间耦合 Controller 直接用 Entity，改表结构影响 API
传输粒度不匹配 前端要 A+B+C 拼装，接口要定制

典型场景：REST API 请求/响应对象、远程调用（RPC 参数）、分页结果封装、批量数据聚合。

4. 代码实现（用户 API）

5. 应用场景

场景 说明
REST API 请求/响应对象
RPC/微服务 服务间传输参数
分页聚合 PageResult 封装
多源数据组装 组装多个来源为一个 DTO
大对象拆分 一次传输所需字段

6. 优缺点

优点 缺点
隔离内部模型（安全） DTO 与实体字段重复（样板代码）
减少网络往返 转换代码要维护
按需裁剪（不多传/不少传） 过细 DTO 导致类爆炸
层间解耦 需要字段映射约定

7. 与相关概念对比

概念 说明
DTO 跨层/跨网络传输（入参/出参）
VO（View Object） 专为视图层定制的 DTO
PO/Entity 持久化模型（对应表）
BO 业务模型（领域）
DO 领域对象

分层铁律：Entity/PO 只在内层；跨网络/跨层一律 DTO/VO——避免”接口直接暴露表结构”。

8. 常见误用与陷阱

坑 现象 解法
DTO 与实体混用 请求体直接绑定 Entity（@RequestBody UserEntity），改张表就破坏 API 入参/出参用独立 record，边界处显式转换
敏感字段未脱敏就暴露 passwordHash、salt、内部状态被 Jackson 原样序列化出去 响应 DTO 走字段白名单；敏感字段根本不放进出参 DTO
过度映射层级 DO→BO→DTO→VO 层层 BeanUtils.copy，样板代码淹没业务 每层都要有明确收益；简单链路允许 DO→DTO 直转
万能 DTO 走所有接口 一个类几十个字段，靠注释区分哪个接口填哪些 按场景定制（CreateUserRequest / UserListResponse）
DTO 里塞业务行为 在传输对象中下单、算价、调 Service DTO 保持贫血数据载体，行为归领域/应用服务

设计模式 · 数据访问对象（DAO）

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与 Repository 对比。

1. 模式概述（意图）

DAO（Data Access Object）把数据访问逻辑从业务逻辑中分离：业务层只面向 DAO 接口，不关心数据来自数据库、Redis 还是外部 API。

2. 要解决的问题

问题 说明
业务代码混 SQL Service 里写 SQL，改库伤筋动骨
数据源可切换 换数据库/缓存要改业务
访问逻辑重复 连接管理、异常处理、事务散落
测试困难 业务测试要连真实数据库

典型场景：所有 ORM 框架（MyBatis Mapper、JPA Repository）本质是 DAO 思想的实现；多数据源切换；缓存与 DB 的双读双写封装。

5. 应用场景

场景 说明
所有 ORM 项目 MyBatis Mapper / JPA Repository
多数据源 同接口多实现（MySQL/PG/缓存）
遗留系统 把老存储封装成统一 DAO
单元测试 Mock DAO 即可测业务

6. 优缺点

优点 缺点
业务与数据访问解耦 简单 CRUD 也建接口+实现（略重）
数据源可替换 接口方法粒度设计要慎重
便于测试（mock） 过度抽象可能”为接口而接口”
访问逻辑集中管理 复杂查询容易让 DAO 膨胀

7. 与 Repository 对比（DDD 语境高频）

维度 DAO Repository
视角 数据访问（面向表） 领域聚合（面向业务）
返回 Entity/数据传输对象 领域聚合对象
接口 CRUD 细粒度 业务语义方法（save(Order)）
场景 简单分层 DDD 战术设计

实践：CRUD 系统用 DAO/Mapper 即可；DDD 系统用 Repository（内部可用 DAO 实现）。

8. 常见误用与陷阱

坑 现象 解法
DAO 泄露连接 异常路径上 Connection 没关闭，连接池很快被耗尽 try-with-resources 或交给 MyBatis-Spring 托管，禁止把连接带出 DAO
N+1 查询 列表 N 条记录，循环里逐条调 DAO，触发 N+1 次 SQL 批量 in 查询 / join / fetch join，一次取回再组装
接口泄漏存储细节 DAO 方法签名出现 ResultSet、RowMapper、findByHql 接口里只出现领域类型，存储细节全部关在实现类
SQL 拼接注入 "where name='" + name + "'" 被 ' or '1'='1 打穿 参数化查询 / #{} 占位符 / PreparedStatement
DAO 里写业务逻辑 在 DAO 中算折扣、改状态机、发消息 DAO 只做存取，业务判断归 Service
