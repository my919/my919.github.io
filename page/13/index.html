设计模式 · 观察者模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与发布订阅对比。代码带详细注释。

1. 模式概述（意图）

观察者模式（Observer）定义对象间一对多依赖：当被观察者（Subject）状态变化时，自动通知所有观察者——发布-订阅思想的基础。

2. 要解决的问题

问题 说明
状态变化要通知多方 订单状态变了要通知库存/物流/用户
通知方与被通知方耦合 硬编码调用导致改一个动一片
观察者动态增删 运行时注册/注销订阅

典型场景：事件监听（GUI 按钮点击）、Spring 事件、消息队列（分布式观察者）、实时推送、MVC（Model 变化刷新 View）。

3. 结构（角色）

4. 代码实现（订单事件通知）

5. 应用场景

场景 说明
Spring 事件 @EventListener（发布-订阅内建）
GUI 事件 按钮点击、键盘事件
消息队列 Kafka/RabbitMQ（分布式观察者）
实时推送 WebSocket 订阅推送
MVC Model 变化刷新 View

6. 优缺点

优点 缺点
主题与观察者解耦（开闭） 通知顺序无保证
动态注册/注销 观察者过多时通知开销
一对多广播 观察者异常会冒泡（需隔离）
支持分布式（MQ 版） 循环依赖可能无限通知

工程注意：同步通知中一个观察者抛异常会中断后续——生产用异步 + 异常隔离（Spring 配 @Async 或事件表）。

7. 与发布-订阅对比

维度 观察者 发布-订阅
通信 主题直接调观察者 经消息队列中间件
解耦 主题认识观察者 完全解耦（互不认识）
场景 单机 JVM 内 分布式系统
实例 Spring 事件 Kafka/RabbitMQ

8. 常见误用与陷阱

坑 现象 解法
观察者异常中断链 一个观察者抛异常，后续观察者收不到通知 每个观察者的调用包 try-catch，或改用异步事件
内存泄漏 观察者注册后忘记 remove，Subject 一直持有引用 用弱引用（WeakReference）或注册时返回 Subscription 句柄
循环通知死锁 A 观察 B，B 观察 A，状态变化导致无限循环 引入版本号/时间戳防重入，或改单向数据流
通知顺序不可控 依赖 List 顺序，观察者优先级无法调整 用 PriorityQueue 或注解标顺序（如 Spring @Order）

技术栈速查

类别 选型 用途
数据库 MySQL 8.4 LTS 主存储
逻辑备份 mysqldump（自带） 全量、跨版本迁移
物理备份 Percona XtraBackup 8.4 热备、增量、恢复快

1. 概念说明：先想清楚要什么

备份的核心是两个指标：

指标 含义 目标
RPO（恢复点目标） 最多丢多少数据 越小越好（如丢 ≤5 分钟）
RTO（恢复时间目标） 多久恢复可用 越小越好（如 1 小时内）

备份类型：

类型 说明 特点
全量备份 备份全部数据 基础，恢复最简单
增量备份 备份上次备份后的变化 省空间、恢复要叠加
逻辑备份 导出 SQL（mysqldump） 可读、跨版本、恢复慢
物理备份 复制数据文件（XtraBackup） 快、恢复快、依赖同版本

2. mysqldump 逻辑备份（入门必备）

逻辑备份的适用边界：数据量 < 50GB 用 mysqldump 够；更大必须上 XtraBackup（mysqldump 恢复太慢）。

备忘录模式详解（Memento）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 3.3k 阅读时长 ≈ 3 分钟

设计模式 · 备忘录模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

备忘录模式（Memento）在不破坏封装的前提下，捕获并保存对象的内部状态，以便将来恢复到该状态——如同游戏的存档。

2. 要解决的问题

问题 说明
需要撤销/回滚 恢复到某个历史状态
状态封装性 外部直接读字段会破坏封装
状态保存多份 历史快照要管理（存档列表）

典型场景：编辑器撤销（配合命令模式）、游戏存档、事务回滚（数据库 undo 日志思想）、浏览器后退。

3. 结构（角色）

关键：备忘录对外不透明——只有 Originator 能读写其内部，Caretaker 只负责保存与归还。

4. 代码实现（游戏角色存档）

5. 应用场景

场景 说明
编辑器撤销 文档快照（常配合命令模式）
游戏存档 角色状态恢复
数据库事务 undo 日志/回滚段（思想）
表单重置 恢复初始数据
配置回滚 配置快照恢复

6. 优缺点

优点 缺点
保存状态且不破坏封装 状态大时快照耗内存
恢复逻辑简单 频繁保存性能开销
状态历史可管理 需注意快照的深拷贝（引用类型）
与命令模式配合强大 备忘录内容变化后难迁移

注意：备忘录保存的是对象状态——内部引用类型要深拷贝，否则存的是引用，状态早就变了。

7. 与其他模式对比

模式 区别
命令模式 命令记录”操作”；备忘录记录”状态快照”（常配合）
原型模式 原型复制当前对象；备忘录保存并恢复历史
观察者 观察者关注变化；备忘录保存过去

8. 常见误用与陷阱

坑 现象 解法
浅拷贝导致状态污染 Memento 存的是 List/Map 引用，改原对象后快照失效 Memento 内对引用类型做深拷贝，或存不可变副本
快照内存爆炸 大对象全量快照频繁保存，OOM 只存变更字段（增量快照），或限制快照数量
恢复时对象状态不一致 Originator 有新字段但 restore 没恢复 用序列化/反序列化保证全字段一致，或加版本号校验
备忘录泄露内部结构 Memento 暴露 getter，外部篡改历史状态 Memento 设为内部类+私有构造，只给 Originator 访问

中介者模式详解（Mediator）

设计模式 · 中介者模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与外观对比。代码带详细注释。

1. 模式概述（意图）

中介者模式（Mediator）用一个中介对象封装一组对象的交互——对象之间不再直接引用，全部通过中介通信，把”多对多”改成”多对一”。

2. 要解决的问题

问题 说明
对象间耦合网状 每个对象都要知道所有其他对象（多对多）
交互逻辑散落 谁通知谁、怎么协调散在各对象里
难以复用与测试 对象强耦合，无法单独测试

错误结构（网状）：

中介者结构（星形）：A/B/C/D → Mediator（n 条依赖）。

典型场景：聊天室（用户之间不直接通信，经服务器）、航班调度塔台、MVC 里的 Controller（协调 Model 与 View）、消息队列。

3. 结构（角色）

4. 代码实现（聊天室）

新增用户：只需要注册到聊天室——原有用户代码零修改。

5. 应用场景

场景 说明
聊天/协作系统 用户经服务器通信
表单组件协调 多个控件联动（互不引用）
航班/交通调度 塔台协调飞机
消息队列 生产者消费者经 MQ 解耦
MVC Controller 协调 Model 与 View

6. 优缺点

优点 缺点
网状耦合 → 星形（n² → n） 中介者可能膨胀成”上帝对象”
交互逻辑集中，易维护 中介者单点故障（挂了全断）
同事类独立可复用 交互逻辑复杂时中介者难理解
符合开闭（加同事不改老代码） 比直接调用多一层

7. 与外观对比（高频考点）

维度 中介者 外观
方向 同事互相交互（双向） 子系统被外观单向封装
协议 同级的同事间协调 上下层简化入口
关注 交互逻辑 接口简化

8. 常见误用与陷阱

坑 现象 解法
中介者膨胀成上帝类 Mediator 内几百行 if-else，改一处动全身 按职责拆为多个中介者（Room/Channel/Topic）
同事类反向穿透 Colleague 直接 get 出其他同事引用调用 强制 Colleague 只持 Mediator 引用，不暴露同事列表
消息广播风暴 中介者广播所有消息，无关同事被迫处理 引入消息标签/主题过滤，只发给关心的订阅者
异步回调地狱 Mediator 内链式调用导致死锁或内存泄漏 用事件队列异步解耦，Mediator 只投递不回调

设计模式 · 迭代器模式

GoF 行为型模式。意图 · 结构 · 代码实现 · 应用场景 · 优缺点。代码带详细注释。

1. 模式概述（意图）

迭代器模式（Iterator）提供一种方法顺序访问聚合对象（集合）内的元素，而不暴露其内部表示——遍历逻辑与集合结构解耦。

2. 要解决的问题

问题 说明
遍历与集合耦合 每种集合写一套遍历代码
内部结构暴露 客户端知道底层是数组还是链表
遍历方式单一 正序/逆序/过滤需要不同遍历器

典型场景：所有 Java 集合的 iterator()、Java 8 之后基本被 for-each/Stream 取代——迭代器已是语言级内建，本模式主要理解思想与 Iterable 接口。

3. 结构（角色）

4. 代码实现（自定义迭代器）

遍历期间修改：迭代器遍历时修改集合会抛 ConcurrentModificationException（Java 用 modCount 快照检测）；需要安全的移除用 iterator.remove()。

5. 应用场景

场景 说明
Java 集合 List/Set/Map 的 iterator()
for-each 语法 编译器展开为迭代器
数据库游标 结果集逐行遍历
自定义数据结构 树/图的自定义遍历
Stream Java 8+ 更声明式的遍历

6. 优缺点

优点 缺点
遍历与集合解耦 简单集合用迭代器是多余抽象
隐藏内部结构（信息隐藏） 迭代器状态管理要小心
支持多种遍历方式 函数式语言中常被 Stream/for-each 取代
统一接口（换集合不改客户端） 并发修改检测增加复杂度

4.1 静态代理（权限控制）

4.2 JDK 动态代理（AOP 基础）

场景 说明

JVM 实战：CPU 飙高排查完整步骤

发表于 2026-09-14 更新于 2026-10-25 分类于 JVM 本文字数： 8k 阅读时长 ≈ 7 分钟

JVM · CPU 飙高排查

从 0 到定位根因：确认是不是 JVM 的锅 · top/jstack 定位线程 · 多次抓取对比 · async-profiler 火焰图 · 七类常见根因的判定与修复。代码带详细注释。

技术栈速查

类别 选型 用途
JDK 21 LTS 运行环境
定位 top / top -Hp 进程与线程级 CPU
线程栈 jstack / jcmd Thread.print 看线程在干什么
火焰图 async-profiler 3.x 精准定位热方法
辅助 GC 日志 / jstat 区分”真忙”与”假忙”

1. 概念说明：CPU 高的本质

CPU 飙高的两种类型，排查方向完全不同：

类型 特征 根因方向
真忙（业务/代码在烧 CPU） GC 正常，线程栈在业务代码里 死循环、正则回溯、序列化、大计算
假忙（GC 在烧 CPU） 堆快满、Full GC 频繁 内存泄漏、堆太小、对象分配过快

为什么第一步要分真假：假忙时去抓线程栈，看到的全是 GC 线程，业务线程在等待——方向错了浪费一小时。先看 GC 日志/jstat，再看线程栈。

排查铁律：现场优先——先抓线程栈和火焰图，再考虑重启；重启后热点线程消失，只能靠猜。

2. 步骤 0：先确认是不是 JVM 在烧 CPU

为什么用 jstat 先看：10 秒钟判断出”真忙/假忙”，避免在错误方向上抓半天线程栈。

3. 步骤 1：定位 CPU 高的线程（top + jstack）

定位示例（grep 输出长这样）：

为什么转十六进制：top -H 显示十进制线程号，jstack 用 nid=0x十六进制 标识线程——不转换就搜不到。

4. 步骤 2：多次抓取对比（区分死循环与正常切换）

判定规则：

两次栈对比 结论
同一线程、同一方法、栈几乎不变 死循环/自旋（一直卡在同一行）
同一线程、方法在变、但总是那几个 高频业务处理（真在干活，看是不是该这么重）
栈在等待（WAITING/BLOCKED） 不是它在烧 CPU，回去找别的线程

为什么必须抓两次：单次抓栈有偶然性——线程恰好在某个方法暂停。两次都停在同一个方法，才能确认它持续在烧 CPU。

5. 步骤 3：火焰图（终极手段，精准到方法）

线程栈只能看到”某个时刻”，火焰图能看到一段时间内所有方法消耗的 CPU 占比。

火焰图怎么读：

看什么 说明
最宽的平顶 烧 CPU 最多的方法，优先查它
一串窄条叠很高 深层调用链，可能有循环嵌套
大块 GC 相关 假忙，转内存排查
锁相关（park/contend） 锁竞争，看等待线程

为什么火焰图是终极手段：30 秒采集成千上万次栈，统计出每个方法真实的 CPU 占比——不用猜热点，图上最宽的平顶就是答案。

6.1 死循环 / 空转（最常见）

判定：火焰图是又宽又平的 loopCheck 平顶；栈顶在 while 行。

6.2 正则回溯爆炸（文本处理高频）

判定：火焰图 java.util.regex 大平顶；GC 不高（纯 CPU）。

6.3 GC 频繁（假忙）

判定：jstat -gcutil 的 FGC/FGCT 快速上涨；火焰图 G1/GC 相关大块。

6.4 序列化 / 大数据对象

判定：火焰图序列化方法平顶；QPS 不高但 CPU 高。

6.5 锁竞争自旋

判定：火焰图 AQS/park 相关；jstack 大量 BLOCKED 线程。

6.6 无限递归 / 方法调用过深

6.7 日志刷屏（隐蔽的 CPU 杀手）

为什么日志也是 CPU 杀手：字符串拼接 + IO 写入 + 线程同步，每个请求多打几行，QPS 高时能吃掉整核 CPU，且线上还不容易察觉。
