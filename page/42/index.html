第一章：C 语言基础

概念基础

  1. 编译型语言：源码经预处理 → 编译 → 汇编 → 链接生成机器码直接执行，不依赖虚拟机，执行路径清晰、开销可预期。
  2. 贴近机器模型：指针、内存布局、调用约定都可由程序员掌控，至今仍是操作系统内核、嵌入式、高性能库的事实标准之一。
  3. 小核心、大标准库：语言关键字很少，能力来自 ISO C 标准库（stdio.h、stdlib.h、string.h 等）与平台 API。
  4. 可移植性：遵循 ISO C（如 C99、C11）的代码在多数平台用对应工具链重新编译即可；平台差异隔离在少量实现定义处。
  5. C ABI 是互操作边界：几乎所有语言都提供与 C 的互操作（FFI），系统级编程绕不开 C。

一、语言特点（为何仍值得学）

  • 贴近机器模型：整型与指针宽度、内存布局、调用约定都可由实现定义，便于写驱动、解释器底层、与汇编或硬件协同。
  • 表达力强、语法紧凑：少量关键字即可完成算法与数据结构；没有面向对象语法糖，但可用结构体 + 函数指针组织模块。
  • 可移植性：遵循 ISO C（如 C99、C11）的代码在多数平台用对应工具链即可重新编译；与平台相关的部分通常隔离在少量文件中。
  • 生态成熟：几乎所有系统提供 C 调用约定，其他语言常以 C ABI 为边界导出/导入库。

二、最小程序与翻译单元

每个可执行程序必须有一个 main 入口（宿主环境下常见两种签名之一）：

  • #include：预处理阶段把头文件文本插入当前翻译单元；<stdio.h> 等尖括号形式通常表示系统/实现提供的头。
  • return 0：向操作系统报告成功退出；省略时 C99 起对 main 有特殊规则（等价于返回 0），其他函数仍必须显式返回值（或 void）。

三、基本类型与字面量

3.1 整数与字符

  • char：至少 8 位，可表示字符（常与 unsigned char 用于字节）；signed char / unsigned char 与 char 是否带符号由实现定义。
  • short / int / long / long long：各有 signed / unsigned 变体；宽度随平台变化，可移植代码应使用 <stdint.h> 中的 int32_t、uint64_t 等定宽别名（若平台提供）。
  • 整数字面量：42（int）、42U（unsigned）、42L（long）、0x2A（十六进制）、052（八进制，易踩坑，少用）。

3.2 浮点

  • float / double / long double：遵循 IEEE 754 的实现上，double 最常用；不要用 == 比较浮点相等，应比较误差或使用整数域计算。

3.3 void 与派生类型

  • void：无值类型，用于「无返回值」或「通用指针」void *（可指向任意对象，不能直接解引用，需先转换）。

四、变量、作用域与存储期

  • 自动变量：块内 int x = 1;，进入块分配（概念上在栈帧），离开块结束生命期；未初始化则值不确定。
  • static（局部）：仍只在块内可见，但只初始化一次，生命期贯穿程序。
  • static（全局/函数）：内部链接，仅在当前翻译单元可见，避免符号冲突。
  • extern：声明在其他翻译单元定义的全局对象或函数。

五、运算符与控制流

5.1 常用运算符

  • 算术：+ - * / %；整数相除向零截断。
  • 关系与逻辑：< <= > >= == !=、&& || !；短路求值：a && b 中 a 为假则不计算 b。
  • 位运算：& | ^ ~ << >>；仅对无符号或明确语义时使用移位更安全。
  • 三元：cond ? a : b。
  • 复合赋值：+=、-= 等。

5.2 分支与循环

  • switch 的 case 通常需要 break，否则落入下一分支（fall-through），有时故意利用，多数情况要避免。

六、数组与指针

6.1 数组

  • 数组名在大多数表达式中会退化为指向首元素的指针，不携带长度信息；跨函数传递数组时常传指针 + 长度或使用哨兵（如字符串的 '\0'）。

6.2 指针

  • NULL：空指针常量；解引用空指针是未定义行为。
  • 指针算术：p + 1 按所指类型大小移动；仅对同一数组对象内或尾后一位置才有标准保证。

6.3 字符串

  • C 字符串是以 '\0' 结尾的 char 序列；字面量 "hi" 类型为 char 数组，在表达式中退化为 char *（C++ 中为 const char *）。
  • 常用 <string.h>：strlen、strcmp、strcpy（注意缓冲区溢出，优先 strncpy/snprintf 或自行边界检查）。

七、函数

  • 按值传递：形参是实参的副本；要通过函数修改调用方变量，传指针。
  • 原型：C99 起调用前必须可见原型，否则旧式隐式声明规则已移除，利于编译器检查实参个数与类型。
  • static 函数：仅本翻译单元可见。

八、结构体、联合体与枚举

8.1 结构体

  • 内存布局：可能有填充字节以满足对齐；不要假设 sizeof 等于各成员之和。
  • typedef 可为 struct 起别名，减少每次写 struct 关键字。

8.2 联合体与枚举

  • union：成员共享同一块存储，同一时刻通常只应语义上使用其中一个成员；写入与读取不同类型成员涉及有效类型规则，滥用为未定义行为。
  • enum：提供命名整型常量；底层仍为整数类型，不提供新类型安全边界。

九、动态内存

  • malloc / calloc / realloc / free：成对使用；双重 free、使用已 free 的指针均为未定义行为。
  • 谁分配谁释放：在模块边界约定清晰，避免交叉所有权。

十、预处理与宏

  • #include / #define / #if 在编译前由预处理器处理；宏不做类型检查，复杂逻辑优先 static inline 函数 或枚举常量。

十一、与「安全可移植」相关的习惯

  • 显式 {} 包住 if/for 体，避免宏或维护时出错。
  • 比较时把常量放左侧：if (NULL == p) 可防止误写 =。
  • 整数运算注意溢出（有符号溢出为未定义行为）；必要时用更大宽度或检查范围。
  • 使用 -Wall -Wextra -Werror（在可接受时）与静态分析工具，尽早暴露问题。

十一·补充、标准版本与编译选项

  • C17（ISO/IEC 9899:2018）：C11 的缺陷修订版，是当前生产代码的事实基准；gcc -std=c17 / MSVC /std:c17。
  • C23（ISO/IEC 9899:2024）：新增 nullptr、true/false 关键字、[[nodiscard]]、constexpr、typeof、#embed 等；GCC 13/14 用 -std=c2x/-std=c23 可尝鲜，注意兼容面。
  • 推荐编译组合：gcc -std=c17 -Wall -Wextra -Wpedantic -g（开发）/ -O2 -DNDEBUG（发布）。

十二、未定义行为（UB）速查清单

UB 意味着标准不做任何保证——编译器可假设它永不发生并据此激进优化，后果包括错误结果、崩溃乃至安全漏洞。入门阶段必须记住的高频 UB：

UB 示例 后果
有符号整数溢出 INT_MAX + 1 任意结果（无符号溢出则定义为回绕）
解引用空/悬空指针 *p（p 为 NULL 或已 free） 段错误或被优化掉
数组越界 a[10] 对 int a[10] 读写未知内存
解引用未初始化变量 int x; return x; 不确定值
移位越界或负数 1 << 33、-1 << 1 未定义
修改字符串字面量 char *s="hi"; s[0]='H'; 字面量在只读段
同一序列点内多次修改 i = i++ C11 起由 sequenced-before 规则界定，仍为 UB
违反严格别名 *(float*)&i 优化期假设失效（用 memcpy 或 union 合规做类型双关）
printf 格式符不匹配 printf("%d", size_t值) 读错栈上数据

工程对策：-Wall -Wextra -Wpedantic 拦编译期可见者；-fsanitize=undefined（UBSan）运行时报告溢出/移位等；-fsanitize=address（ASan）查内存类 UB——第二章详述。

十三、整型提升与寻常算术转换

C 的隐式类型转换是 bug 高发区：

  • 整型提升：比 int 小的类型（char、short）在表达式中先提升为 int。char a=200, b=200; a*b 中间结果是 int，可正确得 40000。
  • 寻常算术转换：混合 int 与 unsigned int 时，int 转 unsigned——经典坑：if (-1 < 1U) 为假（-1 回绕成巨大无符号数）。
  • size_t 是无符号：for (size_t i = n-1; i >= 0; --i) 是死循环（i 减到 0 再减回绕为 SIZE_MAX）。倒序遍历用 for (size_t i = n; i-- > 0;) 或改用有符号索引。

十四、内存布局初识：栈/堆/数据段

程序运行时内存大致分五段（第二章展开）：

  • 代码段（Text）：机器指令与只读常量，字符串字面量常置于此，写入即 UB。
  • 数据段/BSS：已初始化 / 未初始化的全局与 static 变量，生命期贯穿程序。
  • 堆（Heap）：malloc 家族管理，手动释放。
  • 栈（Stack）：函数帧与局部变量，自动回收，容量有限（典型 8MB），返回局部变量地址是经典 UB。

第二章：IO 多路复用与 Netty 线程模型

概念基础

  1. I/O 多路复用在干什么：一条线程调用 Selector.select() 阻塞等待，直到一批 Channel 上有就绪的 I/O 事件（可读、可写等），再依次分发处理——一条线程可以注册并监视成千上万个连接，而不是为每个连接各开一条阻塞线程。
  2. 「很多连接」≠「每条连接占满一条线程」：大量长连接（推送、网关、IM 在线）中许多连接长时间无读写，适合交给一个 Selector 统一等就绪；高 QPS 短连接的瓶颈常在 CPU、GC、协议栈，与「单 Selector 挂很多空闲连接」不是同一维度的问题。
  3. Netty 扮演的角色：在 Java NIO / Epoll（Linux） 之上封装了 Reactor 风格的 EventLoop、Pipeline、内存与缓冲策略，让你用少量 EventLoop 线程管理大量 Channel，并把编解码、业务入 ChannelPipeline。
  4. 线程模型与前提：Boss 负责 accept 新连接并注册给 Worker；每个 Worker EventLoop 是「一条线程 + 一个 Selector」。业务若阻塞（重度 CPU、同步 JDBC、大 Thread.sleep）会占满该 EventLoop 上的所有 Channel——阻塞操作必须丢到业务线程池，这是多路复用发挥作用的前提。
  5. 上量边界：连接规模还受进程最大打开文件数、内核参数、堆外内存约束，多路复用属于应用层模型，不能替代容量规划。

Netty 常见线程模型（Boss / Worker）

1. 典型服务端写法（概念）

  • bossGroup：线程数常为 1（也可更多），负责接受新连接并把 SocketChannel 注册进 workerGroup 中某个 EventLoop 的 Selector。

常见面试题速览

  1. 为什么 Netty 用主从 Reactor——accept 与已连接 IO 解耦：接入抖动不影响存量连接，Worker 池可按压测独立扩缩。
  2. EventLoop 上为什么不能阻塞——一条 EventLoop 串行服务其名下所有 Channel，阻塞 100ms 等于这批连接集体卡顿 100ms。
  3. select/poll/epoll 区别——见上文对比表：核心是「遍历全量 vs 回调就绪」与 fd 拷贝成本。
  4. 一个 Channel 能换 EventLoop 吗——不能：注册即绑定终身，这是单线程串行无锁的前提。
  5. Boss 线程数为什么是 1——单监听端口只需一条 accept 线程；多端口/多 boss 仅在特殊架构下有意义。
  6. NIO 与 Epoll 传输怎么选——跨平台用 NIO；纯 Linux 生产用 Epoll，少一次封装、支持 TCP_CORK 等原生选项（业务代码完全不变，见第六章）。
  7. ioRatio 是什么——EventLoop 主循环里 I/O 处理与任务队列的时间配额比（默认 50），失衡会互相饿死（见上文源码级主循环）。

二、EventLoop 与 EventLoopGroup：执行器

EventLoop = 一条线程 + 一个任务队列（NIO 下还绑一个 Selector）。核心契约：

  1. 一个 Channel 终身只属于一个 EventLoop（注册时分配，不再变更）。
  2. 该 Channel 的所有事件（读、写、触发 Handler）都在这个 EventLoop 的线程上执行。
  3. 因此同一 Channel 上的 Handler 无需加锁——单线程串行。

1. 线程数与分配

新 Channel 注册时，EventLoopGroup 按轮询挑一个 EventLoop 绑定给它，使连接均匀分散。

2. 在 EventLoop 上调度任务

若从非 EventLoop 线程访问 Channel，Netty 会把操作封装成 task投递到该 EventLoop 队列，保证线程安全。这也是 ch.writeAndFlush() 可在任意线程调用的原因。

3. 阻塞操作是头号陷阱

EventLoop 上挂了大量 Channel，若某 Handler 内执行 Thread.sleep、同步 JDBC、重 CPU 计算，会拖死该 EventLoop 上所有连接。正确做法见 第六章：Netty 高级特性与性能调优——把阻塞操作丢进业务线程池。

实战推论：

  • 在业务 Handler（链尾）里 ctx.writeAndFlush 与 ch.writeAndFlush 效果一样——都是从尾向头过完编码器。但如果你在链中间的 Handler里只想让「前面的编码器」处理，用 ctx.writeAndFlush 可跳过自己避免递归。
  • 异常传播：Handler 里抛出的异常沿入站方向向下找 exceptionCaught，最终到链尾的 TailContext——默认只打一行警告日志。生产代码必须自己实现 exceptionCaught（记日志 + 关连接），否则异常被静默吞掉。
  • 事件不续传即断：channelRead 里不写 ctx.fireChannelRead(msg)，事件就停在当前 Handler——这既是有意的「拦截」，也是最常见的「消息莫名消失」原因。

2.1 容量、扩容与读写指针的三段区

一个 ByteBuf 的内部被读写指针分成三段：[0, readerIndex) 已读废弃区、[readerIndex, writerIndex) 可读区、[writerIndex, capacity) 可写区。

要点：clear() 不是清零内存，只是把指针复位；discardReadBytes() 有内存搬移成本，高频调用不如「读完即释放换新 buf」。超 maxCapacity 写会抛 IndexOutOfBoundsException——协议层限制报文大小（maxFrameLength）就是第一道防线。

3. 堆内 vs 堆外（direct）

  • 堆外：socket I/O 时免去一次堆↔内核态拷贝，高吞吐场景首选；但分配/释放代价略高，需手动 release()。
  • 堆内：分配快、GC 可达，适合小数据或测试。
  • Netty 默认用 PooledByteBufAllocator.DEFAULT（池化堆外），可在启动时改：b.option(ChannelOption.ALLOCATOR, UnpooledByteBufAllocator.DEFAULT)。

第四章：编解码与粘包拆包

概念基础

  1. TCP 是字节流，不是消息流：发送方连续 write 两条消息，接收方可能一次读到两条粘在一起（粘包），也可能读到半条（拆包）。这是 TCP 本性，不是 bug。
  2. Netty 的解决思路：在 Pipeline 入口加一个 FrameDecoder（帧解码器），按某种边界规则把字节流切成一条条完整消息，再交给后续 Handler。
  3. 编解码两层：解码（Decoder） 把字节→对象（入站方向），编码（Encoder） 把对象→字节（出站方向）。二者常成对出现，组成「协议层」。
  4. 内置即用：Netty 预置了按换行、分隔符、长度域等切分的解码器，覆盖大多数二进制协议；不满足时继承 ByteToMessageDecoder 自定义。
  5. 正确性 > 性能：编解码是协议正确性的根基，错一个长度域会触发整条连接崩溃。务必先保证语义正确，再做池化/零拷贝优化。

本章承接 第三章：Netty 核心组件深入 的 Pipeline / ByteBuf 知识，把「字节流如何变成消息」讲透。

不解决粘包，业务 Handler 里 channelRead 拿到的 ByteBuf 可能含多条半消息，无法正确解析。必须在业务 Handler 之前加帧解码器。

为什么会发生（三个叠加因素）

  1. 发送端合并：Nagle 算法攒小包一起发，多条消息被合并进一个 TCP 段。
  2. 网络层分段：单个应用消息超过 MSS（约 1460 字节）会被拆成多个段，接收端一次 read 可能只拿到半个消息。
  3. 接收端缓冲：内核接收缓冲里的字节是连续无边界的，read 拿到多少取决于时序——可能一次吐出三轮消息，也可能半轮。

结论：TCP 协议里根本没有「消息」概念，边界必须由应用层协议自己定义——这就是帧解码器存在的理由。

十、常见面试题速览

  1. TCP 为什么会粘包——字节流无消息边界 + Nagle 合并 + MSS 分段 + 接收缓冲时序，四者叠加。
  2. 怎么解决——应用层自己定界：定长 / 分隔符 / 长度字段，Netty 用帧解码器承载这三种思路。
  3. LengthFieldBasedFrameDecoder 五参数——maxFrameLength、lengthFieldOffset、lengthFieldLength、lengthAdjustment、initialBytesToStrip；后两个最易配错。
  4. 解码器里数据不够怎么办——return 前 resetReaderIndex 等下次，或直接用 ReplayingDecoder 自动重放。
  5. 帧解码器与业务解码器的分工——前者切出完整字节帧（ByteToMessage），后者把帧解析成对象（MessageToMessage）。
  6. 如何防恶意巨帧——maxFrameLength 限制 + 解码失败 ctx.close()，缺一不可。
  7. 怎么单测解码器——EmbeddedChannel 喂字节取产物，不起网络（见「调试手段」一节）。
  8. MessageToByteEncoder 里要手动 release 吗——encode 产出的 out 由框架释放；但方法外自己 retain 过的引用仍归你管。
  9. 帧解码器能放 @Sharable 吗——不能：内部累积缓冲是有状态的，共享会串包；每个 Channel 独立实例。
  10. 换行解码器能用于二进制协议吗——不能：二进制载荷可能恰好含 0x0A，会被误切；二进制一律走长度域或自定义。
  11. 解码器报 TooLongFrameException 怎么办——先确认是恶意流量还是 maxFrameLength 设小；正常大报文协议应按业务上限重设。

1. 池化与非池化

Netty 默认用 PooledByteBufAllocator.DEFAULT，从按尺寸分级的 PoolArena 中分配，复用内存块、降低 GC。可关闭池化用于排查或特殊场景：

1.1 分配器参数微调（多数项目用默认值即可）

池化分配器按 PoolArena → PoolChunk(16M) → page(8K) → subpage 分级管理，可用系统属性调整：

系统属性 默认 说明
io.netty.allocator.numHeapArenas CPU×2 堆内 Arena 数（≈线程数，减少竞争）
io.netty.allocator.numDirectArenas CPU×2 堆外 Arena 数
io.netty.allocator.pageSize 8192 页大小

经验：先压测再调；Arena 数与 EventLoop 线程数对齐（默认即如此），本地缓存只在「同一线程反复分配/释放」时有效。堆外总上限用 -XX:MaxDirectMemorySize 卡死，建议显式设为「预计峰值 × 1.5」，并接监控观察 PlatformDependent.usedDirectMemory()。

2. 堆内 vs 堆外（direct）

  • 堆外：socket I/O 免一次堆↔内核态拷贝，高吞吐首选；分配/释放略贵，必须 release。
  • 堆内：分配快、GC 自动回收，适合小数据/测试。
  • Netty 默认堆外。监控直接内存用量，配合 JVM 参数 -XX:MaxDirectMemorySize 设上限，防堆外 OOM。

3. 内存泄漏检测

ByteBuf 不 release 会导致堆外内存泄漏。Netty 提供四级检测（按开销从低到高）：

  • SIMPLE（默认）：抽样 1% 对象，开销小，适合日常。
  • PARANOID：全量追踪，仅排查阶段使用，上线前关掉。
  • 检测到泄漏时，日志会打印分配栈，按栈定位「谁分配没释放」。

1. 生产级心跳设计要点

  • 双向约定：客户端 IdleStateHandler(0, 30, 0) 写空闲 30s 发心跳；服务端 IdleStateHandler(90, 0, 0) 读空闲 90s 判死——服务端阈值取客户端心跳周期的 2~3 倍，容忍偶发丢包。
  • 心跳要回显：客户端发 ping 后应等 pong，连续 N 次没收到 pong 主动重连——单向心跳检测不出「半开连接」（对端进程僵死但 TCP 未断）。
  • 区分空闲类型：ALL_IDLE（读+写）适合「静默即异常」的链路；纯下行推送链路只用 READER_IDLE 即可。

1. SO_BACKLOG 的真实语义（常被误解）

TCP 服务端有两个队列：半连接队列（收到 SYN、未完成握手）与全连接队列（已完成握手、等 accept 取走）。SO_BACKLOG 约束的是全连接队列长度，实际生效值 = min(SO_BACKLOG, net.core.somaxconn)——只改应用参数不调内核 somaxconn，队列仍被截断。

全连接队列溢出时，客户端表现为「connect 成功但请求无响应」或收到 RST——突发流量下「服务没挂但部分请求失败」的经典根因。

2. 生产案例（接入层 backlog 打满）

某网关在秒杀预热时大量新连接涌入，ss -ltn 显示 Recv-Q 长期顶满 128（默认 somaxconn）。把 SO_BACKLOG=8192 并同步 sysctl -w net.core.somaxconn=8192 后，LISTENOVERFLOWS 计数归零，建连超时消失。要点：三个值（应用 backlog、somaxconn、tcp_max_syn_backlog）必须一起调。

十、常见面试题速览

  1. Netty 为什么快——Reactor 少量线程撑大量连接、ByteBuf 池化降 GC、堆外内存与 FileRegion 零拷贝、批量 flush 减 syscall。
  2. EventLoop 阻塞如何排查——TimingHandler 类计时告警 + 线程转储找 EventLoop 线程栈；根因多为同步 JDBC/HTTP 调用，解法业务线程池隔离。
  3. 堆外内存泄漏怎么定位——PARANOID 检测 + Created at 分配栈；观察 usedDirectMemory() 曲线。
  4. 心跳与 SO_KEEPALIVE 的关系——TCP 层 keepalive 默认 2 小时级、不穿透中间件 NAT 超时，生产一律用应用层心跳（IdleStateHandler）。
  5. 为什么需要业务线程池而不是加大 EventLoop 数——EventLoop 多了只增加上下文切换；阻塞型任务扩容 EventLoop 治标，隔离才治本。
  6. 批量写与 TCP_NODELAY 矛盾吗——不矛盾：攒批在应用层，NODELAY 在内核层；攒批后 flush 依然立即下发。
  7. Epoll 相比 NIO 收益在哪——少一层 JDK 封装、可用 ET 模式与 TCP_CORK；前提是部署平台确定是 Linux。
  8. SO_BACKLOG 调大就够吗——不够：实际生效值是 min(SO_BACKLOG, net.core.somaxconn)，内核参数必须同步调（见本章第四节）。
  9. 优雅停机做什么——摘流量 → shutdownGracefully → ChannelGroup.close() → 收尾业务线程池，四步缺一不可。
  10. 写比读快会怎样——ChannelOutboundBuffer 膨胀至 OOM；用 isWritable + 水位线 + writability 事件做写侧背压（见第六节）。
  11. FileRegion 能过 SSL 吗——不能：sendfile 走内核直送、绕过用户态加密；加密链路改用 ChunkedWriteHandler + ChunkedNioFile。
  12. EventLoop 线程数如何定——默认 CPU×2 起步，按压测微调；阻塞业务靠线程池隔离而非加大 EventLoop 数。

最佳实践清单

  1. 先单机 DockerSpawner 验证流程，再上 K8s；不要第一天就扎进 Helm chart 细节。
  2. 认证交给企业 IdP（OIDC），不要自己维护用户密码。
  3. 用户镜像统一构建、统一扫描：固定 tag、CI 里跑漏洞扫描，禁止用户随便填镜像名。
  4. 持久化只挂 home，系统目录随镜像重建，保证「环境可丢弃、数据不丢」。
  5. 必须配 cull-idle：空闲会话自动回收是成本与安全双赢。

第六章：性能调优与运维

概念基础

  1. 优化器是起点：Oracle 用 CBO（基于代价的优化器） 为每条 SQL 选执行计划——统计信息准不准、索引有没有、写法合不合理，决定了计划好不好。调优的第一性原理是「让优化器拿到准确信息、做出正确决策」。
  2. 等待事件是症状：性能问题最终都表现为会话在「等什么」——db file sequential read 等索引块、log file sync 等提交、enq: tx - row lock 等锁。读懂等待事件就找到了瓶颈。
  3. 三层调优：应用层（SQL/索引）→ 实例层（内存/参数）→ 系统层（IO/CPU）。80% 问题在应用层，改一条 SQL 收益常大于加内存。
  4. AWR 是病历：Automatic Workload Repository 周期采集性能快照，是回溯分析的依据——「昨晚 3 点慢」靠 AWR 复盘。
  5. 本章目标：掌握执行计划、索引、统计信息、AWR/ASH、锁与等待，建立系统化的调优方法论。

本章承接 第五章：高可用与备份恢复，是 Oracle 系列的收官章。调优能力 = 统计信息 + 执行计划 + 等待事件 + AWR，四件套缺一不可。

一、CBO 优化器

1. RBO 与 CBO

优化器 机制 现状
RBO（Rule-Based） 基于固定规则（有索引就走索引） 10g 起废弃
CBO（Cost-Based） 基于统计信息估算代价，选最低成本计划 默认，现代标准

CBO 的「成本」是估算的 IO + CPU 开销，依赖对象统计信息（行数、唯一值、直方图）。

2. 统计信息

参数 作用
estimate_percent 采样比例，DBMS_STATS.AUTO_SAMPLE_SIZE 自动
method_opt 直方图策略，SIZE AUTO 自适应
cascade 是否同时收集索引统计
degree 并行度

统计信息失真=计划变差：大批量删除/导入后未及时收集，CBO 据错误行数选错计划（如本该走索引却全表扫）。直方图对「数据倾斜列」（如状态枚举）尤其重要。

直方图类型（12c+）：

类型 触发条件 说明
Frequency 唯一值少（≤254） 每值一个桶，最精确
Top-Frequency 少数值占绝大多数 忽略低频值
Hybrid 唯一值多且倾斜 高度均衡 + 频率混合
Height-Balanced 旧式（12c 前） 已不推荐

实用技巧：

自动统计任务默认夜间窗口运行（DBA_AUTOTASK_CLIENT），对白天大批导入的数据来不及更新——ETL 作业完成后应手动收集；导入前可 EXPORT_TABLE_STATS 备份统计，以防新统计导致计划回退无门。

3. 绑定变量与游标共享

解析类型 说明
硬解析 Hard Parse 新 SQL，解析+优化+生成执行计划，昂贵
软解析 Soft Parse 命中 Shared Pool，跳过优化

绑定变量是 OLTP 性能的生命线：不绑定的系统硬解析吃满 CPU、Shared Pool 争用。cursor_sharing=FORCE 是应急补丁，正确做法是应用层用绑定变量。

阅读顺序：从最深层缩进的叶子开始，自内向外、先子后父。估算与实际差 10 倍以上即说明统计信息或写法有问题（函数包裹列、相关列、数据倾斜），优先修统计而不是上 Hint。Buffers 是逻辑读块数，是衡量 SQL 真实成本的最可靠指标。

Hint 是「硬编码计划」，脆弱：数据变化后可能更差。优先靠统计信息+索引让 CBO 自动选对，Hint 仅作诊断或应急。也可用 SQL Profile / SQL Plan Baseline 固定好计划。

5. SQL Profile 与 SQL Plan Baseline

不改 SQL 文本而引导/锁定执行计划的两件武器：

机制 原理 适用
SQL Profile 给 CBO 补充修正因子（如「此谓词实际选择率 ×0.01」），仍允许计划演进 统计难修、SQL 不可改（三方应用）
SQL Plan Baseline 计划白名单：只准用已验收的计划，新计划先入历史待演进 防计划突变（升级/统计变更后回退）

上线大版本/迁移后计划回退是经典事故：19c→23ai 升级时 CBO 行为变化可能让好计划变坏——用 Baseline 冻结核心 SQL 计划，灰度验证后再演进（DBMS_SPM.EVOLVE_SQL_PLAN_BASELINE）。

四、AWR 与 ASH

1. AWR

AWR 每 1 小时自动采集一次快照（STATISTICS_LEVEL=TYPICAL+），保留 8 天，存 SYSAUX：

AWR 报告核心区域：

区域 内容
Top SQL by Elapsed 最耗时 SQL（首要优化对象）
Top 5 Timed Events Top 等待事件
Load Profile 负载画像（每秒事务/解析/redo）
Instance Efficiency 实例效率（解析命中率、缓冲命中率）
SQL Statistics 各类 SQL 统计

AWR 报告解读流程（自上而下，先全局后局部）：

  1. Header 与 Load Profile：确认时段、DB Time 与 DB CPU 比例——DB Time 远大于 CPU 说明大量时间在等待而非计算。
  2. Top 5 Timed Events：按等待占比定位瓶颈类别（IO/锁/闩锁/网络）。
  3. Instance Efficiency：Execute to Parse % 低 → 硬解析多；Buffer Hit % 低且物理读高 → 缓存或 SQL 问题。
  4. Top SQL：按 Elapsed/CPU/Gets/Reads 排序，逐个用 DBMS_XPLAN.DISPLAY_AWR(sql_id) 看历史计划。
  5. Segment Statistics：哪些段物理读/逻辑读最高，锁定热点对象。
  6. 对比基线：与正常时段的 AWR 对照，「变差」的部分即线索。

1. 等待事件分类

Wait Class 典型事件 含义
User I/O db file sequential read 单块读（索引回表）
db file scattered read 多块读（全表扫）
log file parallel write LGWR 写日志
Commit log file sync 提交等 LGWR
Concurrency enq: tx - row lock contention 行锁争用

判读要点：SQL*Net message from client 是空闲等待（客户端不发请求），不计入瓶颈；log file sync 高居榜首先看提交频率与 redo 盘 IO；gc 类事件高说明 RAC 节点间热点块乒乓，考虑按业务分节点路由。

2. 锁机制

Oracle 锁分两类：

锁类型 粒度 行为
TM（表级 DML 锁） 表 防止 DDL 改结构
TX（行级事务锁） 行 行级排他，提交释放
  • 行级锁：UPDATE 一行只锁该行，靠数据块 ITL 实现，不 escalation（不升级为表锁）。
  • 读不阻塞写、写不阻塞读：查询靠 UNDO 读一致性，不锁行。

死锁（ORA-00060）：Oracle 自动检测死锁并回滚其中一方的当前语句，同时在 alert log 与 trace 文件中记录死锁图。绝大多数死锁是应用层更新顺序不一致导致（A 先改表 1 再改表 2，B 反过来）——统一更新顺序、给外键列建索引（防外键未索引引发的 TM 锁放大）即可消除。

3. 经典等待分析

等待 原因 对策
log file sync 提交等 LGWR IO 慢/过度提交；redo 放快盘
db file sequential read 索引回表 回表过多，看能否覆盖索引
db file scattered read 全表扫 缺索引/统计失真
enq: tx - row lock 行锁争用 应用串行化热点行；尽快提交
library cache lock 硬解析/DDL 争用 绑定变量、避免高峰 DDL
buffer busy waits 块争用 减少热点块（反转索引、散列分区）
free buffer waits Buffer Cache 不足 调大 DB_CACHE
enq: TX - allocate ITL entry 块内事务槽不足（高并发改同块） 提高表/索引 INITRANS
enq: TM - contention 表级锁争用，常见于外键未索引 外键列建索引

两类 enq 易混淆：enq: TX - row lock 是行数据冲突（业务串行化问题），enq: TM 多为外键未索引引发的表级锁放大——后者建索引即解，前者要改应用。

八、调优方法论

  1. 先定位再动手：用 AWR/ASH 找 Top SQL 与等待事件，避免盲目改参数。
  2. 应用层优先：80% 问题在 SQL/索引，改一条 SQL 收益常大于加内存。
  3. 统计信息保新：大批量 DML 后手动收集，避免 CBO 走错计划。
  4. 绑定变量必须：OLTP 不绑定等于慢性自杀。
  5. 验证再推广：调优改动在测试环境验证执行计划，生产用 SQL Plan Baseline 平滑切换。
  6. 监控常态化：空间、归档、长事务、慢 SQL 纳入监控告警。
  7. 避免过度优化：满足业务 SLA 即可，过度优化增加复杂度与风险。
  8. 保留回退手段：改统计、加索引、调参数前先记录现状（导出统计、保存旧计划），出问题能秒级回退。
