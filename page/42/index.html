第八章：Jupyter 入门：经典 Notebook、安装与内核

概念基础

Jupyter 是交互式计算生态的名字（源自 Julia / Python / R 三大语言），核心产品就是「浏览器里的笔记本」：

  1. 代码-输出-说明同页共存：在浏览器里写代码、立即看结果、随手记 Markdown 笔记，一个 .ipynb 文件同时是草稿、报告与教学讲义。
  2. 前端与内核解耦：Notebook / JupyterLab 只是「前端界面」，真正执行代码的是独立的**内核（Kernel）**进程，二者通过协议通信——所以一个环境可注册多个内核，前端也可互换。
  3. .ipynb 文件格式：本质是 JSON，保存单元格代码、输出与元数据；是数据分析与算法实验的「可复现草稿纸」。
  4. 为什么需要它：探索性数据分析需要「改一行、马上看结果」的反馈回路，传统「写脚本 → 运行 → 看日志」的循环太慢，Notebook 正是为这类探索而生。
  5. 学习路径：本章掌握经典 Notebook；需要多标签工作台升级 第九章：JupyterLab 入门：安装、工作区与扩展，团队多用户上 第十章：JupyterHub 入门：多用户架构与部署要点。

官网与组成

  • Jupyter 项目主页：https://jupyter.org/
  • Notebook 文档（经典界面）：https://jupyter-notebook.readthedocs.io/
  • .ipynb 格式说明：以当前 nbformat 文档为准（Notebook 文件为 JSON，含代码单元、输出与元数据）。

Jupyter 与具体「前端」解耦：Notebook 与 JupyterLab 都能打开同一 .ipynb；底层常由 jupyter_server 提供 HTTP 与 WebSocket 服务。团队若只需单用户本机或单容器写分析，Notebook 或 JupyterLab 二选一即可。

环境准备

  1. 安装 Python 3.10+，终端可执行 python --version（或 python3，下文统一写 python，请按本机替换）。
  2. 建议使用虚拟环境（venv、conda 或站内 uv 工具），避免把 Jupyter 装进全局 site-packages 难以清理。

内核与 .ipynb 要点

1. 内核（Kernel）

内核是执行代码的进程；Python 环境装了 ipykernel 并注册后，Notebook 右上角可选该内核。

2. 单元格类型

常见为 Code（运行代码）与 Markdown（写说明）；Shift+Enter 执行当前单元并跳到下一单元（具体快捷键以界面 Help 为准）。

3. 保存与版本

.ipynb 含输出时体积会变大；纳入 Git 前团队可约定是否清空输出再提交，或使用 nbstripout 等工具（按需查阅文档）。

内核管理进阶

1. 查看与删除已注册内核

内核注册信息只是指向某个 Python 环境的 JSON 描述，真正的依赖装在各环境自己的 site-packages 里——所以「内核列表里有但 import 失败」多半是该环境里没装包。

2. 一个 Jupyter 服务挂多个环境

推荐做法：Jupyter 本体装一个干净环境，各项目环境只装 ipykernel 并注册内核：

3. 内核卡死与重启

代码死循环或内存爆掉时，用工具栏 Interrupt（中断）→ Restart（重启）；重启会清空内存中所有变量，但单元格代码与已保存的输出保留。顽固卡死可直接在服务器上 kill 内核进程（jupyter kernelspec list 不含进程信息，需用系统工具按 Python 进程排查）。

调试技巧

  1. 单元格内断点：Python 3.13+ 直接用 breakpoint()，触发后进入 ipdb 交互调试（需 pip install ipdb）。
  2. 事后分析：异常发生后执行 %debug 进入事后调试器，可检查崩溃时各栈帧变量。
  3. 打印优于猜测：探索期多用 display()（比 print 对 DataFrame 等对象渲染更好）。
  4. 大对象内存排查：%memit（需 memory_profiler）测单行内存；del + gc.collect() 释放。

最佳实践清单

  1. 每个项目一个内核：ipykernel install --user --name=<项目>，环境隔离、切换清晰。
  2. 探索归探索、交付归脚本：Notebook 里跑通后把可复用逻辑沉淀到 .py 模块，Notebook 只做编排与展示。
  3. 提交前 Restart & Run All：确认从头到尾顺序执行能复现，避免「隐藏状态依赖」。
  4. 大输出不进 Git：清空输出提交，或用 nbstripout 自动剥离。
  5. 远程访问首选 SSH 转发，公网暴露必须 HTTPS + 强认证。
  6. 耗时单元格留 %time：性能敏感代码随时可回归对比。

Oracle：性能调优与运维

概念基础

  1. 优化器是起点：Oracle 用 CBO（基于代价的优化器） 为每条 SQL 选执行计划——统计信息准不准、索引有没有、写法合不合理，决定了计划好不好。调优的第一性原理是「让优化器拿到准确信息、做出正确决策」。
  2. 等待事件是症状：性能问题最终都表现为会话在「等什么」——db file sequential read 等索引块、log file sync 等提交、enq: tx - row lock 等锁。读懂等待事件就找到了瓶颈。
  3. 三层调优：应用层（SQL/索引）→ 实例层（内存/参数）→ 系统层（IO/CPU）。80% 问题在应用层，改一条 SQL 收益常大于加内存。
  4. AWR 是病历：Automatic Workload Repository 周期采集性能快照，是回溯分析的依据——「昨晚 3 点慢」靠 AWR 复盘。
  5. 本章目标：掌握执行计划、索引、统计信息、AWR/ASH、锁与等待，建立系统化的调优方法论。

本章承接 Oracle：高可用与备份恢复，是 Oracle 系列的收官章。调优能力 = 统计信息 + 执行计划 + 等待事件 + AWR，四件套缺一不可。

一、CBO 优化器

1. RBO 与 CBO

优化器 机制 现状
RBO（Rule-Based） 基于固定规则（有索引就走索引） 10g 起废弃
CBO（Cost-Based） 基于统计信息估算代价，选最低成本计划 默认，现代标准

CBO 的「成本」是估算的 IO + CPU 开销，依赖对象统计信息（行数、唯一值、直方图）。

2. 统计信息

参数 作用
estimate_percent 采样比例，DBMS_STATS.AUTO_SAMPLE_SIZE 自动
method_opt 直方图策略，SIZE AUTO 自适应
cascade 是否同时收集索引统计
degree 并行度

统计信息失真=计划变差：大批量删除/导入后未及时收集，CBO 据错误行数选错计划（如本该走索引却全表扫）。直方图对「数据倾斜列」（如状态枚举）尤其重要。

直方图类型（12c+）：

类型 触发条件 说明
Frequency 唯一值少（≤254） 每值一个桶，最精确
Top-Frequency 少数值占绝大多数 忽略低频值
Hybrid 唯一值多且倾斜 高度均衡 + 频率混合
Height-Balanced 旧式（12c 前） 已不推荐

实用技巧：

自动统计任务默认夜间窗口运行（DBA_AUTOTASK_CLIENT），对白天大批导入的数据来不及更新——ETL 作业完成后应手动收集；导入前可 EXPORT_TABLE_STATS 备份统计，以防新统计导致计划回退无门。

3. 绑定变量与游标共享

解析类型 说明
硬解析 Hard Parse 新 SQL，解析+优化+生成执行计划，昂贵
软解析 Soft Parse 命中 Shared Pool，跳过优化

绑定变量是 OLTP 性能的生命线：不绑定的系统硬解析吃满 CPU、Shared Pool 争用。cursor_sharing=FORCE 是应急补丁，正确做法是应用层用绑定变量。

操作 说明 何时出现

判断执行计划好坏的核心：估算行数（Rows）是否接近实际——偏差大说明统计信息失真。关注高 Cost 节点与「FULL SCAN + 大表」组合。

估算 vs 实际（E-Rows / A-Rows）：DISPLAY_CURSOR(format=>'ALLSTATS LAST') 得到的真实计划含 E-Rows（估算）与 A-Rows（实际）两列——

阅读顺序：从最深层缩进的叶子开始，自内向外、先子后父。估算与实际差 10 倍以上即说明统计信息或写法有问题（函数包裹列、相关列、数据倾斜），优先修统计而不是上 Hint。Buffers 是逻辑读块数，是衡量 SQL 真实成本的最可靠指标。

4. Hint 提示

临时强制执行计划（治标，慎用）：

Hint 是「硬编码计划」，脆弱：数据变化后可能更差。优先靠统计信息+索引让 CBO 自动选对，Hint 仅作诊断或应急。也可用 SQL Profile / SQL Plan Baseline 固定好计划。

5. SQL Profile 与 SQL Plan Baseline

不改 SQL 文本而引导/锁定执行计划的两件武器：

机制 原理 适用
SQL Profile 给 CBO 补充修正因子（如「此谓词实际选择率 ×0.01」），仍允许计划演进 统计难修、SQL 不可改（三方应用）
SQL Plan Baseline 计划白名单：只准用已验收的计划，新计划先入历史待演进 防计划突变（升级/统计变更后回退）

上线大版本/迁移后计划回退是经典事故：19c→23ai 升级时 CBO 行为变化可能让好计划变坏——用 Baseline 冻结核心 SQL 计划，灰度验证后再演进（DBMS_SPM.EVOLVE_SQL_PLAN_BASELINE）。

四、AWR 与 ASH

1. AWR

AWR 每 1 小时自动采集一次快照（STATISTICS_LEVEL=TYPICAL+），保留 8 天，存 SYSAUX：

AWR 报告核心区域：

区域 内容
Top SQL by Elapsed 最耗时 SQL（首要优化对象）
Top 5 Timed Events Top 等待事件
Load Profile 负载画像（每秒事务/解析/redo）
Instance Efficiency 实例效率（解析命中率、缓冲命中率）
SQL Statistics 各类 SQL 统计

AWR 报告解读流程（自上而下，先全局后局部）：

  1. Header 与 Load Profile：确认时段、DB Time 与 DB CPU 比例——DB Time 远大于 CPU 说明大量时间在等待而非计算。
  2. Top 5 Timed Events：按等待占比定位瓶颈类别（IO/锁/闩锁/网络）。
  3. Instance Efficiency：Execute to Parse % 低 → 硬解析多；Buffer Hit % 低且物理读高 → 缓存或 SQL 问题。
  4. Top SQL：按 Elapsed/CPU/Gets/Reads 排序，逐个用 DBMS_XPLAN.DISPLAY_AWR(sql_id) 看历史计划。
  5. Segment Statistics：哪些段物理读/逻辑读最高，锁定热点对象。
  6. 对比基线：与正常时段的 AWR 对照，「变差」的部分即线索。

2. 锁机制

Oracle 锁分两类：

锁类型 粒度 行为
TM（表级 DML 锁） 表 防止 DDL 改结构
TX（行级事务锁） 行 行级排他，提交释放
  • 行级锁：UPDATE 一行只锁该行，靠数据块 ITL 实现，不 escalation（不升级为表锁）。
  • 读不阻塞写、写不阻塞读：查询靠 UNDO 读一致性，不锁行。

死锁（ORA-00060）：Oracle 自动检测死锁并回滚其中一方的当前语句，同时在 alert log 与 trace 文件中记录死锁图。绝大多数死锁是应用层更新顺序不一致导致（A 先改表 1 再改表 2，B 反过来）——统一更新顺序、给外键列建索引（防外键未索引引发的 TM 锁放大）即可消除。

db file scattered read 全表扫 缺索引/统计失真
enq: tx - row lock 行锁争用 应用串行化热点行；尽快提交

enq: TX - allocate ITL entry 块内事务槽不足（高并发改同块） 提高表/索引 INITRANS

八、调优方法论

  1. 先定位再动手：用 AWR/ASH 找 Top SQL 与等待事件，避免盲目改参数。
  2. 应用层优先：80% 问题在 SQL/索引，改一条 SQL 收益常大于加内存。
  3. 统计信息保新：大批量 DML 后手动收集，避免 CBO 走错计划。
  4. 绑定变量必须：OLTP 不绑定等于慢性自杀。
  5. 验证再推广：调优改动在测试环境验证执行计划，生产用 SQL Plan Baseline 平滑切换。
  6. 监控常态化：空间、归档、长事务、慢 SQL 纳入监控告警。
  7. 避免过度优化：满足业务 SLA 即可，过度优化增加复杂度与风险。
  8. 保留回退手段：改统计、加索引、调参数前先记录现状（导出统计、保存旧计划），出问题能秒级回退。

Oracle：高可用与备份恢复

概念基础

  1. 三层防护：Oracle 高可用由「集群防节点故障（RAC） + 容灾防站点故障（Data Guard） + 备份防逻辑/物理损坏（RMAN）」三层叠加构成，各有侧重、互补配合。
  2. RAC 解决单点：多实例共享存储并发读写，任一节点宕机业务自动漂移，做到节点级高可用 + 横向扩展，但不防存储损坏与站点灾难。
  3. Data Guard 解决容灾：主库 redo 实时同步到异地备库，可只读/灾备切换，做到站点级容灾 + 数据零丢失，是 RAC 之外的异地防线。
  4. RMAN 解决恢复：物理备份 + 归档日志支持任意时点恢复，配合闪回快速逆转人为误操作——备份是最后一道防线，”没备份就准备跑路”不是玩笑。
  5. 本章目标：掌握 RAC、Data Guard、RMAN、闪回四大支柱的原理与实操，构建企业级容灾方案。

本章承接 Oracle：体系结构与存储管理。高可用设计的前提是理解实例/数据库/归档的运行机制，本章在此基础上构建可用性方案。

1. 架构

组件 作用
SCAN Single Client Access Name，单一接入点，客户端连 SCAN 不连节点
VIP 节点虚拟 IP，故障时漂移，快速失败转移

2. 工作机制

  1. 多实例共享同一数据文件，各自有独立 SGA/Redo Thread。
  2. 节点 A 要改节点 B 缓存的块，通过私有网络（Cache Fusion）传递，而非走磁盘。
  3. 节点宕机时，VIP 漂移、SCAN 重定向，会话重连到存活节点。
  4. 私有网络心跳丢失时，投票盘决定少数派节点被驱逐（evict）防脑裂。

3. 优缺点

优势 代价

横向扩展读、部分扩展写 写仍共享存储，扩展性有限
在线滚动升级 License 昂贵
单库视图，应用透明 Cache Fusion 网络是瓶颈

RAC 防节点不防存储：共享存储是单点，必须配合 ASM 镜像或外部 RAID。RAC 也防不了站点灾难，需 Data Guard 异地容灾。应用要做「无状态 + 重连」才能享受故障切换红利。

  1. 并发是语言内建能力：Go 在语言层面提供 goroutine 与 channel，无需第三方库即可写出高并发程序，这是 Go 最具辨识度的特性。
  2. CSP 模型：遵循「不要通过共享内存来通信，而要通过通信来共享内存」，用 channel 在 goroutine 之间传递数据与所有权。
  3. M:N 调度：运行时把成千上万个轻量 goroutine 复用到少量 OS 线程上，创建成本远低于线程，适合海量并发任务。
  4. 传统同步工具仍在：sync.Mutex/WaitGroup/Once 处理共享状态与协作，context 统一传递取消与超时。
  5. 工程红线清晰：goroutine 泄漏、循环变量捕获、无界并发是三大常见陷阱；开发与 CI 应常开 go test -race 竞态检测。

一、goroutine 与调度模型

  • goroutine：用 go f() 启动；栈初始很小、可按需增长，创建成本远低于操作系统线程，因此可以大量存在。
  • 调度器：运行时把许多 goroutine 映射到少量 OS 线程（M:N 模型），在阻塞或抢占点切换，避免「一线程一连接」把机器拖垮。
  • 何时用：IO 密集、扇出扇入、后台任务；CPU 密集仍要控制并发度（见第七节），否则和线程池一样会抢满核心。

1.1 GMP 调度模型

Go 1.25 运行时的调度器由三类实体构成，理解它对排查性能问题至关重要：

实体 含义 要点
G（Goroutine） 待执行的任务单元 初始栈仅 2KB 按需增长；含栈、指令指针、上下文
M（Machine） OS 线程 真正跑代码的载体，数量与系统调用阻塞情况联动
P（Processor） 逻辑处理器 默认数 = GOMAXPROCS（CPU 核数）；每个 P 持一个本地可运行队列（LRQ）

调度要点：

  • M:N 复用：N 个 G 跑在 M 个线程上，但任一时刻并行执行的 G 数量受 P 数限制——CPU 密集任务的「有效并发」上限就是 GOMAXPROCS。
  • 工作窃取（work stealing）：某 P 的本地队列空了，会从全局队列（GRQ）或其他 P 的队列偷一半 G 过来，保证负载均衡。
  • 阻塞处理：G 陷入阻塞式系统调用时，其 M 带着 G 脱离 P，P 立即绑定新 M 继续跑其他 G——这就是「几千个并发连接拖不垮 Go」的原因。
  • 抢占：Go 1.14+ 引入基于信号的异步抢占，长时间纯计算（无函数调用）的 G 也会被让出 CPU，避免单个死循环饿死全进程。

容器环境注意：Go 1.25 起 GOMAXPROCS 默认感知 cgroup CPU limit；旧版本在 K8s 里会看到宿主机核数，导致 P 过多、频繁上下文切换，需用 automaxprocs 修正。

二、channel：通信优先于共享内存

  • 声明与创建：var ch chan int 为 nil，发送/接收会永久阻塞；ch := make(chan int) 无缓冲；make(chan int, 10) 带容量为缓冲 channel。
  • 无缓冲：发送方与接收方必须同时就绪，完成一次「交接」，常用于同步节拍。
  • 缓冲：未满时可先发送，常用于限流或解耦；容量为 0 与无缓冲语义一致。
  • 关闭：仅发送方应调用 close(ch)；接收方可用 v, ok := <-ch，ok == false 表示 channel 已关闭且无剩余数据。
  • 单向 channel：类型 chan<- T（只发）、<-chan T（只收）用于函数签名，约束使用方式、减少误用。

操作 nil/关闭 channel 的行为表：向 nil channel 收发→永久阻塞；关闭 nil channel、重复关闭、向已关闭 channel 发送→panic；从已关闭 channel 接收→立即返回零值（ok=false）。「由发送方关闭、只关一次」是避免 panic 的铁律。

2.1 channel 底层结构

make(chan T) 创建的 hchan 结构体核心字段：

  • buf：环形缓冲区（仅缓冲 channel 有），sendx/recvx 记录读写下标。
  • sendq / recvq：因发送/接收而阻塞的 goroutine 等待队列——无缓冲 channel 的交接本质：发送方挂进 sendq，接收方到达后直接从对方栈上拷数据（不经 buf），再唤醒发送方。
  • lock：每个 channel 一把互斥锁，所有队列与缓冲区操作都在锁内——channel 的「无锁」是使用者视角，内部仍有锁。

由此可解释三个现象：

  1. 无缓冲 channel 是同步点：发送方必须等接收方接手才能完成，天然形成「交接内存屏障」，这是它能替代锁做同步的底层依据。
  2. 缓冲 channel 的容量只是解耦窗口：满了照样阻塞发送方；cap 设多大取决于上下游速率差，不是越大越好。
  3. close 是广播：关闭时唤醒所有 recvq 中的接收方（返回零值 + ok=false），所以 close 常作多接收方统一退出信号（比挨个发消息高效）。

三、select：多路等待与超时

  • select 在多个 channel 操作上等待，随机选择一个可执行的 case；若都阻塞且无 default，则阻塞；有 default 则立即走默认分支（常用于非阻塞尝试）。
  • 超时模式：用 time.After 或 context（推荐生产代码）控制最长等待。

四、sync 包：锁与协作原语

4.1 Mutex / RWMutex

  • 多 goroutine 读写同一内存且无 channel 串行化时，用 sync.Mutex 保护临界区；读多写少可考虑 RWMutex。
  • 锁粒度要小、持有时间要短；避免在持锁时做 IO 或可能阻塞很久的逻辑。
  • 读多写少用 RWMutex：读用 RLock/RUnlock 可多读并发，写用 Lock/Unlock 与所有读写互斥；当读操作远多于写、且读临界区稍长时，比 Mutex 更利于吞吐。

注意：RWMutex 并非「必优于 Mutex」。读临界区很短时，RLock/RUnlock 的计数开销可能反超 Mutex；不确定时先 Mutex，用 go test -race + benchmark 验证再换。

4.2 WaitGroup

  • Add / Done / Wait：主 goroutine Wait() 等待一组子任务结束；Add 要在启动 goroutine 之前（或确保不竞态地提前 Add），避免 Wait 早于 Add 导致计数错误。

Add 必须在启动 goroutine 之前调用：Wait() 在计数归零时立即返回，若 Add 落到子 goroutine 内部，Wait 可能在任何 Add 之前就执行而提前放行。这是逻辑时序错误，go test -race 未必能检出，需靠规范避免——Add 在前、Done 用 defer 在内。

4.3 Once

  • sync.Once 保证 Do(f) 里的 f 全局只执行一次，常用于懒初始化单例。

4.4 sync.Map：特定场景的并发映射

  • 普通 map + Mutex 是通用解；sync.Map 为两类特化场景优化：键一次写入、多次读取（缓存）、各 goroutine 操作不相交的键。内部读写分离 + 原子操作，读路径无锁。

不要无脑用 sync.Map：读写混合且键频繁增删时，普通 map + RWMutex 往往更快、类型更安全（sync.Map 的值是 any）。

七、常见陷阱与实践建议

  • main 退出即进程退出：未 Wait 或未收完结果的 goroutine 会被直接掐掉；要有明确的汇合点（WaitGroup、channel 关闭、errgroup 等）。
  • 泄漏 goroutine：向无人接收的 channel 发送、或 goroutine 永远阻塞在 select，都会导致泄漏；长生命周期任务要设计退出信号。
  • 闭包与循环变量：在循环里 go func() { ... } 若引用循环变量，应用参数传入当前值，避免经典「全部打印最后一个」问题（Go 1.22+ 对循环变量语义有调整，仍建议显式传参以增强可读性与兼容旧版本）。
  • CPU 密集：用 runtime.NumCPU() 或带缓冲的 worker channel 限制并发 worker 数量，而不是无节制 go。
  • 竞态检测：开发与 CI 中开启 go test -race，能发现大量数据竞态。

整体上，Go 鼓励用 channel 表达所有权与流水线，在热点路径或简单共享计数时用 Mutex；取消与超时交给 context，代码意图会更清晰、也更容易在团队中保持一致。

Oracle：体系结构与存储管理

概念基础

  1. 内存 + 进程 + 文件三件套：Oracle 实例由 SGA（共享内存）+ PGA（私有内存）+ 后台进程构成，操作 Database 物理文件——理解三者的协作就抓住了 Oracle 运行的本质。
  2. 日志先行是命脉：事务提交时 LGWR 先把 redo 写联机日志才算「提交成功」，脏块由 DBWn 延迟批量落盘。这套 WAL 机制保证了实例崩溃后可恢复，是 Oracle 可靠性的根基。
  3. 逻辑/物理存储两层映射：逻辑上「表空间→段→区→块」，物理上「数据文件→操作系统块」——段对应表/索引、区是分配单位、块是最小 IO 单元。
  4. 多版本读一致性靠 UNDO：查询看到的是「查询开始时点」的数据快照，靠 UNDO 表空间的撤销数据回构——这是 Oracle 实现「读不阻塞写、写不阻塞读」的核心。
  5. 本章目标：从内存、进程、文件到存储分层与 ASM，建立完整的 Oracle 内部运行图景，为高可用与调优打基础。

本章承接 Oracle：PL/SQL 程序设计。体系结构是 DBA 与架构师的必修课，也是后续高可用、调优章节的底层依据。

一、内存结构

1. SGA（System Global Area，共享全局区）

SGA 是所有服务进程共享的内存大区，由若干子池组成：

子池 职责 调优要点
Buffer Cache 缓存数据块，减少物理读 DB_CACHE_SIZE，命中率核心
Shared Pool 库缓存（SQL/PL/SQL 解析结果）+ 数据字典缓存 SHARED_POOL_SIZE，绑定变量缓解
Redo Log Buffer 缓存 redo 条目，LGWR 异步写盘 LOG_BUFFER，通常较小
Large Pool RMAN 备份、并行查询、共享服务器会话 可选，避免挤占 Shared Pool
Java Pool / Streams Pool JVM、GoldenGate/Streams 按需

Buffer Cache 内部：默认缓存 8KB 数据块，可细分三个池——

池 用途
DEFAULT 默认池，未指定的对象进这里
KEEP 钉住热表（STORAGE(BUFFER_POOL KEEP)），防被挤出
RECYCLE 放大表全扫的块，快进快出防污染

脏块通过检查点队列等待 DBWn 落盘，干净块按 LRU 变冷淘汰。

Shared Pool 内部：库缓存（SQL 文本/执行计划，按 SQL_ID 哈希存放）+ 数据字典缓存（row cache，表/列定义）+ 结果缓存（11g+，RESULT_CACHE）。硬解析频繁时 library cache 闩锁争用会成为瓶颈——绑定变量是根治手段（见第六章）。

2. PGA（Program Global Area，私有区）

PGA 是每个会话私有的内存，存放排序区、会话状态、游标：

区域 作用
Sort Area 排序中间结果，不足则写临时段
Hash Area 哈希连接用
Session Memory 会话变量、游标状态

workarea executions - onepass / multipass 持续增长说明排序/哈希内存不足、溢出到 TEMP 磁盘，需调大 PGA_AGGREGATE_TARGET 或优化 SQL（减少排序、加索引消除 ORDER BY）。理想状态是 optimal 占绝对多数。

SGA 是共享、PGA 是私有——这是内存模型的核心区分。排序/哈希在 PGA 跑，超限溢出到 TEMP 表空间（磁盘），是慢查询的常见元凶。

3. 内存管理演进

模式 机制 参数
手动 各池手动设固定值 DB_CACHE_SIZE 等逐个设
ASMM（10g+） SGA 内自动分配 SGA_TARGET + PGA_AGGREGATE_TARGET
AMM（11g+） SGA+PGA 全自动 MEMORY_TARGET（含 PGA）

生产推荐 ASMM（SGA_TARGET+PGA_AGGREGATE_TARGET）。AMM 在大内存/RAC/巨页场景有兼容问题，慎用。

  1. 前滚（Roll Forward）：用联机 redo 把最后一次检查点之后的所有变更重放到数据文件，包括未提交事务的脏块——先把「磁盘状态」追平到宕机瞬间。
  2. 打开数据库：此时库中尚有未提交事务的数据，但已可对外服务。
  3. 回滚（Roll Back）：SMON 用 UNDO 回滚所有未提交事务，恢复一致性；新事务碰到未回滚的行时会触发事务恢复自动清理。

「先追平、再清理」：前滚依赖 redo（已落盘的变更），回滚依赖 UNDO（未提交的旧值）。这解释了为什么实例崩溃不丢已提交数据（redo 已写盘），也不留未提交数据（UNDO 回滚）。FAST_START_MTTR_TARGET 控制前滚时间上限。

1. 数据块内部

一个数据块（默认 8KB）内部结构：

  • 高水位线 HWM：段曾用到的最高块位置，SELECT 全表扫到 HWM 即止。TRUNCATE 重置 HWM，DELETE 不重置。

六、UNDO 与读一致性

1. UNDO 的作用

UNDO 表空间存放「改之前」的旧值，支撑三大机制：

  1. 事务回滚：ROLLBACK 时用 UNDO 恢复原值。
  2. 读一致性：查询看到查询开始时点的数据，靠 UNDO 回构已被改的块。
  3. 闪回查询：AS OF TIMESTAMP 利用 UNDO 看历史数据。

2. 多版本读一致性

参数 作用
UNDO_RETENTION UNDO 保留时间（秒），降低 ORA-01555
UNDO_TABLESPACE 指定 UNDO 表空间
TEMP_UNDO_ENABLED 12c+ 临时表 UNDO 独立

自动 UNDO 管理（AUM）要点：

  • 表空间自动扩展（AUTOEXTEND ON）时，UNDO_RETENTION 是「努力目标」，空间紧张时保留时间可能被压缩。
  • RETENTION GUARANTEE 强制保留（宁可 DML 报错也不覆盖未过期 UNDO），代价是影响并发事务。
  • 估算所需 UNDO 大小：峰值每秒 undo 生成量 × UNDO_RETENTION，生成速率查 V$UNDOSTAT 的 UNDOBLKS。

ORA-01555 快照太旧是长查询经典错误：UNDO 数据被新事务覆盖，旧版本回构不出来。调大 UNDO_RETENTION 与 UNDO 表空间、避免长查询跨大事务可缓解。

七、REDO 与归档

1. REDO 的写入流程

  1. 会话修改块，生成 redo 条目入 Redo Log Buffer。
  2. 提交时 LGWR 把 redo 写联机日志（同步），提交返回。
  3. DBWn 延迟把脏块写数据文件（异步批量）。
  4. 联机日志写满切换，ARCn 归档（ARCHIVELOG 模式）。

LGWR 触发写的时机（满足任一即写）：

  • 事务 COMMIT（同步等待，这是「提交成功」的定义）。
  • Redo Log Buffer 达到 1/3 满。
  • 每 3 秒超时。
  • DBWn 写脏块之前（对应 redo 必须先落盘）。

redo 先行的严格性：DBWn 写任何脏块前，该块对应的 redo 必须已落盘——否则实例崩溃后无法前滚这个块。COMMIT 的 log file sync 等待即等 LGWR 落盘，是 OLTP 提交延迟的关键指标（见第六章）。

2. NOARCHIVELOG vs ARCHIVELOG

模式 联机日志 能力 适用
NOARCHIVELOG 写满即覆盖 只能恢复到上次冷备 开发/测试
ARCHIVELOG 归档保留 可时点恢复（PITR） 生产必须

生产必须 ARCHIVELOG——否则磁盘损坏只能恢复到上次备份点，丢失期间所有数据。归档目录要监控空间，写满会挂起数据库。

ClickHouse：列式存储入门

概念基础

  1. 列式存储：ClickHouse 按列组织数据，SELECT avg(price) 只读 price 一列，IO 远小于行存全表扫描——这是它分析查询快的根源。
  2. 向量化执行：数据按列块批量进入对 CPU 缓存友好的计算路径，充分利用批量计算，吞吐远高于逐行解释执行。
  3. 专为 OLAP 而生：适合大规模聚合、日志与事件分析；不适合高并发单行点查、频繁小事务更新（OLTP 仍用 第一章：MySQL DDL 语句与表设计入门 等）。
  4. MergeTree 引擎家族：核心表引擎支持分区、排序键、TTL、副本，是绝大多数分析表的底座。
  5. 双协议接入：HTTP 8123（curl、JDBC HTTP、BI 工具）与 Native 9000（clickhouse-client、官方驱动）按场景选择。
  6. 版本基准：本文以 ClickHouse 25.x（2025 年稳定线）语法与行为为准；长期支持版（LTS）每年 3 月、8 月发布，生产建议选 LTS 标签。

3. 稀疏索引：为什么主键不占多少内存

MergeTree 的主键索引不是 B-Tree，而是稀疏索引（Sparse Index）：

  • 数据按 ORDER BY 排序后切成 granule（默认每 8192 行一个）。
  • 索引只记录每个 granule 第一行的排序键值——亿行表的主键索引通常只有几万条，可常驻内存。
  • 查询时先二分查找索引定位到候选 granule 区间，再并行扫描这些 granule——这就是「索引在 ClickHouse 里很轻」的原因。
  • partition：分区键值（如 202605）。
  • part：分区内的物理数据块，后台 merge 会持续把小 part 合成大 part。
  • part 过多会触发 Too many parts 报错——写入批量化是预防关键（排查详见 ClickHouse：查询与性能调优）。

向量化执行：快在 CPU 层面

列存解决的是少读盘，向量化解决的是读进来之后算得快：

  • 批量而非逐行：表达式一次处理一个列块（通常几千行的数组），而不是一行行解释执行。
  • SIMD 指令：sum、count 等聚合经编译生成 AVX2/AVX-512 向量化指令，一条指令算多个值。
  • CPU 缓存友好：列块紧凑连续，预取命中率高；行存的「字段散布在行里」会频繁缓存失效。
  • 多核并行：查询按 granule 拆成任务流，默认吃满 max_threads（= CPU 核数）。

这也是为什么 ClickHouse 对虚机 / 容器限核敏感——CPU 被限到 2 核时，聚合吞吐近乎同比腰斩，容量规划要预留核数。

集群部署概览：ReplicatedMergeTree + Keeper

单机之上，生产最小可信拓扑是 2 分片 × 2 副本：

  1. ClickHouse Keeper（或 ZooKeeper）：3 节点小集群，存副本元数据与日志序号，协调「谁同步谁」；自身用 Raft 选主，独立于数据节点部署。
  2. ReplicatedMergeTree：建表加副本参数，同分片的多个副本通过 Keeper 交换 part 清单、互拉数据，写入任一副本即可。
  3. Distributed 表：建在每个节点上，按 sharding key（如 user_id 哈希）把写入/查询路由到目标分片。

要点：ON CLUSTER 让 DDL 在集群所有节点执行；分片键选基数高、分布均匀的列，避免数据倾斜。完整容器化集群清单见 ClickHouse：Docker 部署实践。

生产注意

  • 副本与 Keeper：ClickHouse Keeper（或 ZooKeeper）协调复制与分布式 DDL；Keeper 集群必须奇数节点（3 或 5），与数据节点分开部署。
  • 资源：内存用于 merge 与查询；磁盘顺序写与 merge 压力需监控；CPU 核数直接决定聚合吞吐。
  • 写入纪律：批量写入（每批几万~几十万行），避免高频小批产生海量小 part 触发 Too many parts。
  • 升级：固定版本标签，阅读 Release Notes 中不兼容变更；跨大版本先在测试集群滚动验证。

LIKE 只有 % 和 _ 两个通配符，遇到「以 1 开头、第二位 3-9、共 11 位数字」这类规则就无能为力——该上正则就上正则。注意正则列条件通常不走普通索引，高频过滤场景考虑函数索引或生成列。

十二、常见陷阱

= NULL 查不到 NULL 用 IS NULL，比较运算对 NULL 返回未知
未提交就断连 DML 后没 COMMIT，会话结束自动回滚
VARCHAR vs VARCHAR2 用 VARCHAR2，VARCHAR 未来可能改语义
单双引号混用 单引号字符串、双引号标识符，与 MySQL 相反
ROWNUM 直接分页 排序前分配，必须嵌套子查询
COUNT(列) 漏 NULL 计 NULL 用 COUNT(*) 或 COUNT(1)
DDL 隐式提交 建表/改表/TRUNCATE 前未提交的 DML 会被提交
日期格式依赖 NLS TO_DATE 不指定格式靠 NLS_DATE_FORMAT，生产环境显式写格式
