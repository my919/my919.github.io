设计模式 · 数据传输对象（DTO）

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与 VO/PO 对比。

1. 模式概述（意图）

DTO（Data Transfer Object）是跨层传输数据的载体对象——把多个字段打包成一次传输，避免逐字段多次调用、也避免把内部实体直接暴露给外部。

2. 要解决的问题

问题 说明
网络往返过多 一次要多个数据 → 逐次调用
内部结构暴露 实体含敏感字段/内部结构，直接返回有风险
层间耦合 Controller 直接用 Entity，改表结构影响 API
传输粒度不匹配 前端要 A+B+C 拼装，接口要定制

典型场景：REST API 请求/响应对象、远程调用（RPC 参数）、分页结果封装、批量数据聚合。

5. 应用场景

场景 说明
REST API 请求/响应对象
RPC/微服务 服务间传输参数
分页聚合 PageResult 封装
多源数据组装 组装多个来源为一个 DTO
大对象拆分 一次传输所需字段

6. 优缺点

优点 缺点
隔离内部模型（安全） DTO 与实体字段重复（样板代码）
减少网络往返 转换代码要维护
按需裁剪（不多传/不少传） 过细 DTO 导致类爆炸
层间解耦 需要字段映射约定

7. 与相关概念对比

概念 说明
DTO 跨层/跨网络传输（入参/出参）
VO（View Object） 专为视图层定制的 DTO
PO/Entity 持久化模型（对应表）
BO 业务模型（领域）
DO 领域对象

分层铁律：Entity/PO 只在内层；跨网络/跨层一律 DTO/VO——避免”接口直接暴露表结构”。

8. 常见误用与陷阱

坑 现象 解法
DTO 与实体混用 请求体直接绑定 Entity（@RequestBody UserEntity），改张表就破坏 API 入参/出参用独立 record，边界处显式转换
敏感字段未脱敏就暴露 passwordHash、salt、内部状态被 Jackson 原样序列化出去 响应 DTO 走字段白名单；敏感字段根本不放进出参 DTO
过度映射层级 DO→BO→DTO→VO 层层 BeanUtils.copy，样板代码淹没业务 每层都要有明确收益；简单链路允许 DO→DTO 直转
万能 DTO 走所有接口 一个类几十个字段，靠注释区分哪个接口填哪些 按场景定制（CreateUserRequest / UserListResponse）
DTO 里塞业务行为 在传输对象中下单、算价、调 Service DTO 保持贫血数据载体，行为归领域/应用服务
