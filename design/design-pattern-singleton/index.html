单例模式详解（Singleton）

发表于 2026-09-14 更新于 2026-10-25 分类于 设计模式 本文字数： 2.7k 阅读时长 ≈ 2 分钟

设计模式 · 单例模式

GoF 创建型模式。意图 · 结构 · 线程安全四种写法 · 应用场景 · 优缺点 · 与其他模式对比。代码带详细注释。

1. 模式概述（意图）

单例模式（Singleton）保证一个类只有一个实例，并提供一个全局访问点。核心：把构造函数私有化，由类自己管理唯一实例。

2. 要解决的问题

问题 说明
重复创建浪费资源 连接池、线程池、配置对象创建昂贵
状态不一致 多个实例各自持有状态，互相不同步
全局访问不方便 需要到处传递实例引用

典型场景：数据库连接池、Redis 客户端、Spring 容器、日志记录器、配置管理器——这些对象一个就够，多了反而有害。

4. 代码实现（四种写法，从简单到线程安全）

4.1 懒汉式（线程不安全，仅教学）

5. 应用场景（JDK/Spring 实例）

场景 说明
Spring Bean 默认单例 @Bean 默认 singleton 作用域
JDK Runtime Runtime.getRuntime() 就是单例
数据库连接池 HikariCP DataSource 单例
线程池 Executors 返回的池对象全局共享
配置中心 应用配置只加载一次

6. 优缺点

优点 缺点
节省资源（一个实例） 违反开闭原则（扩展需改类）
全局访问方便 隐藏依赖（全局状态难测试）
保证状态一致 多线程实现要小心（写错有并发隐患）
懒加载可选 滥用导致”上帝对象”

现代观点：单例要克制——能用依赖注入（Spring 容器管单例）就不用全局静态单例；全局可变状态是测试和并发的地雷。

7. 与其他模式的关系

相关模式 关系
工厂模式 工厂常配合单例：返回唯一实例
享元模式 享元强调”复用共享对象”，单例是享元的一种特例
建造者模式 建造者常用于配置复杂对象，可与单例组合

8. 常见误用与陷阱

坑 现象 解法
懒汉式多线程创建多个 高并发下 instance 被 new 两次 用 DCL（volatile + 双重检查）或静态内部类
反射破坏单例 反射调私有构造器创建新实例 用枚举单例（JVM 保证唯一）
序列化反序列化出新实例 反序列化后 != 原实例 枚举单例 / 加 readResolve()
单例持有可变全局状态 测试互相污染，并发难排查 单例只放只读配置，可变状态交给请求上下文
