服务定位器模式详解（Service Locator）

发表于 2026-09-14 更新于 2026-10-29 分类于 设计模式 本文字数： 3.5k 阅读时长 ≈ 3 分钟

设计模式 · 服务定位器

J2EE 核心模式（非 GoF）。意图 · 结构 · 代码实现 · 应用场景 · 优缺点 · 与依赖注入对比。

1. 模式概述（意图）

服务定位器（Service Locator）提供一个中央注册表，客户端通过它查找并获取服务实例——缓存已查到的服务，避免重复创建。

2. 要解决的问题

问题 说明
服务获取逻辑分散 各处 new/初始化服务
服务创建昂贵 连接池、客户端对象重复创建
查找逻辑重复 每个使用方都要知道怎么拿服务

典型场景：JNDI 查找、EJB 容器、老式企业应用、需要”运行时按名字找服务”的框架。

5. 应用场景

场景 说明
JNDI 查找 Java EE 服务查找
框架容器 运行时按名取服务
多实现选择 按配置选择服务实现
客户端缓存 昂贵的客户端对象复用

6. 优缺点

优点 缺点
服务获取统一 隐藏依赖（代码看不出来用了什么服务）
缓存提升性能 测试困难（全局静态缓存）
按名查找灵活 违反依赖倒置（依赖定位器而非接口）
实现简单 定位器易成”上帝对象”

7. 与依赖注入对比（高频考点）

维度 服务定位器 依赖注入（DI）
依赖可见性 代码内查找（隐藏） 构造器/注解声明（显式）
测试 难（全局状态） 易（注入 mock）
反转 客户端主动找（弱反转） 容器注入（强反转）
现代实践 老式方案 现代首选（Spring 容器）

结论：新项目一律用 DI（Spring IoC 容器），服务定位器只出现在遗留系统。

8. 常见误用与陷阱

坑 现象 解法
隐藏依赖导致不可测 类内部 ServiceLocator.get("x")，单测不读源码不知道要 mock 什么 依赖走构造器注入、测试传 mock；定位器只留在组合根
与依赖注入取舍失当 新 Spring 项目仍手写静态定位器，放弃容器能力 能用容器注入就不用定位器；仅「运行时按名动态选择」保留注册表
定位器变全局可变注册表 任意代码都能 register/put，服务在运行时被悄悄替换 注册表启动期一次性填充、只暴露查找；禁止运行时 mutate
缓存有状态服务 静态缓存的实例带成员变量，并发请求共享后串数据 缓存只放无状态单例；有状态对象交容器按作用域管理
查找失败返回 null 未知服务名返回 null，调用方漏判再次 NPE 未知名字快速失败抛异常，或显式返回 Optional
