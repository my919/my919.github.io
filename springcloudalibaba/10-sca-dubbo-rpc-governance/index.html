发表于 2026-05-17 更新于 2026-10-29 分类于 SpringCloudAlibaba 本文字数： 6.1k 阅读时长 ≈ 6 分钟

第九章：Dubbo：RPC 与服务治理扩展

概念基础

Apache Dubbo 是一款 Java RPC 与服务治理框架：

  1. 本质是 RPC：消费方像调用本地方法一样调用远端接口，通过注册中心发现 Provider 地址，通信走二进制协议而非文本 HTTP。
  2. 协议与治理：支持 Triple（tri）、经典 dubbo 协议等，内置负载均衡、集群容错、超时重试等服务治理能力。
  3. 与 HTTP + OpenFeign 的取舍：Dubbo 更适合高频、低延迟的内部核心调用；OpenFeign 更贴近 REST 生态，易与 Gateway、Swagger 统一。
  4. 本仓库现状：cloud 当前未集成 Dubbo。服务间调用使用 OpenFeign（如 cloud-order → cloud-stock），注册发现使用 Nacos，见 第七章：订单下单与库存扣减：Feign 链路与 Seata 全局事务、第二章：集成 Nacos：注册中心与配置中心。
  5. 本文定位：供与 SCA 同栈 时扩展参考，说明「如果要用该怎么加、要注意什么」。

先看 Dubbo 的角色与交互：

架构说明

Dubbo 核心架构角色

角色 职责 本场景对应
Provider 暴露 RPC 服务，向注册中心注册元数据 cloud-stock（若迁移）
Consumer 订阅服务列表，生成接口代理发起调用 cloud-order（若迁移）
Registry 地址注册与订阅推送 复用 Nacos 3.x
Monitor（可选） 调用统计、拓扑展示 Dubbo Admin

Dubbo 3.3 默认走应用级服务发现：注册的是「应用名 → 实例列表」，接口与应用的映射存元数据中心；相比 2.x 的接口级注册（每个接口一条记录），注册中心数据量随接口数膨胀的问题被根治，与 Spring Cloud 的服务模型天然对齐——这也是 Dubbo 3.x 能直接复用 Nacos 服务列表与 Gateway 生态的前提。

Triple 协议

Dubbo 3.3 主推 Triple（tri）：

  • 基于 HTTP/2，兼容 gRPC 协议，天然穿透网关、负载均衡器与 Service Mesh；
  • 支持流式调用（client/server/bidirectional streaming）与多路复用，长连接上可并发大量请求；
  • 跨语言友好：HTTP/2 生态让非 Java 端（Go、前端经 grpc-web）可直接调用。

经典 dubbo 协议（私有 TCP + Hessian2）单连接吞吐略高，但跨语言与基础设施支持弱。新工程直接选 tri；存量 dubbo 协议可通过 dubbo.protocol.name 双注册平滑过渡。

负载均衡

Consumer 拿到多个 Provider 实例后按策略选择：

策略 说明 适用
random（默认） 加权随机 大多数场景
roundrobin 加权轮询 实例性能相近
leastactive 最少活跃调用数 长耗时接口，让空闲实例多承担
consistenthash 一致性哈希（按参数） 会话亲和：同参数打到同实例
shortestresponse 最短响应时间优先 对延迟敏感的核心链路

也可按接口粒度覆盖：@DubboReference(loadbalance = "roundrobin")。权重在 Provider 侧设置（dubbo.provider.weight 或注册中心动态调整），配合同可用区优先（dubbo.consumer.cluster=zoneaware 相关配置）减少跨机房调用。

集群容错

调用失败后的处理策略：

策略 行为 风险/适用
failover（默认） 失败自动换实例重试（默认 2 次） 非幂等接口慎用——下单扣库存会重复执行
failfast 只调一次，失败即抛错 写操作、非幂等接口必选
failsafe 失败吞异常返回空 日志、审计类调用
failback 失败后异步定时重发 通知类场景
broadcast 广播全部实例，逐个调用 本地缓存刷新

对应到下单链路：若改用 Dubbo，扣库存接口必须配 failfast 或先做好幂等——否则网络抖动引发的自动重试可能造成重复扣减，而调用方拿到的只是超时异常。

泛化调用

没有 Provider 的接口 jar 也能调用（网关、测试平台、排障工具常用）：

要点：方法名、参数类型签名、参数值三要素手工指定，返回值是 Map/原生类型而非强类型对象。泛化调用是 Dubbo 网关（Apache ShenYu、Higress 等）把 HTTP 请求转发为 Dubbo 调用的底层机制——想让 cloud-gateway 直接代理 Dubbo 服务时，本质就是引入这层泛化。

服务治理速查

能力 配置示例 说明
超时 dubbo.consumer.timeout: 3000 全局默认，接口级 @DubboReference(timeout=...) 覆盖
重试 dubbo.consumer.retries: 0 幂等接口才可 >0

标签路由 Dubbo Admin 下发路由规则 按应用/参数分流到指定实例组

验证（独立 Demo）

  1. 按 Dubbo 快速开始 起 Provider/Consumer。
  2. Nacos 控制台除 Spring Cloud 服务外，可见 Dubbo 注册元数据。
  3. 压测对比 Feign 与 Dubbo 延迟（本仓库无现成对比脚本）。
  4. 治理面验证：调整 Provider 权重观察流量分布变化；断开一台 Provider 观察 failover/failfast 行为差异。

常见问题

Q：本仓库能否同时 Feign + Dubbo？
A：技术上可以分接口使用，但同一业务链路易维护成本高；未在 cloud 中验证。

Q：Dubbo 与 Seata？
A：需按 Dubbo + Seata 官方组合配置事务传播；当前 cloud 的 @GlobalTransactional 基于 Feign。

Q：Nacos 地址用 30010 还是 8848？
A：与 Spring Cloud 一致：对外 NodePort 用 30010；本地 Docker 用 8848。

Q：Dubbo 注册的服务会出现在 Nacos 服务列表里吗？
A：会——3.3 应用级发现注册为普通服务（应用名），与 Spring Cloud 服务同列表可见；接口元数据在「服务详情 → 元数据」中查看。

Q：已有 Feign 接口能直接改成 Dubbo 吗？
A：不能直接改：Feign 接口没有 Dubbo 所需的接口 jar 契约，需要抽出 xxx-api 模块（只含接口 + DTO），Provider 实现、Consumer 引用都依赖它；DTO 必须实现 Serializable 且避免 Lombok 生成的构造器差异导致反序列化失败。

Q：泛化调用返回的 Map 字段丢了类型怎么办？
A：Dubbo 3.3 泛化默认做类型擦除到 Map；需要强类型时用 generic: "nativejava" 或 bean 模式，或在 Consumer 侧引入 api jar 改用常规调用。

Q：Dubbo 的权重和 Nacos 控制台权重冲突吗？
A：不冲突但生效层级不同：Nacos 权重作用于服务发现列表下发，Dubbo 权重作用于 RPC 层负载均衡选择；建议只用其中一种（推荐 Dubbo 侧），避免双重加权导致流量分布难预测。

Q：Triple 协议端口和 Spring MVC 端口冲突吗？
A：不冲突，tri 默认从 50051 起（port: -1 时自增），与 Web 的 8001–8004 各占各的；防火墙/NodePort 需单独放行 RPC 端口段。

Q：Dubbo 调用能接 Sentinel 限流吗？
A：能，dubbo-spring-boot-starter 体系有 Sentinel 适配（sentinel-apache-dubbo3-adapter），Provider/Consumer 双侧均可按「接口:方法」资源名配流控熔断。
