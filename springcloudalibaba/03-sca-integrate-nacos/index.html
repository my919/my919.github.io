第三章：集成 Nacos：注册中心与配置中心

发表于 2026-05-17 更新于 2026-10-25 分类于 SpringCloudAlibaba 本文字数： 11k 阅读时长 ≈ 10 分钟

第三章：集成 Nacos：注册中心与配置中心

概念基础

  1. Nacos（Naming + Configuration service）是阿里开源的注册中心 + 配置中心一体化组件，本工程用它同时完成服务发现与远程配置两件事。
  2. 注册中心解决「服务在哪」：服务启动后把实例（IP + 端口）注册进去并心跳保活，消费方（如 Gateway 的 lb://）订阅服务列表实现动态寻址，扩缩容无需改任何配置。
  3. 配置中心解决「配置共享与动态化」：公共配置以 DataId 为单位托管，多环境用 namespace / Group 隔离，支持控制台编辑、监听查询、历史版本回滚。
  4. SCA 2025.1 接入方式：经 nacos-discovery / nacos-config starter 接入，配置必须走 spring.config.import（bootstrap 已移除），optional: 前缀保证 Nacos 不可用时仍可本地启动。
  5. 为什么选 Nacos：与 Spring Cloud Alibaba 同栈兼容、临时实例默认 AP 模式高可用、控制台开箱即用，是 SCA 微服务体系默认的基座组件。

概述

Nacos 在本项目中同时承担 服务注册发现 与 配置中心。版本线：SCA 2025.1.0.0 + Spring Boot 4，客户端通过 spring-cloud-starter-alibaba-nacos-discovery 与 nacos-config 接入；不再使用 spring-cloud-starter-bootstrap。

默认地址：192.168.1.22:30010（K8s NodePort，容器内一般为 8848）。

注册发现

fail-fast: false：Nacos 暂不可用时仍允许进程启动（适合本地先起应用后起 Nacos）。

实例模型与健康检查

维度 临时实例（默认） 持久实例
健康判定 客户端心跳保活（默认 5s 一次），超 15s 标记不健康、30s 剔除 Server 端主动探测（TCP/HTTP）
一致性 AP 模式，注册表在内存，牺牲一致保可用 CP 模式（Raft），数据落盘
适用 绝大多数微服务 MySQL、DNS 等「不能误剔除」的基础设施

临时实例宕机时，宁可列表中短暂残留并由调用方容错，也不让注册中心自身成为瓶颈——这是微服务默认选 AP 的原因。声明持久实例：spring.cloud.nacos.discovery.ephemeral: false。

集群与权重

  • 集群划分：spring.cloud.nacos.discovery.cluster-name（如 HZ / SH），配合 NacosRule 负载均衡可实现同集群优先调用，减少跨机房流量。
  • 权重：控制台可对实例设置 0~1 权重，权重为 0 即摘流——发布前先在控制台把老实例权重归零，配合连接排空实现优雅下线。
  • 元数据：spring.cloud.nacos.discovery.metadata.* 携带自定义键值（如 version: v2），配合自定义负载均衡或 Gateway 谓词实现灰度路由。

优雅上下线时序



sequenceDiagram
  participant Ops as 运维
  participant N as Nacos
  participant GW as Gateway / Consumer
  participant App as 目标实例
  Ops->>N: 实例权重置 0（或下线）
  N-->>GW: 推送最新实例列表
  GW->>GW: 不再路由到该实例
  Ops->>App: 等待存量请求处理完，再停进程
  App->>N: 注销（或心跳超时剔除）

直接 kill 进程依赖心跳超时剔除（最长约 30s），期间 Consumer 仍可能打到已死实例；先摘流再停机是发布标配动作。

配置中心（2025.1 必配 import）

namespace / Group / DataId 三元组

Nacos 配置的唯一定位是 namespace + Group + DataId 三元组：

维度 用途 本仓库
namespace 环境级隔离（dev/test/prod 互不可见） 默认 public（生产建议拆分）
Group 业务/用途分组 DEFAULT_GROUP
DataId 配置文件名 application.yml、application-datasource.yml 等

生产建议：dev / test / prod 各建一个 namespace，客户端用 spring.cloud.nacos.config.namespace 指向对应命名空间 ID（一串 UUID，不是名称），杜绝测试配置误发生产；注册发现侧同理（discovery.namespace），两个 namespace 可保持一致。

配置监听与灰度发布

  • 监听机制：2.x/3.x 客户端与 Server 走 gRPC 长连接，配置变更即时推送；控制台「监听查询」可看到已订阅的客户端 IP。
  • 动态刷新：@ConfigurationProperties 与 @RefreshScope Bean 自动生效；普通 @Value 字段需加 @RefreshScope；数据源、Seata 等基础设施项建议重启生效。
  • 灰度（Beta）发布：编辑配置时可按 IP 列表 先对少量实例下发灰度内容，验证后全量——适合数据源参数、功能开关的试点。
  • 历史版本：每次发布留存历史版本，误改可在控制台一键回滚。

监听原理与 @RefreshScope 示例详见 第二章：Spring Cloud 多环境配置与 Nacos：Profile 与 config.import 分层。

扩展配置与共享配置

除 spring.config.import 逐个声明外，SCA 还提供两组「约定式」配置入口：

入口 语义 优先级
shared-configs 多应用共享的公共配置 较低
extension-configs 当前应用的扩展配置（下标越大优先级越高） 高于 shared
spring.config.import 显式声明，推荐主用 由链上位置决定

两种方式不要混用同一 DataId，避免同一属性在多处声明、排查时找不到生效点；本仓库统一只用 spring.config.import。

本仓库需要的 DataId

DataId Group 引入模块 说明
application.yml DEFAULT_GROUP 全部（dev/test/prod） 公共覆盖（日志、开关等）
application-datasource.yml DEFAULT_GROUP cloud-order、cloud-stock 数据源；与 classpath 同名
application-seata.yml DEFAULT_GROUP cloud-order、cloud-stock Seata；可复制 config/nacos-application-seata.yml

spring.config.import 里写的是 optional:nacos:application-datasource.yml，则控制台 Data ID 必须完全一致（含 .yml 后缀），不要写成 application-datasource 或 application-datasource.yaml（除非 import 也改后缀）。

前置条件

组件 本仓库 / 建议版本 说明
SCA BOM 2025.1.0.0 根 pom.xml
nacos-client 3.1.1（BOM 管理） 与 Server 3.1.x 同世代
Nacos Server 3.1.x（自建示例 v3.1.1） 本仓库集群 NodePort 30010 → 8848
JDK 21 各微服务模块

Nacos 3.x 端口：业务配置 server-addr 仍写 8848 所在地址（本仓库为 192.168.1.22:30010）；控制台常为 8080（路径 /index.html），与 2.x 单端口习惯不同。客户端 gRPC（如 9848）由 SDK 处理，一般无需在业务 yml 手写。

鉴权：自 2.2.1 起镜像需配置 NACOS_AUTH_TOKEN、NACOS_AUTH_IDENTITY_KEY、NACOS_AUTH_IDENTITY_VALUE，勿用文档占位符上生产。

Nacos 3.x 相对 2.x 的变化要点

变化 2.x 3.x 对业务的影响
控制台端口 与客户端共用 8848（/nacos 路径） 独立 8080（/index.html） K8s NodePort、防火墙需分别映射
鉴权 可关闭、token 可空 默认强鉴权，三项必填 空 token 无法启动，部署清单必须补全
通信协议 gRPC 为主 gRPC 为主（9848/9849） 防火墙除 8848 外需放行 gRPC 端口
数据模型 namespace/group/dataId 相同 无迁移成本，配置可平滑导入
Admin API /nacos/v1/... 独立 admin 端口与 API 路径 运维脚本中的 OpenAPI 需按 3.x 文档改写

升级路线：先升 Server 到 3.1.x（2.x 客户端可继续工作一段时间做过渡），再随 SCA BOM 升级客户端到 3.1.1；不要长期混用 2.x Server + 3.x 客户端。

客户端容灾与本地快照

Nacos 不可用时业务不至于瘫痪，靠的是多层兜底：

  1. 启动期：optional: 前缀 + fail-fast: false，拉取失败退回 classpath 本地配置。
  2. 运行期：客户端把已拉取的配置与已订阅的服务列表写入本地快照（默认 ${user.home}/nacos/config、${user.home}/nacos/naming 下），Server 宕机后重启进程可加载最后一次成功的快照。
  3. 心跳重试：注册失败按退避策略重试，Server 恢复后自动补注册。

注意快照是容灾而非常态：长期以快照运行意味着 Nacos 集群已不可用，应尽快恢复；不要把快照目录提交进 Git。

集群部署要点（生产）

单机只够开发用，生产至少 3 节点：

要点 说明
节点数 奇数（3 或 5），Raft 选主需要多数派
存储 全部节点指向同一外置 MySQL，Derby 仅限单机
入口 节点前挂 SLB/Nginx，业务 server-addr 填 VIP 而非单节点 IP
端口 8848（客户端）、9848/9849（gRPC）、8080（控制台）按需在 LB 上暴露
数据备份 备份 MySQL 库即可，配置历史与命名空间全在其中

本仓库用 K8s NodePort 暴露单节点属开发形态；上生产请切换为集群 + 外置 MySQL + LB。

常见问题

Q：报错 No spring.config.import set？
A：SCA 2025.1 强制要求。在 application-dev.yml 增加 spring.config.import 的 nacos: 项（见上文）。

Q：服务注册成功但网关 503？
A：检查 gateway 的 lb://服务名 与 Nacos 中 serviceId 是否一致（本仓库为小写 cloud-order 等）；discovery.locator.lower-case-service-id: true 已开启。

Q：Nacos 3.x 与 2.x 客户端兼容性？
A：SCA 2025.1 发布说明建议 Nacos Server 3.1.0+；若用 2.x 服务端，以实际集群文档为准。

Q：控制台已建配置，应用仍用本地 jdbc？
A：检查 DataId/Group/命名空间；确认 spring.config.import 含对应 nacos: 项且已重启；optional: 时拉取失败会静默 fallback 到 classpath。

Q：能否用 application-dev.yml 作为 DataId？
A：可以，但须在 import 中写 optional:nacos:application-dev.yml，与本仓库约定的 application.yml 等不同；团队需统一命名，避免每人一个 DataId。

Q：临时实例与持久实例怎么选？
A：微服务默认临时实例（心跳、AP）；MySQL、DNS 等基础设施类注册用持久实例（Server 探测、CP 落盘），通过 spring.cloud.nacos.discovery.ephemeral: false 声明。

Q：发布时如何避免流量打到正在重启的实例？
A：先在控制台把实例权重置 0 或下线，等存量请求处理完再停进程；直接 kill 依赖心跳剔除（最长约 30s），期间可能产生少量失败。

Q：namespace 填了名称却拉不到配置？
A：spring.cloud.nacos.config.namespace 要填命名空间的 ID（控制台命名空间列表里那串 UUID），不是显示名称。

Q：多实例部署 Gateway 后路由不生效？
A：确认 Gateway 自身也注册到了同一 namespace；lb:// 只能解析本 namespace 内的服务，跨 namespace 不可见。
