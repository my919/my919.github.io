1. 概念说明：为什么必须限流降级

三个为什么：

Sentinel 与 Hystrix 对比：Sentinel 是阿里开源（活跃维护），资源粒度更细、控制台可视化、规则动态生效——新项目选 Sentinel。

两种流控模式怎么选：

模式 适用 为什么
QPS 接口并发大、处理快 直接按流量上限保护
并发线程数 接口耗时波动大 线程数 = 真实占用，防线程池耗尽

4.3 热点参数限流（防热 key 打挂）

为什么需要热点限流：普通 QPS 限流是”整个接口 100 QPS”——一个爆款商品独占 100，其他商品全被误伤。热点限流按参数维度，只限爆款。

熔断状态机（为什么能”自动恢复”）：

为什么 minRequestAmount 要设 20：请求太少时统计不稳定（2 个请求 1 个慢就熔断，误伤）——样本量不足不熔断。

6. 网关限流（入口处兜底）

为什么网关层也要限流：服务层限流时流量已经打到服务（占用了线程/连接）——网关层把超量流量挡在入口，服务层只处理能承受的量。

9. 典型案例：秒杀下单链路的端到端流量防护

问题背景：秒杀活动开始瞬间，下单接口瞬时涌入 5 万 QPS，而全链路压测容量只有 2000。DB 连接池打满、订单服务 Full GC，连带把共享同一 MySQL 的用户服务也拖垮——没有限流降级的系统等于裸奔。

方案（分层设防，阈值来自压测）：

层 规则 阈值依据 兜底
网关 路由流控（资源=路由 id） 压测容量 2000 429 JSON
服务 QPS + 线程数双规则 容量 × 0.75 留余量 “系统繁忙”
热点 ParamFlowRule 按 activityId 单活动缓存可支撑量 排队提示
熔断 慢调用比例（RT>500ms，比例 50%） 下游 SLA 快速失败

踩坑点：

  1. 只压测了”限流生效”，没验证被限流用户的体验——上线后发现 429 页面没有重试引导，转化率跌了 30%；降级文案与产品共同评审。
  2. minRequestAmount 设成 1，发布抖动期几个慢请求就把下单熔断 10 秒——样本量不足时不熔断。
  3. 阈值拍脑袋定 5000，没做压测——真到 5 万 QPS 时网关自己先被打挂；所有阈值必须来自压测数据再乘安全系数。
  4. 热点规则参数传了 ActivityQuery 对象，paramIdx 取不到值静默失效——热点参数只支持基本类型/String。

10. 常见误用与陷阱

坑 现象/后果 解法
规则只在控制台配置 服务/控制台重启后规则全部丢失 Nacos 数据源持久化，控制台只做临时调参
blockHandler 写在另一个类但没配 blockHandlerClass 报错找不到方法，兜底不生效 指定 blockHandlerClass 且方法为 public static
慢接口只用 QPS 限流 RT 一涨线程照样打满，QPS 没超也雪崩 QPS + 并发线程数双规则
熔断 minRequestAmount 设太小 低峰期一两个慢请求就误熔断 ≥ 20，样本不足不判断
热点参数传对象 paramIdx 取不到值，规则静默失效 热点参数用基本类型/String，对象先取出字段
fallback 与 blockHandler 混为一个方法 分不清是被限流还是业务异常，排障困难 两个方法分开：限流提示 vs 异常降级+告警
网关限流资源名写错 规则配了但完全不生效 网关流控资源名 = 路由 id，逐一核对
