1.2 网关与 Sentinel 核心概念

网关 = 系统的唯一入口，集中处理横切关注点：

职责 说明
路由转发 按路径/Header 路由到服务
统一鉴权 JWT 校验一次，后端不管
限流熔断 全局限流保护
灰度发布 按 Header/权重分流
日志审计 访问日志统一收集
跨域 CORS 统一配置

Spring Cloud Gateway 核心：Route（路由规则）+ Predicate（匹配条件）+ Filter（请求处理链）。

Sentinel：阿里开源的流量防护组件——限流（控制 QPS）、熔断（失败降级）、热点参数限流（防单 key 打爆）、系统保护（自适应）。

Sentinel 核心概念（30 秒理解）：

概念 含义
资源 被保护的对象（一个接口/一个方法）
规则 对资源的保护策略（流控/熔断/热点）
流控模式 QPS 限流 / 并发线程数限流 / 热点参数限流
熔断策略 慢调用比例 / 异常比例 / 异常数
降级 触发规则后返回兜底结果（不抛异常给用户）

Sentinel vs Resilience4j/Hystrix：

能力 Sentinel Resilience4j
限流 QPS ✅ 强 一般
热点参数限流 ✅ 独特 ❌
熔断 ✅ ✅
控制台可视化 ✅ ❌
规则持久化 ✅（Nacos） 代码配置

微服务生态内选 Sentinel（与 Nacos 集成好）；非 Spring 环境用 Resilience4j。

5.3 热点参数限流（防单商品打爆）

为什么需要热点限流：普通 QPS 限流是”整个接口 100 QPS”——一个爆款商品独占 100，其他商品全被误伤。热点限流按参数维度，只限爆款。

7. 网关限流（入口处兜底）

为什么网关层也要限流：服务层限流时流量已经打到服务（占用了线程/连接）——网关层把超量流量挡在入口，服务层只处理能承受的量。

13. 常见误用与陷阱

坑 现象/后果 解法
规则只在控制台配置 服务/控制台重启后规则全部丢失 Nacos 数据源持久化，控制台只做临时调参
blockHandler/fallback 签名不一致 兜底方法永远不触发，异常直接抛给用户 参数列表与原方法一致，末尾追加 BlockException/Throwable
blockHandler 写在另一个类 报错找不到方法 指定 blockHandlerClass 且方法为 public static
@SentinelResource 打在同类内部调用 不走 AOP 代理，限流熔断静默失效 从外部 Bean 调用，或注入自身代理（AopContext）
慢接口只用 QPS 限流 RT 一涨线程照样打满 QPS + 并发线程数双规则
熔断 minRequestAmount 设太小 低峰期一两个慢请求就误熔断 ≥ 20，样本不足不判断
热点参数传对象 paramIdx 取不到值，规则静默失效 热点参数用基本类型/String
网关过滤器里做阻塞操作 WebFlux 事件循环线程被卡，吞吐暴跌 用 reactive 客户端，重逻辑下沉到下游
fallback 把所有异常都吞掉 真实 bug 被降级掩盖数周 fallback 里必须记录异常日志+告警
网关限流资源名写错 规则配了但完全不生效 网关流控资源名 = 路由 id，逐一核对
