第九章：集成 Spring Cloud Alibaba：组件总览与多模块搭建

发表于 2026-05-17 更新于 2026-10-25 分类于 SpringCloudAlibaba 本文字数： 7k 阅读时长 ≈ 6 分钟

第九章：集成 Spring Cloud Alibaba：组件总览与多模块搭建

概念基础

Spring Cloud Alibaba（SCA） 是 Spring Cloud 生态的阿里实现，在 Spring Cloud 之上提供 Nacos、Sentinel、Seata、RocketMQ 等集成：

  1. 解决什么问题：Spring Cloud 只定义了注册发现、配置管理、熔断限流、分布式事务等标准接口；SCA 提供这些接口的落地实现，让「API → 实现」通过引入 starter 即可完成。
  2. 版本对齐靠 BOM：SCA、Spring Cloud、Spring Boot 三者版本矩阵严格绑定，统一由 spring-cloud-alibaba-dependencies BOM 管理，避免子模块各写版本号引发冲突。
  3. 本仓库形态：cloud 为 Maven 多模块 工程（非 Gradle 演示项目），已落地 Nacos、Sentinel、Seata、Gateway、OpenFeign；未引入 Dubbo、RocketMQ（见 第十章：Dubbo：RPC 与服务治理扩展、第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展 作扩展阅读）。
  4. 2025.1.x 关键变更：已移除 bootstrap，必须用 spring.config.import 连接 Nacos（详见 第三章：集成 Nacos：注册中心与配置中心）。
  5. 学习路径：本章是全景视图，各组件的细节分见本章小结表中的对应章节。

版本对齐关系

SCA、Spring Cloud、Spring Boot 三者必须按官方矩阵配套，随意混搭会出现 NoSuchMethodError、自动配置失效等隐蔽问题：

Spring Boot Spring Cloud SCA BOM 说明
4.0.x 2025.1.x 2025.1.0.0 本仓库线
3.5.x 2025.0.x 2025.0.0.x 上一代线
3.2.x 2023.0.x 2023.0.x.x 旧线（仍有维护）

BOM 再向下传递管理子组件版本：Nacos Client 3.1.1、Seata 2.5.0、Sentinel 1.8.9、RocketMQ 5.3.1——子模块不要手写这些组件的版本号。查最新对应关系以 SCA 版本说明 为准；升级小版本后必须回归下单链路 + Nacos 配置拉取两个用例。

组件协作关系

组合 协作点 注意事项
Gateway ↔ Nacos lb:// 解析实例 Gateway 最后启动，等下游注册完成
Gateway ↔ Sentinel 按路由 ID 配置流控 需 spring-cloud-alibaba-sentinel-gateway 适配包
Feign ↔ Sentinel 下游调用成独立资源 feign.sentinel.enabled=true
Feign ↔ Seata XID 经请求头传播 starter 自动装配，无需手写
Seata ↔ 动态数据源 关闭自动代理改 dynamic.seata 见 第六章：集成 Seata：AT 模式分布式事务
所有模块 ↔ Nacos Config spring.config.import 拉取 import 链顺序即覆盖语义

模块职责与启动顺序

模块 端口 职责 关键依赖
cloud-gateway 9000 统一入口、路由、限流 gateway、loadbalancer、sentinel
cloud-user 8001 用户域 web、nacos、sentinel
cloud-app 8002 BFF 聚合 web、openfeign、nacos
cloud-order 8003 订单域、全局事务发起 web、openfeign、seata、mybatis-flex
cloud-stock 8004 库存域、分支事务参与 web、seata、mybatis-flex
cloud-common — 公共配置/模型/常量 不含启动类

启动顺序：Nacos → Seata TC → Sentinel Dashboard → cloud-stock / cloud-order（业务服务）→ cloud-gateway（最后，等下游已在注册中心可见）。

多副本部署时，Gateway 与业务服务均为无状态节点，直接扩副本数即可；Seata TC 与 Nacos 属于有状态基座，扩缩容须按各自集群文档操作，不能与业务服务等同对待。

验证

  1. mvn verify 通过（含 Spotless）。
  2. Nacos 服务列表出现 cloud-order、cloud-stock 等。
  3. POST http://127.0.0.1:9000/order/place 成功且库存变化。
  4. Sentinel 控制台可见客户端（需先有流量）。

扩展路径：引入新组件的姿势

以「新增组件」为例的通用步骤（Dubbo / RocketMQ 均适用）：

  1. 父 POM 锁定版本：优先用 SCA BOM 已管理的 starter；BOM 没有（如 Dubbo 3.3.x）再单独 import 其 BOM，禁止子模块直接写 <version>。
  2. 子模块最小依赖：只在需要的模块加 starter，例如消息只在 order 用就只加给 order。
  3. 配置入分层：公共项进 cloud-common 的 yml，环境差异进 application-{profile}.yml 或 Nacos DataId。
  4. 注册与配置对齐 Nacos：注册中心复用现有集群，namespace/group 与业务配置约定一致。
  5. 回归基线：新增组件后必须重跑 POST /order/place 成功 + 回滚两个用例，确认未破坏现有 Feign/Seata 链路。
  6. 文档同步：在本章「已集成 vs 未集成」表中更新状态，避免后来者按过期信息排查。
扩展组件 切入章节 关键注意
Dubbo 3.3 第十章：Dubbo：RPC 与服务治理扩展 与 Feign 并存时分接口隔离，勿混用同一业务链路
RocketMQ 5.3 第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展 事务消息与 Seata 全局事务的边界需单独设计

常见问题

Q：能否用 Boot 3.5 + SCA 2025.0.x？
A：可以，但与本仓库 Boot 4 + SCA 2025.1.0.0 不同线；勿混 BOM。

Q：从 Gradle 教程迁移到本仓库？
A：依赖写法改为 Maven；build.gradle.kts 中的 BOM 与上文 pom.xml 等价；配置仍用 application.yml + spring.config.import。

Q：RocketMQ / Dubbo 如何加？
A：参考 第十一章：Spring Cloud 集成 RocketMQ：异步消息与事件驱动扩展、第十章：Dubbo：RPC 与服务治理扩展 在子模块增加 starter，并单独建 DataId / 注册配置，勿与现有 Feign 链路混淆。

Q：升级 SCA 小版本要注意什么？
A：查 GitHub Releases 中 Nacos/Seata/Sentinel 子版本是否变化，并回归下单与 Nacos 配置拉取。

Q：新增模块（如 cloud-pay）要动哪些公共配置？
A：pom.xml 登记模块；若参与分布式事务，import 链加 application-seata.yml 并在业务库建 undo_log；端口避开 8001–8004/9000 已用段，并在网关补一条路由。

Q：为什么 cloud-common 不含启动类却要放 yml？
A：application-*.yml 作为 classpath 资源被各模块 optional:classpath: 引用，是「配置分层」的物理载体；公共常量、模型同理，避免五份复制。

Q：BOM 锁定了版本还能单独升级某个组件吗？
A：可以，在对应模块 dependencyManagement 或依赖上显式声明更高版本覆盖 BOM，但要承担兼容性自测责任；优先跟随 BOM 整体升级。

Q：为什么 Sentinel 要单独在根 POM 声明 sentinel.version？
A：Boot 4 升级了 Jackson 3 等底层，旧版 Sentinel 控制台/客户端存在序列化不兼容，需要 1.8.9 这一适配版本；等 SCA BOM 跟进后即可删除该覆盖。

Q：多模块工程里公共依赖（如 lombok、mapstruct）放哪？
A：放 cloud-common 或根 POM 的 dependencyManagement 中统一管理版本，子模块按需引用；业务无关的工具类才进 cloud-common，避免把领域代码塞进公共包。

Q：本地只想跑通下单链路，最少要起哪些进程？
A：Nacos + Seata TC + cloud-stock + cloud-order 四个即可；Gateway、Sentinel Dashboard 可跳过，直连 http://127.0.0.1:8003/order/place 验证，见 第八章：订单下单与库存扣减：Feign 链路与 Seata 全局事务。

Q：各章文档与代码不一致时以哪个为准？
A：以仓库代码与 application-*.yml 实际内容为准；文档滞后于代码属正常现象，发现偏差优先看 Git 提交记录，再决定改文档还是回退代码。
