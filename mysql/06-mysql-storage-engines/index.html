第五章：MySQL 存储引擎

发表于 2026-05-03 更新于 2026-10-29 分类于 MySQL 深入 本文字数： 5.6k 阅读时长 ≈ 5 分钟

第五章：MySQL 存储引擎

概念基础

存储引擎是 MySQL 「表数据如何存、如何取」的可插拔实现：

  1. 分层架构的产物：Server 层负责 SQL 解析、优化、权限；引擎层负责数据在磁盘与内存上的组织——索引结构、事务、锁、崩溃恢复都由引擎决定；同一份表结构，换引擎行为完全不同。
  2. InnoDB 是唯一默认答案：支持 ACID 事务、行级锁、MVCC、崩溃恢复（redo / undo）、聚簇索引与外键；官方默认且推荐，第五章讲的 B+ 树与回表，说的就是 InnoDB 的组织方式。
  3. MyISAM 是历史遗产：表级锁、不支持事务、崩溃安全性弱，只存在于老系统与只读库中；新业务一律避开——它也解释了第三章「表锁并发差」的历史背景。
  4. 换引擎不解决性能问题：性能瓶颈优先从索引、SQL 写法、事务与连接设计入手（第三、四、五章的内容）；引擎选型是「事务要不要」的问题，不是「快不快」的问题。
  5. 插件式带来专用选择：ARCHIVE（冷归档压缩）、CSV（数据管道交换）、BLACKHOLE（写入即弃的中继）、NDB（分布式集群）各有专属场景，是否可用以 SHOW ENGINES 为准。

先看怎么查看与确认当前引擎：

一、如何查看支持的引擎与默认值

建表未写 ENGINE 时使用 default_storage_engine（一般为 InnoDB）。

二、InnoDB（事实上的唯一首选）

维度 说明
事务 ACID；COMMIT / ROLLBACK、崩溃恢复（redo / undo）。
锁与并发 以行锁为主；隔离级别与间隙锁等见 MySQL锁详解.md。
索引与数据 聚簇索引即主键 B+ 树，二级索引叶子存主键；详见 MySQL索引与性能优化.md。
外键 支持 FOREIGN KEY（与 MySQL.md 中 DDL 一致）。
适用 OLTP、绝大多数业务库；官方默认与推荐。

InnoDB 架构深入：内存与磁盘的协作

InnoDB 的高性能不是来自单一技巧，而是内存结构 + 磁盘结构 + 后台线程三者协作的结果。理解下面四个组件，才能解释「为什么写入快、为什么崩溃不丢数据」。

1. 缓冲池（Buffer Pool）

  • 定位：InnoDB 最大的内存区域，缓存数据页与索引页（默认页大小 16KB）；读请求先查缓冲池，命中则零磁盘 I/O。
  • ** sizing**：专用库服务器常配物理内存的 50%–70%：
  • 淘汰策略：改良版 LRU——新读入的页先放在「中点」（约 5/8 处），全表扫描的页不会立刻挤掉热数据，由 innodb_old_blocks_pct / innodb_old_blocks_time 控制。
  • 脏页刷盘：修改先在内存中进行，页变「脏页」后由后台线程异步刷回磁盘；这就是写入快的第一层原因。

2. Change Buffer（写缓冲）

  • 解决的问题：二级索引页的更新是随机 I/O——更新一行可能要改散落在磁盘各处的多个索引页。
  • 做法：若目标二级索引页不在缓冲池，先把变更记录到 Change Buffer（缓冲池的一部分），稍后在页被读入内存时再合并（merge），把随机写变成顺序写。
  • 限制：只对非唯一二级索引有效；唯一索引必须立刻读页做唯一性检查，无法缓冲。
  • 适用场景：写多读少、二级索引多的表（如日志表）；8.0 起由 innodb_change_buffering 控制（默认 all）。

3. Doublewrite Buffer（双写缓冲）

  • 解决的问题：页部分写（partial page write）——16KB 的页在操作系统 4KB 扇区下可能只写了一半就宕机，redo log 无法修复不完整的页。
  • 做法：刷脏页时先把页顺序写入共享表空间的 doublewrite 区（2 份，约 2MB×2），确认成功后再写回数据文件；崩溃恢复时若发现数据文件页损坏，从 doublewrite 拷贝完整页再用 redo 前滚。
  • 代价与取舍：带来约一倍写入量，但 doublewrite 区是顺序写，实际开销通常 <10%；严禁为追求性能关闭（innodb_doublewrite=ON 默认）。

4. 自适应哈希索引（Adaptive Hash Index, AHI）

  • InnoDB 观察到某些索引值被频繁等值访问时，自动在内存中为其建立哈希索引，把 B+ 树的 O(log n) 查找降为 O(1)。
  • 全自动：由 innodb_adaptive_hash_index 控制（默认 ON），无需人工干预；高并发下 AHI 的互斥锁偶成瓶颈，可通过 SHOW ENGINE INNODB STATUS 的 SEMAPHORES 段观察，必要时关闭。

5. Redo 与 Undo 的分工回顾

日志 作用 物理/逻辑
Redo Log（ib_logfile / #innodb_redo） 崩溃恢复：保证已提交事务不丢（WAL，先写日志再写页） 物理日志，记录「页上做了什么修改」
Undo Log MVCC 与回滚：存旧版本行，支撑快照读与事务回滚 逻辑日志，记录「如何改回去」

一句话：缓冲池让读快，change buffer 让二级索引写快，doublewrite 保证页完整，redo 保证不丢，undo 支撑 MVCC——这套组合拳就是 InnoDB 的全部底气。

三、MyISAM（ legacy，新业务避免）

维度 说明
事务 不支持事务与崩溃安全意义上的 InnoDB 同级别恢复。
锁 表级锁，写多读少场景易成为瓶颈。
索引 数据与索引布局与 InnoDB 不同；无聚簇主键同义实现。
典型遗留场景 老系统、只读库、部分空间索引历史用法；新表请勿选用。

InnoDB 与 MyISAM 逐项对比

维度 InnoDB MyISAM
事务 ✅ ACID，支持提交/回滚 ❌ 不支持
锁粒度 行锁（锁索引） 表锁，写并发极差
MVCC ✅ 快照读不加锁 ❌ 无
聚簇索引 ✅ 数据随主键组织 ❌ 数据与索引分离（堆表），无回表概念
崩溃恢复 ✅ redo/undo 自动恢复 ❌ 宕机后易损坏，需 REPAIR TABLE
外键 ✅ 支持 ❌ 解析但忽略
全文索引 5.6+ 支持 支持（历史优势已消失）
COUNT(*) 无 WHERE 需扫描（MVCC 代价） O(1) 直接读计数器（带条件同样要扫）
文件布局 .ibd（独立表空间） .MYD（数据）+ .MYI（索引）

一句话：MyISAM 仅在「只读、无事务、可接受损坏后重建」的极端场景有微弱优势；8.0 起系统表已全部迁到 InnoDB，MyISAM 事实上进入维护状态。

四、MEMORY（内存表，谨慎）

  • 数据驻内存，进程崩溃或重启后易失；容量受 max_heap_table_size 等限制。
  • 曾用于临时高速缓存；现代实践更常见 Redis 或 InnoDB + 足够内存 + 合理索引。

五、其它引擎（知道名字即可）

引擎 一句话
ARCHIVE 高压缩追加存储，适合冷归档、很少更新。
CSV 以 CSV 形式存文件，多用于导入导出管道，非通用 OLTP。
BLACKHOLE 写入即丢弃，有时用于复制拓扑中的「中继」等特殊场景。
NDB（MySQL Cluster） 分布式集群专用，与普通单机 InnoDB 运维模型不同。

具体是否编译进你的 mysqld，以 SHOW ENGINES 为准。

小众引擎的真实使用场景

ARCHIVE：以 zlib 高压缩存储，仅支持 INSERT / SELECT（不支持 UPDATE/DELETE，只能全表扫）。典型场景是审计日志、操作流水——写进去就不改、偶尔排查才读，压缩比常达 10:1。注意它不支持索引，查询基本靠扫。

CSV：每张表就是一个 .CSV 文件，可直接用 Excel / pandas 打开，也能被 LOAD DATA 直接消费。适合做异构系统间的数据交换管道：MySQL 导出 CSV 表 → 脚本直接读文件。同样无索引、无事务。

BLACKHOLE：写入即丢弃，但binlog 照常记录。经典用法是复制中继：在跨机房的从库链路中间放一台 BLACKHOLE 实例，本地不落盘、只负责把 binlog 转发给下游多个从库，节省磁盘并做拓扑分发。

NDB Cluster：内存 + 分布式 + 自动分片的共享无架构集群，与单机 InnoDB 是两套完全不同的运维体系，仅在电信级高可用场景使用，普通业务不要碰。

六、表空间管理（Tablespace）

InnoDB 的数据最终落在表空间文件里，理解它才能管好磁盘。

1. 独立表空间 vs 系统表空间

  • ON（推荐，默认）：每张表一个 表名.ibd 文件，存于库目录下；DROP TABLE 直接归还磁盘空间，碎片可单独 OPTIMIZE TABLE 回收。
  • OFF（历史）：所有表挤在 ibdata1 系统表空间，删表不缩文件，磁盘只涨不缩——这是老库 ibdata1 膨胀到几百 GB 的根因。

2. 通用表空间（General Tablespace，8.0+）

可把多张表集中到一个数据文件，便于按业务模块分盘（如报表表放 SATA 大盘、热点表放 NVMe）。日常单实例一般不用，多盘分层存储时才显式规划。

七、选型与迁移建议

  1. 新表一律 ENGINE=InnoDB，并显式 DEFAULT CHARSET=utf8mb4（与 MySQL.md 一致）。
  2. 发现 MyISAM 老表：评估后 ALTER TABLE … ENGINE=InnoDB（需在低峰窗口做；大表走 gh-ost / pt-online-schema-change 等在线 DDL 工具，属运维专题）。
  3. 不要用 ENGINE 解决「性能问题」：优先索引、SQL、连接与事务设计。

本章小结
