第四章：MySQL 高级查询

概念基础

高级查询是超越单表 SELECT ... WHERE 的多表、分组、窗口类查询，核心是把拆开存的关系拼回来：

  1. 为什么数据要拆开存：关系模型按范式把业务拆成多张表（如 emp 员工表与 dept 部门表），避免重复存储；查询的本质就是用 JOIN / 子查询按关联字段把数据重新拼装——第一章建的表结构，在这里被「消费」。
  2. JOIN 的语义差异决定丢不丢数据：INNER JOIN 只保留两表都匹配的行；LEFT JOIN 保留左表全量、右表无匹配补 NULL。选错连接类型，统计结果会悄悄少行，是报表错乱的头号来源。
  3. 聚合把「多行」压成「一行」：GROUP BY 分组后才能用 COUNT / SUM / AVG；过滤顺序是 WHERE（分组前滤行）→ GROUP BY → HAVING（分组后滤组），颠倒位置直接报错或结果不对。
  4. MySQL 8.0+ 的两大武器：CTE（WITH） 把复杂查询拆成可读的「临时结果」并支持 RECURSIVE 查树；窗口函数在不减少行数的前提下做组内排名、累计——「每组 Top N」从此有了标准解法。
  5. 性能意识贯穿始终：判断存在性优先 EXISTS，合并结果优先 UNION ALL（免去去重排序），深分页 LIMIT 大 OFFSET 会越来越慢、生产改用键集分页——写法差异就是性能差异。

把复杂查询拆成可读的多段「临时结果」。

示例结果（dept_stat 中 dept_id 为 NULL 的分组与 dept 内连接时被过滤；AVG(salary) 在部门 2 仅统计非 NULL 薪资）：

递归 CTE（如组织架构、树路径）亦在 8.0+ 支持，需 WITH RECURSIVE。以下用部门树示例完整走一遍：

示例结果（lvl 为层级深度，path 为从根到当前节点的路径）：

id name lvl path

4 后端组 1 1>4

要点：递归 CTE 由锚点成员 + UNION ALL + 递归成员三段构成；递归成员必须引用 CTE 自身一次；默认递归上限 1000 层（cte_max_recursion_depth），深层树需调大；循环数据会导致打满上限报错，可加 WHERE t.lvl < 10 兜底。

4. 错位取值：LAG / LEAD（同比环比的标配）

LAG(col, n) 取当前行前 n 行的值，LEAD(col, n) 取后 n 行——不用自连接就能算「与上期相比」：

示例结果（首日无上期，prev_day / diff 为 NULL，可用 COALESCE 补 0）：

order_date day_amount prev_day diff
2024-06-01 100.00 NULL NULL
2024-06-10 200.50 100.00 100.50
2024-06-12 300.00 200.50 99.50
2024-06-15 50.00 300.00 -250.00

配套常用：

  • FIRST_VALUE(col) OVER w / LAST_VALUE(col) OVER w：取窗口首/尾值，如「与部门最高薪的差距」；
  • NTILE(4) OVER (ORDER BY salary DESC)：把结果均分成 4 桶编号，做四分位分析；
  • CUME_DIST() / PERCENT_RANK()：当前行在分区中的相对位置（0~1），「该员工薪资超过部门 80% 的人」这类口径。

十二、派生表合并与优化器行为（8.0+ 须知）

派生表（FROM 里的子查询）在 5.7 与 8.0 的默认处理不同，升级后慢查询常源于此：

版本 默认行为
5.7 派生表先物化成临时表，外层再查——大结果集代价高
8.0+ 优化器优先合并（derived merge）：把子查询展开进外层一起优化，能用上外层索引条件

结论：8.0 的派生表大多不再是性能毒药；但聚合类子查询仍会物化，数据量大时考虑 CTE + 预过滤 或拆两步查。

十三、EXPLAIN 进阶：FORMAT=JSON 与 ANALYZE（8.0.18+）

1. FORMAT=JSON：看成本明细

JSON 输出中重点看：

  • query_cost：优化器估算的总成本（选计划的直接依据，越小越好）；
  • rows_examined_per_scan / rows_produced_per_join：扫描与产出估算行数；
  • used_key_parts / attached_condition：索引实际用到的列、下推的过滤条件。

2. EXPLAIN ANALYZE：看真实执行（会真的跑查询！）

输出为 FORMAT=TREE 并附加每步真实数据：

  • actual time=首行耗时..全部行耗时、rows=实际行数、loops=执行次数；
  • 估算 rows vs 实际 rows 差距大（如估 1000 实扫 10）→ 统计信息过期 → ANALYZE TABLE emp; 刷新；
  • 注意：EXPLAIN ANALYZE 真实执行语句，DML 会改数据，只读环境外慎用。

3. 优化器提示（Optimizer Hints，温和干预）

使用原则：Hint 是最后手段，先用索引设计、统计信息、改写 SQL 解决；Hint 一旦写入代码，数据分布变化后可能从解药变毒药，必须配注释与复审。

十四、速查小结

场景 典型写法
多表关联 INNER JOIN / LEFT JOIN + ON
是否存在 EXISTS (SELECT 1 …)
合并结果 UNION ALL（优先）/ UNION
可读拆分（8.0+） WITH cte AS (...)
组内排名、累计（8.0+） ROW_NUMBER()、SUM() OVER (...)
聚合后过滤 GROUP BY + HAVING
分支与透视列 CASE WHEN
组内拼字符串 GROUP_CONCAT
分页 ORDER BY + LIMIT；大表慎用深 OFFSET

练习时可在测试库执行文首「示例数据」建表脚本，再逐段复制运行，对照各小节 「示例结果」 表格验算。

本章小结

要点 结论
连接语义 INNER JOIN 只留匹配行，LEFT JOIN 保留左表全量、缺侧补 NULL
存在性判断 EXISTS (SELECT 1 …) 常比大 IN 更省内存
聚合过滤 WHERE 滤行在前，GROUP BY 分组，HAVING 滤组在后；COUNT(列) 不计 NULL
8.0+ 新特性 CTE/递归 WITH 拆复杂逻辑；窗口函数做组内排名、累计与 Top N；LAG/LEAD 免自连接算同环比
JSON ->> 提取、JSON_CONTAINS 判包含、JSON_TABLE 把数组拍平成表；高频键建虚拟列+索引
优化器 8.0 派生表优先合并而非物化；EXPLAIN ANALYZE 看真实行数/耗时（会真跑，慎用于 DML）
Hint /*+ INDEX() / JOIN_ORDER() */ 是最后手段，数据分布变化后需复审
性能习惯 UNION ALL 优先于 UNION；深分页用键集分页代替大 OFFSET

查询写法已经熟练，但要写得快、跑得快，还差最关键的一块拼图——索引。
