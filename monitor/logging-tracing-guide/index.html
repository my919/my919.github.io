1. 概念说明

可观测性三支柱：指标（Metrics：延迟/错误/流量）、日志（Logs：发生了什么）、链路（Traces：一次请求经过哪些服务）。

本篇专注日志 + 链路——排障的核心手段。

为什么需要日志平台：多服务器/多容器，docker logs/journalctl 各自为政，排障要全局搜索——把所有日志集中到一处 + 结构化 + 可检索。

链路追踪解决：一个请求跨 5 个服务，日志散落各处——用 TraceId 串起整条调用链。

2.2 日志级别与量控制

级别 使用
ERROR 异常/失败（必须排查）
WARN 降级/重试/异常输入
INFO 关键业务节点（下单、支付成功）
DEBUG 只在开发/排查时开（生产关闭）

规则：ERROR 要带异常堆栈与业务 ID；避免在循环里打 INFO；敏感字段脱敏（手机号中间 4 位掩码）。

8. 典型案例：一次”支付成功但订单未更新”的跨服务排障

问题背景：客服反馈多名用户支付成功，但订单状态停留在”待支付”。支付是第三方异步回调，跨支付服务与订单服务两个进程。

排查过程：

步骤 操作 观察
① Kibana 搜：service.name:"pay-service" AND message:"回调" AND @timestamp > "now-2h" 大量 PaymentNotifyException: timeout，level=ERROR
② 取一条 ERROR 日志的 traceId（logback %X{traceId} 已输出） traceId=7f3a9c2e1b
③ 用该 traceId 跨服务检索（pay-service + order-service 同一平台） 回调在支付服务 300ms 完成，但调订单服务的 HTTP 请求 5s 超时
④ Zipkin 按该 traceId 查链路 订单服务 span 存在但耗时 5s，期间无 DB/Redis 子 span → 线程被占满
⑤ 订单服务日志 grep 线程池 HikariPool-1 - Connection is not available：DB 连接池耗尽

9. 常见误用与陷阱

坑 现象/后果 解法
日志级别误用：业务失败全打 ERROR ERROR 率天天 3%，告警麻木，真故障被淹没 ERROR 留给”系统异常/需人工介入”；预期内业务失败用 WARN
catch 后只打 e.getMessage() 不打堆栈 只有一句 NPE，定位全靠猜 log.error("msg, id={}", id, e) 把异常对象作为最后一个参数
循环/高频路径打 INFO 日志洪水，磁盘写满，ES 检索变慢 循环外汇总一条；DEBUG 级别 + 生产关闭
敏感信息明文入日志（手机号/密码/token） 合规事故 + 泄漏风险 掩码脱敏（手机号中间 4 位），日志层统一正则替换
字符串拼接打日志而非占位符 高频路径无谓的字符串构造，CPU/内存开销 log.info("id={}", id)，延迟求值
追踪采样率生产仍配 1.0 全量 Zipkin/存储被打爆，应用本身上报开销明显 生产 0.1 起步，问题排查期临时调高
ES 无 ILM/保留策略 索引只增不删，磁盘打满整个集群罢工 ILM 按天滚动 + 14 天删除，磁盘 80% 告警
多行堆栈被拆成多条日志 Kibana 里一行 at java... 无法关联上下文 Filebeat 配 multiline：以空格/日期开头的行归并
