1. 概念说明

可观测性（Observability）三支柱：

支柱 回答的问题 技术
Metrics 指标 系统现在健康吗？（QPS、延迟、错误率、饱和度） Prometheus
Logs 日志 具体发生了什么？（错误详情） Loki / ELK
Traces 链路 一次请求经过了哪些服务、慢在哪？ Zipkin / Jaeger

监控四黄金指标（Google SRE）：延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation）。

架构：exporter/应用暴露指标 → Prometheus 定时抓取 → Grafana 展示 + Alertmanager 告警。

10. 典型案例：一次 5xx 错误率突增的端到端定位（指标 → 日志 → 复盘）

问题背景：周二上午 10:07，企业微信收到 critical 告警”order-service 5xx 错误率 18%”，值班工程师 10 分钟内定位并恢复。

排查过程：

时间 动作 观察
10:07 收到 Alertmanager 告警（企业微信，带 Grafana 链接） 5xx 错误率 18%，持续 3 分钟
10:08 打开 Grafana 业务大盘：错误率 + QPS + 延迟同屏 QPS 正常（非流量洪峰），P99 延迟从 120ms → 2.1s
10:10 PromQL 下钻：errors by (uri, status) /api/orders 500 占 92%，其余接口正常
10:12 Grafana 切 Loki：`{app=”order-service”} = “ERROR”` 按 10:00 后过滤
10:15 确认 Redis 容器 OOM 被杀 → 重启 Redis + 调大 maxmemory 10:17 错误率回落 0%，告警自动 resolved

11. 常见误用与陷阱

坑 现象/后果 解法
告警阈值一刀切（所有指标一个阈值，无分级） 要么深夜被 warning 炸醒，要么 critical 淹没在噪音里 分级 P0 电话 / P1 群通知 / P2 日报，阈值分别设定
告警风暴无收敛 Redis 一挂，500 个实例同时告警，群里刷屏几百条 group_by + group_wait + repeat_interval，同源告警合并
只监控存活（up==0），不监控业务指标 进程活着但下单量归零/错误率飙高，无人知晓 黄金指标全配：QPS、错误率、延迟、饱和度 + 业务指标（下单量）
告警规则不配 for 时长 指标抖动一下就告警，误报多到没人再看告警 短抖动容忍：for: 3m~5m，持续超阈值才触发
只看平均值不看分位数 平均 80ms 岁月静好，P99 已 5s，用户体验崩溃 大盘固定 P95/P99 面板，histogram_quantile 计算
Prometheus 数据无持久化卷 容器重启历史指标全丢，故障复盘无线索 prom-data volume 挂载，配合定期快照
大盘只放基础设施指标，没有业务面板 CPU 内存全绿，业务早停摆——监控”健康”是假象 业务大盘置顶：核心接口 QPS/错误率/时延/关键业务计数
