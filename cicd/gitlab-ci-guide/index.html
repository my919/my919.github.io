1. 概念说明

GitLab CI 是 GitLab 内置的持续集成/部署系统：提交代码 → Runner 执行流水线 → 构建/测试/部署。

核心概念：

概念 说明
Pipeline 一次 CI 执行（每次 push 触发）
Stage 阶段（build → test → deploy），同阶段并行、跨阶段串行
Job 一个任务（一个 stage 下的具体命令）
Runner 执行任务的机器（共享/特定）
Artifacts 任务产物（如 jar），可传递给后续任务

工作流：Merge Request 触发 → 校验（lint/test）→ 合并后自动部署到测试环境 → 手动/自动部署生产。

7. 最佳实践与坑

实践 说明
密钥走 Variables 不写进 yml/仓库，用 Masked + Protected
artifacts 设过期 防止存储膨胀
cache 配 key 分支间隔离缓存
阶段划分清晰 build/test/deploy 分离，便于定位
超时限制 timeout: 30m 防任务挂死
镜像固定版本 避免 latest 漂移导致偶发失败
失败重试 retry: 2 处理网络抖动

8. 典型案例

案例：前端静态站点的 GitLab CI 流水线（构建→测试→镜像→部署）

问题背景：React 站点此前由各人本地 npm run build 后手动拷贝到 Nginx 服务器，产物不一致、偶发漏传静态资源。目标：MR 跑检查，合并 main 自动构建 Docker 镜像并部署测试环境，打 tag 后手动上生产。

方案：缓存按 lock 文件哈希分键 → 构建镜像推 GitLab Registry → 双环境部署（test 自动 / prod 手动），生产发布用 resource_group 防并发。

关键配置（.gitlab-ci.yml）：

踩坑点：

  • cache key 写死 maven-cache/npm-cache 这类固定值：分支间互相覆盖缓存，A 分支的脏依赖污染 B 分支。按 lock 哈希分键最稳。
  • deploy-prod 忘配 when: manual：一打 tag 生产直接被发布，没有任何确认机会。
  • dind 需要 privileged Runner；job 报 Cannot connect to Docker daemon，先查注册时是否 --docker-privileged。
  • 项目 Variables 存密钥必须勾 Masked + Protected，否则变量值会明文打进 job 日志。

9. 常见误用与陷阱

坑 现象/后果 解法
密钥明文写 YAML 或日志可见 凭据随仓库/日志泄露 Variables 勾 Masked+Protected；禁止 echo 密钥
无回滚机制 发布坏版本只能现场手修 镜像用 SHA 标签留存，部署脚本支持回拉旧 tag
测试失败仍部署 门禁形同虚设 阶段/needs 依赖硬阻断，不加 allow_failure: true
缓存键全局固定 分支互相污染依赖缓存 key 含 lock 文件哈希，按内容隔离
并发部署互踩 两个 pipeline 同时 docker compose up 同一 environment 配 resource_group 串行化
镜像固定用 latest 偶发失败难复现，版本不可追溯 基础镜像与产物镜像都固定版本 tag
