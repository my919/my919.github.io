CI/CD · 发布策略与回滚

从 0 到安全的发布体系。发布策略对比 · 发布前置纪律 · 滚动发布与回滚 · 蓝绿发布 · 金丝雀/灰度发布 · 数据库变更纪律 · 回滚决策。命令带详细注释。

技术栈速查

类别 选型 用途
容器 Docker + K8s 部署载体
CI GitLab CI / GitHub Actions 构建镜像
流量 Nginx 1.28 / K8s Service 切流与灰度
配置 Nacos v3.2.4 配置管理

1. 概念说明：四种发布策略

策略 原理 优点 缺点 适用
滚动发布 逐个替换实例 无需额外资源 新旧版本并存，兼容性要求高 默认
蓝绿发布 两套环境，一次性切流 回滚极快（切回） 双倍资源 核心服务
金丝雀 小流量先试新版本 风险最小 需要流量控制能力 大版本
灰度 按比例逐步放量 可观测再放量 时间较长 用户量大

核心原则：发布本身不是风险，不可回滚才是风险——任何发布都必须有回滚预案。

2. 发布前置纪律（回滚失败的最大根源）

为什么大多数回滚失败在数据库：代码可以秒回滚，数据库结构变了就回不去。

加列 vs 删列纪律：

变更 是否允许 原因
新增字段（可空/有默认值） ✅ 新旧代码都能跑
修改字段类型 ⚠️ 谨慎 需双写过渡
删除字段/表 ❌ 当前版本禁止 旧代码会直接报错

3. 滚动发布与回滚（K8s 默认方式）

3.1 发布

为什么用 set image 而非 delete pod：rollout 记录每次发布历史，回滚有据可依；直接删 pod 会丢掉版本历史。

3.2 回滚

回滚判定：新版本 5xx 率上升 / 错误日志爆发 / 核心指标恶化 → 立即回滚，不纠结。

4. 蓝绿发布（双环境切流）

为什么蓝绿回滚最快：回滚 = 把流量切回去（秒级），旧环境一直活着不用重新部署。代价：双倍资源（生产普遍用”同规格减半”的临时绿环境）。

5. 金丝雀/灰度发布（按比例放量）

5.1 Nginx 权重灰度（简单直接）

为什么从 5% 开始：金丝雀的目的是用最小流量暴露最大问题——5% 流量足够发现错误率/延迟异常，又不至于影响大量用户。

7. 回滚决策表

场景 是否回滚 动作
5xx 率 > 1% 且持续 5 分钟 立即回滚 rollout undo / 切回蓝环境
P99 翻倍且业务指标恶化 回滚 同上
功能 bug 但不影响主流程 评估 可热修复，不必回滚
数据错乱（写坏数据） 立即回滚 + 数据修复 回滚代码 + 修数据
数据库迁移失败 不”回滚”迁移，向前修复 修复迁移脚本，禁止反向 drop

为什么数据库迁移失败不反向回滚：表结构变化通常不可逆（数据已迁移），反向 drop 会丢数据——正确做法是修复迁移脚本继续向前。

9. 典型案例

案例：一次内存泄漏事故的蓝绿回滚

问题背景：v2.4.0 订单服务金丝雀放量 5% 后 30 分钟内存平稳，放量到 30% 时 Pod 内存以每分钟约 200MB 的速度增长并开始 OOM，5xx 率升至 3%。必须立刻止血。

方案：按预案执行”停止放量 → 切回蓝环境 → 保留现场 → 排查根因”四步，全程 5 分钟。

关键操作：

踩坑点：

  • 回滚决策要预授权：值班按检查清单（5xx > 1% 持续 5 分钟）直接切流，不等逐级审批——事故中最贵的是等待。
  • 切流前先冻结 CI/CD 的自动部署，避免”一边回滚一边又有新版本推上来”。
  • 绿环境别急着删：内存 dump、日志都还在里面，根因排查完再清理。
  • 复盘结论：v2.4.0 引入了未关闭连接的 HTTP 客户端；修复回归后重新走 5% → 30% → 100% 灰度，而不是直接全量。

10. 常见误用与陷阱

坑 现象/后果 解法
无回滚预案 出事时现场找方案，恢复时间翻倍 发布检查清单强制填写”回滚到哪个版本、怎么操作、谁执行”
数据库删字段与代码同版本发 滚动期间旧实例读不到列，全站 500 只加不删，删列延后两个版本
回滚只回代码不回配置 新配置配旧代码，换个姿势再挂一次 配置随版本留存，回滚时一并回退
灰度只放量不设阈值 指标已恶化还在”再观察观察” 每档放量绑定硬指标（错误率/P99），不达标即回退
金丝雀直接跳 100% 小流量没验证到问题就全量 严格 5% → 30% → 100%，每档观察固定时长
迁移失败执行反向 drop 数据被删，真丢单 迁移失败向前修复脚本，禁止反向回滚
