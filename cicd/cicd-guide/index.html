CICD · 持续集成与部署

从 0 到自动化流水线。CI/CD 概念 · GitHub Actions · GitLab CI · 构建/测试/镜像/部署 · 质量门禁。配置带详细注释。

技术栈速查

类别 选型 用途
CI 平台 GitHub Actions / GitLab CI 流水线执行

1. 概念说明

CI/CD 是”自动化交付”的三种实践的合称：

  • 持续集成（CI, Continuous Integration）：每次代码提交都自动触发构建 + 测试，尽早发现集成问题。核心是”频繁合并、快速反馈”。
  • 持续交付（CD, Continuous Delivery）：CI 通过后自动把产物（镜像/包）准备好，处于”随时可发布”状态。
  • 持续部署（Continuous Deployment）：产物自动部署到生产环境，全流程无人干预。

**流水线（Pipeline）**是这些阶段的编排：提交代码 → 安装依赖 → Lint → 单元测试 → 构建镜像 → 推送制品 → 部署。**质量门禁（Quality Gate）**指某一步失败即中断流水线，保证坏代码无法进入下一步。

2. GitHub Actions 从零开始

2.1 概念：Workflow / Job / Step

术语 含义
Workflow 一个 .yml 文件，定义整条流水线
Event 触发条件（push、PR、定时）
Job 一组 Step，默认并行执行
Step 最小执行单元（一条命令或一个 action）
Runner 执行环境（ubuntu-latest 等）

6. 最佳实践

实践 说明
流水线快 缓存依赖（npm cache / docker layer cache）
失败即中断 每一步都是质量门禁
部署用制品 不要重复构建，测试通过的镜像一路到生产
环境隔离 dev/staging/prod 三套环境与密钥
密钥不入库 全部走 Secrets / Vault
并行化 无依赖的 Job 并行跑，缩短总时长

7. 典型案例

案例：Python Flask 服务的完整流水线（构建→测试→镜像→部署）

问题背景：Flask 服务此前手动 scp + systemctl restart 发版，常出现”本地能跑线上挂”，且两人同时发版会互相覆盖。目标：push 到 main 后自动 测试 → 构建镜像 → 推 GHCR → SSH 部署，并发 push 不互踩，发布失败自动回退。

方案：三个 Job 用 needs 串成门禁链 → concurrency 组按分支排队 → 部署脚本内置健康检查与回退。

踩坑点：

  • 不加 concurrency 时，两次 push 同时部署同一端口，容器名冲突”随机”失败，极难排查。
  • 镜像标签必须用 github.sha 而非 latest：latest 让”回滚到上一版”无从谈起。
  • docker stop app || true 的 || true 是首次部署（容器不存在）的容错，漏掉直接红。
  • Secret 只能在 with: 里引用，绝不要 echo $SECRET 或明文写进 YAML——推过一次就永远留在历史里。

8. 常见误用与陷阱

坑 现象/后果 解法
密钥明文写进 YAML 一次 push 后密钥永远留在 git 历史 全部走 Secrets/Vault；已泄漏立即轮换
测试失败仍继续部署 坏版本直达生产 Job 间用 needs 硬依赖；不开 continue-on-error 跳过测试
缓存键设计错误 缓存永不命中或命中脏缓存 key 含 lock 文件哈希：${{ hashFiles('**/package-lock.json') }}
无回滚机制 发布出事只能现场手修 镜像按 SHA 标签留存，部署脚本内置健康检查+回退
并发部署互踩 两次 push 同时跑，容器/端口冲突 concurrency 组按分支排队或取消旧运行
镜像永远用 latest 标签 生产跑的版本说不清，回滚无据 tag 用 commit SHA/版本号，latest 只做别名
