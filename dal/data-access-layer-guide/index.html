1. 概念说明

**数据访问层（DAL, Data Access Layer）**是业务逻辑与数据库之间的隔离层，职责包括：

  • 屏蔽 SQL 细节：业务层不写 SQL，只调用方法。
  • 统一管理连接：连接池复用连接，避免频繁建连。
  • 事务控制：保证一组操作要么全成功要么全回滚。
  • 对象映射（ORM）：把表记录映射为对象，行转实体。

分层职责：Controller（入参出参）→ Service（业务规则）→ Mapper/Repository（数据访问） → DB。DAL 只做”怎么取数据”，不做业务判断。

ORM vs 原生 JDBC：

维度 原生 JDBC ORM（MyBatis-Plus / JPA）
开发效率 低（样板代码多） 高（CRUD 自动生成）
复杂 SQL 可控 MyBatis 用 XML、JPA 用 JPQL
性能 精细可控 需注意 N+1 问题
学习成本 低 中

12. 最佳实践

实践 说明
禁止循环查询 批量数据用 IN / 批量插入，避免 N+1
事务尽量短 事务内不做远程调用、不做耗时代码

索引先行 查询条件字段建索引，explain 验证
软删除 用逻辑删除字段，不物理删除

13. 典型案例：运营后台用户列表（N+1 治理 + 深分页优化）

问题背景：运营后台「用户列表」页要展示每个用户的订单数。初版在循环里逐个查订单数（N+1）：一页 100 条数据发 101 条 SQL，接口 8 秒才返回；运营翻到第 5000 页时又触发深分页慢查询告警，DBA 直接找上门。

方案：

问题 初版实现 优化后
每行查一次订单数 1 + N 条 SQL，RT 秒级 一条 GROUP BY user_id 聚合 + 内存回填
深分页 LIMIT 100000, 20 扫描并丢弃 10 万行 书签式分页：子查询定位起始 id
偶发 Connection is closed 连接被服务端先回收 maxLifetime 调到小于 wait_timeout

14. 常见误用与陷阱

坑 现象/后果 解法
循环里逐条查询（N+1） 一页数据发上百条 SQL，接口 RT 秒级 IN 批量查 + Map 回填，或 JOIN
大批量 insert 一把梭 超过 max_allowed_packet 整批失败 分批 500~1000 条，JDBC 串加 rewriteBatchedStatements=true
HikariCP maxLifetime 大于 wait_timeout 拿到已被 DB 回收的连接，报 CommunicationsException maxLifetime 调小于 wait_timeout（留 30s 余量）
动态 SQL 用 ${} 拼接用户输入 SQL 注入，数据被拖库 一律 #{} 参数化；排序字段用白名单映射
LIKE '%关键词%' 前导通配符不走索引，全表扫描 改前缀匹配 LIKE 'x%'，或接全文索引/ES
分页不设上限 page_size=10000 一次拖垮数据库与带宽 服务端硬约束（le=100），大数据量改游标
SELECT * 带出大字段 网络 IO 翻倍，无法利用覆盖索引 按需选列，列表页不查 TEXT/BLOB
逻辑删除后唯一键冲突 软删用户重新注册报 Duplicate entry 唯一索引带上删除标记（如 email+deleted 组合）
