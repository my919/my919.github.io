第六章：Java 动态数据源：@DS 切换与事务边界

发表于 2026-05-04 更新于 2026-10-25 分类于 数据访问层 本文字数： 6.5k 阅读时长 ≈ 6 分钟

第六章：Java 动态数据源：@DS 切换与事务边界

概念基础

  1. 为什么需要多数据源：主从读写分离、按库分业务、迁移期新旧库并存等场景，要求应用在运行时切换数据库连接。
  2. 动态数据源方案：Spring 提供 AbstractRoutingDataSource 路由骨架；Baomidou 的 dynamic-datasource 在此之上提供开箱即用的实现。
  3. 核心注解 @DS：通过 @DS("逻辑名") 声明当前类/方法使用的数据源，底层借助 AOP 代理 + ThreadLocal 上下文完成切换，对 MyBatis-Plus、MyBatis-Flex、JdbcTemplate 等均透明适用。
  4. 切换时机是关键：数据源在获取连接时确定；已开启事务并绑定连接后，再切换通常不会生效，须注意事务边界。
  5. 常见陷阱：同类自调用绕过 Spring 代理导致 @DS 失效；编程式切换 push 后忘记 poll 会污染线程上下文。

springboot 仓库落地见 第五章：SpringBoot 集成 MyBatis-Flex 与多数据源。下文以 Boot 4 + MyBatis-Plus 3.5.x + dynamic-datasource 4.x 为例。

先看 @DS 的路由流程：

@DS 路由流程



flowchart TD
  A[Service 方法调用] --> B{Spring 代理?}
  B -->|否 自调用| C[可能不切换]
  B -->|是| D[读取 @DS 注解]
  D --> E[DynamicDataSourceContextHolder]
  E --> F[(目标 DataSource)]

切换原理：从注解到连接获取

@DS 的生效链路可拆成四步：

  1. AOP 拦截：@DS 由 dynamic-datasource 内置切面 DynamicDataSourceAnnotationInterceptor 解析，方法级优先于类级，注解值压入 DynamicDataSourceContextHolder 的 ThreadLocal 栈——栈结构天然支持嵌套（外层 mysql、内层 pgsql，内层返回后自动恢复外层）。
  2. 路由数据源：DynamicRoutingDataSource 继承 Spring 的 AbstractRoutingDataSource，determineCurrentLookupKey() 返回栈顶逻辑名，框架据此在内部的 dataSourceMap 里选出真实数据源。
  3. 连接获取时机：MyBatis 在每次执行 SQL 时才向数据源 getConnection()——因此只要切面在 SQL 执行前完成切换，路由就能生效；反之连接已绑定再切换就晚了（详见下文事务边界）。
  4. 清理：切面 finally 中 poll() 弹栈；编程式 push 必须配对 poll，否则线程池复用线程时会串库（上一个请求的数据源泄漏到下一个请求）。


flowchart TD
  A[调用 @DS 标注方法] --> B[AOP 切面解析注解]
  B --> C[逻辑名 push 到 ThreadLocal 栈]
  C --> D[Mapper 执行 SQL → 向 DataSource 要连接]
  D --> E[determineCurrentLookupKey 读栈顶]
  E --> F[路由到目标库连接]
  F --> G[方法返回 finally poll 清理]

Spring Boot 配置

要点：

  • primary：未加 @DS 时默认使用的数据源逻辑名，需与 datasource 下某一键一致。
  • 逻辑名：mysql、pgsql 等为自定义别名，在 @DS("pgsql") 等处引用。

使用 @DS 切换数据源

在 类 或 方法 上使用 @DS("逻辑名")；方法级优先于类级。

Controller 上也可标注，但更推荐标在 Service 或 Mapper 层，避免 Web 层与持久化策略绑死。

事务与边界情况

  • 同一事务内：已进入 @Transactional 且已绑定连接后，再切换数据源通常不会按预期切到新库（连接已固定）。多数据源写操作应拆到不同事务方法，或调整事务边界，使切换发生在开启事务之前。
  • 只读事务：若使用 @Transactional(readOnly = true)，仍要注意连接从哪个数据源取得，与 @DS 所在方法的事务传播一致。
  • 自调用：同类内 this.method() 不会经过 Spring 代理，@DS 可能不生效，应抽到另一个 Bean 或通过代理调用。

「切换不生效」几乎都源于连接绑定早于切换，对照下表定位：

场景 结果 原因
@Transactional 方法内切库 无效 事务管理器在方法入口已取连接并绑定线程
事务内调另一个 @DS Bean 看传播级别 REQUIRED 复用外层连接；REQUIRES_NEW 挂起外层、取新连接
@DS 标在事务方法上层入口 有效 切换发生在连接获取之前
无事务方法内切库 有效 每条 SQL 现取连接，随切随换

实践规则：

  1. 多库写操作拆成多个事务方法，每个方法自带 @DS + @Transactional，由外层无事务方法编排。
  2. 需要「一次切换覆盖整个事务」时，把 @DS 放在调用事务方法的上层入口（如 Controller 或外层 Service），dynamic-datasource 的切面默认优先级高于事务切面，能保证先切换后开事务。
  3. 跨库原子性本地事务管不了，需要 Seata 之类的全局事务——dynamic-datasource 与 Seata AT 联用时关闭自动代理，改 spring.datasource.dynamic.seata: true，见 Spring Cloud Alibaba 第六章：集成 Seata：AT 模式分布式事务。

与 MyBatis-Plus / MyBatis 的配合

引入 MyBatis-Plus 后，SqlSessionFactory 仍使用 Spring 容器中的动态 DataSource，与 dynamic-datasource 无额外冲突。Mapper（含继承 BaseMapper 的接口）或 XML 无需单独为多数据源改一套配置即可随当前线程数据源路由；若某几个 Mapper 固定走副库，可在 Mapper 接口上加 @DS("pgsql")。

常见问题

现象 可能原因
始终走 primary 未走到带 @DS 的代理方法；或自调用绕过代理
切换无效 已在事务中取连接；或 push 后未 poll 导致线程本地状态错乱
启动报错找不到驱动 driver-class-name 与 runtimeOnly 驱动依赖不一致
Boot 版本不匹配 Boot 4 用 spring-boot4-starter，Boot 3 用 spring-boot3-starter
间歇性串库 编程式 push 未配对 poll，线程池线程被污染
从库读到旧数据 主从复制延迟；强一致读未留在 master

排障三板斧

  1. 看当前逻辑名：在怀疑的 SQL 执行前打印 DynamicDataSourceContextHolder.peek()，确认栈顶是不是预期的库。
  2. 看代理链：在 @DS 方法入口断点，确认调用经过了 DynamicDataSourceAnnotationInterceptor（自调用会跳过）。
  3. 看连接绑定：开启 org.springframework.jdbc.datasource 的 DEBUG 日志，事务方法里只会出现一次 Fetching JDBC Connection，之后切库自然无效。
