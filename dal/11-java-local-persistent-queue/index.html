第三章：Java本地持久化队列方案与实战

概念基础

  1. 是什么：任务先写入磁盘再消费的本地队列——进程重启、宕机后任务不丢失，重启自动恢复继续消费。
  2. 为什么需要：内存队列（如 LinkedBlockingQueue）重启即丢；引入 Redis/MQ 又增加部署与运维成本——本地持久化队列在轻量与可靠之间取得平衡。
  3. 三大成熟方案：Chronicle Queue（MMAP 磁盘映射、零依赖、超高吞吐、金融级）、LMDBQueue（嵌入式 KV、极轻量）、MapDB（纯 Java、一行代码建队列）。
  4. 核心能力：磁盘存储 + 重启恢复 + 自动序列化——任务对象只要实现 Serializable 即可入队出队。
  5. 选型记忆：最强成熟方案选 Chronicle Queue，最简单上手选 MapDB。

🔥 最佳推荐（3 个真正的本地持久化队列）

按易用性、性能、成熟度排序：

1. Chronicle Queue（企业级首选，零依赖、高性能）

最适合你：本地持久化 + 可序列化 + 超高吞吐 + 重启不丢

  • 纯 Java 本地队列
  • 磁盘持久化（MMAP）
  • 支持任意对象序列化
  • 无锁、低延迟、生产级稳定
  • 支持多线程读写
  • 重启自动恢复数据

Maven 依赖

最简 Demo（入队 + 出队 + 持久化）

特点：

  • 关机、重启、kill 进程 都不丢数据
  • 支持超大队列（GB 级）
  • 序列化自动完成
  • 金融系统广泛使用

2. LMDBQueue（极轻量、嵌入式、超快）

极简本地持久化队列

  • 基于 LMDB 嵌入式数据库
  • 极快、极小、稳定
  • 支持 key/value 持久化
  • 天然支持序列化

3. MapDB（嵌入式 Java 数据库，自带持久化队列）

最简单、最容易上手

  • 一行代码创建持久化队列
  • 支持序列化
  • 纯 Java
  • 适合小项目、后台任务

4. H2 MVStore（随 H2 顺带引入的事务型选择）

H2 数据库内置的 MVStore（Multi-Version Store）也能当持久化队列用，纯 Java、单 jar，项目已用 H2 嵌入式库时顺手复用：

特点：MVCC 存储、事务支持、单文件；性能低于 Chronicle Queue，但 API 友好且能复用 H2 生态（备份、工具链）。出队即 remove，天然无「位点管理」负担。

一句话选型：

  • 极致吞吐/低延迟、可投入学习成本 → Chronicle Queue
  • 5 分钟集成、中小流量后台任务 → MapDB
  • 已依赖 H2、需要事务语义 → MVStore
  • 极致读性能、可接受 JNI → LMDB

生产注意事项

  1. 容量与滚动：Chronicle Queue 按天滚动 .cq4 文件，需配置保留策略防磁盘写满；MapDB / MVStore 单文件持续增长，要定期 compact 或归档清理。
  2. 消费位点：Chronicle 的 Tailer 位点需自行持久化，否则重启后从头或从尾重复消费；MapDB / MVStore「出队即删」，天然无位点问题。
  3. 崩溃一致性：MVStore / MapDB 入队后记得 commit()；Chronicle 依赖 MMAP flush 语义。kill -9 场景下的丢失窗口以实际压测为准，不要凭文档承诺设计。
  4. 多实例边界：本地队列不能跨进程共享——集群部署时每个实例只消费自己的队列文件；需要全局可见的任务请升级 Redis / RocketMQ。
  5. 监控：把 size() 暴露到 Micrometer 指标，队列积压时告警；消费线程挂掉时队列会静默堆积，务必加消费线程存活探针。

五、核心特性

  1. 重启不丢数据
    程序停止、重启后，重新 new 相同路径和队列名，自动加载历史任务。
  2. 自动序列化
    只要继承 BaseTask（实现 Serializable），任意业务对象直接入队。
  3. 线程安全
    方法加 synchronized，支持多线程生产、多线程消费。
  4. 轻量无中间件
    纯本地文件存储，不需要 Redis/MQ。

六、使用注意

  1. 任务类所有字段必须可序列化，不要包含非序列化对象；
  2. 程序优雅退出时务必调用 close()；
  3. 不要多个进程同时打开同一个 db 文件，会锁文件报错。

七、消费循环模板（带失败重试）

生产消费通常是「常驻线程 + 失败重投」，参考模板：

两个设计要点：

  1. 失败重投要有上限：任务对象里加 retryCount 字段，超限后写入「死信」文件或告警，避免毒丸消息把队列卡死。
  2. 出队即丢风险：dequeue() 成功但 handle() 前宕机，任务就丢了。需要更强保证时改用 Chronicle Queue 的 Tailer 位点模式（处理成功后再推进位点），或在 MapDB 上实现「处理中队列」二次搬移。

总结

真正的 Java 本地持久化队列 = 磁盘存储 + 重启不丢失 + 可序列化

最强成熟方案：Chronicle Queue
最简单方案：MapDB
