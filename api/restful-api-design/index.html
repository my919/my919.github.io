1. 概念说明

REST（Representational State Transfer，表现层状态转移）是一套架构风格而非协议，核心思想是把一切都抽象为资源，用 HTTP 方法表达对资源的操作：

HTTP 方法 语义 幂等
GET 查询资源 ✅
POST 创建资源 ❌
PUT 整体更新 ✅
PATCH 局部更新 ✅
DELETE 删除资源 ✅

两点细节：① POST 不幂等的生产解法（Idempotency-Key）见 §9.1；② DELETE 重复调用返回 404 还是 204 是设计选择——要暴露「不存在」信息返回 404（本文采用），要严格「目标状态已达成」语义返回 204，全 API 保持一致即可。

RESTful API 设计五原则：资源用名词复数命名（/users 而非 /getUser）、用 HTTP 方法表达动作、无状态（每个请求携带全部信息）、状态码表达结果、版本化管理接口（/v1/users）。

2. 规范速查

2.1 资源命名

命名细则：多词路径用 kebab-case（/v1/user-groups）；嵌套不超过 2 层（过深用顶层资源+过滤参数替代）；查询参数全篇统一 snake_case 或 camelCase。

2.2 状态码

状态码 含义 典型场景
200 OK 查询成功
201 Created 创建成功
204 No Content 删除成功
202 Accepted 异步任务已受理（配合轮询/Webhook）
400 Bad Request 请求格式错误（JSON 语法错、缺必需头）
401 Unauthorized 未认证
403 Forbidden 无权限
404 Not Found 资源不存在
405 Method Not Allowed 方法不允许
409 Conflict 资源冲突（如重复创建）
412 Precondition Failed If-Match/版本冲突（见 §9.2）
422 Unprocessable 语义错误
429 Too Many Requests 限流（应带 Retry-After）
500 Internal Server Error 服务器异常
503 Service Unavailable 下游不可用/熔断

FastAPI 的字段校验失败默认返回 422；JSON 语法错误等「请求本身无法解析」才是 400。

8. 版本管理与兼容

  • URL 版本（推荐，兼容性好）：/v1/users、/v2/users
  • Header 版本：Accept: application/vnd.api+json;version=1

9. 幂等键与 202 长任务设计

9.1 幂等键：POST 不幂等的生产解法

POST 创建资源天然不幂等（重复调用会创建多条），网络超时后客户端重试无法判断「创建成功还是失败」。标准解法：客户端在请求头里带唯一幂等键 Idempotency-Key: <UUID>，服务端先查该 key 是否已有结果——有则直接返回缓存结果，没有才执行业务：

幂等键 请求体 结果 服务端行为
abc {“name”:”a”} 成功(id=1) 首次执行 → 创建 + 缓存结果
abc {“name”:”b”} 成功(id=1) key 已存在 → 直接返回第一次的结果（请求体不再次校验）
xyz {“name”:”a”} 成功(id=2) 新 key → 正常执行

幂等键的作用范围：同一 key + 同一 API 端点。key 一般在客户端生成（UUID），服务端只做「见 key 识结果」。

9.2 并发控制：ETag + If-Match（乐观锁）

多人同时编辑同一资源时，后提交的人可能覆盖前一个人的修改。REST 标准做法是乐观锁：

FastAPI 里用 response.headers["ETag"] = ... 和 if_match = Header(default=None) 配合实现。核心规则：写操作（PUT/PATCH/DELETE）读操作前必须校验 ETag，不一致就拒绝。

9.3 202 Accepted：长任务的 REST 设计

创建需要几秒到几分钟完成的异步任务（如批量导入、视频转码、报表生成），不应让客户端挂等：

202 的设计要点：① 返回任务 ID 和状态查询地址；② 提供任务列表/取消接口；③ 任务完成回调（Webhook）优于客户端轮询；④ 超时任务明确标 timeout 状态。

10.1 限流响应头与客户端退避

触发限流时，服务端应在响应头带 Retry-After（秒数或 HTTP 日期）：

客户端收到 429 应遵循 Retry-After 做指数退避重试（5s → 10s → 20s），而不是立即重试。

上线检查清单

检查项 通过标准
HTTPS 强制 TLS，HTTP 重定向到 HTTPS；HSTS header 开启
鉴权 所有受保护端点要求认证，返回 401 而非 302
授权 接口权限按资源归属判断，不能只靠前端隐藏
限流 按 IP + 用户双维度限流，返回 429 + Retry-After
幂等键 创建类 POST 支持 Idempotency-Key，重复 key 返回缓存结果
错误格式 统一 {code, msg, data}，生产环境隐藏堆栈细节
日志脱敏 access log 不记敏感信息（token、手机号、邮箱打码）
超时 网关/客户端 timeout 都有明确值，不设无限等待
版本 破坏性变更必须升版本号，旧版本保留过渡窗口
分页 大数据集用游标分页，避免 deep offset 性能问题

11. 典型案例：订单 API 版本化迁移（v1 → v2 平稳过渡）

问题背景：v1 的 GET /v1/orders 返回金额字段 price（单位：分）。业务要求 v2 同时返回 price_fen 与 price_yuan，且 status 枚举从数字改为字符串。曾有团队直接改 v1，当晚两个移动端老版本解析崩溃——教训：破坏性变更必须版本化并留过渡期。

方案：

阶段 动作 时长
① 预告 v1 响应加 Deprecation/Sunset 头 + 公告迁移文档 提前 3 个月
② 新增 /v2/orders 上线，与 v1 共存，业务层复用 当周
③ 监控 网关统计 v1 调用方与 QPS，逐家催迁移 3 个月
④ 下线 v1 调用清零 → 返回 410 Gone 引导升级 到期执行

12. 常见误用与陷阱

坑 现象/后果 解法
URL 写动词 /getUser 资源语义混乱，方法与幂等性失控 名词复数资源 + HTTP 方法表动作
全部接口 POST 语义全无、缓存失效、网关重试策略失效 查询 GET / 创建 POST / 更新 PATCH
一律 200 + body 里 code 监控按状态码统计失真，客户端难判断 HTTP 状态码表达结果，业务码做补充
page_size 不设上限 page_size=100000 一次打挂数据库与带宽 服务端硬约束 Query(20, ge=1, le=100)
破坏性变更直接改 v1 老客户端解析崩溃，故障波及所有调用方 升 /v2/ + 过渡期 + Sunset 头
429 不带 Retry-After 客户端立即重试，流量雪崩式放大 限流响应带 Retry-After，客户端指数退避
错误响应带堆栈 框架版本、SQL、路径泄露给攻击者 生产统一错误结构，隐藏内部细节
嵌套资源超过 2 层 路由与权限模型爆炸 拉平为顶层资源 + 过滤参数
