9. 典型案例：开放网关鉴权限流

问题背景：公司将物流查询能力开放给 200+ 外部合作伙伴。早期各业务系统自己接 API Key、自己限流：出现过一次合作伙伴脚本 bug 10 万 QPS 打穿订单库的事故，以及三方密钥硬编码泄露后”无法紧急吊销”的窘境。

方案：所有对外能力收口到 API 网关：统一认证（JWT + AppKey）、多级限流、可观测，业务系统只信任网关：

层 机制 说明
认证 AppKey/HMAC 签名换短期 JWT 密钥不进 URL，可随时吊销
鉴权 scope 模型（如 logistics:read） 最小授权，按伙伴分配
限流 伙伴级 + 接口级 + 全局级 Redis 令牌桶，429 带 Retry-After
内部信任 网关注入身份头 + 内网 mTLS 业务系统不对外暴露
审计 全量访问日志 + 密钥操作留痕 泄露可追溯、可紧急吊销

关键设计：

踩坑点：① 限流键只用了 IP，合作伙伴出口 NAT 后 200 家共享一个 IP，正常调用被误杀——限流维度用 AppKey/JWT 里的 partner_id。② 只限伙伴级没设全局兜底，200 家同时 100 QPS 理论峰值 2 万，大促时仍击穿下游——全局级与接口级限流必须同时存在。③ JWT 有效期给了 24h，吊销密钥后旧 token 依然可用半天——对外 token 5 分钟级，配合吊销列表（jti 黑名单）。④ 业务系统误信了外部伪造的 X-User-Id 头（绕过网关直连内网）——内网服务间 mTLS + 网络策略禁止绕过网关入口。⑤ 限流 429 响应没带 Retry-After，伙伴按 0 退避疯狂重试，放大 3 倍流量——标准限流响应头必须带上。

10. 常见误用与陷阱

坑 现象/后果 解法
限流键用 IP NAT 出口误杀正常伙伴 按 AppKey/partner_id 限流
缺全局/接口级限流 伙伴合规但总量击穿下游 伙伴级+接口级+全局级三级配置
长效 JWT 密钥吊销后旧 token 仍可用 短有效期（5min）+ jti 吊销列表
网关直通后端明文 内网被扫描器伪造身份头 内网 mTLS + 禁止绕过网关访问
密钥放 URL/日志 泄露可追溯性差且直接暴露 HMAC 头部签名 + 日志脱敏
429 无 Retry-After 客户端零退避重试放大流量 标准响应头 + 指数退避文档
scope 过粗（全有或全无） 只读伙伴拿到写权限 细粒度 scope：资源:动作
无伙伴级观测 出问题不知道是哪家 按伙伴/接口维度指标与告警
版本直接改老路径 合作伙伴集成一夜全挂 URL 版本化 /media-type 版本 + 弃用期公告
