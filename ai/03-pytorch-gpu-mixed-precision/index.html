第三章：PyTorch GPU 加速与混合精度

发表于 2026-05-01 更新于 2026-10-25 分类于 人工智能 本文字数： 5.7k 阅读时长 ≈ 5 分钟

第三章：PyTorch GPU 加速与混合精度

概念基础

  1. GPU 擅长并行不擅长分支：大矩阵乘/卷积在 GPU 上快几十倍；数据搬运（CPU↔GPU）反而是瓶颈，少拷贝、大批次是优化方向。
  2. 设备要对齐：模型与数据必须在同一设备，RuntimeError: Expected all tensors to be on the same device 是新手第一错。
  3. AMP 混合精度的本质：前向用 FP16/BF16 省显存提速，梯度更新用 FP32 保精度；autocast + GradScaler（FP16 场景）成对出现。
  4. 显存不够不等于换卡：梯度累积等效大 batch、梯度检查点用算力换显存、小批次 + 累加，都是工程正解。
  5. 测量优先：torch.cuda.synchronize() + 计时、nvidia-smi 看占用，先定位瓶颈（数据加载 or 计算 or 搬运）再优化。

本章承接 第二章：PyTorch 模型与训练 的训练模板。代码按 PyTorch 2.x 官方 API 书写（沙箱无 GPU 与 torch，未逐条运行验证）。

一、设备管理

省一个错误的三行习惯：

别在循环里写 torch.cuda.current_device() 之类的查询；多卡选卡用 CUDA_VISIBLE_DEVICES=1,2 python train.py 从环境层面隔离最干净。

二、混合精度训练（AMP）

要点：

环节 说明
autocast 只包前向 + loss；backward 在上下文外
GradScaler FP16 必需；BF16 不需要 scaler（dtype=torch.bfloat16）
梯度裁剪 必须夹在 unscale_ 与 step 之间
显存收益 权重/激活约省一半，batch 可开大一倍以上

A100/H100 等新卡优先 BF16：指数位与 FP32 相同，无下溢问题，代码更简单（省去 scaler）。

三、显存不够怎么办

1. 梯度累积：小 batch 等效大 batch

2. 梯度检查点：用算力换显存

3. 其他手段

定位显存泄漏：

泄漏最常见原因：把带计算图的 loss/tensor 存进了 list（应 loss.item()），或在验证循环里忘了 no_grad()。

四、torch.compile：内核融合提速

适用 不适用
固定 shape 的静态网络（CNN、MLP） 动态 shape 频繁变化（重编译开销大）
长时间训练（编译费一次摊薄） 短脚本/交互调试

五、测量：瓶颈在哪

瓶颈判别：

现象 瓶颈 对策
GPU 利用率忽高忽低 数据加载跟不上 num_workers 加大、persistent_workers=True、预取
GPU 利用率恒定但很慢 计算本身 AMP、torch.compile、减小模型
memory_allocated 不高但 OOM 显存碎片 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
CPU 单核吃满 DataLoader 简化 __getitem__、预处理离线化

六、BF16 与 FP16 的抉择

FP16 BF16
尾数 / 指数位 10 / 5 7 / 8
动态范围 小，易溢出 与 FP32 同量级
需要 GradScaler 是 否
硬件 老卡（V100）友好 Ampere 及以后（A100/H100、RTX 30 系起）

近两年的新卡默认 BF16；只有老硬件才退回 FP16 + GradScaler。

七、梯度累积 + AMP 完整模板

三个易错点：loss 先除 accum_steps 再 backward；裁剪与 step 只在累积边界做；BF16 路径不需要 unscale_，FP16 + GradScaler 路径才需要。

八、OOM 排查手册

症状 根因 处置
allocated 低却 OOM 显存碎片 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
每轮缓慢上涨 计算图泄漏（list 存 loss） 改存 loss.item()；验证包 no_grad
第一个 batch 就炸 batch/模型确实太大 减 batch + 梯度累积；上检查点
反向炸前向正常 激活占用大 checkpoint 换显存；缩序列长度
多卡只有卡 0 满 用了 DP 而非 DDP 换 DDP（第四章）
reserved 远高于 allocated 缓存池正常行为 不用管；洁癖可 empty_cache()（有性能代价）

九、Profiler：先看数据再优化

TensorBoard 打开 trace：GPU 空隙长 → 数据加载瓶颈；Memcpy HtoD 占比高 → 搬运瓶颈（检查 pin_memory）；kernel 密集但慢 → 算力瓶颈（AMP/compile/换算法）。先看 Profiler 再动手，别凭感觉优化。

常见坑 FAQ

坑 现象 正确做法
数据没搬 GPU device mismatch 报错 模型与每个 batch 都 .to(device)
FP16 不收敛 loss NaN GradScaler + 裁剪；或直接 BF16
梯度累积忘除 等效 lr 放大 N 倍 loss / accum_steps
compile 后 shape 变 反复重编译更慢 固定输入 shape 或加 dynamic=True
计时不同步 测出来 0.01ms 计时前 cuda.synchronize()
empty_cache 滥用 训练变慢 只调试期用，生产别频繁调

生产实践清单

  • 新卡默认 BF16 autocast；老卡 FP16 必配 GradScaler
  • 显存公式心里有数：参数 + 梯度 + 优化器状态 + 激活
  • 大 batch 需求先用梯度累积而非换卡
  • 固定 shape 的长训练任务开 torch.compile
  • OOM 先查 memory_allocated 与碎片，再谈减 batch
  • Profiler trace 存档，性能回归有据可查

本章小结

要点 结论
设备 模型与每个 batch 都 .to(device)；non_blocking + pin_memory 提速搬运
AMP autocast 包前向，FP16 配 GradScaler；BF16 免 scaler
显存 梯度累积等效大 batch；checkpoint 换显存；memory_allocated 定位泄漏
编译 torch.compile 对固定 shape 长训练收益最大
测量 计时前 synchronize()；GPU 忽高忽低查数据加载
