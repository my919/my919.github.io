第四章：PyTorch 部署与分布式

发表于 2026-05-01 更新于 2026-10-25 分类于 人工智能 本文字数： 6.7k 阅读时长 ≈ 6 分钟

第四章：PyTorch 部署与分布式

概念基础

  1. 训练与推理是两种工程：训练求快求全（Python 动态图），部署求稳求小（静态图、无 Python 依赖、常驻服务）。
  2. ONNX 是推理通用货币：把模型导出为 ONNX 后，可用 ONNX Runtime、OpenCV cv2.dnn（见 第五章：视频与深度学习）、TensorRT 等引擎推理，摆脱 Python 环境。
  3. DDP 是多卡标配：每卡一份完整模型 + 独立 DataLoader 分片，前向各算各的、反向自动同步梯度——比早期的 DP 快且稳。
  4. 服务化就是套壳 HTTP：FastAPI 包一层推理函数即可上线；关键在 batch 合并、并发与预热，不在框架。
  5. 大模型时代的延伸：单卡装不下 → 模型并行/ZeRO（FSDP）；Hugging Face Transformers（见 第三章：LLM 大语言模型基础）把这一层封装好。

本章承接 第三章：PyTorch GPU 加速与混合精度。代码按 PyTorch 2.x 官方 API 书写（沙箱未装 torch，未逐条运行验证）。

一、模型导出：TorchScript 与 ONNX

1. TorchScript（PyTorch 原生静态图）

2. ONNX 导出（跨框架部署首选）

方案 优点 适用
TorchScript 无需额外依赖，PyTorch 全兼容 Python 内服务化
ONNX 跨语言/跨设备，生态最广 C++、移动端、TensorRT
直接 PyTorch 零改造 原型、内部工具

3. 服务端编译优化（torch.compile / AOTI）

固定 shape 的服务端推理可用 torch.compile(model, mode="reduce-overhead") 拿内核融合收益；追求零 Python 依赖时走 AOTInductor 导出为 .so 由 C++ 进程加载——介于 TorchScript 与 ONNX 之间的第三条路。注意编译缓存要随模型版本失效，否则线上跑的是旧图。

二、FastAPI 服务化

上线三件事：model.eval() + inference_mode()（必做）；推理进程与训练进程分开部署；给服务加超时与限流（Nginx 层见 第三章：Nginx HTTPS 与安全）。

三、DDP 多卡训练

DDP 三条铁律：模型先 .to(device) 再包 DDP；DataLoader 必须用 DistributedSampler；保存权重用 model.module.state_dict() 且只在 rank 0 做。

四、大规模训练一瞥

技术 一句话 工具
FSDP / ZeRO 参数/梯度/优化器状态分片到各卡，单卡装得下超大模型 torch.distributed.fsdp
梯度检查点 用算力换显存（第三章） torch.utils.checkpoint
量化 INT8/INT4 推理，显存除以 4~8 bitsandbytes、torchao
混合精度 FP16/BF16 训练标配（第三章） torch.amp

一般工程结论：多卡数据并行（DDP）覆盖绝大多数场景；模型大到单卡放不下才进 FSDP/量化的世界。

五、DDP vs FSDP：怎么选

DDP FSDP
模型副本 每卡完整一份 参数/梯度/优化器状态分片
显存占用 模型大小的 1 倍/卡 约 模型大小 ÷ 卡数（+激活）
通信量 只同步梯度 前反向都要取参数，通信更高
适用 单卡装得下 单卡装不下的大模型
改造量 极小（包一层） 中（auto_wrap 策略要调）

选型结论：单卡装得下永远先 DDP；装不下先开 BF16 + 梯度检查点再试；还不行才上 FSDP。ZeRO-3 级别的分片对应 FSDP 默认行为。

六、大模型推理服务一瞥

本章 FastAPI 直包 PyTorch 适合中小模型。LLM 场景需要连续批处理、PagedAttention、多卡张量并行，请直接用专用引擎：

引擎 特点
vLLM PagedAttention + continuous batching，吞吐标杆
TensorRT-LLM 极致延迟优化，NVIDIA 绑定深
SGLang RadixAttention，前缀共享场景强

对外的 API 网关、鉴权、限流层与本章 FastAPI 模式一致，只是推理引擎从 model(x) 换成引擎的 OpenAI 兼容端点。

常见坑 FAQ

坑 现象 正确做法
DDP 存错权重 加载报 key 带 module. 存 model.module.state_dict()
忘 set_epoch 每轮打乱结果相同 每 epoch 调 sampler.set_epoch(epoch)
多进程都写日志 日志重复 N 份 只 rank 0 打印与保存
ONNX 动态 batch 失效 batch≠1 推理报错 export 时配 dynamic_axes
trace 漏分支 if 分支没进图 控制流多的模型用 torch.jit.script
推理忘 eval() Dropout 在线随机 部署前 model.eval() 固化
nccl 初始化卡死 torchrun 挂起 检查防火墙/网卡，设 NCCL_SOCKET_IFNAME
FSDP 直接 save 保存的是分片或报错 state_dict_type(FULL_STATE_DICT) 后 rank 0 落盘
compile 缓存未失效 上线后行为像旧模型 编译缓存随模型版本清理
推理裸用 Python 循环 吞吐上不去 LLM 换 vLLM；小模型做 batch 合并

生产实践清单

  • 导出模型与 PyTorch 对拍（同输入比输出）后才上线
  • 服务启动预热，首请求不带加载/编译开销
  • 推理全部 eval() + inference_mode()
  • DDP 训练只在 rank 0 保存与打日志
  • torchrun 参数、卡数、版本写进启动脚本并入库
  • LLM 推理用 vLLM 等专用引擎，不手搓 batch
  • 推理与训练进程隔离部署，资源互不影响
  • 模型文件带版本号，灰度与回滚可一键切换
  • 服务有超时、限流与就绪探针

本章小结

要点 结论
导出 TorchScript 留在 PyTorch 生态；ONNX 走跨框架，记得 dynamic_axes
服务化 FastAPI + eval() + inference_mode() + 启动预热；推理进程独立部署
DDP torchrun 拉起；DistributedSampler 切数据；rank 0 独占保存与日志
大模型 单卡装不下先想量化与 FSDP；训练推理永远分开
验证 导出后用相同输入对拍 PyTorch 与推理引擎输出
