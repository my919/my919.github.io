第一章：Terraform 基础设施即代码

发表于 2026-09-02 更新于 2026-10-25 分类于 基础设施即代码 本文字数： 12k 阅读时长 ≈ 11 分钟

第一章：Terraform 基础设施即代码

概念基础

  1. 声明式 vs 命令式：声明式描述”要什么样子”（最终状态），由工具计算”怎么达成”；命令式逐步下达”先建 A、再建 B”。Terraform 是声明式：写 resource 即终态，apply 多少次结果一致，代码即文档。
  2. IaC 核心价值：把基础设施变成可版本化、可审查、可复现的代码——git blame 追溯谁改了机器规格，PR 评审取代”工单+点控台”，新环境 apply 同份代码即可，杜绝”雪花服务器”。
  3. 状态文件 state：terraform.tfstate 记录真实资源与代码的映射——apply 前对比 state 与代码算 diff，apply 后更新 state。state 是事实来源，丢失即失去对已建资源的管理权。
  4. Provider 抽象：每个云厂商/服务封装成 Provider（aws/alicloud/kubernetes），对外暴露统一的 resource/data 接口；换云只需换 Provider 与参数，业务模块结构不变。
  5. 不可变基础设施：理想是”改配置即换新机器、旧机器销毁”，而非 SSH 进去打补丁；Terraform 资源生命周期（创建→替换→销毁）契合不可变理念，回滚即切版本。

本章打通 Terraform 的声明式编排与状态管理，配套的配置管理见 第二章：Ansible 配置管理。

资源依赖图 DAG：Terraform 自动分析”A 引用 B 的属性”建依赖，按 有向无环图 并行建无依赖资源、串行建有依赖者；显式依赖用 depends_on = [aws_s3_bucket_policy.x]。执行计划：init 下载 Provider/初始化 backend → fmt 格式化 → validate 静态校验 → plan -out=tfplan 预览并生成计划文件 → apply tfplan 执行（计划即审计凭证）→ destroy 销毁。

三、状态管理

state 文件结构：state 是 JSON，记录 mode/type/name/provider/instances.attributes，是真实资源与代码的映射表。远程状态 S3 + DynamoDB / OSS：

状态隔离 workspace vs 目录拆分：terraform workspace new dev/select dev 共享一套代码靠 workspace 区分，但易混生产/测试；推荐按环境拆目录，每环境独立 backend key 与变量文件，权限彼此隔离。状态迁移与导入 import：terraform import aws_instance.web i-abc123 纳管已存在资源；terraform init -migrate-state 搬迁 backend；terraform state mv/rm 拆分或脱管。状态锁与并发安全：S3 配 DynamoDB 锁表（新版 S3 backend 支持 use_lockfile = true 免 DynamoDB 原生锁），apply 写锁、结束释放，防并发互相覆盖；OSS 自带锁。锁残留用 terraform force-unlock，务必先确认无人操作。

六、最佳实践与反模式

命名规范与标签策略：统一 {project}-{env}-{role}-{index}，标签走 local.common_tags 便于计费检索。生命周期 prevent_destroy 防误删、ignore_changes 跳过控台改动。敏感数据 output 标 sensitive = true，密钥走 Secrets Manager/Vault。

模块粒度与代码组织：一个 module 对应一个可独立验收的能力；目录按 envs/dev/、envs/prod/、modules/ 分层，环境目录只引用与赋值。

反模式 后果 正确做法
单文件千行 难维护复用 拆 module、按职责分文件
state 进 Git 泄露敏感信息 远程 backend + 加密
不锁 Provider 版本 上游更新即破坏 version = "~> 5.0"
手改控台不回写代码 drift 频发 定期 plan + 立即 import

常见避坑

坑 现象 正确做法
state 提交 Git 密码/IP 泄露 远程 backend + *.tfstate 进 .gitignore
不用 backend 锁 并发 apply 互相覆盖 S3+DynamoDB / OSS 锁表
default workspace 当生产 误切环境删资源 按环境拆目录，禁用 workspace 混用
Provider 不锁版本 上游升级破坏 plan version = "~> 5.0" 约束
手动改控台 下次 plan 全是 diff 改完立即 import 或回写代码
apply 无 plan 文件 中途变更无审计 plan -out 存档、apply 该文件
prevent_destroy=true 误删失败 删不掉卡流程 提前规划迁移，临时改 false 要评审
output 敏感值未标 sensitive 日志泄露密钥 标 sensitive = true，密钥外置
count/for_each 随意切换 地址变更触发全量替换 一次定好策略，迁移用 moved 块
Module source=./ 改本地 协作不一致 锁 version 或 Git ref

本章小结

要点 结论
定位 声明式基础设施编排，状态文件是事实来源
核心流程 init → plan → apply → destroy，先预览后执行
状态管理 远程 backend + 锁，按环境拆目录隔离
Module 输入输出明确、锁版本、私有 Registry 托管
协作 PR 预览 plan、合并触发 apply、OPA 策略护栏
安全 sensitive 输出、prevent_destroy、密钥外置
