类别 选型 用途
语言 JDK 21 LTS 运行环境
线程池 ThreadPoolExecutor（JUC） 线程复用

1. 概念说明：线程池原理

为什么用线程池：创建/销毁线程开销大（约 1ms+ 系统调用），线程池复用线程，避免频繁创建销毁。

参数一览：

参数 含义 决定什么
corePoolSize 核心线程数 平时保底并发能力
maximumPoolSize 最大线程数 峰值并发上限
workQueue 任务队列 能缓存多少任务
keepAliveTime 空闲回收时间 超出核心的线程多久回收
threadFactory 线程工厂 线程命名（排障必需）
RejectedExecutionHandler 拒绝策略 满载时怎么办

2. 参数怎么定（先算再配）

核心公式：

为什么 IO 密集乘 2：IO 线程大部分时间在等（网络/DB），等待时 CPU 空闲——多配线程让 CPU 有活干。精确做法：线程数 = CPU核数 × (1 + 等待时间/计算时间)，用监控数据修正。

队列与最大线程：

场景 建议 为什么
核心业务（下单） 队列小（200-500）+ max 适中 请求要响应，排队太久不如拒绝
异步任务（发短信） 队列大（2000+）+ max 适中 任务可延迟，尽量别丢
高并发短任务 队列小 + max 大 快速消化突发

3. 正确创建线程池（生产标准姿势）

为什么线程必须命名：线上排障靠 jstack——没有名字的线程全是 pool-3-thread-1，根本分不清是哪个池、哪个业务。

4. 拒绝策略选择

策略 行为 适用
AbortPolicy（默认） 抛 RejectedExecutionException 必须显式处理的
CallerRunsPolicy 提交者自己执行（线程池满时谁提交谁跑） 核心业务推荐：不丢任务 + 天然限流
DiscardPolicy 静默丢弃 ❌ 不推荐（任务悄悄没了）
DiscardOldestPolicy 丢弃队列最老的 能容忍丢旧任务

为什么核心业务推荐 CallerRunsPolicy：池满时任务回到调用线程执行——不会丢，而且调用线程被占住后天然限流（请求自然变慢而不是崩）。但必须加日志：触发 CallerRuns 说明容量告急。

9. 常见误用与陷阱

坑 现象 解法
Executors.newFixedThreadPool 队列无界 队列容量是 Integer.MAX_VALUE，任务积压时内存直接撑爆 OOM；线程数永远不增长，拒绝策略形同虚设 手写 ThreadPoolExecutor + ArrayBlockingQueue 有界队列（§3）
线程池大小写死成 200 CPU 密集场景上下文切换频繁、吞吐反降；IO 密集高峰又不够用，任务全堆队列里 P99 飙升 按 CPU/IO 密集公式起步（§2），再接 activeCount/queueSize 监控修正
CallerRunsPolicy 用在 Tomcat 入口线程池 池满后请求线程自己跑任务 → Tomcat worker 全被占住 → 整个服务雪崩，健康检查都进不来 面向用户的入口池用 AbortPolicy + 限流降级；CallerRuns 只用在可背压的异步链路
未自定义 ThreadFactory 线程名全是 pool-N-thread-M，jstack 里根本分不清是哪个池、哪个业务，告警串扰 NamedThreadFactory 加业务前缀（如 io-pool、order-worker），并挂 UncaughtExceptionHandler 兜底日志
Future.get() 不带超时 下游 RPC 卡死 → 调用线程永久阻塞，线程池被慢慢掏空，连锁拒绝 get(long, TimeUnit) 设超时 + exceptionally/handle 兜底降级
