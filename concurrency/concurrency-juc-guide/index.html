1. 概念说明

并发编程三个核心问题：

  • 原子性：一个操作不可分割（i++ 不是原子的）。
  • 可见性：线程修改了变量，其他线程能看到（CPU 缓存导致看不到）。
  • 有序性：指令重排导致执行顺序与代码不一致。

Java 内存模型（JMM）：线程共享主内存，各自有工作内存（缓存）；volatile、synchronized、Lock 通过内存屏障保证可见性与有序性。

选择铁律：能用 synchronized 就不用 Lock（jdk8+ 已优化）；能用并发容器就不用手动加锁；锁粒度越小越好。

3. 锁深入

3.1 synchronized 演进（锁升级）

现代 JVM 已自动优化，代码层无需关心；jdk15+ 废弃偏向锁。

synchronized 的优化史就是一部「能不加锁就不加」的历史，锁状态记录在对象头的 Mark Word 里：

状态 触发条件 手段 代价
无锁 无竞争 —— 0
偏向锁 始终同一线程进入 Mark Word 记线程 ID，之后零成本进出 第二个线程出现时需撤销（全局安全点）
轻量级锁 多线程交替进入 栈上 Lock Record + CAS 自旋 自旋空转烧 CPU
重量级锁 真正并发竞争 / 自旋超限 monitor（操作系统互斥量），线程阻塞 内核态切换，最贵

升级只升不降（除偏向撤销）。JDK 15 起偏向锁默认关闭（JEP 374），JDK 21 下你实际面对的是「轻量 ↔ 重量」两档。启示：JVM 一直在把 synchronized 往 ReentrantLock 的性能区间拉，二者差距早已不是当年的量级。

3.2 ReentrantLock（可中断/超时/公平）

3.3 AQS：JUC 锁的共同骨架

ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 的骨架都是 AQS（AbstractQueuedSynchronizer）——理解它等于理解半个 JUC：

  1. 一个 volatile int state：锁的抽象状态。ReentrantLock 里 0=自由、N=重入次数；Semaphore 里是剩余许可数；CountDownLatch 里是剩余计数。
  2. 一条 CLH 变体的 FIFO 等待队列：抢锁失败的线程封装成 Node 入队并 LockSupport.park 挂起，持有者释放时唤醒后继。
  3. 模板方法 + CAS：acquire() 先调子类的 tryAcquire()（CAS 改 state），失败入队；release() 改 state 后唤醒队首。公平与非公平的唯一区别：非公平在 tryAcquire 前先「插队」抢一把——抢到就省一次入队，吞吐更高，代价是可能饿死排队线程。

Condition 则是挂在同一把锁上的另一条等待队列（await 出同步队列进条件队列，signal 移回）——这就是「多 Condition 精准唤醒」的由来。

3.4 读写锁（读多写少）

3.5 StampedLock（更优，乐观读）

注意事项（容易被忽略）：

  • 不可重入：同一线程重复 writeLock() 直接把自己锁死；
  • 不支持 Condition，stamp 不能跨锁实例混用；
  • 乐观读校验失败必须升级为悲观读，不能 validate 失败后裸读；
  • 锁内禁止长耗时 IO——StampedLock 的等待是自旋风格，阻塞会拖垮所有等待者；
  • 中断敏感场景用 tryReadLock / tryWriteLock 带超时版本，readLock() 对中断不敏感。

3.7 锁选型速查表

锁类型 核心特点 适用场景
synchronized 简单自动加解锁、可重入 简单临界区、低并发、快速开发
ReentrantLock 公平/非公平、超时、中断、Condition 复杂同步、需要超时/可中断、生产者消费者
ReentrantReadWriteLock 读读共享、读写互斥 读多写少：本地缓存、配置字典
StampedLock 乐观读、高性能 超高并发、读极多写极少
AtomicXXX CAS无锁、高性能 计数器、自增序号、单个变量原子操作
volatile 可见性+禁止重排 状态标记、双重检查单例

容器 特性 适用
ConcurrentHashMap 分段/粒度锁，读并发 缓存、KV

7. Java 21 虚拟线程（新选择）

适用：IO 密集（HTTP 调用、DB 访问）场景吞吐大幅提升；CPU 密集无收益。Spring Boot 3.2+ 可开启 spring.threads.virtual.enabled=true。

7.1 虚拟线程时代的锁（synchronized 钉住问题）

JDK 21 虚拟线程（Loom）落地后，锁的选择多了一条新约束——synchronized 钉住（pinning）：

  • 虚拟线程在 synchronized 块内发生阻塞（IO、sleep、网络调用）时，JDK 21~23 无法把它从载体平台线程上卸载——载体线程被一并占用，平台线程打满后，「百万并发」就没意义了；
  • JDK 24（JEP 491）已修复：synchronized 内阻塞也能正常卸载。仍在 JDK 21/22/23 的代码按下表处理：
场景 建议
synchronized 内只做内存计算（极短临界区） 保留 synchronized，不会钉住
synchronized 内可能阻塞（IO、RPC、sleep） 换成 ReentrantLock（lock/unlock 不钉住载体线程）
新写的并发代码 默认 ReentrantLock，与虚拟线程、超时、可中断全兼容

排查 pinning：启动加 -Djdk.tracePinnedThreads=full，命中时打印完整堆栈。

8. 常见误用与陷阱

坑 现象 解法
volatile 当计数器用（count++） 多线程下结果偏小——volatile 只保证可见性、不保证 ++ 原子性 改用 AtomicInteger / 高竞争用 LongAdder（§2.2）
ConcurrentHashMap 复合操作未原子化 先 containsKey 再 put，两步之间被插入 → 仍然出现重复或覆盖 用 putIfAbsent / compute / merge 等原子方法，锁粒度交给内部实现
ReentrantLock 忘记 finally unlock 异常路径下锁不释放 → 后续线程全部阻塞，等价死锁 lock() 紧跟 try，finally 中 unlock()（§3.2），可用 try-with-resources 风格包装
StampedLock 乐观读后改写没升级 tryOptimisticRead 失败后直接写值 → 乐观读期间已被写过 → 数据错乱 乐观读仅用于纯读；写必须走 writeLock()；validate 失败后升级读锁再读（§3.4）
CopyOnWriteArrayList 用在写多场景 每次写都复制底层数组，写放大严重 → CPU 飙升、GC 频繁、内存抖动 读多写少才用它（白名单/配置）；写多用 ConcurrentLinkedQueue 或 Collections.synchronizedList
synchronized 锁错对象 锁了不同实例，并发问题依旧；或锁 String/Integer 缓存对象导致”意料之外的互斥” 锁私有 final 监视器对象 private final Object lock = new Object()；或明确锁当前类 Xxx.class（静态）
wait/notify 不在循环中判断条件 虚假唤醒（spurious wakeup）或多线程抢占 → 条件不满足仍继续往下跑 永远用 while (条件不满足) wait()，不要 if；用 Condition.await() 同样规则
notify() 而不是 notifyAll() 多个等待条件的线程互发通知，只有一个被唤醒，另一个永远挂起 除非只存在一种等待条件且线程数严格为 2，否则一律 notifyAll() / signalAll()
ThreadLocal 不 remove Tomcat/Netty 线程池复用时上下文串号、内存泄漏 try 里用，finally { tl.remove(); } 必写；跨请求不要依赖 ThreadLocal 传值
死锁：锁顺序不一致 A 线程拿 lock1 再 lock2，B 线程拿 lock2 再 lock1 → 双方互等 统一全局加锁顺序；用 tryLock(timeout) 加锁失败回退
共享非线程安全工具类 把 SimpleDateFormat、HashMap 当静态字段共用 → 数据错乱 SimpleDateFormat 替换为 DateTimeFormatter（线程安全）；共享集合统一用 JUC 并发集合
CountDownLatch/Semaphore 数量对不上 await() 不结束或过早结束 每一条异常路径都必须 countDown() / release()（放进 finally）
Future.get() 不加超时 单个线程 hang → 整个线程池被拖死 future.get(5, TimeUnit.SECONDS) + 捕获 TimeoutException 并记录/取消任务
虚拟线程里在 synchronized 中做 IO JDK 21~23 载体线程被 pinning 占满，吞吐暴跌 阻塞路径换 ReentrantLock；或升级 JDK 24+（见 §7.1）
