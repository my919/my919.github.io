基于线程池的任务流程编排实战

并发 · 基于线程池的任务流程编排实战

线程池负责「并发执行」，但多个任务之间还有先后、依赖、汇聚、容错。本文用 CompletableFuture + 隔离线程池，把「串行/并行/汇聚/DAG」四类编排讲透：详情页聚合、订单→物流、下单履约全流程。代码带详细注释。

前置阅读：Java 线程池实战与调优（参数怎么定、拒绝策略、监控），本文聚焦「拿到线程池之后怎么编排任务」。

1. 什么是任务流程编排

单个任务扔进线程池就完事的叫「异步」；多个任务、彼此有依赖、最后要拼成一个结果的才叫「编排」。

问题 含义 对应手段

数据 上游结果怎么传给下游 thenApply / thenCombine / 持有 future 引用

2. 为什么用 CompletableFuture 而不是裸 Future

CompletableFuture 既是「结果容器」又是「编排节点」：一个节点完成，可以自动触发下游节点，不需要一个线程在那干等——这正是它和裸 Future 的本质区别。

常用算子速查（先混个脸熟，后面逐个实战）：

算子 作用 关键点
supplyAsync / runAsync 起一个有/无返回值的异步任务 一定显式传线程池
thenApply 拿结果做转换（T→R） 同步，在完成线程里跑
thenAccept 拿结果消费（无返回） 收尾、打日志
thenCompose 串依赖：结果→新的 CF（拍平嵌套） 类似 Optional.flatMap
thenCombine 两个独立 CF 都好后合并 汇聚双任务
allOf / anyOf 等全部 / 等任一 allOf 无返回值，结果要自己留引用
exceptionally 异常兜底（只在出错时走） 返回默认值，恢复正常流
handle 成功失败都处理（BiFunction） 能同时拿到结果和异常
orTimeout / completeOnTimeout 超时抛异常 / 超时给默认值 JDK 9+，链式超时

命名规律：带 Async 后缀的方法（如 thenApplyAsync）会把下一步丢进线程池执行；不带的（thenApply）在「上游完成线程」或「当前线程」里直接跑。编排 IO 任务时统一用 Async 版并指定池，最可控。

3. 先备线程池：编排要「多池隔离」

编排的第一条军规：编排线程池和任务线程池分开，且绝不在池线程里阻塞等子任务。

为什么不能「父子任务用同一个有界池 + 在父任务里 join 等子任务」——这会线程饥饿甚至死锁：

永远不要用 supplyAsync(task) 不传线程池：那会落到 ForkJoinPool.commonPool()——全 JVM 共享、并行度只有 CPU核数-1、线程是守护线程，跑阻塞 IO 会拖累所有用到它的框架（包括 parallelStream）。

3.1 铁律：每个耗时任务都必须带超时——用提交器强制，而不是靠自觉

「记得加 orTimeout」是口头约定，code review 总会漏。把超时做成提交方法的必传参数，编译期就无法构造一个「没有超时的耗时任务」：

本文后续所有耗时调用都走 timed(...) / timedOr(...)，不再出现裸 supplyAsync。超时值按 §8 的分层预算给，且仍要保证 RPC/DB 客户端自身 deadline ≤ 这里的 timeout——提交器超时只让 future 完成，真正释放线程靠客户端 deadline（§8.1）。

4. 实战一：详情页聚合（并行无依赖 + allOf）

商品详情页要查：基础信息、库存、价格、评论，四个 RPC 互不依赖。串行耗时是 4 个之和，并行取最慢的那个。

5. 实战二：串行依赖（thenCompose，避免嵌套地狱）

查完订单，才能拿订单号去查物流——典型的 A → B。

什么时候用 thenCompose 而不是 thenApply：下一步本身是「异步操作」（返回 CompletableFuture<R>）时用 compose 拍平；下一步只是「对结果做同步计算」（返回 R）时用 apply。

6. 实战三：双源汇聚（thenCombine）

到手价 = 商品价格 + 营销活动，两个接口独立，都回来后才能算。

thenCombine 只接受两个任务；三个及以上的汇聚，用 allOf 做屏障 + 各引用取结果（见 §4），或多次 combine 串联。

7. 容错：别让一个慢/挂的子任务拖垮整个页面

allOf 有个大坑：任意一个子任务异常，allOf 整体异常，而且后面 join() 取其它正常结果时也会被带崩。详情页通常要求「评论挂了，评论区显示空，其它照常展示」——必须逐项降级。

三种容错算子的区别：

算子 触发时机 能否拿到异常 返回
exceptionally(fn) 仅异常时 能 兜底值，恢复成正常流
handle((v,ex)->r) 成功/失败都触发 能 统一处理结果或兜底
whenComplete((v,ex)->{}) 成功/失败都触发 能，但不能改结果 用于旁路：日志、埋点

经验：核心数据（价格、商品）失败可以让页面整体报错；边缘数据（评论、推荐）失败就地降级。按业务重要性决定「整页失败」还是「局部兜底」。

8. 超时：每个子任务都要有上限

没有超时的编排，等于把整个接口的命运交给最慢的那个下游。铁律：每一个耗时任务都必须有超时——不要靠手写 orTimeout 时记时忘，统一走 §3.1 的 timed(task, pool, 超时)，让超时成为编译期必传参数。下面看两个底层算子的区别。

8.1 耗时（慢）任务的异常处理与超时专项

allOf 的总耗时 = max(每个子任务)——木桶的长板决定整体耗时：一个本来 100ms 的页面，可能因为某个 3s 的慢任务被整体拖到 3s。对耗时任务要有四个专门处置：

手段 做法 解决什么
池隔离 慢任务用独立线程池，别和短平快查询共用 慢任务占满线程时不拖垮快任务（§3）
强超时 每个慢任务 orTimeout 给硬上限（只是阈值更大），且客户端超时更短 不无限等，不把命运交给下游
降级 / 异步化 非关键慢任务超时给默认值；重活转「后台任务 + 立即返回」 不阻塞用户主链路
放弃等待 超时后 future 立即完成，编排层不再等；但 CF 不会中断工作线程（见下方说明），真正停任务靠客户端 deadline / 协作式取消 别让调用方继续干等

重活不要放在用户请求链路里 allOf 干等——典型如批量导出、大报表生成：提交后立即返回「处理中」，任务在专用慢任务池后台跑，完成后回调落库/发通知，前端轮询或收通知。

关键认知：CompletableFuture.cancel(true) 不会中断工作线程。 它的 mayInterruptIfRunning 参数在 CF 实现中没有任何效果——cancel 只让 future 以 CancellationException 完成，底层任务仍在线程池里继续跑；orTimeout 也一样：future 在 10 分钟时超时了，generate 可能还在后台跑到第 12 分钟。要真正停下底层执行，必须让任务本身配合：

  • 任务内调用可响应中断的阻塞 API，并由持有工作线程的一方中断它（executor.submit(...) 返回的 FutureTask.cancel(true) 才会真正 interrupt() 线程，CF 不会）；
  • 或给 HTTP/RPC 客户端设更短的 deadline，让客户端自己断开连接、释放线程；
  • 或在长任务循环里做协作式取消（定期检查取消标志）。

所以 §8 那句「客户端超时 ≤ CF 超时」是硬要求：真正兜底资源释放的是客户端 deadline，CF 超时只负责让编排层不再等待。

异常必须拆到根因，但先分清你在哪个位置拿异常：

位置 拿到的是什么 要不要解包
join() 调用端 CompletionException（get() 是 ExecutionException），真因在 getCause()，可能多层嵌套 必须解包
exceptionally / handle / whenComplete 回调内 通常已经是原始异常（orTimeout 给的就是 TimeoutException 本身，Supplier 抛出的也是原样透传） 通常不用；但经 thenCompose 嵌套组合后可能仍包着一层，统一解包最稳

多源竞速：anyOf 有坑，失败兜底要用「first-success」模式。

超时 ≠ 任务没执行——超时只代表「我没在规定时间内拿到结果」，下游可能已经成功、只是响应迟到（最典型的超时歧义）。因此：

  • 超时后的重试必须幂等（幂等键 / 唯一请求号 / 去重表），尤其是写操作和耗时任务，否则一次超时可能触发两次扣款、两次发货；
  • 非幂等操作超时后，优先查最终状态（查单、对账），而不是直接重放请求；
  • 降级即使对用户静默，也要留超时计数/告警（上面 timeoutCounter），否则下游持续超时时你会完全无感。

9. 实战四：复杂 DAG——下单履约全流程

真实流程：先风控；风控通过后，扣库存、锁优惠券、冻结积分并行；三者都成功后建订单；最后发消息/通知。

这一段把全文要点全用上了：

  • thenComposeAsync 表达「风控通过才进入下一阶段」的串行闸门；
  • 阶段②三个 supplyAsync 并行，allOf 做阶段屏障；
  • mark 用 handle 把各子任务成败拍平成 Boolean，从而能在阶段③判断哪些成功、哪些要补偿，而不是一异常就全崩；
  • 失败走补偿（Saga 思路）：锁了券、冻了分但库存没扣成，要把成功的步骤回滚；
  • whenCompleteAsync 发消息是旁路动作，不阻断主流程（最终一致性交给 MQ）；
  • 最外层 orTimeout + exceptionally 给整条链路兜底。

生产里「扣库存/退款/发券」这类跨服务的一致性，应由 Seata/TCC/本地消息表等方案保障，上面的 compensate 是编排层的补偿示意。详见微服务分类的分布式事务文章。

10. 实战五：相同资源只算一次——Singleflight（请求合并 / 单飞）

场景：一个请求链路（或多个并发请求）里要多次用到「同一个 key 的结果」——详情页 4 个并行分支里有 2 个都要查商品 1001、缓存失效瞬间 1000 个请求同时打向 DB、批量循环里同一条用户数据被重复查询。让相同 key 的任务只有第一个真正执行，其余等待并共享同一份结果，这就是 Singleflight（Go 里叫 singleflight、Guava 里叫 LoadingCache.getAll 的 in-flight 合并、Hystrix 叫 request collapsing）。

使用——同一个商品查 3 次，DB 只执行 1 次：

SingleFlight 里的两层超时别混淆：leader 的「执行」由组件 ceiling 兜底（§10.3，保证僵尸可自愈）；每个调用方的「等待」由自己的 orTimeout 决定（③，互不连坐）。execute() 故意不内置「每个调用方各自的等待超时」——因为它返回的是一个共享 future，不同调用方预算不同，只能各自在派生视图上加。

10.2 四个必须处理对的细节

① 摘除时必须用 remove(key, f) 做实例比对（防 ABA 误删）

② 失败也要摘除，且失败会传播给所有等待者

whenComplete 不区分成败，异常时同样摘除——下一次调用会重新尝试，不会被一次失败永久污染。代价是：第一个任务失败，所有共享者都收到同一个异常。这是期望行为，各等待者按自己的业务分别降级即可（同一个 CompletableFuture 上挂多个 exceptionally 互不影响，各自拿到自己的兜底值）。

③ 超时加在等待者的派生 future 上，别动共享源 future

orTimeout / completeOnTimeout 返回的是新的派生 future，不会反向影响 map 里的源 future——这恰好是我们要的：

超时预算的真正执行时长由 loader 内部的客户端 deadline 控制；等待者的 orTimeout 只决定「我等多久」。

④ 执行器必须「异步入队、立即返回」——任务绝不能在提交者线程内联执行

computeIfAbsent 执行 mapping 函数期间会锁住该哈希桶，且 mapping 返回后条目才正式入表。正确姿势下 mapping 只做「入队 + 返回 future」，毫秒级返回；一旦 loader 在当前线程内联跑掉，会出两类问题（都已在 JDK 21 实测）：

判定标准只有一句：传给 SingleFlight 的 executor，其 execute() 必须保证任务在另一个线程稍后执行，绝不能在调用栈里同步跑完。 业务池用 CallerRunsPolicy 做背压没问题，但 SingleFlight 要单独配（Abort/Discard 或容量足够、绝不 caller-runs/direct）。

10.3 生产加固：给共享源 future 加内部硬超时（兜底僵尸任务）

③ 解决了「等待者不等了」，但还有一种极端：loader 自己没有有效 deadline 且永久挂起（一个永远不返回的 socket、死循环）。此时源 future 永不完成、whenComplete 永不触发、map 条目永不摘除——它变成一个僵尸条目：之后所有同 key 请求都挂上去、各自等满 200ms 超时，但永远不会触发新的尝试，该 key 在进程生命周期内实质「熔断且无法自愈」。

防御办法是给共享源 future 加一个组件级硬超时（ceiling）——它由 SingleFlight 自己持有，阈值要大于任何等待者预算，正常情况下永远不该触发，只负责保证「任务一定会被摘除、后续一定能重试」。

下面是把前面 ①②④ 与 ceiling 合并后的唯一生产完整版（三者缺一不可，直接抄这一个，不要用前面的分步片段）：

为什么 ceiling 必须加在源 future f 而不是派生视图：源 f 是 map 里持有、决定 whenComplete 何时摘除的那个；只有让 f 自身到点异常完成，才能保证僵尸场景下 remove 一定执行（等待者各自的派生视图被 GC 或放弃，都不影响这条兜底链）。

10.5 边界与选型

关注点 结论
适用 幂等读：查库、查缓存未命中、配置/画像获取；同请求内重复 IO
不适用 写操作（两个「下单」共享一个 future 语义错误）、需要各自独立结果的调用
key 身份要完整 等待者的 loader 会被静默忽略，只跑 leader 的；key 必须编码所有区分维度（资源 id + 租户 + 区域 + 一致性级别等），否则两个租户共用 user:42 会串结果
⚠️ 请求级 ThreadLocal 共享 loader 跑在池线程上，读到的是 leader 提交时传播过去的上下文；等待者自身的 SecurityContext/RequestContextHolder/Locale/MDC 全部被忽略。绝不要在 loader 里读登录态/请求上下文，否则 A 的请求可能带着 B 的权限维度查出数据（越权/串租户）。身份、租户、语言要作为显式参数编进 key（与上一行配合）；跨请求场景不要依赖任何 ThreadLocal
失败后的重试风暴 失败即摘除，下一波请求立刻重试——后端宕机时会形成「失败→摘除→整波重试」的同步脉冲。给失败结果配短 TTL 负缓存、stale-on-error 或重试退避/抖动
空值/不存在 loader 返回 null 也会正常完成并共享；但 in-flight 不缓存它，查不存在的行仍可能反复打库（缓存穿透），用负缓存兜住「不存在」
结果缓存？ SingleFlight 只管「执行中去重」（毫秒级窗口）；要复用历史结果用 Caffeine/Redis，两者可叠加（缓存命中根本不进 singleflight）
执行器 独立池，必须异步入队、提交秒回（AbortPolicy 快速失败）；不要用 CallerRunsPolicy，也不要用 direct/同线程执行器（后者会让条目永久残留，§10.2④）
僵尸兜底 给源 future 加组件级 ceiling 超时，保证条目必摘除（§10.3）
跨请求可观测 合并跨 HTTP 请求时，下游调用只挂在 leader 的 traceId 下，其它等待者链路里看不到这个 DB span；排障时在共享调用处记录全部等待者的 traceId，见 §11
更激进的合并 窗口内多个不同 key 攒成一批一次查回（请求合批 / Request Collapsing），用「时间窗 + 批次 future」实现，但会引入固定等待延迟，仅在高 QPS 批量接口（如批量查库存）下值得
容量防护 极端 key 爆炸（每个 key 只来一次）时 map 条目数等于在途请求数；任务结束即摘除已能回收，必要时给入口限流

11. 链路追踪：traceId 必须跨线程透传

异步编排后，一条请求散落在多个线程，日志没有同一个 traceId 就无法串起来。MDC（SLF4J）基于 ThreadLocal，默认不会带到线程池的新线程，需要在提交任务时手动传递。

Spring 项目可直接用 ThreadPoolTaskExecutor.setTaskDecorator(...)，原理完全相同。除了 MDC，租户上下文、用户身份、Micrometer Tracing 的 scope 也是同样的「提交时拷贝、执行时设置、finally 清理」套路。

坑 现象/后果 正确做法
不传线程池 任务跑在 commonPool，阻塞 IO 拖垮 parallelStream 等 每个 *Async 都显式传池
allOf 单点异常 一个评论挂，整页 500 子任务逐项 handle/exceptionally 降级（§7）
父子任务同池 + join 干等 线程饥饿/池死锁（§3） 链式 Async 回调；等待方与被等方隔离
该用 compose 用了 apply 得到 CF<CF<R>>，join 两次 下一步返回 CF 用 thenCompose
裸 supplyAsync 不给超时 任务挂起则整条链/线程被永久拖死 一律走 timed 必传超时（§3.1）+ 分层预算（§8）
客户端超时 > CF 超时 future 早完成但线程仍被占 下游客户端超时 ≤ CF 超时
MDC 不透传 跨线程日志 traceId 断裂 TaskDecorator 拷贝上下文（§11）
在池线程里 ThreadLocal 忘清理 线程复用导致上下文串号 finally 必 MDC.clear()/恢复
join/get 吞异常 静默失败难排查 handle/whenComplete 记录，或拆 CompletionException 根因

主备竞速直接用 anyOf 主源先失败则整体立即失败，备源白等 用 first-success 忽略中途失败（§8.1）
超时后无脑重试非幂等写操作 超时≠未执行，可能重复扣款/发货 幂等键/查最终状态，而非直接重放（§8.1）
Singleflight 用 remove(key) 摘除 快任务误删下一轮的新条目，合并失效 remove(key, f) 实例比对摘除（§10）

用 direct/同线程执行器 条目入表前 future 已完成，摘除空操作→条目永久残留、永不刷新 executor 必须另起线程异步入队（§10.2④）
