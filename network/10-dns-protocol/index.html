第十章：DNS 详解：解析原理、记录类型与命令/代码示例

概念基础

DNS（Domain Name System）是互联网的「电话簿」：把人类易记的域名翻译成机器路由所需的 IP 地址：

  1. 解决什么问题：IP 难记且可能变化，域名稳定易读；DNS 把二者解耦，换机房只改记录、不改品牌。
  2. 分层委派：根 → TLD → 权威逐级授权，任何递归解析器都能沿这条链问出答案，无单点存储全部数据。
  3. 缓存与 TTL：各级结果按 TTL 缓存，命中秒回；副作用是记录变更存在生效延迟。
  4. 不只有「名字 → IP」：MX（邮件）、TXT（SPF/DKIM/域名验证）、PTR（反向解析）等记录支撑大量基础设施。
  5. 为什么重要：几乎所有 Web 访问的第一步；DNS 故障常表现为「ping IP 正常但域名不通」。

先看一次完整解析的全貌：

递归解析



flowchart LR
  App[应用] --> LR[本地递归解析器]
  LR --> Root[根 DNS]
  Root --> TLD[.com TLD]
  TLD --> Auth[权威 DNS]
  Auth --> IP[A 记录 IP]

一、分层与解析原理

1. 角色

角色 作用
Stub resolver 运行在终端或系统库内，把查询发给递归解析器
Recursive resolver 代客户端迭代问根、TLD、权威 直到拿到答案并缓存 TTL
Authoritative server 对某区（zone）拥有权威数据（NS 委派链终点）

2. 递归解析过程（概念）

查询 www.example.com.（末尾点表示根）时，递归器从根得到 .com 的 NS，再问 .com 得到 example.com 的 NS，最后问 example.com 权威得到 www 的 A / AAAA。结果按 TTL 缓存，命中则直接返回。

更细的时序（客户端只发一问，剩下都是递归器代劳）：



sequenceDiagram
  participant A as 应用(Stub)
  participant R as 递归解析器
  participant Root as 根服务器
  participant TLD as .com TLD
  participant Auth as example.com 权威
  A->>R: www.example.com A?（RD=1）
  R->>Root: www.example.com A?
  Root-->>R: 去问 .com NS（Referral）
  R->>TLD: www.example.com A?
  TLD-->>R: 去问 example.com NS（Referral）
  R->>Auth: www.example.com A?
  Auth-->>R: A 93.184.216.34（AA=1）
  R-->>A: A 93.184.216.34（按 TTL 缓存）

术语：递归查询（RD=1）是客户端对递归器的请求方式；递归器对各级服务器做的是迭代查询——每跳只给「下一层去哪问」的指引。

二、报文与传输（原理）

  • 传统 53 端口：多数查询用 第五章：UDP 协议详解：数据报语义、MTU 与示例代码，报文小、往返少。
  • 响应过大或区域传送等：回退 第一章：TCP 协议详解：连接、可靠传输与编程示例（TCP/53）。
  • DNS 消息结构（概念）：Header（ID、flags、各计数器）+ Question + Answer / Authority / Additional。

首部 12 字节逐字段（RFC 1035）：

字段 位宽 说明
ID 16 请求/响应匹配标识（须随机化）
QR 1 0=查询，1=响应
Opcode 4 0=标准查询
AA 1 权威应答（来自权威服务器时置位）
TC 1 截断：UDP 放不下，提示改用 TCP 重问
RD 1 期望递归
RA 1 递归可用（递归器应答时置位）
RCODE 4 结果码：0 NOERROR、2 SERVFAIL、3 NXDOMAIN
QD/AN/NS/AR COUNT 16×4 四个区段的记录数

ID 用于匹配请求与响应；客户端应随机化 ID 与源端口以降低投毒风险（实现依赖系统解析器）。

三、常见记录类型（作用）

类型 作用
A 主机名 → IPv4
AAAA 主机名 → IPv6
CNAME 别名到另一域名（继续解析目标名）
MX 邮件交换：优先级 + 目标主机
NS 某区的权威服务器
TXT 任意文本（SPF、DKIM、域名验证等）
PTR IP → 主机名（反向解析）

补充两个运维常用类型：SOA（区起始权威，含序列号与刷新/重试/过期计时器，dig example.com SOA 可见）、CAA（声明哪些 CA 允许为本域签发证书，误配会导致证书申请失败）。

注意：CNAME 不能与其他记录共存于同名节点，也不能放在域顶点（apex）——这是 CDN 接入时「裸域无法直接 CNAME」的根因，可用 ALIAS/ANAME（厂商扩展）或扁平化方案绕行。

四、DoT / DoH（加密与传输）

  • DoT（DNS over TLS，RFC 7858）：853/tcp，整流加密。
  • DoH（DNS over HTTPS，RFC 8484）：封装在 第四章：HTTPS 详解：TLS 握手、证书与 openssl/curl 示例 内，常走 443，与网页流量形态相近。

二者可防链路窃听，但递归器仍能看到查询内容；信任模型与日志策略需单独评审。

七、常见故障速查

现象 优先怀疑
ping IP 通、域名不通 DNS 故障：/etc/resolv.conf 错、递归器不可达
改记录后部分用户仍旧 IP TTL 未过期，各级缓存未刷新（属预期行为）
SERVFAIL 权威故障、DNSSEC 校验失败、递归器到权威链路不通
NXDOMAIN 但确定存在 记录名拼错；CNAME 链断裂；区文件未加载（SOA 序列号未递增）
解析慢、偶发超时 UDP 53 被限速/丢包；换 TCP 或 DoH/DoT 验证
境内外解析结果不同 CDN 智能解析（按来源分线路）或链路劫持

八、安全注意

  • 缓存投毒：依赖可预测的 ID/源端口；递归器务必随机化并启用 DNSSEC 校验（RFC 4033+）。
  • 放大攻击：DNS 响应可远大于请求，开放递归器会被当反射放大器——权威与递归分离部署，递归只服务内网。
  • DoT/DoH 防链路窃听，但也让基于 53 端口的安全审计失效，企业需统一出口策略。

本章小结

要点 结论
原理 分层委派 + 缓存 TTL；UDP/TCP 53
作用 名字 ↔ RR；支撑几乎所有 Web 访问
命令 dig、+trace、@server、-x
代码 getaddrinfo 或 dnspython
加密 DoT(853) / DoH(443)，链路防窃听但需重审信任模型

生产关注：权威与递归分离、防缓存投毒、限速、DNSSEC 策略与 TLS 证书透明度。
