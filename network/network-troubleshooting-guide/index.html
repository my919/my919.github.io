1. 排查方法论

网络排障七层（从底到顶）：

核心原则：从底层往上排查，先确认”通不通”，再看”慢不慢”，最后看”应用层错误”。先 ping 通没 → 再端口通没 → 再 curl 看响应。

2. 连通性诊断

关键区分：ping 通 = 网络层通；业务不通还可能是：端口未监听、防火墙拦截、服务没起来。

10. 典型案例

案例：线上接口 502 的定位全过程

问题背景：用户反馈下单接口大面积 502。Nginx 正常监听 443，应用团队坚称”服务没问题”。需要 10 分钟内定界问题在哪一层。

方案：沿”客户端 → Nginx → upstream → 应用进程”逐层收敛，用错误日志和分段 curl 划定边界。

踩坑点：

  • 502 与 504 方向不同：502 是”网关收到无效/拒绝响应”（多为后端挂/拒连），504 是”上游超时”（多为后端太慢），别搞反排查方向。
  • 后端绑定 127.0.0.1 而 Nginx 跑在容器里：容器内的 127.0.0.1 指容器自身——经典”日志全对但一直 502”。
  • 只 systemctl restart 不看死因，故障会带着新姿势再来；先留 journalctl/dmesg 现场。
  • Docker 容器重启策略为 no 时一次 OOM 就永久下线，务必配 --restart=always 或用编排自愈。

11. 常见误用与陷阱

坑 现象/后果 解法
把”ping 通”当成”服务正常” 端口没监听照样 502 分层验证：ping → nc -zv 探端口 → curl 探业务
用 curl -I 测 GET 接口 HEAD 请求被应用 405，误判接口挂了 curl -X GET -o /dev/null -w '%{http_code}'
忽略 DNS 缓存 切换服务器后仍访问旧节点 dig @8.8.8.8 对比权威结果；调低 TTL
抓包只抓 eth0 走 lo/容器网卡的流量漏抓 本机排查用 -i any，容器环境抓宿主机/veth
防火墙规则顺序想当然 先命中 DROP，后面的 ALLOW 形同虚设 按序排查：iptables -L -n --line-numbers / ufw status numbered
无超时的 curl/客户端调用 排障命令自己挂死拖垮终端 一律带 --connect-timeout 3 --max-time 10
