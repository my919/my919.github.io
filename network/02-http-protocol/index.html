第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例

发表于 2026-05-01 更新于 2026-10-26 分类于 计算机网络 本文字数： 11k 阅读时长 ≈ 10 分钟

第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例

概念基础

  1. 应用层的「请求-响应」协议：客户端发请求（方法 + URI + 首部 + 可选正文），服务器回响应（状态码 + 首部 + 正文）；它是 Web 与 API 的基础语义层，每个请求对应一次事务。
  2. 无状态：服务器默认不记住「上一次请求」，会话靠 Cookie、Token、服务端会话存储实现；请求自带全部上下文，天然利于水平扩展。
  3. URI + 方法表达操作语义：GET/POST/PUT/DELETE 等方法对资源（URI）施加操作，配合幂等性约定与状态码（2xx/3xx/4xx/5xx）表达结果。
  4. 可扩展、可分层：首部机制支持缓存、鉴权、内容协商等扩展；传输上先经 TLS 加密即 HTTPS，并把语义承载在 TCP 字节流（HTTP/3 则改由 QUIC 承载）。
  5. 版本演进围绕「效率」：HTTP/1.1 文本协议 + Keep-Alive → HTTP/2 二进制帧多路复用 → HTTP/3 换到 QUIC 传输，语义不变。

先看最抽象的请求响应模型，再逐层深入：

请求响应模型（语义层）



sequenceDiagram
  participant C as Client
  participant S as Server TCP :80/443

  C->>S: HTTP Request 方法 URI 首部
  S->>S: 路由 / 业务处理
  S-->>C: HTTP Response 状态码 首部 Body

报文结构（作用）

1. 请求

  • 请求行：方法、请求目标（路径或绝对 URI）、版本。
  • 首部：Host 在 HTTP/1.1 中语义必填；Content-Length / Transfer-Encoding: chunked 控制正文边界。

2. 响应

常用方法与幂等（原理）

方法 典型语义 幂等
GET 读取资源 是
POST 创建 / 提交 否
PUT 整体替换 是
PATCH 部分更新 视实现
DELETE 删除 是
HEAD 同 GET 无正文 是
OPTIONS 探测支持的方法 是

幂等：多次执行相同请求不应带来额外副作用（仍可能每次返回相同结果）。

状态码（分类）

范围 含义 例
2xx 成功 200、201、204
3xx 重定向 301、302、304
4xx 客户端错误 400、401、403、404
5xx 服务器错误 500、502、503

无状态与资源模型（原理）

HTTP 本身无状态：服务器默认不记住「上一次请求」；会话常靠 Cookie、Token、服务端会话存储实现。REST 风格强调用 URI 表示资源，用 HTTP 方法表达操作（与 第十四章：RPC 概念详解：原理、形态与 JSON-RPC / curl 示例 风格对照）。

内容协商（Agent-Driven Negotiation）

同一个 URI 可返回不同「表示」，客户端用请求首部声明偏好，服务端挑最合适的版本：

请求首部 响应首部 用途
Accept Content-Type MIME 类型偏好（text/html、application/json;q=0.9）
Accept-Encoding Content-Encoding 压缩算法（gzip、br 即 Brotli）
Accept-Language Content-Language 语言偏好（zh-CN,en;q=0.8）
Accept-Charset（已废弃） — 字符集（现代统一 UTF-8）

q 值（0~1）表示权重；服务端无法完全满足时可回 406 Not Acceptable（实践中少见，多数直接降级）。

HTTP 缓存与条件请求

缓存是 HTTP 最重要的性能机制：响应首部声明「能不能存、存多久」，请求首部完成「再验证与条件操作」。

1. 缓存指令（Cache-Control）

指令 含义
max-age=N 可缓存 N 秒（相对时间，优先级高于 Expires）
no-cache 可以缓存，但每次使用前必须向源站再验证（不是「不缓存」）
no-store 真正不写入任何缓存（敏感数据用）
public / private 是否允许共享缓存（CDN / 代理）缓存
immutable 内容永不变（配合带指纹的文件名，浏览器连再验证都省掉）

请求侧还有 Cache-Control: no-cache（强制再验证）等。Pragma: no-cache 与 Expires 是 HTTP/1.0 遗产，现代栈以 Cache-Control 为准。

2. 强缓存与协商缓存

  • 强缓存：Cache-Control: max-age / Expires 未过期时，浏览器根本不发请求，直接用本地副本（开发者工具显示 200 (from disk cache)）。
  • 协商缓存：过期后带 If-None-Match: "etag" 或 If-Modified-Since: 时间 询问源站；未变回 304 Not Modified（无正文），变了回 200 新内容。


sequenceDiagram
  participant B as 浏览器
  participant S as 源站
  B->>S: GET /app.js
  S-->>B: 200 + ETag: "v123" + Cache-Control: max-age=60
  Note over B: 60 秒内强缓存命中，不发请求
  B->>S: GET /app.js（If-None-Match: "v123"）
  S-->>B: 304 Not Modified（无正文）

ETag（内容指纹，强校验）优于 Last-Modified（秒级精度，弱校验）；多机部署时文件修改时间可能不一致，ETag 也常需自定义为内容哈希而非默认的 mtime-size。

3. 条件请求（写并发与乐观锁）

首部 用途 条件不满足时
If-None-Match: * PUT 创建：仅当资源不存在才执行（防覆盖） 412
If-Match: "etag" PUT / DELETE：仅当版本未变（乐观锁） 412 Precondition Failed
If-Unmodified-Since 同上，基于时间戳 412
If-Modified-Since / If-None-Match GET 再验证 回完整 200

4. Range 范围请求（断点续传 / 分片下载）

服务端支持时回 206 Partial Content：

  • Accept-Ranges: bytes 是服务端的能力声明（普通 200 响应里带它表示「支持范围请求」）。
  • 多段请求 Range: bytes=0-99,200-299 回 206 + multipart/byteranges 复合正文。
  • 范围越界回 416 Range Not Satisfiable。
  • If-Range 把「范围条件」与「版本未变」绑定：ETag 变了就整段重新下载，避免拼出「新旧混合」的文件。
  • 手工验证：curl -r 0-1048575 -o part1.bin https://example.com/big.iso。

连接管理：Keep-Alive 与管道化

HTTP/1.0 默认「一请求一连接」，HTTP/1.1 起默认 Connection: keep-alive：同一 TCP 上串行跑多个事务，省掉重复握手与慢启动。

  • Keep-Alive: timeout=5, max=100：服务端提示空闲 5 秒关闭、单连接最多 100 个请求（各实现不一）。
  • 管道化（Pipelining）：HTTP/1.1 允许不等响应连发多个请求，但响应必须按序返回——队头阻塞严重，浏览器普遍禁用，实践中被 HTTP/2 多路复用取代。
  • Connection: close：任一方声明「本响应后关闭连接」，服务端主动关会把 TIME_WAIT 留在服务端，高并发短连接下慎用。
  • 客户端连接数限制：浏览器对单域名通常只开 6 条 HTTP/1.1 持久连接（域名分片曾是绕过手段），HTTP/2 单连接即可，无需分片。

HTTP/1.1 与 HTTP/2（演进）

  • HTTP/1.1（RFC 9112）：文本形态；Keep-Alive 复用连接；队头阻塞限制并发效率。
  • HTTP/2（RFC 9113）：二进制帧；单连接多路复用；HPACK 压缩首部；浏览器场景几乎总与 TLS 同用。
  • HTTP/3（RFC 9114）：基于 第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3（第五章：UDP 协议详解：数据报语义、MTU 与示例代码）。

HTTP/2 的关键细节：所有报文被拆成带 Stream ID 的二进制帧（HEADERS / DATA / SETTINGS / WINDOW_UPDATE / RST_STREAM 等），同一连接上多个流交错传输互不阻塞；首部用 HPACK（静态表 + 动态表 + Huffman 编码）大幅压缩；流控由 WINDOW_UPDATE 帧按流和连接两级控制。但 HTTP/2 仍在 TCP 上——TCP 丢包重传时所有流一起等，这是 HTTP/3 换 QUIC 的根本动机。

常见首部速查

请求侧：

首部 作用
Host 目标主机（虚拟主机路由依据，HTTP/1.1 必填）
Authorization 凭证（Bearer <token>、Basic base64）
Content-Type / Content-Length 正文类型与长度（有 Body 时）
Referer / Origin 来源页面 / 跨域来源（CSRF、CORS 判定）
If-None-Match / If-Modified-Since 协商缓存再验证
Range 范围请求（断点续传）
X-Forwarded-For 代理追加的原始客户端 IP 链（非标准但事实标准）

响应侧：

首部 作用
Set-Cookie 种 Cookie（HttpOnly; Secure; SameSite=Lax）
Location 3xx 重定向目标 / 201 新资源地址
ETag / Last-Modified 资源版本指纹 / 修改时间
Cache-Control 缓存策略
Access-Control-Allow-Origin CORS 放行规则
Content-Security-Policy 等 安全加固（XSS、点击劫持防护）
Retry-After 503/429 时建议的重试等待

HTTPS 性能要点（与首部配合）：TLS 会话复用（session ticket）省握手往返；OCSP Stapling 省证书吊销检查；HSTS（Strict-Transport-Security）强制后续走 HTTPS，消除 301 跳转开销。详见 第四章：HTTPS 详解：TLS 握手、证书与 openssl/curl 示例。

2. 时序：DNS → TCP → TLS → HTTP → 关闭



sequenceDiagram

  participant DNS as DNS 解析器
  participant S as api.example.com :443

  Note over B,DNS: ① 名称解析
  B->>DNS: 查询 api.example.com A/AAAA
  DNS-->>B: 93.184.216.34

  S-->>B: ServerHello + 证书链

  Note over B,S: ④ HTTP 请求 / 响应
  B->>S: GET /v1/users?page=1 HTTP/1.1 Host Accept
  S->>S: 路由 Controller 查库
  S-->>B: 200 OK Content-Type application/json Body

  Note over B,S: ⑤ 连接处置
  alt Connection close
    B->>S: FIN 四次挥手
  else Keep-Alive
    B->>S: 下一请求复用同 TCP
  end

阶段说明：

  1. DNS：若本地/系统缓存无记录，先 第十章：DNS 详解：解析原理、记录类型与命令/代码示例 递归查询得到 IP；否则直接进入 TCP。
  2. TCP 握手：第一章：TCP 协议详解：连接、可靠传输与编程示例 SYN → SYN-ACK → ACK 后，两端才有可用的字节流管道（详见 TCP 文「完整通信流程」）。
  3. TLS（HTTPS）：在 TCP 之上协商密钥；ALPN 常协商 h2（HTTP/2）或 http/1.1。
  4. HTTP 交换：请求/响应作为明文语义（TLS 下被加密后写入 TCP）。
  5. 连接结束：HTTP/1.1 默认 Connection: keep-alive 可复用 TCP；显式 close 或空闲超时后 TCP 挥手。

机制 原理 典型场景
Content-Length 首部给出正文字节数，读满即结束 固定大小 JSON、文件

4. POST 提交 JSON 的完整数据路径

以 POST /v1/users 创建用户为例（仍走 HTTPS）：

5. HTTP/1.1 连接复用 vs HTTP/2 多路复用

HTTP/1.1 + Keep-Alive：多个请求串行占用同一 TCP，避免重复握手，但仍可能队头阻塞（前一响应慢会拖后后续请求）。



sequenceDiagram
  participant C as Client
  participant S as Server
  Note over C,S: 同一 TCP 连接
  C->>S: GET /style.css
  S-->>C: 200 CSS
  C->>S: GET /api/data
  S-->>C: 200 JSON

HTTP/2：在单 TCP 上拆成二进制帧、Stream ID 多路并行（见上文「HTTP/1.1 与 HTTP/2」）。HTTP/3 则把语义映射到 第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3，传输层不再依赖 TCP。

6. 用 curl 对照各阶段

curl 输出段 对应流程

常见面试题速览

  1. GET 与 POST 的本质区别——语义（读 vs 提交）与幂等性；报文层面两者都能带 Body，差异在约定、缓存与重试行为。
  2. HTTP 与 HTTPS——HTTPS = HTTP + TLS；默认 443 vs 80；多一次握手与证书校验；浏览器场景的 HTTP/2 几乎只在 TLS 上启用。
  3. 队头阻塞在哪一层——HTTP/1.1 是应用层串行；HTTP/2 解决了应用层队头阻塞，但 TCP 层丢包仍会整流阻塞；HTTP/3 用 QUIC 流彻底解开。
  4. 301 / 302 / 307 / 308 区别——301/308 永久重定向，302/307 临时；307/308 保证方法与 Body 不变，302 的历史实现可能把 POST 悄悄改成 GET。
  5. Cookie 与 Session——Cookie 是客户端存储凭证的载体，Session 是服务端会话状态，二者常配合使用；HttpOnly / Secure / SameSite 是 Cookie 安全三件套。
  6. 为什么需要 Host 头——一个 IP 可承载多个站点（虚拟主机）；TLS 的 SNI 同理，用于选择证书。
  7. Content-Length 与 chunked 互斥——正文定界二者只居其一；chunked 以 0 长度块结尾，适合流式、未知总长。
  8. no-cache 与 no-store——no-cache 是「存了但每次要再验证」，no-store 才是「完全不存」。
  9. HTTP/2 一定更快吗——不一定：单连接丢包时所有流一起等（TCP 层队头阻塞）；丢包率高的移动弱网下 HTTP/3 优势明显。
  10. 什么时候用 204 而不是 200——操作成功但无内容返回时（如 DELETE、埋点上报），省响应体字节与解析。
  11. POST 为什么不算幂等——重复提交会创建多条资源；需要幂等写时用 PUT 或加幂等键（Idempotency-Key）。
