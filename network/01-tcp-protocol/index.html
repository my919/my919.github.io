第一章：TCP 协议详解：连接、可靠传输与编程示例

发表于 2026-05-01 更新于 2026-10-25 分类于 计算机网络 本文字数： 11k 阅读时长 ≈ 10 分钟

第一章：TCP 协议详解：连接、可靠传输与编程示例

概念基础

  1. 传输层的可靠字节流协议：TCP 位于 IP 之上、应用之下，把 IP 的「无连接、尽力交付」封装成可靠、有序的字节流管道——应用只管读写字节，不感知丢包与乱序。
  2. 面向连接：通信前先三次握手建立连接，结束后四次挥手释放；连接由**四元组（源 IP，源端口，目的 IP，目的端口）**唯一确定，端口解决了「进程到进程」的寻址问题（仅靠 IP 只能定位到主机）。
  3. 可靠如何实现：序号（Sequence）+ 确认（ACK）+ 重传 + 按序重组——每个方向独立编号，ACK 表示「期望收到的下一个序号」，丢失的报文由发送端重传补齐。
  4. 两个「窗口」各管一摊：接收窗口做流量控制（发送速率不超过接收方处理能力）；拥塞窗口做拥塞控制（不压垮网络，算法有 Cubic、BBR 等，依系统而定）。
  5. 为什么选它：需要稳定管道、文件传输、远程登录等「不丢、不乱」的场景选 TCP；可容忍丢包、强实时的场景见 第五章：UDP 协议详解：数据报语义、MTU 与示例代码 与 第十五章：QUIC 详解：基于 UDP 的可靠传输、TLS 集成与 HTTP/3。

TCP 首部逐字段

TCP 报文段 = 首部（20~60 字节） + 数据。首部前 20 字节定长，其后是可选的 Options。

字段 长度 作用
源/目的端口 各 16 bit 进程级寻址，与 IP 组成四元组
Sequence Number 32 bit 本报文段第一个数据字节的序号；SYN 段携带初始序号 ISN
Acknowledgment Number 32 bit 「期望收到的下一个字节」，ACK=1 时有效
数据偏移（Data Offset） 4 bit 首部长度，单位 4 字节；含 Options 时大于 5
标志位 6~9 bit URG / ACK / PSH / RST / SYN / FIN（RFC 3168 又增 ECE / CWR / NS）
Window Size 16 bit 接收窗口通告；配合 Window Scale 可突破 65535
Checksum 16 bit 覆盖伪首部 + TCP 首部 + 数据
Urgent Pointer 16 bit URG=1 时指向紧急数据末尾（现代协议基本不用）
Options 0~40 字节 MSS（仅 SYN 中协商）、SACK、Window Scale、Timestamps（RTT 测量与 PAWS）等

标志位速记：SYN 发起连接、FIN 关闭本方向、RST 异常复位、ACK 确认（建立后几乎所有段都带）、PSH 提示接收端尽快递交应用、URG 紧急指针有效。

建立连接（简化）

SYN 洪泛、半连接队列长度与 SYN Cookie 属于安全与调优范畴。

关闭连接（简化）

任一方发送 FIN 表示本方向不再发送数据；双方都可能 FIN，经过 TIME_WAIT（约 2MSL）状态以便旧报文从网络中消散。RST 表示异常复位。

完整通信流程（与套接字 API 对应）

把「原理」落到一次典型会话上，顺序如下。

  1. 服务端：socket(AF_INET, SOCK_STREAM, 0) → bind 监听地址与端口 → listen（内核维护 LISTEN 与半连接/全连接队列）→ accept 阻塞直至三次握手完成，返回已连接套接字。
  2. 客户端：socket → connect（内核发出 SYN，完成握手后返回）→ 双方进入 ESTABLISHED。
  3. 传数据：send / write 与 recv / read 在用户态与内核发送/接收缓冲区之间搬运字节；TCP 在协议层做序号、确认、重传、按序递交；滑动窗口与拥塞控制限制未确认数据量。
  4. 关闭：任一方 close 或 shutdown(SHUT_WR) 触发本方向 FIN；对端 ACK 后可能仍可收数据（半关闭）；双方都发完 FIN 并确认后，主动关闭端常经历 TIME_WAIT，再回收端口与连接控制块。

状态机：握手与挥手全景

把两端的状态变迁画在一张图上（主动方在左，被动方在右）：



stateDiagram-v2
  [*] --> CLOSED
  CLOSED --> SYN_SENT: 主动方 connect 发 SYN
  CLOSED --> LISTEN: 被动方 listen
  SYN_SENT --> ESTABLISHED: 收 SYN-ACK 回 ACK
  LISTEN --> SYN_RCVD: 收 SYN 回 SYN-ACK

  FIN_WAIT_1 --> FIN_WAIT_2: 收 ACK

  TIME_WAIT --> CLOSED: 2MSL 超时
  ESTABLISHED --> CLOSE_WAIT: 收对端 FIN 回 ACK
  CLOSE_WAIT --> LAST_ACK: 应用 close 发 FIN
  LAST_ACK --> CLOSED: 收 ACK

几个经典追问：

  • 为什么是三次握手而不是两次：两次握手无法让服务端确认「客户端能收到自己的 SYN-ACK」；若一个延迟的旧 SYN 到达，两次握手会让服务端凭空建立连接、浪费资源。第三次 ACK 同时完成了双方**初始序号（ISN）**的互认。
  • 为什么挥手要四次：FIN 只表示「本方向不再发数据」；对端收到后先 ACK，但它可能还有数据没发完，发完再发自己的 FIN——两个方向独立关闭，所以比握手多一次。
  • 为什么 TIME_WAIT 是 2MSL：① 最后一个 ACK 若丢失，对端会重传 FIN，TIME_WAIT 保证还能再回一次 ACK；② 让本连接的旧报文在网络中彻底消散，避免污染相同四元组的新连接。
  • 半开连接与 RST：对端宕机重启后收到旧连接的报文，因无连接记录而回 RST，本端读到 RST 即报「Connection reset」。

可靠性与窗口（原理要点）

  • 字节序号：每个方向独立编号；ACK 表示「期望收到的下一个序号」。
  • 滑动窗口：已发送未确认的字节不能无限堆积；窗口大小受接收方通告与拥塞算法共同约束。
  • Nagle 与延迟 ACK：小报文合并与确认延迟可能增加交互延迟；低延迟场景可在套接字层关闭 Nagle（TCP_NODELAY），需权衡带宽。

拥塞控制：慢启动、CUBIC 与 BBR

发送速率由 发送窗口 = min(接收窗口 rwnd，拥塞窗口 cwnd) 决定：rwnd 由对端通告（流量控制），cwnd 由本端拥塞算法动态调整（拥塞控制）。

1. 经典四阶段（Reno 系）

  1. 慢启动（Slow Start）：cwnd 从初始窗口 IW（现代内核常取 10 个 MSS）起，每收到一个 ACK 近似加一——每 RTT 翻倍，指数增长到阈值 ssthresh。
  2. 拥塞避免（Congestion Avoidance）：超过 ssthresh 后改为线性增长（约每 RTT 加 1 个 MSS），谨慎探路。
  3. 快重传（Fast Retransmit）：收到 3 个重复 ACK 立即重传丢失段，不等超时。
  4. 快恢复（Fast Recovery）：快重传后 ssthresh 减半、cwnd 从 ssthresh 线性恢复，而不是跌回慢启动重来。

2. CUBIC 与 BBR 对照

维度 CUBIC（Linux 默认） BBR（Google，Linux 4.9+）
拥塞信号 丢包（丢包即视为拥塞、减窗） 瓶颈带宽 × 最小 RTT 建模，不以丢包为主要信号
窗口曲线 三次函数，逼近上次丢包点形成「平台期」 按测得带宽 pacing 匀速发送，周期性探测
缓冲膨胀 深 buffer 下倾向填满队列、抬高延迟 主动限制在途字节，抑制 bufferbloat
弱网表现 随机丢包被误判为拥塞，吞吐骤降 非拥塞丢包下吞吐更稳健
部署 内核默认，零配置 需内核支持 tcp_bbr，常配合 fq 队列

3. 治本思路

TIME_WAIT 本身不是病，是协议正确性的一部分。需要处理的是「量太大」：

  1. 客户端侧（主动关闭方）：启用连接池 / Keep-Alive 复用连接，从源头减少短连接；tcp_tw_reuse=1 只对出方向连接有效。
  2. 服务端侧：尽量让客户端先关（响应头不带 Connection: close），把 TIME_WAIT 留在客户端。
  3. 容量侧：每条 TIME_WAIT 只占少量内核内存和一个端口槽位；真正会耗尽的是出方向端口（受 ip_local_port_range 限制）与连接跟踪表（nf_conntrack，若有防火墙）。

常见面试题速览

  1. 三次握手能否只两次——不能：服务端无法确认客户端已收到自己的 ISN；延迟旧 SYN 会导致服务端误建连接。
  2. 挥手为什么是四次——两方向独立关闭；对端 ACK 后可能还有数据要发，自己的 FIN 延后发出。
  3. TIME_WAIT 何时出现、持续多久——主动关闭方，2MSL（Linux 实现约 60 秒）；作用是兜底对端 FIN 重传、等旧报文消散。
  4. CLOSE_WAIT 堆积说明什么——对端已关闭而本端应用没调 close，典型应用层连接泄漏，查代码而非调内核。
  5. SYN 泛洪怎么防——调大半连接队列（net.ipv4.tcp_max_syn_backlog）+ 开启 SYN Cookie（net.ipv4.tcp_syncookies=1）。
  6. accept 从哪个队列取连接——全连接队列（已完成三次握手），其长度受 listen(fd, backlog) 与 net.core.somaxconn 中较小者约束。
  7. TCP 靠什么保证可靠——序号 / ACK / 超时重传与快重传 / 按序重组 / 去重 / 校验和。
  8. Nagle 与延迟 ACK 为何互坑——Nagle 攒小包等对端 ACK，对端延迟 ACK 等攒够数据，两者凑出 40ms 级空等；低延迟场景开 TCP_NODELAY。
