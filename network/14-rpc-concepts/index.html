第十四章：RPC 概念详解：原理、形态与 JSON-RPC / curl 示例

发表于 2026-05-01 更新于 2026-10-25 分类于 计算机网络 本文字数： 3.9k 阅读时长 ≈ 4 分钟

第十四章：RPC 概念详解：原理、形态与 JSON-RPC / curl 示例

概念基础

RPC（Remote Procedure Call，远程过程调用）的目标：让调用远程服务像调用本地函数一样自然：

  1. 解决什么问题：分布式系统中，网络通信的序列化、连接管理、协议细节不应散落在业务代码里，RPC 框架把它们收敛到 stub（存根）。
  2. 如何做到：客户端 stub 把调用序列化成消息发出去；服务端 stub 反序列化、执行、再原路返回——开发者只见函数签名。
  3. 不规定字节格式：JSON-RPC（人可读易调试）、protobuf（见 第十三章：gRPC 详解：Protobuf、HTTP/2 与 grpcurl / Python 示例）、Thrift 等都是可选载体，传输可用 HTTP 或自定义 TCP。
  4. 核心难点：网络不可靠——超时后客户端不知道服务端是否已执行，重试可能重复扣款，必须用幂等设计兜底。

先看一次 RPC 调用的完整链路：

一、原理（.stub 与存根）

RPC 不规定具体字节格式；可由 JSON、protobuf、Thrift 等定义。

一次调用在框架内部到底发生了什么（以典型框架为例）：



sequenceDiagram
  participant App as 业务代码
  participant Stub as 客户端 Stub
  participant Net as 网络层
  participant Skel as 服务端 Stub
  participant Impl as 服务实现
  App->>Stub: add(1, 2)
  Stub->>Stub: 序列化参数 + 生成调用 ID + 附带元数据(traceId/超时)
  Stub->>Net: 发送请求帧
  Net->>Skel: 投递报文
  Skel->>Skel: 反序列化、按方法名路由
  Skel->>Impl: 调用本地实现
  Impl-->>Skel: 返回结果
  Skel->>Net: 序列化响应（含同一调用 ID）
  Net-->>Stub: 投递响应
  Stub-->>App: 按 ID 匹配挂起的调用，返回 3

IDL（接口描述语言）：强类型 RPC 通常先写 .proto / .thrift 契约，再生成各语言 stub——契约即文档、即校验规则、即版本边界。

二、作用与典型场景

  • 微服务内部：低延迟、强类型契约（常选 第十三章：gRPC 详解：Protobuf、HTTP/2 与 grpcurl / Python 示例）。
  • 链上节点：Ethereum JSON-RPC 等文本 RPC。
  • 脚本自动化：轻量 JSON-RPC 管理接口。

三、传输与序列化（对照表）

组合 说明
JSON + HTTP 人可读，易调试
protobuf + HTTP/2 gRPC 默认路径
二进制 + 自定义 TCP 高性能私有协议

序列化选型对比：

格式 体积 速度 可读性 Schema 典型场景
JSON 大 慢 好 无/可选（JSON Schema） 调试、开放 API、低频管理面
protobuf 小 快 差（二进制） 强制 微服务内部、移动弱网
Thrift 小 快 差 强制 跨语言老系统
MessagePack 中 较快 差 无 保留 JSON 结构又要省体积

四、失败语义与幂等（原理）

  • 超时：客户端不知服务端是否已执行；重试可能导致重复扣款。
  • 对策：幂等键、去重表、At-least-once 消费语义与业务配合。

三种投递语义——分布式系统的根本约束是「恰好一次只能在单个参与者内部保证」：

语义 机制 业务要求
At-most-once 不重试，超时即失败 可容忍丢失（日志采集、心跳）
At-least-once 超时重试直到确认 必须幂等（绝大多数业务选此）
Exactly-once 业务层去重 + 状态机 仅能在幂等设计上「等效」实现

配套防护三件套：

  • 超时：每次调用必设截止时间（不是单次重试超时，而是整个调用链预算）。
  • 重试：只对连接失败/明确可重试错误重试；指数退避 + 抖动；限制次数防重试风暴。
  • 熔断：下游持续失败时短路调用，给系统恢复时间（如 Sentinel、resilience4j）。

七、与 REST（第二章：HTTP 详解：报文、方法、版本与 curl/nc 示例 资源风格）对比

RPC REST
建模 过程/动词 中心 资源/名词 中心

落地经验：对内（服务之间、契约可控、追求性能）用 RPC；对外（开放 API、第三方集成、需要 HTTP 缓存与语义）用 REST；两者常以「内 RPC + 网关转 REST」组合出现。

八、生产关注点

  • 服务发现与负载均衡：客户端从注册中心（Nacos、Consul）拿实例列表，配合健康检查剔除坏节点。
  • 观测性：trace id 贯穿调用链（OpenTelemetry），否则「像本地调用」的代价是「排障像猜谜」。
  • 版本演进：protobuf 靠字段编号向前向后兼容；增字段安全、改编号/类型即破坏性变更——契约评审要进 CI。
  • 元数据传递：超时、租户、鉴权 token 走 metadata/headers，别混进业务参数。

本章小结

陷阱 超时后重试 → 幂等设计；Exactly-once 只能等效实现
