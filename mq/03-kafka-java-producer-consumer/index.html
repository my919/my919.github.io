第二章：Kafka Java 发布与消费实战

发表于 2026-07-25 更新于 2026-10-29 分类于 消息队列 本文字数： 11k 阅读时长 ≈ 10 分钟

第二章：Kafka Java 发布与消费实战

概念基础

  1. 客户端只是协议的实现：kafka-clients 是 Kafka 二进制协议的 Java 实现，本身不存消息；版本只需与 Broker 主版本兼容（如 4.x 客户端连 4.x 集群），不必逐位对齐。
  2. 生产者是「异步攒批」模型：send() 只是把消息放进客户端缓冲区（buffer.memory），由后台 Sender 线程按 batch.size / linger.ms 攒批、压缩后发出；get() 等的是「Broker 确认」这个结果，而不是发送过程本身——理解这一点才能解释吞吐与延迟的权衡。
  3. 消费者是「拉模型 + 消费组协调」：一切由 poll() 驱动；Broker 端协调器（GroupCoordinator）负责成员管理与分区分配（再均衡），offset 提交时机决定「重复消费」还是「丢消息」。
  4. 消息去哪里由 key 与序列化器决定：key/value 必须配置序列化器；key 的 hash 决定分区路由——同 key 进同分区，这是「分区内有序」在客户端代码里的落点。

生产消费流程



flowchart LR
  AppP[Java Producer] -->|produce| B[Broker]
  B --> Part[Topic 分区]
  Part --> AppC[Java Consumer]
  AppC --> G[Consumer Group]

发送链路：序列化 → 分区器 → 缓冲攒批 → Sender 发送 → 等确认；消费链路：poll 拉取 → 反序列化 → 业务处理 → 提交 offset。

发布消息（Producer）

要点：

项 说明
acks 0 / 1 / all，权衡延迟与持久性；与幂等常配合 acks=all
key 同 key 映射到同分区，分区内有序
异步发送 producer.send(record, (metadata, exception) -> { ... })
幂等 enable.idempotence=true 时 Broker 按 <PID, 分区, 序号> 去重，重试不产生重复

三种发送方式对照：

方式 写法 适用场景
发后即忘 send(record) 不看结果 日志类可容忍少量丢失
同步 send(record).get() 低频关键消息，简单可控
异步回调 send(record, callback) 高吞吐且需感知失败

可靠性配置：acks、重试与幂等

配置 取值与含义
acks=0 发出即不管，最快也最危险（可能丢）
acks=1 Leader 副本落盘即确认；Leader 宕机且未同步到 Follower 时会丢
acks=all（=-1） ISR 全部确认才返回；配合 Topic 的 min.insync.replicas=2 是「不丢」的基线
retries 可重试错误（网络抖动、Leader 选举）自动重发；4.x 默认 Integer.MAX_VALUE，真正的兜底上限是 delivery.timeout.ms（默认 120s）
enable.idempotence 4.x 默认 true；Broker 按 <PID, 分区, 序号> 去重，重试不重复不乱序；要求 acks=all 且 max.in.flight.requests.per.connection ≤ 5

重试乱序陷阱：不开幂等时，若 max.in.flight.requests.per.connection > 1，第一批失败重试会插到第二批之后——分区内乱序。幂等开启后客户端自动保序，这正是它成为默认值的原因。

吞吐与延迟的三旋钮（发送慢先查这三个）：

参数 默认 调整效果
batch.size 16KB 单批上限；调大提升吞吐、增加延迟
linger.ms 0 愿意等多久凑批；设 5~20ms 常换来数量级吞吐提升
buffer.memory 32MB 总缓冲；打满后 send() 阻塞（上限 max.block.ms）——打满应查下游与网络，而不是扩缓冲

事务：跨分区「要么全成，要么全败」

精确一次（EOS）= 幂等 + 事务。典型场景是 consume-transform-produce：消费 A Topic、写 B Topic、并把 A 的 offset 提交进同一个事务：

代价：下游消费者要读到「已提交」的数据需设 isolation.level=read_committed，且事务有明显吞吐损耗——只在真正跨分区/跨 Topic 的业务里开启。

消费消息（Consumer）

手动提交（处理成功后再提交）：

三种提交方式对比：

方式 特点 风险
commitSync() 阻塞等 Broker 确认，失败自动重试 拖慢消费吞吐
commitAsync() 不阻塞，回调感知结果 失败不重试，可能丢提交
组合：平时 async + 关闭前 sync 吞吐与可靠的折中 生产常用套路

投递语义速查：

语义 做法 结果
at-most-once 先提交 offset 再处理 处理失败即丢消息
at-least-once（默认推荐） 先处理成功再提交 可能重复，业务幂等兜底
exactly-once 生产端事务（见上节） 不丢不重，有性能代价

要点：

项 说明
Consumer Group 组内分摊分区；扩容/缩容触发 Rebalance
offset 处理成功后再提交，接近 at-least-once
幂等 重复投递时按业务主键去重
auto.offset.reset 仅当该组尚无已提交 offset 时生效
poll 循环 两次 poll 间隔超过 max.poll.interval.ms 会被踢出组并触发再均衡

再均衡（Rebalance）：消费组的「重新分桌」

组成员增删、Topic 分区数变化、心跳超时都会触发再均衡：成员先停止消费并上交分区，由协调器重新分配。传统 eager 协议期间整组暂停，抖动源常见排序：

  1. max.poll.interval.ms（默认 5 分钟）内没调 poll() → 被判死亡踢出——单条消息处理慢是第一元凶；
  2. session.timeout.ms 内心跳丢失（GC 停顿、网络抖动）；
  3. 成员频繁上下线（弹性伸缩、滚动发布）。

缓解与正确姿势：

手段 配置 / 写法 效果
静态成员 group.instance.id=instance-1 重启用同一身份回来不触发再均衡，滚动发布利器
增量分配 partition.assignment.strategy=CooperativeStickyAssignor（4.x 默认） 只迁移需要动的分区，其余继续消费，无全局暂停
交还前提交位点 ConsumerRebalanceListener.onPartitionsRevoked() 里 commitSync() 避免「已处理未提交」被重复消费

运行与排障

  1. 确认 Bootstrap 可达，且 advertised.listeners 对客户端可解析（见 第一章：Docker 部署 Kafka 实践）。
  2. 用 Kafka UI 或 kafka-console-consumer 核对 Topic 是否有数据。
  3. 常见错误：
现象 排查
Connection to node -1 could not be established Bootstrap / 防火墙 / advertised 地址错误
消费不到历史消息 auto.offset.reset=latest 且组已有 offset
分区倾斜 key 分布不均，或分区数过少
偶发重复消费 再均衡发生在「已处理未提交」窗口；确认先处理、后提交，业务幂等兜底
CommitFailedException 提交位点时组成员已变化；加大 max.poll.interval.ms 或缩短单批处理耗时

查看消费组积压（lag）：

输出每分区一行，CURRENT-OFFSET（已消费）与 LOG-END-OFFSET（最新）之差即 LAG。排障与告警都围绕它：

  • LAG 持续上涨：消费速度 < 生产速度 → 加消费者实例（不超过分区数）、批处理、查单条耗时；
  • LAG 稳定不为 0：追平中，或个别分区倾斜（查 key 分布）；
  • LAG 为 0 但业务说没收到：多半消费的是别的 group，或被过滤逻辑丢弃。

生产建议把 lag 接入指标系统（Burrow、kafka_exporter 或 Kafka UI 自带的组视图），对核心 group 设阈值告警。

本章小结

要点 结论
生产端 异步攒批；acks + 幂等 定义可靠性；key 决定分区与顺序
消费端 poll 驱动；offset 提交时机决定语义，业务需幂等
再均衡 静态成员 + CooperativeSticky 消除全局暂停；交出分区前 commitSync()
事务 EOS = 幂等 + 事务；consume-transform-produce 一体提交
投递语义 默认 at-least-once：先处理后提交 offset
排障第一步 连不上查 advertised.listeners，收不到查 group / offset
