1. 概念说明：可靠性三环节

消息可靠性三问（面试与生产核心）：

  1. 不丢：消息从生产 → broker → 消费，任何环节都不能丢。
  2. 不重：网络重试导致重复投递，消费端必须幂等。
  3. 不乱：需要顺序的场景保证按序处理。

消息丢失的三个环节：

“不丢”不等于”不重”：保证不丢必然可能重复（网络重试）——所以可靠性 = 不丢（机制保证）+ 不重（幂等消费）。

可靠性铁律：消息丢失的责任最终在消费端兜底——生产者/Broker 尽量可靠，但消费端必须能容忍任意环节的重复与乱序（幂等 + 重试 + 对账）。

为什么确认回调里失败要”补偿”：发布确认只告诉你”这次没成”——不补偿 = 消息悄悄丢了。补偿手段：重试 N 次 → 仍失败进”本地待重发表”（配合对账）。

为什么选 all：acks=all = 主副本 + 所有从副本都落盘才确认——单副本确认（acks=1）在主节点宕机时丢数据。

5. 幂等消费（”不重”的保证）

为什么必须幂等：网络/重试机制天然会重复投递——消费端必须保证”同一条消息处理两次 = 处理一次”。

幂等三方案对比：

方案 实现 适用
唯一键 + 数据库 INSERT IGNORE / 唯一索引冲突即已处理 通用（最可靠）
Redis SETNX setIfAbsent(orderId, 1, TTL) 高频场景
状态机校验 业务状态前置校验（已支付不再支付） 状态明确

为什么”查重→处理→记录”要同一事务：分开了会出现”处理成功但记录失败”→ 下次重发又处理一次（不幂等）。同事务保证原子性。并发场景下”先查后插”不安全，必须用数据库唯一键的原子插入兜底。

11. 常见误用与陷阱

坑 现象/后果 解法
消息重复消费未做幂等 重试/补发导致同一消息处理多次（重复扣库存） 消费端用唯一键 + consume_log 表去重，查重/处理/记录同事务
消息堆积未处理 队列消息数 / consumer lag 持续增长，业务延迟增大 监控 lag 告警；扩容消费者；非核心消息临时降级
顺序消息误解 认为先进先出就全局有序，多消费者时会乱序 按业务 key 路由到同一队列/分区；单消费者或分区内有序
重试风暴 消费失败无限重试，打爆下游 + 坏消息堵队列 重试设上限（max-attempts=3），超限进死信；用延迟队列指数退避
死信队列未监控 坏消息进 DLQ 无人处理，业务静默漏单 DLQ 必须有消费者/监控，数量 > 0 即告警，定期人工重放
消费者位移/ACK 提交时机错误 自动 ACK 下处理失败消息丢失；手动 ACK 忘记 ack 导致重复 禁用自动 ACK，业务成功才 ack；失败走重试/死信
幂等表无限增长 consume_log 只增不删，磁盘爆 按业务保留期定期归档/删除
