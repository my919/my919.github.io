第四章：RocketMQ Java 发布与消费实战

概念基础

  1. 两套客户端 API 并存：rocketmq-client（Remoting 协议） 延续 DefaultMQProducer / DefaultMQPushConsumer 风格，5.x 版本仍与 4.x 用法兼容；另有基于 gRPC 的 rocketmq-client-java（需配合 Proxy）。本文用前者，与国内存量代码一致。
  2. Push 不是真推送：DefaultMQPushConsumer 底层仍是长轮询拉取——框架代你拉取并回调监听器，「像推送」只是封装；拉取节奏、位点管理都由框架接管。
  3. 消费失败有「自动重试 + 死信」兜底：返回 RECONSUME_LATER 或抛异常，消息进入重试队列延时重投（默认 16 次），超限进死信 Topic（%DLQ%组名）——不需要像 Kafka 那样自建重试机制。
  4. 发送三态：同步（等 Broker 确认）、异步（回调）、oneway（不等结果，可能丢）——按业务容忍度选择；顺序消息额外用 MessageQueueSelector 固定 Queue。

生产消费流程



flowchart LR
  AppP[Java Producer] -->|send| NS[NameServer]
  NS -.-> B[Broker]
  AppP -->|Message Topic/Tag| B
  B -->|Push 长轮询| AppC[Java Consumer]
  AppC -->|Consumer Group| B

发送链路：找路由（NameServer）→ 直连 Broker 发送 → 等确认；消费链路：长轮询拉取 → 监听器回调 → 成功 / 重试。

消费消息（Consumer）

要点：

项 说明
CLUSTERING（默认） 同 ConsumerGroup 负载均衡，一条消息只被一个实例消费
BROADCASTING consumer.setMessageModel(MessageModel.BROADCASTING)，组内每实例全量接收
成功 / 重试 返回 CONSUME_SUCCESS；失败返回 RECONSUME_LATER 或抛异常进入重试，超限进死信（%DLQ%组名）
幂等 至少一次投递，业务侧按 msgId / 业务主键去重
重试次数 msg.getReconsumeTimes() 可判断第几次重试，便于降级处理

集群消费 vs 广播消费

CLUSTERING（默认） BROADCASTING
一条消息 组内一个实例消费 组内每个实例都消费
消费进度 位点存 Broker，重启续消费 位点存本地，重启按策略重拉
失败重试 / 死信 支持 不支持（失败即丢）
典型场景 业务消费 本地缓存刷新、配置变更通知

广播模式下每个实例全量接收且没有重试队列兜底——只用于「丢了也无所谓」的通知类场景。

延迟消息（定时投递）

订单超时关单、优惠券到期提醒这类「到点才处理」的场景，不必自己写定时任务扫表：

  • 5.x 用 setDeliverTimeMs 指定任意未来时刻（默认最长 24 小时，可配置延长）；4.x 老写法 setDelayTimeLevel(3) 只有 18 个固定档位（1s 5s 10s 30s 1m ... 2h），新代码不要再写。
  • 原理：消息先落到 SCHEDULE_TOPIC_XXXX，到点由 Broker 投递回真实 Topic——Dashboard 上看到延迟消息「堆积」属正常现象。

事务消息（本地事务与发消息的一致性）

场景：下单要先写库、再发「订单已创建」消息——先写库消息发不出去 / 先发消息库写失败，都会不一致。RocketMQ 用半消息 + 回查解决：

回查是兜底的关键：ProducerGroup 不能随便起名——同组任一存活实例都要能完成回查；executeLocalTransaction 返回 UNKNOW 即触发回查（默认 15 次后按回滚处理）。

  1. 确认 NameServer / Broker 可达：telnet 192.168.1.22 30876（或看 Dashboard）。
  2. 先起 Consumer 再发消息，或发完后在 Dashboard 看 Topic / 消费进度。
  3. 常见错误：
现象 排查
No route info of this topic Topic 未创建，或 NameServer 地址错误
能发不能收 ConsumerGroup / Topic / Tag 过滤不匹配
连接超时 brokerIP1 对客户端不可达（见 第三章：Docker 部署 RocketMQ 实践）
消息进死信 重试 16 次仍失败；监听 %DLQ%demo-consumer-group 做兜底

本章小结

要点 结论
客户端 Remoting 客户端（DefaultMQProducer/Consumer）与 4.x 兼容；gRPC 客户端另选 rocketmq-client-java
发送 同步等确认 / 异步回调 / oneway；顺序消息用 MessageQueueSelector 固定 Queue
消费 Push = 长轮询拉取；失败自动重试 16 次，超限进死信 %DLQ%组名
特性 顺序=固定 Queue + Orderly 监听；延迟=setDeliverTimeMs；事务=半消息+回查
幂等 至少一次投递，业务按 msgId / 业务主键去重
排障第一步 No route info 查 Topic 与 NameServer；收不到查 Group / Tag 与 brokerIP1
