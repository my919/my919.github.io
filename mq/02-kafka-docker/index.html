第一章：Docker 部署 Kafka 实践

发表于 2026-05-01 更新于 2026-10-29 分类于 消息队列 本文字数： 11k 阅读时长 ≈ 10 分钟

第一章：Docker 部署 Kafka 实践

概念基础

  1. KRaft 让单进程成为可能：旧版 Kafka 需要 ZooKeeper + Kafka 两个进程；KRaft 模式下一个容器同时扮演 controller + broker，单机一条命令即可起集群（本章单容器示例的核心）。
  2. 监听器与 advertised.listeners 是第一坑：Kafka 会把 advertised.listeners 里的地址返回给客户端——容器内监听 0.0.0.0 没用，客户端拿到的是这个「广告地址」。本机访问写 127.0.0.1、Compose 内服务访问写服务名、跨网段要双监听，本章三种部署形态的差异全在这一个参数上。
  3. 数据目录与 page cache：数据在 /bitnami/kafka（Bitnami 镜像），必须挂卷；Kafka 依赖磁盘顺序写与 page cache，内存不宜压得过低。
  4. 边界要清楚：单容器 / Compose / 单副本 Deployment 都面向开发验证；生产多 Broker 应使用 Strimzi 等 Operator 或 StatefulSet，不要把单实例 Deployment 当集群扩。

KRaft 架构速览：没有 ZooKeeper 之后

Kafka 4.x 已彻底移除 ZooKeeper（3.x 是过渡双模期），集群元数据由一组 Controller 节点用 Raft 协议自管理：

角色 职责 在本章配置里的位置
Controller 维护元数据日志 __cluster_metadata（Topic、分区、ACL、配置），处理分区选主 KAFKA_CFG_PROCESS_ROLES=controller + KAFKA_CFG_CONTROLLER_QUORUM_VOTERS
Broker 存数据、服务读写 KAFKA_CFG_PROCESS_ROLES=broker
Combined 单进程同时扮演两者 controller,broker（本章单容器正是此形态）

关键点：

  • controller.quorum.voters 格式为 id@host:port[,...]，生产取奇数个（3 或 5）并把 Controller 与 Broker 分开部署；开发环境单节点写 0@... 即可。
  • 元数据变更先写 Raft 日志再生效，Broker 增量拉取元数据——不再有 ZK Watcher 风暴，重启大集群的元数据同步也快了一个量级。
  • node.id 必须唯一且稳定：挂卷重启不能变，Bitnami 镜像由 KAFKA_CFG_NODE_ID 指定；首次启动镜像会自动格式化元数据目录，换数据卷不换 NODE_ID（或反向）会导致 cluster.id 冲突，此时需清空数据目录重来。
  • Controller 端口（示例 9093）只做仲裁通信，永远不要映射给客户端。

Kafka 镜像选择

1. 常用镜像

镜像 说明
apache/kafka Apache 官方维护（Docker Hub：https://hub.docker.com/r/apache/kafka），参数前缀多为 KAFKA_，与发行包行为贴近。
bitnami/kafka Bitnami 打包（https://hub.docker.com/r/bitnami/kafka），参数前缀多为 KAFKA_CFG_，文档与示例丰富，下文默认采用。

2. 版本与标签

  • 开发/学习：固定大版本标签（如 bitnami/kafka:4.0、apache/kafka:4.0.0），避免 latest 漂移。
  • 生产：固定补丁级标签或 digest，并阅读对应镜像的发行说明与安全更新。
  • 4.x 与 3.x 的差异：4.x 彻底移除 ZK 模式与过期客户端协议，存量 3.x 集群升级需先升到 3.9 再跨到 4.x，不可跳级。

3. 监听器与 ADVERTISED_LISTENERS

客户端使用的 bootstrap.servers 必须落在 advertised.listeners 可解析的地址上：

  • 仅本机连 localhost:9092：可把 KAFKA_CFG_ADVERTISED_LISTENERS 设为 PLAINTEXT://127.0.0.1:9092（与下文 「单容器一键部署」 单行示例一致）。
  • Compose 内其它服务连 kafka:9092，同时宿主机还要连：需双监听（下文 「Docker Compose 一键部署」），例如内部 PLAINTEXT://kafka:9092、外部 PLAINTEXT://localhost:9094，并映射两个端口。

4. 资源与持久化

Kafka 依赖磁盘顺序写与充足 page cache；Bitnami 数据目录一般为 /bitnami/kafka。单机开发可适当降低 heap，生产请按吞吐与副本单独规划。

1Panel（推荐）：在 Linux 宿主机上若希望少手写命令、仍以容器方式跑 Apache Kafka，可先安装 1Panel（开源 Linux 运维面板），在 「应用商店」 中选择 Kafka 一键部署：由面板管理镜像版本、数据卷、监听端口与 KRaft 相关环境变量（以当前上架镜像与模板为准）。与下文 docker run / Compose / K8s** 中的 **KAFKA_CFG_ADVERTISED_LISTENERS**、双监听、数据目录与 **heap` 对齐或排障时，自「单容器一键部署」起各节仍可作对照。适合单台 VPS、家庭服务器等「快速起消息流」的场景。

--describe 输出示例解读：

  • Replicas：该分区所有副本所在的 node.id 列表（含 Leader）；
  • ISR（In-Sync Replicas）：当前追得上 Leader 的副本集合——副本掉出 ISR 说明同步滞后或宕机，是可用性告警的第一信号。

启动阶段常见报错速查：

报错 根因与处理
InconsistentClusterIdException 数据卷里残留旧 cluster.id，与当前 node.id 对不上——开发环境直接清空 kafka-data 重来
客户端 Connection refused / TimeoutException 九成是 advertised.listeners 写错（客户端拿到了容器内地址），对照「双监听」一节核对
健康检查反复失败 首启要格式化元数据，适当放大 start_period；再看 docker logs 定位

分区、副本与 ISR：可靠性的三个旋钮

旋钮 作用域 含义与建议
分区数（partitions） Topic 决定并行度上限（消费组内同分区最多 1 个消费者）；创建后只能增不能减，按峰值吞吐估算后留余量
副本因子（replication-factor） Topic 副本总数（含 Leader）；生产至少 3，单机开发用 1
min.insync.replicas Topic / Broker 配合 acks=all 时 ISR 中至少要有这么多副本才确认写入；副本 3 时常设 2，牺牲一点可用性换不丢数据

ISR 是动态集合：Follower 落后超过 replica.lag.time.max.ms（默认 30s 无追平进展）即被踢出，追上后自动回归。unclean.leader.election.enable 默认 false：Leader 宕机只从 ISR 里选新 Leader，宁可分区暂不可用也不让落后副本当选而丢数据——除非业务明确接受丢消息，否则不要为可用性打开它。

多 Broker 集群（多 Compose service 或 K8s 多副本）就绪后，用 --replication-factor 3 建 Topic 再 --describe 观察 Leader 是否均摊，是验证数据面正确性的最快方式。

上生产前的检查清单

本章形态面向开发验证，上生产至少补齐：

项 开发态（本章） 生产态
拓扑 单容器 Combined 3 Controller（独立）+ 3+ Broker，跨机架/AZ
认证加密 PLAINTEXT SASL_SSL（SCRAM 或 mTLS）+ ACL
数据保留 默认 7 天（log.retention.hours） 按磁盘与合规显式设置；审计场景考虑 compact 或分层存储
堆内存 镜像默认 KAFKA_HEAP_OPTS 一般 5~6G，其余内存留给 page cache
监控 无 JMX Exporter + Prometheus：盯 UnderReplicatedPartitions、ActiveControllerCount、ISR 收缩、请求队列深度
多机编排 — Strimzi Operator 管滚动升级与配置漂移
容量规划 单盘混放 日志目录与系统盘分离；按「峰值写入 × 保留期 × 副本数 ÷ 80% 水位」反推磁盘
备份演练 无 Topic 配置/ACL 可导出重建；数据层靠副本与分层存储，而非文件备份

两个最常用告警阈值：UnderReplicatedPartitions > 0（有副本掉队）与 ActiveControllerCount != 1（控制面异常）。

数据保留与磁盘防线

  • 清理策略：cleanup.policy=delete（默认，按 retention.ms / retention.bytes 删旧段）或 compact（按键保留最新值，适合做变更日志）；两者可同时启用。
  • 滚动与检查：日志按 log.segment.bytes（默认 1G）切段，只有非活跃段才会被删——保留期设了不生效，先查是不是段还没滚动。
  • 磁盘水位：Kafka 最经典的「自残」是磁盘写满导致 Broker 宕机。保留策略要按 磁盘容量 × 安全系数（≤80%） 反推，而不是按业务愿望设置。
  • 冷数据：Topic 大且保留期长时评估分层存储（Tiered Storage），把旧段卸载到对象存储，本地只留热段。
  • 检查节奏：log.retention.check.interval.ms 默认 5 分钟，保留配置变更最长一个周期后才生效。
