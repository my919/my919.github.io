1. 概念说明

RabbitMQ 是基于 AMQP 协议的消息队列，以灵活的路由能力著称（对比 Kafka 的线性吞吐，RabbitMQ 胜在交换机模型与低延迟、复杂路由）。

核心模型：

概念 说明
Producer / Consumer 生产者 / 消费者
Exchange 交换机 消息入口，按路由规则分发
Queue 队列 消息存储，消费者从中取
Binding 绑定 队列与交换机的关系（含 routing key）
Virtual Host 隔离环境（租户）
ACK 确认 消费者处理成功后通知删除消息

交换机四种类型：

类型 路由规则 场景
Direct routing key 精确匹配 定向通知
Topic routing key 通配匹配（* 一个词，# 多个词） 分类订阅
Fanout 广播给所有绑定队列 全局通知
Headers 按消息头匹配 复杂条件

3. 概念验证（Web 管理台操作）

  1. Exchanges → 新建 order.direct（type=direct）
  2. Queues → 新建 order.email
  3. Bindings：队列 order.email 绑定交换机 order.direct，routing key = email
  4. Exchanges → 进入 order.direct → Publish message，routing key 填 email
  5. Queues → 进入 order.email → Get messages 可见消息

5. 延迟队列（订单超时关单）

RabbitMQ 4.x 原生支持 x-delayed-message 插件；经典做法：死信 + TTL 实现延迟。

6. 可靠性保障（生产必配）

问题 方案
生产者消息丢失 发布确认（publisher-confirm-type=correlated）+ 失败重发
交换机路由不到队列 publisher-returns + 死信兜底
消费者处理失败丢失 手动 ACK + 重试 + 死信队列
服务器宕机丢失 队列/消息持久化（durable + deliveryMode=2）
消费幂等 消息 ID 去重（Redis setIfAbsent）

8. 落地案例：订单通知中心

选择建议：路由规则复杂、需要多消费者按类型订阅 → RabbitMQ；超高吞吐、日志/事件流 → Kafka。

9. 运维与监控

监控指标：队列堆积数、消费速率、unacked 数量（过高=消费者卡住）、连接数。

10. 典型案例：订单超时自动关单

问题背景：用户下单后 30 分钟未支付，需自动关闭订单并释放库存。若用定时任务轮询订单表，会频繁扫表、延迟不可控（最短 1 分钟）。用 RabbitMQ 的 TTL + 死信队列实现精确延迟关单。

方案：

组件 配置 作用
order.timeout TTL=30min，绑定死信交换机 延迟载体
dlx.exchange direct 类型 过期消息转发
order.timeout.delay 消费者监听 执行关单逻辑

踩坑点：

  1. TTL 必须设在队列或消息上：队列级 TTL 对所有消息生效；消息级 TTL 可单条控制。注意 RabbitMQ 只检查队头消息的 TTL，队头消息 TTL 大会阻塞后面的短 TTL 消息——不同延迟时间建议用不同队列。
  2. 死信队列必须有消费者：若 order.timeout.delay 没有消费者，消息会堆积在死信队列，关单不会执行。必须监控死信队列消息数。
  3. 关单前必须检查订单状态：用户可能在 30 分钟内完成支付，关单消费者必须判断订单当前状态，避免关闭已支付订单。

11. 常见误用与陷阱

坑 现象/后果 解法
消息重复消费未做幂等 重试/补发导致同一订单被多次处理 用消息 ID + 唯一键去重；关单前检查订单状态
消息堆积未处理 队列消息数持续增长，消费延迟增大 监控队列消息数 + 消费速率；扩容消费者；非核心消息降级
顺序消息误解 认为队列先进先出就全局有序，多消费者并发会乱序 单队列单消费者保证有序；或按业务 key 路由到不同队列
重试风暴 basicNack(requeue=true) 无限重投，坏消息堵死队列 重试设上限，超限进死信；用延迟队列做指数退避
死信队列未监控 死信消息无人处理，业务静默漏单 DLQ 必须有消费者/监控，数量 > 0 即告警，定期人工处理
消费者 ACK 提交时机错误 自动 ACK 下处理失败消息丢失；手动 ACK 忘记 ack 导致重复 禁用自动 ACK，业务成功才 ack；失败走重试/死信
