第六章：前端性能优化与监控

概念基础

  1. Core Web Vitals：Google 定义的核心用户体验指标——LCP（最大内容渲染）、INP（交互到下一帧，2024 年起替代 FID）、CLS（累计布局偏移）；三项达标即”良好”体验，影响搜索排名。
  2. 性能预算：给关键指标设上限（如 LCP < 2.5s、JS 体积 < 200KB），超预算即卡 PR；预算是把”性能”从口号变成可执行的工程约束。
  3. 感知性能 vs 实际性能：用户感知的”快”不等于毫秒数；骨架屏、占位、渐进渲染能让等待变得可忍受，先优化感知再优化真实。
  4. 优化层次：加载优化（路由懒加载、代码分割）、渲染优化（虚拟列表、防抖节流）、构建优化（分包、压缩）、运行时监控（上报、告警）四层递进。
  5. 监控闭环：度量 → 定位 → 修复 → 回归，Lighthouse 本地审计 + 线上 RUM（真实用户监控）双轨；没有度量的优化是盲改。承接 第二章：Vite 工程化构建与部署 的构建产物之上。

本章为前端系列收尾，承接 第一章：Vue 3 核心概念与组件开发、第二章：Vite 工程化构建与部署、第三章：前端工程化实战 三章基础，把”能跑”提升到”跑得快且可监控”。

优化闭环：先度量再动手——Lighthouse + RUM 是基线，改一项测一项，警惕”感觉变快”的主观错觉。

常见避坑

坑 现象 正确做法
全量 import bundle 几 MB 按需命名导入，配 Tree Shaking
忘设图片尺寸 布局抖动 CLS 飙升 <img width height> 或 aspect-ratio
字体 FOIT 首屏白屏数秒 font-display: swap + preload
setInterval 动画 掉帧、卡顿 改 requestAnimationFrame
大列表全渲染 滚动卡顿、内存爆 虚拟列表 vue-virtual-scroller
分包过细 HTTP 请求过多 按业务域合并，框架包独立
第三方脚本阻塞 TTFB 高、白屏 加 async/defer，移到 body 末
只测本地 线上慢却不知 上 RUM 真实用户数据 + 告警
过度优化 投入产出失衡 按预算排序，先改影响最大的项
sendBeacon 丢数据 弱网/卸载时上报失败 兜底用 fetch keepalive 或队列重试

本章小结

要点 结论
指标 LCP/INP/CLS 是核心；良好阈值需本地+线上双轨达标
加载 路由懒加载 + 代码分割 + Tree Shaking + 图片/字体优化
渲染 虚拟列表、防抖节流、rAF、用 transform 避免重排
构建 manualChunks 稳定缓存、gzip/brotli 压缩、CDN 部署
监控 PerformanceObserver 上报 RUM；Sentry 捕获错误
闭环 度量→定位→修复→回归；性能预算卡 PR 防回退
