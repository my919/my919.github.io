9. 典型案例：政务服务门户无障碍改造

9.1 问题背景

某政务服务门户收到残障用户投诉与监管整改通知：屏幕阅读器读不出表单、键盘用户无法完成申报、弹窗焦点逃逸到背景页。第三方审计 62/100，要求 45 天整改复检。

9.2 解决方案

按「语义化 → 键盘 → 对比度 → 动态播报 → 自动化门禁」顺序改造：先修结构再修交互，每项修复用 NVDA/VoiceOver 双读屏验证，axe 检查纳入 CI 阻断严重问题。复检得分 96/100。

9.3 关键实现

9.4 踩坑点

  • 用 div+onClick 做按钮，键盘 Tab 永远到不了；全部换语义 button/label 后一大半问题消失
  • 设计稿把焦点 outline 当”丑”去掉了，键盘用户彻底失明，改为 :focus-visible 定制样式
  • aria-label 与可见文本不一致，读屏用户和明眼用户听到两个系统；规则定为继承可见文本
  • 只跑 axe 全绿就交付，人工测试发现”提交成功”没有播报，补 aria-live——自动化只覆盖 30-40%

10. 常见误用与陷阱

坑 现象/后果 解法
div+onClick 当按钮 键盘不可达、读屏不识别 语义 button，键盘行为自带
placeholder 当 label 输入后提示消失，读屏读不到 显式 label for 关联
模态框焦点不困 Tab 跑到背景页误操作 focus trap + ESC + 归还焦点
CSS 去掉焦点轮廓 键盘用户不知道焦点在哪 :focus-visible 定制可见样式
只靠 axe 自动化 覆盖仅 30-40%，问题漏检 自动化门禁 + 人工读屏抽测
状态变更无播报 提交结果读屏用户无感知 role=”alert” / aria-live

12. 总结

12.1 无障碍检查清单

  • 语义化 HTML 结构
  • 所有图片有 alt 文本
  • 表单有 label 关联
  • 键盘可完全操作
  • 焦点顺序合理
  • 颜色对比度达标
  • 不仅依赖颜色传达信息
  • ARIA 角色正确
  • 动态内容有 live region
  • 自动化测试覆盖

12.2 2026 趋势

  • AI 辅助修复：自动检测并建议修复方案
  • 认知无障碍：关注认知障碍用户需求
  • 组件库内置：无障碍成为组件库默认
  • 自动化测试普及：CI/CD 集成无障碍检查
