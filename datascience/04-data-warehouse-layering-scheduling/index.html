第四章：数仓分层与数据管道调度

发表于 2026-05-01 更新于 2026-10-25 分类于 数据工程 本文字数： 6.2k 阅读时长 ≈ 6 分钟

第四章：数仓分层与数据管道调度

概念基础

  1. 数仓分层的目的是治理复杂度：ODS 贴源、DWD 明细、DIM 维度、DWS 汇总、ADS 应用——每层职责单一，下游依赖上游，坏数据能定位到层。
  2. 批流一体靠统一模型：Spark（第一章：Spark 大数据批处理入门）跑离线重算，Flink（第二章：Flink 流式计算入门）跑实时增量，两边共用口径才能「T+1 准确、实时大致对」互为校验。
  3. Kafka 是管道骨架：CDC 与日志先进 Kafka（第三章：Kafka 大数据数据总线）缓冲解耦，再分流到批/流/OLAP 各消费者。
  4. 调度是数据可靠性核心：Airflow/DolphinScheduler 把「每天 2 点跑批」变成有依赖、可重试、有告警的 DAG，而不是一堆 crontab。
  5. ClickHouse 承接分析层：DWS/ADS 汇总结果落到列存引擎供 BI 查询，见 第三章：ClickHouse 查询与性能调优。

本章聚焦管道编排与分层建模方法论；沙箱无 Airflow/Spark 集群，代码按 Airflow 2.x 官方语法书写未逐条运行验证。

一、分层模型



flowchart LR
  S[(业务库/日志)] -->|CDC/采集| O[ODS 贴源层]
  O --> W[DWD 明细层]
  DIM[(维度表)] --> W
  W --> S2[DWS 汇总层]
  S2 --> A[ADS 应用层]
  A --> BI[BI/报表/API]
层 职责 关键约束
ODS 原样落地，不做加工 保留原始格式；按天分区快照
DWD 清洗、去重、脱敏、拆平明细 一行一件事务/事件；只依赖 ODS
DIM 维度表（用户、商品、地区） 缓慢变化维（SCD2）记录历史
DWS 按主题预聚合（日/用户粒度） 口径唯一，重算成本可控
ADS 面向报表/大屏/接口的最终宽表 只依赖 DWS+DIM，不碰 ODS

分层价值：重复计算下沉、口径收敛（改一处全局生效）、问题定位快（ADS 错 → 查 DWS → 查 DWD）。

各层建模案例

二、维度建模：星型与雪花

维度建模三件套：事实表（度量 + 外键）、维度表（描述性属性）、粒度声明（一行代表什么）。

模型 结构 取舍
星型 事实表直连各维表，维表反范式冗余 查询 Join 少、速度快，数仓主流
雪花 维表再拆子维表（商品→类目→行业） 省存储但 Join 链长，仅高基数层级用

事实表三种类型：

类型 语义 案例
事务事实表 一行一事件，可加 订单流水、支付流水
周期快照事实表 定时快照状态，半可加 每日库存、每日账户余额
累积快照事实表 一行跟踪流程全生命周期，可更新 订单从下单→支付→发货→签收各时点

粒度声明是建模第一问：先回答「一行代表什么」（一行 = 一笔订单的一个商品行），再定维度与度量；粒度混乱是数仓后期所有口径打架的根源。

缓慢变化维（SCD）

维度属性会随时间变化（用户换城市、商品改类目），历史报表要不要跟着变？

类型 做法 适用
SCD1 直接覆盖，不留历史 不关心历史的属性（错别字修正）
SCD2 加版本行：生效/失效时间 + 当前标记 需要回溯历史（主流选择）
SCD3 加「前值」列，只记上一次 只需对比新旧两个值的场景

三、CDC 采集：业务库变更入仓

ODS 两种落地形态：每天全量快照（简单、可回溯）与增量 upsert（省存储、需主键合并）——中小规模优先全量快照 + 关键表才做增量。

四、Airflow：把批处理编排成 DAG

调度实践要点：

实践 说明
数据就绪探测 用 Sensor 等「源表分区就绪」（/data/ods/dt=2026-05-01/_SUCCESS）再开跑
幂等设计 所有任务以 dt=日期分区 覆盖写，重跑不产生重复
回刷 补数 = 对历史日期重放 DAG；幂等是回刷安全的前提
分区约定 全公司统一 dt/hh 分区字段，下游依赖检查分区存在性
SLA 与告警 任务超过预期时长告警；失败走 IM webhook（见 第五章：系统运维进阶 的日志与监控）

调度系统选型：Airflow vs DolphinScheduler

维度 Airflow 2.x DolphinScheduler 3.x
DAG 定义 Python 代码，灵活可编程 Web UI 拖拽 + JSON，上手快
扩展性 Operator/Hook 生态极丰富 内置任务类型多（Shell/SQL/Spark/Flink）
多租户/权限 较弱（靠 RBAC 自定义） 原生多租户，适合数据中台
运维 需管 Scheduler/Webserver/Worker 分布式去中心化，国产文档友好
选型倾向 工程团队、代码化偏好 数据分析团队、可视化偏好

共同点：幂等任务 + 分区依赖 + 失败重试 + SLA 告警四件套是任何调度系统落地的底线。

五、批流双跑与一致性

问题 方案
实时与离线口径不一致 统一 DWS 层 SQL 口径，代码同源（或用 Flink 批模式跑离线）
迟到数据 Flink 水位线 + allowed lateness；离线重算兜底
重复写入 Kafka 事务 + 幂等 sink（主键去重），见第三章「精确一次」
大宽表爆炸 ADS 只建高频查询宽表，长尾需求走即席查询

六、数据质量门禁

检查 时机
表行数/波动率 ODS 就绪后
主键唯一、非空 DWD 产出后
口径对账（批 vs 流） ADS 产出后
下游新鲜度 报表侧每天首次访问校验数据日期

质量规则体系化

零散 SQL 检查多了以后难维护，用规则表或框架托管：

规则类别 示例 处置
完整性 非空率 ≥ 99.5% 超阈值阻断下游
唯一性 主键重复数 = 0 阻断
一致性 订单金额 = 明细求和 告警 + 对账任务
时效性 分区在 08:00 前就绪 延迟告警
有效性 枚举值在字典范围内 脏数据进隔离区

工具：自研规则引擎（规则表 + SQL 模板 + Airflow 任务生成）最贴合分层体系；开源侧 Great Expectations（声明式 expectation 套件，可挂进 Airflow）与 Deequ（Spark 原生）是常见选型。质量结果本身也建一张 dqc_result 表，按天趋势监控——坏规则会被时间看出来。

七、分层反模式

反模式 症状 解法
烟囱式直通 报表 SQL 直查 ODS，口径遍地开花 强制 ADS 只依赖 DWS+DIM
层级过多 ODS→DWD→DWS 又插两层中间表，链路一周改不动 层数服务于定位效率，不为分层而分层
维度穿透 DWD 里冗余几十列维度属性 维度归 DIM，Join 在 DWS/ADS 做
口径漂移 同一指标三张表三个数 指标字典 + DWS 层口径唯一收敛
回刷无门禁 补数直接覆盖生产分区 影子分区验证 + 质量门禁通过后切换

本章小结

要点 结论
分层 ODS 贴源 → DWD 明细 → DIM 维度 → DWS 汇总 → ADS 应用；坏数据逐层定位
建模 星型为主、粒度先行；事实表分事务/周期快照/累积快照；维表用 SCD2/拉链 留历史
采集 CDC 入 Kafka；ODS 用「全量快照 + 关键表增量」起步
调度 Airflow DAG + 数据就绪 Sensor + 幂等分区写，重跑回刷才安全；可视化偏好选 DolphinScheduler
批流 实时求快、离线求准；每日对账，超阈值重算
质量 完整性/唯一性/一致性/时效性/有效性五类规则做成门禁，不过检不放行下游

至此 BigData 系列四章完结：第一章：Spark 大数据批处理入门 负责离线、第二章：Flink 流式计算入门 负责实时、第三章：Kafka 大数据数据总线 串管道，本章给管道加上分层与调度。分析层落地见 第三章：ClickHouse 查询与性能调优。
