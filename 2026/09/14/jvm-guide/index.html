1. 概念说明

JVM（Java Virtual Machine）是 Java 跨平台的基石：把字节码翻译为机器指令并管理内存。理解 JVM 是定位内存溢出、CPU 飙高、停顿过长问题的基础。

一次 Java 程序的生命周期：源码 .java → 编译为字节码 .class → 类加载到内存 → 执行引擎解释/编译执行 → 垃圾回收自动清理无用对象。

2. 内存结构（运行时数据区）

区域 共享 作用 溢出错误
堆 是 对象分配 OutOfMemoryError: Java heap space
元空间 是 类元数据 Metaspace
虚拟机栈 否 方法调用帧 StackOverflowError
程序计数器 否 字节码行号 无

3. 类加载机制

加载 → 验证 → 准备 → 解析 → 初始化 五阶段。

双亲委派模型：类加载请求先交给父加载器（App → Platform → Bootstrap），父加载不了才自己加载——保证核心类（如 java.lang.String）不被篡改。

4. 垃圾回收（GC）

判断对象可回收：可达性分析（GC Roots 出发不可达即回收）。GC Roots 包括：栈帧局部变量、静态变量、JNI 引用等。

分代收集（对象年龄小者升代）：新生代用复制算法（Eden/S0/S1），老年代用标记-整理/标记-清除。

JDK 21 可用的收集器：

收集器 特点 适用
G1（默认） 分区化、可预测停顿 大多数服务，默认即最佳
ZGC 亚毫秒停顿、超大堆 大内存低延迟（数百 GB）

7. 实战排查案例

7.1 案例一：内存溢出（OOM）

现象：服务报 java.lang.OutOfMemoryError: Java heap space。

排查流程：

用 MAT / Eclipse Memory Analyzer 打开 heap.hprof，看 Dominator Tree 找占用最大的对象路径，定位到泄漏代码（常见：静态 Map 无限累积、连接未关闭）。

7.2 案例二：CPU 飙高

常见原因：死循环、频繁 Full GC（大量分配）、正则回溯爆炸。

7.3 案例三：频繁 Full GC

常见原因与对策：

原因 对策
堆太小 调大 -Xmx，观察是否稳定
内存泄漏 堆 dump 分析，修复引用
大对象直接进老年代 -XX:PretenureSizeThreshold 或优化代码
系统换页（堆大于物理内存） 保持 -Xmx ≤ 物理内存 70%

8. 调优方法论（不盲目调参）

  1. 先观测：jstat / GC 日志跑一天，看正常基线。
  2. 定位问题：是停顿长（GC）还是吞吐低（业务）还是内存泄漏。
  3. 单点修改：每次只改一个参数，用数据验证。
  4. 对照：压测（wrk / JMH）前后对比 GC 停顿、QPS、P99。

9. 生产基线配置建议

监控指标：GC 频率（Full GC 每天应 < 几次）、P99 停顿、堆使用率曲线。
