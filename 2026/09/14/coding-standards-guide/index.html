1. 概念说明

编码规范是团队统一的代码书写约定，目标是可读、可维护、可审查：代码是写给人看的，规范的代码降低沟通成本、减少低级 bug（命名歧义、魔法数字、空指针）。

规范三层落地：

  1. 文档层：团队约定成文（本文）。
  2. 工具层：编辑器 + CI 自动执行（强制，不靠自觉）。
  3. 审查层：Code Review 检查规范与设计。

核心原则：局部可读性 > 技巧炫耀；显式 > 隐式；简单 > 聪明。

2. 命名规范

2.1 通用

类型 规范 示例
项目/包 小写，点分 com.example.order
类/接口 PascalCase OrderService
方法/变量 camelCase getOrderById
常量 UPPER_SNAKE MAX_RETRY_COUNT
布尔 is/has/can 开头 isActive、hasStock
数据库表 小写下划线 order_item
数据库字段 小写下划线 created_at
URL 路径 小写中划线 /api/user-orders

命名要表达意图：list → listActiveOrders；flag → isVip；禁止 a1/b2、data/data2。

2.2 反例对照

❌ 反例 ✅ 正例 原因
getData() getUserById(id) 表达意图
check() validateEmail() 动词+对象
tmp tempFile 消除歧义
bool flag boolean isEnabled 布尔语义

3. 代码风格规范

3.1 通用规则

3.2 Java 专项

规则 说明
禁止裸 new Thread 用线程池
禁止 printStackTrace 用日志框架
异常不吞 catch 后必须处理或抛出
集合判空 CollectionUtils.isEmpty()
字符串比较 "x".equals(s) 常量前置
事务方法 必须是 public，且不走内部调用
明确 null 语义 用 Optional 或注解

3.3 前端专项（TS/Vue）

  • 组件名 PascalCase，文件 kebab-case 或 PascalCase 二选一统一
  • 类型定义用 interface，不用 any（必须 any 时注释原因）
  • const 优先，禁止 var
  • 样式类名 BEM 或 scoped CSS 内聚

5. Git 提交规范（Conventional Commits）

提交信息四问：改了什么？为什么？影响范围？如何验证？

分支规范：main 只收合并；功能分支 feat/xxx；修复 fix/xxx；版本标签 v1.0.0。

6. 接口规范

项 要求
路径 /api/v1/资源，复数名词
方法 GET/POST/PUT/PATCH/DELETE 语义化
响应 统一 {code, msg, data}
错误码 分段管理（参数/鉴权/业务/系统）
分页 page/page_size + 返回 total
版本 破坏性变更升 v2
文档 OpenAPI 自动生成
鉴权 JWT/Bearer，接口白名单最小化

7. 安全规范（必守底线）

类别 要求
密钥 不提交仓库（.gitignore + 密钥管理）
SQL 注入 全部参数化/预编译，禁止字符串拼接
XSS 前端转义，后端对富文本过滤
越权 每个接口校验资源归属（水平越权）
敏感数据 日志脱敏（手机号/身份证/密码）
密码 BCrypt 加盐哈希，禁止 MD5
依赖 定期扫描 CVE（Dependabot / Trivy）

8. 文档规范

  • README：项目简介、快速启动、目录结构、部署方式
  • 接口文档：OpenAPI 自动生成 + 变更记录
  • 架构文档：架构图 + 关键决策记录（ADR：背景/决策/后果）
  • 数据库变更：迁移脚本 + 变更说明，禁止直接改生产库
