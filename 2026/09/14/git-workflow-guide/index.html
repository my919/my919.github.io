1. 概念说明

单人 Git 只需 commit/branch；团队 Git 的核心是：分支模型（何时建分支）+ 评审流程（代码如何合入）+ 规范（提交/分支命名）+ 保护（主分支防破坏）。

核心原则：

  • main/master 永远可部署（合入即通过 CI）。
  • 每个功能一个分支，生命周期短（1-2 天）。
  • 代码必须经过 Review 才能合入。
  • 提交信息清晰可追溯（关联 issue 编号）。

2. 分支模型对比

2.1 GitHub Flow（最常用，推荐）

流程：从 main 拉分支 → 开发 → 推远程 → 开 PR → 评审+CI → 合并 → 删分支。

2.2 Git Flow（发布节奏固定）

适用：固定版本周期（如月发布）；对持续部署团队过重。

2.3 选择建议

场景 模型
持续部署的 Web 团队 GitHub Flow
版本化发布（SDK/App） Git Flow
中小团队/新项目 GitHub Flow 起步

4. 冲突解决

减少冲突的习惯：分支短命；每天 rebase 一次 main；多人尽量改不同文件。

5. Code Review 实践

Review 重点（不是只点赞）：

维度 检查
正确性 边界条件、空指针、并发安全
安全 SQL 注入、越权、密钥泄露
性能 N+1 查询、大事务、循环里 IO
可维护 命名、重复代码、复杂度过高
测试 关键分支是否有用例

6. 合并策略选择

策略 效果 适用
Squash merge 所有提交压成一个 团队默认推荐
Rebase merge 保留提交、线性历史 需要保留粒度
Merge commit 保留所有提交与分支 记录分支轨迹

7. 保护分支与 CI 联动

GitHub 设置：Settings → Branches → Add rule：

  • 保护 main：禁止直接 push（仅 PR 合入）。
  • 要求 PR 通过 CI 才能合并。
  • 要求 1-2 个 Review。
  • 强制线性历史 / 要求分支最新。

GitLab 对应：Settings → Repository → Protected branches + Merge request approvals。

8. 常见协作问题

问题 解决
提交信息乱写 commitlint + 团队规范
main 被直接 push 保护分支
大 PR 难评审 功能拆小；WIP 标注
合入后发现冲突/坏代码 CI 全量跑；回滚策略（revert）
误提交密钥 git filter-repo 清理 + 立即轮换密钥
