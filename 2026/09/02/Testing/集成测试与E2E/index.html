第二章：集成测试与 E2E 测试

概念基础

  1. 集成测试定义：验证模块间协作是否正确——服务与数据库、服务与服务、模块与模块的接线点，单元测试替不了，E2E 又太贵，集成测试填补中间地带。
  2. E2E：用户视角：从真实入口（浏览器 / App / CLI）走完整业务流，验证「用户真能完成这件事」；它不关心内部实现，只关心端到端结果。
  3. 契约测试：消费者驱动：消费方先写「我期望 Provider 返回什么」的契约，Provider 验证自己满足契约，避免双方联调时的集成地狱。
  4. Testcontainers 革命：用一次性 Docker 容器跑真实依赖（Postgres / Redis / Kafka），让集成测试接近单元测试的速度与隔离性，又不丢真实度。
  5. 测试环境一致性：本地、CI、预发跑的依赖版本必须对齐，否则「我这能过」频发；镜像化依赖是消除环境漂移的根本手段。

本章承接 第一章：测试方法论与单元测试 的单元层，把验证范围抬升到跨模块、真实依赖与浏览器全链路。

一、集成测试策略

模块间集成 vs 外部依赖集成：前者验证自家代码之间的接线（订单服务调用库存服务的客户端）；后者验证自家代码与外部系统（数据库、消息队列、三方 API）的接线。前者偏快、偏纯；后者需要环境，是 Testcontainers 的主战场。

测试双金字塔：金字塔之外再叠一座「契约金字塔」——服务间用契约测试替代大量重型集成测试，E2E 只保留少量关键路径，整体成本骤降。

数据准备：Builder / Fixture / Factory：

  • Fixture：固定数据集（如 users.yml），适合不变的场景底座。
  • Factory：按需造数据（如 OrderFactory.paid()、OrderFactory.pending()），适合多变组合。
  • 原则：测试数据自给自足，不依赖其他测试留下的状态。

事务回滚 vs 清理策略：

策略 做法 优缺点
事务回滚 每个用例开事务，结束回滚 快、干净；不适用于跨连接场景
清理脚本 用例后 TRUNCATE / DELETE 通用；需注意外键顺序
一次性容器 每用例新容器 最隔离；启动开销需用单例缓存优化

二、Testcontainers 实战

真实依赖 vs Mock 取舍：涉及 SQL 方言、事务隔离、连接池行为的逻辑必须用真库；纯协议解析、错误码映射可 Mock。Testcontainers 把「用真库」的成本压到可接受区间。

1. Java：PostgreSQL + Redis

2. Go：testcontainers-go

3. Python：testcontainers-python

性能要点：用 @Container static 或单例缓存容器，跨用例复用，避免每个用例都拉镜像；用 Reuse 模式让本地反复跑更快。

三、API 契约测试

消费者驱动契约测试（CDC）：消费方写「我对 Provider 的期望」→ 生成契约文件 → Provider 在 CI 里拿契约验证自己不破坏消费方。双方无需联调即可发现不兼容。

Spring Cloud Contract：Spring 生态下用 Groovy DSL 定义契约，自动生成 Consumer 桩与 Provider 验证测试，契约随仓库版本管理。

契约 vs Mock vs 集成测试对比：

维度 Mock 契约测试 集成测试
验证对象 消费方单测 双方接口兼容 真实联调
Provider 参与 否 是（CI 验证） 是
脆性 高（自造响应） 低（契约为准） 中
速度 极快 快 慢

四、E2E 测试框架

Playwright 三大优势：跨浏览器（Chromium / Firefox / WebKit 一套 API）、自动等待（元素可操作前自动重试，告别 sleep）、录制（npx playwright codegen 录操作生成脚本）。

定位器最佳实践：优先 get_by_role("button", name="登录")（语义优先）/ get_by_label("用户名")（表单友好），次选 get_by_test_id("order-id")（显式测试锚点），避免脆弱的 CSS / XPath。

1. Page Object + 数据驱动：登录并下单

数据驱动只需把入参抽到参数化夹具，循环跑多组 (用户, SKU, 数量)。

2. Cypress 对比

维度 Playwright Cypress
架构 进程外控制浏览器 浏览器内同源执行
跨域 支持 历史受限
多标签 支持 不支持
语言 多语言 SDK JS / TS 为主
并行 内置分片 需 Dashboard

Cypress 上手快、调试体验好；Playwright 更适合复杂跨域多标签场景与多语言团队。

五、性能测试与压测

四类压测：

类型 目的 典型形态
负载测试 验证预期流量下表现 阶梯升至目标 QPS
压力测试 找崩溃临界点 持续加压至出错
浸泡测试 发现内存泄漏 / 老化 高负载跑数小时
峰值测试 应对突发流量 瞬间尖峰后回落

1. k6 脚本实战

thresholds 是质量门禁：跑完任一阈值未达，k6 以非零码退出，CI 即可拦截。

2. wrk 快速基准

post.lua：wrk.method = "POST"; wrk.body = '{"sku":"SKU-1"}'; wrk.headers["Content-Type"] = "application/json"。

JMeter 分布式压测：单机打不出足够流量时，用一台 master 调度多台 slave 同时发压，结果聚合；适合企业级大流量场景，配置图形化但脚本不如 k6 可版本化。

六、测试流水线与 CI 集成

测试阶段划分：commit → integration → E2E → performance，越往后越慢越贵，触发条件越严：

阶段 触发 内容 时限
commit 每次提交 单元 + 静态检查 < 2 分钟
integration PR / 夜间 集成 + 契约 < 10 分钟
E2E 合并前 / 定时 关键路径 E2E < 30 分钟
performance 夜间 / 发布前 k6 / JMeter 压测 按需

金丝雀测试：发布后先放小比例流量，对关键指标（错误率、延迟）断言一段时间再全量；本质是把 E2E 延伸到生产观测。

常见避坑

坑 现象 正确做法
集成测试共享库 用例互相污染、偶发失败 每用例独立容器或事务回滚
Testcontainers 每用例拉镜像 套件慢到没人跑 用静态 / 单例容器跨用例复用
契约与实现漂移 Consumer 过了 Provider 挂 契约纳入双方 CI，变更先改契约
E2E 依赖固定顺序 改一个步骤全红 每个用例自备数据、幂等可重入
用 CSS / XPath 定位 UI 一改测试崩 用 role / label / test_id
E2E 跑生产数据库 脏数据、误操作 用预发 + 隔离租户 + 自动清理
压测没设阈值 出报告却没人决策 thresholds 当门禁，未达即失败
重试掩盖 flaky 重试几次就绿、问题潜伏 重试打 flaky 标记并限期治理
性能测试只跑一次 数据无意义 多轮取分布，关注 p95/p99 而非均值
流水线全串行 反馈链太长 按 shard 并行，按阶段分层触发

本章小结

要点 结论
集成层 填补单元与 E2E 之间，Testcontainers 是主力
契约 消费者驱动，替代大量重型集成联调
E2E Playwright + Page Object，少而精的关键路径
压测 k6 脚本化、阈值即门禁，关注尾部分位
流水线 分层触发 + 并行 + Allure + 有界重试
一致性 镜像化依赖消除环境漂移

集成与 E2E 是质量护城河的下半段：单元测试保证零件合格，本章保证组装后的系统在真实依赖与用户路径下仍可靠。把这两层与流水线打通，团队的「敢发版」才有了底气。
