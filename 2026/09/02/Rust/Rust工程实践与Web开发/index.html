第四章：Rust 工程实践与 Web 开发

概念基础

  1. Cargo 包管理：官方工具集构建/测试/文档/依赖于一体，配合 crates.io 社区仓库，cargo add/build/test/fmt/clippy 一站式工程化。
  2. 零成本抽象：泛型单态化、迭代器、trait 等高层抽象编译后不引入运行时开销，安全与性能兼得。
  3. 生态选择：CLI（clap）、Web（axum/actix-web）、序列化（serde）、异步运行时（tokio）、数据并行（rayon）、Wasm（wasm-pack）均有成熟方案。
  4. Web 框架选型：axum 与 tokio/tower/serde 生态整合最好；actix-web 性能强、actor 模型；poem/salvo 各有特色。
  5. FFI 互操作：通过 extern "C" 与 C/C++ 混编，bindgen 自动生成绑定，cbindgen 反向生成 C 头文件。

本章聚焦工程实践。所有权与基础语法见 第一章：Rust 入门与所有权系统；类型系统见 第二章：Rust 类型系统与 trait；并发与错误处理见 第三章：Rust 并发与错误处理。

一、模块系统与 Cargo

1. 模块与可见性

  • pub 控制可见性；结构体字段需单独标 pub 才对外可见。
  • pub(crate) 仅对当前 crate 可见，常用于内部共享。
  • 模块可写在单文件里（mod x { ... }），也可放 x.rs 或 x/mod.rs 文件中。

常见避坑

场景 错误 正确做法
unwrap 在生产 unwrap() 遇错 panic 用 ?/expect 带上下文
阻塞 async 运行时 在 async fn 里做 CPU 密集 → 卡死 reactor 用 spawn_blocking
忘 pub 模块私有 → 外部不可见 按需加 pub/pub(crate)
字段未 pub struct 可见但字段私有 每个字段单独标 pub
chrono 缺失 std::time 无日历 → 无法处理日期 引入 chrono crate
Mutex 锁未释放 lock().unwrap() 后长持有 → 阻塞 缩小临界区，及时 drop
编译慢 debug 全量重编 → 慢 用 sccache/cargo-nextest/分 crate
二进制体积大 release 未 strip → 大 strip = true in Cargo.toml
集成测试找不到库 tests/ 无法 use crate lib.rs 导出，集成测试依赖本 crate
镜像过大 用 rust:latest 运行 → 数百 MB 多阶段构建 + distroless/alpine

本章小结

要点 结论
Cargo 统一构建/测试/依赖/文档；Cargo.toml 管依赖，cargo add/test/clippy 日常
模块 mod/use/pub 组织可见性；pub(crate) 限 crate 内
标准库 fs/io、path、env/process、time、fmt、cmp/ops 覆盖日常需求
生态 serde/tokio/axum/rayon/clap 成熟；CLI/Web/Wasm/嵌入式均有方案
axum 路由+提取器+中间件+JSON，与 tokio/tower/serde 整合
tokio 主流异步运行时；join!/spawn/spawn_blocking
serde/sqlx serde 序列化事实标准；sqlx 编译期 SQL 校验
测试 #[test] 单元、tests/ 集成、#[tokio::test] 异步、/// 文档测试
部署 交叉编译 + Docker 多阶段 + 静态链接，镜像可 < 20MB
