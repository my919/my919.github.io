第三章：Agent 工具调用与函数编排

概念基础

  1. Function Calling 是 Agent 的”手”：模型本身只能输出文本，靠工具把意图变成副作用——查数据库、发请求、执行 Shell；没有工具的 Agent 永远只是聊天机器人。
  2. 工具 schema 即接口契约：name / description / parameters 是 LLM 看到的全部信息，模糊的 description 是大部分调用错误根因；schema 一变，模型行为就变。
  3. 并行 vs 串行调用：现代模型一次可返回多个 tool_call，独立工具可并行执行省延迟；有依赖（A 的输出是 B 的输入）必须串行。
  4. MCP 统一工具协议：Anthropic 提的开放协议把”工具定义、传输、客户端”标准化，Server 一次写、多 Client 用，避免每个框架重写工具。
  5. 工具设计决定 Agent 能力上限：颗粒度太粗 LLM 选不到、太细调用爆炸；返回结构化 JSON、错误信息让 LLM 能读懂，工具是 Agent 的”产品接口”。

二、工具设计原则

2.1 好工具 vs 坏工具对比

原则 坏示例 好示例
单一职责 do_anything(action, data) search_orders() / refund_order()
参数最小化 必填 5 个 必填 1 个，其余可选
返回结构化 “成功” {"ok": true, "order_id": "...", "status": "..."}
错误友好 “出错” {"error": "order_not_found", "msg": "..."}
幂等 重复下单扣款 带幂等 key 重复请求安全
命名 proc1 search_orders（动词_名词）

2.2 错误返回要让 LLM 能自救

错误信息含原因 + 重试建议，让模型下一轮能修正参数；纯字符串错误让模型猜半天。

五、MCP (Model Context Protocol) 实战

常见避坑

坑 现象 正确做法
工具参数描述不清 LLM 乱传值 description 写格式 + 示例
返回超长爆上下文 工具返回 100KB 文本 截断 + 摘要 + 摘要回传
无超时工具 hang 一次卡死整个 Agent httpx/subprocess 都设 timeout
并行工具竞态 写同一文件交错 写类工具串行化、加锁
MCP 版本不兼容 Server/Client 报错 锁 mcp 版本，看 protocol 版本字段
沙箱逃逸 容器内跑恶意代码 network=none + 只读挂载 + 最小镜像
工具过多 LLM 选错 30 个工具选不准 分组路由 + 工具检索（meta-agent）
幻觉调用 调不存在的工具 未知工具直接抛错并提示重选

本章小结

要点 结论
工具契约 name + description + schema 是 LLM 看到的全部
调用模式 并行对无依赖工具，串行对依赖链
设计原则 单一职责、参数最小、返回结构化、错误可读
自定义工具 HTTP/DB/Shell/文件各一套，类型注解 + docstring 必备
MCP 工具一次写多 Client 用，stdio/SSE 都支持
安全 pydantic 校验 + Docker 沙箱 + 人在环兜底

本章把工具从设计到执行的全流程拆开讲：OpenAI Function Calling、并行编排、自定义工具族、MCP 协议、安全沙箱。结合 第一章：AI Agent 入门与核心概念 的 ReAct 循环、第二章：Agent 框架实战 的框架封装、第四章：Agent 生产化与工程实践 的部署运维，工具这条主线就闭环了。安全视角更深见 第一章：Web 安全与认证授权：权限、注入、CSRF 在 Agent 工具层同样存在。
