第一章：Web 安全与认证授权

概念基础

  1. 认证（Authentication）与授权（Authorization）是两件事：认证回答”你是谁”——通过用户名密码、短信验证码、生物特征证明身份；授权回答”你能做什么”——在已知身份的前提下，决定能否访问某个资源。先认证、后授权，顺序不能颠倒，且授权模型（RBAC/ABAC）独立于认证方式存在。
  2. OWASP Top 10 是风险地图：它不是漏洞清单，而是 Web 应用最常见、最具影响的十类安全风险归纳（约每 3–4 年更新一次，最新为 2021 版）。把它当作 checklist 能快速自检”我的系统是否覆盖了主流攻击面”，但通过 Top 10 不等于安全，需结合威胁建模与业务实际。
  3. JWT 是无状态令牌：Header（算法）+ Payload（声明）+ Signature（签名）三段 Base64URL 拼接，签名由服务端密钥生成。优点是无需服务端存储会话、易于横向扩展；代价是令牌一旦签发，在过期前无法主动撤销，需配合短期有效期 + 刷新令牌 + 黑名单使用。
  4. Session 与 Token 的取舍：Session 把状态存服务端、靠 Cookie 传递 ID，适合单体应用、易注销；Token（JWT）把状态放客户端、自包含，适合微服务/跨域/移动端，但注销与轮换较复杂。没有银弹，按场景选型而非跟风。
  5. 零信任（Zero Trust）理念：核心是”永不信任，始终验证”——不再以”是否在内网”作为信任依据，而是对每次访问都进行身份认证 + 授权 + 加密 + 持续评估。最小权限、默认拒绝、微隔离是其落地手段，NIST SP 800-207 是其权威参考。

一、OWASP Top 10 速览

下表归纳 OWASP Top 10 (2021) 的十类风险，每项给出一句话描述与典型诱因，便于快速对照自检：

编号 风险类别 一句话描述 典型诱因
A01 失效的访问控制 用户越权访问本不该访问的资源 缺少后端鉴权、依赖前端隐藏菜单
A02 加密失败 敏感数据传输/存储未加密或用了弱算法 HTTP 明文、MD5、硬编码密钥
A03 注入 不可信数据被当作代码执行 拼接 SQL/命令、模板未转义
A04 不安全设计 架构层面缺乏威胁建模与控制 需求阶段未考虑滥用场景
A05 安全配置错误 默认配置、多余功能、错误信息泄露 未关调试、目录列表开启
A06 易受攻击的组件 使用了含已知漏洞的依赖库 不锁版本、不扫描、不升级
A07 身份认证失败 认证逻辑可被绕过或爆破 弱口令、无限重试、凭据填充
A08 数据完整性失败 不可信源更新软件/反序列化数据 未校验签名、反序列化不可信流
A09 日志与监控失败 攻击发生但未被记录与告警 不记关键操作、无告警联动
A10 服务端请求伪造 SSRF 服务端发起请求到任意目标 未限制内网 URL、协议未白名单

提示：Top 10 是入门地图而非审计清单，纵深防御需结合具体业务威胁建模，不可”打钩即安全”。

二、认证与授权基础

1. Authentication vs Authorization

维度 认证（Authentication） 授权（Authorization）
回答的问题 你是谁？ 你能做什么？
时机 先发生 后发生，依赖认证结果
常见手段 密码、OTP、生物特征、SSO RBAC、ABAC、ACL
失败后果 冒充身份 越权访问

2. RBAC 与 ABAC 模型

RBAC（基于角色）：把权限挂在角色上，用户加入角色即继承权限。简单、易管理，适合组织结构稳定的场景。

ABAC（基于属性）：依据用户属性、资源属性、环境属性动态决策，灵活但复杂，适合细粒度、多租户场景。

3. 最小权限原则

无论哪种模型，都应遵循最小权限：默认拒绝，按需授予，定期回收。角色宁可细不可粗，权限宁可少不可多；离职/转岗及时变更，避免”幽灵权限”长期存活。

三、JWT 实战

1. JWT 三段结构

JWT 由 Header.Payload.Signature 三段 Base64URL 编码后用 . 拼接：

  • Header：{"alg":"HS256","typ":"JWT"}，声明算法与令牌类型。
  • Payload：标准声明（sub 主体、exp 过期、iat 签发时间、iss 签发方、aud 接收方）+ 自定义声明。
  • Signature：HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)，防篡改。

注意：Payload 仅做 Base64 编码，不是加密，严禁放密码、手机号等敏感信息。

四、OAuth 2.0 与 OIDC

1. 四种授权模式

| 模式 | 适用场景 | 是否需客户端密钥 |
|——|———|—————-|—————-|
| 授权码 Authorization Code | Web 后端应用（最常用） | 是 |
| 客户端凭证 Client Credentials | 服务到服务调用（M2M） | 是 |
| 密码模式 Resource Owner Password | 高度信任的官方客户端（已不推荐） | 是 |
| 简化模式 Implicit | 纯前端 SPA（已不推荐，改用 PKCE） | 否 |

4. OIDC 与 OAuth 2.0 的区别

OAuth 2.0 只解决授权（委托访问），不解决认证；OIDC 在 OAuth 之上加 ID Token（一个 JWT，含用户身份声明）实现认证。要做”登录”用 OIDC，要做”代为访问 API”用 OAuth 2.0。

五、Session 管理与 Cookie 安全

1. Cookie 安全三属性

属性 作用 推荐值
HttpOnly 禁止 JS 读取 Cookie，防 XSS 窃取 必须开启
Secure 仅 HTTPS 下传输，防中间人嗅探 生产必须开启
SameSite 跨站请求是否带 Cookie，防 CSRF Lax 或 Strict

2. Session 存储

  • 服务端存储会话数据，Cookie 仅存 session_id（随机、足够长）。
  • 多实例部署需把 session 放 Redis 等共享存储，或用粘性会话。
  • 注销即删除服务端 session 与客户端 Cookie，避免”僵尸会话”。

3. CSRF 防护

CSRF（跨站请求伪造）利用浏览器自动带 Cookie 的机制：在用户已登录站点 A 时，被恶意站点诱导对 A 发请求。防护手段：

  • Synchronizer Token：服务端生成随机 token 嵌入表单，提交时校验，攻击者拿不到 token。
  • SameSite Cookie：SameSite=Lax/Strict 阻止跨站带 Cookie，是最简防御。
  • 双重提交 Cookie：token 同时放 Cookie 与请求头，服务端比对两者一致。

对纯 API（前后端分离 + Bearer Token）场景，因不使用 Cookie 传递凭据，通常无 CSRF 风险，但跨站脚本仍需 XSS 防护配合。

常见避坑

坑 现象 正确做法
JWT 存 localStorage XSS 可直接窃取令牌 存 HttpOnly Cookie 或内存，配合短期 access token
Payload 放敏感信息 手机号、权限被 Base64 解出 只放 user_id 等非敏感标识
不校验 exp/iss/aud 令牌被复用、跨服务冒用 验证时显式校验签发方与接收方
接受 alg=none 攻击者伪造无签名令牌 服务端固定算法白名单，禁止 none
Cookie 不设 SameSite 被 CSRF 攻击 SameSite=Lax 起步，关键操作用 Strict
只前端隐藏菜单做鉴权 抓包直接调用接口越权 后端每个接口都做 RBAC 校验
密码用 MD5/SHA1 撞库秒破 用 bcrypt/argon2 加盐慢哈希
access token 长期有效 泄露后窗口期长 access 短期 + refresh 可撤销
OAuth 用 Implicit token 经 URL 暴露 用授权码 + PKCE
refresh token 不轮换 泄露后长期可用 检测重用即吊销整个会话族
弱口令 + 无限重试 被凭据填充爆破 强制密码强度 + 失败次数锁定 + 验证码

本章小结

要点 结论
认证 vs 授权 先认证你是谁，再授权你能做什么，二者不可混用
OWASP Top 10 是风险地图而非审计清单，需结合威胁建模
JWT 无状态、易扩展，但短期 + refresh + 黑名单才安全
Session vs Token 按场景选型，单体偏 Session，分布式跨域偏 Token
Cookie 三属性 HttpOnly + Secure + SameSite 是基线
CSRF SameSite Cookie + Token 双重防御
OAuth/OIDC 授权用 OAuth，登录用 OIDC，公开客户端用 PKCE
零信任 永不信任、始终验证、最小权限

Web 安全是一个系统工程，认证授权只是入口。接口层的注入、跨站脚本与请求伪造防护详见 第二章：API 安全与漏洞防护；证书、TLS、密钥与容器加固等生产环境议题详见 第三章：安全运维与生产加固。建议按章节顺序阅读，形成”设计—编码—运维”的完整安全闭环。
