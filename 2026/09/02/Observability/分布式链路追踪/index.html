第三章：分布式链路追踪

概念基础

  1. Trace / Span / 上下文传播：Trace 是一次完整请求的因果树，Span 是树中一节点（含 traceId、spanId、parentSpanId、起止时间、标签）。上下游服务通过 HTTP Header 或消息头把 traceId/spanId 透传下去，是构建端到端链路的核心。
  2. 采样率：高 QPS 场景全量上报会撑爆存储与网络，常用 head-based（在入口按概率决定）或 tail-based（在出口按错误/延迟决定）采样。错误链路必须 100% 上报，正常路径 1%~10% 即可。
  3. OpenTelemetry 统一标准：CNCF 主推的 OTLP 协议与 API/SDK，把各家厂商（Jaeger、Zipkin、SkyWalking、Datadog）的客户端 API 统一，让应用埋点与后端解耦，迁移成本低。
  4. 追踪 vs 监控：监控（指标）回答”什么坏了”，日志回答”为什么坏”，链路回答”在哪个调用坏了、调用了谁”。三者互补：先指标告警，再日志取证据，链路定位根因 Span。
  5. 后端选型：Jaeger（CNCF，OTel 原生）、Zipkin（轻量）、SkyWalking（含 APM+告警）、Tempo（Grafana 全家桶）。中小规模推荐 Jaeger all-in-one，大规模推荐 Collector + 存储后端（Cassandra/ES）独立部署。

链路是排障的因果图谱，本章是可观测性三支柱收官篇，请同步阅读 第一章：Prometheus 指标监控与 Grafana 可视化 与 第二章：ELK 日志收集与分析，三者协同使用。

二、Jaeger 部署与架构

Jaeger all-in-one 适合开发与中小规模：

生产推荐 Collector 分离架构：App → OTel Collector (Agent DaemonSet) → OTel Collector Gateway (tail sampling) → Jaeger Collector → Storage（Elasticsearch/Cassandra/Kafka）。存储后端按规模选：Badger 嵌入式适合开发，Elasticsearch 查询能力强适合大规模+日志整合，Cassandra 写入吞吐高适合纯链路，Kafka 适合高峰缓冲再落 ES。

五、跨服务传播

HTTP 上下文通过 traceparent 头自动透传，应用无须手工注入。但当链路穿越异步边界（消息队列、定时任务、线程切换）时容易丢失。

Kafka 消息传播：生产者注入上下文到消息 Header，消费者提取后恢复 traceId：

线程切换丢失：CompletableFuture 默认不传播 ThreadLocal，必须用 ContextExecutorService 包装线程池：

上下文丢失排查清单：① 检查下游 Span 的 parentSpanId 是否对齐上游 spanId；② 抓包确认 traceparent 头是否在 HTTP/MQ Header 中存在；③ 异步任务用线程池包装 ContextExecutorService 或 TaskDecorator；④ 日志 MDC 中 traceId 是否贯穿整条调用栈；⑤ 跨域调用是否被代理拦截头（如 Nginx 默认不过滤 traceparent）。

六、链路分析与排障

Jaeger UI 提供多种排障视图：Find a Trace 按 service + operation + tags 过滤（如 tags={"error":true} 找错误链路）；Compare 对比两条相似链路找耗时差异 Span；Dependencies 自动生成服务依赖 DAG 图发现意外依赖；SPM 聚合 RED 指标发现慢调用分布。

错误链路过滤：{"error":true} 找错误链路，{"http.status_code":"500"} 找 5xx，{"user_id":"10086"} 按用户定位。

常见避坑

坑 现象 正确做法
采样率过高 生产存储爆掉 用 tail_sampling 错误链路全保留，正常 1%~10%
异步丢上下文 Span 断裂成孤儿 用 ContextExecutorService 包装线程池
MQ 上下文丢失 生产消费 traceId 不一致 Producer 写 Header，Consumer 注入 Extract
手动 Span 不 end Span 内存泄漏 try-finally span.end() 必须执行
高基数 Attribute Span 标签膨胀 不要把 user_id order_id 写死，改为 trace search tag
W3C 与 B3 共存 跨语言链路断裂 统一用 W3C traceparent，兼容老系统用 b3multi propagator
跨域代理过滤头 链路在网关后断开 Nginx proxy_pass_request_headers on 不过滤 traceparent
Collector 资源不足 出现 Span 丢失、超时 加 memory_limiter + batch 处理器，限制并发
Span 命名混乱 Jaeger 中 operation 几千种 命名 {type}.{method}，HTTP 用路由名而非 URL

本章小结

要点 结论
数据模型 Trace/Span 构成因果树，traceId 跨服务唯一
传播标准 W3C TraceContext traceparent 头是事实标准
后端选型 Jaeger all-in-one 中小规模；大规模 Collector + ES/Cassandra
SDK 选型 OpenTelemetry 统一 API，与后端解耦，优先采用
自动埋点 Spring Boot OTel Starter / Go otelhttp 拦截器覆盖 80% 场景
异步传播 线程池、消息队列必须手动注入/提取上下文
排障闭环 指标告警 → 链路定位根因 Span → 日志取证

可观测性三支柱至此收官：指标维度见 第一章：Prometheus 指标监控与 Grafana 可视化，日志维度见 第二章：ELK 日志收集与分析。三者协同使用才能形成”告警 → 定位 → 取证”的闭环。在 K8s 上部署 OTel Collector DaemonSet 与 Jaeger Collector 时，可结合 第二章：Kubernetes 容器编排入门，用 Helm Charts 一键拉起 DaemonSet、Service、ConfigMap，并配合 Sidecar 注入简化应用接入。
