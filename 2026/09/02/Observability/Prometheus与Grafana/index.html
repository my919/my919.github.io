第一章：Prometheus 指标监控与 Grafana 可视化

发表于 2026-09-02 分类于 Observability 本文字数： 2.2k 阅读时长 ≈ 7 分钟

第一章：Prometheus 指标监控与 Grafana 可视化

概念基础

  1. 指标（Metrics）vs 日志（Logs）vs 链路（Traces）：指标是聚合后的数值时间序列（CPU、QPS），擅长告警与容量规划；日志是离散事件明细，擅长排障取证；链路是跨服务调用的因果树，擅长定位慢调用。三者构成可观测性三支柱，必须协同使用。
  2. Pull 拉取模型：Prometheus 主动按 scrape_interval 抓取各 exporter 的 /metrics 端点，而非被动接收推送。该模型天然契合服务发现，目标失联时可通过 up == 0 直接告警，比 Push 模型更易判断探活状态。
  3. PromQL 查询语言：声明式表达式语言，支持 rate()、increase()、histogram_quantile()、sum by(label) 等多维聚合运算，能在标签维度上做任意切片，是 Grafana 仪表盘与告警规则的核心引擎。
  4. 多维度标签：每个样本附带 {job, instance, method} 等标签，标签数量决定数据基数。合理设计可让一个指标复用上千个视图，但高基数标签（如 user_id）会撑爆存储，需克制。
  5. Grafana 生态：开源时序可视化平台，支持 Prometheus、Loki、Tempo 等数十种数据源，通过 Panel/Variable/Alert 构建一体化仪表盘，支持钉钉、企微、邮件、PagerDuty 等多种通知渠道。

可观测性三支柱环环相扣：本章专注指标维度，日志维度详见 第二章：ELK 日志收集与分析，链路维度详见 第三章：分布式链路追踪。

二、指标类型与数据模型

Prometheus 把指标分为四种类型，对应不同使用场景：

类型 典型场景 查询范式
Counter 累计单调递增（请求数、错误数） rate(x[5m]) / increase(x[1h])
Gauge 可增可减瞬时值（CPU、内存、连接数） 直接 x 或 avg_over_time(x[5m])
Histogram 分桶统计分布（耗时、大小） histogram_quantile(0.95, x)
Summary 客户端预算分位（不可聚合，慎用） x{quantile="0.95"}

常见避坑

坑 现象 正确做法
高基数标签 TSDB 膨胀到几十 GB，查询超时 不要把 user_id、trace_id、url_path 当标签，改为日志记录
rate() 窗口过短 周五流量尖刺导致误告警 用 [5m] 起步，重要指标 [10m,15m] 平滑
Counter 重置误读 服务重启后 increase() 为负 Prometheus 自动处理 Counter 重置，必须用 rate/increase 而非裸值
Histogram 桶溢出 P99 永远等于最大桶边界 桶上界要覆盖 10 倍 P99，例如 P99=200ms 则最大桶设 2s
Summary 跨实例聚合 拿不到全局 P95 改用 Histogram + histogram_quantile，Summary 不可聚合
up==0 误判 DNS 抖动导致漏报 加 for: 5m 持续时长 + 二次探活
告警风暴 单一故障触发上百条告警 配置 inhibit_rules 与 group_by，按集群/节点抑制
Recording Rule 缺失 仪表盘渲染慢、告警评估超时 高频表达式提前 record 预算
时区不一致 Grafana 图表错 8 小时 统一容器时区为 Asia/Shanghai，数据按 UTC 存

本章小结

要点 结论
数据模型 Counter/Gauge/Histogram/Summary 四类型，优先 Histogram 而非 Summary
查询语言 rate / increase / histogram_quantile / by 是 80% 场景的核心函数
部署形态 Pull 模型 + 服务发现 + TSDB 本地存储 + 联邦集群跨机房
仪表盘 Variable 切换环境、Recording Rule 提前预算、Panel 多类型组合
告警 Alertmanager 路由 + 抑制 + 静默，注意 for 持续时长避免抖动
容量 高基数标签是存储杀手，user_id 类标签禁入 Prometheus
