第二章：微服务架构模式

概念基础

  1. 单体 vs 微服务是取舍而非优劣：单体开发部署简单、跨模块调用是进程内方法调用；微服务独立部署、技术栈异构、故障隔离，代价是分布式带来的网络、一致性、运维复杂度——团队规模小、业务边界不清时别上微服务。
  2. 服务边界靠 DDD 限界上下文：拆分不能按「表」或「分层」，要按业务领域能力，用 DDD 的限界上下文划定边界，上下文内高内聚、跨上下文低耦合，避免拆出「贫血微服务」。
  3. 数据一致性是 BASE 而非 ACID：跨服务无法共享数据库事务，从强一致 ACID 退到最终一致 BASE——基本可用、软状态、最终一致；靠 Saga、本地消息表、事务消息等补偿机制达成。
  4. 同步与异步通信各有代价：同步（REST/gRPC）链路直白但放大故障、级联超时；异步（消息队列）解耦削峰但引入最终一致与消息幂等；选型看场景，关键链路常混用。
  5. 可观测性必须先行：微服务调用链变长、故障定位难，日志+指标+链路追踪三件套要在上线前就位，否则线上出了问题只能盲人摸象。

本章聚焦拆分、通信、事务、容错四大主题；配套落地见 第一章：cloud 微服务工程架构总览与生产落地 与 第七章：集成 Sentinel：流控、熔断与服务保护。

一、服务拆分策略

拆分是微服务成败的第一步——拆错边界，后续全是补救。

按业务能力拆分与 DDD 限界上下文

  • 按业务能力：订单、库存、支付、用户各自成服务，能力即服务边界。
  • DDD 限界上下文映射：每个上下文对应一个服务，上下文间通过**防腐层（ACL）**翻译模型，避免领域模型互相渗透。

拆分粒度权衡与绞杀者模式

  • 粒度权衡：太细则跨服务调用爆炸、运维成本高；太粗则退回单体。经验值：一个服务能由一个「两披萨团队」独立维护。
  • 绞杀者模式 Strangler Fig：老单体不敢一刀切，在边界逐步新建微服务、用网关分流流量，老的逐步下线，平滑迁移。

二、服务间通信

同步：REST vs gRPC 选型

维度 REST (HTTP/JSON) gRPC (HTTP/2 + Protobuf)
可读性 人可读、浏览器友好 二进制、需 proto 描述
性能 JSON 序列化较慢 Protobuf 紧凑、流式快
契约 OpenAPI 可选 proto 强契约强制
场景 对外 API、低频 服务间高频内部调用

异步：消息队列事件驱动

消息中间件核心概念见 第一章：Kafka 消息中间件入门：核心概念与架构；削峰与幂等细节在第三章展开。

服务发现与负载均衡

  • 服务发现：Nacos/Eureka 注册中心，服务启动注册、消费方拉取实例列表。
  • 负载均衡：客户端 LB（Ribbon/Spring Cloud LoadBalancer，直连服务实例、少一跳）vs 服务端 LB（Nginx，统一出口、多一跳）。

三、分布式事务

跨服务无法用本地事务，需补偿或预占机制。

方案 一致性 复杂度 适用场景
2PC 两阶段提交 强一致 高、阻塞 数据库层、低并发
TCC 三阶段 强一致 高、业务侵入 资金、库存预占
Saga 编排/协调 最终一致 中 长流程业务
本地消息表 最终一致 低 异步通知
最大努力通知 弱一致 低 对账、短信

Saga 状态机示例

TCC 要点：Try 预占资源、Confirm 确认、Cancel 释放；需保证 Confirm/Cancel 幂等，且 Try 后必须能走到其中之一（空补偿、悬挂问题）。

四、容错与弹性

微服务故障是常态，弹性设计让局部故障不扩散为全局雪崩。

熔断：Sentinel 状态机

  • CLOSED：正常放行；OPEN：直接拒绝、走 fallback；HALF_OPEN：放半数探测请求决定恢复或再开。

限流、降级、隔离

  • 限流算法：计数器（简单有临界突刺）、滑动窗口（平滑）、令牌桶（允许突发）、漏桶（匀速）。
  • 隔离：线程池隔离（资源物理隔离、开销大）、信号量隔离（轻量、限并发数）——即舱壁模式 Bulkhead。
  • 超时级联：上游超时设置应短于下游，避免下游已成功上游却已重试，造成重复。

五、CQRS 与事件溯源

CQRS：读写分离模型

读写负载差异大时，把「命令写模型」与「查询读模型」分离，写走领域模型、读走优化表，二者通过领域事件同步。

事件溯源与快照

  • 事件溯源：不存最终状态，存全量事件序列，状态由回放事件得到，天然有审计与时间旅行能力。
  • 快照：事件太多回放慢，定期打快照保存当前状态，从最近快照 + 增量事件重建。
  • 最终一致：读模型与写库异步同步，存在延迟，查询要容忍。

六、API 网关与 BFF

网关职责与 Spring Cloud Gateway

网关是微服务统一入口，承担路由、鉴权、限流、聚合、协议转换等横切职责。

BFF 与 GraphQL 聚合

  • BFF（Backend For Frontend）：为不同端（Web/App/小程序）定制后端，聚合多个微服务数据，避免前端 N 次调用。
  • GraphQL 聚合层：客户端按需声明字段，聚合层一次返回，解决 REST 过度/不足获取。

常见避坑

坑 现象 正确做法
按表拆服务 一个领域跨多表却拆成多服务，调用爆炸 按 DDD 限界上下文拆，不按物理表
分布式事务强求强一致 套 2PC 性能崩、锁等待严重 业务允许就用 Saga/本地消息表走最终一致
同步链路过长 5 个服务串行 REST 调用，任一慢全链慢 非关键路径改异步事件，关键链路缩短并加超时
熔断只配不复测 OPEN 后不进 HALF_OPEN，服务一直熔断 配休眠窗口与探测半数，自动探活恢复
限流阈值照搬压测峰值 峰值即上限，稍超就全挂 留水位线，超限走降级而非硬拒
超时设成无脑大 上游 30s 下游 10s，下游成功上游已超时重试 上游超时严格短于下游，避免重复请求
消息消费不幂等 重试/重平衡导致重复消费、重复扣款 业务去重表或状态机判断，保证幂等
网关承担业务逻辑 网关里写聚合/计算逻辑，变成新单体 网关只做横切（路由/鉴权/限流），业务下沉服务
没有链路追踪 跨服务报错，不知请求流经哪些节点 接 OpenTelemetry/SkyWalking，traceId 全链贯通
BFF 膨胀 一个 BFF 服务多个端，又退回耦合 每端一个 BFF，独立演进互不影响

本章小结

要点 结论
拆分 按 DDD 限界上下文拆服务，绞杀者模式平滑迁移
通信 对外 REST、内部高频 gRPC、解耦走 MQ，按场景混用
事务 跨服务放弃 ACID 走 BASE，Saga/TCC/本地消息表按一致性需求选
容错 熔断+限流+降级+隔离四件套，超时上游短于下游
CQRS 读写分离提吞吐，事件溯源保审计，靠快照优化回放
网关 统一入口做横切，BFF 按端定制，业务逻辑不下沉网关

微服务管服务间协作，其微观构件是 第一章：设计模式精要 的代理/策略/观察者；当流量洪峰来临，弹性与缓存如何协同，见 第三章：高并发系统设计。落地工程层面，Spring Cloud 全家桶的注册发现与网关见 第一章：cloud 微服务工程架构总览与生产落地，熔断限流细节见 第七章：集成 Sentinel：流控、熔断与服务保护，异步通信的事件驱动见 第一章：Kafka 消息中间件入门：核心概念与架构。
