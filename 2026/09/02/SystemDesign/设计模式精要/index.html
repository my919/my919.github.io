第一章：设计模式精要

概念基础

  1. 模式是经验总结而非教条：GoF 23 种模式是前人对「重复出现问题」的可复用解抽象，目的是沟通词汇与复用经验，不是套用即对的银弹；套错场景比不用更糟。
  2. 三大类划分：按职责分创建型（如何new对象：单例/工厂/建造者/原型）、结构型（如何组合对象：适配器/装饰器/代理/外观/组合/享元/桥接）、行为型（对象如何协作：策略/观察者/模板/责任链/命令/状态/迭代器等）。
  3. 模式 vs 反模式：模式是「验证过的好做法」，反模式是「常见却糟糕的做法」；识别反模式往往比背模式更能提升代码质量——上帝类、箭头嵌套、硬编码都是高频反模式。
  4. 语言差异决定落地形态：Java 经典面向对象，继承/接口齐全，模式以「类结构」呈现；Go 无继承、靠组合与接口隐式实现，单例用 sync.Once、策略靠函数值，形态更轻量；Python 鸭子类型+装饰器语法糖让装饰器/策略写法更自然。
  5. 模式常组合使用：真实框架很少只用一种——Spring Bean 默认单例，AOP 用动态代理，JdbcTemplate 是模板方法，三者叠加才构成「声明式事务」；理解组合才能读懂框架。

本章代码以 Java 17 / Go 1.22 / Python 3.12 为基准，结合框架实例识别模式；后续见 第二章：微服务架构模式 与 第三章：高并发系统设计。

一、创建型模式：对象的构造

创建型关注「谁来 new、怎么 new、何时 new」，核心是把「对象创建」与「对象使用」解耦。

单例：Java 双检锁 vs Go sync.Once

枚举单例更安全：Java 用 enum 实现单例天然防反射攻击与反序列化重建，是《Effective Java》首选。

工厂方法：简单工厂 / 工厂方法 / 抽象工厂

建造者：链式调用

原型：深浅拷贝

模式 意图 典型场景 注意点
单例 全局唯一实例 配置/连接池/日志 线程安全与懒加载
简单工厂 按参数造对象 分支少 违反开闭，分支多则臃肿
工厂方法 每产品一工厂 产品族扩展频繁 类爆炸
抽象工厂 产品族统一创建 跨平台 UI 主题 加产品难、加产品族易
建造者 分步构造复杂对象 多参数可选 链式、不可变对象
原型 克隆已有对象 创建成本高 区分深浅拷贝

二、结构型模式：对象的组合

结构型关注「对象怎么拼」，目标是把小对象组合成大结构同时保持松耦合。

适配器：接口转换

装饰器：Java InputStream 与 Go io.Reader

代理：远程 / 虚拟 / 保护

外观、组合、享元

  • 外观 Facade：复杂子系统（下单=库存+支付+券+物流）收敛成 OrderService.place() 一个入口。
  • 组合 Composite：Directory 含 File 与子 Directory，统一 Component 接口遍历呈树形。
  • 享元 Flyweight：线程池/连接池复用对象；Go sync.Pool 复用临时对象降 GC 压力。

三、行为型模式：对象的协作

行为型关注「对象怎么通信、职责怎么分配」。

策略：算法族替换

观察者：发布订阅基础

模板方法、责任链、命令、状态

四、在框架中识别模式

模式真实价值在框架里——读懂框架的「模式骨架」就抓住了扩展点。

  • Spring：代理（AOP @Transactional 织入事务）+ 单例（Bean 默认 singleton）+ 模板方法（JdbcTemplate 把连接/参数/关闭写死，只填 RowMapper）。
  • Go：策略（sort.Interface 实现三方法即换排序规则）+ 迭代器（range 遍历 slice/map/channel 语言内置）。
  • Vue：观察者（响应式 ref/reactive 拦截读写做依赖收集与派发更新）+ 发布订阅（EventBus 组件间 $emit/$on 松耦合通信）。

五、设计原则 SOLID

原则比模式更根本——模式是原则的落地，违反原则的模式就是反模式。

原则 一句话 示例
SRP 单一职责 一个类只有一个变化的理由 User 只管资料，登录鉴权拆 AuthService
OCP 开闭 对扩展开放、对修改关闭 新增支付走工厂方法，不改 Checkout
LSP 里氏替换 子类能无感替换父类 子类重写不能破坏父类不变量
ISP 接口隔离 不强迫依赖用不到的方法 胖接口拆成 Readable/Writable
DIP 依赖倒置 依赖抽象非具体 业务依赖 Logger 接口不依赖 FileLogger
  • 迪米特法则（最少知道）：只跟直接朋友说话，a.getB().getC().do() 是坏味道，应封装成 a.do()。
  • KISS：能用函数别上模式；DRY：重复即风险抽公共方法；YAGNI：用不到的扩展别提前造。

六、反模式与代码异味

识别坏味道比套模式更能守护代码健康：

  • 上帝类：一个类几千行什么都知道，违反 SRP，用 Extract Class 拆分。
  • 箭头反模式：if 嵌套五六层像箭头，用卫语句/早返回 + Extract Method 摊平。
  • 硬编码：URL/账号写死代码里，改配置或环境变量。
  • 魔法数字：if(status==3) 没人懂 3 是啥，用常量 PAID 或枚举。
坏味道 重构手法 收益
函数过长 Extract Method 小函数易命名易复用
类过大 Extract Class 单一职责、可测
嵌套过深 卫语句取代嵌套 降低圈复杂度
重复代码 抽公共/模板方法 DRY、改一处全改
魔法数字 命名常量/枚举 可读可维护

常见避坑

坑 现象 正确做法
单例不防并发 多线程下 getInstance 创建多个实例 Java 双检锁+volatile 或枚举；Go sync.Once
过度套模式 简单 CRUD 也套工厂+策略+责任链，代码翻倍 按 KISS/YAGNI，复杂度匹配需求
工厂成 if-else 巨型 每加产品改工厂 switch 用注册表 Map<String,Supplier> 替代分支
装饰器顺序错 先加密后压缩 vs 先压缩后加密结果不同 明确职责顺序，文档注明调用约定
观察者内存泄漏 忘记 off 解订阅，主题持有观察者无法回收 用完即 detach；弱引用或一次性订阅
代理与真实对象耦合 代理里写死业务逻辑，丧失透明性 代理只做横切（鉴权/缓存/日志），业务委派
拷贝浅尝辄止 浅拷贝共享内部可变对象，一方改影响另一方 嵌套对象用 deepcopy 或显式克隆
模板方法破坏开闭 父类骨架写死分支，新增要改父类 钩子方法/策略注入替代硬分支
状态机用 if-else switch(status) 几十分支难维护 每状态一个类，next() 委派状态对象
SOLID 套成教条 为 DIP 给一行代码套 4 层接口 简单逻辑直接依赖具体即可

本章小结

要点 结论
模式定位 经验词汇与可复用解，按需套用而非教条
三大类 创建型造对象、结构型拼结构、行为型管协作
语言差异 Java 经典类结构；Go 组合+接口更轻；Python 语法糖天然适配
原则优先 SOLID/迪米特/KISS/DRY/YAGNI 是模式好坏判据
框架识别 Spring 代理+单例+模板、Go 策略+迭代器、Vue 观察者+发布订阅
反模式 上帝类/箭头嵌套/硬编码/魔法数字，重构手法治理

模式是微观工程经验，放大到服务边界与系统层面就是 第二章：微服务架构模式 的服务拆分、数据一致性与容错弹性；再往上看高并发场景的取舍见 第三章：高并发系统设计。模式管类内协作，微服务管服务间协作，高并发管流量与资源，三者层层递进构成系统设计完整骨架。
