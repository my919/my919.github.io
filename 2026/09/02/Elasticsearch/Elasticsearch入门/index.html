第一章：Elasticsearch 入门与索引管理

概念基础

  1. 倒排索引是 ES 的心脏：写入时经分词器把文本拆成 term，建立 term → 文档 ID 列表的倒排表；查询时先在 term 字典命中、再扫倒排表取文档。对比 MySQL 的 B+Tree 是「值→行位置」，倒排索引是「词→文档列表」。
  2. 近实时（NRT）不是实时：写入先入 translog + 内存 buffer，默认每 1 秒 refresh 一次生成新 segment 才可搜；写后立刻查可能查不到，要 ?refresh=wait_for 或手动 _refresh。
  3. 集群三件套：节点 / 分片 / 副本：主分片水平拆数据决定容量上限，副本分片做高可用 + 读扩展；节点角色分 master / data / coordinating / ingest，生产建议 master 与 data 分离。
  4. ES ≈ 倒排索引 + 分布式：MySQL 的事务 / 外键 / 强一致 ES 没有；ES 的全文检索 / 聚合 / 打分 MySQL 也弱——选型看场景，不是替代，常组合使用。
  5. ELK 生态：E + L + K 三件套：Filebeat/Logstash 采集 → Elasticsearch 存储 → Kibana 可视化；现代可观测性栈的事实标准之一，后续可观测性系列会展开。

本章是 ES 系列开篇，安装与索引管理是地基；查询与调优在 第二章：Elasticsearch 查询与性能调优 展开。ES 按 8.x（2024+）语法书写。

一、Docker 部署 ES 8.x + Kibana

ES 8.x 默认开启安全（HTTPS + 账号密码），单节点开发环境可关掉安全简化联调。

生产务必 xpack.security.enabled=true，启动后自动生成 elastic 账号密码与证书，见 docker logs es01 | grep password。

二、核心概念

Index / Document / Mapping / Analyzer 与 MySQL 对照

ES 概念 MySQL 对照 说明
Index（索引） Table 7+ 去掉 mapping type，一索引即一表
Document（文档） Row JSON 文档，最小可检索单元
Mapping Schema 字段名、类型、是否分词、分词器
Analyzer（分词器） 无 拆词 + 归一化（小写 / 去停用词 / 同义词）
Shard 分库 主分片水平拆；建后不可改
Replica 主从 高可用 + 读扩展；可随时改
_id 主键 可自定义，不指定则自动生成
  • 主分片数：单分片建议 10~50GB；过早分多浪费资源，过少后续扩容难。
  • 副本数：读多加副本提升读吞吐；写入压力大时临时降副本（设 0）提速。

三、索引管理

dynamic 取值 行为 适用
true（默认） 新字段自动猜类型写入 探索期、日志
runtime 新字段不进 schema，运行时算 灵活但慢
false 新字段忽略不索引 省空间
strict 新字段直接报错 生产强约束
字段类型 用途 注意
keyword 精确匹配 / 聚合 / 排序 不分词，ID/枚举用
text 全文检索 分词，不能直接聚合（配 .keyword 子字段）
integer / long 数值精确 数值过滤 / 聚合
date 时间 统一 format 避免解析错
nested 对象数组 每个对象独立，比 object 更准但更重

别名是 ES 零停机重建索引（reindex）的关键：业务始终查别名，背后换索引无感。

四、分词器与分析器

分词器 行为 场景
standard 中文逐字、英文按词 兜底默认
ik_max_word 最细粒度切 索引时（recall 高）
ik_smart 智能不重复 查询时（precision 高）

索引 ik_max_word（切得细、多召回）、查询 ik_smart（切得准、少噪音）是中文 ES 的经典组合。

五、文档 CRUD

机制 默认 说明
refresh 1s buffer → segment，可搜
flush 30min / 512MB translog 持久化 + 清 segment
fsync translog 每 5s 真正落盘，崩溃不丢

高频小批量写入：调大 refresh_interval（如 30s）、用 bulk、临时降副本，写完再恢复。

六、Java 客户端集成

同步方案 方向 延迟 适用
Canal + MQ MySQL → ES 秒级 实时、解耦，生产首选
Logstash JDBC MySQL → ES 分钟级 全量 + 定时增量
双写 应用 → 双边 同步 强一致要求低
CDC（Debezium） MySQL → ES 秒级 同 Canal 思路

同步选型：增量靠 CDC（Canal/Debezium）准实时，全量初始化用 Logstash/快照；双写要处理 ES 失败补偿，慎选。

常见避坑

坑 现象 正确做法
text 字段直接聚合 报 fielddata not enabled 或结果错乱 配 .keyword 子字段再聚合
副本数单节点设 1 集群一直 yellow，副本无法分配 单节点设 number_of_replicas: 0
主分片数建后想改 不能直接改 reindex 到新索引 + 别名切换
写完立即查不到 refresh 默认 1s 延迟 ?refresh=wait_for 或批量后统一 refresh
堆内存设超 50% OOM、GC 卡顿 堆 = 物理内存 50%，剩余给 Lucene 文件缓存
dynamic mapping 误判 首值是数字→成 long，后续文本写入失败 生产 dynamic: strict，显式声明
nested 当 object 用 数组对象字段交叉匹配错误 需独立匹配用 nested + nested query
大量小索引 元数据开销大、分片多 合并到同一索引 + 用 routing 区分
bulk 包太大 拒绝、内存涨 单批 5~15MB，并行多批
IK 未装就建索引 分词报错、全部当单字 先装 IK 再建含 ik 分词器的索引

本章小结

要点 结论
倒排索引 term → 文档列表，全文检索的速度本质
近实时 refresh 1s，写后立查用 refresh=wait_for
分片 / 副本 主分片建后不可改、定容量；副本可改、扩读
Mapping 生产 dynamic: strict + 显式类型；keyword 精确、text 分词
别名 业务查别名，背后换索引零停机
分词器 索引 ik_max_word、查询 ik_smart，analyze API 先验证
文档 CRUD bulk 批量、乐观锁防并发覆盖、_doc 是 endpoint
客户端 Spring Boot 3 用 Spring Data ES 5.x + ElasticsearchClient
同步 实时走 Canal/Debezium，初始化用 Logstash，双写慎用

至此 ES 基础打好：索引、mapping、分词、CRUD、Java 集成俱备；查询 DSL、聚合、分页与性能调优请看 第二章：Elasticsearch 查询与性能调优。
