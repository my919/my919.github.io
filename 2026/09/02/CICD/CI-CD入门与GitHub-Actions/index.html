第一章：CI/CD 入门与 GitHub Actions

概念基础

  1. CI / CD / Continuous Deployment 是三个递进概念：CI（持续集成） 把代码合并到主干并自动构建测试；CD（持续交付 Continuous Delivery） 在 CI 基础上把可部署产物推到制品库，发布动作仍需人工点击；Continuous Deployment（持续部署） 把人工环节也省掉，每次主干合并自动上线，差异关键在”最后一公里是否需要人“。
  2. 流水线阶段（Pipeline Stages） 通常按 Checkout → Build → Test → Scan → Package → Publish → Deploy 串联，每阶段失败立即中断，避免错误向下传递；阶段之间通过**构建产物（Artifact）**而非源码传递，保证”构建一次、到处部署”。
  3. 声明式 vs 脚本式：声明式（GitHub Actions YAML、Jenkins Declarative Pipeline）用结构化语法描述”做什么”，可读、可静态校验、IDE 友好；脚本式（Jenkins Scripted Pipeline）用 Groovy 编排”怎么做”，灵活但难审阅，复杂分支逻辑才回退脚本式。
  4. 缓存策略 决定流水线是否”快得起来”：依赖（~/.m2、node_modules）按 依赖锁文件 hash 作 cache key 缓存；Docker 层走 BuildKit --mount=type=cache 共享；不可变产物（jar/wheel）只缓存构建输入，不缓存输出，避免污染发布物。
  5. 密钥管理 铁律是”密钥永远不进代码“：GitHub 用 Secrets（加密、日志自动打码）、Actions 用 OIDC 短期令牌替代长期 Access Key；生产环境靠 Environment + 审批 + 分支保护三重门，避免一人推主干即上线。

本章先打通 CI/CD 与 GitHub Actions 的骨架，进阶的 Jenkins 流水线与蓝绿/金丝雀发布策略见 第二章：Jenkins 与发布策略。

一、CI/CD 核心理念

持续集成 / 交付 / 部署的区别

概念 触发 终点 人工干预点
CI 持续集成 每次 push / PR 通过单测的构建产物 无
CD 持续交付 CI 通过 制品入库（Nexus/GHCR） 点击”发布”
Continuous Deployment 制品入库 生产环境 无（主干即生产）

测试金字塔

测试投入应呈”底大顶小“：底层单元测试大而快（秒级返回，>3s 即慢测）、中层集成测试用 Testcontainers 起真实依赖、顶层 E2E 少而慢（单独 job 夜间或预发跑），避免倒金字塔拖垮流水线。

流水线设计原则

原则 做法 反模式
快速失败 单测 < 3 分钟 一个 job 跑半小时才报错
幂等可重跑 不依赖本机残留状态 依赖 ~/tmp 残留文件
一次构建到处部署 同一镜像走 dev/test/prod 每环境重新 mvn package
不可变产物 产物入库后只读 现网 SSH 改 jar
阶段隔离 阶段间靠 Artifact 传递 阶段间靠全局变量传递

镜像标签策略（生产禁用 latest）

标签 用途 是否可变
latest 便利，但易覆盖、不可追溯 可变，禁用于生产
git-sha 每次构建唯一，可回溯 commit 不可变，推荐
semver v1.2.3 正式发版 不可变
branch-name 分支临时镜像 可变，仅 dev

actions/cache 通用缓存

矩阵构建（多版本×多平台）

并行 job 与 needs 依赖

缓存 key 设计：Maven 用 os-maven-hash(pom.xml)（pom 变即重建）、npm 用 os-node-hash(lock)、Docker 层走 type=gha（BuildKit 自动管理）、需全量强刷时在 key 里加 YYYYMMDD 手动 bump 日期。

六、密钥与环境保护

GitHub Secrets

仓库 Settings → Secrets and variables → Actions 添加 SONAR_TOKEN、ACR_PASS；引用为 ${{ secrets.X }}，日志自动替换为 ***，且默认不注入到 fork PR 构建。

环境保护规则

在 Settings → Environments → production 配置：Required reviewers（至少 2 人审批方可部署）、Deployment branches（仅 main 或 release/*）、Wait timer（5 分钟冷静期便于反悔）。

OIDC 免长期 Token（以 AWS 为例）

AWS 端需在 IAM 创建信任策略允许 token.actions.githubusercontent.com 扮演该角色，并按 sub 限定到本仓库与分支，避免越权。

常见避坑

坑 现象 正确做法
npm install 改 lock CI 跑完 lock 变了 用 npm ci 严格按 lock 安装
缓存 key 只用 OS 改依赖却命中旧缓存 加 hashFiles('**/lock') 作 key
latest 跑生产 昨晚构建覆盖线上，无法回滚 用 git-sha 或 semver 不可变标签
fork PR 拿 Secrets 被恶意 PR 偷 Token 敏感 job 加 if: github.event.pull_request.head.repo.full_name == github.repository
fetch-depth: 1 + Sonar Sonar 报 “no blame info” fetch-depth: 0 拿全历史
job 无 timeout-minutes 死循环跑满 6 小时 每 job 显式 timeout-minutes: 15
permissions: write-all 给得过大，供应链攻击面广 最小权限，按需 contents: read
pull_request_target 乱用 fork 改 workflow 偷 Secrets 仅用 pull_request，必要时显式校验
并行 matrix fail-fast 一个挂全停，看不到全貌 测试/构建矩阵设 fail-fast: false

本章小结

要点 结论
CI vs CD vs Continuous Deployment 差在”最后一公里是否需要人”
流水线设计 快速失败、幂等、一次构建到处部署
GitHub Actions 四层 Workflow → Job → Step → Action
触发条件 push/PR/schedule/dispatch 各有适用
多语言构建 用官方 setup-* action 统一缓存
Docker 镜像 multi-stage + 不可变标签 + OIDC 推送
缓存 锁文件 hash 作 key，BuildKit --mount=type=cache
密钥 Secrets + Environment + OIDC 三重保护

掌握 GitHub Actions 后，企业内部往往还需要 Jenkins 这类可自托管、可深度定制的流水线引擎，并配合蓝绿、金丝雀等发布策略实现零停机上线与快速回滚，进阶内容见 第二章：Jenkins 与发布策略。
