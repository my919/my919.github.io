第三章：Kafka Java 发布与消费实战

概念基础

  1. 客户端只是协议的实现：kafka-clients 是 Kafka 二进制协议的 Java 实现，本身不存消息；版本只需与 Broker 主版本兼容（如 3.x 客户端连 3.x 集群），不必逐位对齐。
  2. 生产者是「异步攒批」模型：send() 只是把消息放进客户端缓冲区（buffer.memory），由后台 Sender 线程按 batch.size / linger.ms 攒批、压缩后发出；get() 等的是「Broker 确认」这个结果，而不是发送过程本身——理解这一点才能解释吞吐与延迟的权衡。
  3. 消费者是「拉模型 + 消费组协调」：一切由 poll() 驱动；Broker 端协调器（GroupCoordinator）负责成员管理与分区分配（再均衡），offset 提交时机决定「重复消费」还是「丢消息」。
  4. 消息去哪里由 key 与序列化器决定：key/value 必须配置序列化器；key 的 hash 决定分区路由——同 key 进同分区，这是「分区内有序」在客户端代码里的落点。

生产消费流程



flowchart LR
  AppP[Java Producer] -->|produce| B[Broker]
  B --> Part[Topic 分区]
  Part --> AppC[Java Consumer]
  AppC --> G[Consumer Group]

发送链路：序列化 → 分区器 → 缓冲攒批 → Sender 发送 → 等确认；消费链路：poll 拉取 → 反序列化 → 业务处理 → 提交 offset。

发布消息（Producer）

要点：

项 说明
acks 0 / 1 / all，权衡延迟与持久性；与幂等常配合 acks=all
key 同 key 映射到同分区，分区内有序
异步发送 producer.send(record, (metadata, exception) -> { ... })
幂等 enable.idempotence=true 时 Broker 按 <PID, 分区, 序号> 去重，重试不产生重复

三种发送方式对照：

方式 写法 适用场景
发后即忘 send(record) 不看结果 日志类可容忍少量丢失
同步 send(record).get() 低频关键消息，简单可控
异步回调 send(record, callback) 高吞吐且需感知失败

  1. 确认 Bootstrap 可达，且 advertised.listeners 对客户端可解析（见 第二章：Docker 部署 Kafka 实践）。

现象 排查

分区倾斜 key 分布不均，或分区数过少

本章小结

要点 结论
生产端 异步攒批；acks + 幂等 定义可靠性；key 决定分区与顺序
消费端 poll 驱动；offset 提交时机决定语义，业务需幂等
投递语义 默认 at-least-once：先处理后提交 offset
排障第一步 连不上查 advertised.listeners，收不到查 group / offset
