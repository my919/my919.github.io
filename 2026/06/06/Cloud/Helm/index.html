第四章：Helm 应用包管理入门

概念基础

  1. Helm 是 Kubernetes 的包管理器（如同 apt / yum 之于 Linux 发行版）：把一个应用所需的全部 K8s 清单打包成 Chart，一条命令完成安装、升级与回滚。
  2. 三大核心模型：Chart（安装包，含模板与默认配置）、Release（Chart 在集群中的运行实例，同 Chart 可装多份）、Repository（Chart 仓库，官方/自建均可）。
  3. 模板化 + values：重复 YAML 抽成模板，由 values.yaml 注入参数，同一套 Chart 适配 dev / test / prod 多环境，避免手抄清单。
  4. 为什么用：一键部署 MySQL、Redis、ES 等中间件栈；版本管理（history / rollback）与 K8s 滚动升级互补；依赖管理自动拉取子 Chart。
  5. 与 kubectl 的分工：kubectl apply -f 适合少量静态清单；Helm 适合可复用、可升级的应用包——二者并存，Helm 管理的资源仍可用 kubectl get 查看。

从 Chart 到 Release 的整体关系：

Chart 到 Release



flowchart LR
  Repo[Repository 仓库] -->|helm pull| Chart[Chart 安装包]
  Chart -->|helm install| Release[Release 运行实例]
  Values[values.yaml 配置] --> Chart
  Release --> K8s[K8s 集群 Pod/Service 等]

核心概念

概念 说明
Chart Helm 的应用安装包，含部署 K8s 应用所需的 YAML 模板、默认配置与 依赖
Release Chart 在集群中运行的实例；同一 Chart 可部署多个 Release（不同命名空间/版本）
Repository Chart 仓库（官方、第三方或自建），用于存储与共享 Chart
Values.yaml Chart 的配置文件，自定义端口、副本数、镜像等参数

为什么要用 Helm？

能力 说明
一键部署 MySQL、Redis、ES、Nginx 等中间件，一行命令起栈
版本管理 upgrade / rollback 与 history，与 K8s 滚动升级互补
模板化 重复 YAML 抽成模板，values 区分 dev/test/prod
依赖管理 Chart.yaml dependencies 自动拉取子 Chart
环境隔离 同一 Chart + 不同 values 文件适配多环境

本站中间件在 K8s 上的部署可参考 服务 与各 *-Docker 文章中的清单；生产环境更推荐用 Helm Chart 或 Operator 替代手写多文档 YAML。

与 kubectl 的关系

  • kubectl apply -f：直接应用静态或 Kustomize 渲染后的清单，适合简单、少量资源。
  • helm install/upgrade：基于模板与 values 生成清单并记录 Release 版本，适合可复用、可升级的应用包。
  • 二者可并存：Helm 管理的资源仍可用 kubectl get 查看；勿对同一 Release 资源混用手动 kubectl edit 导致 drift，升级时以 Helm values 为准。

本章小结

要点 结论
定位 K8s 包管理器：Chart 打包、一条命令装/升/回滚
核心模型 Chart（包）→ Release（实例）→ Repository（仓库）
参数化 模板 + values.yaml，同一 Chart 适配多环境
排障 helm lint 校验、helm template 本地渲染、helm history 看版本
生产建议 优先 Helm Chart / Operator，避免手写多文档 YAML 且勿混用 kubectl edit
