第八章：Java并发锁全解与选型

概念基础

  1. 为什么需要锁：多个线程同时读写共享变量（如 count++）会因原子性、可见性、有序性三大问题产生数据错乱，锁是保证线程安全最直接的手段。
  2. 两大流派：悲观锁先加锁再操作（synchronized、ReentrantLock），乐观锁先操作再校验冲突（Atomic 原子类的 CAS 机制）。
  3. JVM 内置锁 vs JDK 显式锁：synchronized 由 JVM 自动加解锁、可重入、非公平；Lock 接口（ReentrantLock 等）额外支持超时、可中断、公平锁、多 Condition 精准唤醒。
  4. 读写分离优化：读多写少场景用 ReentrantReadWriteLock（读读共享）；追求极致读性能再上 StampedLock 的无锁乐观读。
  5. 无锁更轻：单变量的计数/状态标志可用 Atomic 原子类或 volatile（保证可见性、禁止重排），避免加锁开销。

涵盖：synchronized、ReentrantLock、ReentrantReadWriteLock、StampedLock、Atomic原子类、volatile

一、synchronized 内置锁

特性

可重入、非公平、悲观独占锁，JVM 自动加解锁。

适用场景

简单临界区、单体小并发、不想手动释放锁。

七、锁选型速查表

锁类型 核心特点 适用场景
synchronized 简单自动加解锁、可重入 简单临界区、低并发、快速开发
ReentrantLock 公平/非公平、超时、中断、Condition 复杂同步、需要超时/可中断、生产者消费者
ReentrantReadWriteLock 读读共享、读写互斥 读多写少：本地缓存、配置字典
StampedLock 乐观读、高性能 超高并发、读极多写极少
AtomicXXX CAS无锁、高性能 计数器、自增序号、单个变量原子操作
volatile 可见性+禁止重排 状态标记、双重检查单例

常见避坑

坑 现象 正确做法
synchronized 锁错对象 锁了不同实例，并发问题依旧；或锁 String/Integer 缓存对象导致”意料之外的互斥” 锁私有 final 监视器对象 private final Object lock = new Object()；或明确锁当前类 Xxx.class（静态）
ReentrantLock 忘写 finally unlock 异常路径下锁未释放 → 死锁/永远阻塞 固定模板：lock.lock(); try { … } finally { lock.unlock(); }
wait/notify 不在循环中判断条件 虚假唤醒（spurious wakeup）或多线程抢占 → 条件不满足仍继续往下跑 永远用 while (条件不满足) wait()，不要 if；用 Condition.await() 同样规则
notify() 而不是 notifyAll() 两个等待队列（消费/生产）互发通知，只有一个被唤醒，另一个永远挂起 除非只存在一种等待条件且线程数严格为 2，否则一律 notifyAll() / signalAll()
volatile 当原子用 volatile int i; i++ 仍竞态；以为可见性=原子性 计数类用 AtomicInteger.getAndIncrement，复合操作上 synchronized 或 ReentrantLock
线程池用 Executors.newFixedThreadPool 无界队列 任务堆积 OOM，线上几小时后 JVM 崩溃 自己 new ThreadPoolExecutor(…, new ArrayBlockingQueue<>(N), new CallerRunsPolicy())：有界队列 + 拒绝策略
ThreadLocal 不 remove Tomcat/Netty 线程池复用时上下文串号、内存泄漏、类加载器泄漏 try 里用，finally { tl.remove(); } 必写；跨请求不要依赖 ThreadLocal 传值
死锁：锁顺序不一致 A 线程拿 lock1 再 lock2，B 线程拿 lock2 再 lock1 → 双方互等 统一全局加锁顺序；用 tryLock(timeout) 加锁失败回退；一次性 Lock 组合对象封装
ConcurrentHashMap 的 putIfAbsent/compute 误用 if (!map.contains(k)) map.put(k, v) 仍竞态，出现重复初始化 用 map.computeIfAbsent(k, k -> new Resource())，单步原子
共享可变对象没同步 把非线程安全的 SimpleDateFormat、HashMap 当静态字段共用 SimpleDateFormat 替换为 DateTimeFormatter（线程安全）；跨线程共享集合统一用 JUC 并发集合
CountDownLatch/Semaphore 数量对不上 await() 不结束或过早结束 主线程和工作线程都打印剩余计数做联调；每一条异常路径都必须 countDown() / release()（放进 finally）
Future.get() 不加超时 单个线程 hang → 整个线程池被拖死 future.get(5, TimeUnit.SECONDS) + 捕获 TimeoutException 并记录/取消任务

本章小结

要点 结论
synchronized 简单、自动加解锁、可重入，适合低并发简单临界区
ReentrantLock 超时/可中断/公平/Condition，复杂同步与生产者消费者首选
读写锁 ReentrantReadWriteLock 读读共享，读多写少（缓存、配置）场景
StampedLock 乐观读免加锁，读极多写极少的高并发场景性能最佳
Atomic / volatile 无锁方案：CAS 原子操作与可见性保证，单变量场景开销最小
