第四章：数仓分层与数据管道调度

发表于 2026-05-01 更新于 2026-09-01 分类于 BigData 本文字数： 1.5k 阅读时长 ≈ 5 分钟

第四章：数仓分层与数据管道调度

概念基础

  1. 数仓分层的目的是治理复杂度：ODS 贴源、DWD 明细、DIM 维度、DWS 汇总、ADS 应用——每层职责单一，下游依赖上游，坏数据能定位到层。
  2. 批流一体靠统一模型：Spark（第一章：Spark 大数据批处理入门）跑离线重算，Flink（第二章：Flink 流式计算入门）跑实时增量，两边共用口径才能「T+1 准确、实时大致对」互为校验。
  3. Kafka 是管道骨架：CDC 与日志先进 Kafka（第三章：Kafka 大数据数据总线）缓冲解耦，再分流到批/流/OLAP 各消费者。
  4. 调度是数据可靠性核心：Airflow/DolphinScheduler 把「每天 2 点跑批」变成有依赖、可重试、有告警的 DAG，而不是一堆 crontab。
  5. ClickHouse 承接分析层：DWS/ADS 汇总结果落到列存引擎供 BI 查询，见 第三章：ClickHouse 查询与性能调优。

本章聚焦管道编排与分层建模方法论；沙箱无 Airflow/Spark 集群，代码按 Airflow 2.x 官方语法书写未逐条运行验证。

一、分层模型



flowchart LR
  S[(业务库/日志)] -->|CDC/采集| O[ODS 贴源层]
  O --> W[DWD 明细层]
  DIM[(维度表)] --> W
  W --> S2[DWS 汇总层]
  S2 --> A[ADS 应用层]
  A --> BI[BI/报表/API]
层 职责 关键约束
ODS 原样落地，不做加工 保留原始格式；按天分区快照
DWD 清洗、去重、脱敏、拆平明细 一行一件事务/事件；只依赖 ODS
DIM 维度表（用户、商品、地区） 缓慢变化维（SCD2）记录历史
DWS 按主题预聚合（日/用户粒度） 口径唯一，重算成本可控
ADS 面向报表/大屏/接口的最终宽表 只依赖 DWS+DIM，不碰 ODS

分层价值：重复计算下沉、口径收敛（改一处全局生效）、问题定位快（ADS 错 → 查 DWS → 查 DWD）。

二、CDC 采集：业务库变更入仓

ODS 两种落地形态：每天全量快照（简单、可回溯）与增量 upsert（省存储、需主键合并）——中小规模优先全量快照 + 关键表才做增量。

三、Airflow：把批处理编排成 DAG

调度实践要点：

实践 说明
数据就绪探测 用 Sensor 等「源表分区就绪」（/data/ods/dt=2026-05-01/_SUCCESS）再开跑
幂等设计 所有任务以 dt=日期分区 覆盖写，重跑不产生重复
回刷 补数 = 对历史日期重放 DAG；幂等是回刷安全的前提
分区约定 全公司统一 dt/hh 分区字段，下游依赖检查分区存在性
SLA 与告警 任务超过预期时长告警；失败走 IM webhook（见 第五章：系统运维进阶 的日志与监控）

四、批流双跑与一致性

问题 方案
实时与离线口径不一致 统一 DWS 层 SQL 口径，代码同源（或用 Flink 批模式跑离线）
迟到数据 Flink 水位线 + allowed lateness；离线重算兜底
重复写入 Kafka 事务 + 幂等 sink（主键去重），见第三章「精确一次」
大宽表爆炸 ADS 只建高频查询宽表，长尾需求走即席查询

五、数据质量门禁

检查 时机
表行数/波动率 ODS 就绪后
主键唯一、非空 DWD 产出后
口径对账（批 vs 流） ADS 产出后
下游新鲜度 报表侧每天首次访问校验数据日期

本章小结

要点 结论
分层 ODS 贴源 → DWD 明细 → DIM 维度 → DWS 汇总 → ADS 应用；坏数据逐层定位
采集 CDC 入 Kafka；ODS 用「全量快照 + 关键表增量」起步
调度 Airflow DAG + 数据就绪 Sensor + 幂等分区写，重跑回刷才安全
批流 实时求快、离线求准；每日对账，超阈值重算
质量 唯一性/非空率/波动率做成门禁任务，不过检不放行下游
