第二章：Docker 部署 Kafka 实践

概念基础

  1. KRaft 让单进程成为可能：旧版 Kafka 需要 ZooKeeper + Kafka 两个进程；KRaft 模式下一个容器同时扮演 controller + broker，单机一条命令即可起集群（本章单容器示例的核心）。
  2. 监听器与 advertised.listeners 是第一坑：Kafka 会把 advertised.listeners 里的地址返回给客户端——容器内监听 0.0.0.0 没用，客户端拿到的是这个「广告地址」。本机访问写 127.0.0.1、Compose 内服务访问写服务名、跨网段要双监听，本章三种部署形态的差异全在这一个参数上。
  3. 数据目录与 page cache：数据在 /bitnami/kafka（Bitnami 镜像），必须挂卷；Kafka 依赖磁盘顺序写与 page cache，内存不宜压得过低。
  4. 边界要清楚：单容器 / Compose / 单副本 Deployment 都面向开发验证；生产多 Broker 应使用 Strimzi 等 Operator 或 StatefulSet，不要把单实例 Deployment 当集群扩。

前置条件

本机已安装 docker，并能使用 docker compose（Compose V2 插件，命令为 docker compose；若仍使用旧版独立程序，则将下文中的 docker compose 换成 docker-compose）。

Kafka 镜像选择

1. 常用镜像

镜像 说明
apache/kafka Apache 官方维护（Docker Hub：https://hub.docker.com/r/apache/kafka），参数前缀多为 KAFKA_，与发行包行为贴近。
bitnami/kafka Bitnami 打包（https://hub.docker.com/r/bitnami/kafka），参数前缀多为 KAFKA_CFG_，文档与示例丰富，下文默认采用。

2. 版本与标签

  • 开发/学习：固定大版本标签（如 bitnami/kafka:3.7、apache/kafka:3.9.0），避免 latest 漂移。
  • 生产：固定补丁级标签或 digest，并阅读对应镜像的发行说明与安全更新。

3. 监听器与 ADVERTISED_LISTENERS

客户端使用的 bootstrap.servers 必须落在 advertised.listeners 可解析的地址上：

  • 仅本机连 localhost:9092：可把 KAFKA_CFG_ADVERTISED_LISTENERS 设为 PLAINTEXT://127.0.0.1:9092（与下文 「单容器一键部署」 单行示例一致）。
  • Compose 内其它服务连 kafka:9092，同时宿主机还要连：需双监听（下文 「Docker Compose 一键部署」），例如内部 PLAINTEXT://kafka:9092、外部 PLAINTEXT://localhost:9094，并映射两个端口。

4. 资源与持久化

Kafka 依赖磁盘顺序写与充足 page cache；Bitnami 数据目录一般为 /bitnami/kafka。单机开发可适当降低 heap，生产请按吞吐与副本单独规划。

1Panel（推荐）：在 Linux 宿主机上若希望少手写命令、仍以容器方式跑 Apache Kafka，可先安装 1Panel（开源 Linux 运维面板），在 「应用商店」 中选择 Kafka 一键部署：由面板管理镜像版本、数据卷、监听端口与 KRaft 相关环境变量（以当前上架镜像与模板为准）。与下文 docker run / Compose / K8s** 中的 **KAFKA_CFG_ADVERTISED_LISTENERS**、双监听、数据目录与 **heap` 对齐或排障时，自「单容器一键部署」起各节仍可作对照。适合单台 VPS、家庭服务器等「快速起消息流」的场景。
