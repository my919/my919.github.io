Git 版本控制入门

概念基础

  1. 分布式版本控制：每个开发者本地都有完整的仓库与历史，提交、分支、回滚离线可用；GitHub/Gitee 等远端只是同步与协作节点。
  2. 三大工作区流转：工作区 → 暂存区（git add）→ 本地仓库（git commit）→ 远程仓库（git push），理解这条流水线就掌握了日常九成操作。
  3. 分支极其轻量：分支只是指向提交的可移动指针，创建与切换几乎零成本，因此鼓励「功能分支 + 合并」的协作方式。
  4. 改历史要克制：未推送的提交可用 reset 自由整理；已推送的公共历史应使用 revert 生成反向提交，避免强推坑队友。
  5. 配置先行：首次使用先全局配置 user.name / user.email，提交记录才有可信的作者信息。

十、rebase：变基与历史整理

git rebase（变基）会把当前分支上「自分歧点以来」的提交逐条摘下、再依次重放到指定的新基之上，使历史变成一条直线。常用于同步上游更新、整理杂乱提交、换一个更合适的基础分支。

一句话区分：merge 保留分叉历史（生成合并提交），rebase 改写历史为线性（重放提交、哈希会变）。

6. 已推送分支的 rebase：黄金法则与强推

黄金法则：不要 rebase 已推送、且他人可能基于其开发的历史。因为 rebase 会改写提交哈希，他人 pull 时会出现「历史分叉」，被迫处理大量冲突甚至重复提交。

因此：

  • main / develop 等公共分支：只 merge，不 rebase。
  • 个人功能分支：rebase 后需强推覆盖远程，且确认无他人使用：
  • 用 --force-with-lease 而非 --force：若远程有你未拉取的新提交，它会拒绝推送，避免误覆盖他人劳动。
  • 已开启分支保护的分支（如 main）通常禁止强推，rebase 后推不上去是预期行为。

--onto <新基> <旧基> <分支> 把分支从旧基搬到新基
--continue 解决冲突后继续 rebase
--abort 放弃本次 rebase，回到开始前状态
--skip 跳过当前冲突提交
--autostash 自动 stash 脏工作区，rebase 后恢复
--root 从第一个提交开始 rebase（配合 -i 可改写根提交）
--autosquash 配合 -i，自动归位以 squash! / fixup! 开头的提交

8. rebase 与 merge 的取舍

需求 更合适
公共分支同步、保留完整分叉历史 git merge
个人分支同步上游、追求线性历史 git rebase
清理碎提交、改写未推送历史 git rebase -i
拉取更新且不想留「Merge branch」噪音 git pull --rebase

记法：公共历史用 merge（只增不改），私有历史用 rebase（可改可整）。

二分找 Bug git bisect start → bad / good 交替 → reset；可 run <测试命令> 全自动
仓库嵌套 git submodule add；克隆加 --recurse-submodules
大文件入库 git lfs install → git lfs track "*.onnx" → 正常提交推送

更深入的主题（hooks 钩子、worktree 多工作树、reflog 找回丢失提交 等）可在熟练上述流程后，按 Pro Git 中文版 与团队规范继续深入。
