第四章：RAG 与向量检索实战

发表于 2026-05-01 更新于 2026-09-01 分类于 AI 本文字数： 1.3k 阅读时长 ≈ 4 分钟

第四章：RAG 与向量检索实战

概念基础

  1. RAG = 检索增强生成：把私有知识向量化入库，提问时先检索最相关的片段塞进上下文，再让 LLM 作答——不用重训模型就能注入领域知识，是 LLM 落地性价比最高的路线。
  2. Embedding 是语义坐标系：文本被编码为高维向量（如 1024 维），语义相近的文本距离相近；「检索」从关键词匹配升级为最近邻搜索。
  3. 向量库专管 ANN：Milvus/Qdrant/pgvector 用 HNSW 等索引做近似最近邻查询，毫秒级从千万级向量里捞 Top-K；小规模用 Redis/Postgres 也能起步。
  4. 效果好坏在数据管道：切块（chunking）粒度、检索 Top-K、重排序（rerank）三件事对答案质量的影响大于换模型。
  5. 评估要有 ground truth：召回率（该找的找没找到）与答案忠实度（说的对不对）分开评，肉眼抽查不可持续。

本章承接 第三章：LLM 大语言模型基础 的 RAG 概念，落到工程实现。代码按 LangChain 0.3 / OpenAI SDK 官方 API 风格书写（沙箱未装依赖，未逐条运行验证）。

一、RAG 全链路



flowchart LR
  D[文档] --> C[切块 Chunking]
  C --> E[Embedding 向量化]
  E --> V[(向量库)]
  Q[用户提问] --> QE[问题向量化]
  QE --> V
  V --> R[Top-K 检索 + Rerank]
  R --> P[拼装 Prompt]
  P --> LLM[LLM 生成]
  LLM --> A[带引用的答案]

两条管道：

管道 内容 执行时机
离线索引 文档 → 清洗 → 切块 → 向量化 → 入库 文档新增/变更时
在线问答 问题向量化 → 检索 → 拼 Prompt → LLM 每次提问

二、离线索引：切块与向量化

切块经验值：

参数 建议 理由
chunk_size 300~800 字符 太小丢上下文，太大稀释相关性
chunk_overlap 10%~20% 保住跨界句子
元数据 给每块挂 {"source": 文件名, "section": 标题} 答案引用与按来源过滤都靠它

三、在线检索与生成

Prompt 三原则：明确告知「只依据资料」、资料带来源标记（答案可引用）、temperature=0 降低发挥。

四、向量库选型

方案 定位 适用
Qdrant / Milvus 专用向量库，HNSW/量化，十亿级 独立检索服务
pgvector Postgres 扩展 已有 PG、千万级以内（运维最省）
Redis 向量检索 + 缓存一体 热点数据、低延迟
Elasticsearch BM25 + 向量混合检索 已有 ES、关键词+语义混合
FAISS 进程内库 原型、单机实验

五、评估与迭代

调优顺序（从便宜到贵）：

  1. 切块参数：调 chunk_size/separators，对结构化文档用标题感知切块
  2. 检索深度：先取 Top-20 再 rerank 到 Top-4（召回与精排分工）
  3. 混合检索：加 BM25，专治型号、代码、专有名词
  4. 换 Embedding 模型：领域强的换领域微调模型（中文场景 BGE 系列常用）
  5. 最后才动 LLM：检索对了答案基本就对了

本章小结

要点 结论
RAG 本质 检索注入上下文而非重训模型；离线索引 + 在线问答两条管道
切块 300~800 字符 + 重叠 + 标题感知；每块挂 source/section 元数据
检索 向量 ANN 打底；BM25 混合治专有名词；rerank 精排
选型 有 PG 用 pgvector、独立大规模用 Qdrant/Milvus、原型用 FAISS
评估 召回率与忠实度分开评；调优先动切块与检索，最后动模型
