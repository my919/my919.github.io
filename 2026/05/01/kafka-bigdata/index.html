第三章：Kafka 大数据数据总线

概念基础

  1. 数据总线：业务库、日志、IoT 等各系统把数据统一发布到 Kafka，下游实时计算、数仓、检索各自订阅，生产与消费彻底解耦。
  2. 为什么是 Kafka：分区日志支持高吞吐追加写、多订阅（不同 Consumer Group 各自消费）与按 Offset 回放（补数、审计），保留时长由 retention 策略控制。
  3. 接入与落地：上游用 CDC（Debezium / Connect）把数据库变更流入 Topic，下游由 Flink / Spark 消费进 OLAP / 数据湖。
  4. 治理决定成败：Schema Registry 管演进兼容、死信 Topic（DLQ） 兜底脏数据、幂等写入去重，总线才能长期稳定。
  5. 运维要点：盯 Consumer Lag、副本同步与 Broker 磁盘，工具用 kafka-consumer-groups.sh、Cruise Control。

在数据架构中的位置



flowchart LR
  SRC[业务库 / 日志 / IoT] --> CDC[Debezium / Connect]
  CDC --> K[Kafka Topic]
  K --> F[Flink / Spark]
  F --> WH[(ClickHouse / 湖仓)]
  • 解耦：生产者与消费者独立扩缩容。
  • 回放：按 Offset 重读，便于补数与审计。
  • 多订阅：同一 Topic 可被实时计算与离线同步同时消费（不同 Consumer Group）。

Topic 设计要点

实践 说明
分区数 并行度上限；扩容分区易，缩容难
Key 同 Key 进同一分区，维持局部顺序（如 userId）
保留策略 retention.ms / retention.bytes；合规需更长保留或冷归档
Compact cleanup.policy=compact 存 Key 最新状态（Connect、Streams）
命名 domain.event.v1 便于治理与 Schema 演进

Kafka Connect 与 CDC

组件 作用
Connect Source/Sink 插件，同步 DB、ES、S3

数据质量与治理

  • Schema 演进：新增字段用兼容模式（BACKWARD/FULL），避免消费端反序列化失败。
  • 死信 Topic：解析失败、业务拒绝的消息进入 DLQ 人工处理。
  • 幂等写入：OLAP 侧按 主键 + 版本 或 ReplacingMergeTree 去重。

运维与监控

指标 含义
Consumer Lag 消费落后生产，告警阈值按 SLA 设
Under-replicated 副本未同步，影响可用性
Broker 磁盘 顺序写仍可能打满，需 retention 与扩容

本章小结

要点 结论
总线定位 统一接入、多订阅、可回放，生产与消费独立扩缩容
Topic 设计 分区定并行度，Key 保局部顺序，retention 与 compact 按场景选
数据接入 Connect + Debezium CDC 把 DB 变更流入 Kafka，Schema Registry 管兼容性
引擎集成 Flink 精确一次消费、Spark Structured Streaming 微批、ClickHouse 引擎表入库
稳定运行 盯 Consumer Lag 与副本同步，死信 Topic + 幂等写入保数据质量

至此数据总线主线完成：Spark 承担离线批处理与数仓 ETL，Flink 负责低延迟实时计算，Kafka 作为数据总线把业务库、日志与上下游计算引擎串成完整数据管道。分层建模与 Airflow 调度见 第四章：数仓分层与数据管道调度，实践中按「离线批选 Spark、实时流选 Flink、数据传输靠 Kafka」组合落地。
