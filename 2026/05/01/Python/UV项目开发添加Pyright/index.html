第四章：UV 项目开发添加 Pyright：静态类型检查

概念基础

Pyright 是微软推出的 Python 静态类型检查器，BasedPyright 是其社区增强分支：

  1. 运行前抓 Bug：在代码执行之前发现类型不匹配、None 误用、属性不存在、漏处理返回值等问题，比跑测试更早暴露隐患。
  2. 双发行版：Pyright 基于 Node（常经 npm / VS Code Pylance 使用）；BasedPyright 可用 PyPI 直接安装（uv add --dev basedpyright），配置与 Pyright 完全兼容。
  3. 配置集中：检查范围（include）、Python 版本（pythonVersion）、严格程度（typeCheckingMode）统一写在 pyproject.toml 的 [tool.pyright]，CLI 与编辑器共享同一份配置。
  4. 与 Ruff 分工：Ruff 管风格与格式（见第三章），Pyright 管类型语义；二者互补而非替代，注意避免规则重复。

3. 可选：使用微软原版 Pyright（Node）

若团队统一使用 npm 安装的 Pyright，可在项目外加装 Node 后使用 npx pyright，或在 CI 里 npm install -g pyright 后调用 pyright；配置与下文 [tool.pyright] 键名一致（写在 pyproject.toml 即可）。

二、在 pyproject.toml 中配置

在 pyproject.toml 中增加 [tool.pyright]（BasedPyright 与 Pyright / Pylance 均会读取，勿再单独维护 pyrightconfig.json，避免两处不一致）：

  • include：按仓库实际源码目录修改（例如 ["hello_uv"] 或 ["."]）。
  • pythonVersion：与 [project] requires-python / 本机解释器大版本一致。
  • typeCheckingMode：常用 basic / standard / strict，由严到宽可调。

更多键名与语义见：Pyright Configuration。

四、为类型检查补全注解（简要）

Pyright 依赖 py.typed 标记与类型存根：

  • 若你发布库，在包根放置空文件 py.typed（PEP 561），并对公共 API 逐步补类型。
  • 应用项目可在入口与关键模块为函数参数、返回值写上 str、list[str] 等，复杂结构用 TypedDict、Protocol。

详细规则见官方文档：Pyright Configuration。

五、与编辑器、Ruff 的关系

1. VS Code / Cursor

安装 Pylance（或内置语言服务）后，会在编辑时读取 pyproject.toml 中的 [tool.pyright]；终端里 uv run basedpyright 与编辑器诊断应共用同一 pyproject.toml，避免两套配置。

2. 与 Ruff 分工

  • Ruff：风格、部分 lint、格式化（见《第三章：UV 项目开发添加 Ruff：代码检查与格式化》）。
  • Pyright / BasedPyright：类型与导入解析等静态语义。二者可同时启用；避免用 Ruff 的 ANN 等与 Pyright 重复的规则集，减少噪音。

六、常用命令速查

目的 命令
安装（PyPI） uv add --dev basedpyright
版本 uv run basedpyright --version
按配置检查 uv run basedpyright
检查子路径 uv run basedpyright src/包名

更多说明：BasedPyright · Pyright。

本章小结

要点 结论
工具选型 BasedPyright（PyPI 安装、配置兼容）或微软原版 Pyright（Node），二选一
核心价值 运行前发现类型错误、None 误用等问题，配合类型注解提升代码质量
核心配置 [tool.pyright] 写在 pyproject.toml：include、pythonVersion、typeCheckingMode
注解配套 库发布需 py.typed（PEP 561）；应用项目逐步补参数/返回值注解
工具分工 Ruff 管风格格式、Pyright 管类型语义，避免 ANN 等重复规则
