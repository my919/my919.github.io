第五章：自定义协议实战

概念基础

  1. 真实系统多私有协议：RPC（Dubbo、Motan）、IM、游戏网关、物联网接入，几乎都用自定义二进制协议而非裸文本，追求低带宽、快解析、可扩展。
  2. 协议即契约：定义清楚「魔数 + 版本 + 类型 + 长度 + 载荷」的字节布局，是客户端服务端能互通的根基；编解码器只是这份契约的代码实现。
  3. 本章目标：设计一套完整的私有协议 XProtocol，用第四章的 FrameDecoder + Encoder/Decoder 组装出可运行的服务端与客户端，把前三章的知识串起来落地。
  4. 分层清晰：协议定义（Message POJO）→ 编解码器（切包 + 对象互转）→ Pipeline 装配 → 业务 Handler → 启动类，每层职责单一。
  5. 可演进：带版本号与消息类型，未来加心跳、鉴权、压缩只需扩展类型枚举，不动框架。

本章实战依赖 第三章 的组件知识与 第四章 的编解码器。

一、协议设计：XProtocol 字节布局

一套简单的请求/响应协议，统一报文格式：

字段 长度 说明
魔数 magic 1 固定 0xAB，快速识别错位/非法连接
版本 version 1 协议版本，便于演进
类型 type 1 消息类型：1=请求，2=响应，3=心跳
序列号 requestId 4 关联请求与响应，支持异步
长度 length 4 载荷字节数（不含头部）
载荷 payload length 业务数据

头部固定 11 字节，载荷可变。长度字段值=载荷长度，故 LengthFieldBasedFrameDecoder 配置：lengthFieldOffset=7（前面 7 字节头）、lengthFieldLength=4、lengthAdjustment=0、initialBytesToStrip=0（保留整帧，让解码器读头部）。

七、客户端：连接 + 异步发请求

与同步 Promise + await 风格不同，这里 send 立即返回 CompletableFuture，调用线程不阻塞；响应到达（或超时、连接断开）时由 Handler 完成 future，触发回调链。这样一条连接可并发发多个请求，靠 requestId 区分响应，是 RPC 客户端的典型写法。

客户端 Handler：收到响应按 requestId 找到对应 future 并 complete，触发 send 返回的回调链；连接断开时把所有未完成 future 异常完成，避免调用方无限等待：

三处异步关键点：

  1. send 非阻塞：writeAndFlush 后立即返回 CompletableFuture，调用线程不等响应，可继续发下一条请求——实现一条连接多请求并发（多路复用）。
  2. 回调链：thenAccept 处理成功结果、exceptionally 兜底异常、allOf().join() 汇合多个 future，链式编排避免回调地狱。
  3. 失败传播：超时（orTimeout）、连接断开（channelInactive）都通过 completeExceptionally 让 future 异常完成，异常顺着回调链传到 exceptionally，不会丢失或挂死。

CompletableFuture 的 complete/completeExceptionally 可在任意线程调用（这里是 EventLoop 线程），与 send 的调用线程（如业务线程）安全协作；pending 用 ConcurrentHashMap 保证并发安全。

八、运行与验证

  1. 启动服务端：XServer（监听 8000）。
  2. 启动客户端：XClient，预期输出（三条请求并发发送，hello/netty/protocol 各自的回调在对应响应到达时触发，顺序为响应到达顺序，通常与发送一致但不保证严格一致）：
  1. 若把 send 的超时改短（如 1 秒）再停掉服务端，可验证失败传播：exceptionally 回调打印 xxx 失败: ...，而不会挂死。
  2. 用 nc 也可手工构造字节验证（略），或加 io.netty.handler.logging.LoggingHandler 在 Pipeline 头部打印出入站字节流。

九、可扩展方向

方向 做法
心跳保活 加 IdleStateHandler，空闲时发 TYPE_HEARTBEAT，见 第六章
响应式编排 在 CompletableFuture 之上接 Reactor/RxJava，用 Mono/Flux 编排复杂异步流与背压
多路复用 一条连接并发多个请求，靠 requestId 区分响应（本例已支持）
鉴权 连接建立后第一条消息携带 token，Handler 校验
压缩 载荷用 gzip，加 type 区分是否压缩
TLS 用 SslHandler 放在 Pipeline 最前

本章小结

要点 结论
协议设计 固定头 + 长度域 + 变长载荷；魔数防错位、版本号便于演进
切包 LengthFieldBasedFrameDecoder 按长度字段切，参数对照字节布局核对
编解码 MessageToByteEncoder 出站编码、MessageToMessageDecoder 入站解码
Pipeline 装配 帧解码 → 消息解码 → 消息编码（出站）→ 业务 Handler
请求响应关联 requestId + CompletableFuture，send 非阻塞返回，回调链处理结果，支持一条连接并发多请求
业务 Handler 用 SimpleChannelInboundHandler<Message> 自动释放、类型过滤
可演进 版本号、类型枚举承载心跳/鉴权/压缩等扩展，不动框架
