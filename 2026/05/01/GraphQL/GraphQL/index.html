第一章：GraphQL 入门与 Schema 设计

概念基础

  1. API 查询语言：GraphQL 由 Facebook 开源，客户端在单一端点上按需声明「要哪些字段」，服务端精确返回同构数据，避免多余传输。
  2. Schema 即契约：用 SDL 强类型定义数据模型与入口（Query / Mutation / Subscription），前后端基于同一份 Schema 协作、文档自动生成。
  3. Resolver 解析数据：每个字段对应一个解析器函数，可对接数据库、微服务或第三方 API，天然适合多数据源聚合。
  4. 直击 REST 痛点：避免过度获取（over-fetching）与多次请求瀑布，弱网与移动端收益明显。
  5. 取舍清晰：HTTP 缓存不如 REST 天然、需要防「恶意深查询」；简单 CRUD 留在 REST，复杂关联与聚合才是 GraphQL 主场。

本章是 GraphQL 系列起点：Schema 设计与查询语法。服务端落地见 第二章：GraphQL 服务端实战。

一、核心概念

Schema（模式）：用强类型定义数据结构与关系，是 GraphQL 的「契约」，包含：

  • Query：查询（读操作）入口
  • Mutation：变更（写操作）入口
  • Subscription：订阅（实时更新，基于 WebSocket）

二、与 REST 对比

维度 GraphQL REST
数据获取 客户端精准指定字段，无过度获取 固定返回结构，易冗余
请求次数 单一请求聚合多资源 多端点请求，易「请求瀑布」
版本控制 Schema 渐进演进，无需版本号 维护 v1/v2 多版本
文档 基于 Schema 自动生成（GraphiQL） 手动维护（Swagger 等）
实时能力 原生 Subscription（WebSocket） 轮询/SSE，成本高
缓存 依赖客户端实体缓存（Apollo） 天然适配 HTTP 缓存

结论：GraphQL 显著减少传输量与请求次数，弱网/移动端收益极大；REST 更简单、成熟、缓存友好。两者互补，按场景选择。

三、工作流程



flowchart LR
  Client[GraphQL Client] -->|单 POST /graphql| S[Schema 校验]
  S --> R[Resolver 执行]
  R --> DB[(多数据源)]
  R --> Client
  1. 定义 Schema：服务端用 SDL 定义类型、Query、Mutation。
  2. 实现 Resolver：每个字段对应解析器，对接数据源。
  3. 客户端请求：POST 单一端点（/graphql），携带 Query/Mutation。
  4. 服务端执行：校验 Query → 调用 Resolver → 按请求结构返回 JSON。
  5. 客户端接收：响应结构与 Query 完全一致，直接渲染。

四、适用场景

  • ✅ 复杂前端应用（电商、社交）：多数据关联、按需字段
  • ✅ 移动端/弱网环境：减少请求与数据体积
  • ✅ 微服务架构：统一网关聚合多服务数据
  • ✅ 实时功能（聊天、通知、看板）：Subscription 原生支持
  • ❌ 简单 CRUD 服务：REST 更轻量、易维护
  • ❌ 高缓存吞吐场景：REST 的 HTTP 缓存更高效

  • 服务端：Apollo Server、graphql-yoga、Hasura（数据库自动生成 GraphQL）

本章小结

要点 结论
核心思想 Schema 定义契约，客户端按需查询，响应结构与请求完全同构
三大入口 Query 读、Mutation 写、Subscription 实时订阅
对比 REST 无过度获取、单端点少请求；HTTP 缓存不如 REST 天然
适用判断 复杂关联/弱网/多源聚合选 GraphQL；简单 CRUD 留在 REST
工具链 Apollo 全家桶 + GraphiQL 调试，文档随 Schema 自动生成
