第四章：Golang 工程实践

概念基础

  1. 从会写到能维护：语法与标准库之外，工程化能力（模块管理、测试、错误规范、性能分析）决定代码能否在团队中长期演进。
  2. 测试是一等公民：go test 内建，无第三方框架；表驱动测试与基准测试是 Go 社区的统一语言，CI 里 -race 必开。
  3. 错误处理要规范：%w 包装 + errors.Is/As 判断是 1.13+ 的标准范式；团队需统一「在哪里包装、在哪里兜底日志」。
  4. 泛型已成熟：1.18+ 类型参数消除 interface{} 转换样板，标准库 slices/maps 已泛型化——但泛型不是银弹，接口优先。
  5. 可观测性内建：pprof CPU/内存/协程剖析开箱即用，配合 expvar/metrics 定位线上问题。

三、错误处理工程化

分层规范：底层只包装（%w）不加日志，顶层记一次日志——中间层重复日志是排查噪音主因。errors.Is 判值、errors.As 判类型，别用字符串匹配。

四、泛型

场景 用泛型 用接口
容器/算法对元素类型泛化 ✅ ❌（要断言）
多态行为抽象 ❌ ✅
标准库已提供（slices/maps） 直接用 —

泛型解决「类型不同的相同算法」，接口解决「行为不同的相同契约」；需要运行时动态分发时接口仍是首选。

五、性能分析 pprof

剖面 定位问题
profile CPU 热点、算法复杂度
heap 内存分配大户、泄漏对象
goroutine goroutine 泄漏、阻塞点
block/mutex 锁竞争

压测+剖析联动：先 go test -bench 建基线，再 pprof 找热点；优化后再跑基准对比，数据说话，不凭感觉。

六、工具链与项目规范

1. 常用工具

工具 作用
go vet 静态检查（printf 参数、锁拷贝等），CI 必跑
gofmt/go fmt 格式化，团队零争议
golangci-lint run 聚合 linter（errcheck、staticcheck 等），提交前
go build -trimpath -ldflags "-s -w" 生产构建：去路径、去符号表减小体积

2. 项目布局（社区惯例）

依赖方向单一：handler→service→repo，禁止反向与跨层；internal 防外部引用，cmd 保持薄。

七、常见陷阱

陷阱 说明
go mod tidy 不跑 依赖漂移、CI 失败；提交前必跑
测试只写 happy path 表驱动覆盖边界；错误分支也是需求
t.Fatal 用在子测试外 主测试 Fatal 会跳过后续子测试，用 t.Error 或进子测试
基准没 reset bench 循环外初始化大对象，污染结果；用 b.ResetTimer()
错误在中间层打日志 分层只包装，顶层记一次
滥用泛型 行为多态用接口；泛型仅统一算法
pprof 暴露公网 只监听 localhost + 访问控制
生产构建带调试符号 -ldflags "-s -w" -trimpath 减体积防信息泄露

本章小结

要点 结论
依赖 go get 装包、tidy 清理、go.sum 提交、replace 只用于本地调试
测试 表驱动 + 子测试；-race/-bench/-cover CI 三件套；httptest 测 handler
错误 %w 包装、Is/As 判断、顶层统一兜底日志
泛型 统一算法用泛型、抽象行为用接口、~ 约束底层类型
pprof profile/heap/goroutine 四剖面；压测+剖析+对比闭环
工具 vet/fmt/golangci-lint 流水线；cmd 薄壳 + internal 分层
