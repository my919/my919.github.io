Layer 2 扩容深度指南：Optimistic Rollup · ZK Rollup · EIP-4844

发表于 2026-10-11 更新于 2026-10-25 分类于 区块链 本文字数： 26k 阅读时长 ≈ 23 分钟

区块链 · Layer 2 扩容

执行移到链下，数据与安全留在以太坊。一文讲透 Optimistic Rollup、ZK Rollup 与 EIP-4844 的原理，并附可运行的 Solidity / ethers.js / Hardhat / Python 实战代码，全部中文注释。

1. 为什么需要 Layer 2

1.1 区块链三难困境

区块链领域有一个著名的三难（Trilemma）：安全性、去中心化、可扩展性三者难以同时做到极致。

  • 安全性：链抵抗攻击、保证交易最终有效的能力，以太坊以 PoS + 庞大的验证者集合提供经济安全。
  • 去中心化：普通硬件（一台消费级笔记本/云主机）就能运行节点，验证者和节点数量足够多，没有谁能轻易垄断或审查。
  • 可扩展性：单位时间能处理多少交易（TPS）、每笔交易有多便宜。

以太坊优先保证了前两者，代价是 L1 的吞吐量有限。这个限制不是靠”优化代码”能根治的，而是被有意设计成这样的。

1.2 区块 Gas 上限：一道刻意压低的闸门

每个以太坊区块有 Gas 上限（block gas limit）。它长期维持在 3000 万 Gas 左右；2025 年先上调至 3600 万，Fusaka 升级（EIP-7935）后分阶段提升到约 6000 万 Gas。即便如此，面对全球级应用的需求仍然紧张——一次普通的 USDT Transfer 就要烧掉约 5 万 Gas，一个复杂的 Uniswap V3 交易可能超过 20 万 Gas。

为什么不直接把 Gas 上限提高 10 倍？因为区块越大：

  1. 状态增长越快：节点要存储的链数据、状态数据急速膨胀，硬盘成本上升；
  2. 验证时间越长：出块窗口只有 12 秒，算不完就出块，验证者更容易掉队；
  3. 节点越贵越中心化：能跑节点的人越少，”世界计算机”就退化成”一小撮公司的计算机”，三难中的去中心化与安全性同时被牺牲。

提高 Gas 上限本质上是用去中心化换吞吐量，以太坊社区对此极其谨慎（2025–2026 年的几次上调都配合了 EIP-7883 等真实定价修复，防止被廉价重计算攻击）。

1.3 calldata 成本：Rollup 费用的万恶之源

L1 上最贵的资源之一是 calldata（调用数据）——交易附带的任意字节，会被所有节点永久下载、验证并保存。按 EIP-2028 定价：

  • calldata 的非零字节：16 Gas/字节
  • calldata 的零字节：4 Gas/字节

1 KB 非零 calldata 约 1.6 万 Gas。在 L1 拥堵时，把一批 L2 交易原始数据写进 calldata，可能比执行它们还贵一个数量级——这正是后来 EIP-4844 要解决的问题（见第 5 节）。

1.4 Rollup 的核心思想：执行链下化，数据留在 L1

Rollup（卷叠） 的思路可以浓缩成一句话：

把计算（执行）搬到链下，把数据（交易原文 + 状态承诺）留在 L1；L1 不替你跑计算，只负责数据托管、最终结算与争议仲裁。

具体来说：

  1. 用户把交易发给 L2 的 sequencer（排序器），sequencer 在链下高速执行，给出近乎即时的软确认；
  2. sequencer 把成百上千笔交易压缩成一个 batch（批次），以 calldata（或 blob）形式提交一笔 L1 交易；
  3. L1 合约只校验/记录这批数据，并锚定一个状态承诺（state commitment，通常是新状态根的哈希）；
  4. 任何人都能根据 L1 上的完整数据重放（replay）出全部 L2 状态——这叫数据可用性（Data Availability, DA）。

关键推论：因为重建状态所需的一切数据都在 L1，sequencer 即使作恶，也无法凭空伪造历史或永久扣押资产。Rollup 把以太坊的安全（共识 + DA）”借”了过来，自己只做最擅长的高速执行，从而打破三难的束缚。

简单对比：

维度 L1 直连 Optimistic Rollup ZK Rollup
执行位置 L1 全网逐笔执行 链下 sequencer 链下 sequencer/prover
数据可用性 L1 L1 calldata/blob L1 calldata/blob
L1 如何保证正确 每步都执行验证 欺诈证明（事后抓错） 有效性证明（每批必证）
最终性 约 12 分钟 挑战窗口（主网 7 天） 证明验证通过即最终
EVM 兼容 原生 高（可做到等价） 取决于 zkEVM 类型

2. Rollup 通用架构

无论 Optimistic 还是 ZK，Rollup 的骨架高度一致，由”链下那一套”和”L1 上那几个合约”组成。

2.1 Sequencer：排序、执行、软确认

Sequencer（排序器） 是 L2 的引擎，职责有三：

  1. 接收与排序交易：维护一个 L2 内存池，决定交易先后顺序（先到先得是常态，MEV 拍卖是演进方向）；
  2. 链下执行：在本地跑状态转移（EVM 或自定义 VM），更新 L2 状态树；
  3. 即时软确认（soft confirmation）：用户提交交易后毫秒级收到”已被排序”的反馈，体验像中心化服务器，但此时还没有 L1 最终性。

sequencer 是 Rollup 架构中目前最中心化的环节：它可以审查交易、可以宕机。但它不能永久偷走资金——因为数据和出口都由 L1 兜底（见 2.5）。社区的去中心化路线是多 sequencer 共识（基于 Tendermint、Espresso、Raft 等）与 proposer/builder 分离。

2.2 Batch 提交：把成千上万笔卷成一笔

sequencer 定期（通常几秒到几十秒）把攒下的交易压缩编码成一个 batch，只向 L1 发一笔交易。压缩手段包括：省略大量重复的零字节、索引化地址、只存交易的差分。这就是 “roll-up（卷起来）” 名字的由来——L1 的一个区块可以”卷”进成千上万笔 L2 交易，费用由批次内所有用户分摊。

2.3 State Commitment：链上只锚定一个哈希

逐笔在 L1 执行违背扩容初衷，因此提交批次时，链上只锚定一个状态承诺：执行完这批交易后，整个 L2 状态（所有账户余额、合约存储构成的树）的根哈希，例如 keccak256 或 Verkle/Merkle 树的根。

  • 对 Optimistic Rollup，状态根被”乐观地”接受，等待挑战窗口；
  • 对 ZK Rollup，状态根必须与一个有效性证明同时提交，链上验证通过才接受。

2.4 L1 上的 Rollup 合约

L1 侧通常有三类合约（工程上可能合并）：

  1. 数据/状态合约：接收 batch 数据、记录状态根与批次序号；
  2. 桥合约（standard bridge）：处理 L1↔L2 的资产锁定与铸造（锁在 L1、铸在 L2）；
  3. 验证合约：OR 上是欺诈证明裁判，ZK 上是一个约几千字节 Gas 的 proof verifier。

2.5 强制包含与逃生舱：为什么它们是底线

如果 sequencer 可以拒绝你的提现交易、并且永远不被绕过，那”去中心化安全”就是空话。因此正统 Rollup 必须提供两条退路：

  • 强制包含（forced inclusion / force transaction）：用户可以跳过 sequencer，自费直接把交易（或其哈希）发到 L1 合约的强制队列。协议规定 sequencer 日后必须按顺序处理这批交易，否则无法继续提交正常批次。这保证了抗审查（censorship resistance）。
  • 逃生舱（escape hatch）：当整个 L2 网络停摆、sequencer 长期离线时，用户仍能凭借 L1 上的数据（状态根 + 自己的 Merkle 证明，或直接全量重放）在 L1 合约处自助提款。这保证了活性（liveness）与资产可退出性。

判断一个”L2”成色如何，就问两个问题：数据真的在 L1 吗？sequencer 跑路时我能自助退出吗？ 两个”是”才是 Rollup；任何一个答”否”，更可能是 Validium 或托管侧链（见第 11 节陷阱表）。

3. Optimistic Rollup：乐观相信，事后抓错

3.1 乐观假设与挑战窗口

Optimistic Rollup（OR，乐观卷叠） 的哲学是”无罪推定“：sequencer 提交新状态根时，L1 默认相信它是诚实的，不做任何昂贵的计算校验——因此提交成本极低。

但”相信”附一个期限：挑战窗口（challenge window）。OP Stack 主网设置为 7 天（302400 秒）；Arbitrum 的确认期同样是 7 天量级。在窗口期内，任何监视网络的验证者只要发现状态根是假的，都可以提交**欺诈证明（fraud proof）**发起挑战；挑战成立，假状态根被回滚，作恶者被罚没押金，诚实路径被重新采纳。窗口内无人成功挑战，状态根才算”最终化”。

这个模型成立的前提是至少有一个诚实验证者在线并保有完整数据（因为 DA 在 L1，验证者不需要信任 sequencer，自己就能重放），即”诚实少数（honest minority）假设“。门槛比”全网都要重新执行”低得多。

3.2 欺诈证明：交互式二分挑战

最朴素的欺诈证明是”单轮证明”：挑战者直接把整批交易在 L1 上重放一遍。安全但极贵——违背扩容初衷。于是有了交互式欺诈证明（interactive fraud proof），核心算法是二分挑战（bisection）。

把争议执行看作 N 个顺序步骤，每步之后有一个状态承诺（真实系统里是状态哈希）。双方对初始状态（第 0 步）认识一致，对最终状态（第 N 步）认识不一致：

  1. 挑战者要求主张者公布中点 m = N/2 的状态承诺；
  2. 若中点状态与诚实计算一致，说明争议在后半段，丢弃前半段；否则争议在前半段；
  3. 对争议区间重复二分……

每轮质询都把争议区间缩小一半，只需 ⌈log₂N⌉ 轮往返（比如 100 万步只需约 20 轮），最终定位到相邻的两个步骤——争议必出在这一步单条指令上。最后，L1 只在链上执行这一条指令（one-step execution）并比对结果，谁撒谎一目了然。链上成本从 O(N) 骤降为 O(log N) 次哈希比对 + O(1) 步真实执行。第 10 节的 Python 实战会完整模拟这个二分过程。

3.3 OP Stack 与 Arbitrum Nitro 的差异

两大 OR 技术栈都用交互式二分，差别主要在”最后一步在链上执行什么”：

维度 OP Stack（Optimism、Base、Unichain 等） Arbitrum Nitro
证明程序 Cannon：把执行程序编译成 MIPS 指令集 Nitro：把 Geth 核心编译成 WASM
单步证明 链上验证一条 MIPS 指令的执行 + 预映像（preimage）Oracle 链上验证一条 WASM 指令的执行
状态格式 标准 EVM 状态，利于 EVM 等价 自定义状态机 + EVM 兼容，执行更贴合 Arbitrum 设计
生态 开源超级链（Superchain），可一键发链 Arbitrum Orbit 链生态，Stylus 支持 Rust/C 等多语言合约

简单说：Cannon 在链上仲裁 MIPS 指令，Nitro 在链上仲裁 WASM 指令，其余思想同构。

3.4 提现为什么有 7 天延迟，快速桥如何救场

OR 上 L2→L1 的标准提现是这样走的（OP Stack 为例）：

  1. 发起（initiate）：在 L2 调用标准桥 withdraw，资产被锁定/销毁；
  2. 等待状态根提交：这笔交易随 batch 进入 L1；
  3. 证明（prove）：在 L1 调用 proveWithdrawalTransaction，提交针对已提交状态根的 Merkle 证明；
  4. 等待挑战窗口结束（约 7 天）；
  5. 最终化（finalize）：窗口内无欺诈证明，调用 finalizeWithdrawalTransaction 在 L1 拿回资产。

7 天不是技术失误，而是安全模型的代价——必须给诚实验证者留出抓假的时间。

第三方快速桥（fast bridge） 解决的是流动性问题，而非安全问题：Hop、Across 等协议的流动性提供者（LP）在 L1 先行垫付资产给用户（通常几分钟到账，收一笔手续费），LP 自己再慢慢走完 7 天官方流程。要注意：快速桥引入了对 LP/协议的额外信任与合约风险，它不是官方通道，且小额提现才划算。

4. ZK Rollup：每批必证，证明即最终

4.1 有效性证明：不假设任何人诚实

ZK Rollup 用完全相反的策略取代”乐观 + 挑战”：sequencer 每提交一个 batch，必须同时附上一个密码学证明——有效性证明（validity proof），断言”这批交易从旧状态根出发，诚实地执行后，确实得到新状态根”。

L1 合约用一个内置的**验证器（verifier）**核验这个证明：

  • 验证通过 → 状态根立即最终化（instant finality），不存在 7 天等待；
  • 验证失败 → 该 batch 直接被拒，假状态根根本上不了链。

安全性不再依赖”窗口期内有诚实人盯着”，而是纯数学保证：计算不可伪造，但验证极其廉价。

4.2 SNARK / STARK 的直觉：把一整批计算压成一个证明

零知识证明听起来玄，但用于 Rollup 时只需建立三层直觉：

  1. 算术化（arithmetization）：把程序执行（每笔转账、每个 EVM 操作码）翻译成一组算术电路约束——本质是一大批方程，”执行正确”等价于”这些方程全部成立”。比如一次余额校验被表达成 旧余额 - 金额 = 新余额 这样的约束。
  2. 多项式承诺（polynomial commitment）：证明者把所有约束的解”编码”进一个多项式，并借助 R1CS/QAP（SNARK 路线） 或 AIR（STARK 路线） 把”成千上万条约束都成立”归约为”这几个多项式在一个随机点上相等“。多项式承诺方案（如 KZG、FRI）让证明者可以先承诺多项式、之后无法篡改。
  3. 简短检验：验证者只需检查这一个点上的方程与承诺，O(1) 或对数级复杂度，与计算量几乎无关。于是”执行了 100 万步且步步正确”被压缩成一个几百字节、毫秒级可验的证明。

SNARK 与 STARK 的工程差异：

维度 zkSNARK（如 Groth16、PLONK/KZG） zkSTARK（FRI）
证明体积 极小（数百字节） 较大（数十 KB+）
可信初始化 Groth16 需 per-circuit trusted setup；PLONK/KZG 需 universal setup 完全透明，无需 trusted setup
安全假设 依赖椭圆曲线/配对（有量子破解理论风险） 主要基于哈希与编码（抗量子）
证明速度 较快 较慢，但可高度并行

一句话记忆：SNARK 小而快但要”仪式”，STARK 透明抗量子但证明更胖。

4.3 zkEVM 的类型划分

让 ZK 证明系统理解 EVM（而非另造一种简单的转账电路）是难题。Vitalik 把 zkEVM 分成四类，等价程度从高到低：

  • Type 1（完全等价）：完全按以太坊共识与 EVM 规则证明，无需任何改动，证明生成最慢。代表：以太坊自身视角、Taiko。
  • Type 2（EVM 等价）：EVM 字节码完全兼容，仅改状态树结构等 EVM 之外的数据布局。代表：Scroll、Polygon zkEVM（后者偏 Type 2.5/3）。
  • Type 3（近乎等价）：去掉少数难以证明的 EVM 特性/预编译，绝大多数合约可直接跑。代表：早期 Polygon zkEVM、Scroll 主网初期。
  • Type 4（语言级）：不证明 EVM 字节码，直接把高级语言编译成对证明友好的自定义字节码（VM 级证明）。兼容性要靠 SDK/编译器补齐，但证明最快。代表：zkSync Era（自定义 VM）、Starknet（Cairo 语言）。

类型越靠前兼容性越好、证明成本越高；越靠后性能越好、移植成本越大。这不是高下之分，而是工程取舍。

4.4 证明成本、证明时间与递归证明

ZK Rollup 的瓶颈不在验证（链上验证很便宜），而在链下生成证明：证明一个普通批次可能需要专用硬件（GPU/FPGA）跑几秒到几分钟，成本随链上活跃度波动。这是早期 ZK 链费用与延迟的主要来源。

关键优化是递归证明（recursive proof）与证明聚合：

  • 每个子批次各生成一个证明，再用一个证明来证明”这一批证明全都验证通过”——证明的证明，层层递归，最终 L1 只验证一个证明；
  • 同一 prover 可以把多个 L2（甚至 L3，如 Starknet 上的应用链）的证明聚合成一个提交，进一步摊薄 L1 成本；
  • 递归还能让不同证明系统互转（STARK 快速生成 → 递归压缩成 SNARK 上链），兼得两者优点。

代表项目一句话：zkSync Era 主打原生账户抽象与 Type 4 性能；Starknet 用 Cairo 语言与 STARK 技术，递归聚合是看家本领；Polygon zkEVM 走 EVM 等价路线。加上 Scroll、Linea、Taiko，构成 ZK 阵营第一梯队。

5. EIP-4844：blob 交易与费用骤降

5.1 问题回顾：calldata 又贵又永久

在 EIP-4844 之前，Rollup 只能把 batch 数据写进 calldata。问题有两个：calldata 按 16 Gas/字节收费太贵；而且这些数据会被所有节点永久保存，可 Rollup 其实只需要”足够长时间内数据可得”（让任何人能取回资金、重建状态），并不需要它躺在每个节点的硬盘里一万年。

5.2 Blob 携带交易：一种新的交易类型

2024 年 3 月 Dencun 升级激活 EIP-4844（proto-danksharding，原始 Danksharding），引入一种新的 type-3 交易：blob-carrying transaction（携带 blob 的交易）：

  • 一个 blob 容量为 128 KiB（4096 个域元素 × 32 字节）；
  • blob 数据不进入 EVM：合约只能看到一个 版本化哈希（versioned hash，首字节为版本号 0x01），无法读取 blob 内容本身；
  • blob 由共识层节点保存约 4096 个 epoch（约 18 天），之后可被修剪删除——对 Rollup 来说，这段时间已足够任何人完成挑战与退出。

5.3 Blob 与 calldata 的区别，以及 KZG 承诺

维度 calldata blob
EVM 能否读取 能，合约可逐字节访问 不能，只见版本化哈希
定价 并入主 Gas 费市场（16/4 Gas 每字节） 独立的 blob 费市场（EIP-1559 式动态 base fee）
存储期限 永久 约 18 天后可修剪
每块容量 受区块 Gas 上限约束 专用 blob gas 额度
单位成本 高 低一个数量级以上

KZG 承诺一句话：blob 内容被编码成多项式在若干点上的取值，KZG（Kate–Zaverucha–Goldberg）多项式承诺把整个 blob 压缩成一个椭圆曲线点，任何人都可以凭它对 blob 中任意位置做”打开证明”并验证，而无需拿到全部数据——这也是日后数据可用性采样的密码学地基。

5.4 费用为何骤降

Dencun 激活后，主流 Rollup 上的 L1 数据部分费用普遍下降 80% 以上，许多场景下降 10–100 倍，Base/Arbitrum 上出现了几分钱甚至更低的转账。原因有三：

  1. blob 不走主 Gas 市场，每字节边际成本极低（一个 128 KiB blob 只消耗固定的 2¹⁷ blob gas）；
  2. blob base fee 有独立的 EIP-1559 调节，初始最低价仅 1 gwei，按各块 blob 使用量动态升降；
  3. 数据只临时保存，不为永久状态增长买单。

容量参数也在持续扩容：Dencun 时目标 3 个、上限 6 个 blob/块；2025 年 5 月 Pectra（EIP-7691） 翻倍到目标 6 个、上限 9 个；Fusaka 时代参数改为可配置。注意 blob base fee 在拥堵期同样会飙升（2024 年曾短时涨到 1–2 mgwei 级别），并非恒定为 1 gwei。

5.5 后续：full danksharding 与 PeerDAS

EIP-4844 只是”原型”，真正的 full danksharding 目标是：

  1. 数据可用性采样（DAS）：节点不再下载全部 blob，而是随机抽查很少一些”小块”；若抽查都通过且配合纠删码，就能高概率确认全部数据真的在网络上，任何隐藏数据的行为都会暴露；
  2. 纠删码（erasure coding）：把数据扩展编码，即使丢失一部分也能恢复；
  3. 提议者/构建者分离（PBS）：区块提议者无需自己处理海量数据，由专业 block builder 构造；
  4. PeerDAS：Fusaka 引入的点对点数据采样，已让 DA 容量先提升约一个数量级，是走向完整 DAS 的关键一步。

届时以太坊每个区块的 DA 带宽还能再上一个大台阶，而普通节点依旧轻量。

6. L2 费用构成与安全继承

6.1 L2 费用 = L1 data fee + L2 execution fee

在 L2 发起一笔交易，最终承担的费用由两部分构成：

  1. L1 数据费（L1 data fee）：你的交易作为 batch 的一部分写进 L1 calldata/blob 的成本，按你在批次中占用的字节数均摊。这是早期 OR/ZK 费用的大头——哪怕 L2 执行近乎免费，只要把数据放上 L1 就要付租。EIP-4844 砍掉的正是这一块。
  2. L2 执行费（L2 execution fee）：在 L2 状态机上实际执行操作码的费用，同样走 EIP-1559 式机制（L2 gas price 通常只有 L1 的几十分之一）。

所以 L2 的 Gas 报价（如 Arbitrum 的 getFeeData 返回值）里往往能同时看到执行价与隐含的数据价；估算成本时只看 L2 gas price 会严重低估真实开销。

6.2 为什么说 L2 的安全继承自以太坊

正统 Rollup 的每一层安全都能追溯到 L1：

  • 共识与最终性：batch 和状态根是 L1 上的交易，受以太坊 PoS 共识保护，交易序与时间戳不可伪造；
  • 数据可用性：重建 L2 所需的原始数据在 L1，任何人无需许可即可成为验证者，sequencer 无法靠藏数据作弊；
  • 结算与仲裁：提款在 L1 合约结算，欺诈由 L1 裁决（OR），正确性由 L1 验证的数学证明保证（ZK）。

但要注意三个”不自动继承”：

  1. 桥合约风险：锁在 L1 的资产由桥合约代码和升级密钥控制——若升级密钥是中心化多签且无 timelock，密钥被盗等于桥被搬空（历史上多次大额桥事故）；
  2. Validity/DA 前提：如果数据其实在链下（Validium），或欺诈证明尚未真正启用（Stage 0 阶段的早期 Rollup），安全就要打折，L2BEAT 用 Stage 0/1/2 标注这类成熟度；
  3. 活性 ≠ 安全性：sequencer 宕机不能偷走你的钱，但会让你暂时无法交易，直到强制包含/逃生舱生效。
