1. 从位置寻址到内容寻址：CID 的构造

1.1 位置寻址：HTTP URL 指向“在哪里”

传统 HTTP 使用位置寻址（Location Addressing）：一个 URL 由协议、主机名、路径三部分组成，比如 https://server.com/a.jpg。它描述的是“去哪台机器的哪个目录取文件”，至于取回来的字节是什么，URL 本身不作任何承诺。服务器运维者可以在同一 URL 下随时替换文件内容（内容漂移）；服务器关停、域名过期、链路被墙，链接就会腐烂（link rot）。互联网上大量失效链接都源于此。

1.2 内容寻址：地址就是内容本身

IPFS 采用内容寻址（Content Addressing）：文件经过哈希运算得到一个与内容强绑定的唯一标识——CID（Content Identifier，内容标识符）。你访问的不再是“某台服务器上的某个路径”，而是“哈希等于这个值的那份内容”。它带来三个直接结果：

  • 可验证完整性：取回字节后重新计算哈希，必须等于 CID，否则说明内容损坏或被篡改。
  • 天然不可变：内容改动一个比特，哈希值就完全不同，等于换了一个新地址，旧地址永远对应旧内容。
  • 全局自动去重：相同内容在全网必然得到相同 CID。十个人上传同一张图，网络里只存一份数据块，任何引用都指向同一个 CID。

1.4 CIDv0 与 CIDv1

CIDv0 是 IPFS 最早使用的格式，它就是 multihash 的 Base58btc 编码，隐式约定“编解码器为 dag-pb、哈希为 SHA-256”。因为字节前缀固定为 0x12 0x20，Base58btc 编码后恒以 Qm 开头，例如 QmYwAPJzv5CZsnA625s3Xf2nemtYgPpHdWEz79ojWnPbdG。

  • dag-pb 内容的 CIDv1 形如 bafybeigdyrzt5sfp7udm7hu76uh7y26nf3efuylqabf3oclgtqy55fbzdi；
  • raw 内容的 CIDv1 形如 bafk...（前缀由 0x01 0x55 的 Base32 决定）。

CIDv1 是现在的推荐格式：显式版本、显式 codec、可用多种 multibase 编码、大小写安全。CIDv0 与 CIDv1 描述同一块时可以相互转换。

2. IPFS 工作原理：Merkle DAG · DHT · Bitswap · Pinning

IPFS（InterPlanetary File System）不是某一家公司的云盘，而是一套开放的 P2P 协议族，节点之间地位平等、自由加入退出。理解它要抓住四个部件。

2.1 Merkle DAG：用哈希指针组织数据

文件上传时会被切分成若干数据块（Block），每块拥有自己的 CID。块与块之间通过 CID 互相引用，构成一棵 Merkle DAG（默克有向无环图）：

  • 有向：引用从父节点指向子节点；
  • 无环：子节点不可能再引用回祖先，结构永远收敛；
  • Merkle：父节点的 CID 由“子节点 CID 列表 + 自身数据”计算得到，任何底层字节的改动都会沿路径向上传导，使根 CID 改变。

IPFS 最经典的块格式是 PB-DAG（dag-pb），用 Protocol Buffers 编码，块内只有两类字段：Data（数据）和 Links（指向其他块的 CID 及名字、大小）。在 dag-pb 之上还有一层 UnixFS，负责把“块图”解释成用户熟悉的文件语义：文件大小、分块方式、目录列表等。一个目录本身也是一个 DAG 节点，它的 Links 里记录了每个文件名到对应 CID 的映射。读取目录时，正是顺着这些链接逐块还原出全部文件。

2.2 DHT：怎么找到“谁存了这份内容”

网络中有几十万个节点，你想要某个 CID，如何知道哪些节点持有它？答案是基于 Kademlia 的 DHT（分布式哈希表）。它维护两类关键映射：

  • 内容路由：CID → 提供者（Provider）的 PeerID 列表。节点提供一份内容时，会向 DHT 写入一条 Provider Record，宣告“我有这个 CID”；查找者迭代地询问距离目标 CID 最近的节点，执行 FIND_PROVIDERS，最终拿到提供者的网络地址。
  • 节点路由：PeerID → 节点的多地址（multiaddr），用于真正建立连接。

Provider Record 有过期时间（约 24 小时），提供者必须周期性地重新宣告（reprovide），否则记录失效、别人就找不到你。注意：DHT 只负责“指路”，真正的字节传输不经过 DHT。

2.3 Bitswap：块级别的交换协议

拿到提供者地址后，节点之间通过 Bitswap 协议交换数据块。每个节点维护一个 want-list（想要清单）：连接建立后，双方互相发送 want-have / want-block 消息告知对方自己缺哪些块；持有块的节点回送块数据。Bitswap 是按块而非按文件工作的，配合 Merkle DAG，下载器可以并行向多个节点索取同一文件的不同块（甚至边传边校验）。协议内部还有账本式的记账机制，对长期只拿不给的节点形成信用约束。

2.4 Pinning：不“钉住”，内容就会被 GC

这是新手最容易踩的点：IPFS 节点默认不会永久保存你 add 的所有数据。为了控制磁盘占用，节点把临时获取的块放在缓存里，执行 ipfs repo gc（垃圾回收）时，所有未被 pin、也不在 MFS（可变文件系统）中的块都会被删除。你的节点关机、重装，内容同样可能消失。

**Pin（固定）**就是显式声明“这块数据要长期保留”：

  • ipfs pin add -r <CID> 做递归固定——不仅固定根节点，还固定整棵 DAG 的所有子块；
  • 直接固定（direct）只保留单个块；间接固定（indirect）指某块被递归固定的父节点所覆盖。

只在自己电脑上 pin 仍然是单点。因此生产中通常“自己 pin 一份 + 交给 pinning 服务 / 多节点各 pin 一份”，保证总有在线节点能提供数据并持续向 DHT 重新宣告。

2.5 网关与本地节点

本地 Kubo 节点启动后会开两个端口：5001 是 RPC API（写操作，应只绑 127.0.0.1，切勿暴露公网），8080 是本地只读网关。公共网关（如 https://ipfs.io/ipfs/<CID>、https://cloudflare-ipfs.com/...）是“HTTP 世界通往 IPFS 的桥”，让浏览器无需运行节点也能读取内容。但要清楚：走公共网关意味着信任网关运营方给你的字节（除非客户端本地再按 CID 校验一次）。https://<CID>.ipfs.<网关域名> 形式的子域网关能给每个 CID 独立的浏览器源（Origin），避免不同站点共享源导致的安全问题。

4. Filecoin：为 IPFS 装上激励层

IPFS 解决了“怎么找到并取回内容”，但没有任何协议层机制保证有人愿意一直存你的数据——pin 全靠自愿或付费信任。Filecoin 正是建立在 IPFS 同款技术（libp2p、CID、IPLD）之上的激励层：它是一条区块链，用代币经济和密码学证明，把“存数据”变成可验证、可结算、可惩罚的市场行为。

4.1 复制证明 PoRep：证明“真的存了”

存储矿工接单后要经过 Seal（封存）：把客户数据通过慢编码（耗时的编码运算，消耗真实算力与磁盘）密封成一个扇区（Sector，通常 32GiB），得到唯一的副本承诺 CommR。随后提交 PoRep（Proof-of-Replication，复制证明），密码学地证明：

  • 矿工确实对这份数据做了一次独立、物理存在的编码（CommR 由数据承诺 CommD、扇区编号与封存随机性导出）；
  • 同一份磁盘空间无法被反复声明用于多个订单（抵御 Sybil、女巫、外包攻击）。

证明体本身用 zk-SNARK 压缩，链上只需验证极小的证明，成本很低。封存完成后，矿工还要锁定质押品（FIL）。

4.2 时空证明 PoSt：证明“一直都在存”

“开始时存了”不等于“后来一直存着”。Filecoin 用 PoSt（Proof-of-Spacetime，时空证明）解决：矿工在每个证明周期内会收到对随机选中的扇区的挑战，必须在时限内读出对应编码并生成零知识证明提交上链（WindowPoSt）。全部扇区在一个周期（24 小时）内被覆盖一遍。连续挑战成功，等于向全网证明“这些字节此刻仍然在我磁盘上，且贯穿整个时间段”。一旦漏交证明或证明失败，矿工被罚没质押（slashing），奖励和押金都会受损。这就是“真的存了且一直存着”的技术答案。

4.3 存储市场、检索市场与 IPFS 的关系

  • 存储市场（链上撮合）：客户报价、矿工接单，双方签名形成存储交易（Deal），数据线下传给矿工，存证与结算上链。Filecoin Plus 的“验证数据”还能让矿工获得更高的有效算力权重。
  • 检索市场（链下交付）：检索矿工或网关就近、快速地把数据发给客户，按字节计费（走支付通道），解决封存数据“冷而慢”的问题，适合热点内容。
  • 与 IPFS 的关系：两者共享底层组件但相互独立。IPFS 节点之间免费、尽力而为地交换数据；Filecoin 用合约约束“持久化”。实践中常见组合是 IPFS 负责热分发与寻址，Filecoin 负责可审计的持久备份，内容用同一套 CID 贯通。

5. Arweave：一次付费的 permaweb（含 Irys 上传）

5.1 permaweb 与 blockweave

Arweave 走的是另一条路：数据直接写入链结构，一次付费、永久存储，其上的永久网页被称为 permaweb。Arweave 的底层不是普通区块链，而是 blockweave（区块编织）：每个新区块不仅引用前一个区块，还必须引用一个从历史中随机选中的回忆块（recall block）。矿工出块时要能拿出这个历史块中的数据片段——想挖矿就得存有历史数据，存储因此成为参与共识的前提。

5.2 SPoRA 共识与永久存储经济模型

Arweave 的共识是 SPoRA（Succinct Proofs of Random Access，随机访问的简洁证明）：矿工用密码学证明自己能在出块瞬间随机访问并召回指定的历史数据块，再结合检索速度等因素竞争出块奖励。这比早期的 PoA 更进一步，让“尽量完整、尽量快速地保存全量历史”成为最理性的策略。

经济上，上传者支付的费用不会立刻发给矿工，而是进入捐赠式基金（endowment）：系统按“存储硬件成本长期下降”的模型，把一次付费摊到极长的时间尺度上持续补贴矿工，从而在数学预期上支撑数十年乃至更久的存储。访问通过网关 https://arweave.net/<交易ID> 完成。

5.3 Irys / arbundles：批量上传

直接往 Arweave 链上发交易（L1）受区块吞吐和确认延迟限制。Irys（前身即 Bundlr）这类 L2 把成千上万笔交易在链下打包：每笔数据是一个用 arbundles 库构造、由用户独立签名的 DataItem；Irys 节点把它们打包成一笔 Arweave 交易上链，却给每个 DataItem 立即的上传凭证，并保证最终上链。如今绝大多数 Arweave 上的 NFT 数据都走 Irys。

5.4 与 IPFS 模型的差异

  • IPFS：内容寻址、免费、无内建持久承诺。数据“在不在”取决于有没有人 pin；想变内容可用 IPNS（可变指针）。
  • Filecoin：给 IPFS 式数据加可验证、有期限/交易约束的持久化，适合大容量冷存。
  • Arweave：一次付费、由共识与基金模型保证永久留存，不存在 GC；其标识是 Arweave 交易号而非 multihash CID，内容上链即不可改。

6. NFT 资产存储全流程：metadata、baseURI 与冻结

6.1 为什么 NFT 的图片和 metadata 必须去中心化

ERC-721 的 tokenURI(tokenId) 返回一份 JSON（metadata），里面有名称、描述、图片地址和属性。图片和完整 JSON 体积大、上链存储成本极高，于是项目方普遍把它们放在链下。如果放在自有服务器或云厂商桶里，风险是实打实的：改一下服务器上的图片就能让你的 NFT“变脸”，域名/服务器一停，tokenURI 直接 404——这是最常见的 rug pull 形式之一。正确做法是：图片放 IPFS/Arweave → metadata JSON 也放 IPFS/Arweave → 链上只存一个内容地址，双层资产都脱离单点控制。

6.2 tokenURI 用 ipfs:// 还是 https 网关

推荐链上存原生的 ipfs://<CID>/路径：它不绑定任何一家网关，任何客户端可自选节点/网关解析，天然中立。不要把 https://ipfs.io/ipfs/... 直接写进链——那等于把信任重新押在单一网关的可用性上（网关被墙、限流、关停都会让 NFT“消失”）。网关 URL 应只出现在前端展示层。主流市场（OpenSea 等）已支持解析 ipfs://。

8. 常见误用与陷阱

坑 现象/后果 解法
tokenURI 直接存 https 网关地址 网关被墙/限流/关停，NFT 图片集体 404，信任退回单点 链上只存 ipfs://CID，网关 URL 仅用于前端展示
上传后不 pin 节点 GC、关机后内容消失，tokenURI 变死链 pin add -r + pin 服务多点固定，或做 Filecoin 交易
文件命名为 1.json 却按 tokenId 拼接 链上解析到 /1，目录里只有 /1.json，全部 404 metadata 文件直接以 tokenId 命名（1、2…），不带后缀
baseURI 结尾漏斜杠 拼成 ipfs://bafy...1 之类非法地址 baseURI 一律以 / 结尾，如 ipfs://bafy.../
把 IPNS 当永久存储 IPNS 指针可变，项目方或私钥泄露者可随时改指向 要永久承诺就用 CID + 合约冻结开关
以为“传了 IPFS 就永远在” IPFS 只有路由与交换协议，无人保证别人持续存你的数据 pin 服务 / Filecoin 可验证存储，或 Arweave 一次付费
metadata 未冻结就开卖 owner 私钥被盗或内鬼改 baseURI 换图，典型 rug pull 揭盒后立即调用冻结，置不可逆标志
在浏览器直连 5001 RPC 默认 CORS 拦截；RPC 暴露公网可被任意写，风险极高 浏览器只走只读网关；写操作走自有后端，RPC 绑 127.0.0.1
