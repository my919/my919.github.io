DAO 链上治理深度指南：ERC20Votes · Governor · Timelock · 代币经济

区块链 · DAO 治理

把”规则”写成合约，让提案、投票、执行全部公开可审计。本文从治理代币快照机制讲起，拆解 OpenZeppelin Governor 全家桶与 Timelock 延迟执行，附可运行的 Solidity 合约、Hardhat 部署/测试、链下交互脚本与二次投票演示，代码注释全中文。

1. DAO 是什么

DAO（Decentralized Autonomous Organization，去中心化自治组织） 的核心是把组织的”规则”写成智能合约部署在链上：谁能提提案、谁能投票、多少票算通过、通过后多久执行、执行什么动作——全部由代码决定，任何人都能读取合约状态、审计历史提案与投票记录。

与传统公司/基金会的根本差异在于 信任对象不同：

  • 传统公司：信任人（董事会、管理层），规则写在章程里，执行靠法律体系，决策过程不透明、变更成本高。
  • 基金会（如早期以太坊基金会）：仍然是中心化法人实体，链上资产由多签钱包控制，决策权在少数核心成员手中。
  • DAO：信任代码（合约），规则链上可查，任何持币者都可参与投票，执行由合约自动完成，无人能单方面篡改结果。

典型形态有三类：

  • 协议 DAO（Protocol DAO）：治理 DeFi 协议的参数与升级，如 Uniswap、Compound、Aave。持币者投票决定手续费率、新市场上线、金库资金使用。
  • 投资 DAO（Investment DAO）：成员集资共同投资，按出资比例分享收益与投票权，如 The LAO。
  • 社交 DAO（Social DAO）：围绕共同兴趣/文化聚集，如 Friends with Benefits，治理代币代表社区身份与话语权。

DAO 的本质是 用代码约束权力、用代币分配话语权、用链上执行保证结果不可撤销。但它不是”无需信任”——信任从人转移到了合约代码与治理参数的设计上。

2. 治理代币与 ERC20Votes

2.1 为什么普通 ERC20 不适合治理

如果直接用 balanceOf(address) 作为投票权，会面临两个致命问题：

  1. 双花投票：一个地址在区块 N 有 100 币并投了票，然后把币转给另一个地址，另一个地址在同一提案期间也能投 100 币——同一笔钱投了两次。
  2. 闪电贷劫持：攻击者可以在单个交易内借入巨量代币、投票、归还代币，全程零成本却获得大量投票权。

解决思路是 快照（checkpoint）：投票权不看当前余额，而看提案创建时刻（或某个历史区块高度）的余额快照。代币在快照之后的转账不影响已记录的历史投票权。

2.2 ERC20Votes 的 checkpoint 机制

OpenZeppelin 的 ERC20Votes 在 ERC20 之上维护了一组按区块高度排序的 checkpoint。每次代币转账或委托变更时，合约会在当前区块记录一次”某地址投票权”的快照。关键函数：

  • delegate(address delegatee)：把投票权委托给 delegatee。可以委托给自己（自委托），此时自己的余额 = 自己的投票权；也可以委托给受托人，由对方代投。
  • getVotes(address account)：返回地址在最新区块的投票权。
  • getPastVotes(address account, uint256 blockNumber)：返回地址在指定历史区块高度的投票权——这是防双花与闪电贷的基石。
  • getPastTotalSupply(uint256 blockNumber)：指定历史区块的总供应量，用于计算 quorum。

checkpoint 用一个数组 Checkpoint[] 存储（fromBlock、votes），查询时二分查找最大的 fromBlock <= blockNumber 的那条记录，复杂度 O(log n)。

2.3 delegate 委托模型

ERC20Votes 的余额 ≠ 投票权，必须显式委托才会有投票权。设计原因：

  • 代币在交易所/冷钱包中时，持有者不一定想参与治理，委托机制让”想投票的人”才把权利用起来。
  • 委托可以转交给专业受托人（代表制），形成流动民主（liquid democracy）。
  • 自委托 delegate(self) 是最常见做法，等同于”我自己投票”。

2.4 避免双花投票的原理

提案创建时，Governor 会记录 proposalSnapshot = block.number - votingDelay 对应的区块高度。投票时调用 getPastVotes(voter, snapshot) 查询该地址在快照高度的投票权。即使投票者在快照后把币转给他人、或借入新币，getPastVotes 返回的仍是快照高度的值——转账不改变已发生高度的快照，因此同一笔代币无法在同一提案中被两个地址分别投票。

3. OpenZeppelin Governor 体系

OpenZeppelin 的治理合约采用 核心合约 + 模块化扩展 的拼装模式。Governor 是核心抽象合约，定义提案、投票、排队、执行的状态机；其他模块通过继承叠加功能。

3.1 核心与扩展模块

模块 职责
Governor 核心状态机：propose / castVote / queue / execute，提案 ID 计算，状态查询
GovernorSettings 治理参数：votingDelay、votingPeriod、proposalThreshold
GovernorVotes 接入 ERC20Votes 代币，用 getPastVotes 取投票权
GovernorVotesQuorumFraction 法定人数：总供应量的百分比（如 4%）
GovernorCountingSimple 计票方式：For / Against / Abstain 三选一，简单多数
GovernorTimelockControl 接入 TimelockController，提案通过后进延迟队列再执行

拼装时，MyGovernor 同时继承上述所有模块。由于多个模块都定义了同名虚函数（如 votingDelay、quorum、state），需要在子合约中显式 override 并调用 super，让 Solidity 解析正确的继承链。

3.2 GovernorSettings 三参数与攻击面

  • votingDelay（投票延迟，单位：区块）：提案创建后，等待多少区块才进入投票阶段。快照高度 = 提案区块 + votingDelay。设太短 → 攻击者可在提案同区块借币投票（即使快照，也可能被同区块闪电贷绕过部分检查）；设太长 → 治理效率低。常见 1 块或 1 天。
  • votingPeriod（投票周期，单位：区块）：投票持续多久。太短 → 持币者来不及参与；太长 → 治理拖沓。以太坊主网常见 1 周 ≈ 50400 块。
  • proposalThreshold（提案阈值）：创建提案所需的最小投票权。设为 0 → 任何人都能垃圾提案、 clog 治理；设太高 → 只有巨鲸能提案。常见为总供应量的 0.5%~1%。

4. 提案生命周期

一个提案从创建到执行，经历以下状态流转：

  1. propose（创建提案）：调用者传入 targets[]（要调用的合约地址）、values[]（转账的 ETH 数量）、calldatas[]（编码后的函数调用数据）、description（描述）。合约计算 proposalId = keccak256(targets, values, calldatas, descriptionHash)，记录快照高度与截止高度。calldata 用 interface.encodeFunctionData("transfer", [to, amount]) 生成。

  2. Pending（待开始）：从提案创建到 proposalSnapshot 区块之间，等待投票权快照固定。

  3. Active（投票中）：从 proposalSnapshot 到 proposalDeadline。持币者调用 castVote(proposalId, support)，support 取 0=Against、1=For、2=Abstain。计票模块累加 For/Against/Abstain 的票数。

  4. Succeeded / Defeated（通过/否决）：投票结束后，若 For > Against 且达到 quorum，则 Succeeded，否则 Defeated。

  5. Queued（排队进 Timelock）：通过后，调用 queue() 把提案的 calldata 提交给 TimelockController，Timelock 记录 eta = block.timestamp + minDelay。

  6. 等待延迟：在 minDelay 期间，任何人都能看到即将执行的动作。如果是恶意提案，持币者有时间抛售代币或组织反对——这就是 Timelock 给多数人”跑路时间” 的意义。

  7. Executed（执行）：延迟到期后，调用 execute()，Governor 让 Timelock 以自身身份 call 目标合约的 calldata。Timelock 持有资金与权限，因此执行是可信的。

5. 链下治理：Snapshot 与多签混合

5.1 Snapshot 快照投票

链上投票每个动作都要花 Gas，参与门槛高。Snapshot 是链下投票方案：

  • 投票者用钱包对一条结构化消息（EIP-712 格式）做 离链签名，不上链、零 Gas。
  • 签名消息包含 space（DAO 标识）、proposal（提案 IPFS 哈希）、choice（选项）、timestamp 等。
  • Snapshot 服务收集签名后，从链上读取代币在快照区块的余额（同样依赖 ERC20Votes 的 checkpoint 或 Snapshot 自己的策略）计票。
  • 投票结果 非约束性（non-binding）：链上不会自动执行，需要人或多签钱包根据结果手动操作。

Snapshot 适用于：意见征集、温度测试（temperature check）、低风险决策。核心决策仍需链上 Governor 执行。

5.2 多签 + 快照混合模式

许多实际运行的 DAO 采用 “多签执行 + 代币建议” 的混合模式：

  • Snapshot 上用代币投票产生社区共识（建议性）。
  • 多签钱包（如 Safe）的签名者根据 Snapshot 结果执行链上操作。
  • 优点：灵活、低成本、可快速迭代。
  • 缺点：多签持有者是信任假设，可能与社区共识不一致——本质仍是”受约束的多签”。

完全链上治理（Governor + Timelock）信任最小化，但 Gas 成本高、治理周期长；混合模式用得多，但需社区对多签者有监督与罢免机制。

6. 高级投票机制

6.1 一票一投（1T1V）的财阀问题

1 Token 1 Vote 是最简单的模式，但直接导致 财阀统治（plutocracy）：持币越多话语权越大，巨鲸可以碾压散户。Compound、Uniswap 等主流协议都用 1T1V，实际治理参与度往往不到 10%，且被少数大户主导。

6.2 二次投票（Quadratic Voting, QV）

二次投票由 E. Glen Weyl 与 Eric Posner 提出，核心思想是 投票的边际成本递增：

  • 买 n 票的成本 = n²（或某个二次函数）。
  • 第 1 票花 1 单位，第 2 票花 3 单位（累计 4），第 3 票花 5 单位（累计 9）……
  • 效果：强烈偏好者愿意多花钱买票，但成本随票数平方增长，限制了巨鲸碾压能力；弱偏好者的声音被相对放大。

QV 在 Gitcoin Grants 等资金分配场景被广泛使用（二次融资 Quadratic Funding）。链上实现 QV 需要解决女巫攻击（Sybil）问题，通常配合身份验证（如 Gitcoin Passport）。

6.3 信念投票 / 全息共识

  • 信念投票（Conviction Voting）：投票随时间累积权重，持续支持某提案的时间越长，权重越大。适合资金类持续决策，如 1Hive、Commons Stack。
  • 全息共识（Holographic Consensus, DAOstack）：用预测市场筛选提案——只有被预测会通过的提案才进入全体投票，解决大量提案导致的投票疲劳。

6.4 流动民主（Liquid Democracy）

持币者可以把票委托给受托人，受托人也可以再委托（转委托）。不想投票的人把权交给信任的专家，专家集中投票；同时任何时候都可以撤回委托自己投票。Compound 的 delegate 机制就是流动民主的基础。

7. 代币经济模型

7.1 治理代币 vs 实用代币分离

  • 治理代币（Governance Token）：唯一功能是投票权，本身不产生现金流。如 UNI、COMP。持有者通过治理影响协议，但代币价值依赖市场对未来治理价值的预期。
  • 实用代币（Utility Token）：用于协议内支付手续费、获取服务。如交易平台的平台币抵扣手续费。

两者分离的好处是避免”用协议 = 必须持治理币”的摩擦；坏处是治理代币缺乏内生价值支撑，容易沦为投机品。

7.2 双代币模型

部分协议采用双代币设计：

  • 稳定币/支付代币：用于协议内交易、手续费支付，价值稳定。如 MakerDAO 的 DAI。
  • 治理代币：用于治理，并承担协议风险（亏损时首先被清算）。如 MakerDAO 的 MKR。

双代币实现了 价值稳定 + 治理激励 + 风险吸收 的分层，但设计复杂。

7.3 veToken 模型（Curve 模式）

veToken（vote-escrowed token）由 Curve 首创，核心是 锁仓换权：

  • 用户把 CRV 锁仓 4 年，获得 veCRV（不能转账）。
  • veCRV 持有者享有：投票决定哪个流动性池获得 CRV 通胀奖励、分享协议交易手续费、boost 流动性挖矿收益。
  • 锁仓时间越长，veCRV 越多（线性）。效果是把短期投机者与长期持有者区分开，治理权集中在”长期信仰者”手中。

veToken 被众多协议借鉴（veBAL、veFXS、veAPE 等），但也带来了治理俘获（governance capture）问题——大户长期锁仓垄断投票权。

7.4 代币不是股权

重要提醒：治理代币不是股权。它不代表对协议资产的所有权、不分红（除非治理投票决定）、不享受清算优先权。持币者拥有的是”投票影响规则”的权利，而非”拥有协议”的权利。这也是监管层面 DAO 代币的灰色地带——若被认定为证券，将面临合规风险。

7.5 激励对齐与抛压

治理代币的经济设计需要平衡：

  • 激励对齐：让持币者的利益与协议长期发展一致（veToken 锁仓、手续费回购销毁）。
  • 抛压控制：代币释放过快会导致价格下跌、治理权贬值。常见手段：线性解锁（vesting）、锁仓奖励、手续费回购销毁。

8. 治理攻击经典案例与防护

8.1 闪电贷借币投票：Beanstalk 事件

2022 年 4 月，算法稳定币协议 Beanstalk 遭治理攻击：攻击者用闪电贷借入约 1.8 亿美元的 BEAN 代币，获得超过 quorum 的投票权，在单个区块内通过恶意提案，将协议金库中约 1.82 亿美元资产转给自己，随后归还闪电贷，净赚约 8000 万美元。根因是 Beanstalk 的快照机制允许在提案创建同区块用新借入代币投票——没有设置足够的 votingDelay 让快照落在借币之前。

8.2 防护要点

攻击面 防护
闪电贷借币投票 设置 votingDelay > 0，让快照高度落在借币交易之前；快照用 getPastVotes 历史值
提案阈值为 0 设 proposalThreshold 为总供应量的一定比例，防垃圾提案与低成本攻击
无 Timelock 强制 GovernorTimelockControl，给社区反应时间；minDelay 至少 24~48 小时
quorum 过低 quorum 设为总供应量的 4%~10%，防止少数人强行通过
恶意 calldata 提案描述必须清晰，社区审查 calldata 实际执行的函数与参数；考虑白名单目标合约
治理俘获 引入投票延迟、委托机制、定期选举受托人，防止单一实体长期垄断

核心原则：快照锁定提案创建时刻的投票权 + Timelock 延迟执行 + 足够的 quorum 与提案阈值，三者缺一不可。

9.3 TimelockController 部署要点

TimelockController 构造函数签名：constructor(uint256 minDelay, address[] proposers, address[] executors, address admin)。

  • minDelay：最短延迟，建议 ≥ 2 天（生产）。
  • proposers / executors / cancellers：角色，应在部署后授予 Governor 合约自身，而非 EOA。
  • admin：初始管理员，部署后应立即把 admin 角色也转交给 Governor 或 renounce，避免单点控制。

权限授予顺序：

  1. 部署 GovToken、TimelockController（admin=deployer）、MyGovernor。
  2. 调用 timelock.grantRole(PROPOSER_ROLE, governor)、grantRole(EXECUTOR_ROLE, governor)、grantRole(CANCELLER_ROLE, governor)。
  3. timelock.revokeRole(DEFAULT_ADMIN_ROLE, deployer)，把管理权限移交给治理本身。
  4. 若代币有 Ownable，把所有权转给 timelock，让治理决定增发等操作。
