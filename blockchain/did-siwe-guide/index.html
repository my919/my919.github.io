去中心化身份深度指南：DID · ENS · SIWE 钱包登录实战

区块链 · 去中心化身份

不注册、不记密码、不把身份押在任何平台上。W3C DID 架构 · 以太坊地址即身份 · ENS 名称服务 · EIP-4361 SIWE 钱包登录 · EIP-712 结构化签名 · 可验证凭证 VC。每个概念都有成段原理，每个示例都可直接运行，代码带中文注释。

1. 传统登录之痛：身份为什么不该属于平台

今天的登录方式大体三种，每一种都把「你是谁」的解释权交给了别人。

第一种是账号密码。网站数据库即使只存哈希（bcrypt、argon2），一旦拖库，攻击者仍可以离线爆破弱密码，再用泄露的账号密码到其他网站撞库——多数人习惯复用密码，一个站点失守，处处失守。哈希算法只是提高破解成本，并不改变「凭证存在别人服务器上」这一事实。

第二种是平台账号体系本身。你的身份在平台数据库里只是一行记录：平台可以封禁账号、冻结资料、关停服务，你积累的声誉、关系、数据几乎无法迁移。身份的「产权」和「使用权」是分离的——你在用，但不属于你。

第三种是 OAuth（用 Google、微信、GitHub 登录）。它解决了密码复用问题，却把身份证明外包给了少数大厂：授权方知道你登录了哪些第三方应用，可以随时撤销授权，而用户面对冗长的授权弹窗通常是一路点「同意」。对中小站点而言，登录入口反而被上游卡得更死。

DID（Decentralized Identifier，去中心化标识符）的主张是：身份应当由用户用密码学密钥自持。标识符从你自己生成的公钥推导而来，不需要任何中心注册方批准或登记；登录某个网站时，你不用提交密码，只需用私钥对一段消息签名，网站验证签名即确认「你确实持有该身份对应的密钥」。同一个标识符可以在任意多个服务间通用，服务方无法封禁、无法没收、也无法冒充你。

需要强调的是，DID 不是万能药：密钥自持意味着密钥丢失即身份丢失，因此现实中衍生出助记词、多签、社交恢复等方案；DID 也不等于匿名，它改变的是「控制权模型」——从平台所有，变为用户所有。

2. DID 架构：W3C 标准到底规定了什么

W3C 的 DID 规范把去中心化身份拆成两个核心物件：DID 标识符与 DID Document（DID 文档），外加一个把前者解析成后者的 resolver（解析器）。

2.1 DID 标识符格式

DID 是一个形如 did:<method>:<method-specific-id> 的字符串：

  • did：固定前缀，表明这是一个 DID；
  • <method>：方法名，规定了这个 DID「如何创建、如何解析、如何更新、如何作废」，如 ethr、pkh、web；
  • <method-specific-id>：由该方法自己定义的标识部分，通常直接编码地址或公钥哈希。

例如 did:ethr:0x742d35Cc6634C0532925a3b844Bc9e7595f0bEb0 一看便知：这是一个 ethr 方法的 DID，锚定在某个以太坊地址上。

2.2 DID Document：身份的「公钥与服务说明书」

DID Document 是一份 JSON 文档，回答三个问题：用什么钥匙验证我、我能用哪些方式认证、去哪里找我的服务。关键字段如下：

  • verificationMethod：验证方法列表，每一项给出一把公钥（或一个链上地址），并声明类型（如 JsonWebKey2020、EcdsaSecp256k1VerificationKey2019）、控制器与公钥内容；
  • authentication：认证关系，引用 verificationMethod 中的某把钥匙，表示「这把钥匙专门用来做登录认证」；
  • service：服务端点列表，例如加密通信（DIDComm）、凭证托管、个人网站等链下服务地址。

2.3 Resolver 解析流程

验证方拿到一个 DID 后，并不直接信任它，而是走解析流程：

  1. 校验 DID 语法，取出 method 名；
  2. 把解析工作委托给该 method 对应的 resolver——did:ethr 去读链上事件，did:pkh 按规则静态推导，did:web 去请求 HTTPS 资源；
  3. 得到或构造出 DID Document，连同解析元数据（是否已停用、版本信息等）一起返回给验证方。

通用前端（如 Universal Resolver）把几十种 method 的 resolver 聚合在同一接口下，调用方无需关心底层差异。

2.4 三种常见方法对比

  • did:ethr：锚定在以太坊（或任意 EVM 链）上。标识本身是地址，DID 文档由链上数据（ERC-1056 等）推导，支持通过发链上交易轮换密钥、停用身份，代价是 gas。适合需要密钥生命周期管理的组织和基础设施场景。
  • did:pkh：pkh 即 public key hash。标识里直接编码「链命名空间 + 地址」，如 did:pkh:eip155:1:0x742d...bEb0，DID 文档由公钥哈希确定性地离线生成，解析时连网络请求都不需要。代价是标识符即钥匙，无法轮换。它是 SIWE 这类区块链账户登录最自然的 DID 形态，且天然跨链（Solana、比特币地址都能编码）。
  • did:web：把 DID 文档放在域名下的固定路径（https://<域名>/.well-known/did.json），解析即 HTTPS GET。零 gas、可随意改文档、对企业最友好；但信任假设退回到了 DNS、证书和托管商——域名被接管，身份即易主，去中心化程度三者中最低。适合已牢牢掌握自己域名的机构；另有不需要任何链的 did:key 作为纯静态备选。

3. 以太坊地址即身份：私钥、EOA 与智能合约钱包

在以太坊的世界里，成为一个「身份」不需要注册，流程只有三步：私钥 → 公钥 → 地址，全部单向。

私钥是 32 字节随机数；用 secp256k1 椭圆曲线乘法推导出公钥（64 字节坐标）；再用一句话概括地址推导：地址 = keccak256(公钥) 的末 20 字节，最后通过 EIP-55 给十六进制字符加上大小写校验和。从地址无法反推公钥，更无法反推私钥，这就是「公开地址、藏好私钥」的数学基础。

EOA（外部拥有账户）登录指的就是最常见的形态：私钥保存在 MetaMask 等钱包里，对消息签名后，任何人都能通过 ecrecover 从签名恢复出地址，密码学闭环完全成立。

智能合约钱包登录则不同。多签钱包（如 Safe）、以及 ERC-4337 账户抽象钱包，其背后没有单一私钥：一个签名可能由多个签名者的份额组成，钱包的有效性规则写在合约代码里。对这类签名做 ecrecover 要么恢复出无意义的地址，要么根本不适用。解决办法是 EIP-1271 标准——让验证方反过来「询问合约」：

4. ENS：让区块链地址有名字

0x742d35Cc6634C0532925a3b844Bc9e7595f0bEb0 这样的地址对机器友好，对人却是灾难：难记忆、难核对，视觉上还容易被构造出相似地址进行钓鱼。ENS（Ethereum Name Service） 做的事，就是把 vitalik.eth 这样的名称映射到地址。

4.1 解析原理：Registry + Resolver 两级结构

ENS 的核心是两类合约。Registry（注册表） 合约按名称的 namehash 记录三件事：这个名称归谁所有、它的 resolver 合约在哪、TTL 是多少。namehash 是一种从右向左的递归哈希，保证同名同哈希：

namehash("vitalik.eth") = keccak256( namehash("eth") ‖ keccak256("vitalik") )

真正的数据并不在 Registry 里，而在 Resolver（解析器）合约中。所以一次正向解析是两步：先向 Registry 查到该名称的 resolver 地址，再向 resolver 查询 addr 记录拿到以太坊地址。Resolver 还可以存多种链地址、text 文本记录（com.twitter、url、description）、contenthash（指向 IPFS/Swarm 内容）以及 avatar 头像。

4.2 反向解析与「正向确认」

ENS 还提供反向解析：地址 → 名称。它利用一个特殊的保留域 <地址小写去校验和>.addr.reverse，其 resolver 返回一条 name 记录。但任何人都能给自己的地址设置任意反向记录——攻击者可以把自己的地址反向名称设成 vitalik.eth。因此反向解析必须做正向确认：读出名称后，再查一次该名称指向的地址，二者相等才能信任。ethers 的 lookupName 已内置这一步，手写逻辑时切勿省略。

4.3 为什么名称比裸地址可用

名称解决了可读性，更进一步的是：名称所有者可以在不换名字的情况下把解析地址改到新钱包，对外身份保持连续，朋友的通讯录、dapp 的记忆都不需要改；头像和社交记录让 dapp 可以直接渲染出「带头像的个人主页」。此外 .eth 名称本身是 ERC-721 NFT，可以续费、转让，身份变成了用户真正拥有的资产。头像记录还支持直接写 NFT（如 eip155:1/erc721:0x.../123），ethers 会自动按 EIP-155 解析出 NFT 的图片。

5. SIWE：Sign-In with Ethereum（EIP-4361）

SIWE 是以太坊登录的标准提案（EIP-4361，后归 ERC 编号），它把「钱包签名」约束成一种机器可解析、用户可读、服务端可严格校验的登录消息，让以太坊地址能像「账号」一样登录任意传统 Web 服务，而服务端无需碰任何链上交易。

5.1 完整消息字段

一条 SIWE 消息由以下字段组成：

字段 含义 是否必填
domain 请求登录的站点域名（RFC 3986 authority），如 localhost:3000 必填
address 要登录的以太坊地址 必填
statement 给用户看的一句话说明，解释为什么签名 可选
uri 会话来源 URI，通常是站点 origin 必填
version 协议版本，目前固定为 "1" 必填
chainId 签名时所在的 EIP-155 链 ID 必填
nonce 服务端签发的一次性随机串（至少 8 位字母数字） 必填
issuedAt 消息签发时间（ISO 8601） 必填
expirationTime 消息过期时间，过期签名一律拒绝 可选
notBefore 消息最早生效时间 可选
requestId / resources 请求标识 / 本次登录要访问的资源 URI 列表 可选

5.2 登录四步流程

  1. 取 nonce：前端先请求后端 /nonce，后端生成随机串并存入存储（带过期时间），返回给前端；
  2. 签名消息：前端用钱包连接信息和 nonce 组装 SIWE 消息，调 signer.signMessage 请用户签名（personal_sign，钱包弹窗展示域名与说明，不发交易、不花 gas）；
  3. 后端验签：前端把「消息文本 + 签名」POST 给 /verify，后端解析消息，恢复地址并校验 domain、nonce、chainId、时间窗口；
  4. 签发会话：全部通过后，nonce 立即作废，后端签发自己的会话凭证（JWT 或 HttpOnly Cookie），此后的请求与普通登录会话无异。

5.3 为什么能防钓鱼、防重放

防钓鱼靠域名绑定：domain 是被签名内容的一部分，钱包弹窗会醒目显示。假设钓鱼站点 fake-airdrop.io 骗你签了名，这个签名拿到真站 app.example.com 的后端也无法通过——真站只接受 domain = app.example.com 的消息。签名无法跨站复用，钓鱼收益归零。

防重放靠一次性 nonce：每条消息嵌入服务端随机串，用过后即作废，攻击者即使截获完整的「消息 + 签名」，也无法第二次提交。expirationTime 则把签名的有效窗口压缩到分钟级，进一步降低泄露后的风险。

5.4 SIWE 与 EIP-712 的关系

需要澄清一个常见误解：SIWE 消息本身走的是 EIP-191 的 personal_sign（带专用前缀的纯文本），并不是 EIP-712 签名。这是刻意为之——personal_sign 被所有钱包和所有以太坊工具链支持，兼容性最好。但 SIWE 确实借鉴了 EIP-712 的核心思想：通过绑定 domain 把签名「限定在特定场合」，使签名无法被搬到别的域名或合约下复用。EIP-712 则用于更复杂的结构化业务数据（见第 8 节）。

8. 实战三：EIP-712 结构化数据签名

让用户对一长串拼好的字符串签名有两个问题：钱包里显示的是晦涩文本，用户容易盲签；同一段字符串在不同合约/业务里语义可能冲突。EIP-712 让签名对象变成「带类型的结构化数据」，签名过程需要 domain、types、value 三件套：

EIP-712 最终签名的摘要不是简单哈希整段文本，而是 keccak256( "\x19\x01" ‖ hashStruct(domain) ‖ hashStruct(value) )。这带来三个好处：一是钱包能按 types 逐行渲染「字段名 + 值」，用户读得懂才敢签；二是 domain 隔离，同一份数据换个域名、链或合约，摘要完全不同，签名无法跨场景复用（也防得了「把授权消息当转账消息」的注入攻击）；三是类型系统让合约可以链上高效解析，签名即结构化输入，链上链下口径一致。

9. 可验证凭证 VC：离线可验的数字证明

DID 解决了「你是谁」，现实中还需要证明「你拥有什么属性」——毕业证、会员资格、KYC 结论。W3C Verifiable Credentials（VC，可验证凭证） 就是这类数字证明的标准格式。

一份 VC 有三个角色：issuer（发行方） 签发凭证，subject / holder（主体/持有者） 接收并保管凭证，verifier（验证方） 在需要时核验。凭证本体是一份 JSON，credentialSubject 里放各项声明（claims），proof 里放发行方的签名：

离线可验证性是 VC 的关键性质：验证方不需要回调发行方，只需解析 issuer 的 DID 文档拿到公钥，用 proof 中的签名对凭证内容验签即可——密码学保证凭证未被篡改且确由该 DID 签发。是否吊销则通过凭证中的 credentialStatus 字段选择性地查询发行方的吊销列表，其余时刻发行方完全不参与，也无从得知用户在哪里使用了凭证，天然抑制「身份提供商式」的监控。

更进一步的隐私诉求是选择性披露：直觉上，最简单的做法是把每个属性拆成独立签名，只出示需要的那几张；进阶方案中，BBS+ 类签名允许持有者从一个群签名中派生出任意字段子集的证明而不破坏可验证性；结合零知识证明，还能只证明属性满足某个谓词——比如证明「我已年满 18 岁」而无需出示出生日期，证明「我的学分绩点高于门槛」而不透露具体分数。对应用开发者而言，先理解「签名让声明可验证、拆分让披露最小化」这条主线，零知识的细节可以按需再深入。
