2. 选型对比

方案 特点 结论
SkyWalking Java Agent 无侵入（不改代码）、中文社区活跃、拓扑图强、自带告警 ✅ 首选
Zipkin 只做链路，需代码埋点（Brave），功能单一 轻量场景
Jaeger CNCF 项目，多语言，需埋点 K8s 生态

为什么 SkyWalking 无侵入是杀手锏：其他方案要在代码里加注解/拦截器（要改代码、要发版）；SkyWalking 启动时挂 -javaagent 即可，生产接入不动一行代码。

6. traceId 与日志贯通（链路+日志双保险）

为什么链路和日志必须贯通：Trace 告诉你”哪段慢”，日志告诉你”为什么慢”——只有 traceId 把两者接上，才是完整排障闭环。

traceId 日志里没有 没引 toolkit-logback 引入依赖 + 配置 %tid

9. 典型案例：一次”下单接口偶发 3 秒”的链路追踪定位

问题背景：电商大促前压测，POST /api/orders 平时 80ms，偶发飙到 3 秒以上，单机日志翻不出异常，无法复现。

排查过程：

步骤 操作 观察结果
① SkyWalking 追踪查询：过滤 /api/orders + 耗时 > 1000ms 10 分钟内 14 条慢 Trace，集中在库存服务调用段
② 点开最慢一条 Trace（3.2s），逐 Span 看耗时 网关 20ms → 订单服务 300ms → 库存服务 2800ms
③ 展开库存服务 Span 的子 Span Redis 5ms 正常；MySQL 查询 2700ms ← 定位
④ 复制 traceId → 日志系统检索（%tid 贯通） 找到慢 SQL：SELECT ... WHERE sku_id=? AND status=?，未走索引

10. 常见误用与陷阱

坑 现象/后果 解法
service_name 命名随意（同一服务各实例不同名） 拓扑图碎成多个”假服务”，依赖关系失真 启动脚本统一变量注入，一个服务一个名字
只看平均响应时间排障 偶发慢/长尾被平均掩盖，线上投诉不断但大盘全绿 用 P99/耗时区间看，慢 Trace 直接下钻
生产环境 OAP 用 H2 存储 重启数据全丢，历史 Trace 无法回溯 生产必须 Elasticsearch，H2 只用于测试
采样率一刀切：要么全量要么 1/10000 全量存储爆炸；过低则故障现场没样本 常态 1/100 起步，告警触发后临时调高；配合 tail-sampling
traceId 没贯通日志 Trace 只告诉你”哪段慢”，还得逐服务翻日志猜”为什么慢” 引 toolkit-logback，pattern 加 %tid，全链路 grep traceId
只监控了存活（agent 挂了也没人知道） agent 断连后 UI “无数据”被当成”没流量”，排障两眼一抹黑 监控 agent 上报心跳/OAP 队列积压，断连即告警
