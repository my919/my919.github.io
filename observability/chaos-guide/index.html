8. 典型案例：支付服务混沌演练

8.1 问题背景

支付服务强依赖 Redis 做风控缓存，大促前架构评审担心「Redis 抖动会不会拖垮支付」，但拿不出证据，熔断降级代码写了两年从未被真实触发过。目标：受控环境验证降级有效性并输出演练报告。

8.2 解决方案

用 Chaos Mesh 三段实验：预发注入网络延迟验证降级 → 生产金丝雀 Pod 小范围注入 Pod-kill 验证自愈 → Workflow 编排沉淀为可重复实验。全程定义稳态指标基线，错误率超 1% 自动回收实验。

8.3 关键实现

8.4 踩坑点

  • 首次演练直接打了全部生产 Pod，降级未生效错误率冲到 8% 紧急回滚；此后一律金丝雀先行
  • 只注入故障不定义稳态指标，演练完说不清”降级到底生效没生效”，补齐 P99/错误率/熔断率三项基线
  • 业务 Pod 被删后 NetworkChaos 资源残留继续注入延迟；流程固化为”实验即资源，结束即删除”
  • 演练选在周五下午值班交接混乱，固化为周二上午 + 全员周知

9. 常见误用与陷阱

坑 现象/后果 解法
无爆炸半径直接生产演练 演练变真实事故 namespace/label 白名单 + 金丝雀先行
不设自动中止条件 故障叠加雪崩 错误率/SLO 阈值自动回收实验
无稳态指标假设 演练完说不出结论 先定义基线指标再注入
只打基础设施不验业务 降级/限流从未被验证 业务场景化实验（支付降级链路）
演练资源残留 实验对象删除后故障持续 实验即资源，结束即清理
时间窗选择随意 撞上业务高峰或封网期 演练日历 + 与封网期联动
