6. 典型案例：一次接口大面积超时的命令行排查（15 分钟定位）

问题背景：10:05 收到关键字告警”超时错误激增”。日志平台（ELK）恰好故障维护中，只能靠命令行在服务器上直接分析。

排查过程（组合拳：分钟统计 → traceId → 慢 SQL 关联 → 发布对比）：

步骤 命令思路 结论
① 锁定时间窗 分钟级统计错误数（场景 2.4） 10:03 前错误为 0，10:03 起每分钟 800+ 条
② 提取样本 traceId 取窗口内一条超时日志的 traceId（场景 2.3） traceId=9d2b4f1a
③ 串单请求链路 grep 9d2b4f1a app.log 该请求在 StockMapper.listBySku 处耗时 4200ms
④ 关联慢 SQL 日志 grep 9d2b4f1a sql-slow.log（场景 2.8） 同一 traceId 命中慢日志：SELECT * FROM stock ... 3.9s
⑤ 发布对比 发布前后错误数对比（场景 2.10） 09:00 错误 0 条，10:00 错误 5120 条 → 与 10:03 发布吻合

关键命令：

踩坑点：第 ① 步最初直接 grep -c ERROR app.log，单文件 18GB 跑了 4 分钟才出结果——大文件必须先切时间窗（场景 3②）再统计。另外第一版统计把异常堆栈行也算进了错误数（一行异常拆 30 行堆栈），用 grep -c ERROR 只统计标记行才准确。

7. 常见误用与陷阱

坑 现象/后果 解法
多行堆栈污染统计 一条异常拆成 30+ 行，grep -c ERROR 数字虚高且 grep 单行丢上下文 只统计带级别标记的行；用 grep -A 20 取堆栈
大文件直接全量 grep 18GB 文件单次 grep 数分钟，IO 打满影响业务 先 awk 切时间窗/用 zgrep 压缩文件，再精确匹配
MDC 未在 finally 清理 线程复用后 traceId 串号，A 请求日志挂上 B 的 traceId try/finally { MDC.remove("traceId"); }
日志不滚动 单文件几十 GB，打开就卡死，磁盘爆满 logback 按天滚动 + 压缩 + 保留 14 天
用 tail -f 盯屏当排障手段 只看到”现在”，无统计无对比，看不出趋势 统计类命令 + traceId 串联，形成完整证据链
cron 告警脚本每分钟全量 grep 脚本本身吃满 CPU/IO，越忙越慢 记录 offset 增量读取，或只扫最近 1 分钟切片
