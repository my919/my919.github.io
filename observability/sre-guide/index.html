8. 典型案例：把”100% 稳定”换成”99.95% + 错误预算”的一年

问题背景：某支付网关团队以”追求 100% 可用”为目标，结果是：变更全靠审批、发布窗口挤在凌晨、开发者与 SRE 关系对立（一个想发，一个不敢发），全年却还是出了 3 次 P1。

方案：为三个核心服务设定 SLO，引入错误预算，用数据决定”能发多少、发多快”。

一年效果：发布频率从每两周 1 次提到日均 2-3 次；P1 从 3 次降到 0 次；凌晨 Page 量下降 70%（消灭了大量低价值告警）；开发者与 SRE 的争论从”能不能发”变成”预算还剩多少”。

关键实践：SLO 目标从真实用户能感知的降级倒推（先问”支付认证比 P99 多少毫秒时用户会流失”），不拍脑袋；每条告警必须绑定 runbook 和明确动作；错误预算花在刀刃上——金丝雀、混沌演练、自动化都算”用预算买可靠性”。

踩坑点：SLO 定 100% 意味着零预算，任何变更都违规，团队只能造假数据；另一坑是 SLI 用机器指标（CPU、进程存活）而用户实际在抱怨接口超时，SLO 绿灯但用户骂声不断——SLI 必须贴近用户旅程。

9. 常见误用与陷阱

坑 现象/后果 解法
把可用性目标定为 100% 零预算，发布冻结或数据造假 99.9%~99.99% 区间按业务定
告警无 action 半夜被叫起却无事可做，狼来了 每条告警绑 runbook，否则不上 Page
SLI 用机器指标 SLO 全绿用户却在骂 SLI 贴用户旅程（成功率/延迟）
单窗口告警 一次抖动触发凌晨误报 多窗口 + 烧毁率告警
复盘追责个人 大家隐瞒问题，二次事故 无责复盘，只追系统与流程
错误预算只统计不执行 变回”永远敢发”的旧世界 预算政策写进发布门禁
SLO 一年不回顾 目标与业务现实脱节 季度回顾，随用户预期调整

11.1 SRE 实施清单

  • 定义核心 SLI（延迟、错误率、可用性）
  • 设定 SLO 目标（基于用户需求）

  • 建立事件响应流程
  • 实施事后复盘文化
  • 自动化容量规划
