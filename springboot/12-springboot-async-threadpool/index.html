第十一章：异步线程池

概念基础

Spring Boot 默认的 spring.task.execution 与本项目自定义线程池参数分离，避免重复注册；自定义池供 @Async 及按需注入 TaskExecutor 使用（如异步写操作日志）。

  1. 异步（@Async）：把耗时操作（写审计日志、发通知、导出报表）交给后台线程执行，主线程立即返回，提升接口响应速度与吞吐。
  2. 为什么要自定义线程池：Boot 默认池参数保守，且与本工程配置体系脱节；自定义 app.async.executor.* + ThreadPoolTaskExecutor，让核心线程数、队列容量、拒绝策略、关闭策略全部可控。
  3. 线程池的价值：复用线程，避免频繁创建销毁的开销；用有界队列 + 拒绝策略保护系统不被突发流量压垮——本项目用 CallerRunsPolicy 形成背压，队列满时由调用线程兜底执行。
  4. @Async 生效条件：方法必须经 Spring 代理调用，同类自调用不生效；Bean 名 taskExecutor 是 @Async 的默认执行器。
  5. 典型场景：操作审计日志异步落库（见第十章），OperLogRecordService.saveAsync 即走本池。

线程池参数计算

ThreadPoolExecutor 的任务流转规律：先填满核心线程 → 再进队列 → 队列满才扩到最大线程 → 最后触发拒绝策略。理解这条链是参数计算的前提。



flowchart LR
  T[新任务] --> C{核心线程有空?}
  C -->|是| R1[立即执行]
  C -->|否| Q{队列未满?}
  Q -->|是| R2[入队等待]
  Q -->|否| M{未到最大线程?}
  M -->|是| R3[开新线程执行]
  M -->|否| R4[触发拒绝策略]

线程数估算公式（《Java 并发编程实战》经典口径）：

  • N_cpu：CPU 核数（Runtime.getRuntime().availableProcessors()）
  • U_cpu：期望 CPU 利用率（0~1）
  • W/C：等待时间与计算时间之比（IO 密集高、CPU 密集低）

落地参考值：

任务类型 特点 建议 core 例子
CPU 密集 几乎无等待 核数 + 1 加解密、压缩、本地计算
IO 密集（短） 等待占 50%~80% 核数 × 2~4 写审计日志、发 HTTP 通知
IO 密集（长） 等待占 90%+ 核数 × 8~16，独立池 调慢第三方接口、批量导出

本项目配置解读（core 10 / max 32 / queue 200）：审计日志属短 IO 任务，core 10 覆盖日常并发；队列 200 吸收突发；max 32 只在队列满后才启用——不要为常规流量配置 max。

拒绝策略对比

策略 行为 适用
AbortPolicy（JDK 默认） 抛 RejectedExecutionException 不能丢任务且要求快速失败
CallerRunsPolicy（本项目） 调用线程自己执行 形成背压：Web 线程被迫干活，自然降低接收速度，任务不丢
DiscardPolicy 静默丢弃 可丢失场景（如非关键埋点）
DiscardOldestPolicy 丢队列最老任务 极少用，数据时效性强场景

CallerRunsPolicy 的背压价值：队列满时 Tomcat 线程被拖去执行任务，接收新请求能力下降，用响应变慢换取不丢任务——审计日志场景的正确取舍。

指标 告警线 含义

调优建议

参数 说明
core-pool-size CPU 密集型 ≈ 核数；IO 密集型可适当放大
queue-capacity 过小易触发拒绝；过大可能堆积内存
max-pool-size 峰值并发上限
拒绝策略 当前为 CallerRunsPolicy（调用线程执行，背压）

常见坑速查：

现象 原因 处理
@Async 不生效 同类自调用 / 方法非 public 经代理调用；拆 Bean
异常被吞 @Async void 异常无处理者 返回 CompletableFuture 或配 AsyncUncaughtExceptionHandler
内存溢出 无界队列堆积（LinkedBlockingQueue 默认 Integer.MAX_VALUE） 必须有界队列
ThreadLocal 串数据 线程复用导致上下文残留 TaskDecorator 拷贝/清理，任务结束 remove
停机丢任务 未开优雅关闭 wait-for-tasks-to-complete-on-shutdown: true + await-termination-seconds: 30
池名混乱难排查 线程名无前缀 必配 thread-name-prefix，日志/线程 dump 可定位

@Async 返回值与异常处理

@Async 方法可返回 void、Future<T> 或 CompletableFuture<T>，异常处理路径不同：

返回类型 异常行为 建议
void 异常抛出无人接收，仅打日志（若配置 AsyncUncaughtExceptionHandler） 仅用于「发后即忘」场景（如操作日志落库）
Future<T> 异常包装进 ExecutionException，调用 get() 时才暴露 老代码兼容，新代码推荐 CompletableFuture
CompletableFuture<T> 异常进入 exceptionally/handle 链 支持编排（thenCompose/allOf），首选

调用方拿到 CompletableFuture 后应使用 orTimeout(...)、exceptionally(...) 等显式处理超时与降级，避免线程池被慢任务占满。
