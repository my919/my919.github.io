第十一章：防重提交与接口幂等

发表于 2026-05-16 更新于 2026-10-25 分类于 SpringBoot 本文字数： 4.9k 阅读时长 ≈ 4 分钟

第十一章：防重提交与接口幂等

概念基础

  1. 重复请求从哪来：用户双击表单、页面刷新 / 回退、网络超时重试，都会让同一业务请求到达多次，导致重复下单、重复扣款。
  2. 防重提交（@RepeatSubmit）：计算请求指纹（类名 + 方法 + URI + Token + 参数 JSON 的 SHA256），在 interval 窗口内发现相同指纹直接拒绝（429），解决「手快双击」类问题。
  3. 接口幂等（@Idempotent）：客户端为「业务唯一」请求携带幂等键 Idempotency-Key，服务端首次成功后缓存结果，重放请求直接返回首次结果——多次调用，效果一致。
  4. 为什么基于 Redis：多实例部署下，指纹与结果必须全局共享；Redis 的 TTL 天然适合做时间窗口与结果缓存（部署见第四章）。
  5. 二者关系：防重是「窗口内拒绝」，幂等是「重放返回原结果」，按业务场景选择或组合使用。

本工程基于 Redis 提供两种注解：

注解 场景 行为
@RepeatSubmit 短时防双击 相同指纹在 interval 内拒绝
@Idempotent 支付/下单 相同幂等键返回首次成功结果

流程简述：

  1. 无键 → 400
  2. Redis 无记录 → 加锁执行 → 成功则缓存 Result JSON
  3. 相同键再次请求 → 直接返回缓存
  4. 执行中重复 → 409

切面核心实现（Redis + Lua）

幂等拦截的关键是「检查 + 占位」必须是原子操作，否则两个并发请求可能同时穿透检查。用 Lua 脚本保证原子性：

关键设计决策：

决策点 本工程选择 理由
占位原子性 SET NX EX Lua 脚本 并发下只有一个请求进入业务
失败处理 删除占位，允许重试 业务失败不应永久锁死幂等键
只缓存成功 code == 200 才写缓存 失败结果缓存会让重试永远拿到同样的错
状态机 空 → PROCESSING → 结果 JSON 区分「执行中（409）」与「已完成（重放）」

备选方案：数据库防重表

Redis 之外的经典方案是防重表 + 唯一索引，适合「幂等需强持久化、跨长周期」的场景（如对账回调）：

流程：INSERT 防重表（命中唯一索引即重复请求）→ 执行业务 → 同事务更新结果。

对比选型：

维度 Redis 方案（本工程） 防重表方案
持久性 TTL 过期即失效 永久留存，可追溯
性能 内存级，开销极小 每次多一次 INSERT
适用窗口 分钟~小时级重试窗口 天/月级长周期幂等
依赖 Redis 可用性 数据库可用性

客户端配合协议

幂等键是客户端职责，需与前端/调用方约定：

项 约定
生成时机 进入表单页时生成 UUID，提交即携带，而非每次点击重新生成
复用规则 同一笔业务提交的重试/双击复用同一键；重新填写表单生成新键
传递方式 请求头 Idempotency-Key，勿放 body（拦截器解析更早）
失效感知 收到 409 提示「处理中」；收到缓存结果视为提交成功

本章小结

要点 结论
两个注解 @RepeatSubmit 防双击（指纹 + TTL 拒绝）；@Idempotent 幂等（幂等键 + 结果缓存）
前置条件 Redis 可用 + spring-boot-starter-aspectj 已引入
配置入口 app.repeat-submit.* / app.idempotent.* 控制开关、间隔与过期
幂等协议 请求头 Idempotency-Key；无键 400、重放返回缓存、执行中 409
测试策略 单测环境关闭 app.*.enabled，避免无 Redis 时切面报错
