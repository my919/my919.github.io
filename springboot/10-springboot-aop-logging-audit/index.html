第十章：AOP日志与操作审计

概念基础

  1. AOP（面向切面编程）：把日志、审计这类横切逻辑从业务方法中抽离成切面统一织入，业务代码零侵入、可统一开关。
  2. 请求日志：RequestLogAspect 对 Controller 包做包级切面，记录 URI、参数、IP、耗时，输出到 SLF4J 应用日志，用于开发排障与性能分析。
  3. 操作审计：@OperLog 注解 + OperLogAspect，把谁、何时、对什么、做了什么、结果与异常写入 sys_oper_log 表，满足安全合规与操作追溯。
  4. 为什么异步落库：审计写库不能拖慢主请求，saveAsync + @Async 交给 taskExecutor 线程池执行（见第十二章）。
  5. 两者定位互补：请求日志面向开发排障，操作日志面向业务审计；一个输出到日志文件，一个落库可查询。

本仓库的两类实现：

类型 实现 输出
请求日志 RequestLogAspect 应用日志（SLF4J）
操作审计 @OperLog + OperLogAspect 表 sys_oper_log

注解属性是编译期常量，无法直接写「操作了用户张三」这类动态文案。进阶做法是注解支持 SpEL 模板，切面解析后落库：

要点：

  • Gradle 需开启 -parameters 编译参数，否则参数名变成 arg0、arg1（Boot 4 的 bootJar/compileJava 默认已带上，手动项目自行核对）。
  • SpEL 表达式来自开发者注解而非用户输入，无注入风险；但仍建议 try-catch 解析异常，表达式写错不应搞挂业务接口。
  • 本仓库 @OperLog 走「注解常量 + 请求信息」路线，未启用 SpEL；需要动态文案时可按本节扩展。

5. 异步落库细节

注意事项：

  • 自捕获异常：@Async void 方法的异常不会进 GlobalExceptionHandler，吞掉或仅记日志，绝不能影响主流程。
  • 数据组装在主线程：HttpServletRequest 绑定在请求线程上，saveAsync 入参必须是已组装好的 POJO，不能把 request 传进异步线程。
  • 上下文传递：TraceId / 操作人等 ThreadLocal 数据需在提交任务前拷贝到行数据中，或用 TaskDecorator 装饰器传递。
  • 关闭策略：wait-for-tasks-to-complete-on-shutdown: true 保证停机时队列里的审计日志写完再退出（见第十二章）。

审计表设计建议

sys_oper_log 属流水型大表，设计时提前考虑：

  • 索引：oper_name、create_time 建联合索引支撑「某人的操作记录」查询；title、businessType 基数低，不建议单独建索引。
  • 归档：按月分表或定期归档到历史表，查询接口默认只查近 3 个月。
  • 字段长度：operParam / jsonResult 用 TEXT；errorMsg 建议 VARCHAR(2000) 截断存储，异常堆栈不进表。
  • 只进不出：审计表不提供 UPDATE/DELETE 接口，本仓库也只暴露查询端点，满足合规的不可篡改要求。

常见问题

现象 原因 处理
审计表无数据 app.log.oper.async 开启但线程池未配 检查 taskExecutor Bean 存在且 @EnableAsync 生效
日志里 IP 全是 127.0.0.1 经过 Nginx 未透传真实 IP 网关设 X-Forwarded-For，服务端读取该头
参数被截断 max-param-length 限制 调大或按接口关闭 saveRequestData
请求日志双份 自定义 Filter 也记了日志 全链路只留一个请求日志实现
停机丢审计 未开 wait-for-tasks-to-complete-on-shutdown 第十二章配置项打开

本章小结

要点 结论
两类切面 RequestLogAspect 记请求日志；@OperLog + OperLogAspect 写审计表
启用方式 引入 spring-boot-starter-aspectj 即可，Boot 自动开启代理
审计字段 title、businessType、operIp、operParam、costTime、errorMsg 映射到 sys_oper_log
异步写入 app.log.oper.async: true，saveAsync + @Async 走 taskExecutor，不阻塞业务
验证方式 带 X-Oper-Name 头调用接口，查日志表或 /api/sys-oper-logs
