11. 典型案例：敏感配置加密（数据库密码与 JWT 密钥入库）

问题背景：安全审计发现 application-prod.yml 里数据库密码、JWT 签名密钥全是明文，且文件已提交 Git 历史——拿到仓库读权限就等于拿到生产库。要求：仓库与配置中心里的敏感值必须密文，主密钥不落代码与镜像。

方案（Jasypt 加密属性 + 环境变量注入主密钥）：

资产 存放位置 泄露风险
密文属性 ENC(…) yml / Nacos / Git 可公开（无主密钥解不开）
主密钥 JASYPT_ENCRYPTOR_PASSWORD K8s Secret / 环境变量 集群内才可见
代码与镜像 不含任何明文密钥 轮换主密钥即可重加密

关键代码与配置：

踩坑点：

  1. 图省事把主密钥也写进 yml 或启动脚本——等于锁和钥匙放一个抽屉；主密钥只能走环境变量/Secret，且与代码分开管理。
  2. 升级了 Jasypt 版本但算法变了，老密文在另一台机器解不开、服务起不来——算法与版本一并固定，密文重加密时灰度验证。
  3. 异常日志把 DataSourceProperties 整个打出来，解密后的密码进了日志——日志脱敏，禁止打印 Environment 原始属性。
  4. 密钥从来没轮换过，离职员工仍持有主密钥——建立轮换机制：新主密钥加密新密文，滚动重启。

12. 常见误用与陷阱

坑 现象/后果 解法
JWT 密钥硬编码在源码里 泄露即可伪造任意用户令牌 密钥走环境变量/KMS，支持轮换
CSRF 一刀切对所有接口禁用 Cookie/Session 站点被 CSRF 攻击 仅无状态 JWT API 禁用；表单站点保留并配 token
白名单写成 requestMatchers(“/**”).permitAll() 全站接口裸奔，形同未加密 精确路径放行，默认 anyRequest().authenticated()
hasRole(“ROLE_ADMIN”) 框架再自动加前缀，判断永远不命中 写 hasRole(“ADMIN”)，前缀 ROLE_ 由框架补
登出只在前端删 token 令牌在有效期内仍可继续调用 Redis 黑名单（登出即拉黑至原过期时间）
异步线程里取 SecurityContext 拿不到当前用户，权限校验为空 DelegatingSecurityContextAsyncTaskExecutor 传播上下文
异常响应返回默认错误页 401/403 混乱且暴露框架信息 自定义 authenticationEntryPoint / accessDeniedHandler 输出统一 JSON
密码用 MD5/SHA-256 直接存储 撞库/彩虹表秒破 BCrypt（自带盐与慢哈希）
