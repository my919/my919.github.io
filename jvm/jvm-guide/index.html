1. 概念说明

JVM（Java Virtual Machine）是 Java 跨平台的基石：把字节码翻译为机器指令并管理内存。理解 JVM 是定位内存溢出、CPU 飙高、停顿过长问题的基础。

一次 Java 程序的生命周期：源码 .java → 编译为字节码 .class → 类加载到内存 → 执行引擎解释/编译执行 → 垃圾回收自动清理无用对象。

2. 内存结构（运行时数据区）

区域 共享 作用 溢出错误
堆 是 对象分配 OutOfMemoryError: Java heap space
元空间 是 类元数据 Metaspace
虚拟机栈 否 方法调用帧 StackOverflowError
程序计数器 否 字节码行号 无

3. 类加载机制

加载 → 验证 → 准备 → 解析 → 初始化 五阶段。

双亲委派模型：类加载请求先交给父加载器（App → Platform → Bootstrap），父加载不了才自己加载——保证核心类（如 java.lang.String）不被篡改。

4. 垃圾回收（GC）

判断对象可回收：可达性分析（GC Roots 出发不可达即回收）。GC Roots 包括：栈帧局部变量、静态变量、JNI 引用等。

分代收集（对象年龄小者升代）：新生代用复制算法（Eden/S0/S1），老年代用标记-整理/标记-清除。

JDK 21 可用的收集器：

收集器 特点 适用
G1（默认） 分区化、可预测停顿 大多数服务，默认即最佳
ZGC 亚毫秒停顿、超大堆 大内存低延迟（数百 GB）

7. 实战排查案例

7.1 案例一：内存溢出（OOM）

现象：服务报 java.lang.OutOfMemoryError: Java heap space。

排查流程：

用 MAT / Eclipse Memory Analyzer 打开 heap.hprof，看 Dominator Tree 找占用最大的对象路径，定位到泄漏代码（常见：静态 Map 无限累积、连接未关闭）。

7.2 案例二：CPU 飙高

常见原因：死循环、频繁 Full GC（大量分配）、正则回溯爆炸。

7.3 案例三：频繁 Full GC

常见原因与对策：

原因 对策
堆太小 调大 -Xmx，观察是否稳定
内存泄漏 堆 dump 分析，修复引用
大对象直接进老年代 -XX:PretenureSizeThreshold 或优化代码
系统换页（堆大于物理内存） 保持 -Xmx ≤ 物理内存 70%

8. 调优方法论（不盲目调参）

  1. 先观测：jstat / GC 日志跑一天，看正常基线。
  2. 定位问题：是停顿长（GC）还是吞吐低（业务）还是内存泄漏。
  3. 单点修改：每次只改一个参数，用数据验证。
  4. 对照：压测（wrk / JMH）前后对比 GC 停顿、QPS、P99。

9. 生产基线配置建议

监控指标：GC 频率（Full GC 每天应 < 几次）、P99 停顿、堆使用率曲线。

10. 典型案例：一次压测频繁 Full GC 的调优（GC 日志驱动）

问题背景：订单服务 4C8G、堆 4G、G1。大促前压测目标 2000 QPS，实际 800 QPS 时接口 P99 就从 80ms 飙到 900ms——压测被迫中止。

排查过程（全程 GC 日志驱动，不拍脑袋）：

步骤 操作 观察
① GC 日志统计停顿分布 Young GC 每 400ms 一次、每次 30ms；Full GC 每 90 秒一次、每次 1.2s ← P99 元凶
② 看 Full GC 前日志 Pause Young (Concurrent Start) 后紧跟 Humongous regions: 512 -> 512：大对象占了 512 个 region
③ 核对参数 启动配了 -XX:MaxGCPauseMillis=10（有人拍脑袋设的）：G1 为凑 10ms 目标把年轻代压得极小
④ 代码核对 接口一次性 SELECT 全量 3 万行订单 → 转成 40MB 的 List：单次分配超 region 一半 = 大对象直接进老年代
⑤ 双管齐下修复 参数：MaxGCPauseMillis=100；代码：分页查询（每页 500 行）

11. 常见误用与陷阱

坑 现象/后果 解法
没有数据就调参（拍脑袋） 参数互相纠缠，越调越糟且无法归因 先跑一天 GC 日志取基线，一次只改一个参数并压测对照
MaxGCPauseMillis 设得过小（10ms 级） G1 缩小年轻代凑目标 → GC 频率暴涨、吞吐崩 常规服务 100ms 左右；先满足吞吐再谈停顿
收集器误解：JDK 21 还配 CMS 或”ZGC 万能” CMS 已在 JDK 14 移除（启动报错）；ZGC 用在中小堆纯属浪费 JDK 21 默认 G1 足够；数百 GB 大堆低延迟才上 ZGC
大对象不治理 大 List/byte[] 直进老年代，晋升风暴 + Full GC 分页/分批处理，控制单次分配；关注 Humongous 日志
把 StackOverflowError 当内存不足去调堆 递归没出口/栈深超限，调堆毫无作用 SOE 查递归与栈帧，必要时 -Xss 调栈，别动堆
高峰期对大堆执行 jmap -dump:live :live 触发一次 Full GC + 全程 STW，线上雪上加霜 低峰 dump 或用 OOM 自动 dump；jcmd GC.heap_dump 更稳
