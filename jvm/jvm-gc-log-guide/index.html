1. 概念说明：为什么必须会读 GC 日志

GC 是性能杀手：GC 发生时应用线程要停顿（STW，Stop The World）——停顿总时长直接决定接口延迟。

不读 GC 日志 = 盲调 JVM 参数（见 jar 启动篇的”为什么用数据定堆”）。

2. 开启 GC 日志（JDK 21）

2.1 生产启动参数（直接可用的组合）

为什么必须配滚动（filecount/filesize）：不滚动的话，一个进程跑几个月 GC 日志能占几十 GB 磁盘——磁盘被日志打满是线上故障第一高频。

2.2 线上临时开启（不用重启）

3. G1 日志逐字段解读（JDK 21 默认）

3.1 一次 Young GC 的完整日志

逐行解读：

片段 含义 健康判断
Pause Young (Normal) Young GC（G1 常规停顿） 正常行为
Eden regions: 128->0(256) Eden 区 128 个 → 清空；总容量 256 每次都清空 = 正常
Old regions: 512->512 老年代不变（年轻代回收不碰老年代） 正常
512M->96M(6G) 堆从 512M 用到 96M 活（堆总 6G） 存活率低 = 正常
12.345ms 本次停顿耗时（关注点） < 100ms 正常
Real=0.012s 真实停顿时间 与耗时一致

3.2 老年代增长（Mixed GC / 并发标记）

关键信号：

信号 含义 要警惕什么
Concurrent Start 老年代占比达到阈值（默认 45%）触发并发标记 出现频率升高 = 老年代增长快
Humongous Allocation 大对象分配（> 区域 50%） 大对象直接进老年代，频繁 = 问题
Pause Mixed Mixed GC（回收老年代） 频率升高 = 老年代在涨
Concurrent Cycle 720ms 并发标记耗时（不 STW） 长但不停顿，可接受

3.3 Full GC（红色警报）

Full GC 为什么是警报：全程 STW（1.2 秒应用完全卡死）、需要压缩整理。Full GC 频繁 = 内存有问题（泄漏/堆太小），见内存排查篇。

6. 常见模式与调参（对照日志）

日志模式 根因 调参方向
Young GC 频繁（每秒多次） 分配太快/堆太小 加 Xmx；查大对象分配
Mixed GC 越来越频繁 老年代增长快（对象晋升） 查存活对象多的代码/缓存无界
Full GC 频繁 老年代打满 内存泄漏排查（内存篇）；临时调大 Xmx
频繁 Humongous 大数组/大缓存无界 业务层拆大对象；限制缓存
单次停顿突高（>500ms） 大对象分配/老年代压缩 查大对象来源
GC 正常但接口慢 不是 GC 问题 查锁/IO/CPU（见 CPU 篇）

9. 典型案例：GC 日志正常但接口每 30 秒抖一次（Safepoint 真凶）

问题背景：商品服务每约 30 秒出现一波 200-400ms 的接口抖动，P99 告警持续。第一反应是 GC——但 GC 日志停顿全部 < 30ms，GC 被排除，很多人到这一步就卡住了。

排查过程：

步骤 操作 观察
① GC 日志全量统计（本篇 §4.1 命令） Young GC 每 2 秒一次、每次 15-25ms；Full GC 为 0 → GC 解释不了 300ms 抖动
② 抖动时刻与 GC 时刻对齐 时间轴上 300ms 抖动点不与任何 GC 停顿重合
③ 开 safepoint 日志：-Xlog:safepoint:file=... 每 30 秒一条：Reaching safepoint: 280ms（线程到达安全点慢）← 真凶特征
④ 排查 30 秒周期任务 有个本地统计任务每 30 秒跑一次：单循环遍历 800 万条内存数据做聚合（counted loop 长期不进安全点）
⑤ 修复：任务拆批 + 降频 循环每次处理 50 万条后让出；频率 30s → 5min；可选 -XX:LoopStripMiningIter=1000

10. 常见误用与陷阱

坑 现象/后果 解法
GC 日志没开 / 还在用 JDK 8 的 -Xloggc 语法 出问题无时间线；JDK 9+ 老语法直接失效 统一 -Xlog:gc*:file=... + 滚动参数
日志不配滚动（filecount/filesize） 跑几个月日志几十 GB，磁盘打满成事故 filecount=5,filesize=20m 固定写法
只看平均停顿，不看最坏/P99 平均 20ms 岁月静好，P99 500ms 偶发抖动 `sort -rn
出问题才临时开 GC 日志 覆盖/追加混乱，故障现场的时间线不完整 启动参数常开（滚动成本极低），临时开启只作补充
用 JDK 8 的日志解析习惯/工具读 JDK 21 日志 格式完全不同（统一 -Xlog），字段对不上得出错误结论 按 JDK 21 格式解读；GCeasy 上传时选对版本
只盯 GC 不看 safepoint GC 正常但停顿仍高（长循环/JNI 拖住安全点） 排查深水区开 -Xlog:safepoint，看 Reaching 耗时
日志正常还在调 GC 参数 接口慢根因在锁/IO/CPU，调参白费且引入新风险 先归因再动手：GC 日志洗清嫌疑就转查其他方向
