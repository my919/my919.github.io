1. 概念说明

线上排障方法论：先保留现场 → 收集证据（日志/转储/指标）→ 定位根因 → 修复 → 复盘。切忌重启了事（现场丢失）。

JVM 排查两类核心问题：

问题 表现 工具
内存问题 OOM、频繁 Full GC、内存缓慢增长 jmap/MAT、jstat
CPU 问题 某进程 CPU 100%、响应变慢 top、jstack、async-profiler

诊断前提：启动参数必须开对（见 §6），否则事后无法分析。

2. OOM 分类

错误 原因 对策
Java heap space 堆满（泄漏或过大对象） 堆转储分析
GC overhead limit exceeded 98% 时间在 GC 同上
Metaspace 类加载过多（热部署/反射） 检查类加载器泄漏
Unable to create native thread 线程数超 OS 限制 检查线程创建、ulimit
Direct buffer memory 堆外内存超限 检查 NIO 缓冲区

常见 CPU 高根因：死循环（while 条件永不满足）、正则回溯、大对象序列化、GC 频繁（假 CPU 高）、锁竞争自旋。

GC 日志关键行：

健康指标：

指标 健康值
Full GC 频率 生产 < 1 次/小时
Full GC 单次耗时 < 500ms
GC 总暂停占比 < 5%
老年代使用率 稳定在 60-70% 以下

常见异常模式：

现象 含义 对策

9. 典型案例：一次 OOM 堆转储分析（jmap → MAT → 定位 ThreadLocal 泄漏）

问题背景：网关服务稳定运行 5 天后凌晨 OOM 宕机（java.lang.OutOfMemoryError: Java heap space）。因预配了 HeapDumpOnOutOfMemoryError，现场自动留下一份 2GB 的 heap.hprof。

排查过程：

步骤 操作 观察
① 确认 OOM 类型与 dump 文件（日志 + /data/dumps） heap space OOM，dump 已生成，无需重启抓现场
② MAT 打开 heap.hprof → Leak Suspects 报告 嫌疑：一个 ClassLoader 持有 1.8GB（占堆 90%）
③ Dominator Tree 按 Retained Heap 排序 220 个 ThreadLocalMap$Entry，每个约 8MB，合计 1.76GB
④ Path to GC Roots（排除弱引用） 入口在 Thread.threadLocals → 线程池核心线程长期存活
⑤ 对照代码 拦截器把用户请求上下文（含请求体快照）塞进 ThreadLocal，线程复用后从不 remove

10. 常见误用与陷阱

坑 现象/后果 解法
-Xms 与 -Xmx 不一致 运行期堆扩容抖动，GC 停顿忽长忽短 生产 -Xms = -Xmx，启动即定死
-Xmx 设成物理内存/容器 limit 上限 堆外+Metaspace+线程栈被挤没，容器被 OOM Killer 杀 堆 ≈ 容器内存的 70-75%（或 MaxRAMPercentage=75）
误用 jmap -F 强制 dump 全程 STW，服务假死几分钟，线上事故扩大 用 jcmd GC.heap_dump 或 OOM 自动 dump；-F 仅救命用
GC 日志未开 出问题无线索，性能退化只能盲猜 启动就配 -Xlog:gc*:file=...，轮转防写满磁盘
Metaspace 未设上限 动态类泄漏静默吃光机器内存 -XX:MaxMetaspaceSize=512m 显式封顶
只盯堆内存不看堆外 堆用 60% 却被 OOM Killer 杀（DirectBuffer/Netty/gzip） NMT 跟踪堆外 + 容器内存告警与堆告警分开
OOM 自动 dump 未配路径/未留磁盘 dump 写到默认目录或写满盘，二次事故 HeapDumpPath=/data/dumps + 该目录磁盘告警
