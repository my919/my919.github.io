1. 从一个 jar 开始

1.1 先拿到可执行 jar

为什么是”可执行 jar”：Spring Boot 的 repackage 会把依赖打进 jar 内的 BOOT-INF/lib，java -jar 直接能跑；普通 jar（只有自己编译的类）必须自己拼 classpath，不适合部署。

1.2 前台启动（先跑通）

为什么不直接这样上生产：前台运行 + 无内存上限 + 无 GC 日志 + OOM 不留现场——任何一个生产问题都无法事后分析。下面逐项补。

1.3 后台启动与停止

为什么用 SIGTERM 而不是 SIGKILL：SIGKILL（kill -9）直接杀死进程，正在写库的事务可能中断、缓存未刷盘；SIGTERM 让 Spring Boot 走优雅停机流程（见 Spring Boot 篇），生产停止一律先 SIGTERM。

1.4 用 systemd 守护（生产标准做法）

创建 /etc/systemd/system/app.service：

为什么用 systemd：进程崩溃自动拉起、开机自启、日志统一 journalctl、资源限制可配置——比裸 nohup 可靠得多。

2. JVM 参数为什么这么设（逐项讲透）

2.1 堆内存：-Xms / -Xmx

为什么 -Xms 必须等于 -Xmx：-Xms < -Xmx 时 JVM 会在使用中动态扩容、缩容堆，扩容是 STW 的（Full GC 才能扩容）——线上会出现”流量上来 → 堆不够 → 触发 Full GC 扩容 → 停顿变长 → 更慢”的恶性循环。相等后堆大小恒定，不会因扩容停顿。

数值怎么定（用数据，不拍脑袋）：

经验公式：-Xmx ≈ 物理内存 × 40%~50%（剩余给 OS 缓存、线程栈、堆外、Metaspace）。

2.2 元空间：-XX:MaxMetaspaceSize

为什么要设上限：Metaspace 存类元数据，默认无上限（只受物理内存限制）。一旦发生类加载器泄漏（热部署、反射生成类、动态代理），Metaspace 会一路涨到把内存吃光——设上限后 OOM 抛的是 Metaspace 错误并留下现场，不设上限则直接系统 OOM（系统被杀，什么都没留下）。

2.3 GC 日志：必须开

为什么必须开：GC 日志是事后分析唯一的”时间线证据”——Full GC 什么时候开始、多频繁、老年代怎么涨，全在日志里。filecount=5,filesize=20m 是滚动日志（最多 100MB），防磁盘爆。不开 GC 日志 = 出问题只能猜。

2.4 OOM 现场：必须开

为什么必须开：OOM 发生时自动把堆转储成 .hprof 文件。没有这个参数，进程一死现场就没了，内存泄漏只能靠猜。HeapDumpPath 要指向有足够磁盘空间的目录（dump 文件可能和堆一样大，2g 堆 ≈ 2g dump）。

2.5 容器环境：-XX:MaxRAMPercentage

为什么：JVM 默认按宿主机内存算默认堆（如宿主机 64G，JVM 默认堆 ≈ 1/4 = 16G），容器限额 2G 时会直接 OOM。MaxRAMPercentage=75 让 JVM 按容器 cgroup 限额的 75% 设堆——K8s/Docker 部署必须用百分比，不用写死的 -Xmx。

2.6 G1 相关：默认够用，个别才调

什么时候才调：绝大多数服务用默认 G1 就够。MaxGCPauseMillis 只是优化目标；ParallelGCThreads 在 2C 小容器里默认会按 2 算，一般无需手调。调参前必须有 GC 日志数据支撑，禁止”感觉慢就调”。

6. 参数速查表

参数 作用 为什么
-Xms/-Xmx 初始/最大堆 相等避免扩容 STW
-XX:MaxRAMPercentage=75 容器按限额设堆 防止按宿主机内存误判
-XX:MaxMetaspaceSize 元空间上限 防类加载泄漏吃光内存
-XX:+HeapDumpOnOutOfMemoryError OOM 自动 dump 保留泄漏现场
-XX:HeapDumpPath dump 目录 磁盘要够（≈ 堆大小）
-Xlog:gc*:file=... GC 日志滚动 事后分析的唯一时间线
-Duser.timezone 时区 容器默认 UTC，时间错 8 小时

7. 典型案例：一次 K8s 频繁重启（OOMKilled 137）的参数纠错

问题背景：订单服务迁入 K8s（Pod limit 4G），发布后反复重启：Pod 状态 OOMKilled，退出码 137，平均存活 40 分钟。应用日志里却没有任何 OOM 异常——诡异点所在。

排查过程：

步骤 操作 观察
① kubectl describe pod 看事件 Last State: Terminated, Reason: OOMKilled, Exit Code: 137 → 是系统级杀进程，不是 JVM OOM
② 查启动命令 启动参数是老脚本带来的 -Xmx8g（物理机时代的配置）！容器 limit 只有 4G
③ 核实 JVM 实际堆 `jcmd 1 VM.flags
④ 观察 kubectl top pod 内存爬到 4G 即被杀：JVM 堆按 8G 规划，Metaspace+堆外+线程栈叠加越限
⑤ 修复：改百分比参数并压测复验 MaxRAMPercentage=75 → 实际堆 3G，Pod 稳定，峰值内存 3.4G / 4G

8. 常见误用与陷阱

坑 现象/后果 解法
容器里写死 -Xmx（沿用物理机配置） JVM 按宿主机/旧配置规划堆，Pod 被 OOMKilled 137 且无 dump 容器一律 MaxRAMPercentage=75，迁移必核参数
-Xms 与 -Xmx 不一致 运行期扩容 STW，高峰期停顿忽长忽短 生产 -Xms = -Xmx
堆设成机器/容器内存上限 Metaspace+堆外+线程栈把总内存顶爆，被 OOM Killer 杀 堆 ≤ 总内存 75%，其余留给堆外与栈
kill -9 停服务 正在处理的事务中断、注册中心摘流不及，用户请求报错 一律先 SIGTERM（systemd/K8s 默认），强杀只做兜底
Metaspace 未设上限 类泄漏静默吃光内存，系统被杀且无任何现场 -XX:MaxMetaspaceSize=512m 显式封顶
GC 日志未开 出问题无时间线，只能靠猜 -Xlog:gc*:file=... 滚动配置，启动即开
还配 -XX:+UseCMS 等 CMS 参数 JDK 14+ CMS 已移除，启动直接报错；误留 Parallel 参数与 G1 冲突 JDK 21 用默认 G1，参数从老环境迁移时逐个核对
不设时区 -Duser.timezone 容器 UTC，日志与定时任务时间差 8 小时，排障对时间线全乱 启动参数显式 Asia/Shanghai
