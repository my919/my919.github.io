1. 概念说明

微服务拆分本质：把”一个能跑的大应用”变成”多个能独立部署的小应用”——目标是独立演进、独立伸缩、故障隔离，代价是分布式复杂度（网络、事务、一致性、排障）。

拆分决策前提（先回答）：

  • 团队多大？<10 人且无明确边界 → 慎拆（先模块化单体）。
  • 是否有独立伸缩/部署的明确诉求？
  • 是否有独立的业务所有者（团队/领域）？

拆错代价：分布式事务、跨服务查询、发布联动、调用链复杂——拆比不拆更难。

9. 典型案例：生产级「用户下单」全链路治理

9.1 问题背景

订单服务上线后暴露三个生产问题：偶发下单超时但找不到慢在哪一跳；大促时库存服务响应变慢，订单服务 Feign 线程池被打满，连不依赖库存的查询也 503；多实例日志各说各话，一次请求无法串联。治理目标：统一入口、可控容错、全链可观测。

9.2 全链路结构

9.3 网关：路由 + 统一鉴权

9.4 Feign 调用：超时 + 重试 + 熔断降级（Resilience4j）

重试只能给幂等查询 / 带幂等键的写开放；裸写接口重试会造成重复扣减。多层调用只允许最内层一层重试，避免重试相乘形成风暴。

9.5 链路追踪：traceId 跨服务透传

引入 micrometer-tracing-bridge-brave 后，同进程日志 MDC 自动注入 traceId；跨进程通过 Feign 拦截器透传 B3 头，下游归入同一条 Trace。

日志模板（logback-spring.xml）打印 traceId，排障时一搜到底：

异步场景（线程池、MQ）上下文不会自动传递：线程池要包装 Runnable 捕获/恢复 traceId，MQ 要把 traceId 放进消息 Header 由消费端续接，否则链路会在异步处断开。

9.6 踩坑点

  • 超时层层不设：Feign、网关任一处无限等待，一个慢下游吃光整条链路线程池——全链路统一超时，且上游超时要大于下游超时之和。
  • 写接口盲目重试：非幂等扣减被重试 2 次，库存扣了 3 份——重试白名单化，写接口必须带幂等键。
  • 降级静默：fallback 直接返回空数据，无日志无打点，业务故障无人知——降级路径必须埋点告警并接入异步补偿。
  • 熔断器粒度过粗：整个服务一个熔断器，边缘接口故障把核心扣库存也熔断——按核心方法/业务资源分组隔离。
  • 链路在 MQ 处断开：HTTP 头透传了 traceId，发消息后断链——消息头携带 traceId，消费端恢复 MDC 续接。

10. 常见误用与陷阱

坑 现象/后果 解法
网关只部署单实例 网关重启/宕机 = 全站不可用，入口单点被放大 网关至少 2 实例多活部署，前置 LB/VIP 与健康检查
注册中心心跳误摘 实例长 GC 或网络抖动时心跳超时被摘除，流量集中到剩余实例 合理设置心跳间隔与摘除阈值，开启保护阈值（Nacos 0.8），优雅上下线预热
配置中心变更无审计无灰度 错误配置一键热刷全集群，且无法追溯 变更审批 + 审计留痕 + 灰度生效 + 版本回滚
Feign/HTTP 不设超时 慢请求占满调用方线程池，级联雪崩 connect/read 超时显式配置，超时值沿调用链递减
多层重试形成重试风暴 网关、服务、客户端各重试数次，流量被放大数倍至数十倍 只允许一层重试，指数退避 + 限次，写操作强制幂等键
降级无兜底无监控 用户静默失败，故障被掩盖到对账才发现 fallback 打点告警，结果转异步补偿/人工队列
无灰度直接全量发版 新接口与老消费方契约不兼容，全站故障 OpenAPI 版本化，蓝绿/金丝雀按用户与流量比例切流
traceId 不透传异步链路 跨线程/跨 MQ 调用链断裂，无法端到端排障 线程池包装任务透传；MQ 消息头携带 traceId 由消费端续接
