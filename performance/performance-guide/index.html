6. 典型案例：Core Web Vitals 优化

6.1 问题背景

商品列表页 CrUX 真实用户数据（P75）：LCP 4.2s、INP 380ms、CLS 0.25，移动端转化率比竞品低 15%。先接入 RUM 上报再动手，避免对着实验室数据盲调。

6.2 解决方案

按「先测量再优化」：web-vitals 上报真实用户体验 → 图片与字体治理 LCP/CLS → 长任务切片治理 INP → 每项优化用 A/B 验证收益。四周后 LCP 1.8s / INP 150ms / CLS 0.02。

6.4 踩坑点

  • 给首屏大图加 loading=”lazy”，LCP 反而从 3.1s 恶化到 4.2s——LCP 图必须 eager + 高优先级
  • 只跑 Lighthouse 实验室数据，与真实用户 P75 差 1s 以上，改以 CrUX/RUM 为准后才调对方向
  • 第三方统计脚本同步加载阻塞主线程，INP 恶化 80ms，改 async + 延迟注入
  • 字体 swap 引起二次布局，加 size-adjust 与占位后 CLS 收敛到 0.02

7. 常见误用与陷阱

坑 现象/后果 解法
LCP 图设置懒加载 首屏反而更慢 eager + fetchpriority=”high” + preload
用平均值评估性能 用户 P75 体验差却测不出来 看 P75/P95 分位 + 真实用户 RUM
图片不定宽高 加载时布局跳动，CLS 超标 width/height 或 aspect-ratio 占位
同步加载第三方脚本 主线程阻塞，INP 飙升 async/defer + 延迟注入 + 加载审计
一刀切强缓存 HTML 发布后用户拿到旧页面 HTML no-cache，静态资源指纹长缓存
只优化前端忽略 TTFB LCP 天花板卡在服务端 CDN + 边缘缓存 + 接口预取
