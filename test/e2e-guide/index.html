端到端测试实战指南

相关阅读：第二章：集成测试与 E2E 测试

2026 年 E2E 测试全景：Playwright vs Cypress 选型 · 页面对象模式 · 视觉回归 · API Mock · CI 集成 · 覆盖率度量。

1. E2E 测试定位

1.1 测试金字塔

E2E 成本最高但最接近真实用户，应聚焦核心业务路径而非穷举。

1.2 何时写 E2E

场景 适合
关键转化链路（注册→下单→支付） ✅ 必须
跨页面/跨服务流程 ✅ 必须
表单校验细节 ❌ 单元测试更合适
UI 样式像素级比对 ❌ 视觉回归工具更合适

2. Playwright（推荐首选）

2.1 为什么选 Playwright

能力 Playwright Cypress
多浏览器 Chromium / Firefox / WebKit 仅 Chromium 完整
多 Tab / iframe 原生支持 有限
并行执行 内置 Worker 池 需 Dashboard 付费
自动等待 内置智能等待 内置重试
网络拦截 page.route() cy.intercept()
多用户并发 Browser Context 隔离 需多实例
Codegen codegen 录制生成 Cypress Studio

4. 测试数据策略

4.1 三层数据方案

层级 方式 适用
API Seed 测试前通过 API 创建数据 ✅ 推荐
DB Seed 直接操作数据库 快速但耦合
UI 操作 通过界面创建前置数据 慢但最真实

4.2 数据隔离原则

  • 每个测试用例独立创建、独立清理
  • 不使用共享数据（避免测试间干扰）
  • 使用唯一前缀（如 test-${Date.now()}）防止冲突

6.2 关键指标

指标 目标

Flaky Test 比例 < 1%

7. 最佳实践

7.1 稳定性

  • 不用 waitForTimeout，用 waitForSelector / waitForURL
  • 用 data-testid 选择器，不依赖 CSS 类名或文本
  • 失败截图 + 视频录制，方便排查

7.2 速度优化

  • 复用登录状态（storageState）
  • API Mock 替代真实后端
  • 并行执行 + 分片（--shard=1/4）

7.3 反模式

反模式 正确做法
测试间共享数据 每个测试独立 seed
依赖真实第三方服务 Mock 外部 API
用 sleep 等待 用断言自动等待
一个测试覆盖整个流程 拆分为独立小测试

8. 典型案例：Playwright 关键链路测试

8.1 问题背景

电商「搜索→加购→下单→支付」链路平均每月被改坏 2 次，人工回归总在事故后。目标：核心链路 E2E 化，10 分钟内跑完，失败可自证原因。

8.2 解决方案

只对 3 条转化链路写 E2E：登录态用 storageState 复用；支付走 API Mock 避免真实扣款；关键页面加视觉回归；CI 4 分片并行 + 失败自动归档 trace。

8.3 关键实现

8.4 踩坑点

  • 早期用 waitForTimeout(3000) 等加载，CI 高峰期集体超时，全部换成断言式自动等待
  • 直连真实支付沙箱，第三方抖动导致 30% 假失败，改为路由拦截 + 独立契约测试覆盖网关
  • 测试共享同一账号互相踢下线，改为按 worker 独立账号 + API seed 独立数据
  • 断言依赖 CSS 类名，一次样式重构 60 条用例全红，统一改 data-testid

9. 常见误用与陷阱

坑 现象/后果 解法
waitForTimeout 硬等待 flaky 率高，CI 随机红 waitForURL/expect 自动等待
依赖真实第三方服务 外部抖动导致假失败 page.route 拦截 + 契约测试兜底
测试间共享数据 互相污染，顺序敏感 独立 seed/清理，唯一前缀隔离
选择器绑 CSS 类 重构即大面积失败 data-testid + getByRole 语义定位
E2E 穷举所有细节 套件 30 分钟没人维护 只覆盖关键链路，细节下沉单测
失败无 trace/截图 排障全靠猜 retain-on-failure + artifact 归档
