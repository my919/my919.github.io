1. 概念说明

性能测试目的：验证系统在预期负载下是否达标 + 找出瓶颈 + 给出容量结论（”能抗多少 QPS”）。

关键指标：

指标 含义 常见目标
QPS/TPS 每秒请求/事务数 按业务
并发数 同时在处理的请求 与 QPS 关联
RT（响应时间） 平均/P90/P99 P99 < 500ms
错误率 失败请求占比 < 0.1%
吞吐量 每秒处理字节数 大文件场景

测试类型：

最重要概念：P99 而不是平均值——平均延迟被长尾掩盖；P99 反映真实体验。

5. 瓶颈定位方法论

常见瓶颈速查：

症状 瓶颈
CPU 100% 且 GC 少 业务热点/死循环 → 火焰图
GC 频繁 堆配置/对象过多 → 堆转储
RT 高但 CPU 低 锁竞争/IO 等待/依赖慢
连接池耗尽 连接池小/慢查询占连接
QPS 到某值上不去 数据库/Redis/网络带宽瓶颈

8. 典型案例：订单列表接口压测定位连接池瓶颈

问题背景：订单列表接口目标 3000 QPS、P99<500ms。首轮压测并发 300 时 QPS 卡在 1200 不再上涨，应用 CPU 只有 45%——典型”RT 高但 CPU 低”，优先查依赖层。

方案（阶梯加压 → 四层定位 → 调整 → 复测）：

复测结果：并发 300 → QPS 2850、P99 260ms、CPU 70%，达标；加压到并发 500 出现拐点（QPS 3200、P99 780ms），写入容量报告。

踩坑点：① 曾盲目把连接池调到 200，DB 侧上下文切换暴涨反而整体变慢——连接池大小要配合 DB 的 max_connections 与磁盘 IO，小步调整逐步观察；② 首轮压测表里只有 1000 条数据，QPS 虚高 3 倍，先造真实量级数据（百万行、冷热分布）再压。

9. 常见误用与陷阱

坑 现象/后果 解法
空表/小数据量压测 QPS 虚高数倍，容量结论失真 造生产量级数据 + 冷热分布
只看平均 RT 平均 80ms 掩盖 P99 800ms 长尾 看 P90/P99/P999 与 RT 分布
一次打到最大并发 拐点定位不了，直接打崩无归因数据 阶梯加压，每级跑满 5 分钟
压测机自身是瓶颈 端口/CPU 耗尽，误判服务问题 监控压测机资源，必要时分布式施压
脚本无业务断言 返回全是 500 也算”高吞吐” 内置业务码/关键字段断言
未预热就采数 JIT 未编译、连接池未建，数据偏低 先热身 5 分钟再正式采集
压测不同步监控 出了拐点说不清是 CPU/DB/锁的锅 应用/资源/依赖/网络四层同步采集
连接池盲目调大 DB 上下文切换剧增，吞吐反降 10→30→50 小步调，每步复测
