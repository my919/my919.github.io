1. 概念说明

测试金字塔（投入与收益的平衡）：

层级 验证什么 特点
单元测试 单个类/函数逻辑 毫秒级、定位准
集成测试 模块与中间件协作 秒级、接近真实
API 测试 接口契约与业务流 模拟用户调用
E2E 完整用户旅程 最接近生产、最贵

测试原则：测行为不测实现、先写测试再写代码（TDD）、测试要独立可重复、快速反馈。

7.2 覆盖率不是一切

覆盖率衡量”哪些代码跑了”，不保证”断言是否正确”。重点测核心业务路径、边界条件、异常分支，追求 80% 行覆盖 + 高价值断言。

8. 测试体系落地清单

阶段 动作
1. 单测补齐 Service/Mapper 核心逻辑 ≥80%
2. 集成测试 关键仓储与事务用 Testcontainers
3. API 测试 所有对外接口（成功+失败路径）
4. E2E 冒烟 核心用户旅程 5-10 条
5. CI 门禁 单测+覆盖率+lint 全进流水线
6. 回归 每版本全量跑，失败即阻断

9. 典型案例：下单接口的分层测试落地

问题背景：下单链路（校验 → 扣库存 → 落单）只有一个”启动 Spring 连真实库”的集成测试：跑一次 8 分钟、用例间互相污染数据，团队几乎不再跑。

方案（金字塔重排：单测打底 + Testcontainers 验仓储 + MockMvc 验契约）：

效果：110 个用例从 8 分钟降到 40 秒（98% 为单测），CI 每次提交必跑。

踩坑点：① 仓储测试加了 @Transactional 想自动回滚，但其中一段逻辑走 REQUIRES_NEW 新事务——嵌套事务不受外层回滚控制，数据残留导致下一个用例唯一索引冲突：“@Transactional 测试会清理数据”只对同连接生效；② API 测试最初没 mock 库存服务，CI 偶发因依赖服务超时挂掉——集成测试里”不可控外部依赖”必须 mock，”自己的存储”必须真实。

10. 常见误用与陷阱

坑 现象/后果 解法
测试共享可变状态（static 字段/单例被改） 单独跑绿、全量跑红 每用例自建上下文，@BeforeEach 重置
误以为 @Transactional 会清理所有数据 只回滚本连接的 DB 操作，REQUIRES_NEW/Redis/MQ 不回滚 真清理用 @Sql 清表或容器重建
Mock 过度导致测试空心 只断言”调了 mock”，回归零价值 核心逻辑用真实依赖，只 mock 边界
无断言测试 跑了等于没跑，覆盖率假高 断言结果 + verify 关键交互
用例依赖执行顺序 顺序一变全崩 用例相互独立，数据自备自清
时间相关用例不稳定 跨天/时区偶发失败 注入 Clock，测试用固定时钟
断言错误提示文案 改个提示语几十个用例全红 断言错误码等稳定契约
只看行覆盖率 覆盖率达标但边界/异常分支全没测 重点补边界与异常，覆盖率只是底线
