1. 概念说明：为什么需要全链路压测

单机压测的局限：

全链路压测定义：在生产环境（或镜像环境）按真实流量模型打穿整条调用链，找到链路级瓶颈。

核心难点与解决：

难点 解决
压测流量污染生产数据 影子库/流量染色（见 §3）
打爆生产怎么办 限流保护 + 熔断旁路 + 实时监控（见 §4）
流量模型不真实 从线上复制真实流量分布

2. 方案对比

方案 原理 适用
生产镜像环境 复制一套生产（数据+配置），在镜像上压 成本高，容量测算准
流量染色压测（推荐） 压测流量打标记，写入影子库 生产真实链路，成本低
全链路压测平台（Takin/PTS） 平台化：染色+影子库+报告一体 大厂规模化

为什么推荐流量染色：直接在生产打真实链路（网关→服务→DB 全真实走一遍），压测数据通过染色标记路由到影子库——既不污染生产数据，又是最真实的链路。

8. 典型案例：大促前下单链路全链路压测

问题背景：双 11 预估下单峰值 3 倍日常（5000 QPS）。链路：网关 → 订单服务 → 库存服务 → MySQL + Redis + MQ。历史上单机压测全达标，但上一次大促当天 MQ 积压拖垮整条链路。

方案（准备 → 染色压测 → 定位 → 报告）：

踩坑点：① 第一轮压测漏了支付回调服务的染色改造，回调流量写进了生产库——链路上任何一个服务漏染色，数据隔离就前功尽弃，准备阶段必须逐跳验证而不是抽查；② 告警阈值放宽后忘了恢复，第二天值班对真实告警脱敏了一晚上——收尾清单必须包含”恢复告警阈值”。

9. 常见误用与陷阱

坑 现象/后果 解法
染色标记只做 HTTP 层 MQ/定时任务/线程池里标记丢失，影子数据写进生产 ThreadLocal 全链路透传 + 异步显式传递
只压单接口 混合流量下缓存命中率/锁竞争才暴露真实容量 按线上接口比例混合压测
限流阈值未旁路 压测流量被 Sentinel 拦截，压了个寂寞 压测流量旁路放行，保留熔断兜底
无一键停压 积压雪崩时人工逐台关脚本，损失扩大 网关总开关 + 停压演练
告警阈值改了忘恢复 压测后真实故障被静默 收尾固化：停压→清数据→恢复阈值
影子库结构与生产不一致 少建一个索引，容量结论虚高 影子库 DDL 与生产同走 Flyway
压测数据不清理 残留数据污染报表与缓存预热 影子数据带标记，收尾统一清理
无隔离直接打生产用户流量 误伤真实下单 压测账号 + 染色白名单 + 低峰窗口
