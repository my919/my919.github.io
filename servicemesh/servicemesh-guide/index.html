9. 典型案例：Istio 流量治理（灰度发布实战）

问题背景：电商支付服务 payment-svc 从 v1 升级 v2（重构了渠道适配层）。此前用 K8s 原生 Rolling Update 灰度：错误率飙到 4% 时回滚，但此时 v1/v2 Pod 混布，出现”一半用户付款失败”的事故。需要按流量比例 + 按 Header 精准灰度，且失败能秒级回滚。

方案：Istio Ambient 模式 + VirtualService 分级灰度：先内部账号灰度，再按比例放量，全程金丝雀指标自动观测：

阶段 策略 观察指标 回滚手段
内部灰度 Header 精准路由 功能验证、日志 删除 header 规则
小流量 v2 10% 错误率、P99、渠道成功率 VS 权重改回 0
放量 50% → 100% 业务指标（支付成功率） 秒级改权重
全量 v2 100% 持续 24h 观察 保留 v1 镜像 7 天

关键设计：

踩坑点：① 只建了 VirtualService 忘了 DestinationRule 的 subset，路由报 no healthy upstream——subset 必须与 Pod label 严格对应。② 灰度期间 v1/v2 的数据库 schema 不兼容（v2 多写了一列），回滚 v1 后写入报错——schema 变更要向后兼容（加列不删列），应用与 DDL 分开发布。③ Ambient 模式下忘装 waypoint，L7 的 Header 匹配不生效，按权重规则匹配到了 header 规则——L7 精准路由必须给 namespace 挂 waypoint。④ 回滚只改了 VS 权重，但 Envoy 配置未推送（istiod 与 ztunnel 版本不匹配），”秒级回滚”变成 20 分钟——升级 mesh 组件保持版本矩阵一致。

10. 常见误用与陷阱

坑 现象/后果 解法
VS/DestinationRule 脱节 subset 路由报 no healthy upstream subset 与 Pod label 严格核对，Git 单仓管理
schema 不兼容就灰度 回滚 v1 后数据写入报错 DDL 向后兼容（加列不删列），与应用分开发布
L7 路由没挂 waypoint Header 匹配不生效（Ambient） 需要 L7 的 namespace 显式挂 waypoint
熔断阈值过敏感 正常波动触发大面积摘除 基于错误率百分位 + 预热期调参
mTLS 一刀切 STRICT 未注入流量的服务瞬间全断 PERMISSIVE 观察 → 灰度 → STRICT
Sidecar 资源没算够 envoy OOMKill 拖垮业务容器 按连接数/吞吐压测定容，limits 留余量
灰度只看技术指标 错误率 0 但下单转化率掉了 业务指标（转化/成功率）纳入放量门禁
遥测采样 100% 网格自身开销拖垮集群 按服务等级采样，核心链路全采
