7. 典型案例：Helm + ArgoCD 滚动发布上线

问题背景：团队有 20+ 微服务，原来用 kubectl apply 手动部署，存在三个问题：环境配置散乱（dev/staging/prod 各一套 yaml 难维护）、发布靠人工执行易出错、无法回滚。需要用 Helm Chart 管理模板 + ArgoCD GitOps 实现声明式发布与自动回滚。

方案：

组件 作用
Helm Chart 统一模板，多环境用 values 覆盖
ArgoCD 监听 Git，自动同步到集群，漂移检测
HPA 按 CPU 自动扩缩容
PDB 保证发布中最少可用副本

踩坑点：

  1. Helm values 覆盖顺序要理清：-f values.yaml -f values-prod.yaml 后者覆盖前者，list 类型是追加而非替换。同名 key 后者胜出，容易出现”改了没生效”的困惑。
  2. ArgoCD selfHeal 会覆盖手动修改：开启 selfHeal 后，任何 kubectl edit 的改动都会被 ArgoCD 还原。排障时临时改配置要记得先暂停同步。
  3. prune=true 会删除 Git 中已移除的资源：若不小心从 Chart 中删了一个 Service，ArgoCD 会自动删除集群中的 Service，导致服务中断。删除资源前要确认。

8. 常见误用与陷阱

坑 现象/后果 解法
liveness 探针误配导致重启风暴 探针依赖外部服务，抖动触发重启雪崩 liveness 只探应用自身，依赖外部用 readiness
未设资源限制被驱逐 节点资源不足时 Pod 被驱逐 每个容器配 requests + limits；设 PriorityClass
优雅停机未配 preStop 发布时在途请求中断，502 preStop sleep + terminationGracePeriodSeconds
镜像拉取策略错误 latest + Always 重启时拉取失败 固定版本 tag；生产用 IfNotPresent
Helm values 覆盖顺序不清 改了配置不生效 后者覆盖前者，list 追加；用 helm template 验证
ArgoCD selfHeal 覆盖手动改动 排障时改的配置被还原 排障前 argocd app set --sync-policy none
