第十一章：CoAP：REST over UDP 的物联网应用协议

发表于 2026-05-01 更新于 2026-10-29 分类于 嵌入式与机器人 本文字数： 4.5k 阅读时长 ≈ 4 分钟

第十一章：CoAP：REST over UDP 的物联网应用协议

概念基础

  1. CoAP（Constrained Application Protocol，受限应用协议）是给单片机、低带宽网络用的应用层协议：把 Web 的 REST 模型（GET / PUT / POST / DELETE 操作资源）搬到 UDP 之上。
  2. 为什么轻量：报文头仅 4 字节起（对比 HTTP 动辄数百字节），二进制紧凑编码，默认端口 5683 / 5684（DTLS），RAM/Flash 占用极小，可直接跑在 6LoWPAN 等受限链路上。
  3. 请求/响应 + 订阅两种模式：既支持类 HTTP 的请求-响应，又通过 Observe（RFC 7641） 让服务器在资源变化时主动推送 NOTIFY，传感器上报无需反复轮询。
  4. 可靠性自选：UDP 本身不可靠，CoAP 用 CON / NON / ACK / RST 消息类型自己决定要不要确认重传——把「要不要可靠」交给应用按需选择。
  5. 定位：资源型设备（一台设备就是一组可读写的资源）的首选；海量消息汇聚与发布订阅则更适合 Broker 型的 MQTT，二者在同一系统里常互补出现。

一、设计目标

  • 低开销：适合 MCU、6LoWPAN、低带宽链路。
  • 异步：支持 Separate 响应（ACK 先回，结果稍后 CON 通知）。
  • 发现：.well-known/core 资源目录。

默认端口 5683（CoAPS 5684）。

为什么是 UDP 而不是 TCP

维度 TCP UDP + CoAP
连接状态 三次握手、维持连接 无连接，发完即走
头部开销 TCP 20B + IP UDP 8B + IP
休眠友好 唤醒后需重建/保活 醒来直接发，继续睡
拥塞控制 内核自带 CoAP 简单重传 + 指数退避

电池传感器 99.9% 时间在睡觉，TCP 的保活开销在 6LoWPAN 这种 MTU 只有 127 字节的链路上是无法承受之重。

二、报文（简化）

Type 含义
CON 需确认
NON 不需确认
ACK 确认
RST 复位

Code：0.xx 请求（GET=0.01），2.xx 成功，4.xx/5.xx 错误（类比 HTTP）。

头部逐位拆解

  • Token：0~8 字节，客户端生成，响应必须原样带回——用于请求/响应配对与去重（Message ID 管重传，Token 管应用层配对）。
  • Options 增量编码：每个 Option 只存「编号差值 + 长度 + 值」，Uri-Path 拆成多段存（/sensor/temp → 两个 Option），比 HTTP 文本头省一个数量级。
  • 0xFF 载荷分隔符：Payload 前固定一个 0xFF 字节。

四种消息的组合语义

CON 未收到 ACK 时指数退避重传（默认 ACK_TIMEOUT=2s，最多 4 次）。

三、Observe（RFC 7641）

客户端带 Observe Option 订阅资源；服务器在资源变化时 NOTIFY，适合传感器推送，比轮询省流量。

Observe 交互细节

  • 序号（Observe 值）：单调递增，客户端据此丢弃乱序/过期通知。
  • 通知可以是 CON（重要变化，要确认）或 NON（周期心跳）。
  • 取消订阅：发 GET 带 Observe:1，或对 CON 通知回 RST。
  • Max-Age：响应可带有效期，超期客户端应主动重新注册。

五、与 MQTT

CoAP 第十二章：MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例
模型 REST 资源 发布/订阅 Topic
传输 UDP 为主 TCP 常见
代理 CoAP-HTTP 代理 Broker 中心化

物联网选型：资源型设备、LwM2M（基于 CoAP）vs 海量消息经 Broker 的 MQTT。

更深一层的取舍：

  • 拓扑：CoAP 是端到端直连（客户端知道设备在哪）；MQTT 双方都不知对方存在，只认 Broker——NAT 穿透、设备找零配置上 MQTT 更省心。
  • 功耗：CoAP/UDP 无连接保活；MQTT 长连接 TCP 需要 KeepAlive 心跳。
  • 生态：LwM2M（设备管理、固件升级 FOTA）建立在 CoAP 之上，是运营商/NB-IoT 设备管理的事实标准；MQTT 在互联网云平台侧一家独大。
  • 混合架构：设备侧 CoAP + 边缘网关 CoAP→MQTT 桥接，是常见组合。

六、应用

  • 智能抄表、楼宇传感器、Edge 网关 南向 CoAP、北向 HTTP/第十二章：MQTT 详解：发布订阅、QoS 与 mosquitto / Python 示例。
  • 安全：DTLS 预共享密钥或证书；与 第十二章：LoRaWAN：远距离低功耗星型组网 可组合（应用 payload 再解析）。

库：libcoap、aiocoap（Python）、Californium（Java）。

资源发现与 Content-Format

响应用 CoRE Link Format 列出资源及属性。Payload 格式用 Content-Format 编号声明：0=纯文本、50=JSON、60=CBOR（二进制 JSON，受限设备首选）。

调试与常见问题

  • Wireshark：内置 coap 过滤器，可展开 Options、Code、Token。
  • 常见坑：UDP 被运营商/NAT 限制（NB-IoT 场景需确认 APN 允许 UDP）；Token 不复用导致配对错乱；6LoWPAN 分片下大报文丢包率高，Payload 控制在链路 MTU 内。
  • DTLS 握手开销：首次握手数千字节，受限链路建议 PSK 模式或（D）TLS 1.3 会话恢复；证书模式只适合带宽余量大的场景。

本章小结

要点 结论
模型 REST 风格操作资源，类 HTTP 但跑在 UDP 上
开销 头部 4 字节起，二进制紧凑，适合 MCU 与受限网络
可靠性 CON/NON/ACK/RST 自选确认与重传
推送 Observe 订阅-通知，比轮询省流量
安全 DTLS（PSK 或证书），默认端口 5683/5684
