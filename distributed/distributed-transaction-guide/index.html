分布式事务专题：Seata 与最终一致

发表于 2026-09-14 更新于 2026-10-25 分类于 分布式 本文字数： 10k 阅读时长 ≈ 9 分钟

分布式 · 分布式事务

从 0 到生产选型。事务演进与问题 · XA/AT/TCC/SAGA 对比 · Seata 实战 · 可靠消息最终一致 · 对账与补偿。代码带详细注释。

技术栈速查

类别 选型 用途
框架 Seata 2.x 分布式事务
注册中心 Nacos 3.x 配置与发现
消息 Kafka 4.x 最终一致
数据库 MySQL 8.4 事务存储
场景 订单/库存/账户三服务 典型案例

1. 概念说明

为什么需要分布式事务：微服务拆分后，一次下单跨”订单库 + 库存库 + 账户库”三个独立事务——本地事务无法保证一致性。

分布式事务核心指标：

  • 强一致（CP）：所有节点要么全成功要么全失败（XA/AT/TCC）。
  • 最终一致（AP）：先各自提交，通过异步补偿最终一致（SAGA/消息）。

工程共识：互联网业务 90% 用最终一致；只有资金类强约束场景用强一致。能用单库事务绝不分布式。

2. 四种方案对比

方案 原理 一致性 侵入性 性能 适用
XA 数据库原生 2PC 强 低 差（锁久） 老旧系统
AT 代理层生成反向 SQL 强 低 中 Seata 首选
TCC 业务三方法(Try/Confirm/Cancel) 强 高 高 资金/高并发
SAGA 正向+补偿事务 最终 中 高 长流程

2PC 问题（XA 的短板）：协调者单点、同步阻塞（资源锁定）、脑裂时不一致——所以现代方案用 AT/TCC/SAGA 规避。

3. Seata AT 模式实战（自动回滚）

原理：事务拦截器记录前后镜像（undo_log 表），提交时全局协调（TC）确认；失败时用反向 SQL 自动回滚——业务代码几乎零侵入。

5. SAGA 模式（长流程）

适用：跨天/多步骤长流程（旅行预订、审批流）；每步提交后释放资源，只在失败时执行反向补偿。

6. 可靠消息最终一致（最常用）

不用 Seata，用”本地消息表 + 消息队列”实现最终一致——高并发场景首选：

一致性保证链条：本地事务（写库+写表）→ 定时重发（不丢）→ 消费幂等（不重）→ 对账（最终一致）。

7. 选型决策树

8. 典型案例：订单-库存-账户三服务分布式事务

8.1 问题背景

一次下单要跨三个独立服务与数据库：订单服务写 orders、库存服务扣 sku_stock、账户服务扣 account.balance。三个本地事务无法用 @Transactional 统一提交或回滚，必须选择分布式事务方案。团队对 Seata AT 与本地消息表/事务消息做了对比选型。

8.2 两种落地方案对比

维度 Seata AT 模式 本地消息表 / 事务消息
一致性 强一致（TC 协调 + 全局锁） 最终一致（通常秒级，异常时分钟级）
性能 中：undo 镜像 + 全局锁，热点行易瓶颈 高：本地短事务，无跨库锁等待
业务侵入 低：一个 @GlobalTransactional 中：消息表、轮询、幂等、对账都要自建
额外依赖 TC Server + 每库 undo_log MQ + 定时任务 + 对账任务
适用场景 低并发、内部系统、余额/库存要求实时强一致 高并发电商下单，容忍短暂「处理中」状态
失败处理 自动反向 SQL 回滚 消息重试 + 死信 + 对账补偿

结论：下单主链路用本地消息表（高并发最终一致），资金划拨等少数强一致点用 Seata AT。RocketMQ 事务消息可省掉自建 outbox 轮询（半消息 + 事务回查）；本案例用 Kafka + 本地消息表演示完整骨架。

8.3 方案结构（本地消息表）

8.4 完整代码骨架

建表（订单库的消息表与业务表必须同库，才能纳入同一本地事务）：

① 生产端：业务数据与消息同事务写入。

② 轮询投递：至少一次（at-least-once），进程崩溃可重试。

③ 消费端：先占幂等坑，再执行业务。

④ 对账兜底：重试耗尽、消息进死信、消费遗漏时的最后防线。

一致性保证链条：同库事务写业务+消息（不丢）→ 定时重发（可达）→ 消费端幂等（不重）→ 对账（最终收敛）。

8.5 踩坑点

  • 消息表与业务表不同库：无法纳入同一本地事务，写库成功写表失败就会丢消息——outbox 必须与业务共库。
  • 先发消息再写库：业务回滚了消息却已发出，出现「幽灵订单」，库存凭空被扣——严格先写库（含消息表），再异步投递。
  • 消费端不幂等：at-least-once 重试导致重复扣库存、重复扣款——先插入幂等记录再处理，唯一键冲突即跳过。
  • 没有对账：消息进入死信后无人感知，三方数据永久不一致——定时对账 + 死信告警 + 自动补偿。
  • AT 模式热点行：秒杀商品同一行被全局锁串行化，TPS 上不去——热点链路改用本地消息表 / Redis 预扣。
  • AT 中开异步线程：XID 只在同步调用链透传，子线程分支脱离全局事务无法回滚——跨线程显式传播 XID 或改为同步。

9. 常见误用与陷阱

坑 现象/后果 解法
TCC 空回滚 Try 请求因丢包未执行，Cancel 先到，回滚了一笔从不存在的冻结 Cancel 先查 xid/分支记录；不存在则插入空回滚标记后直接返回成功
TCC 悬挂 空回滚后迟到的 Try 才执行，冻结的资源再无人 Confirm/Cancel Try 前检查是否已回滚；存在空回滚标记则拒绝 Try
TCC 三方法不幂等 TC 超时重试 Confirm/Cancel，造成重复扣款 每阶段以 xid+branchId 建唯一记录，已处理直接返回成功
AT 全局锁热点 热点账户/商品行排队等全局锁，吞吐骤降、锁等待超时 热点数据改 TCC 或本地消息表；合并扣减、缩短全局事务
消息重复消费 at-least-once 投递加消费重试，库存/余额被重复扣 消费端 event_id 唯一表幂等，叠加业务状态机与唯一索引
本地消息表无对账 死信/漏消费永久卡单，且无任何告警 定时对账三方数据，死信告警，状态机驱动自动补偿
XID 跨线程/异步丢失 子线程或 MQ 中的分支不加入全局事务，失败无法回滚 同线程同步调用；必须异步时手动传播 XID，或改用最终一致方案
手工修改参与库数据 undo_log 镜像与实际数据不符，AT 回滚失败、脏数据残留 禁止手工 DML；回滚失败查 rollback_info 后人工对账补偿
