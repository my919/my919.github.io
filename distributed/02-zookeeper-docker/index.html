第二章：Docker 部署 ZooKeeper 实践

概念基础

  1. 分布式协调服务：ZooKeeper 为分布式系统提供配置管理、命名服务、分布式锁与选主等基础原语，是 Kafka、Hadoop 等大数据组件的经典协调底座。
  2. 数据模型像文件树：数据组织为 ZNode 树，节点可存少量元数据，客户端可挂 Watcher 监听节点变化，适合读多写少场景。
  3. 一致性与仲裁：基于 ZAB 协议，集群需奇数个节点投票形成多数派（3 节点容忍 1 节点故障），保证强一致。
  4. 为什么用 Docker 部署：官方镜像开箱即用，ZOO_MY_ID、ZOO_SERVERS 等环境变量即可配置单机/集群，/data 与 /datalog 挂卷即完成持久化。
  5. 部署路径：本地开发用 docker run 单容器，自托管服务用 Docker Compose 编排，K8s 环境用清单部署（生产建议 StatefulSet/Operator）。

一、前置条件

本机已安装 docker，并能使用 docker compose（Compose V2 插件，命令为 docker compose；若仍使用旧版独立程序，则将下文中的 docker compose 换成 docker-compose）。

二、ZooKeeper 镜像选择

1. 官方镜像（推荐）

  • 仓库：zookeeper（Docker Hub 官方库：https://hub.docker.com/_/zookeeper/tags）。
  • 常用标签：
    • zookeeper:3.9：3.9.x 线，与多数依赖 3.5+ / 3.6+ 的组件兼容。
    • zookeeper:3.8：仍广泛使用的上一大版本线。
  • 生产建议：固定小版本标签（如 zookeeper:3.9.2）或记录 digest，避免 latest 漂移导致行为变化。

2. 变体说明

需求 说明
单机 / 集群 单机只需 ZOO_MY_ID（常为 1）；多节点需 ZOO_SERVERS 等与 myid 一致的集群配置（见 官方镜像说明）。
客户端端口 默认 2181（ZOO_PORT 可改）。
ARM64（Apple Silicon 等） 官方 zookeeper 多架构镜像一般可直接拉取；若某标签缺架构，换标签或查 Hub OS/ARCH。
极简/定制 社区有 bitnami/zookeeper 等，环境变量名与数据路径与官方不同，切换镜像时需对照该镜像文档。

3. 数据目录与事务日志

镜像默认 ZOO_DATA_DIR（默认 /data）存放数据快照等，ZOO_DATA_LOG_DIR（默认 /datalog）存放事务 log；持久化时建议分别挂载两目录到卷或绑定目录，便于备份与磁盘规划。

1Panel（推荐）：在 Linux 宿主机上若希望少手写命令、仍以 Docker 管理 ZooKeeper，可先安装 1Panel（开源 Linux 运维面板），在 「容器」 中用 Compose 维护与 # 四 一致或等价的编排（镜像选 zookeeper 官方标签、/data 与 /datalog 卷、ZOO_* 与 2181），启停与日志在界面查看；若在 「应用商店」 中能检索到独立 ZooKeeper 亦可一键安装（以面板当前上架为准）。与下文 docker run / Compose / K8s` 对齐或排障时，自 # 三 起各节仍可作对照。适合单台 VPS、家庭服务器等场景。

六、常用环境变量与 JVM 参数

环境变量 默认 说明
ZOO_TICK_TIME 2000 心跳单位（ms），sessionTimeout 协商区间 2~20 × tickTime
ZOO_INIT_LIMIT 10 Follower 初次同步 Leader 允许的最大 tick 数，数据多要调大
ZOO_SYNC_LIMIT 5 运行期 Follower 落后 Leader 的最大 tick 数
ZOO_MAX_CLIENT_CNXNS 60 单 IP 最大连接数，网关/批处理机器易打满
ZOO_AUTOPURGE_SNAPRETAINCOUNT 3 自动清理时保留的快照数
ZOO_AUTOPURGE_PURGEINTERVAL 0 快照清理间隔（小时），不开 autopurge 磁盘必涨
ZOO_4LW_COMMANDS_WHITELIST srvr 四字命令白名单，监控要加 stat,mntr,ruok
JVMFLAGS 镜像默认 -Xmx1G 堆上限；ZK 数据全在内存，堆要大于数据量并留余量

八、上生产前的检查清单

项 说明
节点数 奇数：3 或 5；跨机架 / AZ 摆放
磁盘 /datalog（事务日志）放 SSD，与快照盘分离，降低 fsync 竞争
堆内存 JVMFLAGS=-Xms4G -Xmx4G，以 zk_approximate_data_size 的两倍起步
快照清理 必开 autopurge，否则磁盘写满直接不可用
监控 mntr 指标入 Prometheus（zk_avg_latency、zk_outstanding_requests、zk_server_state）
备份 备份最新 snapshot.* 即含全量数据；事务日志用于时间点恢复
客户端 连接串写全部节点；会话超时与业务健康检查解耦

本章小结

项 说明
前置 已安装 docker 与 docker compose（或 docker-compose）
镜像 优先官方 zookeeper:3.9 / 固定补丁标签；单机 ZOO_MY_ID=1
单容器 mkdir 后一条 docker run ...（挂载 /data 与 /datalog）
Compose 保存 docker-compose.zookeeper.yml 后 docker compose -f ... up -d
Kubernetes 保存 zookeeper-k8s.yaml 后 kubectl apply -f ...
集群 3 节点 ensemble：ZOO_MY_ID ↔ ZOO_SERVERS 的 server.N 对应；2888/3888 只在集群内部用
生产 奇数节点、autopurge 必开、mntr 入监控

生产环境请配置 ACL / TLS、监控与备份；与 Kafka 同栈时保持 zookeeper 版本与 Kafka 发行说明中的兼容性要求。

部署跑通后回到语义细节：第一章：ZooKeeper 核心概念与 CLI 实战 覆盖 ZNode、Watcher 与锁/选主配方；实际连接用 zkCli.sh -server 127.0.0.1:2181 验证。
