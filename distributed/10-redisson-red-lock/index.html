第十章：Redisson 红锁 RedLock 原理与生产实践

发表于 2026-05-05 更新于 2026-10-25 分类于 分布式 本文字数： 5.6k 阅读时长 ≈ 5 分钟

第十章：Redisson 红锁 RedLock 原理与生产实践

概念基础

  1. 要解决的问题：普通 Redis 锁是单主节点锁——加锁成功后尚未同步到从节点就宕机，主从切换后锁凭空消失，两个客户端可能同时持锁。
  2. 核心思想：把锁同时写到 N 个完全独立的 Redis 主节点上，过半节点加锁成功且总耗时小于锁有效期才算加锁成功。
  3. 为什么有效：基于**多数派（quorum）**机制，任一节点宕机/切换都不影响多数节点上的锁记录，从根本上规避单点故障丢锁。
  4. 代价：要写多个节点，性能低于普通锁；节点必须相互独立（非主从、非集群）且为奇数个。
  5. 适用边界：秒杀、库存、支付、账务等核心强一致场景用 RedLock；后台任务等非核心场景普通 Redisson 锁即可。

最标准、生产可直接用的 Redisson RedLock 实现，包含：配置 + 代码 + 原理 + 生产注意事项

一、先记住一句话

RedLock = 多个独立 Redis 主节点 + 过半写入成功才算加锁成功
目的：彻底解决主从切换丢锁问题
代价：写 N 个节点 + 严格多数派判定，部署与性能成本都高于单节点锁。

二、先懂普通 RLock：可重入与看门狗的实现

RedLock 是架在单节点 RLock 之上的组合，先看清 RLock 在 Redis 里的形态：

  • 加锁：一段 Lua 脚本——Hash 不存在则 HSET + PEXPIRE 新建；已存在且 field 是本线程则 HINCRBY 重入并刷新过期；否则 PTTL 返回剩余存活时间，客户端据此自旋等待。三段逻辑一次往返、原子执行。
  • 解锁：同样是 Lua——HINCRBY -1，归零才真正 DEL；不是自己的锁返回 nil，Java 侧抛 IllegalMonitorStateException。
  • 看门狗：不显式传 leaseTime 时，加锁成功即注册定时任务（默认 30s / 3 = 10s 一次）执行续期；进程死亡 → 续期消失 → 锁到期自然释放。

为什么 RedLock 要逐节点续期：红锁对 N 个节点各持一把 RLock，任一节点上的锁过期而未续约，多数派就可能凑不齐——看门狗按节点独立工作，与红锁的过半判定互不影响。

三、环境要求

  1. 至少 3 个独立的 Redis 主节点（无主从、无集群、互相独立）
  2. Redisson 版本 >= 3.5.0
  3. SpringBoot / Java 项目均可

节点部署建议：3 台独立物理机/虚机、同机房；不要把节点配成主从或集群——那会让「独立多数派」前提直接失效。

六、RedLock 代码使用（生产标准写法）

RedissonRedLock 继承自 RedissonMultiLock，只是把成功判定从「全部」改为「过半」；
任一节点加锁失败会自动回滚已成功的节点，不会留下「半个锁」。

七、RedLock 加锁成功规则（必须记住）

3个节点：
必须 ≥ 2 个节点加锁成功 + 加锁耗时 < 锁超时时间
才算加锁成功。

5个节点：
必须 ≥ 3 个节点加锁成功

为什么要把「耗时」算进去：客户端向 N 个节点顺序加锁，若网络慢导致总耗时逼近锁有效期，最后一把锁拿到时，前面节点的锁可能已临近过期——有效持锁时间 = leaseTime − 加锁总耗时 − 时钟漂移余量。这就是 Redisson 在 tryLock 内部做耗时校验、不达标即整体放弃并回滚已加节点的原因。

八、RedLock 看门狗（自动续期）生效吗？

生效！

RedLock 会对每个节点的锁自动续期。
只要过半节点存活，锁就不会失效。

九、RedLock 之争：Kleppmann 与 Antirez 各说了什么

2016 年 Martin Kleppmann（DDIA 作者）发文质疑 RedLock，Antirez（Redis 作者）逐条反驳。要点各取一瓢：

质疑（Kleppmann） 反驳（Antirez） 工程结论
GC 停顿 / 网络延迟可让客户端拿着「已过期的锁」继续写 加锁耗时计入校验：耗时 > 有效期就主动放弃 反驳成立但不彻底——停顿发生在「拿锁之后、写之前」依然危险
时钟跳变（NTP 大步校时）可能让锁提前过期 运维应保证时钟稳定，崩溃节奏可控 生产盯 NTP（用渐进校时），并监控节点时钟漂移
缺 fencing token，挡不住「过期后继续写」 （未正面解决） 金融级写入：锁 + fencing token 下沉到存储层校验，缺一不可

适用边界（比「必须用 / 不能用」更有用）：

  • 按目的选型：防并发冲缓存、防任务重复调度 → RedLock 够用；账户余额这类错一次就赔钱的写入 → 锁 + fencing token，或改用 ZK/DB 强一致方案；
  • 节点跨机房部署时网络分区概率上升，多数派假设更脆弱——同机房独立物理机/虚机是更稳的落法。

十、MultiLock：容易和 RedLock 搞混的「联锁」

RedissonMultiLock 与 RedissonRedLock 都是 RLock 的组合体，差异只在判定规则：

MultiLock（联锁） RedLock（红锁）
成功条件 全部锁都拿到才算成功 过半节点拿到即成功
典型场景 一个客户端要同时锁住多个资源（同时锁 A、B 两个账户做转账） 同一资源跨多个独立节点抗单点
节点要求 锁可来自同一或不同实例 必须是多个独立 Master

转账这类「多资源同锁」还有个更朴素的解法：按账户 ID 排序后逐个加锁，用确定性顺序消灭死锁环。

十一、生产使用注意事项（非常重要）

1. 必须使用 奇数个节点

3、5、7 个，不能用 2、4、6 个。

2. 节点之间完全独立

不能是主从、不能是集群，必须是独立 Master。

3. 性能比普通锁低

因为要写多个 Redis，高并发秒杀可以接受。

4. 核心业务才用 RedLock

  • 秒杀、库存、订单、支付、账务 → 用 RedLock
  • 后台任务、非核心 → 普通锁即可

5. 不要把 leaseTime 设置太长

默认 30s 足够，看门狗会自动续期。

6. 监控 GC 与时钟

  • Full GC 长停顿是「持锁者假死」的头号来源：换 ZGC/Shenandoah 或合理设堆，把停顿压到秒级以下；
  • NTP 用渐进校时（chrony 或 ntpd -x），避免大步跳变让锁提前过期；
  • 加锁日志里记录实际耗时，逼近 leaseTime 即告警——这是「争议」一节耗时校验的落地。

十二、最终结论

RedLock 是生产上唯一能彻底解决 Redis 主从丢锁的方案
金融、电商、支付、秒杀必须使用！

一句话划界：为效率用 RedLock，为资产安全用「锁 + fencing token」。

本章小结

要点 结论
本质 多个独立 Redis 主节点 + 过半写入成功才算加锁成功
节点要求 至少 3 个、奇数个、完全独立的 Master（非主从非集群）
成功规则 过半节点加锁成功 且 加锁耗时 < 锁有效期
看门狗 生效，对每个节点的锁自动续期
RLock 底座 Hash 存 <UUID:threadId, 重入次数>，Lua 原子加解锁
争议 Kleppmann：GC/时钟/fencing 三连；结论=核心写入加 fencing token
MultiLock 联锁=全部成功才算成，用于同时锁多资源；勿与红锁混淆
价值 生产上彻底解决 Redis 主从切换丢锁，核心业务必用
