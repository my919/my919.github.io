3. 错误处理

Rust 用 Result<T, E> 表达可恢复错误，? 运算符向上传播；Option<T> 表达「可能没有」。生态双雄：thiserror 用 derive 宏定义领域错误类型（#[error("...")] + #[from] 自动转换），适合库；anyhow 用 Context 随手附加上下文、快速原型，适合应用层。

自定义错误类型的手写 impl、panic 的边界场景：深入了解：第二章：Rust 并发与错误处理

4. 异步编程（Tokio）

8. 典型案例：所有权实战——订单管道从 clone 泛滥到零拷贝

问题背景：订单处理服务的初版代码为了「过编译」到处 .clone()：压测下内存占用翻倍、P99 延迟高 40%。根因是没有想清楚「谁拥有数据、谁只是借用」，clone 掩盖了所有权设计问题。

踩坑点：

  • 为过编译滥用 clone：编译器报借用的地方，多数是数据流设计问题；先分清「借用 / 转移 / owned」再动手。
  • 试图返回函数内局部变量的引用：悬垂引用编译期直接拒绝，改返回 owned 值。
  • struct 字段到处挂引用导致生命周期标注满天飞：绝大多数业务代码持有 owned 数据（String/Vec）更简单。

9. 常见误用与陷阱

坑 现象/后果 解法
返回局部变量的引用 编译错误 cannot return reference to local 返回 owned（String/Vec）或让调用方传入缓冲
clone 滥用 内存翻倍、性能劣化，设计问题被掩盖 借用 &T / move 转移 / Cow 按需拷贝
认为 &mut 与 & 可共存 E0502 编译拒绝（同时可变+不可变借用） 先完成读再改；利用 NLL 缩小借用作用域
Rc<RefCell> 循环引用 内存永不释放 环的一侧用 Weak，升级前判空
热路径 unwrap() None/Err 直接 panic 打崩服务 ? 传播 / ok_or 转 Result / expect 带说明
String 与 &str 混淆 函数签名处处类型不匹配 参数用 &str，结构体字段与返回值用 String
乱标 ‘static 试图”解决”生命周期 编译不过：生命周期是引用关系的描述 先改数据流（返回 owned），再谈标注
