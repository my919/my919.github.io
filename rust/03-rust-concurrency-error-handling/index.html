第三章：Rust 并发与错误处理

发表于 2026-09-02 更新于 2026-10-25 分类于 Rust 语言 本文字数： 11k 阅读时长 ≈ 10 分钟

第三章：Rust 并发与错误处理

概念基础

  1. Fearless Concurrency：所有权 + Send/Sync 在编译期阻止数据竞争，称「无畏并发」——多线程代码能编译过，基本就不会有数据竞争。
  2. Send/Sync marker trait：Send 允许跨线程转移所有权，Sync 允许跨线程共享 &T；编译器自动判定，Rc 非 Send、Mutex 内的值变 Sync。
  3. 所有权防数据竞争：多线程共享可变必须经 Arc+Mutex，裸共享 &mut 会被编译器拒绝。
  4. Result/Option 错误模型：可恢复用 Result<T, E>，不可恢复用 panic!；无异常机制，错误是值。
  5. ? 运算符：错误传播语法糖，遇到 Err 提前返回、Ok 取值继续，替代手写 match 层层传播。

本章聚焦并发与错误处理。所有权与基础语法见 第一章：Rust 入门与所有权系统；类型系统与 trait 见 第二章：Rust 类型系统与 trait；工程实践见 第四章：Rust 工程实践与 Web 开发。

二、迭代器与闭包

1. 迭代器

迭代器实现 Iterator trait，惰性：只在被消费时才求值，零成本抽象（编译为高效循环）。

自定义迭代器：实现 Iterator trait 的 next 方法即可，编译器自动适配 map/filter/collect 等所有方法。

2. 闭包

闭包是「可捕获环境的匿名函数」，三种捕获方式由推断决定：

闭包 trait：FnOnce（可消耗捕获值，只能调一次）、FnMut（可变借用）、Fn（不可变借用，可多次调）。按「最强需求」实现，按「最弱约束」接收。

4. panic 与不该 panic 的场景

四、Send/Sync 深入

Send：类型可跨线程转移所有权；Sync：&T 可跨线程共享（即 T 可安全被多线程读）。Arc<T> 要求 T: Sync + Send。

判定规则：

  • Rc<T> 非 Send（引用计数非原子），不能跨线程。
  • Mutex<T> 使 T 满足 Sync（加锁后可安全共享可变）。
  • RefCell<T> 非 Sync（运行期借用检查非线程安全）。
  • 裸指针 *const T/*mut T 既非 Send 也非 Sync。

边界速查（T: Send 且 T: Sync 才能「Arc<T> 多线程共享可变」）：

类型 Send Sync 原因
i32/String/Vec<T> ✅ ✅ 拥有数据，无内部可变性
&T（T: Sync） ✅ ✅ 只读引用共享安全
&mut T（T: Send） ✅ ❌ 可变引用只能独占，不能共享
Cell<T>/RefCell<T> ✅ ❌ 内部可变性无线程安全检查
Rc<T> ❌ ❌ 引用计数非原子
Arc<T>（T: Send+Sync） ✅ ✅ 原子引用计数
Mutex<T>/RwLock<T>（T: Send） ✅ ✅ 锁提供线程安全的内部可变性

这两个 trait 是 unsafe auto trait：编译器为绝大多数类型自动推导，手写 unsafe impl Send for X 等于你向编译器担保线程安全——只有封装 FFI/裸指针时才需要，写错即 UB。

五、Mutex/RwLock/Arc

RwLock 用于读多写少（多个读锁或一个写锁）；单线程内 Rc/RefCell 对应 Arc/Mutex。read() 返回多个只读锁，write() 独占写锁。

锁中毒（poisoning）：持锁线程 panic 后，Mutex 进入中毒态，后续 lock() 返回 Err(PoisonError)——这是 std 故意的设计（锁保护的数据可能处于不一致中间态）。实战对策：

死锁防御：① 固定全局加锁顺序；② 锁粒度最小化，持锁期间不做 IO、不调用未知回调；③ 能用消息传递（channel）就不用共享锁。

六、channel 消息传递

1. std mpsc

2. crossbeam-channel

crossbeam crate 提供多生产者多消费者（MPMC）、有界/无界 channel，接收端可 clone（std mpsc 不行），性能优于 std mpsc：

背压（backpressure）用 bounded(n)：下游慢时发送方自然降速，防内存撑爆；unbounded 只用于确认流量有界的内部管线。消息传递适合线程间通信；共享可变适合细粒度状态。Erlang/Go 偏消息传递，Rust 两者皆可。

七、async/await 与 Tokio 入门

async fn 返回 Future（惰性，不 await 不执行），.await 挂起让出执行权。std 只提供 Future 抽象，运行时需第三方——最常用 Tokio（多线程工作窃取调度器 + IO 驱动 + 定时器）：

场景 工具
并发等待多个 Future（同任务内） tokio::join!
派生独立后台任务 tokio::spawn（’static + Send）
超时/竞速 tokio::select! / tokio::time::timeout
async 版 channel tokio::sync::mpsc（std mpsc 不能 .await）
async 版互斥锁 tokio::sync::Mutex（可跨 .await 持有）

关键纪律：持 std MutexGuard 跨 .await 会死锁（挂起时不放锁）——async 里要么缩小持锁范围，要么换 tokio::sync::Mutex。CPU 密集活别塞进 async 任务，用 tokio::task::spawn_blocking 或 rayon。

rayon 数据并行：把顺序迭代器变并行，零配置利用多核：

async 适合高并发 IO（大量连接等待），CPU 密集仍用线程或 rayon——两者可共存：Tokio 管网络 IO，rayon 管计算热区。

常见避坑

场景 错误 正确做法
Rc 跨线程 thread::spawn(move || rc) → 非 Send 编译错误 改用 Arc
裸 &mut 共享 多线程同时持 &mut → 借用检查拒绝 用 Arc<Mutex<T>>
忘记 drop(tx) mpsc 的 rx 迭代永不结束 关闭所有发送端或用 into_iter
Mutex 死锁 加锁顺序不一致互相等待 固定加锁顺序，或用 parking_lot 防中毒
unwrap 锁中毒 lock().unwrap() 在持锁线程 panic 后 → panic 用 match 处理 PoisonError 或 parking_lot
RefCell 跨线程 RefCell<T> 非 Sync 换 Mutex<T> 或 RwLock<T>
迭代器未消费 v.iter().map(...) 不执行 → 惰性 加 .collect()/for 消费
闭包 move 时机 需转移所有权却未 move → 借用过期 加 move 关键字
unwrap 遇 Err result.unwrap() panic 用 ?/match/unwrap_or
async 无运行时 async fn 直接调用 → Future 不执行 #[tokio::main] 或 block_on

本章小结

要点 结论
集合 Vec/HashMap 常用；BTreeMap 有序，HashSet 去重
迭代器 实现 Iterator，惰性零成本，map/filter/collect 链式
闭包 Fn/FnMut/FnOnce，move 转移捕获环境
错误模型 Result 可恢复、panic! 不可恢复；? 传播
自定义错误 枚举收拢失败模式 + Display/Error/From；库用 thiserror、应用用 anyhow
Send/Sync Send 跨线程转移，Sync 跨线程共享 &T；Rc 双非、Arc+Mutex 双全
