3. Nginx-RTMP 方案（备选）

结论先行：nginx-rtmp-module（arut/nginx-rtmp-module）最后一个正式版本是 2019 年的 1.2.2，之后基本停更，HLS 的 bug 与安全问题无人修。新项目优先 SRS 或 MediaMTX；只有在「公司已深度使用 Nginx、只需要 RTMP → HLS 这一条链路」时才选它。

能力 SRS 6 nginx-rtmp MediaMTX
维护状态 活跃 2019 年后停更 活跃
协议 RTMP / HTTP-FLV / HLS / WebRTC / SRT RTMP / HLS / DASH RTMP / HLS / WebRTC / SRT

3.1 编译安装（模块不在 Nginx 官方包里）

不要用发行版的 nginx 包 + 动态模块：load_module 要求模块与 nginx 二进制由同一份源码、同一编译参数生成，版本稍有不符就会启动失败，排查成本高于直接静态编译。

3.2 完整 nginx.conf

hls_nested on 之后播放地址是 http://live.example.com/hls/<流名>/index.m3u8——远程那篇 2019 笔记里的 /live/test/index.m3u8 正是这个结构。

3.3 目录、权限与状态页资源

不要沿用笔记里的 chmod 777 /tmp/hls：任何本地用户都能改写切片，等于把直播内容交给全机器。权限只需保证 worker 用户可写。

3.5 三个必须配的安全项

项 不配的后果 配置
deny play all 任何人可绕过 HLS 直接拉 RTMP 原始流 在 application 内声明，播放只走 /hls/
on_publish 回调 推流地址泄漏后被人顶替推流 业务服务校验 token、流名归属，失败返回 403
/stat 访问控制 流名、客户端 IP、在线人数全部公开 allow 内网段 + deny all，或加 Basic Auth

3.6 本节专属坑

  • 回调超时：on_publish 默认通知超时很短，业务服务一旦慢查询就会把正常推流拒掉；回调里只做轻量校验（查 Redis / 本地缓存），不要查大表。
  • 录制文件永不清理：hls_cleanup 只清 ts，不清 record 目录，录制必须另配定时清理或对象存储转存。
  • 切片时长与 GOP 不匹配：推流端 -g 大于 hls_fragment 时，切片会被迫对齐关键帧，配置的 2s 实际变成 4s。
  • 模块停更风险：新内核 / 新 Nginx 版本下编译失败或 HLS 行为异常时，社区基本不会再修；这是选 SRS 的主要理由。

4. HLS 直播（浏览器原生播放）

SRS 默认把 RTMP 流转封装为 HLS，无需额外配置：

HLS 原理：直播流切成 4-6 秒的 .ts 分片 + m3u8 播放列表（索引），播放器逐片拉取。延迟 = 切片时长 + 列表缓冲。

降低延迟：-hls_time 2（切 2 秒片）+ 播放器 lowLatencyMode。

5. 多码率转码（自适应）

观众带宽不同 → 服务器转出多档码率，播放器自动切换（ABR）。

生产注意：转码是 CPU/GPU 密集——用硬件编码（NVENC/QuickSync）、转码集群化，或只用 SRS 专业版/云转码。

现象 原因与解决

10. 典型案例：HLS 直播延迟从 12s 优化到 3s

问题背景：带货直播用标准 HLS（6s 切片 × 播放器缓冲 3 片 + CDN 缓存 60s），主播喊”3、2、1 上链接”后观众要 12 秒才看到，互动场直接冷场。

方案：四层压缩延迟——推流端 GOP 对齐切片 → 服务端 2s 切片 → 播放器 lowLatencyMode + 只缓冲 1-2 片 + 超限追帧 → CDN 分级缓存（m3u8 不缓存、ts 长缓存）。

踩坑点：

  • hls_fragment 盲目压到 0.5s：切片数暴涨，CDN 请求量翻 4 倍，回源把源站打死——2s 是平衡点。
  • m3u8 被 CDN 缓存 60s：观众永远落后一分钟且刷新无用，m3u8 必须 no-cache 或 1-2s 微缓存。
  • 主播端编码器 GOP 设 4s、切片 2s：切片被迫对齐 GOP 变成 4s，服务端配置全白改——推流端 GOP ≤ 切片时长。
  • 延迟优化不是免费的：缓冲越浅，弱网观众越容易卡顿——自适应降码率优先保流畅。

11. 常见误用与陷阱

坑 现象/后果 解法
切片越短延迟越低 0.5s 切片请求风暴，源站/CDN 率先崩溃 2s 起步；优化顺序：切片 > 缓冲 > 追帧
m3u8 配长缓存 观众集体落后且不收敛，刷新也没用 m3u8 no-cache（或 1-2s 微缓存），ts 才长缓存
GOP 与切片不对齐 切片实际时长翻倍，配置的延迟没生效 推流端 GOP ≤ hls_fragment + hls_wait_keyframe on
lowLatencyMode 万能论 源站不支持 LL-HLS，开了没效果也不报错 服务端（SRS/NGINX-hls）与播放器同时支持才生效
ts 不做鉴权 m3u8 带 token 但 ts 裸奔，盗链照样白嫖带宽 ts 请求同样校验 token/referer，或用临时签名 URL
只压延迟不管追帧 网络抖一下延迟累积到几十秒 liveMaxLatencyDuration 强制跳到直播边缘
