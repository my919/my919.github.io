1. 概念说明

视频 = 连续图像帧 + 音频，通过**编码（Codec）**压缩存储。三个核心概念：

  • 编码标准：H.264（兼容性最好）、H.265/HEVC（同画质省 50% 码率）、AV1（新一代开源，省更多但编码慢）、VP9。
  • 封装格式（Container）：MP4（通用）、MKV（多轨）、WebM（网页）。编码与封装独立组合：H.264 视频 + AAC 音频 → MP4。
  • 关键参数：分辨率（1080p）、帧率（fps）、码率（bitrate，决定画质与体积）、GOP（关键帧间隔）。

转码为什么重要：源视频（如手机 4K）码率高、格式杂，服务端需统一转成 H.264/AAC + MP4 便于全端播放；按分辨率出多档（1080p/720p/480p）做自适应。

8. 编码选型决策

场景 推荐
全端兼容（Web/移动） H.264 + AAC + MP4
存储成本优先 H.265 / AV1
实时直播 H.264（低延迟）

9. 典型案例：UGC 短视频上传转码管线

问题背景：App 允许用户上传 60s 竖屏视频，手机端拍出的码率/分辨率五花八门，Web 端播放常卡在加载；个别 4K 素材直接把转码机 CPU 打满，整个服务雪崩。

方案：上传后先 ffprobe 摸底 → Celery 队列限并发异步转码 → 转出 720p/480p 两档 HLS + 封面抽帧 → 对象存储托管，mp4 兜底输出加 -movflags +faststart 保证秒开。

踩坑点：

  • 忘加 -movflags +faststart：moov box 在文件尾，浏览器必须全量下载才能播，”卡在加载”多半是它。
  • 上传接口里同步转码：请求超时、用户重传、机器打满三连——转码必须丢队列异步做。
  • worker_concurrency 不限：10 个 4K 任务并行把 CPU 顶满，所有任务互相拖死。
  • 竖屏视频用 scale=1280:-2 写死宽度：画面被裁成横条——用 scale=-2:{height} 按高度缩放。
  • 任务不幂等：重试时 ffprobe 阶段源文件已被清理直接报错——重试前先检查产物是否存在。

10. 常见误用与陷阱

坑 现象/后果 解法
CRF 与 b:v 混用 同一条命令两者都给，码率控制精神分裂 画质优先 CRF（18-28），带宽优先 b:v + maxrate，二选一
-ss 放在 -i 之后 逐帧解码到目标点，1 小时素材剪个头等 5 分钟 快剪把 -ss 放 -i 前；需关键帧对齐再放后面
音画不同步 剪辑后声音慢半拍 视频 -ss 与音频偏移成对处理，或用全局 -ss
转码丢失旋转信息 手机竖拍视频转出来横躺 用新版 ffmpeg 自动读取 side data，避免旧版硬转
队列无并发限制 CPU 打满，转码时长反超视频时长 worker_concurrency=2~4，大素材单独低优队列
全档位无脑转 4K 源只有 720p 却转 1080p，白白浪费算力 按 ffprobe 源分辨率封顶转码阶梯
