1. 概念说明

**领域驱动设计（DDD, Domain-Driven Design）**是一套应对复杂业务的方法论，核心思想：让软件模型与业务语言保持一致。业务专家和开发用同一种语言（通用语言）沟通，软件结构围绕领域模型而非技术框架设计。

DDD 解决什么问题：业务逻辑复杂时，按”数据库表/技术分层”组织代码会导致业务规则散落各处、改一处坏一片。DDD 把业务规则收敛到领域层，让代码可读、可维护、可演进。

两大阶段：

  • 战略设计：先划清业务边界（限界上下文），确定系统间的协作方式。
  • 战术设计：在边界内设计聚合、实体、值对象、领域服务、仓储等模型要素。

2. 核心概念速查

概念 说明 示例
通用语言 业务与代码共用词汇 “下单””支付””取消订单”
限界上下文 业务边界，每个上下文一个模型 订单上下文、库存上下文
聚合 一组内聚对象，聚合根是唯一入口 订单（含订单项）
聚合根 聚合的根实体，外部只能通过它操作 Order
实体 有唯一标识、可变化的对象 User、Order
值对象 无标识、不可变、描述性对象 Money、Address
领域服务 不属于某个实体的业务动作 订单超时关单服务
仓储 聚合的存取接口，屏蔽持久化细节 OrderRepository
领域事件 领域内发生的事实 OrderCreatedEvent

7. 常见误区（避坑）

误区 正确做法
把 DDD 当技术框架 DDD 是设计方法，不绑定任何框架
所有模块都用 DDD 核心业务用 DDD，简单 CRUD 用普通分层
贫血模型（只有 getter/setter） 业务方法放在聚合内，拒绝贫血模型
大聚合（一个聚合管所有） 聚合越小越好，跨聚合用领域事件解耦
仓储就是 DAO 仓储面向聚合，粒度大于 DAO

8. 落地节奏建议

  1. 先事件风暴：与业务方梳理关键流程（半天到一天）
  2. 划分限界上下文：定出上下文地图与依赖关系
  3. 建模核心上下文：识别聚合、实体、值对象
  4. 分层落地：先领域层 + 单测，再接 Spring 基础设施
  5. 演进：聚合边界随业务变化调整，保持通用语言同步更新

9. 典型案例：聚合边界划分实战

问题背景：电商团队最初把「订单 + 库存 + 物流」塞进一个巨型 Order 聚合：下单时一次事务改三张主表，秒杀期间数据库行锁冲突频发；改一个收货地址也要加载全部商品明细。需要重新划分聚合边界。

方案：按「是否必须在同一事务内保持一致」重新切分——聚合间用领域事件解耦：

聚合 职责 一致性 事件
Order 订单项、金额、状态机 聚合内强一致 OrderCreated / OrderCancelled
Inventory 库存数量、占用/释放 聚合内强一致 StockDeducted / StockInsufficient
Shipment 发货单、物流轨迹 聚合内强一致 ShipmentCreated

踩坑点：第一次拆分时把「扣库存」放进了 Order.cancel() 的事务里同步调用库存服务——网络抖动导致订单取消频繁失败。正确姿势是事件驱动：订单先落库，库存消费事件异步释放，失败重投 + 对账兜底。另外注意事件不要携带整个聚合快照，只带 ID 和最小字段，否则消费方会把事件当成 RPC 响应来用，边界又糊了。

10. 常见误用与陷阱

坑 现象/后果 解法
贫血模型假 DDD 包名叫 domain，实体只有 getter/setter，规则全在 Service 业务方法下沉到聚合，Service 只编排
聚合过大 一个事务改 N 张表、加载慢、并发冲突多 按”同事务必须一致”切最小聚合
跨聚合事务 一个事务同时改 Order 和 Inventory 聚合间用领域事件最终一致
仓储当 DAO 用 findByUserIdAndStatus(...) 一堆查询方法 仓储只暴露按聚合根取存，查询走 CQRS
值对象加 setter Money.setAmount() 破坏不可变性 值对象全 final，变更返回新对象
领域事件带全量状态 事件变成”分布式大对象”，消费方依赖发布方模型 事件只带 ID + 最小字段
分层反向依赖 Domain 里 import MyBatis/Spring 注解 依赖倒置 + ArchUnit 守护
所有模块强上 DDD 简单 CRUD 也建聚合/仓储，代码量翻倍 按业务复杂度分级，CRUD 用普通三层
