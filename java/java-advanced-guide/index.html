9. 典型案例：百万级订单报表统计（Stream 大数据量优化）

问题背景：每日跑批统计 300 万条订单的”按省份汇总金额”。初版实现 orderMapper.selectListAll() 一次性加载全部实体到内存（OOM 频发），循环里再按订单逐条查商户名（N+1 查询，DB QPS 打满），累计金额用 Long 装箱累加，全任务耗时 40 分钟。

方案（分批读取 + 一次遍历聚合 + 原始类型流）：

优化点 前 后
数据读取 selectListAll 全量 4GB 游标分批 5000 条/批
商户名 循环内逐条查（N+1） 批内 id 集合一次性 in 查询预取
累加 Stream<Long> 装箱 mapToLong 原始类型
遍历次数 多轮 filter/分组 单次 collect groupingBy 完成

踩坑点：

  1. 处理慢时顺手改成 parallelStream()——但聚合里对共享 HashMap 做了写操作，跑出丢数据；并行流要么用 collect 的组合器，要么别碰共享可变状态。
  2. parallelStream 默认跑在公共 ForkJoinPool 上，批处理里再发起 DB 查询会把公共池占满，Web 请求跟着卡——IO 密集任务别用并行流，或提交到自建线程池。
  3. map(o -> o.amount()).reduce(0L, Long::sum) 全程装箱，300 万条产生海量 Long 对象——mapToLong + 原始类型流。
  4. 优化只盯 CPU，忘了 N+1 才是大头——先看监控里的 DB QPS，再决定优化方向。

10. 常见误用与陷阱

坑 现象/后果 解法
误解 Collectors.toUnmodifiableList 之后 add 直接 UnsupportedOperationException 需要可变集合用 toCollection(ArrayList::new)
toMap 不写 merge 函数 key 重复抛 IllegalStateException toMap(k, v, (a, b) -> a) 指定合并策略
parallelStream 里修改共享集合 丢元素/ConcurrentModificationException 用 collect 收集器，或 ConcurrentHashMap 等并发容器
SimpleDateFormat 静态共享 多线程日期错乱/NumberFormatException 换线程安全的 DateTimeFormatter（java.time）
Optional.get() 裸调用 空值抛 NoSuchElementException orElse / orElseGet / orElseThrow 兜底
Optional 用作字段或方法参数 反序列化失败、API 语义污染 Optional 只做返回值类型
流被复用 IllegalStateException: already operated upon 每次从源集合重新 stream()
大数据量 toList() 全收集 内存峰值高，容易 OOM 边读边聚合（groupingBy/reduce），或分批处理
