第三章：Java 泛型符号与通配符实战

概念基础

泛型（Generics） 是 JDK 5 引入的参数化类型机制，示例代码直接复制即可运行，覆盖常用泛型符号：

  1. 为什么需要泛型：避免 Object 强转与 ClassCastException 风险，让类型检查提前到编译期，集合存取更安全、可读性更好。
  2. 字母约定：T（Type 通用类型）、E（Element 集合元素）、K / V（Key / Value 键值对）、U（第二个泛型参数）。
  3. 通配符 ?：表示未知类型；? extends 限定上界（只读）、? super 限定下界（可写），对应 PECS 原则（Producer Extends, Consumer Super）。
  4. 泛型方法与多限定：<T> 声明方法级泛型；T extends A & B 用 & 要求同时满足多个接口约束。
  5. 类型擦除：泛型信息只在编译期存在，运行时统一擦除为 Object，因此不能 new T()、不能用 T.class。

PECS = Producer Extends, Consumer Super：集合往外给数据（生产者）用 ? extends；往里收数据（消费者）用 ? super。经典案例是 Collections.copy 的签名：

6. 类型擦除与桥接方法

泛型信息只在编译期存在，编译后全部被擦除：

擦除规则：无界泛型 → Object；T extends Number → Number。由此带来三类限制：

限制 原因
不能 new T() / T.class 运行时无 T 的具体类型
不能 instanceof List<String> 运行时只剩 List
不能重载 foo(List<String>) 与 foo(List<Integer>) 擦除后签名相同

桥接方法（bridge method）：实现泛型接口/继承泛型类时，编译器自动合成一个擦除签名方法，把调用转发到真正的实现，保证多态正确：

桥接方法解释了「泛型擦除了为什么多态还工作」；也解释了泛型类里 getMethods() 偶尔冒出同名方法的诡异现象。

7. 泛型与数组协变对比

数组是协变的（Integer[] 是 Number[] 的子类型），泛型不是（List<Integer> 与 List<Number> 无继承关系）——这正是通配符存在的原因：

设计教训：数组把错误推迟到运行期，泛型把错误挡在编译期——能用集合就别用数组（Effective Java 第 28 条）。混用时的硬规则：不能创建泛型数组（new List<String>[10] 编译不过），变通方案是 List<List<String>> 或 @SuppressWarnings("unchecked") 加 Array.newInstance。

注意事项：

  • 只能读声明处的泛型（父类、字段、方法签名）；new ArrayList<String>() 的实参在局部变量上彻底擦除，读不到。
  • 匿名子类技巧：new TypeReference<List<User>>() {}（Jackson/Fastjson）利用的正是「匿名类继承带泛型实参的父类」这一可反射特性。
  • Spring 的 RestTemplate/JdbcTemplate、MyBatis 的 BaseMapper<T> 都是这套机制的工业级应用。

本章小结

要点 结论
字母约定 T 通用类型、E 集合元素、K/V 键值对、U 第二泛型参数
无界通配符 ? 接收任意类型集合，只读
上界 ? extends 匹配本类及子类，只读（生产者），如 List<? extends Number>
下界 ? super 匹配本类及父类，可写（消费者），如 List<? super Integer>
PECS 实战 Collections.copy(dest<? super T>, src<? extends T>)；取出来用 extends、塞进去用 super
类型擦除 运行时无泛型；桥接方法保多态；不能 new T()/instanceof List<String>
数组 vs 泛型 数组协变、运行期才炸；泛型不协变、编译期拦住；不要混用
反射取泛型 类/方法/字段签名可反射读回；匿名子类 TypeReference 是工业套路
实战落地 统一返回类 Result<T> 是泛型最典型的应用场景
