第二章：IO 多路复用与 Netty 线程模型

发表于 2026-05-01 更新于 2026-10-25 分类于 Netty 本文字数： 8.9k 阅读时长 ≈ 8 分钟

第二章：IO 多路复用与 Netty 线程模型

概念基础

  1. I/O 多路复用在干什么：一条线程调用 Selector.select() 阻塞等待，直到一批 Channel 上有就绪的 I/O 事件（可读、可写等），再依次分发处理——一条线程可以注册并监视成千上万个连接，而不是为每个连接各开一条阻塞线程。
  2. 「很多连接」≠「每条连接占满一条线程」：大量长连接（推送、网关、IM 在线）中许多连接长时间无读写，适合交给一个 Selector 统一等就绪；高 QPS 短连接的瓶颈常在 CPU、GC、协议栈，与「单 Selector 挂很多空闲连接」不是同一维度的问题。
  3. Netty 扮演的角色：在 Java NIO / Epoll（Linux） 之上封装了 Reactor 风格的 EventLoop、Pipeline、内存与缓冲策略，让你用少量 EventLoop 线程管理大量 Channel，并把编解码、业务入 ChannelPipeline。
  4. 线程模型与前提：Boss 负责 accept 新连接并注册给 Worker；每个 Worker EventLoop 是「一条线程 + 一个 Selector」。业务若阻塞（重度 CPU、同步 JDBC、大 Thread.sleep）会占满该 EventLoop 上的所有 Channel——阻塞操作必须丢到业务线程池，这是多路复用发挥作用的前提。
  5. 上量边界：连接规模还受进程最大打开文件数、内核参数、堆外内存约束，多路复用属于应用层模型，不能替代容量规划。

从 select/poll/epoll 到 Reactor

1. 三种系统调用的差异（面试高频）

维度 select poll epoll（Linux）
FD 上限 通常 1024（FD_SETSIZE） 无固定上限（链表） 无固定上限（红黑树）
就绪通知 每次全量遍历 fd 集合 同样全量遍历 回调注册，只返回就绪集合
用户/内核拷贝 每次调用拷贝整个 fd 集合 同左 epoll_ctl 注册一次，epoll_wait 只传就绪
复杂度 O(n) O(n) 近似 O(1) 于就绪数

Java NIO 的 Selector 在 Linux 上底层就是 epoll（JDK 自动选择），Netty 的 NioEventLoop 用它；EpollEventLoopGroup 则绕过 JDK 直接调原生 epoll，支持 ET 边缘触发等更多特性。

2. Reactor 三种形态

Reactor 模式 = 「事件分发器（Reactor）+ 处理器（Handler）」，按线程数分三档：



flowchart TB

    S1[一条线程: accept + 读 + 业务 + 写]
  end
  subgraph multi [多线程 Reactor]

形态 特点 适用
单 Reactor 单线程 全在一条线程，简单 连接少、业务极轻（Redis 模型类似）
单 Reactor 多线程 accept/IO 一条线程，业务进线程池 业务重但连接接入压力小
主从 Reactor Boss 专管 accept，Worker 池管 IO Netty 服务端默认形态，接入与 IO 解耦

Netty 的灵活处：new NioEventLoopGroup(1) 单组单线程即可退化出前两种形态；线程模型是构造参数决定的，不是框架锁死的。

Netty 常见线程模型（Boss / Worker）

1. 典型服务端写法（概念）

  • bossGroup：线程数常为 1（也可更多），负责接受新连接并把 SocketChannel 注册进 workerGroup 中某个 EventLoop 的 Selector。
  • workerGroup：每个 NioEventLoop 内一条线程 + 一个 Selector，多路复用其上的所有 Channel 的读/写就绪事件。整体是少量线程 + 大量连接，业务逻辑仍在 Pipeline 里按事件触发执行。

2. 一张逻辑关系（文字版）

角色 大致职责
Boss EventLoop accept，建 Channel，注册到某个 Worker
Worker EventLoop 已连接 Channel 的读/写就绪事件、入站出站 Pipeline

业务若阻塞（重度 CPU、同步 JDBC、大 Thread.sleep），会占满该 EventLoop 上的所有 Channel，拖慢整组连接——因此阻塞操作应丢到业务线程池或异步组件，这是多路复用能发挥作用的前提。

两个关键设计：

  1. ioRatio（默认 50）：I/O 事件与任务队列的时间配额比——runAllTasks 最多跑「I/O 耗时 × (100-ioRatio)/ioRatio」，防止任务积压饿死 I/O，也防止 I/O 频繁饿死任务。
  2. 空轮询 bug 规避：JDK NIO 在 Linux 上曾有「select() 立即返回但无就绪」的空转 bug（CPU 100%）；Netty 统计连续空轮询次数，超阈值就重建 Selector、把旧 Channel 迁移过去，从框架层兜底。

一个 Channel 从 register 起终身绑定一个 EventLoop；跨线程写（业务线程池里 ctx.writeAndFlush）会被检测出来，包装成 task 投入该 EventLoop 的 taskQueue，由第 3 步统一执行——这就是 Netty 「任意线程可写」的实现原理。

大量连接下的系统侧（简述）

要把多路复用撑到很大连接数，通常还要：

  1. 进程最大打开文件数（ulimit -n）调到足够大。
  2. Linux 上 TCP、端口范围、somaxconn 等与接入能力相关的内核参数按运维规范调整。
  3. 堆外内存、直接内存、-Xmx 与 Netty 的 ByteBuf 分配策略匹配业务量，避免 OOM。

常见面试题速览

  1. 为什么 Netty 用主从 Reactor——accept 与已连接 IO 解耦：接入抖动不影响存量连接，Worker 池可按压测独立扩缩。
  2. EventLoop 上为什么不能阻塞——一条 EventLoop 串行服务其名下所有 Channel，阻塞 100ms 等于这批连接集体卡顿 100ms。
  3. select/poll/epoll 区别——见上文对比表：核心是「遍历全量 vs 回调就绪」与 fd 拷贝成本。
  4. 一个 Channel 能换 EventLoop 吗——不能：注册即绑定终身，这是单线程串行无锁的前提。
  5. Boss 线程数为什么是 1——单监听端口只需一条 accept 线程；多端口/多 boss 仅在特殊架构下有意义。
  6. NIO 与 Epoll 传输怎么选——跨平台用 NIO；纯 Linux 生产用 Epoll，少一次封装、支持 TCP_CORK 等原生选项（业务代码完全不变，见第六章）。
  7. ioRatio 是什么——EventLoop 主循环里 I/O 处理与任务队列的时间配额比（默认 50），失衡会互相饿死（见上文源码级主循环）。
