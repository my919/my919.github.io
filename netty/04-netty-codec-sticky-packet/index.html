第三章：编解码与粘包拆包

发表于 2026-05-01 更新于 2026-10-29 分类于 Netty 本文字数： 9k 阅读时长 ≈ 8 分钟

第三章：编解码与粘包拆包

概念基础

  1. TCP 是字节流，不是消息流：发送方连续 write 两条消息，接收方可能一次读到两条粘在一起（粘包），也可能读到半条（拆包）。这是 TCP 本性，不是 bug。
  2. Netty 的解决思路：在 Pipeline 入口加一个 FrameDecoder（帧解码器），按某种边界规则把字节流切成一条条完整消息，再交给后续 Handler。
  3. 编解码两层：解码（Decoder） 把字节→对象（入站方向），编码（Encoder） 把对象→字节（出站方向）。二者常成对出现，组成「协议层」。
  4. 内置即用：Netty 预置了按换行、分隔符、长度域等切分的解码器，覆盖大多数二进制协议；不满足时继承 ByteToMessageDecoder 自定义。
  5. 正确性 > 性能：编解码是协议正确性的根基，错一个长度域会触发整条连接崩溃。务必先保证语义正确，再做池化/零拷贝优化。

本章承接 第二章：Netty 核心组件深入 的 Pipeline / ByteBuf 知识，把「字节流如何变成消息」讲透。

一、粘包与拆包现象

  M2 --> R1
  M1 --> R2
  M1 --> R3
  M2 --> R2
  M2 --> R3

不解决粘包，业务 Handler 里 channelRead 拿到的 ByteBuf 可能含多条半消息，无法正确解析。必须在业务 Handler 之前加帧解码器。

为什么会发生（三个叠加因素）

  1. 发送端合并：Nagle 算法攒小包一起发，多条消息被合并进一个 TCP 段。
  2. 网络层分段：单个应用消息超过 MSS（约 1460 字节）会被拆成多个段，接收端一次 read 可能只拿到半个消息。
  3. 接收端缓冲：内核接收缓冲里的字节是连续无边界的，read 拿到多少取决于时序——可能一次吐出三轮消息，也可能半轮。

结论：TCP 协议里根本没有「消息」概念，边界必须由应用层协议自己定义——这就是帧解码器存在的理由。

二、内置帧解码器（解决切分边界）

Netty 的帧解码器都继承 ByteToMessageDecoder，按规则把入站 ByteBuf 切成完整帧。

0. 四种解码器对比速查

解码器 切分依据 关键参数 适用协议 典型坑
FixedLengthFrameDecoder 固定字节数 frameLength 定长二进制报文 业务字段长度不定就不适用
LineBasedFrameDecoder \n 或 \r\n maxLength 文本协议（HTTP 头、Redis RESP） 数据本身含换行就错乱
DelimiterBasedFrameDecoder 自定义分隔符 maxFrameLength + 分隔符 自定义文本协议 分隔符必须保证不出现在数据里
LengthFieldBasedFrameDecoder 头部长度字段 5 参数（见下） 绝大多数二进制协议 参数配错位，一直读到错数据

选择顺序：先看协议有没有长度字段（有就用长度域），没有再看能否找到不出现在数据里的分隔符，文本协议用换行，都不行再自定义 ByteToMessageDecoder。

四、ByteToMessageDecoder：字节→消息（自定义）

当内置帧解码器都不满足时，直接继承 ByteToMessageDecoder，自己控制累积缓冲的读取。它会把多次到达的字节累积到内部缓冲，直到数据足够：

三个要点：

  1. 不足时 return 前 resetReaderIndex，让下次 decode 从头部重新读。
  2. 切出的 ByteBuf 若放进 out，所有权转移给下游，由下游 release；不要在这里 release。
  3. 多次 decode 调用是 Netty 自动驱动的，不要自己写循环等待（框架已处理）。

五、编码器：对象→字节

出站方向对称。两类基类：

基类 用途
MessageToByteEncoder<I> 对象→单个 ByteBuf
MessageToMessageEncoder<I> 对象→对象（如对象→另一种对象）

MessageToByteEncoder 只在出站消息类型匹配 I 时触发，其他类型直接跳过——可安全混用多种出站消息。

继承 ReplayingDecoder<S> 后，decode 里可以不加可读字节数判断：读到不足会抛内部 Error（不是真异常），框架捕获后自动回滚读指针、等数据齐了再重放：

取舍：代码更直观，但每次「重放」都要从头重读，性能低于手写守卫的 ByteToMessageDecoder；且不能在 decode 里做有副作用的操作（会执行多次）。追求极限性能选前者，追求可读性且吞吐要求一般选后者。

八、典型 Pipeline 编排模板

顺序原则：帧解码器最前→编解码器→心跳→业务。出站编码器位置不影响出站触发（出站会从调用者向链头反向经过所有出站 Handler），但放业务前更清晰。

九、常见陷阱

陷阱 说明
漏 FrameDecoder 业务直接读 ByteBuf，粘包下解析错乱。任何二进制协议都必须先切包
MessageToByteEncoder 不释放 框架会释放 encode 产出的 ByteBuf；但若你 write 的是外部传入的 ByteBuf，需自己管理引用计数
解码 throw 异常未处理 异常会触发 exceptionCaught，默认关闭连接；非法帧应记录日志后 ctx.close()
LengthFieldBasedFrameDecoder 参数错 长度值含不含长度字段自身、有没有调整量，配错会一直读到错位数据。打印十六进制对照
未限制最大帧长 maxFrameLength 过大或缺失，恶意端发巨帧触发 OOM
StringDecoder 后又当 ByteBuf 用 一旦解码成 String，下游类型已变，不会再有 ByteBuf

十、常见面试题速览

  1. TCP 为什么会粘包——字节流无消息边界 + Nagle 合并 + MSS 分段 + 接收缓冲时序，四者叠加。
  2. 怎么解决——应用层自己定界：定长 / 分隔符 / 长度字段，Netty 用帧解码器承载这三种思路。
  3. LengthFieldBasedFrameDecoder 五参数——maxFrameLength、lengthFieldOffset、lengthFieldLength、lengthAdjustment、initialBytesToStrip；后两个最易配错。
  4. 解码器里数据不够怎么办——return 前 resetReaderIndex 等下次，或直接用 ReplayingDecoder 自动重放。
  5. 帧解码器与业务解码器的分工——前者切出完整字节帧（ByteToMessage），后者把帧解析成对象（MessageToMessage）。
  6. 如何防恶意巨帧——maxFrameLength 限制 + 解码失败 ctx.close()，缺一不可。
  7. 怎么单测解码器——EmbeddedChannel 喂字节取产物，不起网络（见「调试手段」一节）。
  8. MessageToByteEncoder 里要手动 release 吗——encode 产出的 out 由框架释放；但方法外自己 retain 过的引用仍归你管。
  9. 帧解码器能放 @Sharable 吗——不能：内部累积缓冲是有状态的，共享会串包；每个 Channel 独立实例。
  10. 换行解码器能用于二进制协议吗——不能：二进制载荷可能恰好含 0x0A，会被误切；二进制一律走长度域或自定义。
  11. 解码器报 TooLongFrameException 怎么办——先确认是恶意流量还是 maxFrameLength 设小；正常大报文协议应按业务上限重设。

本章小结

要点 结论
粘包拆包 TCP 字节流本性，必须用帧解码器切分，业务 Handler 才能拿到完整消息
内置帧解码器 定长 FixedLength、换行 LineBased、分隔符 DelimiterBased、长度域 LengthFieldBasedFrameDecoder 最通用
两层抽象 ByteToMessageDecoder：字节→消息（含切包）；MessageToMessageDecoder：消息→消息
编码器 MessageToByteEncoder<I> 对象→ByteBuf；只在类型匹配时触发
一体化 MessageToMessageCodec 合并编解码，但仍需 FrameDecoder 切包
Pipeline 顺序 帧解码 → 业务编解码 → 心跳 → 业务 Handler
安全 限制 maxFrameLength、处理非法帧异常、对照十六进制调试长度域参数
