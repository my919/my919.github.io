1. 概念说明

Netty 是基于 NIO 的高性能异步事件驱动网络框架，是 Java 网络编程的事实标准：Dubbo、RocketMQ、Elasticsearch、gRPC-Java 都基于它。

为什么不用原生 NIO：原生 NIO 的 Selector 编程复杂（连接管理、拆包、线程模型都要手写），Netty 封装好线程模型、编解码、重连、心跳，开发者只关注业务。

10. 典型案例：长连接网关的心跳保活与断线重连

问题背景：App 推送网关接入 50 万长连接，运行一周后告警频发：堆内存持续走高、连接数只涨不跌。排查发现运营商 NAT 空闲表项约 5 分钟回收，大量 TCP 连接已「半开」——服务端仍显示 ESTABLISHED，客户端早已失联，僵尸连接持有 ByteBuf 与 Session 不释放。

方案：

端 策略 参数
客户端 写空闲发心跳 PING 写空闲 30s < NAT 5 分钟
服务端 读空闲踢线（60s 无任何数据即失联） 读空闲 60s ≈ 心跳间隔 2 倍，容忍一次抖动
客户端 指数退避重连 3s→6s→12s（60s 封顶） 防服务端重启时的重连风暴

踩坑点：

  • 服务端读空闲阈值必须 ≥ 客户端心跳间隔的 2 倍，否则一次网络抖动就误杀正常连接。
  • 重连逻辑不要在 channelInactive 里 Thread.sleep()——那是 EventLoop 线程，sleep 会卡住同组所有 Channel。
  • 心跳建议走独立轻量类型，别让心跳进业务解码与 Handler，避免产生无谓对象与误分发。

11. 常见误用与陷阱

坑 现象/后果 解法
ByteBuf 忘记 release 堆外内存泄漏，运行数日 OOM 业务用 SimpleChannelInboundHandler 自动释放；配合 leakDetection 排查
Handler 里做阻塞操作（DB/HTTP/sleep） EventLoop 卡住，同线程所有连接全部停顿 耗时操作提交业务线程池或 DefaultEventExecutorGroup
有状态 Handler 加到多个 pipeline 状态串线、数据错乱、诡异并发 bug 有状态每连接 new 一个；无状态才标 @Sharable
编解码器加错位置 业务收到未拆帧的 ByteBuf，粘包依旧 入站顺序：帧解码器 → 解码器 → 业务 Handler
IdleStateHandler 加了但没人处理事件 IdleStateEvent 被吞，僵尸连接照旧堆积 必须有 Handler 实现 userEventTriggered
option 与 childOption 混用 SO_BACKLOG 配到 childOption 不生效 服务端端口选项用 option，连接选项用 childOption
长连接不发心跳 NAT/防火墙静默回收，半开连接堆积 双端心跳：客户端保活 + 服务端空闲踢线
