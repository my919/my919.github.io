1. 概念说明

Netty 是基于 NIO 的高性能异步事件驱动网络框架，是 Java 网络编程的事实标准：Dubbo、RocketMQ、Elasticsearch、gRPC-Java 都基于它。

为什么不用原生 NIO：原生 NIO 的 Selector 编程复杂（连接管理、拆包、线程模型都要手写），Netty 封装好线程模型、编解码、重连、心跳，开发者只关注业务。

核心线程模型（Reactor 模式）：BossGroup（少量线程）只 Accept 连接并注册到 WorkerGroup，WorkerGroup（N 线程）处理读写事件；每个 Channel 绑定固定 EventLoop 线程，天然无并发竞争。select/poll/epoll 差异、Reactor 三种形态与 EventLoop 源码级主循环：深入了解：第一章：IO 多路复用与 Netty 线程模型

核心组件一句话速记：EventLoopGroup（线程组）、Channel（连接抽象）、ChannelPipeline（入站/出站 Handler 链）、ByteBuf（池化字节缓冲，引用计数需手动 release）。各组件的异步语义、传播机制与引用计数细节：深入了解：第二章：Netty 核心组件深入

4. 服务端实现

服务端骨架四步：ServerBootstrap.group(boss, worker) 绑两个线程组 → .channel(NioServerSocketChannel.class) 定 NIO 通道 → .childHandler(...) 给每个新连接初始化 pipeline（addLast 业务 Handler）→ bind(8080).sync() 启动，closeFuture().sync() 阻塞保活，finally 里 shutdownGracefully() 优雅关闭。选项分两类：端口级用 option（如 SO_BACKLOG），连接级用 childOption（如 TCP_NODELAY 禁 Nagle 降延迟）。

业务 Handler 继承 ChannelInboundHandlerAdapter，在 channelRead 里收消息、ctx.writeAndFlush(...) 写回；exceptionCaught 里打印异常并 ctx.close()。完整可运行代码（EchoServer/EchoHandler）：深入了解：第一章：IO 多路复用与 Netty 线程模型

6. 粘包/拆包解决方案

TCP 是字节流，多条消息可能粘连或被拆开，必须定义帧边界。三种方案对比：定长帧（固定长度，浪费带宽）、分隔符（DelimiterBasedFrameDecoder，正文不能含分隔符）、长度字段（推荐，通用高效——LengthFieldBasedFrameDecoder 解码 + LengthFieldPrepender 编码，消息格式 [4 字节长度][正文]）。

四种内置帧解码器的参数推导、自定义解码器（ByteToMessageDecoder/ReplayingDecoder）与 Pipeline 编排模板：深入了解：第三章：编解码与粘包拆包

7. 心跳保活与断线重连

IdleStateHandler 检测读/写空闲并触发 IdleStateEvent：客户端写空闲发心跳 PING，服务端读空闲踢线（阈值 ≥ 心跳间隔 2 倍，容忍一次抖动）；断线后客户端用指数退避重连（3s→6s→12s，封顶 60s），由调度器触发而非 Thread.sleep（会卡死 EventLoop）。

10. 典型案例：长连接网关的心跳保活与断线重连

问题背景：App 推送网关接入 50 万长连接，运行一周后告警频发：堆内存持续走高、连接数只涨不跌。排查发现运营商 NAT 空闲表项约 5 分钟回收，大量 TCP 连接已「半开」——服务端仍显示 ESTABLISHED，客户端早已失联，僵尸连接持有 ByteBuf 与 Session 不释放。

方案：双端心跳——客户端写空闲 30s 发 PING（< NAT 5 分钟回收期），服务端读空闲 60s 踢线（≈ 心跳间隔 2 倍，容忍一次抖动）；客户端断线后指数退避重连 3s→6s→12s（60s 封顶），防服务端重启时的重连风暴。

踩坑点：服务端读空闲阈值必须 ≥ 客户端心跳间隔的 2 倍，否则一次网络抖动就误杀正常连接；重连逻辑不要在 channelInactive 里 Thread.sleep()——那是 EventLoop 线程，会卡住同组所有 Channel；心跳走独立轻量类型，别进业务解码链路。

生产级参数推导与完整 HeartbeatTrigger/ReconnectHandler 代码：深入了解：第四章：Netty 高级特性与性能调优

11. 常见误用与陷阱

坑 现象/后果 解法
ByteBuf 忘记 release 堆外内存泄漏，运行数日 OOM 业务用 SimpleChannelInboundHandler 自动释放；配合 leakDetection 排查
Handler 里做阻塞操作（DB/HTTP/sleep） EventLoop 卡住，同线程所有连接全部停顿 耗时操作提交业务线程池或 DefaultEventExecutorGroup
有状态 Handler 加到多个 pipeline 状态串线、数据错乱、诡异并发 bug 有状态每连接 new 一个；无状态才标 @Sharable
编解码器加错位置 业务收到未拆帧的 ByteBuf，粘包依旧 入站顺序：帧解码器 → 解码器 → 业务 Handler
IdleStateHandler 加了但没人处理事件 IdleStateEvent 被吞，僵尸连接照旧堆积 必须有 Handler 实现 userEventTriggered
option 与 childOption 混用 SO_BACKLOG 配到 childOption 不生效 服务端端口选项用 option，连接选项用 childOption
长连接不发心跳 NAT/防火墙静默回收，半开连接堆积 双端心跳：客户端保活 + 服务端空闲踢线
