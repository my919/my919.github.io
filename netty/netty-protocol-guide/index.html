10. 典型案例：IoT 设备接入网关（粘包复现 → 魔数校验 → 修复）

问题背景：工厂传感器经 TCP 上报遥测数据（每条约 40 字节、每秒 10 条）。联调正常、上线后数据偶发错乱：解析出的遥测值离谱巨大。抓包发现基站侧会做报文聚合（几百条粘成一包）与拆分（半条跨包），初版「channelRead 直接读 ByteBuf」的代码在粘包时把两条拼成一条，解析全部错位。

方案：

环节 设计
拆帧 LengthFieldBasedFrameDecoder：offset=4、length=4、adjust=0
准入校验 帧头 magic ≠ 0xCAFE 直接断开（防端口扫描器/误接设备）
防攻击 maxFrameLength=64KB，超长帧立即断连而非无限等待
版本演进 version 字段保留，旧版本设备灰度期双版本共存

踩坑点：

  • lengthAdjustment 最易算错：本协议 length 只指 payload、长度字段前共 4 字节头部，所以 adjust=0；若 length 把头部也算进去则要负值修正——算错的表现是「永远凑不齐一帧」或把帧头当 payload。
  • 魔数校验要用 getShort(readerIndex)（只窥视不移动指针）；误用 readShort 会前移 readerIndex，后续 super.decode 的偏移全部错位。

11. 常见误用与陷阱

坑 现象/后果 解法
lengthAdjustment 算错 永远凑不齐一帧，或把帧头当 payload 画字节布局图逐字段核对官方公式
maxFrameLength 设得过大 恶意/异常客户端超大帧打爆堆外内存 按业务上限收紧（如 64KB），超限断连
带累积状态的 Decoder 标 @Sharable 单例 多连接共享累积缓冲，数据串线 有状态解码器每连接 new 一个
decode 里读完不 release frame 堆外内存持续增长，数日后 OOM try-finally 里 release
校验 magic 用 readShort readerIndex 前移，后续解析错位 用 getShort(readerIndex) 窥视不消费
业务 Handler 放在解码器之前 收到的是未拆帧 ByteBuf，解析崩溃 入站顺序：帧解码 → 解码 → 业务
断线重连复用旧 pipeline/Handler 累积状态（重试计数等）跨连接残留 重连时整体重建 pipeline 与 Handler 实例
