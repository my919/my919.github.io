1. 概念说明

Kubernetes（K8s）是容器编排平台：自动完成容器的部署、伸缩、故障恢复、滚动升级。它解决的是”几十上百个容器如何协作管理”的问题。

核心对象：

对象 作用
Pod 最小调度单元，一个 Pod 内 1+ 容器共享网络与存储
Deployment 管理无状态应用的副本数、滚动更新、自愈
StatefulSet 有状态应用（数据库）稳定标识与顺序
Service 给 Pod 提供稳定访问入口（ClusterIP/NodePort/LB）
Ingress 七层 HTTP 路由，按域名/路径分发
ConfigMap / Secret 配置与密钥注入
Namespace 资源隔离（环境/团队）

工作方式：你声明”期望状态”（3 个副本、镜像 v1），控制器持续对比实际状态并纠正（Pod 挂了自动重建）。

11. 典型案例：Spring Boot 滚动发布 + 探针配置

问题背景：线上 Spring Boot 应用发布新版本时，若直接替换 Pod，会出现：JVM 启动慢（10-30 秒）导致新 Pod 未就绪就接流量 → 502；旧 Pod 立即被杀导致在途请求中断。需要配置滚动发布策略 + 三类探针 + 优雅停机，实现零停机发布。

方案：

探针 作用 配置要点
startupProbe 启动期保护 超时设大（如 120s），给 JVM 足够启动时间
readinessProbe 就绪接流量 通过前不进 Service Endpoints
livenessProbe 存活自动重启 失败重启 Pod

关键 Deployment：

踩坑点：

  1. liveness 探针误配导致重启风暴：若 liveness 探测的接口依赖数据库，数据库短暂抖动会触发 Pod 重启，重启又加重数据库压力，形成雪崩。liveness 应只探测应用自身存活（如一个不依赖外部的轻量接口）。
  2. readiness 和 liveness 不能用同一个接口且配置相同：readiness 失败只是摘除流量，liveness 失败会重启 Pod。若配置相同，一次短暂故障就会触发重启而非摘流。
  3. preStop 的 sleep 时间要小于 terminationGracePeriodSeconds：否则 kubelet 会在 preStop 执行完之前强杀容器，导致在途请求被中断。

12. 常见误用与陷阱

坑 现象/后果 解法
liveness 探针误配导致重启风暴 数据库抖动 → Pod 重启 → 加重压力 → 雪崩 liveness 只探应用自身存活；依赖外部的用 readiness
未设资源限制被驱逐 节点资源不足时 Pod 被驱逐，服务不可用 每个容器配 requests + limits；设 PriorityClass 保核心服务
优雅停机未配 preStop 发布时在途请求被中断，用户看到 502 配 preStop sleep + terminationGracePeriodSeconds
镜像拉取策略错误 用 latest 且 imagePullPolicy=Always，每次重启都拉取可能失败 固定版本 tag；生产用 IfNotPresent
readiness 探针缺失 新 Pod 未启动完就接流量，返回 502 必须配 readinessProbe，就绪才进 Endpoints
