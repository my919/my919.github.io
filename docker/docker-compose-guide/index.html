1. 概念说明

Compose 用一份 compose.yaml 声明”一组容器如何运行”：镜像、端口、卷、环境、依赖、网络——一条命令 docker compose up 拉起整个应用栈。

Compose vs K8s：单机多容器 → Compose；集群/自动扩缩容/自愈 → K8s。生产小团队用 Compose 完全够用（单机高可用靠 Swarm 或外部负载均衡）。

核心概念：service（服务）、network（网络）、volume（数据卷）、dependency（依赖）、healthcheck（健康检查）。

9. 典型案例：本地开发环境一键编排

问题背景：团队开发一个 Spring Boot 应用，依赖 MySQL、Redis、RabbitMQ。新人入职要花半天装环境，且各人版本不一致导致”我电脑上能跑”。需要用 Docker Compose 一键拉起全部依赖，应用用挂载源码 + 热重载，保证环境一致。

方案：

服务 镜像 端口 作用
app 本地构建 8080 Spring Boot 应用
mysql mysql:8.4 3306 数据库
redis redis:8-alpine 6379 缓存
rabbitmq rabbitmq:4-management 5672/15672 消息队列

关键 compose.yaml：

踩坑点：

  1. depends_on 必须配 condition：只写 depends_on: [mysql] 只保证启动顺序，不保证 mysql 就绪。必须用 condition: service_healthy 等健康检查通过。
  2. bind mount 源码要注意权限：容器内非 root 用户可能无法读写挂载的源码，需 user: "${UID}:${GID}" 或调整目录权限。
  3. 数据目录要 gitignore：./data/mysql 等持久化目录必须加入 .gitignore，否则会提交大量二进制文件。

10. 常见误用与陷阱

坑 现象/后果 解法
镜像体积巨大未多阶段构建 镜像 800MB+，构建慢、拉取慢 Dockerfile 用多阶段构建，运行阶段只拷产物
容器内写日志撑爆磁盘 容器持续写日志，宿主机磁盘满 logging driver 配 max-size/max-file；日志走 stdout
privileged 滥用 容器获宿主机 root 权限，安全风险 避免 –privileged，按需 –cap-add 指定能力
latest 标签不可追溯 线上版本不清，回滚困难 固定版本 tag，如 mysql:8.4 而非 mysql:latest
数据未挂载卷丢失 容器删除后数据库/上传文件消失 用 volumes 或 bind mount 持久化数据目录
