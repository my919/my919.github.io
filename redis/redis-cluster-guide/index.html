2. 方案选型（什么时候用什么）

方案 解决 不解决 适用
主从 读扩展 + 数据备份 故障不自动切换 测试/小业务
哨兵 故障自动切换（高可用） 容量上限 数据量 < 单机内存，生产标配
Cluster 高可用 + 分片扩展 复杂度高 数据量 > 单机内存

判定标准：数据能装进单机内存 → 哨兵；装不下 → Cluster。多数业务（缓存类）哨兵就够。

4. Redis Cluster（数据量超单机内存时）

4.1 概念：槽位（Slot）

为什么是 16384 个槽：CRC16 有 65536 个结果，取 16384（2^14）——槽位信息要广播到所有节点，槽太多网络开销大，16384 是”粒度与开销”的平衡。

4.2 部署（6 节点：3 主 3 从）

为什么命令要带 -c：普通模式只连一个节点，key 不在该节点槽位会报 MOVED 错误；-c（cluster 模式）客户端自动重定向。

5. Java 客户端接入（Lettuce 集群/哨兵）

客户端为什么连哨兵/集群而非直连主节点：主节点故障切换后 IP 会变——客户端必须从哨兵/集群元数据动态拿当前主节点，直连 IP 就断连了。

6. 常见问题

问题 原因 解决
切换后客户端连不上 客户端没走哨兵发现 配 sentinel 模式（§5）
脑裂双主 哨兵不足 3 个/网络分区 哨兵奇数 + 多数派
MOVED 错误 没开 -c / 客户端非集群模式 客户端配 cluster 模式
集群槽分配不均 扩容后没 reshard 重新分槽

8. 典型案例：购物车从哨兵架构迁移到 Cluster 的多 key 命令改造

问题背景：电商购物车业务用哨兵架构，三年下来 Redis 单实例内存涨到 48GB（接近单机上限），商品峰会内存持续增长，DB 回源兜不住”扩不了内存”的现状。决定迁移到 3 主 3 从 Cluster。迁移窗口内出现两类事故：① 购物车聚合接口（一次读用户全部购物车项的 Hash 字段 + MGET 批量取商品详情）大面积报 CROSSSLOT/MOVED；② 迁移期间部分请求延迟从 1ms 涨到 200ms。

方案：以”用户维度”做槽位亲和（hash tag），把同一用户的多 key 命令收敛到同一槽；扩容选低峰 + 客户端开启拓扑刷新：

改造项 迁移前 迁移后 原因
购物车 key cart:1001 cart:{1001} 同用户数据同槽，HGETALL/MULTI 不跨槽
商品详情 key product:10086 product:10086（不变） 加 tag 会造成热点倾斜，单节点扛不住
批量取详情 MGET 一次 按 CRC16(key)%16384 分组，每组 pipeline MGET MGET 只支持同槽
客户端 Lettuce 单机模式 Lettuce 集群模式 + 拓扑刷新 自动感知 MOVED/槽迁移
扩容窗口 不涉及 低峰（02:00）+ 预迁移演练 reshard 期间对应槽只读延迟上升

踩坑点：

  1. hash tag 上线时图省事，把商品详情也加了 tag（product:{categoryId}），某分类下 3 万个商品全落在同一槽，该分片内存是其他分片 6 倍、CPU 90%——tag 只给”必须同槽”的数据用，其他数据保持散列。
  2. 购物车结算用的 Redisson 分布式锁 key 没加 tag，锁和被锁的数据不在同一节点，锁语义失效出现超卖——分布式锁与受保护资源使用相同 hash tag（如 lock:{1001} 对 cart:{1001}）。
  3. reshard 迁移槽时选了业务高峰，迁移中的槽（ASKING 状态）请求延迟 200ms+，接口 P99 抖到 800ms——槽迁移必须在低峰分批执行，每批观察客户端错误率再继续。
  4. 客户端没开拓扑刷新（Lettuce 默认 enableAllAdaptiveRefreshTriggers 未开启），扩容新增节点后老节点返回 MOVED，客户端重试风暴持续 5 分钟——集群模式必须开启拓扑刷新 + 重试退避。
  5. 迁移前未演练”半迁移状态”（一部分用户已在新 key 结构、一部分在旧结构），双读兼容逻辑上线时才发现漏了旧 key 的降级读取，造成 30 分钟购物车”丢商品”的假象——迁移类改造必须先写双读/双写影子验证。

9. 常见误用与陷阱

坑 现象/后果 解法
hash tag 乱加（全量 key 加 tag） 数据全部落进同一槽，单分片内存/CPU 爆表，分片形同虚设 只给”需要多 key 命令/事务”的数据加 tag，其余散列
MGET/MSET 跨槽 客户端报 CROSSSLOT，批量接口大面积失败 按槽分组逐组执行，或改 pipeline + 单 key GET
MULTI 事务/Lua 脚本跨槽 事务报错或 Lua 无法执行，”原子操作”悄悄失效 同槽化（hash tag）或改用分布式锁 + 单 key 原子命令
客户端直连主节点 IP 故障切换后连接全断，需要人工重启应用恢复 客户端走哨兵/集群拓扑发现；开拓扑自动刷新
哨兵 quorum 配 1 或哨兵只部署 2 个 单哨兵误判就触发切换；网络分区双主（脑裂） 哨兵 ≥3 奇数，quorum=多数派（3 个配 2）
扩容 reshard 在高峰执行 迁移中槽位延迟飙升，接口 P99 抖动数倍 低峰分批迁移，每批验证客户端错误率；开重试退避
从节点当读库用且强一致依赖 主从复制有延迟，读到几秒前旧数据引发业务错乱 读从节点只放弱一致场景；关键读走主节点
cluster-node-timeout 配置过小（如 1s） 网络轻微抖动即判定节点下线，频繁切换/告警 生产建议 5-15s，结合机房网络质量调参
