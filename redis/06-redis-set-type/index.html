第五章：Redis Set 数据类型：概念、命令与案例

发表于 2026-05-03 更新于 2026-10-29 分类于 Redis 缓存 本文字数： 5.6k 阅读时长 ≈ 5 分钟

第五章：Redis Set 数据类型：概念、命令与案例

概念基础

Set 是无序、不重复的字符串成员集合，直接对应数学里的「集合」：

  1. TYPE key 为 set。
  2. 不保证顺序（遍历顺序实现依赖，勿当有序结构用）。
  3. 成员即字符串；同一成员重复 SADD 只保留一份，判重是 O(1)——这是它与 List 最本质的差异。
  4. 集合间可做 SINTER / SUNION / SDIFF（交 / 并 / 差），把「共同关注」「可能认识的人」这类关系计算下推到 Redis 里完成。
  5. 没有分值、没有序号——需要「第几名」「Top N」请直接上 ZSet，不要用 Set 硬撑。

核心原理：编码与复杂度

1. 两种编码（OBJECT ENCODING key 观察）

  • intset：成员全部是整数且个数不超过 set-max-intset-entries（默认 512）时使用，有序整数数组 + 二分查找，最省内存。intset 内部按值升序排列，查找 O(logN) 但 N≤512 时依旧飞快；一旦有任一成员不是整数或个数超阈值，整体转 hashtable。
  • hashtable：一般情况使用，member 作字典的 key、value 恒为 NULL——「唯一性」由哈希表天然保证，SADD / SISMEMBER / SREM 均 O(1)。

2. 时间复杂度表

命令 复杂度 说明
SADD / SREM / SISMEMBER O(1) 多成员形式 O(N)，N 为本次成员数
SCARD O(1) 计数有缓存
SMEMBERS O(N) 一次返回全量，大集合慎用
SSCAN 单次 O(1) 级别 大集合迭代唯一正确姿势
SPOP / SRANDMEMBER O(1)（带 count 为 O(count)） 见「随机语义」
SINTER O(N·M) 最坏 N、M 为各集合大小
SUNION / SDIFF O(N) N 为所有集合成员总数

3. 集合运算的代价

SINTER / SUNION / SDIFF 是同步计算——两个大集合求交可能耗时几十毫秒甚至秒级，期间 Redis 无法处理其他请求。生产上建议：

  • 用 SINTERSTORE / SUNIONSTORE / SDIFFSTORE 把结果写入新 key，再异步消费；
  • 大运算放到从库或低峰期执行；
  • 能通过业务预计算（如每日离线算好共同关注）就不要实时算。

4. 随机语义

SPOP 是弹出（取出并从集合删除，不放回）；SRANDMEMBER 只读不删——count 为正给不重复成员、为负允许重复。抽奖「不放回」用 SPOP、「仅看看」或「可重复抽取」用 SRANDMEMBER。

常用命令（必会子集）

命令 作用
SADD / SREM 增删成员
SMEMBERS 返回全部成员（大集合慎用，改用 SSCAN）
SISMEMBER / SMISMEMBER 是否在集合（后者批量，Redis 6.2+）
SCARD 成员个数
SRANDMEMBER / SPOP 随机读 / 随机弹出
SINTER / SUNION / SDIFF 交 / 并 / 差（可带 STORE 写到新 key）
SMOVE 把成员从一个 Set 搬到另一个（原子）

典型应用场景

  1. 标签系统：SADD article:7:tags Java Redis；反查「某标签下所有文章」再建 tag:java:articles 反向集合。
  2. 抽奖池 / 去重 ID 池：SPOP 不放回抽样（需理解并发下多个客户端抢 SPOP 的语义——同一成员不会被弹出两次，天然防重）。
  3. 共同关注 / 共同好友：SINTER user:1:following user:2:following。
  4. 可能认识的人：SDIFF user:2:followers user:1:following——「关注了我但我还没回关的人」。
  5. 黑白名单 / 去重过滤：SISMEMBER blacklist:ip 1.2.3.4 O(1) 判定，比查库快几个数量级。
  6. 已读回执去重：消息下发前 SADD msg:9:read u1 返回 0 说明已记录过，实现幂等。
  7. 活动参与去重：SADD act:88:joined u1 返回 0 即重复报名，报名接口幂等一行搞定。

数据量大时把 SINTERSTORE 结果落到新 key（如 filter:java+redis）并设 TTL，列表页直接读结果 key，避免每次请求实时求交。

5. 幂等去重：消息已读回执

SADD 的返回值就是天然的「是否首次」判定，无需先 SISMEMBER 再 SADD（两步并发下有竞态，且多一次往返）。

6. 可能认识的人：二度人脉初筛

这是「可能认识的人」最朴素的一度差集实现；真实产品会叠加共同关注数排序（那时就该换 ZSet：score 存共同好友数）。

7. 原子迁移：SMOVE 调整用户分组

若用 SREM + SADD 两步，中间态可能被其他请求读到「两组都不在」——SMOVE 一条命令消除该窗口。

进阶：intset 编码观察与阈值

intset 内部是升序整数数组 + 二分查找，转 hashtable 后内存约翻数倍——全部成员为整数的小集合是 Set 的最优形态，设计 key 时可有意利用（如「已读消息 ID 集」用纯整型 ID）。

与关系型方案对比

维度 Redis Set MySQL 关系表
判重 SISMEMBER O(1) 唯一索引 + SELECT，毫秒级
共同关注 SINTER 内存计算 多表 JOIN，数据大时慢

常见组合：MySQL 存全量关系，Redis Set 缓存热点关系（如大 V 的粉丝交集离线算好写 Redis）。

常见坑与注意事项

  1. 大 Set：SMEMBERS 一次性拉全量可能阻塞与占带宽，用 SSCAN 迭代。
  2. 大集合运算阻塞：千万级 SINTER 足以让生产 Redis 卡住，务必 STORE 系列 + 从库/低峰执行。
  3. intset 幻觉：intset 编码下遍历是有序的，但这是实现细节不是承诺——业务不得依赖 Set 的任何顺序。
  4. 与 List：Set 无序且唯一；List 有序可重复。
  5. 需要按分数排序（排行榜）→ 用 ZSet，不要用 Set 硬撑。
  6. UV 估算：只要「大约多少人」不要明细时，HyperLogLog 比 Set 省几个数量级内存（见第九章）。
  7. STORE 结果 key 的生命周期：SINTERSTORE 等产物 key 是计算缓存，务必设 TTL 或定期清理，否则日复一日的 filter:* 会悄悄吃光内存。
  8. 批量判重用 SMISMEMBER（6.2+）：循环调 SISMEMBER 是 N 次往返，批量一次搞定，接入层判黑/白名单时收益明显。

本章小结

要点 结论
本质 无序、唯一，O(1) 判重
编码 intset（全整数 ≤512）→ hashtable（member 为 key、value 为 NULL）
集合运算 SINTER/SUNION/SDIFF，大集合用 STORE 系列异步化
高频命令 SADD / SISMEMBER / SCARD / SINTER / SPOP / SSCAN
场景 标签、去重、抽奖、共同关注、黑白名单
