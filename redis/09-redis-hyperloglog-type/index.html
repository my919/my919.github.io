第八章：Redis HyperLogLog：概念、命令与案例

概念基础

HyperLogLog（HLL） 是一种基数（去重计数）估算算法的数据结构——用极小的固定内存回答「这批元素大约有多少个不同的」：

  1. 不是存明细，只支持 PFADD 添加元素、PFCOUNT 估算基数、PFMERGE 合并多个 HLL。
  2. 内存奇迹：无论存 1 万还是 1 亿个元素，每个 HLL 固定约 12 KB——对比 Set 存 1 亿个 ID 要数 GB，差距是数量级的。
  3. 代价是近似：标准误差约 0.81%（1 亿 UV 估出 99.2M±80 万属正常）。
  4. 适合：海量 UV、IP 去重计数等允许近似的报表。
  5. 不适合：必须精确计数、需要枚举曾出现过的元素。
  6. 命令前缀 PF：纪念算法作者 Philippe Flajolet，与结构名 HyperLogLog 不同是历史习惯，别疑惑。

核心原理：直觉理解

1. 伯努利试验直觉

把每个元素哈希成比特串，观察末尾连续 0 的个数。连续 0 越长越罕见；记录见过的最大连续 0 数 k，就用 2^k 粗估基数——「见过 5 个连续 0」说明大约掷过 2^5 量级的硬币。

2. 分桶降方差

单一估计抖动太大，HLL 把哈希值前若干位作桶号，分成 2^14 = 16384 个桶，每桶各自记录最大连续 0 数，最后对全部桶取调和平均再修正——误差稳定在 0.81% 左右。

3. 内存去向

16384 桶 × 每桶 6 bit ≈ 12 KB，与数据量无关；这就是「固定内存估算海量基数」的全部秘密。

4. 两种内部表示

  • dense：12 KB 定长数组，每个桶 6 bit，始终占满 12 KB；
  • sparse：基数很小时用更省内存的稀疏列表表示，元素增多后自动转 dense（hll-sparse-max-bytes 默认 3000 字节控制转换阈值）。

对使用者透明，但解释了「新 HLL 实际占用远小于 12 KB」的现象。

5. 合并即并集

两桶对应位置取最大值就是 PFMERGE——所以「按天分 key、周报 PFMERGE」天然正确，且合并结果仍是近似误差，不会叠加放大。

6. 边界

拿不回成员（哈希不可逆）；PFCOUNT key1 key2 的多 key 形式需要临时合并，开销随 key 数上升（高版本有缓存优化），多 key 高频查询建议先 PFMERGE 落地再查。

常用命令

命令 作用
PFADD key element [element ...] 向 HLL 增加元素（可批量），返回 1 表示内部状态有变化（不等于「新增了一个不同元素」的精确判定）
PFCOUNT key [key ...] 单个或合并估算基数
PFMERGE destkey sourcekey [sourcekey ...] 合并到 dest
PFDEBUG 调试内部表示（运维向，排查 sparse/dense 状态用）

三个业务命令之外无需其他操作——HLL 不支持删除单个元素（哈希不可逆，无法「撤回」某个 ID），要重来只能 DEL 整个 key 重建。

典型应用场景

  1. 页面 / 活动 UV：PFADD uv:2026-05-03:page1 <userId 或 sessionId>，定时 PFCOUNT。
  2. 多维度合并：按天分 key，日报用 PFMERGE 聚合成周 UV。
  3. 搜索引擎独立查询词统计：每天搜索词基数，无需存词本身。
  4. 接口独立 IP 粗估：风控「该接口今天被多少不同 IP 打过」的低成本近似答案。
  5. A/B 实验触达人数：实验组/对照组各一个 HLL，合并即总体触达。
  6. 跨端去重触达：App / Web / 小程序三端各记一个 HLL，总触达 PFMERGE 三端，天然去掉「同人多端」重复。
  7. 爬虫/日志去重粗估：抓取管线按小时 PFADD crawl:{hour} <url指纹>，PFCOUNT 粗估「本小时新 URL 量级」，替代昂贵的全量布隆判重——只要趋势不要精确值时足够。

真实值 100000，估算落在 [99190, 100810] 区间即符合预期；若偏差远超，先检查是否混入了不同语义的 ID。小基数（几百以内）时 HLL 通常恰好准确——稀疏区间走专门的小基数修正（LinearCounting），别把「小规模算得准」当作「它其实是精确的」的证据。

6. 风控：接口独立 IP 粗估

「登录接口今天被多少不同 IP 打过」用于撞库/爬虫初判：平时 1 万、突然 50 万即触发告警。此处只要量级不要精确值，HLL 正好；注意同一 IP 反复出现会被去重，「请求次数」请另用 INCR 计数，两者口径不同勿混用。

7. 合并语义 ≠ 次数相加

PFMERGE 求的是并集基数，不是各 key 计数之和：day1 有 {a,b,c}、day2 有 {c,d,e}，合并基数 5 而不是 3+3=6。做周报时若产品要的是「七天人次的总和」（访问人次），HLL 给不了——那是对每天 PFCOUNT 结果求和的应用层算术，与去重口径是两回事。上报口径（去重人数 vs 人次）务必与数据需求方对齐，这是 HLL 项目最常见的返工原因。

8. A/B 实验触达人数

灰度发布、推送触达、广告曝光等「按桶分组估算人数」的场景同一套路：分桶各存 HLL，汇总用 PFMERGE，绝不直接相加。

进阶：误差为什么是 0.81%

HLL 的相对标准误差公式为 1.04 / √m，m 为桶数。Redis 固定 m = 2^14 = 16384，代入得 1.04 / 128 ≈ 0.81%——误差只由桶数决定，与数据量无关，这就是「10 个元素和 10 亿个元素误差率相同」的数学原因。桶数在实现里写死，用户不可调；要更小误差只能换算法（如 Datasketches 的 Theta），或接受它。

常见坑与注意事项

  1. 误差：报表若要求精确 UV，需 Set（内存大）或离线数仓；把 HLL 结果写进计费系统是典型误用。
  2. 元素语义：PFADD 把参数当字节串；业务上应用统一 ID（如用户 ID），勿混多种粒度（一会 userId 一会 sessionId，基数立刻失真）。
  3. 无法查询成员：不能问「谁访问过」，只能问「大约多少人」。
  4. PFADD 返回值：1 只表示「桶状态变了」，不能当「这是新用户」用——新元素落入已记录过的桶位时不返回 1，旧元素也可能偶然触发状态变化。
  5. key 数量膨胀：按「天 × 页面」分 key 时记得给明细 key 设 TTL，否则 12 KB × 天 × 页面 也会积少成多。
  6. 多 key PFCOUNT 的开销：PFCOUNT k1 k2 … kN 需临时把 N 个 HLL 合并再估，key 多时单次调用变慢；高频多维查询应先 PFMERGE 落物化 key 再单查。
  7. 稀疏 key 内存幻觉：元素少时 sparse 表示只有几百字节，别据此断言「HLL 很省所以随便建」——基数涨上来每个 key 都会爬到 12 KB，亿级 key 总量依然要规划。
  8. HLL 不是普通 String：虽然 TYPE 显示 string，但别对它 GET / APPEND——内容是二进制桶数据，读出无意义，写入会直接毁结构；运维脚本要按类型白名单跳过。

本章小结

要点 结论
定位 固定 ~12 KB 估算基数，误差 ~0.81%（16384 桶 × 6bit）
三个命令 PFADD / PFCOUNT / PFMERGE，无成员查询
原理直觉 哈希尾 0 长度 + 16384 桶调和平均；sparse→dense 自动转换
与 Set 精确去重 → Set（内存换准确）；近似报表 → HLL
与 Bitmap 位图答「谁来过」；HLL 答「多少人」
合并语义 PFMERGE = 并集基数，不等于各 key 计数相加
