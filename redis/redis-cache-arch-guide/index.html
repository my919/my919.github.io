1. 概念说明

缓存解决：数据库读压力大、热点数据响应慢。收益明显，但引入三个核心问题：一致性、击穿、雪崩。

2. 缓存读写策略

2.1 Cache Aside（旁路缓存，最常用）

为什么删缓存而不是更新缓存：删除是幂等、无并发写竞争；更新缓存会产生”中间态”。

2.2 其他策略对比

策略 说明 适用
Cache Aside 业务控制读写 默认首选
Read Through 缓存层自己查 DB 中间件封装
Write Through 先写缓存再写 DB 一致性要求高
Write Behind 先写缓存异步落 DB 写多、容忍丢

3. 缓存一致性

不一致来源：更新 DB 与删缓存不是原子的——两者之间总有时窗。

一致性取舍：缓存是”读性能换一致性”的权衡——业务上接受秒级延迟同步，就不需要分布式事务；强一致场景直接查 DB 不过缓存。

8. 典型案例：商品价格缓存一致性改造（改价后 5 分钟才生效）

问题背景：商品中心价格体系为三层缓存：Caffeine（本地 5min）+ Redis（1h）+ DB。运营在后台改价后，用户端最长 5 分钟仍显示旧价格，期间下单按旧价成交，每月产生约 300 单价格客诉；更严重的一次，某商品成本录错，调价指令发出 8 分钟后仍然在按错误价格自动下单，触发批量取消流程。

方案：按”写路径改造 + 读路径降级 + 本地缓存广播失效”三步收紧一致性窗口，把改价生效时间从 5 分钟压到 1 秒内：

层 失效机制 生效时间 兜底
DB → MQ 本地消息表（同事务） 毫秒级 扫描补偿
MQ → Redis 消费者 DEL <50ms 重试 5 次+告警
Redis → 本地 Pub/Sub 广播 evict <100ms 本地 TTL 30s 收敛
极端情况 本地 TTL 到期 ≤30s 可接受的最终一致窗口

踩坑点：

  1. 广播失效用的 Pub/Sub 没有持久化，实例发布重启期间错过的 evict 消息无法补收——本地缓存 TTL 从 5 分钟压到 30 秒作为兜底收敛，重要场景改用”实例启动时全量刷新本地缓存”。
  2. 消费者第一版重试 5 次后直接丢弃消息，某次 Redis 抖动 30 秒导致 200 个 key 没删掉，价格不一致持续到 TTL——失败必须进补偿表（定时重放），不能静默丢弃。
  3. 布隆过滤器上线时用 tryInit(10万, 1%)，半年后商品量涨到 80 万，实际误判率升到 8%，大量新商品被误拦”不存在”——布隆过滤器容量必须按预估增长留余量（按 3 倍规划），且定期重建。
  4. 改价接口高并发压测时发现”先更新 DB 再删缓存”的窗口内，读请求把旧值回填，不一致仍可能出现——对价格这类强敏感 key 加”延迟双删”（更新后 500ms 再删一次），窗口收敛到读请求耗时内。
  5. 三层缓存各自的 TTL（30s/1h/∞）没有对齐设计，排障时”哪里存的旧值”要逐层排查——建立分层 TTL 表（如上），所有缓存变更对照表执行，排查时按层定位。

9. 常见误用与陷阱

坑 现象/后果 解法
先更新缓存再更新 DB DB 更新失败后缓存是新值、DB 是旧值，回源又把旧值刷回，反复横跳 固定 Cache Aside 顺序：先更新 DB，再删缓存
删缓存失败不重试 删除静默失败，不一致持续到 TTL（可能数小时） 消息表/MQ 可靠投递 + 失败进补偿表定时重放
延迟双删的延迟时间拍脑袋（如 10s） 延迟过短覆盖不了回填窗口；过长窗口内全是脏读 延迟 ≈ 读链路 P99 耗时（几百 ms），且只对强敏感 key 启用
本地缓存多实例无失效同步 改价后部分实例仍返回旧值，问题”随机出现”难复现 Pub/Sub/广播 evict + 本地短 TTL（30s）双保险
布隆过滤器容量按当前量初始化 数据增长后误判率飙升，新数据被误拦 按 3-5 倍余量初始化；误判率写入监控；支持定期重建
空值缓存 TTL 与正常值一样长 新数据写入后 1 小时内查不到（还在空值缓存里） 空值短 TTL（60s 内）；写操作时主动 DEL 对应空值 key
命中率突然下降误判缓存失效 大批量任务启动首次预热也会拉低命中率，误触发扩容 结合 evicted_keys、TTL 分布综合判断；预热期指标单独标注
value 超大不拆分（如整个分类树 2MB） Redis 网络带宽打满、序列化 CPU 飙升、删除阻塞 大对象拆 key（按节点缓存）+ 压缩；value 上限 10KB 预警
