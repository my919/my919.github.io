1. 概念说明（导论）

Redis 是基于内存的高性能键值数据库：单线程（6.x 前）事件循环 + IO 多路复用，吞吐可达 10 万+ QPS。定位是缓存与中间件，不是主存储（数据可丢失场景除外）。

Redis 8 新增：Redis 8.0（2025 年发布）带来原生向量检索（Redis Vector Sets）、增强持久化等能力，是当前主推版本。

单机 Redis 有两大天花板：可用性（宕机全挂）和容量/吞吐（单节点上限）。进阶要解决：

  • 主从复制：数据冗余 + 读写分离（解决可用性基础）。
  • 哨兵（Sentinel）：监控主节点，宕机自动选举新主（解决自动故障转移）。
  • 集群（Cluster）：数据分片到多主多从（解决容量与吞吐）。
  • Lua 脚本：把多条命令打包原子执行（解决”检查-执行”竞态）。

11. 典型案例：商品详情缓存三件套（穿透/击穿/雪崩）整体落地

问题背景：商品服务日活 300 万，详情页读多写少（读写比 100:1）。上线初期裸查库：一次恶意爬虫扫描 20 万个不存在的商品 ID 把 DB 打挂 15 分钟；修复后又因为”热点商品缓存固定 30 分钟过期”，两次整点出现 DB QPS 瞬时 8 倍尖峰。

方案：一个缓存读接口同时防住三件事——空值缓存 + 参数校验防穿透、互斥锁防击穿、随机过期 + 多级缓存防雪崩：

威胁 触发条件 本案防护 兜底
穿透 查不存在的数据，缓存永远不命中 参数范围校验 + 空值缓存 60s 网关限流
击穿 热点 key 过期瞬间大量并发回源 SETNX 互斥锁，单线程重建 未抢到锁读旧值
雪崩 大批 key 同时过期 / Redis 宕机 TTL 加 0-5min 随机抖动 + Caffeine 前置 限流降级 + 哨兵高可用

踩坑点：

  1. 空值缓存最初设 1 小时，商家上架新商品后用户 1 小时内看不到——空值 TTL 必须短（60s 内），并配合”商品创建成功时主动 DEL 空值缓存”。
  2. 互斥锁第一版用 SETNX 不带过期时间，回源线程抛异常后锁永不释放，该商品从此全部走”没抢到锁”分支返回 null——SETNX 必须原子地设置过期（setIfAbsent(key, val, ttl)），且 finally 里 DEL。
  3. TTL 抖动写成了 random(0,300) 直接加在 30 秒的基础 TTL 上，短 TTL 数据同样整点扎堆——抖动基数应与 TTL 同量级（约 10%-20%），且所有缓存入口统一封装，不散落各处。
  4. 本地缓存 Caffeine 用了 5 分钟过期，管理后台改价后前台最长 5 分钟显示旧价——价格类敏感字段单独走”Redis 直读 + 写时主动失效”，本地缓存只放类目/标题等弱变化数据。
  5. 大促前全量预热脚本用 KEYS 遍历预加载，把生产实例阻塞 2 秒——预热必须用 SCAN 游标分批，且避开高峰执行。

21. 典型案例：ZSet 延迟队列实现订单 30 分钟未支付自动关闭

问题背景：订单超时关闭最初用定时任务每 5 分钟扫表，存在两个问题：① 最多有 5 分钟误差——第 6 分钟订单被关闭时用户刚好支付成功，需要退款流程兜底；② 订单量大时扫描本身消耗大量 DB 资源。改造成 ZSet 延迟队列：下单时精确投递，到点精准触发，误差从 5 分钟降到 1 秒内。

方案：ZSet 以”到期时间戳”为 score，消费者循环取到期元素，Lua 原子”取出+顺延”，处理失败自动重试，另有防丢标记兜底：

设计点 选择 原因
score 到期时间戳（毫秒+序列号） ZRANGEBYSCORE 按”到期时间”精准取，同毫秒防并列
原子性 Lua 打包”取出+顺延” 防多实例重复消费同一订单
可靠性 mark 标记 + 对账任务 数据淘汰/进程异常时不丢关单任务
幂等 关单前二次查支付状态 消费重试时不会关掉已支付订单
集群 key 带 hash tag {delay} 所有相关 key 同槽，Lua 可访问

踩坑点：

  1. 消费逻辑最初”ZADD 顺延”与”关单”不在一个事务里，实例在中间宕机后这批订单无人认领——靠 mark 标记 + 对账任务（每 10 分钟扫 mark 存在但队列中超期 5 分钟的订单）兜底重投。
  2. Lua 脚本第一版里写了 redis.call('GET', 'order:'..id) 拼动态 key，Cluster 下报 Lua script attempted to access a non local key——Lua 只能访问 KEYS[] 里声明的同槽 key，相关业务 key 统一带 {delay} tag。
  3. 到期时间用秒级时间戳，同一秒的订单 score 相同，ZRANGEBYSCORE 返回顺序不稳定，对账时误以为”漏单”——score 用毫秒并叠加序列号保证唯一可排序。
  4. 上线后历史积压 400 万条过期任务，每轮 LIMIT 0 100 要 11 小时消化完——消费循环改动态批量（积压多时单轮 2000 条），并给队列长度加告警。
  5. 该 ZSet 实例配了 allkeys-lru 且内存告急，延迟队列冷数据被淘汰导致部分订单没被关闭——不可丢的队列数据要与可淘汰缓存分实例部署（队列实例用 noeviction）。

22. 常见误用与陷阱

入门篇

坑 现象/后果 解法
SETNX 抢锁不设过期时间 持锁线程崩溃后锁永不释放，业务全被”没抢到锁”分支卡死 setIfAbsent(key, val, ttl) 一条命令原子完成；finally 中 DEL
锁的 value 不带身份标识 A 超时后 B 拿到锁，A 恢复后误删 B 的锁，并发重新发生 value 存唯一 ID（UUID+线程 ID），释放用 Lua 校验身份再删
先删缓存再更新数据库 并发读把旧值重新填回缓存，不一致持续到过期 Cache Aside 固定顺序：先更新库，再 DEL 缓存；敏感场景延迟双删
INCR 计数器不设 TTL 统计类 key 只增不减，内存缓慢耗尽开始淘汰 计数器创建即 INCR key; EXPIRE key 86400（仅首次设 TTL）
缓存对象用 JDK 序列化 value 二进制不可读、跨语言不兼容、类结构变更后反序列化失败 统一 JSON（Jackson），配合 @JsonIgnore 排除敏感字段
TTL 一刀切无抖动 整点大批 key 同时过期，DB 瞬时尖峰（雪崩） TTL 基础值 + 10%~20% 随机；热点再叠互斥锁
用 KEYS 做运维遍历 全库扫描阻塞主线程，线上卡顿 SCAN 游标 + COUNT 分批；redis.conf 里 rename-command 禁用 KEYS
缓存与 DB 双写不一致（并发写） 两个写请求交错，缓存存的是先写请求的旧值 写操作按业务主键加锁或用 binlog 订阅（Canal）串行失效缓存

进阶篇

坑 现象/后果 解法
Lua 脚本访问 KEYS 之外的动态 key Cluster 下报 non-local-key 错误，或脚本无法 EVALSHA 复用 所有 key 通过 KEYS[] 传入且同槽；参数用 ARGV 传
Lua 脚本里写大循环/大集合操作 单线程执行长脚本，期间所有请求阻塞 脚本控制 O(小常数)：LIMIT 限量、循环上限固定，超 1ms 拆批
Stream 消费不 XACK PEL 里 unacked 消息无限堆积，重投风暴 + 内存上涨 处理成功立即 XACK；配 XAUTOCLAIM 接管超时消息
延迟队列/计数器与缓存同实例 内存紧张时被 allkeys-lru 淘汰，任务/计数凭空消失 可靠数据与缓存分实例；队列实例 noeviction + 容量告警
ZSet score 用秒级/重复值 同分元素顺序不稳定，业务误判漏处理 score 用毫秒+序列号保证唯一；按 score+member 排序
从节点读延迟队列/锁状态 主从复制延迟下读到旧状态，误判”未处理/未持锁” 状态判断一律读主节点；从节点只放展示类弱一致读
EVAL 每次传全文不缓存脚本 大脚本每秒传几十 KB，网络与解析开销浪费 SCRIPT LOAD 预热 + EVALSHA 摘要执行
repl-backlog 配太小 从库短暂断线触发全量同步，主库 fork + 全网传输抖动 生产 64MB 起步，断线频繁加大到 256MB+
