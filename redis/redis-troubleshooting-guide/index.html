为什么删除用 UNLINK 不用 DEL：DEL 大 key 是 O(N) 且阻塞主线程（几十毫秒到秒级）；UNLINK 把释放内存交给后台线程，主线程立即返回。

5. 慢查询排查

6. 连接数打满

为什么连接数会打满：应用连接池配置错误（无上限/泄漏）或 DB 连接池问题波及 Redis 客户端——连接是有限资源，必须”应用侧限流”。

7. 持久化阻塞（fork 停顿）

处置：关闭自动 RDB（save ""）改主从 + AOF；或调低 save 频率；大实例（> 10GB）高峰期不触发 bgsave。

踩坑点：

  1. 定位初期值班直接跑 MONITOR 想抓热点，结果 MONITOR 自身又给 100% CPU 的节点加了 15% 负载，超时率短时冲到 40%——MONITOR 必须加 timeout 且只抓几秒，或改用客户端埋点/hotkey 探测。
  2. 运营的 KEYS 清理脚本”上周就上过线”没事，是因为平时 key 少；大促写入量暴增后全库扫描耗时翻 20 倍——平时无恙的操作不等于安全，容量变化会让 O(N) 命令从”慢”变”事故”。
  3. 加本地缓存时忘了秒杀库存扣减仍在 Redis，本地缓存的”剩余件数”最多滞后 10 秒，前端显示有货但下单失败——展示字段与交易字段分离：展示走本地缓存，扣减走 Redis 原子操作。
  4. 处置时先扩容后治理（先升配分片 2），结果 KEYS 任务还在持续运行，扩容只是把阻塞从”卡死”变”卡顿”——慢命令不消灭，扩容只是延缓崩溃。

11. 常见误用与陷阱

坑 现象/后果 解法
生产环境用 KEYS * O(N) 全库扫描阻塞主线程，几 GB 实例一次阻塞数秒，所有请求排队 一律改 SCAN（游标分批），运维脚本上线前过 Redis 命令评审
MONITOR 长时间开启 监控命令本身吃掉 15%+ 性能，高峰期越排障越慢 timeout 3-5 限时抓取；长期观测用 hotkey 探测/客户端埋点
DEL 删大 key 主线程同步释放内存，10 万元素集合 DEL 阻塞数百毫秒 统一用 UNLINK（异步释放）；批量清理用 SCAN + 小批 UNLINK
排障只看内存不看 CPU 分布 热 key 把集群单分片 CPU 打 100%，”集群总 CPU 正常”掩盖问题 监控按分片粒度告警；大促前压测识别热点并提前上本地缓存
淘汰策略配 noeviction 写多场景 内存满后所有写入报 OOM 错误，业务大面积失败 缓存场景用 allkeys-lru；持久化数据场景拆库扩容而不是靠淘汰
大 key 排查依赖 DEBUG OBJECT 该命令不稳定且暴露内部信息，部分云厂商禁用 用 MEMORY USAGE key（官方推荐）或 redis-cli --bigkeys
SLOWLOG 阈值默认 10ms 不调整 微秒级抖动看不出趋势，慢命令识别滞后 阈值调到 5ms 并接入告警；slowlog-max-len 调到 256 保留现场
缓存 key 无 TTL 只进不出，内存缓慢涨满后开始淘汰，命中率崩、数据”莫名消失” 代码审查强制：缓存 key 必须设 TTL；定期扫无 TTL 的 key 补过期
