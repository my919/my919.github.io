第二章：Redis String 数据类型：概念、命令与案例

发表于 2026-05-03 更新于 2026-10-29 分类于 Redis 缓存 本文字数： 5.1k 阅读时长 ≈ 5 分钟

第二章：Redis String 数据类型：概念、命令与案例

概念基础

String 是 Redis 最基本的值类型——一个 key 对应一个字符串值：

  1. Redis 是 KV 模型：键（key） 永远是字符串；值（value） 可以是 String / Hash / List 等类型之一。
  2. 本文说的 String 指 value 的类型为 string（TYPE key 显示 string）。
  3. 二进制安全：值可以是任意字节序列——文本、JSON、序列化对象，甚至图片字节，不需要担心内容里出现特殊字符。
  4. 容量上限：单个 String 最大 512 MB，但业务上应把「大 value」视为反模式（见注意事项）。
  5. 编码：底层可能为 int、embstr、raw 等（OBJECT ENCODING key 可查看），对使用者多数时候透明，选型时更关心语义与命令（原理见下一节）。

核心原理：编码与底层结构

  1. SDS（简单动态字符串）：Redis 的字符串不是 C 语言以 \0 结尾的字符数组，而是自研的 SDS 结构——头部记录已用长度与剩余空间，因此 STRLEN 是 O(1)；追加时可预分配空间减少 realloc；内容可含 \0，这是「二进制安全」的基础。
  2. 三种编码与转换：
    • int：值是能放进 64 位有符号整数的数字（如 INCR 计数器），直接存整数，最省内存。
    • embstr：短字符串（≤ 44 字节），redisObject 与 SDS 一次性分配在一块连续内存，读多写少时最省且缓存友好；embstr 是只读的，一旦修改就转成 raw。
    • raw：长字符串（> 44 字节）或被修改过的短字符串，SDS 独立分配，支持高效追加。
  3. 观察方法：
  1. 内存账：同样是 100 万个小 key，编码差异能拉开明显内存差距——int 编码的计数器 key 几乎只有 redisObject 与 dictEntry 开销；raw 长字符串 还要叠一份独立 SDS。海量 key 场景先用 MEMORY USAGE key 抽查，再决定要不要「多 key 合并成 Hash」（见第四章）。
  2. 原子性：命令单线程执行，INCR、SET key val NX 等都是原子操作——这就是「计数器」和「占位锁」不惧并发的根本原因，不需要应用层再包一层锁。

常用命令（必会子集）

1. 读写与删除

MSET / MGET：一次多键，减少往返（注意原子性与键命名规范）。

2. 带条件的写入与过期（业务高频）

SET 常用选项（Redis 2.6+ 语法，具体以你版本文档为准）：

选项 含义
EX 秒 / PX 毫秒 设置过期时间（TTL）
NX 仅当 key 不存在 时写入（常用于抢锁占位）
XX 仅当 key 已存在 时覆盖
KEEPTTL（6.0+） 覆盖时保留原 TTL，不再被默认清空
GET（6.2+） 返回旧值，等价 GETSET 合并进 SET

3. 计数器：INCR / DECR / INCRBY

INCR 在值可解析为整数时原子自增；不存在时按 0 开始。

4. 其它实用命令

命令 作用
APPEND 尾部追加字节
STRLEN 返回字节长度
GETRANGE / SETRANGE 按偏移读写子串（仍整体是 String）
GETSET / GETEX 读旧值并写新值 / 读值并改过期（6.2+，适合做「读后刷新 TTL」的会话续期）

典型应用场景

  1. 缓存整页或对象：值存 JSON 字符串，配合 EX 做短期缓存；更新数据库后删键或覆盖避免脏读。
  2. 会话 / 登录态：SET … EX … 存 token → 用户信息；过期自动消失；续期用 GETEX key EX 3600 一步完成「读 + 续期」。
  3. 计数与限流：INCR 做浏览量、接口调用次数；与滑动窗口等逻辑配合（复杂限流可再引入 Hash / ZSet）。
  4. 分布式锁（谨慎）：SET key token NX PX ttl 仅占位；完整锁需唯一 token、Lua 校验身份释放、续期、Redlock 争议等专题，本文给最小正确版（见案例 3）。
  5. 配置与功能开关：SET feature:x:enabled 1，读时 GET 转布尔。

维度 Redis String MySQL

口诀：热、快、可丢的放 Redis；准、稳、要审计的放 MySQL。

注意事项与选型

  1. 大 value：单 String 过大占用内存与网络带宽，序列化大对象可评估 Hash 分字段或拆 key；超 10 KB 的 value 就该警觉。
  2. 热 key：同一 key 超高并发时，单线程处理该 key 易成瓶颈，需业务侧分片（如 views:{id}:{shard} 写时分片、读时求和）或换结构。
  3. KEY 命名：建议 业务:实体:id:属性 一类可读前缀，避免全局 KEYS * 在生产使用（用 SCAN MATCH）。
  4. 持久化与丢失：String 在内存里，是否落盘取决于 RDB/AOF 与策略；缓存≠数据库，关键数据以库为准并设计降级。
  5. 字符集：Redis String 是字节；UTF-8 文本由客户端编码/解码，不要在服务端假设「一定是中文几个字符」与字节长度一一对应。
  6. TTL 覆盖：SET 不带 KEEPTTL 会清掉旧 TTL，「更新缓存却意外变永久」是高频事故；6.0+ 记得加 KEEPTTL 或重写时重设 EX。
