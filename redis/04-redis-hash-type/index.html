第四章：Redis Hash 数据类型：概念、命令与案例

发表于 2026-05-03 更新于 2026-10-25 分类于 Redis 缓存 本文字数： 6.5k 阅读时长 ≈ 6 分钟

第四章：Redis Hash 数据类型：概念、命令与案例

概念基础

Hash 是「key → 若干 field/value 对」的映射，类似一张微型数据行或一个对象文档：

  1. 一个 key 下挂多对 field / value，field 与 value 均为字符串（二进制安全）。
  2. TYPE key 显示 hash。
  3. 与 String 存 JSON 的区别：String 改一个字段要「读出 → 反序列化 → 改 → 序列化 → 写回」四步，Hash 只需 HSET 一个 field——这就是「局部更新」的价值。
  4. 适合「用户资料、购物车行、配置项分组」等属性较多且常单独更新的场景。
  5. 字段级过期：Redis 7.4 起（含 8.x）Hash 支持字段级 TTL（HEXPIRE / HPEXPIRE / HTTL），可让同一 Hash 内不同字段有不同生命周期；旧版本只能对整个 key 设 EXPIRE，这是选型时容易忽略的版本差异点。

核心原理：编码与底层结构

1. 两种编码（OBJECT ENCODING key 可观察）

  • listpack（Redis 7.0 前为 ziplist）：字段少且值短的紧凑编码，所有 field/value 连续存放，省内存但对中间元素的访问是 O(N)——靠「元素少」保证不慢。listpack 是一段连续字节数组，每个 entry 记录自身长度与编码类型，无指针开销，这正是它比 hashtable 省内存的原因。
  • hashtable：字典结构，field → value 的 O(1) 哈希访问。

2. 编码转换阈值

任一条件超出即从 listpack 转 hashtable（默认如下，以 CONFIG GET hash-max-listpack-* 为准）；转换是单向的，转回不再发生：

配置项 默认值 含义
hash-max-listpack-entries 128 字段数超过该值即转换
hash-max-listpack-value 64（字节） 任一 field 或 value 超过该长度即转换

3. 渐进式 rehash

hashtable 扩容时 Redis 同时持有两张哈希表，把数据分批从旧表搬到新表（每次命令顺带迁一小批 + 定时任务），避免一次搬家阻塞服务——这是单线程 Redis 能平滑扩容的关键设计。

4. 时间复杂度表

命令 复杂度 说明
HSET / HGET / HDEL（单字段） O(1) 多字段形式为 O(N)，N 为本次字段数
HINCRBY / HINCRBYFLOAT O(1) 原子字段加减
HEXISTS / HLEN / HSTRLEN O(1) 判存在 / 字段数 / 值长度
HMGET / HMSET O(N) N 为本次字段数
HGETALL / HKEYS / HVALS O(N) N 为总字段数，大 Hash 慎用
HSCAN 单次 O(1) 级别 分批游标遍历，生产遍历大 Hash 的唯一正确姿势

5. 内存占用对比：一个 Hash vs 拆成多个 String key

「100 个字段放一个 Hash」与「100 个 String key」的内存差距主要来自 key 头开销：每个 String key 都有 redisObject、SDS、dictEntry 等固定成本（约 50~90 字节/key），而 Hash 在 listpack 编码下 field/value 是纯数据连续存放。字段多而值短的对象，Hash 明显更省；反之字段少、值大时两者差距不大，按语义选。

常用命令（必会子集）

命令 作用
HSET key field value [field value …] 设置一个或多个字段（Redis 4.0+ 推荐 HSET 多字段；旧 HMSET 已废弃）
HGET / HMGET / HGETALL 读单字段 / 多字段 / 全表
HDEL 删字段
HEXISTS / HLEN 字段是否存在 / 字段个数
HINCRBY / HINCRBYFLOAT 字段数值原子增减
HSETNX 字段不存在才写入（字段级「占位」）
HSCAN 大 Hash 迭代遍历（生产避免 HGETALL 撑爆网络）
HEXPIRE / HTTL Redis 7.4+/8.x：字段级过期与剩余 TTL 查询

典型应用场景

  1. 用户资料：user:1001 下 name / vip / city 等，改一项只动一个 field。
  2. 购物车行：cart:uid:1001 下 sku:2001 → 数量，加购 HINCRBY、删 SKU HDEL、清空 DEL。
  3. 对象缓存：比整串 String 更易做局部更新；仍要注意过期策略与缓存一致性。
  4. 多维计数器：article:42 下 views / likes / comments 三个字段分别 HINCRBY，比三个独立 String key 省内存、好管理。
  5. 分布式会话属性：会话主键 + 若干部件（角色、权限快照），配合 Redis 8 的字段级 TTL 做「部分字段先过期」。
  6. SKU 库存与销量双记：sku:2001 下 stock / sold 两字段，下单 HINCRBY stock -1 后判负回滚——简单场景的轻量库存方案（高并发超卖控制仍需 Lua 或队列）。
  7. 配置分组：config:pay 下挂 timeout / retry / channel 等开关，改一项 HSET 即刻生效，比重载配置文件轻得多。

5. 对象缓存：Cache Aside 读写流程

Hash 做对象缓存时的标准姿势是 Cache Aside（旁路缓存）：

为什么「先写库、后删缓存」而不是反过来：反过来在并发下存在「缓存已删、旧值被另一读请求回填」的脏读窗口；先写库后删，窗口只剩「删之前的一小段读旧值」，工程上可接受。要求更高时再上延迟双删或订阅 binlog 失效。

6. 内存实测：Hash vs 多 String key

字段越多、值越短，Hash（listpack 编码）的内存优势越大；这就是「海量小对象缓存」优先 Hash 的量化依据。

7. 读全表还是读部分：HGETALL 与 HMGET 的网络成本

HGETALL 把全部字段一次性扛回客户端，字段多、值大时网络与反序列化开销不小；列表页只展示 3 个字段时应 HMGET key f1 f2 f3 按需取。运维排查看大 Hash 时用 HSCAN 分批，勿在高峰期 HGETALL。

8. 字段级占位：HSETNX 抢占唯一资源

相比「每用户名一个 String key + SET NX」，所有用户名收进一个 Hash 内存更省、管理更集中；注意该 Hash 会随注册量增长，超大时按首字母拆 key。

维度 Redis Hash MySQL 行

实践中常见组合：MySQL 为准，Redis Hash 为缓存镜像，写库后删/改缓存字段。

常见坑与注意事项

  1. 大 Hash：字段极多时 HGETALL 成本高（O(N) 且一次扛回全量字节），列表页用 HSCAN 或只取需要的 HMGET；字段数上十万时应拆 key。
  2. 热 key：单个大 Hash 被全站高频读写会成为单点瓶颈，按业务维度拆分（如 user:{id} 天然分片）。
  3. 滥用 KEYS：排查 Hash key 时勿在生产 KEYS user:*，用 SCAN MATCH user:* COUNT 100。
  4. 错误选型：对象总是整体读写、从不久局部更新 → 用 String JSON 更简单；字段需要独立过期（< 7.4）→ Hash 做不到，只能拆 String key。
  5. 小 Hash 编码：字段少且短时可能 listpack 等紧凑编码，内存更省（OBJECT ENCODING 可观察）；超阈值转 hashtable 后内存上升属预期，不是泄漏。
  6. 与 String JSON 选型：读多写少、整体替换频繁 → String；字段独立更新多 → Hash。
  7. 缓存三兄弟：Hash 缓存同样要面对穿透（查不存在的数据，缓存空值或布隆过滤）、击穿（热 key 过期瞬间被打爆，加互斥重建）、雪崩（大量 key 同刻过期，TTL 加随机抖动）——结构选型救不了这三件事，要在读写流程里处理。
  8. TTL 只挂在 key 上（<7.4）：旧版本给单个 field 设过期是做不到的，误信「HSET 带 EX」会留下永不过期的脏字段；7.4+ 用 HEXPIRE，旧版本只能拆 String key。

本章小结

要点 结论
本质 key → 多对 field/value，像「数据行」
编码 listpack（小而省）→ hashtable（O(1) + 渐进式 rehash），阈值 hash-max-listpack-entries 128 / -value 64
复杂度 单字段 O(1)；HGETALL O(N)，大 Hash 用 HSCAN
高频命令 HSET / HGET / HGETALL / HINCRBY / HDEL / HEXPIRE（7.4+）
选型 字段常单独更新 → Hash；整体读写 → String JSON
