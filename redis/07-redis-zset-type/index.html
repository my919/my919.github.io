第七章：Redis ZSet 数据类型：概念、命令与案例

发表于 2026-05-03 更新于 2026-10-25 分类于 Redis 缓存 本文字数： 6.2k 阅读时长 ≈ 6 分钟

第七章：Redis ZSet 数据类型：概念、命令与案例

概念基础

ZSet（Sorted Set，有序集合）给每个成员挂一个分值（score），集合内部始终按 score 排序：

  1. TYPE key 为 zset。
  2. member 唯一；同一 member 再次 ZADD 会更新 score（不是报错、也不是新增——这是「改积分」的基础语义）。
  3. 排序方向：score 从小到大是「正序」；排行榜通常要 ZREVRANGE 降序取 Top N。
  4. 范围查询、排名 ZRANK/ZREVRANK 为高频 API——「第几名」「前 100 名」「积分区间成员」都是 O(logN) 级别的现成能力，这是 Set 给不了的。
  5. score 相同按 member 字典序排序——排行榜想打破并列，可把「先到先排前」编码进 member 或微调 score（如整数积分 + 小数时间戳倒数）。

核心原理：跳表与双结构

1. 两种编码

元素少且成员短时用 listpack（7.0 前 ziplist），阈值默认 zset-max-listpack-entries 128、zset-max-listpack-value 64；一般情况用 skiplist 编码（OBJECT ENCODING 可查）。

2. skiplist 编码 = 双结构

同一份数据同时挂在两个索引上：

  • 跳表（zskiplist）：按 score 排序的有序跳表，负责 ZRANGE / ZRANGEBYSCORE / ZRANK 等范围与排名操作，复杂度 O(logN)。每个节点带随机层数（Redis 中约 1/4 概率升层，最大 32 层），高层是「快车道」，查找时从顶层逐层下沉。
  • 字典（dict）：member → score 映射，负责 ZSCORE 这类按成员查分值的 O(1) 操作。


flowchart LR
  Z[ZSet key] --> S[skiplist 按 score 排序<br/>范围 / 排名 O logN]
  Z --> D[dict: member→score<br/>查分 O 1]

3. 为什么用跳表而不是平衡树

范围查询同样高效、实现远比红黑树简单（无旋转）、节点上的 span 跨度字段让「按排名定位」天然支持（这是 ZRANK O(logN) 的关键）——是工程权衡的典型案例。

4. 时间复杂度表

命令 复杂度 说明
ZADD / ZREM / ZINCRBY O(logN) 跳表定位
ZSCORE O(1) 走 dict
ZRANK / ZREVRANK O(logN) span 字段累加得名次
ZRANGE / ZREVRANGE O(logN + M) M 为返回元素数
ZRANGEBYSCORE O(logN + M) 范围扫描
ZCARD O(1) 计数有缓存
ZPOPMIN / ZPOPMAX O(logN) 延时队列取任务常用
ZUNIONSTORE / ZINTERSTORE O(N)+O(M·logM) 多榜聚合，大集合慎实时算

5. score 精度与并发安全

score 是 double，能精确表示的整数范围约 2^53；时间戳做 score 时统一毫秒或秒，避免大数值浮点误差。ZADD 更新、ZINCRBY 加分都是单线程原子操作，排行榜「并发刷分」不丢更新。

常用命令（必会子集）

命令 作用
ZADD key score member 添加或更新分值（支持 GT/LT/NX/XX 条件）
ZRANGE / ZREVRANGE 按排名升/降序取片段（WITHSCORES 带出分数）
ZRANGEBYSCORE 按 score 区间取（( 表开区间，-inf/+inf 表无穷）
ZRANK / ZREVRANK 升序 / 降序名次（0 基）
ZSCORE / ZCARD / ZINCRBY 查分 / 成员数 / 原子加分
ZREM / ZPOPMIN / ZPOPMAX 删除成员 / 弹出最小/大
ZUNIONSTORE / ZINTERSTORE 多榜聚合（如日榜合周榜）

典型应用场景

  1. 游戏 / 活动排行榜：member=用户 ID，score=积分。
  2. 延时任务：score=执行时间戳，定时 ZRANGEBYSCORE 拉到期任务再 ZREM。
  3. 热搜权重：结合时间衰减可周期性重算 score（逻辑在应用层）。
  4. 滑动窗口限流：member=请求 ID/时间戳，score=时间戳，ZREMRANGEBYSCORE 清窗口外 + ZCARD 判定——精确滑窗的经典实现。
  5. 优先级队列：ZPOPMIN 取最紧急任务（score 越小越优先）。

4. ZADD 条件选项：只在更高分时更新

比「先 ZSCORE 比较再 ZADD」少一次往返且无竞态——「只刷新纪录」类需求请直接用选项，不要应用层判断。

5. 多榜聚合：日榜合成周榜

AGGREGATE SUM/MIN/MAX 可选聚合方式（默认 SUM）。日榜 key 各自设 TTL，周榜随算随弃，存储可控。

6. 榜外用户查名次：Top 页 +「我的位置」

这是排行榜产品的标准两段式：窗口数据走 ZREVRANGE 分页，个人位置走 ZREVRANK + ZSCORE，不要为找一个人把全榜拉回客户端。

7. 热搜榜：时间衰减的落地写法

「热度 = 近期行为 × 衰减系数」是热搜/热门商品的通用模型：写入用 ZINCRBY 累积，周期任务用 Lua 批量乘衰减系数——Lua 保证整个重算原子完成，中途无半新不旧的榜单被读到。

进阶：跳表节点与层数

跳表节点（zskiplistNode）含 score / member / 后退指针 / 多层 level，每层记录 forward 与 span（跨度）；ZRANK 即沿查找路径累加 span 得名次，故为 O(logN)。升层概率约 1/4、最大 32 层——千万级元素下期望层数仍很小，查找路径短。编码阈值：

常见坑与注意事项

  1. 热 key：单排行榜 key 超高并发时考虑分片（如 board:{shard} 再聚合）或本地缓存 + 合并。
  2. 大 ZSet：避免一次 ZRANGE 0 -1；分页用 ZRANGE 窗口。
  3. score 精度：浮点比较注意误差；时间戳建议统一毫秒或秒。
  4. 并列排名：score 相同按字典序，业务若要「先到先排前」需自行编码（如 score = 积分 + (1 - ts/1e13)）。
  5. 滥用 KEYS：线上排查榜类 key 用 SCAN MATCH board:*，勿 KEYS *。
  6. 区间符号：ZRANGEBYSCORE key (100 200 的 ( 表开区间，写错开闭导致边界成员多算/漏算；-inf / +inf 表无穷，延时队列拉全量到期任务时别写成 0 +inf 漏掉历史脏数据。
  7. ZINCRBY 浮点累加：score 是 double，频繁小数加分可能积累浮点误差；金额类积分用「分」为单位的整数，展示时再除。
