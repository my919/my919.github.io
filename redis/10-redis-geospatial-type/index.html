发表于 2026-05-03 更新于 2026-10-25 分类于 Redis 缓存 本文字数： 6.6k 阅读时长 ≈ 6 分钟

第十章：Redis Geospatial：概念、命令与案例

概念基础

Geospatial（GEO） 是 Redis 的地理位置模块——存经纬度坐标，提供「附近有什么」「两点距离多远」的原生查询能力：

  1. 数据仍落在 ZSet 上：TYPE key 一般为 zset；member 为地点 ID，score 为 Geohash 编码（使用者通常只调 GEO 命令）。
  2. 坐标使用经度、纬度（GEOADD 参数顺序为 lon lat，勿写反——这是 GEO 最常见的第一个坑）。
  3. 它是 第七章：Redis ZSet 数据类型：概念、命令与案例 的空间特化：排序键从「积分」变成了「地理位置编码」，排序即「从西到东、从南到北」，近邻查询就是一次score 范围扫描。
  4. 地球模型为球面近似，极高精度场景需自行评估误差。
  5. 合法坐标范围：经度 [-180, 180]、纬度 [-85.05112878, 85.05112878]（Web 墨卡托边界），越界写入会报错。

核心原理：Geohash 编码与近邻查询

1. Geohash 编码

把经度区间 [-180,180]、纬度区间 [-90,90] 反复二分——经度偏西记 0、偏东记 1，纬度偏南记 0、偏北记 1，两边比特交错拼成一串二进制。二分越深，编码越精确。

2. 为什么「二分交错」有效

交错后，前缀相同的两个编码，地理位置必然相近；编码的大小顺序 ≈ 地理位置顺序。Redis 把这个二进制串转成 52 位整数作为 ZSet 的 score——于是「附近查询」变成了「score 在邻域区间内的范围扫描」，完全复用跳表的 O(logN) 能力（这正是第七章双结构的红利）。

3. 距离计算

GEODIST 用球面距离（Haversine 类公式）计算两点弧长，可选 m / km / ft / mi 单位；成员不存在返回 nil。

4. API 演进

Redis 6.2+ 推荐 GEOSEARCH（支持 BYRADIUS / BYBOX、ASC/DESC、COUNT、带 WITHDIST/WITHCOORD/WITHHASH），GEORADIUS / GEORADIUSBYMEMBER 已被视为过时接口；GEOSEARCHSTORE 可把结果直接落到新 key。新代码优先 GEOSEARCH 系列。

5. 时间复杂度

命令 复杂度 说明
GEOADD O(logN) 每成员 本质是 ZADD
GEOSEARCH O(N + logN·M) 级 N 为返回数，邻域扫描
GEODIST / GEOPOS / GEOHASH O(1) 查分/解码

常用命令

命令 作用
GEOADD key lon lat member [lon lat member …] 添加或更新坐标
GEODIST key m1 m2 [单位] 两点距离；单位 m / km / ft / mi
GEOSEARCH key FROMLONLAT lon lat BYRADIUS r km 以坐标为中心查半径内成员（6.2+ 推荐）
GEOSEARCH key FROMMEMBER m BYBOX w h km 以成员为中心查矩形范围
GEOSEARCHSTORE dest src … 把查询结果落到新 key（可 STOREDIST）
GEORADIUS / GEORADIUSBYMEMBER 旧接口，新代码勿用
GEOPOS / GEOHASH 取坐标 / Geohash 字符串

典型应用场景

  1. 附近门店：GEOADD shops …，用户定位后 GEOSEARCH 取 3 km 内门店按距离升序。
  2. 配送范围校验：GEODIST 与阈值比较，或 GEOSEARCH FROMMEMBER user BYRADIUS 3 km 看骑手是否在圈。
  3. 附近的人/动态：社交 App 把用户实时位置定期 GEOADD，下拉刷新时 GEOSEARCH。
  4. 共享单车/充电宝点位：车锁开关闭合时上报坐标，找车页 GEOSEARCH BYRADIUS 1 km。
  5. 同城内容粗筛：动态发布时 GEOADD 到 feed:geo:{city}，同城 Tab 按用户坐标拉附近动态 ID 再回库。
  6. 与外部地图：Redis 做粗筛（候选集），精确路径规划与 ETA 交给地图 API。

3. 「附近的人」：位置更新与离线清理

要点：更新即 GEOADD 重写、下线即 ZREM；另可给 key 本身或业务层「最后活跃时间」配合定时任务清扫僵尸位置，避免「附近的人」里躺着三天前的幽灵坐标。

4. GEOSEARCHSTORE：结果物化与分页

适合「用户原地翻页」场景：第一次查算邻域，后续翻页零地理计算；用户移动了再重算。

5. 城市分片：多 key 路由

分片把单 key 规模锁在「一城 POI 量级」，跨城查询（少见）由应用层并发查多个 key 再归并；这也是第七章「热 key 分片」思路在 GEO 上的复用。

6. 配送范围校验：GEODIST 判圈

注意 GEODIST 是直线球面距离，真实骑行距离更长——阈值要按「直线 × 绕行系数（常取 1.3~1.5）」校准，或候选通过后再调地图 API 算路网距离二次过滤。

7. 与 ZSet 命令混用：清点城市存量

这条「混用通道」是 GEO 运维的常备手段：计数用 ZCARD、删除用 ZREM、遍历用 ZSCAN；只读坐标才走 GEOPOS。

进阶：52 位 Geohash 的精度账

score 用 52 bit：经纬度各 26 bit 交错。经度 360° / 2^26 ≈ 5.4×10^-6°，对应地面约 0.6 m——编码分辨率远高于手机定位精度（通常 5~50 m），所以瓶颈在定位信号，不在 Redis 编码。GEO 系列查询的网格边界效应（同一格子两端可能被算作远邻）由 Redis 内部「查 8 邻域格子」抹平，业务无需处理；但跨 ±180° 经线与两极附近邻域拼接有边界效应，常规城市业务无感。

典型分工：Redis GEO 做实时粗筛（「3 km 内候选骑手」），PostGIS/地图 API 做精算（「沿路网最快 12 分钟」）。

常见坑与注意事项

  1. 经度纬度顺序：lon 在前 lat 在后；写反后不会报错，但查询结果全错——录入后立即 GEOPOS 抽检一个点。
  2. 跨版本 API：Redis 6.2+ 引入 GEOSEARCH 等，生产以当前版本文档为准；Redis 8.x 下旧 GEORADIUS 仍兼容但应迁移。
  3. 数据量：全国级 POI 全进一个 key 可能过大，可按城市分片多个 GEO key（shops:sh / shops:bj），查询时按用户所在城市路由。
  4. 位置更新频率：「附近的人」类业务若每秒 GEOADD 百万次，写放大明显；应降频上报（如移动超 200 m 才更新）并给不活跃成员 ZREM 清理。
  5. 本质是 ZSet：可直接用 ZREM / ZCARD 管理成员；但不要直接 ZADD 数字 score——会破坏 Geohash 语义。
  6. 两极与 180° 经线：Geohash 在经度 ±180° 与纬度极限附近有边界效应，普通业务（城市内）无感，跨国/极地场景需评估。
  7. 坐标系一致性：国内地图常用 GCJ-02（火星坐标），GPS/海外 API 多为 WGS-84，两者同一地点可差数百米——入库前必须统一到同一坐标系，否则 Redis 里的「附近 500 m」全错；且 Redis 不做坐标转换，转换在接入层完成。
  8. GEODIST 的 nil：任一成员不存在返回 nil 而非报错，应用层判空别当成 0 距离；门店被 ZREM 下架后未同步清理依赖方就会出现这种情况。
  9. GEOADD 是「添加或更新」：同 member 重写坐标不报错——这既是更新手段也是坑，写入前确认 member 命名唯一（如统一 store:{id}），误用同名 member 会静默覆盖别人坐标。

本章小结

要点 结论
本质 ZSet 的空间特化：score = 52bit Geohash
近邻查询 编码前缀近 → 位置近；查询 = score 范围扫描
高频命令 GEOADD / GEODIST / GEOSEARCH（6.2+）/ GEOSEARCHSTORE / GEOPOS
易错点 lon 在前 lat 在后；新代码用 GEOSEARCH
边界 球面近似粗筛；导航精度交给地图 API
