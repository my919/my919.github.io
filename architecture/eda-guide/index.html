9. 典型案例：事件驱动订单系统

问题背景：外卖平台下单链路原先同步串行调用 6 个下游（库存、优惠券、积分、通知、风控、发票）：一个接口 5 层 HTTP 嵌套，P99 2.8s；任一下游抖动，下单整体失败率飙升。营销活动还要求”积分服务可以挂，下单不能挂”。

方案：下单核心（库存+订单）保持强一致，其余下游全部事件化解耦，复杂流程用 Temporal 编排：

改造项 改造前 改造后
下游依赖 同步 5 层调用，全链路同生共死 核心同步 1 次，其余事件异步
下游故障 下单整体失败 消费重试/重放，下单不受影响
新增下游 改下单代码 + 联调上线 订阅 topic 即可，发布方零改动
P99 2.8s 180ms（同步部分）

关键设计：

踩坑点：① 早期事件没带 eventId，Kafka at-least-once 重投导致积分翻倍发放——消费必须幂等（唯一键去重）。② 事件无版本演进：加字段后老消费者反序列化崩溃——Schema Registry + 向后兼容策略强制卡点。③ 「订单已创建」事件被库存服务当 RPC 响应反向回查发布方接口，耦合回来了——事件只携带消费所需最小事实，缺数据由消费方自查。④ 事务内直接 kafkaTemplate.send()，事务回滚了消息却发出去了——一律走事务发件箱（outbox）模式。⑤ Temporal Workflow 里写了非幂等的本地副作用，Worker 重放历史时重复执行——Activity 要幂等，副作用放 Activity 不放 Workflow 主干。

10. 常见误用与陷阱

坑 现象/后果 解法
事件无版本 加字段导致老消费者反序列化崩溃 Schema Registry + 向后兼容策略
消费不幂等 重复投递 → 积分/库存重复处理 eventId 唯一约束去重
消费不可重入 重放 offset 就产生二次副作用 副作用幂等设计 + 处理标记表
事务内直接发消息 事务回滚但消息已发出 事务发件箱（outbox）+ 中继发布
事件当 RPC 用 消费方反查发布方接口，耦合回归 事件携带最小事实，消费方自查缺失数据
死信无人管 DLQ 堆积，业务悄悄漏单 DLQ 告警 + 补偿工单流程
无死信只无限重试 一条毒消息卡死整个分区 有限重试 → 死信 → 人工介入
分区键乱选 同一订单事件乱序（先”已支付”后”已创建”） 按 orderId 分区 + 消费端按版本/时间戳判序
编排器里做副作用 Workflow 重放导致重复执行 副作用放 Activity 且幂等
