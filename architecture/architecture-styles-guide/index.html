现代架构风格全景指南

发表于 2026-10-11 更新于 2026-10-29 分类于 系统架构 本文字数： 34k 阅读时长 ≈ 31 分钟

现代架构风格全景指南

架构风格没有”最好的”，只有”为当前痛点愿意承受哪种代价的”。本文是 系统架构设计实战 的风格详解篇：13 种主流风格逐一深挖核心思想、拓扑、优缺点、适用场景、选错的信号与真实案例，并给出风格总对比、选型决策树与演进路径。演进史、C4 / ADR / 适应度函数在总览篇已展开，本文不再重复。

1. 分层架构（Layered）

一句话判断：系统本质是”表单进、表单出”的 CRUD、团队 ≤ 10 人时，分层架构就是最优解——它是被验证了三十年的默认答案，别不好意思。

核心思想

分层架构诞生于 1990 年代企业应用（J2EE PetStore 是教科书样本），它要解决的是”面条代码”：UI、业务规则、SQL 搅在一个文件里，改一个字段要通读全库。分层的做法是把请求的处理过程切成若干层——表现层只管协议与序列化，业务层只管用例与规则，持久层只管数据存取——依赖严格单向向下。变化被局部化在某一层，其余层可以不感知。

它至今仍是默认答案的原因有三个：第一，心智模型最便宜，新人入职半小时就能看懂目录结构并猜对代码位置；第二，框架原生支持，Spring MVC、Django、Rails 的脚手架就是围绕分层设计的，逆着框架走反而费劲；第三，层与层之间可以独立替换技术（换 ORM、换前端框架）而不用全量重写。

它的根本局限也来自”分层”本身：一个业务用例（比如”下单”）的规则天然要横跨三层——参数校验在表现层、折扣规则在业务层、查询拼装在持久层。当业务规则变复杂，每次改动都要翻三个文件，业务逻辑被”横切”得支离破碎，最终退化成一层层的事务脚本。

拓扑草图

优点 / 缺点

优点 缺点
心智模型简单，新人上手最快 业务逻辑横切三层，改一条规则动三个文件
Spring/Django/Rails 原生支持，生态成熟 容易长出贫血模型 + “事务脚本”，领域逻辑无处安放
每层可独立替换技术实现 层间 pass-through 样板代码随规模线性增长
部署与运维零额外成本 DTO ↔ DO 多层转换，纯性能损耗

适用场景

团队 1-10 人；业务以 CRUD 与流程为主（后台管理、内容管理、内部系统）；领域规则简单或中等；DAU 几千到几十万、单库加读写分离可扛。

选错的信号

  • Service 层 80% 的方法只是转发调用 DAO——层已经变成表演；
  • 同一条业务规则（如”VIP 折扣”）在 Controller、Service、DAO 各出现一次；
  • 测一条业务规则必须起整个应用上下文——领域逻辑没有被隔离，继续堆分层只会让脚本越写越长。

此时该看的不是”再加一层”，而是六边形/整洁架构的依赖倒置思路，或者第 2 节的模块化单体。

代表案例

Spring PetStore（教科书原型）、绝大多数 Spring Boot / Django / Rails 企业应用；Django 的 MTV 本质就是分层架构的现代形态。

2. 模块化单体（Modular Monolith）

一句话判断：团队 10-50 人、单进程部署还够用、但代码边界开始腐烂时选它——2024-2026 的行业共识是”先模块化单体，微服务是它的部署形态升级，而不是重写”。

核心思想

模块化单体保留单体”一个进程、一次部署、一个事务”的全部运维红利，同时在代码结构上强制微服务级的模块边界：每个业务模块（订单、库存、用户）拥有独立的包/目录、独立的数据库 schema，对外只暴露接口。它治的不是性能问题，而是熵增：传统单体长到第二年，模块之间随便 import、随便 JOIN 对方的表，任何一次改动都要回归整个系统，发布节奏被最慢的模块拖死。

它与微服务的对比是近两年架构圈的核心话题，四个维度看清：

  • 事务：模块化单体里”下单扣库存”就是一个本地事务，ACID 白送；微服务里要 Saga / Outbox / 补偿，复杂度高出数量级。
  • 部署：一次全量发布 vs 几十次独立发布——前者简单但互相阻塞，后者灵活但要求 CI/CD、灰度、回滚体系全部就位。
  • 重构成本：模块化单体里”把订单拆出去”接近物理搬运（改构建脚本 + 网络调用替换）；微服务里是 API 契约迁移 + 数据迁移 + 分布式事务改造。
  • 调试：一个进程内调用栈 vs 跨进程链路追踪，排障成本不是一个量级。

关键的纪律只有一条：模块间只许走接口，禁止跨模块访问对方的表，并且必须用工具（Java 用 ArchUnit、Python 用 import-linter、Go 用 internal 包可见性）把边界写进 CI 自动守护。边界守不住的模块化单体，比大泥球单体更糟——它多了一层”看起来有架构”的错觉。

代码示例：Go workspace 多 module + 接口隔离

优点 / 缺点

优点 缺点
本地事务 + 进程内调用，无网络与分布式事务 部署耦合仍在：一个模块的 bug 能崩掉整个进程
一次部署，运维成本≈零增量 无法按模块独立扩容，只能整体水平复制
拆微服务 = 物理搬运模块，重构成本低 边界靠纪律 + CI 守护，团队大了执行会走样
边界由编译器（Go internal）与测试强制 技术栈单一：一个模块想换语言/存储只能整进程迁就

适用场景

10-50 人团队；业务领域持续演进但尚未出现”必须物理隔离”的诉求；DAU 十万到百万级、单进程 + 缓存 + 读写分离可扛；计划未来拆微服务——它是公认的最佳中间态（先模块化，后按需拆分，见第 16 节演进路径）。

选错的信号

  • 某模块资源曲线与其他模块严重背离（报表模块吃 CPU、订单模块吃内存），整体扩容开始浪费钱；
  • 出现循环的模块间接口调用，或者有人为了图快开始跨模块查对方的表；
  • 发布节奏诉求分化：A 模块一天发 5 次、B 模块一周发 1 次，发布窗口开始排队；
  • 合规要求某模块的部署环境物理隔离（数据出域、独立等保）。

代表案例

Shopify（著名的模块化单体，模块化后有选择地拆分）、Stack Overflow（巨型单体扛住全球顶级流量）、37signals/Basecamp（ONCE 产品线明确回归单体）；国内美团、有赞的早期体系也属于这一形态。

3. 微服务（Microservices）

一句话判断：当”独立部署与独立扩容”带来的组织收益大于分布式复杂度成本时才选它——大致对应”一个团队已经养不住整个代码库”或”模块间发布节奏严重冲突”的时点。

核心思想

微服务把”拆分”从代码结构升级为进程与数据边界：每个服务独立部署、独立数据库、独立伸缩、独立生命周期，并围绕业务能力组织——这是康威定律的正向运用：先切组织，架构自然长成组织的形状。它解决的核心痛点不是技术而是组织：50 个人共享一个代码库时，发布要排队、责任会模糊、认知负荷超载；微服务让每个团队的变更影响面收敛在自己拥有的服务里。

拆分维度（三个视角交叉验证，而不是拍脑袋）：

  • 业务能力 / DDD 限界上下文：订单、支付、库存各自有独立的语言与模型，服务边界即上下文边界（DDD 展开见 系统架构设计实战 相关章节）；
  • 团队拓扑：按”谁拥有它”切，服务数量 ≈ 团队能养活的上限（两个披萨原则），人均服务数超过 3 个而平台能力不足就是灾难；
  • 变更频率 / 资源曲线：资源画像背离大、发布频率冲突大的模块优先拆——拆分是收益排序，不是”最好拆优先”。

数据自治与最终一致性：每个服务私有数据库，跨服务引用只能走 API 或事件。一致性从”免费”变成”设计出来的”——Saga 编排/协同、Outbox、幂等消费、对账兜底，每一项都要钱。

分布式复杂度清单（选微服务前逐条自问是否接得住）：

  • 网络不可靠：每次调用都可能超时、失败、重复——重试预算、熔断、幂等是基本功；
  • 可用性乘法衰减：链路 5 层、每层 99.9%，端到端只剩 99.5%；
  • 链路追踪：一次请求跨 N 个进程，没有 trace id 就是瞎子（OpenTelemetry 全链路打点）；
  • 契约测试：接口变更不再”同仓库一起改”，需要消费方驱动契约（Pact）防breaking change；
  • 版本兼容：滚动发布期间新旧实例并存，API 必须向后兼容；
  • 本地开发：环境起不全，需要 stub / 容器编排 / 独立测试环境；
  • 平台负担：注册发现、配置中心、网关、灰度、回滚——没有平台工程的微服务是灾难（见 平台工程）。

代码示例：拆分前后的一次下单流程（时序对比）

优点 / 缺点

优点 缺点
独立部署，发布节奏彻底解耦 分布式复杂度全家桶（见上方清单）
独立扩容，按模块真实负载分配资源 一致性降级为最终一致，Saga/补偿是长期税
故障隔离，爆炸半径收敛到单个服务 调试、测试、排障成本数量级上升
技术栈自由（每服务可选最合适的语言/存储） 基础设施投入大：网关/可观测/CI/CD/平台
组织对齐：团队边界=服务边界 拆错边界的返工成本极高（最难撤销的风格）

适用场景

团队 > 50 人或已形成多个独立产品小组；不同模块负载画像差异巨大、需要独立伸缩；发布频率冲突已拖累交付；有平台团队兜底基础设施。反过来：小团队 + 平台能力不足 = 微服务灾难。

选错的信号

  • 跨服务联表查询的诉求超过 3-5 处——拆分边界切错了数据内聚；
  • 一个业务用例要同步串 4 层以上服务调用——可用性按乘法衰减，这是分布式单体前兆；
  • 多个服务共享同一个数据库——最差组合：吃了微服务的苦，没吃到任何好处；
  • 一次需求要同时改 3 个服务一起上线——边界切错了变更内聚；
  • 人均维护服务 > 3 个且没有平台自助能力——团队已在养基础设施而非业务。

代表案例

Netflix（2008 年数据库故障后全面转向云原生微服务）、Amazon（两个披萨团队 + 服务化先驱）、Uber（从单体膨胀到数千微服务后，近年又做领域整合收敛）；国内：阿里中台体系、美团服务体系。治理与流量下沉的后续见 Service Mesh。

4. 面向服务 SOA：ESB 的教训

一句话判断：SOA 已是历史名词，但 ESB 的教训每天都在 API 网关上重演——“把业务逻辑塞进通信层”就是它的现代变体。

核心思想

2000 年代的企业集成答案是 SOA：所有系统通过企业服务总线（ESB）通信，总线负责路由、协议转换、消息编排（BPEL）。它的失败路径非常典型：总线从”管道”进化成”大脑”——编排逻辑、数据转换规则全埋进 XML 配置，成为无人敢动的单点；改一个接口要协调总线团队排队；总线本身成为性能与可用性瓶颈。教训对今天的启示：API 网关 / 服务网格是”瘦版 ESB”——只做横切关注点（认证、限流、路由、可观测），绝不做业务编排。判断标准很简单：网关配置里出现 if/else 业务分支，就是 ESB 幽灵回归。

拓扑草图

优点 / 缺点 / 场景（压缩版）

  • 优点（历史视角）：第一次把”服务复用 + 标准化契约”变成企业级实践。
  • 缺点：总线单点、逻辑黑洞、供应商锁定（WebSphere/OSB 授权费巨大）、发布串行化。
  • 适用场景：已无新增；存量银行/政企仍在维护，新系统一律”瘦网关 + 微服务”。
  • 选错的信号（现代变体）：网关插件里开始写订单状态机；BFF 层长出第二个 BFF。
  • 代表案例：IBM WebSphere ESB、Oracle OSB（存量）；现代对应：Kong、APISIX、Higress。

5. 事件驱动架构（EDA）

一句话判断：当用例是”这件事发生了，多个下游各自关心”而不是”帮我做完这件事”，选 EDA——它换来解耦与削峰，付出的是最终一致与调试代价。

核心思想

同步调用把服务的可用性和延迟绑成一条链（详见第 3 节的乘法衰减）；EDA 用”发布事件”替代”调用接口”：上游只管把事实（OrderCreated）发出去，不关心谁消费。这是从”命令”到”通知”的语义转变——命令要求对方做完，通知只陈述发生过什么。事件驱动是微服务跨服务协调的默认答案（完整生态选型见 EDA 事件驱动）。

两大拓扑各有取舍：

  • Mediator（中介者/编排）：一个编排器（Temporal、事件编排引擎）按流程依次触发步骤——全局流程可见、可监控、可回滚，但编排器是中心节点，流程变更集中。
  • Broker（代理/编舞）：事件进 broker（Kafka/NATS），各消费者自行订阅——最松耦合、无中心，但全局流程无人可见，五跳以上的编舞流程没人画得出全景图。

Outbox 模式解决 EDA 的第一难题：”业务写入”与”事件发布”不是原子的。先发 MQ 再提交事务，可能发出幽灵事件（事务最终回滚）；先提交再发 MQ，可能事件丢失。Outbox 的解法是把”发事件”降级为”写一行”：本地事务里同时写业务表和 outbox 表，由独立 relay（轮询）或 CDC（Debezium 监听 binlog）投递到 broker——保证”状态变了，事件必发；状态没变，事件必不发”。

调试代价是 EDA 最被低估的部分：请求-响应时代”堆栈即链路”；EDA 时代一次用户操作的后果分散在 N 个消费者、异步执行、可延迟、可乱序——排障必须依赖 trace 上下文透传 + 事件 id 贯穿 + 消费幂等 + 消费 lag 监控四件套。

代码示例：Outbox 表结构 + 伪代码

优点 / 缺点

优点 缺点
上下游彻底解耦：新增消费者零改动生产者 最终一致：下游数据延迟可见，产品侧要提前设计
削峰填谷：突发流量被 broker 吸收 排障困难：无堆栈、异步、跨进程、可乱序
天然的事件溯源/审计基础（与第 10 节衔接） 消息 at-least-once 必达 → 消费端必须幂等
失败重试 + 死信队列，故障隔离自然 事件 schema 演化需兼容多版本消费者
事件可回溯重放（补数据/修投影） Broker 拓扑下全局流程不可见，链长后失控

适用场景

高吞吐异步处理（埋点、日志、通知、积分）；跨服务流程协调（下游不阻塞上游）；秒杀/大促下游削峰；事件生态（一个事件被 N 个团队消费）。不适合：用户在等结果且要求强一致的交互（如扣款后的余额展示）——同步段必须兜底。

选错的信号

  • 消费者开始同步等待另一个消费者的事件才能继续——异步被用成了同步，延迟翻倍还引入乱序；
  • 一个流程的事件链超过 5 跳且没人画得出全局流程图——该换 Mediator/编排引擎；
  • 消费 lag 成为常态——吞吐错配，事件链路已经变成隐性同步依赖；
  • 事件 payload 越来越大、越来越像”数据库整行同步”——事件设计已退化为 ETL。

代表案例

LinkedIn（Kafka 的诞生地）、Uber（全链路事件生态）、Netflix、阿里双 11 削峰（RocketMQ）、Stripe（把事件作为对外 API 产品化）。

6. 微内核 / 插件架构（Microkernel）

一句话判断：产品核心稳定、外围需求因客户而异时选它——把”变化”做成插件，把”不变”做成内核。

核心思想

微内核把系统拆成”最小核心”（插件契约 + 注册 + 生命周期）与”插件”（具体功能实现）。核心只定义接口与加载机制，差异全部落在插件里。它解决的是产品化痛点：同一套核心服务 N 个客户（报表格式、计费规则、协议支持各不相同），如果都塞进核心，代码库会变成 if(客户A) else if(客户B) 的泥潭；插件化后，新增一个定制 = 写一个插件，核心零改动。

第二个收益是隔离实验：新功能以插件形态灰度，出问题禁用插件即可，核心与存量插件不动。第三个收益是生态：第三方可以按公开契约开发扩展（VS Code 的插件市场就是终极形态）。最大的难点也在这里：插件契约（API）设计是最难的一步——契约一旦冻结，每次演化都是所有插件的迁移成本；契约设计失误则成为永久税。

优点 / 缺点

优点 缺点
核心稳定，定制隔离，客户需求不污染主干 插件契约演化是长期税：改契约=全部插件重编译
第三方扩展生态（插件市场模式） 插件质量参差会拖垮宿主（需进程/沙箱隔离）
灰度/禁用粒度细：单个插件可独立开关 间接层带来一定性能开销
实验性功能可插拔，试错成本低 注册表膨胀后核心又开始变胖（第二系统效应）

适用场景

IDE 与编辑器（Eclipse/IntelliJ/VS Code）、网关与代理（Nginx 模块、Envoy filter、Kong 插件）、构建工具（Webpack/Tapable）、多租户 SaaS 的定制层、报表与规则引擎。不选：业务域本身快速变化、插件边界画不出来的时候——强行插件化会把”接口”变成垃圾抽屉。

选错的信号

  • 核心开始 import 具体插件包——依赖倒置失败，内核已经不”微”；
  • 插件之间互相感知、互相调用——契约被穿透，出现隐式依赖链；
  • 80% 的需求要同时改内核 + 插件——边界切错了，切分依据不是”变化频率”。

代表案例

Eclipse OSGi（插件架构的工业化鼻祖）、IntelliJ Platform / VS Code 扩展体系、浏览器扩展、Nginx 模块、Envoy filter、Kong 插件、Webpack/Tapable。

7. 空间型架构（Space-Based）

一句话判断：只有在”突发流量会把数据库写垮”且”可以接受秒级数据丢失窗口”的场景（抢购、票务、大促）才考虑它——这是为极端峰值而生的昂贵特化架构。

核心思想

传统扩容的瓶颈在共享数据库：应用无状态可以横向复制，数据库是单点。空间型架构的激进之处在于把”数据库”从请求路径上隐去：数据分区放在各处理单元（Processing Unit）的内存数据网格（IMDG：Hazelcast / Apache Ignite / GigaSpaces）里，单元间网格复制或分区路由，请求进入任意单元即可就地处理；落库通过异步持久化（write-behind）批量进行。突发流量被”空间”（内存集群）整体吸收，数据库只见平滑的异步写。

它真正交易的只有两样东西：用内存成本换数据库容量，以及用数据丢失窗口换吞吐。第二点是致命约束——write-behind 意味着内存态与磁盘之间有时间差，节点崩溃叠加副本同步异常时，最近 N 秒的写入可能丢失。这就是为什么账务、支付链路永远不该用它，而抢购（超卖可用补偿、少卖可复盘）可以。

如今很多”抢购”场景用 Redis 集群 + 内存预扣 + 异步落库 + MQ 的组合达到了类似效果，运维门槛低得多——先试这条便宜的路，再考虑完整的 Space-Based。

拓扑草图

优点 / 缺点

优点 缺点
吞吐随单元数近线性扩展，天然应对突发 数据丢失窗口：write-behind 崩节点可能丢最近写入
数据库压力被削平，只见平滑异步写 一致性弱化：跨单元事务/查询变成分布式难题
单元无状态，任一单元崩溃流量即切 内存成本高：热数据全量驻留内存
峰值后可缩容，适合活动型业务 IMDG 本身是分布式系统，运维门槛高；查询能力受限

适用场景

秒杀、抢购、票务等短时极端写峰；数据”可用即可、允许极小概率丢失”（库存超卖有补偿手段）；活动型业务（峰值后缩容回本）。不选：账务、支付等不允许丢写的核心链路。

选错的信号

  • 你的峰值其实是”慢峰值”（小时级爬升）——普通弹性扩容 + 缓存就够，别上重炮；
  • 团队没有 IMDG 运维经验却要自建网格——这是给运维挖坟；
  • 业务开始要求对网格内数据做复杂 OLAP 查询——用错了工具，那是数仓的活。

代表案例

GigaSpaces（该风格术语的提出者，金融与航司订座系统）、Hazelcast、Apache Ignite；国内大促普遍用 Redis 集群 + 内存预扣 + 异步落库的组合实现同类效果（如淘宝秒杀的内存预扣方案）。

8. 管道 - 过滤器（Pipeline）

一句话判断：当业务本质是”数据流过一串独立变换”（ETL、CI、编译、转码），选它——组合性就是生产力。

核心思想

把处理过程拆成一串过滤器（Filter），过滤器之间通过管道（Pipe）传递数据；每个过滤器只做一件事、不知道上下游是谁。这套思想来自 Unix 哲学：cat access.log | grep 404 | awk '{print $1}' | sort | uniq -c——单一职责的小工具，组合涌现出无限可能。组合性是灵魂：新增能力 = 在链上插入一个过滤器，存量过滤器零改动。

代价集中在状态传递：过滤器之间的序列化/反序列化、格式协商、批处理边界（流式 vs 微批）是主要开销；全局视角（整条管道处理了多少条、失败在哪段）需要额外机制；过滤器一旦有状态，并行度与顺序就成了新问题。另一个易犯错误是把管道用成”同步 RPC 链”——等全部段执行完才返回，延迟叠加，组合性的好处还一点没拿到。

优点 / 缺点

优点 缺点
组合性 / 复用性极高，新增能力=插入过滤器 状态传递成本：序列化、格式转换、批边界
单一职责，每段可独立测试 端到端延迟是各段之和
天然并行：段间流水线、段内分片 段间无事务语义，失败需断点重放机制
失败隔离：记住断点，从失败段重放 全局监控复杂：需要管道级指标与追踪

适用场景

ETL / 数据集成、CI/CD 流水线、编译器前端（词法→语法→语义→优化）、音视频转码、日志处理。不选：需要跨”过滤器”共享大量上下文与事务的业务流程——那是工作流引擎（编排）的地盘。

选错的信号

  • 过滤器之间开始传递”上帝对象”（什么都往里塞）——数据契约已经失效；
  • 某段过滤器偷偷依赖上一段的副作用顺序——组合性被破坏，重排即出错；
  • 管道被当成同步 RPC 链用——延迟叠加，还丢了并行与重放的好处。

代表案例

Unix shell 管道（思想源头）、Jenkins / GitLab CI、Airflow（DAG 是管道的编排化扩展）、Flink / Beam（流式管道）、ffmpeg 滤镜链、LLVM Pass 管道。

9. Serverless / FaaS

一句话判断：流量稀疏、事件驱动、任务短小（< 15 分钟）选 FaaS 能省到肉；高频常驻、长任务、强状态，成本模型会反杀。

核心思想

Serverless 把”运维一个常驻进程”整体外包给云厂商：代码以函数为部署单位，事件触发（HTTP / 消息 / 定时 / 对象上传），按调用次数 × 执行时长 × 内存计费，流量为零时缩容到零。它解决的痛点是”为峰值买单”——为一天 3 次的突发预留 24 小时的服务器，资源利用率常低于 5%；FaaS 让 idle 的成本归零。

成本模型是选型的第一性原理：

  • 低频（偶发 webhook、夜间批处理、对象上传处理）：FaaS 完胜，不为 idle 付费；
  • 高频常态流量：按 GB-s 计费很快超过包月虚机，秒级千 QPS 的 API 放 FaaS 里账单会教育你；
  • 长任务：按执行时长线性计费，分钟级任务（视频转码）成本爆炸；
  • 冷启动：JVM 类运行时秒级冷启动会打爆 P99（需要预热 / 快照，如 SnapStart）；Go / Node / Rust 百毫秒级可接受。

厂商锁定是第二道坎：函数签名、事件格式、部署包与周边（API 网关 / 对象存储 / 队列）全部绑定云生态，迁移 = 重写粘合层。缓解办法有二：用 Knative / OpenFaaS 自建；或者用六边形架构隔离——业务核心是纯函数/普通包，FaaS 函数只是薄薄一层适配器，粘合层可以重写而核心不动。

与微服务的关系：FaaS 可以看作微服务的极简形态（一个函数 = 一个最小的微服务），代价是牺牲常驻连接池、本地缓存与进程内状态（每次调用都可能是新容器）。实践中最常见的形态是混合：核心域用微服务，边缘事件（缩略图、webhook 接收、定时对账）用 FaaS。

优点 / 缺点

优点 缺点
零 idle 成本，缩容到零 冷启动尾延迟（JVM 尤甚）
自动弹性，无需容量规划 高频长任务成本反超包月 3-10 倍
运维外包：OS / 补丁 / 扩容不用管 厂商锁定：迁移 = 重写粘合层
与云事件生态原生集成（存储/MQ/网关） 无常驻状态：连接池、本地缓存全部失效
发布粒度细到函数 执行时长/内存/并发有平台上限；调试依赖厂商工具

适用场景

事件处理（上传、消息、webhook）、定时任务、突发流量（活动页）、IoT 数据摄取、轻量内部 API。不选：常态高流量 API、长任务、需要连接池与本地缓存的有状态服务、P99 < 50ms 的极低延迟要求。

选错的信号

  • 月账单里 duration 费用超过等价包月成本 3 倍——该迁容器了；
  • 函数经常 timeout、靠调大内存续命——这是长任务信号，FaaS 模型不适合；
  • Step Functions 编排图越画越复杂——你缺的可能不是一个常驻服务，而是把业务流程硬塞进了函数编排地狱。

代表案例

AWS Lambda（开创者）、Cloudflare Workers（V8 isolate，冷启动毫秒级）、阿里云 FC、Vercel / Netlify Functions；iRobot 用 Lambda 处理扫地机器人 IoT 遥测是经典公开案例。

10. CQRS + Event Sourcing

一句话判断：审计、回溯、复杂多视图读模型是刚需才上；”读写分开性能好”不是理由——它把写路径复杂度提高一个量级，只为换读路径的自由与时间的可回放。

核心思想

两个正交但常配对的思想：

  • CQRS（命令查询责任分离）：写模型按业务不变式优化（聚合 + 强校验 + 小而硬），读模型按查询形态优化（宽表、ES、物化视图），两者通过事件同步。它解决的痛点是：同一个领域模型既要满足事务校验、又要满足千奇百怪的查询，最后互相妥协出四不像。
  • Event Sourcing（事件溯源）：不存”当前状态”，存”状态变迁的事件序列”；当前状态 = 事件回放的投影。它解决的痛点是：审计（谁在何时对状态做了什么，事件即真相）、时旅行（回放任意历史时点）、调试（重放事件即可复现 bug）。

代价清单（上之前必须读完）：

  • 最终一致：读模型落后写模型毫秒到秒级，”下单后列表没刷新”类产品投诉要提前设计（写后读路由 / 前端 loading 语义）；
  • 事件版本演化：事件是不可变历史，字段与语义升级必须走 upcasting（旧事件载入内存后升级为新版本再驱动聚合）——schema 设计失误是十年长期税；
  • 强一致校验困难：唯一性约束（用户名不重复）在事件流上很难表达，需要额外的快照 / 索引 / 乐观并发；
  • 团队认知门槛：聚合、版本号、快照、投影重建、upcasting——全套概念，缺一个就翻车。

拓扑草图

代码示例：命令侧聚合 + 事件回放重建状态（Python）

优点 / 缺点

优点 缺点
完整审计：事件流即业务日志即真相 读模型最终一致，产品侧要处理”写后读”
时旅行与调试：回放任意时点复现问题 事件 schema 演化（upcasting）是十年长期税
读模型自由：同一事件流投影 N 种视图 唯一性等强一致校验难以表达
天然与 EDA 融合：事件即集成事件 生态与工具链小；团队认知成本高

适用场景

金融账务（监管审计）、风控反欺诈（需要完整行为流）、协同编辑与版本化产品、复杂多视图报表。不选：普通 CRUD（binlog 级审计已够）、团队没有 DDD 基础、读多写少且只有一种读视图。

选错的信号

  • 你开始问”能不能只对部分聚合用 ES”——说明没有刚需，是潮流驱动；
  • 事件里开始塞”当前全量状态”——把 ES 用成了状态同步，退化成双写；
  • 为了查一个数据建了 7 个投影，还说不出哪个是权威——读模型已经失控。

代表案例

Axon Framework（Java 生态标杆）、EventStoreDB、LMAX（Disruptor，事件溯源思想的工程源头之一）、多家银行核心账务系统、需要完整操作留痕的协同类产品。

11. Cell-Based 单元化

一句话判断：SLA 要到 99.99% 以上、或者单 region 的爆炸半径不可接受时才上单元化——它是”用架构换可用性”的终极手段，一切日常操作（发布、扩容、数据迁移）的成本都要乘以单元数。

核心思想

把一整套系统（接入层 + 服务 + 数据）复制成 N 个完全独立的”单元”（cell），流量在入口按路由规则（用户 ID 哈希、租户、地域）固定分片进某个单元；单元之间默认不互访，故障时该单元的流量整体切到健康单元。它解决的是爆炸半径问题：传统部署里，一个坏变更、坏节点、坏缓存可能击穿全站；单元化把最坏故障强制限制在 1/N 以内——其余单元继续服务。

数据分两类处理：单元封闭数据（set 化）——用户维度数据（订单、会话）随路由键分片进单元，单元内闭环读写，这是事务能留在单元内的前提；全局数据——配置、全局唯一 ID、元数据，走全局服务或单元间只读复制。

代价同样明确：资源冗余（每个单元都要能扛全量流量比例 + 余量）、跨单元事务基本不可做（设计上就要避免）、路由规则变更（扩单元 / 再平衡）是高危操作、发布与监控必须”按单元”重新设计——自动化能力不足的团队会先被 N 倍操作量拖垮。反过来，单元级灰度发布与单元级容灾演练，一旦自动化建好，就是单元化送给你的红利。

拓扑草图

代码示例：K8s 单元部署 + 单元切流骨架

优点 / 缺点

优点 缺点
爆炸半径可控：最坏损失 1/N 成本 × N（含故障余量的冗余）
容灾演练单元级，故障切换可常态化 路由键是架构承诺：选错要全量重新分片
按单元灰度发布，变更风险再除以 N 跨单元功能（全局唯一、跨用户关系）设计复杂
合规隔离：数据驻留按单元落地 运维自动化要求极高：N 倍操作量必须自动化

适用场景

金融 / 支付 / IM 等高可用刚需（SLA ≥ 99.99%）；多租户 SaaS（租户即路由键，天然单元化）；异地多活（每地域一个单元，蚂蚁 LDC 模式）。不选：SLA 99.9% 即可满足的业务、数据模型没有天然路由键、没有自动化运维平台的团队。

选错的信号

  • 单元数 < 3（没有冗余与切换的意义）或路由键频繁变更；
  • 业务大量出现跨单元请求——路由键选错了（比如按订单号路由，但社交关系跨用户）；
  • 单元之间开始偷偷互相调用——单元封闭性已被破坏，爆炸半径假象。

代表案例

Slack（cell 架构系列文章是公开的最佳教材）、Cloudflare（控制面 / 数据面单元隔离）、蚂蚁 LDC（异地多活单元化的事实标准）、Amazon（cellular architecture，可用区即 cell 思想的雏形）。

12. 边缘计算架构（Edge）

一句话判断：延迟（全球用户 P99 < 50ms）或合规（数据不能出域）二选一成为硬约束时，把计算推到用户身边；否则中心化 + CDN 静态资源已经够用。

核心思想

传统架构里，用户到中心机房的物理距离决定延迟下限（跨洲 200ms+，光速不可压缩）。边缘架构把计算下沉到 CDN 边缘节点（全球数百个城市级 PoP），在离用户最近的一跳执行代码（边缘函数）。两个驱动力：延迟——个性化首屏、鉴权、AB 实验、请求重写这些”每个请求都要跑的轻计算”放边缘，中心只处理重逻辑；合规——GDPR 数据驻留与部分市场的数据不出境要求，天然需要”计算与存储靠近用户所在地”。

与 Serverless 的异同：相同点是按调用付费、事件触发、无服务器运维；差异在运行时与数据模型——边缘函数运行时受限（V8 isolate / WASM，无任意原生库、CPU 时间片小、常无文件系统与长连接），冷启动毫秒级，部署是全边缘同步发布；数据侧边缘难以直连中心数据库，通常配边缘 KV（最终一致复制），未命中或重逻辑回源中心。一句话：热路径下沉，冷路径集中。

拓扑草图

优点 / 缺点

优点 缺点
延迟数量级改善（就近执行） 调试与观测困难：代码散在数百个 PoP
合规：数据驻留天然满足 运行时受限：无原生库 / 短 CPU / 无长连接
抗 DDoS 第一层，中心压力下降 边缘 KV 与中心数据一致（复制延迟）
冷启动毫秒级，比 FaaS 更激进 per-request 成本未必便宜；边缘也有合规义务

适用场景

全球分布用户 + 个性化 Web（首屏重写、AB、鉴权前置）、IoT 数据预处理、数据驻留合规市场。不选：用户集中单一地域、强事务业务、重计算 / 长连接业务。

选错的信号

  • 边缘函数回源频率 > 50% 且回源都是重逻辑——下沉没有意义，反而多一跳；
  • 团队在边缘 KV 里存了需要强一致的数据——复制延迟会给你上生动一课；
  • P99 问题其实出在中心数据库——下沉边缘只是掩盖病灶。

代表案例

Cloudflare Workers、Vercel Edge Functions / Next.js Middleware、Fastly Compute、AWS CloudFront Functions / Lambda@Edge、Akamai EdgeWorkers。

13. AI-Native 架构

一句话判断：”在微服务里加一个 LLM 服务”是 AI-enabled，”把不确定性、成本、延迟当作一等公民设计约束”才是 AI-Native——这是 2024-2026 的分水岭。

核心思想

传统架构的第一性假设是”确定性”：同输入同输出、毫秒延迟、单次调用成本可忽略。LLM 推理同时打破三条：输出有随机性与幻觉、延迟以秒计、每次调用都是真金白银。AI-Native 架构 = 在架构层面对这三条不确定性做系统化治理，而不是在每个业务里散装调用 SDK。

四个组件构成 AI-Native 的基本盘：

  • 模型推理网关（LLM Gateway）：统一入口做模型路由（按成本 / 能力 / 可用性自动切换）、语义缓存（相同意图命中缓存可省 90% token）、限流与预算（按团队/功能设月度 token 预算）、密钥托管与审计、可观测（token 计量、延迟、质量指标）；
  • RAG 管道：文档 → 切分 → 向量化 → 向量库；检索（BM25 + 向量混合）→ 重排 → 生成。它把”知识更新”从”重训模型”降级为”更新索引”，是企业知识场景的事实标准；
  • Agent 编排：多步工具调用、反思循环、人工兜底（human-in-the-loop）。编排引擎必须支持长事务、断点恢复、确定性重放——Temporal / LangGraph 类引擎把”不可靠的 LLM 步骤”装进”可靠的工作流骨架”；
  • GPU 资源池化：推理成本是大头——MIG / vGPU 切分、continuous batching、KV cache 复用、模型按流量画像调度（KServe / Triton）。自建 GPU 而利用率 < 30% 是 2024-2026 最常见的浪费。

与传统架构的融合点是一条渐进路径：先在微服务架构里加一个”AI 能力服务”（单一职责：摘要 / 分类 / 抽取），网关统一治理；成熟后走向全链路 AI-native——产品交互由 Agent 编排驱动、数据面带向量索引、成本与质量双预算进入 SLO。注意边界：强确定性逻辑（对账、权限判定）永远不要交给概率模型，AI 只该出现在”允许犯错且可校验”的环节。

拓扑草图

优点 / 缺点

优点 缺点
模型可替换：网关路由 + 多厂商 fallback 不确定性带来全新测试体系（evals）
成本可治理：语义缓存 + 预算 + 计量 成本模型与传统容量规划完全不同
能力可复用：RAG / Agent 平台化共享 GPU 供给与调度是全新运维域
安全可收敛：密钥托管、prompt 审计 数据安全新面：prompt 注入、数据出域

适用场景

知识密集型产品（客服、搜索、写作、代码）、内部效率工具、已有微服务团队加 AI 能力层。不选：强确定性业务逻辑；没有 evals 与预算机制就全量上线生成式功能。

选错的信号

  • 各服务各自 import openai SDK——网关缺位，成本、安全、计量全面失控；
  • 没有评测集——质量回归靠肉眼，每次换模型都是赌博；
  • GPU 利用率 < 30% 还在买卡——池化与批处理缺位，先优化再扩容；
  • Agent 无超时、无预算、无人工兜底——生产事故已预定。

代表案例

OpenAI / Anthropic 网关生态（LiteLLM、Portkey）、Cloudflare AI Gateway、Higress AI 网关、K8s 生态 KServe / Triton / GPU Operator、GitHub Copilot（AI-native 产品形态）、Klarna（客服 AI 重构，公开披露的成本数据最完整）。

15. 选型决策树

16. 演进路径：触发信号与迁移要点

单体 → 模块化单体。触发信号：团队过 10 人、模块间随便 import、发布开始排队、改一处要回归全量。迁移要点：按领域分模块；模块间只许走接口；禁止跨模块查表；用 ArchUnit / import-linter / Go internal 把边界写进 CI 第一天就生效。这一步不碰部署形态，纯代码结构调整，成本最低、收益立现。

模块化单体 → 微服务。触发信号：某模块资源曲线与其他模块严重背离（需要独立扩容）；发布频率严重分化；团队按产品线分组且 > 50 人；平台能力（网关、注册发现、可观测、CI/CD）就位。迁移要点：先落事件总线与链路追踪，再拆服务（顺序错了就是同步调用地狱）；第一个拆”资源大户”而不是”最好拆的”；拆分顺序按”资源曲线背离 × 发布频率 × 团队归属 / 数据耦合”打分；每个拆出的服务要有独立 SLA 与演练过的回滚方案。

微服务 → 单元化。触发信号：SLA 要求 99.99% 以上；单 region 故障半径不可接受；多活 / 合规驻留成为硬需求。迁移要点：先选定路由键（用户/租户，一旦选定极难更改）；数据 set 化（单元封闭）先于服务单元化；发布、监控、切流全部按单元维度重建并自动化；先建 2 个单元验证全流程，再扩到 N 个。

拆分过程中的存量流量迁移，用绞杀者模式逐步替换旧接口，而不是大爆炸重写——渐进式演进的完整方法论见 系统架构设计实战。

17. 常见误用与陷阱

误用 现象 / 后果 更好的做法
用户数 < 1 万就上微服务 运维压垮团队，交付反而变慢 模块化单体起步，痛点驱动演进
微服务拆分后共享一个库 分布式单体：最差组合，牵一发动全身 数据所有权随服务走，跨服务走事件
跨服务联表诉求 5+ 处仍硬撑 拆分边界切错了数据内聚，改需求处处跨服务 重新按限界上下文划界，该合的合回来
Serverless 跑高频长任务 账单反超包月 3-10 倍 高频常驻用容器，FaaS 留给低频事件
CQRS 无审计需求硬上 事件演化税 + 认知成本全部白付 普通存储 + CDC 读模型足够
事件溯源里塞当前全量状态 退化成双写，失去审计与回放意义 事件 = 变迁事实，状态只由回放推导
单元化用在无容灾分级的业务 资源 × N 成本，收益为零 先做容灾分级，99.99% 刚需再单元化
缺 Outbox：先发 MQ 再提交事务 幽灵事件 / 事件丢失，对账救火常态化 本地事务写 outbox + relay/CDC 投递

边缘函数高频回源跑重逻辑 延迟没降反多一跳，账单翻倍 只下沉热路径轻计算，重逻辑回中心
AI 功能各自直连模型 API 成本失控 / 密钥泄漏 / 无计量 统一 LLM 网关：路由 + 缓存 + 预算 + 审计
微内核插件契约半年改一次 所有插件反复重编译，生态建不起来 先用 3 个真实插件验证接口，再冻结 v1
