OAuth 2.0 + OIDC 深度技术指南：2026 现代协议栈实战

发表于 2026-09-21 更新于 2026-10-08 分类于 Architecture 本文字数： 19k 阅读时长 ≈ 17 分钟

架构 · OAuth 2.0 + OIDC 2026 现代协议栈

本文不再赘述 OAuth 2.0 (RFC 6749) 基础流程。聚焦 2024-2026 已 RFC 化或即将 RFC 化的现代实践：OAuth 2.1 / RFC 9700 BCP / DPoP / PAR / JAR / JARM / FAPI 2.0 / Back-Channel Logout / Token Exchange / Passkey 融合 / CAEP 共享信号 / AI Agent 授权 / Verifiable Credentials。这些才是 2026 生产环境必须掌握的协议栈。

0. 2026 现代协议栈全景

关键变化（2026 视角）：

  • Implicit / Resource Owner Password Grants 正式废弃。
  • 公共客户端 PKCE 强制；Bearer Token 默认被 sender-constrained 取代。
  • Authorization Request/Response 全链路签名化（PAR + JAR + JARM）。
  • 跨域 SLO 统一走 Back-Channel Logout；front-channel iframe 被第三方 Cookie 限制淘汰。
  • OP 与 RP 之间从”令牌交换”演进到”实时风险事件流”（CAEP）。
  • 身份层扩展到 Verifiable Credentials（可验证凭据）。

1. OAuth 2.1 + BCP (RFC 9700)：基线统一

1.1 RFC 9700 Security Best Current Practice

2025 年正式成 RFC，是新实现的强制基线：

要求 旧 OAuth 2.0 RFC 9700 (2026)
公共客户端 PKCE 推荐 强制
Implicit Grant 允许 禁用
Resource Owner Password 允许 禁用
redirect_uri 匹配 允许子串 / 通配符 精确全字符匹配
redirect_uri 注册 允许通配符 必须含 scheme + host + port + path
state 可选 强制 + 绑定会话
Token 经前端通道传输 允许 禁止，全部 back-channel
Bearer Token 默认 是 推荐 sender-constrained (DPoP/mTLS)
Refresh Token 一次性 Rotation + reuse detection

1.2 OAuth 2.1 (Draft 28)

并非新协议，而是把 OAuth 2.0 + BCP + 弃用流程合并的”教学版”参考实现：

  • 仅保留：Authorization Code + PKCE、Client Credentials、Device Code、Refresh。
  • PKCE 强制、redirect_uri 精确匹配、Bearer 默认被 sender-constrained 替代。
  • 给 2026 新实现者的简明入口；旧系统迁移从 RFC 9700 开始。

2. PAR + JAR + JARM：授权请求/响应全链路签名

2.1 PAR (Pushed Authorization Requests, RFC 9126)

问题：高安全场景授权 URL 长达数 KB（自定义 scope、acr_values、custom params），浏览器 / 反代截断、日志泄露、参数被前端篡改。

方案：把授权参数 POST 到 OP 的 /par 端点，返回 request_uri，浏览器只重定向短 URL。

响应：

强制 PAR：OP 配置 require_pushed_authorization_requests=true 后，所有参数必须走 PAR。这是 FAPI 2.0 的硬性要求。

2.2 JAR (JWT-Secured Authorization Request, RFC 9101)

把整个授权请求打包成签名 JWT（request 参数）。OP 验签后信任其内容，杜绝中间人篡改：

JAR + PAR 组合：把 JAR 的 request JWT 通过 PAR 提交，是 2026 高安全场景标配。

2.3 JARM (JWT-Secured Authorization Response Mode)

授权响应（含 code / state）也用 JWT 签名返回，防止回调被篡改、日志被注入、code 被中间人调换：

RP 用 OP 公钥验签，提取 code 与 state。金融场景（FAPI 2.0）强制使用。

3. DPoP：Sender-Constrained Token 新标准

3.1 DPoP (Demonstrating Proof-of-Possession, RFC 9449)

Bearer Token 一旦泄露即被滥用。DPoP 把 Access Token 绑定到客户端密钥对，没有私钥的窃取者无法使用。

请求：

双端校验：

  • OP 在 token endpoint 接收 DPoP header，校验 proof 签名与 htm/htu/iat/jti，签发的 Access Token 中嵌入 cnf.jkt (pub key thumbprint)。
  • RS 收到请求后，校验：token 中 cnf.jkt == DPoP proof 中 jwk 的 thumbprint，且 htm/htu 与实际请求一致。

3.2 DPoP vs mTLS (RFC 8705) vs 历史方案

方案 机制 优势 局限
DPoP (RFC 9449) JWT 签名绑定密钥对 无需 PKI，浏览器可用 客户端密钥管理责任
mTLS (RFC 8705) 双向 TLS 客户端证书 标准成熟，传输层透明 证书分发 / 轮换复杂
Token Binding (RFC 8471) TLS exporter — 已废弃，浏览器不支持
Bearer 默认 仅凭 token 简单 泄露即滥用

2026 趋势：DPoP 成为浏览器 / 移动端默认，mTLS 服务到服务。两者都满足 sender-constrained。

3.3 DPoP-Nonce 防重放

为防止攻击者截获 proof 后短期重放，OP 可在 401 响应中下发 DPoP-Nonce 头，Client 必须在后续 proof 的 nonce claim 中携带该值。这是 RFC 9449 在 2025 修订后补强点。

4. Token Exchange (RFC 8693)：跨域委托降级

场景：用户登录 Web App 后，Web App 需调用下游微服务，又需让微服务以”用户委托身份”调外部 API（如换一个 scope 更小的 token）。

返回 token 中携带 act (actor) claim 表示”谁在委托谁”，形成委托链。下游服务可审计原始用户身份 + 中间服务身份。最小权限原则的协议级实现。

5. Back-Channel Logout：跨域 SLO 标准方案

5.1 为什么 Front-Channel iframe 死了

第三方 Cookie 在 Safari / Firefox / Chrome 2024+ 默认禁用，OIDC Session Management iframe 无法跨域读 OP cookie。Front-Channel Logout 同样不可靠（依赖浏览器跳转，RP cookie 可能已失效）。

5.2 Back-Channel Logout (RFC)

OP 直接 HTTP POST 到 RP 后端的 backchannel_logout_uri，下发 logout_token (JWT)：

RP 收到后：

  1. 验签 + 校验 iss / aud / exp。
  2. 必须存在 sub 或 sid 至少一个。
  3. 不可同时含 nonce（如有 nonce 则视为普通 ID Token，拒绝）。
  4. 失效本地会话记录（DB / Redis 删除 session_id 对应的 cookie）。
  5. 响应 200 OK，OP 才认为 SLO 推送成功。

这是 2026 跨域 SSO 登出的唯一可靠方案。设计时必须为每个 RP 在 OP 注册 backchannel_logout_uri。

6. CAEP / SET：实时共享信号

6.1 SET (RFC 8698) Security Event Token

事件载体格式：JWT + events claim。OP/RP 间相互推送安全事件，触发跨域的即时撤销 / 重新认证。

6.2 CAEP (Continuous Access Evaluation Profile)

CAEP 是 SET 的应用 profile，把”事件 → 行动”链路标准化。常见事件类型：

事件 含义 RP 行动
session-revoked 会话被吊销 立即失效本地会话
credential-change 用户凭据变更 强制重新认证
assurance-tier-change ACR 等级变化 触发 step-up auth
device-risk-change 设备风险等级变化 触发 MFA
ip-change 用户 IP 跳变 评估是否需 step-up
token-revoked 单个 token 被撤销 加入黑名单

6.3 推送通道

  • Poll：RP 周期性 GET /events 拉取（简单但延迟大）。
  • Push：OP 向 RP 注册的 delivery_endpoint POST（实时，需鉴权与重试）。
  • Stream：HTTP Server-Sent Events / WebSocket 长连接（2026 新趋势，OpenID SSE Profile 草案中）。

7. FAPI 2.0：金融级安全 Profile

FAPI 2.0 是 OpenID Foundation 在 2024-2026 推出的金融场景 profile，强制组合使用：

国内开放银行、英国 Open Banking、日本 FAPI 部署均向 2.0 迁移。

8. Passkey 与 OIDC 融合

8.1 WebAuthn Level 3 + Passkey

2024 W3C 正式发布 WebAuthn Level 3，引入：

  • Device-bound Public Key Credential：跨设备同步 Passkey 之外支持设备绑定凭据。
  • PRF Extension：从 Passkey 派生稳定密钥（用于端到端加密的客户端密钥）。
  • Custom Elements：浏览器原生 <credential-management> 元素统一凭据 UI。

8.2 OP 原生支持 Passkey

现代 IdP（Keycloak 25+、Auth0、Authing）直接在 OP 端用 Passkey 完成用户认证，对 RP 透明：

RP 通过 acr 声明强制要求 Passkey 等级，未达标触发 step-up。密码在 2026 完全被 Passkey 取代。

9. AI Agent 的授权

9.1 非人类主体委托

LLM Agent 代用户操作工具（调 API、下单、转账）。关键问题：Agent 持有什么 token？scope 如何限制？如何审计？

9.2 2026 新研究热点

  • Delegated Authorization for Non-Human Actors：OAuth 2.0 工作组讨论中的 draft，定义 Agent 作为独立 client 时的委托链。
  • Scoped Token + Token Exchange：Agent 用 urn:ietf:params:oauth:grant-type:token-exchange 把用户的 token 降级为更小 scope 的子 token，调用下游工具，留下 act 链。
  • Just-in-Time Token：Agent 每次调工具都向 OP 申请短 exp token，避免长期持权。
  • Verifiable Authorization：Agent 持有的 token 含可验证凭据，证明其在特定 prompt 范围内的合法性。

10. Verifiable Credentials 与 OIDC 集成

10.1 OIDC for Verifiable Credentials (OIDC4VC)

W3C VC Data Model v2 + DIF / OpenID Foundation 定义的 4 个 profile：

Profile 用途
OIDC4VCI Issuance：用户从 Issuer 获取 VC 到自己钱包
OIDC4VP Presentation：用户向 Verifier 出示 VC
SIOPv2 Self-Issued OP：用户钱包自己作为 OP，无需第三方 IdP
DCR Dynamic Client Registration：Verifier 临时向 wallet 注册

10.2 与传统 OIDC 共存

2026 政企应用：电子学历、签证、企业证照、医保凭证等以 VC 形式存于用户 Passkey 同步的钱包，Verifier 用 OIDC4VP 验证。跨域零信任落地。

11.3 Keycloak 25+ 现代配置要点

  • 启用 PAR 强制：Clients → Advanced → “Pushed Authorization Request Required” = ON。
  • 启用 DPoP：Clients → Advanced → “DPoP Bound Access Tokens” = ON。
  • 注册 Back-Channel Logout URL：Clients → Advanced → “Backchannel Logout URL”。
  • 配置 JWKS 轮换：Realm → Keys → add generated，配置新 key 优先级。
  • 启用 Refresh Token Rotation：Clients → “Refresh Token Max Reuse” = 0，”Revoke Refresh Token” = ON。
  • 启用 Passkey / WebAuthn：Authentication → Flows → Browser → 添加 “WebAuthn Authenticator”。
  • 配置 Token Exchange：Clients → “Permissions” → “token-exchange” 启用。

12.2 失败模式速查

现象 根因 排查

14. 演进趋势（2026 → 2027）

  1. OAuth 2.x 协议族化：BCP / 2.1 / FAPI 2.0 / DPoP / PAR / Token Exchange 共同构成现代栈，单一 RFC 不再是入口。
  2. Passkey 全面替代密码：OP 原生支持 WebAuthn L3 + PRF，密码会话退出历史舞台。
  3. DPoP 成为浏览器默认：Fetch + Service Worker 让密钥管理对开发者无感。
  4. CAEP 实时风险流普及：跨域零信任从”事后审计”到”即时撤销”。
  5. AI Agent 授权协议化：Non-Human Actor Delegation 草案成熟，Agent 持 scoped token 调工具成标准模式。
  6. Verifiable Credentials 与 OIDC 合流：OIDC4VC / SIOPv2 让身份层去中心化，政企合规凭据链上可验证。
  7. Stream 通道：从 Poll / Push 到 SSE / WebSocket，CAEP 延迟降至亚秒级。

15. 典型案例：金融级统一身份现代化改造

问题背景：某支付公司有 12 个业务系统，各自维护账号密码；移动 App 与第三方合作伙伴（受监管合规约束）共用一套「隐式流 + 纯 Bearer Token」的老授权链路，安全审计连续两年挂红项：token 可重放、无受众约束、会话注销不跨域生效。

方案：以 Keycloak 25+ 为 OP（OpenID Provider），一次性完成「统一 SSO + 现代协议栈」改造：

改造项 旧状态 新状态 对应机制
授权请求 前端 URL 裸拼参数 后端预注册（短 URL 重定向） PAR (RFC 9126)
访问令牌 纯 Bearer，可重放 令牌与客户端密钥绑定 DPoP (RFC 9449)
登出 各系统 iframe 清 cookie OP 反向回调逐个注销 Back-Channel Logout
合作伙伴接入 隐式流 签名请求/响应 + mTLS JAR/JARM + FAPI 2.0
凭据 密码 Passkey 优先，密码兜底 WebAuthn L3 + ACR

关键设计：资源服务器对 DPoP 令牌做「三重校验」，缺一不可：

踩坑点：① 合作伙伴的旧客户端不支持 PAR，改造时保留了”legacy 分支”并设 90 天下线 deadline——结果两年后还在跑，审计又挂红；教训是兼容通道必须有硬下线日期 + 流量看板。② Back-Channel Logout 回调没做签名校验，被内网扫描器误打误撞批量注销用户会话；logout token 必须验签并校验 events claim。③ DPoP 上线后移动端偶发 401，根因是客户端每次请求重新生成 proof 但设备时钟漂移超 60 秒——客户端 NTP 校时纳入发布检查项。
