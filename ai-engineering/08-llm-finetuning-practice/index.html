第九章：LLM 微调实战：LoRA、QLoRA 与 DPO

微调的价值不是”让模型更聪明”，而是”让模型学会你业务的格式、语气与边界”——本章给出全参 / LoRA / QLoRA 的取舍框架、数据构造与清洗规范、LLaMA-Factory 与 unsloth 实操、DPO 偏好对齐，以及从评测到合并部署的完整闭环。

1. 先想清楚：微调、RAG 还是 Prompt

决策框架一句话：Prompt 教任务、RAG 给知识、微调改行为。

诉求 首选方案 原因
知识时效性、可引用来源 RAG 微调记不住长尾事实，更新成本高
固定输出格式 / 语气 / 领域术语风格 微调 上千次提示不如梯度改一次权重
通用能力缺失（数学、推理） 换更强的基座 小数据微调补不了能力短板
降低提示词长度与成本 微调 把 2K token 的 few-shot 蒸进权重

判断标准：把你想让模型做的事写成 50 条指令数据，如果每一条都能用”例子示范”教会而不是”查资料回答”，那就是微调的活。

2. 全参 vs LoRA vs QLoRA

LoRA 原理：冻结原权重 W，用两个低秩矩阵 B×A（秩 r 通常 8–64）拟合增量 ΔW，训练参数量从 7B 降到 几百万到几千万。

维度 全参微调 LoRA QLoRA
7B 显存需求 ≥ 80GB（Adam 状态 3 倍权重） 16–24GB 10–12GB（4bit 基座）
效果上限 最高 接近全参（多数任务 95%+） 略低于 LoRA，格式任务足够
多任务切换 每任务一份全量权重 只换 Adapter（几十 MB） 同左
训练速度 基准 快 2-3 倍 略慢于 LoRA（量化开销）
适用 领域大改、持续预训练 默认选择 单卡消费级显卡

经验：默认 LoRA；一张 4090/3090 就 QLoRA；只有在”基座模型完全不懂你的领域语言”（如极端专业语料续训）时才考虑全参。

3. 数据构造与清洗

数据质量决定微调上限，1000 条精选胜过 10 万条噪声。

3.1 指令格式（Alpaca / ShareGPT 风格）

3.2 数据构造来源

  1. 真实业务日志改写：脱敏后人工修订成标准答案，质量最高；
  2. 强模型蒸馏：用 GPT-4 级模型按种子问题生成答案，人审后入库（注意合规条款）；
  3. 规则模板扩充：格式转换类任务用脚本生成，保证 100% 正确。

3.3 清洗与去污染

  • 去重：MinHash / SimHash 近重复检测，重复样本会让模型过拟合特定表述；
  • 去污染：用 n-gram 重叠检测训练集与评测集的重合，MMLU 等公开基准早已被爬烂，混入即虚高；
  • 格式校验：schema 强校验（角色齐全、无空轮、无截断），脚本过滤含”作为 AI 我不能”类拒答模板（除非业务需要）；
  • 配比：多任务混训时，核心任务数据占比不低于 30%，防止被通用数据稀释；
  • 长度分布：覆盖业务真实长度，避免全是短样本导致长文输出截断。

6. 超参数怎么调

超参 经验起点 调整信号
lora_rank 16 任务复杂（代码/多步推理）→ 32/64；简单格式任务 8 够
lora_alpha 2×rank 控制 LoRA 缩放强度，一般锁 2 倍关系不动
lora_dropout 0.05 数据 < 2K 条时加 dropout 防过拟合
learning_rate 1e-4（LoRA） loss 不降 → 调大；震荡发散 → 调小；全参用 1e-5 级
epochs 2–3 小数据 3-5，上万条 1-2，看验证集不看训练 loss
cutoff_len 覆盖 P95 样本长度 截断会破坏长文任务，显存不够加梯度累积
batch × accum 等效 32–128 太小 loss 噪声大，太大泛化差

lora_target: all（含 MLP 层）比只挂 attention 效果好一截，代价是参数量翻倍，通常值得。

7. DPO：从”会回答”到”答得好”

SFT 教模型模仿，DPO（Direct Preference Optimization）用偏好对告诉模型哪个更好，不需要训奖励模型（相对 RLHF 大幅简化）。

8. 评测：MMLU 与自建集

两条腿走路：

  1. 通用基准防降智：MMLU / CMMLU / C-Eval 跑一遍，确认微调没把通用能力训崩（灾难性遗忘监控）；
  2. 自建业务集定生死：从真实场景抽 100–300 条带标准答案的 case，人工或强模型（GPT-4 裁判）打分，记录格式合规率、准确率、拒答误判率。

纪律：训练集与评测集严格去污染；每次实验固定评测脚本与裁判模型版本，否则分数无法横向比较；把评测分数、超参、数据版本记进实验表（wandb / 简单的 CSV 都行）。

9. 过拟合识别与对策

信号：

  • 训练 loss 降、验证 loss 升（最可靠）；
  • 输出开始复读训练数据的特定表述，换种问法就露馅；
  • 通用基准分数明显下滑。

对策：减 epoch、降 lr、加 dropout、增数据多样性、混入 10%–20% 通用指令数据（防遗忘的廉价保险）。

常见坑 FAQ

  1. Q：微调后模型变”复读机”，反复输出训练集原句？ A：典型过拟合 + 数据去重没做好。减 epoch、查近重复样本、混通用数据。
  2. Q：loss 降到接近 0 但效果很差？ A：检查是否把 prompt 部分也算了 loss（应只 mask 出答案部分计算，LLaMA-Factory train_on_prompt: false）；以及 chat template 是否配对——template 错一位全盘皆输。
  3. Q：QLoRA 训完合并后精度掉得厉害？ A：QLoRA 的正确姿势是合并 LoRA 到 BF16 基座再量化，而不是直接对 4bit 基座导出的权重上线。
  4. Q：DPO 训完模型变啰嗦/变哑巴？ A：beta 不合适或 chosen/rejected 长度差异太大（模型学会”长=好”的伪相关）。控制长度分布，或换 IPO/KTO。
  5. Q：只有 500 条数据值得微调吗？ A：格式类任务值得（rank 8、3 epoch 常有奇效）；知识类任务不值得，转 RAG。
  6. Q：基座选哪个版本？ A：直接选 Instruct 版做 SFT（别从 Base 重来）；中文任务优先 Qwen 系；留意模型 License（商用限制）。

生产实践清单

  • 明确微调目标属于”行为/格式”而非”知识”，与 RAG 分工清晰
  • 数据去重、去污染、schema 校验三步走完才开训
  • 训练 mask 只算答案部分 loss，chat template 与基座严格匹配
  • 固定评测集与裁判版本，每次实验留记录
  • 通用基准 + 自建集双评测，监控灾难性遗忘
  • LoRA 合并到高精度基座后再量化，不直接部署 4bit 训练产物
  • 多业务线用 vLLM LoRA 热挂载共享基座
  • 线上 badcase 回流数据池，建立月度迭代节奏
