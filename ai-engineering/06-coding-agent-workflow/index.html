第七章：Coding Agent 工作流：AI 编程落地实践

Coding Agent 不是”更快的补全”，而是”会读仓库、会跑测试、会改多个文件的协作者”——本章对比 Claude Code / Cursor / Cline 的工作流，给出 CLAUDE.md 工程约定、Spec 驱动开发、Subagent 自动化、CI 接入与团队度量的完整落地方案。

1. 从补全到 Agent：编程范式的三级跳

三级跳的本质差异：

  • 补全：模型看当前文件光标附近，秒级响应，人无打断。
  • 对话：人把上下文喂给 Chat，模型产出 diff，人粘贴。
  • Agent：模型自己读文件、grep、跑测试、看报错再改，一轮任务可能执行几十步工具调用，人只在关键节点确认。

团队落地 Coding Agent 的关键不是”选哪个工具”，而是把仓库改造成 Agent 友好：清晰的目录约定、可一键运行的测试、写在仓库里的工程规范。Agent 的能力上限，往往被仓库的混乱度决定。

2. Claude Code / Cursor / Cline 工作流对比

维度 Claude Code Cursor Cline（VS Code 插件）
形态 CLI 终端 独立 IDE（VS Code 分支） VS Code 插件
上下文获取 自动检索 + @文件 显式引用 索引 + @ 引用 + Rules 手动添加 + 文件引用
自主性 高，可长时间无人值守（--dangerously-skip-permissions 慎用） 中，Composer/Agent 模式逐步确认 高，每步可批可拒
工程约定文件 CLAUDE.md .cursor/rules/*.mdc、AGENTS.md .clinerules、AGENTS.md
扩展机制 MCP、Subagent、Hooks、Slash Command MCP、Rules MCP
计费 订阅或 API 按量 订阅 + 超额按量 自带 Key 按量
适合场景 大改动、脚本化批量任务、CI 内调用 日常结对、UI 调试、快速迭代 预算敏感、想看每步 diff

选型经验：IDE 派留给探索性编码，CLI 派留给可脚本化的确定性任务。真正拉开差距的是能否把工作流”沉淀进仓库”（约定文件、脚本、钩子），而不是靠个人提示词技巧。

3. CLAUDE.md / AGENTS.md：把团队规范写给 AI 看

CLAUDE.md 是 Claude Code 的”入职文档”，启动时自动注入上下文；AGENTS.md 是跨工具的事实标准（Cursor、Cline、Codex 都读）。建议两者内容一致，仓库根放 AGENTS.md，再 CLAUDE.md 里 @AGENTS.md 引用。

一份好的约定文件回答四个问题：

写法要点：

  • 短而硬：只写”不看就会犯错”的约束，200 行以内；长篇架构文档用链接指出去。
  • 写命令，不写描述：”跑 pytest -x“比”我们重视测试”有效一百倍。
  • 负面约束要明确：Agent 不知道哪目录是产物、哪个文件是手改会被覆盖。
  • 分层放置：根目录放全局，子目录可放局部 CLAUDE.md（如 themes/next/CLAUDE.md 写主题特有规矩），就近生效。

4. Spec 驱动开发：需求 → 计划 → 任务 → 实现

直接让 Agent “帮我实现 XX 功能”，大改动必翻车。稳定的工作流是四段式：

以 Kiro / Spec Kit 风格为例，在仓库建 .specs/user-profile/：

让 Agent 先读 spec 产出 plan，人 Review plan，再让 Agent 拆 tasks 逐个执行。这样做的好处：

  1. 错误拦截在计划层，返工成本最低；
  2. tasks 勾选清单天然是进度条，长任务中断后可续；
  3. spec/plan/tasks 留在仓库里，半年后新人（或新 Agent）知道当初为什么这么改。

实践上，给 Claude Code 配三个 Slash Command（.claude/commands/spec.md、plan.md、implement.md），把四段式固化成团队肌肉记忆。

4.1 一次完整演练

以”给博客后台加文章定时发布”为例，完整对话节奏：

人在三个节点介入：spec 确认边界、plan 选定方案、PR 最终 Review。中间几小时的执行完全放手——这是”自动驾驶”与”遥控驾驶”的分界线。

4.2 上下文管理的硬技巧

  • 大任务拆会话：每完成一个 task 开新会话，用”读 .specs/xxx/tasks.md 继续任务 4”接续，避免 200K 窗口撑满后遗忘早期约束；
  • 显式引用 > 让 Agent 自己找：@src/utils/date.ts 这个文件的 formatDate 有 bug 比”修一下日期格式问题”省 10 倍 token；
  • 先读后改：要求 Agent “先列出你打算改的所有文件并说明原因，确认后再动手”，拦住范围蔓延。

5. Subagent 与 Hooks：把重复动作自动化

Subagent：主 Agent 把子任务委托给带独立上下文的专用 Agent，避免主上下文被探索过程污染。Claude Code 里在 .claude/agents/ 定义：

主 Agent 遇到”补测试”类子任务会自动路由，也可显式 > 用 test-writer 给 order.ts 补测试。常用 Subagent：code-reviewer（只读 Review）、explore（只读检索 codebase）、doc-writer。

Hooks：在 Agent 生命周期的固定点位执行本地命令，用于强制约束。Claude Code 的 settings.json：

典型用法：写文件后自动 prettier/eslint –fix；Bash 执行前拦截 rm -rf、git push --force；任务结束时自动跑相关测试。Hooks 的价值是把”提醒 Agent 记得格式化”这种概率事件变成 100% 确定性。

Headless 模式：claude -p "把 src/ 下所有 console.log 替换为 logger" --allowedTools "Edit,Read,Bash"，可嵌入脚本批量跑，是 CLI 派的核心优势。

6. AI Code Review 流水线接入 CI

AI Review 不是替代人审，而是先把机械问题挡在 CI 层。GitHub Actions 示例：

6.1 Review 提示词的分层设计

把 Review 关注点拆成三层，混在一条提示词里效果会互相稀释：

层 关注点 确定性手段兜底
机械层 格式、lint、类型错误 交给 CI 的 eslint/tsc，不浪费模型 token
逻辑层 边界条件、并发、错误处理 AI Review 主战场
意图层 改动是否符合需求、架构是否腐化 AI 给线索，人做判断

接入要点：

  • 只评论不合并：AI Review 结论作为参考，合并权留在人手里；[blocking] 级问题交给分支保护规则拦。
  • 控制成本：paths-ignore 排除 lock 文件与产物；大 PR 先跑 diff 摘要再决定是否全量 Review。
  • 私库安全：Runner 用自托管 + 最小 Token 权限；不接受 fork PR 触发带密钥的 workflow（防提示词注入偷密钥，这是真实攻击面）。
  • 自建方案也可用 claude -p 或 API + diff 拼装，核心是给模型 AGENTS.md 和完整 diff，而不是让它瞎逛仓库。

7. 团队落地与度量

没有度量的 AI 编程推广，最后都会变成”感觉快了”。建议采集四类指标：

指标 定义 健康参考
采纳率 AI 生成代码进入合并主干的比例（行级或 commit 级） 30%–60% 属正常，>80% 要警惕”照单全收”
返工率 AI 生成代码合入后 14 天内被修改/回滚的比例 高于人工基线 1.5 倍就要复盘
周期时间 需求从立项到合入的 lead time 看分布而不只看均值
评审负载 人均 Review 行数与时长 AI 提速后瓶颈会转移到 Review

落地节奏建议：

  1. 第 1-2 周：小范围试点（2-3 人 + 一个边缘仓库），先把 AGENTS.md 与测试脚本补齐；
  2. 第 3-4 周：沉淀 Slash Command / Subagent / Hooks 进模板仓库；
  3. 第 2 月起：接 CI Review，开始采集采纳率与返工率；
  4. 持续：每月复盘”Agent 犯的典型错”，转化为 AGENTS.md 新条目——规范文件的迭代速度，就是团队 AI 能力的增长速度。

常见组织误区：按人头摊派使用率指标（导致垃圾生成）、用 AI 产出量考核个人（鼓励灌水）、跳过 AGENTS.md 直接谈提示词技巧（个体经验无法沉淀）。

常见坑 FAQ

  1. Q：Agent 改完代码跑测试全绿，但逻辑是错的？ A：测试覆盖不到的地方 Agent 会”自欺”。对策：Spec 里写验收标准，让 Agent 先写测试再实现（TDD 模式对 Agent 尤其有效），关键逻辑坚持人审。
  2. Q：上下文窗口满了 Agent 开始”失忆”乱改？ A：长任务拆 tasks.md 分步执行；每完成一个任务开新会话并引用 spec 文件，不要把 3 小时的会话当常态。
  3. Q：Agent 总喜欢过度工程，加一堆没用的抽象？ A：AGENTS.md 里写”只做需求明确要求的事，不加未要求的配置项与抽象层”；Review 时对超范围改动一律打回。
  4. Q：monorepo 太大，Agent 检索慢且贵？ A：用 .claude/settings.json 或 .cursorignore 排除产物目录；给 AGENTS.md 写清模块地图，让 Agent 直接定位而不是全库 grep。
  5. Q：密钥/内网地址会不会被发给模型厂商？ A：会进入上下文的内容都可能出域。用 .gitignore 同款机制排除 .env；企业部署走第十一章的网关统一做脱敏与审计。
  6. Q：不同成员用不同工具，规范怎么统一？ A：以 AGENTS.md 为单一事实源，各工具的私有配置文件只做一行引用；Hooks 用仓库脚本实现，与工具解耦。

生产实践清单

  • 仓库根有 AGENTS.md，含运行命令、禁区目录、提交规范
  • 测试与 lint 一条命令可跑，且 Agent 知道这条命令
  • 大功能走 spec → plan → tasks 四段式，Spec 文件入库
  • 格式化与危险命令拦截用 Hooks 固化，不靠口头提醒
  • CI 接 AI Review 只评论不合并，fork PR 不带密钥
  • 采集采纳率、返工率，每月复盘并回写 AGENTS.md
  • Headless 批量任务跑在隔离分支，人审后再合
  • 敏感文件（.env、密钥）从 Agent 上下文中排除
