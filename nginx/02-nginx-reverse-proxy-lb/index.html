第二章：Nginx 反向代理与负载均衡

发表于 2026-05-01 更新于 2026-10-25 分类于 Nginx 本文字数： 5.7k 阅读时长 ≈ 5 分钟

第二章：Nginx 反向代理与负载均衡

概念基础

  1. 反向代理是系统入口：客户端只认识 Nginx，真实后端（Spring Boot/Node/Go）藏在 upstream 里——发布、扩缩容、灰度都对客户端无感。
  2. upstream 是逻辑集群：多个后端实例组成一个名字，proxy_pass http://集群名 即完成负载均衡；默认轮询，还有权重、ip_hash、least_conn。
  3. 转发要补头：后端想拿到真实 IP、真实协议，必须配 X-Real-IP、X-Forwarded-For、X-Forwarded-Proto——漏配是日志全是 127.0.0.1 的元凶。
  4. proxy_pass 末尾斜杠有语义：带 / 会替换 location 前缀，不带则原样拼接——路径多一层/少一层的事故九成出在这。
  5. 连接也要调参：proxy_http_version 1.1 + keepalive 复用连接，超时/缓冲/大文件上传各有专属参数。

本章承接 第一章：Nginx 入门与静态服务 的 location 语法，配置基于 nginx 1.28/1.29 官方语法书写（沙箱未装 nginx，未逐条运行验证）。

一、最小反向代理

头 作用
Host 透传原域名，后端按域名路由/生成绝对链接
X-Real-IP 客户端真实 IP（单层代理）
X-Forwarded-For 代理链 IP 列表，$proxy_add_x_forwarded_for 自动追加
X-Forwarded-Proto 客户端是 http 还是 https（后端生成 https 链接必需）

二、proxy_pass 路径规则（高频坑）

记忆法：proxy_pass 的 URL 部分会替换掉 location 匹配的部分；不带路径（只有 host:port）则原样透传。改一条 proxy_pass 必跑 nginx -t + 抓包/日志确认后端实际收到的路径。

三、upstream 与负载均衡策略

策略对比（完整版）：

策略 写法 分发逻辑 适用
轮询（默认） 无参数 按顺序逐个分发 无状态服务
加权轮询 weight=n 按权重比例分发 机器配置不均
ip_hash ip_hash; 按客户端 IP 哈希固定实例 会话粘性
least_conn least_conn; 打当前活跃连接最少者 请求耗时不均
一致性哈希 hash $request_uri consistent; 按任意键哈希，扩缩容漂移少 缓存亲和（同 URL 打同实例）
随机 random two least_conn; 随机抽两台取连接少者 超大 upstream，避免全局扫描
least_time least_time header;（Plus） 打平均响应最快者 商业版，性能敏感场景

故障判定与摘除的完整机制（被动/主动/优雅排空）见下节「四、健康检查与故障摘除」。

四、健康检查与故障摘除

被动检查（开源版自带）

开源 Nginx 不主动探测后端，而是用真实请求的结果判定后端死活：

参数 含义
max_fails fail_timeout 窗口内失败次数达阈值即摘除
fail_timeout 既是统计窗口，也是被摘除后的「冷却时间」
slow_start 恢复节点缓慢放量，避免冷缓存/冷 JIT 被瞬间打满
proxy_next_upstream 定义哪些失败场景换机重试（默认 error + timeout）

非幂等请求慎用重试：POST 下单/扣款请求可能已到达第一台，换机重试会造成重复下单——重试只开给幂等接口。

主动检查与注册中心

方案 说明
商业版 health_check health_check interval=5s uri=/health; 定期主动探测，挂即摘除
nginx_upstream_check_module 淘宝开源补丁（Tengine 内置），主动心跳检查
注册中心联动 Consul/Nacos 上下线时通过 API 动态改 upstream（或 ngx_dyups 模块）

优雅下线（drain）

发布前先把节点「排空」：开源版把该 server 手动标记 down（存量 keepalive 连接服务完再断）；Plus 用 drain 参数只处理存量会话、不接新请求。排空后再重启，实现零请求丢失发布。

五、超时、缓冲与大文件

SSE/流式响应必须关缓冲：proxy_buffering off;（或后端发 X-Accel-Buffering: no），否则事件被攒着不吐。

六、限流与并发控制

关键取舍：

  1. burst 不带 nodelay：超出速率的请求排队匀速放行——削峰填谷，后端不被突发打垮，代价是延迟上升；
  2. burst nodelay：积压请求立即放行，超 burst 才拒绝——适合宁可后端扛、也不让用户等的场景；
  3. 超限默认返回 503，用 limit_req_status 429; 改成更语义化的 429；
  4. 10MB 共享内存约存 16 万个 IP 状态（每条约 64 字节），通常够用；
  5. 被限流的请求会写 error.log（limiting requests, excess: ...），可据此做告警。

会话保持方案对比

方案 实现 代价
ip_hash 一行指令 NAT 出口下大量用户同 IP，负载倾斜
hash $cookie_xxx consistent 按业务键一致性哈希 需先种 cookie；扩缩容时漂移少
应用外置会话（Redis） 后端共享 session 最推荐：Nginx 无感知，后端任意扩缩容
sticky 指令 Nginx Plus 商业版，cookie 路由、无需改应用

本章小结

要点 结论
代理头 X-Real-IP/X-Forwarded-For/-Proto 三件套必配
路径规则 proxy_pass 带路径=替换前缀，不带=原样透传
负载均衡 默认轮询；weight/ip_hash/least_conn 按需选；keepalive 复用连接
超时缓冲 read_timeout 治慢接口；client_max_body_size 治 413；SSE 要关 buffering
WebSocket http_version 1.1 + Upgrade/Connection 头 + 放宽 read_timeout
健康检查 被动：max_fails/fail_timeout + proxy_next_upstream；主动检查需 Plus 或第三方模块
限流 limit_req 限速 + burst 排队削峰，limit_conn 控并发，超限默认 503（可改 429）
