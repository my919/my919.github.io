Nginx · 反向代理、负载均衡与高可用

从最小反向代理到生产级高可用。proxy_pass 路径规则 · upstream 负载均衡策略 · 健康检查与故障摘除 · 超时缓冲与 WebSocket · 限流防刷 · 会话保持 · Keepalived 双机高可用 · 性能调优。配置带详细注释。

技术栈速查

类别 选型 用途
反向代理 Nginx 1.28 负载均衡
高可用 Keepalived 2.3 VIP 漂移
健康检查 nginx upstream / 外部脚本 摘除故障节点
会话 Redis 会话共享 无状态化

1. 概念说明

反向代理是系统入口：客户端只认识 Nginx，真实后端藏在 upstream 里——发布、扩缩容、灰度都对客户端无感。

负载均衡：多台应用服务器分担流量——提升吞吐（横向扩展）与可用性（单点故障不影响）。

Nginx 核心：upstream（后端服务器组）+ proxy_pass（转发）+ 调度算法。

高可用：Nginx 自身不能是单点——两台 Nginx 用 Keepalived 共享虚拟 IP（VIP），主挂备自动接管。

现代替代：K8s Ingress、云 LB（ALB/SLB）；但 Nginx 仍是自建与边缘网关主力。

2. 最小反向代理

头 作用
Host 透传原域名，后端按域名路由/生成绝对链接
X-Real-IP 客户端真实 IP（单层代理）
X-Forwarded-For 代理链 IP 列表，$proxy_add_x_forwarded_for 自动追加
X-Forwarded-Proto 客户端是 http 还是 https（后端生成 https 链接必需）

3. proxy_pass 路径规则（高频坑）

记忆法：proxy_pass 的 URL 部分会替换掉 location 匹配的部分；不带路径（只有 host:port）则原样透传。改一条 proxy_pass 必跑 nginx -t + 抓包/日志确认后端实际收到的路径。

4. upstream 与负载均衡策略

策略对比（完整版）：

策略 写法 分发逻辑 适用
轮询（默认） 无参数 按顺序逐个分发 无状态服务
加权轮询 weight=n 按权重比例分发 机器配置不均
ip_hash ip_hash; 按客户端 IP 哈希固定实例 会话粘性（老系统）
least_conn least_conn; 打当前活跃连接最少者 请求耗时不均
一致性哈希 hash $request_uri consistent; 按任意键哈希，扩缩容漂移少 缓存亲和
随机 random two least_conn; 随机抽两台取连接少者 超大 upstream
least_time least_time header;（Plus） 打平均响应最快者 商业版，性能敏感

注意：加/减后端节点会改变 hash 分布——优先用 Redis 会话共享实现无状态，而不是依赖 ip_hash。

5. 健康检查与故障摘除

5.1 被动检查（开源版自带）

参数 含义
max_fails fail_timeout 窗口内失败次数达阈值即摘除
fail_timeout 既是统计窗口，也是被摘除后的「冷却时间」
slow_start 恢复节点缓慢放量，避免冷缓存被瞬间打满
proxy_next_upstream 定义哪些失败场景换机重试

非幂等请求慎用重试：POST 下单/扣款请求可能已到达第一台，换机重试会造成重复下单——重试只开给幂等接口。

5.2 主动检查与注册中心

方案 说明
商业版 health_check health_check interval=5s uri=/health; 定期主动探测
nginx_upstream_check_module 淘宝开源补丁（Tengine 内置），主动心跳检查
注册中心联动 Consul/Nacos 上下线时通过 API 动态改 upstream

5.3 优雅下线（drain）

发布前先把节点「排空」：开源版把该 server 手动标记 down（存量 keepalive 连接服务完再断）；Plus 用 drain 参数只处理存量会话、不接新请求。排空后再重启，实现零请求丢失发布。

7. 限流与并发控制

关键取舍：

  1. burst 不带 nodelay：超出速率的请求排队匀速放行——削峰填谷，代价是延迟上升；
  2. burst nodelay：积压请求立即放行，超 burst 才拒绝——适合宁可后端扛、也不让用户等；
  3. 超限默认返回 503，用 limit_req_status 429; 改成更语义化的 429；
  4. 10MB 共享内存约存 16 万个 IP 状态，高并发场景需按 IP 数量调大；
  5. $binary_remote_addr vs $remote_addr：用二进制（4 字节）比字符串（7-15 字节）省内存。

8. 会话保持方案

方案 实现 代价
ip_hash 一行指令 NAT 出口下大量用户同 IP，负载倾斜
hash $cookie_xxx consistent 按业务键一致性哈希 需先种 cookie；扩缩容时漂移少
应用外置会话（Redis） 后端共享 session 最推荐：Nginx 无感知，后端任意扩缩容
sticky 指令 Nginx Plus 商业版，cookie 路由

12. 常见问题

问题 原因与解决
502 Bad Gateway 后端没起/端口错 → 检查 upstream 与后端健康
504 Gateway Timeout 后端处理超时 → 调 proxy_read_timeout
后端收到 IP 全一样 没配 X-Real-IP → 补 proxy_set_header
请求分布不均 长连接/耗时差异 → least_conn
节点挂了还转发 max_fails 调小 + 健康检查
会话丢失 依赖 ip_hash 后节点变更 → Redis 会话
路径 404 proxy_pass 斜杠语义 → 确认替换/透传

13. 常见误用与陷阱

坑 现象/后果 解法
proxy_pass 末尾斜杠语义不清 路径被错误替换，后端 404 无斜杠保留 URI，有斜杠替换前缀
if 判断陷阱 if 内逻辑行为不可预期 用 try_files/return 替代，避免复杂 if
worker_connections 误解 认为是全局连接数 全局 = worker_processes × worker_connections
缓冲区大小不合理 大响应缓冲到磁盘，性能下降 调大 proxy_buffer_size/proxy_buffers
超时未分级 慢接口拖累整体 按接口设 proxy_connect/read/send_timeout
限流区内存太小 高并发时限流失效 按 IP 数量调大 zone 内存（10m≈16 万 IP）
非幂等请求开重试 重复下单/扣款 重试只开给幂等接口
